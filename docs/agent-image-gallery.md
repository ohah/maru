# 에이전트 이미지 갤러리 (Claude·Codex)

우측 도크의 `image_gallery` 뷰가 보이는 **에이전트와 주고받은 이미지**의 단일 출처다. 사용자가 붙여넣은 이미지와 에이전트가 읽은 이미지를 한자리에 모아 보고, 크게 보고, 그 세션으로 이동한다.

이 문서의 모든 수치는 **2026-08-29에 이 저장소 개발 머신(Apple M4 Max, macOS 26.5.1)에서 직접 측정**한 값이다. 측정 방법은 §9에 적는다. 추정치는 쓰지 않는다.

## 1. 목표와 경계

목표는 "아까 그 스크린샷 어디 갔지"를 **스크롤백을 되짚지 않고** 푸는 것이다. v1 provider는 [에이전트 세션 기록 도크](agent-session-list.md)와 같은 **Codex와 Claude Code만**이고, 같은 로컬 JSONL을 읽는다. provider API·계정·네트워크를 쓰지 않는다.

**소스는 트랜스크립트 파일이며, 화면이 아니다.** 이 결정이 이 문서의 나머지를 지배한다 — 근거는 §3.1.

| 구분 | 권위 | 이 문서와의 관계 |
| --- | --- | --- |
| 터미널 화면·스크롤백 | 그 순간의 렌더 결과 | **권위 아님** — alt 화면은 스크롤백 용량이 0이다(§3.1) |
| kitty graphics 이미지 | PTY로 흘러온 픽셀 | 별개 기능. 갤러리는 여기 관여하지 않는다 |
| provider JSONL | provider가 쓴 대화 기록 | **유일한 소스** |

**비목표**(사용자 결정 2026-08-29): 이미지·썸네일·인덱스의 **디스크 보존**, **활성 pane 밖의 범위**(전체·프로젝트·워크스페이스 필터, §2.1), 서브에이전트 기록(§8 M4), 영상(§3.4), 원격/SSH 이력, 다른 provider, 원문 대화 뷰어.

## 2. 화면과 상호작용

```text
이미지                                        12장   [새로 고침]
────────────────────────────────────────────────────────
  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐
  │      │ │      │ │      │ │      │      ← 썸네일 격자(가상 스크롤)
  └──────┘ └──────┘ └──────┘ └──────┘
   3분 전   1시간 전  어제      어제
```

**범위 선택 UI가 없다.** 갤러리는 항상 **활성 pane**의 것을 보여준다(§2.1). 포커스가 다른 pane으로 가면 내용이 따라 바뀐다.

- **클릭** = 크게 보기(같은 도크 안에서 전체 폭, 팬·줌). 닫기는 **Esc** 또는 **이미지 밖 클릭**이다.
  - Esc 는 **도크를 누른 적이 있을 때만** 가져간다(에이전트 도크와 같은 키 소유권 게이트). 그러지 않으면
    이미지를 열어 둔 채 터미널로 돌아간 사용자의 vim Esc 가 사라진다.
  - 여는 동안(원본 디코드 ~20 ms)에는 **격자를 그대로 둔다.** 클릭 직후 화면이 비면 「눌렀더니
    사라졌다」로 보인다. 못 풀면 닫지 않고 「이 이미지를 열 수 없습니다」로 말한다.
  - 처음 배율은 **전체가 들어가는 크기이되 1 을 넘지 않는다.** 작은 이미지를 흐리게 늘려 놓으면
    원본을 확인하러 온 사람에게 거짓말이 된다. 확대는 사용자가 한다(최대 8배).
  - 확대해 그림이 도크보다 커지면 **UV 로 잘라 낸다** — 이미지 quad 에는 scissor 가 없어, 안 자르면
    터미널 위로 넘쳐 흐른다.
  - **←→ 로 다음·이전 이미지.** 썸네일이 160 px 라 내용을 못 읽으니 결국 하나씩 열어 보게 되는데,
    넘기기가 없으면 열고 닫기를 반복해야 한다. **끝에서는 멈춘다**(순환하지 않는다) — 순환하면 끝에
    닿았다는 것을 알 수 없어 같은 것을 두 번 본다. 넘기면 **격자도 그 칸으로 따라간다**(안 그러면
    닫는 순간 옛 자리를 보여준다). ↑↓ 도 같다.
  - 화살표는 **크게 보기 중일 때만** 가져간다(Esc 와 같은 키 소유권 게이트 위에 «열려 있는가» 를 더한다).
    격자만 보고 있을 때 삼키면 터미널의 히스토리 탐색이 사라진다.
  - **휠 = 확대·축소**(포인터를 붙잡고), **드래그 = 밀기**. 격자에서는 휠을 흘려보낸다(스크롤이 아직 없다).
    크게 보기에서 휠을 팬으로 두지 않은 이유는, 처음 배율이 fit 이라 밀 것이 없어 **아무 일도 안 하는
    것처럼 보이기** 때문이다. 트랙패드는 점 단위로 훨씬 촘촘히 오므로 계수를 나눈다.
- **세션으로 가기** = 그 세션이 열린 pane을 활성화(`activateSurfaceById`, ABI v78 — 알림 클릭 점프와 같은 지점).
- 이미지가 없으면 격자 대신 안내 한 줄. 도크 슬롯은 늘 존재한다.
- **격자에 다 안 들어가면 「12장 중 8장」으로 말한다.** 스크롤이 아직 없어 첫 화면만 보이는데, 그 사실을
  안 알리면 사용자가 이미지를 놓치고도 모른다 — 「없다」와 「안 보인다」를 가르는 같은 규율이다.
  문구는 **한 개의 i18n 템플릿**(`{0}`/`{1}`)이다. 영어 "8 of 12 images" 와 한국어 "12장 중 8장" 은
  **어순이 반대**라, 조각을 이어 붙이면 한쪽이 반드시 틀린다.

표시 문자열은 예외 없이 [i18n](i18n.md)의 키를 거친다.

### 2.1 범위는 활성 pane이다 — 세션 하나가 아니라 pane의 세션 목록

사용자 결정(2026-08-29)이다. 전체·프로젝트·워크스페이스 필터를 두지 않는다.

다만 **"현재 세션 하나"로 잡으면 안 된다.** `/clear`가 새 세션 파일을 만들기 때문이다(실측: 직전 세션 종료 46 ms 뒤 새 파일). 그렇게 잡으면 `/clear` 할 때마다 갤러리가 통째로 빈다 — 자주 하는 동작이라 치명적이다.

그래서 범위는 **활성 pane에서 이번 실행 중 관측된 세션 전부**다. 훅이 `SessionStart`마다 `transcript_path`를 주므로(§4.4) pane별로 그 목록을 이어 붙이기만 하면 된다. 비용은 pane당 경로 문자열 몇 개다.

| 상황 | 갤러리에 남나 |
| --- | --- |
| `/clear` 후 | **남는다** — 이전 세션이 목록에 그대로 있다 |
| 재개(`--resume` / `codex exec resume`) | 남는다 — **양쪽 provider 모두 같은 파일에 이어붙는다**(각각 격리 재현 확인) |
| 다른 pane으로 포커스 이동 | 그 pane의 목록으로 바뀐다 |
| 앱 재시작 | 현재 세션부터 다시 쌓인다(메모리 전용, §4.5) |
| 에이전트 없는 pane(셸만) | 빈 화면 + 안내 한 줄 |
| **원격 pane**(ssh 너머) | 빈 화면 + **다른** 안내 — 「원격이라 못 읽는다」(§4.1.2) |

Codex도 새 세션은 **새 rollout 파일**이다(같은 cwd에서 3~8초 만에 이어 시작한 쌍 6건 관측). 다만 그것이 in-process `/new`인지 재실행인지는 이 기록으로 구분되지 않는다 — **설계는 어느 쪽이든 같다.** 새 `transcript_path`가 오면 목록에 더할 뿐이다.

이 결정이 §4.1의 스캔 정책을 통째로 바꾼다.

### 2.2 이미지 문맥 — 이 화면이 스크롤을 대체한다

인덱스가 이미지의 **줄 오프셋**을 들고 있으므로, 그 근처 몇 줄만 읽어 "이 이미지가 무엇이었는지"를 복원한다. 실측 **0.12~0.18 ms**(±6줄 창). 두 종류로 갈린다.

| provider | 이미지 출처 | 보여 줄 것 | 실측 예 |
| --- | --- | --- | --- |
| Claude | 사용자가 붙여넣음 | **같은 메시지의 텍스트** | `[Image #1] 에디터에서 닫기 아이콘 실제 동작도 안되고 숫자랑…` |
| Claude | 에이전트가 읽음 | **직전 `tool_use`** | `Read(/private/tmp/claude-501/…)` |
| Codex | 사용자가 붙여넣음 | **같은 메시지의 `input_text` 블록들** | `<image name=[Image #1] path="…/pasted-54737-2.png">` + `[Image #1] 셀렉터 테마 색상으로 인해 원본 글자색이 잘 안보이네요` |

**두 provider의 모양이 다르다.** Claude는 텍스트와 이미지가 한 메시지의 형제 블록이고, Codex는 `<image name=… path=…>` … `</image>` 래퍼 뒤에 질문 텍스트가 붙는 `input_text` 여러 개다. 파서는 이 둘을 각각 다뤄야 한다.

양쪽 모두 **원본 경로를 기록한다**(Claude `[Image: source: …/pasted-20726-1.png]`, Codex 래퍼의 `path=`). 그 파일은 대개 이미 지워졌지만(§6), 이름은 남아 있어 표시할 수 있다.

**이 절이 "스크롤백을 그 지점으로 보내기"를 비목표로 만드는 근거다.** 불가능해서가 아니다 — §3.1에 적었듯 구현 자체는 가능하다. 대체 수단이 0.2 ms이고 부작용이 없기 때문이다.

## 3. provider 입력

### 3.1 왜 파일이고 화면이 아닌가

Claude Code는 fullscreen TUI에서 `[?1049h`(대체 화면)·`[?1000h`·`[?1006h`·`[?1007h`를 켠다(바이너리 실측). 그리고 maru의 대체 화면은 **스크롤백 용량이 0**이다.

> `screen.zig` — alt 진입 시 primary grid·scrollback·커서를 saved_* 슬롯으로 스왑하고 빈 alt 버퍼를 쓴다(alt는 cap=0 스크롤백 → history 안 쌓임).

즉 화면에서 긁는 설계였다면 **fullscreen 사용자에게는 아무것도 보이지 않는다.** 게다가 첨부 이미지는 화면에 픽셀로 존재한 적이 없다 — TUI는 `[Image #1]` 같은 **글자**로 그린다.

### 3.1.1 "그 지점으로 스크롤"은 불가능하지 않다 — 하지 않는 것이다

정확히 나누면 셋이다.

| 경로 | 판정 |
| --- | --- |
| maru **자체 스크롤백**으로 올리기 | **불가능** — alt는 `cap=0`이라 history가 없다 |
| **앱에 화살표를 보내** 앱이 자기 화면을 올리게 | **가능** — `scroll.zig`이 이미 휠→화살표(DECSET 1007) 변환을 한다 |
| 목표 지점에서 **멈추기**(닫힌 루프) | **가능** — alt에서도 화면 검색이 된다 |

마지막 줄의 근거는 `selection.zig`이다 — *"스크롤백 포함 `[0,total)` 전체를 검색한다. **alt에선 `sb.count==0`이라 자연히 현재 화면뿐**"*. 즉 "한 배치 올리고 → 지금 화면에 마커가 있나 검색 → 반복"이 성립한다.

그럼에도 v1 비목표인 이유는 **부작용과 대체재**다. 화살표는 사용자가 휠을 굴릴 때와 **같은 바이트**라 앱이 구분할 수 없어, 입력창에 글자가 있으면 프롬프트 히스토리 탐색으로 샌다. 되돌리기도 보장되지 않는다(앱이 끝에서 clamp하면 올린 횟수 ≠ 내린 횟수). 그리고 §2.2가 같은 정보를 **0.2 ms에 부작용 없이** 준다.

### 3.2 레코드 모양

| provider | 이미지 레코드 | 비고 |
| --- | --- | --- |
| Claude | `{"type":"image","source":{"type":"base64","media_type":…,"data":"…"}}` | user 메시지와 `tool_result` 양쪽 |
| Claude | `toolUseResult.file.base64` | **같은 이미지의 2중 저장**(§4.3) |
| Codex | `{"type":"input_image","image_url":"data:image/png;base64,…"}` | 앞선 `input_text`에 원본 경로가 함께 남는다 |
| Codex | `payload.output[]` 안의 같은 `input_image` | **에이전트가 읽은 것**(`view_image` 결과). 마커가 같아 스캐너는 그대로 잡는다 |

**Codex 도 «읽은» 이미지를 남긴다**(2026-08-30 실측). `view_image` 도구의 결과가 `function_call_output`
레코드의 `payload.output[]` 에 `"type":"input_image"` 로 들어간다 — 사용자 붙여넣기와 **같은 마커**라
스캐너는 이미 잡고 있었다. 다만 그 정체(경로)는 이렇게 다르다:

| | Claude | Codex |
| --- | --- | --- |
| 상관 키 | `tool_use_id` → `"id"` | `call_id` → `"call_id"` |
| 경로 키 | `input.file_path` | `path` |
| 호출이 몇 줄 뒤 | **언제나 1줄**(1,074/1,074) | **1~2줄**(2줄이 12/16) |

그래서 문맥 파서는 창을 «앞선 줄들» 로 보고 **id 가 든 줄 안에서만** 경로를 뽑는다(§2.2). 창을 통째로
훑으면 id 는 A 레코드에서, 경로는 B 레코드에서 나온다 — 그것이 이 기능이 처음부터 막으려던 「틀린 라벨」이다.

`payload.images`·`payload.local_images` 는 **보지 않는다**: 실측 2,322건이 전부 빈 배열이고, 비어 있지
않은 4건도 base64 가 아니라 경로다(그 파일은 대개 이미 지워진다, §6).

**⚠️ 스캐너는 provider 가 JSON 을 «공백 없이» 쓴다고 가정한다.** 마커가 `{"type":"image"` 이므로
`{"type": "image"`(콜론 뒤 공백)는 **하나도 안 걸린다**. 실측상 Claude·Codex 모두 compact 로 쓰므로
지금은 성립하지만, **어긋나면 「이미지가 없습니다」로 조용히 실패한다** — 사용자에게는 고장과 구분되지
않는다. 실제로 이 함정에 걸려 본 적이 있다: 헤드리스 캡처용 픽스처를 `json.dumps` 기본값(콜론 뒤 공백)
으로 만들었더니 첫 캡처가 빈 화면으로 나왔다(2026-08-29).

가정을 지금 없애지 않는 이유는 **비용이 근거 없이 늘기 때문**이다 — 공백을 허용하려면 마커가 아니라
토크나이저가 되고, 그것은 1.68 GB 파일을 줄마다 파싱하지 않으려고 마커를 고른 결정을 되돌린다(§4.1.1).
대신 **가정을 여기 적어 두고**, provider 출력이 바뀌면 이 줄이 조사 시작점이 되게 한다.

**바이트 마커로 찾아도 안전하다.** JSON은 문자열 안의 따옴표를 이스케이프하므로, 본문이 `"type":"image"`를 언급해도 파일에는 `\"type\":\"image\"`로 들어간다. 이스케이프되지 않은 형태는 **구조로만** 존재한다. 실측 오탐 0(엄격 패턴 364 = `grep` 364). 따라서 후보를 찾는 데 JSON 파서가 필요 없고, 찾은 줄만 파싱한다.

### 3.3 Codex `compacted` 는 제외한다

Codex는 압축 요약을 **append**하는데, 그 레코드가 **이전 대화를 이미지째 다시 싣는다**. 실측: 한 레코드 7,194,746바이트, 한 파일에 `compacted` 376개. 그래서 순진하게 세면 Codex 이미지가 15,140개로 나오지만 실제 사용자가 보낸 것은 **151개**다.

`type == "compacted"` 레코드는 이미지 인덱싱에서 **제외**한다.

**⚠️ 「잃는 것이 없다」는 fork/재개 세션에서 깨진다(2026-08-30 실측).** 초안은 «원본이 같은 파일 앞쪽에
이미 있다» 고 적었는데, 실제 코퍼스로 재 보니 그렇지 않았다:

| 잰 것 | 값 |
| --- | --- |
| `compacted` 안 고유 이미지 | 159 |
| 살아 있는 이미지 | 140 |
| **원본이 이 파일에 없는 것** | **42** |
| 그런 파일 | **20 / 90 (22%)** |
| 최악 | 살아 있는 것 **0장**인데 `compacted` 안에 4장 — 갤러리는 「이미지가 없습니다」라고 말한다 |

원인은 fork/재개다. 그 파일들의 `session_meta` 에는 `forked_from_id`·`parent_thread_id` 가 있고, 부모
세션의 이미지가 이 파일에는 **압축 사본으로만** 남는다(원본은 부모 rollout 에 있다).

**대응은 부모 rollout 까지 스캔하는 것이다**(사용자 결정 2026-08-30). 사용자에게 재개된 세션은 **같은
대화**이고, 「아까 그 스크린샷」이 거기 있기 때문이다. `compacted` 안을 인덱싱하는 대신 원본을 원본
자리에서 보므로 중복도 없다. 비용 실측:

| 잰 것 | 값 |
| --- | --- |
| fork/재개 세션 | **172 / 296 (58%)** — 예외가 아니라 일상 |
| 부모 id 가 파일명에 있나 | 172/172 (**100%**) — 찾기 쉽다 |
| 체인 깊이 | 중앙 1, **최대 2** — 상한을 낮게 둘 수 있다 |
| 부모 파일 크기 | 중앙 **338 MB**, 최대 **1.8 GB** |
| 그 스캔 시간(467 MB/s) | 중앙 **0.72 초**, 최악 **3.9 초** |

워커에서 도므로 화면은 안 멈추지만 갤러리가 늦게 찬다. 그래서 **현재 파일을 먼저 끝내고 부모를 이어
훑는다** — 최신 우선이라 부모 이미지는 뒤쪽에 붙는 것이 자연스럽다.

### 3.4 영상은 존재하지 않는다

트랜스크립트에 영상 바이트는 들어가지 않는다(모델이 영상을 읽지 않는다). 영상은 대화 중 **경로**로만 나타난다. 따라서 "에이전트가 읽은 영상"은 성립하지 않는 범주이며 v1 비목표다.

## 4. 스캔·인덱스·수명

### 4.1 활성 pane의 세션 파일만 읽는다

§2.1의 결정에 따라 스캔 대상은 **디렉터리 순회가 아니라 파일 목록**이다 — 훅이 그 pane에 대해 알려 준 `transcript_path`들. 보통 1~3개다.

그래서 **디렉터리 열거가 없다.** 후보 수집·정렬·필터가 통째로 사라지고, 첫 진입 비용이 "그 파일 하나를 훑는 값"으로 떨어진다.

| 대상 | 마커 스캔 |
| --- | --- |
| 전형 파일(Claude 중앙값 1.3 MB / Codex 2.7 MB) | **3 ms** 미만 |
| 최악(1,680 MB Codex rollout) | **3.6 초** — 제품 스캐너 실측(467 MB/s) |

### 4.1.2 원격 pane은 읽지 않는다 — 그리고 그렇게 **말한다**

§1의 비목표 「원격/SSH 이력」은 «원격에서는 갤러리가 안 뜬다»는 뜻이었지만, 코드는 그렇게 하고 있지 않았다.
원격 훅(RA5 채널)이 보내 온 `transcript_path`는 **저쪽 기계**의 절대 경로인데, 스캐너와 디코더는
`Dir.cwd().openFile`로 **로컬**을 연다. 그래서 두 갈래가 생긴다.

| 로컬에 그 경로가 | 결과 |
| --- | --- |
| 없다 | 빈 갤러리 — 「에이전트 세션이 없습니다」로 보인다 |
| **있다** | **그 로컬 파일이 실제로 열려**, 다른 대화의 이미지가 이 원격 세션 이름표 밑에 뜬다 |

두 번째는 드문 일이 아니다. 양쪽이 macOS이고 사용자 이름이 같으면 `~/.claude/projects/…` 는 **양쪽에 같은
모양으로 있다**. `Source.set`이 이미 지키던 「추측한 경로로 남의 파일을 읽지 않는다」와 같은 규율을 원격
축으로 넓힌 것이 이 절이다.

**판정은 읽는 쪽 한 곳**(`activeSourcePath`)에 둔다. 채택하는 쪽(`adoptHookImageSource`)에도 두면 같은
판정이 두 곳에서 갈린다(`refresh` 주석이 같은 이유로 신선도 판정을 한 곳에 모아 둔다). 한 곳이라서
**ssh에 들어가기 전 담아 둔 로컬 소스가 남아 있는 경우**까지 함께 막힌다 — 그것도 원격 pane 이름표
밑의 남의 이미지다.

원격의 증거는 **RA5 채널이 열렸다는 사실**이다(SSH 통합 §11.1: ssh 너머는 `agent_kind`가 영영 `none`이고
로컬 로그 파일도 없어 그 둘로는 판정할 수 없다). ssh를 빠져나오면 채널을 떼어 내므로 이 값은 **래치가
아니다** — 돌아오면 갤러리도 돌아온다.

그리고 문구를 가른다. 원격 pane에는 에이전트가 **있다**(사이드바 배지가 그 증거다). 거기에
「에이전트 세션이 없습니다」라고 하면 사용자는 훅이 깨진 줄 알고 설치부터 다시 훑는다 — 실제로 그 길을
걸어 본 뒤에 나눈 것이다. §2의 안내는 이제 **넷이 아니라 다섯**을 가른다.

### 4.1.1 그래서 스캔은 **반드시 워커에서** 돈다 ⚠️

초안은 최악을 «약 0.7 초»로 적었다. 그것은 Python 의 SIMD `count()` 로 잰 값이었고, **제품 코드로 다시 재니 3.6 초였다**(1,680.3 MB / 3,599.9 ms / 467 MB/s, 2026-08-29). 60 Hz 기준 **216 프레임 정지**다.

차이의 원인은 훑는 횟수다. I/O 는 4,126 MB/s 이므로 1.68 GB 면 0.4 초이고, 나머지 3.2 초가 CPU 다 — 스캐너가 줄마다 **네 번** 훑는다(Claude image · `toolUseResult` · Codex `input_image` · `compacted` 판정).

그래서 **동기 스캔은 성립하지 않는다.** 파일 하나를 훑는 일이 프레임 예산(16.7 ms)의 200배를 넘으므로, 이것은 «전형 파일에서는 괜찮다» 로 넘길 문제가 아니다 — 이 기계의 **활성 세션이 실제로 1.68 GB** 였다(§9).

점진 publish 도 그래서 유지한다: 워커가 찾는 대로 넘기고, 다 읽을 때까지 기다리지 않는다. 콜드 읽기가 웜과 같으므로(**4,126 MB/s**, NVMe) 캐시 상태는 결과를 바꾸지 않는다.

[아카이브 도크](agent-session-list.md) §4의 24초·전체 코퍼스 12.28 GB는 **이 기능의 예산이 아니다.** 그쪽은 줄마다 JSON을 파싱해 제목·요약·redaction까지 만들고 이력 전체를 대상으로 한다. 두 스캐너는 목적도 대상도 달라 공유하지 않는다. (범위를 넓히는 후속이 온다면 그때의 전체 스캔 비용은 §9에 실측해 두었다.)

### 4.2 이어읽기 — `last_offset` 은 마지막 개행까지만 전진한다

인덱스는 파일마다 `(device, inode, size, mtime, last_offset)`을 들고, `stat` 하나로 셋 중 하나로 갈린다.

| 상태 | 하는 일 |
| --- | --- |
| size 동일 | 아무것도 읽지 않는다 |
| inode 같고 size 증가 | `last_offset`부터 **델타만** positional read |
| inode 변경 또는 size 감소 | 파일 교체 — 인덱스를 버리고 0부터 |

> ⚠️ **구현은 여기까지 안 왔다(2026-08-31).** 지금 코드는 `(inode, size, mtime)` 자국으로 «달라졌나» 만
> 보고, 달라졌으면 **전량 다시 훑는다** — `last_offset` 델타 읽기는 없다. 아래 「3,133배」는 그 근거로
> 적힌 값인데, 재측정이 전제를 바꿨다:
>
> | | 크기 | 스캔 |
> | --- | --- | --- |
> | 중앙 | 2.5 MB | **11 ms** |
> | p99 | 258.6 MB | 1,175 ms |
> | 최대 | 1,981 MB | 9,007 ms |
>
> **98.4% 가 1 초 안**이라 전량 재스캔으로 충분하고, 오프셋 영속·부분 줄 경계·교체 감지를 들일 근거가
> 지금은 없다. 대신 큰 세션에서 워커가 쉬지 않는 문제는 **쉬는 시간**(직전 스캔의 10 배, 상한 120 초)
> 으로 막는다. 델타 읽기가 필요해지는 조건은 「1 초를 넘는 세션이 흔해질 때」다.
>
> 아래 표는 **그때 따를 설계**로 남긴다.

**위 세 갈래의 근거.** 실측 최대 파일이 **1,626 MB**(Codex rollout)이고 측정 시점에도 쓰이고 있었다. 그 파일에서 전체 읽기 75.8 ms 대 델타 1 MiB pread 0.024 ms로 **3,133배**, `stat`만은 **54,296배** 저렴하다. 4,156개 전부 `stat`해도 34.3 ms다.

append-only 전제는 추론이 아니라 **양쪽 provider 각각의 격리 재현으로 확인했다**(§9) — Claude `--resume`과 Codex `codex exec resume` 모두 **같은 `transcript_path`에 새 턴을 붙였다**(session_id도 동일). compaction도 재작성이 아니라 append다. 설령 어느 provider가 새 파일을 만들더라도 inode가 달라 0부터 다시 읽으므로 계약은 깨지지 않는다.

**Codex는 fork를 한다**(`codex exec fork`가 정식 서브커맨드다). 파일 앞머리에 `session_meta`가 둘이면 첫 번째가 새 스레드(`forked_from_id`·`parent_thread_id` 보유), 두 번째가 부모의 복사본이다 — **재개 표시가 아니다.** 근거 둘: 전수 294개에서 `session_meta`가 줄 5보다 뒤에 나온 경우 **0건**이고, 격리 재개 실측에서 재개 후에도 `session_meta`가 **줄 1 하나뿐**이었다. 갤러리는 훅이 준 **현재 스레드 경로만** 보므로 부모 파일을 따라가지 않는다.

`last_offset`은 **마지막 개행 위치까지만** 전진시킨다. 델타 끝이 줄 중간이면 그 조각을 버리고 다음 회차에 온전한 줄로 다시 읽는다. 반쪽 JSON을 파싱하지 않는다는 뜻이고, base64는 한 줄 안에 통째로 있으므로 이미지가 경계에서 잘리지 않는다. 한 줄 상한은 아카이브 스캐너와 같은 **16 MiB**를 쓴다(Codex `compacted`가 7.2 MB까지 간다).

### 4.3 중복 제거는 선택이 아니다

실측 중복률 **65%**다. 원인이 셋이다.

1. Claude가 도구가 읽은 이미지를 `tool_result`와 `toolUseResult.file.base64`로 **두 번** 적는다.
2. Codex `compacted`가 이전 이미지를 통째로 재수록한다(§3.3에서 제외해 해소).
3. 같은 이미지를 서로 다른 세션에서 다시 쓴다(실측: 같은 PNG가 두 세션 파일에).

**해시는 쓰지 않는다(2026-08-29 실측으로 정정).** 초안은 base64 구간의 내용 해시를 계획했는데, 원인 1을
실제 코퍼스(2,548 파일)로 재 보니 해시가 필요 없었다.

| 잰 것 | 값 | 뜻 |
| --- | --- | --- |
| `toolUseResult.file.base64` 가 있는 줄 | 1,425 | |
| 그중 같은 줄에 `content[].source.data` 도 있는 줄 | 1,425 | **언제나 짝이다** |
| `tool_file` 만 있는 줄 | **0** | 접어도 잃는 것이 없다 |
| 개수 불일치 줄 | **0** | 언제나 1:1 |
| payload 가 다른 줄 | **0** | base64 바이트가 글자 그대로 같다 |

그래서 접는 기준은 **「같은 줄에 `claude_image` 가 있는가」** 하나다 — 오프셋 구간을 다시 읽지도, 해시하지도
않는다. 조건절(「같은 줄에 있으면」)은 남긴다: provider 가 언젠가 `toolUseResult` 만 쓰는 레코드를 내보내면
그것은 사본이 아니라 **유일본**이고, 무조건 버리면 그 이미지가 통째로 사라진다(증상은 「어떤 이미지는 안
보인다」라 원인을 못 찾는다).

전체 3,226 장 중 **1,424 장(44%)**이 이 사본이었다 — 접기 전에는 에이전트가 읽은 이미지가 갤러리에 전부
두 번 떴다.

원인 3(다른 세션의 같은 이미지)은 **범위가 활성 pane 하나로 좁아져 사라졌다**(§2.1).

### 4.4 라이브 갱신과 폴백

`sidebar.agent-hooks`(기본 `true`)가 켜져 있으면 훅이 **push**로 알려 준다 — `SessionStart`·`UserPromptSubmit` payload에 `session_id`와 **`transcript_path`**가 실린다(실 페이로드 포착, §9). `/resume`은 `source:"resume"`으로 다시 발화하고 `transcript_path`가 같다. `/clear`는 **새 파일**을 만든다(직전 세션 종료 46 ms 뒤 새 세션 시작).

**범위가 활성 pane이므로 훅은 이제 부수적 편의가 아니라 주 경로다**(§2.1) — pane과 세션 파일을 잇는 것이 훅이기 때문이다. 훅이 꺼지면 이렇게 메운다.

| 잃는 것 | 폴백 |
| --- | --- |
| **pane ↔ 세션 파일 매핑**(주 경로) | `agentSessionIdentity`(`pty/macos.zig`) — 자식 프로세스의 `KERN_PROCARGS2` envp에서 `CLAUDE_CODE_SESSION_ID`/`CODEX_THREAD_ID` |
| 방금 붙여넣은 이미지가 즉시 뜨는 것 | 그 파일 하나의 **mtime 폴링**. 디렉터리 순회가 없으므로 `stat` 한 번이다 |

env 폴백의 한계를 명시한다: 에이전트가 자식을 한 번도 띄우지 않았으면 신원이 없고, `KERN_PROCARGS2`는 exec 시점에 고정이라 **오래 살아 있는 자식이 옛 id를 들고 있을 수 있다**(`/clear` 직후 stale). `--resume`은 session_id가 유지되므로 이 경로에서도 문제가 없다.

### 4.5 수명

인덱스와 디코드 픽셀은 **메모리 전용**이다(사용자 결정). 앱을 끄면 사라지고 다음 실행에서 다시 훑는다. 그 비용은 §4.1대로 파일 하나 몫이다. **pane별 세션 목록도 함께 사라지므로**, 재시작 후에는 그 pane의 현재 세션부터 다시 쌓인다(§2.1).

**스캔 시점과 읽기 시점 사이에 파일이 사라질 수 있다** — Claude 트랜스크립트는 47일에서 정리되고(실측: 42~48일 구간에 1,162개, 그보다 오래된 것 0개), 사용자가 직접 지울 수도 있다. 그래서 디코드 직전에 `(device, inode)`를 다시 확인하고, 어긋나면 그 항목을 목록에서 조용히 뺀다. Codex는 정리하지 않는다(124일까지 확인).

## 5. 디코드와 렌더

### 5.1 ImageIO로 디코드한다

`terminal/png.zig`는 kitty graphics용 **이식 가능 코어**이고 8-bit truecolor PNG만 받는다. 뷰어는 `platform/macos`에 살므로 그 제약이 없다. macOS **ImageIO가 62종**을 디코드한다(실측: png·jpeg·webp·heic·heif·avif·gif·tiff·bmp·ico·jpeg-xl 등). WebKit도 같은 ImageIO를 쓰므로 **네이티브가 웹뷰보다 커버리지가 좁지 않다.**

실제 코퍼스는 PNG 98.2% / JPEG 1.9%이고 JPEG 74장 중 EXIF는 **0장**이라 방향 회전 처리가 필요 없다.

### 5.2 축소는 시간이 아니라 메모리를 줄인다

2830×1662 PNG 기준 실측이다(매 반복 `CGImageSource`를 새로 만들어 캐시 오염을 제거한 값).

| 경로 | 시간 | 텍스처 |
| --- | --- | --- |
| 전체 디코드 | 19.78 ms | 17.94 MB |
| 서브샘플 1/8 | 19.59 ms | 0.28 MB |
| 썸네일 160 px | 19.72 ms | 0.06 MB |

PNG 압축 해제 자체가 비용이고 목표 크기와 무관하다. 그래서 **축소의 목적은 속도가 아니라 텍스처 메모리**다(300배).

여기서 세 가지가 강제된다.

1. **가상화**: 이미지가 1,546장(직속 기준)이고 장당 20 ms면 전부 디코드에 30초다. 보이는 타일만 디코드하고 LRU로 버린다. 한 파일에 이미지가 770개까지 몰린 경우가 있다.
2. **워커 디코드**: 20 ms는 60 Hz 프레임 예산 16.7 ms를 넘는다. 렌더 tick에서 디코드하지 않는다. 도착 전에는 자리표시자를 그린다.
3. **썸네일 160 px**: 장당 0.06 MB라 200장 상주해도 12 MB다. 원본 해상도로 들면 200장에 3.6 GB로 불가능하다.

### 5.3 텍스처 한 변을 반드시 clamp한다 ⚠️

**Metal은 한계를 넘는 텍스처 디스크립터에 `nil`을 돌려주지 않고 프로세스를 abort한다**(`_MTLMessageContextEndNewNSErrorOrAbort` → validation abort). 이 머신의 한 변 상한은 16,384이고, 실측 최대 이미지가 **1440×14771**이라 여유가 1,613 px뿐이다. 긴 페이지 전체 스크린샷 하나면 넘는다.

그러므로 **텍스처 생성 전에 반드시 clamp**한다(서브샘플로 목표 크기 이하로 줄인 뒤 업로드). 격자는 160 px라 안전하고, **위험 지점은 "크게 보기"에서 원본을 올릴 때**다. 이 검사는 방어가 아니라 정확성 요구다.

### 5.4 렌더는 기존 이미지 채널을 그대로 쓴다

`MaruAppHostGpuImage`는 셀 좌표가 아니라 **픽셀 사각형 + 소스 UV 크롭**이다.

```c
typedef struct MaruAppHostGpuImage {
    uint32_t image_id;
    float dest_x, dest_y, dest_w, dest_h;   /* 픽셀 사각형 */
    float src_u0, src_v0, src_u1, src_v1;   /* 소스 UV 크롭 */
    int32_t z; uint32_t pass;
} MaruAppHostGpuImage;
```

격자 배치·팬·줌이 모두 이 구조체로 표현된다. 텍스처 업로드(`MaruAppHostGpuImageUpload`, `image_id`/`generation` 캐시)와 회수(`live_image_ids`)도 kitty graphics 경로가 이미 한다. `buildGpuImages`는 kitty placement 전용 **변환기**일 뿐이므로 갤러리는 자기 builder로 같은 구조체를 채운다.

따라서 **`chrome/draw.zig`의 `Op`에 image를 추가하지 않는다.** 터미널이 "셀 + 이미지"로 그리듯 갤러리도 "chrome이 격자·라벨, `gpu_images`가 픽셀"로 그린다. 서드파티 이미지 라이브러리를 벤더링하지 않는다.

**상한은 실전에서 안 걸린다(2026-08-30 실측).** 실제 트랜스크립트 1,745장에서 최대변 16384 초과가
**0장**, 64 MP 초과도 **0장**이었다(최대 1440×14771 = 21.3 MP). 그래도 clamp 를 남기는 이유는 초과가
`nil` 이 아니라 **abort** 이기 때문이다 — 한 번 걸리면 앱이 죽는다.

다만 그 최대 이미지를 **크게 보기**로 열면 21.3 MP × 4 = **85 MB** 를 상주·업로드해 도크 400 px 에
그렸다. 결함은 아니지만 200 배 낭비다.

**해소했다(2026-08-31, IG15).** 크게 보기도 먼저 **뷰포트에 맞춰** 푼다(`target_side = max(vp.w, vp.h)`).
확대해서 가진 픽셀을 늘려 그리기 시작하면(`scale > 1`) 그때 **원본으로 한 번** 다시 푼다 — 확대 화질은
그대로다. 올릴 때 `pan` 은 화면 px 라 그대로 두고 `scale` 만 텍스처가 커진 만큼 나눠 **보던 자리를
지킨다**. 되풀이는 없다: 원본을 달라고 해도 텍스처 상한 때문에 `subsample > 1` 로 돌아올 수 있어
(§5.3) `decoded_subsample` 만으로는 매 tick 다시 걸리므로 «해 봤다» 를 따로 든다.

**메모리는 잘 묶여 있다(실측)**: 48 MB · 151 장짜리 실제 세션을 열어도 RSS 는 작은 픽스처 대비 **+5 MB**
였다. 인덱스가 오프셋만 들고(§4) 디코드가 보이는 창만 하기 때문이다.

## 6. 보안·개인정보·관측

- 트랜스크립트는 민감한 개인 데이터다([agent-session-list.md](agent-session-list.md) §5와 같은 기준). **이미지 바이트·절대 경로·session id를 trace·crash artifact·fixture·metrics에 쓰지 않는다.** fixture는 synthetic만 허용한다.
- **디스크에 아무것도 남기지 않는다.** 썸네일 캐시·인덱스 영속은 비목표다(사용자 결정). 그래서 §5 계약의 개정이 필요 없다.
- 스크린샷에는 토큰·비밀번호·타인의 정보가 흔히 찍힌다. 갤러리는 그것을 **의도적으로 크게 보여주는** 화면이므로, 화면 공유 중 노출은 사용자가 인지해야 하는 성질이다. 이 문서는 그것을 숨기지 않는다.
- 파일은 no-follow로 열고 `(device, inode)`를 스캔 시점과 다시 대조한다(§4.5).
- metrics는 개수·바이트 수·스캔 시간만 남긴다.

## 10. 선행 조건 — `View` 를 더하기 전에

**측정으로 초안을 정정했다(2026-08-29).** 초안은 *"`.agent_sessions` 비교 29곳이 새 뷰에서 조용히 잘못 동작한다"*였으나, 더미 4번째 값을 넣고 전수 분류한 결과 **28곳이 가드이고 나머지 1곳도 `else null`이라 안전**했다. 도크 셀 조립(`main.zig`)과 `setDockView`도 뷰마다 각각 분기해 새 뷰는 "아무 훅도 없는 뷰"가 될 뿐이다. 그래서 그 29곳은 **건드리지 않는다**.

실제로 필요한 것은 둘이다.

**① 손-미러 제거.** `dockViewSlotIndex`(`dock.zig`)가 `View.slot()`을 손으로 다시 적어 두고 있었다 — 바로 위 `dockViewForSlot`은 `View.forSlot`에 위임하는데 **역방향만 복사본**이었다. 그 비대칭을 없애 순서의 단일 출처를 `dock_panel.View` 하나로 되돌린다.

**② 컴파일 게이트를 바로 잡는다.** enum exhaustiveness를 잡는 것은 `zig build`가 **아니다**.

| 명령 | 잡은 곳 |
| --- | --- |
| `zig build` | **0** — CLI(`maru`)만 짓고 macOS 앱 호스트를 안 건드린다 |
| `zig build macos-app-host-abi-lib` | **2**(`dock.zig`·`dock_layout.zig`) |

`defaultRightPtForView`(`dock_layout.zig`)가 exhaustive인 것은 **정상**이다 — 새 뷰의 기본 폭을 정하도록 컴파일러가 강제한다.

`workspace.zig`의 `View.parse(field.raw) orelse .explorer`는 이미 있어, 새 값을 모르는 옛 빌드가 창을 통째로 버리지는 않는다.
