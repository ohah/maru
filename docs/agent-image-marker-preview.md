# 터미널 마커 이미지 프리뷰 (`[Image #N]` Cmd+클릭)

이 문서는 **터미널 화면에 글자로 찍힌 `[Image #N]` 마커를 Cmd+클릭해 그 이미지를 그 자리에서 보는** 기능의
단일 출처다. [에이전트 이미지 갤러리](agent-image-gallery.md)가 **도크 안의** 이미지를 소유하고, 이 문서는
**터미널 화면 위의** 같은 이미지를 소유한다. 픽셀 소스·디코드·텍스처 규율은 갤러리 §5를 그대로 따르며 여기서
다시 정의하지 않는다.

이 문서의 모든 수치는 **2026-09-14에 이 저장소 개발 머신(Apple M4 Max, macOS 26.5.1)에서 직접 측정**한 값이다.
측정 방법은 §10에 적는다. 추정치는 쓰지 않는다.

## 1. 목표와 경계

목표는 "방금 붙여넣은 그 이미지가 맞나"를 **눈으로 확인**하는 것이다. 갤러리가 「아까 그 스크린샷 어디 갔지」를
푼다면, 이 기능은 **보내기 전에** 그리고 **보낸 자리에서** 같은 질문을 푼다.

provider는 갤러리와 같은 **Codex와 Claude Code 둘**이다. 둘 다 입력창에 같은 마커를 그린다(§4.1 실측).

| 구분 | 권위 | 이 문서와의 관계 |
| --- | --- | --- |
| 터미널 그리드(셀) | PTY가 소유 | **읽기만 한다.** 마커를 찾을 뿐 한 바이트도 쓰지 않는다 |
| 붙여넣기 전 클립보드 | maru 자신 | **전송 전 프리뷰의 유일한 소스**(§4.2) — 그 PNG를 저장한 것이 maru다 |
| provider JSONL | provider가 쓴 기록 | **전송 후 프리뷰의 소스**. 갤러리 인덱스를 그대로 읽는다 |
| 이미지 픽셀 렌더 | `MaruAppHostGpuImage` | kitty graphics·갤러리와 **같은 채널**. 새 렌더 경로를 만들지 않는다 |

**비목표**: 인라인 삽입(§2.1이 근거), 마커가 아닌 이미지 경로 텍스트의 프리뷰(링크 감지가 이미 연다),
원본 크기로 화면 위에서 보기(§2.3 — 원본은 도크가 소유한다), kitty graphics 이미지(이미 픽셀로 그려져 있다).

## 2. 화면과 상호작용

```text
❯ [Image #1] [Image #2] 이 화면 정렬이 틀어졌어요
  └────┬───┘
       │ Cmd+클릭
       ▼
  ┌─────────────┐
  │             │   ← 마커 바로 아래에 떠 있는 프리뷰(workspace 기준 · 팝오버)
  │             │      다시 Cmd+클릭 = 닫기
  └─────────────┘
     원본 크기로 ↗   ← 도크 갤러리로 점프(전송 후에만)
```

### 2.1 그리드를 건드리지 않는다 — 인라인이 아니라 떠 있는 레이어다

**행을 밀어내는 인라인 삽입은 불가능하다.** 두 provider의 TUI는 alt 화면에서 매 프레임 화면 전체를 다시
그린다. maru가 행을 끼워 넣으면 ⑴ PTY가 아는 커서 좌표와 화면이 어긋나고 ⑵ 다음 리페인트가 그 행을 덮는다.
그리드는 PTY 소유라는 [PTY 운영 모델](pty-operating-model.md)의 경계가 여기서 강제된다.

그래서 프리뷰는 **갤러리와 같은 이미지 채널**로 그린다. `MaruAppHostGpuImage`는 셀이 아니라 픽셀 사각형 +
UV 크롭 + z이므로(갤러리 §5.4) 터미널 위에 떠 있는 그림이 자연스럽게 표현된다. `chrome/draw.zig`의 `Op`에
image를 **추가하지 않는다** — 갤러리가 정한 "chrome이 테두리·라벨, `gpu_images`가 픽셀" 분업을 따른다.

z는 **셀 패스 뒤**(`z ≥ 0`)다. 텍스트 앞에 떠야 가리는 것이 보인다.

### 2.2 제스처는 Cmd+클릭 하나다 — 맨 클릭은 쓸 수 없다

**두 TUI 모두 마우스를 소유한다.** [config 문서](configuration.md) `input.right-click` 항목이 이미
"vim·tmux·**Claude Code** 등 DECSET 1000~1003을 켠 TUI"를 명시하고, 리포팅 중 버튼 이벤트는
[키 입력 경계](key-input-and-shortcuts.md)대로 **예외 없이** 앱에 간다. 맨 클릭에 프리뷰를 얹으면 TUI의
클릭을 빼앗는다.

그래서 링크와 **같은 수식키**를 쓴다(`input.url-click-modifier`, 기본 Cmd). 이미 있는 게이트를 빌리므로
사용자가 배울 것이 없고, 리포팅 통과 규칙도 이미 그 경로가 지킨다.

**토글이다.** 같은 마커를 다시 Cmd+클릭하면 닫힌다. Esc도 닫는다(도크 갤러리와 같은 키 소유권 게이트 —
누른 적이 있을 때만 가져간다). 한 번에 **하나만** 열린다: 다른 마커를 누르면 이전 것이 닫히고 그것이 열린다.
여럿을 동시에 띄우면 서로를 가리고, 닫는 방법이 사용자에게 분명하지 않다.

**링크 감지와 부딪히지 않는다(실측).** 두 provider 모두 붙여넣은 **경로를 화면에 남기지 않고** 즉시
`[Image #N]`으로 치환한다(§4.1). 그래서 같은 셀을 두고 파일 링크와 마커가 경합하는 상황이 애초에 없다.
그래도 우선순위는 정해 둔다 — **마커가 먼저다.** 마커는 분류가 `stat` 없이 끝나고(문자열), 링크는 존재
검증까지 가므로 순서를 뒤집으면 헛 `stat`이 붙는다.

### 2.3 크기는 **workspace**에 반응한다 — 프리뷰는 pane의 자식이 아니라 팝오버다

사용자 결정(2026-09-14)이다. 화면 위 프리뷰는 **확인용**이고, 원본을 보는 곳은 우측 도크다.

**초안은 크기와 클립을 모두 pane 기준으로 잡았는데, 그것이 이 저장소의 관례에서 벗어난 것이었다.**
`chrome/components/context_menu.zig`는 **pane을 아예 모르고** 앵커(클릭 px)에서 시작해 **workspace
경계**로 clamp한다(사이드바 오른쪽, 상태바 위). 드롭다운·단축키 힌트도 같다. 떠 있는 것이 부모 컨테이너를
넘는 것은 예외가 아니라 **그 컴포넌트들의 정상 동작**이다. 프리뷰도 같은 부류다.

| 축 | 값 | 근거 |
| --- | --- | --- |
| 최대 폭 | **workspace 폭의 1/2** | 옆 텍스트를 읽으면서 비교할 수 있어야 한다 |
| 최대 높이 | **workspace 높이의 1/2** | 세로로 긴 스크린샷이 화면을 통째로 덮으면 닫을 곳을 못 찾는다 |
| 배율 상한 | **1.0** | 작은 이미지를 늘려 흐리게 만들면 «원본 확인»이 거짓말이 된다(갤러리 §2와 같은 규율) |
| 경계 | **workspace** — 사이드바 오른쪽, 상태바 위 | `context_menu`의 clamp와 **같은 사각형**을 쓴다 |

**최소 폭 규칙이 사라졌다.** 크기가 pane과 무관해졌으므로 좁은 pane에서도 읽을 수 있는 프리뷰가 나온다 —
초안의 「160 px 미만이면 열지 않는다」와 그것이 만든 **무반응 모순(옛 M7)이 함께 해소됐다**.

표시 문자열은 예외 없이 [i18n](i18n.md)의 키를 거친다(갤러리와 같은 규율). 이 화면이 내는 문자열은
**「도크에서 보기」와 실패 안내 둘뿐**이고, 실패 안내는 조각을 이어 붙이지 않는다 — 갤러리 §2가
「12장 중 8장」에서 겪은 대로 어순이 반대인 언어에서 한쪽이 반드시 틀린다.

**확대·팬을 두지 않는다.** 그 상호작용은 도크의 「크게 보기」가 이미 소유하고(갤러리 §2), 화면 위에서 휠을
가로채면 TUI의 스크롤을 빼앗는다. 대신 프리뷰 모서리에 **「도크에서 보기」** 를 두고, 그것이 갤러리의 크게
보기로 점프한다(`enterDockView(.agent_activity)` + 그 `hit_index`로 `Open` — 둘 다 기존 부품이다).

⚠️ **전송 전에는 도크 점프가 없다.** 아직 트랜스크립트에 없어 `hit_index`가 존재하지 않는다(§4.2). 갤러리의
소스는 트랜스크립트뿐이라는 계약(§3.1)을 이 기능이 깨지 않는다. 전송 전 프리뷰는 **화면 위 확인이 전부**이고,
원본이 필요하면 그 PNG는 `$TMPDIR/maru-paste/`에 있으므로 기존 파일 열기로 빠진다.

### 2.4 배치 — 마커 아래, 넘치면 위

프리뷰는 마커 span의 **바로 아래 줄**에 왼쪽을 맞춘다. 아래로 **workspace**를 넘치면 위로 뒤집고,
오른쪽으로 넘치면 workspace 오른쪽 끝에 맞춰 민다. 이 계산은 **직접 하지 않는다** — 앵커 팝업의 공유
프리미티브 `chrome/components/popup_box.zig`(`vertical = .below_flip_up`)가 소유한다. 우클릭 메뉴도 같은
것을 쓰므로 「가장자리에 딱 붙이지 않는다」 같은 규칙이 한 곳에서만 산다(chrome-strategy.md §5.4). 입력창이 화면 하단에 있으므로
(두 provider 모두) **실전에서는 위로 뒤집히는 쪽이 기본 경로다** — 이 분기를 나중에 붙이는 예외로 두면 안 된다.

**pane 경계는 보지 않는다.** 마커가 좁은 pane에 있어도 프리뷰는 옆 pane 위로 떠서 읽을 수 있는 크기를
가진다(§2.3). 가려진 pane이 신경 쓰이면 다시 눌러 닫으면 된다 — 토글이 그 대가를 싸게 만든다.

## 3. 마커를 찾는다 — 새 스캐너를 만들지 않는다

마커는 `[Image #` + 십진수 + `]`로 고정된 문자열이다(§4.1 실측 — 두 provider가 같다). 그래서 화면 검색이
이미 가진 것을 그대로 쓴다.

| 필요 | 구현 | 위치 |
| --- | --- | --- |
| 한 줄에서 마커 파싱 | `scanLine` — 고정 접두사 + 십진수 + `]`. **정규식을 쓰지 않는다** | `session/agent_image_staging.zig` |
| 뷰포트에서 긁기(셀 열까지) | `scan(snap, scope, out)` | `session/agent_image_markers.zig` |
| 클릭한 셀이 마커 안인가 | `hitAt(hits, row, col)` | 같음 |
| 관찰·`syncVisible`이 먹을 N 목록 | `numbersOf` | 같음 |
| 원격 화면의 마커 목록 | `collectViewportLinks`와 **같은 패턴** | `selection.zig:824`, §6 |

**바이트가 아니라 셀 열로 답한다.** 프리뷰를 놓으려면 열이 필요한데 한글·이모지가 섞이면 바이트와 열이
1:1이 아니다. `agent_image_markers`가 행 텍스트를 풀면서 「바이트 → 열」 표를 함께 만드는 이유다.

**한 줄에 여러 개가 온다.** 실측에서 `❯ [Image #1] [Image #2]`가 공백 하나로 이어 붙어 나왔다. 줄에서 첫
매치만 보고 끝내면 두 번째 이미지는 영영 못 연다 — 줄 단위로 **모두** 수집해야 한다.

### 3.1 패턴은 마커를 **구분하지 못한다** — 후보만 낸다 ⚠️

**마커에는 아무 표시가 없다(실측).** 이스케이프까지 캡처해 보면 이렇다.

```text
ESC[39m ❯ [Image #1] [Image #2]
        └ 기본 전경색(39). 굵기·색·OSC 8 — 아무것도 없다
```

즉 TUI가 그린 마커와 **사람이 타이핑한 같은 글자가 바이트 단위로 동일하다.** 그리고 그 글자는 화면에
흔하게 나타난다 — 이 기능을 이야기하는 대화, 에이전트의 응답, `git diff`, **이 설계 문서를 `cat` 한 화면**
전부다. 패턴을 아무리 좁혀도(정규식이든 고정 문자열이든) 이 셋을 가를 수 없다.

그러므로 규율은 이렇다.

> **스캔은 후보만 낸다. 「진짜 마커인가」를 정하는 것은 화면이 아니라 우리가 가진 기록이다.**

| 축 | 무엇이 정하나 | 없으면 |
| --- | --- | --- |
| 후보 찾기 | `findMatches("[Image #")` — 정규식이 필요 없다(고정 접두사 + 십진수 + `]`) | — |
| **이것이 마커인가** | **전송 전**: 붙여넣기 때 관찰해 둔 기록(§4.2)에 그 N이 있는가 · **전송 후**: 인덱스에 그 N이 있는가(§4.4) | 열지 않는다 |
| 어느 그림인가 | 같은 기록의 `N → PNG` | 열지 않는다 |

**전송 전에는 범위도 좁힌다.** 입력창은 **커서가 있는 블록**이므로, 그 밖의 마커는 후보에서 뺀다. 커서
위치는 코어가 권위 있게 안다(`RenderSnapshot`의 cursor).

⚠️ **그 범위 판정이 Codex에서는 스크롤에 깨진다(§3.3).**

### 3.3 두 provider는 화면 모델이 다르다 ⚠️ (실측)

| | `alternate_on` | `history_size` | 뜻 |
| --- | --- | --- | --- |
| Claude Code 2.1.267 | **1** | **0** | alt 화면. 스크롤백이 없다 |
| Codex 0.154.0 | **0** | **12**(이미 쌓임) | **primary 화면.** 스크롤백에 대화가 쌓인다 |

갤러리 §3.1이 *"사용자 환경이 `tui: fullscreen`이라 alt 화면이고 스크롤백 용량이 0"* 이라고 적은 것은
**Claude 쪽 이야기였다.** 그 문서의 결론(소스는 트랜스크립트뿐)은 그대로 옳지만, 근거 문장이 provider
하나에만 맞다. 프리뷰는 화면을 직접 건드리므로 이 차이가 그대로 결함이 된다.

**Codex에서 따라오는 것 둘.**

1. **스크롤백에 마커가 쌓이고, 그 번호는 유일하지 않다.** Codex의 N은 입력창을 비울 때마다 1로
   돌아가므로(§4.3) 스크롤백에는 **같은 `#1`이 여러 개** 남는다. A10의 오탐 표면이 Claude보다 훨씬 넓고,
   전송 후 매핑의 "N 단독으로는 부족하다"(§4.3)가 화면에서도 그대로 문제가 된다.
2. **커서가 화면 밖으로 나갈 수 있다.** 사용자가 위로 스크롤하면 입력창이 보이지 않는다. 그러면
   "커서가 있는 블록" 판정이 성립하지 않는다.

그래서 규칙을 이렇게 못박는다.

> **커서가 화면에 보이지 않으면 전송 전 프리뷰는 동작하지 않는다.** 그때 눌린 마커는 전송 후 경로
> (인덱스, §4.4)로만 푼다. 인덱스가 모르면 열지 않는다.

스크롤을 올린 사용자가 보고 있는 것은 **지난 대화**이고, 거기 있는 마커는 이미 전송된 것이다 — 전송 전
경로가 답할 이유가 없다. 이 규칙은 Claude에서는 아무것도 바꾸지 않는다(alt 화면이라 커서가 늘 보인다).

**그래도 뚫리는 경우가 있다.** 사용자가 입력창에 **맵에 있는 번호를** 손으로 타이핑하면(`[Image #1]`을
글자로 치면) 후보·기록·범위가 모두 맞아 프리뷰가 뜬다. 이것은 **막지 않는다** — 막으려면 화면에 없는
정보가 필요하다. 피해가 작기 때문이다: ⑴ Cmd+클릭이라 **의도적으로 눌러야** 뜨고, ⑵ 뜬 그림은 실제로
그 세션에 붙여넣은 이미지이며, ⑶ 다시 누르면 닫힌다. 지나가다 뜨는 일이 없다는 것이 §2.2에서 hover가
아니라 명시 제스처를 고른 이유의 절반이다.

**전송 후는 한 겹 더 필요하다.** 그때의 후보 범위는 입력창이 아니라 대화 영역 전체라 오탐 표면이 훨씬
넓다(위의 `cat` 예가 정확히 그 경우다). 인덱스는 그 마커가 **어느 메시지의 것인지**와 **그 메시지의 텍스트**를
이미 안다(갤러리 §2.2의 라벨). 화면의 마커 뒤에 오는 글자가 그 텍스트와 어긋나면 **열지 않는다.**
§9 M2가 Codex 쪽 메시지 구분과 함께 이 판정을 소유한다.

**앵커는 절대 좌표로 들고 매 프레임 재검증한다.** 링크 밑줄이 `hover_url_anchor`/`hover_url_pos_px`로 이미
하는 것과 같다(`app_session.zig`). TUI가 그 자리를 다른 내용으로 덮어도 우리는 통보받지 못하므로, 프레임마다
"그 앵커에 아직 같은 마커가 있는가"를 확인하고 아니면 **조용히 닫는다**. 이 재검증이 없으면 프리뷰가 엉뚱한
글자 위에 남는다.

### 3.2 스캔은 수식키를 누른 동안에만 한다

**매 프레임 화면 전체를 훑지 않는다.** [링크 감지](link-detection.md)가 같은 문제를 이미 실측으로 풀어 뒀다 —
분류는 **수식키를 누른 동안에만** 돌고, 링크가 아닌 단어에서는 분류가 먼저 null을 내 비용이 변하지 않는다.
마커도 같은 게이트 아래 둔다. 제스처가 Cmd+클릭이므로(§2.2) Cmd를 누르지 않은 프레임에 후보를 계산할
이유가 없다.

| 언제 | 무엇을 | 비용 |
| --- | --- | --- |
| Cmd 홀드 중 | 화면에서 마커 후보 스캔(`findMatches`) | 링크 분류와 같은 자리 |
| 매 프레임 | **열려 있는 프리뷰의 앵커 한 곳만** 재검증 | 셀 몇 개 비교 |
| 그 밖 | 아무것도 안 한다 | 0 |

## 4. 마커 → 이미지

여기가 이 설계의 전부다. 마커는 **번호밖에 없는데** 그 번호의 의미가 provider마다 다르고, 소스도 전송 전후로
갈린다.

### 4.1 마커의 모양 — 두 provider가 같다 (실측)

| provider | 버전 | 1장 | 2장 | 프롬프트 글리프 |
| --- | --- | --- | --- | --- |
| Claude Code | 2.1.267 | `❯ [Image #1]` | `❯ [Image #1] [Image #2]` | `❯` |
| Codex | 0.154.0 | `› [Image #1]` | `› [Image #1] [Image #2]` | `›` |

**마커 문자열이 동일하다.** 스캐너는 한 벌이면 된다. 그리고 **붙여넣은 경로는 화면에 남지 않는다** — 두 TUI가
즉시 마커로 치환한다. 이것이 §2.2의 "링크와 경합이 없다"의 근거다.

전제는 **bracketed paste**다. ABI v58이 기록한 대로, 드래그 삽입을 직접 입력으로 바꿨더니 TUI가 경로를
한 덩어리로 못 보고 `[Image]` 인식이 깨졌다. maru의 paste 경로(`sendPasteText`)는 DECSET 2004가 켜져 있을
때 bracketed로 감싸므로 이 전제가 성립한다.

### 4.2 전송 전 — 그 PNG를 저장한 것이 maru다

`MaruAppHost.swift:7550`의 경로가 이미 이렇게 돈다.

```text
클립보드 비트맵 ──► clipboardImagePng()  PNG로 정규화(TIFF·JPEG도)
                        │
                        ├─► saveTempPng()  $TMPDIR/maru-paste/<UUID>.png (atomic)
                        │
                        └─► sendPasteText(경로, escapeItems: true)  ──► PTY
                                                                        └─► TUI가 [Image #N]으로 치환
```

그러므로 **전송 전 프리뷰에 새 데이터 소스가 필요 없다.** 붙여넣는 순간 maru가 PNG 바이트와 경로를 손에
쥐고 있다. `cleanupPasteImages`는 **앱 시작 시에만** 비우므로(paste 직후엔 provider가 언제 읽을지 몰라 못
지운다) 실행 중에는 파일이 살아 있다.

**대응 규칙: 번호를 추측하지 않고 관찰한다.**

**「순서」로 잡으면 틀린다(실측이 반증했다).** 초안은 *"보이는 마커 k개는 스테이징의 마지막 k개와 순서대로
대응한다"* 였는데, Claude에서 두 장을 붙이고 뒤쪽을 지운 뒤 다시 붙이면 화면이 **`#1 #3`** 이 된다(§10).
스테이징은 세 번 쌓였고 화면에는 둘인데, 그 둘은 **1번째와 3번째**다 — "마지막 2개"는 2번째와 3번째를
가리키므로 **왼쪽 프리뷰가 남의 그림이 된다.** 번호는 재사용되지 않고 건너뛴다.

그래서 이렇게 잡는다.

> 붙여넣기 직후 화면에 **새로 나타난 마커의 N**을 읽어, 그 N에 이 PNG를 묶는다.
> 스테이징은 순서 목록이 아니라 **`N → PNG` 맵**이다.

| 단계 | 하는 일 |
| --- | --- |
| 붙여넣기 직전 | 화면의 마커 N 집합을 기록한다(`S_before`) |
| paste 전송 | 기존 경로(`sendPasteText`) 그대로 |
| 마커 등장 후 | `S_after \ S_before`가 새 N이다. 하나면 그것에 묶는다 |
| 여러 장 연속 | 새 N이 여럿이면 **오름차순으로** 붙여넣은 큐 순서에 묶는다 |
| 안 나타나면 | **스테이징에 넣지 않는다** — 프리뷰 없음. 틀린 그림보다 없는 편이 낫다 |

이 규칙은 provider의 번호 규칙을 **몰라도 성립한다.** 추측하는 대신 화면이 말한 것을 받아 적기 때문이다.

**관찰 창은 넉넉히 잡는다.** 마커는 실측 **42 ms 안에** 뜬다(§10 — 첫 캡처에 이미 있었으므로 상한이다).
그래도 창을 그 근처로 조이지 않는다. 이 값은 이 머신·tmux·로컬의 것이고, 원격이나 부하에서는 느려지는데
**놓치면 그 장은 영영 안 열리기** 때문이다. 짧게 잡아 얻는 것이 없다 — 창이 길어도 그동안 하는 일은
마커 집합 비교뿐이다.

**연속 붙여넣기는 큐 순서로 묶는다.** 간격 없이 두 장을 넣으면 화면에 `#2 #3`이 **한꺼번에** 나타난다
(실측 — 중간 상태가 잡히지 않았다). 새 N이 여럿일 때 오름차순으로 큐에 대응시키는 것이 이 때문에 필요하다.

**맵에 없는 N은 열지 않는다.** 앱을 재시작했거나 maru를 거치지 않고 들어온 이미지는 맵에 없다. 그때는
**프리뷰를 띄우지 않는다** — 틀린 이미지를 자신 있게 보여주는 것이 아무것도 안 보여주는 것보다 나쁘다.

#### 전송은 「입력창 비우기」와 화면상 구분되지 않는다 ⚠️

초안은 *"화면 마커가 0이 되면 맵을 비운다"* 로 Codex의 번호 리셋(§4.3)을 흡수했다. **그 규칙은 전송을
망가뜨린다.** Enter로 보내도 입력창 마커는 0이 되기 때문이다 — 화면만 보면 C-u와 구분이 안 된다. 맵을
비우면 방금 보낸 이미지의 픽셀을 잃는데, 인덱스는 아직 그것을 모른다(훅 push든 mtime 폴링이든 지연이
있다, 갤러리 §4.4). 그 사이 사용자가 **바로 그 마커**(전송되어 대화 영역에 에코된 것)를 눌러도 아무 데서도
못 찾는다. §4.4의 "인덱스에 나타나면 버린다"와도 정면으로 모순이다.

그래서 **버리지 않고 상태를 옮긴다.**

| 상태 | 뜻 | 픽셀 |
| --- | --- | --- |
| `staged` | 입력창에 마커가 보인다 | 스테이징이 든다 |
| `sent` | 입력창에서 사라졌다(전송 또는 비우기) | **계속 든다** — 인덱스가 받을 때까지 |
| `indexed` | 트랜스크립트에 같은 이미지가 나타났다 | 놓는다. 이후는 갤러리 인덱스가 소유(§4.4) |

**Codex의 N 리셋으로 번호가 겹치는 것은 §3.1의 범위가 가른다.** 입력창(커서 블록)의 마커는 `staged`에서
찾고, 대화 영역의 마커는 `sent`와 인덱스에서 찾는다. 같은 `#1`이 두 곳에 있어도 어느 쪽을 눌렀는지로
갈리므로 모호하지 않다.

`sent`가 영영 안 걷히는 경우(전송하지 않고 비웠다 — 그 이미지는 트랜스크립트에 안 들어온다)를 위해
**pane당 상한**을 둔다. 넘으면 오래된 `sent`부터 픽셀을 놓는다. 스테이징은 메모리 전용이므로(§7) 이
상한이 유일한 방어다. **상한은 개수가 아니라 바이트로 잡는다** — 같은 이미지를 두 번 붙여넣으면
`saveTempPng`가 UUID로 **매번 새 파일**을 만들어 사본이 둘이 되고(갤러리 §4.3의 dedup은 트랜스크립트
쪽 이야기라 여기 적용되지 않는다), 스크린샷 한 장이 수십 MB일 수 있어 개수 상한은 실제 메모리를
묶지 못한다.

#### 맵은 **surface별**이다 — 세션에 하나로 두면 pane을 섞는다

갤러리의 `agent_activity: State`는 **AppSession에 하나**이고 포커스가 옮겨가면 내용이 바뀐다(갤러리 §2.1).
**그 패턴을 베끼면 안 된다.** N의 네임스페이스는 **에이전트 프로세스별**이고 프로세스는 pane에 하나씩이라,
세션에 맵 하나를 두면 두 pane의 `#1`이 같은 칸을 다툰다. 게다가 프리뷰는 **비활성 pane의 마커도** 눌릴 수
있다 — 링크 hover가 활성 pane 고정을 버리고 `paneTargetAt` 라우팅을 쓰는 이유와 같다(`app_session.zig`
hover 경로 주석: 활성 pane 고정이면 "비활성 pane에서 밑줄이 안 뜨거나 엉뚱한 pane에 그려진다").

그래서 맵은 `surface_id`로 스코프한다. **surface 수명에 묶인다**: pane을 닫거나 다른 창으로 옮기면
(detach/reattach) 그 맵도 함께 간다. 파괴 경로(`destroyTerm`·세션 `deinit`)에서 픽셀을 해제하고,
같은 자리에서 **텍스처 회수 표시**(§5)도 세운다 — 안 그러면 죽은 pane의 `image_id`가 유령으로 남는다.

### 4.3 번호의 의미가 provider마다 다르다 ⚠️ (실측)

이 표가 §4.2의 "번호를 믿지 않는다"를 정한 근거다.

| 동작 | Claude Code 2.1.267 | Codex 0.154.0 |
| --- | --- | --- |
| 2장 붙여넣기 | `#1 #2` | `#1 #2` |
| 입력창 비우기(C-u) | 마커 사라짐 | 마커 사라짐 |
| 그 뒤 1장 붙여넣기 | **`#3`** — 이어진다 | **`#1`** — 리셋된다 |
| `/clear` 뒤 1장 | **`#4`** — 세션을 새로 만들어도 이어진다 | (미측정) |
| 백스페이스로 마커 1개 삭제 | `#1 #2` → **`#1`** (한 덩어리로 지워진다) | `#1 #2` → **`#1 #2`** (지워지지 않는다) |
| 그 뒤 1장 붙여넣기 | **`#1 #3`** — **번호를 건너뛴다** | `#1 #2 #3` |

**빈 번호는 재사용되지 않는다.** Claude에서 `#2`를 지운 자리에 다음 이미지가 `#2`로 들어오지 않고 `#3`이
된다. 그래서 화면의 마커 번호는 **연속이 아니며**, 순서로 세면 어긋난다 — §4.2의 관찰 규칙이 이것 때문에
있다.

**Codex의 N도 완전한 입력창 단위는 아니다.** C-u로 **통째로** 비우면 1로 돌아가지만, 마커가 하나라도 남아
있는 동안은 계속 올라간다(`#1 #2 #3`). 즉 두 provider 모두 "비어 있지 않은 동안 단조 증가"이고, 다른 것은
**원점**뿐이다 — Claude는 프로세스 시작, Codex는 입력창이 마지막으로 빈 시점.

**Claude의 N은 프로세스 수명 카운터다.** `/clear`가 새 트랜스크립트 파일을 만드는데도 번호가 이어진다는
것이 그 증거다. 이것이 트랜스크립트 실측의 되감김(`3→4→5→2→3→10→13→36→39`)도 설명한다 — 되감김은
**다른 실행이 같은 파일에 이어붙을 때**만 일어난다(`--resume`은 같은 파일에 이어붙는다, 갤러리 §2.1).

**Codex의 N은 입력창(composer) 안의 슬롯 번호다.** 전송하거나 비우면 1부터 다시 센다.

그래서 **전송 후** 매핑도 갈린다.

| provider | 전송 후 유일 키 | 근거 |
| --- | --- | --- |
| Claude | `(pane 프로세스, N)` | N이 프로세스 안에서 단조 증가한다. pane↔프로세스는 훅이 잇는다(갤러리 §4.4) |
| Codex | `(그 메시지, N)` — **N 단독으로는 부족하다** | N이 메시지 안에서만 유일하다. 인덱스는 `<image name=[Image #N] path="…">` 래퍼로 메시지와 경로를 함께 안다(갤러리 §2.2) |

Codex 쪽에서 "그 메시지"를 화면만 보고 어떻게 가르는가가 남는 문제다. §9 M2가 그 결정을 소유한다.

### 4.4 전송 후 — 갤러리 인덱스를 그대로 읽는다

전송되면 같은 이미지가 트랜스크립트에 들어오고, 갤러리 인덱스(`session/agent_image_index.zig`)가 이미 그것을
`(줄 오프셋, 데이터 오프셋, 길이)`로 들고 있다. 프리뷰는 **그 인덱스를 조회할 뿐 새로 스캔하지 않는다.**
디코드도 갤러리의 워커 경로(`agent_image_decode_backend`)를 그대로 쓴다.

**전송의 순간이 아니라 인덱스 도착이 소스를 갈아탄다.** 스테이징 항목은 트랜스크립트에 같은 이미지가
나타났을 때(`indexed`) 픽셀을 놓는다 — 그 전까지는 `sent`로 계속 든다(§4.2). 그러지 않으면 전송 직후부터
인덱스 갱신(훅 push 또는 mtime 폴링, 갤러리 §4.4)까지의 구간에 그 이미지가 **어디에도 없다.**

## 5. 렌더 — 갤러리 §5의 규율을 그대로 진다

새 규율은 없지만, **토글**이라는 형태 때문에 그중 하나가 정면으로 걸린다.

**⚠️ 끌 때 반드시 「다시 올려야 함」으로 표시한다.** 갤러리 §5.4가 기록한 대로, `live_image_ids`에서 한
프레임이라도 빠진 텍스처는 회수되는데 "이미 올렸다" 표시가 참으로 남아 있으면 다음에 그릴 때 업로드 없이
id만 실려 **빈 자리**가 된다. 갤러리에서 실제로 빠져 있던 길이 「도크 접기」였고, **끄고 켜는 토글은 그 길
자체**다. 닫기·앵커 재검증 실패·pane 전환 — 프리뷰가 사라지는 **모든** 길에 같은 표시가 붙어야 한다.

**⚠️ UV로 잘라 workspace 밖으로 넘치지 않게 한다.** 이미지 quad에는 scissor가 없다(갤러리 §2). 자를
사각형은 **pane이 아니라 workspace**다(§2.3) — 프리뷰가 옆 pane 위로 뜨는 것은 결함이 아니라 팝오버의
정상 동작이고, 막아야 하는 것은 **사이드바·상태바·창 밖으로 새는 것**이다. §2.4의 clamp가 대부분을
막지만 그것은 배치 규칙이지 클립이 아니다 — 둘 다 있어야 한다.

**⚠️ `image_id` 공간을 갤러리와 나눈다.** 갤러리가 `activity_image_id_base = 0xFFF0_0000`부터 격자 타일
(`+n`, n ≤ 0xFFFF)과 크게 보기(`+0x10000`)를 이미 쓴다(`agent_activity.zig:934`·`949`). 프리뷰가 그 공간에
끼어들면 **도크 갤러리와 프리뷰가 동시에 열렸을 때 서로의 텍스처를 덮는다** — 렌더러는 `image_id`로만
캐시를 찾으므로 증상이 "가끔 다른 그림이 뜬다"로 나와 원인을 못 찾는다. 프리뷰는 **자기 base**를 따로
잡는다(제안: `0xFFF2_0000`). 한 번에 하나만 열리므로(§2.2) 상수 하나면 된다.

**⚠️ 텍스처 한 변을 clamp한다.** Metal은 상한 초과 디스크립터에 `nil`이 아니라 **abort**를 낸다(갤러리 §5.3,
이 머신 상한 16,384). §2.3이 pane의 1/2로 줄여 올리므로 실전에서 닿지 않지만, clamp는 방어가 아니라
정확성 요구다.

디코드 비용은 갤러리 실측을 그대로 쓴다 — 2830×1662 PNG **19.78 ms**, 축소해도 같다(압축 해제가 비용이다).
60 Hz 예산 16.7 ms를 넘으므로 **렌더 tick에서 풀지 않는다.** 도착 전에는 자리표시자를 그린다.

## 6. 원격(ssh) — 바이트는 이미 우리를 거친다

갤러리는 원격에서 트랜스크립트를 못 읽어 차단돼 있었고, [원격 활동 뷰](plans/remote-agent-activity.md)가
host가 `Hit`+라벨을 보내는 길을 깔았다. 프리뷰는 그 위에 두 가지를 더한다.

**바이트는 원격에서도 우리를 거친다.** ABI v69의 `drop_image`가 원격 세션에서 PNG 바이트를 control socket으로
업로드하고 원격 경로(`pasted-<pid>-N.png`)를 paste한다. 스테이징은 로컬 임시파일이 아니라 그 바이트를 들면
된다.

⚠️ **그러나 「로컬과 같다」는 틀렸다 — 관찰이 안 된다.** §4.2의 대응은 **붙여넣기 직후 화면에서 새 N을
읽는** 것인데, host-backed 세션의 client core는 **빈 placeholder**다(`app_session.zig`의 원격 placeholder
규율 · `remoteLinkSpanAt` 주석). client는 화면 텍스트를 갖고 있지 않으므로 새 N을 스스로 볼 수 없다.

그러므로 원격에서는 **host가 관찰한다.** 링크가 이미 "host가 최대 집합을 계산해 보내고 client가 자기
config로 거른다"로 풀었으므로 마커 span도 같은 길에 실린다 — 다만 프리뷰는 **타이밍이 붙는다**: 마커는
42 ms 안에 뜨므로(§10) host가 그 변화를 다음 프레임에 실어 보내야 관찰 창 안에 들어온다. 이것이 P3의
작업량을 "픽셀 pull 하나"에서 **"관찰 경로까지"** 로 늘린다.

**전송 후는 pull이 필요하다.** 원격 활동 뷰는 「파일 대신 Hit+라벨을 보내 499:1」로 아꼈으므로 픽셀이
client에 없다. 프리뷰가 열릴 때 **그 한 장만** 요청하는 경로를 더한다. 목록 전송을 다시 무겁게 만들지
않는 것이 그 설계의 요점이므로, push로 되돌리지 않는다.

**화면 마커 스캔도 host가 한다.** host-backed 세션의 client core는 빈 placeholder다(`app_session.zig`의
`remoteLinkSpanAt` 주석). 링크가 이미 "host가 최대 집합을 계산해 보내고 client가 자기 config로 거른다"로
풀었으므로, 마커 span도 **같은 길**에 실어 보낸다.

## 7. 보안·개인정보

갤러리 §6과 같은 기준이며, 프리뷰가 더하는 것은 없다.

- 이미지 바이트·절대 경로·session id를 trace·crash artifact·fixture·metrics에 쓰지 않는다. fixture는
  synthetic만 허용한다.
- **디스크에 새로 남기는 것이 없다.** 스테이징은 maru가 **이미 저장한** `$TMPDIR/maru-paste/` 파일을 가리킬
  뿐이고, 그 수명은 `cleanupPasteImages`가 이미 소유한다.
- 스크린샷에는 토큰·비밀번호가 흔히 찍힌다. 프리뷰는 그것을 **터미널 한가운데에** 띄우므로 화면 공유 중
  노출 위험이 갤러리보다 높다. 이 문서는 그것을 숨기지 않는다 — 다만 §2.2의 **명시 제스처**(Cmd+클릭)가
  방어다. 지나가다 뜨는 일이 없다.

## 8. 적대적 검토

**A7·A10·A11·A15·A16이 초안을 다섯 번 뒤집었다** — 설계가 아니라 실측과 기존 코드가 규칙을 정했다.
그중 셋(A7·A15·A16)은 **"두 provider가 같을 것"** 또는 **"원격도 같을 것"** 이라는 추측에서 나왔다.

| **M7** | 좁은 pane에서 전송 전 마커를 누르면 | **해소됐다(2026-09-14 · 사용자 지적).** 세 선택지를 놓고 고민한 것 자체가 **틀린 프레임**이었다 — 프리뷰를 pane의 자식으로 전제했기 때문이다. `context_menu`는 pane을 아예 모르고 workspace로 clamp하며, 떠 있는 것이 부모를 넘는 것은 그 컴포넌트들의 **정상 동작**이다. 크기 기준을 workspace로 옮기자 최소 폭 규칙도 무반응 모순도 함께 사라졌다(§2.3) |
| M6 | 창 크기를 바꾸면 | TUI가 입력창을 다시 그리므로 앵커 재검증이 실패해 **프리뷰가 닫힌다**(§3). 정상 동작으로 둔다 — 닫힌 자리를 다시 누르면 열린다. 리사이즈를 따라가려면 TUI 레이아웃을 추정해야 하는데 그 추정은 깨진다 |
| M2 | Codex의 전송 후 매핑에서 "그 메시지"를 화면만 보고 어떻게 가르나 | **미결.** N이 메시지 안에서만 유일한데 **A15가 이것을 더 나쁘게 만들었다** — Codex는 primary 화면이라 스크롤백에 같은 `#1`이 여러 개 **실제로 보인다**. 화면의 프롬프트 블록 경계를 읽거나, Codex는 전송 후 매핑을 **보류**하고 전송 전만 지원하는 선택지가 있다. **P2의 선행 조건**이며 P1을 막지 않는다 |
| M3 | 앱을 재시작하면 | 스테이징은 메모리 전용이라 사라진다. 입력창에는 마커가 남아 있을 수 있으므로 **개수가 어긋나 열리지 않는다**(§4.2) — 틀린 그림 대신 아무것도 안 뜬다 |
| M4 | Windows | 갤러리와 같다 — ImageIO가 없어 **macOS 전용으로 시작**한다(갤러리 §8 M5) |
| M5 | 마커가 줄바꿈으로 갈라지면 | 마커는 11~13자라 폭 좁은 pane에서 래핑될 수 있다. `findMatches`는 래핑을 넘어 잇는 경로가 이미 있다(`urlSpanAtAbs`의 wide glyph wrap 테스트와 같은 축) — 그 경로를 재사용하고 테스트로 고정한다 |

## 10. 측정 방법과 값

2026-09-14, Apple M4 Max / macOS 26.5.1 / Claude Code 2.1.267 · Codex 0.154.0.

입력창 동작은 **tmux 안에서 실제 TUI를 띄우고 bracketed paste로 PNG 절대경로를 넣어**(maru의
`sendPasteText(escapeItems: true)`와 동형) `capture-pane`으로 화면을 읽어 쟀다. 합성 트랜스크립트가 아니라
**실제 제품의 화면**이다.

### 10.1 maru 안에서의 재대조 — 시도했고, 막혔다

⚠️ **이 실측은 tmux 안에서 쟀다.** 2026-09-14에 maru 안에서 같은 표를 재려고 시도했으나 **완료하지
못했다.** 숨기지 않고 적는다.

| 시도 | 결과 |
| --- | --- |
| 현재 코드로 `zig build macos-app-bundle` | **성공** |
| 앱 실행 | 프로세스는 뜬다(`visible_ui=true`·`metal_frames_drawn=3`) |
| 창 잡기 | **창 0개**, `frontmost=false` |
| `screencapture` | **실패** — `could not create image from display` |
| `MARU_SCREENSHOT` 하네스 | 앱이 스스로 찍는 길이라 권한은 우회하지만, 그 앞의 **키 입력이 안 들어간다** |

원인은 권한이 아니라 **세션 종류**다 — 이 작업 환경은 `launchctl managername`이 **Background**이고
`/dev/console` 소유자가 `root`, 접속은 원격 tty다. GUI 로그인 세션에 붙어 있지 않으므로 창·키보드
포커스·화면 캡처가 **원리적으로** 없다. 자동화로는 이 표를 maru 안에서 못 잰다.

**그래서 이 값들이 제품에 그대로 적용되는지는 논증으로만 받쳐져 있다.** 근거는 이렇다.

1. maru는 붙여넣은 이미지를 **경로 문자열로 바꿔 bracketed paste로 보낸다**(`sendPasteText`, §4.2).
   tmux 프로브는 `paste-buffer -p`로 **같은 바이트**를 보냈다.
2. 마커를 만드는 것은 터미널이 아니라 **TUI 자신**이다. 입력이 같으면 결과가 같다.
3. 이스케이프(`escapeItems: true`)가 붙지만 경로가 `<UUID>.png`라 이스케이프할 문자가 없다.

**논증이 닿지 않는 항목은 §3.3(alt 화면 여부)이다.** 그것은 TUI가 터미널 능력을 보고 정할 수 있으므로
terminfo가 다르면 달라질 여지가 있다. **사람이 maru 앞에서 확인해야 하는 유일한 값**이다.

확인은 간단하다 — maru에서 Claude·Codex를 띄우고 이미지를 붙여넣은 뒤 ⑴ 입력창에 `[Image #N]`이 뜨는지,
⑵ 두 장이면 `#1 #2`인지, ⑶ 하나 지우고 다시 붙이면 `#1 #3`인지 보면 된다. 붙여넣은 직후라면
`$TMPDIR/maru-paste/`에 PNG가 생긴 것으로 **paste 경로가 실제로 탔다는 직접 증거**도 함께 잡힌다.
