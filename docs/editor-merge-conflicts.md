# 병합 충돌 해결 — 인라인과 3-way (계약)

**결정(2026-09-12 사용자): 두 방식 다 간다. 한 조각씩.**

`git merge`(또는 rebase·cherry-pick)가 같은 줄을 양쪽이 다르게 고친 것을 만나면 자동으로 끝내지 못하고
파일에 충돌 표시를 남긴다.

```
<<<<<<< HEAD
const timeout = 30;
=======
const timeout = 60;
>>>>>>> feature/slow-net
```

**「3-way」는 세 벌을 본다는 뜻**이다 — 내 것(ours) · 상대 것(theirs) · **둘이 갈리기 전의 원본**(base).
원본이 있어야 *누가 무엇을 바꿨는가*가 갈린다: 「내가 30으로 바꿨고 상대가 60으로 바꿨다」와 「원래
30이었고 상대만 바꿨다」는 다른 상황이고, 원본 없이는 그 둘이 같아 보인다.

## 1. 지금 무엇이 막혀 있는가 (실측 2026-09-12)

- SCM 패널에 **충돌 행이 있다**. `app_session/git.zig`가 그 행에 `DiffBase.conflict`를 붙여 비교를 연다.
- 그 기준은 `HEAD ↔ 작업트리`다(`dock_panel.DiffBase.conflict` — *"index에 stage 0이 없어 `:<경로>`를
  못 읽으므로 왼쪽을 HEAD로 잡는다"*). 그래서 **작업트리의 충돌 표시를 그대로 보여 준다.**
- **그런데 비교 뷰는 읽기 전용이다.** 보이기만 하고 **그 화면에서 고칠 수 없다** — 사용자는 같은 파일을
  다른 편집기 탭으로 따로 열어 `<<<<<<<` 를 손으로 지운다.
- **마커를 아는 코드가 어디에도 없다.** `docs/`·`src/` 전체에서 `<<<<<<<` 는 `git_backend.zig`의
  테스트 단언 하나뿐이다(「병합이 마커를 만들었다」를 확인하는 자리).

즉 **충돌을 «발견하는 것»까지는 앱 안에서 되고 «해결하는 것»에서 앱을 벗어난다.**

## 3. 데이터는 어디서 오는가

충돌 중 git 의 index 는 **stage 0 이 없고 stage 1·2·3 이 있다**(`git ls-files -u`가 그 셋을 낸다):

| stage | 무엇 | 읽는 법 |
| --- | --- | --- |
| 1 | **base** — 공통 조상 | `:1:<경로>` |
| 2 | **ours** — 지금 브랜치(HEAD) | `:2:<경로>` |
| 3 | **theirs** — 병합해 오는 쪽 | `:3:<경로>` |

**`DiffBase.conflict`의 주석은 「stage 0 이 없다」까지만 적고 있다** — 그 문장은 맞지만, 1·2·3 이
있다는 사실이 3-way 의 출처다. 기존 비교 경로가 이미 **rev + 경로**로 내용을 읽으므로
(`git_backend`의 diff 작업이 `left_rev`·`right_rev`를 든다) 세 stage 도 같은 기계로 읽는다.

**base 가 없을 수 있다**(양쪽이 파일을 각자 새로 만든 add/add 충돌 — stage 1 이 없다). 그때는 3-way 의
Base pane 을 비우고 **2-way 로 저하한다** — 없는 것을 지어내지 않는다.

## 4. 선례 — VSCode 는 두 방식을 다 준다

실측과 출처 URL은 [native-editor-multi-view.md §5.2·§5.4](plans/native-editor-multi-view.md)가 소유한다.
요지만 옮긴다.

| 방식 | 모양 | VSCode 문서의 서술 |
| --- | --- | --- |
| **인라인 마커** | 평범한 편집기에서 마커를 강조하고 그 자리에 **Accept Current / Accept Incoming / Accept Both** | *간단한 충돌에는 이쪽이 빠르다* |
| **3-way 병합 편집기** | 한 탭에 pane 넷(Incoming·Current·Result·Base). 충돌마다 체크박스, Result 는 직접 편집 | *복잡한 것에는 3-way 가 낫다* |

**둘은 경쟁이 아니라 층이다.** 그래서 순서가 정해진다 — 인라인이 먼저다(선행 하나만 필요하고 계약을
새로 세울 필요가 없다), 3-way 는 그 위에 선다.

## 5. 슬라이스 — 하나씩

### S1. 충돌 파일을 **편집 가능하게** 여는 길 — **섰다(2026-09-12)**

**그 전에는 충돌 행을 누르면 읽기 전용 비교만 열렸다.** 해결하려면 편집 가능한 편집기가 필요하다.

- 충돌 행에서 **편집기 탭으로 여는 길**을 만든다. 비교를 여는 길은 **그대로 둔다** — 「무엇이
  충돌했나」를 보는 것과 「고치는 것」은 다른 일이고, `editor-surface-dock.md`가 비교 기준을
  이미 소유한다.
- **두 길이 같은 행에 붙는다.** 어느 것이 기본인지는 §7 미결이었고, **기본 클릭은 비교 그대로**로
  정했다(2026-09-12) — 이미 있는 동작을 뺏으면 「훑어본다」가 사라진다. 편집기는 **행 호버에 뜨는
  동작 버튼**이 연다.
- 파일은 작업트리의 그 파일이므로 **평범한 편집기가 그대로 편집한다**(권한이 읽기 전용이 아닌 한).
  새 문서 모델이 필요 없다.

**선 모양**:

| 자리 | 무엇 |
| --- | --- |
| `scm_view.RowAction.resolve` | 충돌 행의 동작. **스테이지 어휘가 아니다** — `git_write_command.kindForRow`가 `null`을 내고, 섹션 머리 줄의 일괄 동작도 이 값을 세지 않는다(「모두 해결」은 없는 동작이다) |
| `→`(`icons.arrow_right`) | 그 버튼의 글리프. `+`/`−`는 「그 행이 다른 그룹으로 옮겨 간다」를 뜻하는데 이 동작은 **아무 그룹도 안 바꾼다** — 같은 어휘로 적으면 스테이지로 읽힌다 |
| `git.openEditorForScmRow` | 여는 함수. 루트 밖 경로·하위 모듈 거부는 **비교 경로와 같은 판정**이고, 여는 일 자체는 탐색기가 쓰는 검증 경로(`openFilePanelPathAs`)를 그대로 탄다(새 문서 모델 없음) |
| **종류는 `.text`로 못박는다** | 확장자 분류를 그대로 쓰면 `.md`·`.svg`가 기본 모드 `.read`(렌더된 화면)로 열리는데 **거기에는 마커가 안 보인다**(실측 2026-09-12) — 고치러 연 화면이 고칠 것을 감춘다. 이미지·미디어·PDF·이진 확장자는 글로 못 고치므로 **열지 않고 말한다** |
| `git_conflict_not_editable`·`git_conflict_open_failed` | 이진 파일이라 편집기가 없는 경우와 못 연 경우를 **가른다**(§3.8 — 저하는 말한다) |

**관측점**: 그 길로 연 Term 이 `kind == .editor` 이고 `editor_doc.file.read_only == false` 다
(읽을 수 없는 파일 — UTF-8 아님·상한 초과 — 만 CM6 텍스트 편집기로 떨어지고, 그쪽도 편집 가능하다).
판정자 `SCMC1`(published tree의 버튼 rect에 포인터 → intent → 제품 핸들러 → 편집기 Term)과
`SCMC2`(같은 행의 두 길이 서로를 안 뺏는다), `SCMC3`(거부하는 넷 + 마크다운이 원문으로 열린다),
Chrome Lab 시나리오 `scm-conflict-hover`가 이것을 든다.

**여기서 실측한 것**: 그 전의 골든 case `scm-conflict-no-action`은 **충돌 행의 동작을 증언하지
못했다** — 쓰던 캡처(`scm-row-hover`)가 호버하는 것이 **다른 행**이라, 충돌 행의 동작 값을 무엇으로
바꿔도 그 crop은 똑같았다. 「충돌 행에는 동작이 없다」를 지킨다고 믿은 동안 그 축은 비어 있었다.

### S1.5. 인라인 위젯 행 — «문서 줄이 아닌 행» — **섰다(2026-09-13)**

**S2 의 동작을 어디에 그릴지가 정해지면서(§7 ②) 이 조각이 생겼다.** VS Code 는 충돌 구간 **위**에 별도
줄을 띄우고 거기에 `Accept Current / Incoming / Both` 를 놓는다. 우리에게는 그런 행이 없다.

**지금 무엇이 없는가**(실측 2026-09-12):

- `visual_map.VisualRow` 는 `line: u32` 를 **필수**로 든다(`src/chrome/ui/visual_map.zig:149`). 모든
  시각 행은 문서 줄에서 나오고, 랩은 한 줄을 여러 행으로 **나눌** 뿐 행을 **더하지** 않는다.
- 편집기의 `props.lines` 는 **실제 문서**다. 거기에 행을 끼우면 byte offset 매핑이 통째로 어긋난다.
  비교 뷰가 짝을 맞추려고 빈 행을 넣을 수 있는 것은 그쪽 `lines` 가 **합성된 배열**이기 때문이다.
- 그 축을 지나는 참조는 **14 개 파일 262 곳**이다(`frame` 101 · `editor` 64 · `diff_frame` 27 ·
  `main` 16 · `hit` 11 · `gutter` 10 · `app_session` 9 · `scrollbar` 7 · 나머지 넷).

**그런데 절반은 이미 있다.** 「줄 번호를 안 그리는 행」이라는 개념이 **랩 이어짐으로 이미 서 있다**:
`VisualRow.showsLineNumber()` 가 `piece == 0` 하나로 그 규칙을 소유하고(`visual_map.zig:191`),
gutter 는 번호와 접힘 표식 **둘 다** 그 술어만 본다(`gutter.zig:265`·`271`). 그리고 비교 본문은
「번호가 없는 행」을 이미 다룬다 — `rowsForVisual` 의 `numbers` 표가 `null` 을 받고, 그 주석이
*"없는 줄에 번호를 붙이면 거짓이다"* 라고 적어 둔 자리다.

**그래서 계약은 이렇게 좁힌다.**

| 결정 | 왜 |
| --- | --- |
| 위젯 행도 **`line` 을 든다** — 자기가 붙는 **앵커 줄**이다 | `line` 을 옵셔널로 바꾸면 262 곳이 전부 **결정 지점**이 된다. 앵커를 들면 「행 → 줄」을 읽는 자리는 계속 유효한 값을 받는다(스크롤·검색 표식·접힘 판정이 그 축이다) |
| **`kind`(`text`\|`widget`)를 새로 둔다**. `showsLineNumber()` 는 위젯에 `false` | 번호·접힘 표식이 **이미 그 술어 하나**만 보므로, gutter 는 한 줄도 안 고쳐진다 |
| 위젯 행은 **`props.lines` 에 안 들어간다** | 문서는 그대로다. content 가 행을 **더 내는** 것이지 줄을 더 내는 것이 아니다 — byte offset 매핑을 안 건드린다 |
| 클릭은 **offset 을 내지 않는다** | `hit.bodyPoint` 가 위젯 행에서 문서 좌표를 만들어 내면 **없는 자리**를 가리킨다. 위젯 행의 클릭은 「이 위젯의 이 동작」이다 |
| caret 은 위젯 행에 **서지 않는다** | 위아래로 **지나간다**. 서면 「거기서 타이핑하면 어디에 들어가나」가 답이 없다 |
| 세로 계산은 위젯 행을 **센다** | `visible_rows`·스크롤 상한·스크롤바 총 길이가 안 세면 화면 아래가 그만큼 잘린다 |

**하지 않는 것**: 확장용 일반 위젯 API 를 지금 만들지 않는다. 소비자가 충돌 마커 **하나**뿐이고,
그 하나를 세우기 전에 일반형을 정하면 [§3.8 의 규율](native-editor-visual-mapping.md)과 반대로
**쓰이지 않는 축**을 계약에 넣게 된다.

**관측점**: 위젯 행이 있는 문서에서 ⑴ 줄 번호가 **건너뛰지 않는다**(그 행에 번호가 없다) ⑵ caret 을
위아래로 옮기면 위젯 행을 **지나간다** ⑶ 그 행을 클릭해도 caret 이 안 움직인다 ⑷ 문서 끝까지
스크롤하면 마지막 줄이 보인다(위젯 행만큼 잘리지 않는다) ⑸ 랩·접힘과 섞어도 ⑴~⑷ 가 유지된다.

**섰다(2026-09-13).** 판정자 `WID1`~`WID10`(`editor_view/frame.zig`·`hit.zig`)과 Chrome Lab
시나리오 `editor-widget-row` + 골든 둘이 이것을 든다. 구현하며 **계약이 말하지 않았던 것 셋**이
드러났다:

| 드러난 것 | 정한 것 |
| --- | --- |
| `line_widgets` 의 **축** | `lines` 와 같은 축, 즉 **보이는 줄** 기준이다(`line_colors`·`folds` 와 같다). 그래서 접힘은 **호출자의 일**이다 — 접으면 위젯 표도 함께 다시 투영해야 하고, 그것이 관측점 ⑸ 의 「접힘」 쪽 답이다 |
| **스크롤 정지 자리** | `first_piece` 는 위젯 행을 **포함해** 센다. 그래서 위젯 행에서도 화면이 멈출 수 있다 — 「그 줄과 함께만 움직인다」로 두면 세로 축의 단위가 둘이 되어 문서 끝에서 어긋난다 |
| caret 이 위젯을 **지나가는** 이유 | 새로 막은 것이 아니다. caret 은 byte offset 이고 세로 이동은 문서 줄 사이를 도는 계산이라, **구조적으로** 위젯 행에 설 자리가 없다. 클릭만 막으면 된다(`hit.bodyPoint` → `null`) |

**아직 안 한 것**: `app_session` 쪽 세로 계산(`piecesOfLine`)은 위젯 표를 **아직 안 본다**(생산자가
없으므로 0 을 넘긴다). **S2 의 첫 요구사항이 그것을 잇는 일이다** — 안 이으면 위젯이 있는 줄에서
스크롤과 화면이 갈린다. 그 자리에 같은 문장을 주석으로 남겼다.

### S2. 인라인 충돌 마커 — 인식과 고르기 — **섰다(2026-09-13)**

- **마커를 구간으로 인식한다**: `<<<<<<< ` / `||||||| `(diff3 스타일의 base) / `======= ` /
  `>>>>>>> `. **diff3 을 빠뜨리지 않는다** — `merge.conflictStyle = diff3`·`zdiff3` 이면 base 구간이
  끼고, 그것을 모르면 base 를 «내 것»의 일부로 읽어 Accept 가 엉뚱한 것을 남긴다.
- **줄 머리에서만 인식한다.** 문자열·주석 안의 같은 글자를 마커로 읽으면 멀쩡한 파일이 충돌로 보인다.
  git 자신이 줄 머리 기준으로 쓴다.
- 그 구간을 **강조**하고 **구간 위 위젯 행**(S1.5)에 동작을 붙인다: **Accept Current · Accept Incoming ·
  Accept Both**. 자리는 VS Code 그대로다(§7 ② — 사용자 결정 2026-09-12).
  「Ignore」는 «손으로 고친다»와 같으므로 두지 않는다 — 편집기에서 그냥 고치면 된다.
- **동작은 편집 하나다.** 고른 결과로 그 구간을 대체하는 **한 번의 편집**이고, 그래서 **되돌리기 한
  번에 풀린다**(§3.3 — 같은 묶음). 여러 편집으로 쪼개면 사용자가 여러 번 되돌려야 한다.
- **마커가 남아 있는 동안은 그 사실을 말한다**(§2.2 저하 자리와 같은 부류). 조용히 두면 사용자가 마커를
  남긴 채 커밋한다 — `editor-surface-dock.md`가 `+`를 두지 않는 이유로 든 바로 그 사고다.

**관측점**: 인식한 구간 수, 동작 뒤의 구간 수(하나 줄었는가), 되돌리기 한 번에 복원되는가.

**선 모양**:

| 자리 | 무엇 |
| --- | --- |
| `session/editor/conflict.zig` | 구간 인식. **순수 계산**이라 중립에 산다 — `markerOf`(줄 머리·정확히 일곱 자·뒤는 공백이나 줄 끝) · `scan` · `hasUnresolved` |
| `editor.ensureConflicts` | 문서를 훑어 **보이는 줄** 축의 위젯·밴드·동작 구간 표를 만든다. 접힌 구간의 위젯은 안 세운다(누를 수 없는 자리에 뜨면 엉뚱한 줄 위다) |
| `editor.acceptConflict` | 고른 대로 **한 번의 편집**(`applyEditAsOne`) — 되돌리기 한 번에 마커까지 돌아온다 |
| `editor.conflictActionAtPoint` | 좌표 → 어느 이름인가. **열 구간을 그리는 쪽과 같은 함수가 만든다**(`buildConflictLabel`) — 따로 재면 폰트·언어가 바뀌는 날 누르는 자리와 글자가 갈린다 |
| `saveDocument` | 마커가 남았으면 **말한다**(막지는 않는다 — 반쯤 고치다 멈추는 것은 정당한 중간 상태다) |

**§7 ③ 의 답(2026-09-13)**: 마커 강조는 **배경 밴드 층**을 쓴다. 구문 색은 **전경**이라 구간 안의
코드가 그대로 읽히고, 그래서 색 층을 새로 만들 필요가 없었다. **칠하는 것은 마커 줄뿐이다** —
「현재 것」을 초록, 「들어온 것」을 빨강으로 칠하면 그것은 이미 답을 말하는 것이고, 들어온 쪽은
지워질 것이 아니라 **고를 후보**다. 지워야 할 기계 장치(마커 줄)에만 위험 계열을 깐다
(`RowBand.conflict_marker` → `danger_bg`).

**여기서 실측한 것**:

- **diff3 의 라벨은 낱말이 아니라 짧은 SHA 다**(`||||||| d7db4cc`). 임시 저장소에 진짜 `git merge` 를
  돌려 확인했고, 그 바이트를 그대로 판정자에 넣었다(`CFL9`) — 손으로 적은 모양만 검사하면 이런
  자리가 안 보인다.
- **커서가 없는 문서에서도 눌린다.** 편집 경로는 커서 집합을 통해 문서를 고치는데, 위젯을 누르는
  것은 **본문을 한 번도 안 누른 상태**에서 일어난다(파일을 열자마자 고르는 흐름). 커서가 없으면
  구간 머리에 놓는다 — 있으면 안 건드린다(CodeLens 를 누르는 것이 커서를 옮기는 동작은 아니다).

판정자 `CFL1`~`CFL9`(`app_session/editor.zig`)와 파서 판정자 일곱(`session/editor/conflict.zig`),
Chrome Lab 시나리오 `editor-conflict` + 골든 둘이 이것을 든다. **Lab 픽스처의 밴드·위젯 표는 손으로
안 적는다** — 제품과 **같은 파서**가 만든다(손으로 적으면 파서가 망가져도 그림은 예쁘게 나온다).

### S3. 3-way 병합 편집기 — **두 조각으로 가른다(2026-09-14)**

**왜 가르나.** 계약 §7 ④(「어느 표면에 둘까」)가 아직 열려 있고 **그 답이 화면 쪽 일의 크기를
정한다**. 그런데 **stage 를 읽어 오는 일은 그 답과 무관하다** — 새 Term 이든 비교 Term 의 다른
모드든, 원본·내 것·들어온 것 셋을 손에 쥐어야 시작한다. 그래서 데이터를 먼저 세운다.

| 조각 | 내용 | ④ 에 걸리나 |
| --- | --- | --- |
| **S3a** | git 의 **stage 1·2·3** 을 읽어 온다(`:1:`·`:2:`·`:3:`). base 가 없으면 **2-way 로 저하** — **섰다**(2026-09-14) | 아니다 |
| **S3b** | pane 넷 화면 | **그렇다** |

**S3b 의 크기를 재 두었다**(§7 ④ 를 답할 때 쓴다). 비교 뷰는 좌우 **두 벌**을 필드 이름에
하드코딩해 두었다 — `_left`/`_right` 짝이 13 개다(`diff_hit_rows_left/_right`·`first_col_right`·
`scrollbar_right` …). pane 이 넷이 되면 그 방식은 배열로 바뀌어야 하고, 그것이
[multi-view §3](plans/native-editor-multi-view.md) 가 적은 **뷰 상태 약 35 개 + 입력 라우팅 약
50 곳**이다. 그리고 비교 뷰는 좌우가 세로를 **일부러 공유**하는데(§3.5) 3-way 는 정반대다 —
계약이 「비교 뷰 기계를 재활용하지 않는다」고 적은 이유가 그것이다.

#### S3a. stage 1·2·3 을 읽는다

- **출처는 §3 의 세 stage 다**: `:1:<경로>`(공통 조상) · `:2:<경로>`(현재 것) · `:3:<경로>`(들어온 것).
  `git show` 가 그 지정자를 받는다 — 우리가 이미 `HEAD:` 와 `:` 를 읽는 그 길이다.
- **rev 자리에 임의 문자열을 안 넣는다.** stage 번호는 우리가 고정한 **리터럴**이라, 커밋 blob 이
  hex 만 받게 막아 둔 것과 같은 성질을 자동으로 갖는다(§6 심층 방어).
- **base 가 없는 것은 «정상»이다**(add/add 충돌 — 양쪽이 같은 경로를 **새로** 만들었다). 그때
  stage 1 이 아예 없고 git 이 실패하는데, 그것을 실패로 접으면 그 충돌을 아예 못 연다. 루트 커밋의
  부모 blob 을 **왼쪽이 없다**로 읽는 것과 같은 판단이다.
- **진짜 실패는 `:2:` 와 `:3:` 을 둘 다 못 읽은 때**뿐이다 — 보여 줄 것이 없다.

**관측점**: 실제 `git merge` 로 만든 충돌에서 세 판이 오고(add/add 면 둘), 그 내용이 각각
「원본·현재 것·들어온 것」이다.

##### S3a 를 세우며 «계약이 배운 것» (2026-09-14)

구현하며 실측으로 갈린 것들이다. 넷 다 **계약이 몰랐던 갈림**이고, S3b 가 그대로 물려받는다.

- **「없는 조상」과 「빈 조상」은 다르다.** add/add 는 `:1:` 이 **아예 없지만**, 조상이 **빈 파일**인
  충돌은 stage 1 이 **빈 blob**(`e69de29…`)으로 멀쩡히 실린다(실측). 둘을 **길이로 가르면** 빈 조상이
  「없음」으로 읽혀 3-way 가 근거 없이 2-way 로 저하한다 — 그래서 「무엇을 읽었나」를 내용과 **따로**
  든다(`conflict.StageSet`). 저하 판정은 그 타입 하나가 소유한다(두 자리에 적으면 한쪽만 바뀐다).
- **rename 의 옛 경로는 stage 에 쓰지 않는다.** 왼쪽이 HEAD 인 기준은 옛 경로로 읽어야 blob 이 잡히지만,
  충돌 stage 는 **지금 경로**에 실린다. 옛 경로로 읽으면 세 판이 전부 안 잡혀 충돌을 **못 연다**.
- **`../` 지정자는 git 이 먼저 거절한다**(`fatal: '../f.txt' is outside repository`, 실측). 우리 쪽
  경로 방어는 그대로 두지만(안 보내는 편이 낫다), 이 갈래에서 그것은 **심층 방어**이지 유일한 방어가
  아니다 — 적대적 검증에서 **등가 변이**로 기록했다.
- **상한(16 MiB)에서 잘린 판은 「잘렸다」를 달고 온다.** 세 판을 갈래 셋으로 풀어 읽으면 그 표시를
  옮기는 자리도 셋이 되어 **서로 덮어 준다**(변이 하나를 지워도 나머지 둘이 세운다) — 읽기를 한
  자리로 모아 그 변이가 존재할 곳을 없앴다.

**하네스**(왜 여기 적나): 제품의 git **쓰기 어휘**는 `init`·`merge` 를 **일부러** 안 갖는다(닫힌
어휘가 그 모듈의 계약이다). 그래서 「진짜 충돌 저장소」를 만드는 픽스처는 제품 어휘를 늘리는 대신
**판정자 안에서** 러너를 직접 부른다(`zig build test-merge-stages-e2e`). 이 하네스가 없던 동안
워커의 세 판 배선은 **통째로 무판정**이었다.

#### S3b. pane 넷 화면 — **새 `merge` Term 위에**(§7 ④, 2026-09-14)

- **pane 넷**: Current(`:2:`) · Result(**편집 가능**) · Incoming(`:3:`) · Base(`:1:`, 선택).
- 출처는 §3 의 세 stage 이고(**S3a 가 이미 읽어 온다**) **Result 는 작업트리 파일**이다 — 저장이 곧 해결이다.
- **base 가 없으면 Base pane 을 비우고 2-way 로 저하한다**(§3) — 그 판정도 **S3a 가 이미 낸다**
  (`conflict.StageSet.degradesToTwoWay()`).
- **비교 뷰 기계를 재활용하지 않는다**(§7 ④ 의 답이 그것이다). 비교 뷰는 좌우가 세로를 **일부러**
  공유하는데(§3.5) 3-way 는 정반대다.

**다시 조각으로 가른다.** 화면 넷을 한 번에 세우면 「Term 이 서지도 않았는데 그림을 그리는」 상태가
길게 남는다.

| 조각 | 내용 | 화면이 달라지나 |
| --- | --- | --- |
| **S3b-1** | **병합 모드를 세운다** — 충돌 행이 `rt.editor_merge` 를 든 편집기 Term 을 열고·닫는다. 세 판은 S3a 가 읽어 싣는다. 그림은 아직 편집기 하나(Result) | 조금(탭 라벨이 갈린다) |
| **S3b-2** | pane 넷 **배치와 그리기**(읽기 전용 셋 + Result) | **그렇다** |
| **S3b-3** | Result 편집·저장 = 해결. S2 의 「고르기」를 pane 에서 부른다 | **그렇다** |

##### S3b-2. pane 넷을 «어떻게» 놓나 (2026-09-14)

- **배치**: 위에 세 열 `Current(:2:) | Result | Incoming(:3:)`, 아래에 `Base(:1:)` 한 띠.

  ```
  ┌──────────┬──────────┬──────────┐
  │ Current  │  Result  │ Incoming │
  │  (:2:)   │  (편집)   │  (:3:)   │
  ├──────────┴──────────┴──────────┤
  │ Base (:1:) — 조상 없으면 사라진다 │
  └────────────────────────────────┘
  ```

  **Result 가 가운데인 이유**: 고르는 방향이 양쪽에서 가운데로 온다. 끝에 두면 한쪽 판이 화면을
  가로질러 반대편으로 가야 한다.

- **조상이 없으면 Base 띠가 «사라진다»**(add/add — 세 열이 높이를 다 쓴다). 비워 두지 않는 이유는
  빈 띠가 「읽는 중」과 구별되지 않기 때문이다. 그 판정은 **S3a 가 이미 낸다**
  (`conflict.StageSet.degradesToTwoWay()`) — 여기서 길이로 다시 재지 않는다.

- **세로는 각자다.** 비교 뷰는 좌우가 세로를 **일부러 공유**하지만(§3.5 — 같은 줄이 같은 높이에
  서야 비교가 성립한다), 세 판은 줄 수도 내용도 서로 다르다. 한쪽을 따라가면 나머지가 엉뚱한 곳을
  본다. **스크롤 동기가 필요한가는 §7 ⑥ 으로 연다** — 관례를 인용해 답할 문제이지 여기서 연역할
  것이 아니다.

- **입력은 Result 만 받는다**(이 조각에서). 나머지 셋의 클릭은 **아무 일도 안 한다** — 그 pane 의
  caret·선택·검색은 S3b-3 이다. 지금 아무 규칙도 안 두면 Base pane 을 눌렀을 때 **Result 문서의
  caret 이 움직인다**(같은 Term 의 히트테스트가 통째로 하나이기 때문이다).

- **좁으면 접는 순서**: `Result` > `Current`·`Incoming` > `Base`. 최소 폭에 못 미치는 pane 은
  **안 그린다**(글자가 한 칸씩 잘린 세 열보다 두 열이 읽을 수 있다).

- **아직 안 왔거나 못 읽었으면 한 줄로 말한다** — 비교 뷰가 네 상태를 말하는 그 규율이다(§7).
  조용한 빈 화면을 남기지 않는다.

- **`merge_frame` 은 컴포넌트 층에 둔다.** 비교 뷰가 그렇게 서 있는 이유가 그대로 걸린다:
  제품과 Chrome Lab 이 **같은 함수**를 불러야 캡처가 제품을 예고한다. 한쪽만 조합을 들면 골든은
  초록인데 제품만 틀린 상태가 만들어진다(편집기 배경 층에서 실제로 그랬다).

  **그래서 S3b-2 는 PNG 캡처가 나온다** — S3b-1 의 탭 라벨과 달리 이 조각은 Lab 이 그리는
  `editor_view` 안에 산다.

##### S3b-3. 다시 셋으로 가른다 — 계획을 «공격해» 보고 (2026-09-15)

처음 계획(「고르기 버튼이 맞는 자리에서 잡히나 판정자」→ caret → pane 쪽 고르기)을 코드로 공격했더니
**셋이 틀렸다**.

- **버튼이 잡히나가 아니라, 버튼이 «없다».** `merge_frame.Pane` 에 위젯·밴드 필드가 없어 병합
  갈래가 Result 에 줄·색·위치·caret 만 넘긴다 — pane 넷이 뜨는 순간 **S2 가 세운 해결 UI 가
  사라진다**(실측). 첫 조각은 판정자가 아니라 **복구**다.
- **pane 쪽 고르기는 대응표를 요구한다.** Current pane 의 어느 줄이 Result 의 어느 충돌 구간인지는
  §7 ⑥ 이 말한 **그 diff 대응표**가 있어야 안다. VS Code 도 입력 pane 의 체크박스를 대응표로 자리
  잡는다. 그래서 이 항목은 대응표 조각 **뒤**로 간다.
- **세 판의 caret 은 미결이었다.** 선례가 답한다 — 비교 뷰는 읽기 전용에도 caret 을 세웠다
  (키보드로 읽는다, `2763a3436`). 같은 판단을 따른다.

| 조각 | 내용 | 화면이 달라지나 |
| --- | --- | --- |
| **S3b-3a** | Result pane 이 S2 의 **위젯 행·밴드를 다시 그린다** + `conflictActionAtPoint` 에 병합 가드(Result 밖 클릭 무시) | **그렇다** — 사라졌던 「현재 것 / 들어온 것 / 둘 다」가 돌아온다 |
| **S3b-3b** | 세 판에 caret 이 선다(키보드로 읽는다) | 그렇다 |
| **S3b-3c** | pane 쪽 고르기(VS Code 체크박스 상당) — **대응표 뒤** | 그렇다 |

**S3b-1 이 먼저인 이유**: pane 을 그리려면 **그릴 것을 든 Term** 이 먼저 있어야 한다 — 세 판을
누가 들고, 언제 버리고, 탭이 무엇이라 부르는지가 정해지기 전에 배치부터 하면 그 답들이 그리는
코드 안으로 숨는다. 그리고 그 조각은 **혼자서도 쓸모가 있다** — 충돌 파일을 여는 전용 모드가
생기고, 그 안은 지금의 편집기 그대로다(S1·S2 가 이미 선 자리).

**S2 는 S1.5 가 선 뒤에 착수한다** — 동작을 놓을 행이 없으면 인식만 해 놓고 부를 길이 없다.

**S3 은 S2 가 선 뒤에 착수한다** — S2 가 「마커 구간 인식」과 「고르기 동작」을 세우고, S3 은 그것을
다른 배치로 보여 주는 일이다. 순서를 뒤집으면 인식 로직이 pane 배치와 엉킨다.

## 6. 이 계약이 «하지 않는» 것

- **`git merge`·`rebase` 를 대신 실행하지 않는다.** `editor-surface-dock-write.md`가 `push`·`pull` 을
  *"사용자가 엔터를 친다"* 로 둔 것과 같은 판단이다 — 남의 저장소를 바꾸는 일이 걸린다.
- **`git add`(해결 표시)를 자동으로 하지 않는다.** 마커가 사라지면 그 파일은 평범한 `M`이 되고 `+`가
  생긴다(§2 사후 조건). 스테이지는 사용자가 누른다.
- **충돌을 자동으로 고르지 않는다**(`ours`/`theirs` 일괄 적용 같은 것). 그것은 git 명령이 이미 하는
  일이고, 편집기가 조용히 하면 사용자가 무엇을 잃었는지 모른다.

## 7. 미결 — 착수할 때 답해야 할 것

1. ~~**충돌 행의 기본 동작**~~ — **답했다(2026-09-12)**: 기본 클릭은 **비교 그대로**, 편집기는 행 호버의
   동작 버튼이 연다(S1). 이미 있는 동작을 뺏으면 「무엇이 충돌했나」를 훑는 길이 사라진다.
2. ~~**동작을 무엇으로 부를까**~~ — **답했다(2026-09-12)**: **VS Code 그대로, 충돌 구간 «위»에 뜨는 별도
   줄**이다(사용자 결정). gutter 표식·커맨드 팔레트·chord 는 고르지 않았다.

   **그 답이 조각을 하나 낳았다.** 우리 편집기에는 «문서 줄이 아닌 행»이 없다 — `VisualRow` 는 `line` 을
   **필수**로 들고(`src/chrome/ui/visual_map.zig:149`) 모든 행이 문서 줄에서 나온다. 그래서 **S1.5** 가
   S2 앞에 선다(§5).
3. ~~**마커 강조를 구문 강조와 어떻게 섞을까**~~ — **답했다(2026-09-13)**: 겹치지 않는다. 강조는
   **배경 밴드**이고 구문 색은 **전경**이다. 그리고 칠하는 것은 **마커 줄뿐**이다(§5 S2).
4. ~~**3-way 를 어느 표면에 둘까**~~ — **답했다(2026-09-14)**: **비교 뷰를 재활용하지 않는다**
   (사용자 결정). 3-way 는 자기 Term 이고, 그 Term 은 **편집기 Term 의 «모드»** 다 —
   `kind == .editor` + `rt.editor_merge != null`.

   **왜 비교 뷰가 아닌가.** 비교 뷰를 pane N 개로 일반화하면 좌우를 필드 이름에 하드코딩한 자리
   (`_left`/`_right` 짝 13 개)가 전부 배열이 되고, [multi-view §3](plans/native-editor-multi-view.md)
   가 잰 **뷰 상태 약 35 개 + 입력 라우팅 약 50 곳**이 그대로 걸린다. 게다가 비교 뷰는 좌우가 세로를
   **일부러 공유**하는데(§3.5) 3-way 는 정반대라, 같은 기계에 두면 그 규칙이 모드마다 갈린다 —
   **이미 서 있는 기능이 같이 흔들린다.**

   **왜 새 `SurfaceKind` 가 아닌가 — 수치를 고쳐 적는다(2026-09-14).** 처음에는 「종류를 더하는 값은
   싸다」고 적었다. `SurfaceKind` 에 값을 하나 넣고 **컴파일러가 거절하는 자리**를 전부 채우면
   **8 줄 · 4 파일**이고 `check-targets` 와 macOS 앱 호스트가 둘 다 통과한다 — 그것은 **사실이지만
   절반이다.** 컴파일러가 **안 잡는** 자리가 따로 있다:

   > `kind == .editor` / `kind != .editor` 술어가 **제품 코드 80 곳**이다(실측 2026-09-14).
   > 전부 같은 질문을 한다 — 「이 Term 이 편집기 문서를 들고 있나」. 종류를 나누면 그 80 곳이
   > 각각 「merge 도 해당되나」를 답해야 하고, `==` 비교라 **컴파일러가 한 곳도 안 알려 준다.**

   **이 저장소에 이미 선례가 있다**: **비교 뷰도 종류가 아니다**(`kind == .editor` +
   `rt.editor_diff != null`). 그래서 그 80 개 술어를 **한 줄도 안 건드리고** 섰고, 입력·찾기·저장·
   teardown 이 전부 그대로 돌았다. 3-way 도 같은 자리에 선다.

   **대가(정직하게)**: 컨트롤 플레인 wire 에서 이 표면은 계속 `kind = "editor"` 다
   ([control-plane.md](control-plane.md)). 외부 소비자가 「이건 병합 표면이다」를 구별해야 할 이유가
   **실제로 생기면** 그때 종류로 승격하고, 그 시점에 위 80 곳을 **단일 소유 술어**(예:
   `hasEditorDocument()`)로 바꾼다. 그 이유가 없는 동안 열거를 넓히는 것은 **값을 안 주고 비용만
   치르는 일**이다.

5. **파일이 여럿 충돌했을 때의 이동**: 「다음 충돌 파일」이 필요한가. **아직 열려 있다** — S3b 를
   세운 뒤에 답한다(그 전에는 「이동」이 무엇 사이의 이동인지가 안 정해진다).
6. **세 판의 스크롤을 맞출까** — **관례를 실측했다(2026-09-14)**. VS Code 1.137.0 을 내려받아 실제
   3-way 병합 편집기를 띄우고(`--merge input1 input2 base result`, 창 제목 `Merging: result.txt`),
   그 제품이 선적한 동작을 읽었다. **답은 「맞춘다」이고, 맞추는 방식이 두 가지다.**

   | 축 | VS Code 가 하는 일 |
   | --- | --- |
   | **가로** | 네 pane 이 **무조건 같이** 움직인다(대응표 없이 `scrollLeft` 를 그대로 복사) |
   | **세로 — 잠금** | 짝에 따라 `scrollTop` 을 **픽셀 그대로** 복사한다 |
   | **세로 — 환산** | 잠금이 아닌 짝은 **diff 대응표로 옮긴다**(아래) |

   **무엇이 픽셀로 잠기나**(배치에 따라 갈린다 — 그 제품의 배치는 `mixed` 와 `columns` 둘이다):

   - `input1 ↔ input2`: **언제나** 잠긴다(둘 다 「들어온 판」이라 같은 축이다).
   - `result ↔ input*`: **columns 배치일 때만** 잠긴다.
   - `base ↔ input*`: **mixed 배치이고 base 가 위에 있지 않을 때만** 잠긴다.

   **환산은 「보이는 첫 줄」을 기준으로 한다.** 잠기지 않은 짝은 diff 대응표(`input1↔result`,
   `base↔input1` …)로 **저쪽의 대응 줄**을 찾고, 그 구간 안에서의 **비율**을 그대로 옮긴다 —
   보이는 첫 줄이 그쪽 구간의 30 % 지점이면 저쪽도 대응 구간의 30 % 지점에 놓는다. 즉 **문서 줄도,
   충돌 구간도 아니라 «diff 대응 구간 안의 비율»** 이 축이다.

   **우리에게 뜻하는 것**: 이 답은 **세 판 사이의 diff 대응표**를 요구한다 — 지금 우리에게는 없다
   (S3a 는 세 판의 **바이트**만 읽어 온다). 그래서 이 미결은 「맞출까」가 아니라 **「그 대응표를 언제
   만들까」**로 바뀐다. 붙일 자리는 S3b-3 이거나 그 뒤의 독립 조각이고, 그 전까지 pane 은 각자
   세로를 갖는다(S3b-2 가 그렇게 섰다).

   ⚠️ **화면 픽셀로는 못 봤다.** 이 기계에서 `screencapture` 가 화면 접근 권한이 없어
   (`could not create image from display`) 캡처 오라클을 못 썼고, Electron 의 손쉬운 사용 트리도
   편집기 본문 글자를 안 내줬다. 그래서 근거는 **그 제품이 선적한 코드의 동작**이다 — VS Code 는
   MIT 라 이 저장소가 소스 열람을 금지한 copyleft 레퍼런스(GNOME vte·kitty)가 아니고
   (`project-rules.md`), 읽은 것은 **동작**이며 코드 표현은 옮기지 않았다.
