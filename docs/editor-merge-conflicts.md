# 병합 충돌 해결 — 인라인과 3-way (계약)

**결정(2026-09-12 사용자): 두 방식 다 간다. 한 조각씩.**

`git merge`(또는 rebase·cherry-pick)가 같은 줄을 양쪽이 다르게 고친 것을 만나면 자동으로 끝내지 못하고
파일에 충돌 표시를 남긴다.

```
<<<<<<< HEAD
const timeout = 30;
=======
const timeout = 60;
>>>>>>> feature/slow-net
```

**「3-way」는 세 벌을 본다는 뜻**이다 — 내 것(ours) · 상대 것(theirs) · **둘이 갈리기 전의 원본**(base).
원본이 있어야 *누가 무엇을 바꿨는가*가 갈린다: 「내가 30으로 바꿨고 상대가 60으로 바꿨다」와 「원래
30이었고 상대만 바꿨다」는 다른 상황이고, 원본 없이는 그 둘이 같아 보인다.

## 1. 지금 무엇이 막혀 있는가 (실측 2026-09-12)

- SCM 패널에 **충돌 행이 있다**. `app_session/git.zig`가 그 행에 `DiffBase.conflict`를 붙여 비교를 연다.
- 그 기준은 `HEAD ↔ 작업트리`다(`dock_panel.DiffBase.conflict` — *"index에 stage 0이 없어 `:<경로>`를
  못 읽으므로 왼쪽을 HEAD로 잡는다"*). 그래서 **작업트리의 충돌 표시를 그대로 보여 준다.**
- **그런데 비교 뷰는 읽기 전용이다.** 보이기만 하고 **그 화면에서 고칠 수 없다** — 사용자는 같은 파일을
  다른 편집기 탭으로 따로 열어 `<<<<<<<` 를 손으로 지운다.
- **마커를 아는 코드가 어디에도 없다.** `docs/`·`src/` 전체에서 `<<<<<<<` 는 `git_backend.zig`의
  테스트 단언 하나뿐이다(「병합이 마커를 만들었다」를 확인하는 자리).

즉 **충돌을 «발견하는 것»까지는 앱 안에서 되고 «해결하는 것»에서 앱을 벗어난다.**

## 3. 데이터는 어디서 오는가

충돌 중 git 의 index 는 **stage 0 이 없고 stage 1·2·3 이 있다**(`git ls-files -u`가 그 셋을 낸다):

| stage | 무엇 | 읽는 법 |
| --- | --- | --- |
| 1 | **base** — 공통 조상 | `:1:<경로>` |
| 2 | **ours** — 지금 브랜치(HEAD) | `:2:<경로>` |
| 3 | **theirs** — 병합해 오는 쪽 | `:3:<경로>` |

**`DiffBase.conflict`의 주석은 「stage 0 이 없다」까지만 적고 있다** — 그 문장은 맞지만, 1·2·3 이
있다는 사실이 3-way 의 출처다. 기존 비교 경로가 이미 **rev + 경로**로 내용을 읽으므로
(`git_backend`의 diff 작업이 `left_rev`·`right_rev`를 든다) 세 stage 도 같은 기계로 읽는다.

**base 가 없을 수 있다**(양쪽이 파일을 각자 새로 만든 add/add 충돌 — stage 1 이 없다). 그때는 3-way 의
Base pane 을 비우고 **2-way 로 저하한다** — 없는 것을 지어내지 않는다.

## 4. 선례 — VSCode 는 두 방식을 다 준다

실측과 출처 URL은 [native-editor-multi-view.md §5.2·§5.4](plans/native-editor-multi-view.md)가 소유한다.
요지만 옮긴다.

| 방식 | 모양 | VSCode 문서의 서술 |
| --- | --- | --- |
| **인라인 마커** | 평범한 편집기에서 마커를 강조하고 그 자리에 **Accept Current / Accept Incoming / Accept Both** | *간단한 충돌에는 이쪽이 빠르다* |
| **3-way 병합 편집기** | 한 탭에 pane 넷(Incoming·Current·Result·Base). 충돌마다 체크박스, Result 는 직접 편집 | *복잡한 것에는 3-way 가 낫다* |

**둘은 경쟁이 아니라 층이다.** 그래서 순서가 정해진다 — 인라인이 먼저다(선행 하나만 필요하고 계약을
새로 세울 필요가 없다), 3-way 는 그 위에 선다.

## 5. 슬라이스 — 하나씩

### S1. 충돌 파일을 **편집 가능하게** 여는 길

**지금 충돌 행을 누르면 읽기 전용 비교가 열린다.** 해결하려면 편집 가능한 편집기가 필요하다.

- 충돌 행에서 **편집기 탭으로 여는 길**을 만든다. 비교를 여는 길은 **그대로 둔다** — 「무엇이
  충돌했나」를 보는 것과 「고치는 것」은 다른 일이고, `editor-surface-dock.md`가 비교 기준을
  이미 소유한다.
- **두 길이 같은 행에 붙는다.** 어느 것이 기본인지는 §7 미결이다.
- 파일은 작업트리의 그 파일이므로 **평범한 편집기가 그대로 편집한다**(권한이 읽기 전용이 아닌 한).
  새 문서 모델이 필요 없다.

**관측점**: 그 길로 연 Term 이 `kind == .editor` 이고 `editor_doc.file.read_only == false` 다.

### S2. 인라인 충돌 마커 — 인식과 고르기

- **마커를 구간으로 인식한다**: `<<<<<<< ` / `||||||| `(diff3 스타일의 base) / `======= ` /
  `>>>>>>> `. **diff3 을 빠뜨리지 않는다** — `merge.conflictStyle = diff3`·`zdiff3` 이면 base 구간이
  끼고, 그것을 모르면 base 를 «내 것»의 일부로 읽어 Accept 가 엉뚱한 것을 남긴다.
- **줄 머리에서만 인식한다.** 문자열·주석 안의 같은 글자를 마커로 읽으면 멀쩡한 파일이 충돌로 보인다.
  git 자신이 줄 머리 기준으로 쓴다.
- 그 구간을 **강조**하고 그 자리에 동작을 붙인다: **Accept Current · Accept Incoming · Accept Both**.
  「Ignore」는 «손으로 고친다»와 같으므로 두지 않는다 — 편집기에서 그냥 고치면 된다.
- **동작은 편집 하나다.** 고른 결과로 그 구간을 대체하는 **한 번의 편집**이고, 그래서 **되돌리기 한
  번에 풀린다**(§3.3 — 같은 묶음). 여러 편집으로 쪼개면 사용자가 여러 번 되돌려야 한다.
- **마커가 남아 있는 동안은 그 사실을 말한다**(§2.2 저하 자리와 같은 부류). 조용히 두면 사용자가 마커를
  남긴 채 커밋한다 — `editor-surface-dock.md`가 `+`를 두지 않는 이유로 든 바로 그 사고다.

**관측점**: 인식한 구간 수, 동작 뒤의 구간 수(하나 줄었는가), 되돌리기 한 번에 복원되는가.

### S3. 3-way 병합 편집기

- **pane 넷**: Incoming(theirs) · Current(ours) · **Result(편집 가능)** · Base(선택).
- 출처는 §3 의 세 stage 이고 **Result 는 작업트리 파일**이다 — 저장이 곧 해결이다.
- **비교 뷰 기계를 재활용하지 않는다.** [multi-view §3·§4](plans/native-editor-multi-view.md)가
  실측했듯 비교 뷰는 세로를 **일부러 공유**하고(§3.5) 이쪽은 정반대다. 그 문서가 Split in Group 에
  대해 적은 비용(뷰 상태 약 35개 + 입력 라우팅 약 50곳)이 여기에도 걸린다.
- **base 가 없으면 Base pane 을 비우고 2-way 로 저하한다**(§3).

**S3 은 S2 가 선 뒤에 착수한다** — S2 가 「마커 구간 인식」과 「고르기 동작」을 세우고, S3 은 그것을
다른 배치로 보여 주는 일이다. 순서를 뒤집으면 인식 로직이 pane 배치와 엉킨다.

## 6. 이 계약이 «하지 않는» 것

- **`git merge`·`rebase` 를 대신 실행하지 않는다.** `editor-surface-dock-write.md`가 `push`·`pull` 을
  *"사용자가 엔터를 친다"* 로 둔 것과 같은 판단이다 — 남의 저장소를 바꾸는 일이 걸린다.
- **`git add`(해결 표시)를 자동으로 하지 않는다.** 마커가 사라지면 그 파일은 평범한 `M`이 되고 `+`가
  생긴다(§2 사후 조건). 스테이지는 사용자가 누른다.
- **충돌을 자동으로 고르지 않는다**(`ours`/`theirs` 일괄 적용 같은 것). 그것은 git 명령이 이미 하는
  일이고, 편집기가 조용히 하면 사용자가 무엇을 잃었는지 모른다.

## 7. 미결 — 착수할 때 답해야 할 것

1. **충돌 행의 기본 동작**: 지금처럼 비교를 열까, 편집기를 열까. 둘을 어떻게 갈라 붙일까(클릭 vs 보조 동작).
2. **동작을 무엇으로 부를까**: 우리에게 CodeLens 가 없다. gutter 표식·본문 위 줄·커맨드 팔레트·chord 중
   무엇인가. 이것이 S2 의 가장 큰 미결이고, [key-input-and-shortcuts.md](key-input-and-shortcuts.md)와
   [configuration-input.md](configuration-input.md)가 chord 쪽을 소유한다.
3. **마커 강조를 구문 강조와 어떻게 섞을까**: 충돌 구간 안에도 코드가 있다. §5.3 의 색 층과 겹치는 자리다.
4. **3-way 를 어느 표면에 둘까**: 새 Term 종류인가, 비교 Term 의 다른 모드인가.
5. **파일이 여럿 충돌했을 때의 이동**: 「다음 충돌 파일」이 필요한가.
