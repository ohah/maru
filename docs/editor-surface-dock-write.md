# 에디터 Surface — 소스 컨트롤 쓰기·원격 (§3.6)

도크 소스 컨트롤 뷰가 **저장소를 바꾸는** 명령(stage/unstage/commit)과 **네트워크를 쓰는** 명령(fetch)의 단일 출처다.
읽기 명령의 계약은 [diff/git API](editor-surface-tooling.md) §6이 계속 소유하고, 화면 구조는
[도크 소스 컨트롤 뷰](editor-surface-dock.md) §3.5가 소유한다. 단계 순서는 [단계 계획](plans/scm-dock.md)에 있다.

> **왜 새 문서인가.** §6은 "읽기 전용"을 **전제**로 쓰인 계약이다(외부 프로세스 실행 차단·index 무접촉·네트워크 없음).
> 쓰기는 그 전제 중 셋을 의도적으로 뒤집으므로, 같은 문서 안에서 "다만 이 경우엔 아니다"를 덧붙이면 어느 규칙이 어느
> 명령에 걸리는지 아무도 못 읽는다. 규칙을 **명령 종류별로 갈라** 둔다.

## 1. 읽기와 쓰기는 다른 환경으로 돈다

같은 `git` 실행 파일을 쓰지만 **환경과 플래그가 다르다**. 한 헬퍼가 둘 다 만들지 않는다 — 조립 함수를 갈라 두면
"이 플래그가 정말 붙었나"를 테스트가 명령 종류별로 전수로 고정한다.

| 축 | 읽기(`git_command.zig`) | 쓰기(`git_write_command.zig`) | 왜 다른가 |
|---|---|---|---|
| index 잠금 | `GIT_OPTIONAL_LOCKS=0` | **해제** | 쓰기는 index를 잠가야 한다. 잠그지 않으면 동시 실행이 index를 깬다 |
| hook | `core.hooksPath=/dev/null` | **commit만 허용**(§3) | 읽기가 남의 hook을 실행하면 안 되지만, 커밋 hook은 사용자가 기대하는 동작이다 |
| 외부 프로세스 | external diff·textconv·pager 전부 빈 값 | **동일하게 차단** | 저장소 config가 우리를 통해 프로그램을 실행하는 경로는 쓰기에서도 안 연다 |
| 네트워크 | 없음(credential helper 제거) | fetch만 허용(§4) | |
| 대화형 프롬프트 | `GIT_TERMINAL_PROMPT=0` | **동일** | 프롬프트는 우리 화면에 그릴 수 없다 — 뜨면 그 명령은 영영 안 끝난다 |
| stderr | 화면·로그에 싣지 않는다 | **가공해서 보여 준다**(§5) | 커밋이 왜 거부됐는지 못 보여 주면 쓸 수 없는 기능이다 |
| 셸 경유 | 없음(argv를 그대로 execve) | **동일** | |

## 2. 명령과 인자 (v1)

경로 인자는 전부 **저장소 루트 기준 상대경로**이고 `--` 뒤에만 온다. `--`가 없으면 `-`로 시작하는 파일 이름이
옵션으로 해석되고, 절대경로·`..` 세그먼트는 루트 밖을 가리킨다 — 셋 다 조립 단계에서 거부한다(§6의 3겹 경계와 같은 규율).

| 동작 | argv | 비고 |
|---|---|---|
| 스테이지 | `add -- <경로>…` | 새 파일·수정·삭제를 한 명령이 덮는다 |
| 언스테이지 | `restore --staged -- <경로>…` | **unborn(첫 커밋 전)에서는 `rm --cached -- <경로>…`** — HEAD가 없어 `restore`가 실패한다 |
| 모두 스테이지 | `add -A --` | 추적되지 않은 파일까지 든다 |
| 모두 언스테이지 | `restore --staged -- .` / unborn이면 `rm --cached -r -- .` | |
| 커밋 | `commit -F <메시지 파일>` | `-m`이 아니다 — 여러 줄·따옴표·비ASCII를 argv에 싣지 않는다. 파일은 **저장소 밖**(`~/.cache/maru/`)에 만들고 성공·실패와 무관하게 지운다 |

**경로를 한 번에 몇 개까지 넘기나.** argv 길이 상한(`ARG_MAX`)이 있으므로 경로 수와 총 바이트로 나눠 여러 번 부른다.
나눠 부르면 **중간에 실패할 수 있다** — 그때는 어디까지 됐는지 목록을 다시 읽어 화면을 사실과 맞춘다(성공한 부분을
되돌리지 않는다. 되돌리기 역시 쓰기라 실패할 수 있고, 그러면 사용자가 시키지도 않은 상태로 끝난다).

## 3. 커밋은 hook을 막지 않는다

읽기 명령은 `core.hooksPath=/dev/null`로 hook을 통째로 막는다 — 목록을 그리려고 남의 스크립트를 실행할 이유가 없기
때문이다. **커밋은 반대다.** `pre-commit`·`commit-msg`는 사용자가 자기 저장소에 의도적으로 설치한 것이고, 그걸 건너뛰는
커밋은 터미널에서 친 `git commit`과 **다른 일**이 된다(린트를 통과하지 않은 커밋이 조용히 들어간다).

그래서 커밋만 hook을 그대로 돌린다. 대신 두 가지를 지킨다.

- **`GIT_TERMINAL_PROMPT=0`은 유지한다.** hook이 입력을 물으면 우리는 답할 수 없다. 프롬프트 대신 실패로 끝나는 편이
  영원히 안 끝나는 것보다 낫다.
- **시간 상한을 둔다.** hook은 임의로 오래 걸릴 수 있다(테스트 전체를 도는 저장소가 흔하다). 상한을 넘으면 프로세스를
  죽이지 말고 **"커밋이 오래 걸리는 중"으로 화면에 남긴다** — 죽이면 index/`.git` 상태가 어중간해진다.

`--no-verify`는 v1에 넣지 않는다. 넣는다면 그건 "hook을 건너뛴다"는 뜻이 화면에 분명히 보이는 별도 항목이어야 한다.

## 4. 원격은 fetch만 우리가 실행한다

> **여기서 「원격」은 `origin` 이다**(로컬 저장소의 remote). **SSH 원격 호스트의 저장소에 쓰는 축**은 다른
> 문제이고 [remote-scm.md](plans/remote-scm.md)가 소유한다 — 그쪽은 RS4까지 가면 stage·commit·discard를 전부
> ControlMaster 위에서 실행한다. 그때까지 원격 목록을 보는 동안에는 이 절의 쓰기가 **거부되고 이유를 말한다**
> (`scm_remote_read_only`) — 로컬 index에 걸리면 보고 있지도 않은 파일이 바뀌기 때문이다.

| 명령 | 누가 실행하나 | 왜 |
|---|---|---|
| `fetch` | **maru**(`fetch --prune`) | 읽기 방향이라 저장소가 안 바뀌고, 실패해도 로컬 상태가 그대로다 |
| `push`·`pull` | **사용자** — 활성 터미널에 명령을 넣어 주고 엔터는 사용자가 친다 | 남의 저장소를 바꾸는 일이고 hook·충돌·강제 여부가 걸린다. 브랜치 전환이 이미 같은 패턴을 쓴다(`branchSwitchCommand` — 개행을 붙이지 않는 이유가 여기 있다) |

**그 `∨` 메뉴에는 세 번째 항목이 있다** — `기준 브랜치 고르기…`([도크 §3.5](editor-surface-dock.md)). 그것은
명령이 아니라 **다음 읽기의 인자**를 바꾸는 선택이라 터미널로 나가지 않는다. 그래서 이 절의 "누가 실행하나"
표에 줄이 늘지 않는다 — 실행되는 것이 없다.

그 항목 때문에 **메뉴가 열리는 조건이 `fetch` 칩과 갈라졌다**: 원격이 없는 저장소에서도 고를 것이 남는다
(오히려 `origin/HEAD`가 없는 저장소가 곧 원격 없는 저장소다). 대신 실리는 항목이 저장소마다 달라지므로
`push`/`pull`은 **원격이 있을 때만** 실린다 — "무엇을 골라도 실패하는 줄은 안 싣는다"는 규칙은 그대로다.
고른 자리를 뜻으로 되돌리는 표는 **열 때 함께 만든다**(자리를 나중에 다시 세면 원격 없는 저장소에서 0번이
`git push`가 된다).

**주입은 `pasteText`가 아니다**(P6b 구현 규칙). 그 함수는 **커밋 상자가 입력을 소유하면 글자를 커밋 메시지로**
보낸다 — 사용자가 고른 것은 "터미널에서 실행할 명령"이므로 그 라우팅이 여기서는 틀리고, 증상은 상자에
`git push`가 적히고 아무 일도 안 일어나는 것이다. 대상 surface를 명시해 붙여넣기 경로로 보내고, 활성 Term이
터미널이 아니면 **그 사실을 적는다**(조용히 사라지면 사용자는 앱이 멈춘 줄 안다).

**인증은 우리가 대신하지 않는다.** 읽기 명령은 credential helper를 빈 값으로 덮지만, fetch는 그러면 인증이 필요한
원격에서 **항상** 실패한다. 그래서 fetch는 사용자의 helper 설정을 그대로 쓰되 `GIT_TERMINAL_PROMPT=0`으로 대화형
프롬프트만 막는다. 프롬프트가 필요한 원격(helper 미설정·만료)은 실패로 끝나고, 안내는 "터미널에서 `git fetch`를
실행하세요"다 — 우리가 자격증명을 묻는 창을 만들지 않는다.

**SSH도 마찬가지다.** `ssh-askpass`가 뜨는 상황은 우리 프로세스 밖의 일이라 통제할 수 없다. `GIT_SSH_COMMAND`에
`BatchMode=yes`를 실어 **묻지 않고 실패**하게 한다.

**시스템 config를 배제하지 않는다**(P6에서 추가 — 실측이 규칙을 하나 더 낳았다). 나머지 쓰기는
`GIT_CONFIG_NOSYSTEM=1`로 `/etc/gitconfig`의 외부 프로그램 설정을 배제하는데, fetch가 그러면 **helper 자체가
사라진다**: macOS에서 `credential.helper=osxkeychain`을 주는 것이 바로 그 시스템 config다(실측 2026-08-18 —
`git config --show-origin --get credential.helper` →
`file:/Applications/Xcode.app/Contents/Developer/usr/share/git-core/gitconfig`, 그리고 `GIT_CONFIG_NOSYSTEM=1`을
걸면 그 값이 사라진다). 그러면 helper를 빈 값으로 덮은 것과 결과가 같아져 이 절의 예외가 무의미해진다.
시스템 config가 pager·external diff를 지정할 위험은 남지만, 우리가 붙이는 `-c`가 config보다 **뒤에 이겨서**
그 축은 그대로 닫힌다.

**fetch는 쓰기 슬롯을 쓰지 않는다**(P6). §6의 직렬화는 `index.lock` 때문에 있는 규칙이고 `fetch`는 index를
만지지 않는다 — remote-tracking ref만 쓴다. 무엇보다 **네트워크라 오래 걸려서**, 같은 슬롯에 넣으면 느린 원격
하나가 커밋·스테이지는 물론 §6-1대로 **목록 읽기까지** 붙잡아 도크가 멈춘 것처럼 보인다. 그래서 in-flight를
따로 두고, 그 동안에도 쓰기와 읽기는 평소대로 돈다.

**원격이 없으면 누를 수 없다.** 그 판정의 출처는 `git remote`(읽기 명령) **하나**다. 없는 저장소에서 버튼을
켜 두고 실패로 배우게 하지 않는다 — 자리는 그대로 두고 비활성으로 그리며, 눌리면 이유를 적는다(§3.5).
성공도 말한다: 원격에 새 것이 없으면 화면 숫자가 그대로라, 아무 말이 없으면 "눌렀는데 아무 일도 안 일어났다"가 된다.

## 5. 실패는 사실대로 보여 준다

읽기 명령의 stderr는 화면·로그에 싣지 않는다(§6 — 경로·사용자·저장소 정보가 든다). 쓰기는 그럴 수 없다: hook이 거부한
커밋의 이유가 안 보이면 사용자는 무엇을 고쳐야 할지 모른다.

- **가공해서 싣는다.** 홈 경로 세그먼트·IPv4·`user@host`는 [redaction 기준](project-rules.md#민감정보-redaction-기준-단일-출처)의
  `redact.anonymizeAlloc`을 그대로 통과시킨 뒤 화면에 낸다. trace·로그에는 여전히 싣지 않는다(화면은 사용자가 방금
  누른 동작의 결과이고, 로그는 나중에 공유되는 산출물이다 — 둘의 위험이 다르다).
- **길이를 자른다.** hook 출력은 수천 줄이 될 수 있다. 마지막 N줄만 보여 주고 잘렸다는 사실을 함께 말한다.
- **성공을 추정하지 않는다.** 종료 코드가 0이 아니면 실패이고, 화면 상태는 명령 전으로 되돌린 뒤 **목록을 다시 읽는다**.

## 6. 동시성 — 쓰기가 도는 동안 읽기를 걸지 않는다

`index.lock`은 git이 index를 만질 때 만드는 잠금 파일이고, 두 명령이 겹치면 뒤엣것이 즉시 실패한다. 우리 쪽에서
겹칠 수 있는 짝이 셋이다.

1. **우리 쓰기 ↔ 우리 읽기**: 쓰기가 in-flight인 동안 상태 읽기를 걸지 않는다. 쓰기가 끝난 뒤 **한 번** 읽는다
   (쓰기마다 읽기를 걸면 `+`를 여러 행에 빠르게 누를 때 프로세스가 줄줄이 뜬다).
2. **우리 쓰기 ↔ 우리 쓰기**: 직렬화한다. 큐가 아니라 **in-flight 하나**이고, 그 동안 눌린 `+`/`−`는 낙관적 상태로
   화면에만 반영했다가 결과가 오면 사실과 맞춘다.
3. **우리 쓰기 ↔ 사용자의 터미널 git**: 막을 방법이 없다. 실패하면 §5대로 그 사실을 보여 주고 목록을 다시 읽는다 —
   조용히 재시도하지 않는다(사용자가 그 사이에 무엇을 했는지 우리가 모른다).

## 7. 낙관적 반영의 경계

`+`를 누르면 **화면은 즉시** 바뀐다 — 그 행이 위 그룹으로 옮겨 가고 명령은 뒤따라 돈다. 안 그러면 100 ms 남짓
아무 일도 안 일어나 두 번 누르게 된다. 다만 낙관은 **그 행 하나**에만 걸고, 다음 셋은 낙관하지 않는다.

- **개수·요약 숫자**(`+588 -588`, 탭의 `(16)`)는 실제 결과가 온 뒤에 바꾼다. 낙관으로 계산하면 부분 스테이지·rename에서
  틀린 숫자가 나오고, 그건 사용자가 커밋 직전에 보는 값이다.
- **커밋 버튼의 활성 여부**는 실제 index 상태로만 정한다.
- **실패하면 되돌린다.** 되돌린 뒤에는 반드시 목록을 다시 읽는다 — 우리가 아는 상태와 저장소가 갈렸다는 뜻이므로.

## 8. 권한 경계

이 뷰는 native chrome이라 `EditorGrant`의 대상이 아니다(§3.5의 권한 경계와 같다 — 웹 브리지가 아니다). 다만
**`EditorGrant.git_write`는 웹 브리지 축에서 계속 별도 capability로 둔다**(§10.4·§6). 웹이 stage/commit을 부를 수 있게
되는 것은 이 문서의 범위가 아니며, 지금은 **아무 웹 표면도 이 명령들에 닿지 않는다** — 유일한 진입점은 도크의 사용자
클릭이다.
