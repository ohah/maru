# 에디터 Surface — 우측 도크 소스 컨트롤 뷰 (§3.5)

도크 소스 컨트롤 뷰의 시각 구조와 정보 계층 계약이다. 이 절을 가리키는 참조가 이 문서에서 가장 많다. 도크가 **어디에 놓이고 무엇을 신뢰하는지**는 [권장 구조](editor-surface-structure.md)가 소유한다.

### 3.5 우측 도크 소스 컨트롤 뷰 (시각 구조·정보 계층)

**권한 경계.** 이 뷰는 **native chrome**이라 `EditorGrant`/`git_read`의 대상이 아니다 — 그 grant들은 *웹 브리지*가 넘는 경계를
게이트하는 장치이고(§3.2), 도크는 웹이 아니다. 사용자가 연 창에서 사용자의 저장소를 읽는 것이므로 추가 승인 계단을 만들지 않는다.
반대로 **diff 본문을 그리는 파일 Term은 웹**이므로 `diff.open`은 그대로 grant 게이트를 통과해야 한다. 이 비대칭이 §3 경계의
직접적 귀결이다.

**시각 구조 기준 = 사용자 제공 목업 2판(2026-08-14).** 레퍼런스 앱의 코드·DOM은 사용하지 않고 **배치와 정보 계층만**
받아 maru GPU chrome으로 독립 구현한다([project-rules.md](project-rules.md) 레퍼런스 경계,
[no-external-ref](pr-checklist.md)). 초판(2026-07-31)은 한 화면에 다섯 섹션을 쌓은 **읽기 전용** 목록이었고, 2판은
**탭 3개로 축을 나누고 스테이징·커밋·원격까지** 담는다. 무엇이 왜 뒤집혔는지는 [단계 계획](plans/scm-dock.md) §0에 있다.

```text
┌ 우측 도크(폭 조절·접기는 탐색기와 공유) ─────────────┐
│ [트리] [·] [브랜치] [체크]            [패널 토글]   │ ← 뷰 스위처(아이콘 줄, 2판에서 변동 없음)
├──────────────────────────────────────────────────┤
│  변경 사항 (16) │ 히스토리 │ 에이전트            │ ← 탭 줄(§3.5.1)
├──────────────────────────────────────────────────┤
│ 커밋 메시지…                                      │ ← 커밋 메시지 입력(여러 줄)
│                                      [커밋 ∨]    │
├──────────────────────────────────────────────────┤
│ diff 보기  +588 -588             [필터] [모두 ∨] │ ← 요약·일괄 동작 줄
│ ⌄ 스테이지된 변경                            2  │ ← 그룹(호버하면 헤더에 `−`)
│   ▣ ExchangeConfirmModal.js …/Exchange +14 -59 M │ ← 행: 이름·흐린 경로·증감·상태 문자
│ ⌄ 변경 사항                                 16  │ ← 호버하면 행에 [열기] [되돌리기] [+]
│   ▣ cart-vat.png            apps/pc-seller     U │
│                                                  │
│ (남는 공간)                                       │
├──────────────────────────────────────────────────┤
│ ⑂ payhere-pos-pc / fix/mqtt-…      [Fetch ∨]     │ ← 브랜치·원격 줄
└──────────────────────────────────────────────────┘
```

**파일 행의 타이포·전경은 파일 탐색기와 같다**(2026-08-23). 이름은 목록 행 role(`list_row`)로 그리고 전경은 `list_secondary_fg`, 그 뒤 경로 꼬리는 한 단 더 물러난 `list_disabled_fg`, 종류 아이콘은 **자기 라벨과 같은 단**이다. 섹션 제목만 `control` + bold로 남아 "제목 아래 항목들"이라는 층이 선다.

같은 도크 컬럼에서 뷰만 바꿨는데 글자 크기·밝기가 달라지면 그 자체가 두 화면처럼 읽힌다 — 옮기기 전에는 파일 이름이 13pt medium·최대 대비였고 경로 꼬리가 이름보다 **밝았다**(실측 207 대 169로 역전). 값의 소유자는 `chrome/ui/typography.zig`의 role 표와 `chrome/tokens.zig`의 전경 위계이며, 이 절은 **어느 요소가 어느 단인가**만 정한다.

**좁은 폭의 열화 규칙 — "이름은 마지막까지 남는다"**(2026-08-25). 파일 탐색기와 같은 규칙이고
([file-explorer.md](file-explorer.md) §3이 그 원본을 소유한다), 이 뷰의 순서는 이렇다:

- **파일 행**: 들여쓰기(disclosure 열) → 증감 수 → 동작 버튼 자리 → 상태 문자.
  못 버림 = 좌우 패딩 · 종류 아이콘 · **이름**.
- **섹션 머리**: 개수 배지 → 일괄 동작 자리. 개수는 목록을 세면 알 수 있지만, 그 아래가 **무엇의
  목록인지**는 제목만이 말한다. 배지는 예산만 비우지 않고 **그리지도 않는다** — 자리를 내주고 그리면
  제목 위에 겹친다.

이 규칙 전에는 도크 하한(행 폭 104pt = 도크 120 − 스크롤 거터 16)에서 **파일 이름이 통째로 사라지고**
증감이 아이콘 위에 겹쳤으며 섹션 제목은 `…` 하나였다(Lab 실측). 예산이 음수가 되면 글자를 조용히
건너뛰기 때문이다 — 가장 지켜야 할 것을 가장 먼저 버리고 있었다.

### 3.5.1 탭 3개 — 축이 다르면 화면을 나눈다

초판은 성질이 다른 다섯 묶음을 한 화면에 쌓았다. 그중 셋(스테이지된 변경·변경 사항·추적되지 않은 파일)은 "지금
커밋할 것"이라 **같이 봐야** 하지만, "브랜치에 COMMIT 됨"은 이미 커밋한 것이고 "에이전트가 방금 바꾼 것"은 git이
아니라 턴 경계가 기준이다. 셋을 한 목록에 두면 스크롤 한 번에 세 가지 질문이 섞인다.

| 탭 | 무엇에 답하나 | 단위 | 쓰기 |
|---|---|---|---|
| **변경 사항 (N)** | 지금 무엇을 커밋할 것인가 | 파일 | stage/unstage/commit |
| **히스토리** | 이 저장소에 무슨 일이 있었나 | 커밋 | 없음(읽기) |
| **에이전트** | 에이전트가 어느 턴에 무엇을 바꿨나 | **턴** | 없음(읽기) |

**에이전트 탭이 파일이 아니라 턴 단위인 이유**(2026-08-14 사용자 지적): 에이전트의 변경은 "직전 턴·그 이전 턴"으로
쌓이므로 한 목록으로 **합칠 수 없다.** 합치면 두 턴이 같은 파일을 고쳤을 때 어느 턴의 것인지 말할 수 없고, 그건 이
탭이 존재하는 이유 그 자체다. 그래서 탭의 1급 항목은 파일이 아니라 턴이고, 파일은 턴 아래 하위 목록이다(§3.5.4).

탭 선택은 **창별 chrome 상태**이며 workspace에 영속한다(뷰 선택과 같은 급 — 재시작이 사용자를 다른 탭으로 되돌리지
않는다). 모르는 값은 `변경 사항`으로 clamp한다.

**뷰 스위처.** 도크는 지금 탐색기 하나만 담지만, 이 목업은 **같은 컬럼에서 뷰를 갈아 끼우는** 구조다. 그래서 도크 상단에
아이콘 줄을 두고 `탐색기 | 소스 컨트롤`을 전환한다(후속 뷰는 자리만 예약). 이는 새 도크를 만드는 것이 아니라 **하나의 도크가
여러 뷰를 갖는 것**이며, 폭·접기·`⌘⇧E` 왕복·포커스 축(`FocusOwner.file_tree`)은 그대로 공유한다. 뷰 선택은 창별 chrome 상태이고
workspace에 영속한다(탐색기로 되돌아오는 재시작을 강요하지 않는다).

> **4판(②b, 2026-08-17): 커밋 줄은 고정 chrome이 아니라 그 저장소 그룹 안에 산다.** 아래 3판 설명은
> 도크가 저장소 하나를 보던 시절의 것이다. 목록이 저장소 여럿을 세우게 되면서(§3.5.1c) 상자가 하나면
> **"지금 어느 저장소로 커밋하는가"가 화면에 없다** — 아래 그룹의 파일을 보면서 위 상자에 쓰면 다른
> 저장소로 커밋된다. 그래서 상자·버튼은 머리 줄 바로 아래 **목록 줄**이 됐고, 고정 chrome에는 탭 줄·
> 요약 줄·브랜치 줄만 남는다. 3판이 세운 근거(주 동작이 목록에 밀려 스크롤 밖으로 나가면 안 된다)는
> 그대로다 — 이제 **그 그룹의** 머리 줄 바로 아래가 그 자리다.

**커밋 줄은 목록 위, 브랜치 줄은 목록 아래다(3판 — 2026-08-16 사용자 결정).** 2판은 커밋 입력을 맨 아래에 두고
"위쪽 공간은 *무엇을 커밋할 것인가*가 다 쓴다"를 근거로 삼았는데, 실제로 써 보니 **커밋 상자가 이 뷰의 주 동작인데
가장 먼 곳에 있었다.** 목록은 길어질 수 있어 상자가 스크롤 밖으로 밀려 보이지 않는 상태도 생긴다. VS Code도 메시지
입력과 `Commit`을 목록 위에 둔다.

**브랜치 줄은 아래에 남는다.** 2판이 그것을 커밋 버튼 옆으로 내린 근거("커밋 직전에 확인하는 값")는 커밋이 아래에
있을 때의 논리였다. 지금은 다른 이유로 같은 자리를 지킨다 — 브랜치·ahead/behind는 **"지금 어디에 있나"라는 상태**이고,
상태는 바닥에 사는 것이 이 앱의 규율이다(창 상태바와 같은 축). VS Code도 브랜치를 패널이 아니라 상태바에 둔다.

내용의 출처는 초판과 같다(명령은 2026-07-31 실측).

| 항목 | 내용 | 출처 | v1 |
|---|---|---|---|
| 리뷰 대상(PR 번호·제목) | **로컬 git 밖** — GitHub API/`gh` 필요 | **범위 밖**(§10.12) | 자리도 두지 않는다 — 히스토리 탭이 로컬 커밋을 보여 준다 |
| 원격 / 현재 브랜치 | `git symbolic-ref --short HEAD` + 원격 이름 | 포함(`payhere-pos-pc / fix/…` 형태) | |
| ahead/behind | `git rev-parse --abbrev-ref origin/HEAD` → `git rev-list --count --left-right <base>...HEAD` | 포함 | |
| `Fetch ∨` | 원격 갱신 + 보조 메뉴(`push`·`pull`은 터미널 주입) | 포함 — [쓰기·원격](editor-surface-dock-write.md) §4 | 갱신 P6a · `∨` 보조 메뉴 P6b(둘 다 2026-08-18 완료) |

**구현 완료(2026-08-18).** 아래 규칙대로 `rev-list --count --left-right origin/HEAD...HEAD`를 목록 읽기에 함께
건다(선택 명령 — 실패하면 그 저장소는 `@{u}` 값으로 돌아간다). 그 전까지 화면은 `status --branch`의
`# branch.ab`를 그렸고, 그래서 **작업 브랜치에서 늘 `↑0 ↓0`**이었다(실측: 같은 브랜치가 기본 브랜치 기준으로는
`0 1`). 색이 붙은 뒤라 그 거짓말이 더 눈에 띄었다.

**ahead/behind의 기준은 `@{u}`가 아니라 기본 브랜치다.** 초판 목업이 `→ origin/main`을 보여 주는데, PR 브랜치의 `@{u}`는 보통
`origin/<자기 브랜치>`라 그걸 쓰면 항상 `0 0`이 나온다(실측 확인). 리뷰가 알고 싶은 것은 "기본 브랜치 대비 내 브랜치"이므로
**`origin/HEAD`가 가리키는 기본 브랜치를 기준으로 쓴다** — 이 값은 네트워크 없이 로컬에서 읽힌다(실측: `origin/main`).
`origin/HEAD`가 없으면(clone 방식에 따라 없을 수 있다) 사용자가 기준을 고르게 하고, 그 선택을 workspace에 기억한다.
`@{u}`는 별도로 "push 됐는지"를 보여 주는 데만 쓴다.

**기준 고르기(2026-08-19 구현).** 자리는 브랜치 줄 `∨` 메뉴의 `기준 브랜치 고르기…`이고, 고르면 그 값이
**다음 읽기의 인자**가 된다(우리가 실행하는 것은 읽기뿐이다 — 터미널로 나가는 명령이 아니다).

| 규칙 | 왜 |
|---|---|
| 고른 기준이 **`↑N ↓N`의 범위**를 정한다(`origin/HEAD...HEAD` — 삼점) | 두 점으로 물으면 기본 브랜치에 새로 들어온 커밋까지 "내가 안 보낸 커밋"으로 잡혀 숫자가 부풀어 오른다. **예전에는 세 명령이 이 기준을 함께 썼다**(ahead/behind · `merge-base` · 브랜치 범위 diff) — 뒤의 둘은 「브랜치에 COMMIT 됨」섹션의 것이었고 그 섹션이 사라지며 소비자를 잃어 2026-08-27 에 걷혔다 |
| 후보에 **원격 추적 ref를 넣는다**(`refs/heads` + `refs/remotes`) | `origin/HEAD`가 없는 저장소의 대표가 `clone --single-branch`인데, 거기서 고르고 싶은 이름은 보통 `origin/main`이다. 브랜치 **전환** 목록은 그대로 로컬만 본다(원격 추적 ref로 checkout하면 detached HEAD) |
| 후보에서 **원격 이름 자체**(`origin`)는 뺀다 | `refs/remotes/origin/HEAD`의 짧은 이름이라 `기본값` 줄과 **같은 것**을 가리킨다(제품 캡처에서 나란히 떴다). 판정은 이미 읽어 둔 `git remote` 출력으로 한다 — git 버전에 기대지 않는다 |
| 후보 목록은 **최근 순 상한(24개)**이다 | 목록은 브랜치 전환 메뉴와 **같은 읽기**를 쓰는데, 그쪽 정렬 근거("최근 것이 원하는 것")는 **전환**의 근거다. 기준으로 고르는 이름은 보통 `main`·`origin/main`처럼 **내가 건드리지 않는** ref라 정렬이 그것을 아래로 민다 — 그래서 12에서 24로 넓혔다(컨텍스트 메뉴 상한이 25라 `기본값` 줄까지 정확히 들어간다). 그래도 브랜치가 아주 많은 저장소에서는 원하는 이름이 안 보일 수 있다 |
| `기본값` 줄은 **`origin/HEAD`가 있을 때만** 뜬다 | 없는 저장소에서 그 줄을 고르면 고르기 전과 후가 같다(아무 말도 하지 않는 선택지다) |
| `∨`는 **원격이 없어도 열린다**(`fetch` 칩과 판정을 나눴다) | `origin/HEAD`가 없는 저장소가 곧 원격 없는 저장소다 — fetch에 묶어 두면 이 기능이 가장 필요한 곳에서 안 열린다. 메뉴에 실리는 항목은 그때그때 다르고(`push`/`pull`은 원격이 있을 때만), 그래서 **고른 자리를 뜻으로 되돌리는 표**를 열 때 함께 만든다 |
| 기준은 **저장소와 짝으로** 든다 | 기준은 저장소마다 다른 사실이라, 짝을 안 보면 남의 저장소에서 고른 이름으로 숫자를 센다 |
| 고른 기준을 **못 읽었으면 사실로 남긴다**(`scm_base_reread_pending`) | 읽기·쓰기가 도는 동안 갱신은 그냥 돌아간다(§6-1). 거기서 끝내면 고른 것이 흔적 없이 사라지고, 같은 값을 다시 골라도 상태가 이미 그 값이라 **아무 일도 안 일어난다**. 도는 읽기를 버리지는 않는다 — 그 슬롯은 깊이 1이라 안 걷힌 결과가 있으면 새 제출이 거절돼 갱신이 통째로 사라질 수 있다. 옛 기준의 답이 한 프레임 늦는 쪽이 낫다 |
| 그 재시도는 **도는 것이 끝난 뒤 한 번**이다 | 이 자리는 tick housekeeping이고 그 블록의 규율이 "blocking I/O를 늘리지 않는다"인데, 갱신은 저장소 walk-up과 git 탐색으로 `access(2)`를 친다. 플래그가 오래 서 있는 상황(git 없음·저장소 아님)에서 매 프레임 되물으면 답은 늘 같고 비용만 든다. 한 번 시도하고 내린다 — 그때도 못 걸었다면 이유가 지속적인 것이고, 도크를 여는 경로가 어차피 새 읽기를 건다 |
| 기준 목록이 열려 있으면 **이름 버퍼를 비울 때 함께 닫는다** | 그 목록은 브랜치 전환 메뉴와 같은 버퍼에서 이름을 빌린다 — 열린 채 해제하면 다음 draw가 해제된 메모리를 읽는다(전환 메뉴가 이미 같은 이유로 그 가드를 갖고 있었고, 기준 목록이 그 밖에 있었다) |
| 기준 이름은 argv에 싣기 전에 **형태를 강제한다**(`isSafeBaseRef`) | `-`로 시작하면 git이 옵션으로 읽고(`--upload-pack=…` — 닫아 둔 외부 프로세스 경로가 열린다), `..`가 들어가면 우리가 붙이는 `...HEAD`와 합쳐져 다른 범위가 된다. 고르는 쪽과 argv를 만드는 쪽 **양쪽에서** 본다(뒤쪽은 이 값이 파일을 거쳐 올 것이기 때문이다) |

**workspace에 남는다(2026-08-19 P7b).** 고른 기준은 저장소마다 따로 기억되고 앱을 다시 켜도 남는다.

| 규칙 | 왜 |
|---|---|
| **창 줄에 실린다**(`scm-bases`, 탐색기 root와 같은 인코딩) | 저장은 창마다 따로 일어난다(`serializeWindow` — 각 세션이 자기 블록을 내고 Swift가 헤더 아래로 모은다). 최상위 섹션은 **쓸 주인이 없다** |
| 저장할 때 건 검사를 **읽을 때 다시 건다**(절대 경로·`isSafeBaseRef`·중복 없음) | 파일은 우리 밖의 것이고, 이 값의 다음 정거장은 git argv다(§6 심층 방어) |
| 한 항목이라도 이상하면 **목록 전체를 버린다** | 부분 복원은 "어떤 저장소는 기억됐고 어떤 것은 아니다"를 만드는데, 사용자에게 둘은 구별되지 않는다(둘 다 기본값으로 보인다) |
| 고른 것이 없으면 그 키를 **아예 안 쓴다** | 옛 리더가 모르는 키를 만나지 않고 파일도 짧게 유지된다(도크 기본값과 같은 규율) |
| 자리가 꽉 차면(`max_scm_bases`) **거절한다** | 오래된 것을 조용히 밀어내면 사용자는 "어제 고른 기준이 왜 기본값이지"를 겪고, 그 이유가 화면 어디에도 없다 |
| 복원할 때 **저장소가 지금 있는지는 안 본다** | 없는 저장소의 기억은 화면에 아무 영향이 없다(그 저장소를 열 때만 쓰인다). 여기서 지우면 잠시 마운트가 빠진 외장 디스크의 기억이 조용히 사라진다 |

**옛 빌드로 한 번 열면 그 기억은 사라진다** — 그 빌드는 이 키를 모른 채 workspace를 다시 쓰기 때문이다.
파일 형식 버전을 올리지 않은 대가이고, 잃는 것이 "다시 고르면 되는 값"이라 그쪽을 택했다.

**원격 갱신은 글자가 아니라 아이콘이다**(2026-08-20 사용자 결정). `가져오기` 넉 자가 브랜치 줄 오른쪽을
계속 차지했고, 도는 중에는 `가져오는 중…`으로 더 넓어져 그 옆 `↑`/`↓`를 밀었다 — **상태가 바뀌었다고 다른
값의 자리가 움직이면** 사용자는 숫자를 다시 찾아 읽어야 한다. 아이콘이면 폭이 상태와 무관하게 같다.

| 무엇 | 왜 그 글리프인가 |
|---|---|
| 평소 · 꺼짐 | **구름↓**(`cloud_download`). `reset`(⟳)을 안 쓰는 이유는 그것이 같은 패널에서 이미 **로컬 다시 읽기**(머리 줄 새로고침)를 뜻하기 때문이다 — 같은 그림이 두 동작이면 어느 쪽이 네트워크를 타는지 화면으로 알 수 없다. `arrow_down`도 안 쓴다: 바로 옆 `↓ N`(behind 개수)과 화살표가 겹친다 |
| 도는 중 | **모래시계**(`hourglass`). 글자를 뗀 뒤로 이 상태를 말할 것이 색뿐인데, 꺼진 칩도 같은 회색이라 "돌고 있다"와 "원격이 없다"가 한 그림이 된다. 눌렀는데 표시가 없으면 사용자는 다시 누르고, 그 두 번째 누름은 조용히 거부된다 |

**목록 오른쪽의 스크롤바 자리는 넘칠 때만 준다**(같은 날 결정). 늘 비워 두면 스크롤바가 서지 않는 화면에도
이유를 말하지 않는 12px 띠가 남는다(머리 줄 동작 아이콘의 빈 띠와 같은 종류의 문제다). 폭이 바뀌는 순간은
**목록이 창을 넘기 시작하거나 멈추는 때**뿐이고, 그때는 어차피 행이 늘거나 준 때라 폭 변화가 따로 도드라지지
않는다 — 스크롤하는 동안에는 절대 안 바뀐다(그것이 원래 이 예약이 막으려던 것이다). 넘치는지는 **창 높이를
아는 host**가 판정해 props로 준다(component가 다시 재면 같은 값의 출처가 둘이 된다). **그 판정은 스크롤 상한과
같은 자리**(투영)에서 한다 — 커밋 상자의 랩 계산이 이 값으로 스크롤바 자리를 빼는데, 판정을 props 만드는 쪽에
따로 두면 두 값이 갈릴 창이 생긴다(props는 그리는 프레임에만 지나가고 투영은 포인터 경로에서도 지나간다).

**그 표시는 브랜치 이름 뒤의 점 하나다**(2026-08-19 사용자 결정). `@{u}` 기준으로 앞선 커밋이 있으면 켜고,
없거나 upstream이 없으면 끈다 — **개수는 적지 않는다**: 바로 옆 `↑`/`↓`가 **기본 브랜치** 기준이라, 기준이
다른 숫자를 나란히 놓으면 어느 쪽이 무엇인지 읽을 수 없다(그 혼동이 이 두 값을 가른 이유다). 색은 "보낼 것이
있다"는 신호이므로 테마 시그니처 색을 쓰고, 없을 때는 **아무것도 그리지 않는다**(늘 켜진 표시는 말이 없다).
글자 하나(`●`)로 그린다 — 컨트롤이 아니라 상태 표식이고 PUA가 아니라 어떤 폰트에도 있는 글자다.

**PR 헤더는 여전히 넣지 않는다.** 네트워크·인증·호스트별 API가 붙는 순간 로컬 git 경계를 넘고, 실패 모드(토큰 만료·
rate limit·사설 호스트)가 리뷰 UI 전체의 신뢰도를 떨어뜨린다. **2판은 자리조차 두지 않는다** — 초판이 비워 둔 그 줄이
"곧 채워질 것"처럼 보였는데, 히스토리 탭이 로컬 커밋을 전부 보여 주므로 빈자리를 유지할 이유가 사라졌다.
PR 연동은 §10.12 결정 뒤 별도 슬라이스로 얹는다.

**대상 저장소를 정하는 규칙**(2026-08-10 사용자 보고로 추가 — 그전까지 이 문서에 규칙이 **없었고**, 구현이 임의로
탐색기 root를 우선했다).

**기준은 활성 터미널이 서 있는 폴더다.** 사용자가 "지금 명령을 치는 곳"이 곧 리뷰 대상이라는 뜻이고, 파일 탐색기가
이미 같은 축으로 움직인다([file-explorer.md §1](file-explorer.md) — 탐색기 root가 활성 터미널 cwd와 같게 유지된다). 두 뷰가 서로 다른
저장소를 보면 같은 컬럼에서 뷰를 갈아 끼우는 이 구조가 성립하지 않는다.

| 순위 | 출처 | 왜 이 자리인가 |
|---|---|---|
| 1 | **활성 pane·활성 Term의 cwd**의 git 루트 | 사용자가 보고 있는 것의 권위. 탐색기에 다른 저장소를 열어 뒀어도 터미널을 옮기면 목록이 따라온다 |
| 2 | **직전에 목록을 읽은 저장소** | diff를 열면 활성 Term이 **파일 Term으로 바뀌어 1번이 사라진다**. 여기서 3번으로 떨어지면 열려 있는 diff와 목록이 다른 저장소를 가리킨다 |
| 3 | **파일 탐색기 root** | 터미널이 아직 아무것도 보고하지 않은 첫 진입의 바닥값 |

**터미널이 답했으면 거기서 끝난다.** 그 폴더가 저장소가 아니면 결론은 "저장소 없음"이지 2·3순위로 내려가는 것이
아니다 — 내려가면 저장소 아닌 곳으로 `cd` 했을 때 2·3순위가 계속 답을 줘서 **옛 저장소에 영영 고정**되고, 탐색기는
새 폴더를 목록은 옛 저장소를 가리키게 된다(이 문서가 고치려던 바로 그 불일치다). 2·3순위는 터미널이 **답을 못 준**
경우(파일 Term·원격 세션)의 것이다. 그때도 답이 없으면 뷰는 빈 안내를 낸다(오류가 아니다).

**판정은 3-상태다 — "없다"와 "모른다"를 한 값으로 뭉개지 않는다**(2026-08-12 사용자 보고로 추가). 위 두 결론은
호출자에게 서로 **반대되는** 행동을 요구한다: "저장소 없음"은 화면에 남은 목록을 **버려야** 하고, "모른다"는 직전
판단을 **유지해야** 한다. 그런데 판정자가 둘을 같은 `null`로 돌려주던 동안 호출자는 구별할 방법이 없어 안전한
쪽(유지)으로만 읽었고, 그래서 **저장소 아닌 폴더로 `cd` 하면 옛 목록이 그대로 남았다** — 위 단락이 금지한 바로 그
상태가 다른 경로로 재현된 것이다(사용자 보고: "깃 연결 안 된 터미널이 활성될 때 이전 깃 이력이 나온다").
그래서 판정자는 `.repo`(대상 확정)·`.none`(터미널이 답했고 그 폴더는 저장소가 아님)·`.unknown`(아무도 답을 못 줌)을
가려 돌려주고, **`.none`에서만** 목록·실패·선택·in-flight를 버린다. `.unknown`은 유지이므로 아래 원격 세션의 2순위
폴백은 규정대로 남는다. `.none` 무효화는 "지금 보는 저장소"(2순위 값) 자체는 놓지 않는다 — 그 값은 열려 있는
diff와 턴 스냅샷이 대상 저장소로 쓰는 것이고, 화면에서 지워야 하는 것은 목록이다.

**원격 세션에서는 터미널이 로컬 답을 주지 않는다.** OSC 7은 host authority를 버리고 경로만 남기고, 커널 조회는 로컬
`ssh` 클라이언트 프로세스의 cwd를 답한다 — 둘 다 원격 경로를 **로컬 파일시스템에 대고** 해석하게 만든다. 로컬에 같은
경로가 있으면 남의 저장소를 원격인 척 보여 주고, 거기서 stage/discard 하면 보고 있지도 않은 로컬 파일이 바뀐다.
그래서 OSC 7 authority가 로컬이 아니거나 알려진 ssh 세션이면 **로컬 판정의** 1순위를 비운다(링크 감지가 같은 함정을
같은 판정으로 막는다 — [ssh-integration.md §9.4](ssh-integration.md)). maru 통합을 거치지 않은 맨 `ssh`이고 원격
보고자도 없으면 두 신호가 다 비어 원격임을 알 수 없다는 한계는 링크 감지와 동일하다.

> **원격 축은 [remote-scm.md](plans/remote-scm.md)가 소유한다**(사용자 결정 2026-08-31 — 「원격일 때도 변경사항이
> 갱신되게」). 그 문서가 정한 것: 저장소 신원은 **(host, path) 쌍**이고, 활성 Term이 원격이면 도크는 **그 원격
> 저장소**를 ControlMaster 위에서 읽는다. 위 문단의 "1순위를 비운다"는 **로컬 판정**에 대한 서술로 남고, 원격
> 판정은 그 앞에서 갈린다(`remoteScmTarget`).
>
> **옛 규정 하나가 여기서 폐기됐다**: 「원격에서는 2순위(직전에 읽은 로컬 저장소)가 잡는다」. 그 규정은 *읽을 방법이
> 없다*는 전제 위에 있었는데 ControlMaster 사이드채널이 그 전제를 깼고, 실사용에서는 그것이 곧 **원격 pane을 보는
> 동안 로컬 목록이 남는** 증상이었다(사용자 보고 2026-08-31). 지금은 원격 목록을 보는 동안 `gitRepoTarget`이
> `.unknown`을 답한다 — 그 상태에서 로컬 walk-up은 뜻이 없기 때문이다.

**저장소 루트 walk-up은 저주기로 캐시한다.** `repoRootFor`는 경로 구성요소마다 `access(2)`를 쓰는데 이 판정이 매
프레임 돌기 때문이다(캐시가 없으면 blocking syscall이 초당 수천 번). 키는 cwd이고 cwd가 같아도 cwd 조회와 같은
주기로 다시 걷는다 — 같은 폴더에서 `git init`을 하면 답이 바뀌므로 영구 캐시는 틀리고, 그 주기가 반영 지연의 상한이다.

**cwd의 출처는 둘이고 순서가 있다.**

1. **OSC 7**(셸이 프롬프트마다 보고). 가장 싸다 — syscall이 없다.
2. **커널 조회**(`proc_pidinfo(PROC_PIDVNODEPATHINFO)`). OSC 7이 **빈 경우가 드물지
   않아서** 필요하다. 실측된 경우가 셋이다(2026-08-12).
   - maru의 셸 통합은 **zsh 전용**이라 bash/fish는 아예 안 보낸다.
   - **재개 Term은 평생 한 번도 안 보낸다.** 에이전트 세션 기록의 이어하기는 셸을
     `zsh -l -i -c "exec <provider> --resume <id>"`로 띄우는데, `-c`는 프롬프트를 한 번도 그리지 않아
     `_maru_osc7` precmd 훅이 돌지 않는다(`.zshrc`는 source되고 훅 등록도 되지만 precmd는 안 돈다).
   - `TerminalCore.fullReset`이 RIS(`ESC c`)에 보고된 cwd를 지운다. **다만 claude·codex는 RIS를 보내지 않는다** —
     pty 캡처상 둘 다 alt screen(`CSI ?1049h`)+`ED 2`로 화면만 지운다. 예전 판에 그 둘을 이 항목의 예로 든 것은
     실측과 다르다. 이 갈래는 실제로 RIS를 보내는 프로그램에만 해당한다.

   커널을 물어보면 셸 종류·화면 리셋·셸 기동 형태와 무관하게 답이 나온다.

   **알려진 결함: 낡은 OSC 7이 정확한 커널 값을 이긴다(미해결).** 1단이 값을 내면 2단을 보지 않는데, OSC 7은
   **프롬프트를 그릴 때만** 갱신되고 한 번 받으면 덮어쓸 때까지 남는다(지우는 유일한 경로는 RIS이고 그걸
   보내는 프로그램은 거의 없다). 그래서 셸이 보고 없이 움직이면 낡은 값이 계속 이긴다. 2026-08-13 제품에서
   재현했다 — 셸이 `maru3`를 OSC 7으로 보고한 뒤 `/`로 이동하면:

   | 무엇 | 값 |
   |---|---|
   | 셸의 실제 위치 (`pwd`) | `/` |
   | 커널이 보는 위치 (`lsof -d cwd`) | `/` |
   | maru가 답하는 값 | `/Users/…/maru3` |

   **`git=`까지 오염된다** — `/`는 저장소가 아닌데 `maru3`의 브랜치가 붙는다. 즉 폴더줄뿐 아니라 소스 컨트롤
   판정이 함께 틀린다. 재현은 `SHELL`을 OSC 7을 한 번 보낸 뒤 `cd` 하는 스크립트로 두고 앱을 띄운 다음,
   그 안에서 `maru sessions list`를 돌리면 된다(제어 평면은 maru 터미널 안에서만 자기 surface를 본다).

   **왜 아직 안 고쳤나.** 설계를 세 번 시도해 세 번 다 적대적 검증에서 뒤집혔다. 남은 제약을 적어 둔다 —
   다음 사람이 같은 벽을 다시 만나지 않도록.

   - **"커널을 항상 우선"은 답이 아니다.** 두 출처는 다른 질문에 답한다 — OSC 7은 *셸이* 선 곳, 커널은 *지금
     돌고 있는 프로세스가* 선 곳이다. 폴더줄이 원하는 건 전자다(다음 명령이 실행될 곳). 커널을 항상 쓰면
     `sh -c 'cd /tmp; …'` 같은 명령이 도는 동안 폴더줄과 저장소가 그리로 튄다.
   - **읽을 때마다 고르면 깜빡인다.** "포그라운드가 셸이면 커널" 같은 규칙은 프롬프트에 앉아 있을 때와 명령이
     도는 동안 답이 갈려, 사이드바가 두 값을 오간다. 지금은 일관되게 틀리기라도 하는데 그 일관성마저 깨진다.
     맞는 모양은 우선순위 전환이 아니라 **정정 이벤트**다 — 다른 셸이 앞에 있는 것을 관측한 순간 그 값을
     기록하고, 보고자가 돌아올 때까지 세운다.
   - **"새 OSC 7이 왔다"를 알 신호가 없다.** `bumpTitleGeneration`은 경로가 **바뀔 때만** 오르고,
     `observation.revision`은 아무 출력에나 오른다. 셸 이벤트(`recordShellEvent(.cwd_changed)`)는 매 보고마다
     기록되지만 `drainShellEventsForFrame`이 **활성 Term 하나만** 매 프레임 비우므로 제품 신호로 못 쓴다.
     해제 조건을 만들려면 이 신호부터 만들거나, 신호 없이 되는 조건(예: 포그라운드가 세션 루트 그룹으로 복귀)을
     써야 한다.
   - **관측 창을 놓치면 아무 일도 안 일어난다.** 포그라운드 이름은 500 ms 주기라, 셸이 프롬프트에 앉은 순간을
     한 번도 샘플하지 못하는 형태(`sh -c "cd /; 긴명령"`)는 어떤 사건 기반 규칙으로도 안 잡힌다. 대화형
     사용에서도 진입 후 최대 0.5초는 옛 값이 보인다.
   - **판정은 `pty/macos.zig` 안이어야 한다.** 필요한 재료(`child_pid`, 포그라운드 그룹)가 거기 있고,
     `app_session`이 pid·libproc을 만지지 않는 것이 규약이다(`term_runtime_backend.zig`의 seam 주석). 관측
     구조체에 필드를 더하는 것 자체는 wire 파손이 아니다 — `bell_count`·`mouse_tracking_mode`처럼 "구 host면
     기본값 = 기존 동작"이라는 호환 패턴이 이미 있다. 비용은 `C3-3b2b0` exact-capacity 게이트 갱신이다.

   **닿지 않는 곳이 하나 있다.** 영속 세션 호스트(`session.keep-alive-after-quit` — 값과 설명은 [설정](configuration.md)이 단일 출처)로
   연 Term은 PTY와 그 자식이 `maru-sessiond` 프로세스에 살아서 GUI 프로세스의 `proc_pidinfo`가 닿지 않는다
   (pid 네임스페이스 문제가 아니라 소유 프로세스가 다른 문제다 — `session_host/remote_term_backend.zig`의
   `processCwd`가 그래서 `null`을 낸다). 그 Term에서는 OSC 7이 **유일한** 출처다. 메우려면 host가 관측
   payload에 cwd authority를 실어야 하고 그 순서는
   [Session host kernel cwd parity 구현 계획](plans/session-host-kernel-cwd.md)이 소유한다. **축이 갈리지는 않는다** — 폴백이
   없어도 GUI와 제어 평면이 같은 지점을 거치므로 둘 다 함께 비고, 한쪽만 아는 상태가 되지 않는다.

   **이 2단 규칙은 게이트가 강제한다**(`tests/boundary/cwd_axis.zig`, `check-boundaries`). 규칙이 주석에만
   있던 2026-08-10~08-12 사이에 소비자 **여섯**이 관측(`observation.cwd`)을 직독해 축이 갈렸고, 셸 통합이
   없는 셸과 재개 Term에서 사이드바·상태바·검색·아카이브 범위 칩·대화 매핑이 한꺼번에 죽었다. 게이트는
   정당한 직독이 일어나는 **함수 이름을 파일별로 고정**하고(별칭은 개수로) — "0건"은 세울 수 없는 규칙이다
   (Q1 직독이 실재한다). 개수만 고정하던 첫 판은 같은 파일에서 정당한 직독 하나를 빼고 부정한 직독 하나를
   더하면 총합이 보존돼 통과했다(실제로 뚫렸다). 새
   소비자는 `git_ops.termCwd`(저장소 판정) 또는 `git_ops.termCwdForDisplay`(표시)를 쓰고, 직독이 맞다면
   그 재고에 **이유와 함께** 올려야 한다.
   - 베이스: 공개 libproc API다(clean-room — 공개 API 호출만 하고 레퍼런스 코드 표현은 옮기지 않는다,
     [project-rules.md](project-rules.md)).

     **레퍼런스가 우리와 같지 않다 — 예전 문장은 틀렸다.** 여기엔 "iTerm2·Ghostty가 같은 목적으로 쓰는 사실상
     표준 경로"라고 적혀 있었는데, 레퍼런스 소스로 확인하니 **Ghostty는 커널을 전혀 묻지 않는다**
     (`references/ghostty` @ `b2fa2931b`, 2026-08-13 확인). 제품 코드에서 pwd를 세우는 곳은 OSC 7 핸들러
     (`stream_terminal.zig`)와 스냅샷 복원(`snapshot/terminal.zig`) 둘뿐이고, `libproc`·`proc_pidinfo`·`lsof`·
     `KERN_PROC`은 트리 전체에 없다. iTerm2는 레퍼런스에 없어 **확인하지 못했다** — 확인 전까지 근거로 쓰지 말 것.

     대신 Ghostty는 **모른다고 말할 수 있게** 한다: 빈 OSC 7(`OSC 7 ;`)을 pwd 리셋으로 받아, macOS proxy icon을
     낡은 값으로 그리는 대신 **숨긴다**(`stream_handler.zig` `reportPwd`). 터미널이 추측하지 않는 설계다.

     같은 계열 중 커널을 함께 쓰는 구현도 있다 — **확인된 OSC 7 → 커널(`/proc` 또는 `lsof`) → 확인 안 된
     (재생된) OSC 7 → worktree 루트** 4단으로 내려가는 방식이다. 동기는 같다(OSC 7 을 영영 안 내보내는 셸 —
     **agent TUI**, minimal sh). 다만 그건 "새 split을 어디서 시작할까"라 **반드시 답이 있어야 하는** 질문이고,
     우리 폴더줄은 "모른다"가 유효한 답인 질문이라 그 방식을 그대로 옮기면 안 된다. 비용도 다르다 — 그런
     구현은 macOS에서 `lsof` 서브프로세스(100~500 ms)라 split 순간에만 물을 수 있고, 우리 `proc_pidinfo`는
     0.78 µs라 상시 축에 넣을 수 있다.
   - **누구의 cwd를 묻는가**: foreground process group의 **leader가 아닌 구성원 → leader → 세션의 child** 순이다.
     `PGID를 그대로 PID로 쓰면 안 된다` — 제품 spawn은 `/usr/bin/login`이 wrapper로 남고 실제 셸이 같은 그룹의
     child로 돌아서, leader만 조회하면 **wrapper의 cwd(홈 등)** 를 읽고 저장소가 통째로 틀린다(적대적 검증에서
     실제로 재현했고 `processCwd`의 login wrapper 테스트가 그 회귀를 막는다). claude·vim처럼 자기 그룹을 만든
     프로세스는 구성원이 하나뿐이라 leader가 곧 정답이다. 열거와 조회 사이의 PID 재사용은 `getpgid` 재확인으로
     막는다 — 안 그러면 무관한 프로세스의 cwd를 읽어 조용히 엉뚱한 저장소가 잡힌다.
   - **관측(`read_observation`)이 아니라 별도 seam**(`TermRuntimeBackend.process_cwd`)이다. 관측 캐시는 title
     generation이 안 바뀌면 early-return하므로 정작 필요한 순간에 안 돌고, 거기 넣으면 매 프레임 syscall이 된다.
     syscall이라 OSC 7이 빈 경우에만 부르고 ≈0.5초 주기로 캐시한다(활성 Term이 바뀌면 즉시 다시 묻는다).
   - **원격(session-host keep-alive) Term은 이 폴백이 없다** — PTY와 그 자식이 host 데몬 프로세스에 살아 GUI
     프로세스의 조회가 닿지 않는다. 메우려면 host가 관측 payload에 cwd를 실어야 하고 그건 wire schema 변경이라
     [session-host-upgrade.md](session-host-upgrade.md)의 호환 규약을 건드린다(별도 슬라이스). `keep_alive_after_quit`
     기본값이 꺼짐이라 기본 경로는 영향받지 않는다.

**턴 스냅샷은 그것을 뜬 저장소에서만 유효하다.** 다른 저장소에 그 tree OID를 넘기면 `git diff <남의 tree>`가 그
저장소 안에서 해석돼 "에이전트가 방금 바꾼 것" 섹션이 엉뚱한 diff로 채워진다 — 같은 프로젝트의 다른 clone이나
`git worktree`면 object DB에 그 tree가 실제로 있어 **조용히 성공한다.** 그래서 스냅샷을 만들 때뿐 아니라 **소비할
때도** 저장소를 대조한다(어긋나면 그 섹션 없이 읽는다). 소비 쪽에 두어야 저장소를 바꾸는 모든 경로가 덮인다.

**활성 터미널이 다른 저장소로 옮겨 가면 목록을 다시 읽는다.** 이게 없으면 `refreshGitStatus` 트리거가 도크 뷰 전환·
`.git` 감시·턴 스냅샷뿐이라 탭을 옮기거나 `cd`해도 목록이 옛 저장소에 멈추고 감시자도 옛 `.git`을 계속 본다. 저장소가
갈리면 ⑴ 옛 결과·실패·선택을 버리고(남의 저장소 상태가 화면에 남지 않게) ⑵ **옛 요청을 포기하며**(늦게 온 응답이
새 화면을 덮지 않게 — in-flight를 0으로 두면 기존 `request_id` 대조가 그 응답을 걸러낸다) ⑶ 감시 대상을 새 `.git`으로
옮긴다. **cwd를 모를 때는 아무것도 하지 않는다** — "모른다"를 "저장소 없음"으로 읽으면 diff를 여는 순간 목록이 사라진다.

### 3.5.1b 커밋 메시지 초안은 저장소마다 따로 든다 (2026-08-16 사용자 결정)

목록·스크롤·선택은 저장소가 갈릴 때 **버린다**("다른 목록이므로 의미가 없다"). 메시지는 다르다 — **사용자가 쓴
글**이라 버리면 예고 없이 사라지고, 그대로 두면 다른 저장소를 향해 쓴 글로 커밋하게 된다. 그래서 버리지도 두지도
않고 **저장소 루트 경로를 키로 따로 든다**.

- **워크트리도 자연히 갈린다.** 링크된 워크트리는 루트 경로가 다르고(`repoRootFor`가 `.git` 파일도 저장소로 본다)
  그 값이 곧 키다. VS Code가 워크트리를 별도 저장소 행으로 세우는 것과 같은 단위다.
- 저장소를 떠날 때 담고 돌아올 때 꺼낸다. **비운 것도 뜻이므로** 빈 글은 초안을 지운다.
- 초안 수에 상한을 두고(32) 넘으면 가장 오래된 것부터 버린다 — 무한히 쌓으면 세션이 오래 살수록 메모리가 늘고,
  사용자는 몇 달 전 저장소의 초안을 기억하지 못한다.
- 커밋에 **성공하면** 상자와 그 저장소의 초안을 함께 비운다(그 글은 이제 커밋에 들어갔다).

### 3.5.1c 여러 저장소·워크트리를 한 목록에 (설계 확정 2026-08-16, 구현 진행 중)

**목록의 단위는 저장소가 아니라 워크트리다.** 링크된 워크트리는 자기 루트·자기 index·자기 HEAD를 갖는
독립된 작업 대상이므로, 한 줄로 접히는 그룹 하나가 곧 워크트리 하나다(사용자가 VS Code 화면을 목표로
제시했다 — 거기서도 워크트리가 별도 행이다).

```
Changes                                        [+]
 › ⑂ maru3              ⑂ main        ⟳ ⌫ ⇱ ⑂ ✓ …
 › ⑂ maru3/wt-review    ⑂ review-wt   ⟳ ⌫ ⇱ ⑂ ✓ …
 ⌄ ⑂ payhere-pos-pc     ⑂ refactor/…  ⟳ ⌫ ⇱ ⑂ ✓ …
     커밋 메시지…
     [ 커밋 ∨ ]
     스테이지된 변경 (2)
       …
```

**무엇이 목록에 뜨는가 — 활성 터미널이 선 저장소와 그 워크트리**(사용자 결정 2026-08-17로 **좁혔다**).

- 처음 결정(2026-08-16)은 "열려 있는 터미널들이 선 저장소 전부"였다. 실제로 그 화면을 보니 탭을 여럿
  띄운 사용자에게 **여덟 줄**이 서고, 그중 무엇이 지금 보고 있는 것인지가 사라졌다(사용자 화면 제시).
- 그래서 목록의 뿌리는 **활성 터미널의 cwd 하나**다. 거기서 저장소 루트를 구하고 `git worktree list
  --porcelain`으로 그 저장소의 워크트리를 펼친다 — 워크트리가 여럿이면 줄도 여럿이지만, **한 저장소의
  것**이라 "지금 무엇을 보고 있나"가 유지된다.
- **활성 Term이 터미널이 아니면(파일·원격) 목록을 비우지 않는다.** `termCwd`가 주는 null은 "저장소가
  없다"가 아니라 "물어볼 곳이 없다"이고(§3.5의 3-상태), 그때는 마지막으로 읽은 저장소가 그대로
  남는다(`ensureListed`). **"마지막 터미널"을 따로 들지 않는 이유**가 이것이다: 그 값은 `git_repo`와
  같은 사실이라 두 곳이 같은 것을 들면 어느 쪽이 최신인지 판정이 하나 더 생긴다. 다음 터미널 활성화가
  올 때까지 화면은 **현상 유지**다.

**접기 상태는 세션 한정이다.** 목록 자체가 매번 새로 계산되는 값이라 접힘만 저장해도 다음 실행의 목록과
대응이 보장되지 않는다 — 섹션 접힘이 workspace에 저장되지 않는 것과 같은 규율(§3.5.2).

**⌘Enter는 지금 편집 중인 상자의 저장소로 간다.** 포커스가 곧 대상이다. 상자가 여럿이므로 "활성 저장소"
같은 두 번째 개념을 만들면 사용자가 보는 것과 커밋되는 곳이 갈릴 수 있다. 포커스가 없으면 아무 일도
하지 않는다.

**읽기는 배치를 줄이고 순차로 돈다(2026-08-17 정정).** 처음에는 근거를 §6의 `index.lock`으로 적었는데
그건 **같은 저장소** 안의 규율이다 — 저장소가 다르면 lock 파일이 달라 겹치지 않는다. 실제 비용은 **몇
개의 프로세스를 띄우는가**이고, 거기서 답이 갈린다.

- **비활성 저장소는 `status --porcelain=v2 --branch` 하나만** 읽는다. 머리 줄에 필요한 것(브랜치·분리
  HEAD·ahead/behind·파일 개수)이 전부 그 출력에 있다. `numstat` 셋은 **펼쳐서 파일 줄을 그릴 때만** 쓰인다.
- 그래서 저장소 여덟이면 프로세스가 48개가 아니라 **활성 한 벌 + 나머지 하나씩**이다. 병렬로 4배 빨리
  돌리는 것보다 이쪽이 크다.
- **활성 한 벌에서 셋이 빠졌다(2026-08-27).** `merge-base`·브랜치 범위 `--name-status`·`--numstat` 은
  「브랜치에 COMMIT 됨」섹션이 2026-08-14 의 2섹션 재작성(P1a)에서 사라진 뒤로 **소비자 없이 매 읽기마다
  돌고 출력이 버려지고 있었다.** 화면(`scm_view`)과 배관(`git_backend`)이 다른 파일이라 섹션을 지우면서
  그쪽까지 따라가지 않은 것이다.
- **활성 저장소를 먼저** 읽는다. 사용자가 보고 있는 것이 가장 먼저 채워진다.
- **병렬은 지금 열지 않는다.** backend가 결과 슬롯 하나·in-flight 하나라 큐와 저장소별 결과 구조가
  필요하고, 위 둘을 하면 남는 이득이 작다. 필요해지면 **재고 아니라 측정으로** 연다.

목록에 상한을 두고(8) 넘으면 **그 사실을 화면에 적는다** — 조용히 자르면 사용자는 없는 저장소를 없다고
믿는다.

**상자는 저장소마다 하나다(②b).** 그 그룹의 머리 줄 바로 아래에 입력이, 그 아래에 버튼이 온다.

- **포커스는 상자 하나**다. "편집 중"만 아는 플래그로는 부족하다 — 상자가 여럿이면 글자가 **어디로
  가는지**를 두 번째 개념이 정하게 되고, 그러면 사용자가 보는 곳과 글자가 가는 곳이 갈린다. 그래서
  포커스는 **저장소 경로**로 든다.
- 편집 중이 아닌 상자는 그 저장소의 **초안 글**을 보여 준다(§3.5.1b) — 화면에 있는 글이 곧 그 저장소로
  커밋될 글이다.
- 상자를 옮기는 것은 저장소를 옮기는 것과 같다: 쓰던 글을 그 저장소 초안으로 담고 새 상자의 초안을 꺼낸다.
- **버튼은 그 저장소로 커밋한다.** 다만 지금은 **활성 저장소만** 실행한다 — 스테이지 여부·메시지 판정이
  그 저장소의 목록 읽기에서 나오는데 비활성 저장소는 머리 줄 요약(개수)만 있기 때문이다. 그 상태에서
  누르면 "그 저장소를 먼저 여세요"라고 적는다(감추지 않는다).

**목록이 삼킨 것들 — 적대적 검증 3~5회차에서 드러난 계약(2026-08-17).** 상자·머리 줄이 목록 항목이
되면서 "목록 밖"을 전제하던 규칙이 셋 깨졌다. 셋 다 같은 종류다: **화면에 없는 것이 있다고 믿는 코드.**

- **"변경 사항 없음"은 그 그룹의 줄이다.** 스크롤 영역 위쪽에 직접 그리던 문장이 저장소 머리 줄과
  같은 자리에 **겹쳐** 둘 다 못 읽는 화면이 됐다(제품 캡처로 확인). 저장소가 여럿이면 "어느 저장소가
  비었나"도 그 그룹의 줄이라야 말이 된다. 컴포넌트의 `empty_notice` prop은 지웠다.
- **목록 창 = 도크 content − (탭 줄 + 요약 줄 + 브랜치 줄).** 커밋 줄은 이제 목록 항목이므로 창에서
  빼지 않는다. 빼면 호스트가 세는 창이 `build`가 세우는 창보다 작아져 **항목이 있는데도 아래쪽이 안
  그려지고** 스크롤이 끝을 지나 빈 자리로 간다.
- **탭 이름 옆의 개수는 활성 탭과 무관하다**(2026-08-20 사용자 보고). 히스토리·에이전트 탭의 투영이
  `file_count`를 0으로 두는 바람에, `변경 사항 (285)`인 저장소에서 다른 탭에 서면 `변경 사항 (0)`이 됐다 —
  탭을 눌러야 숫자가 돌아왔다. 그 수는 **작업트리가 답하는 사실**이라 무엇을 보고 있든 참이고, `(0)`은
  "바뀐 것이 없다"는 틀린 진술이다(요약 줄을 히스토리에서 **끄는** 것과 같은 이유이고, 반대 방향의 답이다 —
  요약은 그 탭에서 **뜻이 없어** 자리까지 없애지만, 탭 이름의 개수는 그 탭 자신을 가리키므로 늘 참이어야 한다).
  **그 수를 알려고 목록 모델을 만들지 않는다**(적대적 검증 4회차): `build`는 행마다 numstat 전체를 훑는데
  (`findDelta`) 그 숫자는 탭 라벨에 쓰이지 않는다 — 285파일·"모두 보기" 상태에서 실측 378µs 대 12.8µs이고,
  이 자리는 히스토리·에이전트 탭의 **매 프레임 투영**이라 그 차이가 그대로 낭비가 된다. 세는 술어
  (`scm_view.belongs`)는 목록·섹션 배지와 같은 것을 쓰고, 두 합산 경로가 같은 답을 낸다는 것은 테스트가 못 박는다.
- **스크롤 상한은 지금 그린 목록이 정한다**(같은 날). 상한을 내는 함수가 활성 탭과 무관하게 **작업트리
  모델을 다시 세고** 있었다. 그래서 ⑴ 히스토리·에이전트 탭은 자기 목록과 무관한 상한이 걸려 — 작업트리가
  깨끗하면 0이라 — 커밋이 몇백 개여도 **휠도 스크롤바 드래그도 먹지 않았고**(막대 기하는 `max_offset == 0`
  이면 아예 null이라 잡히지 않는다), ⑵ 변경 사항 탭에서도 파일 줄만 세어 저장소 머리 줄·커밋 상자가 빠진
  만큼 목록 끝에 닿지 못했다. 상한의 단일 출처는 **투영**(`scm_dock.project`)이다 — 목록을 만든 자리가 그
  목록의 높이를 아는 유일한 자리이고, 휠·드래그·클램프는 그 값을 읽기만 한다. 투영이 없으면 상한도 버린다:
  옛 값이 남으면 아무것도 안 그린 화면에서 막대가 서고 휠이 먹는다.
- **켜진 컨트롤의 글자색은 `accent_bar`다**(P6 실측). rich 토큰셋의 `focus_accent`는 `sidebar_active`
  (배경색)를 밝힌 값이라 **글자에 쓰면 오히려 어둡다** — 켜진 칩이 (128,132,140)인데 꺼진 `muted_fg`가
  (207,207,207)이라 **꺼진 쪽이 더 밝은** 화면이 나왔다(제품 캡처로 확인). 배경 role을 글자에 쓰지 않는다.
- **방금 누른 동작의 결과 줄은 세 탭 모두에 있다**(P6에서 추가). 그 줄(`notice`)은 처음에 변경 사항 탭의
  목록에만 있었다. **쓰기를 거는 컨트롤은 전부 변경 사항 탭에 있지만**(커밋 상자·머리 줄 동작·브랜치 줄의
  `가져오기`), **결과는 탭을 따라와야 한다** — 커밋한 직후 히스토리 탭으로 옮겨 방금 만든 커밋을 확인하는
  것이 자연스러운 흐름인데, 옮기는 순간 방금 읽은 답이 사라지면 커밋이 됐는지 알 길이 없다. 성공·실패 둘
  다 이 자리를 쓴다.
  - **브랜치 줄은 변경 사항 탭에만 선다.** `projectHistory`·`projectAgentTurns`가 `.branch = ""`를 내고,
    `build`는 그때 줄 높이를 0으로 두는 데 그치지 않고 **자식을 빈 배열로** 둔다 — `가져오기`와 `∨`는 그
    두 탭의 tree에 **존재하지 않는다**. P6a는 "`가져오기`는 어느 탭에서도 눌린다"를 결과 줄의 근거로 적었는데
    그 커밋이 `.branch = ""`보다 **나중**이라 전제가 이미 깨져 있었다. 결론(세 탭에 결과 줄)은 위의 다른
    이유로 옳아서 오래 드러나지 않았다 — **결론이 맞았다고 근거까지 맞은 것은 아니다.**
- **상자가 화면에서 사라지면 편집을 붙들지 않는다.** 목록에서 빠졌거나 그룹이 접히면 포커스를 뗀다
  (글은 초안으로 남는다). 스크롤로 창 밖에 있는 것뿐이면 반대로 **창을 상자 쪽으로 끌어온다** —
  글자는 들어가는데 화면은 그대로인 상태가 없어야 한다.

**주/부 판정은 git이 준다.** `git worktree list --porcelain`의 **첫 줄이 주 워크트리**다. 우리가 선
자리(`repoRootFor(cwd)`)로 판정하면 링크된 워크트리에 선 터미널에서 **신원이 뒤집힌다** — 그 워크트리가
주 워크트리로, 진짜 주 워크트리가 딸린 것으로 그려진다(제품 캡처 2026-08-17). 아이콘이 그 판정을 보여
주므로 화면이 곧바로 거짓말이 된다.

**펼친 저장소는 활성이 아니어도 파일 줄을 낸다(②d, 2026-08-17).** 사용자가 "VS Code는 설정에 따라 그냥
다 읽지 않느냐"고 물어 다시 봤고, 우리 코드가 이미 그렇게 되어 있었다: **파일 줄의 실체는 `status`
하나에서 나온다**(경로·그룹·상태 문자·스테이지 동작). `numstat` 셋은 **증감 숫자와 요약 줄에만** 쓰인다. 그래서 비활성 저장소를 펼쳐 목록을 세우는 데 드는 **추가 프로세스는 0개**다 — 머리 줄
읽기가 이미 그 출력을 가져왔고, 지금까지는 개수만 세고 버렸을 뿐이다.

- 증감 숫자는 **비운다**(`unknown_delta`). 0으로 적으면 "안 바뀐 파일"이라고 거짓말한다 — 추적되지 않은
  파일·충돌이 쓰는 길과 같다. 그 저장소를 열면(터미널이 그리로 가면) 숫자가 채워진다.
- 그래서 **쓰기 게이트도 바뀐다**: 무엇을 커밋·스테이지하는지 화면에 있으므로 막을 이유가 없다. 아직
  **읽지 못한** 저장소만 막는다("그 저장소를 아직 읽지 못했습니다").
- 대신 **행·그룹 intent가 저장소를 싣는다**(`RowRef`·`SectionRef`). 모델이 저장소마다 따로 서므로 같은
  번호가 저장소마다 다른 파일이다 — 인덱스만 실으면 아래 그룹의 파일을 눌렀는데 위 저장소의 파일이
  열리고, 더 나쁘게는 **거기에 스테이지된다**. 강조(`선택된 행`)도 같은 이유로 (저장소, 인덱스) 쌍이다.
- **섹션 접힘은 목록 전체가 공유한다**(저장소별로 두지 않는다). 그룹 이름이 같은 뜻이고, 저장소마다
  따로 접히면 "스테이지된 변경을 접었는데 아래 저장소는 펼쳐져 있다"가 되어 읽기 어렵다.
- 쓰기가 끝나면 **그 저장소를** 다시 읽는다: 활성이면 목록 읽기, 아니면 그 머리 줄 읽기를 낡았다고
  표시한다. 안 그러면 방금 스테이지한 파일이 그 자리에 그대로 남는다.

**저장소 머리 줄의 동작 아이콘(②c).** 오른쪽 끝에 **새로고침 ⟳ · 전체 스테이지 ＋** 둘이 앉는다.
목업의 커밋 ✓는 **넣지 않는다** — 그 그룹 안에 이미 커밋 버튼 줄이 있어 같은 동작이 두 자리가 된다
(VS Code에 ✓가 있는 이유는 그쪽 커밋 상자가 목록 밖에 하나뿐이기 때문이다). 아이콘은 **이미 있는
자산**(`reset`·`plus`)을 쓴다. 규율은 파일 행 동작과 같다: **히트 사각형은 늘 있고 글리프만 호버를 따른다**(그래야 tree가
포인터마다 달라지지 않는다).

**자리는 예약하지 않고, 호버하는 동안 그 자리의 글자를 안 그린다**(2026-08-19 지적으로 예약을 버렸고,
2026-08-21 지적으로 "덮어 그린다"까지 버렸다). 늘 예약하면 — 호버할 때만 자리를 만들면 브랜치 칩과 개수
배지가 마우스를 따라 움직이기 때문에 그렇게 했었다 — 아이콘은 호버해야 나타나므로 **평소 화면에는 이유를
말하지 않는 빈 띠**가 52px 남았다. 네 번째 답이 지금 것이다:

| | 예약한다 | 호버 때만 비킨다 | 덮어 그린다 | **호버 동안 안 그린다**(지금) |
|---|---|---|---|---|
| 평소 화면 | 빈 띠가 남는다 | 깔끔 | 깔끔 | 깔끔 |
| 호버 순간 | 안 움직인다 | 배지·브랜치가 **밀린다** | 안 움직인다 | 안 움직인다(사라질 뿐) |
| 겹침 | 없음 | 없음 | **남는다** | 없음 |

**"덮어 그린다"가 통하지 않은 이유는 층을 잘못 골랐기 때문이다.** 이 도크는 배경 quad를
`layers.bottom`(2)로 내리는데(`app_session/scm_dock.zig`), 렌더러의 네 패스에서 **2만 셀 텍스트 앞**이다.
그 층에 낸 사각형은 이미 그린 글자를 덮지 못하고, 그래서 새로고침 아이콘이 브랜치 이름 위에 그대로 겹쳐
보였다(사용자 캡처 2026-08-21) — 덮개는 **호버 색까지 맞춰 놓고도** 글자를 하나도 못 가렸다.

**렌더러가 못 하는 일이 아니다**(2026-08-21 정정 — 앞 판은 "원리적으로 통하지 않는다"고 적었다). 실측에서
같은 배경 quad를 layer 3으로 올리자 도크 글자를 **전부** 덮었다(Chrome Lab `scm_repo_hover` 캡처). 층별
사실은 이렇다:

| 층 | 그리는 자리 | 글자를 덮나 |
|---|---|---|
| `layers.bottom`(2) | 셀 텍스트 **앞**(유일) | 못 덮는다 |
| `layers.under`(0) | 셀 텍스트 **뒤**(이름과 반대다 — `isBelowText`가 그 함정을 적어 뒀다) | 덮는다 |
| `layers.over`(1)·그 밖의 값 | 오버레이 레이어 맨 위 | 덮는다 |

그러니 지금 답을 고른 이유는 "불가능해서"가 아니라 **브랜치·개수 배지·아이콘 셋이 자리 둘을 다투기
때문**이다. 텍스트 위 quad를 쓰면 브랜치를 마스크로 가리고 배지를 살릴 수 있지만, 그러려면 아이콘이 배지
왼쪽으로 옮겨 가고 그 자리가 개수 자릿수(배지 폭)를 따라 흔들린다. 그 맞바꿈을 할 이유가 생기면 그때
연다 — 지금은 호버하는 동안만 배지가 안 보이는 것이 더 싼 값이다.

그래서 겹침은 **그리지 않는 것**으로 없앤다: 호버하는 동안 그 자리의 브랜치·개수 배지·상태 라벨을
안 내고, 남는 저장소 이름은 아이콘 띠 왼쪽에서 멈춘다(길면 말줄임). 자리는 그대로라 아무것도 움직이지
않는다. 아이콘을 그리는 쪽과 글자를 접는 쪽은 **같은 판정 하나**(`repoActionsLeftX`)를 본다 — 두 벌로
두면 한쪽만 호버를 놓쳐 다시 겹친다. 히트 사각형은 그대로 두므로 클릭 판정은 안 바뀐다: 어차피 호버해야
누를 수 있어 "보이는 것과 눌리는 것"이 갈리지 않는다.

**그 줄의 가로 자리 셋**(같은 지적에서 함께 고쳤다):

- **아이콘 열은 하나다**(`iconColumnX()` = 왼쪽 여백 + 화살표 칸 + 한 칸). 머리 줄의 종류 아이콘, 파일
  행의 아이콘, 안내·`더 보기` 글자가 전부 이 열에 선다. 그전에는 아이콘만 화살표 칸 **바로 뒤**(간격 0)에
  붙어 있었고, 그룹 제목·브랜치 글자는 이미 한 칸 띄운 자리에 있었다 — 즉 아이콘만 혼자 6px 왼쪽이었다.
- **배지 왼쪽 여백은 `gap`의 두 배다**(`badgeGapPx()`). 배지는 칠해진 알약이라 같은 간격이면 시각 무게
  때문에 브랜치 이름에 달라붙어 보인다(사용자가 "겹쳐 보인다"고 읽었다).

**게이트는 "그 저장소를 읽었나"다**(②d가 전제를 바꿨다 — 처음 결정은 "비활성은 새로고침만"이었지만
펼친 저장소가 파일 줄을 내면서 "무엇이 대상인지 화면에 없다"가 더는 사실이 아니게 됐다). 새로고침은
읽기라 언제나 실행하고, 전체 스테이지는 그 저장소의 status를 들고 있을 때 켠다. 막을 때는 **감추지
않고** 비활성으로 표시한다 — 눌리면 이유를 적는다.

**커서와 호버는 component가 선언한다.** 커서 모양(`ui/style.zig`의 `CursorHint` — 상자 `.text`, 누를 수
있는 줄 `.press`)은 published tree에 실리고 host는 그것을 NSCursor로 옮기기만 한다. host가 "무엇을 누를
수 있나"를 다시 추론하면 판정의 주인이 둘이 되고, 실제로 이 도크는 탐색기 행 판정을 물려받아 **전체가
화살표**였다(사용자 지적 2026-08-17). 같은 이유로 **텍스트 입력면은 호버로 배경이 바뀌지 않는다**
(`PaintStyle.state_fill = false`): 거기서 마우스가 뜻하는 것은 "누를 수 있다"가 아니라 "여기에 caret을
놓는다"이고, 그 신호는 커서가 이미 낸다 — 면까지 밝아지면 편집 중임을 말하는 테두리와 섞인다.

**상자도 넘치면 스크롤바를 낸다**(사용자 요청 2026-08-17). 상자는 8행에서 자라기를 멈추고 안에서
스크롤되는데, 그때까지 화면에 아무 표시가 없어 **글이 잘린 것처럼** 보였다. 막대는 목록 스크롤바와
같은 기하 함수(`scroll_area.scrollbarGeometry`)를 쓰고 — 두 곳이 각자 비율을 재면 같은 화면에서 막대
길이 규칙이 갈린다 — 자리(`commitGutterPx`)는 **늘 비워 둔다**: 나타났다 사라지며 폭이 바뀌면 글이
통째로 다시 접혀 커서가 튄다(목록이 gutter를 상시 소유하는 것과 같은 이유).

**막대 자체는 여전히 그리기 전용이고, 상자는 휠로 굴린다**(2026-08-18 사용자 결정으로 개정). 초판은
"상자 안 스크롤은 caret이 끌고 가고(§12.2), 끌어서 옮기는 것은 목록 스크롤바의 일"이라고 적었는데, 그
근거가 사실과 어긋나 있었다 — ⑴ **휠은 상자 위에서도 목록을 굴렸다**(대상 판정이 "도크 content 안"이라
상자를 구별하지 않았다), ⑵ SCM 도크에는 스크롤바 드래그 경로가 **아예 없다**(`scrollbar_drag_target`은
파일 트리·사이드바·오버레이뿐이라 목록 막대도 못 끈다). 그래서 상자 안 스크롤에 **포인터로 닿는 길이
하나도 없었다**: 막대는 "글이 더 있다"고 말하는데 그 위에서 굴리면 다른 것이 움직였다.

휠 규칙 셋:

- **편집 중인 상자만 굴린다.** 스크롤 위치(`scm_commit_first_row`)는 그 상자에만 실린다(포커스 없는
  상자의 투영은 늘 첫 행부터다) — 다른 상자를 굴리면 화면은 그대로인데 상태만 움직인다. 그 상자를
  굴리려면 눌러서 편집을 시작하면 되고, 그건 이미 있는 길이다.
- **끝에 닿아도 소비한다**(도크·탐색기와 같은 규율). 잔여만 쌓인 틱도 상자의 것이다 — 안 그러면
  트랙패드로 천천히 굴리는 동안 뒤의 목록이 대신 움직인다.
- **글이 다 보이면 넘긴다.** 그때는 막대도 안 그려지고, 삼키면 상자 위가 죽은 구역이 되어 목록이
  안 굴러간다(짧은 메시지가 기본 상태다).

포인터가 상자를 뜻하는지는 **클릭(포커스 해제)과 같은 함수**가 판정한다(`pointInCommitBox`) — 두 곳이
각자 재면 경계 한 픽셀에서 갈리고, 그 갈림은 "가장자리에서만 휠이 목록으로 샌다"처럼 재현하기 어렵다.
부호·잔여·클램프는 목록·사이드바가 쓰는 순수 함수(`scroll_area.State.scrollByWheel`)가 그대로 정한다.
**목록 막대는 끌 수 있다**(2026-08-19). 그전까지 이 도크의 스크롤바는 그림만 있었다 — tree가 drag를 선언하는데
host가 `dispatch` 결과의 `.drag`를 흘렸다. 새 기계는 만들지 않았다: 도크는 이미 캡처 수명을 갖고 move/up을
자기 tree로 보내고 있었고(파일 트리의 carry-verdict 기계는 그쪽이 매 프레임 재발행하기 때문에 있다), 잡은
자리·track 빈 곳 점프·틱 합치기는 `scroll_area.Drag`가 이미 소유한다. **끄는 동안 기하가 바뀌면 드래그를
끝낸다** — 잡을 때의 기하로 계속 계산하면 손가락과 화면이 어긋난다.

**커밋 상자 막대는 여전히 그리기 전용이다** — 그쪽의 포인터 경로는 휠이다(위 문단).

**커밋 버튼 줄은 면(28px)과 아래 여백(8px)이다 — 칠은 면만 받는다.** 줄 카드가 통째로 칠해지면 파랑이
여백까지 덮고, 글자는 면 안에서 가운데라 **그 띠의 가운데보다 위에** 앉는다(사용자 지적 2026-08-17).
그래서 면을 자식 노드로 세우고 칠·action·호버 해석을 전부 거기에 둔다 — 여백을 눌러도 커밋이 걸리지
않는 것은 덤이 아니라 같은 규칙의 결과다.

**사라진 워크트리는 줄을 세우지 않는다.** `git worktree list --porcelain`이 `prunable`로 말해 준다 —
디렉터리가 없어진 워크트리다. 그 줄을 그리면 **커밋 상자가 달린 빈 줄**이 되고(눌러도 할 수 있는 일이
없다) 읽기는 실패만 되풀이한다. 아래 "읽지 못함"은 그것 말고의 실패(권한·경합)를 위한 안전망이다.

**읽지 못한 저장소는 "0건"이 아니다.** 실패를 캐시에 기록하지 않으면 그 저장소는 계속 "아직 안 읽은
것"이라 **매 tick git을 다시 띄우고**, 읽기가 하나씩 도는 규율 때문에 뒤의 저장소는 차례가 영영 오지
않는다(사라진 워크트리 하나면 충분하다). 그래서 실패도 싣고 **5초 쉬었다** 다시 읽으며, 머리 줄은
`읽지 못함`이라고 적는다 — 배지 없음(=변경 없음)도, `읽는 중…`(=곧 온다)도 그 상태에서는 거짓말이다.

### 3.5.1d 옛 단일 저장소 뷰에서 무엇이 그대로 쓰이나

P3c까지 도크는 **활성 터미널이 선 저장소 하나**를 봤다. 목록으로 가면서 바뀌는 것은 **모델**이다 — "지금 저장소"
하나가 아니라 N개를 읽고, 커밋·스테이지 intent가 **어느 저장소를 향하는지** 실어야 한다.

이미 그 방향으로 되어 있어 **그대로 쓰이는 것**:

- 커밋 메시지 초안이 **저장소 루트를 키로** 든다(§3.5.1b) — 워크트리는 루트가 달라 자연히 갈린다.
- 쓰기 실행이 저장소를 인자로 받는다(`submitWrite(git_exe, repo, …)`).
- 감시 대상이 저장소마다 자기 git 디렉터리로 해석된다(§3.5의 워크트리 규약).
- 목록·섹션·행 모델(`scm_view`)이 저장소 하나를 받는 순수 함수다 — N개면 N번 부른다.

### 3.5.2 섹션 모델 — 그룹이 곧 비교 기준이다

**시각 기준이 둘이다(2026-08-14 사용자 결정 2차).** 탭 구조는 Zed 목업을, **목록 안쪽 UI는 VS Code 목업을** 따른다.
사용자가 준 두 화면 이미지에서 **배치와 정보 계층만** 받았고 어느 쪽 소스도 열지 않았다([project-rules.md](project-rules.md)
레퍼런스 경계 — Zed·VS Code 모두 화면 비교로만 쓴다).

**그래서 스테이징은 체크박스가 아니라 행 호버의 `+`다.** 이 결정이 섹션 모델을 되돌린다 — `+`를 누르면 **그 행이 위
그룹으로 올라가는 것**이 곧 피드백이므로, 그룹은 비교 기준으로 갈려 있어야 한다.

| 섹션 | 비교 기준 | 무엇이 드나 | 행 동작(호버) |
|---|---|---|---|
| 스테이지된 변경 | `HEAD ↔ index` | index에 올라간 것 | `−` 언스테이지 |
| 변경 사항 | `index ↔ 작업트리` | 아직 안 올린 것 + **추적되지 않은 파일**(`U`) + 충돌 | `+` 스테이지 |

**`MM`(일부만 스테이지한) 파일은 양쪽에 각각 난다.** 초판에도 그랬고 VS Code도 그렇다. 한 줄 전 판(체크박스)에서는
이것이 문제였지만 — 같은 파일이 두 행이면 어느 체크박스가 무엇을 스테이지하는지 말할 수 없다 — `+`/`−`에서는
애매하지 않다: **위 행은 커밋될 것, 아래 행은 아직 아닌 것**이고 각 행의 버튼은 자기 축만 움직인다.

**추적되지 않은 파일은 별도 그룹을 만들지 않는다.** VS Code처럼 `변경 사항` 안에 `U`로 든다 — 새 파일도 "아직 안
올린 것"이라 같은 질문에 답하고, 그룹을 하나 더 두면 첫 화면이 헤더로 채워진다.

**행의 상태 문자는 그 행이 선 그룹의 축을 말한다.** `AM`(index엔 새 파일, 그 뒤 작업트리에서 수정)이면 위 행은 `A`,
아래 행은 `M`이다. 같은 파일의 두 행이 다른 글자를 갖는 것이 정상이고, 그것이 두 행이 다른 것을 가리킨다는 표시다.

**동작 버튼은 호버에만 뜬다(VS Code와 같다).** 평소에는 `+N -N`과 상태 문자만 보이고, 행에 포인터를 올리면 그
자리에 `열기`·`되돌리기`·`+`가 뜬다. 항상 보이게 하면 행마다 버튼이 있어 목록이 시끄럽고 증감 숫자 자리를 먹는다.
**충돌 행에는 동작을 붙이지 않는다** — 충돌은 스테이지 여부의 문제가 아니라 해결되지 않은 상태이고, `+`를 두면
누르는 순간 충돌 표시가 든 파일이 "해결됨"으로 커밋된다.

**행 클릭의 비교는 그 행의 그룹이 정한다**(§10.10 그대로 유지). 스테이지 행은 `HEAD ↔ index`, 변경 행은
`index ↔ 작업트리`, 추적되지 않은 파일은 비교 대상이 없어 파일을 그대로 연다. 전역 base 선택기는 두지 않는다.

**초판의 두 섹션은 탭으로 옮겨 간다.** "브랜치에 COMMIT 됨"은 히스토리 탭이(§3.5.3), "에이전트가 방금 바꾼 것"은
에이전트 탭이(§3.5.4) 흡수한다.

⚠️ **이 문단은 오래 절반만 맞았다(2026-08-27 정정).** 예전 판은 "`merge-base`·삼점 범위 계산은 사라지지 않고
히스토리 탭에서 「이 브랜치의 커밋」을 가르는 데 쓰인다"고 적었는데, 실제로 그 일을 하는 것은 `git log` 다.
삼점 범위 diff와 `merge-base` 는 **갈 곳이 없었고**, 그런데도 status 읽기 worker 는 13일 동안 그 셋을 계속
실행했다 — `Result` 에 담고, 다음 읽기에서 free 하고, 그 사이 아무도 읽지 않았다. 배관은 2026-08-27 에 걷혔다.
**소비자가 사라진 읽기는 화면과 같은 PR 에서 걷어야 한다**는 것이 이 건의 교훈이다. 삼점 범위 규율 자체는
`↑N ↓N`(`ahead_behind`)이 계속 쓰므로 §3.5 표에 남는다.

**개수가 0인 섹션은 숨긴다.** 섹션 접힘 상태는 뷰 상태로 기억한다. 섹션마다 기본 10행 상한과 `모두 보기 (N개 더)`
행을 두는 규칙은 초판 그대로다(아래 "섹션은 기본 10행까지" 문단).

**행의 정보 계층.** `종류 아이콘 · 파일명 · 흐린 상대경로 · +N -N · 상태 문자` 순이고, 폭이 좁아지면 **경로가 먼저
말줄임**된다(파일명·증감·상태는 끝까지 유지 — 셋이 스캔의 축이다). 말줄임은 chrome 공통 `appendEllipsizedTitle`
경로를 쓴다(한글 자모가 흩어지지 않게 — [chrome 셀 cluster 계약](grapheme-clustering.md)). 상태 문자는 **색과 글자
둘 다로** 구분한다(색만으로 구분하지 않는다). 호버 동작은 `+N -N` 자리에 겹쳐 뜬다 — 그 순간 숫자는 가려도 되는
정보이고(사용자가 이미 그 행을 보고 있다) 파일명은 끝까지 남는다.

**증감 숫자는 목록에 필수다.** 그래서 §6의 `diff.list`는 `added_lines`/`removed_lines`를 선택이 아닌 **필수 필드**로 둔다
(`hunk_summary?`는 헝크 단위 요약이라 별개이고 계속 선택이다). 출처는 `git diff --numstat`이고(실측), **binary는 numstat이 `-\t-\t경로`로 표시**하므로 그대로 `bin`으로 옮긴다 —
`0/0`으로 거짓 표시하지 않는다. `status --porcelain=v2` 한 번으로 두 그룹의 상태 문자(두 축)를 모두 얻지만
**증감은 들어 있지 않으므로** `--numstat`을 따로 부른다. **2판은 그 범위가 `HEAD`다**(`git diff --numstat HEAD --`) —
행의 기본 비교와 같아야 화면의 `+3 -1`과 눌러서 열리는 diff의 줄 수가 맞는다. rename은 `--find-renames`가 필요하다.

**`--`를 반드시 붙인다(2026-08-14 실측).** 저장소에 `HEAD`라는 이름의 *파일*이 있으면 git이
`ambiguous argument 'HEAD': both revision and filename`으로 exit 128을 낸다 — 목록 전체가 증감을 잃는다.
**unborn(첫 커밋 전)에서는 그 명령이 원래 실패하므로**(HEAD가 없다) `--cached` 출력을 대신 쓰는데, 그 갈림은
`# branch.oid (initial)`로 판정한다 — "출력이 비었다"로 대신 보면 평범한 저장소의 실패까지 같은 폴백을 타서
**index 범위 숫자를 HEAD 범위인 척** 보여 준다.

**행 클릭 = 파일 Term 열기.** 파일 하나를 고르면 diff kind 파일 Term이 열리고 도크는 목록으로 남는다. **도크 안에서 diff를
그리지 않는다**(§3의 경계).

FP16의 "파일 1개 = 창당 Term 1개" 불변식과의 관계를 명시한다 — **유일성 키는 경로가 아니라 `(경로, kind, base)`다.** 같은
`README.md`를 읽기 모드로 보면서 그 파일의 diff도 함께 보는 것은 정상적인 리뷰 흐름이라, diff Term이 markdown Term을 빼앗거나
kind를 갈아 끼우면 안 된다. **base까지 키에 드는 이유는 같은 파일을 서로 다른 기준으로 동시에 열 수 있기 때문이다** —
2판에서는 한 행이 기본 비교(`HEAD ↔ 작업트리`)로 열려 있는 채 컨텍스트 메뉴로 스테이지 쪽 비교를 또 여는 흐름이
그 자리다(초판에서는 `MM` 파일이 두 섹션에 나는 것이 이유였다). 하나가 다른 하나를 덮으면 사용자가
방금 누른 행이 아닌 것을 보게 된다. 이 확장은 FP16 불변식의 **예외가 아니라 키의 명시화**이며, 구현 시
[file-panel.md](file-panel.md)의 유일성 조회 지점과 함께 갱신한다(그 문서가 키의 단일 출처다).

**diff Term은 workspace에 저장하지 않는다.** diff는 디스크 파일이 아니라 **그 시점 git 상태의 비교 결과**다. 다음 실행에서
되살리면 저장할 때 보던 화면과 다른 것을 같은 것처럼 보여 준다(그 사이 stage·commit·checkout이 있었을 수 있다). 되살릴 값이
아니라 다시 계산할 값이므로, 복원 대신 소스 컨트롤 목록에서 다시 연다. writer가 diff entry를 건너뛰고 reader도 `diff` kind
이름을 받지 않는다 — 손으로 쓴 파일이 복원 못 할 상태를 만들지 못하게 한다. (저장이 필요해지면 base를 함께 적어야 하므로
workspace 포맷 개정과 같이 다룬다.)

**주 동작 줄.** 탭 줄 바로 아래 커밋 줄이 메시지 입력과 `커밋` 분할 버튼을 담고(3판 — 위 참조), 그 아래 요약 줄이
`diff 보기 · +N -N`과 일괄 동작(`모두 스테이지`/`모두 언스테이지` 분할 버튼)을 담는다. 전부 **write 동작**이라 규칙은
[쓰기·원격](editor-surface-dock-write.md)이 소유한다. **초판의 "감춘다" 규칙은 폐기됐다**(2026-08-14 사용자 결정) —
대신 누를 수 없는 상황(스테이지 0건에서의 커밋, 원격 없는 저장소의 `Fetch`)은 **비활성으로 보여 주고 왜 안 되는지를
말한다.** 감추면 사용자는 그 기능이 없는 줄 안다.

### 3.5.3 히스토리 탭

커밋 목록(그래프가 아니라 **선형 목록**)이다. 초판이 하단 접이식 `COMMITS` 섹션으로 자리만 잡아 두었던 것이 자기 탭을
얻었다 — 목록과 자리를 다투지 않으므로 접이식일 이유가 없다.

행은 두 줄이다: `제목` / `작성자 · 상대시각 · 짧은 SHA`, 그리고 그 커밋을 가리키는 **ref 칩**(태그·브랜치)이 제목 옆에
붙는다. 칩이 많으면 `+N`으로 접는다.

**접힘은 개수만 싣는다**(2026-08-19 구현). 이름들을 props로 나르면 화면에 못 그릴 문자열을 프레임마다 들고
다니게 되고, 접힌 이름을 보여 주는 길(툴팁·펼치기)이 아직 없다 — 그 길이 생기는 날 그때 싣는다. `%D`의
`HEAD -> main`은 **칩 하나**로 세므로(그 둘은 같은 자리를 가리킨다) `+N`의 N도 그 규칙을 따른다.

**`+N`은 제목보다 먼저 사라진다.** 칩을 그린 뒤 제목에 최소 칸(`commit_subject_min_cols`)이 안 남으면 접힘
표시를 그리지 않는다 — 부가 정보가 "무엇을 한 커밋인가"를 밀어내면 이 목록의 쓸모가 사라진다. 그 값은
`DockMetrics`가 소유하고, 좁은 줄에서 `+N`이 빠지고 제목이 남는 것을 뷰 테스트가 고정한다.

**두 줄 행에는 세 가지 시각 신호가 더 붙는다(2026-08-27 — 사용자 요청 「디자인도 색상이나 모던하게」).** 셋 다
새 색을 만들지 않고 **자리**로 말한다 — 목록의 색 위계(§3.5 파일 행)를 흔들지 않으려는 규율이다.

- **ref 칩은 면을 갖는다**(`inset_bg` + 3px 반지름). 배경 없이 글자만 두면 같은 줄의 제목과 한 덩어리로 읽혀,
  브랜치 이름이 커밋 제목의 앞부분처럼 보였다(사용자 캡처).
- **항목 사이에 얇은 가로선**(`divider`, 1px, `rowTopDivider`). 두 줄 행은 자기 안에 이미 두 층이 있어, 선이
  없으면 어디서 한 커밋이 끝나는지가 안 보인다. **첫 줄에는 안 그린다**(위 고정 chrome과 맞닿아 이중선이 된다)
  — 그리고 **파일 행에는 안 그린다**: 한 줄짜리 행에 줄마다 선을 그으면 목록이 표가 된다(2026-08-14 지적).
- **고른 줄은 좌측 강조 막대**(`accent_bar`, `accent_bar_w`)를 갖는다. 밴드(`variant = .selected`)만으로는 두 줄
  행이 이어지는 목록에서 「조금 밝은 줄」로만 읽힌다. 막대는 행 **왼쪽 끝**에 붙는다 — 목록 격자 밖이어야 그 줄
  전체를 가리키는 표시로 읽히고, 안쪽에 두면 아이콘 열과 다툰다. 파일 탐색기의 포커스 막대와 같은 규율이다.

- 출처는 `git log --format`이고 필드 구분자는 **제어문자**(`%x1f`/`%x1e`)다 — 제목·작성자에 어떤 문자가 있어도 파싱이
  깨지지 않아야 한다(비ASCII·따옴표·개행이 실제로 온다). ref는 `%D`가 준다.
- **상대시각은 우리가 만든다(2026-08-17 정정).** 초판은 `%ar`를 그대로 쓰기로 했다 — 직접 계산하면 로케일·시간대·
  미래 커밋 처리를 다시 정의해야 한다는 이유였다. 그 사이 **앱에 i18n이 들어왔고**(`src/i18n.zig`), `%ar`는 git의
  언어로 답한다: 한국어로 쓰는 화면에서 그 줄만 `2 hours ago`가 된다. 그래서 규칙을 우리가 갖는다 —
  `방금`/`N분 전`/`N시간 전`/`N일 전`/`N개월 전`/`N년 전`이고, **미래 시각은 `방금`으로 접는다**(시계가 어긋난
  커밋에 `-3시간 전`을 적을 수는 없다). 시각을 못 읽으면 그 자리를 **비운다** — 0을 1970년으로 그리지 않는다.
- 기본 200개 + `더 보기`. **상한만큼 읽었을 때만** 그 줄을 세운다 — 끝까지 읽었는데 세우면 눌러도 아무 일이 없어
  고장으로 읽힌다. 누르면 상한을 200 더 올리고 다시 읽는다(읽기를 거는 자리는 tick 하나뿐이다).
- unborn 저장소는 커밋이 없으므로 빈 안내를 낸다(오류가 아니다). 그 문구는 **셋을 구별한다**: `읽는 중…`(아직 못
  읽음) · `커밋이 없습니다`(읽었는데 없음) · `커밋을 읽지 못했습니다`(실패). 셋이 한 문장으로 접히면 사용자는
  기다려야 할지 고쳐야 할지 알 수 없다.
- **읽기는 그 탭을 볼 때만 돈다.** 백엔드에 자기 슬롯을 둔다(`submitLog`) — 목록 읽기와 겹쳐도 안전하고(둘 다
  `index.lock`을 잡지 않는다), 탭을 오가는 동안 목록 읽기가 취소되지 않는다.
- **탭을 바꾸면 목록 스크롤은 맨 위에서 시작한다.** 두 탭이 스크롤 상태를 공유하므로, 남겨 두면
  히스토리 첫 화면이 파일 목록의 offset에서 시작해 "빈 화면"으로 보인다. 탭마다 따로 들 수도 있지만
  그건 상태가 하나 더 느는 일이라, 그 요구가 실제로 나오면 그때 연다.
- **다른 탭에서는 커밋 상자가 키를 먹지 않는다.** 상자는 변경 사항 탭에만 그려지므로, 판정
  (`scmCommitOwnsInput`)이 탭까지 본다 — 안 그러면 히스토리에서 친 글자가 보이지 않는 상자로 들어간다.
  쓰던 글은 그대로 있어 돌아오면 이어 쓴다.
- **쓰기가 끝나면 커밋 목록도 다시 읽는다.** 커밋을 했는데 히스토리에 그 커밋이 없으면 사용자는
  커밋이 안 된 줄 안다. 저장소가 바뀌면 **고른 커밋도 버린다** — 인덱스는 그 목록 안의 자리다.
- **요약 줄(`+N -N`)은 이 탭에서 끈다.** 그 숫자는 작업트리의 것이라 커밋 목록과 관계가 없고, 0으로 두면 "바뀐 것이
  없다"는 틀린 진술이 된다. **자리까지 없앤다** — 그리기만 건너뛰면 탭 위에 빈 띠가 남는다.
- **행 클릭은 고르기이자 펼치기다(P4b).** 커밋을 누르면 그 커밋이 **바꾼 파일 목록**이 바로 아래에 온다 — 사용자가
  커밋을 누를 때 보려는 것이 그것이고, 그걸 여는 두 번째 컨트롤을 따로 만들 이유가 없다. 같은 줄을 다시 누르면
  접힌다(자리를 돌려받는 길이 그 줄 자신이어야 한다). **한 번에 하나만 펼친다** — 여럿이면 각각 읽기가 필요하고,
  히스토리에서 두 커밋의 파일을 동시에 보는 일은 드물다.
- 파일 목록은 `git show --format= --raw --numstat --first-parent -m <oid>` 하나로 읽는다.
  - **`diff <oid>^ <oid>`가 아니다**: 루트 커밋에는 `^`가 없어 그 명령이 실패한다. `show`는 루트 커밋도 "전부 새로
    생긴 파일"로 낸다.
  - **`--first-parent -m`**: 병합 커밋은 기본적으로 아무 파일도 안 낸다(combined diff 생략). 첫 부모 기준이면 한 줄에
    한 상태라 이 목록의 모양과 맞는다.
  - **증감도 같은 프로세스에서 읽는다**(2026-08-27 — 사용자 요청 「라인 몇 개 바뀐지 나왔으면」). 옛 판단은
    "`numstat`은 프로세스를 하나 더 쓴다"였고 그 전제가 `--name-status`였다: 그 옵션은 `--numstat`과 **같은 출력
    그룹**이라 함께 걸면 뒤에 온 쪽만 나온다(실측 git 2.50.1). `--raw`는 다른 그룹이라 numstat 블록과 나란히 오므로
    **프로세스는 그대로 하나**다. 상태 문자는 raw 줄의 마지막 필드에 그대로 있다.
  - **두 블록은 자리로 짝짓는다**(`git_status.iterateCommitFiles`) — git이 같은 diff queue를 두 형식으로 내므로
    i번째끼리 맞는다. **개수가 다르면 짝짓지 않는다**: 출력이 상한에서 잘리면 numstat 블록이 짧게 오는데, 그때
    자리로만 이으면 그 뒤 전부가 남의 숫자를 단다 — 빈 자리가 틀린 숫자보다 낫다(②d의 `unknown_delta`와 같은 규율).
  - 읽는 중·실패·**빈 커밋**(`--allow-empty`)을 각각 다른 한 줄로 말한다.
- 그 파일을 누르면 **`커밋^ ↔ 커밋`** 비교가 열린다(`DiffBase.commit`). 유일성 키는 다른 기준과 같은 `(경로, kind,
  base)`이고, **어느 커밋인지는 그 탭이 들고 다닌다**(`diff_commit_oid`) — 나중에 다시 구하면 그 사이 다른 커밋을
  펼쳤을 때 남의 커밋을 읽는다.
  - **루트 커밋은 왼쪽이 없다**: `커밋^`이 존재하지 않아 왼쪽 읽기가 실패하고, 그때 화면은 `untracked`와 같은 모양
    (오른쪽만)이 된다 — 루트 커밋의 파일은 실제로 그렇다.
  - 부모 판정은 목록이 이미 갖고 있다(`%P`) — 그 값을 위해 git을 다시 부르지 않는다.
- **유일성 키에 커밋이 들어간다**(적대적 검증): `(경로, kind, base)`뿐이면 다른 커밋의 같은 파일이 같은 탭을
  재사용해, 방금 누른 커밋을 눌렀는데 앞서 본 커밋의 내용이 보인다. 탭 라벨에도 짧은 해시를 적는다 — 커밋마다
  탭이 열리는데 라벨이 전부 `이름 · 커밋`이면 탭 줄에서 구별할 수 없다.
- **목록이 새로 오면 스냅샷 세대를 올린다**(적대적 검증). 커밋 줄의 intent는 **자리**를 싣고, 그 자리가 새 목록에서
  다른 커밋을 가리키기 때문이다(파일 행이 같은 이유로 세대를 쓴다).
  - **그 세대를 action 표가 따라오는 길은 발행이다.** 발행은 같은 tree가 다시 나와도 표를 **항상** 갱신하고,
    `capture`만 실제 교체일 때 버린다. 둘을 한 조건에 묶어 표까지 얼리면, **목록을 안 바꾸는 읽기**가 세대만
    올릴 때 표가 옛 세대로 굳어 그 화면의 클릭이 **영영** 거부된다 — 히스토리 탭이 정확히 그 경우였다
    (그 목록은 `git log`에서 오는데 `git status` 결과가 세대를 올린다). capture 보존과 표 동결은 다른 요구다.
  - **세대를 올리는 쪽은 다시 그리기를 함께 세운다**(`bumpScmDockGeneration`). 발행이 도는 프레임이 없으면
    표가 따라올 길도 없다 — 그 짝을 호출 규약에 맡기면 호출부 하나만 빠져도 같은 결함이 조용히 돌아온다.
- **저장소가 갈리면 펼친 커밋도 버린다** — 남겨 두면 그 OID를 새 저장소에서 읽는다.
- **rev는 hex만 넘긴다**(`git_command.isHexRev` — §6 심층 방어). 커밋 파일 목록 읽기는 rev를 **그대로 인자로**
  실으므로, 그 검사가 없으면 `--upload-pack=…` 같은 값이 우리가 닫아 둔 외부 프로세스 경로를 다시 연다.
- **출력이 잘리면 그 사실을 적는다**(커밋 목록·파일 목록 둘 다) — "더 없다"와 "더 못 읽었다"는 다른 사실이다.
- 지금 열어 둔 파일은 **강조로 말한다** — 파일 여럿을 오갈 때 무엇을 보고 있는지가 목록에 있어야 한다.
- **파일 줄에도 증감이 선다**(2026-08-27). 변경 사항 탭의 파일 행과 **같은 세 필드·같은 색 역할**이다
  (`+N` `git_added_fg` / `-N` `git_deleted_fg` / 이진은 `bin`) — 한 화면의 두 목록이 같은 사실을 다른 모양으로
  말하면 그 자체가 두 화면처럼 읽힌다. 오른쪽부터 `상태 문자 → 증감 → 소행 표시` 순으로 앉고, 좁아지면 그
  **역순으로** 내려놓는다(이름이 마지막까지 남는다 — 어느 파일인지가 그 줄의 존재 이유다).
- **파일 줄 묶음은 한 단 들어간 면**(`inset_bg`)에 앉고 왼쪽에 **세로 안내선**(`divider`, `childRail`)이 선다.
  들여쓰기 하나로는 좁은 도크에서 약해, 사용자 캡처에서 파일 목록이 목록 전체의 다음 항목처럼 보였다.
  **고른 줄은 면을 지정하지 않는다** — `resolveCard`는 paint override를 variant 뒤에 얹으므로, 지정하면 선택
  밴드를 덮어써 지금 열어 둔 비교가 목록에서 사라진다.

### 3.5.4 에이전트 탭 — 턴 타임라인

**1급 항목은 파일이 아니라 턴이다.** 에이전트의 변경은 "직전 턴·그 이전 턴"으로 쌓이므로 한 목록으로 합칠 수 없다
(§3.5.1). 항목을 펴면 그 턴이 바꾼 파일이 하위 목록으로 나온다.

| 항목 | 비교 기준 | 성질 |
|---|---|---|
| 마지막 턴 이후 | `스냅샷[0] ↔ 작업트리` | 계속 변한다(사용자가 손댄 것도 여기 든다) |
| 마지막 턴 | `스냅샷[1] ↔ 스냅샷[0]` | **양쪽 다 tree라 고정** |
| K턴 전 | `스냅샷[K+1] ↔ 스냅샷[K]` | 고정 |

여기서 `K`는 **그 세션 기준**이다(2026-08-23) — 표의 `스냅샷[K]`는 링 전역 자리이고, 화면의 `K턴 전`은 같은
세션의 스냅샷만 세어 매긴다. 세션이 하나면 둘이 일치한다.

링이 8개이므로 **그 세션당 최대 7턴 + `마지막 턴 이후` 한 줄**이다(가장 오래된 스냅샷은 짝이 될 이전 스냅샷이 없어 그 턴을 만들 수 없다).

**이 구조가 현행 결함을 고친다.** 지금은 `latest() ↔ 작업트리` 하나만 보는데, 스냅샷은 **턴이 끝날 때** 찍히므로
(`turn_snapshot.isTurnEnd` — `running → idle`) 턴이 완료되는 순간 기준이 "지금"으로 옮겨 가 그 섹션이 **빈다.**
사용자가 결과를 보러 오는 바로 그 시점이다. 턴 K의 변경을 스냅샷 **두 개 사이**로 잡으면 작업트리가 어떻게 바뀌든
그 항목은 고정된다.

**목록에 필요한데 지금 없는 것**: 링은 `tree`와 `surface_id`만 들고 있어 "언제·어느 에이전트"를 쓸 수 없다. 캡처
시각과 에이전트 종류를 링에 더한다([단계 계획](plans/scm-dock.md) P5).

**구현 규약(P5, 2026-08-18).**

- **행은 두 줄이다**: 제목(`마지막 턴 이후`·`마지막 턴`·`N턴 전`) / 에이전트 · **시각**. **맨 위 줄만 강조색**이다 —
  그 줄만 오른쪽이 작업트리라 계속 변한다는 사실을 색이 말한다.
- **맨 위 줄의 이름은 `마지막 턴 이후`다**(2026-08-23 — 예전에는 `진행 중`이었다). 그 줄은 링에 스냅샷이 하나라도
  있으면 **늘 선다** — 에이전트가 놀고 있어도, 사용자가 에디터로 고친 것만 있어도 선다. 즉 **에이전트 실행 상태가
  아니라** «마지막으로 굳힌 턴 이후에 생긴 변경»이다. `진행 중`이라는 옛 문구는 «에이전트가 지금 돌고 있다»로
  읽혔고 실제로 그렇게 오해됐다(사용자 지적). 진짜 실행 상태는 사이드바 배지가 말한다.
- **"언제·누가"는 오른쪽 스냅샷이 든다**(그 턴이 끝난 순간). 맨 위 줄은 아직 끝나지 않아 시각이 없다. 시각을 못 읽으면
  자리를 비운다(0을 1970년으로 그리지 않는다).
- **시각은 절대 표기다**(2026-08-23). 오늘이면 `14:32`, 아니면 `08-22 14:32`. 커밋 히스토리 탭은 그대로 상대
  표기(`2시간 전` — 에이전트 도크·알림과 같은 키)를 쓴다. 턴 목록에서 알고 싶은 것은 «얼마나 지났나»가 아니라
  «언제 것인가»이고, `2턴 전` 옆의 `5분 전`은 둘 다 상대라 서로를 설명하지 못한다. 특히 같은 저장소에 세션이
  여럿이면 «어느 것이 내가 방금 돌린 턴인가»를 시각으로 짚게 된다. 로컬 오프셋은 그 **시점마다** 구한다(서머타임
  경계를 넘은 턴이 한 시간 어긋나지 않게).
- **`N턴 전`은 그 세션 기준으로 센다**(2026-08-23). 링에는 여러 세션의 스냅샷이 번갈아 쌓이므로 전역으로 세면
  사이에 낀 남의 턴이 숫자를 밀어 화면이 거짓을 말한다. **비교 기준은 그대로 인접 스냅샷이다** — 같은 세션의
  이전 스냅샷까지 건너뛰면 그 사이 모든 변경이 이 턴 것으로 보인다. 숫자는 세션 기준, 비교는 인접 기준.
- **목록은 «활성 세션»의 턴만 그린다**(2026-08-23 개정 — [§6.1](editor-surface-tooling.md)이 링 소유를 세션으로
  옮겼다). 활성 pane을 옮기면 목록이 **통째로 바뀐다** — «세션별»이라는 말의 정직한 귀결이고 사용자가 그것을
  요구했다. 에이전트가 붙지 않은 Term이 활성이면 목록은 빈다(오류가 아니다 — `scm_no_turns`와 같은 자리).
- ~~세션이 둘 이상이면 에이전트 자리에 순번을 붙인다(`claude #2`)~~ **(2026-08-23 도입, 같은 날 폐기.)** 그 표시는
  «한 링에 여러 세션이 섞인다»는 초판 구조에 대한 대응이었다. 한 링이 한 세션이면 번호가 가리킬 대상이 없고,
  `마지막 턴`이 세션마다 한 줄씩 나오던 문제도 함께 사라진다. `N턴 전`을 «세션별로 센다»는 규칙도 자연히
  성립한다 — 링 안의 모든 턴이 이미 한 세션 것이다.
  ⚠️ 시각이 오른쪽에 먼저 앉으므로 **날짜가 붙은 줄에서는 에이전트 라벨이 밀릴 수 있다**(좁은 사이드바). 링이
  메모리·Term 로컬이라 그런 턴 자체가 드물고, 그때도 제목은 남는다.
- **제목 줄 오른쪽에 `N개 파일` 요약이 선다**(2026-08-23). 펼치지 않고도 그 턴이 무엇을 건드렸는지 크기를
  알 수 있어야 한다는 요구다. 값은 `git diff --raw --numstat <base> <head>` 의 **상태 줄** 수이고 **링에 캐시된다**
  (`Snapshot.changed_files`) — 한 턴에 한 번만 묻는다.
  - **`pumpCommitFiles` 의 «펼쳤을 때만 읽는다»와 다른 판단이다.** 커밋 히스토리는 수백 개라 미리 읽으면
    프로세스를 공짜로 띄우지만, 턴은 **최대 7개**고 결과가 링에 남아 다시 묻지 않는다. tree↔tree
    `--raw --numstat` 은 실측 **30 ms**(2026-08-23)라 목록 하나를 다 채워도 210 ms 남짓이고, 그것도 에이전트
    탭을 **보고 있을 때만** 든다.
  - **파일 목록 슬롯을 펼침 요청과 공유한다**(`git_backend` 의 결과 자리가 하나다). 그래서 둘을 동시에 걸지
    않고 도착한 결과를 요청 번호로 갈라 보낸다. **펼침이 먼저다** — 사용자가 방금 누른 것이 요약보다 급하다.
  - **모르거나 0이면 자리를 비운다.** 읽기에 실패한 턴도 0으로 적히기 때문이다(같은 턴을 매 tick 다시 물어
    프로세스를 무한히 띄우지 않으려고 실패도 «읽었다»로 표시한다). «바꾼 것이 없다»와 «못 읽었다»를 한 글자로
    가를 수 없으니 둘 다 조용히 비운다 — 아무것도 안 바꾼 턴은 링이 이미 걸러 낸다(같은 tree 연속이면 push
    하지 않는다).
  - **제목이 우선이다.** 요약이 안 들어가면 요약을 뺀다(제목을 밀어내지 않는다).
- **기록하지 못한 턴은 목록 머리에서 수를 말한다**(`기록하지 못한 턴 N개` — AT0). 백엔드의 스냅샷 자리가
  하나라 다른 세션의 캡처가 도는 중에 턴이 끝나면 그 요청이 거절되고 **그 턴은 영영 안 찍힌다.** 재시도하지
  않는다 — 스냅샷 시점이 «턴이 끝난 순간»이 아니라 «재시도한 순간»이 되어 **내용이 틀린 턴**을 만들고, 그것은
  없는 것보다 나쁘다.
  **이 수는 지우지 않는다**(적대적 검증 5회차 판단): «이 목록은 N개가 빠져 있다»는 그 링이 사는 동안 계속
  참인 사실이라, 지우면 불완전한 목록을 완전한 것처럼 보이게 만든다. 링이 세션 맵에서 밀려날 때 함께 사라진다.
- **줄 클릭은 고르기이자 펼치기**다(커밋 줄과 같은 규율). 펼치면 그 턴이 바꾼 파일이 아래에 온다.
  **한 번에 하나만** 펼치고, 히스토리 탭의 펼침과 **같은 읽기 슬롯**을 쓴다 — 두 탭이 동시에 펼쳐져 있으면
  서로의 파일을 그리게 되므로 한쪽을 펼칠 때 다른 쪽을 접는다.
- **`마지막 턴 이후` 줄은 tree 둘로 읽지 않는다.** 오른쪽이 작업트리라 그 비교가 성립하지 않고, 그 줄의 파일은 변경 사항
  탭이 이미 보여 준다.
- 파일 목록은 `git diff --raw --numstat <treeA> <treeB>` 하나다. 두 tree를 **각각의 인자**로 넘긴다 — `A..B`는 커밋 범위
  문법이라 tree에는 쓰지 않는다. rev는 hex만 넘긴다(`isRevKey` — 커밋 하나든 tree 둘이든 같은 규율).
  **커밋 파일 목록과 같은 형식이다**(위 P4b) — 두 탭이 같은 파서·같은 행 모양을 쓰므로 출력이 갈리면 한쪽에만
  증감이 선다.
- 파일을 누르면 **`스냅샷[K+1] ↔ 스냅샷[K]`**(`DiffBase.turn_range`)가 열린다. 유일성 키에 두 tree가 들어간다 —
  턴마다 다른 탭이어야 두 턴을 나란히 볼 수 있다. (`마지막 스냅샷 ↔ 작업트리` 기준도 `DiffBase.turn` 으로
  선언돼 있었으나 **대입하는 코드가 끝내 안 생겨** 2026-08-25 에 걷어냈다 — 위 규칙대로 그 줄은 변경 사항
  탭으로 보내므로 필요가 없었다.)

**적대적 검증에서 고친 것(2026-08-18).**

- **펼침·강조는 자리가 아니라 두 tree 키로 든다.** 새 턴이 들어오면 자리가 밀려 같은 번호가 다른 턴을
  가리킨다 — 사용자가 펼쳐 둔 줄이 조용히 바뀐다.
- **`마지막 턴 이후` 줄을 누르면 변경 사항 탭으로 간다.** 그 줄은 tree 둘로 읽을 수 없어 펼칠 것이 없는데, 아무 일도
  안 하면 죽은 컨트롤이 된다 — 그 줄이 가리키는 목록이 실제로 그 탭이다.
- **파일 줄이 어느 탭 것인지 스스로 말한다**(`from_turn`). 같은 줄 모양을 두 탭이 쓰지만 여는 비교가 다르다 —
  구분이 없으면 intent가 한쪽으로만 가서 다른 탭의 클릭이 죽는다.
- **저장소가 갈리면 펼친 턴도 버린다**(링이 통째로 비워지므로 그 키는 어느 턴도 가리키지 않는다).
- 탭 라벨에 **오른쪽 tree의 짧은 해시**를 적는다 — 턴마다 탭이 열리는데 라벨이 전부 `이름 · 턴`이면 구별할 수 없다.
- **읽기 슬롯을 공유하므로 키를 확인한다.** 실려 있는 파일 목록이 **그 항목의 것일 때만** 그리고, 그 클릭도
  같은 검사를 지난다(늦게 온 클릭이 다른 항목의 목록에서 같은 번호를 집으면 엉뚱한 파일이 열린다).
  한쪽 탭에서 펼치면 다른 쪽 펼침을 접는 것도 같은 규율이다.
- **자리로 드는 상태는 목록이 바뀌면 틀린다.** 고른 커밋·고른 턴·펼친 항목은 전부 **키**(커밋 OID·두 tree)로
  든다 — 커밋을 하나 만들거나 턴이 하나 늘면 목록이 밀려 같은 번호가 다른 것을 가리키기 때문이다.

**한계를 화면에 적는다.** 링은 **메모리·창 로컬**이라 앱을 껐다 켜면 사라지고, maru가 안 떠 있는 동안의 턴은 애초에
없다. 그래서 이 탭은 "기록"이 아니라 **이번 실행에서 관측한 턴**이고, 빈 목록은 오류가 아니라 정상이다 — 안내 문구도
그렇게 쓴다(`이번 실행에서 관측한 에이전트 턴이 없습니다`).

**빈 상태.** ⑴ git 저장소가 아님(판정 `.none` — 터미널이 답했고 그 폴더가 저장소가 아니다) → `git 저장소가 아닙니다`와
탐색기 뷰로 돌아가는 힌트. ⑵ 저장소지만 변경 0 → `변경 사항 없음`. ⑶ unborn(첫 커밋 전) → `변경 사항`에 추적되지 않은 파일만 들고 히스토리 탭은 비어 있다. ⑷ 아무도 답을 못 줌(판정 `.unknown` — 원격 세션·파일 Term) → `저장소를 확인할 수 없습니다`. 넷 다 오류가 아니라
정상 상태이므로 경고색을 쓰지 않는다.

**⑴과 ⑷를 한 문구로 뭉개지 않는다.** 판정을 3-상태로 나눈 이유(§3.5)가 표시에도 그대로 적용된다 — 저장소 안에 서
있는데 **물어볼 곳만 없는** 상태에서 "저장소가 아니다"라고 단정하면, 사용자는 없는 사실을 믿고 원인을 엉뚱한 곳에서
찾는다. 2026-08-13에 로컬 세션이 원격으로 오판됐을 때 이 문구가 정확히 그 역할을 했다(진짜 원인은 OSC 7 authority와
로컬 hostname의 어긋남 — ssh-integration.md §9.2). 문구 선택은 `git_ops.scmEmptyNotice` 한 자리가 소유하고, 렌더는
그것을 부르기만 한다 — 렌더 안 표현식으로 두면 세 상태를 테스트에서 짚을 수 없어 같은 회귀가 조용히 돌아온다.

**안내를 내는 소비처는 전수로 같은 구분을 쓴다.** 저장소 판정을 쓰는 자리는 다섯이다.

| 소비처 | 답이 없을 때 |
|---|---|
| `refreshGitStatus` | 조용히 돌아간다(읽을 저장소가 없다) |
| `followActiveTerminalRepo` | `.none`이면 목록을 버리고 `.unknown`이면 유지한다(§3.5) — 문구를 내지 않는다 |
| `openDiffForScmRow` | 조용히 돌아간다 |
| `captureTurnSnapshot` | 조용히 돌아간다(다음 턴에 다시 시도) |
| `requestBranchMenu` | **사용자에게 말한다** |

사용자에게 말하는 것은 도크의 빈 안내(`scmEmptyNotice`)와 **브랜치 메뉴** 둘뿐이라, 두 곳이 같은 상수
(`git_ops.notice_not_a_repo`·`notice_repo_unknown`)를 참조한다. 도크만 고치고 브랜치 메뉴를 놓쳤던 것을 적대적
검증에서 잡았고, 그때 적은 목록이 `followActiveTerminalRepo`를 빠뜨려 "전수"가 아니었던 것도 같은 방식으로 잡았다 —
새로 판정을 쓰는 자리를 추가하면 이 표에 함께 적는다.

**목록은 스스로 갱신된다.** `<repo>/.git`을 감시해 stage·commit·checkout을 잡고, 작업트리 파일 변경도 같이 본다.
폴링하지 않는다 — 안 보는 화면 때문에 프로세스를 띄우지 않고, 이벤트가 몰려도 진행 중이면 건너뛴다. **작업트리만
감시하면 안 되는 이유**는 `git add`가 작업트리를 안 건드리고 index만 바꾸기 때문이다.

**섹션은 기본 10행까지 보여 주고 남으면 `모두 보기 (N개 더)`를 낸다.** 변경이 수백 개면 한 섹션이 첫 화면을 다
먹어 나머지 섹션이 **있는지조차 모르게** 된다(스크롤이 있어도 마찬가지다 — 사람은 첫 화면으로 판단한다). 그래서
섹션마다 자리를 나눠 주되 **잘렸다는 사실을 행으로 말한다** — 조용히 자르면 사용자는 자기가 바꾼 파일이 없어졌다고
읽는다. 섹션 헤더의 개수는 언제나 **전체**이고, 그 행은 **숨은 수**를 말한다. 누르면 그 섹션만 전부 펴고, 상한 안이면
그 행을 아예 내지 않는다(눌러도 아무 일 없는 컨트롤을 두지 않는다). 접힘과 마찬가지로 **행 모델 단계**에서 자른다 —
렌더만 자르면 화면에 없는 행이 클릭 좌표 계산에 남아 누른 것과 열리는 것이 어긋난다.

**목록 chrome.** 스크롤에서 고정되는 것은 **탭 줄과 요약 줄**(위), **브랜치 줄과 커밋 줄**(아래)이고 그 사이 목록만
스크롤한다(2판 — 초판은 첫 줄이 브랜치 헤더였다). 섹션 헤더를 누르면 접히고, 접어도
개수는 남는다(몇 개가 숨었는지 모르면 접는 의미가 없다). 접힘은 **행 모델 단계**에서 처리한다 — 렌더만 숨기면
화면에 없는 행이 클릭 좌표 계산에 남아 누른 것과 열리는 것이 어긋난다. 파일 아이콘은 탐색기와 같은 분류기를 쓰고,
선택한 행은 강조해 지금 보고 있는 비교를 남긴다. 목록 스크롤 상태는 탐색기와 **따로** 갖는다.

**diff 본문의 시각 언어.** 왼쪽은 삭제(빨강)·오른쪽은 추가(초록)이고, 줄 전체에 옅은 색을 깔고 바뀐 글자만 진하게
겹친다(GitHub과 같은 관례 — 리뷰어가 새 언어를 배우지 않게). 색은 **터미널 팔레트에서 파생**한다(`--maru-diff-*`,
syntax 하이라이트와 같은 배관) — 테마를 바꾸면 diff도 따라와야 한 창 안에서 색 언어가 갈리지 않는다. 색만으로
구분하지 않도록 바뀐 줄 왼쪽에 색 띠를 함께 둔다. 줄 번호는 필수이고, **각 편집기가 자기 안에서 스크롤**한다 —
바깥이 스크롤하면 가로 막대가 문서 맨 아래에 생겨 긴 줄을 볼 수 없다. 세로 위치는 두 편집기 사이에서 맞춘다.

**포인터는 뷰별로 갈린다.** 도크 rect는 뷰가 공유하지만 그 안의 조작은 공유하지 않는다 — 탐색기 전용 동작(행 활성화·
폴더 선택 다이얼로그·배경 컨텍스트 메뉴·트리 스크롤·트리 스크롤바·트리 포커스 획득)은 **탐색기 뷰에서만** 탄다. 좌표가
같은 rect 안이라는 이유로 타면 소스 컨트롤 행을 누른 것이 폴더 선택 창이 된다(실측). 다른 뷰의 클릭은 도크가 소비하되
아무 동작도 하지 않는다 — 행 클릭의 diff 열기는 diff 뷰가 생길 때 붙인다(위 표). 뷰 전환 바는 언제나 트리보다 먼저 본다.

**경계 상태의 실측 결과(2026-08-01).** 아래는 실제 저장소를 만들어 확인한 것이고, 각 줄이 코드의 분기와 1:1이다.

| 상태 | git이 주는 것 | 목록 | 행 클릭 |
| --- | --- | --- | --- |
| 병합 충돌(`u UU`) | index에 stage 0 **없음**, numstat이 같은 경로에 여러 줄(첫 줄 `0 0`) | **변경 사항**에만 `U`, 증감 자리는 빈다. **호버 동작이 없다**(스테이지할 수 있는 상태가 아니다) | `HEAD ↔ 작업트리` — 충돌 표시를 그대로 본다 |
| 하위 모듈(`S...`, mode 160000) | blob 없음, 작업트리 쪽은 디렉터리 | 경로만(증감 없음) | 열지 않고 "하위 모듈은 비교를 표시하지 않습니다" |
| unborn(첫 커밋 전) | `# branch.oid (initial)`, `numstat_head`·ahead/behind 실패 | 브랜치 이름은 나오고 추적되지 않은 파일만 | 평소와 같다 |
| 링크 워크트리(`.git`가 파일) | `rev-parse --show-toplevel` 정상 | 평소와 같다 | 평소와 같다 |
| rename(`2 R.`) | 새 경로 + 옛 경로 | 새 경로 | 왼쪽은 **옛 경로**로 읽는다 |
| 비ASCII 경로 | 기본값이면 C-quote | `core.quotePath=false`로 원문 | 원문 경로로 읽는다 |

**충돌에 `+`를 두지 않는 이유**: 충돌은 스테이지 여부의 문제가 아니라 **해결되지 않은 상태**다. `+`를 두면 누르는
순간 `git add`가 돌아 "해결됨"으로 표시되는데, 사용자는 충돌 표시를 파일에 남긴 채 그걸 커밋하게 된다. 해결은
편집기에서 하는 일이고, 해결하면 그 파일이 평범한 `M`으로 바뀌어 `+`가 생긴다. 충돌을 "스테이지된 변경"이 아니라
"변경 사항"에만 넣는 것도 같은 판단이다.
**충돌·하위 모듈의 증감을 비우는 이유**: numstat의
첫 줄(`0 0`)을 그대로 쓰면 방금 충돌한 파일이 "안 바뀐 파일"로 보이고, 하위 모듈은 커밋 포인터라 줄 수 자체가
의미가 없다.

**말할 수 없는 상태를 "읽는 중"으로 위장하지 않는다.** 읽기가 끝나지 않는 것과 읽을 수 없는 것은 사용자에게 전혀 다른 일이다.

| 상태 | 안내 | 판정 |
| --- | --- | --- |
| git CLI 없음 | `git이 설치되어 있지 않습니다` | 실행 파일 후보를 다 봐도 없음(§6) — **실행을 시도하지 않는다** |
| 읽기 실패 | `git 읽기에 실패했습니다` | 명령이 0이 아닌 코드로 끝남. 직전 성공 목록은 버린다(다른 시점과 섞지 않는다) |
| 읽는 중 | `읽는 중…` | 요청이 실제로 떠 있는 동안만 |

실패는 화면에 남는다 — 뷰를 다시 선택하면 재시도한다. 자동 재시도는 넣지 않는다(같은 이유로 계속 실패할 명령을 매 프레임
돌릴 이유가 없다). git stderr는 어떤 상태에서도 화면·로그에 싣지 않는다(§6).

**갱신 시점.** 목록은 폴링하지 않는다. ⑴ 도크 뷰가 소스 컨트롤로 바뀔 때, ⑵ 파일 Term 저장 성공 뒤, ⑶ 창이 다시 포커스를
받을 때, ⑷ 사용자가 헤더 새로고침을 누를 때 다시 읽는다.

**감시 대상은 `.git`이 아니라 "그 저장소의 git 디렉터리"다(2026-08-16 정정).** 일반 저장소에서는 둘이 같지만,
**링크된 워크트리**(`git worktree add`)에서는 `.git`이 디렉터리가 아니라 `gitdir: <경로>` 한 줄이 든 **파일**이고
index·HEAD는 그 경로(`<주 저장소>/.git/worktrees/<이름>/`) 아래에 산다.

그래서 `.git`만 감시하면 **워크트리에서는 아무 일도 일어나지 않는다** — 실측(2026-08-16)으로 워크트리에서
`git add`를 하면 `.git` 파일의 mtime은 그대로이고 바뀐 것은 `<주 저장소>/.git/worktrees/<이름>/index`였다.
증상은 "터미널에서 stage/commit 했는데 도크 목록이 그대로"이고, 목록 자체는 다시 읽으면 맞으므로 **틀린 화면이
아니라 늦은 화면**이다.

- 판정은 `repo_path.gitDirFromDotGitFile`(순수)이 한다 — `.git`을 읽어 그 형식이면 가리키는 경로를, 아니면 null.
- **추측하지 않는다.** 읽기 실패·형식 불일치면 `<repo>/.git`으로 되돌린다. 일반 저장소가 그 답이고, 워크트리에서
  실패하면 예전과 같은(갱신 없는) 상태일 뿐 **남의 디렉터리를 감시하지는 않는다**.
- 상대 경로(`gitdir: ../.git/worktrees/x`)도 형식의 일부다 — 워크트리 디렉터리 기준으로 합친다.

**저장소 판정 자체는 원래도 워크트리를 안다** — `repoRootFor`는 `.git`이 디렉터리든 파일이든 **존재만** 보므로
워크트리 루트가 그대로 저장소 루트가 된다. 그 값이 커밋 메시지 초안의 키이기도 해서(§3.5.4), 워크트리마다 초안이
자연히 갈린다.

**저장소 전체 watcher는 v1에 넣지 않는다.** §5.2의 watcher는 *열린 문서의 디렉터리*를 보는 것이고, worktree 전체를 보는 것은
다른 비용 문제다 — 대형 저장소·`node_modules`·`.git` 내부 churn(index.lock·objects)이 이벤트를 쏟아 낸다. 에이전트가 파일을
바꾸는 동안 목록이 저절로 갱신되는 것은 분명 바람직하지만, 그건 **감시 범위·필터·coalesce를 따로 설계해야 하는 별도 슬라이스**다.
v1은 위 네 시점으로 충분하고, 그중 ⑶이 "터미널에서 에이전트가 일하고 도크로 돌아온다"는 실제 흐름을 덮는다.
