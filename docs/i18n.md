# 다국어(i18n) — UI 표시 문자열 로컬라이제이션

Maru **UI 표시 문자열**의 소유 위치·키 모델·언어 선택·레이아웃 계약의 단일 출처다. 진행과 검증 상태는
[다국어 구현 계획](plans/i18n.md)과 [검증 매트릭스](verification-matrix.md)가 소유하고, 이 문서는 계약만 서술한다.

**이 문서가 담지 않는 것** — 텍스트 *처리*는 이미 다른 문서가 소유하며, 그것들은 이 계약의 전제다.

| chrome 문자열의 셀 배치·말줄임 | [레이어링과 이식성](layering-and-portability.md) §7.9 (CT-OWN) |
| 폰트 fallback cascade | [폰트 전략](font-strategy.md) |
| IME 조합(preedit) | [키 입력과 단축키 경계](key-input-and-shortcuts.md) |

## 1. 왜 필요한가 — 언어를 고를 수단이 없고, 소유가 macOS에 갇혔다

두 문제가 겹쳐 있다. 하나는 표시 언어가 코드에 고정되어 사용자가 고를 수 없다는 것이고, 다른 하나는
문자열 소유의 **위상**이다. 뒤엣것이 더 급하다 — Windows가 오는 중이기 때문이다.

### 1.1 표시 언어가 코드에 고정돼 있고, 두 표면은 섞여 있다

사용자에게 보이는 문자열이 **어디서 어느 언어로 갈리는지** 보여주는 대표 항목이다(2026-08-16).
**전수가 아니다** — 전체 규모와 레이어 분포는 §1.2가 든다(합계 559~634).

| 영역 | 한국어 | 영어 | 사용자가 보는 곳 |
| --- | ---: | ---: | --- |
| `src/config/*.zig`의 `Meta.doc` | 85 | 0 | 세팅 페이지 설명문 |
| `command_catalog.global_entries`의 `.title` | 3 | 0 | 세팅 페이지 전역 단축키 섹션 |
| `src/chrome/tokens.zig` 테마 프리셋명 | 3 | 3 | 세팅 페이지 |
| `command_catalog.entries`의 `.title` | 0 | 66 | 메뉴바 + 커맨드 팝업 |
| Swift `NSMenuItem(title:)` | **3** | 12 | 메뉴바(Browser Grants 서브메뉴가 한국어 — §2와 어긋난다) |
| Swift `NSOpenPanel.message` | **4** | 0 | OS 파일 선택창 |
| Swift → ABI `show_notice` | 1 | 0 | notice 오버레이(표시는 chrome) |
| `src/main.zig`·`src/cli/*.zig` 출력 | **100** | 다수 | 터미널 (전수 조사 수치 — §7.1이 영어로 고정. **2026-08-20 에 영어화 완료** — 리터럴 원장에서 그 항목들이 빠졌다) |

큰 덩어리는 화면 단위로 갈렸다 — 세팅 페이지는 한국어(설명문 85 + 전역 단축키 3), 메뉴바와 커맨드 팝업은
영어(66 + 12)다. `command_catalog`의 두 배열이 서로 다른 화면에 노출되기 때문이다 — `entries`는 메뉴/팝업,
`global_entries`는 세팅 페이지 `.global_hotkey` 섹션 전용이다(`app_session/settings.zig`에서만 참조).

**그러나 한 표면 안에서 섞인 곳이 둘 있다.**

- **CLI** — `maru install-cli`는 `"maru CLI 설치 완료"`라고 말하는데 그 옆 `"unknown maru command"`는 영어다.
  한국어 출력이 100개다(`cli/browser/run.zig` 41·`main.zig` 30·`cli/browser.zig` 20 …).
- **find 오버레이** — 프롬프트는 `"Find: "`(영어)인데 페이지 검색 표시기는 `"찾음"`·`"없음"`(한국어)이다
  (`chrome/components/find.zig`). 같은 오버레이에 두 언어가 동시에 그려진다.

이 분포가 §5의 기본값을 정한다: **세팅 페이지는 이미 한국어이므로**, 기본값을 `en`으로 두면 이 계약을
적용하는 순간 한국어 사용자의 세팅 화면이 영어로 **퇴보한다**.

### 1.2 UI 문자열의 "단일 출처"가 macOS 디렉터리에 있다

`command_catalog.zig`는 스스로를 "메뉴바·커맨드 팝업이 공유하는 단일 출처(Zig)"라고 선언하지만 경로가
`src/platform/macos/` 아래다. 그리고 `src/chrome/components/palette.zig`가 명시하듯 **chrome(L3 중립)은 그것을
import할 수 없다** — 표시할 문자열을 host가 주입받는다.

[Windows 플랫폼](windows-platform.md)에는 메뉴·커맨드 카탈로그를 어디서 가져올지가 없다(§8 "아직 정하지 않은 것"에
해당). 지금 상태로 Windows 메뉴를 만들면 영문 title 66개를 다시 쓰거나 macOS 디렉터리를 참조해야 하고, 둘 다
[레이어링과 이식성](layering-and-portability.md) §2("OS-중립 코드를 platform에 가두지 않는다")에 어긋난다.

**그리고 카탈로그는 이 문제의 작은 쪽이다.** 사용자가 읽고 판단하는 한국어 문장 — 확인 대화상자·notice·
세팅 라벨 — 의 **실제 소유자는 `src/platform/macos/app_session/`**이다. chrome 컴포넌트는 그 문자열을
주입받을 뿐이다.

```zig
// src/platform/macos/app_session/file_panel.zig
showConfirmButtons(.file_tree_delete, "선택한 항목을 macOS 휴지통으로 이동할까요?", …);
showNotice("프로젝트 파일 또는 폴더를 먼저 선택해 주세요.");
```

전수 조사(2026-08-16, [구현 계획](plans/i18n.md) "전수 조사")가 낸 번역 대상은 **559~634개**이고, 그중
**348개가 `platform/` 아래**다. 확정치가 아니라 범위인 이유는 그 절이 설명한다 — 자동 분류가 수렴하지 않는다.

| 레이어 | 개수 | 위상 |
| --- | ---: | --- |
| `platform/macos` (Zig) | 339 | **갇혀 있다** |
| `platform/macos` (Swift) | 5 | **갇혀 있다** |
| `platform/mobile` | 4 | **갇혀 있다** |
| `config` | 113 | 이미 중립 |
| `chrome` (L3) | 68 | 이미 중립 |
| `session` (L2) | 30 | 이미 중립 |

합계 559가 하한이고, `.zig` 자동 분류에서 아직 미분류로 남은 문장형 75건이 상한까지의 폭이다
(Zig 554 + Swift 5 = 559 … 634).

`app_session`은 macOS 앱 로직이라 통째로 중립 층에 옮길 수 없다. **따라서 문자열만 키로 빼는 것이 이
위상 문제의 유일한 해법이고, 그것이 곧 §3의 키 모델이다** — 번역과 이식성이 같은 작업으로 풀린다.
나머지 217개는 이미 중립 레이어에 있어 위상 문제가 없고, 번역만 하면 된다.

**이 프로젝트는 같은 문제를 이미 한 번 겪고 해결했다.** CT-OWN(§7.9)은 텍스트 *배치*가
`platform/macos/coretext_frame_builder`에 갇혀 있어 chrome으로 올렸다. 지금은 텍스트 *내용*이 같은 자리에 갇혀
있고, 같은 처방을 쓴다.

**실증된 반례** — Ghostty는 gettext를 택했고, 그 결과 번역 시스템이 GTK(Linux)·Windows에만 적용되고
macOS/Swift 문자열은 시스템 밖에 남았다(`po/README_TRANSLATORS.md`: "The localization system is not yet
implemented for macOS"). 문자열 소유를 플랫폼에 두면 플랫폼 수만큼 분열한다.

## 2. 범위 — 읽고 이해하는 텍스트만 번역한다

**언어**: 영어(`en`)·한국어(`ko`). 중국어·일본어는 이 계약을 바꾸지 않고 확장된다(§6.2).

**경계**(사용자 결정 2026-08-16): 사용자가 **읽고 이해해야 하는 설명·상태 문장**을 번역하고,
**명령을 찾고 실행하는 짧은 이름**과 **기계가 읽는 출력**은 영어로 고정한다.

| 표면 | 언어 | 성격 |
| --- | --- | --- |
| 세팅 페이지 — 설명문·섹션·전역 단축키 항목 | **번역** | 읽고 이해해 값을 고르는 자리 |
| 알림 패널·확인 대화상자·notice | **번역** | 상태 문장·질문 |
| 커맨드 팝업 | 영어 고정 | 명령 이름 — 찾아서 실행한다(§2.1) |
| find 오버레이 | 영어 고정 | 프롬프트·상태 표시기 — 팝업과 같은 `modal` 오버레이 |
| macOS 메뉴바 | 영어 고정 | 명령 이름 — 팝업과 같은 카탈로그(§2.1) |
| OS 파일 선택창(`NSOpenPanel.message`) | **번역** | 읽고 판단해 파일을 고르는 자리 — 설명문이다 |
| `maru` CLI 출력 | 영어 고정 | 스크립트가 파싱한다(§7.1) |

**"창 안이냐 밖이냐"는 축이 아니다.** 세팅·팝업·find는 모두 `draw.Layer.modal`의 창 안 chrome인데 결정이
갈린다. 가르는 것은 그리는 위치가 아니라 **사용자가 그 문자열로 무엇을 하는가**다 — 읽고 판단하면 번역하고,
찾아서 실행하거나 파이프로 넘기면 영어다.

### 2.1 커맨드 팝업·메뉴바가 영어인 이유

`command_catalog.entries`는 메뉴바와 커맨드 팝업이 **공유하는 하나의 목록**이다
(`MaruAppHost.swift`가 `catalogMenuItem(...)`으로 같은 title을 읽는다). 둘을 가르려면 표시명을 두 벌 들어야
하고, 그것은 이 계약이 없애려는 이중 출처다.

그리고 팝업 필터는 바이트 단위 부분일치라(`platform/macos/command_palette.zig`) 한국어 title을 넣으면
영어 키워드로 아무것도 찾지 못한다. 영어 유지가 그 문제를 열지 않는다.

**현재 코드가 이 경계와 어긋난 곳이 하나 있다** — Browser Grants 서브메뉴 항목이 한국어다
(`MaruAppHost.swift`의 `"쿠키·스토리지"`·`"… 취소"`). 메뉴바는 영어이므로 I5가 영어로 맞춘다.

같은 이유로 **find 오버레이도 영어다.** 팝업과 같은 `modal` 레이어의 명령형 오버레이이고, 표시하는 것도
`cur/total` 카운터 같은 짧은 상태다. 현재 한국어인 `"찾음"`·`"없음"`은 영어로 맞춘다.

**BiDi(아랍어·히브리어)는 이 계약 밖이다.** 등폭 셀 그리드 위의 양방향 재정렬은 별도 전략이며,
`src/hazard.zig`가 BiDi 제어 문자를 *위험*으로 분류하는 현재 정책과의 정합도 함께 정해야 한다.

## 3. 결정 — enum 키 + comptime 테이블

문자열은 **키로 참조하고, 언어별 테이블은 comptime struct**로 둔다. 값은 컴파일타임 문자열 리터럴이다.

```zig
// 모양 스케치(정확한 문법 아님 — 단일 출처는 구현 시 src/i18n.zig).
const Table = struct {              // 기본값을 주지 않는다 — 누락이 컴파일 에러가 되는 근거
                                    // (밖에 소비처가 0 이라 비공개다 — §7.2 가 그 가시성을 comptime 에 못 박는다)
    cmd_new_terminal: [:0]const u8,
    find_page_found: [:0]const u8,
    // ...
};
const en: Table = .{ .cmd_new_terminal = "New Terminal", .find_page_found = "Found", ... };
const ko: Table = .{ .cmd_new_terminal = "새 터미널",    .find_page_found = "찾음",  ... };

pub const Key = std.meta.FieldEnum(Table);   // 키 목록을 손으로 두 벌 유지하지 않는다

pub fn t(lang: Lang, key: Key) [:0]const u8 {
    const tbl: *const Table = switch (lang) { .en => &en, .ko => &ko };
    return switch (key) { inline else => |k| @field(tbl.*, @tagName(k)) };
}
```

### 3.1 이 형태를 고른 이유

- **번역 누락이 컴파일 에러다.** `Table`에 기본값이 없으므로 언어 테이블이 필드를 빠뜨리면
  `error: missing struct field: <키>`가 난다. [config 스키마](config-schema.md) §8이 세운 "드리프트는 comptime
  컴파일 에러로 막는다"와 같은 규율이며, 새 관용구를 들여오지 않는다.
- **런타임 의존성이 0이다.** [필수 프로젝트 규칙](project-rules.md) "의존성"이 요구하는 기본값을 지킨다.
- **언어 전환에 heap이 없다.** 모든 언어의 문자열이 static이라 전환은 `switch` 하나이고 해제가 불필요하다.
  `command_catalog.Entry`의 "컴파일타임 문자열 리터럴(널 종단) — ABI에서 그대로 가리킨다"는 계약이
  언어를 바꿔도 유지된다. 반환 타입 `[:0]const u8`은 chrome의 `[]const u8` 소비자로 그대로 coerce되고
  ABI가 요구하는 널 종단도 만족해 **양쪽에 하나의 타입으로 통한다.**

**미래 소비자 — 접근성.** [Chrome 상호작용 이관](chrome-interaction-migration.md) §3은 interactive node가
snapshot에 **localized label**을 담은 semantic descriptor를 내라고 요구한다(`archive_detail/view.zig`가
"첫 accessibility descriptor 소비자가 생기는 PR"로 미뤄 둔 것). 그 label은 published tree보다 오래 살아야
하는데, **이 계약의 문자열이 static이라 그 수명 문제가 처음부터 없다.**

### 3.2 대안과 그것을 택하지 않은 이유

**베이스/의사결정**: i18n에는 단일 표준이 없다. 네 방식을 비교했고 동작·제약만 보았다(코드 표현은 옮기지 않았다 —
[project-rules.md](project-rules.md) clean-room).

| 방식 | 대표 | 택하지 않은 이유 |
| --- | --- | --- |
| **gettext** (소스 문자열이 키) | Ghostty, Qt `tr()`, GNOME | `libintl`이 **런타임 의존성**이다. 런타임 언어 전환이 어렵고(Ghostty 메인테이너: hot-reload는 "very cursed"), 플랫폼 분열이 실증됐다(§1.2). GTK 앱이면 생태계에 딸려오지만 Maru는 GTK를 쓰지 않는다 |
| **Fluent** (`.ftl`) | Firefox | CLDR/ICU 기반이고 **BiDi를 지원하는 유일한 후보**지만, Zig 구현이 없고 런타임 파서가 필요하다 |
| **ICU MessageFormat** | 업계 포맷 표준 | ICU 자체가 대형 런타임 의존성이다 |
| **comptime 테이블** (채택) | Crystal의 Rosetta | — |

**번역 문자열은 Zig 소스에만 둔다.** 외부 파일(JSON·`.po`·`.ftl`)을 소스로 두고 런타임에 읽거나 빌드 시
코드를 생성하는 방식은 쓰지 않는다(사용자 결정 2026-08-16). 런타임 로딩은 §3.1의 세 이점(컴파일 타임 누락
검출·의존성 0·static 수명)을 모두 잃고, 빌드 시 codegen은 그 이점을 지키는 대신 생성 단계와 소스 이중화를
들여온다 — 언어 둘에 번역가가 없는 단계에서는 둘 다 순수 비용이다.

이 선택으로 **번역가 도구 생태계**(Weblate·Crowdin 연동)는 잃는다. 번역이 코드 편집이라는 뜻이며, 전업
번역자가 참여하는 규모가 되면 다시 논의할 자리다.

**소스 문자열을 키로 쓰지 않는 이유**(같은 방식을 comptime map으로 흉내 낼 수는 있다): 원문 오타가 컴파일을
통과해 런타임에 미번역으로 표시되고, 원문을 다듬으면 그 항목의 번역이 경고 없이 끊기며, 맥락이 다른
동음이의어(`"Close"`)를 구분할 수 없다. 다만 이 셋 중 앞의 둘은 gettext 도구 체인(`xgettext`·`msgfmt --check`)이
잡아주므로, 이 비교는 **도구 없이 자력으로 얻는 안전성**의 차이다.

**포기하는 것**: 호출부에 원문이 보이지 않는다(`.cmd_new_terminal` vs `"New Terminal"`). 리뷰 시 문자열을
확인하려면 테이블을 열어야 한다. 원문을 코드와 테이블 양쪽에 두는 절충은 **하지 않는다** — 이중 출처가 된다.

## 4. 문자열은 중립 층이 소유한다

키·테이블은 **중립 leaf**에 둔다(`src/redact.zig`와 같은 위상 — 아무것도 import하지 않고 모두가 import한다).
`platform/`·`chrome/`·`config/` 중 어느 것도 번역 대상 문자열의 소유자가 되지 않는다.

- macOS Swift는 지금처럼 ABI로 받은 문자열을 그리기만 한다. `.lproj`/`.strings`를 만들지 않는다.
- Windows·Linux host가 와도 같은 테이블을 그대로 쓴다. 플랫폼별 번역 사본이 생기지 않는다.

**§2가 영어로 고정한 표면도 중립 층으로 옮긴다 — 다만 근거가 다르다.** `command_catalog`는 번역 대상이
아니지만(§2.1) 여전히 `src/platform/macos/` 아래에 있어 Windows가 재사용할 수 없다(§1.2). 이 이동의 근거는
i18n이 아니라 **레이어링**이며, 문자열을 키로 뺄 필요 없이 파일 위상만 바꾸면 된다. 이 계약은 그 사실을
기록만 하고, 실행 순서는 [구현 계획](plans/i18n.md)이 소유한다.

## 5. 언어 선택

[config 스키마](config-schema.md)의 메타 1급 필드로 둔다. `Config`에 `ui` sub-struct는 없으므로 **직속
스칼라 필드**로 두고 `Meta.key`로 전체 키 `"ui.language"`를 지정한다 — `blink_text` 필드가 `"text.blink"`
키를 갖는 것과 같은 패턴이다(config-schema.md CS-2b). 세팅 GUI의 드롭다운은 스키마에서 파생되므로 따로
만들지 않는다.

| 값 | 동작 |
| --- | --- |
| `auto` (**기본값**) | OS 로케일을 따른다. 해석 실패·미지원 언어는 `en`으로 떨어진다 |
| `en` | 영어 고정 |
| `ko` | 한국어 고정 |

**기본값이 `auto`인 이유**: 세팅 페이지는 이미 한국어다(§1.1). 기본값을 `en`으로 두면 이 계약을 적용하는
순간 한국어 사용자의 세팅 화면이 영어로 바뀌어, 기능을 추가했는데 경험이 퇴보한다. `auto`는 한국어
로케일에서 현재 화면을 그대로 보존하고, 영어권 로케일에서만 개선이 된다.

**섹션**: 현재 `Section` enum(`config/theme.zig`)에는 언어가 들어갈 자리가 없다(`font`·`theme`·`cursor`·
`window`·`input`·`terminal`·`workspace`·`quick_terminal`·`sidebar`·`global_hotkey`·`editor`). 앱 전역 설정을
담을 새 섹션을 추가한다.

**드롭다운 표시**: enum 값은 기본적으로 `@tagName` 그대로 그려진다(`app_session/settings.zig`의
`.dropdown = e.current`). 그대로 두면 `auto`·`en`·`ko`가 보인다. 언어 이름은 **자기 언어로** 표시한다
(`자동`/`English`/`한국어`) — 자기가 읽을 수 있는 언어를 찾는 자리이므로 현재 UI 언어로 번역하면 오히려
못 찾는다. 이 표시명은 번역 테이블이 아니라 **언어별 고정 매핑**이며, `theme.preset`이 사람이 읽는 이름을
따로 쓰는 선례(`settings.zig`)와 같은 예외 경로를 쓴다.

> **함정**: `EnumField.current`는 표시값이면서 동시에 **기본값 판정의 비교 키**다
> (`settings.zig`: `std.mem.eql(u8, dv, e.current)`). 표시명을 넣으면 그 비교가 표시값 대 저장값을 비교하게
> 되어 "기본값인가" 표시가 틀어진다. `theme.preset`이 이미 `"사용자 지정"`을 `current`에 넣어 이 혼재를
> 갖고 있다. **언어 행은 저장값(`@tagName`)으로 비교하고 표시만 매핑을 거치게** 분리해야 한다.
>
> config 파일 자체는 안전하다 — `serialize.zig`는 키와 값만 부분 갱신하고 `doc`이나 표시명을 쓰지 않으므로
> **파일 내용은 언어에 독립**이다.

### 5.1 `auto`의 로케일은 platform이 읽고, 판정은 중립 층이 한다

중립 층은 OS API를 부를 수 없으므로 경계를 이렇게 나눈다.

- **platform이 읽는다** — OS가 주는 로케일 식별자를 **문자열 그대로** 중립 층에 넘긴다
  (macOS `NSLocale`, Windows `GetUserDefaultLocaleName`). platform은 그 문자열의 의미를 해석하지 않는다.
- **중립 층이 판정한다** — 로케일 문자열 → `Lang` 매핑은 `src/i18n.zig`가 소유한다. 플랫폼마다 표기가
  다르므로(`ko-KR`·`ko_KR`·`ko`) 정규화도 여기서 한 번만 한다. 알 수 없는 값은 `en`으로 떨어진다.

이 분리가 있어야 판정 규칙이 플랫폼 수만큼 복제되지 않고, 로케일 문자열을 주입해 판정을 **OS 없이 테스트**할
수 있다.

**언어 전환에 재시작을 요구하지 않는다.** 번역 대상(§2)이 전부 chrome이 매 프레임 그리는 표면이므로, config
값이 바뀌면 다음 프레임에 반영된다. 메뉴바는 영어 고정이라 `command_catalog_dirty` 재빌드가 이 경로에
필요하지 않다.

### 5.2 언어 상태는 UI 스레드가 소유한다

현재 언어는 프로세스 전역 하나다(창마다 다를 이유가 없고, 호출부 수백 곳에 파라미터를 실어 나르지 않기
위해). 그래서 [I/O–렌더 스레딩 분리](io-render-threading.md) 모델 안에서 소유자를 못 박는다.

- **쓰기**: config 로드·설정 변경 경로에서만. 즉 **UI 스레드**다.
- **읽기**: 문자열을 DrawList로 옮기는 시점 — `app/host.zig`가 "코어→DrawList 복사는 **락 아래**"라고 둔
  그 구간이며, 역시 UI 스레드다.
- **렌더 스레드는 이 전역을 보지 않는다.** shaping은 DrawList 복사본만 보므로(락 밖) 이미 해석된 문자열
  슬라이스만 만진다. 문자열이 static이라 그 슬라이스는 언어가 바뀌어도 유효하다(§3.1).

즉 언어 전환은 **프레임 경계에서만** 일어나고, 한 프레임 안에서 두 언어가 섞이지 않는다. 이 불변식이
깨지는 곳(예: 렌더 스레드가 직접 `t()`를 부르는 경로)이 생기면 그때 잠금이 아니라 **소유 경계**를 다시 본다.

**워커는 문장을 만들지 않는다 — 키만 넘긴다.** 원자화는 경합을 없애지만 그것으로 끝이 아니다. 워커가
`t()` 로 만든 문장을 **소유해서 캐시하면** 그 문장은 워커가 돈 시점의 언어에 얼어붙는다. 아카이브 상세를
한국어로 연 뒤 화면 언어를 영어로 바꾸면 가림 문구만 한국어로 남아, 바로 위의 "한 프레임 안에 두 언어가
섞이지 않는다"가 깨진다. 그래서 워커는 `Turn.redacted` 같은 **상태만** 세우고, 문구는 그리는 쪽(UI
스레드)이 키에서 푼다. 일반화하면 — **번역 문자열의 수명은 프레임을 넘기지 않는다.** 넘기는 것은 키다.

**쓰기는 UI 스레드뿐이지만 읽기는 아닐 수 있다 — 그래서 전역을 원자적으로 둔다.** 이것을 넣게 만든 사고는
아카이브 상세를 읽는 **떼어낸 워커**가 가림 문구를 만들며 `t()`를 부르던 것이었다. 평범한 `var`였을 때 그
조합은 UI 스레드의 쓰기와 동기화 없이 겹치는 자료 경합이다 — 값이 enum 하나뿐이라 눈에 보이는 손상은
없더라도 정의되지 않은 동작이다.

**그 호출부는 바로 위 규칙(워커는 키만 넘긴다)으로 이미 없어졌다.** 그래도 원자성을 되돌리지 않는 이유는,
그 규칙이 깨졌다는 것을 **컴파일러가 말해 주지 않기 때문**이다 — 워커에서 `t()`를 한 줄 부르는 것은 아무
경고 없이 통과하고, 그때 평범한 `var`는 조용히 UB가 된다. `.monotonic` 한 쌍의 값이 그 위험보다 싸다.
그 이상의 순서가 필요 없는 이유는 **이 값과 함께 건너가는 다른 상태가 없기 때문**이다(문자열은 static).
소유 규칙은 그대로다 — 쓰기는 여전히 UI 스레드뿐이다.

**필터 판정에서 언어를 뺀다 — 그래서 화면의 인덱스가 안 흔들린다.** 설정 폼의 검색 필터는 `meta.doc`으로
매칭하는데 그 `doc`이 언어를 탄다. 그대로 두면 언어가 바뀌는 순간 **통과 행 집합과 그 순서가 함께 바뀌고**,
`selected`는 인덱스일 뿐이라 그 자리에 다른 설정이 들어와도 모른다 — 확정하면 사용자가 열지도 않은 키에 값이
써진다. 실측(쿼리 4186개, 전 섹션, 순서 포함 비교)으로 **1499개(35.8%)** 가 두 언어에서 서로 다른 나열을 냈다.

그래서 `settingsRowMatches`가 **키 + 모든 언어의 문장**을 본다. 현재 언어를 안 보는 것이 그 함수의 계약이고,
`Field` 5종이 해석된 `doc`과 함께 `doc_key`를 싣는 이유가 그것이다. 판정이 언어를 안 타면 집합도 순서도 안
흔들리고, 그러면 **선택뿐 아니라 `count`·스크롤 위치·열린 팝업의 인덱스·사용자의 검색어까지 전부** 따라온다.

**전환 지점마다 다시 앉히는 방식은 버렸다.** 그 방식은 "언어가 바뀌는 지점"을 하나씩 세는 것이라 **네 번
연속으로 구멍을 냈다** — 경로 넷 중 둘만 막음 → 스키마 밖 행을 못 봄 → 앵커를 뜨는 쪽이 행 종류 다섯만 앎 →
그리고 **다른 창은 그 지점을 아예 안 지남**. 마지막 것은 원리적으로 못 고친다: 창 A가 언어를 바꾸면 창 B의
`selected`는 그 프레임에 이미 정체를 잃는데 B는 그때 아무 코드도 안 돌린다. 세는 방식으로는 다 셀 수 없다는
것이 그 네 번이 보여 준 것이고, 그래서 지점이 아니라 **성질**을 지킨다 — "통과 행 집합과 순서는 `i18n.lang()`에
의존하지 않는다"를 전칭 테스트가 잰다.

**대가**: 화면에 안 보이는 문장으로 행이 통과한다(영어 화면에서 `폰트`로 걸러도 그 행이 남는다). 그 성질 자체는
새롭지 않다 — 키 매칭이 이미 그랬다. 실측으로 통과 행이 **15.8% 늘고**, 그 증가는 한국어 화면에 몰린다(en +8.2% / ko +24.5%). 그것을 감수하는 이유는
"결과가 조금 많다"와 "선택이 조용히 다른 키로 미끄러진다"가 같은 무게가 아니기 때문이다. 부수 효과로 **영어
이름으로도 찾을 수 있다**(한국어 화면에서 `language`로 `ui.language`를).

**언어가 아닌 축은 이것으로 안 닫힌다.** 행 집합을 바꾸는 것이 파일일 때 — `reloadConfig`가 설정 폼을 닫지 않고
도는 동안 `env.*`·`macro.*`가 늘거나 줄 때 — 같은 미끄러짐이 난다. 그 축은 **키로 다시 앉혀서** 닫는다
(`captureSelectedRowKey` → 바꿈 → `restoreSelectedRowKey`). 뜨는 것이 **바꾸기 전**이어야 한다는 것이 그
배선의 전부다. 바뀐 뒤에 뜨면 이미 미끄러진 자리를 그대로 고정한다.

**초기값**: config 로드 전에는 `en`이다. config 로드가 첫 프레임보다 늦어 한국어 사용자가 영어 화면을
스치는 일이 없어야 하며, 그렇지 않다면 로드 완료 전 렌더를 미루는 쪽이 맞다(구현 시 확인할 것).

**전역 하나의 대가 — 창이 여럿일 때 마지막 적용이 이긴다.** 언어는 프로세스 전역인데 `Config` 사본은
**창마다** 있다(`AppSession.loaded_config`). config 재로드는 활성 세션 하나에만 걸리므로, 창 A에서 언어를
바꾼 뒤 창 B가 아직 옛 사본을 든 채 설정을 만지면(`reapplyLoadedConfig`) 그 옛 값이 전역을 덮어 **창 A의
언어까지 되돌아간다.**

이것을 "언어를 창별로 둔다"로 풀지 않는다 — 창마다 다른 언어를 쓸 이유가 없고, 호출부 수백 곳에 언어를
실어 나르는 비용이 이 드묾에 비해 크다. 근본은 언어가 아니라 **창마다 config 사본이 갈릴 수 있다**는
구조이고(다른 설정도 같은 성질을 갖는다), 그것을 언어만 특별 취급해 우회하면 일관성이 깨진다. config는
파일 하나이므로 재로드하면 수렴한다.

## 6. 레이아웃 계약

### 6.1 표시 폭을 상수로 박지 않는다

chrome은 등폭 셀 그리드이고(`chrome/components/text_area.zig`: "chrome 글자가 등폭이라 셀 = 실제 advance"),
그래서 **문자열 길이가 좌표를 직접 결정한다.** 번역 대상 문자열의 칸 수를 상수로 두면 언어가 바뀔 때 좌표가
어긋난다. 칸 수는 [CT-OWN](layering-and-portability.md) §7.9의 배치(`chrome/text_layout.zig`)에서 **측정해서**
얻는다.

이 규칙이 없을 때 무엇이 깨지는지는 이미 코드에 있다 — `chrome/components/find.zig`의 페이지 표시기는
한국어 `"찾음"`·`"없음"`(각 4칸)에 맞춰 예약 폭을 `4`로 두었다. 영어 `"Found"`는 5칸이라 그 예약을 침범한다.
**즉 이 코드베이스에서 깨지는 방향은 en→ko가 아니라 ko→en이다.** 이 자리는 §2가 find를 영어로 고정했으므로
그 표시기를 영어로 바꿀 때 함께 고친다.

**다만 이 규칙의 적용 범위는 좁다.** 번역 대상 표면(세팅·알림·모달)의 `_cols` 상수는 전수 확인 결과 문자열
폭이 아니라 위젯·여백 기하였고(HSV picker 그리드·라벨 간격·패널 폭), 문자열 폭 상수를 든 `find`·`palette`는
영어로 고정됐다. 이 절은 **새 문자열을 넣을 때 지켜야 할 규칙**으로 유효하며, 지금 고칠 부채 목록이 아니다.

### 6.2 문자열 안에 정렬·상태 기호를 넣지 않는다

번역 대상 문자열에는 **글자만** 넣는다. 다음은 전부 배치나 상태 모델이 소유해야 한다.

| 섞인 것 | 실제 코드 | 왜 문제인가 |
| --- | --- | --- |
| 정렬 공백 | `"Enter to close   Esc to cancel"`, `"Settings   19/20"` | 번역하면 열이 어긋난다 |
| 들여쓰기 | `"  브랜치 표시"` | 번역자가 앞 공백을 지우거나 늘린다 |
| 상태 기호 | `"✓ 브랜치 표시"`, `"✓ 대기중"` | 체크 상태가 **문자열 안에** 있어 상태 모델과 이중화된다 |
| 스피너 | `"◴ 분석 중"`, `"◷ 분석 중"` | 애니메이션 프레임이 번역 단위에 섞인다 |

이 깨짐들은 **넘침을 만들지 않으므로 pseudolocale이 잡지 못한다.**

### 6.3 값이 끼어드는 문자열은 자체 보간을 쓴다 — `std.fmt`를 쓸 수 없다

**`std.fmt`는 포맷 문자열이 comptime-known이어야 한다**(`comptime fmt: []const u8`). 번역 문자열은 언어에
따라 런타임에 고르는 값이므로 그대로 넘기면 컴파일 에러다.

```zig
std.fmt.bufPrint(&buf, "{d}분 전", .{7})    // OK — 틀이 리터럴
std.fmt.bufPrint(&buf, t(.rel_ago),  .{7})  // error: unable to resolve comptime value
```

그래서 **런타임 틀을 받는 보간 함수를 `src/i18n.zig`가 함께 소유한다**. gettext·i18next가 자체 보간을 갖는
것과 같은 이유다(C `printf`는 런타임 틀을 받으므로 gettext는 그것을 그대로 쓴다 — Zig는 못 쓴다).

```zig
pub const Arg = union(enum) { s: []const u8, d: i64 };
pub fn format(buf: []u8, template: []const u8, args: []const Arg) ![]u8;
```

- **문법은 `{0}`·`{1}` 위치 자리표시자만** 지원한다. 타입 지정자(`{d}`·`{s}`)를 두지 않는 이유는 값의 타입이
  `Arg`에 이미 있어 번역자가 틀에서 타입을 맞출 필요가 없기 때문이다 — 번역자가 `{s}`를 `{d}`로 잘못 옮기는
  실패 모드를 없앤다.
- **인자가 하나여도 번호를 쓴다.** 예외를 두지 않아 파서와 번역 규칙이 하나로 유지된다.
- **번호가 필요한 이유는 어순이다.** 번역자가 문장 안에서 자리를 바꿔도 올바른 값이 들어간다.

  ```
  en: "Moved {0} to {1}"                   → Moved report.md to docs/
  ko: "{1}(으)로 {0}을(를) 옮겼습니다"       → docs/(으)로 report.md을(를) 옮겼습니다
  ```
- **범위 밖 인덱스는 원문을 그대로 남긴다.** 번역 실수로 앱이 죽지 않게 한다 — 표시가 이상해질 뿐이다.
- **버퍼가 모자라면 자른다.** 에러를 올려 호출부마다 처리하게 하지 않는다. 이 자리의 실패는 "메시지가
  길다"이지 "앱이 멈출 일"이 아니고, 잘림은 이미 `truncateToBoundary`가 쓰는 처리다(§6.4). 자를 때는
  UTF-8 경계를 지킨다.

**포맷 실패 폴백은 별도 키를 둔다.** 현재 코드에 이 패턴이 있다 — `file_panel.zig`가 경로를 끼운 안내를
만들다 실패하면 **인자 없는 짧은 문장**으로 떨어진다. 번역 대상이 되면 정상형과 폴백형이 **각각 키**를
가져야 한다(같은 키의 두 변형이 아니라 서로 다른 문장이기 때문이다).

### 6.4 고정 바이트 버퍼는 언어별 예산이 다르다

표시 칸(§6.1)과 **별개 축**이다. 메시지를 고정 배열에 복사하는 경로가 있고
(`app_session.zig`의 `notice_message_buf: [512]u8`·`confirm_message_buf: [256]u8`), 그 복사는
`truncateToBoundary`로 **에러 없이 조용히 절단**한다. 번역으로 길이가 늘면 경고 없이 잘린다.

한국어는 같은 문장이 영어의 **1.4~2.2배 바이트**다(한글 3바이트 + ASCII 혼합 실측). 현재 메시지는 전부
버퍼 안에 들어가므로 **지금 고칠 부채는 아니고**, 새 문자열을 넣거나 기존 문장을 늘릴 때 지킬 규칙이다 —
버퍼 크기는 **가장 긴 언어 기준**으로 잡고, 절단이 일어났는지 알 수 있어야 한다.

### 6.5 중국어·일본어가 저렴한 이유

CJK는 한글과 같은 EAW Wide(2칸)라 §6.1의 측정 경로가 그대로 성립하고, 폰트는 `font.fallback` cascade에
얹으면 된다. BiDi처럼 배치 자체를 바꾸는 요구가 없다. 한중일 한자의 자형 차이(Han unification)는
[폰트 전략](font-strategy.md)의 fallback 캐시 키가 `locale hint` 자리를 이미 열어 두었으나, **UI 문자열에서는
문제가 되지 않는다** — 한 화면의 UI 문장은 한 언어이고, 한중일이 섞이는 것은 터미널 *출력*이라 이 계약 밖이다.

## 7. 번역하지 않는 것

기계 판독 경로에 로케일이 섞이면 fixture 재생과 round-trip이 깨진다.

- PTY 출력·터미널 화면 내용
- config 키 이름, `action_key`(`parseAction` round-trip이 고정한다)
- trace·구조화 로그·snapshot artifact
- 파일 경로

### 7.1 CLI 출력은 영어로 고정한다

`maru` 명령의 stdout/stderr는 `ui.language`를 **따르지 않고 항상 영어**다(§2 경계). 키로 빼지 않으며
번역 테이블에 넣지 않는다.

근거 셋:

- **스크립트가 출력을 파싱한다.** CLI는 파이프라인·CI·셸 스크립트에서 쓰이므로, 출력이 사용자 로케일에
  따라 바뀌면 `grep`·조건 분기가 환경마다 다르게 동작한다. 이는 §7 앞 목록의 "기계 판독 경로"와 같은 이유다.
- **Unix 관례.** 도구의 진단 출력은 로케일 중립(`LC_ALL=C`)이 기본이고, 사용자가 그 출력을 그대로 복사해
  검색·이슈 보고에 쓴다.
- **앱 UI와 표면이 다르다.** CLI는 터미널에 직접 쓰고 세팅 화면을 갖지 않는다. 언어 선택 UI가 닿지 않는
  자리에 언어 분기를 두면, 사용자가 바꿀 수 없는 상태가 생긴다.

현재 한국어인 7개(`main.zig`의 `install-cli`·`terminfo` 캐시·`trace anonymize` 진단)를 영어로 맞춘다.

**config 파일에 쓰는 텍스트도 같다.** `app_session/settings.zig`가 Reset 시 파일에 넣는 헤더 주석
(`"# Maru config — Reset to Defaults로 초기화됨…"`)은 UI가 아니라 **파일 내용**이다. 사용자가 편집기로 열어
보는 텍스트이고 앱 언어 설정과 함께 움직이지 않으므로(파일은 남고 설정은 바뀐다) 영어로 둔다.

### 7.2 키를 안 거친 문자열은 타입과 리터럴 검사로 막는다

**판정자는 문자열이 아니라 경계다.** "이 문자열이 사용자에게 보이는가"는 토크나이저가 판정할 수 없지만
(한글 리터럴로 치면 주석·테스트가 대량 오탐 — `src/chrome`에만 1000줄 이상), **그 문자열을 받는 함수는
이미 그것을 선언하고 있다.** [아이콘 리터럴 가드](../tests/boundary/icon_literals.zig)가 값(등록 cp 집합)을
판정자로 삼은 것과 달리, i18n은 **호출 경계**를 판정자로 삼는다.

**1차 — 타입.** 번역 대상 문자열을 받는 자리는 `[]const u8`이 아니라 `i18n.Key`를 받는다. `switch` 분기로
문자열을 **반환**하는 함수는 반환 타입을 `Key`로 바꾼다. 그 경로에는 리터럴이 컴파일되지 않는다. 값이
섞이는 자리는 §6.3의 보간 진입점(`Key` + `[]const Arg`)을 쓴다.

**문자열 진입점(`…Raw`)을 만들지 않는다.** 필요해 보이는 두 경로가 실측 결과 모두 다른 것으로 풀린다.

| 경로 | 실제 | 처리 |
| --- | --- | --- |
| `app_host_abi.zig`가 Swift 바이트를 `showNotice`로 전달 | 외부 유래 텍스트가 아니라 **Swift가 만든 UI 문자열**이고 그런 호출이 전부 1개다(`MaruAppHost.swift`의 workspace 부분 복원 안내) | **Swift가 UI 문자열을 만들지 않게** 한다 — 상태만 알리고 문장은 Zig가 만든다 |
| `file_panel.zig`의 `showNotice(message)` | 리터럴 틀 + 동적 인자(`bufPrint`) | **보간 진입점** |

첫 줄에서 ABI가 바이트 대신 **키**를 받게 하는 길도 있다(`icon_codepoints.h`가 Zig 상수를 C 헤더로
내보내는 선례). 하지만 호출 하나를 위해 헤더 생성 도구와 ABI 버전 인상을 들이는 것보다, **문장을 만드는
자리를 Zig로 옮기는 쪽이 싸다.** 규칙은 하나다 — **Swift는 UI 문자열을 만들지 않는다.**

**단, `NSOpenPanel.message` 4건은 별도 판단이 남는다.** OS 파일 선택창은 Swift가 띄우고 그리므로, 이
규칙을 그대로 적용하려면 선택창 종류별 메시지를 ABI로 실어 날라야 한다. 이미 `take_file_pick_request`가
"어떤 선택창인가"를 Zig에서 Swift로 넘기므로 **그 요청에 메시지 키를 함께 싣는 길**이 있으나, 4건을 위해
ABI를 넓히는 것이 맞는지는 구현 시 정한다.

`Raw`를 두지 않으면 우회로도 없다. **나중에 진짜 외부 텍스트를 표시할 필요가 생기면** 그때 진입점을
추가하되, 그것이 §7.2의 봉쇄를 여는 결정임을 알고 열어야 한다.

**2차 — 리터럴 검사.** 타입으로 덮이지 않는 자리가 남는다. `std.zig.Tokenizer`로 우변이 리터럴인지
`t(...)`/`Key`인지 판정한다. 한글 여부를 보지 않으므로 오탐이 없다.

- 전환 중인 함수 — 아직 `Key`로 바꾸지 않은 sink의 인자(`showNotice` 호출 130,
  `showConfirmButtons`/`showConfirmChoices` 14). **전환이 끝나면 없어진다.**
- **정적·동적이 섞이는 컬렉션 — 여기는 없어지지 않는다.** `context_menu_items_buf`는
  `[N][]const u8`인데 리터럴 대입 20개(번역 대상)와 동적 대입 15개(브랜치명·잘린 제목)가 **같은 배열을
  공유**한다. 원소 타입을 `Key`로 바꿀 수 없고, `union { key, dynamic }`으로 바꿔도 `dynamic` 쪽이 같은
  우회로가 된다. **이런 자리에서는 2차 검사가 영구적으로 유일한 방어다.**

**전환기 운영 — baseline 원장.** I3가 끝나기 전에는 위반이 남으므로 남은 개수를 원장에 고정하고 **늘면
실패**시킨다. [external source digest](../tests/boundary/external_source_digests.zig)가 이 저장소에 이미 쓰는
패턴이다 — 판정 로직과 실측값 원장을 분리하고, 값이 예상과 다르게 움직이면 갱신을 거부해 사람이 보게 한다.
부수 효과로 원장 숫자가 **I3의 진행률**이 된다. 이것은 별도 층이 아니라 **2차 검사의 운영 방식**이다(판정자를
공유한다).

**반대 방향도 막는다.** §2가 영어로 고정한 표면(CLI·find·메뉴/팝업)에는 "한글이 없어야 한다"는 단순 판정이
성립하므로 별도 게이트를 둔다.

**게이트 파일은 독립으로 둔다.** `tests/boundary/imports.zig`는 레이어 import 전용이고, 그 밖의 경계 규칙은
`icon_literals.zig`·`cli_purity.zig`처럼 별도 파일로 추가하는 것이 이 저장소의 관례다.

**3차 — 표에 아무도 안 쓰는 키가 남지 않는가.** 1차·2차는 "화면 문자열이 키를 거치는가"를 보는데, **되돌린
작업의 잔해로 남은 키**는 둘 다 통과한다. 실제로 15개가 쌓여 있었고, 그중 `git_local_check` 은 자동 치환이
셸 스크립트 본문에 `maru.i18n.t(.git_local_check)` 를 글자 그대로 써 넣은 사고를 되돌리며 남은 것이다. 즉
고아 키는 "안 쓰는 문장"이 아니라 **옮기다 만 자리**라서, 다음 사람이 살아 있는 계약으로 오해한다. 표의 모든
키가 `src/**`·`tests/**` 어딘가에서 `.<key>` 로 참조되어야 하고, 아니면 이름을 전부 출력하며 실패한다
([i18n_orphan_keys.zig](../tests/boundary/i18n_orphan_keys.zig)). 참조가 테스트에만 있는 키는 통과한다 —
"먼저 키를 넣고 화면을 붙이는" 정상 순서를 막지 않기 위해서다.

**4차 — 문자열이 한 언어로 얼어붙지 않는가.** 1~3차는 "화면 문자열이 키를 거치는가"를 보는데, **키를
거치고도 굳는 형태**가 하나 있다. 컴파일러가 절반은 막는다 — 컨테이너 수준 `const` 에 런타임 조회를 넣으면
거부한다.

```zig
const frozen = i18n.t(.set_nav_hint);
// error: unable to evaluate comptime expression        (std/atomic.zig — 언어 상태가 원자값이라 여기서 걸린다)
// note:  initializer of container-level variable must be comptime-known
```

**그런데 언어를 인자로 박으면 통과한다.** `tIn(<언어>, …)` 은 comptime 에 값이 정해지므로 comptime 자리에
들어갈 수 있고, 그 순간 그 문자열은 한 언어로 굳는다. 실측(같은 프레임, 다른 언어):

```
PINNED = ← 섹션 · → 설정 · ↑↓ 이동 · ⏎ 선택      const pinned = i18n.tIn(.ko, .set_nav_hint);
LIVE   = ← section · → setting · ↑↓ move · ⏎ select   i18n.t(.set_nav_hint)
```

**앞의 세 방어가 전부 통과시킨다.** 2차는 "우변이 리터럴인가"를 보는데 우변은 `tIn(...)` 호출이고, 3차는
"참조가 있는가"를 보는데 참조는 있다. 즉 이 형태는 **모든 검사를 통과하면서 `ui.language` 를 안 따른다** —
사용자에게는 "그 화면만 안 바뀌는" 것으로 보인다.

[pinned_language.zig](../tests/boundary/pinned_language.zig)가 제품 코드에서 **언어를 리터럴로 박은** `tIn`
호출 수를 파일별 원장에 고정한다. **0 이 아니라 원장인 이유**는 실재하는 자리가 있고 그 원인이 번역이 아니기
때문이다 — **모바일 표면 전체가 아직 런타임 언어 전환을 안 받는다.** 설정 행 목록이 `inline for` 로 만드는
comptime 테이블이라 런타임 조회를 못 쓰고(`mobile_config.zig` 의 `mobileDocLabel` doc 주석), 그리기 경로는 그
화면과 **같은 말을 써야** 해서 함께 `ko` 로 고정돼 있다(`mobile_bridge.zig` 의 `session_title` doc 주석). 그
구조를 고치는 것은 별개 작업이고, 지금 막을 수 있는 것은 **수가 느는 것**이다.

**값의 단일 출처는 그 파일의 `inventory` 다** — 아래는 지금 어느 파일이 원장에 올라 있는지를 보이려는
것이고, 수는 슬라이스마다 움직인다. 실제로 이 문서가 한동안 `mobile_bridge.zig → 30` 이라고 적고 있었는데
그때 원장은 이미 37 이었다(원격 세션 목록이 일곱을 더한 뒤였다) — **산문 속 숫자는 컴파일러도 게이트도 안
본다.** 대조할 일이 있으면 원장을 열어 본다.

```
src/platform/mobile/mobile_bridge.zig  →  38
src/platform/mobile/mobile_config.zig  →   8
```

**원장 숫자는 부채의 크기가 아니라 진입점 수다.** `mobileDocLabel` 은 `tIn` 호출 **하나**로 스키마의 모든 doc
라벨을 박는다 — 라벨을 백 개 붙여도 원장은 안 움직인다. 원장이 막는 것은 "박는 **자리**가 느는 것" 이지 "박힌
문자열이 느는 것" 이 아니다.

**세는 쪽이 기본값이고, 예외만 뺀다.** `tIn` 은 언어를 인자로 받는 순간 그 자리를 `ui.language` 에서 떼어
놓는다 — 어떻게 적었든 그렇다. 그래서 "박은 형태를 알아보고 센다" 가 아니라 **"전부 세고 예외만 뺀다"** 로
짠다. 반대로 짜면 한 글자로 빠져나간다:

```zig
const a = i18n.tIn(.ko, k);            // 센다
const b = i18n.tIn(Lang.ko, k);        // ← "첫 인자가 `.` 일 때만" 세면 여기서 샌다
const c = i18n.tIn(pinned_lang, k);    // ← const 를 거쳐도 샌다
const d = i18n.tIn(if (x) .ko else .en, k);  // ← 분기로도 샌다
```

넷 다 컴파일되고 넷 다 언어가 박힌다. 처음에는 좁게 짰다가 적대적 검증이 실측으로 잡았다. 그리고 그것은
특이한 표기도 아니다 — enum 을 이미 import 한 파일에서는 `Lang.ko` 가 오히려 자연스럽다.

**빼는 것은 셋뿐이다.** ① 모든 언어를 **도는** 호출(`tIn(@field(Lang, lf.name), …)`) — 설정 검색 필터가 화면
언어 의존을 없애려고 그렇게 쓴다(§5.2). 빼는 조건은 정확히 **첫 인자의 첫 토큰이 `@field` 이고 그 이름이
문자열 리터럴이 아닐 때**다. `@field(Lang, "ko")` 는 반사로 적었을 뿐 정확히 한 언어를 고른다 — 처음에는
`@field` 이면 무조건 뺐고, 그 한 줄로 컨테이너 수준 `const` 에 언어를 박을 수 있었다. 여러 줄 문자열도
리터럴로 친다 — 따옴표만 보다가 그 철자로 면제가 다시 열렸고, 그것은 철자 문제가 아니라 **면제 로직 자신의
버그**였다.

② `test` 블록 안의 것 — 두 언어를 나란히 확인하는 것은 오히려 권장하는 형태다. **중첩된 `test` 까지**
뺀다(`remote_term_backend.zig` 가 `struct { test "…" {…} }` 형태로 쓴다) — 최상위만 빼면 권장하는 테스트를
쓴 사람이 벌받는다. 오늘 그 파일의 중첩 `test` 안에는
`tIn` 이 없어 실제로 갈리는 자리는 **0 개다** — 지금 나는 오탐을 고친 것이 아니라 그 형태를 쓸 때 나지 않게
미리 막은 것이다.

③ `fn <이름>(` 정의 — 호출이 아니다. 앞 판은 이 제외가 프로세스 축에만 있었는데 커밋 메시지는 **두 축
모두에** 적었다. 한쪽만 돌려 보고 전체로 적은 것이다.

**이것은 토큰 스캐너이고, 스캐너는 철자를 본다.** 같은 일을 하는 표기는 무한히 많으므로 "전부 잡는다" 는
목표가 될 수 없다. 이 게이트를 세우는 동안 적대적 검증이 새 철자를 **여섯 라운드** 내리 찾아냈다
(`Lang.ko` → `@field(Lang, "ko")` → `@field(Lang, name)` → `@call(.auto, tIn, …)` → 여러 줄 문자열 `\\ko`
→ `@import("i18n.zig").setLang(.ko)`).
그래서 이 게이트가 서 있는 자리는 §7.3 이 리터럴 게이트에 대해 이미 받아들인 선과 같다 — **실수는 잡고,
의도적 우회는 리뷰가 잡는다.** 지금 열려 있는 철자(`@call`, 별칭, 따옴표 식별자, `@field(i18n, "setLang")(…)`)는 게이트 머리에 알면서 적어
두었다. **이름이 식별자인 `@field(Lang, name)` 만은 `tIn` 축에만 해당한다** — 프로세스 축에는 그 면제가
없어 닫혀 있다.

**넓게 세는 쪽이 기본값이라는 것을 한 번 어겼다.** 프로세스 축에서 흔한 이름의 오탐이 **걱정돼** 한정자
(`i18n.<이름>(`)를 요구했는데, 그 오탐은 저장소에 실재하지 않았고(충돌하는 정의는 표 자신뿐) 대신
`@import("i18n.zig").setLang(.ko)` 을 놓쳤다 — 그 인라인 import 표기는 `schema.zig` 가 이미 쓰는 관용이다.
**없는 오탐을 막느라 있는 검출을 버렸다.** 오탐은 원장에 사유를 적으면 되지만 누락은 조용하다.

**표를 직접 읽는 길은 가시성으로 닫는다.** `i18n.ko.<키>` 는 `tIn` 이라는 글자가 없어 두 축이 영영 못
본다(실측으로 컴파일되고 언어가 박힌다). 그래서 `en`/`ko` 를 **비공개로 바꿨고**, 밖에 소비처가 0 인
`Table` 도 함께 닫았다. 그 셋이 다시 `pub` 이 되면 게이트가 **컴파일 시각에** 거부한다(`@hasDecl` 세 줄).

**표의 공개 표면 전체를 명부로 고정하는 판도 만들어 봤다가 걷어냈다.** 표는 파일째 면제라 그 안에
`pub fn koLabel(k) { return tIn(.ko, k); }` 을 두면 호출부의 이름이 두 축 어디에도 없어 영영 0 이다 —
그것이 명부의 근거였다. 그러나 **그 위반은 오늘 0 이고, 명부는 가정에 대한 방어였다.** 손으로 짠
스캐너로 만들다 네 라운드를 잃었고(`pub inline fn`·중첩·`extern "c"`·비공개 컨테이너 오탐·별칭 재수출·
조건부 컨테이너가 차례로 새어 나갔다), `@typeInfo` 로 옮긴 뒤에도 깊이 상한과 `is_test` 갈림 같은
곁가지를 계속 낳았다. **표에 새 진입점을 만드는 것은 리뷰가 본다** — §7.3 이 리터럴 게이트에 대해 이미
받아들인 선과 같다. 실제로 이 계약이 바꾼 것은 위 셋의 가시성이고, 못 박는 것도 그것뿐이다.

**이 게이트는 언어 인자가 어디서 왔는지 못 본다.** `tIn(.ko, k)`(박은 것)와 `tIn(resolved, k)`(해상도가 끝난
값을 흘린 것)는 토큰으로 구별할 수 없다 — 후자는 이 계약을 **지키는** 형태인데도 세어진다. 그래서 세는 쪽을
기본값으로 두고, **판정은 사람이 해서 원장에 사유와 함께 적는다.** 원장은 부채 목록이자 "사람이 봤다" 는
기록이다. 놓치는 쪽으로 기울이면 그 기록조차 안 남는다.

**언어를 정하는 자리는 따로, 그리고 전부 센다.** `tIn` 이 한 문자열을 얼린다면 이쪽은 **모든 키**를 얼린다.
표가 언어를 정하는 길은 셋이고 셋 다 같은 일을 한다:

| 호출 | 하는 일 |
| --- | --- |
| `setLang(<언어>)` | 직접 박는다 |
| `applyPreference(<선택>)` | 안에서 `setLang(resolve(…))` 을 부른다. `resolve(.ko, …)` 는 무조건 `.ko` 이므로 `applyPreference(.ko)` 는 `setLang(.ko)` 와 같다 |
| `setOsLocale(<태그>)` | `auto` 와 짝지으면 그 태그가 언어를 정한다 |

**넷째 길이 하나 더 있는데 이 게이트가 지키지 않는다.** `ui.language` 의 **기본값**(`theme.zig` 의
`ui_language: UiLanguage = .auto`)을 `.ko` 로 바꾸면 `applyPreference` 가 프로세스째 한국어로 고정되는데,
호출 수는 하나도 안 움직인다. 그것을 지키는 것은 이 게이트가 아니라 `loader.zig` 의 파싱 테스트
(`test "parse: ui.language auto(default)/en/ko + invalid is forgiving"`)다 — 기본값이 `.auto` 임을 고정한다.

처음에는 `setLang` 만 셌고, **실패 진단문이 "정당한 자리는 `applyPreference` 가 한다" 고 이름까지 적어
가리켰다** — 그 문장을 읽고 그대로 따라간 사람이 정확히 구멍에 도착한다. 그래서 지금은 **정당한 자리도
센다.** 이 축의 원장은 부채 목록이 아니라 **"언어를 정하는 자리의 명부"** 다 — 늘면 사람이 한 번 봐야 한다는
뜻이고, 정당하면 사유를 적고 올린다. 지금 다섯이 적혀 있고 그중 셋이 정당하다: 설정 적용 둘(정당), host
로케일 전달 하나(정당, §5.1), 골든 캡처용 실행 파일 하나(사용자 화면이 아니다), 두 언어의 행 집합을 비교하는
테스트 헬퍼 하나(최상위 `fn` 이라 `test` 마스크에 안 걸린다).

**명부는 이름별로 적는다.** 한 숫자로 합치면 같은 파일 안에서 **정당한 자리를 지우고 그 자리에 못을 박는**
치환이 수를 안 바꿔 초록으로 지나간다(실측했다 — `applyPreference(cfg)` 를 `setLang(.ko)` 로 바꾸면 런타임
언어 전환이 죽는데 합계는 그대로다). 그래서 진단이 증가·감소·**내역 변경**을 구분하고, 줄 번호를 함께 찍는다.
줄었을 때 할 일은 명부를 내리는 것이 아니라 **무엇이 사라졌는지 먼저 보는 것**이다 — 이 축에는 정당한 자리가
들어 있어서, 명부를 내리면 회귀가 정상으로 기록된다.

### 7.3 여기까지 해도 남는 것

2차 검사는 **우변이 리터럴인가**만 본다. `const msg = "한국어"; buf[n] = msg;`처럼 변수를 거치면 데이터 흐름
분석이 필요해 토크나이저로 잡지 못한다. 즉 **실수는 대부분 잡히고, 의도적 우회는 리뷰가 잡는다.**

1차가 끝난 경로는 이 구멍이 없다(타입이 다르므로 변수를 거쳐도 컴파일되지 않는다). 그러나 **모든 sink를
1차로 옮길 수는 없다** — 정적·동적이 섞이는 컬렉션이 남는다. 그 자리에서는 이 구멍이 영구적이며, 이것이
이 계약이 인정하는 최종 한계다.

| sink 종류 | 최종 방어 | 구멍 |
| --- | --- | --- |
| 함수 파라미터 | 1차(타입) | 없음 |
| 정적·동적 혼재 컬렉션(`context_menu_items_buf`) | 2차(리터럴 검사) | 변수를 거치는 우회 |
| ABI(host 가 넘기는 문자열) | **상태만 받는 진입점** | 없음 — 아래 |
| 언어를 박은 호출(모바일 표면) | 4차(언어 고정 원장) | 원장은 **자리**를 센다 — 한 자리가 박는 문자열이 늘어도 안 움직인다 |

**ABI 구멍은 닫혔다(I3f).** 이 계약을 쓸 때는 `app_host_abi` 가 Swift 저작 UI 문자열을 받는 경로가
남아 있었다(workspace 부분 복원 안내 1건). 그 문장을 Zig 로 옮기고 Swift 는 **상태만** 알리게 바꾸면서
`maru_macos_app_session_show_notice` 의 host 소비처가 0 이 됐다. 파일 선택 패널 안내 4 건도 같은 방식으로
**종류만 받는** `maru_macos_file_pick_message` 로 옮겼다.

규율: **표시 문장이 필요한 host 경로가 생기면 그 상태를 받는 export 를 열고 문장은 Zig 가 고른다.**
문자열을 받는 옛 진입점에 새 호출을 붙이면 그 문장이 `ui.language` 를 안 따르고, 번역 대상이 다시
두 언어(Zig·Swift)로 흩어진다.


## 8. 이 계약 밖

다음은 이 문서의 계약에 포함되지 않으며, 각각 별도 이니셔티브다.

- **BiDi 렌더링**(§2).
- **메뉴바·커맨드 팝업·find 오버레이를 번역하는 일.** §2가 영어로 고정했다. 이 결정을 뒤집으려면 아래
  팔레트 검색이 **함께** 열려야 한다 — 표시명이 한국어가 되는 순간 영어 키워드 검색이 끊기기 때문이다.
- **팔레트 검색 품질.** 현재 필터는 fuzzy도 점수도 없는 바이트 단위 부분일치다
  (`platform/macos/command_palette.zig`). 영어를 유지하는 한 이 계약은 그것을 건드리지 않는다.
  (번역하게 되면 코드포인트 단위 비교·영어 원문 병행 검색·초성 검색이 필요하지만, 그것은 i18n이 아니라
  팔레트 UX 과제다.)
- **웹 패널 콘텐츠(`web/`).** WKWebView에 로드되는 TypeScript·HTML은 이 계약 밖이다(사용자 결정
  2026-08-16). 전수 조사 시점에는 번역 대상이 **없다** — `web/src`의 한글은 `//!` 문서 주석이고
  `web/tests`는 마크다운 파서 fixture다. 앞으로 그쪽에 UI 문자열이 생기더라도 이 계약이 자동으로 적용되지
  않으며, 웹 스택은 자기 방식(런타임 로딩이 자연스러운 환경이다)을 고를 수 있다.

- **복수형 규칙.** 이 계약에는 복수형 엔진이 없다. 영·한·중·일 범위에서는 영어 2형(one/other)만 다루면
  되므로 키를 나누어 감당한다. 6형 규칙을 갖는 언어(러시아어 등)를 추가하려면 이 절을 다시 연다.
