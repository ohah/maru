# 모바일 플랫폼 (iOS · Android)

이 문서는 iOS·Android 어댑터(L4)의 계약을 정한다. 층 경계 자체는
[레이어링과 이식성 전략](layering-and-portability.md)이 단일 출처이고, 이 문서는 그 L4 자리에
모바일 두 타깃이 어떻게 들어가는지만 소유한다. 진행 상황은
[모바일 플랫폼 구현 계획](plans/mobile-platform.md)이 소유한다.

**무엇을 그리는가는 여기, 사용자가 어떻게 쓰는가는 [모바일 UX](mobile-ux.md)** 가 소유한다 —
화면 목록·전환 규칙·터치가 컴포넌트에 요구하는 것이 그쪽이다.

**베이스**: PoC 로 실측했다([측정 기록](../tools/mobile-harness/README.md)). 코어 컴파일·GPU
렌더·chrome 컴포넌트·터미널 격자·폰트 래스터·입력·터치·생명주기·present 페이싱을 두
플랫폼에서 확인했고, 여기 적힌 계약은 그 측정 위에 선다.

## 1. 확정 결정

- **모바일은 두 플랫폼 다 원격 전용이다(사용자 확정).** 로컬 PTY 를 아예 두지 않는다.
  iOS 는 선택의 여지도 없다 — 샌드박스가 `fork()`/`exec()` 를 금지한다([베이스](#6-베이스):
  출시된 iOS 터미널이 전부 SSH/Mosh 클라이언트인 것이 같은 결론이다). Android 는 기술적으로
  가능하지만 **일부러 안 한다**: 두 타깃이 같은 모양이 되고, 모바일에 셸 환경(툴체인·패키지)을
  싣는 일이 통째로 사라진다.

  **그래서 모바일 앱은 PC 세션의 원격 뷰어다.** [컨트롤 플레인](control-plane.md)이 선택이
  아니라 전제다. 실측: 모바일 정적 라이브러리에 maru 의 `pty` 심볼이 **0개**다(libc 의
  `_execve` 참조는 std 경로에서 오는 것이고 우리 셸 경로가 아니다).

  **이 결정이 컨트롤 플레인의 현재 계약과 충돌한다.** 지금 계약은 "wire 는 TCP/HTTP 를
  바인드하지 않는다" 이고 보안이 "같은 uid 안의 신뢰 차등" 이다 — peer-cred 는 기계를
  넘으면 존재하지 않는다. 원격 축(전송·인증·암호화)은 그 문서가 새로 소유해야 하고,
  정하기 전에는 모바일에서 붙일 수 없다([계획 M3](plans/mobile-platform.md)).
- **모바일 config 는 데스크톱과 따로다(사용자 확정).** 파일도 스키마도 공유하지 않는다.
  [설정](configuration.md)의 키를 전부 훑어 보면 이유가 드러난다 — `quick-terminal.*`·
  `shell.command`·`input.option-as-meta`·`input.right-click` 처럼 **모바일에 뜻이 없는 것**이
  큰 덩어리이고, 반대로 모바일에만 필요한 것(보조 키바 구성·터치 임계값·원격 접속 프로필·
  배경 동작)은 데스크톱 스키마에 아예 없다. 공유하면 양쪽 다 쓰지 않는 키를 이고 간다.

  **공유하는 것은 값이 아니라 기계다.** 파서·resolve 규율·"파일이 단일 출처" 원칙은
  `src/config` 를 그대로 쓰고, 스키마와 파일 위치만 모바일 것으로 둔다. 원격 세션에 붙어도
  **PC 의 config 를 끌어오지 않는다** — 화면 크기·입력 방식·전력 사정이 다른 기기의 값을
  베끼면 대부분 틀린다. 스키마·파일 위치·읽고 쓰는 경로의 단일 출처는 [모바일 config](mobile-config.md)이고,
  계획은 [M10](plans/mobile-platform.md)이 소유한다.
- **Android IME 는 자체 Java shim 이 받는다**(`NativeActivity` 유지). `NativeActivity` 만으로는
  소프트 키보드가 ASCII 물리 키 이벤트를 줄 때만 입력이 되고 **IME 를 못 받는다** — 한글
  조합이 필수인 터미널에서는 쓸 수 없다. 구글의 `GameActivity`/`GameTextInput` 이 그 자리를
  채우지만 **`AppCompatActivity` 를 상속해 AndroidX 의존 트리와 Gradle 을 끌고 온다**(실측:
  1.2.2~4.4.2 전 버전). 그래서 `InputConnection` 을 직접 받는 ~120줄 Java 로 간다.

  **한글 조합 알고리즘은 우리 것이 아니다.** IME 가 계산해 문자열로 주고, shim 은
  `setComposingText`(조합 중)·`commitText`(확정)를 JNI 로 넘기기만 한다. 같은 조건의
  터미널(Termux)이 `GameActivity` 없이 이 방식으로 선다.

  **판단 근거는 유지보수다.** 모바일은 CI 에 안 붙으므로([계획](plans/mobile-platform.md)) Gradle·AGP·JDK 삼각 버전은
  **정기적으로 돌지 않으면 조용히 썩는다**. `javac` + `android.jar` + `d8` 은 의존이 없고
  안드로이드 SDK 의 하위 호환이 강하다. Gradle 은 Play 배포·App Bundle 처럼 실제로 필요해질
  때 도입한다 — 지금 넣으면 쓰지 않으면서 썩는다.

  **Kotlin 은 쓰지 않는다.** 구조가 같고(같은 콜백 두 개), 대가로 `kotlin-stdlib` 가 APK 에
  들어가며 `companion object` 의 JNI 심볼이 `@JvmStatic` 없이는 런타임에 죽는다. 이 120줄에는
  Kotlin 의 이점이 나올 자리가 없다.
- **draw-list 는 배칭해 그린다.** quad 하나당 draw call 하나는 모바일 타일 기반 GPU 에서
  특히 비싸다. 데스크톱이 이미 vertex buffer 로 배칭하므로(`maru_metal_renderer.m`) 같은
  모양을 쓴다 — 새 경로를 만들지 않는다.
- **두 타깃의 공통분모는 `platform/mobile` 에 둔다.** 창이 하나뿐이고, 좌표가 논리 px 이고,
  터치가 1급 입력이라는 점이 iOS·Android 의 공통이고 macOS 와의 차이다. 반대로 GPU 백엔드는
  공유하지 않는다(Metal↔Vulkan).

## 2. 폴더 구조

```text
src/platform/
  mobile/                  두 모바일 타깃의 공통분모(OS 호출 없음)
    mobile_host_abi.h      플랫폼↔코어 C ABI(quad·입력·조회·SSH 세션)
    mobile_bridge.zig      chrome→quad 투영, 아틀라스 등록부, 입력·hit-test
    mobile_ssh.zig         SSH 세션 ABI(핸들·배압·오류 코드 — §3.0)
  mobile_host/             두 host 가 함께 쓰는 **OS 를 부르는** C
    ssh_pump.{c,h}         소켓·스레드·세션 루프. 화면과 자물쇠는 host 가 훅으로 준다
  ios/
    ios_app_host.m         UIKit host + Metal 백엔드 + CoreText 래스터
  android/
    android_app_host.c     NativeActivity host + Vulkan 백엔드 + JNI Paint 래스터
    MaruActivity.java      IME shim: 조합 중/확정 문자열을 JNI 로 넘긴다
    AndroidManifest.xml
    shaders/               SPIR-V 소스(chrome.vert·chrome.frag)
```

**셰이더와 폰트는 APK asset 으로 들어간다.** 개발 스크립트가 `adb push` 로 넣어 주는 자리
(`/data/local/tmp`)에 기대면 **그 스크립트를 안 돌린 기기에서는 앱이 검은 화면**이다 —
셰이더가 없으면 초기화가 실패한다. 폰트는 조용히 시스템 글꼴로 떨어져 §4 와 어긋난다.

**기기에서 도는 ELF 는 16KB 페이지로 정렬한다**(`-Wl,-z,max-page-size=16384`). Android 15+ 는
16KB 페이지 기기를 허용하고, 4KB 정렬 바이너리는 그 커널에서 **로드 자체가 안 된다** — 경고가
아니라 앱이 안 뜬다. NDK r27 부터 16KB 가 기본이지만 **그 기본값은 ndk-build/CMake 가 넣어 주는
것**이라, 하네스처럼 `clang` 을 직접 부르는 경로에는 안 들어온다. 실측으로 `libmaruchrome.so` 의
LOAD 정렬이 전부 `0x1000` 이었고 4KB 기기가 "ELF 정렬 검사 실패" 를 띄웠다(2026-08-20).
정렬은 `llvm-readelf -l <so> | grep LOAD` 의 마지막 열로 확인한다 — `0x4000` 이어야 한다.

**host 파일 하나가 창·GPU·폰트를 다 갖는다.** 지금 규모(iOS 430줄·Android 977줄)에서는
나누는 것이 이득이 아니다 — 셋이 같은 상태(스왑체인·아틀라스·스케일)를 공유해서, 가르면 그 상태를
넘기는 배관이 코드보다 커진다. 커지면 그때 가른다.

**`platform/mobile` 에는 OS 호출이 없다.** 있으면 `ios/`·`android/` 로 내려야 한다. 이
규칙이 "공통분모" 를 관찰 가능하게 만든다 — 지키는지 여부를 파일 내용으로 판정할 수 있다.

**`platform/mobile_host` 는 그 규칙의 예외가 아니라 다른 층이다.** 소켓·스레드·OS 난수처럼
**두 host 가 똑같이 필요한 OS 호출**을 여기 모은다. 두 host 에 같은 루프를 두 벌 쓰면 갈리고,
갈리면 한쪽에서만 나는 결함이 생긴다 — 그리고 그 결함은 기기에서만 보인다. 여기 있는 것은
데스크톱에서 **그대로 링크해 실서버와 왕복**하므로(`mise run ssh-client-smoke` 의 펌프 회차)
기기에 올리기 전에 초록을 볼 수 있다.

> **그 "데스크톱" 에 Windows 는 없다 — 호스트가 Windows 면 펌프 스텝이 통째로 빠진다.**
> 펌프는 `<netdb.h>`·`<sys/socket.h>` 를 직접 부르는 POSIX 코드이고 스모크도 `std.c.timespec`
> 처럼 Windows 에서 `void` 로 풀리는 타입을 쓴다. 모바일 = iOS + Android 라 **Windows 는 이
> 펌프의 소비자가 아니다.** 그런데 한때 스텝이 호스트 무관하게 걸려 있어, Windows 기기에서는
> `zig build test` 가 자기 변경과 무관하게 통째로 실패했다 — 그 기기의 개발자가 게이트를 아예
> 못 돌린다. `build.zig` 가 `target.result.os.tag != .windows` 로 가른다.
>
> **이식성 가드는 안 빠진다.** `zig build check-ssh-pump-portable` 이 linux-gnu 로 **크로스
> 컴파일**하므로 Windows 호스트에서도 돈다 — glibc feature macro 조합처럼 "한 경로에서만 깨지는"
> 사고를 잡는 진짜 자리는 그쪽이다. Windows 에서 빠지는 것은 **실서버와 왕복하는 스모크**뿐이고,
> 그 회차는 macOS·Linux CI 가 계속 돈다.
>
> **드라이버 둘(`ssh-client-smoke`·`ssh-abi-smoke`)도 같은 이유로 빠진다.** 이유가 두 겹이고
> 둘 다 실측했다. ⒜ `tools/ssh/{client,abi}_smoke.zig` 가 `std.c.socket`·`std.c.open` 을 직접
> 부르는데 Windows 에서 `std.c.O` 는 `void` 라 컴파일이 안 되고, `std.process.Args.Iterator.init`
> 도 Windows 에서 `@compileError` 다. Zig 0.16 의 크로스플랫폼 소켓 API 는 `std.Io.net` 인데
> **이 저장소는 아직 한 곳도 안 쓴다.** ⒝ 더 중요한 것은 **구동할 하네스가 없다**는 점이다 —
> `tools/ssh/client_smoke.sh` 는 `#!/bin/sh` 이고 `/usr/sbin/sshd`·`ssh-keygen` 을 찾아 일회용
> sshd 를 띄운다. Zig 쪽만 포팅하면 **Windows 에서 돌릴 것이 없는 소켓 코드 한 벌**이 남는다.
>
> Windows 에서 이 스모크를 진짜로 돌리려면 ⒜ `std.Io.net` 포팅과 ⒝ OpenSSH for Windows 를 쓰는
> PowerShell 하네스가 **둘 다** 필요하고, 그것은 `maru ssh` 의 Windows 지원(W9)과 함께 갈 일이다.
>
> **빠지는 것은 조용하지 않다.** 빠진 자리마다 빌드가 `[skip] <스텝>: <이유>` 한 줄을 찍는다
> (`noteSkippedStep`). 아무것도 안 만드는 스텝이 말없이 exit 0 이면 그 기기의 개발자가 "돌았다"
> 고 읽는데, 이 저장소는 그 부류의 사고를 이미 한 번 밟았다(체크가 0 개인데 전부 초록으로 봄).

**Vulkan 백엔드를 Linux 와 공유할지는 아직 정하지 않는다.** Linux 백엔드가 생길 때
공통분모가 드러나므로, 그전에 추상 층을 만들면 하나뿐인 사용처에 맞춘 잘못된 경계가 된다.

## 3. 플랫폼↔코어 경계

**플랫폼은 배치를 모른다.** 화면의 쓸 수 있는 크기를 논리 px 로 넘기고 quad 목록을 받는다.
셀 판정도 코어가 한다 — 플랫폼은 점만 넘긴다.

| 방향 | 무엇 | 누가 |
|---|---|---|
| 플랫폼 → 코어 | 논리 크기(safe area 뺀 값) | `maru_mobile_build(w, h)` |
| 코어 → 플랫폼 | quad 목록(rect·색·radius·kind·아틀라스 셀) | `maru_mobile_quads()` |
| 플랫폼 → 코어 | 확정된 키 입력 바이트 | `maru_mobile_input(bytes, len)` |
| 플랫폼 → 코어 | 조합 중 문자열(IME preedit) | `maru_mobile_set_preedit(bytes, len)` |
| 플랫폼 → 코어 | 본문 셀 조회(논리 px) | `maru_mobile_hit_cell(x, y)` |
| 코어 → 플랫폼 | 아직 아틀라스에 없는 코드포인트 | `maru_mobile_missing_*` |
| 코어 → 플랫폼 | 그 글자가 **컬러**인가(어느 아틀라스에 구울지) | `maru_mobile_missing_is_color` |
| 플랫폼 → 코어 | 컬러 아틀라스에 구운 글리프 등록 | `maru_mobile_color_atlas_add` · `maru_mobile_next_color_slot` |
| 코어 → 플랫폼 | 마지막 실패 이름(읽은 쪽이 비운다) | `maru_mobile_last_error` / `_clear_error` |
| 플랫폼 → 코어 | 원격에서 읽은 바이트(SSH) | `maru_mobile_ssh_feed(h, bytes, len, &consumed)` |
| 코어 → 플랫폼 | 원격으로 보낼 바이트 | `maru_mobile_ssh_out_ptr/len` · `_out_consume` |
| 코어 → 플랫폼 | 화면에 그릴 원격 출력 | `maru_mobile_ssh_screen_ptr/len` · `_screen_consume` |
| 플랫폼 → 코어 | **두 번째 채널**을 연다(원격 명령 하나) | `maru_mobile_ssh_open_control(h, cmd, len)` |
| 코어 → 플랫폼 | 컨트롤 채널이 받은 ndjson | `maru_mobile_ssh_control_ptr/len` · `_control_consume` |
| 플랫폼 → 코어 | 컨트롤 채널로 보낼 ndjson | `maru_mobile_ssh_write_control(h, bytes, len, &sent)` |
| 코어 → 플랫폼 | 컨트롤 채널 상태·종료 코드·stderr | `maru_mobile_ssh_control_state` · `_control_exit_status` · `_control_stderr` |
| 플랫폼 → 코어 | 컨트롤 채널에서 읽은 ndjson | `maru_mobile_control_feed(bytes, len)` |
| 코어 → 플랫폼 | 코어가 만든 컨트롤 요청 | `maru_mobile_take_control_request(out, cap)` |
| 플랫폼 → 코어 | `hello` 시한 초과 알림 | `maru_mobile_control_timeout()` |
| 플랫폼 → 코어 | **채널을 못 열었다** 알림(여는 것은 host 다 — 실패도 host 만 안다) | `maru_mobile_control_open_failed()` |
| 플랫폼 → 코어 | 원격 명령이 그냥 끝났다(그 종료 코드) | `maru_mobile_control_note_exit(code)` |
| 코어 → 플랫폼 | 컨트롤 축 상태(host 가 시한 판정에 쓴다) | `maru_mobile_control_state` |
| 코어 → 플랫폼 | **host 진단용** — 껀 이유·세션 수·받은 적 있나(화면은 브리지가 직접 그린다) | `maru_mobile_control_off_reason` · `_session_count` · `_listed` |
| 플랫폼 → 코어 | 새 연결에서 축을 처음부터 | `maru_mobile_control_reset()` |
| 플랫폼 → 코어 | 호스트키 승인(사용자가 답한 뒤) | `maru_mobile_ssh_accept_host_key(h)` |
| 플랫폼 → 코어 | **난수**(OS 난수를 채워 준다) | `maru_mobile_ssh_open(..., entropy, ...)` |
| 플랫폼 → 코어 | 원격 출력을 화면에 넣는다 | `maru_mobile_term_write(bytes, len)` |
| 코어 → 플랫폼 | **키보드를 내려 달라**(올리는 쪽과 대칭) | `maru_mobile_take_keyboard_hide()` |
| 플랫폼 → 코어 | 키보드가 사라졌다 — 편집 중이었으면 확정한다 | `maru_mobile_keyboard_hidden()` |
| 플랫폼 → 코어 | 입력 목적지(로컬 코어 / 원격) | `maru_mobile_set_input_sink(sink)` |
| 코어 → 플랫폼 | 원격으로 보낼 입력 바이트 | `maru_mobile_take_input(out, cap)` |
| 코어 → 플랫폼 | 원격에 돌려보낼 답(DSR·DA) | `maru_mobile_take_response(out, cap)` |
| 코어 → 플랫폼 | **끊어 달라는 요청**(브리지는 소켓을 모른다 — 펌프를 세우는 것은 host 다) | `maru_mobile_take_disconnect()` |

### 3.0 SSH 세션 — 여기만 핸들을 쓴다

**소켓은 host 가 든다.** 브리지에 OS 호출이 0이라는 규칙(§2)은 원격에도 그대로 걸린다 — host 가
TCP 를 열고, 읽은 바이트를 `feed` 로 밀어 넣고, 쌓인 바이트를 `out` 에서 가져가 보낸다.
프로토콜 판단은 전부 코어가 한다([SSH 계약](ssh-client.md) §2). 단일 출처는
`mobile_host_abi.h` 의 `MARU_SSH_*` 와 `src/platform/mobile/mobile_ssh.zig` 다.

**나머지 ABI 는 화면이 하나라는 전제의 싱글턴인데, 원격 세션은 그렇지 않다.** 서버가 여럿일 수
있고 **재접속은 새 세션**이다(SSH 에 재개가 없다 — SSH 계약 §4.1). 그래서 여기만 핸들을 쓰고,
핸들에는 **세대**가 섞여 있다. 번호만 쓰면 닫은 뒤 재사용된 자리를 옛 핸들이 건드려 **끝난
세션의 입력이 새 세션으로 나간다** — 증상이 원인과 멀어 잡기 어려운 부류라 자료구조로 막는다.

**양방향에 배압이 있다.** `out`·`screen` 이 차면 `feed` 는 먹은 만큼만 알려 주고 멈춘다.
`out` 은 **`consume` 할 때까지 남는다** — 소켓이 부분만 받아도 잃지 않는다(부분 전송은 예외가
아니라 정상이다).

**난수는 host 가 준다.** 이 층은 OS 를 못 부르는데 SSH 는 임시키·패딩·cookie 에 예측 불가능한
바이트가 필요하다. `open` 이 32바이트 씨앗을 받아 CSPRNG 를 세우고, **0 씨앗은 거절한다** —
그대로 열면 그 세션의 비밀이 통째로 깨지는데 화면은 멀쩡해서 아무도 모른다.

**접속 정보는 config 에서 온다**(S9b-2a). `ssh.server.<n>.*`([모바일 config](mobile-config.md)
§4.3)를 브리지가 파싱해 들고, host 는 **그 목록만 본다** — 개발용 `ssh.conf` 는 없앴다(같은 사실을
두 자리에 두면 갈리고, 파일 문법도 두 벌이 된다).

**요청을 세우는 자리는 둘이고 요청은 하나다** — 사용자가 목록에서 고른 줄(S9b-2b)과, 원격
세션이 없을 때의 자동 요청이다. host 는 어디서 왔는지 안 본다.

**어느 서버에 붙을지는 브리지가 말한다.** host 가 매 프레임 `maru_mobile_take_server_connect()` 로
가져가고(0=없음, 아니면 **번호+1**), 있으면 그 서버의 값을 읽어 붙는다. 판단이 브리지에 있는
이유는 **누르는 화면이 거기**라서다 — host 가 목록을 다시 해석하면 화면이 고른 것과 갈린다.

- **원격 세션이 없을 때만 자동으로 요청한다**(임시 — 목록 화면이 생기기 전까지 붙을 길이
  그것뿐이다). config 를 읽는 자리에서 판단하고, 이미 붙어 있으면 조용하다 — 배경에서 돌아올
  때마다 config 를 다시 읽으므로(config 계약 §7) 그냥 요청하면 **세션이 둘** 생긴다. 끊긴 뒤
  돌아오면 그때는 다시 붙는다(SSH 에 재개가 없어 되살리기는 없다 — SSH 계약 §4.1).
  **"원격 세션이 있나" 는 입력 목적지가 이미 아는 사실**이라 그것을 본다(host 가 세션 상태로
  세운다) — 같은 사실을 두 번 세면 갈린다.
- **온전하지 않은 줄은 요청하지 않는다.** 주소·이름·지문 중 하나라도 비면 접속 대상이 아니다.
- **실패는 화면이 말한다**(`maru_mobile_set_ssh_status`). host 는 상태와 **실패 이름**만 넘기고,
  사람 말로 바꾸는 것은 브리지가 한다 — host 마다 문구를 적으면 두 플랫폼이 다르게 말한다.

  **그 이름은 터미널 축의 것이다.** 펌프는 실패 이름을 **두 슬롯**에 나눠 든다 —
  `maru_ssh_pump_error`(터미널)와 `maru_ssh_pump_control_error`(컨트롤 채널). 한 슬롯을 같이 쓰던
  시절에는 세션 목록을 열려다 난 이름이 이 자리로 실려 와, **셸이 멀쩡히 떠 있는데 배너가
  "붙지 못했다" 를 세션 내내** 보였다(기기 실측). 컨트롤 축이 안 서는 것은 "세션 목록이 안 보이는
  것" 이지 "접속이 안 되는 것" 이 아니다([§4a](control-plane.md) · [SSH §3.4.1](ssh-client.md)).
  두 슬롯은 규율도 다르다: 터미널은 **먼저 난 것**이 남고(세션이 한 번 무너지는 이야기라 첫 원인이
  답이다), 컨트롤은 **최신이 이긴다**(화면에 들어갈 때마다 여는 독립 사건이라 첫 실패를 붙들면 그
  뒤 이유를 못 본다).

  **화면도 상태를 이름보다 먼저 본다.** `READY` 면 남은 이름이 있어도 배너를 안 띄운다 — 그때는
  화면이 곧 답이다. 순서가 반대면 새는 이름 하나가 멀쩡한 셸 위에 실패를 그린다.
  **배너는 본문보다 나중에 그린다**: 앱 바 아래는 본문 사각형이 시작하는 자리라 먼저 그리면
  셀 격자가 그 위를 덮는다(기기에서 아무것도 안 보였다).
- **처음 보는 서버의 지문도 화면이 묻는다**(`maru_mobile_set_host_key_prompt` ·
  `maru_mobile_take_host_key_decision` · 펌프 `maru_ssh_pump_accept_host_key`). 승인하면 브리지가
  그 지문을 **그 서버 줄에 적는다** — host 는 나르기만 한다. 지문이 이미 있으면 펌프가 그것만
  보고 판정하므로 화면이 안 뜬다(**다르면 묻지 않고 끊는다**).
- **비밀번호는 화면이 묻고 host 가 나른다.** 세션이 `MARU_SSH_STATE_PASSWORD_NEEDED` 로 서면
  host 가 `maru_mobile_set_password_prompt(1)` 로 화면을 열고, 사용자가 확정하면
  `maru_mobile_take_password` 로 가져가 펌프(`maru_ssh_pump_password`)에 넘긴다. **가져가면
  사라지고**(브리지에도 안 남는다) host 도 넘긴 뒤 자기 버퍼를 지운다(SSH 계약 §3.4).
  세션이 그 자리를 벗어나면 host 가 화면을 **끈다** — 안 끄면 사용자는 안 가는 곳에 계속 친다.
  펌프는 2분을 기다리고 그 뒤엔 `password_timeout` 으로 끝낸다(무한히 기다리면 스레드가 남는다).
- **친 글자는 안 보인다.** 화면이 가림표(●)만 그린다 — 어깨 너머로 읽히는 자리다. 다만 **몇 자
  쳤는지**는 보인다: 아무 표시도 없으면 키보드가 먹는지 알 수 없다.
- **공개키 한 줄은 앱이 뜰 때 알린다**(`maru_mobile_set_public_key`). 사용자는 그 줄을 서버
  `authorized_keys` 에 붙여야 처음 붙을 수 있는데, 접속할 때 키를 처음 열면 순서가 거꾸로다.
  Android 는 `id_ed25519.pub` 가 있으면 **개인키를 안 열고** 그것을 읽는다(없을 때만 Keystore 를
  열어 한 줄을 만들고 파일로 남긴다). iOS 는 앱 전용 키 파일에서 만든다.
- **키가 없어도 붙는다**(`maru_mobile_ssh_open` 의 `secret` 이 NULL, 펌프 `cfg.secret` 도 NULL).
  키가 아직 없는 기기는 코어가 `none` 으로 방법 목록만 물어 비밀번호만 여는 서버에 붙는다 —
  iOS 는 키 파일이 없으면 **접속 자체를 안 하고 있었다**.
- **키는 config 에 없다.** Android 는 Keystore 가 봉인한 것을 풀어 쓰고, iOS 는 앱 전용 파일
  (`Application Support/maru/id_ed25519`)을 읽는다 — 경로가 고정이라 설정에 적을 것이 없다
  (iOS Keychain 은 실기기 검증까지 보류: [SSH 계획](plans/ssh-client.md) S9c-2).

**주고받는 자리는 프레임이지만, 그리기와는 무관하다.** 두 host 다 프레임마다 원격에 보낼 것을
가져가는데, **그리기가 실패한 프레임에서도 가져가야 한다**(iOS 의 `nextDrawable` 이 nil 인 순간
등) — 그리기가 잠깐 막힌 것과 친 글자가 안 나가는 것은 사용자에게 전혀 다른 일이다.

**답(DSR·DA)을 가져가는 자리는 플랫폼마다 다르다** — Android 는 펌프 훅에서(화면 바이트 직후),
iOS 는 프레임에서 가져간다. 답은 원격이 보낸 질의에 대한 것이라 **화면 바이트와 같은 걸음에
생기므로** 둘 다 한 걸음 안에 나간다.

**입력은 목적지만 갈린다 — 인코딩은 한 곳이다.** 확정된 글자·특수키·수정자 조합을 바이트로
만드는 일은 코어 몫이고(§3), 원격 세션에서는 그 바이트가 **코어로 가면 안 된다**: 코어에 쓰는
것은 *출력*을 그리는 일이라 사용자가 친 글자가 화면에 한 번 찍히고 원격에는 영영 안 간다
(실측: `whoami` 를 쳐도 아무 일도 안 났다). `maru_mobile_set_input_sink(1)` 이면 브리지가 그
바이트를 모아 두고 host 가 `maru_mobile_take_input` 으로 가져가 원격에 보낸다.

**셸이 뜨기 전에 친 것도 잃지 않는다.** host 는 세션이 `ready` 일 때만 가져간다 — 가져가면
브리지에서 사라지는데 그때 못 보내면 그 글자가 통째로 없어진다. 그래서 그전에는 브리지에
남아 있다가 함께 나간다(type-ahead — 실제 터미널이 그렇게 군다).

**목적지를 바꾸면 밀린 것은 버린다.** 로컬에서 친 글자가 원격으로 뒤늦게 흘러가면 **사용자가
안 친 명령이 실행된다.**

**오래 산 세션은 반드시 재키잉을 지난다**(OpenSSH 기본 1GB·1시간 — [SSH 계약](ssh-client.md)
§3.0.1). 그 길을 펌프·ABI 로 실제로 지나는지는 `maru_mobile_ssh_rekeys` 로 **센다** — 안 세면
서버가 키를 한 번도 안 갈아도 검증이 초록이 된다(실측: 스모크 열세째 회차에서 16 회).

**세션은 첫 프레임보다 빨리 붙는다.** 코어는 첫 `build` 에서 서는데 접속은 그보다 빠를 수 있어
(실측: iOS 에서 150ms), 그때 온 원격 출력을 버리면 **세션의 첫 출력이 통째로 사라진다** —
배너·프롬프트가 그 자리다. 브리지가 그 바이트를 들고 있다가 코어가 서면 흘려 넣는다.

**받은 바이트는 갈 곳이 있어야 한다.** `screen` 에서 가져온 것을 `maru_mobile_term_write` 로 넣고,
코어가 만든 답은 `maru_mobile_take_response` 로 가져가 `maru_mobile_ssh_write` 로 **돌려보낸다** —
안 돌려보내면 커서 위치를 묻는 프로그램이 답을 기다리며 멈춘다(그전에는 답을 버리고 이름만
남겼는데, 그때는 돌려보낼 상대가 없었다). **터미널 바이트는 어느 세션의 것인지 아직 안 가른다** — 화면이
하나이기 때문이고(U2), 세션이 여럿이 되면 그때 라우팅을 정한다. **컨트롤 채널은 이미 가른다**:
같은 연결의 두 번째 채널이라 다른 버퍼·다른 훅으로 오고(S10b-2), 그래야 ndjson 파서가 사람
화면을 읽지 않는다.

**끝은 반드시 알린다.** 어떻게 끝나든(정상 종료·선 끊김·오류) 펌프가 마지막으로
`MARU_SSH_STATE_CLOSED` 를 한 번 올린다. **코어 상태를 그대로 올리면 안 된다** — 선이 끊겼을 때
코어는 여전히 `ready` 다(끊긴 것은 소켓이지 프로토콜이 아니다). 그러면 host 는 붙어 있다고
믿고, 알림은 "유지 중" 인 채로 남는다(실측: 서버를 죽여도 아무 일도 안 났다). host 는 그 신호로
알림을 내리고 서비스를 접는다.

**"다시 붙어도 되나" 는 상태로 판단하지 않는다.** 끝난 세션도 `CLOSED` 를 들고 있어야 하므로,
그것으로 재시작을 막으면 **한 번 끊긴 뒤 재접속이 영영 막힌다**(프로세스를 죽였다 켜야만 된다).
`maru_ssh_pump_is_running()` 이 그 물음에 답한다.

**컨트롤 채널은 화면과 다른 흐름이다**(계약 [컨트롤 플레인 §4a](control-plane.md)). 같은 연결에
채널을 하나 더 열어 원격 명령을 돌리는 길이고, ABI 도 **다른 이름·다른 버퍼**로 낸다 — 한 흐름에
합치면 ndjson 파서가 사람 화면을 읽게 된다. 규약은 화면·선과 같다: **가져갈 때까지 남아 있고,
안 가져가면 배압으로 멈춘다**(잃지 않는다). 여는 것은 **사용자가 세션 목록을 보려 할 때**이고,
터미널만 쓰는 접속에서는 열지 않는다 — 채널을 여는 것은 그 서버에서 명령을 하나 실행하는 일이라
감사 로그에 남는다. 펌프도 같은 축을 낸다(`maru_ssh_pump_open_control` 과 `control` 훅) —
**훅이 없으면 채널을 아예 안 연다**(`no_control_hook`). 받을 사람이 없으면 컨트롤 버퍼가 차서
코어가 배압으로 멈추고 **터미널까지 함께 멈추기** 때문이다 — 채널 둘을 독립으로 만든 이유를
그 자리에서 잃는다.

**키는 앱이 만든다**([SSH 계약](ssh-client.md) §3.4). `maru_mobile_ssh_generate_key` 가 host 가
준 32바이트 씨앗으로 ed25519 를 만들고, `open` 에 넘길 64바이트와 사용자가 서버
`authorized_keys` 에 붙일 **한 줄**을 함께 준다 — 개인키는 그 함수 밖으로 안 나가고, 나가는
줄에는 공개키만 있다. **씨앗이 곧 개인키다**: 0 은 거절한다(예측 가능한 씨앗이면 그 키로 지킬
수 있는 것이 없는데 화면은 정상으로 보인다). 줄을 담을 자리가 모자라면 **자르지 않고 실패**한다
— 잘린 공개키는 붙여 넣어도 안 먹고, 그때 원인을 짚기가 아주 어렵다.

**Android 는 그 키를 Keystore 로 봉인해 둔다.** Keystore 는 **임의 바이트를 못 담는다**(키만
든다) — 우리 개인키는 ed25519 씨앗이고 서명은 코어가 하므로 Keystore 가 대신 서명해 줄 수도
없다. 그래서 **Keystore 의 AES-GCM 키로 감싸** 앱 저장소에 둔다: 그 AES 키는 기기 밖으로 못
나가므로, 파일을 통째로 꺼내 가도 다른 기기에서는 못 푼다.

**못 풀면 새로 만들지 않는다.** 새로 만들면 서버에 등록해 둔 공개키가 하루아침에 안 맞게 되고
사용자는 이유도 모른 채 못 붙는다 — 그때는 **안 붙고 이유를 남기는 편**이 낫다(실측: 봉인
파일을 망가뜨리자 `AEADBadTagException` → `sealed_key_unreadable` → 접속 안 함).

**잠금 화면을 요구하지 않는다.** 요구하면 배경에서 세션을 되살릴 때 못 풀어 접속이 끊긴다 —
그 정책은 화면(S9b)이 생긴 뒤 사용자가 고를 일이다.

**iOS 는 당분간 파일이다 (사용자 확정 2026-08-19).** Keychain 배선은 코드까지 됐지만 검증할
수단이 없다: 서명에 entitlement 가 없으면 Keychain 이 `errSecMissingEntitlement` 로 전부
거절하고, entitlement 를 실어 서명하면 시뮬레이터가 **실행 자체를 거부**한다(코드사인 인증서가
없어 ad-hoc 서명뿐이다 — 실측).

**검증 못 하는 코드는 머지하지 않는다.** 그래서 iOS 는 **실기기 검증이 가능해질 때까지** 키
파일 경로로 둔다 — 그동안 iOS 만 계약 §3.4 를 절반만 지키는 상태이고, 그것을 아는 채로 둔다
(코드는 `park/ssh-ios-keychain-s9c-2` 에 세워 뒀다). **두 플랫폼이 갈린 것은 실수가 아니라
결정이다** — Android 는 Keystore 로 봉인하고 파일 경로가 없다.

**개인키는 남는 시간이 짧아야 한다.** 파일 바이트는 host 가 **자기 버퍼**로 읽고 곧바로 지운다
(`NSData`·JVM 배열처럼 우리가 못 지우는 자리에 두지 않는다 — iOS 가 그렇게 되어 있었다).
푼 64바이트도 `open` 에 넘긴 **직후** 지운다: 코어가 자기 몫을 챙겼고 그쪽은 `close` 가 지우므로,
사본을 세션 내내 들고 있을 이유가 없다.

**개인키는 프로세스 밖으로 안 나간다.** Android 에서 서비스를 시작하는 `Intent` 의 extra 는
`system_server` 를 지나므로 거기 키를 실으면 안 된다 — **경로만 넘기고 파일은 네이티브가
우리 프로세스 안에서 읽는다.**

**격자가 바뀌면 원격에 알린다.** 키보드가 오르내리면 보이는 행 수가 바뀐다 — 안 알리면 원격은
처음 크기를 믿고 그려서 `less`·`vim` 이 어긋난다(실측: 키보드를 내리자 51×33 으로 바뀌었다).

**iOS 는 그것을 못 한다 — 그래서 정직하게 끊는다.** 포그라운드 서비스에 해당하는 것이 없어
배경에서 소켓을 계속 들 방법이 없다. host 는 배경에 들어갈 때 **유예 시간**만 얻고
(`beginBackgroundTask`), 그 시간이 끝나면 세션을 **직접 끊는다** — 그냥 두면 앱이 정지되며
소켓이 조용히 죽고, 돌아왔을 때 화면은 붙어 있는 것처럼 보인다(그 상태가 가장 헷갈린다).
돌아오면 다시 붙는다(SSH 에는 재개가 없다 — [SSH 계약](ssh-client.md) §4.1).
**실측**: 홈으로 나가 `background_grace` → 26초 뒤 `background_expired` → `state=12`, 복귀 시
재접속(시뮬레이터).

**Android 는 포그라운드 서비스가 그 소켓을 든다.** 앱이 배경으로 가면 OS 가 프로세스를 언제든
거두고, 그러면 "잠깐 다른 앱 봤더니 접속이 끊겼다" 가 매번 난다 — 알림 하나를 대가로 그 회수
대상에서 빠진다(`MaruSshService`, `foregroundServiceType=dataSync`). **실측**: 홈으로 나가
20초 뒤 돌아왔더니 그 사이 도착한 줄들이 그대로 화면에 있었다(에뮬레이터).

**소켓 루프는 `mobile_host/ssh_pump.c` 하나다.** host 가 하는 일은 (1) 키 바이트를 읽어
`maru_mobile_ssh_load_key` 에 넣고, (2) 접속 정보와 훅(자물쇠·화면·답 가져오기)을 주어
`maru_ssh_pump_start` 를 부르고, (3) 화면 훅에서 `maru_mobile_term_write` 를 부르는 것뿐이다.
**호스트키는 핀 고정으로 판정한다** — 자동 승인은 없다는 약속([SSH 계약](ssh-client.md) §4)을
물어볼 화면이 없는 지금도 지키는 방법이고, 목록 화면(S9b)이 생기면 물어보기 + `known_hosts` 로
옮긴다.

**펌프는 두 자물쇠를 동시에 안 쥔다.** 세션 자물쇠(펌프 것)와 브리지 자물쇠(host 것)를 겹쳐
쥐면, 그리는 스레드가 반대 순서로 잡는 순간 교착한다 — 펌프는 세션 쪽을 놓은 뒤에 host 훅을
부른다.

**그 스레드는 스택을 크게 잡아야 한다.** 코어가 패킷 상한(256KiB)짜리 버퍼를 스택에 잡아
한 번의 `feed` 가 500KiB 를 넘는데, 새 스레드의 기본 스택은 그보다 작다(iOS 512KiB ·
Android 1MiB) — 명시하지 않으면 **첫 걸음에서 앱이 죽는다**(실측: `SIGILL`, 스택 가드).

**실패는 두 벌로 답한다.** host 가 분기해야 하는 것(호스트키 승인 · 인증 실패)은 `MARU_SSH_ERR_*`
정수 코드이고, 진단용 이름은 `maru_mobile_ssh_last_error` 다 — 이름만으로는 UI 를 못 고르고,
코드만으로는 무엇이 틀렸는지 로그에 안 남는다.

**브리지는 스레드를 모른다.** 자물쇠는 스레드가 둘인 플랫폼이 갖는다. Android 는 IME 가
Java UI 스레드에서 오고 그리는 쪽은 NativeActivity 스레드라(실측 tid 14832 vs 14850) host 가
`pthread_mutex` 로 브리지 호출을 직렬화한다. iOS 는 UIKit 이 둘 다 main 에서 부르므로 없다 —
대칭이 깨진 게 아니라 사정이 다른 것이고, 그 차이는 각 host 파일 머리에 적는다.

**SSH 가 이 사정을 바꾼다 — 다만 답이 플랫폼마다 다르다.** 소켓을 읽는 곳은 UI 스레드가
아니므로(펌프가 자기 스레드에서 돈다) 두 host 다 **직렬화가 필요해진다**. 답은 이렇게 갈렸다:

- **Android**: 이미 `pthread_mutex` 가 있으므로 그것을 펌프에 훅으로 넘긴다 — 펌프가 화면에
  넣기 직전에 그 자물쇠를 잡는다.
- **iOS**: 자물쇠를 새로 만들지 않고 **main 큐**를 쓴다. 브리지 호출이 전부 main 에서 돈다는
  것이 이 host 의 모델이라, 펌프가 주는 것은 `dispatch_async` 로 main 에 던지고 가져오는 것은
  프레임 tick 이 main 에서 한다. **`dispatch_sync` 는 안 쓴다** — `stop` 이 main 에서 펌프
  스레드를 `join` 하는 순간 교착한다(main 은 join 을, 펌프는 main 을 기다린다).

**대칭이 깨진 게 아니라 사정이 다른 것이다** — 61 곳의 브리지 호출에 자물쇠를 새로 두르는 것보다
이미 성립하는 불변(전부 main)을 지키는 편이 안전하다.

### 3.1 포인터는 누가 해석하는가

**네 단계를 다 받는다**(down·move·up·cancel — `maru_mobile_pointer`). 그래서 탭과 롱프레스가
갈리고(코어가 프레임 시각으로 판정), 끌면 스크롤이 된다.

#### 어디로 갈지는 코어가 정한다 (R)

**`down` 이 목적지를 정하고, 그 제스처는 끝까지 거기로 간다.** 목적지는 셋이고 순서가 있다 —
**밀린 화면(chrome) → 보조 키바 → 본문**. 위가 떠 있으면 아래는 없는 것과 같다.

**그 판정은 코어가 한다.** host 는 좌표와 손가락 id 를 나를 뿐이고, "어느 표면이 이 터치를
먹었나" 를 기억하지 않는다 — 같은 상태를 두 층에 두면 정리도 두 곳에서 해야 하고, 실제로
한쪽을 빠뜨려 **복귀 후 첫 손짓이 통째로 삼켜지는** 결함이 났다(iOS 주석이 "브리지와 뷰
**양쪽**을 푼다" 고 적고 있던 자리다).

**제스처의 목적지는 소유 손가락에 딸린다.** 둘째 손가락이 다른 표면 위에 닿아도 그 제스처의
목적지는 안 바뀐다 — 키바를 밀면서 본문이 같이 스크롤되는 상태를 막는다. **다만 그 "소유
손가락" 을 목적지 옆에 따로 두지는 않는다** — 표면마다 이미 자기 소유자를 들고 있고
(`kb_owner`·`body_owner`·`set_touch.owner`), 목적지가 살아 있는지는 **그것들에게 물어서** 판정한다. 같은
사실을 두 벌 두면 정리도 두 곳이 되고, 그것이 이 계약이 host 에서 없앤 바로 그 병이다.

**끝나는 자리도 하나다**: 마지막 손가락이 떼지거나 `cancel` 이 오면 목적지가 지워진다.

#### 한 제스처의 뜻은 상태 하나가 든다

**"이 손짓이 무슨 뜻인가" 를 조합으로 다시 만들지 않는다.** 표면마다 제스처 상태를 **하나**
들고, 각 자리는 그것을 **물어본다**.

```
        down
 idle ────────> pressed ──┬── 슬롭을 넘었다 ──> scrolling
   ^                      │
   │                      └── 시계가 지났다 ──> long_pressed   (본문만)
   │
   └──────────── up · cancel ────────────────────
```

| 상태 | 뜻 | 떼면 |
|---|---|---|
| `idle` | 닿은 손가락이 없다 | — |
| `pressed` | 짚었고 아직 슬롭 안이다 — **탭이 될 수 있다** | 탭 |
| `scrolling` | 슬롭을 넘었다 — 이 제스처는 끝까지 스크롤이다 | 아무 일 없음 |
| `long_pressed` | 짚은 채 시계가 지났다(본문의 선택) | 아무 일 없음 |

**`stop_tap` 은 상태가 아니라 그 제스처에 붙는 표시다.** 흐르는 면을 세우려고 짚은 것이면
떼도 아무것도 활성화하지 않는다 — 세우려던 손짓이 키를 내보내거나 화면을 넘기면 안 된다.
상태로 두지 않는 이유는 그 뒤에도 **스크롤로 이어질 수 있기** 때문이다(짚어 세우고 그대로 민다).

**왜 조합이 아니라 상태인가.** 전에는 표면마다 `active`·`moved`·`stop_tap`·`pressed` 를 따로
들고 "탭이다" 를 **`up` 인데 `moved < slop` 이고 `stop_tap` 이 아니고 `pressed` 가 있다** 로
자리마다 다시 만들었다. 한 자리에서 한 항을 빠뜨려도 컴파일도 테스트도 통과한다 — 실제로 그
조합 하나가 톱니 판정으로 새어 **설정이 안 열렸고**, 본문에서는 선택으로 들어갈 때 옆 변수
(관성 속도)를 안 지워 **떼는 순간 고른 글자가 흘러갔다**. 전이를 한 곳에 모으면 "선택으로
들어갈 때 속도를 거둔다" 가 **전이의 일부**라 빠뜨릴 자리가 없다.

**표면마다 하나씩 갖는다 — 화면끼리 나눠 쓰지 않는다.** 세션 목록이 설정 화면의 변수를 그대로
쓰고 있었다(`set_active`·`set_moved`). 한 번에 한 화면만 떠서 오늘은 동작하지만, 이름이
거짓말을 하고 둘 중 하나를 고치면 다른 하나가 조용히 바뀐다.

**제스처 조합(arena)은 안 만든다.** RNGH 가 그것을 갖는 이유는 사용자가 임의로 중첩한 뷰들이
경쟁하기 때문이다. 우리 표면은 `chrome → 키바 → 본문` 셋이고 우선순위를 우리가 정한다(§3.1) —
답이 하나로 정해진 협상에 협상 기계를 들이는 꼴이다. 중첩 스크롤이 생기면 재검토한다.

**시계가 필요한 전이는 프레임에서 돈다.** `long_pressed` 는 `move` 에서 판정할 수 없다 —
손가락이 가만히 있으면 `move` 가 아예 안 온다(2초를 눌러도 아무 일도 안 났다, 실측).

#### 손가락 id 와 소유권

**포인터 함수는 `maru_mobile_pointer` 하나이고 그것이 `pointer_id` 를 싣는다.** id 는 **host 가 주는 불투명한 정수**이고 보장은 하나뿐이다 — **`down` 부터
그 손가락의 `up`/`cancel` 까지 같다**. 값의 범위도 재사용 규칙도 코어가 가정하지 않는다
(Android 는 `getPointerId` 가 이미 정수이고, iOS 의 `UITouch` 는 숫자 id 가 없어 host 가 매핑을
든다 — 그 매핑이 host 몫인 이유는 그것이 OS 자료구조를 다루는 일이기 때문이다).

**소유권 규칙은 코어가 소유한다.** 표면(본문·키바·chrome)마다 **한 번에 한 손가락**이 제스처를
소유한다:

| 언제 | 무엇 |
|---|---|
| 첫 `down` | 그 id 가 소유권을 잡는다 |
| 비소유자의 `down`·`move` | **무시하되 개수는 센다**(핀치가 붙을 자리) |
| 비소유자의 `up` | 아무 일도 안 한다 — 제스처는 계속된다 |
| **소유자의 `up`** | 남은 손가락이 있으면 **그중 하나가 이어받고**, 없으면 제스처가 끝난다 |
| `cancel` | id 와 무관하게 전부 끝난다(OS 가 제스처를 통째로 뺏은 것이다) |

**기준 좌표와 속도는 손가락마다 둔다.** 코어는 닿아 있는 손가락 각각의 직전 좌표·속도를 들고,
소유자의 것만 화면에 적용한다. 그래서 **이어받을 때 할 일이 없다** — 새 소유자는 자기 `down`
이후로 이미 자기 기준을 갱신해 왔다. (분수 누적(`residue`)은 손가락이 아니라 **스크롤 면**의
것이므로 면에 둔다.)

**진짜 병은 "절대 기준" 이 아니라 "기준 하나를 손가락들이 공유하는 것" 이다.** 공유하면 남은
손가락의 좌표가 그대로 이어져 **화면이 점프하고**, 그 점프가 속도 계산(px/ms)에 들어가 **상한까지
튄 fling** 이 된다 — 한 번의 손가락 교체가 1600px 를 흘려보낸다. 소스로 읽은 두 길이 있다: Android
AOSP `ScrollView` 는 기준을 **하나**(`mLastMotionY`) 두므로 `onSecondaryPointerUp` 에서 새 기준을
잡고 `VelocityTracker` 를 비운다. Flutter 는 기준과 속도를 **포인터마다** 두므로 소유자를 넘기기만
하고 아무것도 안 한다 — **할 게 없다**. React Native 는 `ReactScrollView : ScrollView` 라 AOSP 것을
그대로 쓴다(셋 다 원문 확인). UIKit 이 어떻게 합성하는지는 문서에도 소스에도 없어 **확인하지
못했다** — 통설(무게중심)을 근거로 적지 않는다.

**우리는 Flutter 쪽을 고른다.** 재기준·속도 버리기는 **빠뜨릴 수 있는 명시적 처리**이고, 이
저장소에서 그 부류가 반복해서 새어 나왔다(감쇠 세 곳·슬롭 네 곳·반쪽 이관). 손가락마다 기준을
두면 그 처리 자체가 없어진다. ABI 는 그대로 절대 좌표를 나른다 — hit-test·선택·롱프레스가 이미
그것을 쓰고, 델타는 코어가 **id 별로** 만든다.

**왜 host 가 아니라 코어가 이 규칙을 갖나.** "어느 손가락이 소유하나" 는 OS 호출이 아니라
**판정**이다(§3). host 에 두면 두 벌이 되고, 두 벌은 갈린다 — 이 저장소에서 관성 감쇠(세 곳)·
터치 슬롭(네 곳)·스크롤 상태(세 곳)가 실제로 갈렸다. host 가 하는 일은 **OS 의 index↔id 를
풀어 id 를 그대로 나르는 것**까지다.

**의미는 코어가, 느낌은 플랫폼이 갖는다.**

| 무엇 | 누가 | 왜 |
|---|---|---|
| hit-test, 탭↔롱프레스 판정, 텍스트 선택 드래그 | **코어** | 데스크톱과 같은 의미여야 한다(롱프레스는 우클릭 자리). 합성 이벤트로 **헤드리스 검증**이 되는데, 모바일은 CI 가 없어 이 값이 특히 크다 |
| 러버밴딩, 핀치 줌, 시스템 제스처 협조 | **플랫폼** | OS 느낌이라 직접 만들면 어색하고, 뒤로가기·엣지 스와이프와 충돌한다. 결과(Δ·scale)만 넘긴다 |
| 스크롤 관성 | **코어** | 처음에는 플랫폼 것으로 뒀다가 **옮겼다**(아래 문단). 관성은 "이 제스처가 누구 것이었나" 를 알아야 흘릴 수 있는데 그 판정은 코어 것이다(§3.1) — host 에 두니 목적지를 몰라 **키바로 간 손짓의 세로 성분까지 본문에 흘렸다**(재현: view_offset 18 → 16). 값도 하나가 된다: 본문·설정·서버 목록이 `scroll_area.Touch` 의 감쇠·상한을 같이 쓴다(**키바는 이제 안 흐른다** — 두 줄 격자라 밀 곳이 없다, [UX §5.4](mobile-ux.md)) |

**관성을 OS 기계에 맡기지 않는 이유.** 이 표가 처음에 관성을 플랫폼에 준 근거는 "OS 느낌이라
직접 만들면 어색하다" 였다. 그런데 **그렇게 구현한 적이 없다** — `UIScrollView` 도
`OverScroller` 도 쓴 적이 없고, 두 host 가 같은 지수 감쇠를 **손수** 돌렸다(상수가 세 곳으로
갈려 사고가 난 자리이기도 하다). 즉 스펙의 이득(OS 곡선·러버밴딩·시스템 제스처 협조)은
받은 적이 없으면서 소유만 플랫폼에 있었고, 그 사이로 **남의 제스처가 본문을 흘리는** 결함이
났다.

그 이득을 실제로 받으려면 **본문을 진짜 네이티브 스크롤 뷰로 떼어내야** 한다. OS 스크롤
기계는 히트테스트를 자기가 갖기 때문이다 — 키바 위 터치가 거기로 안 가게 하려면 표면을
네이티브 뷰로 갈라야 하고, 그러면 §3.1 이 코어에 모아 둔 라우팅이 다시 두 층으로 나뉜다.
[UI 전략](layering-and-portability.md)의 "chrome 은 네이티브 뷰가 아니라 Zig draw-list" 와도
부딪힌다. **하려면 반쪽이 아니라 통째로 해야 하고**(그때는 손맛이 OS 곡선으로 바뀐다),
그것은 별도 결정이다. 지금은 세 면이 같은 값 하나로 흐르는 쪽을 택했다.

**안전 영역은 네 변 다다.** 위·아래(상태바·제스처바·컷아웃)만이 아니라 **좌우**도 온다 —
곡면(waterfall) 화면은 유리가 옆으로 말려 그 띠의 글자가 휘어 읽히고, 가로 모드에서는 노치가
옆으로 간다. iOS 는 처음부터 `safeAreaInsets` 로 넷을 다 썼고 **Android 만 위·아래만 읽고
있었다**.

**가로 모드가 온다** — 안드로이드 액티비티의 세로 잠금은 풀렸고(`screenOrientation="unspecified"`),
돌리면 격자를 다시 잡는다(실측 2026-09-05: 세로 51×31 ↔ 가로 108×9). 그러니 좌우 inset 은 이제
곡면 기기 밖에서도 0 이 아닐 수 있다.

**누를 수 있는 면은 접근성 서술자를 낸다.** 계약은 데스크톱 것을 그대로 쓴다
([CIM §3](chrome-interaction-migration.md) — `chrome/ui/semantics.zig` 의 `Role`·`Semantics`).
**내는 자리는 rect 를 적는 그 줄 옆**이다 — 「그리는 자리와 누르는 자리가 같아야 한다」는 규율에
**읽는 자리**를 묶는다. 다른 곳에서 만들면 세 번째 진실이 생겨, 스크린 리더가 짚은 곳과 손가락이
닿는 곳이 조용히 어긋난다. 프레임마다 다시 만들고(쌓이지 않는다), **없는 index 는 0 으로 답한다**
— 옛 자리를 돌려주면 없는 버튼이 읽힌다. 못 쓰는 컨트롤은 **빼지 않고** `enabled = false` 로 낸다.

**터미널 본문은 «줄마다 하나»다.** 화면 전체를 값 하나로 주면 스크린 리더가 통째로 한 번에 읽고
줄 이동이 안 된다 — macOS 는 텍스트 영역 프로토콜(줄·범위 조회)이 있어 그렇게 해도 되지만
(Ghostty 가 그 길이다) UIKit·Android 의 요소에는 그것이 없다. 웹 터미널이 행마다 요소를 두는 것과
같은 이유다(xterm.js `AccessibilityManager`).

**이름은 줄 번호, 글자는 값이다.** 글자를 이름에 담으면 출력이 흐를 때마다 「생김새가 바뀌었다」가
되어 host 가 요소를 다시 만들고 알림을 보낸다 — 스크린 리더의 커서가 계속 처음으로 튕긴다. 이름을
번호로 두면 **줄의 신원이 고정**되어 값만 갱신된다(실측: 입력이 오가는 동안 레이아웃 알림 0건).
빈 줄은 안 내고 끝의 여백은 턴다 — 그대로 주면 「명령어 뒤에 공백 일흔 개」가 읽힌다.

**보는 글자와 읽는 글자가 같다.** 코어는 base 를 셀에 두고 결합 문자를 따로 보관하므로, base 만
읽으면 `❤` 와 `❤️` 가 같아진다 — 그리는 쪽이 쓰는 그 배관을 읽는 쪽도 쓴다. 담을 수 없는 값이 오면
건너뛰지 않고 **대체 문자로 자리를 지킨다**(건너뛰면 뒤 칸이 앞으로 밀려 줄이 어긋난다).

**줄은 「전체 중 몇째」를 말한다.** 목록은 흐르고 터미널은 스크롤백을 든다 — 화면은 그것을
스크롤바로 말하는데 **색과 길이라 안 읽힌다.** 본문 줄의 번호는 스크롤백을 포함한 절대 줄 번호이고,
집합 크기도 스크롤백을 포함한다(웹 터미널이 행마다 `aria-posinset`/`aria-setsize` 를 다는 그 자리다).

**그 값이 host 로 나가는 길이 있어야 사용자가 듣는다**(`maru_mobile_a11y_set_pos` — 위 16비트가
몇째, 아래 16비트가 전부 몇). Android 는 그 뜻을 담는 자리가 있다(`CollectionItemInfo`).
**iOS 에는 없다** — `UIAccessibilityElement` 에 그 슬롯이 없어서 지금은 안 실린다. 값에 이어
붙이면 줄마다 「412 / 1082」가 함께 읽혀 시끄러워지므로, **실기기에서 들어 보고 정한다**.

**커서가 있는 줄은 그렇다고 말한다.** 화면은 그것을 깜빡이는 사각형으로만 말하는데 색도 모양도 안
읽힌다 — 치는 글자가 어디로 가는지 모르면 터미널을 쓸 수가 없다.

**새 출력을 소리로 알리는 일**(live region)은 아직 없다. 그것이 없으면 흐르는 출력을 스스로 훑기
전에는 모른다 — xterm.js 는 그 자리를 20줄 상한과 에코 중복 방지까지 갖춘 live region 으로 채운다.
이 환경에서는 **낭독을 못 재므로** 실기기 확인과 함께 다룬다.

**목록 줄은 「몇 분의 몇」을 말한다.** 목록이 흐르므로(가상화) 집합 크기는 **있는 줄 전부**로 센다 —
보이는 것만 세면 늘 창 크기가 나온다. 그리고 **값은 이름과 따로** 낸다(`maru_mobile_a11y_value`):
스크린 리더는 둘을 다른 시점에 읽고 값만 바뀌었을 때 이름을 다시 읽지 않으므로, 「서버 3」처럼 이어
붙이면 3 이 바뀔 때마다 이름이 바뀐 것이 된다. iOS 는 값 자리가 따로 있고, Android 는 없어서
(`setStateDescription` 은 API 30) `contentDescription` 에 쉼표로 잇는다 — **이어 붙이는 자리는
host 안 한 곳**이다.

**설정 줄은 이름과 «값» 을 함께 낸다.** 토글의 켜짐/꺼짐은 화면에서 **손잡이 자리와 색으로만**
말해지므로 둘 다 안 읽힌다 — 값(`켜짐`/`꺼짐`)과 `selected` 두 가지로 준다. 갈래 머리글은 누를 수
없는 글자(`text`)로 내고, **붙임 머리글도 낸다** — 그것이 덮은 인라인 머리글은 안 그려지므로,
안 내면 맨 위 갈래의 이름이 어디에서도 안 읽힌다.

**묻는 화면은 «묻는 것» 을 값으로 낸다.** 호스트키 화면은 지문 대조가 존재 이유라, 화면이 눈으로
맞대기 좋게 두 줄로 쪼개 그려도 **통째로** 읽힌다. 비밀번호 화면은 반대다 — **친 글자를 절대 안
읽어 준다**(스크린 리더는 소리로 나가고 곁에 사람이 있을 수 있다. 화면이 점으로만 그리는 그
이유다). 대신 몇 글자인지를 값으로 준다: 아무 표시가 없으면 키보드가 먹고 있는지조차 모른다.

**값은 «줄인 것» 이 아니라 온전한 것을 낸다.** 화면은 자리에 맞춰 앞을 자르지만 스크린 리더에는
잘릴 이유가 없다 — 주소가 반쪽이면 어느 서버인지 모른다.

**편집 중이라는 사실도 싣는다.** 화면은 그것을 캐럿(▏)과 색으로 말하는데 **색은 안 읽히고 캐럿은
글자로 읽힌다** — 사실은 `selected` 로 주고 값에서는 캐럿을 뗀다. 토글의 켜짐/꺼짐과 같은 규율이다.

**팝업이 열리면 그 아래는 안 낸다.** 그때 포인터는 「항목 아니면 닫기」만 하므로 아래 줄도
뒤로가기도 안 눌린다 — **누르는 쪽과 같은 조건**이다.

**누르는 자리가 둘이면 서술자도 둘이다.** 서버 줄은 줄 전체가 접속이고 오른쪽 끝이 편집이다 —
하나만 내면 스크린 리더 사용자는 둘 중 하나를 못 쓴다.

**흐르는 목록의 줄은 그 창으로 잘라서 낸다.** 화면에서는 고정 헤더를 나중에 그려 지나간 줄을
덮지만 **서술자에는 덮개가 없다** — 자리를 그대로 내면 스크린 리더가 헤더 자리에서 그 줄을 짚고
톱니와 겹친다.

**이름·값 글자는 브리지가 복사해 든다.** 부르는 쪽이 주는 슬라이스는 i18n 표일 수도, 목록 줄일
수도, **그리면서 만든 스택 버퍼**일 수도 있다 — host 는 프레임이 끝난 뒤에 읽으므로 복사하지 않으면
남의 메모리를 읽는다. 자리가 모자라면 조용히 자르지 않고 `a11y_text_overflow` 로 알린다.

**덮인 것은 안 낸다.** 빌드는 어느 화면이든 터미널 층을 먼저 세우므로(코어 격자가 살아 있어야
돌아왔을 때 화면이 그대로다) 밀린 화면이 떠 있어도 앱 바·키바의 rect 는 서 있다 — 그런데 그때
포인터는 **모든 터치를 밀린 화면이 먹는다**. 그러니 서술자도 **누르는 쪽과 같은 조건**을 본다.
이것은 위의 `enabled = false` 와 다른 이야기다: 그 말은 지금 보이는 면 안의 꺼진 버튼을 가리키고,
이것은 **이 면에 속하지도 않는** 것을 가리킨다.

**이름은 글자 단위로 끊는다.** `maru_mobile_a11y_label` 은 쓴 바이트 수를 답하고 `cap == 0` 이면
필요한 길이만 답한다(먼저 물어보고 자리를 잡는 법). **UTF-8 한가운데서는 안 끊는다** — 반쪽
글자를 받은 iOS `NSString` 은 nil 이라 짧게 읽히는 대신 **이름이 통째로 사라진다**.

**역할 번호의 단일 출처는 ABI 헤더다**(`MARU_MOBILE_A11Y_ROLE_*`). 브리지는 계약 enum 의 순번을
그대로 내보내지 않는다 — 그 enum 에 줄을 하나 끼워 넣는 순간 host 가 **조용히 다른 역할**을 읽는다.

**읽는 순서는 보는 순서이고, 그것을 정하는 자리는 브리지다.** 서술자가 나오는 순서는 *그리는*
순서라 그대로 두면 훑을 때 오른쪽에 갔다가 왼쪽으로 되돌아온다 — 그래서 프레임 끝에서 위에서
아래로·왼쪽에서 오른쪽으로 세운다(같은 줄인지는 y 값이 같은가로 잰다: 한 줄의 사각형은 레이아웃이
같은 값을 준다). **host 는 다시 세우지 않는다** — 각자 정렬하면 두 host 가 조용히 갈리고 그
갈림은 스크린 리더에게만 보인다. 좌우가 뒤집히는 언어를 알아야 할 자리도 문구가 있는 이 층이다.

**알림은 «생김새»가 바뀔 때만 보낸다.** 서술자 지문을 둘로 가른다: 생김새(개수·자리·이름)와
상태(역할·비트). 상태만 바뀌었는데 알리면 스크린 리더가 읽던 것을 끊고 커서를 되돌린다 — 키바에서
수정자를 켜자마자 커서를 잃으면 다음 키까지 처음부터 다시 훑는다. 그때는 **같은 객체의 trait 만**
갈아 끼운다: 객체를 새로 만들면 알림을 안 보내도 커서가 붙잡고 있던 것이 사라진다.

**iOS 는 이것을 `UIAccessibilityElement` 로 투영한다.** 뷰가 컨테이너가 되고(자기 자신은 요소가
아니다), 요소는 **들고 있는다** — iOS 는 index 별로 따로 묻는데 질의마다 새 배열을 주면 앞서 준
요소가 그 배열과 함께 사라진다(실측: 열다섯 중 마지막 하나만 이름과 자리가 남았다). 그래서
서술자 묶음의 **지문이 바뀔 때만** 다시 만들고, 그때 `UIAccessibilityLayoutChangedNotification`
을 보낸다 — 안 보내면 화면을 옮겨도 스크린 리더 커서가 옛 버튼에 남는다. 좌표는 **누르는 쪽과
같은 식으로** 되돌린다(브리지 좌표 + safe area).

**Android 는 `AccessibilityNodeProvider` 의 가상 뷰 계층으로 낸다.** IME 를 받는 전면 뷰가 그
계층을 들고, 노드는 **질의마다 새로 만든다**(iOS 와 반대다 — 거기서는 들고 있어야 커서를 안 잃는다.
`AccessibilityNodeInfo` 는 프레임워크가 회수하는 값이다).

**두 번 두드리기는 `ACTION_CLICK` 으로 온다** — iOS 처럼 터치를 합성해 주지 않는다. 그래서 그
동작을 받아 **누르는 경로 그대로** 눌러 준다(포인터 down/up 한 쌍). 이 길이 없으면 읽히기만 하고
안 눌린다. 좌표를 뷰 픽셀로 되돌리는 것도 네이티브에서 한다 — 그 식(`* scale + inset`)은 누르는
경로가 이미 아는 것이고, Java 가 따로 알면 두 번째 진실이 된다.

알림은 iOS 와 같은 규율이다: **생김새가 바뀔 때만** `TYPE_WINDOW_CONTENT_CHANGED` 를 보낸다.

**읽어 준 것과 누를 것이 같은지 본다.** 접근성 커서는 index 로 붙잡는데, 그 사이에 화면이 바뀌면
같은 index 가 **다른 버튼**이 된다 — 「esc」라고 듣고 tab 이 눌린다. 커서를 놓을 때 읽어 준 이름을
기억해 두고, 누를 때 그 이름이 아직 그 자리인지 대조해 다르면 **아무것도 안 누른다**(잘못 누르면
무엇이 눌렸는지 볼 수 없다).

**이름은 `NewStringUTF` 로 만들지 않는다.** 그것은 modified UTF-8 을 기대해서 이모지(4바이트 UTF-8)에
정의되지 않은 동작이고, CheckJNI 를 켠 빌드에서는 abort 한다 — 클립보드 경로가 같은 이유로 이미
UTF-16 변환을 쓴다. 서술자 이름도 같은 규율을 따른다(다음 슬라이스가 세션·서버 이름을 낸다).

**노드 하나는 한 번에 받는다.** 자리·역할·상태·이름을 나눠 물으면 그 사이에 프레임이 바뀌어 **서로
다른 프레임의 값이 섞인다** — 이름은 `esc` 인데 자리는 다른 키가 된다. 스크린 리더가 누를 때 쓰는
손가락 id 도 진짜 손가락과 **겹치지 않는 값**(`MARU_MOBILE_POINTER_ID_A11Y`)이어야 한다: 같은
번호를 쓰면 손가락이 내려와 있는 동안 활성화했을 때 그 손가락의 자리를 덮어써 화면이 튄다.

**안 바뀐 프레임은 GPU 를 안 쓴다.** 빌드는 매 tick 그대로 돌고, 낸 quad 가 지난 프레임과 같으면
host 가 획득·제출·프레젠트를 통째로 건너뛴다(`maru_mobile_frame_changed`). **깃발이 아니라 결과를
견주는 이유**는 상태를 바꾸는 진입점이 아흔 개라, 「바꾸는 자리마다 dirty 를 세운다」는 하나만
빠뜨려도 화면이 얼기 때문이다 — 화면에 보이는 변화는 반드시 quad 를 바꾸므로 견주기에는 빠뜨릴
목록이 없다. **빌드를 안 건너뛰는 것이 요점**이다: 관성 감쇠·길게 누름 승격·아틀라스 축출 순번이
멈추면 안 된다. 같은 이유로 host 는 **글자 굽기·config 저장·컨트롤 채널을 다 하고** 나서 쉰다.
**GPU 자원은 빌드 뒤에 잡는다** — 스왑체인 이미지도 Metal 드로어블도 한 번 잡으면 되돌릴 수 없어서,
먼저 잡으면 「안 그리기」를 못 한다.

**색은 시스템 외관을 따라갈 수 있다.** `theme.follow-system` 이 켜지면 host 가 알려 준 다크/라이트에
따라 `theme.preset-dark`·`theme.preset-light` 가 색을 정한다(데스크톱 F2-9 와 **같은 키·같은 뜻**).
꺼져 있으면 파일 색이 그대로이고, host 가 아직 안 알려 줬으면 **따라가지 않는다** — 모르는 값으로
화면을 바꾸지 않는다. **config 는 안 바뀐다**: 색은 그릴 때 골라지므로 시스템이 정한 색이 파일에
실릴 길이 없고, 끄면 다음 프레임에 파일 색으로 돌아온다.

**보조 키바의 줄 수는 폭이 정한다.** 열둘이 한 줄에 들어가면서 키가 손가락 크기(44)를 지키면
한 줄, 아니면 두 줄이다 — 두 줄이 된 이유가 폭이었으니 푸는 기준도 폭이다([UX §5.4](mobile-ux.md)).
**화면 방향은 안 본다**: 방향으로 가르면 「세로인데 넓은」 태블릿을 틀리게 답한다. 폰 가로에서는
이것이 세로 한 줄(53px)을 본문에 돌려주고도 키가 오히려 넓어지는 자리다(실측 2026-09-05:
본문 9줄 → 11줄). **가로 전용 레이아웃은 그 밖에 아직 없다** — 태블릿·분할 화면은
[계획 M5](plans/mobile-platform.md)가 소유한다.

**자리가 없으면 보조 키바를 안 그린다.** 세로 열은 `앱 바 + 본문 + 키바` 인데, 남는 높이가 앱 바와
키바를 빼고 **본문 최소 줄수**(격자가 반드시 그리는 바닥과 같은 수)를 못 남기면 키바를 접는다.
안 그러면 격자가 제 사각형 밖으로 넘쳐 **키바 밑에 깔린다**(가로에서 소프트 키보드를 올리면 그
모양이 됐다 — 실측 2026-09-05). 접히면 `maru_mobile_keybar_rect` 가 0 이라 **없는 키가 눌리지도 않는다**
(그리는 자리와 누르는 자리는 같다 — §3.1). 키바의 존재 이유가 「소프트 키보드에 없는 키」인데,
그것을 남기려다 터미널이 사라지면 앞뒤가 바뀐다.

**홀펀치·평면 기기에서는 그 값이 0 이라 아무 차이가 없다** — 그래서 기기에서 안 드러난 채 오래
잠복하고, 실기가 없으면 화면으로 확인할 수도 없다. 그 자리는 **판정자가 유일한 방벽**이다:
네 변을 다 읽는가 · 좌우를 폭에서 빼는가 · 좌측만큼 그림을 미는가 · **터치 x 도 같이 옮기는가**.
마지막 것이 빠지면 그리는 자리와 누르는 자리가 어긋나 오른쪽 끝이 안 눌린다(이 저장소가 여러
번 겪은 결함이다).

**플랫폼은 스크롤 델타조차 안 넘긴다 — 원시 포인터 이벤트뿐이다.** 델타도 관성도 코어가
만든다. 전에는 `maru_mobile_scroll(float)` 이 ABI 에 있었고 host 의 관성 루프가 그것을 불렀는데,
관성이 코어로 오면서 **부르는 host 가 하나도 안 남아** 선언을 내렸다(있으면 "host 가 이걸
불러야 한다" 는 거짓 약속이 된다).

px 를 줄로 환산하는 것은 코어 쪽이다 — 셀 높이는 플랫폼이 모르는 값이다. 한 줄이 안 되는
나머지는 코어가 누적하므로 **천천히 끌어도 잃지 않는다**(버리면 느린 드래그가 아예 안 움직인다).

마우스 휠·트랙패드(`ACTION_SCROLL`)를 붙이면 델타 진입점이 다시 필요해진다. 그때는 손가락과
입력원이 달라 **서명도 달라진다**(가로 성분·노치 단위) — 그 슬라이스에서 새로 정한다.

코어가 정하는 것은 데스크톱과 같다:

| 언제 | 무엇 |
|---|---|
| alt screen + DECSET 1007 | 뷰포트를 안 움직이고 **화살표 키**를 보낸다. 여러 줄은 **한 버퍼에 묶어** 보낸다 — 줄마다 쓰면 빠른 플릭에서 뒷부분이 드랍된다 |
| 그 변환을 할 때 | **선택을 해제한다** — 프로그램이 화면을 다시 그리므로 남은 선택은 좌표가 어긋난 유령이다 |
| 그 외 | `scrollViewport` — clamp 도 코어가 한다 |
| 입력이 들어오면 | **바닥으로 스냅한다** — 과거를 보는 중에 친 글자가 화면 밖에 찍히면 친 것이 사라진 것처럼 보인다 |

**그리는 근거는 `renderSnapshot` 이지 활성 화면이 아니다.** 스크롤백을 보는 동안 코어는 보이는
윈도를 따로 합성하는데(`viewport_cells`), `screen.cells` 를 직접 읽으면 그 합성을 지나쳐
**스크롤해도 화면이 안 바뀐다** — `view_offset` 은 올라가는데 픽셀이 그대로였다(실측). 커서
가시성도 같은 자리에 있다: snapshot 이 DECTCEM **그리고** 스크롤 여부를 이미 합성해 준다.

**개행은 문자가 아니라 Enter 키다.** IME 는 소프트 Return 을 `"\n"` 으로 커밋하는데 그대로
쓰면 LF 가 나가고, 하드웨어 Return 은 키 경로로 CR 이 나간다 — 안 가르면 **같은 Enter 가 입력
수단에 따라 다른 바이트**가 된다. `maru_mobile_input` 이 개행을 잘라 Enter 키로 보낸다(CRLF 는
Enter 한 번이다).

**그래서 지금은 개행으로 줄이 안 넘어간다.** Enter 는 CR 이고, 그것을 CRLF 로 되돌려 주는
**셸 에코가 아직 없다** — 입력 바이트가 그대로 파서로 들어가는 구조라 열만 0 으로 가고 행은
그대로다. 원격 세션(M3)이 붙어 반대편 프로그램이 응답하면 자연히 풀린다. 그 전까지 화면에
여러 줄을 만들려면 **출력 쪽 경로**(대본·`\r\n` 을 포함한 출력)를 써야 한다 — 계약 테스트가
그렇게 하고 있고, 그 사실을 모르면 "왜 한 줄만 나오지" 로 시간을 쓴다(실제로 그랬다).

**손가락 하나의 뜻은 코어가 정한다.** 플랫폼은 원시 이벤트(down·move·up·cancel)와 **시각**만
넘긴다(`maru_mobile_pointer`) — 코어에 시계가 없어 길게 누름을 판정할 수 없다. **관성도 코어
것이다**: 시각이 이미 넘어오고(`maru_mobile_build` 의 프레임 간격), 흘릴지 말지는 목적지를
아는 쪽만 정할 수 있다.

| 무엇 | 언제 |
|---|---|
| 스크롤 | 그냥 끈다 |
| 선택 | **길게 누른다**(OS 가 정한 지연, 10 논리 px 안에서). 그 자리의 단어를 잡는다 |
| 선택 확장 | 잡은 뒤 **누른 칸을 벗어나** 끈다 |

- **길게 누름은 프레임마다 본다 — move 에서 보면 안 된다.** 손가락이 가만히 있으면 move 가
  아예 안 와서 **2초를 눌러도 아무 일도 안 난다**(실측). 코어에 시계가 없으므로 `maru_mobile_build`
  가 프레임 시각을 받아 그 자리에서 판정한다.
- **길게 누름 지연은 OS 것이다.** 코어에 박으면 두 가지가 깨진다 — 플랫폼 차이(실측: iOS
  500ms · Android 400ms)와 **사용자 접근성 설정**(Android "길게 누르기 지연", iOS "터치 조절 →
  유지 시간"). 플랫폼이 `maru_mobile_set_long_press_ms` 로 넘기고, Android 는 **재개할 때마다**
  다시 읽는다(설정을 바꾸고 돌아오면 그때부터 새 값이어야 한다 — 실측으로 확인했다).
  iOS 의 접근성 값은 공개 API 로 못 읽는다(§한계).
- **누른 칸을 벗어나기 전에는 안 늘린다.** 길게 눌러 단어를 잡은 직후에도 move 는 계속 오는데,
  그때마다 늘리면 head 가 누른 칸으로 당겨져 **단어 끝이 잘린다**(3칸이 2칸이 됐다).
- **끝 열은 포함이다** — 데스크톱 렌더가 `col <= end.col` 로 쓴다. 배타로 그리면 한 칸 모자란다.
- **선택은 손을 떼도 남는다** — 떼자마자 사라지면 복사할 수가 없다. 다시 누르면 사라진다.
- **취소(phase 3)도 선택을 안 지운다.** 두 host 가 이 phase 를 제스처 취소가 아니라 **수명
  정리**로도 쓰고(배경 전환·포커스 상실), ABI 가 두 뜻에 같은 번호를 줘서 브리지는 구분할 수
  없다. 지우면 Android 에서 **알림 셰이드 한 번 내렸다 온 사이에 선택이 사라진다**. 이미 만들어진
  선택은 진행 중인 제스처가 아니라 **결과**이므로, 치우는 자리는 언제나 **다음 누름**이다.
- **"누른 칸을 벗어났다" 는 px 임계로 판정하지 않는다.** 셀 폭(8)이 이동 임계(10)보다 좁아
  **가로에서만 거짓**이 된다 — 9px 끌면 다른 칸으로 넘어가 선택이 늘어나는데 "안 움직였다" 로
  남아, 다음 프레임의 길게-누름 판정이 그것을 **되돌린다**(한 칸 넓히기가 아예 불가능했다).
  칸이 바뀌었는지는 이미 계산하므로, 그 자리에서 "움직였다" 를 세운다.
- 표시는 **배경 위·글자 아래**에 깐다. 위에 얹으면 글자를 가린다.

**복사는 꺼내는 쪽과 쓰는 쪽이 갈린다.** 추출은 **코어**가 한다 — soft-wrap 잇기·줄끝 개행·
2셀 뒷칸 제외가 전부 거기 있고, 플랫폼마다 다시 짜면 갈린다. 플랫폼은 **클립보드에 쓰기만**
한다(브리지엔 OS 호출이 없다, §3). 브리지는 `maru_mobile_take_copy` 로 바이트만 건넨다.

- `copy` 는 **선택이 있을 때만** 키바에 나타나고 자리도 안 차지한다 — 누를 수 없는 버튼이
  계속 보이면 안 되고, 한 줄에 자리도 모자란다.
- **한 번 가져가면 요청이 사라진다** — 매 프레임 같은 것을 다시 쓰지 않게.
- 버퍼가 모자라면 자르고 `copy_truncated` 를 남긴다 — 조용히 자르지 않는다.
- 복사해도 **선택은 남는다**(데스크톱과 같다).
- Android 는 클립보드가 Java 쪽이라 shim 이 맡는다. **네이티브 스레드에서 `FindClass` 로 앱
  클래스를 찾으면 시스템 클래스로더를 보게 돼 조용히 못 찾는다** — Java 에서 들어온 호출 때
  전역 참조로 붙들어 둔다(그 자리에서 복사가 말없이 죽었다).

**글자 경계는 host 와 코어 사이에서 지킨다.** 코어는 UTF-8 만 안다. 그 경계를 건너는 두
방향(입력·복사) 다 **잘못된 바이트를 만들 수 있는 자리**를 아예 없애는 쪽으로 짠다 — 만들어
놓고 검사하면 그 검사가 실패했을 때 조용히 아무 일도 안 일어난다.

| 어디 | 규칙 |
|---|---|
| Android JNI | `GetStringUTFChars`·`NewStringUTF` 를 **안 쓴다**. 그것이 주고받는 것은 UTF-8 이 아니라 **modified UTF-8(CESU-8)** 이라 BMP 밖 글자가 서러게이트 쌍 6바이트로 온다. `GetStringChars`/`NewString` 으로 UTF-16 을 주고받고 변환은 우리가 한다(양방향 대칭) |
| iOS 클립보드 | 바이트로 `NSString` 을 만들지 않는다. `setData:forPasteboardType:` 로 UTF-8 바이트를 그대로 넣는다 — 변환이 없으니 실패할 자리도 없다 |
| 자를 때 | 항상 **글자 경계**에서 자른다(`width.truncateToBoundary` 가 그 규칙의 단일 출처). 바이트 수로 자르면 조각난 글자가 나가고, 받는 쪽이 그 조각 때문에 통째로 버린다 |
| 수정자 실린 첫 글자 | 자르기 **전에** lead 바이트가 요구하는 길이를 본다. 길이 없는 포인터(`[*]const u8`)는 Zig 도 경계를 못 잡아 **버퍼 밖을 읽는다** |
| 짝 없는 서러게이트 | 버리되 **로그로 남긴다**. 버퍼가 모자라 자른 것도 남긴다(복사의 `copy_truncated` 와 같은 규율) |

**클립보드에 레거시 인코딩 플레이버는 없다.** 두 OS 다 클립보드의 단위가 **유니코드 문자열**이라
(iOS `public.utf8-plain-text`, Android `text/plain` = Java `String`) EUC-KR·CP949 같은 바이트
인코딩은 그 계층에 나타나지 않는다 — 넣을 자리가 없다. 레거시 인코딩이 실제로 닿는 곳은 **PTY
입력**(원격 로케일)이고 그것은 코어 파서 계약이라 여기 밖이다.

**보조 키바가 소프트 키보드에 없는 키를 만든다.** Ctrl·Esc·Tab·화살표는 소프트 키보드에
**아예 없다** — 그것 없이는 프로세스를 못 멈추고(Ctrl+C) vim 에서 못 빠져나온다. 문장부호는
`123` 레이어로 칠 수 있지만 이 키들은 칠 방법이 없다.

- **정의를 한곳에 둔다.** 라벨·레이아웃·탭 판정이 같은 표를 본다. 갈리면 **엉뚱한 키가
  나가면서 화면에는 맞게 보인다**.
- **좌표 해석은 코어 쪽이 한다**(§3 — 플랫폼은 점만 넘긴다). 그리는 자리와 판정하는 자리가
  갈리면 눌러도 다른 키가 나간다.
- **Ctrl 은 sticky 다** — 다음 **한 키**에만 실리고, **소프트 키보드로 친 글자에도** 실린다
  (그게 실제 쓰임이다). 계속 걸려 있으면 그 뒤 타이핑이 전부 제어문자가 된다.
- **수정자가 붙은 문자는 IME 가 안 준다.** Ctrl+C 는 글자가 아니라서 `commitText` 로 오지 않는다 —
  이름 붙인 키 표에도 없으니, 그 자리를 따로 안 채우면 **조용히 사라진다**(블루투스 키보드를 붙인
  태블릿·크롬북에서 Ctrl+C 로 프로세스를 못 멈췄다). 두 플랫폼 다 **수정자를 뺀 글자**를 실어
  코어의 인코더에 태운다(iOS `charactersIgnoringModifiers`, Android `getUnicodeChar(0)`).
- **이스케이프 시퀀스는 타이핑이 아니다** — 눌러 둔 수정자를 안 먹는다. 먹게 두면 `\x1b[2J`
  같은 것이 Ctrl 을 가져가고, ESC 는 문자 키 표에 없어 **그 바이트가 조용히 사라진다**.
- 눌러 둔 상태는 **화면에 보인다** — 안 보이면 왜 제어문자가 나가는지 알 수 없다.

**숫자 패드는 `sendKeyEvent` 필터를 안 건다.** 위의 중복 방지("소프트 키보드의 글자는
`commitText` 가 이미 보냈다")는 **조합하는 키보드의 이야기**다. `TYPE_CLASS_NUMBER` 는 숫자를
`commitText` 로 보내지 않고 키 이벤트로만 보내므로(§3.1 이 이미 적어 둔 사실), 막으면 **대신
보내 줄 사람이 없어 통째로 사라진다** — 설정의 숫자 줄에 아무것도 못 쳤다(기기 실측). 엔터가
사라졌던 것과 같은 모양이고, 그때 좁힌 기준("인쇄 가능한가")은 제어문자만 갈랐지 이 자리까지는
못 갈랐다. 판별은 `maru_mobile_input_kind()` 로 한다 — 그 값이 이미 키보드 종류를 고르고 있다.

**완성된 글자는 조합이 끝나기를 기다리지 않는다.** 한글은 한 음절씩 조합되므로, 조합 문자열이
두 글자가 됐다는 것은 **앞 글자가 더는 안 바뀐다**는 뜻이다(`가나` 의 `가` 에는 받침이 붙을 수
없다). 마지막 한 글자만 preedit 으로 남기고 나머지는 그 자리에서 원격으로 보낸다.

**터미널에서 이 기다림은 그냥 늦는 것이 아니다.** 원격의 TUI(claude·codex)는 자기가 받은 글자로
자동완성과 선입력을 계산하는데, preedit 은 우리 화면에만 있어 그쪽은 아무것도 못 본다 — 다 치고
확정한 뒤에야 한꺼번에 도착하면 그 계산이 통째로 죽는다(사용자 보고). macOS 터미널도 같은 규칙이다.

**조합은 자라기만 하지 않는다 — 줄고 갈아치워진다.** 백스페이스와 후보 선택이 그렇다. 늘어난 것만
보내고 줄어든 것을 안 지우면 **지울수록 늘어난다**(기기 실측: `가나다` 를 지웠더니 화면이
`가나다아 가나다 가나당`). 그래서 접두사를 비교하는 대신 **원격이 든 상태를 목표와 맞춘다**:

- 공통 접두사까지는 그대로 두고, **넘치는 만큼 지우고 모자라는 만큼 보낸다.**
- 지우는 수단은 **백스페이스 키**다 — 터미널에는 "앞의 n글자를 지워라" 가 없고 그 자리를 셸·TUI 가
  해석한다.
- 공통 접두사는 **코드포인트 경계**로 되돌린다. 서로게이트 쌍 가운데서 끊으면 반쪽 글자가 남는다.
- 확정(`commitText`)은 조합 **전체**를 주므로, 이미 내보낸 앞부분을 빼고 넘긴다 — 안 빼면 두 번 나간다.

**조합할지 말지는 문자 종류로 가른다 — 수정자 유무가 아니다.** 삼성 키보드는 영문도 조합으로
넘긴다(`setComposingText`). 그러면 글자가 preedit 으로 화면에만 떠 있고 `commitText` 는 확정될
때까지 안 온다. 터미널에서 그 기다림은 곧 **안 나간 키**다.

한때 기준이 "**수정자가 걸려 있으면** 조합하지 않는다" 였는데, 그것으로는 `Ctrl+B` 는 나가고
**그 다음 키가 안 나갔다** — tmux prefix 다음 키에는 수정자가 없다(기기 실측: 나가는 바이트 로그가
`02` 를 찍고 이어질 `6d` 를 안 찍었다 — 그 태그(`MARU_OUT`)는 지금 없다. tmux 는 오지 않는 키를 기다렸다).

- **ASCII 는 즉시 확정한다.** 터미널에서 영문 예측 입력은 방해다 — 누른 글자는 그 자리에서
  나가야 하고 확정을 기다릴 이유가 없다.
- **조합이 필요한 것은 한글뿐이고 그것은 항상 ASCII 밖이다.** 자모가 모여 글자가 되는 과정을
  화면에 보여야 하므로 그대로 조합한다.
- 즉시 확정할 때는 **프레임워크의 조합도 끊는다**(`restartInput`). 우리가 가로채 커밋해도
  Editable 은 조합 중이라 다음 글자가 **이어붙는다** — `Ctrl+B` 뒤 `m` 이 `bm` 한 덩어리로 왔다.

**글리프는 자기 칸 안만 샘플링한다.** 아틀라스는 칸 사이에 여백이 없고 블록 글자(`█`)는 칸을
가득 채운다 — 그래서 바로 아래 칸을 그릴 때 **위 칸의 아래 모서리가 딸려 온다**(화살표 라벨
위에 없는 가로 획으로 나타났다. 아틀라스를 덤프해 위 슬롯이 블록인 것을 확인했다). 두 셰이더
다 샘플 좌표를 자기 칸 안으로 **반 텍셀** 물려 자른다. 여백을 두는 쪽은 못 쓴다 — 블록 글자는
칸을 가득 채워야 본문에서 이음매가 안 보인다.

**Android 는 키가 두 길로 온다.** 소프트 키보드의 글자는 `MaruActivity` 의 InputConnection 이
주지만, **숫자 키보드**(`TYPE_CLASS_NUMBER`)는 숫자를 `commitText` 가 아니라 **키 이벤트**로
보내고 그것은 NativeActivity 의 입력 큐로 들어온다(하드웨어 키보드도 같은 길이다). 그 큐에서
키를 버리면 **숫자 칸에 아무것도 못 친다** — 칸은 편집 중인데 화면이 안 바뀐다(기기에서 그
상태로 막혔다). 두 길은 **같은 함수**(`dispatchKey`)로 모은다: 각자 표를 들면 어느 한쪽에서만
되는 키가 생긴다.

**IME 가 입력을 고쳐 쓰지 못하게 한다.** 두 OS 다 텍스트 입력의 기본값이 **글 쓰기용**이라
자동 대문자·자동 수정·스마트 문장부호가 켜져 있다. 터미널에서는 그것이 곧 손상이다 — iOS 는
아무것도 선언하지 않아 `"` 가 `“ ”` 로, `--` 가 `- –` 로 바뀌어 들어갔다(실측). **셸 따옴표도
`--` 플래그도 못 치는 상태였다.** 두 플랫폼이 같은 것을 끈다:

| | 무엇으로 |
|---|---|
| iOS | `UITextInputTraits` — autocapitalization·autocorrection·spellChecking·smartQuotes·smartDashes·smartInsertDelete 를 전부 끈다 |
| Android | `EditorInfo.TYPE_TEXT_FLAG_NO_SUGGESTIONS` + `IME_FLAG_NO_EXTRACT_UI`·`NO_FULLSCREEN`·`ACTION_NONE` |

**키보드 종류(`keyboardType`)는 터미널에서 안 건드린다** — ASCII 배열을 요구하면 한글 입력이
불편해진다. 설정 칸은 다르다(아래).

### 설정 칸 입력 (S9b-1)

설정 화면의 줄은 셋이다: 켜고 끄는 것(toggle)·고르는 것(choice)·**치는 것**(숫자·글자).
치는 줄을 누르면 그 줄이 입력 대상이 되고, 그때부터 들어오는 글자는 터미널이 아니라 그 칸으로
간다. 무엇을 편집 중인지는 브리지만 알므로 **키보드 종류도 브리지가 정한다**:

| `maru_mobile_input_kind()` | 뜻 | host 가 하는 일 |
|---|---|---|
| 0 | 터미널 | 기본 키보드. 친 글자는 코어로 |
| 1 | 숫자 칸 | 숫자 패드(iOS `UIKeyboardTypeNumberPad`). 친 글자는 편집 칸으로 |
| 2 | 글자 칸 | 기본 키보드. 친 글자는 편집 칸으로 |

**1 과 2 를 가르는 것은 배열이고, 0 과 2 를 가르는 것은 목적지다.** 색(`#RRGGBB`) 같은 글자
칸에 숫자 패드를 띄우면 `#` 도 `a~f` 도 못 쳐 **아무것도 못 넣는다**(기기에서 그 상태로 막혔다).
반대로 글자 칸을 터미널과 같은 0 으로 말하면, host 는 하드웨어 키보드로 온 글자를 어디로 보낼지
못 고른다 — 그 글자가 **조용히 사라진다**(블루투스 키보드로 색을 못 쳤다).

편집 중의 키는 **줄 종류에 맞는 자리로 간다**: 백스페이스는 한 바이트가 아니라 **한 글자**를
지우고(한글이 반쪽으로 남으면 화면과 파일이 같이 깨진다), 엔터는 숫자 칸이면 숫자 확정,
글자 칸이면 글자 확정이다. 확정된 값만 `maru_mobile_take_config_write` 로 나가 파일이 된다 —
치는 도중에는 안 쓴다.

색 칸은 **팔레트(`theme.palette*`)를 안 낸다** — 16색을 한 줄씩 늘어놓으면 화면이 그것뿐이고,
고르는 UI 없이 hex 를 손으로 치게 하는 것도 맞지 않다. 그 줄은 화면이 생길 때 따로 정한다.

**버튼은 좌표로 실행하지 않는다.** chrome 이 이미 `UiActionId` + `snapshot_generation` 계약을
갖고 있고([chrome 상호작용 이관](chrome-interaction-migration.md)의 intent table), 모바일도
그 경로를 쓴다. 좌표나 인덱스를 들고 down→up 을 건너면 **그 사이에 화면이 바뀌었을 때 엉뚱한
명령이 실행된다** — 원격 세션 목록은 수시로 바뀌므로 실제로 일어나는 일이다. generation 이
다르면 `resolve` 가 null 을 내 그 누름은 무시된다(잘못 실행하느니 아무 일도 안 한다).

**`maru_mobile_hit_cell` 은 본문 전용으로 남는다.** "어느 셀을 만졌나" 는 터미널 의미(텍스트
선택)라 그 자리가 맞다. 탭·사이드바·아이콘까지 이 함수로 넓히면 위 계약을 우회하게 된다.

**BMP 밖 글자(이모지)는 컬러 아틀라스로 간다.** 글자 아틀라스는 커버리지(R8)라 컬러 비트맵을
넣으면 실루엣이 되므로, **컬러 전용 RGBA 아틀라스**를 따로 세운다(아이콘 아틀라스와 같은 모양).
어디에 구울지는 브리지가 알리고(`maru_mobile_missing_is_color`), 판정의 단일 출처는 코어의
`width.isEmojiPresentation` 이다 — 데스크톱 렌더러도 같은 함수를 본다. 등록은 별도 등록부
(`maru_mobile_color_atlas_add`·`next_color_slot`)라 두 아틀라스가 슬롯을 각자 센다.

quad `kind` **4·5** 가 컬러 텍스처를 가리킨다(전체 / 왼쪽 절반). 커버리지는 전경색을 곱하지만
**컬러는 아틀라스 색이 곧 결과**다 — 곱하면 이모지가 글자색으로 물든다.

host 는 셋을 함께 해야 한다: ① BMP 밖 글자를 **UTF-16 서러게이트 쌍**으로 조립(16비트 한
단위로 자르면 엉뚱한 글자가 된다) ② 이모지 폰트 폴백 ③ RGBA 로 굽기.

**컬러 아틀라스가 없는 host 도 굶기지 않는다.** 컬러 등록부에서만 찾으면 이모지를 커버리지에
굽는 host 는 영영 못 찾아 **매 프레임 다시 굽는다**(실측). 컬러 등록부에 없으면 커버리지에 구운
것이라도 쓴다 — 색은 없지만 글자는 보이고 굽기는 멈춘다.

**창이 부서져도 아틀라스 성장분이 남아야 한다.** Android 는 홈으로 나가면 창이 죽어 텍스처가
사라지는데(iOS 는 UIKit 이 레이어를 살린다) **브리지의 등록부는 살아남는다** — 코어는 "있다" 고
믿어 미스를 안 내고, host 는 미스가 없으니 다시 굽지 않는다. 그래서 host 는 **두 아틀라스 다
CPU 원본을 들고** 재개할 때 그것으로 텍스처를 세운다. 컬러 쪽만 원본이 없던 동안 홈에 다녀오면
**이모지가 영영 빈칸**이었다(한글·ASCII 는 멀쩡해서 더 헷갈렸다 — 그쪽만 원본이 있었다).

- 굽는 자리에서 **GPU 와 원본에 함께** 쓴다. GPU 에만 쓰면 그 프레임만 맞고 재개 때 사라진다.
- 원본은 **슬롯 전체**를 덮는다 — 축출로 자리를 재사용해도 옛 글리프가 안 남는다.
- 등록부를 비우는 쪽으로 풀지 않는다. 그러면 재개 직후 프레임에 **화면 글자 전부가 미스**로
  몰려 한 프레임에 다 못 굽고, 그 사이 빈칸이 보인다.

**폰트에 없는 글자는 시스템에서 찾는다.** Android 는 `Canvas.drawText` 라 폴백 체인이 그냥
붙지만, iOS 는 특정 `CTFont` 에 조회해 없으면 예전에는 **안 그린 채 등록**했다 — 등록부에
"있음" 으로 박혀 다시 굽지도 않아 **영구 공백**이었다(`❤`·`✔` 처럼 번들 폰트에 없는 기호가
통째로 빈칸이었다, 화면으로 확인). 이제 두 경로(컬러·커버리지) 다 `CTFontCreateForString` 으로
폴백한다.

**클러스터는 열째로 host 에 간다.** 코어는 base 코드포인트를 셀에 두고 나머지를 `grapheme_id` 로
따로 보관한다. 브리지가 base 만 넘기던 동안 host 에게는 `❤`(U+2764)와 `❤️`(U+2764 U+FE0F)가
**같아 보였다** — VS16 결합이 커버리지 아틀라스로 가 단색으로 그려졌다.

| 무엇 | 규칙 |
|---|---|
| 미스 목록 | 글자당 **코드포인트 열**(`missing_len`·`missing_cp_at`). 상한 `MARU_MAX_CLUSTER`=12 |
| 두 등록부 | 열까지 비교한다 — base+style 로 1차, 열로 2차(대부분 1차에서 갈린다) |
| `atlas_add`·`color_atlas_add` | 열을 받는다(`cps, n`). 단일 코드포인트는 `n=1` — **경로를 둘로 안 나눈다** |
| 컬러 판정 | **열을 본다.** base 는 코어(`width.isEmojiPresentation`)가 정하고, 그 위에 VS16(U+FE0F)이 이모지 표현으로, VS15(U+FE0E)가 텍스트 표현으로 뒤집는다 |
| host 굽기 | 열을 **문자열 하나로 이어** 그린다(iOS `CTLine`·Android `Canvas.drawText`). 코드포인트를 따로 그리면 결합이 안 일어난다 |

iOS 커버리지 경로가 `CTFontGetGlyphsForCharacters` + `CTFontDrawGlyphs`(코드포인트당 글리프
하나)라 클러스터를 못 그렸다. `CTLine` 으로 바꾸면 결합·리거처·**폰트 폴백**이 한 자리에서
처리된다 — 번들 폰트에 없는 기호를 시스템 폰트로 잇던 수동 폴백도 여기에 흡수된다.

**코어가 안 묶어 준 것은 여전히 안 묶인다.** 이 규칙은 `grapheme_id` 에 담긴 것만 나른다.
grapheme cluster mode(DECSET 2027) 합의가 없으면 코어는 ZWJ 시퀀스와 지역 표시자 쌍을 각각의
셀에 두므로, 국기(`🇰🇷`)는 여전히 글리프 두 개고 가족 이모지도 갈린다. 그건 2027 계약 축이다.

**보이지 않는 글자는 굽지 않는다.** 코어는 grapheme cluster mode(DECSET 2027) 합의가 없으면
ZWJ(U+200D) 같은 0폭 format 문자를 **제 셀에 담는다** — 코어의 계약이고 브리지가 바꾸지 않는다.
다만 그 셀을 미스로 올리면 host 가 **빈 글리프**를 구워 아틀라스 512칸 중 하나를 영구히 먹는다
(실측: `👨‍👩‍👧` 한 줄이 U+200D 를 두 번 올렸다). 브리지가 걸러 **안 올리고 안 그린다** —
올린 채 안 구우면 매 프레임 다시 올라와 목록이 찬다. 위 클러스터 구멍이 풀리기 전까지는 ZWJ 가
셀을 차지하는 것 자체는 남는다.

**Vulkan 은 디스크립터를 세 곳에서 늘려야 한다** — 레이아웃·풀·**쓰기**. 하나만 빠뜨리면
셰이더가 안 쓴 디스크립터를 읽어 UB 가 되고, 릴리즈 빌드에는 validation layer 가 없어 **경고
없이 화면만 안 나온다**(컬러 아틀라스를 넣다 실제로 그랬다). Metal 은 `setFragmentTexture:`
한 줄이라 이 상태가 안 생긴다.

**폴백 아틀라스는 없다.** 기기 래스터가 실패하면 글리프 없이 뜬다 — 예전에 두던 "호스트가
만든 아틀라스를 읽는" 경로는 개발 스크립트가 넣어 준 파일에 기대는 것이라 **실제 앱에는 그
파일이 없었다**. 제품 폴백이 아니라 PoC 잔재였다.

**크기가 바뀌면 코어를 `resize` 한다 — 다시 만들지 않는다.** 새로 만들면 스크롤백과 화면
상태가 통째로 날아간다. 모바일에서는 **키보드를 올렸다 내리기만 해도** 창이 리사이즈되므로
그 차이가 크다.

**논리 좌표계로 되돌리는 자리는 플랫폼이 갖는다.** iOS 는 `UIScreen.scale` + `safeAreaInsets`,
Android 는 `AConfiguration_getDensity` + `getRootWindowInsets` 다. 실측으로 확인했다 — 같은
논리 좌표를 주면 두 플랫폼이 같은 셀을 답한다(물리 좌표는 200,300 과 525,753 으로 다르다).

### 하단 inset — 0 은 값이 아니라 가림의 표시다

소프트 키보드가 떠 있는 프레임에서 Android 는 `systemBars().bottom` 을 **0 으로 보고한다** —
키보드가 navigation bar 를 덮고 있어 바가 화면을 차지하지 않는다고 보기 때문이다. 하필 그때
inset 재조회가 걸리면 그 0 이 저장되고, **키보드를 내려도 남아** 보조 키바가 3버튼 위에
겹친다(기기 실측: `bottom=135` 가 키보드가 뜬 프레임의 재조회 뒤 `bottom=0` 이 됐다).

- **0 은 저장하지 않는다.** 조회하는 쪽(`queryInsets`)과 리스너 양쪽 다 같은 규칙을 쓴다.
- 키보드가 덮는 높이는 `keyboard_px` 가 따로 든다 — 겹쳐 뺄 일이 없다.
- **`WindowInsets` 리스너에서도 갱신한다.** `queryInsets` 는 창이 생기거나 크기가 바뀔 때만
  도는데, 3버튼↔제스처 전환처럼 **창 크기는 그대로고 바 높이만 바뀌는** 경우를 놓친다.

## 3.2 프레임 주기

**30Hz(comfort)로 그린다 — 처음부터.** 터미널은 매 vsync 마다 새로 그릴 것이 없고, 모바일은
배터리·발열이 **사용자에게 보인다**. **데스크톱과는 다른 값이다** — 데스크톱은
`render.frame-rate` 기본이 60 이고([io-render-present](io-render-present.md)), hover/scroll
지연을 우선하며 전력 여유가 있다. 모바일은 그 둘이 뒤집힌다.

| | 어떻게 |
|---|---|
| iOS | `CADisplayLink.preferredFrameRateRange = 30` — **OS 에 선언한다** |
| Android | `AChoreographer` vsync 를 받아 **경과 시간으로** present(Vulkan 에는 하위 주기 모드가 없어 앱이 잰다) |

**주기는 기기 주사율과 무관해야 한다.** Android 를 "vsync 한 번 걸러" 로 두면 그건 30Hz 가
아니라 **패널의 절반**이다 — 90Hz 폰에서 45, 120Hz 에서 60 이 나온다. 배터리·발열 때문에 고른
값이 정작 고주사율 기기에서 두 배가 되므로, 경과 시간으로 재고 문턱은 **패널 반 주기만큼**
당긴다(정확히 목표를 요구하면 vsync 지터로 한 주기를 통째로 놓쳐 실효 주기가 널뛴다).

**타이핑 지연은 이 축이 아니다.** 30Hz 는 한 프레임 33ms 이고 원격 왕복은 그보다 크지만, 둘 다 합쳐도 "친 글자가 한참 뒤에 뜬다" 는 안 나온다 — 그것이 났을 때 범인은 **펌프가 깨어나는 방식** 이었다(`ssh_pump.c` 의 깨우기 관). 프레임 주기를 의심하기 전에 그쪽을 먼저 본다: 여기를 올리면 배터리만 쓰고 지연은 그대로다.

**목표는 패널 주기의 배수로만 맞는다.** present 는 vsync 에만 나가므로 30Hz 가 정수배로
떨어지는 패널(60·90·120·240)에서는 정확히 30 이고, 아닌 패널에서는 가장 가까운 배수로 간다
(144Hz→28.8, 72Hz→36, 48Hz→24). 이보다 좁히려면 프레임을 vsync 사이에 내보내야 하는데
그건 티어링이라 안 한다.

**동률이면 적게 그리는 쪽으로 간다.** 목표가 패널 주기의 딱 1.5배인 45Hz 에서 문턱을
"이상"으로 두면 매 vsync 를 그려 **45Hz 가 된다** — 페이싱이 통째로 사라진다. "초과"로 두면
22.5Hz 다. 45Hz 패널에는 45 나 22.5 뿐이라 **30 이 애초에 없고**, 그런 기기에서 `MARU_PACE`
가 FAIL 을 내는 것은 회귀가 아니라 사실이다.

**iOS 는 `Info.plist` 에 `CADisableMinimumFrameDuration` 을 켜 둔다.** 없으면 ProMotion
기기에서도 60 에서 잘리고 `preferredFrameRateRange` 로 그 위를 요청해도 무시된다. **지금
요청값이 30 이라 켜도 동작은 안 바뀐다** — 그런데도 미리 켜는 이유는 이것이 설정이 아니라
**번들에 박히는 능력 선언**이기 때문이다. config 로는 못 켠다. 주기를 config 로 여는 것
자체는 이 계약 밖이지만([M10](plans/mobile-platform.md)), **그때 런타임에 추가할 수 없는
것은 지금 넣어 둔다.**

**두 플랫폼 다 자기 주기를 확인한다.** iOS 의 `preferredFrameRateRange` 는 **힌트라 무시될 수
있고**, Android 는 우리가 직접 세는 것이라 어긋날 수 있다. 그래서 둘 다 표시 클럭 간격의
중앙값을 재서 `MARU_PACE median_ms` 로 한 번 남긴다 — 30Hz 가 조용히 깨지면 그 줄로 드러난다.

**표본을 고르는 방식도 같아야 한다.** 판정 기준만 같고 표본을 다르게 모으면 두 수를 나란히
놓는 것 자체가 무의미하다 — 실제로 Android 만 첫 프레임들을 버리고 iOS 는 안 버려, **같은
이름의 로그가 다른 것을 재고 있었다**. 목표·PASS 창·표본 수·워밍업은 전부 ABI 헤더가
소유한다(`MARU_FRAME_*`). 워밍업이 필요한 이유는 아틀라스를 굽고 스왑체인이 서는 동안의
간격이 정상 주기가 아니기 때문이다.

**시계는 다르고, 그건 맞다.** iOS 는 `CADisplayLink.timestamp`(직전 vsync), Android 는
`CLOCK_MONOTONIC` present 간격을 쓴다 — 각 플랫폼이 내주는 가장 정확한 값이 다르기 때문이고
둘 다 표시 간격을 잰다. **같아야 하는 것은 "무엇을 표본에 넣는가" 지 "어느 시계로 읽는가"가
아니다.**

**계측은 동작을 바꾸지 않는다.** 예전에는 60Hz 로 시작해 80프레임쯤 뒤 계측이 끝나면 30Hz 로
넘어갔다 — 측정의 부산물이 제품 동작이었고, iOS 엔 그 전환이 없어 두 플랫폼이 달랐다. 지금은
둘 다 처음부터 30Hz 이고 `MARU_PACE` 는 도는 주기를 재서 한 번 기록만 한다.

## 3.3 배경으로 나갈 때

**두 플랫폼이 하는 일이 다르다 — OS 가 요구하는 것이 다르기 때문이다.**

| | 나갈 때 | 돌아올 때 |
|---|---|---|
| iOS | `CADisplayLink` 를 **멈춘다**(`paused`). 배경에서 GPU 작업을 계속하면 앱이 종료될 수 있다 | 다시 돌린다. 레이어·텍스처는 UIKit 이 살려 둔다 |
| Android | 창 자체가 사라진다(`APP_CMD_TERM_WINDOW`) → **Vulkan 을 통째로 부순다** | `APP_CMD_INIT_WINDOW` 에서 다시 세운다 |

Android 가 더 무거운 이유는 창이 진짜로 없어지기 때문이다 — 스왑체인을 들고 있으면 죽은
surface 로 present 하게 된다. iOS 는 그 파괴가 필요 없고, **대신 그리기를 멈추지 않으면
안 된다**(한동안 iOS 만 아무것도 안 하고 있었다).

**재개해도 살아야 하는 것은 `g` 밖에 둔다**(Android). teardown 이 상태를 memset 하므로 안에
두면 재개할 때마다 초기화된다 — vsync 체인 소유 플래그가 그래서 왕복마다 체인을 쌓았다
(실측: 3회 왕복에 33.4ms → 16.7ms). 반대로 **새 네이티브 스레드는 체인이 없으므로**
`android_main` 시작 때 그 플래그를 0 으로 되돌린다.

## 4. 폰트

**동봉 폰트를 쓴다.** `assets/fonts/Jetendard`(OFL)는 영문과 한글을 한 파일에 담아 폴백이
필요 없다. 시스템 폰트는 플랫폼마다 글자가 갈리는 데다 라이선스상 옮길 수도 없다.

**래스터는 각 플랫폼 것을 쓴다**(iOS CoreText, Android `android.graphics.Paint` — NDK 에는
폰트 래스터가 없다). 같은 폰트를 쓰면 남는 차이는 안티에일리어싱뿐이고, 실측으로 **글자
위치·크기는 완전히 같다**(무게중심 밀림 0/64 셀, 평균 |Δ| 17.5/255).

**아틀라스는 자란다.** 고정 집합으로 두면 처음 보는 글자가 **조용히** 안 그려진다. 코어가
못 찾은 코드포인트를 모으고 플랫폼이 그 슬롯만 구워 올린다(부분 업데이트).

**용량은 코어가 소유한다**(`maru_mobile_atlas_rows/cols` — 32행 × 16열 = 512슬롯).
헤더 매크로로 두면 등록부보다 큰 슬롯을 약속하게 되고, 남는 슬롯은 등록이 안 된 채 매
프레임 다시 구워진다(실제로 등록부 256 vs 슬롯 512 로 어긋나 있었다). 미리 굽는 글자 수로 정하면
안 된다 — 남는 슬롯이 곧 성장의 상한이 되고, 한글은 수천 자라 금세 막힌다(실측: 여유가
15칸이라 15자에서 멈췄다).

**꽉 차면 가장 안 쓰인 자리를 내준다**(축출). 예전에는 `next_slot` 이 거기서 sentinel 을 냈고,
그 뒤 나온 글자는 미스로 올라오는데 구울 자리가 없어 **영영 안 그려졌다** — 오류도 로그도 없이.
512칸은 데모 피드로는 안 차지만 **실제 셸은 금방 채운다**(ASCII + 한글 음절 + CJK + 박스 문자에,
굵게/기울임이 각각 별도 슬롯이다).

기준은 **마지막으로 그려진 프레임 순번**이다. 벽시계가 아니라 순번인 이유는, 판정해야 하는 것이
"몇 초 전"이 아니라 **"이번 프레임에 쓰였나"** 이기 때문이다. 이번 프레임에 그려진 글자는 후보에서
뺀다 — 안 그러면 한 화면이 512종을 넘겼을 때 글자들이 서로를 밀어내며 매 프레임 다시 구워진다.
전부 이번 프레임 것이면 그때만 sentinel 을 내고, host 는 그 글자를 이번 프레임에 못 그린다.

**자리는 인덱스로 오간다.** `next_slot` 이 고른 항목을 브리지가 기억하고 `atlas_add` 가 그것을
쓴다 — 좌표로 되찾으면 같은 (열,행)을 가진 항목이 둘일 때 엉뚱한 것을 덮어쓰고, 고른 자리는
옛 상태로 남아 다음 호출이 또 같은 자리를 고른다(실측: 다섯 글자를 구웠는데 하나만 등록됐다).
좌표는 "host 가 시킨 자리에 구웠나" 를 확인하는 **검증용**이다.

host 는 빈 자리와 재사용 자리를 가릴 필요가 없다 — 두 플랫폼 다 슬롯을 0 으로 지운 뒤 슬롯
**전체**를 올리므로 옛 글리프 잔상이 안 남는다. 컬러 아틀라스도 같은 규칙이다.

## 5. 조용히 실패하지 않는다

모바일 host 는 화면 하나가 전부라, 무엇이 안 그려져도 **사용자에게는 그냥 이상한 화면**이다.
그래서 실패를 삼키지 않는다 — 코어 write, quad 버퍼 넘침, 코어 init, 아틀라스 만원은 전부
`maru_mobile_last_error` 에 남는다(`mobile_bridge.zig` 에 `catch {}` 가 0개다).

이 원칙이 없을 때 실제로 생긴 일: 입력이 512바이트에서 죽었는데 **로그가 같은 수를 계속
찍어** 죽은 줄 몰랐다. 그래서 `maru_mobile_input` 의 반환값도 내부 기록 길이가 아니라
**코어에 전달한 누적 바이트**다 — 안 늘면 안 닿은 것이다.

**키는 코어의 인코더를 탄다.** 플랫폼은 **인코딩 전** 상태(키 id·코드포인트·수정자)를
`maru_mobile_key` 로 넘기고, 바이트는 `core.encodeKey` 가 만든다 — DECCKM(커서키 모드)·
수정자(Ctrl·Alt)·kitty 프로토콜·application keypad 가 전부 거기 있다. 손으로 `\r`·`0x7F` 를
적어 넣으면 그 전부가 빠지고, 표에 없는 키(화살표 등)는 **아예 사라진다**.

키 id 숫자의 단일 출처는 `mobile_host_abi.h` 다. **계약 테스트가 헤더를 그대로 읽어** 브리지
매핑이 그 전부를 아는지 검사한다 — 한쪽만 고치면 host 가 모르는 id 를 보내고 키가 조용히
사라지기 때문이다.

**포커스 변화도 알린다**(DEC 1004 — `maru_mobile_report_focus`). 모바일은 배경↔복귀가
데스크톱보다 훨씬 잦고, vim 의 FocusGained/Lost 가 그 신호를 본다.

**오류는 읽은 쪽이 비운다.** build 가 프레임 시작마다 비우면 프레임 *사이*에 난 실패
(입력의 core write)가 아무도 읽기 전에 지워진다 — 이 원칙을 만든 바로 그 경로에서만 신호가
안 남는 셈이었다. host 는 매 프레임 읽고, 값이 있으면 로그하고 `maru_mobile_clear_error` 한다.

**고정 버퍼 위에 코어를 세우지 않는다.** `FixedBufferAllocator` 는 마지막 할당 말고는 free 가
no-op 이라 격자가 바뀔 때마다 옛 격자를 못 돌려받는다 — 512KB 로 **resize 7번**이면
OutOfMemory 였다(헤드리스 실측). 모바일은 **키보드를 올렸다 내리기만 해도** 리사이즈다.

**resize 가 실패하면 기록도 안 바꾼다.** 실패한 채 크기 기록만 새 값으로 덮으면 코어는 옛
크기인데 순회는 새 크기로 돌아 없는 셀을 읽는다. 순회 기준을 **코어가 들고 있는 크기**로
두어 갈릴 자리 자체를 없앤다.

**코어가 만드는 것은 쓰는 자리에서 함께 치운다.** 데스크톱은 매 프레임 답을 PTY 로 흘리고
셸 이벤트를 소비 후 비운다. 모바일은 코어에 쓰는 자리가 둘뿐이라(입력·최초 대본) 거기서
같이 치운다 — 안 치우면 셸 이벤트가 상한 4096 에 닿고 그 뒤로 **전부 드롭되며 overflow 가
영원히 선다**(프롬프트 사이클 2000회면 닿는다. 코어 주석이 "프레임마다 drain 되면 닿을 일이
없다" 고 전제하는 자리다).

**답은 아직 흘려보낼 곳이 없다.** 코어는 질의(DA·DSR·커서 위치)에 답을 만들고 데스크톱은
그것을 PTY 로 흘린다. 모바일에는 그 자리가 없어 안 치우면 쌓이기만 한다 — 질의 3000번에
15005바이트(실측). 지금은 **버리되 조용히 버리지 않는다**(`response_dropped`). 원격
세션(M3)이 붙으면 그쪽으로 흘려보낸다.

**셀 속성은 코어가 담은 것을 그대로 푼다.** 배경·reverse(7)·dim(2)·conceal(8)·밑줄(4)·
이중밑줄(21)·취소선(9)·윗줄(53)·밑줄색(58)·굵게(1)·기울임(3). 규칙은 데스크톱과 같은 것을
쓴다 — reverse 는 **default 를 테마 값으로 푼 뒤** 맞바꾸고(안 그러면 기본색끼리 바꿔 아무
일도 안 난다), dim 은 전경을 배경 쪽으로 절반 보간하고, conceal 은 전경을 배경색으로 만든다.

**굵게·기울임은 아틀라스 슬롯이 따로다.** 같은 글자라도 다른 글리프라, 등록부 키가
코드포인트+스타일이다(키가 코드포인트뿐이면 굵은 판이 보통 판을 덮어써서 한 줄이 굵어지는
순간 그 글자가 화면 전체에서 굵어진다). 가짜 굵게(획 덧그리기) 대신 **번들 폰트 네 판**을
쓴다 — 가짜는 advance 가 달라져 자간이 어긋난다.

**커서는 코어가 정한 대로 그린다.** 모양(DECSCUSR — 블록·밑줄·막대)도 표시 여부(DECTCEM
`CSI ?25 l` — TUI 가 화면을 그리는 동안 숨긴다)도 코어에 있다. 플랫폼이 다시 판단하면 어긋난다.

**커서 가시성은 코어의 합성과 같은 규칙이다** — DECTCEM(`CSI ?25 l`) **그리고** 스크롤백을
보고 있지 않을 것. `screen.cursor.visible` 은 코어가 "내부 불변" 이라고 적어 둔 값이라 늘
참이므로 그것만 보면 **스크롤백을 볼 때도 커서를 그린다**.

**2셀 글자 위에서는 두 칸을 덮는다.** 폭은 코어가 정한 `cell.width` 를 쓴다 — 한 칸만 덮으면
한글 절반에만 걸린다. 마지막 칸에서 넘칠 일은 없다(코어가 wide-push 로 막는다).

**커서 확인은 하네스가 소유한다**(`run.sh cursor-android`). 모양·자리는 이스케이프라 입력으로
못 치므로 대본을 잠시 고쳐 빌드했다 원복한다.

**블록 커서는 반투명으로 얹는다** — 불투명하게 칠하면 그 칸 글자가 사라진다. 전경/배경을
맞바꾸는 것은 셀 속성(reverse)이 하는 일이지 커서가 하는 일이 아니다.

커서가 없으면 **화살표·선택이 눈으로 검증되지 않는다**(로그가 유일한 판정자가 된다). 그래서
이 자리가 포인터·스크롤·선택 슬라이스 전부의 선행 조건이다.

**장식선은 칸이 아니라 글자 띠에 붙인다.** 밑줄은 **베이스라인 아래 1.5 논리 px**, 윗줄은
**어센더 위 1.3 px** 다(픽셀 실측). 칸 위/아래에 두는 것이 터미널 관례지만, 우리 셀은 굽는
baseline 이 칸의 3/4 지점이라 위쪽에 5 px 여백이 남는다 — 그 여백은 폰트 메트릭이 아니라
**굽는 방식의 부산물**이라 그대로 두면 윗줄만 글자에서 멀어 보인다(그래서 앞 줄 글자에
붙은 것처럼 읽힌다).

**배경·장식선은 칸 단위로 묶어 그린다.** 칸마다 quad 를 내면 80x24 만 해도 배경에서만 1920
개다. 같은 색이 이어지는 구간을 하나로 합친다.

**blink(5)는 아직 정적이다** — 코어도 "렌더는 정적" 이라고 적어 둔 자리다(프레임 루프 연동
후속).

**quad 용량은 격자를 따라 자란다.** 셀 속성이 붙으면서 한 칸이 낼 수 있는 quad 가 6개가
됐다(배경·밑줄·이중밑줄·취소선·윗줄·글자). 최대 격자에 그대로 곱해 정적으로 잡으면 3.5MB 를
**쓰지도 않을 최악을 위해 늘 이고 가게** 된다 — 폰의 실제 최악은 3577 개였다(실측). 그래서
필요할 때 배로 늘리고, 늘어나는 시점은 격자가 커질 때뿐이다(=리사이즈, 어차피 플랫폼이 GPU
자원을 다시 세우는 순간).

**용량 상한은 코어가 답한다.** quad 버퍼 크기를 host 마다 손으로 적어 두면 어긋난다 —
실제로 iOS 는 필요할 때 늘리고 Android 는 4096 에서 **조용히 자르고** 있었다. 지금은 코어가
격자 상한(`max_cols`×`max_rows`)에서 계산해 `maru_mobile_max_quads()` 로 답하고, 두 host 가
그만큼 잡는다. 늘어난 상주 메모리는 약 1.4MB 로, 앱 PSS(약 57MB) 안에서 구분되지 않는다.

**GPU 자원은 device 보다 오래 살면 안 된다.** 업로드용 staging 버퍼를 안 지운 채
`vkDestroyDevice` 를 불렀더니 창 크기를 아홉 번 바꾸는 것만으로 드라이버 안에서 SIGSEGV 가
났다(툼스톤 `on_vkDestroyDevice_pre`). 실패 경로에서도 자식을 남기지 않는다.

**문자열은 UTF-8 경계에서 자른다.** 조합 중 문자열을 바이트 수로만 자르면 한글이 반토막
나고, 그리는 쪽이 그 문자열을 통째로 버려 **조합이 화면에서 사라진다**(멈춘 것처럼 보인다).

이 계약들은 `tests/mobile_bridge_contract.zig` 가 지킨다 — 브리지가 OS 를 안 부르므로
시뮬레이터 없이 `zig build test` 에서 돈다.

### 글리프 기하 (M4a3)

**아틀라스 슬롯 하나는 양폭(한글) 상자다.** 24x32 는 텍스트 크기 22 의 2셀 글자가 들어갈
크기이고, 단폭 글자는 그 **왼쪽 절반**만 쓴다. 이 사실이 기하의 출발점이다.

그래서 칸과 상자를 이렇게 맞춘다:

| | 규칙 |
|---|---|
| 줄 높이 | `line_h` (칸 높이) |
| 배율 | `s = line_h / MARU_ATLAS_CELL_H` |
| 칸 너비 | `cell_w = (MARU_ATLAS_CELL_W / 2) * s` |
| 단폭 글자 | quad = `cell_w x line_h`, 슬롯의 **왼쪽 절반**을 샘플링 |
| 양폭 글자 | quad = `2*cell_w x line_h`, 슬롯 **전체**를 샘플링 |

**왼쪽 절반에는 셰이더를 안 고친다.** 두 셰이더 다 `uv = (cell.xy + t) / cell.zw` 라, 왼쪽
절반은 열과 나누는 수를 **함께 2배** 하면 그대로 나온다(`2*col / 2*cols`). 그 신호는 `kind` 로
준다 — quad 구조체를 넓히면 `float4` 배수가 깨진다(그 정렬을 어겼다가 NDC 가 깨진 적이 있다).

(**텍스처가 늘 때는 셰이더를 고친다.** 이모지 컬러 아틀라스는 샘플링할 텍스처 자체가 달라
분기가 필요했다 — 위 요령은 "같은 텍스처 안에서 좌표만 바꾸는" 경우에만 통한다.)

이렇게 하면 **글자 상자가 곧 칸**이라, 셀을 가장자리까지 채우는 합성 글리프가 이음매 없이
붙는다. 그 전에는 상자(11x15)와 칸(5x22)이 달라 원리상 불가능했다.

**`line_h` 를 무엇으로 정하는지는 이 표 밖의 일이다.** 표는 `line_h` 를 받아 쓸 뿐이고, 그것을
어떻게 정하든 슬롯↔칸 매핑은 그대로다. 지금은 이렇게 정한다:

| | |
|---|---|
| `line_h` | `font.size × font.line-height / 100` (100 이면 `font.size` 그대로) |
| 굽는 크기 | `MARU_ATLAS_CELL_H × 7/10` — **설정과 무관한 고정값** |

**굽는 크기를 설정에서 뗀 이유.** 예전에는 `min(font.size, cell_h*0.7)` 이라 **설정값이 굽는
크기이자 축소 계수**였다. 화면 글자는 `굽는 크기 × (line_h / cell_h)` 이므로 둘이 곱해져,
`font.size = 19` 가 화면에서 `19 × 19/32 = 11.3px` 로 나왔다 — 설정값의 60% 다. 곱이라 크기를
올리면 글자가 제곱에 가깝게 커졌다(16→19 는 19% 인데 글자는 41%). 고정하면 화면 글자가
`line_h` 에 **정비례**한다.

**7/10 은 baseline 이 정한 한계다.** host 는 글자를 셀 하단에서 8px 위(`CH - 8`)에 앉힌다.
한글은 ascent 가 em 에 가까워 그보다 크게 구우면 **위가 깎인다** — 26(13/16)으로 올렸다가
기기에서 잘리는 것을 봤다. 굽는 쪽과 이 값이 갈리면 글자가 상자를 넘으므로 **두 자리를 같이
본다**(브리지의 `maru_mobile_atlas_text_px`, host 의 `drawText` baseline).

**줄 높이를 뗀 이유.** 하나로 두면 글자 크기와 화면 밀도가 한 몸이라, 글자를 키우면 보이는 줄이
반드시 준다 — 폰에서는 그 한 줄이 비싸다(사용자 요청). 낮추면 글자는 그대로 두고 줄만 늘릴 수
있고, `폰트 크기 24 + 줄 높이 70` 처럼 **더 크고 더 많은** 조합도 가능해진다. 데스크톱의
`font.line-height` 와 뜻이 같다 — 이 config 는 값이 전부 정수라 배수 대신 백분율을 쓴다.

**합성 글리프는 폰트보다 먼저 본다.** 박스 드로잉·블록·브라유·파워라인·legacy mosaic 은
`renderer.synthesizeGlyph` 가 절차 합성해 셀을 가장자리까지 채운다 — 플랫폼은 폰트 경로
**앞에서** `maru_mobile_synthesize` 를 한 번 부르고, 0 이면 그때 폰트로 굽는다(그게 renderer
계약이다). 폰트 글리프로 그리면 셀에 안 맞아 끊기고 이음매가 보인다.

**커버리지는 RGBA 로 받는다.** `glyph_pixels.slotFits` 가 `bytes_per_row >= w*4` 를 요구하고
커버리지는 **alpha 채널**로 온다 — 단일 채널 버퍼를 그대로 주면 **조용히 null** 이다(아이콘에서
한 번, 합성에서 또 한 번 걸린 함정). 브리지가 RGBA 스크래치에 받아 alpha 만 아틀라스로 옮긴다.

**합성은 슬롯의 왼쪽 절반에 채운다** — 대상이 전부 단폭이고, 그리는 쪽도 단폭 글자는 슬롯
절반만 샘플링한다(위 글리프 기하).

## 6. 베이스

**같은 구조의 제품이 이미 출시돼 있다.** libghostty(Zig 터미널 코어) + 네이티브 GPU 로
만든 iOS 터미널이 여럿이다(Metal 렌더링). 우리 구조가 외톨이가 아니라는 뜻이고, 자체
성능 측정 전까지는 이것이 가장 강한 근거다.

**그리고 그것들이 전부 SSH/Mosh 클라이언트다** — §1 의 "iOS 는 원격 전용" 이 우리만의
제약이 아니라 플랫폼이 강제하는 결론이라는 독립 증거다.

`GameActivity` 권장과 `NativeActivity` 의 텍스트 입력 한계는 Android 공식 문서가 소유한다.
모바일 GPU 가 draw call 오버헤드에 민감하다는 것은 Vulkan 공식 모바일 가이드가 소유한다.

## 7. 아직 안 따르고 있는 기존 계약

**새로 정할 것이 아니라 이행이 빠진 것들**이다. 데스크톱이 이미 계약으로 정해 뒀다.

| 계약 | 모바일 상태 |
|---|---|
| [chrome 상호작용 이관](chrome-interaction-migration.md) — interactive node 가 semantic descriptor 를 내고 플랫폼이 네이티브 접근성 요소로 투영한다 | **따른다**(2026-09-06). 브리지가 서술자를 내고 두 host 가 투영한다(iOS `UIAccessibilityElement`·Android `AccessibilityNodeProvider`) — 앱 바·키바·본문 줄·목록·설정·묻는 화면들. 남은 것은 새 출력 알림·스크롤백 훑기·선택 영역이고 [계획 M9](plans/mobile-platform.md)가 소유한다 |
| [설정](configuration.md) — config 스키마·resolve 계약 | **따른다**(M10). 모바일 스키마로 파일을 읽고 쓴다 — 화면이 스키마에서 줄을 만들고 값은 config 가 든다. 파일도 스키마도 데스크톱과 **따로**다(§1) |
| [배포](distribution.md) — 채널·서명·업데이트 | **모바일 스토어를 안 다룬다.** `AndroidManifest.xml` 의 `android:debuggable="true"` 는 개발용이라 배포 전에 반드시 뺀다 |

계획은 [M9~M11](plans/mobile-platform.md)이 소유한다.

## 8. 아직 정하지 않은 것

**여기 있는 것은 "무엇을 할지 정하는 것" 이 남은 자리다.** 무엇을 할지는 정했는데 아직 안
한 것(스크롤·선택·보조 키바·회전·iOS preedit…)은 여기가 아니라
[계획](plans/mobile-platform.md)이 소유한다 — 이 문서는 현재형 계약만 담는다.

- **원격 전송·인증**(§1 의 충돌). **사용자 결정이 먼저다** — SSH 터널·mesh VPN·자체 릴레이·
  Cloudflare Tunnel 이 비용·계정·인바운드 포트 요구가 갈린다. 정해지기 전에는 모바일이
  세션에 붙지 못한다.
  - **방향(2026-09-02 사용자 논의)**: mesh VPN(Tailscale) 쪽이되 **첫 소비자는 모바일**이다.
    막고 있는 것은 두 축에서 **같다**(기계 경계를 넘으면 peer-cred 가 없다) — 그래서 이 결정은
    한 번이고, 모바일 전용으로 **좁혀 설계하지 않는다**. 인증을 「이 사용자의 기계들」 수준으로
    잡아 두면 뒤에 원격 축이 붙을 때 전송을 다시 짜지 않는다.
    ⚠️ 아직 **확정이 아니다** — 비용·계정 요구를 재고 정한다. 이 줄은 방향만 적는다.
- **아틀라스 용량 자체.** 축출은 정해졌지만(§4 — 프레임 순번 LRU) 512칸이 맞는 수인지는 안 쟀다.
  한 화면이 512종을 넘기면 축출로도 못 메운다. 늘릴지(텍스처 메모리 ↔ 축출 빈도)는 실기기에서
  재고 정할 일이다.
- **성능 예산.** 정하려면 재야 하는데 실기기가 없다. 에뮬레이터 GPU 는 `llvmpipe`
  소프트웨어 래스터라 숫자가 의미 없다.
