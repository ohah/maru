# 모바일 UX — 화면과 전환

이 문서는 모바일 앱의 **화면 목록과 화면 사이 전환 규칙**을 정한다. 무엇을 그리는가(렌더·입력·
아틀라스·ABI)는 [모바일 플랫폼](mobile-platform.md)이 소유하고, 여기는 **사용자가 이 앱을 어떻게
쓰는가**만 담는다. 진행은 [계획](plans/mobile-platform.md)이 소유한다.

**이 문서가 생긴 이유**: 엔진 계약은 촘촘한데 앱 설계가 없어서, 데스크톱 chrome(사이드바 + 상단
탭)을 폰에 그대로 축소해 그리고 있었다. 폰 세로에서 사이드바가 **화면 폭의 3분의 1**을 상시
점유한다 — 읽는 것이 1순위인 앱에서 UI 가 읽을 면적을 먹는다.

## 1. 무엇을 만드는가 — 이미 정해진 것

[계약 §1](mobile-platform.md)이 못박았다:

> **모바일 앱은 PC 세션의 원격 뷰어다.**

터미널 앱이 아니라 **컴패니언**이다. 판단 기준이 "터미널을 얼마나 잘 쓰나" 가 아니라 **"자리를
비운 사이 무슨 일이 있었는지 얼마나 빨리 아나"** 다. 여기서 화면 우선순위가 나온다:

**출력 읽기 > 세션 전환 > 짧은 개입(`y`/`n`·Ctrl-C·재시작) > 긴 입력**

긴 편집은 목표가 아니다. 폰에서 vim 을 쓰게 만드는 것이 이 앱의 일이 아니다 — 그 자리는 PC 가
갖고, 폰은 **보고 짧게 찌르는** 자리다.

## 2. 화면 목록

세 계층이다. 위에서 아래로 내려가며, 아래로 갈수록 오래 머문다.

### 2.1 연결 계층

| 화면 | 무엇 | 언제 |
|---|---|---|
| **서버 목록** | 등록한 PC 들. 각 줄에 이름·연결 상태 | 앱을 켜면 여기(등록된 것이 없으면 서버 추가로) |
| **서버 추가** | 페어링. 방식은 [M3a](plans/mobile-platform.md) 의 인증 결정에 달렸다 | 목록에서 `+` |
| **연결 진단** | 왜 못 붙었나 — 네트워크·인증·버전이 각각 다른 안내 | 연결 실패 시 |

**연결 실패는 화면이다.** 지금은 로그 한 줄이라 사용자가 무엇이 잘못됐는지 알 방법이 없다.

### 2.2 본체 계층

| 화면 | 무엇 | 언제 |
|---|---|---|
| **세션 목록** | 그 서버의 Term 들. 이름·`cwd`·`git_branch`·상태(`agent`·`at_prompt`) | 서버를 고르면 |
| **터미널** | 본체. 화면 대부분이 출력 | 세션을 고르면 |

**세션 목록이 "무슨 일이 있었나" 를 터미널에 들어가기 전에 답한다** — 그게 이 앱의 값이다.

**그런데 무엇을 보여줄 수 있는지가 아직 안 정해졌다.** 컨트롤 플레인
[`sessions.list`](control-plane.md)가 주는 것은 `cwd`·`git_branch`·`agent`·`at_prompt` 까지다.
**마지막 출력 미리보기는 그 안에 없다** — `session.capture` 는 별도 메서드이고
`read-output` [capability](control-plane-security.md)가 따로 필요하다(A2b 라이브 서버는 그것을
애초에 안 연다). 즉 미리보기는 UX 결정이 아니라 **권한 결정**에 달렸다([M3a](plans/mobile-platform.md)).

**그리고 이 화면은 두 면을 다 쓴다** — 목록·메타는 컨트롤 플레인, 화면 픽셀은 MRSH(session
host)다. 모바일이 어느 면에 붙을지가 M3 에서 보류 중이라, **세션 목록은 M3 결정 없이 완성되지
않는다.** 화면 구조는 지금 정할 수 있지만 무엇이 채워지는지는 그때 정해진다.

### 2.3 부가 계층

| 화면 | 무엇 |
|---|---|
| **설정** | 폰트 크기·테마·키바 구성·전원 정책([M10](plans/mobile-platform.md) 스키마) |
| **알림** | 무엇을 알릴지와 지난 알림 |

## 2.4 하지 않는 것

**원격 뷰어라는 전제만으로는 부족하다.** 화면이 좁고 손가락이 부정확하고 키보드가 화면 절반을
먹는다는 사실이 데스크톱 기능 상당수를 **못 쓰게** 만든다. 무엇을 버리는지 적어 두지 않으면
데스크톱 chrome 을 그대로 옮기다 **아무 반응 없는 UI** 가 된다.

| 왜 | 무엇을 안 하나 |
|---|---|
| **화면이 좁다** | 분할(split)·여러 pane 동시 표시 · 데스크톱 도크(파일 탐색기·소스 컨트롤·에디터)의 전면 이식 |
| **손가락이 부정확하다** | 정밀 caret 배치 · **hover 기반 전부**(툴팁·hover 하이라이트·Cmd+hover 링크) · 드래그&드롭 재정렬 · 우클릭(**롱프레스로 대체**) |
| **키보드가 화면 절반** | 수정자 조합 단축키 대부분(**보조 키바로 추린 것만**) · 긴 편집(vim 등) |
| **원격이라서**([§1](mobile-platform.md)) | 로컬 PTY·로컬 셸·로컬 파일 |
| **자원이 사용자에게 보인다** | 긴 스크롤백(메모리) · 고주사율(30Hz 기본, [§3.2](mobile-platform.md)) |

**hover 가 통째로 사라지는 것이 가장 크다.** 데스크톱 chrome 의 상호작용 상당수가 hover 에
기대고 있어서, 그 컴포넌트를 그대로 가져오면 폰에서 **누를 수는 있는데 아무 표시가 없는** 상태가
된다. 터치에서 그 자리를 메우는 것은 **눌림 상태(pressed)** 와 **롱프레스**다.

## 3. 전환 규칙

**스택이다.** 앞으로 밀고(push) 뒤로 뺀다(pop). Android 하드웨어 뒤로가기 = pop, 스택이 비면 앱을
내린다. iOS 는 좌측 가장자리 스와이프 = pop.

```
서버 목록 → 세션 목록 → 터미널
    ↓
서버 추가 / 연결 진단        설정 · 알림 (어디서든 push, pop 으로 복귀)
```

**터미널에서 시간을 가장 많이 쓴다.** 그래서 터미널에서 나가지 않고 할 수 있어야 하는 것이 있다:

| 무엇 | 규칙 |
|---|---|
| **세션 전환** | 터미널 안에서 된다. 목록까지 pop 했다 다시 push 하지 않는다 |
| 세션 목록 보기 | 터미널 위에 **덮어서** 연다(pop 아님) — 닫으면 보던 자리로 돌아온다 |
| 알림 탭 | 그 세션의 터미널로 **바로** 간다(스택을 그 경로로 세운다) |

**전환에서 스크롤 위치를 잃지 않는다.** 세션을 바꿨다 돌아오면 보던 자리에 있어야 한다 — 긴
빌드 로그를 보다 다른 세션을 확인하는 것이 주 사용 흐름이라, 매번 바닥으로 튀면 못 쓴다.

> **지금은 세션이 하나뿐이다.** 브리지가 `term_core` **단일 변수**를 들고 있고, 화면의 탭 셋
> (`zsh`·`vim`·`logs`)은 `tree.text` 에 박힌 **라벨**이지 세션이 아니다. 눌리지도 않는다.
> 그래서 위 규칙들은 **목표이고, 그 앞에 다중 세션 상태 구조가 먼저 온다** — 세션마다 코어(또는
> 원격 runtime 핸들)와 뷰포트를 따로 들어야 "돌아오면 보던 자리" 가 성립한다.

## 4. 아직 정하지 않은 것 (사용자 결정)

**세션 전환의 손짓**을 안 정했다. 셋 중 하나다:

| | 어떻게 | 값 | 대가 |
|---|---|---|---|
| A | 좌우 **스와이프** | 가장 빠르다(한 손) | 터미널 가로 스크롤·선택 드래그와 충돌 판정이 필요하다 |
| B | 상단 **탭 줄** | 무엇이 있는지 늘 보인다 | 세로 공간을 상시 먹는다. 세션이 많으면 넘친다 |
| C | **덮개 목록**(서랍) | 공간을 안 먹고 세션 수에 안 눌린다 | 두 번 만져야 바뀐다 |

지금 구현은 B(데스크톱 탭 이식)인데, 그건 **결정이 아니라 데스크톱을 그대로 옮긴 결과**다.

**만져 보고 정한다(사용자 결정).** 손짓의 좋고 나쁨은 문서로 못 가른다 — 엄지 하나로 닿는지,
가로 스크롤·선택 드래그와 헷갈리는지는 손가락이 답한다. [U1](plans/mobile-platform.md)에서 터치
기본기가 서면 그 위에서 재 보고 여기에 확정을 적는다.

**그때까지 세 안을 다 살려 둔다** — 어느 것도 전제로 깔지 않는다. 특히 지금의 상단 탭 줄을
"이미 정해진 것" 으로 두고 그 위에 쌓지 않는다.

## 5. 화면이 요구하는 컴포넌트

**공용 컴포넌트 계층은 있는데 모바일이 아직 안 쓴다.** 브리지가 쓰는 것은 `chrome.ui` 의
**레이아웃·그리기 기반**(`tree`·`layout`·`paint`)과 `draw`·`tokens` 뿐이고,
`chrome/components/*`(`text_field`·`input_box`·`toggle`·`dropdown`·`confirm`·`modal_box`)는
**하나도 안 쓴다** — 키바·탭·사이드바를 `tree.card`/`tree.text` 로 직접 조립한다.

그래서 U1 은 "있는 컴포넌트를 터치용으로 고치는 일" 이 아니라 **두 가지가 겹친 일**이다:
① 모바일이 그 컴포넌트를 **쓰기 시작하고**, ② 그 컴포넌트가 **터치를 받도록** 한다. ①을 건너뛰고
계속 직접 조립하면 데스크톱과 두 벌이 되고, ②를 건너뛰면 hover 전제라 폰에서 반응이 없다.

| 화면 | 필요한 것 | 지금 상태 |
|---|---|---|
| 서버 목록·세션 목록 | 긴 목록 **터치 스크롤** | `scroll_area` 가 **마우스 휠 모델** — 관성·bounce·콘텐츠 직접 드래그가 없다. 보조 키바만 브리지가 직접 쥐고 있다(§5.4) |
| 서버 추가 | 텍스트 입력(주소·이름) | `text_field` 는 마우스 caret 모델. 소프트 키보드는 **뜨지만 다시 못 올린다**(아래 §5.2) |
| 설정 | 토글·수치 입력·선택 | `toggle`·`input_box`·`dropdown` 있음. 터치 히트 크기 미검증 |
| 모든 화면 | 손가락 히트 영역 | **보조 키바는 44 로 섰다**(§5.4). 탭(34)·그 밖은 아직 |
| 입력이 있는 화면 | **키보드가 가리지 않게** | **된다**(§5.2) — 양 host 가 키보드 높이를 빼고 가용 높이를 넘긴다 |
| 터미널 | 세션 전환·덮개 | 지금 눌리는 것은 **보조 키바뿐** — 탭·사이드바는 그리기만 한다 |

### 5.1 터치가 요구하는 것 (컴포넌트 공통 계약)

- **히트 영역은 iOS 44pt · Android 48dp 이상**이다. 그리는 크기와 다를 수 있다 — 작게 그리고
  넓게 받는다.
- **스크롤은 콘텐츠를 직접 끈다.** 손가락을 놓으면 관성으로 미끄러지고, 끝에서 튕긴다. 스크롤바
  드래그는 보조다(터미널 스크롤은 이미 host 가 `fling` 을 들고 있다 — 그 모델을 컴포넌트 계층으로
  올린다).
- **관성·러버밴딩은 플랫폼, 의미는 코어**([계약 §3.1](mobile-platform.md)). 이 문서가 그 경계를
  바꾸지 않는다.
- **포커스는 손짓으로 온다.** 입력 필드를 탭하면 소프트 키보드가 뜨고, 바깥을 탭하면 내려간다.

### 5.2 소프트 키보드 — 실측으로 갈라 둔다

**앱은 정상이다.** iOS `ChromeView` 는 `UITextInput` 을 채택하고 `becomeFirstResponder` 가
성공하며(로그 `first_responder=1`) 입력이 실제로 코어까지 들어간다(`MARU_INPUT text=…`).
실기기에서는 키보드가 뜬다.

**시뮬레이터에서는 안 뜨는데 그건 환경 탓이다** — 하드웨어 키보드가 붙어 있으면 iOS 가 소프트
키보드를 숨기고, 앱이 강제할 공개 API 가 없다. `defaults` 를 끄고 시뮬레이터를 재기동해도
`idb ui text` 가 하드웨어 경로로 들어가는 것을 실측했다.

**켜는 길은 메뉴에 하나 있고, 그것뿐이다.** `defaults` 는 안 통한다(값이 0 이어도 안 뜬다 — 같은 상태에서
**Safari 조차 안 떴다**). 지배권은 메뉴에 있다:

```sh
osascript -e 'tell application "System Events" to tell process "Simulator" \
  to click menu item "Toggle Software Keyboard" of menu 1 of menu item "Keyboard" \
  of menu 1 of menu bar item "I/O" of menu bar 1'
```

`ime-ios` 하네스가 이것을 자동으로 누른다. 이걸 찾기 전에는 **소프트 키보드 UX 를 만질 수단이
아예 없었다** — "만져 보고 정한다" 는 결정(§4)이 이 한 줄에 걸려 있었다.

**그래도 자동 판정자는 없다.** 이 토글은 사람이 화면을 보며 누르는 경로라 `mise run check` 에도
CI 에도 없고, **키보드가 뜬 상태의 레이아웃은 캡처로만 판정된다**. 실기기의 키보드 높이·애니메이션
길이·예측 줄 토글은 시뮬레이터와 다르므로 [검증 매트릭스](verification-matrix.md)의 실기기 대기
항목으로 남는다.

**"한 번 내리면 다시 못 올린다" 는 없는 문제였다.** 앱이 `resignFirstResponder` 를 안 부르고
키보드를 내리는 UI 도 없으며, 백그라운드 왕복 뒤에도 입력이 그대로 들어간다(실측 —
Safari 로 나갔다 돌아와 `MARU_INPUT text=…` 확인). **가려진 자리를 피하는 것**만 진짜 공백이었고
그건 아래에서 닫았다.

### 5.3 키보드가 덮는 만큼 레이아웃이 줄어든다

**양 host 가 키보드 높이를 빼고 가용 높이를 넘긴다.** 브리지는 그 값을 그대로 쓰므로 column
레이아웃이 알아서 위로 올라온다 — 브리지에 키보드 개념이 없다(§3.1 "느낌은 플랫폼").

| | 어떻게 |
|---|---|
| iOS | `UIKeyboardWillChangeFrameNotification` → 뷰와의 교집합 높이. show/hide 를 따로 안 받는다(회전·분할 키보드·예측 줄 토글이 전부 같은 알림으로 온다) |
| Android | `WindowInsets.Type.ime()` 를 **decorView** 리스너에서. `adjustResize` 는 **targetSdk 35 부터 무시**되고, `addContentView` 로 얹은 뷰는 insets dispatch 를 못 받는다(둘 다 실측) |

**둘 다 navigation bar·safe area 하단과 겹치는 만큼은 두 번 빼지 않는다** — 키보드가 그 영역을
덮기 때문이다.

**이걸 고치기 전에는 보조 키바가 키보드 아래로 사라졌다.** 그 키바의 존재 이유가 "소프트
키보드에 Ctrl·Esc·Tab·화살표가 없다" 인데, 정작 키보드가 뜨면 못 쓰게 되는 상태였다.

### 5.4 보조 키바 — 크기를 지키고 가로로 스크롤한다

키가 **손가락 크기(44)** 여야 하는데, 그러면 키 11개가 폰 세로 폭을 **못 들어간다**(가용 390 에
44×11 + 3×10 = 514). 셋 중 하나를 골라야 했고 다섯 배치를 실제로 만들어 화면으로 비교했다:

| 안 | 대가 |
|---|---|
| 키를 3개 버린다 | `\|` `~` `/` `-` 가 사라진다 — 셸에서 자주 쓴다 |
| 2줄로 | 세로를 54px 더 먹는다. 키보드가 이미 절반을 먹는데 |
| flex 로 줄인다 | **44 가 35 가 된다** — 기준을 지킨 것이 아니다(`ctrl` 라벨이 카드 밖으로 삐져나왔다) |
| **크기를 지키고 가로 스크롤**(택) | 스크롤·관성·여지 표시를 직접 만들어야 한다 |

**규칙**:

- **44 고정폭**(`shrink = 0`) · **키캡 면**(배경보다 밝게) · **2px 테두리** · **20px 라벨**.
  손가락은 hover 로 더듬을 수 없어 **눌리는 자리가 보이는 것이 크기보다 먼저**다.
- **방향키는 합성 아이콘, 나머지는 글자다.** `↑↓←→`(U+2190~2193)는 폰트마다 작게 디자인돼 44px
  키캡에서 `esc`·`tab` 보다 훨씬 작아 보였다(화면으로 확인) — SVG→coverage 자산으로 바꿨다
  ([chrome-strategy §9.6](chrome-strategy.md), 자산 provenance 는
  [third-party-licenses](third-party-licenses.md)). 나머지는 **글자가 맞다**: `esc`·`tab`·`ctrl` 의
  기호(`⎋`·`⇥`·`⌃`)는 맥 사용자만 알고, `|`·`~`·`/`·`-` 는 **입력되는 문자 그 자체**라 아이콘으로
  바꾸면 무엇이 들어가는지 알 수 없다.
- **탭과 밀기는 브리지가 가른다** — down 에서 바로 치지 않고 up 까지 기다려 **움직인 거리가
  10px 미만일 때만** 친다. 밀려던 것이 입력이 되면 안 된다.
- **`<` `>` 는 신호이지 버튼이 아니다.** 잘린 자리는 화면에서 "끝" 과 구별되지 않아 표시가
  필요하지만, **누르는 것은 아니다** — 데스크톱 탭바의 `‹›` 가 클릭 가능한 것은 마우스이기
  때문이고 터치에서는 **밀면 된다**(§2.4). 한때 누르면 한 화면씩 옮기게 했다가 되돌렸다:
  표시 폭이 26px 이라 **44 기준에 미달하는 버튼을 새로 만드는 꼴**이었다(44 를 지키려고 시작한
  작업에서). 키가 지나가는 창은 그 표시 **안쪽**이다(밴드 전체로 두면 표시가 가장자리 키
  라벨을 지운다).
- **창에 완전히 들어온 것만 그리고, 그것만 누른다** — 조건이 하나다. 그리는 범위와 누르는 범위가
  갈리면 **보이는데 안 눌리는 키**가 생기고, 걸친 것을 그리면 반쯤 잘린 키가 `>` 옆에 붙어 표시를
  묻는다(둘 다 화면에서 잡았다). 스크롤 중 키가 44px 단위로 나타났다 사라지지만 **"보이는 것이
  눌린다"** 가 그보다 중요하다.
- **`copy` 는 늘 줄에 있다.** 한때 선택이 있을 때만 나타나게 두고 그 자리를 예약했는데, 예약분이
  평소엔 **죽은 공간**이었다. 상시 표시하니 나타났다 사라지며 줄이 흔들리는 일이 없어져 예약도
  필요 없어졌고(그 자리에 키가 하나 더 들어간다), 쓸 수 없을 때는 **흐리게** 그린다 — 눌러도
  아무 일이 없다는 것이 보여야 한다(무반응은 고장으로 읽힌다).
- **눌린 키는 눌린 것처럼 보인다.** `armed`(`ctrl` 처럼 다음 글자까지 유지)와 **다른 축**인
  `pressed`(지금 손가락이 닿아 있다)를 따로 둔다 — 이것이 hover 가 사라진 자리를 메운다(§2.4).
- **임계를 넘기 전에는 스크롤도 안 한다.** 이동량을 늘 반영하면 살짝 민 손짓이 **화면도 움직이고
  키도 내보낸다** — 같은 손짓이 어떨 때는 스크롤로, 어떨 때는 입력으로 보인다.
- **창은 키 배수로 맞춘다.** 자투리를 남기면 완전히 들어온 키만 그리는 규칙 탓에 그 자리가 영영
  안 채워진다. 남는 폭은 좌우 표시가 나눠 먹어 눈에 안 띈다.

**레이아웃으로는 못 했다.** 음수 margin 으로 밀면 `tree` 가 `error.NegativeValue` 로 거부해 화면이
통째로 검게 나가고, `chrome/ui/scroll_area` 는 세로 전용이다. 그래서 **키바를 레이아웃에서 빼고
브리지가 직접 그린다**(레이아웃은 밴드 자리만). **컴포넌트 계층에 가로 스크롤이 생기면 이 직접
그리기를 그쪽으로 옮긴다** — U1 이 닫을 공백이 여기 남는다.

## 6. 베이스

**Orca 모바일 컴패니언**(references/orca/mobile)을 화면 구성의 참고로 봤다 — 같은 위치(데스크톱
앱 + 폰 컴패니언)라 무엇이 화면이 되는지가 드러난다. 연결 계층이 `pair`·`pair-scan`·
`pair-confirm`·`connection-log`·`troubleshoot` **다섯 화면**이고, 본체가 호스트별 스택
(`/h/[hostId]/…`)으로 갈린다. 우리 §2 의 3계층이 그 모양과 같은 갈래다.

**형태만 참고했고 구현은 우리 것이다.** Orca 는 React Native 라 스크롤·제스처·내비게이션·
키보드 대응을 프레임워크가 주지만, maru 는 Zig+GPU 로 직접 그린다([계약 §1](mobile-platform.md)) —
그래서 §5 의 "터치에서 쓸 수 있게 하는 일" 이 이 앱에서는 UX 작업의 절반이다.
