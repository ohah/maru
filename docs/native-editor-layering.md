# 네이티브 편집기 — 레이어 배치 (§2)

편집기를 어느 레이어에 놓고 무엇을 새로 만들지, 스레딩·상태바·탭 이름·같은 파일 다중 뷰를 정한다. 편집기 계약 전체의 진입점은 [네이티브 편집기](native-editor.md)이고, 이 문서는 그 §2를 소유한다.

> **절 번호는 파일을 넘어 이어진다.** 본문이 `§4.1`처럼 절만 가리키면 아래에서 소유 파일을 찾는다 — §1·§10~§12 [native-editor.md](native-editor.md) · §2 [레이어 배치](native-editor-layering.md) · §3 [문서 모델](native-editor-document-model.md) · §4~§6 [시각 매핑](native-editor-visual-mapping.md) · §7~§9 [diff·떠 있는 UI·설정](native-editor-ui.md)

## 2. 레이어 배치

[layering-and-portability.md](layering-and-portability.md) §2의 4층 위상을 그대로 따른다. **새 최상위 namespace를 만들지 않는다.**

```text
L2  src/session/editor/          문서 모델 — chrome·OS를 모름
      buffer.zig                 텍스트 저장 + 편집 연산 + undo (표현은 §3.0 실측 후 결정, N2)
      line_index.zig             byte offset ↔ 논리행 (N1 — buffer 도입 시 흡수 여부를 함께 정한다)
      selection.zig              multi-selection(byte range 배열) + goal column
      document.zig               파일 → 문서 해석(BOM·줄바꿈·파일 끝 개행 보존, §3.5)
      hazard.zig                 적대적 입력 판정(BiDi·제어·폭 0·비표준 공백, §3.8)
      span.zig                   Span/role + SpanProvider 주입점
      (기존 계약) protocol.zig · grant.zig · document_registry.zig · diff_model.zig

L3  src/chrome/components/editor_view/    표시 — 모델을 props로 읽음
      visual_map.zig             §4 시각 매핑(접힘 → 가상줄 → 랩 → 시각행)
      viewport.zig               스크롤 → 보이는 시각행 범위
      geometry.zig               caret/선택 rect ↔ hit-test 역함수(단일 레이아웃 소스)
      gutter.zig                 줄 번호 · git 변경 마커 · 접기 화살표 · 진단 마커(N4, §4.1)
      content.zig                본문 텍스트(탭 전개 · 셀 격자 배치)
      minimap.zig                §6 전 문서 집약 → 색 블록

L4  src/platform/macos/          셀·quad lowering · 입력 이벤트 · IME(§11)
```

**기존 컴포넌트 두 계열 중 어느 쪽인지 명시한다.** `chrome/components/` 아래에는 성격이 다른 둘이 있다 — `session_dock/`·`archive_detail/`은 **새 typed tree 계열**로 `ui/tree.zig`·`ui/layout.zig`를 쓰고 `build.zig`(UiNode 조립)·`ids.zig`(UiActionId)·`types.zig`·`view.zig` 규약을 따른다([metal-ui-layout.md](metal-ui-layout.md) §2). 나머지 다수(`tabbar`·`sidebar`·`find` 등)는 자체 레이아웃을 가진 단일 파일이다.

**`editor_view/`는 후자 계열이다** — 등폭이라 flex tree가 필요 없으므로 `build.zig`/`ids.zig` 규약을 따르지 않는다. 디렉터리로 나누는 것은 파일 수 때문이지 새 tree 규약을 쓰기 때문이 아니다. **구현 시 `session_dock/`을 형태의 본으로 삼지 않는다.**

**facade에 export 줄을 더해야 한다.** `chrome.zig`의 `pub const components = struct { … }`와 `session.zig`의 `pub const x = @import("session/x.zig")`가 명시 목록이므로 새 모듈마다 한 줄이 필요하다. 반면 `build.zig`는 `src/maru.zig` 루트 모듈 하나를 쓰므로 **새 파일에 대한 빌드 배선은 없다**(import 체인에 들어가면 자동으로 컴파일된다).

**L3를 단일 파일로 두지 않는 이유**: 시각 매핑·뷰포트·기하·gutter·미니맵은 서로 다른 이유로 바뀐다. [project-rules.md](project-rules.md) §구조와 파일 분리("한 모듈이 서로 무관한 책임을 갖기 시작하면 모듈을 분리한다")와 [project-structure.md](project-structure.md)의 "폴더가 domain, 파일명이 그 안의 한 책임" 규칙을 그대로 적용한다. 단 **`geometry.zig`는 쪼개지 않는다** — 그리기와 hit-test가 한 레이아웃 소스를 공유해야 한다는 [chrome-strategy.md](chrome-strategy.md) §5.4 MUST가 그 둘을 같은 파일에 묶는 근거다.

**L2가 모델을 갖는 근거**: L2 session core의 책임에 이미 "scroll/reorder 수학"이 들어 있고, [editor-surface-structure.md](editor-surface-structure.md) §3.4가 `src/session/editor/`를 editor L2 코어 자리로 이미 정해 두었다. 문서 모델은 그 옆에 선다.

**L3가 표시를 갖는 근거**: 표시에 필요한 것이 전부 chrome 소유다 — 색·폰트 토큰(테마 일관성), 스크롤바·포커스 테두리(사이드바·도크와 같아 보여야 함), gutter·미니맵 프레임, pointer 상태 관리. [layering-and-portability.md](layering-and-portability.md)의 "chrome이 session을 props로만 읽음" 패턴을 그대로 쓴다.

**`editor_view`는 `ui/layout.zig`의 typed flex를 쓰지 않는다.** 등폭이라 레이아웃이 산술로 끝나기 때문이며, [metal-ui-layout.md](metal-ui-layout.md) §1의 "새 chrome tree는 셀 row/column과 섞지 않는다"와 충돌하지 않는다 — flex tree를 쓰지 않을 뿐 chrome의 토큰·`ChromeDraw`·interaction 어휘는 그대로 쓴다. `chrome/components/`의 다수 컴포넌트가 아직 같은 상태이며([chrome-interaction-migration.md](chrome-interaction-migration.md)), 예외가 아니다.

**파생 캐시의 소유는 "뷰에 의존하는가"로 가른다.** 층 사이에 캐시가 걸치면 무효화 주체가 둘이 되어 어긋난다.

| 파생값 | 소유 | 근거 |
|---|---|---|
| 줄별 **표시 폭 합** | **L2** | 문서 내용과 탭 폭 설정만의 함수다(`width.displayCols` 누적 + 탭스톱 — §4). 뷰 폭·스크롤과 무관하므로 뷰가 바뀌어도 무효화되지 않는다(탭 폭 설정이 바뀌면 무효) |
| **구문 트리**(§5.3) + 파생 스팬 | **L2** | 문서 내용과 언어만의 함수다. provider가 트리를 소유하고(§5) 편집 통지로 증분 갱신하며, **persistent 스냅샷이라 워커에 넘길 수 있다**(§2.1). §6 미니맵이 전 문서 스팬을 요구하는 것도 이 소유 때문에 성립한다 |
| **가상 텍스트 반영 폭** | **L3** | `L2 폭 합 + 인레이 힌트 폭`(§4). 힌트는 LSP 응답이라 문서 내용의 함수가 아니므로 L2 캐시를 오염시키지 않는다 |
| **줄별 랩 분할 결과** | **L3** | word wrap이면 폭만으로 유도되지 않고, 입력도 L2 폭 합이 아니라 위 파생 폭이다(§4). 뷰 열수에 의존하므로 폭 변경 시 무효 |
| **시각행 수·시각행 ↔ 논리행** | **L3** | 뷰 열수·접힘·가상줄에 의존한다. 뷰 폭이 바뀌면 통째로 무효 |
| 뷰포트 범위·caret rect | **L3** | 스크롤 상태에 의존 |

L3는 L2 캐시를 **복사하지 않고 읽는다** — chrome이 session을 props로 읽는 기존 패턴 그대로이며, 전 문서 스팬이 props에 실려도 소유권이 옮겨가지 않는다.

**`text_field.zig`와 코드를 공유하지 않는다.** [text-field-editor.md](text-field-editor.md) §2.2가 단일행 필드를 새 컴포넌트로 분리한 것과 같은 판단이다 — 소비자도 규율도 다르다. 공유하는 것은 순수 헬퍼(`src/grapheme.zig`·`width.displayCols`)뿐이며, 폭 규약(`@max(1, cellWidth)`)은 같은 값을 쓴다.

### 2.0 무엇을 새로 만들고 무엇을 재활용하는가

**chrome 디자인 시스템은 거의 다 있다.** 새로 만드는 것은 "문서 본문"에 특화된 몇 개뿐이며, 떠 있는 UI·스크롤·상태 표시는 기존 컴포넌트의 확장이다.

**이 표가 §1.0의 "역량·통제력" 대가를 구체화한다** — 직접 지어야 하는 것은 UI 위젯이 아니라 **문서 모델과 그 렌더**(§3·§4)이고, 위젯은 대부분 이미 있다.

**재활용 대상이 두 세대로 갈려 있다는 것을 알고 붙는다.** chrome은 [chrome-interaction-migration.md](chrome-interaction-migration.md)에 따라 **점진 이관 중**이고, 위 표의 컴포넌트가 서로 다른 지점에 있다.

판별 기준은 **`ui/` 모듈(tree·layout)을 쓰는가**다. `draw.zig`(`ChromeDraw`)는 세대와 무관한 공통 emission 경계이므로 판별에 쓰지 않는다.

| 세대 | 컴포넌트 | 편집기에 대한 의미 |
|---|---|---|
| 신규 typed tree(`ui/tree` + `ui/layout`) | `status_bar` · `ui/scroll_area` | 그대로 붙으면 된다 |
| 이주 완료([chrome-strategy.md](chrome-strategy.md) C1·C2) — `ui/layout` + `ChromeDraw` | `find` · `divider` | 같음. **`divider`가 이 문서가 지으려는 형태의 선례다** — `ui/` 기하를 쓰되 flex tree를 강요받지 않고 `ChromeDraw`로 내보낸다 |
| **레거시**(`ui/` 미사용) | `context_menu` · `dropdown` · `tabbar` | **이관 예정이므로 그때 편집기도 함께 움직인다** |

**그럼에도 재활용이 옳다** — 새로 만들어도 같은 이관을 겪고, 재활용하면 이관이 올 때 **한 번에** 움직인다. 위젯을 새로 짜는 것은 [chrome-strategy.md](chrome-strategy.md)가 경계하는 "네 번째 스타일"을 만들 뿐이다.

**단, 이 문서가 새로 만드는 넷(본문 렌더·gutter·미니맵·diff 배치)은 처음부터 신규 세대 규약으로 짓는다.** 레거시 형태로 지으면 태어나자마자 이관 부채가 된다. 다만 §2가 적었듯 **`ui/layout.zig`의 flex tree는 쓰지 않는다**(등폭이라 레이아웃이 산술이다) — 따르는 것은 픽셀 rect·clip·hit-test 규약과 `ChromeDraw` 경계이지 flex가 아니다.

**chrome 이관(CIM) 전체를 기다리지는 않는다.** [chrome-interaction-migration.md](chrome-interaction-migration.md)는 별개 이니셔티브이고 그 완료를 선행 조건으로 두면 편집기가 무기한 대기한다. 그럴 필요도 없다 — **첫 제품 가치(diff 본문)까지 필요한 컴포넌트에 레거시가 사실상 없다**(`divider`·`find`는 이주 완료, `scroll_area`·`status_bar`는 신규 세대, 본문·diff 배치는 어차피 신규).

**그러나 편집기가 실제로 쓰는 레거시는 "확장"이 아니라 "이관"으로 처리한다.** 그 둘(`context_menu`·`dropdown`)은 CIM 순서의 마지막(CIM6 Input/overlay composite → `Menu`/`Popover`)에 있는데, **편집기가 그 composite의 first consumer가 되는 것**이 CIM 자신의 방식과 맞다 — 그 문서가 `ScrollArea`에 대해 *"file tree와 Session Dock 중 하나를 first consumer로 삼는다"*고 한 것과 같은 이유다. **consumer 없이 설계한 composite는 요구를 모른다.**

- **한 번만 만진다.** 이관 때 한 번, 편집기 요구를 붙일 때 또 한 번 건드리면 같은 파일을 두 번 여는 것이다. **옮기면서 편집기가 필요한 props를 함께 넣는다** — 메뉴는 대상 종류(text·link·image)와 선택 유무, 팝업 목록은 항목·필터·선택 인덱스가 그 요구다.
- **시점은 그 기능이 필요한 슬라이스다** — 메뉴는 편집이 서는 단계, 팝업은 자동완성이 붙는 단계. 미리 당겨서 이관만 해 두지 않는다(consumer 없는 이관은 다시 CIM의 문제가 된다).
- **CIM 문서가 순서의 소유자다.** 편집기가 first consumer로 CIM6 일부를 앞당기는 것이므로 **그 문서와 조율**하고, 편집기가 임의로 composite 계약을 정하지 않는다.
- **이관이 먼저 도착하면** 편집기는 새 형태에 붙고 옛 형태를 되살리지 않는다.

**`tabbar`의 알려진 리스크를 물려받는다.** [chrome-strategy.md](chrome-strategy.md) §10이 "(높음) rich-layout seam — 탭 분할과 hit-test가 셀-열에 고정 결합"을 등록해 두었고, 파일 Term의 탭도 같은 탭 바가 그린다. 편집기가 그 결합을 **더 굳히지 않도록** 탭 기하에 새 의존을 만들지 않는다.

**이관 축이 하나가 아니다 — 텍스트 배치는 별개 축이고, 편집기는 두 규칙을 동시에 쓴다.** 위 세대 표는 CIM 축(`ui/tree`·`ui/layout`을 쓰는가)만 가른다. 텍스트를 **셀 격자에 놓는가** 폰트 advance로 **이어 붙이는가**는 그것과 직교하는 다른 축이며, 한쪽을 안다고 다른 쪽이 정해지지 않는다.

**measured 이관은 "전부 옮기기"가 아니다.** [file-explorer.md](file-explorer.md)가 그 이관의 소유자이고 목적이 좁게 정의돼 있다 — **고정 높이 chrome 바(40pt) 안의 텍스트가 큰 폰트에서 밴드를 넘치는 결함**을 없애는 것이다. 셀 높이는 편집기 폰트에 비례해 커지는데 바 높이는 pt로 고정이라, 폰트를 키우면 글자가 바 아래로 삐져나왔다. measured 텍스트의 line box는 **chrome role 토큰(pt)에서 나와 폰트에 불변**이라 밴드 안에 정확히 들어간다. 순서는 캐시 확장 → 사이드바 검색 줄 → 탭 제목이었고 그 셋은 끝났다.

**그래서 판별 기준은 "낡았는가"가 아니라 "고정 높이 chrome 바 안에 있는가"다.** 같은 문서가 `find`·`palette`를 **이관 대상에서 뺀 이유**가 정확히 이것이다 — 화면 중앙 오버레이라 40pt 바 안에 있지 않아 넘치는 결함이 없다. tui 경로도 사용자 결정으로 제외됐다(셀 격자 정렬이 정체성). **셀 경로는 폐기 대상이 아니라 현역이다.**

**용어를 먼저 바로잡는다 — 이것은 렌더 경로가 아니라 배치 규칙이다.** 편집기 텍스트도 도크·탭과 **같은 measured 백엔드**(`platform/macos/chrome/system_text.zig`)를 탄다. 다른 것은 그 안에서 **글자 x를 무엇으로 정하느냐**뿐이다 — 폰트 advance를 누적하면 measured 배치, `Op.text.cell_w_px`가 있으면 셀 폭(EAW)을 누적한 **셀 인덱스** 배치다. 아래 표의 "셀"은 후자를 뜻하며, 별도 렌더 경로가 있다는 뜻이 아니다.

| 요소 | 배치 규칙 | 근거 |
|---|---|---|
| 본문 텍스트 | **셀** | 등폭 고정이 기능 요구다(§1.1) — 세로 정렬·블록 선택·goal column이 셀 격자에 의존한다. 배치는 `Op.text.cell_w_px`가 보장한다(아래) |
| **gutter 줄 번호** | **셀** | 아래 |
| gutter 접기 화살표·진단 마커 | 셀 정렬 + 아이콘 | 위치는 본문 행에 묶이고 그리기는 아이콘 축이다 |
| gutter git 변경 마커 | 셀 정렬 + **세로 바** | 아이콘이 아니다 — 기존 `GutterMark`(커서 bar kind=3)를 재사용해 **셀 폭을 먹지 않는다**(§4.1) |
| 미니맵 | 해당 없음 | 글리프를 그리지 않는다(§6 색 블록 quad) |
| 상태바 항목·탭 제목 | **measured** | 편집기 밖 chrome이고 **고정 높이 바 안**이라 위 기준에 해당한다 |

**gutter가 chrome measured **배치** 대상이 아닌 이유는 `find`·`palette`와 같다 — 고정 높이 바 안에 있지 않다.** gutter는 본문과 함께 흐르고 함께 스크롤하며, 높이를 제한하는 pt 컨테이너가 없다. 따라서 폰트를 키워 셀이 커져도 **넘칠 밴드가 없다.**

**오히려 셀이라서 얻는 것이 폰트 크기 연동이다.** measured의 line box는 chrome role 토큰(pt)에서 나오므로 **편집기 폰트를 키워도 그대로**다 — chrome 바에서는 그것이 정확히 원하는 성질이지만, gutter에서는 본문만 커지고 줄 번호는 작게 남는다는 뜻이 된다. 셀 경로는 그 연동이 공짜다. 폰트 크기 조절은 실제로 자주 쓰는 기능이라 이것이 실질적인 UX 이득이다.

**이 주장은 캡처로 확인했다.** Chrome Lab의 `editor-font-large`가 폰트를 1.5배로 주면 글리프 높이가 10px에서 14px로 커지고 배치도 함께 비례한다(본문 시작 64px → 96px, gutter는 계속 8셀). 시각 골든이 이것을 고정한다.

**초판은 이것을 두 번 잘못 적었다.** 처음에는 "셀 크기가 곧 폰트 래스터 크기"라고 단정했는데 `CoreTextFrameBuilder` 인자만 보고 결과를 확인하지 않은 것이었고(실제로는 글리프가 안 커졌다), 다음에는 "measured라 연동이 불가능하다"고 적었는데 그것도 틀렸다 — `Op.text.font_px`/`line_height_px`를 더해 폰트 크기를 셀에서 오게 하면 measured 경로에서도 연동된다. **폰트 크기의 출처가 문제였지 렌더 경로가 문제가 아니었다.**

**아직 확인되지 않은 것 하나**가 남는다 — **제품 경로의 폰트 메트릭 → 셀 크기 배선**. Lab은 시나리오가 셀과 폰트 크기를 함께 정해 주고(역산은 픽스처가 소유한다), 실제 사용자 `font.size`가 그 값을 만드는 경로는 N2에서 배선한다.

부수적으로 둘 더 있다. ⑴ 사용자 시선이 "번호 → 코드"로 가로로 이어지므로 gutter가 통일감을 가져야 할 대상은 chrome UI가 아니라 **본문**이다. ⑵ 줄 번호는 본문 줄과 1:1로 세로 정렬돼야 하는데(랩이 켜지면 첫 시각 행에만 붙는다), 행 높이 기준이 둘이면 긴 파일에서 오차가 누적된다.

**정직한 대가: 줄 번호만 본문보다 작게 만들 수 없다.** 크기가 셀에 묶이기 때문이다. 다만 **흐리게 하는 것은 된다** — 셀마다 전경색이 이미 있어 색 토큰 하나로 처리되고, 주요 편집기가 줄 번호를 눈에 덜 띄게 만드는 방식도 크기가 아니라 색이다. 크기까지 달라야 할 요구가 생기면 그때 measured로 옮기되, **세로 정렬을 별도로 보장하는 비용**이 딸려온다는 것을 함께 판단한다.

**이 계약을 지키려면 백엔드에 한 가지가 필요했고, 그것을 넣었다.** `chrome.draw.Op.text`에 문자열을 넘기면 백엔드가 measured로 처리해 op 안의 글자들이 셀 폭이 아니라 **폰트 advance**로 이어 붙는다 — 등폭 폰트도 advance가 7.8px인데 셀은 8px이라 두 번째 글자부터 격자를 벗어났고, 셀 기준으로 계산한 탭 위치가 화면과 갈렸다(실측: 계산 x=224인데 화면 x=167).

- **해법은 `Op.text.cell_w_px`다.** 값이 있으면 백엔드가 글자마다 **셀 폭(EAW)을 누적해** 몇 번째 칸인지 세고 그 인덱스로 x를 놓는다(`system_text.zig`). 한글·CJK·이모지는 두 칸, 결합 문자는 0칸이라 앞 글자와 같은 칸에 놓인다. 지금은 계산과 실측이 일치한다(224/256).
- **x를 셀 배수로 반올림하는 방식은 기각했다.** 글자마다 advance가 다르면 여러 글자가 같은 칸으로 몰려 문자열이 겹쳐 그려진다(실제로 그렇게 깨진 캡처를 확인했다). **인덱스를 세는 것과 좌표를 반올림하는 것은 다르다.**
- **터미널 셀 배열(`NativeMetalCell`)로 옮기는 것도 기각했다.** 그것은 renderer DTO이고 chrome은 renderer를 import할 수 없어(경계 가드) 편집기가 터미널 렌더에 결합된다. §2가 말한 "터미널 셀 렌더 경로"는 **등폭 격자에 그린다**는 뜻이지 그 구현을 재사용한다는 뜻이 아니다.
- **도크·탭은 이 값을 싣지 않으므로 기존 measured 배치 그대로다.** `retained-list` 캡처가 수정 전후 바이트 동일함을 확인했다.

**⚠️ 그런데 그 선택은 옵션 필드라 조용히 놓칠 수 있다 — 다음 표면이 같은 결함을 다시 낼 자리다.**

`Op.text.cell_w_px`는 `?u16 = null`이고 **기본이 measured**다(`chrome/draw.zig`). 저장소의 `Op.text` 생성
지점은 96곳인데 격자를 원하는 것은 편집기 둘(`gutter.zig`·`content.zig`)뿐이다 — **다수의 기본값이 소수
경로를 덮는 구조**이고, 새 편집기 표면이 안 실으면 **컴파일도 테스트도 통과하고 화면에서만** 드러난다.
위에 적은 x=224/167이 정확히 그 사고였고, 잡아낸 것은 컴파일러도 테스트도 아닌 **캡처**였다.

**골든이 이 부류를 막아 주지 않는다.** 골든은 회귀는 잡지만 **첫 구현은 그 상태로 비준한다** —
`editor-font-large.ppm`은 이 스택에서 **다섯 번 갱신됐고**(`91a6ab5b` → `88793277` → `c20c9c1d` →
`03148c21` → `4dead08f`), 글리프가 안 커지던 동안에도 그 골든은 **통과**했다. 그리고 Lab 시나리오가
없는 새 표면은 애초에 골든 자체가 없다.

**지금 둔 방어는 `system_text.zig`의 assert 하나다.** 편집기 전용 필드 셋(`font_px`·`line_height_px`·
`cell_w_px`)이 **다 있거나 다 없어야** 한다고 못박는다. 원래 앞의 둘만 재고 있었는데, 빠진 하나가 하필
배치 의미를 가르는 필드였다. **이 방어의 사정거리는 알고 쓴다** — `std.debug.assert`는
Debug·ReleaseSafe에서는 멈추지만 **ReleaseFast에서는 사라진다**. 배포 DMG가 ReleaseFast이므로
(`.mise.toml`의 `macos-dmg -Doptimize=ReleaseFast`) **제품 바이너리는 이 검사를 받지 않는다** —
잡아 주는 것은 테스트·Lab·ReleaseSafe 게이트다.

**더 강한 형태(세 필드를 `editor_metrics: ?struct{...}` 하나로 묶어 잘못된 조합을 표현 불가로 만들기)는
N2 이후로 미룬다.** 인레이 힌트·ghost text가 "편집기 폰트 크기는 따르되 배치는 flow"를 원할 수 있는데
(§4는 힌트 폭이 줄 폭에 되먹인다고만 하고 배치 축을 정하지 않았다), 그 결정 전에 묶으면 코드가 결정을
앞질러 내린다. **선언을 필수 필드(`lattice: .grid | .flow`)로 바꾸는 안은 기각한다** — 96곳 중 92곳을
기계적으로 `.flow`로 치환하는 대량 diff가 나오고, 지키려는 것은 편집기 경로 둘이다.

**따라서 이 축에서 편집기가 기다릴 이관은 없다.** 편집기가 새로 짓는 텍스트는 전부 셀 경로이고, measured 쪽(상태바·탭)은 이미 옮겨져 있다. **셀로 짓는 것이 부채가 아니라는 뜻이다** — 위 기준상 gutter는 애초에 대상이 아니므로, 나중에 "measured로 옮겨야 하는 빚"이 생기지 않는다. 이는 CIM 축과 대조된다(그쪽은 `context_menu`·`dropdown`이 실제로 이관 예정이라 first consumer로 함께 움직인다).

### 2.0a 소유 이동 — 넘긴 뒤에는 errdefer를 남기지 않는다 (2026-08-15)

**세 번 같은 자리에서 이중 해제가 났다.** 편집기 축은 "잡아서 오래 사는 곳(`Term.rt`·`State`)에
넘긴다"가 반복되는데, 그 사이에 실패 지점이 있으면 다음이 성립한다:

```
잡는다 → errdefer 건다 → 오래 사는 곳에 넘긴다 → …여기서 실패
              ↑ errdefer가 한 번 해제        그 오래 사는 곳의 해제 경로가 또 한 번
```

**규칙: 실패할 수 있는 일을 먼저 끝내고, 넘기는 것은 마지막에 한꺼번에 한다.** 넘긴 뒤에 실패
지점이 없으면 errdefer가 겹칠 여지 자체가 사라진다. 그렇게 못 하면 **넘기는 순간 errdefer를 두지
않는다**(그 자원의 주인이 이제 그쪽이므로).

**잡은 방법은 할당 실패 주입이다**(`std.testing.checkAllAllocationFailures`). 이 결함은 정상
경로에서 **절대** 나타나지 않는다 — 단위 테스트는 성공 경로만 돌고, 뮤턴트는 그 경로를 도는 테스트가
없으면 소용없으며, 캡처에는 안 보인다. 크래시는 사용자 환경에서 메모리가 모자랄 때만 난다.

**층마다 따로 봐야 한다.** L2(`session/editor/intraline.zig`)가 같은 검사를 통과했는데도 그 위
두 층(`materialize`·`computeMarks`)에서 각각 나왔다 — 아래층이 깨끗하다는 것이 위층의 소유를
보장하지 않는다.

**세 자리**: `editor_diff.computeMarks`(행별 마크 배열) · `editor_diff.materialize`(표시 배열 여섯) ·
`editor.openPathInActivePane`(문서·줄 배열·경로). 앞의 둘은 주입 테스트가 잡았고, 셋째는 그 패턴을
알고 나서 **읽어서** 찾았다.

**세션 allocator를 쓰는 자리는 `checkAllAllocationFailures`를 그대로 못 쓴다.** allocator가 init에
고정이고, 함수에 다른 allocator를 넘기면 나중에 해제하는 쪽(`releaseEditorTerm`)과 어긋나 **진짜
버그**가 된다. 대신 **세션을 `FailingAllocator`로 만들고 init이 끝난 뒤부터 `fail_index`를 옮긴다** —
init은 흔들지 않으므로 남의 코드를 시험하지 않고 빠르다(`editor.zig`의 "파일 열기가 어디서 할당에
실패해도 새지 않는다"). 그 테스트는 **실패를 몇 번 겪었는지 세어서 단언한다**: 열기가 쓰는 할당 수가
줄어 창을 벗어나면 한 번도 실패하지 않고 조용히 통과할 수 있기 때문이다.

### 2.1 스레딩 — 무거운 작업을 렌더 루프에 두지 않는다

레이어(§2)와 **직교하는 축**이다([io-render-threading.md](io-render-threading.md)가 같은 규정을 쓴다).

**편집 자체는 메인 chrome 스레드다**([text-field-editor.md](text-field-editor.md) §2.4와 같이 직접 mutate). **터미널처럼 코어를 통째로 별도 스레드가 소유하는 모델은 채택하지 않는다** — 두 도메인의 입력 성격이 다르기 때문이다.

- **터미널**은 입력이 PTY로 **나가고** 출력이 **비동기로 온다**. 코어를 reader 스레드가 소유하는 것이 자연스럽고, [io-render-threading.md](io-render-threading.md)가 그렇게 했다.
- **편집기**는 입력이 **곧 문서 변경**이고 즉시 화면에 반영돼야 한다. 워커로 넘기면 `키 → 전달 → 편집 → 회수 → 렌더`로 **최소 한 프레임이 더 붙는다.** 터미널은 PTY 왕복에 그것이 묻히지만 편집기는 로컬 편집이라 그대로 드러난다.
- **IME가 결정적이다.** `NSTextInputClient`는 AppKit 메인 스레드에서 호출된다. 조합 중 preedit를 다른 스레드의 모델에 반영하고 되받으면 왕복이 늘어나는데, 이 프로젝트에서 가장 깨지기 쉬운 지점이 정확히 거기다(§11).

이 선택은 **N2(편집) 구현 중 타이핑 반응으로 확인한다** — 별도 계측을 선행하지 않는다(§10). 메인 처리가 프레임 예산을 넘는 것이 관측되면 그때 근거와 함께 뒤집는데, **그때 틀린 것이 스레딩인지 버퍼 표현인지는 갈라야 한다**([문서 모델](native-editor-document-model.md) §3.0의 뒤집힐 조건 넷째).

**그러나 문서 크기에 비례하는 작업은 메인에서 하지 않는다.** 이는 취향이 아니라 실측된 결함의 재발 방지다 — [io-render-threading.md](io-render-threading.md)가 메인 렌더 스레드의 blocking 작업 때문에 **질의 응답이 4.2초 지연**된 것을 측정해 PTY I/O를 분리했다. 아래는 같은 계열의 위험이다.

| 작업 | 비용 | 배치 |
|---|---|---|
| 편집·selection·caret·뷰포트 | 입력 하나에 비례 | **메인** |
| 구문 트리 **조회**(`spansForRange`) | 뷰포트에 비례 | **메인** (프레임 예산 안) |
| **구문 트리 파싱·증분 갱신**(§5.3) | 내용에 달렸다 — 크기로 예측되지 않는다(아래 실측) | **점진**(메인, 프레임 분할) — tree-sitter가 파싱을 끊고 재개할 수 있다(아래 §2.1a). 뷰포트 한정 파싱은 없어서 트리는 언제나 문서 전체이지만, **한 번의 파싱을 나눌 수는 있다** |
| **전 문서 랩 재계산**(뷰 폭 변경) | 문서 크기 | **점진**(메인, 프레임 분할) — 줄마다 독립이라 나눠 셀 수 있다. 워커가 아닌 이유는 아래 |
| **문서 전체 검색**(§5.1) | 문서 크기 | **분리** |
| 파일 open/저장 I/O | 파일 크기 | **분리**(기존 파일 어댑터 경로) |
| LSP 왕복 | 서버에 의존 | **분리**(이미 별도 프로세스) |

**분리하기 전에 "매 프레임 하지 않기"가 먼저다.** 위 표는 *언제* 그 작업을 피할 수 없는지를 적은 것이지 *늘* 해야 한다는 뜻이 아니다. 랩 재계산이 그 예다 — 계약은 **뷰 폭 변경**을 비용의 계기로 적었는데, 실제 구현은 폭이 그대로인 정지 상태에서도 매 프레임 전 문서를 다시 접어 보고 있었다(실측: 4,000줄 랩 문서가 프레임당 12.9ms, ReleaseFast, 2026-08-18 — 60fps 예산의 76%). **줄별 행 수를 접두합으로 캐시하고 조건(줄 배열·본문 폭·랩·탭 폭)이 갈릴 때만 다시 세도록** 고쳐 그 자리가 0.2ms가 됐다(`components/editor_view/frame.zig`의 `RowCache` — 저장소는 제품이 소유하고 유효성 판정과 계수는 컴포넌트가 한다. 랩이 갈리는 본문 폭이 컴포넌트 안에서 정해지므로 제품이 그 폭을 다시 구하면 출처가 둘이 된다).

같은 수정이 **정확성 결함도 함께 닫았다.** 계수 상한이 호출자가 준 스택 배열 길이(`[4096]u32`)였어서 4,096줄을 넘는 문서는 나머지가 "논리 줄 하나"로 근사됐고, 20,000줄 랩 문서의 시각 행이 40,000이 아니라 24,096으로 나와 **스크롤바가 실제보다 1.66배 길게** 떴다. 성능과 정확성이 한 상한에 묶여 있었다.

**"창 리사이즈 중"이라는 근거는 이 구현에서 성립하지 않는다.** `MaruAppHost.windowDidResize`가 `inLiveResize` 동안 세션 resize를 **보류**하고 `windowDidEndLiveResize`에서 최종 크기로 한 번만 적용하기 때문이다(zsh가 SIGWINCH마다 상대 커서 이동으로 redraw하며 프롬프트를 중복시키던 문제로 도입된 정책). 창을 끄는 동안 편집기 폭은 바뀌지 않고, 그래서 계수도 돌지 않는다.

**라이브로 폭을 끄는 경로는 셋이다** — 사이드바 우측 경계 드래그(`sidebar_ops.setSidebarWidthPx`를 drag마다 부른다), pane divider 드래그(CIM2로 `InteractionState`에 이관됐고 tick coalescer가 최종 좌표 하나를 적용한다), dock 바깥 경계 드래그(`dock_ops.setDockSizeFromPointer` — dock이 `.right`면 x를 끌고 `resizeTabPanes`로 전 탭 pane을 다시 재운다). **셋을 각각 물어야 하는 것 자체가 상태를 드러낸다** — "지금 폭을 끄는 중인가"의 단일 출처가 없고 capture 권위가 `InteractionState`와 `PointerGestureOwner`의 두 variant로 갈려 있다([Chrome 상호작용 이관](chrome-interaction-migration.md) CIM2가 그 통합을 소유한다). 실측으로 그 상태의 2만 줄 랩 문서가 프레임당 **60.9ms**였다(ReleaseFast — 약 16fps). **그 구간은 §2.1이 같은 절에서 규정한 "저하 동작"으로 닫았다**: 그 드래그가 활성인 동안 계수를 보류하고 직전 결과로 그린다(`frame.RowCache.hold` — 조건은 제품의 `widthDragActive`가 정한다). 60.9ms → 0.2ms이고, 대가는 드래그 중 막대 길이가 옛 폭 기준인 것이다. **줄 배열이 그대로일 때만 저하한다** — 저하가 겨냥한 것은 폭 변경이고, 줄이 바뀐 상태에서 옛 접두합을 쓰면 그것은 "직전 결과"가 아니라 다른 문서의 값이다.

**이 선택의 베이스.** 저하 동작도 "드래그 중인지 명시적으로 묻는 방식"도 이 문서가 지어낸 것이 아니라 선례가 있다.

- **부정확한 값으로 계속 그린다** — [xi-editor #610](https://github.com/xi-editor/xi-editor/issues/610)이 같은 문제(*"incremental computation is not always possible … when changing the wrap width"*)를 다루며 async로 가고, 그동안 *"for pending chunks, the breaks are not necessarily accurate … in these intermediate states, the document is still rendered, and interaction is still possible"*라고 적었다. 동기도 같다 — *"this is all motivated by drag-resizing of the window."* §2.1의 "저하 동작을 허용한다"가 그것과 같은 결론이다.
- **드래그 중인지 상태로 묻는다** — Apple의 live resize 권고가 [`inLiveResize`](https://developer.apple.com/documentation/appkit/nsview/inliveresize)를 검사해 비싼 계산을 건너뛰고 [`viewDidEndLiveResize`](https://developer.apple.com/documentation/appkit/nsview/1483543-viewdidendliveresize)에서 수행하라고 한다(캐시 준비는 `viewWillStartLiveResize`). `widthDragActive` + `RowCache.hold`가 그 구조이고, 이 저장소의 `windowDidResize` 보류도 같은 패턴이다.

**택하지 않은 것과 이유.** "캐시가 직전 프레임 폭을 기억해 변동 중인지 스스로 판정"하는 방식도 검토했고 **버렸다.** ⑴ 위 두 선례 모두 상태를 명시적으로 알지 추론하지 않는다(async pending 여부 / live resize 플래그). ⑵ 그것은 사실상 1프레임 debounce인데, 웹에서 흔한 debounce는 시간 기반이고 프레임 기반은 **렌더 루프가 계속 돈다는 전제**를 요구한다. 이 루프에는 idle skip이 있어(§투영 게이트) 드래그를 놓은 뒤 프레임이 한 번 더 온다는 보장이 없고, 그러면 손을 뗐는데도 막대가 옛 폭 기준으로 남는다. ⑶ 저하 중에는 캐시 키를 갱신하지 않으므로 "직전 폭"을 키와 별개 필드로 들어야 하고, 안 그러면 한 번 저하한 뒤 영영 miss로 남아 절대 정확해지지 않는다.

**남은 것은 "드래그를 놓는 순간의 한 프레임"이고, 그것은 워커가 아니라 점진 계수로 다룬다**(2026-08-18 사용자 결정). 그때 전 문서를 한 번 세므로 2만 줄에서 ~62ms가 한 번 튄다(창 리사이즈도 같은 자리에서 한 번 든다). 이 표의 다른 "분리" 항목과 달리 여기를 **메인에 두는 이유**는 셋이다.

1. **작업의 성질이 다르다.** 랩 계수는 **줄마다 독립**이라 프레임당 N줄씩 나눠 세면 각 프레임이 예산 안에 들어온다. ~~구문 트리 파싱은 그렇지 않다 — 나눌 지점이 없어서 분리가 유일한 답이다.~~ **2026-08-29에 이 문장이 틀린 것을 확인했다**(§2.1a) — tree-sitter가 파싱을 끊고 재개하는 API를 준다. 두 작업은 이제 **같은 칸**이고, 랩 계수를 메인에 둔 나머지 근거(둘·셋)가 파싱에도 그대로 적용된다.
2. **스레딩의 유지보수 비용이 이득보다 크다.** 워커를 놓으면 스냅샷 수명(줄 배열은 문서 버퍼를 빌린다), revision 폐기, 취소, 콜백 재진입이 전부 따라온다 — 이 저장소의 session host 스레딩이 그 비용을 이미 보여 준다. 반면 점진 계수가 더하는 상태는 **"어디까지 셌나" 인덱스 하나**이고 단일 스레드라 테스트가 결정적이다.
3. **저하 동작이 이미 서 있다.** 아직 다 세지 못한 동안 무엇을 그릴지는 §2.1이 이미 규정했고(*"랩은 직전 결과를 쓴다"*) 그 자리가 구현돼 있다(`RowCache.hold`). 점진 계수는 그 위에 얹힌다.

**가로 축(가장 긴 줄 세기)은 점진으로 나누지 않는다**(2026-08-18 결정). `ensureMaxCols`는 같은 부류의 전 문서 훑기이고 여는 경로에 붙어 있지만, 나누면 **화면이 깨진다** — `content_max_cols`가 아직 `null`인 동안 가로 막대를 아예 안 그리는데 그 막대는 본문 아래 여백에서 **자리를 먹으므로**(§4.1a) 생겼다 사라지면 본문 높이가 출렁인다. 세로 막대가 "안 센 줄은 한 행"으로 짧게라도 그려지는 것과 다르다.

**그대로 두는 근거는 절대값이다.** 실측(ReleaseFast, 단계마다 직접)으로 2만 줄(2.1MB)에서 읽기+파싱 3ms, 줄 배열 ~0ms, 이 셈이 **24ms**다 — **"읽기에 묻힌다"는 근거는 성립하지 않는다**(그렇게 짐작했다가 재 보고 틀린 것을 확인했다. 읽기의 8배다). 읽기 값은 하니스가 방금 쓴 파일을 읽어 페이지 캐시가 따뜻하므로 **하한**이지만, 그 값이 커져도 이 셈이 사라지지는 않는다. 남는 근거는 25ms가 한 번 툭 끊기는 정도라는 것뿐이며, 그 값이 커지면 위의 "잠정 막대" 문제를 풀고 점진으로 가야 한다. 셈 자체의 상한(`max_cols_count_limit`)은 이미 있어 **긴 줄**은 방어돼 있고, 남은 것은 **줄 수**에 비례하는 몫이다.

~~**이 판단은 랩 계수에 한정된다.** N2와 tree-sitter가 오면 파싱은 위 표대로 **분리**해야 하고, 그때 워커 경로가 선다.~~ **2026-08-29에 뒤집혔다** — 파싱도 같은 점진 장치로 간다(§2.1a). 워커 경로는 이 문서의 어느 항목도 아직 요구하지 않는다(검색·파일 I/O·LSP는 각자 다른 이유로 분리이고, 그것들은 애초에 프로세스·syscall 경계다).

**워커에는 스냅샷을 넘긴다.** §3.0이 고를 버퍼는 **persistent/copy-on-write인 것이 요구**이므로(rope든 아니든 — §3.0이 그 성질을 **요구**로 둔다) **메인은 옛 스냅샷으로 계속 그리면서** 워커가 새 결과를 만들 수 있다 — Zed가 tree-sitter 백그라운드 파싱을 지탱하는 방식과 같고, **이것이 §3.0이 persistent를 **요구**로 둔 두 번째 이유다**(첫째는 §3.0의 편집 복잡도).

**결과는 메인에서만 반영한다.** 워커가 L2 모델을 직접 mutate하지 않고 결과를 메인에 넘겨 적용하며, 그 사이 문서가 바뀌었으면 revision으로 폐기한다(§3.6과 같은 축). 이 규칙이 없으면 버퍼를 여러 스레드가 동시에 건드리게 되고, 그것은 이 문서가 요구하는 자료구조가 아니다.

**저하 동작을 허용한다.** 분리한 결과가 아직 안 왔으면 그 프레임은 **없는 대로 그린다** — 미니맵은 비어 있고, 랩은 직전 결과를 쓰고, 검색은 진행 중으로 표시한다. 결과를 기다리며 프레임을 멈추지 않는다.

### 2.1a 구문 파싱은 끊고 재개한다 — 워커가 아니다 (2026-08-29)

**§2.1이 파싱을 "분리"로 보낸 근거는 틀렸다.** 그 근거는 *"트리는 언제나 문서 전체이고 뷰포트 한정
파싱이 없어서 **나눌 지점이 없다**"* 였는데, 우리가 링크하는 tree-sitter가 그 지점을 준다:

```c
typedef struct TSParseOptions {
  void *payload;
  bool (*progress_callback)(TSParseState *state);   // true 를 돌려주면 파싱이 끊긴다
} TSParseOptions;

TSTree *ts_parser_parse_with_options(TSParser *, const TSTree *old_tree, TSInput, TSParseOptions);
```

그리고 `ts_parser_reset`의 계약이 재개를 명시한다 — *"파서가 progress callback 때문에 실패했다면,
기본적으로 다음 호출에서 **멈춘 자리부터 재개한다**"*. 즉 한 번의 파싱을 **프레임에 걸쳐 나눌 수
있다**. 뷰포트 한정 파싱이 없다는 것은 여전히 사실이지만, 그것과 "나눌 수 없다"는 다른 말이었다.

#### 왜 크기로 가르면 안 되는가 — 실측

`ReleaseFast`, 191KB 합성 Zig 소스(`pub fn f() void { const s = "abc"; _ = s; } // c` 4,000줄):

| 작업 | 시간 | 전체 파싱 대비 |
|---|---|---|
| 한 글자 편집 | **1.2ms** | 8% |
| 문서 절반 교체 | **9.7ms** | **65%** |
| 전체 파싱 | 15ms | 100% |

**둘이 드러났다.**

1. **큰 편집은 사실상 전체 파싱이다**(65%). "증분이니까 싸다"는 편집이 작을 때만 참이다.
2. **작은 편집도 항상 싸지는 않다.** 한 글자에 1.2ms인데, §5.3이 실제 Zig 파일 154KB에서 잰 값은
   **65µs**다 — **20배** 차이다. 위 합성 소스가 바이트당 구문 노드가 훨씬 조밀해서다. 즉 **비용이
   내용에 달렸고 크기로 예측되지 않는다**.

⑵가 설계를 정한다. 경로로 갈라도(`open` 대 `onEdit`) 크기로 갈라도 **빗나간다**. 가를 기준은 **실제로
쓴 시간**이고, 그것을 아는 유일한 자리가 progress callback이다.

#### 구현 뒤 실측 — 예산이 실제로 지켜진다 (2026-08-29)

위 표는 합성 소스였다. **실제 파일**로 다시 쟀다(`ReleaseFast`, 이 저장소의 `build.zig` 675KB):

| 항목 | 값 |
|---|---|
| 한 번에 파싱 | **22.5ms** — 프레임 예산 16.7ms를 넘는다(이 장치가 필요한 이유) |
| 예산 4ms로 나눔 | **6라운드** · 합 23.1ms |
| 최대 라운드 | **4.007ms** — 초과 **7µs** |
| 나누는 비용 | 563µs (**2.5%**) |

**초과가 7µs라는 것이 이 설계의 실효를 정한다.** progress callback을 파서가 촘촘히 부르므로 예산이
사실상 정확히 지켜진다 — 이 값이 크면 "예산"이라는 말이 무의미해진다. 나누는 대가는 2.5%이고,
675KB 문서가 여섯 프레임(60fps에서 ~100ms) 안에 색을 얻는다.

**앞서 이 자리를 `~50ms`로 추정했던 것은 틀렸다** — 합성 소스의 노드 밀도로 외삽한 값이었다. 실제는
22.5ms다. 결론(프레임 예산 초과)은 그대로지만, **추정으로 적은 수치는 근거가 못 된다**.

#### 계약

- 파싱은 **프레임 예산**을 들고 들어간다. 예산이 차면 콜백이 끊고, 다음 프레임에 재개한다.
- 아직 새 트리가 없으면 **직전 트리로 그린다**. 없으면 무색이다 — §5의 *"grammar가 없으면 무색"*과
  같은 저하이고, 랩 계수의 *"직전 결과를 쓴다"*와 같은 규율이다.
- 재개 도중 **문서가 바뀌면 `ts_parser_reset`** 하고 새 내용으로 다시 시작한다. 반쯤 판 트리를 다른
  문서에 이어 붙이지 않는다.
- **조회(`spansForRange`)는 지금처럼 메인에서 즉시** 한다(위 표) — 뷰포트에 비례하고 예산 안이다.

#### 워커를 안 쓰는 이유 — 랩 계수와 같다

§2.1이 랩 계수에서 든 근거 둘·셋이 그대로 적용된다. 워커를 놓으면 **스냅샷 수명·revision 폐기·취소·
콜백 재진입**이 따라오고, 점진이 더하는 상태는 **"어디까지 팠나"** 하나이며 단일 스레드라 테스트가
결정적이다.

거기에 이 자리만의 이유가 하나 더 있다. **스레드 분리는 persistent 스냅샷을 전제로 하는데**(위 *"워커에는
스냅샷을 넘긴다"* · [문서 모델](native-editor-document-model.md) §3.0) 그 버퍼는 아직 없다. 지금 워커로
가면 **바이트를 통째로 복사해 넘기는 임시 구조물**(상한 4MiB)을 세워야 하고, 그것은 §3.0이 서면 걷어낼
것이다. 점진은 그 전제가 **아예 필요 없다** — 메인에 있으므로 파싱 중 버퍼가 바뀌지 않는다.

**그리고 트리를 스레드 사이로 넘기는 것 자체가 계약을 요구한다.** `api.h`가 못박는다 — *"syntax trees
are not thread safe"*, 여러 스레드가 동시에 쓰려면 `ts_tree_copy`가 필요하다. 증분은 **옛 트리를 입력으로
받는데** 그 트리를 메인이 매 프레임 조회에 쓰므로, 워커 설계에서는 편집마다 복사가 끼어든다. 점진에서는
그 지점이 생기지 않는다.

#### 선례

- **Neovim**이 같은 방식이다(메인 루프에서 시간 예산으로 끊는 파싱).
- **Zed·Xi**는 워커로 가지만 **둘 다 persistent rope가 먼저 있다** — 우리가 아직 갖지 못한 전제다.
- **Helix·Emacs**는 동기 파싱이다. tree-sitter가 충분히 빠르다는 쪽에 건 선택이고, 위 실측이 보여 주듯
  내용이 조밀하면 그 전제가 무너진다.

### 2.2 상태바에 내보내는 값

하단 상태표시줄의 **항목 배치·폭 부족 시 버리는 순서·렌더는 [status-bar.md](status-bar.md)가 소유한다.** 이 문서는 편집기가 **무엇을 제공하는가**만 정한다.

| 값 | 출처 | 비고 |
|---|---|---|
| 커서 위치 (줄:열) | primary selection(§3.2) | 열의 정의는 아래. **구현됨**(2026-08-21) |
| 선택 크기 | selection 배열 | 하나면 문자·줄 수, 여럿이면 **커서 개수** |
| 인코딩·줄바꿈 | §3.5 | `UTF-8` · `LF`/`CRLF` |
| 들여쓰기 | §9 설정 | 탭 폭 |
| 언어 | [문서 모델](native-editor-document-model.md) §3.7a 언어 판정 | 없으면 표시하지 않는다. **판정은 섰지만 칸이 아직 없다** — 아래 |
| 읽기 전용 | §3.5 | 편집이 막혀 있음을 알린다 — **그 문서가 실제로 읽기 전용일 때만** 뜬다 |
| **저하 상태** | §3.0·§2.1 | 아래 |

**「읽기 전용」은 상시 자리가 아니다(2026-09-03 정정).** 이 표는 오래 *"편집이 막혀 있음을 알리는
유일한 **상시** 자리"* 라고 적었고 구현도 **조건 없이** 그렸다 — N1 편집기가 전부 읽기 전용이던
시절의 문장이다. **N2 가 편집을 세우면서(2026-08-25 — 타이핑·저장·undo) 그 문장이 거짓이 됐고**,
사용자는 **글자가 들어가는 편집기 옆에서 「읽기 전용」을 읽는다**. 그 항목의 존재 이유가 *"사용자는
「왜 안 써지지」를 묻는다"* 인데, 지금은 정확히 반대로 오해를 만든다.

**그래서 조건은 문서의 `read_only` 다** — 열 때 쓰기 권한이 없으면 참이고(`isWritable`), 그때만 뜬다.
값이 늘 같지 않으므로 **폭을 다투는 띠에서 자리를 상시 먹지도 않는다**(같은 절이 인코딩 칸을 뺀 것과
같은 근거: *"변하지 않는 값은 자리만 먹는다"*).

**이 결함은 캡처가 잡았다.** 판정자는 상태바 항목이 **있는지**만 재고 그것이 **참인지**는 안 쟀다 —
줄 조작·대소문자 슬라이스(#3126·#3143)의 화면을 찍고 나서야, 탭에 dirty 점이 뜬 채로 「읽기 전용」이
함께 떠 있는 것이 보였다.

**언어 칸은 아직 배치되지 않았다(2026-08-27).** 판정(§3.7a)은 `language.zig`로 섰고 주석 토글이 그것을 쓰지만, 배치를 소유하는 [status-bar.md](status-bar.md)에는 언어 항목이 없다 — 이 표가 *"제공한다"*고 적은 값 중 **받는 쪽이 없는 유일한 항목**이다. 칸을 만들 때 폭 부족 시 버리는 순서를 함께 정해야 하므로 그 문서에서 결정한다.

**열은 그래핌 클러스터 기준 1-based로 센다.** byte offset은 내부 축이고(§3.1) 사람이 읽는 값이 아니다. **탭은 탭스톱까지의 폭이 아니라 문자 하나로 센다** — 상태바의 열은 "몇 번째 글자인가"를 답하는 값이지 화면 위치가 아니며, 화면 위치는 caret이 이미 보여준다. **가상 텍스트(인레이 힌트·ghost text)는 세지 않는다**(문서에 없는 글자다, §4).

**줄 끝을 넘지 않는다.** CRLF 줄에서 CR을 한 글자로 세면 **줄에 있는 글자 수보다 큰 열**이 나온다(글자 셋인 줄에서 `1:5`). 줄 끝 문자 앞에서 묶는다 — `line_index`가 같은 clamp를 같은 이유로 지킨다.

**세는 데에 상한을 둔다: 14,096.** 상태바는 **프레임마다 다시 조립되고** 열은 줄 머리부터 세므로, 긴 줄 끝에 caret이 있으면 그 길이에 비례하는 일이 렌더 루프에 들어온다 — 1MB 한 줄에서 ASCII 기준 프레임당 6.5~9.5ms(ReleaseFast, 부하 있는 머신에서 잰 상한값)로 60fps 예산의 절반쯤이다. 더블·트리플 클릭 한 번이면 focus가 줄 끝으로 가므로 도달도 쉽다.

값은 렌더의 `max_cols_count_limit`을 따른다. **가로 스크롤 상한(`max_first_col` = 10,000)이 아니다** — 그건 *가장 왼쪽* 열의 한계라 최대로 밀어도 화면 오른쪽 끝은 그보다 `보이는 열`만큼 더 가고, 그 글자는 **실제로 보이고 클릭도 된다**. 그 값으로 묶으면 상태바가 눈에 보이는 caret을 못 세면서 `+`로 "그 너머는 볼 수 없다"는 거짓을 말한다. 그리고 **단위가 같지도 않다** — 렌더의 열은 탭을 탭스톱까지·전각을 두 칸으로 세고 이 값은 클러스터를 센다. 클러스터 수 ≤ 열 수이므로 열 상한을 클러스터 상한으로 쓰면 보수적인 방향으로만 어긋난다.

넘으면 `14097+`처럼 `+`를 붙여 **세기를 멈췄다는 사실을 숨기지 않는다**(§3.0의 저하 표시와 같은 규율). 정확한 값이 필요해지면 그때는 이 셈이 아니라 캐시된 줄별 클러스터 색인이 답이다.

**자리는 우측이다.** [status-bar.md](status-bar.md)가 *"부딪히면 우측을 먼저 지킨다 — 우측 항목(개수·상태값)은 폭이 작고 고정적이라 잘리면 의미가 사라지는 반면, 좌측(경로·브랜치)은 길어서 부딪히는 원인 자체가 대개 좌측"*이라고 정했고, 편집기 항목은 전부 짧고 고정적인 상태값이라 그 성격에 맞는다. VSCode도 줄:열·인코딩·줄바꿈·언어를 우측에 두고 좌측은 브랜치·진단 개수를 쓰므로 **§1.1 기준과도 어긋나지 않는다.**

**활성 pane이 편집기일 때만 나타난다.** 상태바는 **창 전폭 띠**라 항상 떠 있으면 터미널을 쓰는 동안에도 기존 항목(브랜치·cwd·에이전트 수)을 밀어낸다 — `status-bar.md`의 "폭이 부족하면 뒤쪽부터 통째로 버린다" 규칙 아래에서는 **밀려난 항목이 사라진다는 뜻**이다. 편집기 항목은 조건부이며, 터미널 pane이 활성이면 하나도 내보내지 않는다.

**`ItemId` 확장이 필요하다.** 그 enum은 닫힌 목록(`git_branch`·`cwd`·`running_agents`·`notifications`·`blocked_agents`)이라 편집기 항목마다 값을 더해야 하고, **더하는 순서가 곧 폭 부족 시 버려지는 순서**다. 위 표의 항목을 한꺼번에 다 더하지 않고 **읽기 단계에 커서 위치 → 편집 단계에 선택 크기 → 이후 나머지** 순으로 넣는다(슬라이스 배정은 [네이티브 편집기 구현 계획](plans/native-editor.md)).

> **항목을 더할 때 우측 배열 상한도 함께 올린다.** 안 올리면 마지막 후보가 **폭과 무관하게** 빠지는데, 화면만 봐서는 폭 부족과 구분되지 않는다(커서 위치를 더했을 때 리소스가 폭 2,500px를 남기고 사라졌다). 상한은 `status_bar.right_candidates` 원장 길이에서 되짚어 comptime에 묶여 있다.

**저하 상태를 여기서 알린다.** §3.0의 큰 파일 기능 축소(미니맵·랩·구문 파싱이 꺼짐)와 §2.1의 "결과가 아직 없어 없는 대로 그림"은 §10.1이 관측 가능해야 한다고 요구하는데, **사용자에게 보이는 자리가 상태바다.** 조용히 줄어들면 사용자는 버그로 읽는다. `status-bar.md`의 "폭이 부족하면 뒤쪽부터 버린다" 규칙에서 **이 항목은 앞쪽에 둔다** — 평소에는 비어 있다가 축소가 일어났을 때만 나타나므로 자리를 상시 점유하지 않는다.

### 2.3 파일 Term의 탭 이름은 편집 대상이 아니다

**현행 코드는 `Term` 이름 편집을 지원한다** — `RenameTarget` union에 `term: *Term` arm이 있고, FP16으로 파일이 `Term`이 되면서 **파일 탭도 그 대상에 들어간다.** [file-panel.md](file-panel.md) §1이 "파일 탭 계약은 터미널 탭의 기존 pane 탭바 계약을 그대로 쓴다"고 정했으므로 현재 예외가 없다.

**파일 Term은 이 대상에서 제외한다.** 근거 둘:

- **파일명이 정본이다.** 임의 라벨을 붙이면 탭 목록에서 어느 파일인지 알 수 없다. 헤더 밴드의 breadcrumb가 경로를 보여주지만 그것은 **활성 탭 하나**뿐이라 탭 스트립의 식별 기능을 대신하지 못한다. VSCode도 탭 이름 편집을 제공하지 않는다(§1.1 기준과 정합).
- **더 위험한 것은 착각이다.** 같은 앱에 **디스크 파일을 실제로 rename하는 기능**이 이미 있다(`F2` — file tree inline rename, `RenameTarget.file_tree`). 탭에서 이름을 바꿀 수 있으면 사용자는 **파일 이름을 바꿨다고 믿는데 디스크는 그대로**다. 한 단어가 두 가지 다른 일을 하는 상태를 만들지 않는다.

**터미널 Term의 rename은 그대로 둔다** — 거기서는 탭 라벨이 정본이고 바꿀 파일명이 없다. 즉 이 제외는 kind별 분기이지 기능 제거가 아니다.

**열린 파일의 이름을 바꾸고 싶으면 탐색기 rename을 쓴다.** 그 경로는 [file-panel.md](file-panel.md) §1이 이미 계약했다(신뢰 kind·kind 유지면 surface를 유지하고 `entry.path`만 교체, kind가 바뀌면 Term 재생성).

### 2.4 같은 파일을 두 곳에서 본다 (2026-08-09 사용자 결정)

긴 파일의 위아래를 나란히 보는 것은 코드 편집의 일상 동작이다(§1.1 기준). **네이티브 이관이 그 장벽을 없앤다** — [editor-surface.md](editor-surface.md) §4가 막은 이유는 *"native가 전체 text 정본을 보유하지 않는 v1에서는… 두 page의 editable model 실시간 동기화는 native canonical text 또는 CRDT/OT가 필요"*였고, §2·§3.0이 정확히 그 **native canonical text**를 만든다. 웹 시절엔 WKWebView마다 자기 CM6 문서를 가져 생긴 제약이었다.

**불변식을 폐기하는 것이 아니라 명시적 예외를 만든다.**

| 경로 | 동작 |
|---|---|
| 탐색기·`⌘O`·정의로 이동(§5.2) 등 **경로로 열기** | **기존 Term 활성화** — [file-panel.md](file-panel.md) §1의 "파일 1개 = 창당 Term 1개"가 그대로 산다 |
| **"나눠서 보기" 명시 명령** | 같은 문서를 보는 **두 번째 Term 생성** |

**뷰가 여럿일 때의 규칙**(불변식을 푸는 순간 1:1이던 것이 1:N이 되므로 명시한다):

- **"기존 Term 활성화"의 대상은 가장 최근에 활성이었던 뷰다.** 여럿 중 임의로 고르면 사용자가 방금 보던 곳이 아닌 데로 튄다. §5.2의 "이미 열려 있으면 활성화"도 같은 규칙을 쓴다.
- **뷰는 한 창 안에 머문다.** [file-panel.md](file-panel.md) §1의 유일성이 원래 **창 전체** 불변식이었으므로, 이 예외도 그 범위를 넘지 않는다 — 다른 창에서 같은 파일을 열면 그 창의 Term이 따로 선다(문서 identity를 창 위에서 묶는 것은 [editor-surface.md](editor-surface.md) §4의 app-global `DocumentRegistry` 몫이고, 이 규칙은 **뷰**의 배치에 관한 것이다).
- **rename은 모든 뷰의 경로를 함께 갱신한다.** [file-panel.md](file-panel.md) §1의 rename 계약(신뢰 kind·kind 유지면 `entry.path`만 교체)이 이제 **1:N 갱신**이다. 한 뷰만 갱신하면 나머지가 옛 경로를 가리켜 저장 대상이 갈린다.
- **경로 → Term 조회가 1:N이 된다.** 그 조회를 쓰는 곳(열기 중복 판정·rename remap)은 전부 목록을 받도록 바꾼다 — "하나를 반환한다"는 전제가 남아 있으면 두 번째 뷰가 조용히 무시된다.
- **창 간 워크스페이스 이동과 구분한다.** [file-panel.md](file-panel.md) §1에는 워크스페이스를 다른 창으로 옮길 때 *"대상 창이 이미 같은 경로를 열어 두었으면"*을 처리하는 규칙이 따로 있는데, **그것은 우연한 중복이고 이 절의 예외는 명시 요청**이다. 둘을 같은 것으로 보면 창을 옮겼다는 이유로 사용자가 만들지 않은 두 번째 뷰가 생긴다. 그 규칙의 갱신 여부는 [file-panel.md](file-panel.md)가 판단하며, 이 문서는 **두 상황이 다르다는 것**만 못박는다.

**무엇을 공유하고 무엇이 독립인가**:

- **공유(문서가 하나다)**: 버퍼·undo/redo 스택·revision·**dirty**. 한쪽에서 편집하면 다른 쪽에 즉시 보이고, 어느 Term에서 저장해도 같은 문서가 저장된다. dirty 표시는 두 탭에 함께 뜬다.
- **독립(뷰 상태다)**: selection·caret·**열 선택 원본**·스크롤·랩 토글·접힘 상태.
- **닫기**: 뷰 하나를 닫아도 다른 뷰가 남아 있으면 문서는 살아 있으므로 **dirty 확인을 하지 않는다.** 마지막 뷰를 닫을 때만 [file-panel.md](file-panel.md)의 dirty 게이트가 걸린다.
- **소유자**: 경로 → 문서 하나의 매핑은 [editor-surface.md](editor-surface.md) §4의 **app-global `DocumentRegistry`**가 이미 그 자리다("여러 창이 같은 파일을 열 때 identity를 하나로 묶는 건 창 위 계층이어야 한다"). 이 결정은 그 설계와 새로 충돌하지 않는다.

**[file-panel.md](file-panel.md)가 불변식 문구를 갱신해야 한다** — 그 문서가 소유자이고, "다시 열면 기존 Term 활성화"는 유지하되 명시 명령의 예외를 적는다.
