# 에이전트 활동 뷰 — 구현 계획

계약은 [에이전트 활동 뷰](../agent-activity-view.md)다. 이미지 종류의 계약은
[에이전트 이미지 갤러리](../agent-image-gallery.md)가 계속 소유한다.

## 1. 슬라이스 개요

| 슬라이스 | 내용 | 상태 |
| --- | --- | --- |
| **AV1-a** | 인덱스에 도구 호출을 더한다(마커·활동 축·종류별 상한) + 스캔 비용 실측 | ✅ 완료 |
| **AV1-b** | 그 인덱스를 **줄 목록으로 그린다**(대상 한 줄) + 종류 필터 최소 형태 | ✅ 완료 |
| **AV2** | 호출↔결과를 잇고 줄 오른쪽에 **결과 요약** | ✅ 2026-09-07 — §3 |
| **AV2b** | 넷째 칸 **시각**(계약 §2.2) — provider 마다 반대편이라 자리를 따로 잰다 | ✅ 2026-09-07 — §3.2 |
| **AV3** | 눌러서 **펼침** — 명령 전문 + 결과 전문 + 상한 | ✅ 2026-09-08 — §4.1 |
| **AV4** | **종류 필터 칩** — 안내 줄 아래 전용 줄, `Tab` 제거 | ✅ 2026-09-08 — §5 |
| **AV4b** | **「전체」의 중복 접기**(§2.2.1) — 결과가 이미지인 호출은 한 줄 | ✅ 2026-09-08 — §5.1 |
| **AV5** | 「전체」의 접힌 줄에 **썸네일** — 줄 높이에 맞춘 작은 그림 | ✅ 2026-09-08 — §6.1 |
| **AV6** | 개명 `image_gallery` → **`agent_activity`** | ✅ 2026-09-08 — §7.1 |

**순서의 근거는 갤러리 계획의 적대적 검토 P1과 같다** — 순수 모듈을 먼저 여러 PR로 내면 소비자 없는
코드가 쌓이고 첫 사용자 가시 결과가 늦어진다. 그래서 AV1이 스캐너부터 화면까지 **세로로** 뚫는다.

### 1.1 AV6(개명)을 마지막에 두는 이유

이름이 거짓인 채로 코드가 쌓이는 것은 나쁘다. 그런데 개명을 먼저 하면 **AV1~AV5 전부가 개명 뒤
좌표로 쓰여** 리베이스 충돌 면적이 최대가 된다 — `app_session.zig` 는 이 저장소에서 가장 자주
충돌하는 두 파일 중 하나다([project-rules](../project-rules.md) 리베이스 절). 개명은 기계적이라
**나중에 해도 값이 안 변하는 유일한 슬라이스**이므로 뒤로 민다.

⚠️ 그때까지 문서와 코드의 이름이 다르다. 계약 §7이 그것을 「남은 결정」으로 들고 있는 것이 그
불일치의 표식이다 — 감추지 않는다.

## 2. AV1 — 인덱스 확장과 첫 목록

**바꾸는 것**

- `session/agent_image_index.zig`: `Kind` 에 도구 호출 종류를 더하고 마커를 넷 더한다
  (`"type":"tool_use"` · `"type":"tool_result"` · `"custom_tool_call"` · `"function_call"`).
  `Hit` 의 `data_offset`/`data_len` 은 **대상 문자열의 자리**를 가리킨다(이미지는 base64 자리를 가리킨다 —
  «그 종류에서 본체가 되는 바이트» 라는 뜻으로 이미 일반적이다).
- 도크 뷰: 이미지가 아닌 `Hit` 은 격자가 아니라 **줄**로 그린다. 이 슬라이스에서는 필터가 없으므로
  **시간순 역순 한 목록**이다.

**측정(계약 §4.1이 비워 둔 자리)**

마커 추가 전후로 **제품 스캐너**의 같은 파일 스캔 시간을 잰다. Python 추정으로 대신하지 않는다 —
갤러리에서 그 추정이 5배 틀렸다(0.7초 추정 / 3.6초 실측).

| 재는 것 | 대상 |
| --- | --- |
| 전형 파일 | Claude 중앙 1.3 MB · Codex 2.7 MB |
| 최악 | 이 맥의 최대 rollout |
| 항목 수가 가장 많은 파일 | 도구 호출 12,200개짜리 Claude 세션 |

**대상 문자열은 우선순위로 고른다**(계약 §2.2, 적대적 A2): `description` → `file_path` → 명령 첫 줄.
초안의 「명령 첫 줄」 하나로는 **52.4%(여러 줄)** 와 **27.4%(상한 초과)** 에서 껍데기가 뜬다.

**라벨은 스캔 때 전부 만든다**(계약 §4.2, 적대적 A2). 검색이 전량을 요구하기 때문이고, 고정 160 B라
12,200개라도 2.3 MB다. AV1 에서 **가장 큰 세션의 실제 상주 메모리를 잰다** — 계산과 실측이 갈리면
그 자리가 이 슬라이스의 결함이다.

**완료 조건**: CI — 마커 파싱 단위 테스트(두 provider 구조, `compacted` 제외가 활동에도 걸리는지,
공백 없는 JSON 가정, **대상 우선순위 셋과 셋 다 없는 줄**). 수동 — 헤드리스 캡처로 목록이 실제로 뜨는 것.

### AV1-a 가 실제로 찾은 것 (2026-09-07)

계획에 없던 결함 둘을 구현 중에 만났다. 둘 다 **적대적 검증이 못 본 것**이다 — A2 가 「규모」를 봤지만
그것은 «메모리와 라벨» 축이었고, 아래는 «상한»과 «파싱 비용» 축이다.

| 찾은 것 | 왜 위험한가 | 반영 |
| --- | --- | --- |
| **인덱스 상한을 활동이 잡아먹는다** | `max_hits_per_file` 이 4,096 인데 활동은 세션당 12,200개다. 한 통으로 세면 활동이 많은 파일에서 **이미지가 밀려나** 갤러리가 「이미지가 없습니다」로 빈다 — 고장과 구분되지 않는다 | 종류별 상한(`max_activity_hits_per_file` = 16,384)으로 가르고, 판정자와 뮤테이션으로 못박았다 |
| **값 끝을 찾느라 23 KB 를 훑는다** | 명령은 최대 23,866 B 인데 라벨은 160 B 다. 아무도 안 쓰는 값을 위해 스캔이 몇 배가 된다 | `max_target_scan_bytes`(512 B) 상한. `data_len` 의 의미를 「대상의 길이」에서 「시작 자리 + 라벨에 쓸 만큼」으로 못박았다(계약 §4.1) |

**갤러리 판정자 하나가 깨졌다 — 제품이 아니라 판정자가.** 「검색이 켜진 채 자동 갱신이 와도 앞뒤가
맞는다」가 `all_hits.items.len < 2` 로 「두 장이 왔나」를 기다렸는데, 그 fixture 가 `tool_use` +
`tool_result` 짝이라 **활동 `Hit` 이 그 수를 미리 채워** 갱신을 안 기다리고 빠져나갔다. 인덱스가 이제
두 축을 담으므로 **「몇 개인가」를 셀 때는 축을 말해야 한다**(`activityImageHits`). 다른 갤러리 판정자
38 개는 fixture 에 도구 호출이 없어 안 걸렸다 — 즉 이 함정은 조용하다.

**검증에서도 하나 배웠다.** 「Codex 결과 레코드에는 안 걸린다」 판정자가 뮤테이션(마커에서 닫는 따옴표
제거)을 **못 잡았다** — 실제로 막고 있던 것은 마커가 아니라 「결과 레코드에 `name` 이 없다」는 성질
(실측 3,966 / 3,966)이었기 때문이다. 방어가 둘이면 각각 시험해야 한다는 것이고, 마커 자신을 보는
판정자를 따로 뒀다.

### AV1-b 가 실제로 한 것과 미룬 것 (2026-09-07)

**한 것**: `context.activityLabel`(대상 바이트 → 사람이 읽는 한 줄, `writeText` 재사용), 스캔 워커의
활동 라벨 경로(`readActivityLabel` — 이미지와 달리 **앞선 줄을 뒤질 필요가 없다**), `Filter`
(images·reads·execs·all)와 `Filter.admits` 단일 판정, 줄 목록 렌더(`collectActivityList`),
그리고 활동 필터에서 「이미지가 없습니다」가 뜨던 **거짓 문구**를 `agent_activity_none_of_kind` 로 가른 것.

**필터 전환은 `Tab` 이고 임시다.** 계약 §8 이 「필터 UI 의 자리」를 남은 결정으로 들고 있어, 그것이
정해지기 전까지 결과를 만져 볼 길로 둔다. 갤러리가 키를 쥐고 있을 때만 가져가므로 터미널의 Tab 은
그대로다. **AV4 가 이것을 대체한다.**

**미룬 것 — 자리를 잡아 두지 않는다.** 시각과 결과 요약은 AV2, 펼침은 AV3 다. 없는 것을 위해 빈 띠를
남기면 「없다」와 「아직 안 붙였다」가 섞인다. 특히 **시각을 이미지 경로로 재사용하지 않았다**: 활동
레코드에서 timestamp 의 자리를 확인하지 않은 채 같은 코드를 쓰면 **남의 시각**이 붙는다.

**판정자가 두 번 성급했다.** ⑴ 필터를 바꾸면 `rebuildFilter` 가 타일을 버리므로(인덱스 도메인이 새로
만들어진다) 되돌린 직후에는 픽셀이 없다 — 워커 왕복을 기다리지 않으면 「그림이 안 실린다」를 결함이
아니라 타이밍으로 보게 된다. ⑵ AV1-a 에서 겪은 것과 같은 축이다(`all_hits` 로 세기).

**실사용에서 무엇이 깨지는가**를 봤다.

| --- | --- | --- | --- |
| **B1** | 합성 fixture 로만 시험했다 | **Codex 라벨의 96%(1,756/1,830)가 상한을 꽉 채운 채 잘린다** — 그 세션의 `input` 이 명령이 아니라 `text(await tools.web__run({…}))` 같은 JS 덩어리다. Claude 는 정상(빈 라벨 0·껍데기 0·중앙 23 B) | **안 고침** — 안쪽 의미를 뽑는 것은 계약 §2.3 이 경계한 명령 해석이다. AV3 펼침이 전문을 보이면 실질 해소 |

### 적대적 검증 3회차 — D1~D4 (2026-09-07)

| 회차 | 공격 관점 | 찾은 것 | 처리 |
| --- | --- | --- | --- |
| **D1** | 필터를 `Tab` 에 걸었으니 터미널 키를 뺏는다 | **확정.** `key_focus` 는 도크를 한 번 클릭하면 켜진 채 남는다. 그 상태에서 터미널에 글자를 치면 **문자는 터미널로 가는데 Tab 만 갤러리가 가져간다** — 사용자에게는 자동완성이 죽은 것으로 보인다. ←→ 는 「크게보기가 열렸을 때만」으로 좁혀 뒀는데(그 주석이 이유를 적고 있다) Tab 에는 그 좁힘이 없다 | **사용자가 감수하기로 결정(2026-09-07)** — 대안 셋(안내 줄 클릭 · `Cmd` 조합 · 아예 빼기)을 제시했고 「뺏겨도 된다」는 답이 나왔다. **못 본 결함이 아니라 고른 트레이드오프**다. 제대로 된 필터 UI 는 AV4 |
| **D2** | 손상·극단 입력이 파서를 깨뜨린다 | **조용한 결함.** 「한 줄에 호출 둘」에서 첫 호출의 라벨로 **두 번째 호출의 경로**가 나왔다 — A1 실측(한 줄에 하나)에 코드가 **의존**하고 있었다. 그 밖(잘린 줄·안 닫힌 값·널 바이트·5000자 name·이스케이프된 마커)은 전부 안전 | 레코드 범위 안에서만 값을 찾게 고침 |
| **D3** | 「전체」 필터가 정보를 잃는다 | **확정.** 목록이 라벨 본문만 그려 이미지 줄의 **「첨부 / 읽음」 접두가 사라졌다** — 계약 §2.2.1 이 「화면에 던지는 첫 물음」이라 못박은 정보다 | 격자와 **같은 순수 함수**(`splitLabelRow`)로 자리를 나눠 복원 |
| **D4** | 판정자 자신이 헐겁다 | **확정.** **목록 렌더 함수를 부르는 판정자가 하나도 없었다** — 그림 채널(`appendGpuImages`)만 보고 있었다. 목록은 글자가 전부라 렌더가 죽어도 「활동이 없다」로 보일 뿐이다 | `drawn_rows` 를 남기고 제품 `tick()` 으로 확인. 뮤테이션(렌더를 통째로 죽임)이 `expected 2, found 0` 으로 잡힌다 |

**D2 가 가장 값졌다.** 실측을 근거로 삼는 것과 **실측에 의존하는 것**은 다르다 — 「한 줄에 하나」는
관측이지 계약이 아닌데 코드가 그것에 기대고 있었고, 깨지는 날 **조용히 남의 값을 집는다**. 이제
전제가 참인 동안 비용은 그대로이면서, 전제가 틀려도 각자 제 값을 갖는다.

### 적대적 검증 4회차 — E1~E3 (2026-09-07)

| 회차 | 공격 관점 | 찾은 것 | 처리 |
| --- | --- | --- | --- |
| **E1** | 계약이 말하는 것과 코드가 하는 것이 갈렸다 | **둘.** ⑴ 계약 §2.2 는 3순위를 「명령 **첫 줄**」이라 적었지만 코드는 명령을 **접어서**(줄바꿈→공백) 앞 160 B 를 보인다. ⑵ 그 오해 위에 §5(개인정보)가 「첫 줄만 보이니 긴 명령 뒤쪽 비밀은 화면에 없다」고 적고 있었다 — **보안 판단을 틀리게 만드는 문장**이다 | 계약 두 곳을 고침 |
| **E2** | 되풀이하면 샌다 | **반박됨.** 네 필터를 스무 바퀴(80 전환) 돌리며 tick 을 섞어도 `testing.allocator` 가 누수를 못 잡았고 상태도 그대로였다 | 판정자로 고정 |
| **E3** | 훑는 중에 필터를 바꾸면 옛 필터로 걸러진다 | **반박됨.** 스캔이 끝난 뒤 결과가 **바꾼 필터**를 따른다(인덱스에는 둘 다 담기고 걸러질 뿐) | 판정자로 고정 |

**E1 이 이 회차의 값이다.** 코드가 문서보다 옳았고(첫 줄은 52.4% 가 껍데기다), 문서가 그 사실을
모른 채 **그 위에 보안 결론을 쌓고 있었다**. 드리프트는 「문서가 낡았다」로 끝나지 않는다 — 낡은
문장이 다음 판단의 전제가 된다.

지금 참이고, 이제 그것이 깨지면 CI 가 안다.

### 3.1 AV2 가 실제로 한 것 (2026-09-07)

**요약 칸의 내용을 실측이 바꿨다** — 계약 §2.2 의 표가 그 결정이다(첫 줄은 잡음이라 버리고 «크기 +
실패»만 말한다). 실패의 근거는 **provider 가 적은 것뿐**이다.

**구조** — 링크는 `StreamScanner` 가 든다(줄 사이의 상태라 줄 단위 헬퍼로는 못 잰다).

⚠️ **퇴출과 부딪힌다 — 리베이스에서 잡았다.** 같은 날 main 에 들어간 `evictOldestActivities`(상한을
넘으면 오래된 활동 1/8 을 버린다)는 `out` 을 **제자리 압축**하므로 그 배열을 가리키던 **인덱스를 전부
무효화**한다. 대기 링이 그런 인덱스를 드는 **첫 소비자**라, 그대로 두면 퇴출 뒤에 온 결과가 **남의 줄에
결말을 붙인다**(상한의 11 배가 오는 파일이 실제로 있다). 그래서 ⑴ 퇴출이 「마지막으로 버린 옛 인덱스」와
버린 개수를 돌려주고, ⑵ 대기 항목은 그 경계 이하면 죽이고 넘으면 버린 개수만큼 당기며, ⑶ `admit` 이
**새로 받은 것의 시작**을 돌려줘 링크가 그 범위를 쓴다. 그 함수 주석에 「이 함수는 인덱스를
무효화한다」도 함께 적었다(다음 소비자가 같은 데 안 걸리게).

- `Hit.result: ResultSummary{found, failed, lines}` — 요약을 **`Hit` 안에** 둔다. 라벨처럼 나란한
  배열로 두면 「스캔 순서대로 append」가 깨진다(요약은 **뒤에 오는 줄**에서 만들어져 **앞의 호출**에 붙는다).
- 기다리는 호출은 **개수로 유계인 링**(`max_pending_calls = 256`)이다. 계약 §3.2 의 「줄 수로 창을
  고정하지 않는다」를 지키면서(실측 최대 48 줄) 메모리를 유계로 만든다. 넘치면 가장 오래된 것을 덮는다.
- id 는 **사본**이다(줄은 곧 이월 버퍼에서 사라진다). 상한 48 B — 실측 Claude 30 고정 · Codex 29/41.
  **넘는 id 는 링크하지 않는다**(잘라 비교하면 남의 결과를 집는다).
- **id 의 자리는 그 호출이 든다**(`Hit.id_rel`/`id_len`). 줄에서 다시 찾으면 **한 줄에 호출이 둘일 때**
  남의 id 를 집는다 — 라벨이 같은 이유로 레코드 범위를 이미 닫아 뒀고, 링크도 그 범위를 쓴다.

**줄 수를 세는 방법이 provider 마다 다르다 — 실측이 갈랐다.**

| provider | 방법 | 근거 |
| --- | --- | --- |
| Claude | 값의 **끝을 찾아 그 안만** 센다 | 꼬리까지 세면 **81.1%(32,849/40,495)** 가 틀린다 — `content` 뒤에 `toolUseResult` 가 **같은 텍스트를 다시** 싣는다(대개 두 배). 값이 작아서(중앙 318 B) 끝을 찾는 대가가 싸다 |
| Codex | 값 시작부터 **줄 끝까지** 센다 | 비어 있지 않은 출력 **179,396 건에서 정확한 줄 수와 완전히 같았다**(다른 2.7% 는 전부 빈 출력이라 빈 값 검사가 가른다). 값 뒤에 오는 것은 `call_id`·`type` 뿐이라 개행이 없다. 끝을 찾으면 값을 한 번 더 지나야 하는데 3.2 GB 파일에서 그 한 패스가 초 단위다 |

**스캔 비용 — 재고 고쳤다**(계획이 요구한 실측. 제품 스캐너, ReleaseFast, 이 맥):

| 파일 | 전 | 후 | 차이 |
| --- | ---: | ---: | ---: |
| 전형 1.1 MB (Claude) | 3.3–4.4 ms | 3.8–3.9 ms | 잡음 안 |
| 247 MB (Claude) | 512–517 ms | 655–672 ms | **+28%** |
| 3.2 GB (Codex, 이 맥 최대) | 5.17–5.23 s | 5.45–5.50 s | **+4~5%** |

⚠️ **리베이스 뒤에 다시 쟀다**(위 표는 병합 전 판이다). main 의 퇴출이 들어오면서 대기 링이 비는
구간이 줄어 짧은 회로가 덜 걸린다 — 같은 3.2 GB 파일에서 **2,566–2,662 ms → 3,083–3,103 ms(+18~20%)**
이고 링크는 14,939 건이다(퇴출된 호출은 결말을 못 받는다 — 화면에서도 사라진 줄이다).

첫 판은 **+64%(5.2 → 8.7 초)** 였고, 그것을 셋으로 나눠 잡았다:

| 무엇이 비쌌나 | 처방 | 되찾은 것 |
| --- | --- | --- |
| **결과 마커를 줄 전수로 훑었다** | `result_search_window`(512 B) — 실측: Claude 마커 최대 250, Codex p99.9 90. 창 밖 132 건(0.07%)은 **전부 compacted** 라 어차피 건너뛴다 = 잃는 것 0 | ~2.3 초 |
| **`compacted` 조기 반환을 우회했다** | 링크·분류를 그 검사 **뒤로** 옮겼다. 그 줄이 실측 파일 바이트의 41% 라, 앞에 두면 그 절약이 통째로 사라진다 | ~1.4 초 |
| **기다리는 호출이 없는데도 결과를 훑었다** | `pending_live == 0` 이면 곧장 되돌아간다 | ~1.7 초 |
| **실패 표시를 줄 전수로 훑었다**(적대적 1 회차) | `is_error` 는 **본문 값 끝 뒤 창**에서만 — 실측 715/715 가 `content` 뒤이고 거리가 **중앙·p99·최대 모두 2 바이트** | 247 MB Claude 에서 ~7% |

⚠️ **접두를 합쳐 탐색을 줄이려던 판은 기각했다** — `"type":"tool_` 처럼 **덜 선택적인 needle** 은
`indexOf` 가 더 느려서 오히려 손해였다(실측). 마커는 AV1 그대로 두고 창으로 줄이는 쪽이 맞았다.

**적대적 검증 4 회(구현 직후)**:

| # | 판 것 | 결말 |
| --- | --- | --- |
| 1 | 방금 최적화한 것과 **같은 부류가 더 있나** | **결함 2 건** — 아래 ⑴⑵ |
| 2 | 새로 갈린 갈래에 **판정자가 있나** | **결함**: 「본문을 못 읽음」·「빈 결과」·「기다림 상한」 셋이 판정 밖이었다 → 판정자 셋을 더했다 |
| 3 | **화면에 적히는 문자열**은 누가 재나 | **결함**: 아무도 안 쟀다 → `formatResultSummary` 를 `pub` 으로 열고 네 갈래(빈 칸·크기·실패·0 줄)를 재는 판정자를 더했다 |
| 4 | 판정자가 **실제로 무나**(뮤테이션) | **결함**: 「쓴 자리를 죽인다」를 지워도 판정자가 살아남았다 — **짧은 회로(`pending_live == 0`)가 먼저 막아** 그 축을 못 재고 있었다. 픽스처에 **다른 호출 하나를 살려 두어** 그 회로를 지나게 고쳤고, 그제야 죽는다. 이 축은 표시만의 문제가 아니다: 죽이지 않으면 같은 자리에서 살아 있는 수가 두 번 줄어 **0 아래로 내려간다**(usize 라 즉사) |

뮤테이션 3 종이 전부 즉사한다: ⓐ 이스케이프 건너뛰기 제거(`\\n` 판정자) · ⓑ 쓴 자리를 안 죽임(중복 결과
판정자) · ⓒ `parsed` 를 항상 참으로(「모른다」 판정자).

**1 회차가 찾은 것**: ⑴ 실패 표시를 줄 전수로 훑고 있었다(위 표). ⑵ **본문을 못 읽었는데
`0줄` 이라 말할 수 있었다** — 「모른다」와 「빈 결과」가 같은 값으로 접혔다. 이제 본문을 못 읽으면
결과를 **아예 안 붙인다**(요약 칸이 빈다). 그 대가를 실측으로 셌다: 247 MB Claude 에서 링크가
9,844 → 9,464 로 **380 건(3.9%) 줄었고**, 그 380 건은 본문이 이미지·참조 블록이라 줄 수가 애초에
없는 것들이다(이미지 결과는 AV4 가 이미지 줄로 접는다).

### 3.2 AV2b — 넷째 칸 시각 (2026-09-07)

AV1-b 가 「활동 레코드에서 timestamp 의 자리를 확인하지 않은 채 같은 코드를 쓰면 **남의 시각**이
붙는다」로 미뤄 둔 자리다. **그 자리를 먼저 쟀다**(계약 §2.2 의 표) — Claude 는 100% 가 **마커 뒤**
(중앙 1,454 · 최대 38,753), Codex 는 100% 가 **줄 머리**(자리 1)다. 정반대라 이미지 경로를 재사용할
수 없다는 AV1-b 의 판단이 실측으로 확인됐다.

**구조** — 스캐너는 **자리만** 적고(`Hit.time_rel` — `"timestamp":"` 키의 줄 시작 상대 오프셋),
값 파싱은 라벨 패스가 `agent_image_context.timestampSeconds` 로 한다. 층을 지키는 선택이다: ISO 파서는
그 모듈이 소유하고 스캐너는 바이트 자리만 다룬다. 라벨 패스는 그 자리에서 **64 B 창 하나**만 읽는다
(이미지처럼 앞뒤를 뒤지지 않는다).

**자리 나누기는 순수 모듈이 정한다** — `splitActivityRow`(격자의 `splitLabelRow` 에 **결과 요약** 한
조각을 더한 판, 네 조각이다). 좁아지면 **시각 → 요약 → 접두** 순으로 버리고 **대상은 마지막까지**
지킨다(계약 §2.2). 접두가 요약보다 먼저 자리를 얻는 것은 격자에서 정한 그대로다.

**렌더는 이미 있었다** — 같은 날 main 에 들어간 목록 그리기가 접두·대상·시각을 이미 그리고 있었고
(그때 활동 라벨의 `time_s` 가 0 이라 시각만 안 보였다), AV2b 는 그 값을 채운다. 이 슬라이스가 화면
쪽에 더한 것은 **요약 한 조각과 네 조각짜리 자리 나누기**뿐이다.

**표기는 격자와 같은 함수**(`formatImageTime`)를 쓴다 — 같은 시각을 두 모양으로 적지 않는다.

**비용**: 측정 가능한 증가가 **없다**(3.2 GB Codex 2,814 → 2,640 ms · 247 MB Claude 398 → 388 ms,
둘 다 잡음 범위). Codex 는 창이 256 B 이고, Claude 는 탐색이 첫 값에서 멈추기 때문이다(중앙 1.5 KB).

**검증**: 판정자 3(Claude 마커 뒤 · Codex 줄 머리 · 마커 앞 시각을 안 집는다 · 없으면 0) + 순수
자리 나누기 판정자 1(넉넉·시각 버림·요약까지 버림·폭 0·u16 넘침). 뮤테이션(두 provider 의 탐색
시작점을 맞바꿈)이 즉사한다.

**한계**: ⑴ Claude 결과가 **배열**이면 첫 원소만 센다(실측 122/40,424 = 0.3%) — 배열의 끝을 안전하게
찾으려면 JSON 을 실제로 파싱해야 한다. ⑵ 요약은 **시각을 아직 안 싣는다**(계약 §2.2 의 넷째 칸).
AV1-b 가 「시각과 결과 요약은 AV2」로 적었지만 슬라이스 표는 AV2 를 「결과 잇기」로 정의한다 — 그
어긋남을 여기 적어 두고, 시각은 활동 레코드의 timestamp 자리를 **실측한 뒤** 별도로 붙인다.

## 4. AV3 — 펼침

- 명령 전문 + 결과 전문. **파일을 다시 읽지 않는다** — 그때의 바이트를 그 자리에서 읽는다(계약 §2.4).
- 상한을 넘으면 앞에서부터 상한까지 싣고 「이하 생략」. 상한 상수는 코드가 소유하고 문서는 이름으로
  가리킨다([pr-checklist](../pr-checklist.md) 상수 규율).
- 크게 보기(이미지)와 **같은 자리**를 쓴다 — 둘 다 「한 항목을 크게 본다」이고, 동시에 열릴 수 없다.

**완료 조건**: CI — 상한 초과에서 잘리고 그 사실을 말하는 것, 멀티바이트(한글)가 상한 경계에서
쪼개지지 않는 것. 수동 — 실제 세션에서 긴 출력 하나를 열어 확인.

### 4.1 AV3 가 실제로 한 것 (2026-09-08)

**줄 클릭이 비어 있던 자리를 채운다.** main 이 「줄을 눌렀을 때의 동작(펼침)은 AV3 가 정의한다」로
남겨 둔 그 자리다. 창(`listWindow`)이 그리기와 클릭의 **단일 출처**라 눌린 줄과 그려진 줄이 갈리지 않는다.

**같은 자리를 쓴다**(계약 §2.4) — 이미지의 「크게 보기」와 같은 `open` 상태다. 채우는 것만 다르다:
이미지는 픽셀, 활동은 글. `isDetailOpen` 하나가 그 갈림을 소유하고 클릭·렌더가 그것을 공유한다.
그래서 **동시에 열릴 수 없다**는 계약이 구조적으로 참이다.

**바이트는 안 담는다.** 스캐너는 결과 본문의 **자리**만 적고(`ResultSummary.body_offset`), 펼칠 때
그 구간만 읽는다(§2.4 의 「자리(offset)만 들고 있다가」). 결과는 최대 2.8 MB 이고 세션당 12,200 개라,
담았으면 상주 메모리가 그만큼 는다.

**여러 줄을 그대로 푸는 함수가 따로 필요했다.** 라벨의 `writeText` 는 줄바꿈을 **공백으로 접는다**
(한 줄 목록이라 그래야 한다). 펼침의 값어치는 「그때 받은 것 그대로」이므로 접으면 diff 도 로그도 못
읽는다. `unescapeBlock` 이 셋을 다르게 한다 — ⑴ 줄바꿈·탭을 살리고 ⑵ 이스케이프 안 된 `"` 에서
멈추고(창에는 값 뒤의 JSON 이 섞여 있다) ⑶ 상한에서 **글자 경계로** 자르고 잘렸다고 말한다.

**상한은 8 KiB 다**(코드가 소유: `max_detail_bytes`). 실측 결과 바이트는 Claude 중앙 318 · p99 21 KB ·
최대 616 KB, Codex 중앙 1,190 · p99 365 KB · 최대 2.8 MB 이고 명령은 최대 23,866 B 다. 8 KiB 는 **화면에
그릴 수 있는 것보다 크다** — 이 판의 패널은 스크롤이 없어 들어가는 줄만 그리고 나머지는 「이하 생략」이
말한다. 못 그리는 바이트를 위해 2.8 MB 를 읽을 이유가 없다.

**검증**: 순수 판정자 둘(줄바꿈·값의 끝·제어문자 / 상한과 **한글이 경계에서 안 쪼개지는 것**) · 인덱스
판정자 둘(Codex·Claude 본문 자리가 값의 첫 바이트인가) · 세로 판정자 하나(줄을 눌러 열고, 본문이
그때의 바이트이고, 실제로 **그려지고**, 목록이 물러나고, Esc 로 닫힌다).

**적대적 검증 3 회차(머지 뒤)가 찾은 것 — 계약이 갚기로 한 대가를 안 갚고 있었다**:

계약 §2.2 는 라벨이 `description`(모델이 쓴 요약)을 먼저 고르는 대가를 이렇게 갚기로 했다 —
「명령과 어긋날 수 있다, **그래서 펼치면 언제나 명령 전문이 먼저 나온다**」. 그런데 AV3 은 라벨의
**대상 자리**(`data_offset`)를 그대로 읽었다. 그 자리는 `description → file_path → 명령` 순이라
**Claude Bash 의 68.8%** 에서 요약이다 — 펼쳐도 **같은 요약이 두 번** 뜨고 명령은 영영 안 보였다.

처방은 `Hit.cmd_rel`(명령의 줄 상대 자리, **0 이면 대상이 곧 명령**)이다. `pickClaudeTargetKeyed` 가
「무엇이 골라졌는지」도 알려 주므로 대상이 이미 명령이면 같은 줄을 다시 안 훑는다(AV2 가 배운 비용).
Codex 는 대상이 곧 명령이라(`input`/`arguments`) 언제나 0 이다.

⚠️ **판정자도 같은 회차에서 고쳤다** — 호출이 하나뿐인 픽스처는 자리를 잘못 골라도 우연히 맞는다.
**한 줄에 호출이 둘**인 픽스처를 더해 각자 제 명령·제 id 를 가리키는지 단언한다(옆 세션이 같은 함정을
두 번 밟은 것을 알려 와서 바로 적용했다). 세로 판정자는 Claude 픽스처로 **그 자리를 실제로 읽는가**를
재고, 뮤테이션(대상 자리로 되돌리기)에서 즉사한다.

**적대적 검증 2 회가 찾은 것**:

| # | 결함 | 처방 |
| --- | --- | --- |
| 1 | `realloc` 실패 경로가 **할당 길이와 다른 슬라이스**를 내보냈다 — 그것을 `free` 하는 순간 할당자가 죽는다. 성공 경로만 보면 안 보인다 | 정확한 길이로 새로 잡아 복사한다 |
| 2 | 펼쳤는데 **목록이 안 물러났다** — 본문 글자가 목록 글자 위에 얹혀 둘 다 못 읽는다(격자는 크게 보기 앞에서 물러나는데 목록만 그 규율이 없었다) | `collectActivityList` 가 `open != null` 이면 되돌아간다 + 판정자(뮤테이션 즉사) |

**한계**: ⑴ **패널 스크롤이 없다** — 들어가는 줄까지만 보이고 나머지는 「이하 생략」이다. ⑵ 결과가
없는 호출은 명령만 뜬다(「결과」 머리도 안 그린다 — 없는 것을 빈 칸으로 말한다). ⑶ 실서버 GUI 확인은
수동이다(갤러리 캡처 레시피와 같은 자리).

## 5. AV4 — 종류 필터

**「전체」는 같은 호출을 두 번 싣지 않는다**(계약 §2.2.1, 적대적 A3). 결과가 이미지인 호출은 활동

**이미지 기준으로는 대다수**)이라 「전체」를 켜는 순간 눈에 띈다.

**완료 조건**: CI — 필터별 목록 구성, 전환 시 업로드 표시, **결과-이미지 호출이 「전체」에서 한 줄인 것**.
수동 — 헤드리스 캡처 네 장(필터마다).

### AV3 와 합치고 나서야 보인 것 (2026-09-08)

AV4 를 AV3 위로 리베이스하자 **각자는 멀쩡한데 합쳐야 생기는** 결함이 하나 나왔다. 기록해 두는
이유는 그 형태 때문이다 — 충돌은 안 났다. 자동으로 합쳐졌고, 컴파일도 됐고, 양쪽 판정자도 그대로
통과했다. **자동 병합이 「의미가 맞다」는 뜻이 아니라는 것**의 실례다.

칩 줄은 `gridArea` 에서 자리를 빼 간다. 그런데 칩은 크게 보기·펼침이 열리면 **그리지 않는다**
(`open != null`). 그리기와 자리가 갈린 것이고, 결과가 둘이었다.

1. 펼침이 한 줄을 **빈 채로** 잃는다 — AV3 의 「이하 생략」이 한 줄 일찍 온다.
2. 그 한 줄이 `gridArea` **밖**이라 `handleDown` 이 경계에서 `false` 를 낸다. 즉 **펼침이 열린 채
   그 줄을 누르면 안 닫히고 클릭이 뒤 터미널로 샌다** — 계약이 못박은 「어디를 눌러도 닫는다」에
   칩 줄만 예외가 된다.

`chipRowTakenPx` 로 자리와 그리기를 한 함수에 묶었다. ②는 사실 AV4 혼자서도 **이미지 크게 보기**에
있던 결함이라(같은 경계 검사) 함께 없어진다 — 합침이 없었다면 못 봤을 것이다.

⚠️ **그 수정이 IG13 을 깨뜨렸고, 그것이 옳았다.** IG13 은 「문맥이 있으면 그림 자리가 줄어든다」를
**닫힌 상태**에서 잰 값을 기준선으로 확인하고 있었다. 이제 닫힌 화면과 연 화면은 세로 자리가
다르므로 그 기준선이 거짓이 된다. 기준선을 **연 상태에서 예약 줄을 다 뺀 값**으로 옮겼다 —
판정자가 재던 것(예약 줄이 자리를 먹는가)은 그대로다.

### 5.1 AV4b — 접기가 실제로 한 것 (2026-09-08)

계약 §2.2.1 은 「`tool_use_id` 로 정확히 접는다 — 추측이 필요 없다」였는데, **실측이 그 문장에 빠진
절반을 채웠다**: Claude 는 그 열쇠를 쥐고도 **링크 자체가 안 서고 있었다.** 이미지 결과의 `content`
는 이미지 블록만 든 배열이라(542/542) 본문 파서가 `"text"` 를 못 찾고 되돌아가고, 그러면
`scanResultLine` 이 null 을 내 결말도 접기도 없다. 즉 접기는 **중복을 없애는 일**이면서 동시에
**끊긴 링크를 잇는 일**이었다.

- **접기의 열쇠는 스캐너 자신이다.** 「이 줄이 이미지 결과인가」를 결과 줄에서 다시 찾지 않고,
  이미지 패스가 이미 답한 사실을 `linkResult` 로 넘긴다. 마커를 두 번 찾으면 규칙이 두 벌이 된다.
- **자리(인덱스)로 맨다.** 「호출이 사라지면 접기도 풀려야」 하기 때문이다 — 불리언이면 주인이
  퇴출된 이미지가 접힌 채 남아 **「전체」에서 통째로 사라진다**.
- ⚠️ 그래서 배열이 움직이는 곳을 **전수로** 찾아야 했다: 퇴출(`remapFoldsAfterEvict`)과 화면의
  뒤집기(`reverseFoldOwners`). 대기 링(AV2)이 이미 같은 이유로 remap 을 갖고 있었고, 이 슬라이스는
  그 목록에 **소비자를 하나 더 얹은 것**이다.

⚠️ **뮤테이션 하나가 빠져나갔고 그것이 판정자를 고쳤다.** 뒤집기 remap 의 **호출부**를 지운
뮤테이션이 통과했다 — 픽스처에 호출·이미지 쌍이 **하나뿐**이라, 주인이 어긋나 자기 자신을 가리켜도
여전히 「접혔다」로 세어졌기 때문이다. 쌍을 **둘**로 늘리고 「주인이 이미지가 아니다」를 단언하자
잡힌다. AV4 의 칩 판정자가 「가운데만 눌러서」 빠져나간 것과 **같은 형태**다 — 하나짜리 표본은
어긋남을 감춘다.

⚠️ **실측이 설계를 한 번 되돌렸다.** 처음에는 「결과가 이미지면 요약을 「이미지」로 덮는다」로 짰는데,
Codex 의 `output` 이 `[{text}, …, {input_image}]` 라 **본문이 실제로 있다**. 덮으면 provider 가 적어
준 말을 우리가 지우는 것이라, 규칙을 「**본문이 없을 때만**」으로 좁혔다.

#### A5 — 판정자의 전제가 이 슬라이스로 낡았다

AV2 적대적 1 회차가 세운 「줄 수를 모르면 요약을 안 붙인다」가 **정확히 이미지 결과**를 픽스처로
쓰고 있었다. 그때는 「모른다(`found=false`)」가 유일한 정직한 답이었는데, §2.2.1 이 그 답을 바꿨다.
판정자를 **성질 기준**(「0 줄이라고 적지 않는다」)으로 다시 쓰고 갈래를 하나 더 뒀다 — 이미지도
아니고 본문도 못 읽는 것(참조 블록)은 **여전히 `found=false`** 다. 그 갈래가 없으면 원래 물음이
사라진다.

⚠️ **그리고 이것을 CI 가 잡았다.** 로컬에서 `zig build test` 를 `접기:|error:` 로만 걸러 다른 실패를
못 봤고, exit 1 을 워크트리 상한(`SocketPathTooLong`) 탓으로만 돌렸다. 「FAIL 줄이 없다」가 아니라
**개수로** 확인해야 한다는 규율을 어긴 것이다.

#### A4 — 파일 번호가 어긋난다 (기존 결함, 이 슬라이스 밖)

백엔드는 파일마다 `first_hit = hits.items.len` 을 잡아 두고 스캔이 끝난 뒤
`hits.items[first_hit..]` 에 그 파일 번호를 찍는다. 그런데 **퇴출은 배열을 제자리 압축한다** —
앞 파일 항목이 버려지면 살아남은 것들이 앞으로 당겨지고, 그만큼 이 파일의 앞부분이 `first_hit`
**밖**으로 밀려 번호를 못 받는다(기본값 0 = 첫 파일로 읽힌다).

프로브로 재현했다: 앞 파일 51 개(활동 50 + 이미지 1) 중 **50 개가 버려지자**, 이 파일의 앞
**50 개**가 파일 번호를 못 받았다. 조건은 「다중 파일 체인(재개 세션) + 한 파일이 활동 상한 초과」
이고 둘 다 실측에 있다(최악 세션 181,907 건).

**접기와는 독립이다** — `fold_owner` 는 배열 자리라 정확하지만, 파일 번호가 틀리면 라벨·펼침·
디코드가 **엉뚱한 파일**을 읽는다.

✅ **별도 슬라이스로 고쳤다**(2026-09-08, 사용자 결정). `StreamScanner.file_index` 를 두고
`admit` 이 받아들이는 히트마다 찍는다 — 그 뒤로 어떤 압축이 와도 스탬프가 값과 함께 움직인다.

이 처방의 값은 **「자리를 값으로 드는 필드」를 하나 줄인다**는 데 있다. 대기 링
(`remapPendingAfterEvict`)과 접기(`remapFoldsAfterEvict`)는 자리를 **따라가야** 했지만, 이쪽은
애초에 자리에 매이지 않는 것이 답이었다. 퇴출 쪽(압축 루프·`boundary` 계산)은 한 글자도 안
건드렸다 — 요점이 「퇴출이 무엇을 하든」이라 그쪽을 **안 건드리는 것**이 처방이다.

## 6. AV5 — 「전체」의 썸네일

- 줄 높이에 맞춘 작은 그림. 디코드는 이미 격자용 160 px 가 있으므로 **새 디코드 경로를 만들지 않는다**.
- 보이는 줄만 디코드하는 규율은 그대로(`max_inflight`).

**완료 조건**: CI — 이미지 줄에만 그림이 붙는 것. 수동 — 캡처 1장.

### 6.1 AV5 가 실제로 한 것 (2026-09-08)

**남은 결정(계약 §8)이 먼저였다.** 「줄 높이에 맞춰 줄일지, 안 그릴지」를 실측과 함께 물어
**사용자가 「줄 높이에 맞춘 작은 그림」을 골랐다.** 근거로 낸 수치는 셋이다 — 그림이 붙는 줄이
이미지가 있는 세션에서도 **60 줄에 한 줄**(중앙 1.7% · 최소 0.16% · 최대 9.0%), 목록 줄 높이가
**약 24 px**, 격자 타일이 **160×80**.

구현에서 지킨 것은 넷이다.

- **디코드 경로를 새로 만들지 않았다.** `ensureTiles` 가 그대로 돌고, 갈린 것은 **바이트가 어디
  있나** 하나뿐이다(`thumbSource`) — 이미지 항목은 자기 자리를, 접힌 호출은 결과가 든 자리를 준다.
  두 벌로 뒀으면 「격자에는 뜨는데 목록에는 안 뜬다」가 생긴다.
- **그림 자리를 값으로 든다.** `ResultSummary.image_offset/len/file` 이다 — 「그 이미지가 배열의
  몇 번째인가」로 들면 배열이 움직일 때마다 따라가야 하는데(퇴출 · 화면의 뒤집기), 오프셋은 파일
  안에서 변하지 않는다. **이 스택에서 「따라가야 하는 필드」를 이미 셋 만들었고 넷째는 안 만든다.**
- **자리는 모든 줄이 똑같이 비운다**(`thumbCols`). 그림이 붙는 줄만 밀면 이름이 세로로 안 맞아
  훑기 어렵다. 「명령」·「읽기」 필터에서는 자리도 안 먹는다 — 없는 것을 위해 칸을 비우지 않는다.
- **없으면 건너뛴다(포기하지 않는다).** `ensureTiles` 는 원래 경로를 못 찾으면 `return` 이었는데,
  격자에서는 모든 항목이 그림이라 차이가 없었다. 「전체」에서는 **60 줄에 한 줄**이라 그대로 두면
  첫 번째 그림 없는 줄에서 멈춰 뒤쪽 그림을 영영 안 건다.

⚠️ **`git checkout --` 으로 작업을 두 번 날렸다.** 뮤테이션을 되돌리려고 부른 것이 그 파일의
변경 전체를 되돌렸다. 두 번째에는 스크립트로 복구한 뒤 **먼저 커밋**하고 뮤테이션을 걸었다 —

## 7. AV6 — 개명

### 7.1 AV6 가 실제로 한 것 (2026-09-08)

**이름은 사용자가 골랐다** — `agent_activity`. 선택지 셋(`agent_activity` · `activity` · 미룬다)을
범위 수치와 함께 제시했고, 이웃(`agent_sessions`)과 접두어가 맞는 쪽이 「에이전트 계」임을 한눈에
보인다는 이유였다.

**범위 실측**: `image_gallery` 가 **1,199 곳**. 치환은 두 벌로 나눴다 — `image_gallery`/`image_gallery_ops`
(1,252 곳 · 19 파일)와 이름에 `Gallery` 가 남은 판정자 헬퍼·예약 id(148 곳 · 4 파일). 파일도
`app_session/agent_activity.zig` 로 옮겼다(`git mv` 라 이력이 이어진다).

**바꾸지 않은 것 둘**을 적어 둔다.

- **디버그 훅의 환경변수**(`MARU_FORCE_IMAGE_GALLERY*`) — 저장소 **밖**의 캡처 스크립트·문서가 그
  이름을 참조한다. 바꾸면 조용히 안 먹고, 증상이 「캡처가 빈 화면」이라 원인을 찾기 어렵다. 주석에
  「왜 그대로인가」를 적었다.
- **`docs/agent-image-gallery.md`** — 이미지 **종류**의 계약은 그 문서가 계속 소유한다(계획 머리말이
  그렇게 적었다). 활동 뷰 계약이 그것을 참조하는 구조는 그대로다.

⚠️ **치환이 문서까지 먹었다.** 계약 §8 의 「코드는 `dock_panel.View.image_gallery` 이고」라는 **문제
설명**이 `agent_activity` 로 바뀌어 「코드는 `agent_activity` 인데 화면 이름은 「이미지 갤러리」다」라는
뜻 없는 문장이 됐다. 기계적 치환은 **낱말이 무엇을 가리키는지 모른다** — 문서에서 그 낱말이 「지금
이름」을 가리키는 자리와 「바꿀 대상」을 가리키는 자리가 섞여 있었다. 결정 기록으로 다시 썼다.

#### A2 — 판정자 이름이 두 벌인 것은 결함이 아니다

`app_session.zig` 의 갤러리 판정자는 **「이미지 갤러리: …」 39 개**와 **「활동 뷰: …」 27 개**로 갈려
있다. 모듈은 `agent_activity` 하나인데 이름이 둘이라 언뜻 어긋나 보인다.

**그런데 계약이 둘이다.** 앞의 39 개는 격자·크게 보기·디코드 — **이미지 종류의 계약**
(`agent-image-gallery.md`)이 소유하는 것이고, 뒤의 27 개가 활동 뷰 계약의 것이다. 판정자 이름의
「이미지 갤러리」는 **모듈 이름이 아니라 계약 이름**이므로, 개명을 따라가면 오히려 그 대응이 흐려진다.

⚠️ 다만 **그 사실이 어디에도 안 적혀 있었다.** 다음 사람이 「왜 판정자 이름만 옛날 이름이지」에서
멈춘다 — 그래서 여기 적는다. 판정자 이름은 **그것이 지키는 계약**을 따르고, 모듈 이름은 그 뷰가
지금 무엇인가를 따른다.


- `dock_panel.View.agent_activity`, `app_session/agent_activity.zig`, `AppSession.agent_activity`,
  i18n 키, 설정·문서의 이름.
- **기계적 개명만** 한다. 동작 변화 0 — diff 가 커도 읽는 사람이 「이름만 바뀌었다」를 확인할 수 있어야 한다.
- 개명 뒤 `zig build macos-app-host-abi-lib` 로 enum exhaustiveness를 확인한다(갤러리 IG0의 함정:
  `zig build` 는 그것을 **0곳** 잡는다).

## 8. 검증 방법 — 갤러리 계획을 그대로 쓴다

- **실패는 베이스라인과 비교해서 센다.** 이 워크트리에는 원래 실패가 있다(`poll_owner` 의
  `SocketPathTooLong`). "FAIL 이 있나"로는 아무것도 모른다.
- **테스트는 개수로 확인한다.** `app_session.test.이미지 갤러리` 처럼 접두로 필터해 세고
  (`MARU_TEST_KEEP_ONLY_PREFIX`), 뮤테이션은 「실패했다」가 아니라 **「실패 수가 늘었다」**로 판정한다.
- **헤드리스 시각 검증이 된다**: `MARU_SCREENSHOT=<out.ppm> MARU_SCREENSHOT_DELAY_MS=4000
  MARU_FORCE_IMAGE_GALLERY=<트랜스크립트 절대경로> mise run macos-app` → PPM 을 `sips` 로 PNG 변환.

## 9. 계획 검토 기록 — 적대적 3회가 이 계획에 준 것

계약 §7 이 회차별 기록을 소유한다. 계획이 그 때문에 바뀐 것은 셋이다.

| 바뀐 곳 | 왜 |
| --- | --- |
| AV1 에 **대상 우선순위 판정자**가 들어왔다 | 「명령 첫 줄」이 실측에 깨졌다(52.4% 여러 줄) — 우선순위가 없으면 라벨의 4분의 1이 껍데기다 |
| AV1 에 **메모리 실측**이 들어왔다 | 라벨 전량 생성이 계산상 2.3 MB 인데, 계산과 실측이 갈리는 자리를 갤러리가 이미 두 번 겪었다(스캔 0.7초 추정 / 3.6초 실측) |
| AV4 에 **중복 접기 판정자**가 들어왔다 | 「전체」의 이미지 중복은 필터가 생기는 순간 드러난다 — AV5(썸네일)까지 미루면 그 사이 화면이 거짓말을 한다 |

**슬라이스 순서는 안 바뀌었다.** 세 결함 다 «그 슬라이스 안에서» 고칠 수 있는 것이었고, 의존성을
뒤집는 종류가 아니었다(갤러리 계획의 P4 가 범위 결정 때문에 IG1↔IG6 의존성을 뒤집었던 것과 대비된다).
