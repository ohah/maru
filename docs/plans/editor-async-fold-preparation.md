# 비동기 완료의 접힘 후보 준비

상태: 초기 전체 준비의 검증과 #4672 머지 이력은 아래에 보존한다. 후속 변경은 worker 기준에도 접힘 후보의 증분 재사용을 연결하며 마지막 절과 별도 결과 문서가 범위를 소유한다. CI는 별도 상태다.

## 재현과 경계

PR #4670은 `82cde4ab36c9ae7cd3bdf2bbc104b58ed7ff9dc8`로 머지됐다.
심볼 요약 다음 경계는 접힘 승격이다. 주소 조사에서 비동기 main Running 표본의 약 44%가
접힘 승격에 포함됐지만, 이는 CPU 시간·키별 원인·개선율이 아니다.
실제 Runtime 완료를 두 뷰에 설치하고 첫 접힘 조회의 노드를 검사한 회귀는
수정 전 `expected 0, found 33`으로 실패했다.

`syntax/folds.zig`의 기존 수집을 byte 후보 준비와 현재 줄로의 투영으로 나눈다.
워커의 Job이 독립 후보 배열·트리 참조를 소유하고 `copy_allocator`로 해제한다.
완료 공개 이후 후보는 불변이며 Completion 보유 참조를 가진 동안만 빌린다.
워커는 문서·뷰 포인터나 메인의 줄 배열을 받지 않는다.

뷰 설치는 기존 문서 identity·요청 번호·본문/문법 판 검증 뒤 현재 후보만 독립 복사한다.
`copyMatchedInto`는 기존 뷰 배열 용량을 재사용하고 parser·세대를 수신 뷰에 묶는다.
이전 판 후보는 그대로 무효화하며, 현재 줄의 접힘 좌표·접힌 머리·스크롤·LSP 우선순위는
기존 뷰 경로가 소유한다. 심볼·괄호·색의 무효화와 완료 보유 수명도 유지한다.

동일 parser·세대이고 편집/dirty가 없는 준비된 캐시는 트리 비교·순회·정렬을 건너뛴다.
행 좌표는 매 조회 현재 줄 배열로 다시 투영하므로 줄 힌트나 뷰 상태를 워커에서 가져오지 않는다.

## 실패와 비용

순회·후보 제거 중 취소를 확인하고 취소/OOM의 부분 후보는 무효화한다. 정렬·native 복사에
강제 선점은 없으며, 정렬 후에도 취소를 확인한다. worker 준비 OOM이나 뷰 복사 OOM은
정상 파싱을 버리지 않고 기존 첫 조회 집계로 복구한다. 입력·Undo·새 알림 정책은 추가하지 않는다.
Job 후보는 성공·취소·교체·종료 모두 기존 worker 퇴역 경로에서 해제한다.

초기 구현은 완료마다 worker에서 후보를 전체 수집했다. 후속 증분 재사용은 마지막 절에서
다룬다. 메인에서 트리 재탐색을 없애도 byte 후보 복사·행 투영·
접힘 표 재구성은 남는다. worker 완료 지연·추가 메모리와 최종 색 완료를 함께 측정해야 한다.
worker는 뷰의 LSP 상태를 받지 않으므로 LSP 접힘 우선으로 구문 후보를 쓰지 않는 뷰에도 준비 비용이 있다.

## 검증

  시작 전/cold/증분 순회 중 취소, 준비/복사의 모든 Zig 할당 실패, 틀린 parser/세대/편집 이력.
- `test-editor-parse-worker` 23개: 실제 준비 장벽의 취소·OOM, 완료 수락·조회 복구와 자원 회수.
- `test-editor-parse-view` 6개: 두 뷰 첫 조회 재순회 0, 64회 교체의 현재 판, 뷰 복사 OOM 뒤 정상 조회.
- 기존 접힘 캐시·변경 범위·정렬·행 좌표, syntax 전체 및 제품 입력 회귀를 유지한다.

외부 `prepare.py --stream --fold-control`과 `summary_study.py --cache fold`는 같은 실행 파일에서
접힘 준비만 끄고 켠다. 심볼 준비는 양쪽 모두 켠다. 제품 환경변수·ABI가 아니며,
실제 worker 시도/준비/우회와 뷰 순회 계수로 분기를 검증한다. 프로파일러는 붙이지 않는다.
같은 판의 조회 생략은 양쪽에 적용되어 있어 이 대조는 준비/복사의 효과만 분리한다.
GUI 개선율은 행렬을 마친 뒤 기록하며, 물리 키보드·IME·광학 표시 검증과 구분한다.

두 fixture 모두 8조건의 첫 표시 중앙값이 낮았으며, 여러 줄의 작은 단일 뷰 한 조건은 p95가
소폭 늘었다. 색 완료 최대가 늘어난 표본도 보존한다. 각 fixture에서 준비를 켠 24프로세스의
뷰 순회는 0이다. 전체 PR 전후·모든 언어·물리 IME의 개선율로 일반화하지 않는다.


[괄호 잎 준비 후속](editor-async-bracket-preparation.md)은 별도 대조와 실패 경로로 검증한다.


## 후속: worker 기준의 접힘 후보 증분 재사용

사용자 승인(2026-11-03)에 따라 새 작업의 빈 캐시에서 전체 수집하던 경로를 줄인다.
[앞선 단계 진단](../../tools/editor-parse-incremental/stage-results.md)에서 큰 문서의 접힘 준비가
worker 경과의 약 67%였고 `Job.folds`가 이전 완료의 후보를 받지 않는 것이 확인됐다.

기존 괄호 기준의 내부 빌림을 `cache_source`로 일반화한다. 동일 문서/문법/언어의 완료를
독립 복사한 native 기준이 있을 때, main에서는 배열을 복사하지 않고 worker allocator에서
접힘 후보 값만 복사한다. 실행/대기 취소 시 빌림 반환과 main/work 참조의 퇴역 조건은 유지한다.
다른 서비스와는 캐시 수명을 연결하지 않으며 기준 부재는 기존 전체 준비를 사용한다.

`Cache.copyMatchedOnto`는 원본의 parser/세대·편집/dirty 부재를 검사한 뒤 값만 읽는다.
native 트리 복사는 worker가 이미 독립 소유한 Provider 기준에서 만든다. 원본 캐시의
트리 핸들에는 native 호출을 하지 않는다. caller는 대상 트리가 실제 동일 판의 독립 복제임을
보장한다. 기존 main의 `copyMatchedInto`는 자기 소유 경로의 native 복사를 유지한다.
둘은 대상 교체와 할당 실패 원자성의 공통 구현을 사용한다.

같은 본문은 준비된 후보를 재사용한다. 편집은 `Cache.edit`로 byte 후보/독립 캐시 트리를
옮긴 뒤 기존 Provider 파싱과 `Cache.prepare`의 변경 범위 갱신을 사용한다. 상한/변경 범위
부재의 비교 복구, 정렬·중복 제거·현재 줄 투영과 뷰별 접힘/LSP 우선순위는 바꾸지 않는다.
worker 복사/준비 OOM은 정상 파싱을 유지하고 전체 준비 또는 기존 뷰 조회로 복구한다.
취소 결과는 공개하지 않고 worker 퇴역에서 독립 native 자원을 해제한다.

[결과와 재현](../../tools/editor-parse-incremental/fold-results.md)은 같은 ReleaseFast 실행
파일의 성능 24프로세스/480편집과 정확성 8프로세스/160편집을 구분한다. 양쪽의 괄호 재사용은
유지하고 접힘 후보 복사만 끄고 켠다. 과거 GUI 96프로세스 자료와 한 분포로 합치지 않는다.
배열 복사·위치 보정·뷰 투영의 선형 비용과 초기 전체 수집은 남는다. 복사/위치 보정과
native 호출·정렬은 강제 선점하지 않는다. GUI/IME·CPU 시간·RSS 개선은 이번 실측 범위가 아니다.

native 준비 10개와 worker 31개 검사는 원본 핸들 비접근, 잘못된 판/dirty/없는 대상 거절,
복사/갱신의 Zig 할당 실패, 언어별 줄·구조 편집 20가지의 전체 후보/행 투영 대조,
기준 부재 복구·취소·연속 편집 퇴역을 확인한다. 초기 검증 수는 이전 구현의 이력이다.

## 후속 표시 지연 검증

같은 진단용 앱에서 재사용만 끄고 켠 [100ms 입력](../../tools/editor-input-stream/fold-reuse-results.md)과
[50ms 연타](../../tools/editor-input-stream/fold-reuse-50ms-results.md)는 각각 24프로세스·720키의
별도 모집단이다. 큰 문서의 입력 종료 후 구문 표시 개선은 확인됐으나, 50ms에서는 양쪽 모두
다음 키 전 구문 표시가 0/87이다. 첫 글자 표시의 개선은 일관되지 않고 지연 표본도 보존한다.
이는 앞 절의 native worker 내부 실측과 구분하며, 실제 IME·물리 HID 검증은 아니다.

[후속 단계 진단](../../tools/editor-input-stream/parse-stage-results.md)은 50ms·5만 함수의
단일/공유 각 3프로세스에서 마지막 입력 6개를 요청 identity로 귀속했다. 워커 실행과
설치 이후 표시 구간이 컸고 완료 전달/뷰 설치는 짧았다. 계측 부하가 있는 별도 모집단이다.
다음 조사 지점은 설치 이후 프레임 준비·제출·표시이며 GPU/timer 원인은 아직 확정하지 않았다.
