# 워크스페이스에서 빠진 편집기 백업 복구

상태: 구현 완료. #4113의 ID 백업·워크스페이스 복원 다음 단계다. 실행 검증 범위는 아래에 구분한다.

## 재현과 목표

백업 쓰기 이후 checkpoint가 게시되기 전에 프로세스가 끝나면 `d-<ID>.bak`는 남지만
기존 복원은 그 ID를 찾지 못한다. 같은 경로의 독립 문서는 후보도 각각 유지해야 한다.
기존 U4d-8·U4d-9 실행에서는 빈 본문의 삭제와 읽기 실패 항목의 큐 이탈도 확인했다.

백업 폴더를 읽어 후보를 찾고 사용자가 선택한 사본을 별도 문서로 연다. 발견이나 실패를
삭제 권한으로 취급하지 않는다. 원래 파일이 사라졌거나 현재 내용이 달라도 자동으로 덮어쓰지 않는다.

## 승인된 화면 정책

- 명령 팔레트의 ‘미저장 편집 복구’에서 후보 목록을 연다. 시작 시 자동으로 문서를 열지 않는다.
- 기존 팔레트 컴포넌트를 사용하되 검색·선택 상태는 복구 목록이 독립적으로 소유한다.
- 경로/원격 목적지/이름 없는 문서 번호와 목록 번호, ID 앞 8자리, 크기로 후보를 구분한다.
  경로가 같다고 합치지 않으며 전체 백업 파일 이름으로도 검색할 수 있다.
- 선택하면 이름 없는 새 문서로 연다. 저장 시 기존 Save As를 사용하므로 사용자가 저장 대상을 정한다.
- 빈 본문도 유효한 복구다. 복구 문서는 성공적으로 저장하거나 명시적으로 버릴 때까지 미저장 상태다.
- 손상·읽기 실패는 ‘열 수 없음’ 행으로 남긴다. 살아 있는 문서와 다른 writer가 claim을
  잠근 항목은 후보에서 제외한다. 원본 백업은 유지하며 목록을 다시 열어 재시도한다.
- 목록 닫기는 복구 취소일 뿐 백업 삭제가 아니다. 목록에서 일괄 삭제 기능은 추가하지 않는다.

이 정책은 [공유 복원 계획](editor-shared-restore.md)의 ‘UI 정책은 구현 전에 논의한다’에
따라 2026-10-04 사용자가 ‘제안한 별도 문서 복구로 진행’을 선택했다.

## 구현 경계

- 현재 `d-*.bak`와 기존 `p-*.bak`·`u-*.bak`·`r-*.bak`를 검사한다. 포맷은 바꾸지 않는다.
- 파일 이름과 레코드 신원을 대조하고, 기존 레코드/본문 크기 상한과 UTF-8 규칙을 적용한다.
- 루트와 파일은 소유자·권한·파일 종류를 검사한다. 심볼릭 링크를 따라가지 않는다.
- ID 백업의 기존 claim만 잠근다. 발견 단계에서 폴더·claim·레코드를 생성하거나 수정하지 않는다.
- 후보의 본문 전체를 목록에 누적하지 않는다. 디렉터리 열거와 읽기는 프레임마다 제한하고,
  부분 열거·할당 실패를 완료로 바꾸지 않는다. 다음 후보가 앞선 실패에 막히지 않아야 한다.
- 사용 중인 문서와 이미 복구 중인 source는 앱 전역 문서 목록과 claim으로 제외한다.
- 선택 시 루트·파일 신원과 내용 지문을 다시 확인한다. 목록을 띄운 뒤 교체된 후보는 재검색을 요구한다.
- 본문·줄 배열·문서 소유자와 pane 용량을 모두 준비한 뒤 문서를 게시한다. 실패 시 빈 탭을 남기지 않는다.
- 백업 본문은 이미 해석된 문서 내용이다. `EditableFile.initContent`로 준비하여 선두 U+FEFF를
  파일 BOM으로 다시 떼지 않고, CRLF·LF·NUL과 함께 재백업·저장에 그대로 보존한다.
- 원본 백업과 새 문서 백업의 소유권을 구분한다. 원본은 새 백업·저장·명시적 버리기 성공 전까지 보존한다.
  지울 때도 선택한 파일이 현재 이름의 파일과 같은지 검사한다. 재백업의 임시 파일은 `umask`와
  무관하게 0600으로 맞춘 뒤 게시하며, 권한 설정 실패도 쓰기 실패로 처리해 원본을 남긴다.

## 검증

별도 프로세스에서 checkpoint 없이 남긴 ID 백업, 같은 경로의 독립 사본, 누락 원본,
빈 본문, 손상, 읽기 실패 뒤 재시도, 열거 중 실패, 오래된 선택, 사용 중 claim,
복구 준비의 할당 실패, 저장/재백업/버리기 뒤 source 정리를 검사한다.
`zig build test-editor-backup-discovery`는 후보·보존·UI 판정자와
`tools/test-editor-backup-discovery-process.py`를 실행한다. 프로세스 판정자는 실제 백업 쓰기를
마친 자식을 checkpoint 전에 SIGKILL한 뒤 원본 파일을 없애고, 두 번의 새 실행에서 독립 사본과
빈 본문을 복구한다. 원본 백업의 SHA-256이 바뀌지 않고 원래 파일도 다시 생성되지 않는지 검사한다.
복구 사본을 재백업한 직후에도 다시 SIGKILL한다. 원래 ID 백업과 claim이 정리된 뒤 새 이름 없는
백업만으로 두 번 더 재검색하며, 빈 본문과 선두 U+FEFF의 보존 및 새 파일의 0600 권한을 검사한다.

추가 실패 경로는 선택 후 루트·claim 교체, 하드링크·잘못된 UTF-8·과대 파일,
재백업의 I/O·할당 실패 후 재시도, Save As 취소·실패·성공 시 같은 경로의 다른 ID 보존이다.
엄격한 `umask`에서 읽을 수 없는 재백업과 복구 본문의 선두 문자 유실을 재현하고 수정했다.

목록의 한글 검색은 NFD 조합·확정 callback, 휠 이동, 실제 `AppSession.mouse` 행 선택을 검사한다.
스크롤된 마지막 행, 헤더·우클릭 무동작, 바깥 클릭·Escape 취소와 원본 보존도 같은 입력 경로로 검사한다.
`tools/capture-editor-backup-discovery.py`는 격리된 앱의 제품 Metal 렌더로 목록과 선택 후
문서를 PNG로 촬영한다. 명령 선택은 debug dispatch이며 물리 키 입력이나 실제 OS IME 검증은 아니다.

기존 workspace 전체 창 복원의 실패 정책, Undo 직렬화, 백업 GC/tombstone,
close 정리의 기존 한도, 공개 공유 split 명령과 두 pane IME 검증은 이번 변경 범위가 아니다.
기존 자동 복구의 `pending_backup_revivals` 8개 큐와 읽기 전 dequeue도 바꾸지 않는다.
수동 목록은 그 큐와 독립적으로 파일을 다시 열거하므로 큐에서 빠진 백업도 재시도할 수 있다.
프로세스 강제 종료 검증을 물리 전원 차단 검증으로 표현하지 않는다.
