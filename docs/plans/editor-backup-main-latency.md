# 미저장 백업의 동기 호출 비용 실측

상태: 계측 도구·ReleaseFast 실측 및 결함 주입 검증 완료. 백업 worker나 저장 정책을 바꾸는 단계가 아니다.

## 측정 대상

[저장 메인 큐 통지](editor-save-event-wake.md) 뒤 남은 백업의 동기 I/O를 잰다.
`AppSession.tick`이 부르는 `editor/backup.zig::tick`을 제품 AppSession의 헤드리스 fixture에서
호출한다. 실제 AppKit main run loop·입력 지연·Metal 프레임 시간의 측정으로 해석하지 않는다.

- 경로: 이름 없는 문서의 기존 레코드, 이름 있는 로컬 문서의 복구 ID 레코드.
- 크기: 64KiB·1MiB·8MiB. ASCII 본문, 128바이트마다 LF. 문서 생성·편집·검증은 측정 밖이다.
- 조건: 첫 기록 한 표본, 같은 미저장 본문 반복 기록 세 표본, 백업 삭제 한 표본.
- 측정 문서의 allocator는 macOS 앱과 같은 `std.heap.smp_allocator`다. 검증용 되읽기와 기존 회귀 검사는 테스트 allocator를 쓴다.
- `total_ns`: 만기를 넘긴 백업 tick 호출 전체. `write_ns`: `writeCurrent` 전체.
- `encode_ns`: 기존 encode/encodeRecovery의 직렬화·할당·UTF-8 검사 비용.
- `read_ns`: 복구 ID writer가 기존 레코드를 읽고 파싱·신원 대조하는 비용.

구간은 중첩된다. `write_ns`에는 `encode_ns`와 `read_ns`가 포함된다.
`write_ns - encode_ns - read_ns`에는 권한·잠금·원자 쓰기·namespace 재검증·해제가 섞이므로
이를 순수 디스크 쓰기 시간이라고 부르지 않는다. 삭제는 별도 호출 전체만 재므로 삭제 행의 구간별 0은
그 구간을 따로 계측하지 않았다는 뜻이다. 원자 교체 함수의 반환 시각을 재며 디바이스 영구 기록이나 fsync 비용을 재는 것이 아니다.

새 임시 루트와 테스트 전용 백업 디렉터리를 쓰며 사용자 백업은 접근하지 않는다.
소스 사본에서만 계측을 넣고 원본 파일 hash를 전후로 대조한다. 제품 빌드에는 계측이나 훅이 없다.
각 기록은 제품 parser로 내용과 신원을 되읽고, 삭제는 실제 파일 부재를 확인한 뒤 표본으로 채택한다.

## 재현과 검증

```sh
python3 tools/probe-editor-backup.py --adversarial
python3 tools/test-editor-backup-probe.py
```

기본 빌드 모드는 ReleaseFast이며 `--optimize Debug`도 지원한다. 별도 사본에서 기존 빌드의
저장 통지 테스트 실행 경로를 재사용해 계측 한 검사·기존 U4a 백업 계약 13개·초기화 5개를 실행한다.
결과는 출력된 임시 경로의 `provenance.json`·`samples.json`·`summary.json`·`run.log`에 남는다.
일반 CI에 시간 상한을 추가하지 않는다.

`--adversarial`은 만기 무시, 한 tick에 여러 문서 쓰기, 백업 성공 상태 누락, 실패 재시도 누락,
삭제 생략을 사본에 각각 주입해 기존 U4a 계약이 의미 실패로 잡는지 검사하고 원복 대조군을 실행한다.
컴파일 오류를 검출 성공으로 세지 않는다. 결과는 `adversarial.json`과 조건별 로그에 남는다.
결과 판정기의 기본 다섯 검사는 누락·중복/잘못된 크기·내용 검증 실패·불가능한 시간·잘못된 구간 귀속을 거절한다.

## 판단 범위

로컬 warm-cache 실측이다. 첫 기록도 OS cold-cache를 뜻하지 않는다. 같은 본문 반복 쓰기는
기존 백업 크기에 따른 비용을 분리하는 실험이며 실제 매번 다른 입력의 전체 앱 작업량과는 다르다.
하나의 문서에서 첫 기록·삭제 한 표본은 분포를 대표하지 않는다. 다른 프로세스 부하는 수치를 흔든다.
느린/원격 파일시스템, 전원 손실, 종료 전체 flush, 많은 문서의 backlog, 공유 뷰를 포함한 실제 화면 지연은 별도다.
worker로 옮길 때의 신원·오래된 snapshot·저장/닫기/종료 정합성 설계는 이 측정 PR의 범위 밖이다.

## 실측 결과

2026-10-21, main `de2281c99`의 백업 구현. macOS arm64, ReleaseFast, 앱과 같은 smp allocator.
근거는 `/var/folders/51/mr5cjhg13v324f1vgg9m237c0000gn/T/maru-backup-probe-iwum01l1/`의
`provenance.json`·`samples.json`·`summary.json`·`run.log`다. 제품 원본 5파일의 SHA256,
사본 계측 파일과 fixture SHA256을 남겼다. 동시 다른 앱/에이전트 부하를 통제한 벤치마크는 아니다.

| 이름 없음 | 64KiB | 0.197 | 0.230 | 0.036 |
| 이름 없음 | 1MiB | 0.404 | 0.336 | 0.032 |
| 이름 없음 | 8MiB | 1.940 | 2.529 | 0.080 |
| 로컬 ID | 64KiB | 0.291 | 0.227 | 0.061 |
| 로컬 ID | 1MiB | 0.722 | 0.523 | 0.142 |
| 로컬 ID | 8MiB | 2.244 | 3.419 | 0.859 |

로컬 ID 8MiB 반복 기록의 구간별 중앙값은 전체 3.419ms, `writeCurrent` 3.177ms,
직렬화 0.705ms, 기존 기록 읽기/파싱/신원 대조 0.721ms다. 각각의 중앙값이므로 뺄셈으로 구한
값을 다른 구간의 중앙값으로 간주하지 않는다. 원자료에는 각 표본의 중첩 구간이 있다.

이번 표본에서는 백업이 긴 멈춤을 유발한다는 증거를 얻지 못했다. 따라서 이 PR은 기존 동기 백업을 유지하며
worker 이관은 미착수로 남긴다. 저장 통지의 프레임 대기 개선 수치를 백업 최적화 효과로 재사용하지 않는다.
실제 화면 지연이나 느린 저장소에서 백업 호출이 원인으로 재현될 때 이 도구/프로파일을 함께 사용해 범위를 정한다.

ReleaseFast 정상 19개와 원복 18개가 통과했다. 다섯 의도적 회귀는 모두 컴파일된 뒤 의미 실패로 검출했다.
`adversarial.json`과 변이별 로그가 근거다. 측정 결과 판정기 5개·문서 링크 11개·줄 참조 4개와
fixture 형식 검사도 통과했다. 이번 검증에서 제품 수정이 필요한 새 결함은 발견하지 못했다.


## 측정 도구의 추가 검증

표본 번호에 `True` 또는 `1.0`을 주어도 정수 `1`로 인정되는 허점을 재현하고 정확한 타입을
확인하도록 수정했다. 결함 주입은 다른 검사의 실패를 성공으로 세지 않도록 목표 U4a 검사와
18개 전체 실행·실패 요약을 함께 대조한다. 중간 중단이나 컴파일 실패는 검출 성공이 아니다.
원본 hash 검증과 변이 원복 확인은 `python -O`에서도 생략되지 않도록 명시적인 오류로 처리한다.

추가 다섯 검사는 잘못된 조건 타입, 다른 검사의 실패, 중간 중단/컴파일 실패,
최적화 Python의 hash 불일치, 패치 지점 누락/중복을 공격한다. 결과 판정기는 총 10개가
일반 Python과 `python -O`에서 통과했다. 기존 실측 30표본과 다섯 실제 변이 로그도 강화한
판정기를 통과했고, 동일한 제품 소스 사본의 ReleaseFast 원복 18개를 다시 실행해 통과했다.
실측 조건과 수치는 변경하지 않았다. 근거는 `/tmp/maru-backup-extra-review/`의
`tests.log`·`optimized.log`·`restored-product.log`와 기존 실측 artifact다.
