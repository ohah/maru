# 괄호 부분 수집의 앞 형제 탐색

상태: 선행 PR #4596이 실제 main `007306be0`에 머지됐고 집중·문서/config 68개 빌드 단계를
재검증했다. 별도 브랜치에 보호된 범위 이동과 native·제품 회귀를 구현했다. Debug·ReleaseFast
집중 검사 각각 47개 빌드 단계와 다섯 결함 주입/정상 대조가 통과했다. 성능 교차 실측과 별도 정확성 대조를 마쳤다. 전체 경계 및 최종 문서/config 검사도 통과했다. 원격 CI·머지 결과는 PR #4598에서 확인한다.

## 재현과 선택

현재 `BracketIndex.collectLeaves`는 범위 앞 형제를 Zig 재귀와 native node 호출로
하나씩 확인한다. 공유 편집의 수신 뷰 재수집은 선행 변경으로 제거했지만 원본 뷰의
부분 수집은 남는다. 선행 보존 문맥의 대형 Zig 괄호 갱신 p50은 두 뷰 합계 2.223ms였다.
이 수치를 새 최적화의 효과나 최신 앱 GUI 지연으로 해석하지 않는다.

고정 Zig·JavaScript·Markdown 입력의 323개 조회에서 node 자식 조회 API는 순차 자식
목록과 전부 일치했고 byte cursor 조회는 Markdown에서 세 번 달랐다. 첫 반례는
section의 goal=10, 실제 다음 자식 11..38인데 cursor 결과가 -1이었다.
초기 재현 생성기와 저장소 밖
`native-bracket-cursor-padding-1`에 소스·로그·빌드·해시를 보존한다.
이는 현재 잠근 의존성에서 확인한 API 반례이며 예전 SYNU2의 특정 Zig 입력을
그대로 재현했다고 주장하지 않는다. SYNU2는 기존 제품 회귀로 계속 검사한다.

잠근 `tree_sitter/api.h`의 public 계약을 확인했다. 이전 형제 이동도 최악에는 앞쪽을
다시 선형 순회하므로 반복 backtrack을 기본 구조로 채택하지 않는다. 다음 독립 구조를
후보로 검증한다. C 구현의 자료구조나 control flow를 복사하지 않는다.

## 후보 구조와 불변식

오류가 포함된 부모는 기존 첫 자식 순회를 그대로 사용한다. 오류 없는 부모에서만
현재 범위 시작의 직전 byte를 포화 뺄셈으로 구한다. 이 지점을 넘는 첫 자식을
`ts_node_first_child_for_byte`로 구하고 cursor byte 이동의 실제 노드와 비교한다.
일치할 때만 그 자리부터 기존 수집을 이어간다. 이동 실패/불일치는 cursor를 원래
부모로 reset한 뒤 기존 첫 자식부터 순회한다. 실제 후보가 없으면 수집도 없다.
범위 시작에 끝나는 왼쪽 토큰과 폭 0 편집의 기존 포함 규칙을 보존한다.

잎 판정·언어별 제외·cover 확장·범위 정렬/병합·배열 이동·수신 판·할당 실패 정책은
바꾸지 않는다. 새 저장 필드·worker·영속 데이터·외부 의존성·UX는 없다.
이 API들도 내부적으로 앞부분을 선형 순회할 수 있으므로 O(log n) 탐색으로 부르지 않는다.
절약하려는 것은 Zig 재귀/native 호출 경계와 불필요한 노드 처리다.

## 채택 조건

- 기존 순차 자식 전체 조회와 잎 값 및 cover를 대조한다. 시작/중간/끝, 폭 0 범위,
  긴 padding, UTF8, 문자열/주석, 오류 복구, 여러 언어와 여러 형제 범위를 포함한다.
- 기존 증분 목록·전체 수집 및 제품의 색/모든 byte 탐색과 일치해야 한다. Undo/Redo와
  기존 SYNU2를 함께 실행한다. 할당 실패의 정리/복귀를 유지한다.
- 다섯 독립 결함 주입과 정상 전후 대조를 실행한다. 컴파일 실패를 검출로 세지 않는다.
- native 미시 비용과 제품 입력/프레임을 구분해 전후 교차 측정한다. 시작/중간/끝 입력과
  불일치 복귀 비용을 보존한다. 실제 효과·추가 비용을 확인하기 전에는 채택 완료로 쓰지 않는다.
- Debug·ReleaseFast·전체 경계와 문서/config 및 관련 제품 회귀를 통과한 뒤 PR에 연결한다.

## 오류 복구와 최종 검증

초기 후보는 Bash SYN47과 DTD 범위 42..59에서 기존 괄호를 누락했다. 같은 새 오라클을
기존 main 순회로 실행하면 통과했다. 추가 진단에서는 오류가 있는 DTD 부모에서
실제 자식 44..45가 있는데 goal=41의 node 조회가 NULL을 반환했다. 따라서 node API도
오류 복구 구간의 기준으로 쓰지 않는다. 오류 부모를 기존 순회로 보내 수정했다.

최종 `tools/editor-bracket-range-cursor/reproduce.py`는 DTD를 포함한 고정 네 입력을
실제 잠근 라이브러리로 검사한다. `native-bracket-cursor-padding-3`의 471개 조회에서
cursor 불일치 26개와 오류 부모의 node 불일치 1개를 관측했다. 이는 그 표본의 결과이며
모든 정상 트리에서 API가 정확하다는 증명은 아니다.

새 native 검사는 번들 31개 문법의 잘못된 입력과 언어별 입력에서 모든 byte의 범위·
폭 0 범위·cover를 독립적인 전체 자식 순회와 비교한다. 실제 C cursor를 잘못된 형제로
옮겨도 검증 후 원래 부모부터 복귀하는지 검사한다. 할당 실패별 정리도 검사한다.
제품 검사는 편집 후 cold 색·토큰·탐색과 대조하고, OOM 뒤 무효화와 재시도를 검사한다.
기존 SYNU2 Undo/Redo도 포함한다.

`tools/editor-bracket-range-cursor/review.py`는 오류 부모 보호 제거, 왼쪽 경계 이동,
cursor 노드 비교 무력화, 잘못된 부모로 복귀, 빈 범위의 불필요한 재순회를 주입한다.
다섯 개 모두 컴파일 후 런타임에서 검출됐고 정상 대조 명령 여섯 개가 통과했다.
근거는 저장소 밖 `bracket-range-cursor-attacks-1/receipt.json`이다. 마지막 항목은
결과 값 손상 대신 빈 후보의 불필요한 작업을 검출한다.

## 성능 판정

[전체 실측](../../tools/editor-bracket-range-cursor/results.md)에 첫 입력을 포함한 분포와
불리한 표본을 보존했다. 제품 문맥 112프로세스·2,240편집을 확인했다. 큰 Zig 문서의
중간 입력 p50은 45.762→40.624ms, 끝은 42.080→39.510ms였고 시작은
41.923→42.428ms였다. Swift 중간 p95는 11.191→16.284ms로 증가했다. 다른 빌드와
같은 머신에서 측정했으며 작은 차이와 tail 악화를 숨기지 않는다.

독립 native 구간에서 시작/Markdown 복귀의 추가 비용과 긴 앞 형제 구간의 비용 감소를
각각 확인했다. 저장 필드와 추가 worker 없이 올바른 기존 결과를 보존하는 제한된 최적화로
채택한다. 모든 문서/입력의 지연 개선이나 로그 시간 탐색으로 일반화하지 않는다.

## 진단 입력의 빌드 경계

PR의 첫 일반 CI는 생성기에서 다른 파일 뒤에 붙이는 진단 조각을 독립 `.zig`로
검사해 `c` 미정의 오류를 냈다. 같은 중간 커밋 검사로 로컬 재현했다. 조각은
`padding_fixture.zig.in`으로 구분하고 생성기만 읽도록 했다. 제품 소스와 빌드 내용은
그대로다. 수정된 생성기로 native 진단 2개·28개 빌드 단계를 다시 통과했다.
실패한 중간 커밋은 PR 이력에 남기지 않으며 새 커밋 범위 검사도 확인한다.
