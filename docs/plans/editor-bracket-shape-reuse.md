# 괄호 구조가 같은 편집의 판정 재사용

상태: 최종 측정판 `95cf7b84f`의 Debug·ReleaseFast 중립 33개/제품 7개·판독기
5개, 다섯 결함의 정상·주입·복원 대조와 전체 경계·문서/config 검사를 통과했다.
성공 실행 160개·성능 2,400편집·정확성 800편집/1,200뷰 및 소스·실행 파일·원시
로그의 독립 재검증도 완료했다. [전체 분포와 한계](../../tools/editor-bracket-reposition/results.md)를 따른다.
실측 후 함수 설명 주석 두 개의 위치만 바로잡았으며 실행문은 바꾸지 않았다.
PR CI·main 합류는 미완료다.

## 관측과 목표

선행 pane 구문 계측에서 큰 합성 Zig 공유 입력의 `advanceBrackets` p50은
2.367ms였다. 이 수치는 두 뷰의 CPU 호출 시간이며 실제 입력 지연이나 개선량이 아니다.
현재 native 목록의 version이 바뀌면 `prepareBrackets`는 전체 짝·색 단계와
탐색 인덱스를 다시 만든다. 괄호 사이의 일반 글자만 바뀌어도 이 경로를 지난다.

## 동일성 조건

`bracket_colors.resolve`의 결과는 문서 순서의 `open`·`open_kind`·`close_kind`·
`colorized`, 토큰 수, 독립 풀 설정에 의존한다. byte 시작과 길이는 판정에 쓰이지 않는다.
`brackets.Index`도 짝·감싸는 쌍·다음 여는 괄호를 토큰 번호로 저장한다.
따라서 현재 필터를 통과한 목록의 구조와 설정이 모두 같으면 좌표만 갱신할 수 있다.

긴 줄 제외는 반드시 현재 원문에 먼저 적용한다. UTF-16 20,000 단위 경계를 넘으면
원래 괄호 종류가 같아도 대상 목록이 바뀐다. 기존 `dropLongLines`와 재사용 경로는
같은 중립 필터를 호출해야 하며 CRLF·Unicode 길이 규칙을 복제하지 않는다.

전체 비교가 끝나기 전에 이전 토큰 좌표를 변경하지 않는다. 기존 scratch의 두 구간에
새 시작과 길이를 임시 보관하고, 입력을 끝까지 소비해 목록 수·구조·설정이 모두 맞은 뒤
좌표를 함께 반영한다. 불일치가 확정되면 나머지 비교를 중단하고 기존 전체 판정 경로를 사용한다.
이전 판정이 없거나 배열 길이가 맞지 않아도 전체 판정한다.

편집 시 이전 resolved 설정은 그대로 유지한다. `finishBrackets`가 이전 독립 풀 설정을
사용하는 계약을 바꾸지 않는다. 새 version 게시 시점과 실패 시 낡은 결과 차단도 유지한다.
새 문서 공유 캐시·할당·영속 필드·제품 ABI·UX 정책은 추가하지 않는다.
중립 모듈의 내부 공개 타입으로 `LineFilter`·`Reposition`을 두며 테스트 전용 실제 호출
카운터는 제품 실행 파일에 저장소를 만들지 않는다.

## 제품 연결 전후 검증

- 중립 판정·탐색의 전체 재계산과 좌표 갱신 결과를 비교한다. 정상/잘못된/깊은 중첩,
  여러 byte 괄호, 독립 풀, 색칠 여부, 빈 목록, Unicode·CRLF·긴 줄 경계를 포함한다.
- 마지막 토큰에서 구조가 달라진 경우에도 이전 토큰이 부분 변경되지 않아야 한다.
- 실제 제품에서 여러 편집·공유 뷰·Undo/Redo와 현재 전체 판정 기준을 비교한다.
- 빠른 경로 표시만 검사하지 않고 실제 resolver 호출 감소를 별도 증거로 확인한다.
- 재사용 끄기, 풀 설정 무시, 색칠 속성 무시, 긴 줄 필터 생략, 비교 중 좌표 조기 변경의
  다섯 독립 결함에 정상·복원 대조군을 적용한다.
- 일반/공유 입력의 기준·개선 실행을 짝지어 비교하며 구조 변경의 전체 경로 비용도 잰다.
  이익이 확인되기 전에는 성능 개선이나 제품 적용 완료로 설명하지 않는다.

이 계획은 기존 결과와 정책을 보존하는 최적화의 검증안이다. 실제 구현에서 이 동일성
조건으로 안전한 재사용이 불가능하면 조건을 느슨하게 바꾸지 않고 원인을 보고한다.

## 재현 도구

`mise exec -- zig build test-editor-bracket-reposition -j2`와
`-Doptimize=ReleaseFast`로 실제 native 구문 상태·공유 문서 입력/Undo·색/짝/탐색을 검사한다.
선택 수는 중립 행동 5개+초기화 28개, 제품 행동 3개+초기화 4개를 강제한다.
물리 IME·GPU 픽셀 검증을 뜻하지 않는다.

`python3 tools/editor-bracket-reposition/review.py --output <새 저장소 밖 경로>`는
사본에 다섯 결함을 주입하고 각 전후 정상 대조군과 원본 불변을 검사한다.
컴파일 오류와 선택 개수 오류는 결함 검출로 세지 않는다.

`python3 tools/editor-bracket-reposition/measure.py --output <새 저장소 밖 경로>
--fixtures <고정 다섯 원문 폴더> --deps <Zig 패키지 경로>`는 같은 원문으로
재사용 없는 기준/현재 구현의 ReleaseFast 실행 파일을 빌드한다.
실제 AppSession의 편집과 괄호 준비가 완료될 때까지의 pane frame 작업을 측정하며, 일반/공유와
구조 유지/실제 괄호 하나 추가를 구분한다. 원문은 입력한 prefix와 원본 suffix까지 모두
대조한다. 구조 변경은 canonical 토큰 수가 하나 늘고 실제 resolver 호출이 뷰 수만큼
발생해야 인정한다. 성능 3반복과 별도 정확성 1반복을 실행한다.
입력마다 실제 resolver 호출·frame 반복 수(상한 128)와 원시 시간, 정확성 실행의 전체 색/짝/탐색 인덱스 대조를 남긴다.
파일·workload·반복별 순서를 교대한다. frame 사이의 실제 대기 시간을 모델링하지 않으므로 이 값도 실제 AppKit/HID·present 지연은 아니다.

## 기존 진단 자료와의 구분

`bracket-reposition-measure-1`은 초기 파싱 준비 단계에서 표본 없이 중단했다.
`bracket-reposition-measure-2`는 160개 프로세스의 원시 로그·해시·정확성 대조를
완료했으나, 주석 입력이 실제 괄호 구조를 바꿨다는 검증이 빠졌다.
실제 수정판의 resolver 호출이 모두 0이어서 전체 판정 경로의 추가 비용을 입증하지 못한다.
이 자료는 보존하되 정식 구조 변경 비교로 합치거나 이름을 바꾸어 설명하지 않는다.
새 형식은 schema 1·target `bracket-reposition-comparison`·workload model
`exact-prefix-and-canonical-delimiter-growth`를 명시하고 구형 자료를 거절한다.
`verify.py`는 Git의 실제 준비 HEAD, 1,288개 원본 소스/빌드 파일, 사본·실행 파일·
생성기·원시 로그·실행 순서·모든 표본을 다시 대조한다. 파일 수는 준비 HEAD의 값이다.
`python3 -m unittest discover -s tools/editor-bracket-reposition -p 'test_*.py'`는
이 판독기의 합성 반례를 검사하며 실제 제품 실행 근거와 구분한다.

## 자원 부족으로 중단된 실행의 처리

정식 세 번째 자료의 최초 실행은 성공한 20개 프로세스를 기록한 뒤 다음 프로세스의
준비 중 `NoSpaceLeft`로 중단됐다. 실패한 프로세스는 표본으로 세지 않는다.
원래 소스·생성기·원문·실행 파일·완료된 모든 원시 로그와 순서를 다시 검증한 뒤,
같은 실행 파일·cwd·명시한 `MARU_BRACKET_*` 환경 인수와 고정 행렬의 다음 항목부터 재개한다.
재개 도구의 사본·해시, 재개 전 metadata와 실패 로그는 자료의 `resume-attempts/`에
보존한다. 코드의 의미 실패는 자원 부족으로 분류해 재시도하지 않는다.
기록 갱신은 별도 단일 checkpoint에 metadata와 표본을 함께 남긴 뒤 수행하며,
모든 160개 성공 실행·2,400개 성능 편집·800개 정확성 편집이 완성되고 독립 검증기가
원시 자료를 다시 대조하기 전에는 전체 완료로 표시하지 않는다.
이 중단과 배경 부하는 숨기지 않으며 단일 연속 실행이나 실제 HID/present 지연을 주장하지 않는다.
