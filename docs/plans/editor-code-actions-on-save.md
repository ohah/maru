# 저장 시 code action 구현 계획

상태: CSA1 완료(한 조각). 계약은 [tooling §8.2s](../editor-surface-tooling.md)가 소유하고, 이 문서는 결정·설계·조각·검증을 소유한다.

## 왜

[저장 시 포맷](editor-format-on-save.md)이 섰고, code action 메뉴(§8.2h — `⌘.`)도 있다. 그런데 저장할 때 import 정리(`source.organizeImports`)나 자동 수정(`source.fixAll`)을 적용하는 길은 없었다. §8.2h 는 이것을 「하지 않는 것」으로 두었다. VS Code 의 `editor.codeActionsOnSave` 자리다.

## 결정 (2026-10-11 사용자)

- **기본은 끔** — 설정 `editor.code-actions-on-save` 의 기본은 빈 값이다. VS Code(`editor.codeActionsOnSave`)·Zed(`code_actions_on_format`)도 기본 빈 값이다. import 정리·fixAll 은 코드의 뜻을 바꿀 수 있어 사용자가 켠다.
- **설정은 kind 목록** — 쉼표로 가른 LSP `CodeActionKind`(`source.organizeImports, source.fixAll`)다. VS Code 와 같은 이름이라 서버별 kind(`source.fixAll.eslint`)도 적을 수 있다. 토글 두 개 안은 고르지 않았다(서버별 kind 를 못 고른다).
- **그 문서만 고친다** — 다른 파일·파일 연산을 건드리는 항목은 건너뛴다. `⌘S` 하나가 화면에 없는 파일을 디스크에 쓰지 않는다. 사용자는 질문에 직접 답하지 않았고, 「그렇게 해주세요」로 권장안을 받았다.

## 설계

- **새 모듈** `editor/save_actions.zig` — `⌘S` 의 첫 단계다. 순서는 code action → 포맷(§8.2r) → 저장이다.
- **kind 하나씩**: 설정의 kind 를 적힌 순서대로 하나 묻는다(`only`·문서 전체·`triggerKind: 2`). 응답에서 그 kind(또는 하위 계층)에 드는 첫 항목을 적용하고 다음 kind 로 간다. 적용하면 revision 이 올라 다음 요청이 새 본문을 본다.
- **resolve**: `edit` 이 없으면 §8.2h 와 같은 `codeAction/resolve` 를 보낸다.
- **응답 분기**: lsp.zig 의 codeAction·resolve 응답은 먼저 `save_actions.onClient…` 에 묻고, 아니면 메뉴(§8.2h)로 간다. seq 는 같은 카운터라 겹치지 않는다. 받는 응답은 그 문서를 연 클라이언트의 것만이다.
- **끝**: 목록 끝·시한·낡음·보내지 못함이면 `format.continueSave` 로 넘긴다. 이 함수는 저장 시 포맷의 입구이고, 응답 뒤라 실패 알림은 늦은 응답의 규칙(`showResponseNotice`)을 따른다.
- **순수 층**: `code_action.nextKind`(설정 가르기)·`kindMatches`(점 경계 계층), `rpc.codeActionOnSaveRequest`.
- **세팅 화면**: 텍스트 행이 빈 값을 받는다(끄기 — 일반 `setText` 는 빈 값을 거부한다). 기본값 되돌리기도 빈 값이다. 환경 제외 목록과 같은 방식이다.

## 한계 (받아들인 것)

- 한 kind 에서 첫 항목 하나만 적용한다(서버가 kind 하나에 항목 여럿을 내는 경우는 드물다).
- kind 마다 시한이 1 초라, kind 가 많고 서버가 느리면 저장이 그만큼 늦는다. 넘기면 남은 것을 건너뛴다.
- 다른 파일을 고치는 항목은 이 문서의 부분도 적용하지 않는다(반만 적용하지 않는다).
- 언어별 목록이 없다 — 한 목록이 모든 서버에 간다(서버가 모르는 kind 면 빈 응답이다).

## 적대적 검증 (5회)

1. 재진입 — 응답 처리(pump) 안에서 적용·다음 요청·포맷 요청이 이어지는 것: 클라이언트 목록을 늘리지 않고, 다음 요청 전에 밀린 didChange 를 보낸다(결함 없음).
2. 설정이 바뀌는 사이 — 처음엔 설정 문자열 안의 위치만 들어, 기다리는 사이 Reload Config(파일 감시 자동 reload 포함)가 설정을 바꾸면 새 문자열의 엉뚱한 자리부터 kind 를 읽었다. → `⌘S` 순간의 목록을 사본으로 든다(고침, 변이 S22 가 잡는다).
3. 메뉴와의 공존 — `⌘.` 메뉴(§8.2h)가 같은 seq 카운터를 쓰므로 번호가 겹치지 않고, 응답은 seq·클라이언트로 갈린다(결함 없음).
4. 문서 정합성 — §8.2h·§8.2r·§8.2k 의 「하지 않는 것」과 저장 시 포맷 계획의 한계를 이 계획으로 이었다. 남은 「저장 시 code action 없음」 표기는 없다.
5. 순서와 알림 — code action 이 포맷보다 먼저이고, 건너뛴 경우(다른 파일·겹침·시한·낡음)마다 알림이 「저장은 했다」를 말하거나 이유를 말한다. 저장 실패면 포맷 단계의 알림이 덮는다(결함 없음).

변이 22개 — 21개가 잡혔다. 남은 1개(S11 — 빈 설정 조기 반환)는 등가라 그 코드를 지웠다(빈 목록이면 kind 를 못 찾아 곧바로 포맷 단계로 간다). S19(읽기 전용 조기 반환)는 처음 살아남아 판정자를 더해 잡았다. 셋(S6·S7·S14)은 처음 컴파일 오류로만 죽어 의미 변이로 다시 써 돌렸다.

## 검증

- `CAK1`(순수): 설정 목록 가르기, kind 계층 판정.
- `LSJ11`(순수): 저장 시 요청의 id·`only`·`triggerKind`.
- `CSA1`(제품 경계 — 가짜 서버의 `only` 응답): kind 둘을 하나씩 적용하고 저장, 같은 문서의 `⌘S`, 다른 kind 거름, resolve, 다른 파일 건너뜀, 겹침 거부, 시한(`CASTALL`), 낡은 revision, 빈 설정, 포맷보다 먼저, 남의 클라이언트 응답, 기다리는 사이 설정 변경, 읽기 전용.
