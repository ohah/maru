# 편집 한 번의 메인 스레드 비용 계획

상태: EW0 완료(계측 — 원인 확정), EW1 구현, [EW2 제품 연결](editor-incremental-folds.md) 머지 완료, [EW3 비용 분리](editor-storage-cost-measurement.md) 완료·제품 변경 보류(2026-10-22 사용자 결정 — 「원인을 계측으로 하나씩 확정하는 계획부터」). 2026-10-27 재측정에서 드러난 큰 삭제 뒤 멈춤(고정 머리줄 요약)을 [고쳤다](#큰-삭제-뒤-고정-머리줄-요약-2026-10-27). 배치 원칙(파싱은 메인에서 프레임 예산으로
끊는다 — 워커가 아니다)은 [편집기 층](../native-editor-layering.md) §2.1·§2.1a 가 소유하고, 이 문서는 **편집 한 번 뒤의 메인 스레드 비용**의
실측·원인·조각·검증을 소유한다.

## 왜

「하이라이트 쿼리 미리 데우기」([남은 일](editor-remaining-work.md))를 따지다 「편집할 때마다의 파싱·색칠을 메인 스레드 밖으로 빼야 하는가」를
쟀다(VS Code 는 토큰화를 기본으로 web worker 에서 한다 — `editor.experimental.asyncTokenization` 기본 `true`, 소스 MIT 로 확인). 결론은 **뺄
일이 아니라, 편집마다 문서 크기에 비례해 도는 일이 프레임 예산을 먹는다**는 것이다. 보통 크기 파일은 예산 안이고 700 KB 를 넘으면 한 글자에
60 fps 예산(16.7 ms — `render.frame-rate` 기본 60)을 넘는다.

## 실측 (2026-10-22)

임시 판정자(커밋 안 함): `PaneFixture`(pane 800×600)로 실제 파일을 열고 여는 파싱을 끝낸 뒤, 문서 가운데에서 **한 글자 편집(`insertText`) + 그
pane 의 프레임(`appendPaneFrame` — `advanceSyntax`·고정 머리줄·미니맵이 다 여기서 돈다)** 을 40 번 잰다. `ReleaseFast`, macOS arm64.

| 파일 | 크기 | 편집(중앙) | 프레임(중앙) | 합 중앙 / 최대 | 편집 없는 프레임 |
| --- | --- | --- | --- | --- | --- |
| `web/src/viewer.ts` | 72 KB | 0.26 ms | 3.2 ms | 3.5 / 4.7 ms | 1.3 ms |
| `src/platform/android/android_app_host.c` | 178 KB | 0.74 ms | 4.8 ms | 5.5 / 7.0 ms | 1.6 ms |
| `build.zig` | 719 KB | 3.7 ms | **15.4 ms** | **19.1 / 22.1 ms** | 2.7 ms |
| `src/platform/macos/MaruAppHost.swift` | 1.1 MB | 2.7 ms | **25.3 ms** | **28.0 / 30.9 ms** | 2.3 ms |

- **비용은 편집 뒤 프레임에 있다.** 편집 자체(증분 파싱 포함)는 합의 1/5 안팎이고, 편집 없는 프레임은 2~3 ms 다. 편집이 무효화한 것을 그 다음
  프레임이 문서 크기에 비례해 다시 만든다(프레임 몫이 KB 당 약 21 µs).
- 4.2 MB 문서는 이 표에 넣지 않는다 — 구문 파싱 상한(`syntax/tree_sitter.zig` `max_parse_bytes` = 4 MiB)을 넘어 색·구문 접힘이 꺼진 상태라 견줄
  수 없다(설계된 동작).
- 큰 편집도 쟀다: 50 KB 붙여넣기·문서 1/3 지우기·되돌리기는 build.zig 에서 편집 6~14 ms + 뒤 프레임 12~18 ms, Swift 에서 편집 6~41 ms + 뒤 프레임
  19~28 ms.

### 귀속 — 확정 (EW0, 2026-10-22)

`sample` 표본이 지목한 둘을 하나씩·둘 다 끈 판(임시 코드)으로 다시 쟀다(같은 판정자, 프레임 중앙).

| 설정 | build.zig | MaruAppHost.swift |
| --- | --- | --- |
| 그대로 | 15.7 ms | 25.8 ms |
| 고정 머리줄 끔(`sticky.compute` 가 곧 돌아간다) | 9.3 ms | 12.6 ms |
| 접힘 승격 끔(`promoteFoldRangesToSyntax` 가 곧 돌아간다) | 9.6 ms | 16.9 ms |
| **둘 다 끔** | **3.1 ms** | **3.5 ms** |

- **둘이 프레임 비용의 거의 전부다.** 둘 다 끄면 한 글자 합(편집 + 프레임)이 build.zig 6.9 ms·Swift 6.2 ms 로 예산 안이다.
- **둘은 별개의 전체 트리 순회다** — 고정 머리줄은 `Provider.symbols`(`sticky.zig` `refreshScopes` 가 version 이 바뀔 때마다), 접힘 승격은
  `Provider.foldSpans`. EW0 관측점(`Provider.stats`)으로 셌다: 편집 없는 프레임은 둘 다 0 노드, 한 글자 편집 뒤 프레임은 **각각 트리 전체를
  한 번**(build.zig 123,184 노드 · MaruAppHost.swift 200,850 노드 — 둘 다 정확히 노드 수와 같다).
- **순회가 원래 느리다** — 노드 수로 나누면 심볼 순회 55~80 ns·접힘 순회 42~49 ns(ReleaseFast). 같은 트리를 곧바로 다시 걸어도 같은 값이라
  메모리가 차가워서가 아니다(그 가설은 기각했다). 심볼 순회는 노드마다 종류 이름을 문자열로 목록과 견준다(`hasKind` — `ts_node_type` 의 길이를
  재고 비교한다).

| 실제 파일 | 노드 | 심볼 순회 | 접힘 순회 |
| --- | --- | --- | --- |
| `build.zig` 720 KB | 123,184 | 6.7 ms | 6.0 ms |
| `MaruAppHost.swift` 1.1 MB | 200,850 | 12.3 ms | 8.8 ms |

- **구문 색 질의는 보이는 범위만 묻는다** — 편집 뒤 프레임이 4~5 번 묻는 byte 합이 build.zig 38 KB·Swift 32 KB(문서의 3~5%)이고 **범위 밖 조각은
  0** 이다(Zig 의 큰 struct · Swift 의 거대한 class 꼴로도 0 — 「큰 노드에 걸린 패턴이 범위 밖까지 모은다」는 걱정은 이 문법들에선 서지
  않았다). 편집 없는 프레임도 질의는 한다(색을 캐시하지 않고 프레임마다 묻는다 — 정지 프레임 2~3 ms 안에 든다).
- **편집 쪽(3~4 ms)** 은 증분 파싱 말고 문서 사본(`buffer.copyAll`)·줄 인덱스(`line_index.build`)·줄 배열을 편집마다 처음부터 만드는 몫이다
  (`EditableFile.apply` — 단순함을 고른 설계).

**측정 사고 하나**(같은 날 바로잡았다): 처음 「둘 다 끔」은 zsh 가 따옴표 없는 `$E` 를 단어로 쪼개지 않아 **고정 머리줄만 끈 판**이었고, 그
결과(「하나만 꺼도 같은 양 · 둘 다 꺼도 그대로」)로 「두 순회가 비용을 나눠 쓴다·첫 순회가 차가운 메모리를 치른다」는 거짓 가설을 이 문서의
첫 판(#4545)에 적었다. 환경을 Python 으로 넘겨 다시 잰 것이 위 표다.

### 검증한 것 — 숫자를 믿는 근거

- 프레임 주기: 제품 기본 60 Hz(`config/theme.zig` `render_frame_rate_default`). 고정 머리줄은 기본 켬(`editor.sticky-scroll` — VS Code 와 같다).
- 할당자: 테스트 할당자가 부풀리지 않는다 — 바쁜 표본 가운데 할당·복사 몫이 약 2% 다.
- **pane 이 작다**: 800×600 이다. 보이는 줄에 비례하는 몫(구문 색·미니맵)은 실제 창에서 더 클 수 있다 — 이 표는 하한 쪽이다.
- 프로파일은 실 프로세스 표본(`sample`)이다. 처음 표본은 컴파일러 프로세스를 떠서 버렸다(테스트 바이너리 경로로 다시 떴다).

## 원칙

- **판정은 시간이 아니라 구조값으로 한다**([성능 예산](../performance-budget.md) §원칙 — 답이 기계 속도에 달린 판정은 러너 부하와 구분이 안
  된다). 단계마다 「걸은 노드 수」·「훑은 줄 수」·「질의한 byte 범위」를 세는 판정자 관측점을 두고, 편집 한 번에 그 수가 **문서 크기가 아니라
  편집·화면 크기에 비례**하는지를 잰다. 시간은 위 표처럼 실측으로 PR 에 싣는다.
- **워커로 빼지 않는다**(§2.1a 의 결정을 그대로 — 스냅샷 수명·폐기·재진입 비용). 이 계획의 일은 「편집마다 문서 전체를 하지 않기」다.
- 고친 뒤 색·접힘·고정 머리줄의 **결과는 지금과 같아야 한다** — 순회를 줄인 판과 전체 순회 판의 결과를 무작위 편집 열로 맞대 보는 판정자를 함께 둔다.

## 조각

조각 이름은 **EW**(편집 작업)다 — 첫 판(#4545)의 EC 는 판정자 이름 `EC0` 이 집중 게이트 `test-editor-untitled` 의 필터 `"C0"`(부분 일치 — 판정자 수를
박는다)에 걸려 바꿨다.


- **EW0 계측** — 완료(이 문서의 「귀속」). `Provider.stats`(심볼·접힘 순회가 걸은 노드, 구문 색 질의의 수·byte·조각·범위 밖 조각)와
  `Provider.nodeCount`, 판정자 `EW0`(합성 큰 문서 셋 — 납작한 Zig·큰 struct 하나의 Zig·거대한 class 의 Swift).
- **EW1 고정 머리줄** — 화면 맨 위 줄의 노드에서 **부모를 거슬러 올라가** 그 줄을 감싸는 심볼만 구한다(`ts_node_descendant_for_byte_range` → 부모
  사슬, 심볼 종류 거르기는 지금과 같다). 비용이 문서 크기가 아니라 중첩 깊이에 비례한다. 심볼 2층(LSP)·접힘 범위 3층으로 떨어지는 순서는 그대로.
  `EW0` 의 「심볼 순회 = 트리 전체」 단언이 「깊이 × 상수」로 뒤집힌다.
- **EW2 접힘 승격** — 승인한 증분 캐시를 [제품에 연결한다](editor-incremental-folds.md). `EW0` 의 「접힘 순회 = 트리 전체」 단언을 작은 편집 뒤 국소 방문으로 뒤집는다.
- **EW3 편집 쪽** — [EW2 이후 비용 분리](editor-storage-cost-measurement.md)에서 Swift 재구축 세 단계의 중앙값 합은 약 0.40 ms였다. 기존 3~4 ms는 편집 전체 비용이며 재구축만의 몫으로 볼 수 없다. 저장소 변경은 보류하고 큰 문서의 잔여 비용을 다시 귀속한다.
- 구문 색·미니맵 질의와 괄호 목록은 **조각에서 뺐다** — 질의는 보이는 범위만 묻고 범위 밖 조각이 0 이며, 둘을 끈 프레임 전체가 3 ms 다.

## 결정 필요

- **EW2 의 길.** ① tree-sitter 의 「바뀐 범위」(`ts_tree_get_changed_ranges` — 이미 `Provider.noteChanged` 가 부른다)만 다시 뽑아 기존 목록에
  잇는다. ② 접힘은 매 글자마다 맞을 필요가 없으니 **타이핑이 멎은 뒤** 한 번 다시 뽑는다(LSP 의 「조용해지면」 시계와 같은 꼴 — 그동안은 위치를
  민 옛 목록). 실측 전에는 ②를 우선 가설로 두었다. [비교 실측](editor-fold-cost-measurement.md)에서는 입력 비용 감소가 비슷한 반면 ②의 지연·유휴 프레임 비용과 범위 유지/깨우기 배선이 남아 ①을 권고했고, 사용자 승인에 따라 [제품 연결](editor-incremental-folds.md)을 진행한다.
- **목표 수치.** 「1 MB 문서 한 글자 = 편집 + 프레임이 프레임 예산 안」을 [성능 예산](../performance-budget.md)에 둘지(지금은 편집기 타이핑
  예산이 없다). 권장: 수치는 실측으로 PR 에 싣고, 예산 표에는 구조값(편집 한 번이 걷는 노드가 문서 크기에 비례하지 않는다)으로 둔다.

## 검증

- 구조: 조각마다 관측점 판정자 — 큰 문서(합성 · 수만 줄)에서 한 글자 편집 뒤 그 단계가 걸은 노드·줄 수가 문서 전체보다 **자릿수로 작다**.
- 같음: 무작위 편집 열(삽입·삭제·붙여넣기·되돌리기)마다 고친 판의 결과(고정 머리줄의 줄·접힘 범위·색)가 전체 순회 판과 같다.
- 실측: 위 표를 같은 임시 판정자로 다시 재 PR 에 싣는다(ReleaseFast, 같은 파일).

## 범위 밖

- 여는 비용(여는 파싱은 이미 4 ms 예산으로 끊긴다 — §2.1a)·쿼리 첫 컴파일(Swift 84 ms — [남은 일](editor-remaining-work.md) 「하이라이트 쿼리
  미리 데우기」).
- 4 MiB 를 넘는 문서(구문 기능이 꺼진다 — 설계된 동작).
- 파싱을 워커로 옮기기(§2.1a).

## EW0 후속 검증

`test-editor-edit-cost`는 EW0 제품 프레임 판정과 관측 경계 판정을 독립 실행한다.
macOS에서는 실행 수와 통과 수를 모두 6개(동작 판정 2개와 공통 import 판정 4개)로 고정한다.
Debug와 ReleaseFast를 각각 실행하며, 실제 AppKit 표시·키 입력 지연이나 첫 표시 시간의 증거는 아니다.

프레임을 관측하기 전에 별도의 심볼·접힘 순회를 하면 캐시를 데워 측정 조건을 바꾼다.
별도 순회 시간은 프레임 관측 뒤에 재고, 그 순회의 카운터는 원복한다.
이 별도 순회는 이미 프레임이 트리를 읽은 뒤이므로 차가운 첫 순회의 시간으로 해석하지 않는다.
호스트의 언어 서버는 fixture에서 끄며, 제품의 LSP 정책은 바꾸지 않는다.

누적 카운터의 상한을 주입했을 때 기존 Debug의 심볼 순회가 overflow로 중단되는 것을 재현했다.
관측값은 u64 상한에서 포화시키며, 포화 이후의 차이는 실제 작업량으로 해석하지 않는다.
카운터 상한 주입은 인공 실패 조건이고, 일상 사용에서 이 상한에 도달했다는 증거는 아니다.

추가 공격 조건은 다음 20개다. 같은 테스트의 단순 반복은 별도로 세지 않는다.

- 여섯 카운터 각각의 상한 주입과 구문 결과 보존.
- 빈 시작 범위·문서 중간 빈 범위·역순·EOF 빈 범위·EOF 밖·EOF 초과 요청의 여섯 경계.
- 심볼/접힘 반복 누적 각각과 다른 Provider의 심볼/접힘 계측 분리 각각.
- 트리가 없을 때 노드 수 0·이전 심볼 제거·이전 접힘 제거·질의 무계측 및 빈 색 결과.

기존 EW0의 큰 Zig/Swift 세 문서에서는 정지 프레임의 두 순회가 0이고 편집 뒤에는 각각 트리 노드 수와
일치하는지 대조했던 것이 EW0 기준이다. EW1 이후에는 심볼 전체 순회가 0이고 조상·변경 범위 방문이 국소적인지 검사한다. 접힘 전체 순회는 EW2까지 남는다.

### 반복 검토에서 보강한 판정

20개 경계 조건을 한 번 실행한 것과 적대적 검토를 20회 반복한 것은 구분한다.
후속 반복 검토에서는 기존 결과를 그대로 두는 색 목록 결함과, 심볼 개수는 같지만 위치가 틀리는
결함을 실제로 넣어도 이전 판정자가 통과하는 빈틈을 확인했다. 색 목록을 먼저 채운 뒤 트리를
없애고, 포화 전후의 심볼·접힘·색 결과는 개수뿐 아니라 모든 필드를 비교하도록 보강했다.

또한 편집 직후에 별도 관측값을 잡아 프레임의 차이를 계산한다. 편집 자체의 심볼·접힘 순회가
없다는 것도 별도로 단언하며, 처음 파싱을 기다리는 반복이 끝나도 pending이면 측정을 진행하지 않는다.
`query_bytes`는 요청한 범위의 합이며 tree-sitter 내부가 방문한 노드 수를 뜻하지 않는다.
범위 밖 색 조각이 0이라는 사실도 질의 엔진 내부의 전체 작업량 상한을 증명하지 않는다.
질의·미니맵 최적화를 뒤로 둔 근거는 해당 파일의 초기 실측 결과이며 모든 언어의 비용 보장이 아니다.


## EW1 구현과 검증

고정 헤더의 tree-sitter 후보는 화면 위쪽 최대 고정 행에 해당하는 논리 줄 끝에서 조상으로 찾는다.
첫 줄 하나만 보면 바로 아래에서 시작하는 중첩 헤더를 놓친다. Dart의 시그니처와 본문이 형제인 경우와
그 사이 빈 줄도 기존 `symbolEnd` 규칙으로 연결한다. LSP 심볼 목록이 있으면 기존대로 우선한다.

현재 창의 후보가 없는 것과 파일 전체에 심볼이 없는 것은 다르다. 후자일 때만 접힘 출처로 내려간다.
Provider가 마지막 집계 트리의 참조 계수 사본과 심볼 개수를 보관하고, 같은 편집을 사본에도 적용한다.
다음 조회는 구조 변경 범위와 실제 편집 범위에 닿는 옛/새 심볼을 빼고 더한다. 구조 변경 범위만 쓰면
동일 구조 선언 삭제를 놓치는 것을 재현했다. 0폭으로 접힌 옛 선언도 경계에 포함한다.
여러 편집 뒤 한꺼번에 조회하면 실제 편집 구간을 마지막 좌표로 옮겨 합친 경계를 사용하므로,
멀리 떨어진 편집을 모으면 그 사이까지 다시 검사할 수 있다. 처음 열기·전체 교체는 전체 집계하며,
대규모 구조 변경의 비용이 항상 화면 크기로 제한된다고 주장하지 않는다.

후보 목록은 매 프레임 다시 구한다. 뷰·접힘·랩·파서 세대를 조합한 별도 캐시를 만들지 않는다.
조상·집계 방문 카운터는 Maru가 명시적으로 방문한 노드이며 C API 내부 탐색 비용까지 세는 값은 아니다.
종료·전체 교체·파싱 상한/빈 문서에서는 C 트리 참조를 놓는다. Zig 할당이 실패하면 빈 후보를 반환하고 기존 집계를
보존하거나 완료된 집계에서 재시도한다. 호출자의 Zig allocator를 Provider에 보관하지 않는다.

기존 랩 매핑에서 화면 위로 지나간 논리 줄의 음수 근삿값에 전체 조각 수를 더하면 닫힌 함수 헤더가
남는 결함도 재현했다. 이미 지나간 논리 줄은 화면 밖으로 판정하되 첫 논리 줄의 부분 스크롤은 유지한다.

집중 명령 `mise exec -- zig build test-editor-sticky-ancestors -j2`는 제품 헤더와 전체 목록 대조,
기존 STK 출처·클릭·접힘·랩 회귀, 다국어 줄별 후보, 무작위 편집과 지연 조회, UTF-8/CRLF,
선언 삭제·재삽입, Zig 할당 실패 재시도와 C 메모리 해제를 실행한다. Debug·ReleaseFast를 각각 확인한다.
`test-editor-edit-cost`는 큰 합성 Zig/Swift 문서의 전체 노드 수와 편집 뒤 국소 작업량을 함께 대조한다.
실제 AppKit 캡처는 `python3 tools/editor-sticky-ancestors-app/run.py --output <빈 외부 경로>`로
사용자 프로필과 분리한 앱 사본을 빌드한다. fixture가 스크롤을 배치하고 제품 Metal 결과를 읽으며,
물리 HID 입력·외부 화면 녹화나 사용자 체감 지연의 증거로 확대하지 않는다.


### EW1 로컬 실측(2026-10-23)

기준 `3d4a0fbf7`과 EW1의 ReleaseFast 바이너리에서 같은 fixture를 5번씩 교차 실행한 중앙값이다.
실제 파일 둘은 기준 커밋의 원문을 고정해 양쪽에 같은 바이트를 넣었다. 시계 구간은 `insertText`
직전부터 다음 `appendPaneFrame` 완료까지다. LSP는 fixture에서 끄고 파싱·초기 프레임은 미리 끝낸다.
이것은 제품 편집·프레임 함수의 로컬 실행이며 AppKit 키 입력부터 화면 표시까지의 지연은 아니다.
다른 로컬 검사가 돌아간 환경이므로 출하 성능 예산이나 모든 문서의 상한으로 사용하지 않는다.

| 입력 | 기존 편집+프레임 | EW1 | 편집 뒤 심볼 전체 순회 |
| --- | ---: | ---: | ---: |
| 납작한 Zig(205 KB) | 15.36 ms | 7.74 ms | 96,001 → 0 |
| 중첩 Zig(217 KB) | 17.69 ms | 9.09 ms | 96,010 → 0 |
| 중첩 Swift(243 KB) | 21.63 ms | 11.97 ms | 99,010 → 0 |

합성 문서의 헤더 조상 방문은 각각 13·23·26, 변경 범위 방문은 8·12·14, 재구축은 모두 0이었다.
접힘 승격의 전체 순회는 여전히 남고 큰 Swift 원문은 60 fps의 16.7 ms보다 길다. EW1을 편집 비용
문제 전체의 해결로 해석하지 않는다. 이후 EW2를 제품에 연결했고, [EW3 비용 분리](editor-storage-cost-measurement.md)로 저장소 재구축의 실제 몫을 확인했다.

## 큰 삭제 뒤 고정 머리줄 요약 (2026-10-27)

EW1~EW3 뒤 main `b99dbfd50`에서 처음 실측(2026-10-22)과 같은 임시 판정자로 다시 쟀다. 편집 한 번과 그 뒤 pane 프레임 하나이고,
ReleaseFast·같은 바이너리 3회다. 한 글자 입력은 `build.zig` 19.5 → 7.35 ms, `MaruAppHost.swift` 28.6 → 6.85 ms로 줄었다(합 중앙값).
글자당 심볼 순회는 0, 접힘 순회는 6~16 노드였다. 그런데 **파일의 1/3을 지운 직후 프레임**은 나빠졌다. Swift는 3.13~3.16 초로 세 번 다
재현됐고, 다른 파일도 36~54 ms였다(10-22에는 3.6~18.9 ms).

**원인.** `sample`의 거의 전부가 `sticky.compute` → `symbols.Summary.hasSymbols` → `touched` → `symbolForNode` →
`ts_node_child_with_descendant`였다. 임시 계측으로 갈라 보니 2.15 초 전부가 **편집을 받은 옛 트리** 쪽 `touched`였다(새 트리 쪽은 4 ms).
옛 트리에서 지운 노드는 0폭이 된다. tree-sitter는 0폭 노드의 부모를 그 byte에 닿는 자식마다 재귀로 찾는다
(MIT 소스 `lib/src/node.c` `ts_node_child_with_descendant`의 `is_empty` 갈래). 요약은 지운 노드마다 `symbolForNode`를 불렀고,
`symbolForNode`는 이름 끝·본문 끝을 고르려고 형제·부모를 조회한다. 같은 byte에 그런 노드가 수백 개 쌓이면 조회가 폭주한다.
실제 파일에서 옛 코드의 요약 한 번은 삭제 크기에 따라 초선형으로 늘었다(Swift 약 120 KB 삭제 111~209 ms, 380 KB 2.15 초).
되살림은 0폭 노드가 없어 차이가 없었다.

**수정.** 존재 판정을 `Provider.symbolName`(종류·`isSymbolWorthy`·이름 노드)으로 떼었다. `symbolForNode`는 그것을 거쳐 값을 채우고,
요약(`touched`·`fullCount`)은 adapter의 `isSymbol`로 그것만 부른다. `symbolForNode`가 null을 내는 조건은 이것뿐이라 집계 의미는 같다.

**검증.**
- 판정자 `sticky changes 큰 삭제 뒤 요약은 존재만 세고 심볼 값은 조상 사슬에서만 채운다`: 여섯 언어 일곱 사례(이름 없는 Zig `test {}` 포함)로 다음을 단언한다.
  - 재구축 없이 고친다.
  - 지운 범위를 걷는다.
  - `Stats.symbol_values`(`symbolForNode`가 값을 채운 수)는 조상 사슬 몫만 는다.
  - 집계가 전체 목록과 같다. 지운 것을 되살린 뒤도 같다.
- 변이 여섯:
  - `touched`·`fullCount`를 옛 호출로 되돌림.
  - `isSymbol`이 `symbolForNode`를 직접 부름.
  - 항상 참.
  - 이름 확인 누락.
  - 카운터 삭제.

  이 판정자가 모두 잡았다. 이름 확인 누락은 이름 없는 사례를 더한 뒤에야 잡혔다.
- 실제 파일 다섯 × 삭제 세 종 × 지움·되살림 30경우에서 요약 집계가 전체 목록과 같았다. 요약 한 번은 0.3~16 ms였다.

| 1/3 지운 직후 프레임 | main `b99dbfd50` | 수정 뒤 |
| --- | ---: | ---: |
| `web/src/viewer.ts` | 54 ms | 4.1 ms |
| `android_app_host.c` | 36 ms | 5.8 ms |
| `build.zig` | 38 ms | 23 ms |
| `MaruAppHost.swift` | 3,160 ms | 28.9 ms |

다른 파일의 36~54 ms도 같은 원인이었다. 처음엔 `sample`에서 고정 머리줄 쪽 표본이 적어 별개라고 봤는데, 수정 뒤 제품 경로 실측에서 함께 사라졌다.
한 글자 입력은 바뀌지 않았다(Swift 6.8 ms, `build.zig` 7.6 ms). 이 숫자도 로컬 실행이며 AppKit 입력에서 화면 표시까지의 지연이나 출하 예산은 아니다.
