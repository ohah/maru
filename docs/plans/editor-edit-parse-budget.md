# 일반 편집의 파싱 예산 비교

상태: PR #4607이 main `1cbbcf260`으로 머지된 뒤 조사를 시작했다.
제품 실행 코드 변경 없이 성능 600입력·별도 정확성 200입력과 기존 구문 상태의 pending/공유 소유권 대조를 완료했다.
콜백 간격·스레드 CPU 진단과 독립 원시 통계 대조도 완료했다.
[실측 결과](../../tools/editor-parse-budget/results.md)에 범위와 분포를 기록한다.
이 문서는 당시 동기 후보 비교의 기록이다. 이후 일반 입력·공유 뷰·Undo/IME 연결은 [비동기 파싱](editor-async-parse.md#제품-화면-연결)에서 구현했다. 아래 수치는 새 worker 제품 경로의 지연 개선량이 아니다.

## 확인할 문제

[native 내부 샘플링](editor-native-sampling.md)은 큰 문서의 동기 편집에서
파싱과 변경 범위 계산 비용을 확인했다. `frame_parse_budget_ns`의 4ms는 문서 열기와
`resumeParse`에서 사용하지만 일반 편집의 `editProvider`는 예산 없는 `Provider.onEdit`을
호출한다. 현재 `onEditSpanFromReady`의 완료·캐시 처리도 동기 완료를 전제한다.

따라서 호출 상수만 바꾸는 제품 변경을 먼저 하지 않는다. 실제 편집에서 첫 호출·재개·완료 뒤
조회 비용과 정확성을 분리해 비교한다. 새 worker나 편집 UX 변경은 이 조사 범위 밖이다.

## 첫 진단에서 확인한 사실

머지된 제품의 별도 사본에서 실제 시계와 C 파서를 사용했다. 강제 만료 조건은 넣지 않았다.
생성 Zig 3,000·50,000줄 각각에 공백을 세 번 삽입하고 예산 0·4ms를 비교했다.
보관 실행 파일을 다시 실행했으며 두 실행 각각 진단 12행과 실제 C 검사 1개·모듈 참조 1개가 통과했다.

50,000줄의 4ms 첫 호출은 두 실행에서 약 4.005~4.011ms에 pending으로 돌아왔고
각각 두 차례 재개한 뒤 완료됐다. 최종 트리의 S-expression과 root 끝 바이트는
같은 원문을 새로 파싱한 결과와 일치했다. 이는 전체 노드의 위치·표시 캐시·공유 뷰 정확성 검사가 아니다.

자료는 저장소 밖 `~/.cache/maru-agent-artifacts/native-edit-budget-feasibility-1/`에 있다.
`source.json`·fixture·보관 바이너리·원시 로그·`readback.json`이 대상과 실행을 묶는다.
초기 의존성 링크 오류와 테스트 선택 개수 설정 오류는 별도 실패 로그로 보존하며
제품 결함이나 적대적 검증의 의미 결함 검출로 세지 않는다.
콜백 계수를 추가한 진단 바이너리의 소수 시간값은 성능 분포나 개선율로 채택하지 않는다.

## 비교 설계

- 현재 동기 편집을 기준으로, 같은 입력·원문·빌드 모드의 별도 사본에서 예산을 비교한다.
- 첫 호출과 모든 재개 호출의 전체 시간·native parse·변경 범위·최대 한 호출 시간을 남긴다.
  여러 호출의 완료 시간과 한 프레임의 대기 시간을 구분한다.
- `setSourceBudgeted` 재개는 기존 트리·변경 범위를 보수적으로 무효화한다.
  파서 반환 시간만 줄고 색·괄호·접힘 조회가 늘어나는지 제품 경로에서 함께 확인한다.
- 성능과 매 편집의 새 파싱 대조를 별도 실행으로 둔다. 첫 입력과 pending 실행을 제외하지 않는다.
- 같은 문서의 공유 뷰, pending 중 다음 입력·Undo/Redo·전체 치환과 늦은 재개를 검사한다.
  입력 판·트리 세대·캐시 수명이 맞지 않으면 성공으로 판정하지 않는다.

## 채택 기준과 후속 결정

독립 reader가 호출별 원시 시간·판·세대·완료 상태와 모집단을 대조해야 한다.
다섯 독립 가설에서 실제 의미 손상을 거절하고 정상 전후 대조를 보존한다.
후보는 실제 제품 조회 결과를 기준 및 새 파싱과 비교하고, 성능은 반복 분포로 제시한다.

4ms 값이 모든 내부 연산의 강제 상한이라고 가정하지 않는다. progress callback 사이의 작업과
완료 뒤 변경 범위·트리 해제 시간도 측정한다. GUI/HID 지연이나 공유 편집의 개선은 별도 증거가 필요하다.

동기 완료 전제를 바꾸면 문서화된 편집·미완료 표시 정책에 영향이 생긴다.
측정과 정확성 대조를 마친 뒤 구체안을 보고하고, 제품 계약 변경은 사용자와 논의한 다음 구현한다.

## 이번 단계의 판단

4ms의 첫 호출만으로 모든 호출이 4ms 이하라고 볼 수 없다. 실제 재개 호출의 초과와 C 콜백 사이의
긴 CPU 구간을 관측했고, 완료 뒤 전체 변경 및 입력 판 재발급도 확인했다. 따라서 상수만 바꿔
제품에 연결하지 않는다. 기존 API의 안전성 대조와 후보를 연결한 제품 검증을 구분한다.
