# EW2 접힘 계산 방식 비교 실측

상태: 제품 함수 비교와 전면 AppKit 합성 입력 실측을 완료했다.
증분 방식의 제품 연결은 [별도 EW2 구현](editor-incremental-folds.md)이 소유하며, 아래 수치는 독립 사본의 프로토타입이다.

## 판단

이번 비교에서는 **변경 범위 갱신을 권장한다**. 기존 계획의 조용 시계 우선 권장은 실측 전 가설이었다.
제품 함수 비교에서 증분은 실제 두 원문의 입력 프레임 중앙값을 약 43~50% 줄이고, 각 입력 뒤 접힘 범위를 즉시 정확하게 유지했다.
지연은 입력 비용을 비슷하게 줄이지만 재계산과 가시 줄 재구성이 나중 프레임에 남는다.
캐시의 대가는 실제 원문에서 뷰당 약 56/84 KiB이고, 접힘 후보가 많은 3.13 MB 합성 문서에서는 약 3.16 MiB다.

이 판단은 비교한 두 방식의 이번 입력 자료에 대한 권고다. 모든 입력에 증분 작업량이 작다는 뜻은 아니다.
지연 방식의 시간은 150 ms를 실험 값으로 썼으며 새 제품 설정이나 UX 정책으로 채택하지 않았다.

## 비교 대상과 경로

- 기준: EW1 뒤 기존 `Provider.foldSpans` 전체 순회.
- 증분: 같은 `TSInputEdit`을 적용한 이전 트리 사본을 보관한다. 실제 편집 범위와 구조 변경 범위의
  후보를 갱신하고, 그 밖의 후보의 byte·행 좌표를 이동한다. 한 시작 행의 최장 후보가 없어지는 경우에
  대비해 최장 결과만이 아닌 개별 후보를 보관한다. 결과는 기존과 같은 시작 행별 최장 범위다.
- 지연: 기존 범위를 편집 좌표로 이동해 유지하고, 조용해진 뒤 전체 순회를 수행한다. 단일 뷰의 빠른 경로도
  범위를 보존하도록 준비·게시 경로에 연결했다. 타이머 하나만 넣은 경우는 정확한 비교 대상으로 삼지 않았다.

모든 방식은 같은 제품 `insertText`/`undoEdit` → 접힘 승격 → `appendPaneFrame`을 실행한다.
증분·지연 패치는 계측 사본에서만 활성화되고, 저장소의 제품 소스는 바꾸지 않는다.
파싱과 초기 접힘 계산을 완료한 뒤 입력을 시작한다. 공유 뷰는 실제 `split_editor_right` 명령으로 만들고
양쪽 준비가 끝난 뒤 측정한다. LSP는 끈다. 한 뷰는 800×600, 두 뷰는 같은 폭을 나눈 400×600 각각이다.

## 자료와 반복

| 자료 | 원문 byte |
| --- | ---: |
| 작은 Zig 합성 문서, 함수 3,000개 | 180,780 |
| Zig 합성 문서, 함수 15,000개 | 922,780 |
| 큰 Zig 합성 문서, 함수 50,000개 | 3,127,780 |
| 고정한 build.zig 원문 | 744,535 |
| 고정한 MaruAppHost.swift 원문 | 1,169,769 |

파일 5개 × 입력 종류 8개 × 방식 3개 × 3회 = 360회 실행이다.
입력 종류는 50 ms 간격 20회, 250 ms 간격 6회, 주석·줄바꿈 구조 변경 10회, 여러 줄 붙여넣기,
입력/Undo, 공유 두 뷰, 이미 접힌 상태, 같은 이벤트 안의 입력+접기 명령이다.
시각은 재현 가능한 가상 시계로 진행하고, 입력 사이에는 파싱 재개·재계산 만기에 필요한 프레임을 실행한다.
각 단계의 CPU 경과 시간은 실제 단조 시계로 잰다. 매 입력 뒤 전체 순회를 하면 다음 입력의 트리 캐시를
덥히는 효과가 있어, 정확성 120회와 성능 360회는 별도 실행한다. 성능 실행은 마지막 안정 상태에서만
전체 순회와 비교하며, 이 비교는 시간 구간 밖이다.

ReleaseFast, Apple M4 Max 16 logical CPU, RAM 64 GiB, macOS 26.5.1에서 실행했다.
테스트 allocator를 쓰는 제품 함수 측정이며 물리 키 입력부터 화면 표시까지의 시간은 아니다.
실제 두 원문과 바이너리의 SHA-256, 각 키의 원시 표본, 프로세스 peak RSS를 함께 기록한다.
중앙값·p95는 해당 조건의 입력 표본을 합쳐 계산한다. 전체 프로세스 RSS는 폰트·파서·원문·테스트 저장소도
포함하므로 캐시만의 크기로 해석하지 않는다.

아래는 반복 측정의 입력+다음 프레임 중앙값이다. 지연 방식의 별도 유휴 프레임은 입력 표본에 합치지 않는다.

| 원문 | 기존 전체 순회 p50 / p95 | 변경 범위 갱신 p50 / p95 | 조용 시계 p50 / p95 |
| --- | ---: | ---: | ---: |
| build.zig | 13.56 / 14.21 ms | 7.74 / 8.29 ms | 7.36 / 7.84 ms |
| MaruAppHost.swift | 16.98 / 17.94 ms | 8.47 / 9.09 ms | 8.08 / 9.07 ms |
| build.zig 공유 두 뷰 | 24.67 / 26.14 ms | 13.06 / 15.33 ms | 11.99 / 13.87 ms |
| MaruAppHost.swift 공유 두 뷰 | 30.60 / 32.95 ms | 13.38 / 16.34 ms | 12.99 / 14.37 ms |
| 3.13 MB Zig | 88.83 / 91.13 ms | 39.09 / 45.65 ms | 45.60 / 50.14 ms |

지연 방식은 Swift 빠른 입력이 끝난 뒤 별도 프레임에 13.42 ms, 공유 두 뷰에서 24.19 ms를 사용했다.
느린 Swift 입력에서는 키 사이의 재계산 프레임이 13.69 ms였다. 큰 Zig에서는 입력 후 재계산이
60.39 ms, 두 뷰는 121.44 ms에 이르렀다. 지연 방식은 큰 계산을 제거하지 않고 뒤로 옮긴다.

명시 접기 명령은 최신 범위 승격까지 포함한다. build.zig의 기존/증분/지연 중앙값은
91.47/85.87/91.38 ms, Swift는 51.74/43.33/52.35 ms였다. 지연의 이점은 이 경로에서 사라지고,
범위 설치·가시 줄 재구성의 별도 비용이 남는다. 이미 접힌 상태는 기준과 같은 해제 동작으로 맞췄다.

타이머 만기 150 ms와 실제 계산 시간은 서로 다르다. 가상 시계 만기는 AppKit 스케줄 지연이 아니며,
이 수치를 전면 앱의 키 입력→표시 지연으로 인용하지 않는다.
전체 120개 조건의 수치와 입력 해시는 [실측 결과표](../../tools/editor-fold-measure/results.md)에 둔다.

일반 입력에서 증분 캐시의 후보 배열 backing 저장소는 build.zig 57,240 B, Swift 86,016 B였고 공유 두 뷰는 각각 두 배다.
큰 Zig에서는 두 뷰 합계 최대 6,635,616 B였다. C 트리 참조·결과 범위 배열·일시 할당은 이 값과 별도다.
캐시는 후보 수에 비례하며, 행·byte 이동과 결과 정렬/설치는 여전히 후보 전체를 다룬다.

## 정확성과 검토에서 보강한 부분

- 별도 정확성 120회에서 기존 전체 순회와 매 단계의 머리/끝 행을 대조했다. 기준·증분은 범위 불일치가
  0이었다. 지연 방식은 구조 변경·붙여넣기 중 불일치 15건을 기록했고, 만기 뒤에는 모든 실행에서 같았다.
- 31개 언어, 5개 언어의 무작위 편집 2,000회, 여러 편집 뒤 조회, 전체 교체·빈 문서와 C 트리 반환을 검사했다.
- 무작위 입력만으로는 문서가 빠르게 오류 상태가 되어 정상 선언의 행 이동 결함을 놓쳤다.
  온전한 함수 500개 앞의 줄 삽입, 행 이동과 국소 방문 상한, 블록 주석을 줄 주석으로 바꿔 먼 선언이
  나타나고 사라지는 조건, 한 행의 최장 범위와 다음 줄 0열 끝점을 추가했다.
- 공유 뷰 보조 함수가 이름 없는 문서의 문법을 유지하던 계측 오류를 발견했다. 실제 분할 명령과 양쪽
  파싱 완료 확인으로 교체했다. 단일 뷰의 빠른 편집 경로도 위치 매핑 비용에 포함하도록 보강했다.
- 독립 실패 주입에서 좌표·범위·트리 수명·이전 결과 지우기 등 18개 결함을 런타임으로 검출했다.
  현재 접힘 행 결과에 영향을 주지 않은 두 변이는 등가 대조군으로 구분했다. 컴파일 오류를 검출 성공으로
  세지 않았으며, 주입 전후 원본 대조군은 각각 실제 4/4 통과했다.

접힌 상태 입력은 기준과 같은 단일 뷰 동작(입력 직후 접힌 표시 해제)으로 맞추고 매 단계 확인한다.
입력+접기 명령은 세 방식 모두 명시적으로 최신 범위를 승격한 뒤 `foldAll`을 부르는 실험 모델이다.
이는 현재 제품 명령이 강제 승격을 보장한다는 주장이 아니다. 지연을 채택하면 이 명령 정책과 파싱 진행 중
동작을 제품에 연결해야 한다.

## AppKit 확인

격리한 실제 앱에서 합성 `keyDown` 20회와 제품 `renderTick`을 실행했다. 입력 byte 증가 20과 마지막 접힘
범위가 전체 순회와 같은지 검증하고 Metal readback으로 화면을 남겼다. 50/250 ms 간격을 각각 3회 실행했다.
이는 실제 AppKit 경로이지만 물리 HID나 compositor present의 측정은 아니다.

첫 지연 프로토타입에서는 Swift의 Metal 재칠 표시만 세워 Zig의 프레임 투영이 바로 일어나지 않는 연결
빈틈을 확인했다. 만기에는 backend의 `metal_dirty` 무효화도 필요하다. 보완한 앱으로 같은 잠금·백그라운드
조건을 3회 다시 실행해 마지막 입력 처리 완료 뒤 최신 범위까지 161.2~163.5 ms를 확인했다.
이는 150 ms 실험 지연에 재계산이 더해진 값이며, 입력 20 byte와 최종 범위 일치도 모두 통과했다.
초기 잠금 상태의 측정과 아래 잠금 해제 뒤 전면 측정은 분리한다.

같은 1.17 MB Swift 원문과 고정 바이너리로, 방식·간격별 유효한 3회씩 총 18회/360개 입력을 대조했다.
모든 키에서 전면 앱·key window 상태, 누적 입력 1~20 byte, 마지막 전체 순회 일치와 원본 파일 보존을 확인했다.
시작 활성화 뒤 1초 안정 구간을 두고, 실행 전후 바이너리 SHA-256도 검사한다.
포커스가 바뀐 실행은 제외·보존했으며 각 조건에서 시간순으로 첫 유효 실행 3개를 썼다.
수치가 크거나 작다는 이유로 표본을 고르지 않았다. 진단용 전면 앱 감시 실행은 성능 집계에서 제외했다.

| 입력 간격 | 방식 | 처리 p50 / p95 | 예정 시각→렌더 반환 p50 / p95 | 마지막 처리 후 최신 범위 |
| --- | --- | ---: | ---: | ---: |
| 50 ms | 전체 순회 | 29.08 / 31.15 ms | 31.73 / 35.45 ms | 0.04~0.04 ms |
| 50 ms | 증분 갱신 | 20.54 / 22.53 ms | 23.73 / 26.78 ms | 0.04~0.04 ms |
| 50 ms | 지연 재계산 | 20.21 / 22.50 ms | 23.44 / 26.68 ms | 153.91~163.03 ms |
| 250 ms | 전체 순회 | 29.16 / 31.41 ms | 37.76 / 43.02 ms | 0.04~0.04 ms |
| 250 ms | 증분 갱신 | 20.60 / 22.54 ms | 29.66 / 35.59 ms | 0.04~0.04 ms |
| 250 ms | 지연 재계산 | 20.26 / 22.55 ms | 32.04 / 35.05 ms | 157.13~161.36 ms |

50 ms 간격에서 실제 AppKit 처리 중앙값은 29.08→20.54 ms로 약 29% 감소했다.
예정 시각→렌더 반환은 main queue 대기를 포함하며, 마지막 열은 입력 처리 반환 뒤의 추가 대기다.
증분의 약 0.04 ms는 관측·검증 호출 지연이며 접힘 갱신을 미룬 시간이 아니다.
이 결과도 물리 HID 입력이나 compositor가 실제 픽셀을 표시한 시점까지 잰 것은 아니다.

## 재현과 증거

```sh
python3 tools/editor-fold-measure/run.py --output /tmp/maru-ew2-new --deps "$PWD/zig-pkg"
python3 tools/editor-fold-measure/run.py --output /tmp/maru-ew2-new --deps "$PWD/zig-pkg" --resume --run-only --verify-each-edit 1 --prefix verify --repetitions 1
python3 tools/editor-fold-measure/summarize.py /tmp/maru-ew2-new
python3 tools/editor-fold-measure/summarize.py /tmp/maru-ew2-new --prefix verify --repetitions 1
python3 tools/editor-fold-measure/review.py /tmp/maru-ew2-new
python3 tools/editor-fold-measure/gui.py /tmp/maru-ew2-new --output /tmp/maru-ew2-gui --web-deps "$PWD/web/node_modules" --foreground
```

프로젝트 개발 의존성을 준비한 뒤 실행한다. 출력은 저장소 밖의 새 디렉터리여야 하며, `--resume --run-only`는
기록한 바이너리 해시를 확인해 빌드 없이 같은 행렬을 교차 재생한다. 계측 프로세스끼리의 중복 실행은 잠금으로
막는다. GUI는 사용자 설정·백업·session host와 분리한 프로필에서 실행하고 원본 파일을 저장하지 않았는지 확인한다.

로컬 증거는 `/Users/yoonhb/.cache/maru-agent-artifacts/editor-fold-measure-v2/`의 `inputs.json`, `binaries.json`,
`hardware.json`, `setup-*.json`, `summary.json`, `summary.md`, `run-*.log`,
`verify-summary.json`, `verify-*.log`, `review-v3/`다.
AppKit 로그·PNG·바이너리 해시는 `editor-fold-gui/`, 보완 뒤 대조군은
`editor-fold-gui-wake-background/`에 별도로 보관한다. 초기의 단일 뷰 매핑 누락 결과는
`summary-before-single-view-mapping.json`으로 분리했으며 최종 결과로 인용하지 않는다.
전면 집계는 같은 artifacts 루트의 `editor-fold-gui-foreground-summary.json`이며, 각 표본의 경로·제외 목록을
기록한다. 원시 로그·PNG는 `editor-fold-gui-foreground-final-v2/`, `editor-fold-gui-foreground-final-v3/`,
`editor-fold-gui-foreground-topup/`에 있다. 초기 계측·진단 자료는 이 최종 집계에 섞지 않았다.

## 제품 적용 전에 남은 것

- 후속 [제품 구현](editor-incremental-folds.md)에서 캐시 소유권과 행 좌표를 보강한다. 이 프로토타입의 수치를 제품 결과로 인용하지 않는다.
- 프로토타입의 캐시는 동일한 호출 allocator를 보관한다. 제품 API는 소유자가 저장소를 관리하고 allocator
  수명을 명시하도록 분리해야 한다. Zig OOM 재시도와 파싱 중/언어 변경·LSP 승격의 전체 제품 gate는 후속이다.
