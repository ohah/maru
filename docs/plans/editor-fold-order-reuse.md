# 접힘 후보의 정렬 순서 재사용

상태: #4585가 머지된 main `fd953386b`에 구현했다. 제품 Debug·ReleaseFast의
접힘 정렬·캐시·변경 범위·좌표 검사와 별도 사본의 전후 비교를 통과했다.
#4587은 필수 CI를 통과해 `eefbca9de`로 머지됐다. 해당 main의 문서/config 검사도 통과했다.
그 커밋의 main CI `40178718975`는 취소됐으며 취소 원인은 확인하지 않았다.
이를 포함하는 후속 main `04c78fa1d`의 CI `40182245831`은 성공했다.

## 문제와 선택

`syntax/folds.zig`의 `Cache.query`는 작은 편집 뒤에도 모든 byte 후보를 정렬했다.
`Cache.edit`는 겹친 후보를 안정적으로 제거하고, 뒤쪽의 겹치지 않은 후보에 같은
좌표 차이를 적용한다. 따라서 남은 후보는 시작 오름차순·같은 시작의 끝 내림차순을
유지한다. 구문 구조 변경 범위가 없는 조회에서는 실제 편집 범위로 제거한 뒤의
길이를 정렬된 앞부분으로 잡고, 새 순회가 덧붙인 작은 뒷부분만 끼울 수 있다.

`Cache.orderRecords`는 추가분이 여덟 개 이하일 때 이진 탐색과 겹침에 안전한
뒤쪽 복사로 삽입한다. 여덟 개는 알고리즘 선택 기준이며 후보를 자르는 제한이 아니다.
초기 조회, 구조 변경 범위가 있는 조회, 큰 추가분은 기존 전체 정렬을 사용한다.
구조 변경이 없다는 이유로 실제 편집 범위의 후보 갱신을 생략하지 않는다.

매 조회의 지역 변수만 추가하며 지속 캐시 필드·할당·ABI·접힘 정책을 추가하지 않는다.
중복 제거, byte에서 행으로의 매핑, snapshot 복사, 실패 시 invalidate는 기존 순서다.
범위 설치와 보이는 줄·열 폭·스크롤 갱신도 그대로 실행한다.

## 검증

`test-editor-fold-order`는 4,096개 무작위 후보 배열의 동률·빈 목록·추가분 0~16개,
200개 안정적 삭제·좌표 이동·추가 주기, 실제 native parser의 함수 이름 변경과
구조 추가를 전체 정렬 또는 전체 접힘 재계산과 대조한다. 첫 주기는 전체 삭제다.
비교 함수 자체와 oracle이 함께 틀리지 않도록 같은 시작·다른 끝·중복 후보의 고정
정답도 대조한다. 끝 위치의 정렬 방향을 반전한 결함을 이 정답이 잡고 정상 전후 대조도 통과했다.
기존 캐시의 언어별·무작위 편집·지연 조회·할당 실패·native 해제 검사도 유지한다.

```sh
mise exec -- zig build test-editor-fold-order test-editor-fold-cache \
  test-editor-fold-changes test-editor-fold-points -j2
mise exec -- zig build test-editor-fold-order test-editor-fold-cache \
  test-editor-fold-changes test-editor-fold-points -Doptimize=ReleaseFast -j2
```

실제 정렬 함수의 별도 추출 사본에 비교 방향 반전, 겹친 원소 이동 누락, 추가 후보 처리
누락, 큰 추가분의 전체 정렬 누락, 끝 위치 훼손을 주입했다. 다섯 결함 모두 의미 비교로
거절됐고 각 전후 정상 대조·소스 불변도 통과했다. 이 검사는 native·제품 대조를 대체하지 않는다.

초기 native 실행 경로 확인에서는 숫자 토큰 앞 삽입이 실제 구조 변경 범위 한 건을
만들었다. 전체 정렬로 간 것은 정상이며 결과도 전체 재계산과 일치했다. 기존에 구조
변경 범위가 비는 것으로 확인한 같은 길이 함수명 변경으로 조건을 확인했다.
검증 보조 도구의 함수명 변환·실패 요약 판정 오류도 수정했으며 실패 실행은 보존했다.

## 실측과 한계

[전체 분포와 원시 증거](../../tools/editor-fold-order-measure/results.md)를 따른다.
전체 편집·다음 프레임 비교 240개 실행/3,090편집과 구간 비교 60개/1,200편집을
완료했다. 매 편집 전체 접힘 대조와 기존 계측의 부모/자식 시간·호출 수 계약을 유지했다.
대형 Zig의 조회 중앙값은 일반 0.820→0.507ms, 공유 두 뷰 합계 1.595→0.977ms였다.
전체 편집 시간 차이는 작고 일부 조건은 느렸다. 구간 개선율을 전체 입력 개선율로 쓰지 않는다.

실측은 기존 main `a5b7b22ca` 기반 사본과 정렬 함수만 바꾼 사본을 비교했다.
최종 구현은 이후 이름 변경 IME가 합류한 `fd953386b`에 옮겨 native 검사를 다시 했다.
고정 다섯 입력과 테스트 allocator의 함수 경과시간이며 GUI/HID·GPU present·RSS 검증이 아니다.
동시 컴파일을 관측했으므로 전체 지연 수치는 탐색 자료다. 모든 언어·편집의 최대 이득을
보장하지 않으며 정렬 외 비용을 줄였다는 주장도 하지 않는다.
