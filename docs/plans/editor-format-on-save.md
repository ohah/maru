# 저장 시 포맷 구현 계획

상태: FOS1 완료(한 조각). 계약은 [tooling §8.2r](../editor-surface-tooling.md)이 소유하고, 이 문서는 결정·설계·조각·검증을 소유한다.

## 왜

문서 포맷(§8.2e — `⇧⌥F`)은 있었지만 저장 때 포맷하는 길이 없었다. §8.2e·§8.2k 는 「저장 시 포맷」을 「하지 않는 것」으로 두었다. 그 이유는 §8.1 의 도구 실행 판정(신뢰)이 먼저였기 때문이다. 워크스페이스 신뢰 계획([workspace-trust](workspace-trust.md))이 끝나 서버는 신뢰한 저장소에서만 뜨므로, 그 선행 조건이 섰다.

## 결정 (2026-10-11 사용자)

- **기본은 켬** — 설정 `editor.format-on-save`(기본 `true`). VS Code `editor.formatOnSave` 는 기본 끔이고, Zed `format_on_save` 는 켬이다. 신뢰 전 저장소에는 서버가 없으므로 곧바로 저장한다.
- **서버가 늦으면 시한 뒤 포맷 없이 저장한다** — 저장이 서버 때문에 막히지 않는다. 시한은 1 초다(구현이 정함 — 근거는 §8.2r).
- **사용자의 `⌘S` 만** — 프로젝트 바꾸기·이름 바꾸기의 저장은 포맷하지 않는다. 여러 파일 저장이 파일마다 서버를 기다리고, 바꾸기 결과와 포맷 변경이 섞이는 것을 피한다. VS Code 도 `applyEdit` 저장은 포맷하지 않는다.

## 설계

- **새 상태는 하나다.** §8.2e 의 기다림 자리(`format.State` — 세션 하나)에 `then_save`·`save_deadline_ms` 를 더했다. 요청·변환·revision 검증·적용은 §8.2e 그대로다.
- **진입점**: `editor_save` → `format.saveCommand`. 포맷할 수 있으면(설정·서버 ready·`documentFormattingProvider`·읽기 전용·비교 뷰 아님) 요청하고 저장을 미룬다. 아니면 곧바로 저장한다.
- **저장은 응답 뒤**(`onResponse`): 적용했든 버렸든 그 뒤에 저장한다. 버린 경우(낡은 revision·겹침)는 「…포맷 없이 저장했습니다」를 알린다(§8.2e 의 「버렸습니다」만으로는 저장도 안 된 줄 안다). 오류 응답은 결과 없음과 같다.
- **시한**은 `editor_lsp.pump` 첫머리의 `format.tick` 이 잰다. 언어 서버를 꺼도 잰다.
- **저장과 결과 말하기는 한 함수**(`format.saveNow`)다. `⌘S` 의 즉시 저장과 응답·시한 뒤의 저장이 같은 길을 쓴다(실패는 이유별로, 외부 충돌은 묻는다). 응답·시한 뒤의 실패 알림은 늦은 응답의 규칙(`showResponseNotice`)을 따른다.
- **응답의 출처**: formatting 응답은 그 문서를 연 클라이언트가 보낸 것만 받는다(`format.onClientResponse`). seq 가 클라이언트마다 따로라 다른 저장소 서버의 같은 번호 응답이 남의 문서에 적용될 수 있었다(§8.2e 에도 있던 구멍).
- **읽기 전용 문서**: `⌘S` 가 `ReadOnly` 를 `@errorCast` 해 panic 하던 것을 이유 알림으로 바꿨다(이 계획의 판정자가 드러냈다).
- **선택 없는 문서**: 포맷 적용을 `applyEditAsOneWithUndo` 로 바꿨다. 예전 `applyEditAsOne` 은 선택이 null(열고 caret 을 안 놓음)이면 조용히 실패했다. 이 계획의 판정자가 드러낸 §8.2e 의 결함이고, `⇧⌥F` 도 함께 고쳐진다.

## 한계 (받아들인 것)

- 기다리는 1 초 안에 창을 닫거나 앱을 끝내면 그 저장은 일어나지 않는다. 문서는 아직 수정됨이라 닫기 확인이 묻는다.
- 기다림 자리가 하나라, 다른 문서의 `⌘S` 는 기다리던 문서를 포맷 없이 저장한다.
- 시한은 고정(1 초)이다. 첫 포맷이 느린 서버(빌드를 도는 zls 의 첫 실행 등)는 처음 몇 번 포맷 없이 저장될 수 있다.
- 저장 시 code action(`source.organizeImports` 등)은 [다음 계획](editor-code-actions-on-save.md)이 했다(이 단계보다 먼저 돈다).

## 적대적 검증 (5회)

1. 재진입 — 응답 처리(pump) 안에서 저장·didSave·충돌 상자가 도는 것: 클라이언트 목록을 늘리지 않고 충돌 상자는 surface id 로 다시 찾는다(결함 없음).
2. 저장 진입점 — `⌘S` 외에 새 길을 우회하는 저장(메뉴·팔레트)이 있나: 모두 `editor_save` 하나다(결함 없음). 판정자가 읽기 전용 `⌘S` 의 panic 을 드러냈다(고침).
3. 문서 정합성 — 「저장 시 자동 포맷은 없다」가 네 문서에 남아 있었다(configuration-input·document-model·editor-remaining-work·native-editor — 고침).
4. 여러 서버 — 클라이언트마다 따로 세는 seq 로 다른 저장소 서버의 응답이 남의 문서에 적용될 수 있었다(고침 — `onClientResponse`, FOS2).
5. 알림 문구 — 결과를 버린 저장이 「버렸습니다」만 말해 저장도 안 된 줄 알게 했다(고침 — 「포맷 없이 저장했습니다」).

변이 17개 — 모두 잡혔다(한 번 살아남은 읽기 전용 조기 반환은 판정자를 더해 고정했다).

## 검증

- `FOS1`(제품 경계 — 가짜 서버): `⌘S` 의 요청과 미룬 저장, 응답 뒤 되돌리기 하나와 저장·didSave, 기다리는 동안의 `⌘S`·`⇧⌥F`, 설정 끔·포맷 못 하는 서버·읽기 전용, 남의 클라이언트 응답, 낡은 revision·겹침, 시한(가짜의 `FMTSTALL` — 시한은 구조 필드로 당긴다), 다른 문서의 `⌘S`, 응답 뒤 저장 실패의 늦은 알림, 언어 서버를 끈 뒤의 시한.
- `FOS2`(소스 판정): lsp.zig 는 formatting 응답을 `onClientResponse` 로만 넘긴다.
- `FMT1`·`FMT2`·`LATE5`·`SAV1`·`SAV2` 는 그대로 초록이다.
