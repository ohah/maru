# 비동기 입력 중 구문 강조의 표시 연속성

상태: 사용자 승인 후 구현 완료. 순수 보정·제품 입력·기존 구문 회귀·Metal 대조·전체 경계 검사를 통과했다. 실제 AppKit 연속 입력과 PR CI는 별도 확인 중이다.

## 확인한 현상과 현재 계약

사용자가 실제 입력 실측 중 키마다 하이라이트가 깜빡인다고 보고했다.
`refreshSyntaxForInput`의 일반 비동기 경로는 `parse/client.refresh`를 호출한다.
새 판에서 `State.discardCompleted`는 provider·완료 참조와 본문/미니맵 색 버퍼를 비운다.
`lineColorsInto`는 provider가 없으면 빈 색 목록을 반환하고 새 결과 설치 뒤 다시 색을 만든다.

[기존 제품 연결](editor-async-parse.md#제품-화면-연결)은 "준비 중에는 무색으로 표시한다"고 명시한다.
현재 동작은 진단 후보의 예산 변경에만 한정된 것이 아니라 제품의 일반 입력 경로다.
`observer-work-study-1`의 12프로세스·360입력 모두 첫 표시의 구문 준비가 0이었다.
이는 원시 프레임 상태와 렌더 색 조회 경로의 확인이며, 영상/픽셀 연속성 검증을 대신하지 않는다.

## 승인한 동작과 구현

파싱 중에도 마지막 구문 강조의 **표시 정보만** 편집 위치에 맞춰 유지하고, 현재 판 결과가 준비되면 교체한다.
기존 문서·판 검증, worker 완료 수명, 이전 트리 조회 금지와 실패 중단 정책은 유지한다.
이전 트리를 현재 문서의 구조로 인정하거나 메인에서 다시 파싱하지 않는다.

- 표시 캐시는 native 참조 없이 byte 범위와 색/스타일 값만 독립 소유한다. 원본 문서 신원·revision·문법 신원을 묶는다. 테마의 실제 색 대신 ColorRole을 보관하므로 새 테마가 즉시 해석한다.
- 이미 통과한 편집 범위로 위치를 보정한다. 바뀌지 않은 토큰은 유지하고 삽입/삭제에 닿은 표시 범위는 보정·절단한다. 경계 삽입은 왼쪽 표시를 늘리고 오른쪽 표시를 민다. 문서 시작의 첫 스팬은 시작을 유지한다. 전부 삭제된 스팬은 새 텍스트에 물려주지 않는다.
- 보정 정보가 불완전하거나 다른 문서·언어로 바뀌면 낡은 표시를 사용하지 않는다. 캐시에 없는 새 영역은 기존 무색 경로를 쓴다.
- 표시 캐시는 구문 정확성의 증거가 아니다. 심볼·접힘 승격·구문 괄호·탐색/선택 판정에는 현재 판의 검증된 결과만 쓴다.
- 공유 뷰는 같은 문서 편집을 받되 뷰별 화면 캐시를 독립 관리한다. viewport와 기존 색 조회 예산을 따르고 매 키마다 문서 전체를 복제하지 않는다.
- 캐시 할당/보정 실패는 본문·Undo·IME를 보존하고 해당 표시만 기존 무색 경로로 저하시킨다. 새 엔진 자동 재시도나 입력 거부를 도입하지 않는다.

기존 무색 대기를 바꾸는 사용자 승인에 따라 [시각 매핑](../native-editor-visual-mapping.md)과 비동기 계획을 동기화한다.

`src/syntax_paint.zig`의 `Cache`는 호스트 중립의 표시 보정 계약이다.
기존 `ColorBufs.byte_spans`를 재사용하며 본문과 미니맵은 각각 metadata를 갖는다.
편집 중 추가 할당이나 문서 복제는 없다. 마지막으로 질의한 원본 byte 범위로 캡처를 잘라
질의 밖의 새 스크롤 영역에는 색을 추측하지 않는다. 캐시가 없는 첫 표시도 무색이다.
여러 편집을 한 번에 전달한 포괄 범위에서는 내부의 전부 지워진 표시를 버리고 외부만 보정한다.
따라서 Undo·다중 커서의 임시 표시가 부분적으로 줄어들 수 있고, 완료 후 현재 결과로 채운다.

`parse/client.refreshForEdit`는 begin 성공 때만 보정하고 `discardForPaint`로 native 자원을 반환한다.
문서/문법 재설정·수동 재분석·창 해제·새 완료 설치는 기존 `discardCompleted`로 표시도 버린다.
`lineColorsInto`는 provider가 없는 동안 현재 신원·길이가 맞고 pending인 표시만 사용한다.
실패 중단 후 옛 색을 계속 보여 주거나 편집으로 엔진을 자동 재시도하지 않는다.
semantic·괄호의 기존 역할 값도 임시 paint에 포함될 수 있지만 구조 정보는 전혀 보관하지 않는다.

## 검증

현재 판 조회와 임시 paint를 분리하는 순수 계약을 호스트 중립 계층에 둔다.
삽입·삭제·치환·UTF-8/한글·줄바꿈·연속 편집·Undo/Redo·공유 뷰·스크롤·문법/문서/테마 교체·
할당 실패·실패 엔진·늦은 완료·문서 닫기를 검사한다. 기존 native 참조 수명과 구조 판정을 회귀 검증한다.

실제 Metal 경로에서 입력 전/대기/완료 프레임을 기록해 바뀌지 않은 토큰의 색이 무색으로 빠지지 않는지 확인한다.
최종 구문 색은 동일 입력의 현재 판 결과와 같아야 한다. 구문 준비 비트만으로 시각 문제가 해결됐다고 판정하지 않는다.

## 확인된 결과와 남은 검증

`test-editor-parse-input`은 Debug·ReleaseFast에서 순수 paint gate와 제품 입력 gate를 통과했다.
기존 완료 설치·구문 회귀, 문서 링크/행 참조, 전체 `check-boundaries`, macOS 앱 bundle도 통과했다.
초기 경계 검사가 발견한 한글 fixture 예외 원장 누락은 해당 파일의 주석과 원장 합계를 함께 고쳤다.
새 제품 테스트가 서로 다른 viewport 범위를 비교하던 오류도 동일 범위로 고친 뒤 재검증했다.

`tools/editor-highlight-continuity/capture.py`로 baseline
`cdb01f1246160932fb27a89df5b8e0a2632fa1a0`과 후보 제품 소스
`98163b4578f8ed4b8e21b8dba33cdd6e0a6d35c9`를 비교했다.
기본 어두운 테마·800×480·함수명 한 글자 편집에서 입력 전과 완료 후 PNG는 각각 동일하고,
수정 후 pending PNG는 completed PNG와 완전히 같았다. 수정 전 pending은 색이 빠졌다.
첫 촬영은 ready 프레임의 헤더 배치가 안정되지 않아 따로 보존하고, 최종 대조는 워밍업 뒤 수행했다.
원본/후보 src와 build 해시를 커밋과 대조했으며 결과는
`~/.cache/maru-agent-artifacts/highlight-continuity-metal-2/`에 보존한다.

`Cache` metadata는 로컬 aarch64 빌드의 `@sizeOf` 실측에서 72바이트다(타입이 값의 소유자).
뷰마다 본문/미니맵 두 개를 두고 기존 색 배열을 재사용한다. 편집 보정 자체는 할당하지 않는다.
실제 AppKit 연속 입력은 화면 조작 시간 확인을 기다린다. 이 Metal fixture 증거는 실제 OS 키보드·
IME·연속 영상·광학 표시 시각의 증거가 아니며 첫 표시 지연이나 전력 개선을 주장하지 않는다.
