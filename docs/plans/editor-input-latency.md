# 비동기 파싱 전환의 실제 입력 표시 지연

상태: 외부 고정 주기 48프로세스·1,440입력과 후속 6프로세스·180입력의 주소 조사를 완료했다.

## 질문

일반 편집기의 파싱을 worker로 옮긴 뒤 입력을 담은 화면이 빨리 나오는지, 구문 색과 괄호 색의
완성이 늦어지는지, 앱 메모리가 늘어나는지 같은 조건에서 비교한다. 이전 native C 함수 시간은
GUI 지연의 근거로 쓰지 않는다.

## 대조 설계

같은 제품 HEAD와 실행 파일에서 기존 내부 동기 경로와 비동기 제품 경로만 바꾼다.
과거 커밋을 각각 빌드하면 그 사이의 LSP/렌더 변경이 섞이므로 이 실험은 모드의 효과를 분리한다.
두 경로의 실제 상태도 읽어 이름만 바꾼 실험을 거절한다. 제품 소스는 바꾸지 않고 외부 사본에만
입력·성공한 frame 게시·인코딩·Metal 표시 시각을 잇는 witness를 둔다.

3,000/50,000 함수와 일반 입력·실제 두벌식·동일 문서 2분할을 비교한다. 각 모드 독립 3프로세스,
30입력의 원문·실행 순서·PID·해시·실제 문자열을 보관한다. 포커스를 잃거나 결과가 불완전한 실행은
성능 모집단으로 쓰지 않는다. 구체적인 명령·필드·집계 기준은 [도구 계약](../../tools/editor-input-latency/README.md)을 따른다.

## 해석

첫 변경 프레임, 문법 준비 프레임, 괄호까지 준비된 프레임의 표시를 따로 비교한다.
RSS 최대값은 앱 시작을 포함하므로 입력 순간의 추가 할당량과 같다고 주장하지 않는다.
측정 사본의 공통 관측 비용·호스트 스케줄링·vsync를 포함한 제한된 workload의 비교다.
원시 자료의 누락·오염을 독립적으로 거절한 뒤에만 다음 병목과 개선 필요성을 정한다.


## 사전 실행과 범위

최초 실행은 일반 launch의 deferred surface가 준비되지 않아 표본 없이 종료됐다. 기존 IME smoke의
초기화와 같은 제품 이벤트/렌더 경로로 진입하도록 외부 사본의 수명 설정을 맞췄다.
Debug 실행은 본 통계에 사용하지 않으며 본 빌드는 ReleaseFast로 고정했다.

ReleaseFast 사전 실행에서 큰 문서의 비동기 괄호 색은 한 입력 후 약 18초, 다음 입력은 20초 마감에
도달했다. 원시 기록은 `input-latency-preflight-release`에 보존한다. 빠른 글자 표시와 혼동하지 않는다.
본 실험은 첫 글자가 표시된 뒤 입력을 이어가며, 마지막 입력 뒤 색 완성을 따로 관측한다.
현재 Mac에는 높은 시스템 부하가 관측되어 실행별 load average를 함께 기록한다.
조용한 환경의 일반적인 개선량으로 확대하지 않는다.

## 실측 결론과 후속

[결과와 한계](../../tools/editor-input-latency/results.md)에 6조건별 첫 표시·문법/괄호 색·RSS를 기록했다.
큰 문서는 첫 표시가 빨라졌고 작은 문서는 느려졌다. 큰 문서의 비동기 괄호 색 복구는
중앙값 약 13–14초였으며 최대 29.54초를 포함해 보존했다. blink 주기만 바꾼 별도 관측은
후속 프레임 공급 의존을 보여 주었다.

최초 측정 PR은 런타임 변경 없이 도구·검증·결과만 반영했다. 당시 단순 플래그 보존 실험의
표시 검증 실패는 수정 성공으로 계산하지 않았다.

## 후속 프레임 요청 보존

제품 `tick()`으로 성공한 전체 프레임 게시까지 실행한 판정자에서, 괄호 목록이 미완료인데
`metal_dirty`가 지워지는 것을 재현했다. 기존 `BPP3`은 `appendPaneFrame`까지만 호출해서
게시 뒤 소거를 검출하지 못했다. `advanceSyntax`는 괄호 순회나 동기 파싱의 미완료 요청에
`reproject_after_frame`을 함께 세운다. 게시 실패 때의 기존 dirty 유지와 준비 완료 뒤 idle은 유지한다.

판정자는 아주 작은 괄호 예산과 긴 blink 주기로 외부 입력 없이 계속되는지 검사한다.
동기/비동기·공유 2분할·IME preedit·중간 편집/Undo·색/강조 옵션·작업 중 비활성화·빈 문서·
미지원 문법과 완료 뒤 idle을 대조한다. 실제 표시 지연은 ReleaseFast 앱에서 별도 재측정한다.

[수정 후 결과](../../tools/editor-input-latency/continuation-results.md)에서 큰 문서의 마지막 입력 후
괄호 색 복구 중앙값은 일반 13.06→0.69초, 두벌식 14.09→0.74초, 공유 분할 13.55→0.85초였다.
blink 500/100ms 별도 진단도 약 686/683ms로 비슷해졌다. 첫 표시·RSS·거절 실행·수집기 변경과
높은 호스트 부하의 한계를 함께 기록했다. 큰 문서의 빠른 연속 입력 중 pending 저하까지 없앤 것은 아니다.

## 단계 분해와 timer 대조

[단계별 결과](../../tools/editor-input-latency/stage-results.md)는 기존 36프로세스의 시각을 다시 검증했다.
큰 문서는 문법 준비 표시 이후에도 약 467ms와 28–29개 프레임 세대가 더 필요했다.
별도 18프로세스에서 요청 timer 주기만 30/60/120Hz로 바꾸면 그 구간은 약 947/507/373ms였다.
제품 기본값 60Hz는 유지하며 CPU·전력이나 worker 이관 효과를 측정한 것으로 해석하지 않는다.

기존 수집기는 앱 메인이 다음 입력도 게시하는 닫힌 루프다. 120ms는 최소 관측 대기이며 실제
입력 간격은 큰 문서에서 중앙값 약 347–500ms였다. 이 수치를 외부 고정 주기 연타의 결과로 쓰지 않는다.

## 외부 고정 주기 입력

[독립 생산자 계약](../../tools/editor-input-stream/README.md)은 별도 프로세스가 절대 시각에
PID 대상 ASCII 키를 게시하고 native 도착·정확한 문서 접두부·실제 Metal 표시를 연결한다.
앱 메인을 500ms 멈춰도 그 사이 5개 게시가 계속되는 것을 검증했다. 표시 관측 제거와 입력 ID
누락을 실제로 실행했으며, 원시 기록의 의미 손상을 거절하는 정상 전후 대조도 유지했다.

[48프로세스 결과](../../tools/editor-input-stream/results.md)는 두 문서 크기·100/50ms·단일/공유
분할·동기/비동기·독립 3반복의 1,440입력을 첫 키부터 모두 포함한다. 비동기가 모든 조건에서
빠르지는 않았다. 큰 문서·공유 분할·100ms에서는 비동기 native 도착 전 대기가 세 반복 모두
약 140–148ms의 중앙값으로 관측됐다. 이를 아래의 같은 입력 조건 주소·스택 조사로 이어갔다.
이 타이밍만으로 CPU 비용이나 특정 함수의 원인을 확정하지 않는다.

수집 전 provider 훅 자동 갱신과 초기 마감 지각을 발견했다. 현재 측정 사본은 해당 설치·정리를
막고 실제 설정 해시를 검사하며, 초기 준비를 일정 시작 전에 수행한다. 준비 실패·사용자 훅 경로
복구 확인 중인 사항과 기존 HID 경로와의 차이는 결과 문서에 기록한다. 제품 동작은 바꾸지 않았다.

## 준비 뒤 메인 실행 위치 조사

PR #4666은 `c84b6659782a9343e506cd080ec8954f85272b91`로 머지됐다.
[후속 주소 조사](../../tools/editor-input-attribution/README.md)는 기존 불변 앱의 준비 뒤에
Time Profiler를 붙여 고정 입력을 유지했다. 동기/비동기 각각 3프로세스·30입력의 진단이며
프로파일러의 시각은 정상 성능 모집단에 넣지 않는다. SDK 기록 시작 통지를 받은 뒤 생산자를
시작하고, trace 재내보내기와 실제 주소·dSYM·atos를 대조한다.

[반복 결과](../../tools/editor-input-attribution/results.md)에서 비동기 main Running 표본은
접힘 승격 경로 약 44%, 고정 머리줄의 심볼 확인 경로 약 41%의 포함 weight를 보였다.
동기 경로와 차이를 보인 실제 메인 실행 위치를 좁힌 것이며, 키별 지연 원인이나 개선율의
확정은 아니다. 다음은 비동기 결과 설치의 캐시 재구축 재현과 프로파일러 없는 대조다.

후속 [심볼 요약 준비](editor-async-sticky-preparation.md)는 실제 설치 후 두 뷰의 첫 조회 재구축을
재현하고 기존 요약 복제 경로를 워커에서 준비했다. 같은 실행 파일의 48회/1,440입력
[대조 결과](../../tools/editor-input-stream/summary-results.md)에서 준비 유무와 뷰 재구축을 확인했다.
접힘 캐시의 소유권 변경은 포함하지 않는다.

대상·recorder에는 환경 허용 목록을 적용하고, TOC의 알 수 없는 환경 키를 거절한다.
환경 허용 목록 적용 전의 사전 실행은 채택하지 않으며 공개 결과에는 환경 값을 싣지 않는다.


## 완료 접힘 후보 준비

[후속 구현](editor-async-fold-preparation.md)은 완료의 byte 후보를 워커에서 만들고 뷰의
기존 배열에 독립 복사한다. 각 뷰의 줄 투영과 접힌 상태는 유지한다. 준비 끔/켬의
같은 바이너리 대조와 worker/뷰 OOM·취소 검증은 해당 계획과 결과 문서를 따른다.
