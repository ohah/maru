# 큰 문서의 native 파싱·변경 범위 비용 귀속

상태: 실제 main `fc2d697cfbc4732f5dc06508b86832e50c19215a`의 기준 실측과 별도 콜백 진단을 수집했다.
판정기·독립 원시 대조·다섯 적대적 가설과 실제 C 양성 대조를 완료했다. `c683e1250` 리베이스 뒤 전체 경계·문서/config 702개 빌드 단계와 단위 8개를 통과했다.
후속 main `3084f9136`의 LSP·사이드바 IME 변경과 합류한 뒤 전체 702개 빌드 단계·단위 8개와 실제 C 대조도 통과했다.
실측 표본의 제품 기준은 계속 `fc2d697cf`이며 LSP 변경 뒤 성능을 측정했다는 뜻은 아니다.
선행 PR #4602는 원격 PR 검사 뒤 실제 머지됐고 검토한 head와 전체 트리가 같다.
실제 main의 집중·문서/config 69개 빌드 단계와 메인 push의 CI·Performance·Packages도 모두 통과했다.

## 확인할 문제

[본문 색 조회 실측](../../tools/editor-visible-colors/results.md)의 리베이스 전 자료에서는
큰 합성 Zig의 Provider 포함 시간이 여전히 컸다. 이는 새 main의 원인이나 개선량을 확정하는
근거가 아니다. 현재 제품의 native 파싱과 변경 범위 계산을 새로 재현하고 작업량을 대조한다.
Worker 이동·저장소 재설계·편집기 UX·파싱 예산 변경을 이 측정만으로 승인하지 않는다.

## 계측 계약

제품 src·빌드·ABI·설정·저장 형식은 바꾸지 않고 저장소 밖 사본에만 계측한다.
기존 `tools/editor-provider-measure/`의 준비·타이머·본문/접힘 대조와 provenance를 재사용한다.
Provider 포함 시간과 그 안의 native 호출·변경 통지·변경 범위 시간을 구분하며 중첩 구간을 더하지 않는다.
awake 경과시간과 스레드 CPU 시간을 혼동하지 않는다. 이 자료는 전자를 측정한다.
기존 형식을 느슨하게 바꾸거나 옛 원시 표본의 메타데이터를 고쳐 새 형식으로 채택하지 않는다.

추가 관측은 실제 호출 경계에서 입력별로 기록한다. 구현 전 다음 의미를 유지한다.

- 파싱 호출: 옛 트리 전달 여부, 원문 길이, 호출 예산, 완료/미완료 결과와 호출 수.
- reader 콜백: 호출 수와 API에 제시한 바이트 수. 슬라이스 끝까지 제시해도 C 파서가 그 전부를
  소비했다는 뜻은 아니다. 중복 제공 합계와 실제 lexing 작업량을 혼동하지 않는다.
- progress 콜백: 호출 수와 취소 반환 수. 실행 중 파싱을 단순 관측 시간 초과로 실패 처리하지 않는다.
- 변경 범위: 실제 native 호출 수와 반환 개수·통지의 범위. 공유 뷰의 기존 인계/재사용 경로와 구분한다.

옛 트리를 전달했다는 사실만으로 실제 노드 재사용이나 완전 파싱 여부를 확정하지 않는다.
공개 API만으로 작업량이 드러나지 않으면 그 한계를 남기고 별도 진단의 필요성을 판단한다.
추가 진단·전수 대조의 비용은 성능 구간 밖에 두고 별도 실행과 실행 파일 해시로 구분한다.

## 표본과 대조

고정 Zig 3,000·15,000·50,000 선언과 실제 build.zig·Swift 호스트의 다섯 원문을 고정한다.
기존 원문의 바이트·해시를 재사용할 수 있지만 옛 시간 표본은 새 모집단에 섞지 않는다.
일반/공유 입력은 성능 3프로세스×20입력과 별도 정확성 1프로세스×20입력으로 구분한다.
기본 모집단은 40프로세스, 성능 600입력과 정확성 200입력이다. 준비 실행은 제외한다.
추가 콜백 진단은 별도 바이너리의 10프로세스·정확성 200입력이다. 기본 40프로세스와 섞지 않고,
추가 계수 작업이 들어간 진단 시간으로 기본 성능 표를 만들지 않는다.
첫 입력·미완료·재개를 임의로 빼지 않고 실제 호출 경로와 맞는 판정 모델로 기록한다.
입력·원본/계측 소스·빌드·도구·실행 파일·원시 기록을 해시로 묶고 바이너리를 캐시 밖에 보존한다.
이번 일반/공유 workload의 실제 입력은 공백 한 글자 삽입 20회다. 구조 편집·붙여넣기·Undo로 확대하지 않는다.

## 채택 기준

정상 제품 결과·호출 수·시간 포함 관계·모집단·근거 파일을 확인하고 독립 원시 계산으로 대조한다.
다섯 독립 적대적 가설에서 잘못된 관측을 거절하고 각 가설 전후 정상 대조를 보존한다.
컴파일 오류나 선택 개수 오류를 의미 결함 검출로 세지 않는다. 실패 자료를 덮어쓰지 않는다.
관측 결과에 따라 다음 변경 대상을 고르며 원인이 재현되지 않으면 제품 최적화를 추가하지 않는다.
GUI/HID·실제 GPU present·사용자 체감 지연·RSS·모든 언어의 최악 비용으로 일반화하지 않는다.

## 확인한 결과

[전체 표와 범위](../../tools/editor-native-parse-measure/results.md)와
[재현 명령](../../tools/editor-native-parse-measure/README.md)을 함께 본다.
기준 40프로세스의 성능 600·정확성 200입력과 별도 진단 10프로세스의 정확성 200입력을 대조했다.
진단에서는 옛 트리 전달·완료·reader 호출이 입력마다 한 번이었다. 제공 바이트나 progress 횟수로
실제 노드 재사용·전체 재파싱 여부를 확정하지 않는다. 다음 변경 선택에는 native 내부 작업량 진단이 더 필요하다.

정수 버전에 bool/float를 허용하던 판정을 고쳤고, 기준·진단 바이너리를 같은 것으로 바꿔도
받아들이던 빈틈도 수정 전후 재현으로 확인해 막았다. 다섯 독립 가설의 실제 기록 손상 29건을 거절하고
정상 전후 대조 10건을 통과했다. 독립 token reader에서 시간 180필드·콜백 140필드·첫 입력 10그룹이 일치했다.
실제 C 양성 대조는 초기/구조 변경 파싱의 EOF·반환 범위와, 대조 사본에서 강제한 만료 조건의 취소·재개를 확인했다.
전용 선택 2개가 통과했으며 이 대조의 시간은 성능 표에 넣지 않는다. 제품 소스는 그대로다.
