# Native 파싱 내부 비용의 샘플링

상태: 수집기·주소 기반 판정기의 최초 순수 단위 30개를 구현했고, GUI 이미지 바인딩 확장 후 현재는 32개다.
측정 커밋 `54aacc5b7`의 기준 40프로세스와 별도 프로파일 30개를 채택했다.
원본 trace의 SDK 재내보내기와 독립 주소/통계 reader의 대조도 통과했다.
다섯 가설의 실제 손상 23건 거절·정상/등가 대조 12개를 통과했다. `aa4d1fbb8` 기준 전체 경계·문서/config 702개 단계도 통과했다. 추가 통합 검사·원격 CI 결과는 PR #4607 본문에 분리해 기록한다.
[실측 결과](../../tools/editor-native-sampling/results.md)는 시간 분포·함수 비중과 한계를 구분한다.
[선행 계측](editor-native-parse-attribution.md)의 PR #4604는 실제 main `54aacc5b7`로 머지됐고
전체 통합 트리 대조·머지 후 단위 8개와 보관 C 실행 파일의 테스트 2개도 통과했다.

## 확인할 문제

공개 API 콜백의 제공 바이트·progress 횟수만으로 실제 노드 재사용이나 native 내부의 병목을
확정할 수 없다. [프로파일링 전략](../profiling.md)의 opt-in macOS 샘플링으로
`ts_parser_parse_with_options`와 `ts_tree_get_changed_ranges` 아래의 실제 스택을 관측한다.
제품 src·빌드·ABI·UX·저장 형식은 유지한다. 외부 구현 코드는 복사하지 않는다.

## 이미 확인한 수집 가능성

기존 `fc2d697cf` 기준의 해시를 보존한 실행 파일과 50,000 선언 Zig 원문을 재사용했다.
새 main의 성능 표본으로 채택하지 않는, 도구의 가능성 확인 자료다.
공유 편집에서 공백 한 글자 삽입 20회를 실행했고 기존 제품 판정과 선택한 테스트 5개가 통과했다.

- 첫 입력 완료 뒤 `/usr/bin/sample`을 붙인 실행은 exit 0이어도 스택이 하나도 없었다.
  호출 그래프가 빈 결과를 native 비용 자료로 채택하지 않는다.
- 실행 전에 연결한 Time Profiler는 대상의 정상 종료와 PID를 기록했다.
  원시 XML 1,569행 중 스택 1,563행·스택 없는 sentinel 6행을 구분했다.
  파서 또는 변경 범위 함수가 있는 행은 760개, 편집 함수 문맥이 있는 행은 565개였다.
  두 부분집합은 겹칠 수 있어 더하지 않는다.
- 이 trace는 초기 준비·워밍업·편집을 포함한다. 전체 trace의 native 비율을 편집 한 번의
  비용으로 읽지 않는다. 포함 스택의 weight 역시 서로 겹치며 호출별 경과시간이 아니다.
- feasibility 자료는 저장소 밖 `native-sampling-feasibility-1`·`-2`와 독립 readback에 보존한다.
  두 번째 원시 trace·XML·대상 로그의 전체 크기는 약 6MiB 이내다.

## 반복 수집에서 확인한 보강점

실제 XML에는 이미지가 없는 주소 frame과 이름이 있는 미해결 frame이 모두 있었다.
이를 누락하거나 이름만으로 native 함수에 넣지 않고 별도 미해결 표본으로 보존한다.
또 실행 중 사용하는 frame 계약 파일과 그 해시를 함께 빼도 통과하던 근거 목록을
수정 전 실패·수정 후 통과로 재현해 필수 계약에 추가했다.

같은 바이너리의 일부 trace는 Zig 편집 함수의 이미지 연결이 없어 기존 이름 판정에서 빠졌다.
바이너리에는 해당 함수의 심벌이 존재했다. 재내보내기와 dSYM을 연결한 trace에서도 이름 판정은
실패했지만, 코드 영역 안의 주소 14개는 `nm`과 보관 dSYM의 `atos`가 같은 실제 함수를 가리켰다.
독립 대조 자료는 저장소 밖 `native-sampling-address-association-proof-1`과
`native-sampling-dsym-atos-readback-1.json`이다. 원시 trace/XML은 그대로 보존했다.
주소를 복원한 진단용 XML 사본은 최종 프로파일 모집단으로 채택하지 않는다.

후속 `symbols.py`는 공개 SDK의 `mach-o/loader.h` 선언에서 UUID와 코드 영역을 읽는다.
대상 PID·실행 이미지 UUID·유일한 load address를 대조한 뒤 실제 코드 영역의 주소만
보관 dSYM의 `atos`로 해석한다. 심벌 파일의 UUID는 보관 실행 파일과 같아야 한다.
검증에서도 같은 주소를 SDK 도구로 다시 대조한다. 주소 목록·명령·원시 출력·심벌 파일의
전체 해시를 보존하고, 확인할 수 없는 주소는 미해결로 남긴다.
심벌 시작 주소에서 단순히 가장 가까운 이름을 고르는 방식만으로 함수 범위를 확정하지 않는다.

## 수집 계약

측정 커밋으로 고정한 Git 소스의 별도 사본에서 기존 Provider 기준 수집기를 사용한다. 기준 성능·정확성은
선행 도구의 모집단을 유지하고, 프로파일러가 연결된 실행의 시간을 기준 성능에 섞지 않는다.
고정 원문 다섯 개와 일반/공유 입력을 각각 세 프로세스로 샘플링한다. 프로세스마다 첫 입력을
포함한 20편집과 제품 판정이 통과해야 한다. 준비 빌드와 별도 정확성 실행은 구분한다.

Xcode의 `xctrace`는 opt-in 개발 도구다. 런타임 의존성이나 일반 제품 실행 경로에 추가하지 않는다.
대상 실행 전에 기록을 시작하고, 프로세스 종료 결과·실제 PID·실행 이미지·보관 바이너리의
identity를 함께 대조한다. 관측 구간이 끝났다는 이유로 제품 편집을 실패로 해석하지 않는다.
모든 기록은 새 외부 경로에 보존하며 기존 실패 자료를 덮어쓰지 않는다.

원본 Git 소스·실제 계측 사본·수집 도구·입력·보관 실행 파일·대상 로그·trace·export XML을
해시로 묶는다. 현재 머신의 기기 이름·UUID·환경 전체를 공개 결과에 옮기지 않는다.
프로파일링 준비로 늘어나는 사본과 캐시는 공유 디스크 여유와 활성 빌드를 확인한 뒤 만든다.

## 판정 계약

XML의 열 순서·engineering type과 ID/ref의 유일성·참조 타입·순환을 검사한다.
실제 대상 PID의 행만 채택하고, sentinel은 전체 모집단과 누락 weight에 남긴다.
빈 스택·알 수 없는 열·다른 대상·정상 종료가 확인되지 않는 자료는 비용 판정에 사용하지 않는다.

전체 프로세스와 실제 편집 호출 문맥을 구분한다. 편집 문맥의 근거는 핀한 소스와 실행 파일의
실제 함수 스택이다. 최적화·인라이닝으로 문맥이 없으면 그 자료로 편집 비용을 확정하지 않는다.
한 행에서 같은 함수가 재귀적으로 나타나도 포함 weight는 한 번만 더한다. self weight와
누락 weight의 합은 전체 weight와 같아야 한다. 중첩 함수의 포함 weight를 더하지 않는다.

초기 성공 대조가 다섯 가설에서 실제 손상을 거절하고, 각 손상 전후 정상 자료는 통과해야 한다.
컴파일 오류·선택 실패·XML 문법 오류만으로 의미 결함 검출을 대신하지 않는다.

1. exit 0이지만 표본·스택·편집 문맥이 없는 자료.
2. 대상 PID·실행 이미지 또는 바이너리 근거가 일치하지 않는 자료.
3. 유효 XML이지만 ID/ref·열 타입·sentinel 모집단이 어긋나는 자료.
4. 초기 준비를 편집으로 분류하거나 재귀·중첩 스택의 weight를 중복 집계한 자료.
5. 입력·제품 결과·명령·Git 소스·로그 또는 보존 파일이 다른 자료.

독립 원시 reader로 표본 개수·문맥 분류·weight 합과 상위 함수를 대조한 뒤에만 결과를 채택한다.
이 단계는 내부 비용의 위치를 좁힌다. 실제 노드 재사용 개수·스레드 CPU 시간·GUI 입력·present·
RSS·모든 언어의 최악 비용이나 개선율은 별도 근거 없이는 확정하지 않는다.
