# 편집기 B2 op 저장소 후보 판정 (2026-09-29)

이 문서는 [native-editor.md](native-editor.md) B2의 **실험 기록**이다. 저장소 방식이나 메모리 상한을 확정하지 않는다. 실험 코드는 `frame.zig`의 `B2` 판정자에 있다.

## 동일 출력과 비용

80행 × 160열, 각 행에 1글자 검색 표식 120개를 둔 화면은 총 **9,762 op**를 낸다. 그중 검색 강조가 9,600개, 다른 층이 162개다. 기존 2,560 op 저장소에서 다른 층을 전부 보존하는 층별 상한을 쓰더라도 검색 강조는 최대 2,398개만 남고 **7,202개(75.0%)가 빠진다**. 층별 우선순위는 중요한 조작 표시를 지킬 수 있지만, 이 크기의 저장소에서 온전한 화면을 만드는 방법은 아니다.

`paintRowMarksInto`에 고정 슬라이스와 `ArrayList` writer를 붙여 **동일한 좌표 계산으로 9,600개 op을 실제 방출**했다. 결과 op은 내용까지 같았다. macOS ReleaseFast, 프로세스를 새로 띄운 세 번의 실행에서 40회 평균은 다음 범위였다. 단위는 µs다.

| 검색 강조 방출 | 세 번의 범위 | 저장소 |
|---|---:|---:|
| 충분한 고정 슬라이스 | 40–43 | 9,600 op 이상 |
| 2,560개부터 늘리는 새 `ArrayList` | 214–216 | 최종 1,453,088바이트 예약 |
| 전 프레임의 가변 용량을 유지한 `ArrayList` | 72–73 | 동일 용량 재사용 |

프레임 전체를 충분한 16,000 op 저장소로 **한 번** 그린 시간은 813–824µs, 2,560 op에서 절단된 뒤 16,000 op로 **재그리기**는 1,197–1,230µs였다. 재그리기의 추가 비용은 383–406µs다. 검색 writer의 시간과 전체 프레임 시간은 **서로 다른 범위의 측정**이므로 단순 합산해 통합 가변 프레임 시간을 주장할 수 없다. 실제 통합 writer는 본문·gutter·막대·sticky까지 바꾸어 재야 한다. Debug 측정(고정 448µs·새 가변 2,638µs·재사용 878µs)은 빌드 모드의 영향이 커서 제품 시간의 근거로 쓰지 않는다.

## 재그리기 동등성

`frame.build`는 `RowCache`를 읽기만 하지 않는다. 한 호출에서 최대 2,048줄의 접두합을 채운다. 2,049줄 랩 문서에서 작은 op 버퍼로 한 번 그린 뒤 재호출하면, 충분한 버퍼로 **처음부터 한 번** 그린 경우보다 캐시가 한 줄 더 전진하여 전체 시각 행 수와 스크롤바 축이 달라진다. 판정자가 실제 불일치를 재현했다. 첫 호출 전 캐시 메타데이터·접두합을 복원한 뒤 재호출하면 op 내용과 전체 행 수가 한 번 그리기와 같아졌다. 따라서 재그리기는 불가능한 방식이 아니라 **캐시 상태 트랜잭션을 추가해야 하는 방식**이다. 이 실험은 `RowCache` 외의 모든 가변 상태에 대한 동등성 증명이 아니다.

## 큰 화면과 실패 경로

200행 × 300열에서 검색 강조와 줄 전체 진단 지그재그가 겹치면 **175,001 op, 실제 op 바이트 19,600,112**가 나왔다. 2,560개부터 늘린 `ArrayList`의 최종 예약 용량은 **24,835,552바이트**였다. 여러 pane이 각자 이 크기의 버퍼를 유지한다면 합이 커진다. 한 세션에서 버퍼를 공유·재사용하는 설계라면 합산 방식이 달라지므로, 소유 범위를 정하기 전에는 창 메모리 증가량을 확정할 수 없다. 할당 실패 주입 판정자는 가변 writer가 크래시 대신 부분 출력과 실패 신호를 남기는 것을 확인했다.

## 잠정 판단과 남은 결정

- **층별 상한만**으로는 일반적인 조작 표시를 보호할 수 있지만, 밀집 화면의 빠진 검색 강조를 복원할 수 없다.
- **절단 후 재그리기**는 기존 컴포넌트의 고정 슬라이스 계약을 덜 바꾸지만 캐시 롤백이 필수이고, 절단 프레임에 전체 그리기 한 번이 더 든다. 절단의 실제 발생 빈도는 측정하지 못했으므로 평상시 평균 비용은 모른다.
- **호출자 소유의 재사용 가변 writer**는 이 검색 층에서 출력 동일성과 낮은 ReleaseFast 추가 비용을 보였다. 전체 편집기 writer의 시간·OOM 정책·Windows 호스트·Chrome Lab·diff/merge 배선은 아직 검증하지 않았다. 큰 화면의 수십 MB 요구를 보았으므로 무상한 증가는 후보에서 제외한다.

따라서 다음 구현 후보로는 **호출자 소유의 재사용 가변 writer + 명시적 메모리 상한 + 상한/OOM에서 중요한 층을 보존하는 부분 출력**을 권한다. 이것은 구조 변경 제안이며 확정된 프로젝트 규칙이 아니다. 상한 수치와 버퍼 소유 범위(세션 공유인지 pane별인지), 실제 통합 writer의 출력·성능을 검증한 뒤 B2 방식을 결정해야 한다.

재현 명령: `mise exec -- zig test -OReleaseFast -lc -Mroot=src/ui_test.zig --test-filter 'B2 검색 표식의 실제'`와 같은 명령의 필터 `B2 밀집 화면의 한 번`, `B2 큰 화면의 겹친`, `B2 재그리기 반례`. 전체 편집기 판정은 `mise exec -- zig build test-editor`, 이식성은 `mise exec -- zig build check-targets` 및 libc 없는 Linux `zig test -ODebug -target x86_64-linux -Mroot=src/ui_test.zig -fno-emit-bin`으로 확인한다.
