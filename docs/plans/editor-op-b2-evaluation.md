# 편집기 B2 op 저장소 후보 판정 (2026-09-29)

이 문서는 [native-editor.md](native-editor.md) B2의 **실험 기록**이다. 저장소 방식이나 메모리 상한을 확정하지 않는다. 실험 코드는 `frame.zig`의 `B2` 판정자에 있다.

## 동일 출력과 비용

다음 수치는 **인접 검색 강조를 합치기 전**의 실험 기록이다. 80행 × 160열, 각 행에 1글자 검색 표식 120개를 둔 화면은 총 **9,762 op**를 냈다. 그중 검색 강조가 9,600개, 다른 층이 162개였다. 기존 2,560 op 저장소에서 다른 층을 전부 보존하는 층별 상한을 쓰더라도 검색 강조는 최대 2,398개만 남고 **7,202개(75.0%)가 빠졌다**. 층별 우선순위는 중요한 조작 표시를 지킬 수 있지만, 이 크기의 저장소에서 온전한 화면을 만드는 방법은 아니다.

`paintRowMarksInto`에 고정 슬라이스와 `ArrayList` writer를 붙여 **동일한 좌표 계산으로 9,600개 op을 실제 방출**했다. 결과 op은 내용까지 같았다. macOS ReleaseFast, 프로세스를 새로 띄운 세 번의 실행에서 40회 평균은 다음 범위였다. 단위는 µs다.

| 검색 강조 방출 | 세 번의 범위 | 저장소 |
|---|---:|---:|
| 충분한 고정 슬라이스 | 40–43 | 9,600 op 이상 |
| 2,560개부터 늘리는 새 `ArrayList` | 214–216 | 최종 1,453,088바이트 예약 |
| 전 프레임의 가변 용량을 유지한 `ArrayList` | 72–73 | 동일 용량 재사용 |

프레임 전체를 충분한 16,000 op 저장소로 **한 번** 그린 시간은 844–847µs, 2,560 op에서 절단된 뒤 16,000 op로 **재그리기**는 1,231–1,242µs였다(각 반복의 실제 op 출력을 최적화 방지 대상으로 둔 ReleaseFast 새 프로세스 세 번, 40회 평균). 재그리기의 추가 비용은 384–395µs다. 이전 계측은 반환 op 내용을 매 반복 관측하지 않아 컴파일러가 작업을 줄일 여지가 있었으므로 이 새 수치로 대체한다. 검색 writer의 시간과 전체 프레임 시간은 **서로 다른 범위의 측정**이므로 단순 합산해 통합 가변 프레임 시간을 주장할 수 없다. 당시에는 전체 프레임 writer를 재지 않았다. 아래 2026-09-30 실험은 기본 층을 한 번 만든 뒤 검색·진단을 직접 방출하여 전체 결과를 측정한다. Debug 측정(고정 448µs·새 가변 2,638µs·재사용 878µs)은 빌드 모드의 영향이 커서 제품 시간의 근거로 쓰지 않는다.

## 스트레스 후 국소 개선 (2026-09-29)

같은 80행 × 120글자 검색 화면을 세 패턴으로 측정했다. 각 실행은 새 ReleaseFast 프로세스이고, 프레임 전체 `build` 40회의 평균이다. 숫자는 이 합성 입력의 측정값이며 일반 문서의 프레임 시간을 뜻하지 않는다. 검색 표식의 논리적 목록과 우선순위는 그대로 두고, 같은 행에서 맞닿은 **테두리 없는 보통 검색 채움**만 draw op 하나로 합쳤다. 현재 매치·괄호 테두리·진단 밑줄은 합치지 않는다. 80×120칸의 강조 범위를 출력 op에서 독립적으로 복원해 원래 마크와 셀마다 비교한다.

**시각상 주의:** 이 셀 범위 비교는 Metal 픽셀 동일성을 뜻하지 않는다. `maru_metal_shader.h`의 quad fragment는 각 사각형 경계에 `fwidth` 기반 안티앨리어싱을 건다. 인접한 여러 quad를 하나로 만들면 내부 경계의 미세한 농도가 사라질 수 있다. 가로 스크롤·랩의 전체 draw op과 시각 행·스크롤 기하는 긴 단일 매치와의 교차 판정에서 같지만, PR #4010에서 같은 Metal 경로의 480×720 캡처를 비교했다. 129픽셀에서 RGB 최대 3의 차이가 있었고, 사용자 확인 후 머지했다. 픽셀 동일성은 주장하지 않는다.

| 패턴 | 검색 op 전 → 후 | 전체 op 전 → 후 | 전체 프레임 평균 전 → 후 |
|---|---:|---:|---:|
| 매 칸 연속 120개/행 | 9,600 → 80 | 9,761 → 241 | 819–836 → 241–246 µs |
| 한 칸씩 띄운 60개/행 | 4,800 → 4,800 | 4,961 → 4,961 | 518–530 → 529–537 µs |
| 네 칸씩 붙은 24묶음/행 | 7,680 → 1,920 | 7,841 → 2,081 | 703–720 → 355–360 µs |

따라서 연속 강조가 주인 화면은 고정 2,560칸 안에 들고 전체 프레임 시간은 이 입력에서 약 70% 줄었지만, **띄운 검색 4,800개만으로도 여전히 넘친다**. 띄운 경우는 op 절감 없이 시간만 조금 늘었으므로 전체 입력에 대한 속도 개선이라고 주장하지 않는다. 큰 화면에서 검색+진단이 겹치는 사례의 op은 175,001 → 117,001로 줄었으나, 대부분은 진단 밑줄이어서 저장소 정책이 여전히 필요하다. 아래의 실패 경로·비교 뷰 판정은 합쳐지지 않는 표식으로 다시 세웠다. 이 최적화는 B2의 저장소 방식이나 메모리 상한을 결정하지 않는다.

## 재그리기 동등성

이하 후보 비교의 시간·메모리 수치는 인접 검색 op 병합 **이전**의 실험 기록이다. 현재 판정자는 저장소 부족 반례가 계속 성립하도록 붙지 않은 표식을 사용하며, 같은 입력의 직접 비교는 위 표를 따른다.

`frame.build`는 `RowCache`를 읽기만 하지 않는다. 한 호출에서 최대 2,048줄의 접두합을 채운다. 2,049줄 랩 문서에서 작은 op 버퍼로 한 번 그린 뒤 재호출하면, 충분한 버퍼로 **처음부터 한 번** 그린 경우보다 캐시가 한 줄 더 전진하여 전체 시각 행 수와 스크롤바 축이 달라진다. 판정자가 실제 불일치를 재현했다. 첫 호출 전 캐시 메타데이터·접두합을 복원한 뒤 재호출하면 op 내용과 전체 행 수가 한 번 그리기와 같아졌다. 따라서 재그리기는 불가능한 방식이 아니라 **캐시 상태 트랜잭션을 추가해야 하는 방식**이다. 이 실험은 `RowCache` 외의 모든 가변 상태에 대한 동등성 증명이 아니다.

## 큰 화면과 실패 경로

200행 × 300열에서 검색 강조와 줄 전체 진단 지그재그가 겹치는 판정은 병합 전 **175,001 op, 실제 op 바이트 19,600,112**, `ArrayList` 최종 예약 **24,835,552바이트**였다. 병합 후에는 **117,001 op, 실제 op 바이트 13,104,112**, 최종 예약 **16,556,848바이트**다. 여러 pane이 각자 이 크기의 버퍼를 유지한다면 합이 커진다. 한 세션에서 버퍼를 공유·재사용하는 설계라면 합산 방식이 달라지므로, 소유 범위를 정하기 전에는 창 메모리 증가량을 확정할 수 없다. 할당 실패 주입 판정자는 가변 writer가 크래시 대신 부분 출력과 실패 신호를 남기는 것을 확인했다.

## 전체 프레임 재시도 실험과 새 반례 (2026-09-29 추가)

실험용 호출자 소유 `ArrayList`를 `frame.build`의 op 저장소로 주고, 부족하면 1.5배로 늘려 전체 프레임을 다시 그렸다. 첫 호출 전 `RowCache` 구조체와 **이번 호출이 바꿀 수 있는 접두합 구간**(최대 2,049항목)을 보관하여 각 재시도 전에 복원했다. 2,049줄 랩 문서에 밀집 검색을 얹어 충분한 고정 저장소로 한 번 그린 결과와 **op 내용·총 시각 행 수·캐시 접두합·스크롤바 기하**가 같은 것을 확인했다. 같은 저장소를 다음 프레임에 재사용하면 한 번만 그렸다. 이 방식은 실제 전체 프레임 결과를 검증하지만 **방출 중 성장 writer는 아니다**.

**적대적 재검토에서 판정자 자체를 고쳤다.** 처음에는 기준 프레임과 재시도 프레임이 같은 run·글자 저장소를 써서, 재시도가 기준의 텍스트를 덮어써도 `sameOpContent`가 같다고 답할 수 있었다. 두 저장소를 분리하고 결과 텍스트 한 바이트를 일부러 바꾸면 비교가 실패하는 음성 대조군을 추가했다. 캐시도 진행 위치만이 아니라 실제 접두합과 스크롤바 기하를 비교한다.

첫 재시도 헬퍼는 완전히 채워진 `RowCache.prefix` 전체를 **절단이 없는 프레임에도** 복사했다. 10만 줄·400,004바이트 캐시에서 직접 그리기 1µs 대비 래퍼 26µs였다(ReleaseFast, 100회 평균). 실제로 한 호출이 덮는 범위를 최대 2,049항목으로 제한하고, 계수가 끝난 캐시는 복사하지 않도록 바꾸자 새 프로세스 두 번의 1,000회 평균이 양쪽 모두 **1.2–1.3µs**였다(직접 1,242·1,270ns, 래퍼 1,253·1,265ns). 이는 실험 헬퍼의 국소 비용이며 실제 제품의 전체 프레임 시간을 대변하지 않는다. 캐시 키가 바뀌거나 점진 계수 중일 때의 제한 구간 복원도 동등성 판정으로 확인했다.

80행 밀집 검색의 ReleaseFast 40회 평균에서 재사용된 전체 프레임 재시도 래퍼는 약 850µs, 2,560칸부터 **상한을 넘지 않도록 정확히 1.5배씩** 키우면 약 3,280µs와 다섯 번의 `frame.build` 호출이 나왔다. 별도 충분한 고정 버퍼 한 번 그리기는 위 계측에서 844–847µs였다. 서로 다른 판정자·실행의 측정이므로 작은 차이를 우열로 해석하지 않는다. 재사용 시 비용이 한 번 그리기와 같은 자릿수이고, 첫 성장에는 반복 그리기 비용이 붙는다는 범위만 확인된다.

**재시도 신호에 결함이 있다.** `Written.truncated`는 op·run·글자·행 저장소의 누락을 합친 값이다. run을 0으로 제한하고 op에는 256칸을 준 판정에서, op 사용량은 256 미만인데도 이 신호만 믿는 래퍼가 op 저장소를 1,024칸까지 키우며 여러 번 그렸다. 제품 후보에는 **어느 저장소가 부족했는지 구별하는 신호**가 필요하다. 단순히 전체 저장소를 계속 키우는 구현은 근거 없는 재할당을 한다.

**비교 뷰의 균등 op 분할도 총량만으로 상한을 정하지 못하게 한다.** 한쪽에만 밀집 검색을 넣은 합성 입력에서 완전한 좌우 화면은 9,922 op로 16,000칸보다 작았지만, `diff_frame.splitScratch`가 8,000칸씩 가르자 밀집한 쪽이 잘렸다. 32,000칸에서는 잘리지 않았다. 이는 현재 제품 비교 검색을 재현한 것이 아니라 `Side.search_marks`를 사용한 저장소 분할 반례다. 병합 뷰도 op을 넷으로 균등 분할하므로 한 pane만 커지면 같은 종류의 낭비가 생길 수 있다. pane별 수요에 따라 op 범위를 나누거나 개별 성장시키는 정책이 필요하다.

한도 2,560칸에서는 `truncated`와 부분 출력이 남았다. 성장 할당 실패와 캐시 체크포인트 할당 실패를 각각 주입했고, 둘 다 원래 버퍼로 그린 부분 출력과 실패 신호를 남겼다. **중요한 층을 실제로 보존한다는 뜻은 아니다**. 80행에 모두 caret이 있는 밀집 검색 화면의 실측에서 충분한 저장소는 caret 80개를 냈지만 2,560칸은 **0개**를 냈다. 검색은 스크롤바 두 칸만 예약하고 caret 몫은 남기지 않기 때문이다. 이 실험 래퍼에는 우선순위별 한도 정책이 없고, 현재 `frame.build`의 앞 층은 스크롤바 자리까지 예약하지 않는다. 메모리 상한/OOM을 제품 정책으로 닫으려면 한도에서 무엇을 먼저 남길지 정하고 조작 표시·막대·caret까지 판정해야 한다.

따라서 기존 제안은 여전히 **구조 후보**다. 아래 실험은 방출 중 성장 후보의 전체 출력·비용과 일부 실패 경계를 확인한다. 모든 층의 직접 방출과 실제 호스트 배선·소유 범위·한도 정책이 닫히기 전에는 제품 방식으로 확정하지 않는다. 테스트용 전체 프레임 재시도는 기존 컴포넌트 계약을 유지하며 동등성을 보인 대안이지만, 평상시 절단 빈도와 실제 제품 배선의 비용은 아직 측정하지 않았다.

## 전체 프레임 staged writer 실험 (2026-09-30)

`B2Experiment.build`는 테스트 전용이다. 본문·gutter·caret·막대 등 기본 층을 기존 2,560 op scratch에 **한 번** 그리고, 검색·진단은 호출자가 유지하는 `ArrayList`에 직접 방출한다. 기본 층과 sticky 몫을 매 append에서 예약하고, 기본 op을 합류·회전하여 기존 painter 순서를 복원한 뒤 sticky를 한 번 그린다. 따라서 전체 프레임 출력과 비용을 재지만 **모든 생산자를 직접 writer로 옮긴 구현은 아니다**. 제품 `build`는 여전히 고정 슬라이스를 사용하며 호스트에 후보를 연결하지 않았다.

macOS ReleaseFast, 다른 테스트와 겹치지 않은 새 프로세스 세 번, 각 방법 20회 평균의 범위다. 단위는 µs이며 합성 입력 결과다. 충분한 고정 저장소, staged writer, 캐시 복원 후 전체 재시도를 같은 입력에서 비교했다. warm은 전 프레임 용량 유지, cold는 매번 새 목록이다. retry cold는 2,560칸부터 시작한다.

| 입력 / 전체 op | 고정 | staged warm | staged cold | retry warm | retry cold |
|---|---:|---:|---:|---:|---:|
| 소형 / 41 | 6 | 6–8 | 11 | 6 | 8–11 |
| 흩어진 검색 / 4,962 | 636–641 | 648–652 | 758–775 | 640–647 | 1,760–1,793 |
| 검색+진단 / 150,401 | 10,755–10,796 | 10,696–10,963 | 13,265–13,744 | 10,774–11,625 | 57,430–60,059 |

마지막 입력은 200행 × 320열, 300글자/행, 띄운 검색 150개/행과 전체 줄 진단이다. 앞의 117,001 op 실험과 **다른 입력**이다. staged cold 성장 횟수는 차례로 1·10·16회, retry cold의 전체 build 호출은 1·3·12회다. 큰 입력에서 staged cold는 retry cold보다 약 76–78% 적은 시간이 들었지만, warm에서는 충분한 고정 저장소와 비슷한 범위다. 이는 모든 문서·호스트에서의 성능 보장이 아니다.

writer 예약 바이트는 차례로 4,592·696,192·19,622,848이며, **기본 stage 286,720바이트가 별도**로 든다. run·글자·행 scratch는 이 op 수치에 포함하지 않는다. 실험의 `max_ops`는 writer 출력 상한이지 전체 메모리 상한이 아니다. 200,000칸은 판정용 한도이며 제품 상한으로 선택하지 않았다.

**동등성과 실패 판정**: `B2FW1`은 랩·가로 스크롤·선택·8행 sticky·2,050줄 점진 캐시의 cold/warm에서 op 종류·순서·좌표·run 글자·시각 행·캐시 접두합을 충분한 고정 출력과 비교한다. 기준과 후보 run/text 저장소를 분리하고 quad 좌표를 바꾸는 음성 대조군을 둔다. `B2FW6`은 Unicode·탭·inlay·widget·공백 표시를 포함한 16개 무작위 입력을 비교한다. 이 검증에서 sticky 예약 산술의 좁은 정수 추론으로 8행 이상일 때 넘치던 실험 결함을 찾았고, `usize` 계산과 8행 고정 회귀 입력으로 수정했다.

`B2FW2`는 2,560칸 상한과 성장 할당 실패에서 caret 80개·현재 검색 1개·스크롤바 thumb 2개를 보존한다. 최초 목록 할당부터 실패하면 기존 base scratch로 돌아가 caret·막대는 남지만 **현재 검색은 보장하지 않는다**. base 자체가 한도를 넘으면 `BaseExceedsLimit`, 유지된 목록 용량이 새 한도를 넘으면 `RetainedCapacityExceedsLimit`로 거절한다. run 부족은 `base_truncated`로 별도 보고하고 op 부족으로 오인하지 않는다. 기본 scratch가 먼저 절단되는 문제를 모두 해결한 정책은 아니다.

**불균등 pane**: 실제 diff plan에서 한쪽만 검색이 많은 입력은 전체 9,922 op를 16,000칸 공유 목록으로 순차 처리할 수 있고, 기존 8,000칸 균등 분할은 일부를 잃는다. `B2FW5`는 실제 merge layout/paneProps에서 결과 pane에만 합성 검색을 주입해 전체 10,165 op를 확인한다. 제품 merge에는 이 검색 입력 API가 없으므로 실제 검색 UI 재현이 아니다. 두 경우의 공유 writer 최대 예약은 1,551,312바이트다. 각 pane 결과를 소비한 뒤 목록을 재사용하는 판정이며, 실제 호스트의 동시 결과 수명이나 창 전체 한도를 구현하지 않았다.

## 잠정 판단과 남은 결정

- **층별 상한만**으로는 일반적인 조작 표시를 보호할 수 있지만, 밀집 화면의 빠진 검색 강조를 복원할 수 없다.
- **절단 후 재그리기**는 기존 컴포넌트의 고정 슬라이스 계약을 덜 바꾸지만 캐시 롤백이 필수이고, 절단 프레임에 전체 그리기 한 번이 더 든다. 절단의 실제 발생 빈도는 측정하지 못했으므로 평상시 평균 비용은 모른다.
- **호출자 소유의 재사용 가변 writer**는 전체 프레임 staged 실험에서 출력 동일성과 cold 재시도 대비 비용 감소를 보였다. 모든 층 직접 방출·최초 OOM의 현재 검색 보장·Windows 호스트·Chrome Lab·제품 diff/merge 배선은 아직 검증하지 않았다. 큰 화면의 수십 MB 요구를 보았으므로 무상한 증가는 후보에서 제외한다.

따라서 다음 구현 후보로는 **호출자 소유의 재사용 가변 writer + 명시적 메모리 상한 + 상한/OOM에서 중요한 층을 보존하는 부분 출력**을 권한다. 이것은 구조 변경 제안이며 확정된 프로젝트 규칙이 아니다. 상한 수치와 버퍼 소유 범위(세션 공유인지 pane별인지), 실제 제품 배선과 모든 층의 상한·실패 정책을 검증한 뒤 B2 방식을 결정해야 한다.

재현 명령: `mise exec -- zig test -OReleaseFast -lc -Mroot=src/ui_test.zig --test-filter 'B2'`(비교 뷰 분할·전체 프레임 재시도·신호 반례 포함). 전체 편집기 판정은 `mise exec -- zig build test-editor`, 이식성은 `mise exec -- zig build check-targets` 및 libc 없는 Linux `zig test -ODebug -target x86_64-linux -Mroot=src/ui_test.zig -fno-emit-bin`으로 확인한다.
