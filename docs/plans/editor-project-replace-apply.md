# 프로젝트 바꾸기 적용 — S4 단일 파일

상태: S4a 열린 문서와 S4b 디스크 결과 단일 파일의 적용·자동 저장·실패 표시를 구현했다. 검증 결과는 아래에 기록한다.
사용자가 2026-10-09 단일 파일 적용과 자동 저장·실패 시 편집/Undo 유지 정책을 승인했다.
[기존 검색 계획](editor-project-search.md)의 S4와 [미리보기](editor-project-replace-preview.md)의 후속이다.

## 동작

1. ready 미리보기에서 명시적 적용 버튼을 누른다. 선택한 일치 하나 또는 그 파일의 표시 일치 전체가 대상이다.
2. 입력·root capability·문서 신원·revision·조합 상태·원문이 미리보기와 같은지 재검증한다.
3. 변경 범위와 Undo, 공유 뷰 게시에 필요한 자원을 먼저 준비한다. 실패하면 본문·선택·이력을 보존한다.
4. 선택한 정본 문서에 한 번의 편집으로 반영하고 한 번의 Undo로 되돌리게 한다. 공유 뷰는 함께 갱신한다.
5. 적용 후 기존 CAS 저장을 시도한다. 저장 실패는 편집을 되감지 않고 변경된 문서와 Undo를 유지하며,
   **적용됨·저장 실패**로 구분한다. 사용자에게 재저장·충돌 해결·Undo가 가능한 상태를 남긴다.

자동 저장은 기존 미저장 편집도 함께 저장한다. 이 UX와 실패 시 메모리 변경 유지 정책은 승인됐다.
대안은 문서 편집만 반영하고 저장은 사용자의 기존 Save 명령으로 남기는 것이다.

## 참고와 근거

[VS Code replaceService](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/search/browser/replaceService.ts)는
편집 서비스 적용 후 각 대상의 save를 시도한다. 2026-10-09 공식 소스를 `references/vscode/`에서 읽어 동작 정책을 확인했다.
Maru 구현에 외부 코드 표현을 복사하지 않는다. 저장 실패 시 Maru의 표시·재시도 계약까지 이 소스가 대신 정하는 것은 아니다.

기존 `workspace_edit.apply`는 경로에 대응하는 독립 문서들을 함께 처리한다. S4의 선택한 문서 적용에는 이 경로만의
식별을 그대로 쓰지 않는다. 선택한 document owner/slot/generation을 사용해 같은 경로의 독립 문서는 제외한다.

## 구현 순서

- S4a: 열린 네이티브 문서 하나. 문서 신원 재검증·커서가 없는 문서 지원·범위별 delta·한 Undo·공유 뷰·IME·OOM·저장 결과를 연결한다.
- S4b: 디스크 결과 하나. 전문/root/hash 재검증과 문서 로드·적용·기존 원자 저장·실패 시 복구 가능한 문서 수명을 연결한다.
  디스크 미리보기만 믿고 쓰지 않는다. 새로 열린 다른 문서나 변경된 디스크를 덮어쓰지 않는다.
- S4c: [여러 파일 적용 설계](editor-project-replace-batch.md). 부분 성공·재시도·되돌리기 정책을 별도로 승인한 후 구현한다.

## 준비할 데이터와 경계

- neutral `search.preview.Plan`은 before/after와 diff뿐 아니라 각 수정의 원문 byte 범위와 after 안의 대체 텍스트 범위를 보관한다.
  작은 치환을 파일 전체 교체로 보내지 않아 Undo가 불필요하게 전문을 복사하지 않게 한다.
- PCRE2 캡처 확장은 미리보기 준비 때 한 번 계산한 대체 텍스트를 사용한다. 적용 시 다른 엔진으로 재계산하지 않는다.
  UTF-8·raw LF/CRLF·빈 매치·같은 offset의 변경 순서를 기존 delta 계약과 대조한다.
- platform 미리보기 State에 선택한 target 신원을 유지한다. worker 종료 후 Input과 source snapshot이 해제되므로
  title이나 현재 활성 문서로 대상을 추측해서는 안 된다.
- read_only, IME transaction/확정 대기, 조합 중 대상·공유 뷰, 충돌·부분·취소·실패 상태는 적용을 거절한다.
- 공유 게시 coordinator를 재사용하고 `applyEditAsOneWithUndo`로 Undo 슬롯을 본문 변경 전에 예약한다. 기존 일반 편집 함수는 기록 실패 시 이력을 비우므로 S4에는 그 정책을 적용하지 않는다.
- 이미 열린 이름 있는 문서만 S4a 대상이다. 결과 사본 탭·diff·원격·이름 없는 문서에 우회 적용하지 않는다.
- 적용 성공으로 검색 generation이 바뀌면서 기존 Plan이 정산되어도 빌린 대체 텍스트를 사용하지 않도록 수명을 보장한다.
- 저장 API의 기존 byte 한도·BOM·CAS·백업 정산 계약을 유지한다. 앱 전체 RSS·모든 파일의 원자 성공·영속 Undo를 새로 보장하지 않는다.

## 검증 계획

- 독립 오라클: Plan의 범위별 변경을 실제 EditableFile에 적용하면 Plan.after와 같고, 역연산은 before로 돌아온다.
- 전체 준비 할당 실패, 여러 줄/CRLF/Unicode/capture/삭제/빈 매치·대체 문자열에 검색어가 다시 있는 경우.
- 실제 원문·selection·Undo/Redo·공유 뷰와 같은 경로의 독립 문서, revision 변경·닫기·IME transaction.
- 쓰기 전 hash 불일치·읽기 전용·저장 byte 한도·권한/쓰기 실패. 저장 실패는 적용 실패와 따로 판정한다.
- 실제 제품 우측/하단 도크의 적용 버튼·완료/실패 표시·Undo를 AppKit/Metal로 확인하고 PR 본문에 첨부한다.

S4b는 디스크 미리보기에서도 적용 버튼을 제공한다. S4c는 [열린 문서 배치 UI](editor-project-replace-batch-ui.md)까지 연결했으며 닫힌 파일 배치는 미구현이다.

## S4b 디스크 결과 적용

- `preview.State.disk_target`이 root 경로·capability 신원·상대/절대 경로·검증 SHA-256을 소유한다.
  미리보기 worker의 Input이 해제되어도 대상은 유지한다. SHA-256은 기존 검색/navigation처럼 UTF-8 BOM을 제외한 본문 축이다.
- 적용은 `disk_apply.Check`의 새 worker를 시작하고 `.applying` 상태로 바뀐다. 이때 적용 버튼과 결과 탭 열기는 비활성화되며,
  기존 진행 표시를 쓴다. 취소·입력/옵션 변경·root 변경·IME·새 문서 열기로 무효화되면 늦은 완료는 적용하지 않는다.
- worker는 `verify.disk`로 regular file·읽기 한도·root 신원·읽는 중 변경·hash를 재검증한다.
  완료 시 검색 fingerprint·입력과 조합 상태를 다시 확인한다. 현재 창의 패널과 앱 전역 registry가 같은 정규화 경로를 점유하면 거절한다.
  경로 별칭을 새로 정본 문서로 통합하지 않는다.
- 검증 뒤 기존 `pane.openNativeFileTermInActivePane`으로 로컬 문서를 연다. 기존 문서를 재사용하지 않고,
  root가 유지되는지·로드한 본문이 Plan.before인지·읽기 전용/복구된 미저장 문서가 아닌지를 확인한다.
  load 도중 변경된 파일은 적용하지 않는다. 열기 자체가 성공한 뒤 적용 준비가 실패하면 변경하지 않은 문서는 열린 상태로 남을 수 있다.
- Plan은 live 도크에서 호출 지역 transaction으로 옮긴 뒤 편집한다. 열기/편집 통지가 미리보기를 정산해도 빌린 대체 텍스트가 해제되지 않는다.
  적용은 기존 `applyEditAsOneWithUndo`, 저장은 기존 CAS 경로다. 준비 실패는 본문·이력을 보존하고,
  저장 실패는 새 문서의 편집·Undo·dirty 상태를 보존한다. 사용자에게 같은 완료/저장 실패 안내를 보여 준다.
- 새 파일 열기는 기존 문서 loader의 동기 경로를 재사용한다. 전문 hash 재검증은 worker이며, 문서 생성·syntax·선택·저장은 기존 main actor 책임이다.
  모든 파일시스템에서 외부 프로세스 쓰기와 앱 저장이 완전히 원자적이라는 새 보장은 하지 않는다.

## 실행 검증

- 중립 Plan 10개: 실제 EditableFile과 역연산으로 CRLF/Unicode/여러 줄 capture/삭제/빈 match를 대조하고, 동일 치환은 변경 없음으로 처리한다.
- AppSession RPA 판정 32개(이름 있는 28개 + 초기화 4개): 단일 일치/파일 적용·기존 미저장 편집 자동 저장·한 Undo/Redo·외부 CAS 충돌·공유/독립 문서·조합/읽기 전용·원문/검색어 변경 거절을 확인한다.
- 준비와 저장 경로의 15개 할당 지점을 하나씩 실패시킨다. 본문 변경 전에 거절된 4개 지점은 선택·기존 이력을 보존하며, 적용 후 저장 실패는 새 Undo를 유지한다. 이 숫자는 fixture 경로의 할당 표본이며 앱 전체 OOM 보장을 뜻하지 않는다.
- 격리 소스에서 Undo 사전 예약을 제거한 음성 대조군은 RPA3/RPA5가 실패했다. 정상 코드에서는 이력이 보존된다.
- 제품 AppKit/Metal 하네스는 실제 적용 버튼 클릭→자동 저장→Esc로 기존 완료 알림 닫기→Cmd+Z→Cmd+S를 검사하고 마지막 디스크가 처음 원문과 같은지도 대조한다. 완료 알림의 첫 닫기 키 소비는 기존 계약이며 Undo 실패로 오판하지 않는다.
- 완료한 미리보기는 정산한다. 성공 후 지난 미리보기의 충돌 표시가 남지 않게 한다. 저장 실패 알림은 적용됨과 Undo 유지, 알려진 실패 원인을 함께 표시한다.
- 실제 화면은 960×600 1×와 640×480 논리 크기/주입 2×에서 확인한다. 물리 OS IME 후보창·VoiceOver·전체 파일시스템 쓰기 실패의 증거로 해석하지 않는다.

## 적대적 재검증에서 수정한 내용

- 저장 성공 알림이 기존 충돌 마커 경고를 덮는 것을 실제 AppSession에서 재현했다. 완료 문구와 기존 경고를 함께 표시하며, 저장을 거절하는 새 정책을 추가하지 않는다. `RPA8`과 제품 AppKit/Metal의 `--conflict-markers` 입력·캡처로 확인한다.
- `aa`에서 `((?<=a)a|)a?`를 `$1$1`로 바꾸면 개별 치환은 달라도 최종 본문은 같다. 기존에는 diff가 없는데 수정 목록이 남았다. 최종 diff가 변경 없음이면 수정 목록을 비워 적용·Undo 추가·자동 저장을 막는다. 중립 오라클과 실제 검색 worker를 거친 `RPA9`로 확인한다.
- 선택한 범위의 256개 고정 seed 표본을 독립 문자열 오라클·실제 EditableFile·역연산으로 대조했다. BMP 밖 emoji·한글·CRLF·삭제·여러 줄 대체 문자열과 일부 매치만 선택한 경우를 포함한다.
- 원본 삭제/디렉터리 교체의 저장 실패, BOM/CRLF/한글/emoji 저장과 Undo 뒤 재저장, root 교체/문서 닫기/디스크 전용 결과 거절, 기존 Redo·연속 클릭·후속 타이핑 경계를 검사했다.
- 공유 뷰·추가 커서를 포함한 fixture의 22개 할당 지점을 각각 실패시켜 본문/양쪽 선택/기존 Undo 보존과 적용 후 Undo를 대조했다. 앱 전체의 모든 할당 실패를 보장하는 수치가 아니다.
- 격리 소스에서 충돌 경고·원문 대조·검색 입력 대조를 각각 무력화한 컴파일 가능한 대조군은 관련 테스트에서 실패했다. 제품 소스에 변이를 남기지 않는다.

미참여 캡처를 치환하면 기존 PCRE2 설정은 `EngineFailure`로 거절하며 미리보기/적용이 진행되지 않는다. 빈 문자열 치환으로의 전환은 사용자 논의 중이며 현재 동작을 바꾸지 않았다. 패턴에 없는 번호·이름과 구분해야 한다.


## S4b 실행 검증

- `RPA14~23`은 실제 rg 검색→미리보기→새 worker→문서 로드→적용을 사용한다.
  파일/단일 일치, 한 Undo, 독립 control 문서, 외부 수정/삭제/디렉터리 교체, 취소/입력 변경/IME/새 문서,
  worker 완료 후 외부 수정, BOM/CRLF/한글/emoji, 읽기 전용, 앱 전역 정본 점유, 같은 bytes의 root 교체를 판정한다.
  여러 줄 정규식 캡처·빈 파일로 삭제·빈 매치는 저장 bytes를 Plan과 대조한다.
- 적용 준비/저장의 46개 할당 표본에서 44개는 편집 전 거절되고 2개는 저장 실패로 새 문서/Undo를 유지했다.
  재검증 시작/worker의 13개 할당 표본은 디스크 변경 없이 거절했다. fixture의 표본이며 앱 전체 OOM 보장이 아니다.
  문서가 테스트용 allocator를 소유하므로 메모리 부족 주입을 해제한 뒤 그 문서의 Undo를 확인한다.
- `tools/test-editor-project-replace-disk-adversarial.py`는 격리 소스에서 late load 원문 비교·입력 stamp·root 신원 검사를
  각각 무력화한 컴파일 가능한 대조군을 실행한다. 각각 실제 RPA 판정이 실패하며 정상·등가·복원 대조는 통과한다.
- 제품 하네스 `--replace-disk-apply --disk-files 2`는 실제 Apply 버튼→새 문서/완료 안내→Esc→Cmd+Z→Cmd+S를 수행한다.
  원래 열린 문서뿐 아니라 디스크 fixture 전부가 처음 bytes로 돌아왔는지도 별도로 확인한다.
  960×600 1×와 640×480 논리 크기/주입 2×를 확인했다. 물리 OS 입력기·전체 파일시스템·VoiceOver의 검증은 아니다.
- 검색 갱신은 기존 `apply_outcome`을 정산할 수 있으므로 실제 제품 완료는 저장 완료 안내·dirty/Undo·최종 디스크로 판정한다.
  첫 하네스 실행의 일시적 상태 값 판정 실패를 제품 저장 실패로 해석하지 않는다.


## S4b 추가 검증과 수정

- worker 완료 직전에 IME 활성/확정 대기나 필드 조합이 생기면 쓰기는 거절했지만, 앞 프레임이 dirty를 내린 뒤에는
  진행 UI를 다시 그리도록 표시하지 않았다. `RPA28`의 실제 publish→dirty 해제→완료 수확 순서로 수정 전 실패를 재현했다.
  `invalidateApply`가 미리보기·입력 트리·세대·화면 dirty를 함께 갱신하며, 원문/IME 텍스트는 유지한다.
- 실제 Cancel·옵션 변경·필드 조합·확정 대기·leave가 늦은 완료를 거절하는지 확인한다(`RPA24`).
- 공백/한글/emoji/개행/옵션 같은 파일명과 하위 경로는 정확한 대상만 쓰며 독립 파일을 유지한다(`RPA25`).
- 준비 이후 FIFO·비UTF8·기존 읽기 한도 초과로 교체된 파일은 쓰거나 새 탭을 만들지 않는다. sparse 파일로 한도만 재현한다(`RPA26`).
- 취소 직후 새 State를 만드는 순서를 반복하고 마지막 요청의 대체 텍스트만 적용한다. detached worker는 결산 전에 정산된다(`RPA27`).
- 대조 도구는 화면 dirty 표시를 무력화한 컴파일 가능한 변이도 `RPA28`로 거절한다. 정상/등가/복원 대조를 함께 실행한다.

- 제품 `--replace-ime-refuse --disk-files 2`는 진행 프레임 이후 완료 수확 직전에 IME 확정 대기를 주입한다.
  실제 Metal의 진행→충돌 화면과 새 입력 세대 publish, 원래 문서·모든 디스크 fixture의 bytes 보존을 확인했다.
  물리 OS IME 입력 검증은 아니다. `maru-editor-project-search-app-we1wkla2/manifest.json`에 소스/바이너리/캡처 hash를 기록했다.

열린 모델 적용의 root 검증은 `search/owner.zig::validateRoots`를 배치와 공유한다.
watcher 세대와 cached capability가 그대로여도 실제 root 디렉터리가 같은 본문의 다른
device/inode로 교체됐으면 편집 전에 거절한다. `RPA29`는 실제 디렉터리 교체 뒤 모델 본문·
Undo와 교체 디렉터리의 원문이 모두 보존되는 것을 검사한다.
