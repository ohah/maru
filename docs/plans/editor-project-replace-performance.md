# 프로젝트 바꾸기 — 적용·저장 실측

2026-10-11 사용자가 파일 수·크기와 느린 저장의 실측을 요청했다. 이 기록은 최적화 전 제품 경로의 측정이며, 제품 동작이나 저장 정책을 바꾸지 않는다.

## 조건과 판정 범위

- Apple M4 Max / RAM 64GiB, macOS 26.5.1 (25F80), 로컬 `/System/Volumes/Data`.
- Zig 0.16.0 ReleaseFast. 같은 바이너리를 모든 집계 표본에서 재사용한다.
- 제품 소스 기준은 `a08fa681b6b6d5a3d4eba567cb64e52a3be16926`. 계측·큰 본문 fixture·지연 주입은 격리 source 복사본에만 추가한다.
- 열린 모델 2/32/64개와 닫힌 파일 2개. symbols의 일치 20개, 나머지 파일의 일치 1개씩을 유지한다.
  큰 본문은 검색어가 없는 주석/줄로 늘려 일치 개수 증가와 본문 크기 증가를 구분한다.
- 첫 여섯 조건을 각 반복마다 순서대로 실행해 3개 표본씩 얻었다. 한도 근처 조건은 그 뒤 별도로 3회 측정했다.
  새 프로세스·격리 HOME·새 파일을 사용하며 OS 캐시는 강제로 비우지 않는다.
- 각 실행에서 실제 AppKit 적용·파일별 저장·연결 Undo·재저장이 성공했고, 종료 후 원문 byte oracle과 비교했다.
  같은 binary SHA, 파일/일치/byte 개수, 준비 두 화면의 Plan 일치, phase 시간 순서를 별도 검증한다.

## 시간의 의미

- 수집: 선택 명세·snapshot 수집의 동기 호출. 준비 완료: 수집 시작부터 worker/RG 검증과 UI polling을 거쳐 ready까지의 경과 시간.
- 적용: `batch/ui.apply`의 동기 전체 호출. 원문/신원 검사, 편집/history 준비, commit·새 뷰 게시, 파일별 저장과 결과 게시를 포함한다.
- 저장: `batch.finishApply`의 결과 분류·CAS 저장 루프. 주입한 대기도 이 구간에 포함한다.
- main queue 대기: 적용 클릭 직전에 게시한 main queue 작업이 실행될 때까지의 시간. 실제 main queue 응답 지연이며 프레임 간격/FPS 측정은 아니다.
- RSS: 50ms 간격으로 읽은 메인 앱 프로세스의 전체 시나리오 peak. batch만의 메모리나 allocator/GPU/자식 프로세스를 합친 총량은 아니다. 짧은 peak는 놓칠 수 있다.
- 지연 조건은 파일마다 `sleep(10ms)`를 요청한 fault injection이다. 실제 네트워크/원격 파일시스템 실측이 아니며 OS 대기·스케줄링 초과 시간도 들어간다.

중앙값이며 괄호는 최소–최대다. 조건마다 표본 3개이며 분위수 상한을 주장하지 않는다.

파일 수와 지연이 단조 증가하는 표본은 아니다. 작은 34개는 저장의 변동이 커 22.2–82.1ms의 queue 범위를 보였다.
따라서 한 수치로 파일당 비용을 선형 추정하지 않는다. 4개 기준과 66개/큰 입력/지연 주입 조건에서 main queue 대기 증가가 관측됐다.

총 61.13MiB 표본의 적용 중앙값은 144.8ms, 저장 중앙값은 70.2ms다.
같은 표본에서 적용에서 저장을 뺀 시간의 중앙값은 70.9ms다. 저장만 분리해도 이 나머지 구간은 남는다.

준비 완료 경과 시간 중앙값은 97.8–147.2ms, 동기 수집 중앙값은 0.13–1.65ms였다.
정확한 조건별 원시값은 아래 JSON에 보존한다. 준비 완료 경과 시간 전체를 main thread 정지 시간으로 해석하지 않는다.


## 판단과 다음 검증

main queue의 동기 저장 경로가 I/O 대기 동안 응답을 막는지를 직접 확인한다. 다만 적용에서 저장을 뺀 시간에는 준비·신원 검사·본문 반영·뷰 게시도 들어가므로 그 차이를 순수 CPU 비용이라고 부르지 않는다.
후속 개선은 측정된 구간을 대상으로 한다. 저장을 worker로 옮길 때는 본문 revision·외부 CAS·완료 후 dirty 판정·Undo와 닫기 수명을 보존하는 설계를 먼저 검토한다.
저장만 분리해서 모든 응답 지연이 해결된다고 주장하지 않으며, 남는 준비·반영 구간은 별도 프로파일링 대상으로 둔다.

## 재현

```sh
python3 tools/editor-project-search-app/run.py --replace-batch --disk-files 2 --count 20 --optimize ReleaseFast --timeout-seconds 180
python3 tools/editor-project-search-app/measure.py --app <위 하네스의 maru-macos-app 경로> --output <저장소 밖의 새 보존 디렉터리> --repetitions 3
```

`measure.py`는 파일 수·입력 크기·계측 phase·fixture byte oracle과 binary SHA를 고정한다.
첫 임시 `/tmp` 측정의 결과 디렉터리가 사라져 그 표본은 최종 집계에서 제외했다. 보존 경로의 원본 manifest·로그·화면·RSS를 기준으로 다시 측정했다.
독립 byte oracle을 더하는 과정에서 peer prefix를 27byte로 잘못 적은 실험 검증 코드도 실행 거절로 발견했고, 실제 fixture 문자열 길이로 고쳤다.
실제 물리 IME·VoiceOver·전원 손실·다른 저장장치·높은 일치 개수·최대 파일 수 전체는 이 실측의 범위가 아니다.
