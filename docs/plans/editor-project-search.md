# 프로젝트 전체 검색과 바꾸기 미리보기

상태: **설계·후보 비교 중, 프로젝트 검색 제품 구현 미착수.**
2026-10-06 사용자가 [VS Code 방향의 검색 판정](editor-search-policy.md)을 승인했다. 아래 기존 비교는 정책 변경 전 기록이며 현재 대조는 후속 절에서 구분한다. 기존 문서 내 평문 검색 개선을 S1의 선행 작업으로
진행한다. 사용자의 다음 편집기 작업 진행 요청에 따라
검색 도크의 선행 결정을 검토한다. 이 문서의 제안은 새 의존성 채택이나 배포 승인을 뜻하지 않는다.
기존 파일 안 찾기·바꾸기는 그대로이며, 아래 제품 단계가 연결될 때 상태를 갱신한다.

## 먼저 결정할 것

**검색 엔진 구성은 아직 채택하지 않았다.** 파일 목록에만 ripgrep을 쓰고 기존 matcher를 순차 호출하는 안을
처음 제안했지만, 그것의 비용을 공통 matcher 구조 전체의 한계로 해석할 수는 없다.
사용자는 결과 차이와 다른 에디터의 방식을 확인한 뒤 후보들을 더 실행해 보도록 요청했다.
디스크 파일과 열린 문서의 일치 규칙을 맞추면서 후보 선별과 일치 계산을 빠르게 할 수 있는지도 함께 비교한다.
UI는 VS Code의 한 검색칸과 `Aa`·단어·`.*`, 파일별 결과 묶음·포함/제외 패턴을 참고한다.
검색을 먼저 구현하고 여러 파일 쓰기를 수반하는 바꾸기 미리보기·적용은 후속 단계로 둔다.

아래 실험에서 ripgrep 전체 검색이 순차 재사용보다 훨씬 빨랐다.
그대로 섞으면 **파일을 여는 것만으로 결과가 달라지는 반례**도 있다. 현재 Maru 규칙이 항상 더 좋은 정책이라는
결론은 이 반례에서 나오지 않는다. 특히 단어 경계와 빈 일치 반복은 엔진 이름뿐 아니라 호출자가 정하는 규칙이다.
자체 matcher를 거치는 검색을 ripgrep 전체 검색 속도로 소개하지 않으며, 기존 의미 변경도 몰래 하지 않는다.

| 후보 | 장점 | 비용·판정 |
|---|---|---|
| 직접 디렉터리 순회 + 기존 찾기 | 새 실행 파일이 필요 없고 일치 규칙도 같다 | 중첩 ignore·부정 패턴·우선순위·전역 규칙을 새로 구현하거나 범위를 줄여야 한다. 이 후보의 성능은 측정하지 않았다 |
| ripgrep 전체 검색 + 열린 문서의 기존 찾기 | 디스크 검색·ignore·취소가 한 도구에 있고 드문 평문 검색이 빠르다 | 빈 대안과 단어 경계의 불일치를 재현했다. 단순히 `--pcre2`로 바꿔도 빈 대안의 반복 규칙은 맞지 않는다 |
| ripgrep 파일 목록 + 디스크/열린 문서의 기존 찾기 | 복잡한 파일 선정 규칙을 직접 만들지 않고 기존 검색 의미를 유지한다 | 번들 helper 의존성이 추가되고, 내용 읽기·UTF-8 검사·일치 계산·취소는 Maru worker가 담당해야 한다. 현재 순차 재사용 실험은 더 느리다 |
| 후보 내용 선별 + 기존 찾기 | 일치가 없는 대부분의 파일을 빠르게 걸러 정확한 범위 계산을 줄인다 | 안전한 상위 집합일 때만 쓸 수 있다. 실험은 한 줄 ASCII 평문만 선별하고 단어 판정은 Maru에 남긴다. 정규식·비ASCII는 목록 전체를 검색한다 |
| 평문 byte 탐색 경로 개선 | 후보마다 UTF-8을 다시 해독하는 대신 표준 byte 검색을 쓰는 비용 비교 | 초기 실험은 대소문자를 구분하는 평문에 한정했다. 후속 개선은 기존 `findMatches`의 정확한 byte 탐색과 ASCII 디코드 절약에 반영하며 아래 별도 기록으로 검증한다. 정규식 최적화의 근거는 아니다 |

프로젝트 규칙의 “새 런타임 의존성을 추가하려면 먼저 사용자와 논의한다”와
[전략 수정 규칙](../pr-checklist.md#전략-수정-규칙)의 외부 의존성·미정 UX 항목에 따라,
**최종 엔진 구성·ripgrep 번들 여부와 아래 초기 범위를 확인한 뒤 제품에 연결한다.**
실험은 설치된 CLI를 명시적으로 사용하는 개발 도구이며 앱이나 기본 CI가 실행하지 않는다.

## VS Code에서 확인한 근거

2026-10-05 조사 시점의 소스를 커밋 `24a41178148f72f49e4ac0756ddb3b5347429a91`로 고정했다.
로컬 사본은 `references/vscode/project-search/<commit>/`에만 두고 코드 표현은 복사하지 않았다.

- [검색 UI 문서](https://code.visualstudio.com/docs/editing/codebasics#_search-across-files): 폴더 검색, 파일별 결과, include/exclude와 ignore 토글을 제공한다.
- [검색 서비스](https://github.com/microsoft/vscode/blob/24a41178148f72f49e4ac0756ddb3b5347429a91/src/vs/workbench/services/search/common/searchService.ts): 열린 문서를 editor model로 검색하고 디스크 결과보다 우선한다. **일치 0건도 점유 기록을 남겨** 디스크의 옛 결과를 막는다. “dirty인 파일만 우선한다”는 설명은 정확하지 않다.
- [열린 경로의 선정](https://github.com/microsoft/vscode/blob/24a41178148f72f49e4ac0756ddb3b5347429a91/src/vs/workbench/services/search/common/search.ts): `pathIncludedInQuery`는 요청의 경로·include/exclude를 검사하며 디스크의 ignore 파일을 읽지 않는다. 열린 문서 검색과 디스크 탐색의 ignore 적용은 같은 절차가 아니다.
- [ripgrep 어댑터](https://github.com/microsoft/vscode/blob/24a41178148f72f49e4ac0756ddb3b5347429a91/src/vs/workbench/services/search/node/ripgrepTextSearchEngine.ts): 디스크 검색을 별도 프로세스로 실행하고 취소 시 종료한다. 정규식은 `--engine auto`, 사용자 CLI 설정은 `--no-config`, 출력은 JSON이다. ignore·symlink 옵션은 요청 설정에 따라 전달한다.
- [패키지 선언](https://github.com/microsoft/vscode/blob/24a41178148f72f49e4ac0756ddb3b5347429a91/package.json): ripgrep 배포 패키지가 별도로 있다. **사용자 PATH의 임의 rg를 자동 실행하는 설계 근거가 아니다.**

공통 matcher 후보는 UI·열린 문서 우선 정책을 참고하되 내용 matcher를 통일한다는 점에서 VS Code와 다르다.
현재 한 파일 찾기의 의미는 [시각 매핑 §5.1](../native-editor-visual-mapping.md)이 소유한다.
S0 실험 시점에는 줄별 정규식을 사용했다. 이후 사용자 승인한 [문서 전체 정규식](editor-document-regex.md)이
현재 편집기의 검색 계약이며, 프로젝트 검색의 공통 엔진도 그 계약을 사용한다. 다른 엔진 문법 추가는 별도다.

### 다른 에디터의 선택

| 에디터 | 확인한 방식 | 이 조사에서의 의미 |
|---|---|---|
| Zed | [개발팀의 검색 개선 설명](https://zed.dev/blog/nerd-sniped-project-search)은 메모리 내용을 우선하고, 디스크 후보를 좁힌 뒤 편집기 버퍼에서 정확한 범위를 계산한다고 설명한다. Rust regex를 사용하며 별도 rg로 교체하지 않고 작업 우선순위·동시성으로 첫 결과 지연을 개선했다 | 일치 판정을 통일하는 구조와 빠른 검색이 양립할 수 있다. 2025-11-26 설명이며 현재 버전의 성능을 직접 측정한 것은 아니다 |
| IntelliJ 계열 | [공식 정규식 안내](https://www.jetbrains.com/help/idea/tutorial-finding-and-replacing-text-using-regular-expressions.html)는 파일/프로젝트 검색에 JDK의 Java 정규식을 사용한다고 설명한다 | 프로젝트 검색에 외부 rg를 쓰는 방식만 있는 것은 아니다. 미저장 문서 반영의 모든 내부 경로까지 이번에 실행 검증한 것은 아니다 |
| Vim | [공식 매뉴얼](https://vimhelp.org/quickfix.txt.html#grep)은 자체 `vimgrep`과 외부 `grep`을 모두 제공하며, 큰 프로젝트에서는 외부 프로그램을 고려하도록 안내한다 | 검색 문법을 통일하는 명령과 외부 도구의 속도를 선택할 수 있게 분리한 사례다 |

제3자 앱의 숫자를 Maru 예상 속도로 옮기지 않는다. Zed는 공식 설명의 동작·책임만 참고했으며 GPL 구현 소스를
읽어 코드 구조를 옮기지 않았다. 비교 프로브는 Maru 함수와 공개 CLI를 호출하는 독립 실험이다.

## 실제 파일로 확인한 것

실험 도구는 CLI 동작을 보는 [probe.py](../../tools/editor-project-search/probe.py), 후보별 지연/RSS를 비교하는
[compare.py](../../tools/editor-project-search/compare.py), 모든 일치 범위를 대조하는
[verify.py](../../tools/editor-project-search/verify.py)와 기존 `findMatches`를 직접 호출하는
[native.zig](../../tools/editor-project-search/native.zig)다. CLI가 반환한 JSON·오류·버전·바이너리/도구 해시를
지정한 새 디렉터리에 남긴다. 경로와 본문은 도구가 만든 합성 자료만 사용한다.

```sh
mise exec -- zig build editor-project-search-probe -Doptimize=ReleaseFast
python3 tools/editor-project-search/probe.py \
  --native zig-out/bin/maru-project-search-probe \
  --output zig-out/project-search-probe-<새이름>
python3 tools/editor-project-search/verify.py \
  --native zig-out/bin/maru-project-search-probe \
  --output zig-out/project-search-verification-<새이름>
python3 tools/editor-project-search/compare.py \
  --native zig-out/bin/maru-project-search-probe \
  --output zig-out/project-search-comparison-<새이름> --runs 5
```

성능 비교와 빌드·다른 스트레스를 동시에 실행하지 않는다. 각 명령의 출력 디렉터리는 새 이름이어야 하며,
이 도구들은 자료를 자동 삭제하지 않는다. `compare.py`의 peak RSS 측정은 `wait4`가 있는 macOS/Linux용이다.

| 관측 | 결과와 의미 |
|---|---|
| 숨김 파일·중첩 `.gitignore`·부정 패턴·`.ignore`·`.rgignore` | 기대한 파일 집합과 일치. `.git` 내부·외부로 향하는 symlink·앞에 NUL이 있는 파일은 제외 |
| `-g`의 명시적 include | ignore된 확장자도 포함된다. “include는 ignore 후의 단순 교집합”으로 설명하면 틀린다 |
| 한글·CRLF·lookbehind·역참조·빈 일치 | UTF-8 byte 범위와 예상 파일을 확인. 잘못된 패턴은 exit 2, 결과 없음은 exit 1 |
| CLI 설정 주입 | 모든 파일을 제외하는 `RIPGREP_CONFIG_PATH`가 있어도 `--no-config`로 결과 보존 |
| 개행 파일명·깨진 UTF-8 본문 | JSON 프레이밍과 `bytes` 복호화 확인. macOS 파일 시스템이 깨진 UTF-8 **파일명 생성은 거부**했으므로 그 실제 파일명 경로는 미검증 |
| `foo`에서 정규식 `^\|foo` | ripgrep은 길이 0, 기존 Maru는 길이 3. 네이티브 호출로 대조 |
| `foo😀bar`에서 단어 단위 `foo` | ripgrep은 1건, 기존 Maru는 0건. Maru는 ASCII 밖의 byte도 현재 낱말에 포함한다 |

### 재검토에서 확인한 오류와 설계 빈틈

기존 비교 도구는 줄 끝의 CR을 전부 제거하고 UTF-8 BOM을 본문에 남겼다. 실제 편집기는 BOM을 파일 속성으로
분리하며 LF 바로 앞의 CR 하나만 줄바꿈으로 처리한다. 그래서 BOM 파일의 `needle` 시작 byte가 0 대신 3이 되고,
`needle\r`·`needle\r\r\n`에서 `^needle$`가 잘못 일치했다. 두 후보가 같은 전처리 오류를 공유하여 범위 대조도
통과한 결함이다. 도구를 실제 `document.open`·`line_index.build`로 바꾸고, 후보 비교와 별도로 고정 기대 범위를
검사한다. 기존 바이너리가 이 독립 검사에서 실패하는지도 확인한다. 깨진 byte 선별 검사는 `--raw-bytes`로
분리하며 제품의 파일 열기 성공으로 세지 않는다.

| 재현·소스 확인 | 보완할 제품 조건 |
|---|---|
| 고정 VCS 제외 뒤에 사용자 include를 넣으면 `.git` 내부가 검색된다. VCS 내부를 root로 삼으면 상대 glob에는 `.git`이 없다 | 고정 제외를 마지막에 적용하고, root·상위 경로의 VCS 신원도 검사한다. glob 순서만으로 root 검증을 대체하지 않는다 |
| 상위 root가 `sub/`를 ignore해도 `sub` 자체를 별도 root로 검색하면 파일이 포함된다 | root별 선정 결과를 먼저 계산하고 허용된 경로의 합집합에서 중복을 제거한다. 먼저 도착한 제외 결과가 다른 root의 허용을 막아서는 안 된다 |
| 일치가 없어 후보에서 빠진 파일을 수정하면 새 검색에서는 일치한다 | 양성 결과의 클릭 재검증만으로 누락을 복구할 수 없다. 후보 제외·ignore·디렉터리 변경도 무효화해야 한다 |
| 열린 문서의 `Document.content`는 입력 버퍼를 빌리며 `document_state.State`의 편집 버퍼는 가변이다 | revision 비교만으로 worker의 버퍼 수명이 안전해지지 않는다. 소유한 불변 사본과 IME 상태 신원이 필요하다 |

앞의 세 파일 사례는 CLI에서 재현했고 마지막 항목은 기존 소유권 구현을 확인한 설계 검토다.
제품의 root 검증·동시 변경·문서 사본 worker를 구현하거나 실행 검증했다는 뜻은 아니다.

### 같은 자료에서 비교한 비용

아래 S0 표는 커밋 `a6470cc6dc98d341a125a1004b0cd2b75ff15247`의 기존 matcher를 사용한 후보 비교 기록이다.
후속 평문 개선의 수정 전후 비용은 별도 기록으로 남기며, 이 표의 숫자를 현재 matcher의 측정값으로 바꾸어 읽지 않는다.

2026-10-05, Apple M4 Max(16코어·64 GiB), macOS 26.5.1, ripgrep 15.2.0/PCRE2 10.45,
Maru ReleaseFast로 파일 해석 수정 후 재측정했다. 2,048파일·64 MiB이며 실행 순서를 회전한 5회 **전체 시간 중앙값(ms)**이다.
기존 matcher를 부르는 경로는 rg 목록·Python 경로 변환·별도 프로세스·순차 파일 읽기 비용을 포함한다.

한글·정규식은 내용 선별을 하지 않으므로 해당 열에 우열을 적지 않았다. 그 경로의 반복값도 기록에는 남긴다.
평문 byte 탐색은 **대소문자를 구분하는 경우만** 측정했다. 기본 대소문자 무시와 단어 판정의 최적화가
끝났다는 뜻이 아니다. 흔한 단어는 선별해도 대부분을 다시 읽으므로 오히려 느려질 수 있다.

첫 결과를 pipe에서 실제로 받은 시간은 드문 평문에서 rg **23.31 ms**, 기존 찾기 **429.13 ms**,
선별 후 찾기 **44.13 ms**, byte 탐색 **76.18 ms**였다.
흔한 평문에서는 기존 찾기 **23.83 ms**보다 선별 후 찾기 **63.88 ms**가 늦었다.
이 비용 실험은 후보 목록 전체를 받은 뒤 matcher를 시작한다. 제품 worker의 점진 수신·우선순위 스케줄링을
구현한 결과가 아니며, 이 first-result 신호도 화면에 미리보기가 그려진 시점은 아니다.

`wait4`로 잰 시나리오별 **자식 peak RSS 중앙값**은 rg 전체 검색 6.41~6.84 MiB,
목록 뒤 기존 Maru 검색 프로세스 2.09~2.31 MiB, rg 목록/선별 프로세스 5.12~6.84 MiB였다.
별도 수명의 peak를 단순히 합치지 않는다. Python·앱·렌더·열린 문서 사본·검색 결과 UI 메모리는 포함하지 않는다.

캐시를 비우지 않았고 시스템의 배경 부하를 격리하지 않았다. 반복값의 범위도
[비교 원시 기록](../../tools/editor-project-search/results/comparison-macos-arm64.json)에 남겼다.
Maru 도구는 성능 측정 때 개수/첫 범위만 출력하므로 rg JSON의 전체 미리보기 생성·직렬화와 같은 일이 아니다.
따라서 수십 ms 차이로 범용 우열이나 제품 성능 예산 통과를 선언하지 않는다. 대량 일치·거대한 단일 파일·
원격 파일 시스템·플랫폼별 배포물은 별도 gate다.

실제 출력 중인 rg에 종료 신호를 보내 수거하는 데 4.59~41.90 ms가 걸렸다.
[CLI 동작 기록](../../tools/editor-project-search/results/macos-arm64.json)에 오류/취소 검사와 별도의 기초 측정도 있다.
그 기초 측정은 비교 표와 다른 실행이다. **Maru matcher/파일 읽기의 취소나 앱 반응성을 검증한 것은 아니다.**

### 찾아 수정한 선별 누락과 범위 대조

처음의 내용 선별은 앞에 NUL이 있는 파일과 BOM 변환 대상 파일을 누락했다. 기존 matcher에는 보이는 ASCII
일치가 rg의 바이너리 판정·자동 변환 뒤에는 사라진 것이다. 실험의 선별을 `--text --encoding none`으로 바꾸어
원본 byte의 후보를 넓게 잡도록 했다. 이것은 바이너리를 제품 검색 대상으로 승인한 것이 아니다.
자동 변환 반례의 `FF FE` 접두 자료는 잘못된 UTF-8이므로 현재 편집기가 열지 못한다. 이 반례는 raw 선별의
상위 집합 검사이며 제품에서 실제로 열리는 문서의 누락 증거와 구분한다. 유효한 UTF-8 BOM은 별도 oracle로 검증한다.
제품은 파일 허용·인코딩 검사를 별도로 하고 제외 사유를 표시해야 한다. 기존 문서 계약은 유효한 UTF-8의
NUL을 거부하지 않는다. 따라서 rg가 바이너리로 분류한다는 이유만으로 편집기에서도 못 여는 파일이라고 설명하면
틀린다. NUL 포함 파일의 프로젝트 선정 정책은 제품 연결 전에 확인할 항목이다.

`verify.py`는 후보별 **파일·줄·시작 byte·길이 전체**를 기존 `findMatches`와 대조한다. 개수만 같으면
통과시키지 않는다. 한글/결합 문자, Kelvin 기호·긴 s·터키어 I, emoji와 `$`/밑줄의 단어 경계,
겹치는 평문, CRLF·고립 CR·중복 CR·UTF-8 BOM, 빈 파일, 빈 대안·lookbehind·역참조, 깨진 byte와 특수 파일명을 포함한다.
제품 문서 계약의 독립 oracle은 BOM 좌표·앵커·CR·NUL 범위를 고정하고, 잘못된 UTF-8의 기본 경로 거부도 확인한다.
빈/여러 줄/정규식/비ASCII 검색어에는 이 후보 필터를 적용하지 않는지도 검사한다.

수정 후 모든 실험 범위가 같았다. 바이너리 허용·원본 인코딩·대소문자 처리·단어 필터·비ASCII 보호를
각각 잘못 바꾼 음성 대조군도 누락/잘못된 경로 선택으로 실패했다.
[범위 대조와 음성 대조 기록](../../tools/editor-project-search/results/verification-macos-arm64.json)을 보존한다.
이것은 합성 자료에서의 증거이며 모든 Unicode·파일 경합에 대한 증명은 아니다.

### 실측 뒤 권고

1. **공통 matcher를 쓴다는 이유만으로 느리다고 판단하지 않는다.** 대소문자를 구분하는 평문에는 반복 디코드를
   줄일 근거가 있다. 기본 대소문자 무시까지 같은 개선을 얻었다는 뜻은 아니다. byte 탐색을 제품에 넣기 전에
   기본 옵션·단어 판정과 실제 호출 경로를 검증한다. 초기 후보는 실험 도구였고 후속 평문 개선은 기존 찾기에 연결한다.
2. 후보 선별은 드문 ASCII 검색에서 유효하지만 모든 검색에 강제로 켜지 않는다. 흔한 검색·첫 결과 지연·
   취소·입출력 예산을 함께 보고, 목록을 전부 기다리는 실험 구조도 점진 처리로 바꿔야 한다. 정적인 합성 자료의
   범위 동등성만으로 선별을 채택하지 않는다. 제외 후보의 변경·무효화까지 검증하기 전에는 제품에 연결하지 않는다.
3. 파일 선정은 rg 재사용이 ignore 구현 부담을 줄인다. 다만 **번들 채택은 아직 미결**이다. 직접 순회 후보는
   동일 ignore 정책을 구현하지 않았으므로 속도를 꾸며 동등한 대안으로 평가하지 않았다.
   기존 의미를 보존하는 평문 개선의 효과를 확인하고, 파일 해석·사본 소유권·변경 무효화 계약을 확정한 뒤
   최종 프로젝트 검색 엔진 구성을 결정하는 순서를 권한다.

### 기존 평문 검색 개선

`findMatches`는 대소문자를 구분하는 평문을 `std.mem.indexOfPos`로 찾는다. 검색어 UTF-8 검사 뒤에만 사용하므로
continuation byte에 새 시작점을 만들지 않는다. 단어 판정은 기존 `selection.wordRangeAt`을 쓰고,
거절한 후보 뒤에는 다음 코드포인트부터 다시 검사한다. 대소문자 무시는 양쪽 문자가 ASCII일 때의 디코드만 줄이며
현재 검색의 접기 판정은 #4148에서 도입한 `search_case_fold.fold`의 Unicode 17 C/S 매핑을 쓴다.
이전 비용 비교는 그 변경 전 기록이며 현재 동작·재비교는 아래 절이 소유한다. Unicode 정규화는 하지 않는다.

`FND33`은 독립된 코드포인트 판정으로 유효/깨진 byte·NUL·결합 문자·Unicode 접기·두 토글의 조합 전체를 대조한다.
CLI의 `--baseline-native`는 수정 전 바이너리와 파일·줄·byte·길이 전체를 대조하고, 비용 비교에서는 정렬된 같은
파일 순서와 실행 순서 회전을 사용한다. S0의 후보 선별과 별개로 기존 문서 내 검색의 개선을 검증하는 경로다.
이 작업으로 worker 취소·불변 사본·프로젝트 파일 선정·검색 도크가 구현됐다고 표시하지 않는다.

## 검색 도크의 초기 범위 제안

### 대상과 입력

- 현재 창의 **탐색기에 확정된 로컬 루트들**을 검색 범위로 표시한다. 미검증 root나 MRU 전체를 검색하지 않는다.
  겹치는 root는 각 root 기준으로 glob·ignore를 판정한 뒤 허용 경로를 합친다. 같은 정규화 경로는 한 번만 검색하며
  표시 root는 요청의 root 순서에서 처음 허용한 항목으로 고정한다. hard link의 서로 다른 이름은 별도 경로다.
  루트가 없으면 폴더 열기를 안내한다. 원격 pane에서는 로컬의 직전 경로를 원격 프로젝트인 것처럼 검색하지 않는다.
- 검색 요청은 root 목록·신원·세대와 검색어·옵션의 사본을 소유한다. 폴더 선택이나 탐색기 추종으로 root가 달라지면
  진행 중 작업과 결과를 무효화한다. 검색 도크의 `refreshForFocus`는 원격 여부·문서 사본·확정된 root 세대를 확인한다.
  로컬 pane 이동만으로 검색 범위를 넓히지 않는다. 범위 칩은 현재 검색 root를 계속 보여주며,
  검색 때문에 탐색기의 root 정책이나 터미널 cwd를 바꾸지 않는다.
- 기존 도크에 검색 뷰·팔레트 명령을 추가한다. 우측/하단 위치와 크기는 기존 도크 설정을 따른다.
  검색칸 하나, 대소문자·단어·정규식 토글, 펼칠 수 있는 포함/제외 입력, 검색/취소 버튼을 둔다.
  첫 단계는 Enter로 시작한다. IME 조합 중 Enter는 조합 확정에 쓰고 미완성 문자열로 작업을 시작하지 않는다.
  자동 입력 중 검색은 debounce 비용과 한국어 입력 동작을 측정한 뒤 별도 도입한다.
  입력 중인 검색어·옵션과 적용된 요청은 구분한다. 입력을 바꾸면 이전 결과가 새 입력의 결과처럼 보이거나
  새 요청의 행으로 동작하지 않게 상태와 클릭 신원을 함께 갱신한다.
- 평문은 기존 문자열 검색, 정규식은 파일 안 찾기와 같은 원문 문서 전체 계약을 사용한다.
  여러 줄 결과는 시작 위치와 원문 span을 보존하며 미리보기의 표시 예산은 별도로 제한한다. 빈 검색어는 작업을 시작하지 않으며,
  정규식 오류는 기존 결과를 현재 검색어의 성공 결과처럼 남기지 않고 입력 옆에 표시한다.

### 파일 선정과 열린 문서

- 일반 dotfile은 포함하며 `.git`·`.hg`·`.svn` 이름의 메타데이터 파일과 내부는 항상 제외한다. symlink는 따라가지 않는다.
  VCS 내부를 root로 지정한 경우도 거부한다. 상대 경로 glob 외에 root와 상위 경로의 검사가 필요하다.
  루트 안 ignore 파일을 기본 적용하고, 초기 범위에서는 상위/전역 ignore를 끄며 그 범위를 UI 설명에 적는다.
  이는 모든 VS Code 기본 설정을 그대로 채택한다는 뜻이 아니다.
- 포함 패턴의 명시적 선택이 ignore보다 우선할 수 있는 rg 규칙을 그대로 설명한다. 명시적 제외는 마지막에 적용한다.
  `*`·`**`·`?`·문자 클래스·중괄호와 쉼표 구분의 모호함은 입력 파서 fixture로 확정하며,
  shell glob이나 사용자의 rg 설정 파일을 실행하지 않는다. 사용자 패턴 뒤에 고정 VCS 제외를 적용하여,
  include나 ignore 해제도 고정 제외를 덮지 않게 한다. 열린 문서의 경로 필터도 같은 우선순위를 따른다.
- 디스크 본문도 기존 `document.open`·`line_index` 계약으로 해석한다. UTF-8 BOM은 속성으로 분리하고 CRLF의 CR
  하나만 줄바꿈에 포함한다. 고립 CR·추가 CR은 본문이다. 결과 좌표는 BOM을 제외한 문서의 줄·byte 범위이며,
  원본 파일 offset이 필요할 때만 `Document.fileOffset`과 줄 인덱스로 변환한다. 잘못된 UTF-8은 변환을 추측하지
  않고 제외 사유를 알린다. **NUL 파일을 포함할지 별도 제외할지는 미결**이며, 후자를 택하면 열린 파일과 디스크의
  대상 차이를 명시해야 한다. `--raw-bytes` 결과는 이 제품 계약을 대체하지 않는다.
- 경로가 범위에 들어오는 **열린 네이티브 문서는 dirty 여부와 무관하게 현재 내용**을 검색한다.
  동일 공유 문서는 registry/document 신원으로 한 번만 캡처한다. 같은 경로의 독립 문서들은 합치지 않고
  각각의 열린 문서 결과로 구분하며, 그 경로의 디스크 결과는 억제한다. **0건인 문서도 억제 목록에 남긴다.**
  사본 준비 중·할당 실패·정규식 실행 실패·예산 도달도 점유 기록을 유지한다. 해당 열린 문서가 검색되지 못했다고
  디스크의 옛 결과를 되살리지 않으며, 부분 실패를 표시한다.
  문서의 생성·닫기·Save As·편집·IME 조합 변화로 사본이 낡으면 해당 결과는 무효화하고 다시 검색한다.
- VS Code처럼 **열린 문서는 디스크 ignore와 별도로** root·명시적 include/exclude를 검사한다.
  ignore된 열린 문서와 아직 디스크에 없는 이름 있는 문서도 포함될 수 있으며 “열린 편집 내용”으로 출처를 표시한다.
  디스크와 열린 문서의 명시적 glob 판정이 같도록 경로 필터를 검증한다. 후보 목록에 없다는 이유만으로 열린 문서를
  빠뜨리지 않는다. VCS 내부 제외·symlink 범위 경계는 여기에도 적용한다.
- 이름 없는 문서·원격·diff/merge 가상 문서는 초기 프로젝트 범위 밖이다. 웹 편집기의 최신 본문을 확보하지 못한
  Markdown/SVG 등은 **디스크 결과로 대체하지 않고 해당 파일 제외 안내**를 남긴다. 이를 전체 프로젝트 완료로
  오인하지 않도록 제외 파일 수를 표시한다. 웹 본문 사본 연결은 후속 gate다.

### 수명·출력·실패

- L2 `session/editor/search/`는 요청 신원·파일별 결과·상태·취소 세대를 소유한다. L3 컴포넌트는
  보이는 행과 입력/접근성 표만 투영한다. L4 `app_session/editor/search/`가 I/O·worker·열린 문서 사본·이동을 연결한다.
  기존 찾기에서 재사용할 matcher는 파일 I/O를 모르고 query를 한 번 준비하며 worker마다 독립 상태를 갖는다.
- 목록 helper는 앱 번들의 고정 실행 파일을 shell 없이 argv로 실행한다. 배포 버전·해시·라이선스·아키텍처·서명을
  묶어 검증한다. 임의 PATH 탐색이나 저장소 안 실행 파일은 허용하지 않는다. 설치된 Codex/Homebrew의 rg는 배포물이 아니다.
  `--files --null --no-config`의 목록을 점진적으로 읽고, 실제 내용은 검증된 root 아래 descriptor 기준으로 연다.
  목록 생성 뒤 root/디렉터리가 링크로 바뀌는 경쟁도 제품 테스트에서 거부해야 한다. 읽는 대상은 일반 파일인지
  descriptor로 확인한다. FIFO로 교체된 파일을 여는 동안 막히지 않도록 비차단 열기와 플랫폼별 동등 경로를 검증한다.
  이 본문 읽기 검사는 rg 자체의 ignore 파일 읽기를 OS sandbox로 가둔다는 보장이 아니다.
- worker는 살아 있는 `Term`·가변 문서·빌린 줄 slice를 직접 읽지 않는다. 소유한 불변 사본의 준비·예산 예약이
  끝나야 검색을 시작한다. 현재 그런 snapshot API가 이미 있다는 가정은 하지 않는다. owner 측에서 나누어 복사한다면
  각 배치의 문서 신원·revision·IME 조합 세대를 확인하고, 중간 변경은 폐기/재시도한다. 결과를 받는 시점에도
  요청·root·열린 경로 점유 집합·문서·조합 신원이 모두 맞아야 한다. 사본 확보 방법과 최대 비용은 S1 선행 설계다.
- 목록 전부나 문서 전부를 main tick에서 복사/검색하지 않는다. 초기 worker의 파일·줄·byte 배치 사이에 취소를 관측하고,
  PCRE2에는 기존 실행 한도를 유지한다. 거대한 한 줄의 평문 탐색도 배치 경계가 필요하다.
  분할은 UTF-8·겹침 없는 반복·단어 앞뒤 문맥을 보존해야 한다. 정규식을 단순 조각별 실행하면 앵커·lookbehind·역참조의
  의미가 달라지므로 그렇게 배치화하지 않는다. PCRE2 실행 한도만으로 파일 I/O나 벽시계 취소 지연이 보장되지는 않는다.
  취소/새 요청/창 닫기는 세대를 먼저 폐기한다. 늦은 완료는 버리고 helper는 kill/reap한다.
  느린 파일 I/O를 main actor에서 join하지 않는다. 교체 대기 요청과 종료 중 worker 수도 제한하고 수거 기한을 검증한다.
- 행·미리보기 byte·완료 queue·열린 문서 사본에 각각 예산이 필요하다. 고정 숫자는 이번 실험으로 정하지 않는다.
  과밀 결과·긴 한 줄·큰 열린 문서에서 메모리와 첫 결과/취소 지연을 측정한 뒤 정한다.
  용량에 도달하거나 일부 파일을 읽지 못하면 **일부 결과/제외 사유**를 표시하고 0건 성공으로 바꾸지 않는다.
  완료·취소·오류는 일치 행 queue가 가득 차도 전달되어야 한다. 종료 상태 전달 공간은 결과 행 예산과 분리한다.
  전체 파일 수를 모르는 동안 가짜 진행 퍼센트 대신 검색 중·처리 파일 수·결과 수를 표시한다.
- 결과를 누르면 파일·줄·범위로 이동한다. 누름/놓음 사이 요청·행·geometry가 바뀌면 취소한다.
  열린 문서는 revision, 디스크 파일은 읽은 본문의 신원/내용을 재검증한다. 외부 변경이 있으면 옛 offset으로 이동하지 않고
  해당 파일을 재검색한다. OOM·입력 표·접근성 발행 실패는 낡은 행 동작을 남기지 않는다.
- 디스크 전체의 원자적 snapshot은 약속하지 않는다. 결과는 스캔 동안 관측한 내용이며, 이후 변경은 낡은 결과로
  표시하고 재검색한다. 변경 감지는 양성 파일뿐 아니라 제외 후보·새 파일·이름 변경·ignore 파일·디렉터리에도 필요하다.
  탐색 시작 전 감시 등록과 스캔 중 변경 기록, 감시 누락/overflow 시 요청 전체 무효화를 S1에서 검증한다.
  이 연결이 없으면 내용 선별 이후 제외 파일에 생긴 일치는 클릭 재검증만으로 찾을 수 없다.
- 진단은 요청 세대·원인·처리량·지연·제외 수만 남긴다. 사용자 검색어·본문·절대경로는 일반 로그에 남기지 않는다.
  제품 테스트의 합성 fixture와 같은 상태 이벤트를 snapshot/trace가 소비하게 한다.

## 구현 순서와 완료 조건

| 단계 | 범위 | 완료 조건 |
|---|---|---|
| S0 | 후보 실측·설계 | 이 변경의 범위. CLI/기존 matcher 차이·비용, 문서 계약의 독립 oracle·전체 범위 대조·경로/변경 반례를 기록. 엔진·새 의존성·NUL 선정·초기 범위와 사본 확보 방식은 미결 |
| S1 | 공통 matcher·경로 선정·worker | bounded/cancel 가능한 matcher와 문서/디스크 해석 동등성, 불변 사본 소유권·기본 옵션 비용, root별 glob·VCS root 거부·FIFO 교체, helper 수명·부분 실패·제외 후보/ignore 변경·감시 overflow 검증 |
| S2 | 검색 도크·열린 문서·클릭 이동 | 우측/하단·좁은 폭·배율·스크롤·공유/독립 문서·0건 덮어쓰기·IME Enter·root 변경·낡은 클릭·실제 여러 파일 이동을 제품 앱에서 검증. Metal PNG를 PR 본문에 첨부 |
| S3 | 바꾸기 미리보기 | 선택한 파일/일치별 전후 diff. 표시 revision과 원본 bytes를 고정하고 미리보기 뒤 변경은 충돌로 표시 |
| S4 | 선택 적용 | 열린 문서는 Undo와 IME, 디스크는 외부 변경·저장 실패·권한·원자 저장을 검증. 여러 파일 실패/부분 성공·재시도·되돌리기 정책을 별도 승인한 뒤 연결 |

S1/S2는 바꾸기를 실행하지 않는다. S4도 여러 파일 전체의 원자적 성공이나 crash 이후 Undo 보존을 약속하지 않는다.
최종 저장은 기존 파일 저장/복구 계약을 재사용하되, 이미 구현된 `WorkspaceEdit`의 존재만으로 이 gate를 닫지 않는다.

현재 **제품 검색·도크·사용자 취소·미저장 덮어쓰기·실제 IME·앱 전체 RSS·바꾸기는 미검증**이다.
위 CLI 프로브 통과를 그 기능의 완료로 표시하지 않는다.


## 후속 검색 규칙 개선 — Unicode 평문 검색

검색용 접기와 편집용 대소문자 변환을 분리했다. 편집기·터미널 평문 검색은 `search_case_fold.fold`의
Unicode 17.0.0 C/S 전체 1,512개 매핑을 사용한다. 원문 byte·셀 범위는 보존하며, 편집용
`terminal.selection.foldCase`·`upperCase`와 NFC/NFD 정규화·full folding 정책은 변경하지 않는다.
`FND34`와 `SCF1~3`이 검색 별칭·표의 전체 코드포인트 탐색·터미널 셀 결과·변환 분리를 검증한다.

[후속 범위 대조](../../tools/editor-project-search/results/unicode-verification-macos-arm64.json)에서
기존 Unicode 별칭 차이는 해소됐지만 정규식·빈 검색어 차이는 남았다. 이 기록은 프로젝트 검색 제품
구현이나 ripgrep 전체 호환성 완료를 뜻하지 않는다. 문서 전체 정규식과 줄별 검색 중 어떤 계약을
택할지는 논의했고 사용자가 문서 전체 정규식의 설계 후 구현을 선택했다. 기존 줄별 검색·치환은
Unicode 개선에서 유지하고, [문서 전체 확장](editor-document-regex.md)에서 매치 범위·캡처·치환을 함께 이관한다.

## 문서 전체 검색 계약으로 재비교한 결과

2026-10-05, #4145·#4148·#4153을 포함한 `6119e8de8eb46e378f89c967b25a5dd334d7b5a1`의
현재 검색을 ripgrep 15.2.0(PCRE2 10.45)과 다시 비교했다. 기존 S0의 줄별 정규식 결과와 구분한다.
[contract.py](../../tools/editor-project-search/contract.py)는 61개 파일·183개 질의에서 모든 절대 byte 범위를
대조한다. `document.open`과 같이 유효한 UTF-8 BOM만 제거하며 줄바꿈이나 EOF에 LF를 추가하지 않는다.
빈 파일·BOM·고립 CR·혼합 줄바꿈·NUL·Unicode·단어 옵션·빈 매치·여러 줄 정규식·오류를 포함한다.

| 실제 CLI 구성 | 같은 범위 | 다른 범위 | 한쪽 이상 오류 |
|---|---:|---:|---:|
| rg auto, 정규식 `--multiline --crlf` | 117 | 63 | 3 |
| rg PCRE2, 정규식 `--multiline --crlf` | 119 | 61 | 3 |

이 숫자는 질의별 판정이며 파일별 건수나 무작위 정규식 전체의 호환률이 아니다.
두 오류 질의 `[`·`(?<=a+)b`는 양쪽에서 거절됐다. `(*LF)^bar$`는 Maru가 실행하지만 rg는 거절했다.
rg가 패턴을 감싸는 CLI에서는 시작 위치 전용 newline verb를 덧붙이는 방법이 오류를 냈으므로,
비교기는 임의의 `(*ANYCRLF)`를 주입하지 않고 실제 `--crlf` 옵션을 쓴다. 원문 directive는 그대로 전달한다.
[rg 15.2.0 공개 소스](https://github.com/BurntSushi/ripgrep/blob/15.2.0/crates/pcre2/src/matcher.rs#L41-L74)에서
패턴마다 그룹을 덧붙이는 점을 확인했다. 구현 표현을 복사하지 않고 실제 CLI 거절 원인을 확인하는 데만 사용했다.
이 자료에서는 `^foo$`·`foo\r?\nbar`·`\Afoo`의 범위가 같았고, 단순히 문서 전체 정규식이라는 이유만으로
불일치한다고 결론 내리지 않는다.

남는 차이는 다음과 같다.

- 빈 평문 검색: Maru는 0건, rg는 빈 범위를 생성한다. 제품 어댑터에서 빈 질의를 실행하지 않으면 피할 수 있다.
- 단어 옵션: Maru는 편집기의 단일 낱말과 정확히 같아야 하고 rg는 자체 word 경계를 쓴다.
  문장부호·emoji·`$`와 여러 줄 정규식의 단어 옵션은 서로 같은 계약이 아니다.
- 빈 정규식 대안: `^|foo`에서 Maru는 같은 위치의 비어 있지 않은 대안을 우선하고 빈 마지막 줄도 검사한다.
  rg는 이 자료에서 다른 범위를 보고한다. `--pcre2`만으로 호출자의 반복 정책까지 같아지지 않는다.
- Unicode 버전: 공식 Unicode 17 C/S 1,512 매핑으로 만든 자료의 2,994개 질의에서 Maru의 **모든 byte 범위가
  공식 데이터에서 독립 계산한 기대값과 같았다**. 설치된 rg 기본 엔진과는 56개 질의의 범위가 달랐다.
  비교한 코드포인트는 U+A7CE/U+A7CF·U+A7D2..U+A7D5·U+16EA0..U+16ED3 안의 해당 문자다.
  특정 엔진 이름이 항상 더 정확하다는 근거가 아니라 이 실행 파일과 데이터 버전의 차이다.

Apple M4 Max·64GiB에서 2,048파일·64MiB, 순서 회전 5회, 캐시 미제거·배경 부하 미격리로 다시 잰 전체 시간 중앙값(ms):

| 검색 | rg 전체 검색 | 목록 + Maru | 후보 선별 + Maru |
|---|---:|---:|---:|
| 드문 평문 | 26.16 | 65.43 | 32.78 |
| 흔한 평문 | 27.90 | 67.23 | 99.95 |

[성능 원시 기록](../../tools/editor-project-search/results/current-comparison-macos-arm64.json)은 반복값과 자식 RSS를 보존한다.
기존 범위 oracle 24개·오류 3개와 후보 선별의 누락 방지/음성 대조도 다시 통과했다.
좌표를 +1로 변형한 실행 파일은 `contract.py`의 고정 oracle에서 실패하여 비교기의 판정력도 확인했다.

**재비교 후 권고(아직 미채택):** rg는 고정 버전 번들로 파일 목록·ignore에만 사용하고,
열린 문서와 디스크 내용은 현재 Maru matcher로 일치 판정한다. 초기 worker에는 내용 선별을 넣지 않는다.
새 worker의 점진 결과·공정한 스케줄링·취소·불변 사본을 먼저 검증하고, 후보 선별은 누락 방지와 첫 결과
지연이 확인된 경우에만 후속 채택한다. rg의 시스템 PATH를 제품 실행 경로로 사용하지 않는다.
번들 의존성·초기 선정 범위에 대한 사용자 확인 전에는 이 권고를 구현 완료나 최종 결정으로 표시하지 않는다.

## VS Code 방향의 정책 변경 후 비교

2026-10-06 승인한 [기본 단어·빈 일치 정책](editor-search-policy.md)을 적용한 뒤 같은 61파일·183질의를 재대조했다.
rg auto는 동일 122/다름 58/오류 3, rg PCRE2는 동일 124/다름 56/오류 3이다.
앞 절의 숫자는 이전 정책의 역사적 기록이며 최신 정책과 구분한다. `^|foo`는 앞의 빈 대안을 유지하고
단어 검색은 기본 구분자의 양끝을 검사하지만, emoji·마지막 빈 줄·빈 파일·PCRE2 문법·Unicode 데이터 차이는
이 변경만으로 사라지지 않는다. Unicode 17 C/S 2,994질의의 Maru 기대값은 계속 모두 통과했고,
설치된 rg 기본 엔진과의 56차이도 유지됐다. 실제 VS Code Searcher의 공통 문법·단일 줄 1,380조합은 모두 같았다.
[정책 변경 후 기록](../../tools/editor-project-search/results/vscode-search-policy-macos-arm64.json)을 보존한다.

`contract.py`의 음성 대조는 새 정책에서 남는 단어 `foo`/정규식 `^$` 반례를 고정한다.
기존 `^|foo` 반례만으로 옛 빈 대안 우선 정책을 계속 강제하지 않는다. 엔진/rg 번들 채택·프로젝트 worker·도크는 여전히 별도 단계다.
