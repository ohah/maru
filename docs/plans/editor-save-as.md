# 이름 있는 문서의 Save As — 검토안

상태: 후속 저장 순서·취소 정책 승인, 순수 상태 전이 기반 구현. 새 대상 writer·모델 경로 전환 기반 추가. 제품 UI·저장 접수 조정은 미연결.
기준: main `eac3677dd3370e87be9cd6aa1c39b65c503cf796`.

## 현재 코드에서 확인한 범위

`editor/untitled_save.zig::begin`과 `commit`은 이름 없는 문서만 받는다.
`writeAndAdopt`는 동기 쓰기에 성공한 뒤 경로를 붙인다. 이름 있는 파일의
다른 경로 저장은 이 경로에서 제공하지 않는다. 따라서 「이미 구현된 Save As의
늦은 완료 결함」은 아직 재현한 사실이 아니다.

비동기 저장은 문서 신원·대상 epoch·원본 경로를 고정한다. 새 경로 저장은
이름 없는 문서 저장에 이름 있는 문서를 단순히 허용하는 것으로 구현하지 않는다.
원본 저장의 디스크 기준과 새 대상 저장의 기준은 다르다.

## 제안하는 첫 범위

이름 있는 일반 로컬 네이티브 문서에 다른 경로 저장을 제공한다.
원격·웹 bridge·diff는 기존 계약을 유지한다. UI 진입점은 별도로 검토한다.

1. 원본 문서 신원과 대상 epoch를 고정하고 사용자가 새 경로를 선택한다.
2. 원본 문서의 접수된 저장·포맷이 끝날 때까지 main actor를 막지 않고 기다린다.
   원본 저장 실패도 정산한 뒤 진행할 수 있다. 새 경로 저장은 원본 저장 성공을
   전제로 하지 않는다.
3. 입력 확정 뒤 현재 본문을 snapshot으로 고정한다. 논리적인 선행 조건은 원본 문서의
   저장으로 한정한다. 현재 전역 큐는 단일 worker이므로 다른 문서의 쓰기가 막히면
   새 대상의 실제 쓰기도 기다릴 수 있다. 다른 문서의 독립 완료를 보장하지 않는다.
4. 같은 경로면 일반 저장으로 보낸다. 다른 열린 독립 문서가 점유한 경로는 거절한다.
   새 파일은 배타 생성하고 기존 파일은 덮어쓰기 확인을 거친다.
5. 새 대상의 실제 쓰기가 성공하고 동일 문서·epoch가 살아 있을 때만 경로를 바꾼다.
   공유 뷰는 같은 문서의 새 경로를 함께 본다. Undo는 유지한다.
6. 저장 중 추가 편집은 새 경로에서도 dirty로 남긴다. clean 여부는 개정 번호만이 아니라
   실제 저장 snapshot과 현재 본문의 비교로 판정한다. 입력 후 Undo로 snapshot에 돌아온
   경우도 검사한다. 실패·쓰기 접수 전 취소 시 원본 경로와 본문·Undo를 유지한다.
   접수 뒤 UI 취소는 연산을 중단하지 않으며 실제 결과까지 정산한다.

## 승인한 순서·취소 정책의 기반

2026-10-14 사용자는 후속 ⌘S를 대기시켜 성공 시 새 경로, 실패 시 원본 경로로
보내고 접수 전 취소만 작업을 중단하는 제안을 승인했다. `ops/save_as.zig::State`는
이 판정을 OS·I/O·UI 없이 구현한다. `accept` 이후 새 저장은 `deferred`이고,
`start`는 원본 선행 저장 정산과 입력 확정을 모두 요구한다. 성공은 실제 쓰기와
문서 경로 전환 뒤에만 `finish(true)`로 전달한다. 등록/준비 실패는 `finish(false)`다.
중복 완료·접수·조기 성공을 거절하며 최종 저장 경로를 뒤집지 않는다.

이 모듈은 아직 제품 저장 진입점에 연결되지 않았다. 문서 신원·대상 예약·worker·
필수 메모리 선확보·경로 바인딩은 후속 actor의 책임이다. 이 기반 테스트로 실제
디스크 순서나 앱 동작을 검증했다고 보고하지 않는다.

`mise exec -- zig build test-editor-save-as-policy`는 상태 전이 계약을 실행한다.

원본 경로의 파일은 유지한다. 대상 성공 전 원본 문서를 revert하지 않는다.
이는 Maru의 제안이며 VS Code와 모든 내부 단계가 동일하다는 주장이 아니다.

## 구현 전에 해결할 경계

- symlink·hardlink·대소문자 차이 등 같은 실제 파일은 단순 문자열 비교만으로
  다른 대상이라고 처리하지 않는다. 동일 파일의 별칭 경로 정책은 구현 전에 검토한다.
- 경로 변경에 필요한 메모리·registry 갱신을 쓰기 전에 준비하여 디스크 성공 뒤
  경로 갱신 OOM으로 중간 상태가 남지 않도록 한다.
- 새 대상 쓰기 동안 원본 ⌘S의 추가 접수·닫기·두 번째 Save As가 어떻게 정렬되는지
  상태 전이와 함께 정한다. 전역 큐 drain으로 UI를 막는 방식은 사용하지 않는다.
- 새 대상 쓰기 성공 뒤 원본 문서가 사라지면 다른 문서에 완료를 적용하지 않는다.
  생성한 파일을 자동 삭제하여 다른 프로세스의 후속 편집을 지우지 않는다.
- 새 경로의 LSP·syntax·watcher·백업 신원 갱신을 성공 경계에 연결한다.

## 반복 설계 검증에서 발견한 누락

아래는 코드와 사건 순서를 대조한 설계 검증이다. 새 Save As 제품 실행이나
결함 주입 테스트를 수행한 증거는 아니다. 다섯 관점의 검토에서 나온 항목을 정리한다.

| 사건/반례 | 빠져 있던 계약 | 구현 전 필요한 결정·검증 |
|---|---|---|
| 원본 저장을 기다리는 동안 ⌘S가 계속 들어옴 | 단순 pending 확인은 영원히 끝나지 않을 수 있음 | 어느 시점까지의 요청을 선행 집합으로 잡는지, 이후 요청을 언제·어느 경로로 보내는지 결정 |
| batch·공유 뷰·다른 창에서 같은 문서를 저장 | 활성 뷰에서만 막으면 원본 쓰기가 다시 들어옴 | 문서 신원 기준으로 모든 접수 경로를 조정하고 receipt를 유실하지 않는지 검사 |
| 덮어쓰기 확인 후 원본 저장 대기 중 대상이 바뀜 | 오래된 확인으로 최신 외부 편집을 덮어쓸 수 있음 | 실제 접수 전 대상 신원/내용 재검증과 충돌 안내 정책 결정; 새 대상 기준을 원본 CAS hash로 대체하지 않음 |
| 목적지를 준비한 뒤 다른 창이 같은 경로를 열거나 Save As로 점유 | 최초 열린 문서 검사만으로는 중복 바인딩을 막지 못함 | 앱 전체 대상 예약의 수명·할당 실패·취소 정산과 경로 별칭 검사 설계 |
| worker 성공 후 경로 바인딩/백업 갱신 실패 | 파일은 생겼지만 문서는 옛 경로이고 성공 알림만 남을 수 있음 | 필수 메모리를 선확보하고 no-fail 모델 전환을 설계; 부가 서비스 실패와 디스크 실패를 구분 |
| 저장 중 편집→Undo, BOM·CRLF 문서 저장 | raw bytes hash와 logical content hash를 혼용하면 dirty가 틀림 | 새 대상 raw disk 기준과 실제 snapshot의 logical saved 기준을 각각 갱신; encoding 보존 검증 |
| 접수 후 Esc·포커스 이동·마지막 뷰 닫기 | 「취소면 경로 유지」와 「성공이면 경로 변경」이 충돌 | 접수 후 UI 소비자 취소와 문서 연산 취소를 구분하는 정책 필요; receipt 해제가 쓰기를 취소하지 않음 |
| 기존 닫기 actor와 Save As가 같은 문서에 겹침 | epoch 변경으로 닫기 의도만 취소되거나 옛 경로 저장이 접수될 수 있음 | 닫기·저장·새 경로 전환의 우선순위를 명시하고 양방향 경합 검사 |
| 다른 문서의 writer가 막힘 | 초안의 독립 완료 검증은 단일 worker 구조에서 성립하지 않음 | UI 이벤트 처리와 등록의 비차단성을 검증하고 실제 I/O 완료 지연은 별도로 보고 |
| 읽기 전용 원본, read-only 파일 패널 | 원본 쓰기 금지와 새 대상 쓰기 허용 여부가 다름 | 첫 범위는 편집 가능한 일반 문서로 제한할지, 읽기 전용 Save As도 허용할지 사용자 계약 확정 |

현재 `save.Owner.enqueueNotified`는 현재 경로의 `Prepared`를 만들고 read-only를
거절한다. `Queue.applyRetained`도 현재 Target과의 일치를 요구한다. 따라서 기존
enqueue/apply를 새 경로에 그대로 재사용하면 목적지 검증·완료 적용이 성립하지 않는다.
새 대상 준비와 성공 시 문서 전환을 별도 계약으로 설계해야 한다.

접수 뒤 취소와 후속 저장 라우팅은 위 승인 정책으로 정했다. 표는 최초 검토에서
발견한 누락의 기록이다. 동일 파일 별칭·열린 대상 충돌과 실제 actor 연결은 아직
미결이므로 제품 구현 완료로 판정하지 않는다. 기존 규칙의 변경을 이 검토 문서만으로 승인 처리하지 않는다.

## 검증 계획

차단된 실제 writer로 원본 A 저장→새 대상 B 저장의 순서를 관측한다.
동시에 다른 문서의 저장 등록과 UI 이벤트가 막히지 않는지 확인한다. 단일 writer의
순서 대기는 별도로 관측한다. 원본 실패·새 대상 실패·외부
수정·배타 생성 경쟁·추가 편집/Undo·공유 뷰·소비자 취소·문서 재사용·할당 실패를
디스크 bytes와 모델 상태로 대조한다. 기존 닫기·첫 저장·포맷 테스트를 함께 실행한다.
구현 PR마다 정상/결함 주입/복원 대조군과 실제 AppKit·Metal 캡처를 수행한다.

## 새 대상 writer·모델 전환 기반

`save/destination.zig::Prepared`는 원본 Target(문서 신원·경로·epoch)과 목적지
write path를 따로 소유한다. 목적지가 없으면 기존 첫 저장과 공유하는 배타 생성,
있으면 목적지의 명시적 raw hash로 CAS 쓰기를 한다. 원본 disk hash로 목적지를
검증하지 않는다. 같은 문자열 경로는 일반 저장으로 보내도록 준비를 거절한다.

작업 자료는 기존 `save/worker.zig::Service`에 넘길 수 있다. 넘긴 동안 caller의
`work`를 null로 비우고, 실제 Completion이 돌아온 뒤에만 되돌려 놓는다. actor가
문서 lease와 자료 수명을 보존해야 한다. 기존 전역 큐의 일반 저장 접수 경로에
이 자료를 그대로 넣는 구현은 아니다.

`adopt`는 실제 written, 미정산 상태, 원본 Target을 재검증한다. 필수 binding
메모리를 준비 때 확보하여 성공 경계에서는 할당하지 않고 경로·epoch·logical saved
hash와 raw disk hash를 갱신한다. 추가 편집과 Undo는 건드리지 않는다. 문서 모델과
자료의 allocator는 같아야 한다. caller는 올바른 모델 allocator를 전달해야 하며
서로 다른 자료 allocator로 adopt하는 호출은 거절한다.

아직 AppSession 저장 진입점에는 연결하지 않는다. 같은 실제 파일 별칭·앱 전체
목적지 예약·선행/후속 저장 조정·공유 뷰 entry/syntax·백업/LSP 갱신이 필요하다.
모델의 path가 바뀌었다는 테스트만으로 앱 전체 경로 전환 완료를 주장하지 않는다.
새 파일 생성의 I/O 실패 때 이미 생성한 일부 파일이 남을 수 있는 기존 첫 저장
계약은 바꾸지 않는다. 생성한 파일의 자동 삭제·전원 손실 복구를 보장하지 않는다.

`test-editor-save-as-write`는 실제 blocked worker와 디스크 bytes를 대조한다.
조기/중복 전환, 추가 편집/Undo 보존, 배타 생성 경쟁, 목적지 CAS 실패,
BOM/CRLF 보존, epoch 변경, 다른 문서 lease, 준비 할당 실패를 검사한다.
`test-editor-local-save`와 `test-editor-untitled`는 공용 writer로 옮긴 기존 경로의 회귀다.

격리 사본의 결함 주입 검증은 조기 전환·원본 Target/epoch 무시·목적지 CAS 무시·
배타 생성 무시·현재 본문을 잘못 clean으로 게시하는 변이를 실제 실행 단언으로 검출한다.
정상·복원 대조군은 10개(의미 테스트 6개와 공용 모듈 테스트 4개)를 모두 실행한다.
