# 이름 있는 문서의 Save As — 검토안

상태: 실제 명령·NSSavePanel·저장 접수 조정 구현. 기본 저장·취소·저장 중 추가 입력·한국어 OS 입력기 조합 중 저장과 화면 촬영 검증 완료. 한국어 입력은 CGEvent이며 사람의 키보드 조작·VoiceOver는 별도다.
기준: main `eac3677dd3370e87be9cd6aa1c39b65c503cf796`.

## 초기 설계 당시 코드에서 확인한 범위

`editor/untitled_save.zig::begin`과 `commit`은 이름 없는 문서만 받는다.
`writeAndAdopt`는 동기 쓰기에 성공한 뒤 경로를 붙인다. 이름 있는 파일의
다른 경로 저장은 이 경로에서 제공하지 않는다. 따라서 「이미 구현된 Save As의
늦은 완료 결함」은 아직 재현한 사실이 아니다.

비동기 저장은 문서 신원·대상 epoch·원본 경로를 고정한다. 새 경로 저장은
이름 없는 문서 저장에 이름 있는 문서를 단순히 허용하는 것으로 구현하지 않는다.
원본 저장의 디스크 기준과 새 대상 저장의 기준은 다르다.

## 제안하는 첫 범위

이름 있는 일반 로컬 네이티브 문서에 다른 경로 저장을 제공한다.
원격·웹 bridge·diff는 기존 계약을 유지한다. UI 진입점은 별도로 검토한다.

1. 원본 문서 신원과 대상 epoch를 고정하고 사용자가 새 경로를 선택한다.
2. 원본 문서의 접수된 저장·포맷이 끝날 때까지 main actor를 막지 않고 기다린다.
   원본 저장 실패도 정산한 뒤 진행할 수 있다. 새 경로 저장은 원본 저장 성공을
   전제로 하지 않는다.
3. 입력 확정 뒤 현재 본문을 snapshot으로 고정한다. 논리적인 선행 조건은 원본 문서의
   저장으로 한정한다. 현재 전역 큐는 단일 worker이므로 다른 문서의 쓰기가 막히면
   새 대상의 실제 쓰기도 기다릴 수 있다. 다른 문서의 독립 완료를 보장하지 않는다.
4. 같은 경로면 일반 저장으로 보낸다. 다른 열린 독립 문서가 점유한 경로는 거절한다.
   새 파일은 배타 생성하고 기존 파일은 덮어쓰기 확인을 거친다.
5. 새 대상의 실제 쓰기가 성공하고 동일 문서·epoch가 살아 있을 때만 경로를 바꾼다.
   공유 뷰는 같은 문서의 새 경로를 함께 본다. Undo는 유지한다.
6. 저장 중 추가 편집은 새 경로에서도 dirty로 남긴다. clean 여부는 개정 번호만이 아니라
   실제 저장 snapshot과 현재 본문의 비교로 판정한다. 입력 후 Undo로 snapshot에 돌아온
   경우도 검사한다. 실패·쓰기 접수 전 취소 시 원본 경로와 본문·Undo를 유지한다.
   접수 뒤 UI 취소는 연산을 중단하지 않으며 실제 결과까지 정산한다.

## 승인한 순서·취소 정책의 기반

2026-10-14 사용자는 후속 ⌘S를 대기시켜 성공 시 새 경로, 실패 시 원본 경로로
보내고 접수 전 취소만 작업을 중단하는 제안을 승인했다. `ops/save_as.zig::State`는
이 판정을 OS·I/O·UI 없이 구현한다. `accept` 이후 새 저장은 `deferred`이고,
`start`는 원본 선행 저장 정산과 입력 확정을 모두 요구한다. 성공은 실제 쓰기와
문서 경로 전환 뒤에만 `finish(true)`로 전달한다. 등록/준비 실패는 `finish(false)`다.
중복 완료·접수·조기 성공을 거절하며 최종 저장 경로를 뒤집지 않는다.

이 모듈은 아직 제품 저장 진입점에 연결되지 않았다. 문서 신원·대상 예약·worker·
필수 메모리 선확보·경로 바인딩은 후속 actor의 책임이다. 이 기반 테스트로 실제
디스크 순서나 앱 동작을 검증했다고 보고하지 않는다.

`mise exec -- zig build test-editor-save-as-policy`는 상태 전이 계약을 실행한다.

원본 경로의 파일은 유지한다. 대상 성공 전 원본 문서를 revert하지 않는다.
이는 Maru의 제안이며 VS Code와 모든 내부 단계가 동일하다는 주장이 아니다.

## 구현 전에 해결할 경계

- symlink·hardlink·대소문자 차이 등 같은 실제 파일은 단순 문자열 비교만으로
  다른 대상이라고 처리하지 않는다. 동일 디렉터리 항목의 별칭은 일반 저장으로 처리하고, 서로 다른 hardlink 항목은 원본을 보존하며 선택한 경로에 저장한다.
- 경로 변경에 필요한 메모리·registry 갱신을 쓰기 전에 준비하여 디스크 성공 뒤
  경로 갱신 OOM으로 중간 상태가 남지 않도록 한다.
- 새 대상 쓰기 동안 원본 ⌘S의 추가 접수·닫기·두 번째 Save As가 어떻게 정렬되는지
  상태 전이와 함께 정한다. 전역 큐 drain으로 UI를 막는 방식은 사용하지 않는다.
- 새 대상 쓰기 성공 뒤 원본 문서가 사라지면 다른 문서에 완료를 적용하지 않는다.
  생성한 파일을 자동 삭제하여 다른 프로세스의 후속 편집을 지우지 않는다.
- 새 경로의 LSP·syntax·watcher·백업 신원 갱신을 성공 경계에 연결한다.

## 반복 설계 검증에서 발견한 누락

아래는 코드와 사건 순서를 대조한 설계 검증이다. 새 Save As 제품 실행이나
결함 주입 테스트를 수행한 증거는 아니다. 다섯 관점의 검토에서 나온 항목을 정리한다.

| 사건/반례 | 빠져 있던 계약 | 구현 전 필요한 결정·검증 |
|---|---|---|
| 원본 저장을 기다리는 동안 ⌘S가 계속 들어옴 | 단순 pending 확인은 영원히 끝나지 않을 수 있음 | 어느 시점까지의 요청을 선행 집합으로 잡는지, 이후 요청을 언제·어느 경로로 보내는지 결정 |
| batch·공유 뷰·다른 창에서 같은 문서를 저장 | 활성 뷰에서만 막으면 원본 쓰기가 다시 들어옴 | 문서 신원 기준으로 모든 접수 경로를 조정하고 receipt를 유실하지 않는지 검사 |
| 덮어쓰기 확인 후 원본 저장 대기 중 대상이 바뀜 | 오래된 확인으로 최신 외부 편집을 덮어쓸 수 있음 | 실제 접수 전 대상 신원/내용 재검증과 충돌 안내 정책 결정; 새 대상 기준을 원본 CAS hash로 대체하지 않음 |
| 목적지를 준비한 뒤 다른 창이 같은 경로를 열거나 Save As로 점유 | 최초 열린 문서 검사만으로는 중복 바인딩을 막지 못함 | 앱 전체 대상 예약의 수명·할당 실패·취소 정산과 경로 별칭 검사 설계 |
| worker 성공 후 경로 바인딩/백업 갱신 실패 | 파일은 생겼지만 문서는 옛 경로이고 성공 알림만 남을 수 있음 | 필수 메모리를 선확보하고 no-fail 모델 전환을 설계; 부가 서비스 실패와 디스크 실패를 구분 |
| 저장 중 편집→Undo, BOM·CRLF 문서 저장 | raw bytes hash와 logical content hash를 혼용하면 dirty가 틀림 | 새 대상 raw disk 기준과 실제 snapshot의 logical saved 기준을 각각 갱신; encoding 보존 검증 |
| 접수 후 Esc·포커스 이동·마지막 뷰 닫기 | 「취소면 경로 유지」와 「성공이면 경로 변경」이 충돌 | 접수 후 UI 소비자 취소와 문서 연산 취소를 구분하는 정책 필요; receipt 해제가 쓰기를 취소하지 않음 |
| 기존 닫기 actor와 Save As가 같은 문서에 겹침 | epoch 변경으로 닫기 의도만 취소되거나 옛 경로 저장이 접수될 수 있음 | 닫기·저장·새 경로 전환의 우선순위를 명시하고 양방향 경합 검사 |
| 다른 문서의 writer가 막힘 | 초안의 독립 완료 검증은 단일 worker 구조에서 성립하지 않음 | UI 이벤트 처리와 등록의 비차단성을 검증하고 실제 I/O 완료 지연은 별도로 보고 |
| 읽기 전용 원본, read-only 파일 패널 | 원본 쓰기 금지와 새 대상 쓰기 허용 여부가 다름 | 첫 범위는 편집 가능한 일반 문서로 제한할지, 읽기 전용 Save As도 허용할지 사용자 계약 확정 |

현재 `save.Owner.enqueueNotified`는 현재 경로의 `Prepared`를 만들고 read-only를
거절한다. `Queue.applyRetained`도 현재 Target과의 일치를 요구한다. 따라서 기존
enqueue/apply를 새 경로에 그대로 재사용하면 목적지 검증·완료 적용이 성립하지 않는다.
새 대상 준비와 성공 시 문서 전환을 별도 계약으로 설계해야 한다.

접수 뒤 취소와 후속 저장 라우팅은 위 승인 정책으로 정했다. 표는 최초 검토에서
발견 당시 누락의 기록이다. 이후 연결 상태와 남은 검증은 아래 실제 명령 연결 절을 따른다. 기존 규칙의 변경을 이 검토 문서만으로 승인 처리하지 않는다.

## 새 대상 writer·모델 전환 기반

`save/destination.zig::Prepared`는 원본 Target(문서 신원·경로·epoch)과 목적지
write path를 따로 소유한다. 목적지가 없으면 기존 첫 저장과 공유하는 배타 생성,
있으면 목적지의 명시적 raw hash로 CAS 쓰기를 한다. 원본 disk hash로 목적지를
검증하지 않는다. 같은 문자열 경로는 일반 저장으로 보내도록 준비를 거절한다.

작업 자료는 기존 `save/worker.zig::Service`에 넘길 수 있다. 넘긴 동안 caller의
`work`를 null로 비우고, 실제 Completion이 돌아온 뒤에만 되돌려 놓는다. actor가
문서 lease와 자료 수명을 보존해야 한다. 기존 전역 큐의 일반 저장 접수 경로에
이 자료를 그대로 넣는 구현은 아니다.

`adopt`는 실제 written, 미정산 상태, 원본 Target을 재검증한다. 필수 binding
메모리를 준비 때 확보하여 성공 경계에서는 할당하지 않고 경로·epoch·logical saved
hash와 raw disk hash를 갱신한다. 추가 편집과 Undo는 건드리지 않는다. 문서 모델과
자료의 allocator는 같아야 한다. caller는 올바른 모델 allocator를 전달해야 하며
서로 다른 자료 allocator로 adopt하는 호출은 거절한다.

아직 AppSession 저장 진입점에는 연결하지 않는다. 같은 실제 파일 별칭·앱 전체
목적지 예약·선행/후속 저장 조정·공유 뷰 entry/syntax·백업/LSP 갱신이 필요하다.
모델의 path가 바뀌었다는 테스트만으로 앱 전체 경로 전환 완료를 주장하지 않는다.
새 파일 생성의 I/O 실패 때 이미 생성한 일부 파일이 남을 수 있는 기존 첫 저장
계약은 바꾸지 않는다. 생성한 파일의 자동 삭제·전원 손실 복구를 보장하지 않는다.

`test-editor-save-as-write`는 실제 blocked worker와 디스크 bytes를 대조한다.
조기/중복 전환, 추가 편집/Undo 보존, 배타 생성 경쟁, 목적지 CAS 실패,
BOM/CRLF 보존, epoch 변경, 다른 문서 lease, 준비 할당 실패를 검사한다.
`test-editor-local-save`와 `test-editor-untitled`는 공용 writer로 옮긴 기존 경로의 회귀다.

격리 사본의 결함 주입 검증은 조기 전환·원본 Target/epoch 무시·목적지 CAS 무시·
배타 생성 무시·현재 본문을 잘못 clean으로 게시하는 변이를 실제 실행 단언으로 검출한다.
정상·복원 대조군은 10개(의미 테스트 6개와 공용 모듈 테스트 4개)를 모두 실행한다.

## 제품 연결 전 문서·목적지 예약 기반

2026-10-14 사용자가 권장한 macOS 저장 대화상자로 다음 작업을 진행하도록 지시했다.
진입점은 명령 팔레트와 ⌘⇧S, 기본 위치는 현재 파일명/부모 디렉터리이며 workspace
밖도 선택하는 계약으로 연결한다. 저장 순서·접수 전 취소 계약은 이미 승인한 내용을 유지한다.
아직 이 명령이나 NSSavePanel을 제품에 연결한 상태는 아니다.

`ops/save_as_reservation.zig::Store(Identity)`는 실제 document_registry.DocumentIdentity를
키로 받는 main-actor 예약 기반이다. 같은 문서의 두 요청은 거절하고 독립 문서는
동적 배열에 보존한다. 단조 증가 요청 ID와 발신 창 generation/surface를 함께
대조하여 취소된 패널의 늦은 콜백이 새 요청에 붙지 않도록 한다. ID 고갈은 되감지 않는다.

caller가 실제 부모 디렉터리 신원·volume의 이름 비교 규칙으로 만든 namespace key와,
기존 파일의 device/inode를 전달한다. 같은 이름은 inode가 바뀌어도 겹치지 않고,
다른 이름의 같은 실제 파일도 동시 예약하지 않는다. 이 모듈이 경로 canonicalization을
수행하거나 앱에서 이미 열린 독립 문서를 검사한 것으로 보고하지 않는다.

예약 키는 소유 복사한다. 등록/키 복사 OOM은 아직 접수하지 않은 상태와 다음 요청
번호를 보존한다. 접수 뒤 취소나 조기 성공으로 예약을 풀지 않는다. 실제 실패나
쓰기·경로 전환 성공을 정산한 뒤 키를 해제하고 후속 저장 경로를 caller에 반환한다.
성공 뒤 일반 저장은 caller가 전환한 현재 문서 경로를 사용해야 한다. 예약은 문서
lease를 보존하지 않으므로 host actor가 request lease를 별도로 유지해야 한다.

남은 연결: NSSavePanel·ABI request/result 배선, 실제 경로 canonicalization/열린 대상
검사, 접수 경로 전체의 문서 예약 조회와 후속 snapshot/receipt 보존, 공유 뷰 표시
경로·백업·syntax/LSP 전환, 닫기·정상 종료 정산이다. 예약 모듈 테스트를 실제 OS
대화상자나 제품 저장 순서의 실행 증거로 대신하지 않는다.

검증 명령: `zig build test-editor-save-as-reservation`(Debug/ReleaseFast).
`python3 tools/test-editor-save-as-reservation.py`는 요청 번호 재사용·발신 신원 무시·
문서/이름/실제 파일 충돌 무시·접수 뒤 취소 해제 변이와 정상/복원 대조군을 검사한다.

콜백 Token 일치는 살아 있는 창/문서의 권한 확인을 대신하지 않는다. 창이 닫히면
미접수 요청을 취소하고, callback을 accept하기 전에 host가 실제 창 generation과
문서 lease·저장 대상 epoch를 다시 확인해야 한다. 접수된 요청은 UI가 없어져도
request lease와 writer 결과를 정산한다.

순수 판정의 std.meta.eql 값 비교는 sans-io 허용 목록에 이유와 함께 등록했다.
경계 판정자의 OS namespace 허용 결함과 순수 비교 오탐 결함을 각각 주입해
기존 금지 호출 단언·실제 ops 폴더 검사에서 검출하고 정상/복원 대조군을 확인했다.

## 실제 명령 연결 — 기본 GUI 저장 검증, 물리 IME 미검증

`editor_save_as` 액션은 이름 있는 일반 로컬 네이티브 문서에서 명령 팔레트와
⌘⇧S로 진입한다. Swift는 현재 창에 NSSavePanel을 sheet로 열고 현재 파일명과
부모 디렉터리를 넣는다. callback은 요청 ID, 창 generation, 원본 surface,
문서 lease와 대상 epoch를 다시 대조한다. 이미 다른 sheet가 있으면 열기를 기다린다.
이름 없는 문서·원격·웹 bridge·diff·읽기 전용 문서는 이 새 경로를 사용하지 않는다.

`save/as.zig`가 request lease와 목적지 예약을 유지한다. 확인한 목적지는 원본
저장·포맷이 정산된 뒤 재검증하고, 입력 확정과 모델/표시 경로 메모리 확보 후
worker에 넘긴다. 목적지 parent device/inode도 worker가 다시 확인한다.
필수 모델 전환은 실제 완료 이후에만 수행한다. 공유 뷰의 경로·syntax와 LSP URI를
같은 완료 경계에서 갱신하며, 이전 백업 신원은 전환 전에 보존한다.

후속 ⌘S는 저장 의도를 보류했다가 결과 뒤 기존 code-action/format 파이프라인으로
재실행한다. 배치/닫기처럼 이미 본문을 제출한 요청은 실제 snapshot과 receipt를
기존 큐에 hold하여 유지한다. 성공하면 새 경로와 실제 disk 기준으로, 실패하면
원래 경로로 해제한다. 선행 원본 요청이 held 요청 뒤에 있어도 먼저 실행할 수 있다.
동기 저장 caller는 같은 문서의 전환 중 쓰기를 거절하며 held 요청을 drain하지 않는다.
활성 Term 하나의 닫기는 요청한 창/surface를 보존해 저장 정산 뒤 다시 판단한다.
웹/네이티브 파일 패널의 새 열기도 목적지 예약을 조회해 중복 점유를 거절한다.
이미 열린 entry 없는 네이티브 MRU/공유 뷰를 재사용한 열기는 정상 결과를 반환한다.

현재 이름 예약 key는 실제 부모 신원과 basename 원문을 사용한다. volume별 Unicode/
대소문자 이름 규칙을 완전히 구현했다고 주장하지 않는다. 실제 파일의 device/inode
충돌과 배타 생성/CAS는 별도로 검사한다. 같은 inode라도 서로 다른 hardlink 항목이면
선택한 경로를 교체하고 원본을 보존한다. 동일 항목의 대소문자 별칭은 일반 저장한다.
macOS 어댑터가 부모 신원·link count·실제 디렉터리 항목을 관측하고 L2의
`namespaceRelation`이 이를 판정한다. 판정이 불명확하면 쓰지 않고 실패를 안내한다.
Unicode와 volume 이름 규칙의 완전한 정규화는 구현하지 않았다.

실행 검증: `test-editor-save-as-command`는 의미 테스트 12개와 공용 모듈 테스트 4개를
실행한다. 원본 보존·추가 편집·후속 저장·늦은 콜백·독립 열린 목적지·예약·배치 receipt·
실패 후 원본 라우팅·쓰기 중 새 공유 뷰·parent 교체·hardlink·대소문자 별칭을
디스크와 모델로 대조한다. 순수 예약 검사는 12개다.
`tools/test-editor-save-as-command-adversarial.py`는 정상·복원·동등 변경 대조군과
후속 저장·라우팅·콜백·parent·held 접수·목적지 열기·hardlink 결함 주입을 검사한다.
Debug/ReleaseFast 대상 검사, 전체 ReleaseFast 에디터 검사(1,511 통과·5 건너뜀),
`check-boundaries`가 통과했다.

수정 후 통과하며, 정상·복원 대조군도 통과한다. 과거 CI의 일반 오류 메시지만으로
동일 실패 지점이었다고 확정하지 않는다. 변경된 head의 CI로 재확인한다.

추가 입력을 이 성공 결과로 대체하지 않는다.

## GUI 취소·저장 중 추가 입력 — 실제 실행 검증 완료

`--save-as-scenario cancel`은 실제 Cancel 버튼 뒤 원본 경로·미저장 본문 유지와 목적지
미생성, Undo/Redo 복원을 검사한다. `--save-as-scenario edit-during-write`는 격리 앱에만
writer gate를 주입한다. 저장 snapshot을 원자적으로 게시한 뒤 writer를 대기시키고,
UI에서 추가 입력·캡처를 마친 뒤 해제한다. 최종 디스크는 이전 snapshot, 본문은 추가
입력과 dirty를 유지하는지와 Undo/Redo를 검사한다. 시간 지연만으로 순서를 추정하지 않는다.
두 시나리오는 `--save-as-command --native-panel-capture-app <허용된 앱>`과 함께 사용한다.
2026-10-19 잠금 해제 후 실제 Cancel·저장 중 추가 입력·기본 Save As가 통과했다.
취소 뒤 본문 `foo!`·원본 경로·dirty 유지와 목적지 미생성을 확인했다.
writer 대기 중 `?`를 추가한 뒤 디스크 `foo!`·본문 `foo!?`·새 경로·dirty 유지를 확인했다.
세 시나리오 모두 Undo 뒤 본문 변경과 Redo 뒤 원문 복원, 최종 경로·dirty를 재검사했다.
취소 후·writer 대기 중·저장 후 Metal 이미지도 직접 확인했다.
잘못된 실행 옵션과 잠금 상태는 실패로 중단한다. 물리 한글 IME·VoiceOver는 별도다.

## 한국어 IME Save As — 실제 OS 입력기 실행 검증 완료

`--save-as-physical-ime`는 한국어 입력 소스에서 CGEvent 키 세 개로 `한`을 조합한다.
Enter로 먼저 확정하지 않는다. 제품의 preedit가 정확히 `한`이고 AppKit marked range가
한 글자인 상태를 관측·촬영한 뒤 기존 NSEvent ⌘⇧S 경로를 실행한다. 이후 실제 저장 창을
확인하고 원본 `foo`·목적지/본문 `foo한`·dirty 해제·preedit 종료·Undo/Redo를 검사한다.
입력 소스는 성공·실패 모두 기존 복원 기록 계약으로 복원하고 로그를 검사한다.

한국어 입력은 OS 입력기 경로를 거치는 CGEvent이며 사람의 물리 키보드 조작은 아니다.
저장 단축키는 기존 AppKit NSEvent, 저장 창 확인은 접근성 API다. VoiceOver와 한자
후보창 위치 검증을 대신하지 않는다. 2026-10-19 잠금 해제 후 실제 한국어 입력기의
조합 중 marked range·preedit `한`을 확인하고 저장했다. 원본 `foo` 보존·목적지와 본문
`foo한`·새 경로·dirty 해제·조합 종료·Undo/Redo와 입력 소스 복원이 모두 통과했다.
조합 중/저장 후 Metal 이미지도 직접 확인했다. 첫 실행은 입력기 복원 enum `.restored`를
boolean 문자열로 기대한 하네스 판정 오류로 거절됐으며 실제 로그 계약에 맞춰 수정하고
새 실행 전체가 통과했다. 옵션 누락·검색 IME와 중복·취소 시나리오와 중복·오래된 앱은
GUI/HID 실행 전에 거절한다. 사람의 키보드 조작과 VoiceOver는 여전히 별도다.
