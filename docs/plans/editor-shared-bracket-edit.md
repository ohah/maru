# 공유 편집 후 완료한 괄호 목록 재사용

상태: 구현 후보의 Debug 집중·기존 회귀 47개 빌드 단계와 ReleaseFast 집중 44개 빌드 단계를 통과했다. 최종 소스의 독립 결함 다섯 개와 정상 대조 여섯 건을 확인했다. 일반·증가·추가 반복 실측도 완료했다. 전체 경계·문서/config·집중/기존 회귀 게이트 725개 빌드 단계를 통과했다. 원격 PR 검증은 후속이다. 선행 PR #4594가 머지된 실제 main `8787fef0d`에 리베이스했고 변경 패치와 네 검증 소스의 해시가 보존됐다.

## 근거와 범위

별도 계측 사본에서 두 뷰의 편집 경계를 분리했다. 대형 Zig의 완료 트리를 받는 뷰는
provider 갱신 중앙값 0.009ms, 괄호 refresh 2.152ms였다. 실제 build.zig에서는
각각 0.005ms와 0.065ms였다. 성능 12개 실행/240편집과 별도 정확성 4개/80편집,
원시 기록 16개·집계 재계산·손상 로그 다섯 개를 검증했다. 동시에 다른 컴파일·테스트가
실행됐으므로 절대 지연이나 개선 효과의 확정값으로 쓰지 않는다. 원시 자료는 저장소 밖
`shared-bracket-edit-attribution-1`에 보존한다. 앱 GUI/HID·GPU present 측정은 아니다.

현재 문서·입력 판을 증명한 State의 native 트리를 실제로 수신한 경우에만 완료한 잎 값을
수신 뷰의 독립 배열로 옮긴다. parser·세대·ready·walking 검사는 선행 복사와 같다.
첫 준비 스냅샷의 새 배열 복사와 달리 수신 목록의 기존 여유 용량을 재사용한다.
순회 자원·색 판정·탐색 인덱스·계수·선택·표시 설정은 전달하지 않는다.

## 실패와 캐시 판

기존 shift와 provider 갱신 순서는 유지한다. 배열 용량 준비가 실패하거나 원본이 완료 전이면
기존 refresh를 실행한다. 실패한 복사 자체는 수신 목록·진행 중 순회·원본을 변경하지 않는다.
성공 뒤에만 수신 순회를 정리하고 현재 잎 값·수신 parser·세대를 게시한다.
수신의 목록 판을 증가시키며 판을 1로 초기화하거나 원본 판을 가져오지 않는다.
그래야 이전 색/점프 판정을 새 위치에 그대로 게시하지 않고 기존 재배치/재판정을 거친다.
기존 refresh가 소비하던 일회성 changed ranges도 성공 경로에서 소비하되 retained 범위는 보존한다.

## 검증·채택 조건

- native: 독립 배열·기존 용량·판 증가·계수 보존·빈 값·현재 parser/세대·자기 복사 거부.
- 실패: 할당 실패 전후 수신 값/순회와 원본 보존, 실패 해제 후 정상 재시도.
- 제품: 실제 입력 증명과 완료 트리 인계, 다른 문서/판·미완료 목록의 기존 갱신 복귀.
- 색과 모든 byte의 점프/강조를 전체 판정과 비교한다. 위치 이동·구조 변경·Markdown·독립 풀·
  긴 줄·원본 종료·Undo/Redo를 포함한다.
- 다섯 독립 결함 주입과 정상 전후 대조, Debug·ReleaseFast 및 기존 스냅샷/재배치 회귀를 실행한다.
- 동일 사본의 전후 교차 성능과 매 입력 정확성·메모리 용량을 실측하고 비용까지 보존한 뒤 채택한다.
  기존 완료 기록을 이번 구현의 통과로 계산하지 않는다. 새 UX·스레드·의존성·영속 포맷은 없다.

## 현재 확인한 내용

`BracketIndex.replaceMatched`가 현재 원본 parser·세대·ready·walking과 자기 복사를 검사한다.
수신 용량을 먼저 준비하고 성공 뒤에만 기존 순회 자원을 정리한다. 잎 배열의 기존 용량·
계수는 유지하며 수신 목록 판은 증가한다. `onEditSpanFromReady`는 증명된 입력을 가진
State를 받아 실제 native 인계 성공을 확인하고 선택적으로 목록을 옮긴다. 실패/거절은 기존
refresh를 실행한다. 색/탐색은 기존 재배치 또는 재판정을 통해 수신 설정으로 만든다.

집중 native 4개·새 제품 8개와 기존 재배치 제품 7개·중립 33개·스냅샷 제품 7개를 대조했다.
입력 판을 발급한 실제 분할의 입력·Undo/Redo는 특정 뷰가 항상 먼저라는 가정 대신 두 뷰
전체의 부분 재수집 합계가 한 번만 늘어나는지 검사한다. 원본 종료 후 생존 뷰의 색/탐색도
전체 재계산과 비교한다. 단위 fixture는 다른 언어·다른 문서·다른 입력 판·미완료 원본·
할당 실패·Markdown·독립 풀·긴 줄의 복귀 및 판정을 검증한다.

`tools/editor-shared-bracket-edit/review.py`의 parser 검사 무력화, 수신 판 증가 누락,
할당 전 순회 정리, 실제 native 인계 성공 검사 무력화, 실패 시 refresh 누락은 모두
컴파일 후 실행에서 검출됐다. 증거는 저장소 밖 `shared-bracket-edit-attacks-1/receipt.json`이다.
네 제품/테스트·build 파일의 해시를 실제 소스와 대조했다. 최초 제품 red의 선택 개수 오류와
소비 후 changed ranges를 null로 가정한 테스트 오류는 제품 결함으로 계산하지 않는다.
해당 API의 소비 후 결과는 빈 범위다. 실제 GUI/HID·GPU present와 C allocator 실패 전수 강제는
이번 자동 검증 범위 밖이다. 실측의 분포별 차이와 첫 증가 자료의 p95 증가까지 [전체 표](../../tools/editor-shared-bracket-edit/results.md)에 보존한다. 같은 바이너리의 추가 반복에서는 전체 p95가 감소했지만 모든 입력의 개선을 주장하지 않는다.

## 전후 대조와 한계

성능 104개 실행/2080편집과 별도 정확성 12개 실행/240편집을 완료했다. 각 정확성 입력의
전체 잎·색 토큰·짝/단계·탐색 인덱스와 본문·접힘 결과가 일치한다. 큰 Zig 일반 입력 p50은
47.382→45.600ms, 괄호 갱신 p50은 4.278→2.223ms였다. 증가 자료의 전체 p95 증가도
보존하고 같은 바이너리의 추가 반복에서 60.088→57.973ms를 확인했다. 실제 build.zig의
반복 첫 입력은 약 0.025ms 늘었다. 두 조건의 증가 뒤 배열 용량은 같다.
이는 보존 계측 문맥의 CPU 경과시간이며 실제 GUI/HID·RSS 결과가 아니다. 동시 외부 부하와
작은 표본의 영향을 구분하고, 모든 입력·파일·환경의 개선으로 일반화하지 않는다.
