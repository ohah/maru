# 공유 분할의 완료한 괄호 목록 복사

상태: 로컬 구현·native 집중 5개·기존 요약 4개·새 제품 7개와 기존 제품 회귀 및 중립
판정 검증을 완료했다. 최종 테스트의 독립 결함 5개와 정상 대조 6건도 실행에서 확인했다.
전체 경계·문서/config·제품 회귀 게이트 722개 빌드 단계를 통과했다. PR #4594의 필수 CI가 통과해 실제 main `8787fef0d`로 머지됐다. 기대 머지 트리와 일치하며 해당 main의 집중·문서/config 검사 62개 빌드 단계를 다시 통과했다. 별도 push(main) CI 40208824603도 통과했다.
초기 교차 측정·후속 반복·괄호 증가 입력의 확장 대조와 실제 타입 크기 확인도 완료했다.
선행 PR #4593의 실제 머지 main `6dee25c06`에 기준을 맞췄다. 이전 측정 기준과 전체
트리가 동일하며 기존 작업 패치도 그대로 보존했다.

## 문제와 범위

심볼 요약 복사 후보의 교차 측정에서 대형 Zig 분할 준비 중앙값은 72.449ms였다.
그중 수신 뷰의 괄호 처리 중앙값은 60.348ms, 목록 수집은 58.618ms였다. 짝/색 판정과
탐색 인덱스는 각각 0.436ms·0.386ms였다. 서로 다른 중앙값을 더해 전체 시간을
재구성하거나 아직 구현하지 않은 복사의 효과로 표현하지 않는다.

완료한 괄호 잎 값만 독립 복사한다. 색 판정·탐색 목록·scratch·진행 중 cursor·walk
tree/text·편집 큐·작업 계수는 복사하지 않는다. 수신 뷰는 기존 경로로 자기 설정의
짝/색 판정과 점프/강조 인덱스를 만든다. Markdown의 색 비활성·점프/강조 활성 계약도
그대로 유지한다. 새 UX·worker·의존성·영속 데이터·전역 캐시를 도입하지 않는다.

## 복사 전제와 소유

`State.prepareSharedSnapshot`에서 같은 언어의 실제 provider 복사가 성공한 뒤에만 시도한다.
목록이 ready이고 walking이 아니며, 정리 완료를 기록한 원본 parser 신원과 트리 세대가
현재 원본 provider와 같아야 한다. 수신 목록은 수신 allocator가 소유하는 새 배열과
수신 parser·세대에 묶는다. 새 뷰의 목록 판과 작업 계수는 독립적으로 시작한다.

세대만으로는 같은 번호의 다른 parser를 구별할 수 없어 `BracketIndex`에 parser 바인딩을
추가한다. 전체 수집·부분 갱신이 성공한 뒤에만 바인딩을 게시한다. invalidate와 위치 shift는
바인딩을 지운다. 특히 shift 직후에는 값만 새 좌표로 옮겨졌고 provider는 아직 이전 세대일
수 있으므로, 세대가 같다는 이유로 중간 상태를 복사하지 않는다. 기존 순회/갱신 알고리즘을
대체하지 않고 이 바인딩은 선택적 복사의 전제로 사용한다.

할당 실패는 복사한 provider·입력 증명·접힘 캐시를 유지하고 괄호 목록만 기존 수집 경로로
돌린다. 부분 복사를 게시하지 않는다. 0개인 유효한 목록도 복사하며 원본 종료와 수신 준비
취소에서 다른 뷰의 배열이나 parser를 해제하지 않는다.

## 검증과 채택 조건

- 같은 세대의 다른 parser, 오래된 세대, 미완료/walking, shift 직후를 각각 거절한다.
- 독립 배열·0개 목록·원본 종료·취소·모든 Zig 할당 실패 후 재시도를 대조한다.
- 편집·Undo/Redo·독립 괄호 풀·Markdown에서 전체 수집/색/탐색 결과와 일치한다.
- parser·세대·중간 상태·소유권·선택적 실패 정책을 겨냥한 서로 다른 결함 5개를 실행에서
  검출하고 정상 전후 대조를 통과한다. 아직 실행 전인 검증을 완료로 표시하지 않는다.
- 복사 자체를 포함한 분할 준비·첫 입력·후속 입력을 교차 측정하고, 메타데이터 크기와
  배열 소유 비용을 확인한다. 효과와 비용을 확인한 다음 채택한다.

원인 자료는 저장소 밖 `next-bracket-copy-cost-evidence.json`과
`shared-sticky-summary-measure-1`의 실제 원시 기록에 보존한다.

## 확인한 결과와 교환 관계

[실측 전체 표](../../tools/editor-shared-bracket-snapshot/results.md)에 일반 입력과 괄호 증가
입력의 첫 표본을 포함해 보존한다. 첫 대조의 대형 Zig 준비는 72.004→14.731ms였다.
수신 뷰의 전체 재수집은 1회→0회이며 독립 배열과 같은 항목 수를 확인했다. 일반 반복의
첫 입력 55.020→56.095ms와 괄호 증가 입력 67.660→68.932ms의 작은 증가도 보존한다.
증가 입력의 준비+첫 입력은 138.796→83.512ms였으며 모든 입력의 개선을 주장하지 않는다.

현재 항목만 복사하므로 원본의 남은 큰 여유 용량을 복제하지 않는다. 대신 첫 증가 입력에서
배열이 확장될 수 있다. 별도 제품 소스의 ReleaseFast 타입 대조에서 `BracketIndex`는
200→208바이트, `State`는 1600→1608바이트, 공통 `TermRuntime`은 17792→17824바이트였다.
계측 문맥의 다른 runtime 크기를 제품 크기로 사용하지 않으며 allocator/RSS와 구분한다.

`tools/editor-shared-bracket-snapshot/review.py`의 parser·세대·shift 바인딩·배열 공유·
선택적 실패의 다섯 결함은 컴파일 후 실행에서 검출됐다. 최종 검증 사본의 제품/테스트
세 파일과 build가 실제 작업 소스와 같다. 계보·접힘·괄호가 함께 있는 단위 fixture에서
Zig 할당 실패 지점을 순회하고 본체·입력 증명·원본 보존과 실패 해제 뒤 재수집을 대조했다.
실제 분할은 registry 경로에서 입력·Undo로 유효한 계보를 만든 뒤 원본 종료·괄호 증가·
Undo/Redo를 대조한다. C allocator 실패 전수 강제와 실제 GUI/HID 검증은 없다.
