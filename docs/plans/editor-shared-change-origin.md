# 같은 이전 구문 스냅샷의 변경 범위 재사용

상태: 구현 뒤 최신 main `7ca13662c`로 리베이스했다. registry 발급기와 순수 증명 코드를 작성했다.
집중 37개·기존 입력 증명 30개 검사를 Debug·ReleaseFast에서 통과했다.
앱 registry·native·뷰 상태 연결을 작성했다. 제품 경로의 양쪽 입력·Undo/Redo·증명
훼손·메타데이터 할당 실패·세 뷰·직접 재파싱·제공 뷰 닫기는 Debug에서 통과했다.
제품 집중 검사 8개는 리베이스 전 Debug·ReleaseFast에서 통과했다. 리베이스 뒤 제품
검사는 Debug에서 통과했다(새 제품 8개·기존 공유 제품 7개·native snapshot 3개·접힘 변경 6개).
실제 registry·계보 판정 코드의 다섯 독립 결함 주입은 모두 컴파일되어
실행 중 거절됐고, 최초 정상 대조와 각 복구 뒤 정상 대조는 통과했다.
리베이스 뒤 ReleaseFast에서도 집중 37개·입력 증명 30개·강화한 제품 8개가 통과했다.
전체 경계·문서/config 702개 빌드 단계와 포맷 검사도 통과했다.
전후 함수 지연·구조 크기 실측은 완료했다. #4589은 모든 필수 CI를 통과해
`00c1a9080`으로 머지됐다. 실제 머지 트리는 검증한 head와 동일하며, 머지된 main의
집중 37개·제품 8개·문서/config 검사도 통과했다. 별도 main CI `40193930955`도 전체 통과했다.

PR #4589의 첫 macOS CI에서 프로젝트 검색 집계의 기대 개수 289와 실제 298이 달랐다.
기준 main과 검사 이름을 대조해 추가된 registry 3개·계보 판정 6개만 늘었고 빠진 검사는
없음을 확인했다. 기대 개수를 298, 통과 개수를 297로 갱신한 집중 실행은 통과했다.
Windows 전용 1개 skip은 기준과 동일하다. 원시 목록 차이는 저장소 밖
`shared-change-origin-ci-count-proof.json`에 보존한다.
이후 main의 LSP 수정도 합쳐 LSP 복구 31개·제품 7개·계보 제품 8개와 검색 집계
298개(297개 통과·의도된 skip 1개)를 다시 확인했다. 계보·registry·syntax 구현 파일은
이 리베이스에서 바뀌지 않았다. 전후 성능 표는 당시 기준 main의 사본 실측으로 유지한다.

## 근거와 경계

공유 파싱은 이미 한 번이지만 변경 범위는 뷰마다 계산한다. 기존 로그 재집계에서
대형 Zig 공유 입력의 변경 범위 계산 중앙값은 16.150ms였다. 과거 계측 사본의 함수
경과시간이며 현재 main의 새 실측이나 최적화 개선량으로 쓰지 않는다.

이전 트리가 다른 늦은 뷰에서는 제공 범위가 0건, 수신 범위가 1건인 사례를 재현했다.
따라서 같은 현재 입력만으로 변경 범위를 복사하지 않는다. native 사본의 뿌리 노드 ID도
달라 직접적인 복사 계보 증명에 사용할 수 없었다. 두 사실 모두 Debug·ReleaseFast에서 확인했다.

## 소유와 증명

registry의 비공개 `Document`가 발급 번호를 소유한다. 문서 `State`를 교체하거나 같은
본문으로 돌아가도 번호를 되감지 않는다. `reserveSyntaxOrigin`은 살아 있는 lease와
실제 문서 리비전을 확인해 문서 신원·리비전·번호를 함께 반환한다. 다른 문서에서 발급한
번호를 호출자가 잘못 묶는 것도 피한다. 발급은 할당하지 않고 실패한 예약도 재사용하지 않는다.
고갈·오래된 참조·리비전 불일치는 `null`로 최적화만 포기한다. 파일 포맷에 저장하지 않는다.

`session/editor/syntax/origin.zig`는 현재 자원과 계보의 관계만 판정한다. 독립 파싱은 새
번호를 사용하고, 실제 native 복사 성공 때만 번호를 전달한다. `parsed`·`copied` 생성자는
갱신되지 않은 자원·실패한 복사·없거나 오래된 제공 증명을 거절한다. native 성공 여부는
호출자가 실제 결과로 전달해야 하며 이 모델만으로 앱 수명 연결이 증명되지는 않는다.

`Receipt`는 같은 문서·이전 입력/복사 계보·현재 제공 자원·정확한 편집 좌표·보관된 범위 판을
요구한다. 각 뷰의 parser와 트리 세대는 달라도 된다. 범위 값을 가져올 때는 제공자의 세대를
복사하지 않고 수신 뷰 자신의 이전/현재 세대로 기록해야 한다. 증명 부재·pending·재파싱·
grammar 변경·지연된 입력은 기존 뷰별 계산으로 돌아간다. native의
`onEditFromMatchingPrior`는 증명이 성립할 때만 호출하며, 값은 수신 뷰 소유 배열에 복사한다.

## 완료한 탐색

외부 사본의 31개 언어·네 편집에서 같은 이전 판을 직접 복사한 범위 값이 일치했다.
이어 실제 범위 재사용 사본에서 1→2인 제공 세대와 91→92인 수신 세대의 매핑, 소비된 색
변경 통지 뒤의 범위 보존, 전체 native 트리·접힘 결과를 대조했다. 다섯 훼손 증명은 실제
비교 한 번으로 복귀했고 각각의 정상 전후 대조는 비교 0회·범위 가져오기 1회였다.
두 뷰가 번갈아 20번 입력하며 개행 삽입/삭제로 원문에 돌아오는 경우도 두 빌드에서 통과했다.

이 사본의 발급기는 fixture 소유이며 앱 registry와의 연결이나 실제 입력 지연 개선을 뜻하지 않는다.
원시 자료는 저장소 밖 `fold-change-identity-native-1`, `fold-change-origin-native-1`,
`fold-change-borrow-native-1`, `fold-change-borrow-native-2`에 준비 소스 목록·실행 로그·판정으로 보존한다.
순수 모델의 다섯 결함 주입과 각 전후 정상 대조는 `fold-change-origin-model-attacks-1`에 있다.
이 자료들을 최종 앱 구현의 검증 완료로 대체하지 않는다.

실제 구현의 계보 일치·제공 자원의 현재 판·정확한 편집·범위 가용성·registry 리비전
검사를 각각 무력화한 기록은 `shared-change-origin-final-attacks-2/receipt.json`에 있다.
다섯 결함은 집중 검사에서 실행 실패했고, 정상 대조 6건은 통과했다. 앞선 `final-attacks-1`은
테스트 실행 실패를 컴파일 실패로 오인한 하네스 판정 오류로 중단했으며 완료 자료로 세지 않는다.
이 결함 주입은 registry·순수 판정 경계의 증거이며, 전체 앱 수명·실제 OS 입력 검증을 대신하지 않는다.

계측기는 `adoptParsed`에서 두 복사 경로를 함께 재고 provider schema 3에서 C 비교와
`range_reuses`를 구분한다. 이전 schema 2 기록은 그대로 읽는다. 새 집계기는 기록 누락·
과잉 재사용·비교 누락·중복 계산을 거절하는 합성 기록 검사까지 통과했다. 새 제품 실측은 남아 있다.

## 구현과 검증 현황

1. 구현: 앱은 실제 registry 발급 값을 사용하고 native 성공 뒤에만 자원에 묶는다. 구문 provider와
   표시 캐시는 뷰 소유를 유지한다. 기존 입력 증명·파싱 결과 재사용은 계보 발급 실패에도 계속 동작한다.
2. 구현: State의 직접 편집·재파싱·pending 재개·deinit은 공통 증명 무효화 경계에 연결했다.
   메타데이터는 뷰별 지연 할당으로 보관한다. aarch64 macOS 구조 크기 실측은 `TermRuntime`
   18,432→18,512바이트, syntax `State` 1,816→1,840바이트, native `Provider`
   528→544바이트, registry `Document` 480→496바이트였다. 별도 origin payload는
   파싱 뷰당 368바이트이며 allocator 관리 정보·RSS는 이 수치에 포함하지 않는다.
   중첩 구조 크기를 더하면 중복 계산하므로 `TermRuntime` 증가는 직접 잰 80바이트를 쓴다.
   원본 로그·종료 코드는 저장소 밖 `shared-change-origin-memory-3`에 보존했다.
3. 구현: 실제 native 범위 적용 API는 값만 수신 뷰 소유 배열로 옮기고 자신의 세대로 기록한다.
   기존 API와 증명 없는 호출은 이전 계산을 유지한다. 세 뷰와 제공 뷰 닫기는 제품 Debug에서
   독립 전체 파싱 결과와 대조했다. 늦은 뷰에 실제 문서와 다른 이전 트리를 넣은 제품
   검사도 Debug에서 통과했고, 후속 입력은 새 복사 계보로 다시 합류했다.
4. 메타데이터 할당 실패는 제품 State 경로, 발급 고갈·문서 슬롯 재사용은 registry 경로,
   Undo/Redo·다른 이전 트리·제공 뷰 닫기는 실제 coordinator에서 대조했다. 기존 공유 편집
   72개·게시 22개·앵커 11개·Save As 쓰기 10개(import 포함)도 통과했다. 이 검사는
   IME 투영·NFD·조합 취소·뷰 닫기와 멀티커서 경계를 포함한다. 입력·Undo·저장 정책은 바꾸지 않는다.
   native `ts_tree_copy` 자체의 실제 malloc 실패와 실제 OS IME 입력은 강제 재현하지 않았다.
5. 실제 C 비교와 재사용 호출 수를 구분하는 provider schema 3을 추가했고 이전 기록의 계약은 유지한다.
   전후 240개 프로세스/3,090편집의 전체 접힘 대조, 별도 성능 60개/1,200편집과 정확성
   20개/400편집을 완료했다. 공유 대형 Zig의 C 범위 계산 중앙값은 15.748→7.670ms,
   전체 입력 함수는 51.513→42.429ms였다. 첫 입력도 포함했다.
   최초 구조 편집의 느린 표본은 추가 20개/200편집에서 같은 차이가 재현되지 않았고,
   원인은 확정하지 않았다. [전체 분포와 원시 자료 해시](../../tools/editor-provider-measure/shared-change-results.md)를 남긴다.
