# 공유 분할 스냅샷의 입력·복사 계보 전달

상태: 로컬 구현·독립 검증·실측과 718개 빌드 단계를 통과했다. PR #4591의 모든 필수
CI가 통과해 실제 main `5fbfd92f3471b64475f0871720cc7fffed79e430`로 머지됐다.
실제 머지 트리는 최신 부모와 검증 head의 예상 통합 트리와 일치한다. main에 합류한
찾기 IME 변경도 유지했다. 실제 main에서 제품 6개·기존 공유 스냅샷 10개·문서/config
검사 48개 빌드 단계를 다시 통과했다. 해당 main의 별도 CI 40198099324도 통과했다.

## 재현과 범위

원본 뷰에서 편집해 유효한 입력·복사 계보가 생겨도 `prepareSharedSnapshot`은 이를 새 뷰에
전달하지 않았다. 실제 native 트리는 복사했지만, 분할 뒤 첫 입력은 이전 계보를 증명할 수 없어
C 범위 계산 2회·재사용 0회였다. 독립 전체 파싱 결과와 실제 호출 수로 재현했다.

원본에 유효한 증명이 있는 경우만 전달한다. 한 번도 증명을 확보하지 않은 초기 문서,
오래된 입력 판·pending·다른 grammar는 기존 경로를 유지한다. 현재 입력을 추측해 새로
발급하거나 분할 중 강제로 재파싱하지 않는다. 저장·Undo·분할 UX·영속 포맷은 바꾸지 않는다.

## 구현

`Provider.copyReady` 성공 뒤 원본의 `matchesInput`을 확인한다. 입력 증명은 문서 신원과
리비전을 그대로 두고 parser 신원·트리 세대만 실제 수신 provider로 바꾼다.
`origin.copied`가 현재 원본 자원과 계보를 검증한 경우에만, 수신 allocator로 만든 별도
`OriginState.current`에 결과를 보관한다. 원본의 과거 변경 `receipt`는 전달하지 않는다.

메타데이터 할당 실패는 이미 복제한 provider와 입력 증명을 유지한다. 접힘 캐시의 기존
선택적 복사도 계속한다. 준비 취소는 수신 메타데이터만 해제하며 원본과 컨테이너를 공유하지 않는다.
새 필드나 별도 전역 캐시는 추가하지 않는다. 계보 없는 기존 호출도 native 스냅샷을 계속 받는다.

## 검증

저장소 밖 `shared-change-origin-split-diagnostic-1` 사본에서 정상 입력의 첫 계산이
2회→1회, 재사용은 0회→1회로 바뀌고 전체 색·심볼·접힘 결과가 일치했다.
Debug·ReleaseFast에서 입력 판 부재·잘못된 parser·오래된 계보·pending·선택적 할당 실패와
독립 소유·취소 후 원본 보존을 대조했다. 입력 증명·계보의 현재 판·할당 실패 정책·수신 parser
매핑·pending 검사를 각각 훼손한 다섯 결함은 컴파일 후 실행에서 검출됐고 정상 전후 대조는 통과했다.
이는 사본의 증거이며 최종 브랜치의 검증과 구분한다.

제품 집중 명령은 `mise exec -- zig build test-editor-shared-origin-snapshot test-editor-shared-snapshot -j2`다.
브랜치의 집중 6개·기존 스냅샷 10개·기존 계보 제품 8개는 Debug에서 통과했다.
원본 뷰를 닫은 뒤 살아 있는 뷰의 입력·전체 색·심볼·접힘도 대조했다. 같은 집중 검사와
기존 공유 파싱 제품 7개는 ReleaseFast에서도 통과했다. 실제 브랜치 코드의 다섯 결함
주입도 컴파일 후 실행에서 검출됐고 정상 대조 6건은 통과했다.
원시 자료는 `split-origin-product-attacks-1`과 `split-origin-product-source-proof.json`에 보존한다.
CI 개수 수정 head에서는 제품·검색·경계·문서 검사 714개 빌드 단계가 통과했다.
이후 최신 LSP 수정을 합친 head로 재배치하며 파일 끝의 검사 추가 충돌을 해결했고,
LSP 검사와 두 스냅샷 검사 본문을 모두 보존했음을 대조했다. 이 상태의 제품·검색·
LSP 복구·경계·문서 검사 718개 빌드 단계도 모두 통과했다.
실제 OS 입력·GPU present·native malloc 실패를 검증했다는 주장은 하지 않는다.

## 실측

`split-origin-measure-3`은 원본에서 삽입·Undo 후 본문이 원문과 같고 계보가 유효함을
확인한 뒤 분할한다. 원본 준비 시간은 별도로 보존하며 cold open 측정으로 쓰지 않는다.
분할 명령·두 뷰 준비·첫 입력을 모두 잰다. 첫 입력만 떼어 준비 비용을 숨기지 않는다.
분할 준비 구간의 native 파싱 계측시간은 두 사본 모두 0ns였다.

고정 파일 5종의 전후 성능 30개 프로세스/600편집과 별도 정확성 10개/200편집을 완료했다.
첫 입력을 포함한 모든 입력의 호출 수·부모/자식 시간·전체 접힘 결과를 검증하고,
전체 소스·빌드·바이너리·입력 해시와 실행 순서를 보존했다.

대형 Zig의 첫 입력 중앙값은 57.951→50.382ms, 준비+첫 입력은 260.399→252.680ms였다.
각 조건당 성능 실행은 3회이므로 작은 차이를 보편적 개선·퇴보로 확정하지 않는다.
앞선 2번 자료도 보존하지만, 캐시 바이너리 부재와 재빌드 해시 차이 때문에 새 실행파일을
캐시 밖에 보관하고 전체 측정을 다시 실행한 3번 자료를 최종 표의 근거로 삼는다.
[전체 분포·보존 경위·해시](../../tools/editor-shared-snapshot/origin-results.md)를 함께 남긴다.
이 수치는 계측된 함수 경과시간이며 실제 키 입력부터 표시까지의 지연·RSS·cold open 결과는 아니다.
