# 이름 없는 로컬 문서의 첫 저장 — 비동기 전환과 실측

상태: 비동기 제품 연결 구현. 로컬 회귀 검사 통과, 최종 실측·CI·병합 확인은 별도다.
기존 계약은 [문서 모델 §3.11](../native-editor-document-model.md), 저장 기반은
[비동기 로컬 저장](editor-local-save-async.md), 대상 예약·경로 전환은
[Save As](editor-save-as.md)가 소유한다. 아래는 승인된 기존 계약과 구현·검증 범위다.

## 먼저 재현한 문제

전환 전 `untitled_save.writeAndAdopt`는 이름 확정 caller에서 `saveBytes`·배타 생성/덮어쓰기·
경로/도크 등록을 마친 뒤 반환한다. 명명 모달을 확정하는 main queue가 이 일을 모두 기다린다.
하네스는 격리 사본에만 시계와 쓰기 직전의 지연을 넣는다. 실제 파일 쓰기와 제품 경로 채택은
그대로 실행하며, 완료 뒤 디스크 bytes·문서 경로·도크 entry·clean을 검사한다.

`tools/measure-editor-untitled-save.py`는 크기별 무지연/200ms 주입을 각각 세 번 순차 실행한다.
`call_ns`는 이름 확정 진입부터 반환, `next_event_ns`는 같은 시작부터 다음 main queue
블록 실행까지다. snapshot 직렬화와 실제 I/O 구간도 따로 기록한다. I/O 구간은 주입 지연을
제외하며, 전체 호출에는 분류·경로 전환 등도 포함된다. 문서 생성/초기 입력과 캡처·종료 시간은
측정 밖이다. 다음 이벤트 지연은 프레임률이나 모든 사용자 이벤트의 상한이 아니다.

측정값과 원본 manifest는 실행 산출물 `samples.json`·`summary.json`에 보존한다.
200ms는 느린 디스크를 실제 측정한 값이 아니라 차단을 재현하기 위한 통제된 주입이다.
무지연 값도 이 기계·Debug·warm-cache·짧은 줄 반복 본문의 표본이다.

## 구현 범위

첫 범위는 **이쪽에 저장하는 이름 없는 일반 네이티브 문서**다. SSH 원격 첫 저장과
이름 묻기/덮어쓰기 확인 UI는 기존 경로를 유지한다. 새 파일은 배타 생성, 기존 파일은
사용자가 확인한 대상과 쓰기 시점의 보호 계약을 유지한다. 새 스레드가 Term이나 AppSession을
읽는 방식은 사용하지 않는다.

1. 이름 확정 뒤 문서 registry lease·대상 epoch·선택 경로를 소유한다. 입력 해석/조합 확정이
   끝난 뒤 불변 저장 bytes를 만든다. live 본문 포인터를 worker가 빌리지 않는다.
2. 경로 복사·도크 entry·완료 슬롯 등 성공에 필수인 메모리를 **쓰기 전에** 준비하되, 실제 경로와
   도크 목록에는 성공 전 공개하지 않는다. 준비 실패는 이름 없는 본문·Undo를 그대로 보존한다.
   전환 전 동기 경로의 쓰기 후 할당 실패(`editor_untitled_written_not_adopted`)와 구분한다.
3. 기존 Save As actor의 예약/worker 경계를 재사용한다. 이름 없는 문서에는
   원본 경로가 없으므로 가짜 빈 경로를 만들어 named `Target`을 통과시키지 않는다.
   원본 종류·완료 승인 같은 순수 판정은 중립 저장 계약에 두고 앱 actor는 I/O와 수명을 맡는다.
4. 실제 쓰기 성공 뒤 같은 문서·epoch에만 준비한 경로와 도크 entry를 붙이고 untitled 표식을
   해제한다. 저장 중 추가 편집은 새 경로에서 dirty로 남긴다. 실제 저장 snapshot과 현재 본문을
   비교하므로 입력 뒤 Undo로 돌아온 경우도 검사한다. 다른 문서/재사용된 surface는 바꾸지 않는다.
5. 저장 기준·원시 disk hash·언어/들여쓰기·백업 신원·workspace checkpoint·LSP를 같은 성공
   경계에서 맞춘다. 새 파일 bytes만 생긴 것을 UI 성공으로 알리지 않는다.
6. 반복 ⌘S·닫기/종료·후속 이름 변경이 첫 저장과 경합하는 경우 기존 비동기 저장의 대기 후
   재검사 원칙을 적용한다. 저장 중 다른 문서를 막거나 전역 drain으로 UI를
   기다리게 하지 않는다. registry lease를 보유하며 완료 시 문서 신원과 대상 epoch를 다시 검사한다.

## 도크 entry의 준비와 수명

`save/as.zig`는 경로와 entry를 쓰기 전에 준비하지만 실제 Term에는 완료 뒤 붙인다.
준비한 entry는 `AppSession.editor_batch_reserved_entries`에 포함하므로 일반 파일 열기와
workspace 이동이 그 자리를 먼저 소비하지 않는다. 성공·실패 모두 원래 창 generation으로
예약을 해제하며, 해제된 창의 포인터는 보관하지 않는다.
쓰기 중 workspace가 이동하면 경로 채택 전에 수신 창의 allocator와 남은 용량을 검사한다.
채택할 수 없는 늦은 완료는 실제 디스크 파일을 삭제하지 않고 기존
`editor_untitled_written_not_adopted` 안내와 이름 없는 본문·Undo를 보존한다.

`mise exec -- zig build test-editor-first-save-async test-editor-untitled -j2`는
차단한 worker로 성공 전 미공개·추가 입력/Undo·배타 생성 경쟁·세대 변경·반복 저장·
닫기 재확인·준비 할당 실패·동일 목적지 경합·마지막 도크 자리·쓰기 중 창 이동을 검사한다.
제품 전체 회귀 152개와 중립 규칙 45개, 별도 집중 그래프 16개가 통과했다.
집중 그래프는 실제 첫 저장 시나리오 9개와 복구 사본 저장·언어별 들여쓰기 안내선 회귀 2개를 포함한다. 나머지는 import test 블록이다.

## 다른 창의 열린 문서와 대상 예약

2026-10-19 사용자 확인: **다른 창에서 같은 경로를 열고 있다는 이유만으로 첫 저장을
거절하지 않는다.** 이는 새로 허용하는 동작이 아니라 [문서 모델 §3.11](../native-editor-document-model.md)의
기존 창 단위 계약과 `editor/mod.zig`의 U2y 회귀 조건을 유지하는 결정이다.
비동기화 때문에 이름 있는 문서의 Save As 정책을 첫 저장에 확대하지 않는다.

- **같은 창에서 이미 열린 대상**: 기존처럼 첫 저장을 거절한다. 디스크 덮어쓰기 확인과
  별개이며, 확인을 받았다고 이 검사를 건너뛰지 않는다.
- **다른 창에서 이미 열린 대상**: 열려 있다는 사실만으로 거절하지 않는다. 기존 파일의
  덮어쓰기 확인·선택한 대상의 상태 검사·실제 쓰기 시점의 충돌 보호는 유지한다.
- **동시에 같은 대상으로 저장하는 요청**: 열린 문서 검사의 창 범위와 별개로 앱 전역
  대상 예약을 공유한다. 첫 저장과 Save As가 같은 목적지에 동시에 쓰도록 허용하지 않는다.
- **다른 창의 본문·Undo**: 이번 변경이 다른 창의 독립 문서를 공유 문서로 바꾸거나,
  미저장 본문을 덮어쓰거나, 창 사이의 실시간 본문 동기화를 추가하지 않는다.
  외부 변경 감지와 이후 저장 충돌은 기존 계약을 따른다.

VS Code 소스 확인은 정책 비교에만 사용했다. `textFileService.doSaveAsTextFile`은 대상
모델을 재사용하며, `TextFileEditorModelManager.onDidFilesChange`는 dirty 모델을 자동으로
다시 읽지 않는다. `TextFileEditorModel`의 저장은 수정 시각·etag를 전달해 충돌을 검사한다.
이는 다른 창의 미저장 본문까지 항상 자동 갱신한다는 의미가 아니다. 확인한 소스는
[VS Code 113947563a의 저장 처리](https://github.com/microsoft/vscode/blob/113947563a3837013dbff0095e2bf29880b5d354/src/vs/workbench/services/textfile/browser/textFileService.ts#L500),
[파일 변경 처리](https://github.com/microsoft/vscode/blob/113947563a3837013dbff0095e2bf29880b5d354/src/vs/workbench/services/textfile/common/textFileEditorModelManager.ts#L122),
[저장 충돌 검사](https://github.com/microsoft/vscode/blob/113947563a3837013dbff0095e2bf29880b5d354/src/vs/workbench/services/textfile/common/textFileEditorModel.ts#L938)다.
VS Code의 실제 다중 창 GUI 재현을 완료했다는 주장은 하지 않는다.

## 반례와 검증 조건

- 0바이트·BOM·CRLF·저장 상한, 새 대상/덮어쓰기, 쓰기 실패와 모든 준비 할당 실패.
- 저장 중 편집·Undo/Redo, ⌘S 반복, 같은 이름으로 다른 문서 첫 저장/Save As/열기 경합.
- 마지막 뷰 닫기·앱 종료·원래 창 해제·문서 slot 재사용·늦은 완료·취소 후 완료.
- 목적지 외부 변경·부모 교체·배타 생성 경쟁과 예약 해제의 성공/실패 대조군.
- 백업/재시작, 도크 표시·언어·LSP, 기존 원격 첫 저장과 일반 로컬 저장 회귀.
- 동일 지연/본문으로 전환 전후의 호출/다음 이벤트/전체 완료를 따로 실측한다. worker 분리만으로
  main의 snapshot 준비 비용이나 전체 저장 완료 시간이 줄어든다고 주장하지 않는다.

위 로컬 검사에 명시된 경합은 재현했다. 사람의 키보드·VoiceOver·전원 손실과
모든 창 종료 조합을 검증했다는 의미는 아니다.

## 측정 판정의 보강과 결함 대조

기존 parser가 성공 접미사나 중복 레코드를 받아들이는 반례를 재현해 수정했다.
각 표본은 완전한 측정/직렬화/I/O 레코드가 정확히 하나씩 있어야 하며, phase 합과 주입
지연이 전체 완료 시간을 넘거나 다음 블록 시각이 호출 반환보다 빠르면 거절한다.
현재 하네스는 `settled_ns`를 별도 기록하므로 비동기 caller가 I/O보다 먼저 반환할 수 있다.
기존 동기 로그는 호출 안에 phase와 주입 지연이 포함되는 원래 조건도 유지해 판정한다.
집계는 boolean 성공·요청한 크기/지연·정수 ns·동일 바이너리/준비 소스/하네스/실행기/
판정 코드와 실제 빌드 모드를 검사한다. 중복 크기로 같은 집계를 두 번 세는 입력도 거절한다.
`--optimize`는 실제 앱이 보고하는 `builtin.mode`와 일치해야 한다. 실제 Debug 앱에
ReleaseFast를 지정한 실행은 거절됐고, 측정 비활성의 기존 실행은 통과했다.

본문·정확한 전체 경로·entry 경로/surface·모달 종료 검사를 다음 블록 시각 기록 **뒤**에
수행한다. 디스크 검사는 Python이 따로 수행한다. 실제 앱의 도크 surface 연결에 결함을
넣으면 디스크가 써져도 `passed=false`로 실패하는 것을 확인했다. 결함 제거 뒤 정상/최소
크기와 홀수 길이 표본도 무지연/200ms 각각 통과했다. 위 표는 원래 12개 로그의 값이며, 엄격해진 로그
판정에서도 값이 그대로 통과했다. 서로 다른 하네스 버전의 새 결과를 같은 표본군에 섞지 않는다.

집계기의 전체 timeout이 실행기만 먼저 종료하면 분리된 앱이 남을 수 있는 프로세스 구조도
소유한 임시 프로세스로 재현했다. 집계기에서 하위 실행기를 먼저 죽이는 timeout을 제거하고,
하위 실행기의 복사·빌드·실제 앱 timeout과 finally 정리를 사용한다.

`python3 tools/test-editor-untitled-measurement.py`는 손상/누락/중복 로그, 잘못된 성공 값·
조건·시계·빌드 모드와 표본 신원 혼합을 거절하는 반례를 검사한다.
`python3 tools/test-editor-untitled-measurement-adversarial.py`는 성공 접미사·중복·truthy 성공·
신원 혼합·phase 합 보호를 각각 제거하면 반례 검사가 실제로 실패하는지 정상/결함/복원
사본으로 대조한다. 이 도구도 제품 소스를 바꾸지 않는다.

## CI에서 발견한 기존 소비자 검사의 동기 가정

최초 CI에서 복구한 빈 사본을 저장한 직후 파일을 읽는 검사가 `FileNotFound`로 실패했다.
비동기 완료를 기다리지 않았던 것이 원인이며, 같은 저장 확정을 사용하는 기존 검사 호출부를
대조해 복구 저장 2곳과 언어별 들여쓰기 안내선 2곳에 완료 대기를 반영했다. 이 두 소비자
회귀도 `test-editor-first-save-async`에 포함해 첫 저장 경합만 통과하고 누락하지 않도록 했다.
기존 실패 로그에는 이후 30분 job 시간 초과도 있으므로 성공한 CI로 취급하지 않는다.
