# 실제 렌더 범위에 맞춘 본문 색 조회

상태: 일반 본문 구현·집중 검사·제품 Metal 대조·다섯 독립 결함·전후 실측과
전체 편집기·경계·문서·config 게이트를 완료했다. 원격 CI와 머지 상태는 PR에서 확인한다.
선행 #4600은 실제 메인 `711591ffa`에 머지됐고 전체 트리 일치·로컬 재검증·메인 CI를 확인했다.

## 구현 계약

일반 본문의 색 조회를 현재 화면 기하와 실제 행 저장소의 예산으로 묶는다.
중립 `viewport.logicalLineBudget`은 `diff_frame.sideMetrics`의 화면 행과 호출자가 넘긴
scratch 용량에서 논리 줄 상한을 구한다. 호스트의 저장소 크기를 상수로 복사하지 않는다.
빈 화면은 예산이 없고, 나머지는 경계 여유를 보되 실제 행 저장소를 넘지 않는다.
색 배열은 앞쪽 빈 슬롯을 포함한 절대 렌더 줄 첨자를 유지하고 접히면 보이는 줄 축을 따른다.
모델 편집·검색·명령의 범위를 이 상한으로 제한하지 않는다.

공통 진입점 `syntaxColors`가 표시 예산을 받는다. 기존 계측도 이 진입점을 재므로
일반 본문 호출을 새 보조 함수 이름 때문에 누락하지 않는다. 기하를 받지 않는 호출자는
`null`로 기존 창을 유지한다. IME 투영·병합의 조회량 최적화는 이 변경의 범위 밖이다.
semantic/inlay 미리 읽기는 기존 예산에서 별도로 구해 본문 색 조회량에 연결하지 않는다.
새 UX·저장 포맷·worker·의존성은 추가하지 않는다.

## 확인한 동작

수정 전 실제 `appendPaneFrame`의 hit 행과 색 저장소를 대조했다.
첫 줄 31에서 작은 창은 실제 8행에 256줄을 조회했고, 큰 창은 실제 512행에 256줄만 조회했다.
앞쪽 빈 31슬롯을 조회 개수로 세지 않는다. 수정 후에는 각각 9줄과 512줄을 조회하고
실제 그린 모든 행의 색을 확인했다. 희망 범위 공식을 기대값으로 반복하지 않았다.

랩 중간 조각·좁은/넓은 화면·스크롤·문서 끝과 접힘 축을 대조했다.
C 원문은 LF/CRLF·한글·결합 문자·이모지·긴 줄·여러 줄 주석을 포함한다.
실제 표시 행의 색을 남은 원문 전체 조회와 비교했다. 이는 같은 색 알고리즘의 범위 대조이며
외부 문법의 독립 정답은 아니다. 가짜 LSP 서버에서는 provider의 지원·실제 송신 횟수를
양성 대조로 확인하고 작은/큰 창의 semantic/inlay 요청 범위가 기존 창과 같은지 검사했다.

리베이스 전 ReleaseFast·Debug에서 중립 1개(7개 입력)·호스트 19개·기존 병합 43개가 통과했다.
최신 main 합류 후에도 ReleaseFast의 같은 검사와 프로젝트 검색 IME 호스트 34개를 다시 통과했다.
호스트 19개는 새 제품 판정 5개·IME 투영 제품 6개·모델 4개·익명 import 4개다.
기존 IME/병합 사례의 회귀 대조이며 모든 OS 입력기 동작을 검증했다는 뜻은 아니다.

## 독립 결함 검증

기존 조회 고정·색 공급 제거·실제 행 용량 무시·접힘 원문 축 무시·LSP 범위 결합을
각각 컴파일해 실제 해당 판정자의 실패를 확인했다. 각 결함 전후 정상 대조 10개와
원본 소스·빌드 해시 불변도 확인했다. 실행 파일과 로그를 각각 보존하고 다시 해시를 대조했다.
근거는 저장소 밖 `visible-color-window-hostile-4/result.json`과 각 patch·로그·실행 파일이다.

검증 도구의 정상 대조에서 테스트가 바깥 체크아웃에 의존하는 문제가 드러났다.
기존 실패 실행 파일을 다시 돌려 재현하고 임시 Git 루트를 소유한 fixture에서 두 번 통과했다.
제품 권한 정책 대신 테스트를 `SmtFixture.openRepo`로 격리했다.
소스 원복 후 실행 파일의 바이트 해시가 다른 경우도 있어, 바이트 재현성을 전제로 삼지 않고
모든 대조 실행 파일을 개별 해시와 함께 보존한다. 두 이전 부분 실행은 채택하지 않았다.

## 제품 시각 대조

`visible-color-window-gpu-4`에서 실제 제품 `appendPaneFrame` → CoreText → Metal readback을
촬영했다. 같은 800×4800px·첫 줄 31·실제 297행에서 기준은 256줄, 수정본은 298줄을 조회했다.
PNG를 직접 열어 하단의 무색 영역이 복원된 것을 확인했다. 독립 PPM 읽기에서는 바뀐
24,600픽셀의 경계가 `[77, 4141, 241, 4794]`였으며 그 밖의 픽셀은 같았다.
GPU 생성·atlas·제출·읽기·PNG/PPM·소스·실행 파일·로그 해시를 함께 확인했다.

기준은 리베이스한 main `078a8dcef`이며 수정본은 최종 제품 소스로 고정했다.
`pixel-readback.json`에서 캡처 사본의 소스·빌드·로그·보관 실행 파일·PNG/PPM 해시와
현재 제품 소스의 일치를 다시 확인했다. 두 PNG를 직접 열어 확인했다.
[캡처 명령](../../tools/editor-visible-colors/README.md)은 제품 코드 사본만 수정한다.
GUI/HID·실제 입력기·물리 화면 해상도 검증으로 확대하지 않는다.

## 전후 실측

[전체 결과](../../tools/editor-visible-colors/results.md)는 같은 다섯 입력의 전후 80프로세스를 기록한다.
이 실측은 `711591ffa` 기준의 리베이스 전 자료이며 새 main의 검색 IME 변경을 포함한 전체 시간은 측정하지 않았다.
성능 1,200입력과 별도 정확성 400입력이다. 정확성 실행은 매 입력·각 뷰의 표시 색을 대조하고, 성능 실행은 마지막 표시 색을 별도로 대조한다.
프로세스별 첫 입력을 보존하고 실행 순서를 번갈아 배치한다. 원시 기록의 모든 구간 통계·
첫 입력·호출 수는 별도 계산으로 대조했다. 다른 작업 부하는 통제하지 않았다.
전체 최대값과 첫 입력까지 모두 개선됐다는 뜻은 아니며, 큰 화면의 색 공급 증가 비용은 별도다.
이전 자료의 시간을 빼 개선량으로 만들거나 GUI 입력 지연·RSS의 증거로 사용하지 않는다.
