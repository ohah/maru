## 판정 기록

- ~~`'render'` 모드 존치~~ → **제외로 판정**(P5). 명분이던 "동기 조회"는 조회가 전부 `Promise`가 되며 사라졌고, 남은 이득으로 꼽았던 "워커 번들에서 wasm 제외"도 성립하지 않았다 — wasm 은 번들에 들어가지 않고 `new URL` 로 참조되는 별도 파일이다(워커 번들 21 KB, wasm 127 KB 별도). 2모드(`'full'`/`false`)로 줄였다.
- ~~Lit `static properties` 빌드 통과~~ → **확인**(P10). 데코레이터 없이 zntc 를 통과하고, 브라우저에서 `<maru-terminal>` 마운트·렌더·`ready` 이벤트까지 검증했다.

- ~~프로시저럴 글리프를 `box_glyph` 로 구현~~ → **`renderer.synthesizeGlyph` 로 정정**. 박스만 덮고 블록·파워라인·브라유·모자이크는 폰트로 흘렸다. 본체가 이미 10개 계열을 한 자리에서 디스패치하므로 wasm 브리지도 그걸 부른다(wasm 127 KB → 220 KB).
- **컨테이너 자동 맞춤이 기본이 됐다**. `open(el)` 로 요소를 받는 API 인데 `fit()` 을 아무도 부르지 않아 80×24 고정으로 떠 컨테이너에 여백이 남았다. `cols`/`rows` 를 명시하지 않으면 `ResizeObserver` 로 따라간다.
- **번들러가 워커 청크의 `import.meta.url` 을 빈 문자열로 접는다**(zntc 실측). `new URL(rel, "")` 은 "Invalid base URL" 로 죽어 `worker: 'full'` 이 통째로 실패했다. 로더가 `location.href` 로 물러서고, 메인이 절대 URL 을 넘기고, 빌드가 그 패턴을 fail-closed 로 막는다.

- **IME 는 `onPreedit` 구독으로 책임이 갈린다**(계약 §5). 처음엔 라이브러리가 오버레이만 그려 조합 글자가 화면에 없었고, 코어 삽입을 넣었더니 이번엔 줄을 다시 그리는 앱과 어긋났다 — 프로토타입은 셸이 `before + preedit + after` 로 함께 그려서 그 문제가 없었다. 구독 여부로 삽입 주체를 정하고, 오버레이는 항상 라이브러리가 그린다.
- **워커의 `resize` 가 backing store 를 안 잡고 있었다**. CSS 만 늘고 backing 은 옛 격자로 남아 `worker: false` 와 레이아웃이 갈렸다(966×528 CSS 에 672×528 backing). 캔버스 소유권이 워커에 있으므로 메인은 CSS 만 바꿀 수 있다 — 두 곳을 함께 고쳐야 한다.
- **기본 키바인딩 표를 본체와 맞췄다**(계약 §5.1). 코어 인코딩은 `Cmd+Backspace` 를 `Backspace` 와 구분하지 않아 줄 삭제가 한 글자 삭제로 나갔다.

- **추측으로 넣은 방어 코드가 워커를 멈춰 세웠다.** 폰트 등록 직후 격자를 재면 폴백 값이 나올까 봐 `fonts.ready` 를 기다리게 했는데, **워커의 `fonts.ready` 는 resolve 되지 않는다**(문서가 없다). `WorkerBackend.create` 가 끝나지 않아 백엔드가 끝내 null 이었고, 깜빡임 신호가 워커에 닿지 않아 커서가 멈춘 화면이 나왔다. `FontFace.load()` 가 이미 로드를 보장하므로 그 대기는 애초에 불필요했다 — 근거 없이 방어를 더하지 않는다.
- **`onBlink` 가 `this.#backend` 를 직접 읽어 항상 null 이었다.** 그 콜백은 `attachDom` 안의 타이머에서 불리는데 워커 백엔드는 그 뒤에 대입된다. 지역 변수로 잡아 고쳤다.
- **줄 간격 여백을 위아래로 나눈다**(계약 §5). 기본 `lineHeight` 는 1.22 다. 전부 아래에 두면 선택 배경이 하단 패딩처럼 보인다.

**목록의 근거**: xterm.js 의 `Terminal` 공개 타입(`typings/xterm.d.ts`)과 1:1 대조해 뽑았다.
처음 세었던 "빠진 기능 7가지"는 **애드온급 기능만 본 것**이라 API 표면 격차(이벤트 6종, 메서드
10여 개)를 놓쳤다. 계약 §7 의 표가 그 대조 결과다.

- **리뷰 15건 cap 밖에도 결함이 있었다.** `/code-review max` 가 상한에 걸려 잘라 낸 목록에서 8건을 더 고쳤다(라이선스 표기, 실패한 wasm 로드의 영구 캐시, `linkAt` 미처리 거부, Lit 재마운트 불가, `sideEffects` 거짓, `setOptions` 가 옵션을 버리던 것, `packages:check` 가 브라우저 검사를 빼먹던 것, 문서의 옛 bun 버전). **상한이 있는 리뷰 한 번으로 끝났다고 보면 안 된다.**
- **정적 리뷰와 실사용은 겹치지 않는다.** 리뷰가 찾은 것들은 대부분 특정 조건에서만 드러나 데모 사용으로는 체감되지 않았고(마우스는 앱이 DECSET 을 켜야, 스냅샷 절단은 1440p 최대화, 트리셰이킹은 프로덕션 번들), 반대로 실사용에서 나온 것들(IME 밀림, 리가처, 커서 깜빡임, 하단 패딩)은 리뷰가 못 찾았다. **F1 이 1순위인 이유다.**

- **F1 첫 라운드 통과**(2026-08-23). `Bun.Terminal` 로 PTY 를 열어 nvim·htop·tmux 를 띄웠다.
  대체 화면 진입·복원, 256색 미터, pane 분할선, 한글 폭이 모두 정상이고, **이번에 배선한 마우스
  리포트가 실제 앱에서 처음 검증됐다**(htop 이 DECSET 1000 을 켜자 모드 비트 2, 클릭이
  `ESC[<0;12;2M`). 확인한 시퀀스는 결정적 테스트로 옮겼다(대체 화면·마우스 단계·스크롤 영역·
  DECSCUSR) — 모드 비트를 훼손하면 2건이 실패하는 것으로 검증력을 확인했다.
- **F1 이 실제 결함을 찾았다** — 진짜 셸에서 한글을 치면 **앞 글자가 지워졌다**(`echo ` → `ho`).
  라이브러리가 조합을 코어에 `ICH`/`DCH` 로 넣는데 화면을 소유한 zsh 와 어긋난 것이다. 화면
  버퍼를 건드리지 않고 **렌더러가 밀어 그리도록** 바꿨다(계약 §5). 가짜 셸로는 앱이 화면을
  관리하지 않아 절대 드러나지 않는 종류다.
- **탐색으로 확인한 것**: 스크롤백(휠로 448~450 행 확인), 리사이즈(`tput cols` 가 115 → 46 을
  정확히 읽는다 — SIGWINCH 전달), 대량 출력(20만 줄 중 메인 스레드 최장 정지 17ms, 유실 없음).
- **앱이 실제로 반응하는 것까지 확인했다.** `less --mouse` 에서 휠을 굴리니 첫 줄이 1 → 6 으로
  이동했고, tmux(`set -g mouse on`, 모드 3)에서는 copy-mode 로 들어가 스크롤했다. "올바른
  바이트를 보냈다" 를 넘어 **앱이 그걸 처리했다** 까지 왔다. 휠 인코딩(버튼 64/65)은 결정적
  테스트로 옮겼다.
- **종료·재연결**: `exit` 로 셸이 끝나면 소켓이 닫히고 `[PTY 끊김]` 이 뜨며 터미널은 살아 있다.
- **F1 1라운드 종료.** 남은 것은 Safari/Firefox, 모바일 터치, 접근성 — 전부 F8 이다.

- **F2 의 "export + 얇은 래핑" 전제는 틀렸다.** 코어에 구현이 있는 것은 맞지만 **시맨틱이
  xterm.js 와 다르다**. `clearScreen()` 은 OSC 133 상태에 따라 3갈래로 갈리고 alt screen 에선
  무동작이며, 반환 bool 은 "셸에 ^L 을 보내라"는 뜻이다(본체 `.clear_screen` 이 그렇게 쓴다).
  `scrollToAbs()` 는 Find 용이라 대상 행을 **화면 중앙**에 두는데 xterm.js `scrollToLine` 은
  **맨 위**다. 그래서 코어 함수를 그대로 노출하지 않고, 본체 계약을 문서화한 뒤 그쪽에 맞췄다
  (계약 §7). 라이브러리는 xterm.js 클론이 아니라 **maru 코어를 내는 것**이라 이 편이 옳다.
- **`reset` 은 export 를 늘리지 않는다.** `ESC c` 를 흘리면 파서가 이미 `fullReset` 을 부른다 —
  앱이 보낸 RIS 와 경로가 하나로 유지된다.
- **F2 가 기존 결함을 하나 찾았다 — 스크롤 위치가 65535 행에서 잘렸다.** `vt_scroll_state` 가
  `(offset << 16) | len` 으로 둘을 한 u32 에 실으며 각 필드를 `0xffff` 로 잘랐다. 70000 행을
  쌓고 재보니 길이가 **4464** 로 보고됐다(실측) — 스크롤바가 6% 만 그려지고 절대 행 스크롤은
  아예 불가능하다. `scrollback: 100000` 은 실제로 쓰는 설정이다([wasm 이식성](../wasm-portability.md)
  §5.2 가 63.94MB 로 측정한 그 값이다). `vt_view_offset`·`vt_scrollback_len` 으로 나눴다.
- **브라우저 검사에서 가짜 통과를 잡았다.** 새로 넣은 워커 제어 검사가 `0/0` 으로 통과하고
  있었다 — 앞 검사가 `scrollback: 0` 을 남기고 가 스크롤백이 애초에 안 쌓였다. "쌓였는지"를
  먼저 단언하도록 고쳤다(42 행 → clear 후 0). **0 대 0 비교는 통과가 아니다.**

- **F3 은 wasm 을 건드리지 않았다.** "워커 모드에서 이벤트 채널을 태워야 한다"고 봤는데,
  이미 매 프레임 커서·선택·스크롤이 `FrameMeta` 로 실려 온다 — **직전 프레임과 비교**하면
  된다. 파생을 `Terminal#publishFrame` 한 곳에 두어 두 모드가 같은 경로를 탄다.
- **커서 이동은 위치만 본다.** 모양·가시성까지 비교하면 깜빡임이 매 프레임 토글되므로
  `onCursorMove` 가 초당 수 회 발화해 쓸 수 없게 된다.
- **첫 프레임은 기준선이다.** 초기 상태를 변화로 내면 마운트 직후 무의미한 알림이 간다.
  `makeTerminal` 은 프레임을 안 내므로 테스트는 `write("")` 로 기준선을 세워야 한다(실사용은
  `open()` 의 초기 렌더가 그 역할을 한다).
- **애드온으로 나누지 않기로 판정했다**(계약 §8). xterm.js 의 분리는 JS 라서 가능한 것이고,
  wasm 은 linear memory 가 분리돼 코어 상태를 볼 수 없다. 게다가 Zig 가 도달 불가 코드를
  이미 지운다 — 실측으로 뗄 것이 프로시저럴 글리프 18.7 KB(gzip 6.1 KB)뿐이고 그건
  차별점이라 뺄 수 없다. 무거운 기능(Kitty PNG 디코더)은 **wasm 변종 + `wasmUrl`** 로 간다.

- **F4a: "검색 하이라이트를 그리려면 마커/장식이 함께 있어야 한다"는 틀렸다.** `findNext` 가
  매치를 **선택**하면 기존 선택 렌더가 그대로 칠한다 — 마커 없이 동작한다. 장식이 필요한 것은
  **여러 매치를 동시에** 칠할 때뿐이라 F4b 로 미룬다.
- **검색이 wasm 을 2.8 KB(gzip 1.1 KB) 늘렸다.** 애드온 판정(계약 §8)의 근거가 하나 더 늘었다 —
  기능 하나가 이 정도면 뗄 이유가 없다.
- **좌표계가 갈린다.** 매치는 **절대 행**, 선택 API 는 **뷰포트 행**이다. 처음에 절대 행을 그대로
  `selectStart` 에 넘겼고, 스크롤백 깊은 매치에서 엉뚱한 줄이 잡혔다. `findNext` 안에서 변환한다 —
  훼손 테스트로 그 변환이 실제로 필요함을 확인했다.

- **F5 의 "이벤트 채널 설계가 필요하다"는 맞았지만, 설계의 핵심은 채널이 아니라 정책이었다.**
  코어는 OS 를 직접 만지지 않고 대기 상태로 쌓아 둔다 — 본체에서는 platform 이 정책을 확인한 뒤
  시스템 클립보드에 쓴다. 브라우저에서는 그 판단이 더 중요하다(터미널에서 도는 아무 프로그램이나
  사용자 클립보드를 덮어쓰거나 **읽어 갈** 수 있으면 안 된다). **라이브러리는 알리기만 하고
  아무것도 자동으로 하지 않는다**(계약 §7).
- **wasm `i32` 는 JS 에서 부호 있는 수로 온다.** "없음" 표식으로 `0xffff_ffff` 를 쓴 `vt_notification`
  이 `-1` 로 도착해 비교가 늘 통과했고, titleLen 이 65535 가 돼 `link_buf`(2048)를 넘어 읽으며
  **매 write 마다 빈 알림이 샜다**. `>>> 0` 로 받는다.
  - **로컬 테스트는 이걸 놓쳤다** — write 가 하나뿐이라 알림이 실제로 있는 경로만 밟았다.
    "알림이 없을 때 아무것도 오면 안 된다"를 추가했고, 브라우저 검사도 OSC 를 **연달아** 보내
    그 경로를 밟게 했다. 하나씩 떼어 보내면 결함이 숨는다.
- **F5 가 wasm 을 1.1 KB(gzip 439 B) 늘렸다.** export 13 개가 그 정도다 — 애드온 판정의 근거가
  또 하나 늘었다(F4a 는 2.8 KB 였다).

- **F6 을 "API 표면 마무리"로 넓혔다.** 계획서는 화면 직렬화와 `attachCustomKeyEventHandler`
  둘만 묶었는데, 남은 xterm.js 격차를 다시 재 보니 **선택 조회 4종이 거의 공짜**였다 — 선택이
  이미 매 프레임 실려 오므로 `hasSelection`·`getSelectionPosition` 은 wasm 변경 없이 나오고,
  `select`·`selectLines` 는 기존 `selectStart`/`selectExtend` 래핑이다. 한 번에 끝냈다.
- **동기 조회를 되살렸다.** `hasSelection()` 은 Promise 가 아니다 — 복사 버튼의 `disabled` 를
  이벤트 핸들러 안에서 정해야 하는데 Promise 면 못 쓴다. F3 에서 만든 `#prevMeta` 가 두 모드
  모두에서 갱신되므로 **워커에서도 왕복 없이** 답한다(대가: 한 프레임 뒤처질 수 있다).
- **xterm.js 에 있어도 넣지 않기로 한 것들**(계약 §7):
  - `onLineFeed` — 코어에 훅이 없다. 프레임 파생으로는 한 프레임에 접힌 여러 LF 를 구별할 수
    없어 **부정확한 이벤트가 된다** — 없는 것보다 나쁘다.
  - `onWriteParsed` — `write()` 가 동기라 호출 직후가 곧 그 시점이다.
  - `onBinary`·`input`·`refresh` — 각각 `onData`·`sendText`·dirty 렌더가 이미 덮는다.
- **커스텀 키 핸들러는 IME 조합 정리 뒤에 부른다.** xterm.js 는 맨 앞에서 부르지만, 우리는
  조합 중 `Cmd` 조합이 오면 먼저 조합을 취소해야 한다(안 그러면 조합 글자가 화면에 남는다 —
  F2 에서 고친 그 문제다). 조합 자체를 가로채려면 `ev.isComposing` 을 보게 문서화했다.
- **브라우저 검사에 기준선을 함께 넣었다.** "핸들러가 false 면 ⌘A 가 무시된다"만 보면 ⌘A 가
  애초에 동작하지 않아도 통과한다 — F2 에서 겪은 `0/0` 통과와 같은 함정이다. "핸들러 없이는
  ⌘A 가 전체 선택한다"를 먼저 단언한다.

- **적대적 검증에서 결함 셋이 더 나왔다**(F6 이후).
  1. **음수 좌표가 엉뚱한 칸을 선택했다.** `select(0, -3, 2)` 가 마지막 열을 잡았다 — 음수가
     wasm 에서 u32 로 캐스팅돼 거대한 수가 되고 코어의 clamp 를 거친 결과다. JS 쪽에서 격자
     안으로 clamp 하고, 겹치는 구간이 없으면 무동작으로 바꿨다.
  2. **`dispose()` 뒤에도 `hasSelection()` 이 `true` 였다.** `#prevMeta` 만 보므로 죽은 터미널이
     살아 있는 것처럼 답했다 — 다른 메서드는 `#need()` 가 throw 하는데 일관성이 없었다.
  3. **종료 코드 -1 이 "없음"으로 보고됐다.** `0xffff_ffff` 를 "없음" 표식으로 썼는데 그건
     `@bitCast(@as(i32, -1))` 과 같은 비트다. 유무를 **별도 칸**으로 받도록 바꿨다(버퍼 stride 가
     이미 4 라 빈 칸이 있었다). **값 공간과 표식 공간이 겹치면 언젠가 부딪힌다.**
- **브라우저 검사가 전부 `worker=full` 에서만 돌고 있었다.** `worker=false` 는 픽셀 비교만
  했다 — 커스텀 키 핸들러는 DOM 이 필요해 `bun test` 로도 못 덮으므로 **메인 모드에서 한 번도
  검증된 적이 없었다.** 검사를 함수로 빼서 두 모드에서 돌린다.

- **2차 적대적 검증: 두 모드 API 동일성 대조를 넣었다.** 개별 API 를 워커에서 하나씩 확인해도
  **같은 입력에 두 모드가 다른 답을 내는 회귀**는 못 잡는다 — 계약 §2 가 약속하는 것이 바로 그
  동일성이다. 정해진 시퀀스를 넣고 조회 10종을 걷어 비교한다.
  - **처음 쓴 대조는 검증력이 없었다.** 시퀀스가 `OSC 133;D`(명령 종료)로 끝나 `cursorAtPrompt`
    가 **원래 false** 였고, 워커 쪽 그 조회를 망가뜨려도 둘 다 false 라 통과했다. 프롬프트
    상태로 되돌리도록 시퀀스를 고치고, "의미 있는 값을 봤는지"를 별도 검사로 못 박았다
    (`findTotal > 0 && selText !== null && atPrompt === true && cells === 6`).
    **"둘 다 빈 값"도 일치는 통과한다.**
- **의심했지만 문제없던 것들**(2차): 콜백 재진입(`onSelectionChange` 안에서 선택 변경 — 2회에
  수렴), 조회 도중 `dispose`(워커 프록시가 pending 을 reject 한다), 여러 인스턴스의 정적 버퍼
  공유(JS 단일 스레드라 동기 구간이 지켜진다), `#drainResponse` 커버리지(OSC 는 `write` 로만
  들어오고 `write` 마다 drain 한다).
  - **`onRender` 안에서 `write` 하면 자기 유발 루프가 된다.** xterm.js 도 막지 않는 종류이고
    프레임이 마이크로태스크로 접혀 브라우저가 멈추지는 않지만, 소비자가 알아야 할 함정이다.

- **3차 적대적 검증: 배포물·성능·UTF-8·특수 상태.** 앞 두 번이 안 본 각도를 봤다.
  - **찾은 한계 하나 — `findNext` 가 앞 4096 건 안에서만 순회한다.** 매치 5000 건에서 순회가
    0·1·2 행으로 돌고 4097 번째에는 갈 수 없다(실측). 코어 API 가 전체 검색만 지원하므로
    "현재 위치 이후만 찾기" 를 할 수 없다 — 계약 §7 에 한계로 적었다.
  - **`findNext` 는 매번 전체 재검색이다** — 5만 행에서 9.5 ms. 프레임 예산 안이라 지금은
    괜찮지만 캐시하려면 무효화 규칙이 필요해 넣지 않았다.
  - **문제없던 것**: 배포 `.d.ts` 에 새 API 전부 포함, 네 래퍼가 모두 `Terminal` 인스턴스를
    노출(새 API 가 자동으로 닿는다), UTF-8 전반(이모지 검색·직렬화, **나눠 쓴 멀티바이트
    재조립**, OSC 52 이모지), alt screen 에서 find/select/serialize, 스크롤백 0 에서 스크롤 API.

- **F7.5(WebGL 렌더러)를 지웠다 — 실측으로 불필요하다고 판정.** `packages/scripts/bench-render.ts`
  가 재현한다(`bun run --cwd packages bench:render`).

  | **palette-16 — btop 형(8셀마다 색 변경)** | **6.22 ms** | 1.80 ms |

  "화면 전체가 셀마다 다른 색 + 최대 화면 + 매 프레임 갱신" 셋이 **동시에** 성립해야 한다.
  실제 앱은 그렇지 않다 — btop 은 팔레트가 블록 단위로 반복돼 6.2 ms 이고, lolcat 도 보통 몇
  줄이며 정적이다. WebGL 은 그 한 경우를 위해 셰이더·글리프 아틀라스·폴백 경로를 새로 지어야
  한다. **이득이 비용보다 작다.**

  다시 볼 조건: 전체 화면 truecolour 갱신이 상시인 소비자가 나타나거나, 4K 이상에서 그런
  화면을 매 프레임 그려야 할 때.
- **계약 §5 의 렌더 수치가 재현되지 않았다.** 문서는 "셀마다 `fillText` 8.64 ms vs run 병합
  0.08 ms = 108배"라고 적었는데 실측은 **28.22 ms vs 2.51 ms = 11배**다(같은 304×84). 절대값도
  배수도 다르다 — 프로토타입 시절 다른 조건의 측정으로 보인다. **상대적 결론(run 병합이 크게
  이득)은 그대로**여서 정정만 하고 판단은 유지한다.
- **처음 잰 파싱 시간은 내가 넣은 대기였다.** `write()` 뒤 `setTimeout(300)` 을 포함해 재는
  바람에 모든 케이스가 ~300 ms 로 같게 나왔고, "파싱이 렌더보다 11배 큰 병목"이라는 **틀린
  결론**을 낼 뻔했다. 실제로는 파싱이 1.4~4.2 ms 로 렌더보다 **작다**.

- **구형 브라우저 폴백을 검증했다 — 그리고 그러는 데 구형 브라우저가 필요 없었다.** 폴백은
  `typeof Worker`·`typeof OffscreenCanvas` 하나로 결정되므로, `addInitScript` 로 그 전역을 지우면
  Chromium 에서 **정확히 같은 분기**를 밟는다. 실제 Safari 를 받는 것보다 싸고 **결정적**이다 —
  버전이 오르면 진짜 Safari 로는 그 경로를 더는 밟지 못한다.
  - 그때까지 폴백은 **한 번도 밟힌 적이 없었다.** `worker.html` 이 늘 `worker` 를 명시해
    능력 감지 분기 자체를 지나갔다. `auto-worker.html`(미명시)을 새로 뒀다.
  - **WebKit·Firefox 엔진을 받는 것은 보류한다.** 남는 가치는 "아예 안 뜨는지" 스모크뿐이고,
    Canvas 렌더 차이는 알아도 대응할 것이 적으며, IME 이벤트 순서는 **Playwright WebKit 으로도
    못 잡는다**(실제 IME 는 OS 통합이라 자동화 불가, Playwright WebKit ≠ Safari).
- **그 과정에서 결함 하나를 찾았다 — 워커 모드에서 `open()` 직후 화면이 흐렸다.**
  `sizeCanvas` 가 워커 모드에서 backing 을 건드리지 않아(넘긴 뒤에는 못 쓰는 것이 맞다) 기본값
  300×150 인 채로 넘어갔고, 워커가 resize 를 받아 잡을 때까지 CSS 크기로 늘어났다. 실측:
  `open()` resolve 뒤 **4프레임(22 ms)**. 넘기기 전에 `presizeBacking()` 으로 한 번 잡는다.
- **그 회귀 테스트도 처음엔 못 잡았다.** `waitForFunction` → `evaluate` 왕복 사이에 워커가 이미
  크기를 잡아 버려, 훼손해도 통과했다. **픽스처가 `open()` 직후 값을 굳히도록** 바꿔서야
  `300x150 vs 504x440` 으로 잡는다. "없음 vs 없음"도 일치라 값 유무도 함께 단언한다.

- **코어에 필드를 하나 더하는 데 게이트 둘을 지나야 했다.** `TerminalCore` 에 `evicted_total` 을
  넣자 `mise run check` 가 두 번 막았다:
  1. `handoff_inventory.zig` — "각 필드는 정확히 한 disposition 에 있어야 한다". 세션 host 를
     `exec` 로 업그레이드하면 userspace 상태가 사라지므로, 새 필드가 **"기본값으로 복구되겠지"
     하고 조용히 누락되는 것**을 컴파일 타임에 막는다.
  2. `handoff_codec.zig` — `serialized` 로 분류했으면 코덱이 **정확히 한 번** 매핑해야 한다.
     새 태그(91)를 썼다 — 기존 번호를 건드리면 옛 host 가 만든 상태를 못 읽는다.

  `serialized` 를 고른 이유: 단조 증가 카운터라 **이어져야 의미가 있다**. 0 으로 되돌아가면
  소비자가 재는 델타가 음수가 돼 보정이 통째로 건너뛴다.
- **F4b 의 진짜 난제는 장식이 아니라 좌표 안정성이었다.** 절대 행은 스크롤백이 가득 차면
  앞으로 밀린다(실측: 같은 줄이 10행 → 7행). 코어는 selection·kitty placement 를 스스로
  보정하지만 **라이브러리가 든 좌표는 그럴 수 없고, 몇 줄이 밀렸는지 알 방법도 없었다.**
  코어에 `evicted_total`(단조 증가) 필드를 두고 `shiftCoordsForEviction` chokepoint 에서 세어,
  프레임에 실어 보낸다. drain 이 아니라 누적이라 소비자가 여럿이어도 각자 델타를 잰다.
- **DOM element 를 주지 않기로 했다.** xterm.js 는 장식마다 `<div>` 를 얹지만 우리는 (1) 렌더가
  워커에 있을 수 있어 DOM 을 만질 수 없고, (2) 검색 하이라이트처럼 수천 개가 되는 용도가
  주력이다. 색을 받아 렌더러가 칠한다 — 커스텀 UI 는 `onRender` 오버레이로 남긴다.
- **모델만 테스트하면 "안 그려지는" 것을 못 잡는다.** `bun test` 로 마커 좌표를 다 덮었는데도
  **메인 모드에서 장식이 화면에 나타나지 않았다**(브라우저 검사: 0px). `#pushDecorations` 가
  프레임 발행 때만 불려, 등록 직후에는 다음 출력이 있을 때까지 반영되지 않았다. 등록·해제
  시점에도 밀도록 고쳤다 — **픽셀을 세는 검사가 아니었으면 놓쳤다.**
- **지운 장식이 화면에 남는 것도 같은 부류다.** `Decoration.dispose()` 가 목록에서만 빼고 화면을
  갱신하지 않았다. store 에 `onChange` 를 두어 소유자가 다시 밀게 했다.

- **`registerLinkProvider` 로 xterm.js 격차 표가 비었다.** 이 하나가 **자동 URL 감지의 부재도
  실질적으로 메운다** — 코어의 감지는 libc 를 요구해 wasm 에 없지만(계약 §8), 규칙을 소비자가
  넣으면 같은 결과이고 무엇을 링크로 볼지는 앱이 정하는 편이 낫다.
- **줄 텍스트를 provider 에게 함께 준다.** xterm.js 는 행 번호만 주고 provider 가 `buffer` API 로
  꺼내는데, 우리는 코어가 워커에 있을 수 있어 그 API 를 **동기로 열 수 없다.** 라이브러리가 한 번
  뽑아 넘기면 provider 는 정규식만 돌리면 된다.
- **hover 는 초당 수십 번 온다.** 매번 화면을 직렬화하지 않도록 프레임 단위로 캐시하고, 같은
  셀에 대한 되풀이 조회도 기억한다. 프레임이 오면 버린다.
- **OSC 8 이 provider 보다 먼저다.** 앱이 직접 선언한 링크를 규칙이 덮으면 안 된다 — OSC 8 이
  잡히면 provider 를 부르지도 않는다(테스트가 그 호출 여부까지 단언한다).
- **모델과 배선을 따로 검증했다.** `bun test` 가 우선순위·범위·캐시를 덮고, 브라우저 검사가
  **실제 mousemove/click** 으로 커서 모양과 `activate` 호출을 본다 — F4b 에서 "모델만 통과하고
  화면에는 안 나타나던" 일을 겪은 뒤라 두 층을 함께 뒀다.

- **F8: 캔버스가 접근성의 근본 문제였다.** 픽셀뿐이라 보조기술에게는 빈 요소다. 캔버스를
  트리에서 빼고 **이미 포커스를 받는 textarea 를 앵커로** 삼았다 — 새 요소를 만들 필요가 없었다.
  기본 ARIA 는 비용이 0 이라 항상 켜고, 라이브 리전은 옵션이다(프레임마다 텍스트 비교).
- **바뀐 줄만 읽힌다.** 화면 전체를 읽으면 출력 하나마다 24 줄을 듣게 된다 — 훼손 테스트로
  그 차이를 못 박았다(전체를 읽게 하면 2건 실패).
- **터치는 브라우저 에뮬레이션에 기대지 않는다.** 합성 `mousedown` 은 **드래그를 선택으로
  오해한다** — 손가락으로 밀면 스크롤을 기대한다. 직접 다루고 합성 이벤트는 막는다.
  뜻은 셋(탭·세로 드래그·길게 누르기)이고 두 손가락은 브라우저에 맡긴다.
- **테스트가 정상 코드를 실패로 만든 적이 있다.** "떨림은 탭으로 본다" 검사가 `check` 만
  추가되고 **evaluate 안의 측정 코드와 반환 필드가 빠져** undefined 를 비교하고 있었다.
  코드는 멀쩡했다 — 실패를 보면 **구현부터 의심하기 전에 검사 자체가 옳은지** 봐야 한다.
- **실기기 검증은 여전히 남는다.** 합성 터치 이벤트로 경로는 덮었지만, 실제 손가락의 좌표
  정밀도·소프트 키보드가 화면을 밀 때의 리사이즈·관성 스크롤은 기기에서만 볼 수 있다.

- **데모에 IME 회귀 둘이 있었다.** 계약이 바뀌었는데 데모가 안 따라온 것이다.
  1. **조합 글자가 두 번 보였다**(`한글한글`). [#2567](https://github.com/ohah/maru/pull/2567) 에서
     "오버레이는 항상 라이브러리가 그린다" 로 바꿨는데, 데모가 옛 주석("구독하면 라이브러리는
     화면에 넣지 않는다") 그대로 조합을 자기 줄에 끼워 넣고 있었다.
  2. **조합 중 `Cmd+←` 가 글자를 뒤집었다**(`무` + 조합 `야` → `야무`). 확정 글자는 `key()` 로
     **코어(워커)를 거쳐** 나오고 바인딩은 `sendText` 로 **메인에서 곧바로** 나가 순서가 갈린다.
     `setTimeout` 으로 미뤄도 워커 왕복이 더 느려 소용없다 — **조합 중 `Cmd` 는 확정에만 쓰고
     키는 버린다**(계약 §5). 네이티브 앱들도 그렇다.
- **`sendText` 가 코어를 거치지 않는 것이 순서 문제의 뿌리다.** 계약 §5 가 그렇게 정한 이유는
  "에코는 호스트 몫" 이라 코어가 할 일이 없어서인데, 그 대가로 **같은 keydown 에서 나온 두
  바이트가 다른 지연을 갖는다.** 지금은 조합 중 바인딩을 버려 피했지만, 비슷한 조합이 또
  나오면 `sendText` 를 백엔드 큐에 태우는 쪽을 다시 봐야 한다.

- **적대적 검증이 내 수정의 과잉을 잡았다.** 조합 중 `Cmd` 조합을 통째로 삼키게 했더니
  **⌘A·⌘C 와 `customKeyHandler` 까지 막혔다**(계약 §7 이 "앱이 먼저 본다" 고 약속한 것을
  어긴다). 순서 문제는 **바이트를 보내는 경로**(`sendText`)에서만 생기므로 거기서만 멈춘다 —
  선택·복사·폰트 크기·앱 단축키는 바이트를 안 보내 순서와 무관하다.
- **`themeKey` 를 참조 비교로 바꾸며 동작이 하나 달라졌다.** 이제 **테마 객체를 제자리에서
  고치면 반영되지 않는다**(`buildPalette` 가 값을 복사하므로 재구축이 필요하다). 매 프레임
  256 개 문자열을 잇는 낭비를 없애는 대가이고, "새 객체를 넘긴다" 는 흔한 규약이라 받아들였다 —
  계약 §5 에 적었다.
- **재마운트에서 구독이 중복되지 않는 것을 확인했다**(워커 모드 3회 전환 × `onClipboardWrite`
  호출 수 1,1,1).

- **F4b 가 무한 렌더 루프를 만들었다 — 사용자가 "테마를 바꾸면 느려진다" 로 발견했다.**
  `#pushDecorations` 가 매 프레임 장식을 워커로 보냈고, 워커는 받으면 다시 그렸으며, 그 프레임이
  또 여기로 왔다. **장식이 하나도 없어도 빈 배열이 오갔다.** 실측: 유휴 상태에서 초당 1638
  프레임, Performance 녹화에서 `HandlePostMessage` 4882 건 / 2792 ms(GPU 는 178 ms 로 작았다).
  - **테마는 원인이 아니라 방아쇠였다** — 프레임이 늘어 루프가 가속됐다. 테마 변경 시간만
    재느라 두 번 헛짚었고(`themeKey` join, 글리프 캐시), **유휴 상태 프레임 수**를 세는 것이
    정답이었다. 녹화 하나가 그것을 알려줬다.
  - **방어는 양쪽에 둔다.** 보내는 쪽이 바뀐 것만 보내고, 받는 쪽도 같은 내용이면 다시 그리지
    않는다 — 한 겹이 뚫려도 루프가 되지 않는 것을 훼손 테스트로 확인했다(메인 필터를 없애도
    유휴 6프레임). 장식을 아예 안 쓰면 `spansFor` 순회도 건너뛴다.
  - **회귀는 "유휴 상태에서 계속 그리지 않는다"** 로 못 박았다(1.5초에 20프레임 미만). 원래
    결함을 되살리면 7693 프레임으로 실패한다.

## 선행 조건

P1은 [터미널 코어의 wasm 이식성](../wasm-portability.md)이 규정한 제약 위에서만 성립한다 — 특히 `addLibrary`가 아니라 `addExecutable` + `entry = .disabled` + `rdynamic`을 써야 하고(§5 재현법), `max_memory`를 명시해야 한다(§5.2).

프로토타입은 저장소 밖(세션 scratchpad)에 있으므로 P1·P3·P4는 그 코드를 **이식**하는 작업이지 새로 쓰는 작업이 아니다. 이식 대상은 wasm export 47개, Canvas 렌더러, IME·선택·스크롤백·readline 편집, 테마 파서다.
