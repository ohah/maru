# 모바일 플랫폼 구현 계획

계약은 [모바일 플랫폼](../mobile-platform.md)이 소유한다. 이 문서는 **진행**만 소유한다.

## 배경

PoC 로 "Zig 코어 + 네이티브 GPU 가 iOS/Android 에서 서는가" 를 실측했고 답은 예다
([측정 기록](../../tools/mobile-poc/README.md)). 그 과정에서 **바꿔야 할 것 둘**이 드러났다.

- quad 하나당 draw call 하나 — 모바일 타일 기반 GPU 에 특히 비싸다. 148 quad 는 괜찮지만
  80×40 터미널은 3200 draw call 이 된다.
- `NativeActivity` 는 IME 를 못 받는다 — 한글 조합이 필수라 `GameActivity` 여야 한다.

성능 예산.


## M0 — 폴더 구조

PoC 는 `tools/mobile-poc/` 에 앱 전체를 담고 있었다. 제품 코드는 `src/platform/` 으로 옮기고,
`tools/mobile-poc/` 는 **측정 하네스**로 남긴다(빌드 스크립트 + 측정 기록). 코드를 양쪽에 두지
않는다 — `run.sh` 가 `src/platform/` 을 빌드한다.

## M1 — 배칭

각 quad 를 push constant + `vkCmdDraw`/`drawPrimitives` 로 그리던 것을, **quad 배열을
버퍼에 한 번 올리고 인스턴스 드로우 한 번**으로 바꾼다. 셰이더는 push constant 대신 버퍼를
읽는다(Metal `[[instance_id]]`, Vulkan `gl_InstanceIndex`).

판정: 프레임당 draw call 수를 로그로 낸다. 148 quad 에서 **1** 이어야 한다.
실측: 두 플랫폼 모두 `MARU_DRAW calls=1 instances=148`, 화면은 이전과 동일.

Metal 은 `setVertexBytes:` 가 4KB 한계라 148 quad(9.5KB)도 못 실어 `MTLBuffer` 가 필요했다.
Vulkan 은 push constant 를 통째로 버리고 storage buffer + `gl_InstanceIndex` 로 갔다 —
quad 마다 다른 값을 한 번의 draw call 에 실을 수 없기 때문이다. 그 결과 **프래그먼트가
push constant 를 못 읽게 되어** 색·radius·kind 를 varying 으로 넘긴다.

**CI 에는 붙이지 않는다(사용자 결정).** 모바일 빌드는 Xcode·NDK·에뮬레이터가 필요해
러너 비용이 크고, 지금 단계에서 막아야 할 회귀가 없다. 검증은 로컬에서 `run.sh` 로 한다 —
필요해지면 그때 넣는다.

## M1.5 — build.zig

제품 코드를 셸 스크립트가 빌드하는 것은 정식 도입이 아니다. `build.zig` 가 모바일 타깃을
소유하고, `tools/mobile-poc/run.sh` 는 **기기 조작**(설치·실행·캡쳐·계측)만 남긴다.

```sh
zig build mobile-libs -Doptimize=ReleaseSafe   # 세 타깃 전부
zig build mobile-lib-ios-sim | mobile-lib-ios | mobile-lib-android
```

**Debug 는 iOS 에서 링크가 깨진다** — std 의 스택 트레이스가 시뮬레이터 SDK 에 없는
`_dyld_get_image_header_containing_address` 를 참조한다. `simple_panic` 이 ReleaseSafe 에서
그 경로를 걷어내고 **안전 검사는 그대로 산다**(PoC 때 기록한 내용이 그대로 확인됐다).

**대체된 초기 하네스는 지웠다.** `chrome-ios`/`chrome-android-app` 이 `ios`·`ios-app`·
`android`·`chrome-android` 가 하던 일을 포함한다 — 남겨 두면 어느 쪽이 진짜인지 흐려진다.
측정 **결과**(표·스크린샷)는 전부 남는다. 여섯 기능 판정기(`features-*`)는 다른 모드가
대체하지 않는 별도 측정이라 남긴다.

## M2 — Android IME (자체 Java shim)

**`GameActivity` 를 시도했다가 되돌렸다.** 코드 이관과 빌드까지 통과했지만 실행에서
`ClassNotFoundException: androidx.appcompat.app.AppCompatActivity` 로 죽었다 — `GameActivity`
가 전 버전에서 `AppCompatActivity` 를 상속해 AndroidX 20여 개와 리소스 컴파일이 필요하고,
그건 Gradle 없이 손으로 조립할 수 없다. 계획할 때 못 본 비용이라 결정을 다시 했다
(근거는 [계약 §1](../mobile-platform.md#1-확정-결정)).

`NativeActivity` 를 유지하고 IME 만 자체 shim 으로 받는다.

```text
MaruActivity(NativeActivity)   투명 입력 View 를 얹고 소프트 키보드를 띄운다
  └ MaruInputView              onCheckIsTextEditor()=true → IME 가 입력 대상으로 인정
      └ MaruInputConn          setComposingText/commitText 를 JNI 로 넘긴다
```

### 검증된 것과 안 된 것

| | 상태 |
|---|---|
| shim 이 입력 대상으로 인정됨 | **OK** — 소프트 키보드가 뜬다 |
| `commitText` → 코어 | **OK** — 키를 눌러 `commit="a"` 도달 |
| preedit 렌더(커서 자리에 흐리게) | **OK** — 주입해서 확인 |
| IME 조합 → preedit 왕복 | **미검증**(아래) |

**조합을 실제로 흘려 보지 못했다.** 이 에뮬레이터에는 Gboard(LatinIME)뿐이고 한글 IME 가
없다. 영어 Gboard 는 이 입력 타입에서 `setComposingText` 없이 바로 `commitText` 를 부른다.
그래서 "IME 가 만든 조합 문자열이 preedit 으로 그려진다" 는 왕복은 **한글 키보드가 있는
기기에서 손으로 확인해야 한다**.

실측으로 잡은 것들:

  - `adb shell input text` 는 **IME 를 우회**한다(키 이벤트 주입). IME 경로 검증에 못 쓴다.
  - `BaseInputConnection(view, false)` 면 IME 가 "편집기가 아니다" 로 보고 조합 없이 바로
    확정한다 — `true` 여야 한다.
  - `NativeActivity` 는 `android.app.lib_name` 의 .so 를 **클래스로더 밖에서 dlopen** 한다.
    Java 쪽 `System.loadLibrary` 를 한 번 더 해야 JNI 이름 해석이 된다.
  - `d8` 8.2.2 가 **익명 내부 클래스에서 내부 오류로 죽는다**. 이름 있는 중첩 클래스만 쓴다.

## M3 — 원격 연결

**두 플랫폼 다 원격 전용이다**(사용자 확정). 로컬 PTY 를 안 둔다.

그런데 지금 컨트롤 플레인은 **명시적으로 로컬 전용**이다 — "wire 는 TCP/HTTP 를 바인드하지
않는다", 보안은 "같은 uid 안의 신뢰 차등"(peer-cred + 0700/0600). **peer-cred 는 기계를
넘으면 존재하지 않는다.** 그래서 M3 는 클라이언트를 붙이는 일이 아니라 **계약을 넓히는
일**이고, M3a(문서)가 먼저다.

정해야 할 것:

  - **전송**: 무엇을 타고 가는가(SSH 터널 · Tailscale 같은 mesh VPN · 자체 릴레이 ·
    Cloudflare Tunnel). 각각 비용·계정·인바운드 포트 요구가 다르다.
  - **인증**: peer-cred 를 대신할 것. 기기 페어링? 토큰? 공개키?
  - **암호화**: 전송이 이미 암호화하는가, 아니면 우리가 종단간으로 하는가.
  - **신뢰 등급**: 원격 클라이언트가 `browser.*` 같은 write 능력을 갖는가.
  - **코어가 만든 답을 어디로 흘리는가**: 지금은 `response_dropped` 로 버린다. 원격 쪽이
    정해질 때 `maru_mobile_take_response` 류 ABI 를 함께 낸다(지금 뚫으면 소비처 없는
    인터페이스가 된다).

한 가지는 이미 실측했다 — `session_host` 클라이언트(23k줄)가 **iOS 타깃으로 그대로
컴파일된다**. 코어 쪽은 이식 가능하고, 막는 것은 전송·인증 계약뿐이다.

## 코드 리뷰 후속 (M2 뒤)

`/code-review high` 가 13건을 냈고 **상위 여섯이 제품 경로 결함**이었다. 10라운드 적대적
검증이 문서·구조 정합성에 치우쳐 **오래 돌 때 생기는 것**을 못 봤다 — 시뮬레이터에서 몇 초
띄워 스크린샷만 확인했으니 512바이트도, 재개 후 글리프 손실도 드러날 수가 없었다.

| 결함 | 상태 | 검증 |
|---|---|---|
| 입력이 512바이트에서 영구히 죽음 | 수정 | **재현→해소**(`total=512` 고정 → `total=1995`) |
| 아틀라스 여유 슬롯 15개 | 수정 | **재현→해소**(성장 27자, 384x1024) |
| 미스 목록 swap-remove 로 절반 건너뜀 | 수정 | 배치당 8·6자로 늘어남 |
| 재개 후 성장 글리프 소실 | 수정 | 원본 버퍼에도 기록(경로 검증은 미실시) |
| 제품이 `/data/local/tmp` 의존 | 수정 | **tmp 를 비우고 정상 기동 확인** |
| 단폭 셀 종횡비 | 수정 | 화면 대조 |
| teardown 이 자식을 안 지움 | 수정 | 코드 검토(누수 계측 미실시) |
| 스왑체인 재생성 없음 | 수정 | **재현 불가**(아래) |
| `chor_started` 잔존 · 100% CPU 스핀 | 수정 | 코드 검토 |
| quad 버퍼 넘침이 조용함 | 수정 | `last_error` 로 노출 |
| 미리 굽는 글자 집합 중복 | 수정 | 헤더 단일 출처 |
| push 전용 job 의 무의미한 draft 가드 | 수정 | — |

**스왑체인 재생성은 이 환경에서 재현하지 못했다.** `wm size` 로 표시 해상도를 바꿔도
`vkAcquireNextImageKHR` 이 계속 `VK_SUCCESS` 를 돌려주고, `vulkan_recreated`·새 `logical=`
로그가 하나도 안 나오는데 화면은 새 크기로 맞아 보인다 — **SurfaceFlinger 가 낡은 버퍼를
늘려 준 것**이다(그 둘이 동시에 참인 다른 설명이 없다). 액티비티가 portrait 고정이라
`wm size` 는 앱 surface 를 리사이즈하지 않고 디스플레이만 바꾼다.

그래서 두 겹으로 고쳤다: (1) `OUT_OF_DATE`/`SUBOPTIMAL` 을 받으면 다시 만든다(스펙 경로),
(2) **매 프레임 창 크기를 직접 비교**한다 — 드라이버가 안 알려 줘도 잡히도록. 실기기에서
회전으로 확인해야 한다.

### 페이싱 정책화 뒤 적대적 검증

**choreographer 체인이 배경↔복귀마다 늘어났다.** teardown 이 `g` 를 memset 해 소유 플래그가
지워지고, 재개할 때 새 체인을 거는데 **이미 떠 있던 체인은 스스로 다시 등록하며 살아남는다**.

계측이 그대로 판정자가 됐다 — 체인이 늘면 `drawFrame` 이 더 자주 불려 median 이 짧아진다.

| 왕복 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1~2회 | 33.4 ms | 33.5 ms |
| 3~4회 | **16.7 ms**(주기 두 배) | 33.3 ms |

플래그를 `g` 밖으로 뺐다 — 체인은 앱 수명 동안 하나면 되고, 창이 없을 때는 `drawFrame` 이
알아서 쉰다.

### 리뷰 수정 뒤 적대적 검증

**내 수정이 결함을 하나 다시 만들었다.** 미스 목록을 스냅샷하려고 host 마다 `want[64]` 를
뒀는데, 그 `64` 는 Zig 의 `miss_cp` 크기와 같아야 하는 값이라 **5라운드에서 고친 셀 기하
중복과 같은 종류**였다. 스냅샷을 버리고 **역순 훑기**로 바꿨다 — 지워지는 자리가 항상
훑은 뒤쪽이라 앞쪽이 흔들리지 않고, host 가 목록 크기를 알 필요가 없어진다.

**오래 돌 때를 실제로 쟀다**(지난 검증이 빠뜨린 축).

| 확인 | 결과 |
|---|---|
| 배경↔복귀 8회 PSS | 62077 → 62069 KB (평평 — teardown 누수 없음) |
| 왕복 뒤 렌더 재개 | `quads=148` 재출력 |
| 아틀라스 성장 반복 | 배치마다 2~7자, 멈추지 않음 |
| 512바이트 넘는 입력 | `total=1995` 까지 전달 |

### 오래 사는 상태를 겨눈 적대적 검증

지난 라운드들은 **한 프레임**을 봤다. 이번에는 "여러 번 반복하면" 을 겨눴고, 그 축에서만
다섯 건이 나왔다. 셋은 실제로 앱을 죽이거나 화면을 지웠다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| 코어가 512KB 고정 버퍼 위에 서 있어 **resize 7번**이면 OOM | 헤드리스로 셈(`7번째 resize 에서 OutOfMemory`) | 수정 |
| resize 실패해도 크기 기록을 덮어 **없는 셀을 읽음** | 테스트에서 재현(`index 1320, len 1320`) | 수정 |
| staging 버퍼를 안 지운 채 device 파괴 → **SIGSEGV** | 창 크기 9회 변경으로 앱 사망, 툼스톤 `on_vkDestroyDevice_pre` | 수정 |
| 입력의 실패가 다음 build 의 `memset` 에 지워짐 | 코드 검토(§5 가 약속한 경로에서만 신호가 안 남음) | 수정 |
| Android 입력은 UI 스레드, 렌더는 native 스레드 — **동기화 없음** | logcat tid 대조(14832 vs 14850) | 수정 |

세 번째가 제일 컸다. 리뷰 때 "teardown 이 자식을 안 지움" 을 **코드 검토만으로** 닫았는데,
그때 본 것은 `teardownVulkan` 안이었고 진짜로 남는 자식은 **업로드 함수 안**에 있었다.
같은 표를 다시 보니 "누수 계측 미실시" 라고 내가 적어 뒀다 — 그 자리가 정확히 터졌다.

수정 뒤 같은 시나리오를 20회로 늘려 다시 돌렸다: **재생성 21회, 오류 0, 크래시 0**, 이후에도
`quads=148 / calls=1` 로 계속 그린다.

이 다섯 중 넷은 `tests/mobile_bridge_contract.zig` 로 내려 `zig build test` 에서 돈다(브리지가
OS 를 안 부르므로 시뮬레이터가 필요 없다). **옛 코드에서 실제로 깨지는 것까지 확인**했다 —
안 그러면 회귀 테스트가 아니다.

### 용량 한계를 겨눈 적대적 검증

앞 라운드가 "오래 돌면" 이었다면 이번은 **"꽉 차면"** 이다. 셋이 나왔고, 그중 둘은 서로 물려
있었다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| quad 버퍼 2048 — 태블릿 크기에서 **격자만으로 넘침**(폰 세로도 1828/2048) | 헤드리스로 네 크기 측정 | 수정 |
| Android 는 4096 에서 **조용히 자름**, iOS 는 늘림 — 상한이 서로 다름 | 두 host 코드 대조 | 수정 |
| 새로 넣은 뮤텍스가 **아틀라스 굽기(GPU 대기)까지** 감쌈 → 타이핑이 GPU 를 기다림 | 잠금 구간 재검토 | 수정 |

둘째가 이번 라운드의 교훈이다. **첫째를 고치자 둘째가 live 가 됐다** — 버퍼 상한을 2048 에서
12768 로 올리는 순간 Android 의 4096 이 실제로 자르는 값이 된다. 상한을 host 마다 적어 두는
구조 자체가 원인이라, 값을 옮기는 대신 **코어가 답하게** 했다(`maru_mobile_max_quads`).

의심 하나는 측정으로 닫았다. 아틀라스 조회가 셀마다 선형 탐색이라 큰 격자에서 비쌀 줄
알았는데, 꽉 찬 화면의 build 가 **0.04ms(폰) / 0.10ms(태블릿, 등록부 495개)** 였다 — 30Hz
예산 33.3ms 대비 무시할 수준이다. 자료구조를 바꿀 이유가 없다.

### "누가 치우는가" 를 겨눈 적대적 검증

앞 두 라운드가 "오래 돌면"·"꽉 차면" 이었다면 이번은 **"코어가 만든 것을 누가 가져가는가"**
와 **"계약 문구가 실제로 참인가"** 다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| 코어가 만든 답(DA·DSR)을 **아무도 안 치움** — 질의 3000번에 15005바이트 | 데스크톱 소비처 grep → 모바일에 없음, 누적량 실측 | 수정 |
| `maru_mobile_input` 반환값이 **닿지도 않은 바이트를 셈** | 헤더 문구와 코드 대조 | 수정 |
| 조합 중 문자열이 셀 **밑에** 깔림(주석은 "위" 라고 적혀 있었다) | 그리는 순서 확인 | 수정 |
| 지난 라운드에 넣은 drift 로그가 매 프레임 도배 가능 | 내 코드 재검토 | 수정 |

첫째가 이번의 본체다. 데스크톱에는 `pendingResponse` 를 PTY 로 흘리고 `clearResponse` 하는
자리가 두 군데 있는데(`runtime.zig`·`pty_reader.zig`), 모바일에는 **그 자리 자체가 없었다**.
오늘도 ESC 를 누르고 `[c` 를 치면 닿는 경로이고, 원격 세션이 붙으면 셸이 알아서 질의한다.
흘려보낼 곳이 없는 지금은 버리는 게 맞지만, **조용히** 버리면 §5 를 어긴다.

`maru_mobile_take_response` 같은 ABI 를 지금 뚫는 것은 **소비처 없는 인터페이스**가 되므로
하지 않았다 — M3 에서 원격 쪽을 정할 때 함께 낸다.

### 코어 API 전수 대조 (데스크톱 ↔ 모바일)

지난 세 라운드의 결함이 전부 같은 자리에서 나왔다 — **데스크톱이 이미 하는 일을 모바일이
안 하는 곳**. 그래서 짐작하지 말고 `TerminalCore` 의 공개 API 109개를 전수로 갈랐다:
데스크톱(`src/app`·`src/platform/macos`·`src/chrome`)은 부르는데 모바일은 안 부르는 것이
**76개**.

대부분은 이름 충돌(`eql`·`hash`·`push`)이거나 아직 안 만든 기능이라, 두 부류로 다시 갈랐다.

**(가) 코어가 만드는데 가져갈 사람이 없는 것** — 지난 라운드 `pendingResponse` 와 같은 부류.
짐작 대신 **실제로 쌓이는지 쟀다**.

| 생산자 | 안 치우면 | 판정 |
|---|---|---|
| `pendingResponse` | 질의 3000번에 15005바이트, 무한 | **수정**(지난 라운드) |
| `shellEvents` | 상한 4096 에 닿고 **그 뒤 전부 드롭 + overflow 영구** — 프롬프트 사이클 2000회면 닿는다 | **수정** |
| `pendingClipboardWrite` | 1000번 써도 5바이트(덮어쓴다) | 유계 |
| `pendingNotification` | 슬롯 하나(최신만) | 유계 |
| `bellPending`·`clipboardReadPending` | bool | 유계 |
| 스크롤백 | 기본 상한 1000행에서 평평(2만 줄 먹여도 1000) | 유계 |

`shellEvents` 는 코어 주석이 **"프레임마다 drain 되면 닿을 일이 없다"** 고 전제하는 자리다.
모바일은 안 했다. 메모리는 유계지만 소비자(에이전트 상태·프롬프트 표시)가 생겼을 때 낡은
4096건과 선 채로 굳은 overflow 를 물려받는 함정이라, 쓰는 자리에서 함께 비운다.

덤으로 **모바일 코어의 메모리 평형점**을 얻었다: 80x24 격자 + 스크롤백 1000행에서 약
1.35MB(할당 바이트 실측, 평평해진 뒤).

**(나) 계획에 없던 기능 공백.** 나머지는 대부분 M4b·M9~M16 이 이미 안고 있었지만 둘이 빠져
있었다.

  - **키가 `core.encodeKey` 를 안 탄다.** 모바일은 `\r`·`0x7F`·`\t`·`\x1B` 를 손으로 적어
    넣는다. 데스크톱은 모든 키를 인코더에 태워 DECCKM(커서키 모드)·수정자(Ctrl·Alt)·kitty
    프로토콜·Option-as-Meta 를 처리한다. 계획에는 "보조 키바" 만 있어서, **키바를 만들어도
    바이트를 직접 적으면 인코딩이 틀린다**. 키바는 UI 고, 그 앞에 키 이벤트 ABI 가 필요하다.
  - **포커스 보고(DEC 1004)가 없다.** 데스크톱은 포커스 변화를 CSI I/O 로 흘린다(vim 의
    FocusGained/Lost). 모바일은 배경↔복귀가 데스크톱보다 훨씬 잦은데 아무것도 안 보낸다.

둘 다 M4b 앞에 놓는다 — 키 인코딩은 키바의 **선행 조건**이다.

### chrome/renderer · config 전수 대조

코어 API 대조가 값을 했으므로 같은 방식을 chrome/renderer 모듈(45개)과 config 키(93개)에
돌렸다. **가장 큰 것이 나왔다** — 모바일은 maru 의 합성 글리프 경로를 아예 안 탄다.

**합성 글리프.** `renderer.synthesizeGlyph` 는 "rasterizer 는 폰트 경로 **전에** 이걸 한 번
호출한다" 가 계약인 dispatch 단일 출처다. 박스 드로잉(U+2500~257F)·블록(U+2580~259F)·
브라유(U+2800~28FF)·파워라인(U+E0B0~)·legacy mosaic 을 **폰트 대신 절차 합성**해 셀에 꽉
채운다("폰트 글리프는 셀에 안 맞아 gap·흐림·끊김"). 두 모바일 host 는 그냥 폰트로 굽는다.

데모 대본에 TUI 한 줄을 넣어 화면으로 확인했다(`tools/mobile-poc/out/synth-before-android.png`):
박스가 **끊기고**, 블록에 **이음매**가 보이고, 브라유가 어긋난다. 계약 주석이 예고한 그대로다.

**그런데 호출만 추가해서는 못 고친다.** 모바일의 글리프 기하가 격자와 안 맞기 때문이다:

| | 값(논리 px) |
|---|---|
| 격자 한 칸 | **5 × 22** (열 간격 `cw/2`, `line_h = font_px + 7`) |
| 그리는 quad | **11 × 15** (`w = cw`, `h = font_px`) |
| 아틀라스 셀 | 24 × 32 (셰이더가 이 전체를 quad 에 매핑) |

폰트 글리프는 잉크가 셀 안쪽에 앉아 이 어긋남이 안 보인다. 합성 글리프는 **셀을 가장자리까지
채우는 것이 목적**이라 곧바로 드러난다 — 블록(█)은 세로로 7px 뜨고 가로로 6px 겹친다.
즉 **기하 정합이 합성의 선행 조건**이다. M4a3 으로 세운다.

**셀 속성.** terminfo 축으로도 봤다. `xterm-maru` 는 truecolor(`Tc`)·Sync 를 광고하는데,
모바일은 원격 전용이라 `TERM` 을 스스로 정하지 않는다 — 원격 PC 의 maru 세션이 이미 그 값으로
셸을 띄우므로 모바일이 terminfo 를 들고 갈 일은 없다. **문제는 그 광고를 렌더가 뒷받침하는가**
쪽이었다: 코어가 담는 셀 속성 12개 중 모바일은 `foreground` 하나만 읽는다. 대본에 SGR 한 줄을
넣어 화면으로 확인했다 — `bg`·`rev`·`under`·`bold` 가 전부 똑같은 평범한 글자다. 배경색은
상태줄·선택·`ls` 색이 전부 쓰는 것이라 M4a4 로 세운다.

**config.** 모바일이 config 를 안 읽는 것은 이미 계약 §7 에 있다. 대조로 새로 나온 것은
**같은 값이 여러 곳에 흩어져 있다**는 쪽이었다: 굽는 글자 크기 22 가 네 곳(iOS 2·Android 2)에
따로 적혀 있었다. 셀 크기는 헤더가 소유하는데 **그 셀을 채우는 크기**는 아니었다 — 한쪽만
고치면 두 플랫폼이 다른 굵기로 구워 픽셀 대조가 조용히 무의미해진다. `MARU_ATLAS_TEXT_PX`
로 올렸다.

나머지 모듈 공백은 대부분 이미 계획이 안고 있다(`state`·`input`·`interaction`·`intent_table`
→ M4a·M12, `scroll_area` → M4b, `typography`·`text_layout` → 아래 참고). 하나만 짚어 둔다:
모바일은 텍스트 배치를 `pushText` 로 직접 한다 — chrome 텍스트는 `appendEllipsizedTitle`
경유가 계약인데(cluster 모델) 그 경로를 안 탄다. chrome 라벨이 길어지면 말줄임이 없다.

### M2b 한글 IME — 여기서 멈춘 이유

`UITextInput` 까지는 넣었다(일본어·중국어 marked text 경로는 그것으로 선다). 한글만 남았고,
남은 일이 **휴리스틱 판단**이라 사용자 결정 전에는 안 넣는다.

확인된 사실: iOS 한글은 `setMarkedText` 를 안 쓰고 `deleteBackward`+`insertText` 로 마지막
음절을 갈아 끼운다. 우리가 `UITextInput` 을 구현하고 UIKit 이 그것을 쓰는 것까지 확인한
뒤에도 그렇다(`MARU_IME protocol=UITextInput` 이 찍히는데 조합은 안 온다). 같은 동작이
다른 iOS 프로젝트에서도 보고돼 있다(동작 비교만 참조 — 구현은 안 봤다).

남은 선택은 둘이고, 어느 쪽도 공짜가 아니다:

| 방식 | 장점 | 위험 |
|---|---|---|
| 패턴 기반(직전 insert 와 길이가 같은 backspace) | 언어 분기 없음 | **방금 친 글자를 backspace 로 지우는** 흔한 동작과 구분 불가 |
| 한글 범위 기반(자모·음절일 때만) | 오탐 없음 | 언어 특정 분기가 계약에 들어간다 |

**Android 는 별개로 여전히 미검증이다** — 에뮬레이터 Gboard 에 한국어 언어팩이 없고 받을
경로도 없다(Play 스토어 없는 이미지). 실기기 항목이다.

### M4a4 셀 속성 렌더 (완료)

코어가 셀에 담는 속성 12개 중 **전경색 하나만** 읽던 것을 전부 푼다. 규칙은 데스크톱과 같은
것을 쓴다(reverse 는 default 를 테마 값으로 푼 뒤 맞바꾸고, dim 은 배경 쪽으로 절반 보간,
conceal 은 전경을 배경색으로).

**굵게·기울임은 아틀라스 키를 바꿔야 했다.** 같은 글자라도 다른 글리프라 슬롯이 따로 있어야
한다 — 키가 코드포인트뿐이면 굵은 판이 보통 판을 덮어써서 **한 줄이 굵어지는 순간 그 글자가
화면 전체에서 굵어진다**. 등록부 키를 코드포인트+스타일로 바꾸고, ABI 도 그에 맞춰
넓혔다(`atlas_add` 에 style, `missing_style` 추가). 가짜 굵게 대신 **번들 폰트 네 판**을
쓴다 — 가짜는 advance 가 달라져 자간이 어긋난다.

**quad 예산이 함께 바뀌었다.** 한 칸이 최대 6 quad(배경·밑줄·이중밑줄·취소선·윗줄·글자)를
내므로 최대 격자에 곱하면 3.5MB 다. 정적으로 잡는 대신 **격자를 따라 자라게** 했다 — 폰의
실제 최악은 3577 개였고(실측), 자라는 시점은 리사이즈뿐이라 플랫폼이 GPU 자원을 다시 세우는
순간과 겹친다. 배경·장식선은 같은 색이 이어지는 구간을 하나로 묶어 그린다(안 묶으면 80x24
에서 배경만 1920 개다).

| 확인 | 결과 |
|---|---|
| 두 플랫폼 화면 | **12개 전부** 눈으로 확인 — 배경(44)·반전(7)·밑줄(4)·굵게(1)·흐림(2)·기울임(3)·이중밑줄(21)·취소선(9)·윗줄(53)·밑줄색(58, 빨강)·숨김(8, 안 보임). 밑줄은 그 구간에만 걸린다 |
| 밑줄 자리 | **처음엔 틀렸다** — 칸 높이(22) 기준으로 잡아 글자 상자(15)에서 5 논리 px 떨어져 줄 사이에 떴다(픽셀 실측). 글자 상자 기준으로 옮겨 붙였다 |
| quad 버퍼 성장 | 기기에서 **두 단계 실측**: `n=1542 cap=1536` → 재생성 → `n=3076 cap=3072` → 재생성 → `quads=3082 calls=1` 로 온전히 그림 |
| 최악 quad(칸마다 색·장식이 다름) | 폰 3577 / 태블릿 12615 — 상한이 그만큼 따라 늘어 안 잘림 |
| 계약 테스트 | 8개(굵기가 다르면 다른 슬롯을 쓴다 포함) |

**여기서 오래 헤맸고, 원인은 내 결함이었다.** Android 를 돌리려 할 때마다 에뮬레이터가
사라져서 "표준 포트 대신 임의 IPv6 포트에 바인딩하는 환경 문제" 로 진단했다. 틀렸다.
에뮬레이터 로그의 마지막 줄이 답이었다:

```
Assertion failed: (pCreateInfo->size > 0), function vk_buffer_init
```

quad 버퍼를 동적 성장으로 바꾸면서 `maru_mobile_max_quads()` 가 **첫 build 전에 0** 을
돌려줬고, Android 는 창이 서는 순간(=build 보다 먼저) 그 값으로 GPU 버퍼를 잡는다. 크기 0
짜리 `VkBuffer` 가 드라이버 단언에 걸려 **에뮬레이터를 통째로 abort** 시켰다. iOS 는 매 프레임
용량을 다시 보므로 첫 프레임에 0 이어도 살아남아, **한쪽만 죽는 비대칭**이 원인을 가렸다.

거기에 두 번째 함정이 겹쳤다 — abort 가 크래시 기록을 남기면 다음 기동에서 에뮬레이터가
**동의 대화상자를 띄운 채 멈춘다**(로그: `Showing crashdialog to get consent`). 그래서 "부팅이
안 된다" 로 보였다. 기록을 지우고 `-no-metrics` 로 띄우면 정상 부팅한다.

교훈은 로그를 끝까지 읽는 것이었다. `adb devices` 가 비어 있는 것만 보고 환경을 의심하는
동안, 답은 에뮬레이터 로그 마지막 줄에 그대로 있었다. `maru_mobile_max_quads() > 0` 은
이제 계약 테스트가 지킨다.

## 기획 공백 (M9~M12, M2b, M3c)

PoC 는 "되는가" 에 답했고 지금 계획은 **PoC 가 드러낸 것**만 담고 있었다. 제품이 되려면
필요한데 아직 아무 데도 없던 것들을 넣는다. **둘은 새 결정이 아니라 이행 누락이다** —
데스크톱이 이미 계약으로 정해 둔 것을 모바일이 안 따른다.

### M9 접근성 (이행 누락)

[chrome 상호작용 이관](../chrome-interaction-migration.md)이 정한 계약: interactive node 가
**semantic descriptor** 를 내고 플랫폼 어댑터가 그것을 네이티브 접근성 요소로 투영한다.
**모바일은 그 어댑터가 없다** — GPU 로 그린 quad 뿐이라 VoiceOver·TalkBack 에게는 빈 화면이다.

GPU 로 UI 를 그리는 선택의 대가라 나중에 붙이기 비싸다. 지금 계약이 이미 있으므로 iOS 는
`UIAccessibilityElement`, Android 는 `AccessibilityNodeInfo` 로 같은 descriptor 를 투영하면 된다.

### M10 모바일 config 스키마

[설정](../configuration.md)이 config 계약의 단일 출처인데 **모바일은 config 를 아예 안 읽는다**
(`mobile_bridge.zig` 의 `themeColors()` 가 값을 고정한다). 폰트 크기 하나 못 바꾸는 상태다.

**어디서 오는지는 정해졌다(사용자 확정, 계약 §1): 모바일 config 는 데스크톱과 따로다.**
파일도 스키마도 공유하지 않고, 원격 세션에 붙어도 PC 의 config 를 끌어오지 않는다. 공유하는
것은 값이 아니라 기계다 — `src/config` 의 파서·resolve 규율·"파일이 단일 출처" 원칙은
그대로 쓰고 스키마와 파일 위치만 모바일 것으로 둔다.

그래서 M10 의 일은 "어디서 받을까" 가 아니라 **모바일 스키마를 짜는 것**이다. 지금 값이
박혀 있는 자리가 곧 첫 후보다:

  - `font.size`(브리지 `font_px=15`)·줄 높이 — **M4a3(글리프 기하)과 함께 정해야 한다.**
    지금은 굽는 크기(`MARU_ATLAS_TEXT_PX`)와 그리는 크기가 따로 놀아, 크기를 config 로 여는
    순간 그 어긋남이 사용자에게 드러난다.
  - 테마(`themeColors()` 고정) — 데스크톱 `chrome.theme` 와 **같은 이름을 쓰되 값은 따로**.
  - 프레임 주기(30Hz 고정) — 모바일에는 데스크톱에 없는 축이 붙는다(저전력 모드·배터리).
  - 스크롤백 줄 수(코어 기본 1000) — 기기 메모리가 데스크톱과 다르다.
  - 원격 접속 프로필(호스트·인증) — **데스크톱에 대응하는 키가 없다.** M3 가 전송·인증을
    정한 뒤에 형태가 나온다.
  - 보조 키바 구성·터치 임계값 — 데스크톱에 대응 키가 없다(M4a2·M4b).

데스크톱 키 93개 중 `quick-terminal.*`·`shell.command`·`shell.args`·`input.option-as-meta`·
`input.right-click`·`session.keep-alive-after-quit` 처럼 **모바일에 뜻이 없는 것**은 안 가져온다.

### M11 스토어 배포

[배포](../distribution.md)는 macOS 채널·서명·공증·업데이트를 소유하지만 **모바일 스토어는
다루지 않는다**. 지금 상태로는 배포가 불가능하다.

  - `AndroidManifest.xml` 에 `android:debuggable="true"` 가 남아 있다(개발용 — `run-as` 로
    래스터 결과를 꺼내려고 넣었다). **배포 빌드에서는 반드시 빼야 한다.**
  - 앱 아이콘·런치 스크린이 없다.
  - iOS 는 privacy manifest(`PrivacyInfo.xcprivacy`)와 프로비저닝이 필요하다.
  - Play 는 targetSdk 하한과 App Bundle 을 요구한다 — Gradle 을 안 쓰기로 한 결정([계약 §1])과
    다시 만나는 지점이라, 그때 Gradle 도입을 재검토한다.

### M4a·M12 포인터 (계약 §3.1)

**"세션 전환 UI" 라고만 적어 둔 것이 범위를 과소평가했다.** 실제 일은 **포인터를 chrome 의
`UiActionId` 경로에 태우는 것**이고, 스크롤·멀티터치는 그 위에 올라간다.

지금 받는 것은 `ACTION_DOWN`·`touchesBegan` 뿐이라 **탭과 롱프레스를 구분할 수 없다**(뗀
시점을 모른다). 먼저 M4a 로 down/move/up/cancel·포인터 id·시각을 코어로 넘기는 ABI 를 만들고,
그 위에서 판정한다.

**버튼을 좌표로 실행하지 않는다.** down→up 사이에 원격 세션 목록이 바뀌면 같은 인덱스가 다른
탭을 가리킨다 — `(UiActionId, snapshot_generation)` 으로 태워야 그 누름이 무시된다.

판정: 합성 이벤트 열을 넣어 intent 가 나오는지 **헤드리스로** 단언한다(모바일은 CI 가 없으니
이 경로가 유일한 자동 검증이다). 스크롤 관성·핀치는 플랫폼 인식기 결과를 받으므로 그쪽은
손 검증이다.

### M2b iOS IME preedit

Android 는 정했고 iOS 는 안 했다(계약 §7). `UITextInput` 의 marked text 를
`maru_mobile_set_preedit` 에 태우면 되는 자리다.

### M3c 연결 수명

M3 는 "무엇을 타고 가는가" 만 다뤘다. 모바일은 그 뒤가 더 어렵다.

  - **네트워크가 끊긴다** — 셀룰러↔Wi-Fi 전환, 지하철, 화면 잠금. 재접속·backoff·중복 세션
    방지가 필요하다. Mosh 가 존재하는 이유가 이것이다.
  - **백그라운드에서 소켓이 죽는다**(iOS 는 특히). 세션을 서버가 붙들고 있다가 다시 붙는
    모델인지, 클라가 상태를 들고 있는지 정해야 한다 — [영속 세션 호스트](../persistent-session-host.md)와
    같은 문제를 다른 조건에서 푸는 셈이다.
  - **자격증명을 어디에 두는가** — iOS Keychain / Android Keystore. 지금 계획에 없다.
  - **프로토콜 버전** — 모바일 앱과 데스크톱 host 의 버전이 갈린다(스토어 심사·사용자 업데이트
    지연). 호환 규칙이 필요하다.

## 앱 수준 공백 (M13~M16)

M9~M12 가 **기능·계약** 축이었다면 이건 **앱으로서 갖춰야 하는 것** 축이다. 코드로 확인한
현재 상태를 그대로 적는다.

### M13 표시 설정

`font_px` 가 **상수 15로 박혀 있다**(`mobile_bridge.zig`). 폰트 크기를 못 바꾸는 터미널은
폰에서 쓸모가 크게 준다 — 손가락 크기와 화면 크기가 사람마다 다르다.

  - **핀치 줌**으로 폰트 크기를 바꾸는 것이 모바일 터미널의 사실상 표준이다(플랫폼 인식기 →
    코어, 계약 §3.1 의 "느낌은 플랫폼" 에 해당).
  - **다크/라이트 전환을 안 본다** — `traitCollection`(iOS)·`UI_MODE_NIGHT`(Android) 를 읽는
    코드가 없어 시스템 설정을 바꿔도 그대로다.
  - **접근성 글자 크기**(Dynamic Type / 글꼴 크기 설정)도 안 본다. M9 접근성과 함께 봐야 한다.

셋 다 config 를 어디서 받는가(M10)와 얽힌다.

### M14 전원·네트워크 예의

모바일은 데스크톱과 달리 **자원이 사용자에게 보인다**(배터리·데이터·발열).

  - **저전력 모드를 안 본다.** 기본이 30Hz(계약 §3.2)이므로 저전력에서는 더 낮추거나
    갱신이 없을 때 아예 쉬는 쪽을 봐야 한다 — `isLowPowerModeEnabled`(iOS)·`PowerManager`(Android).
  - **백그라운드에서 무엇을 멈추는가**가 정해지지 않았다. 지금은 창이 사라지면 Vulkan 을
    부수지만(생명주기), 원격 연결(M3c)이 붙으면 소켓·재접속 타이머도 같이 정해야 한다.
  - **데이터 절약** — 셀룰러에서 화면 갱신 전송량을 줄일지. 원격 프로토콜 설계(M3a)의 입력이다.

### M15 진단

**크래시 보고와 로그 수집이 없다.** 데스크톱은 사용자가 로그를 찾아 줄 수 있지만 폰은 아니다 —
재현 못 하는 버그가 그대로 미제로 남는다.

[trace·replay](../trace-replay.md)가 진단 산출물 계약을 소유하므로 거기에 모바일 축을 더한다. **개인정보
경계가 먼저다** — 터미널 로그에는 명령어·경로·호스트명이 들어가고, 그걸 수집하면 그 자체가
사고다(`src/redact.zig` 가 이미 그 판정을 갖는다).

### M16 첫 실행 경험

지금 앱을 처음 켜면 **아무 안내 없이 하드코딩된 화면**이 뜬다. 원격 전용(계약 §1)이므로 실제
제품의 첫 화면은 "무엇에 연결할까" 다.

  - 온보딩·서버 등록·페어링(M3c 의 자격증명 저장과 같은 화면).
  - **연결 실패 UX** — 지금은 실패해도 로그 한 줄뿐이다. 사용자에게 무엇이 잘못됐는지 보여야
    한다(네트워크·인증·버전 불일치가 각각 다른 안내다).
  - 권한 요청 — 알림 권한 정도지만 시점이 UX 다.
