# 모바일 플랫폼 구현 계획

계약은 [모바일 플랫폼](../mobile-platform.md)이 소유한다. 이 문서는 **진행**만 소유한다.

## 배경

PoC 로 "Zig 코어 + 네이티브 GPU 가 iOS/Android 에서 서는가" 를 실측했고 답은 예다
([측정 기록](../../tools/mobile-harness/README.md)). 그 과정에서 **바꿔야 할 것 둘**이 드러났다.

- quad 하나당 draw call 하나 — 모바일 타일 기반 GPU 에 특히 비싸다. 148 quad 는 괜찮지만
  80×40 터미널은 3200 draw call 이 된다.
- `NativeActivity` 는 IME 를 못 받는다 — 한글 조합이 필수라 `GameActivity` 여야 한다.

## M0 — 폴더 구조

PoC 는 `tools/mobile-poc/` 에 앱 전체를 담고 있었다. 제품 코드는 `src/platform/` 으로 옮기고,
그 폴더는 **측정 하네스**로 남긴다(빌드 스크립트 + 측정 기록). 코드를 양쪽에 두지
않는다 — `run.sh` 가 `src/platform/` 을 빌드한다.

폴더는 뒤에 `tools/mobile-harness/` 로 바꿔 부른다. 앱을 들어내고 나서도 이름만 `poc` 로
남아 있었는데, 그 사이 이 폴더는 습작이 아니게 됐다 — `doc_claims.sh` 는 `mise run check`
에서 도는 **CI 게이트**이고 `Info.plist.in` 은 **번들에 실려 나간다**. 이름이 "버려도 되는
것"이라고 말하면 다음 사람이 그렇게 읽는다.

## M1 — 배칭

각 quad 를 push constant + `vkCmdDraw`/`drawPrimitives` 로 그리던 것을, **quad 배열을
버퍼에 한 번 올리고 인스턴스 드로우 한 번**으로 바꾼다. 셰이더는 push constant 대신 버퍼를
읽는다(Metal `[[instance_id]]`, Vulkan `gl_InstanceIndex`).

판정: 프레임당 draw call 수를 로그로 낸다. **`calls == 1` 이 판정이지 `instances` 수가 아니다** —
quad 수는 화면 구성이 바뀔 때마다 달라진다(U3 에서 148 → 174 → 173 으로 움직였다). 그 수를
기대치로 적으면 화면을 고칠 때마다 판정을 고치게 되고, 그러면 판정이 아니다.
실측: 두 플랫폼 모두 `MARU_DRAW calls=1`, 화면은 이전과 동일.

Metal 은 `setVertexBytes:` 가 4KB 한계라 148 quad(9.5KB)도 못 실어 `MTLBuffer` 가 필요했다.
Vulkan 은 push constant 를 통째로 버리고 storage buffer + `gl_InstanceIndex` 로 갔다 —
quad 마다 다른 값을 한 번의 draw call 에 실을 수 없기 때문이다. 그 결과 **프래그먼트가
push constant 를 못 읽게 되어** 색·radius·kind 를 varying 으로 넘긴다.

**CI 에는 붙이지 않는다(사용자 결정).** 모바일 빌드는 Xcode·NDK·에뮬레이터가 필요해
러너 비용이 크고, 지금 단계에서 막아야 할 회귀가 없다. 검증은 로컬에서 `run.sh` 로 한다 —
필요해지면 그때 넣는다.

## M1.5 — build.zig

제품 코드를 셸 스크립트가 빌드하는 것은 정식 도입이 아니다. `build.zig` 가 모바일 타깃을
소유하고, `tools/mobile-harness/run.sh` 는 **기기 조작**(설치·실행·캡쳐·계측)만 남긴다.

```sh
zig build mobile-libs -Doptimize=ReleaseSafe   # 세 타깃 전부
zig build mobile-lib-ios-sim | mobile-lib-ios | mobile-lib-android
```

**Debug 는 iOS 에서 링크가 깨진다** — std 의 스택 트레이스가 시뮬레이터 SDK 에 없는
`_dyld_get_image_header_containing_address` 를 참조한다. `simple_panic` 이 ReleaseSafe 에서
그 경로를 걷어내고 **안전 검사는 그대로 산다**(PoC 때 기록한 내용이 그대로 확인됐다).

**대체된 초기 하네스는 지웠다.** `chrome-ios`/`chrome-android-app` 이 `ios`·`ios-app`·
`android`·`chrome-android` 가 하던 일을 포함한다 — 남겨 두면 어느 쪽이 진짜인지 흐려진다.
측정 **결과**(표·스크린샷)는 전부 남는다. 여섯 기능 판정기(`features-*`)는 다른 모드가
대체하지 않는 별도 측정이라 남긴다.

## M2 — Android IME (자체 Java shim)

**`GameActivity` 를 시도했다가 되돌렸다.** 코드 이관과 빌드까지 통과했지만 실행에서
`ClassNotFoundException: androidx.appcompat.app.AppCompatActivity` 로 죽었다 — `GameActivity`
가 전 버전에서 `AppCompatActivity` 를 상속해 AndroidX 20여 개와 리소스 컴파일이 필요하고,
그건 Gradle 없이 손으로 조립할 수 없다. 계획할 때 못 본 비용이라 결정을 다시 했다
(근거는 [계약 §1](../mobile-platform.md#1-확정-결정)).

`NativeActivity` 를 유지하고 IME 만 자체 shim 으로 받는다.

```text
MaruActivity(NativeActivity)   투명 입력 View 를 얹고 소프트 키보드를 띄운다
  └ MaruInputView              onCheckIsTextEditor()=true → IME 가 입력 대상으로 인정
      └ MaruInputConn          setComposingText/commitText 를 JNI 로 넘긴다
```

### 검증된 것과 안 된 것

| | 상태 |
|---|---|
| shim 이 입력 대상으로 인정됨 | **OK** — 소프트 키보드가 뜬다 |
| `commitText` → 코어 | **OK** — 키를 눌러 `commit="a"` 도달 |
| preedit 렌더(커서 자리에 흐리게) | **OK** — 주입해서 확인 |
| IME 조합 → preedit 왕복 | **미검증**(아래) |

**조합을 실제로 흘려 보지 못했다.** 이 에뮬레이터에는 Gboard(LatinIME)뿐이고 한글 IME 가
없다. 영어 Gboard 는 이 입력 타입에서 `setComposingText` 없이 바로 `commitText` 를 부른다.
그래서 "IME 가 만든 조합 문자열이 preedit 으로 그려진다" 는 왕복은 **한글 키보드가 있는
기기에서 손으로 확인해야 한다**.

실측으로 잡은 것들:

  - `adb shell input text` 는 **IME 를 우회**한다(키 이벤트 주입). IME 경로 검증에 못 쓴다.
  - `BaseInputConnection(view, false)` 면 IME 가 "편집기가 아니다" 로 보고 조합 없이 바로
    확정한다 — `true` 여야 한다.
  - `NativeActivity` 는 `android.app.lib_name` 의 .so 를 **클래스로더 밖에서 dlopen** 한다.
    Java 쪽 `System.loadLibrary` 를 한 번 더 해야 JNI 이름 해석이 된다.
  - `d8` 8.2.2 가 **익명 내부 클래스에서 내부 오류로 죽는다**. 이름 있는 중첩 클래스만 쓴다.

## M3 — 원격 연결

**두 플랫폼 다 원격 전용이다**(사용자 확정). 로컬 PTY 를 안 둔다.

그런데 지금 컨트롤 플레인은 **명시적으로 로컬 전용**이다 — "wire 는 TCP/HTTP 를 바인드하지
않는다", 보안은 "같은 uid 안의 신뢰 차등"(peer-cred + 0700/0600). **peer-cred 는 기계를
넘으면 존재하지 않는다.** 그래서 M3 는 클라이언트를 붙이는 일이 아니라 **계약을 넓히는
일**이고, M3a(문서)가 먼저다.

**정해졌다(2026-08-20 — [컨트롤 플레인 §4a](../control-plane.md)).** 아래는 그 결정의 목록이다:

  - **전송**: **SSH** — 이미 붙어 있는 그 연결에 채널을 하나 더 연다(`exec maru control --stdio`).
    인바운드 포트도 계정도 더 필요 없다. 릴레이·VPN 은 안 쓴다.
  - **인증**: **SSH 사용자 인증이 곧 신원**이다. 페어링 토큰을 새로 만들지 않는다 — 만들면 그
    수명·폐기·저장을 우리가 또 설계해야 한다. 폐기는 `authorized_keys` 한 곳에서 한다.
  - **암호화**: 전송(SSH)이 한다. 종단간을 따로 얹지 않는다.
  - **신뢰 등급**: **데스크톱 클라이언트와 동등**(사용자 확정). 좁혀도 실질 노출이 안 준다 —
    폰은 이미 셸을 여는 열쇠를 들고 있고, 셸이 있으면 그 계정으로 무엇이든 할 수 있다.
  - **코어가 만든 답을 어디로 흘리는가**: **닫혔다**(S9-2). 전송이 SSH 로 정해졌으므로
    `maru_mobile_take_response(out, cap)` 이 답을 내주고, host 가 `maru_mobile_ssh_write` 로
    돌려보낸다. 받는 쪽은 `maru_mobile_term_write` 다. 자리가 모자라면 **자르지 않고 0** 을
    돌려준다 — 반쪽 시퀀스를 보내면 원격 화면이 그때부터 어긋난다.

한 가지는 이미 실측했다 — `session_host` 클라이언트(23k줄)가 **iOS 타깃으로 그대로
컴파일된다**. 코어 쪽은 이식 가능하고, 막는 것은 전송·인증 계약뿐이다.

## M4b — 스크롤·선택·복사·보조 키바

**네 조각으로 가른다.** 한 덩어리로 하면 "포인터 ABI 가 없어서 선택을 못 하고, 선택이 없어서
복사를 못 하는" 의존이 한 PR 안에 다 들어온다.

**M4b1(스크롤)이 먼저다.** 지금은 **화면 밖으로 나간 출력을 볼 방법이 아예 없다**. 게다가
이 자리가 [적대적 검증에서 못 닫은 계약](../verification-matrix.md) 하나를 닫는다 — "스크롤백을
보는 동안에는 커서를 안 그린다" 는 뷰포트를 올리는 수단이 없어 테스트가 그 상태를 **만들 수
없었다**. 스크롤 ABI 가 생기면 그 규칙이 계약 테스트에 들어온다.

경계는 §3.1 이 이미 정해 뒀다 — **관성·러버밴딩은 플랫폼, 의미는 코어**. 플랫폼은 논리 px
델타만 넘기고, 줄로 환산하는 것도 코어 쪽(브리지)이 한다(플랫폼은 셀 크기를 모른다).

데스크톱이 이미 정한 것을 그대로 따른다(`app_session/scroll.zig`):

| 언제 | 무엇 |
|---|---|
| alt screen + DECSET 1007 | 뷰포트를 안 움직이고 **화살표 키**를 보낸다. 여러 줄은 **한 버퍼에 묶어** 보낸다 — 줄마다 쓰면 빠른 플릭에서 뒷부분이 드랍된다 |
| 그 변환을 할 때 | **선택을 해제한다** — 프로그램이 화면을 다시 그리므로 남은 선택은 좌표가 어긋난 유령이다 |
| 그 외 | `scrollViewport(delta_up)` — clamp 도 코어가 한다 |
| 입력이 들어오면 | **바닥으로 스냅한다** — 과거를 보는 중에 친 글자가 화면 밖에 찍히면 안 된다 |

## 이모지 (M4a6 — 완료)

M4b 뒤로 미뤘다가(2026-08-13 사용자 결정) M4b 완료 뒤 진행했다.

**증상이었던 것**: U+FFFF 위 글자가 통째로 빈칸이었다. 자리(2셀)는 코어가 정확히 잡는데 픽셀이
없었다. **막고 있던 것은 host 의 한 줄**이다 — 두 host 다 `cp > 0xFFFF` 를 건너뛰어, 미스 목록에
올라와도 아무도 굽지 않았다. 아래 셋을 함께 넣어 해소했다(iOS 는 화면으로 확인).

세 가지가 **함께** 필요하다:

| | 무엇 | 어디 |
|---|---|---|
| ① | 서러게이트 쌍을 만든다 | 지금 두 host 다 16비트 한 단위로 넘긴다(iOS `unichar`, Android `jchar`) |
| ② | 이모지 폰트로 폴백한다 | Jetendard 에 이모지가 없다. Android 는 `Canvas.drawText` 라 시스템 폴백이 붙지만, iOS 는 `CTFontCreateForString` 으로 직접 골라야 한다 |
| ③ | **컬러 아틀라스** | 글리프 아틀라스가 `R8`(커버리지)이라 컬러 비트맵을 넣으면 실루엣이 된다 |

**③ 을 어떻게 할지가 이 슬라이스의 설계 결정이다.** 두 갈래가 있고, 지금 기울어 있는 쪽은
**세 번째 텍스처**다:

| | 장점 | 대가 |
|---|---|---|
| 글리프 아틀라스를 RGBA 로 승격 | 텍스처가 하나로 유지된다 | 메모리 4배, **합성 글리프의 커버리지 계약**(alpha 채널, §3)이 흔들린다 |
| 컬러 전용 세 번째 아틀라스 + 새 `kind` | 텍스트 아틀라스는 `R8` 그대로. **아이콘 아틀라스가 이미 `RGBA8` + `kind=2`** 라 같은 모양이 하나 더 서는 것뿐이다 | 텍스처 하나가 늘고 등록부가 둘로 갈린다 |

데스크톱은 UV sentinel(`u >= 2.0`)로 한 텍스처 안에서 가르는데, 모바일은 이미 텍스처를 나눠
쓰고 있어서 **모바일의 기존 구조를 따르는 쪽**이 맞다.

**코어에서 새로 만들 것은 없다** — 단, **base 코드포인트에 한해서다.** 컬러 판정의 단일 출처가
이미 `width.isEmojiPresentation` 이고 width 2 도 코어가 잡는다. 브리지가 "이 코드포인트는
컬러다" 를 알리는 한 필드로 M4a6 을 닫았다.

**클러스터 열 (완료).** 미스에 **코드포인트 열**을 실어 host 가 문자열 하나로 이어 굽게 했다.
두 등록부도 열까지 비교하고, 컬러 판정도 열을 본다(VS16/VS15 가 표현을 뒤집는다). 화면으로
확인했다 — `❤` 와 `❤️` 가 **나란히 다르게** 그려진다(데모 피드의 판정자).

**iOS 는 굽는 방식을 바꿔야 했다.** 커버리지 경로가 `CTFontGetGlyphsForCharacters` +
`CTFontDrawGlyphs`(코드포인트당 글리프 하나)라 결합이 안 됐다. `CTLine` 으로 옮기니 결합·
리거처·폰트 폴백이 한 자리에 모였다 — 다만 **`CTLineDraw` 는 컨텍스트 fill color 를 안 본다.**
전경색을 문자열 속성으로 안 실어 회색조 아틀라스에 검정으로 그렸고, 온디맨드로 굽는 글자가
통째로 사라졌다(화면으로 잡았다). Android 는 `Canvas.drawText` 가 원래 문자열을 받아 무변경이다.

**남은 것은 코어가 안 묶어 주는 것들이다.** 이 경로는 `grapheme_id` 에 담긴 것만 나른다.
grapheme cluster mode(DECSET 2027) 합의가 없으면 코어는 ZWJ 시퀀스와 지역 표시자 쌍을 각각의
셀에 두므로 국기(`🇰🇷`)는 여전히 글리프 두 개고 가족 이모지도 갈린다. **2027 계약 축이고 별도
슬라이스다.**

**ZWJ 는 그 전에 한 겹만 막아 뒀다.** 그 셀이 미스로 올라가 host 가 **빈 글리프**를 굽고 아틀라스
슬롯을 먹고 있었다. 브리지에서 0폭 format 문자를 걸렀다(계약 테스트 있음). **코어의 2027 계약은
안 건드렸다** — 폭 표에서 ZWJ 를 0폭으로 만들면 모드와 무관하게 붙어 버려 2027 꺼짐을 전제한
테스트 둘이 깨진다(실측).

## U — 앱으로서의 UX (U0~U2)

**엔진 계약은 촘촘한데 앱 설계가 없었다.** 데스크톱 chrome(사이드바 + 상단 탭)을 폰에 그대로
축소해 그리고 있었고, 폰 세로에서 사이드바가 화면 폭의 3분의 1을 상시 점유한다.

**U0(문서)은 [mobile-ux.md](../mobile-ux.md)가 소유한다** — 3계층 화면(연결·본체·부가), 스택
전환, 터미널 안에서 세션을 바꾼다는 규칙.

**세션 전환의 손짓은 «덮개» 로 정했다**(사용자 확정 2026-09-04). 세션을 바꾸려면 **세션 목록으로
나갔다 고른다** — 지금 「줄을 눌러 그 화면을 연다」와 **같은 길**이다. 셋 중에서 이것을 고른 이유:

- **탭 줄**은 폰 폭에서 서넛만 넘어가도 라벨이 뭉개진다. 그리고 지금 화면의 탭 셋은 하드코딩
  라벨이라, 그걸 진짜 탭으로 만드는 chrome 작업이 통째로 붙는다 — **결정이 아니라 데스크톱을
  옮긴 결과**였다.
- **스와이프**는 chrome 을 안 늘리고 화면을 가장 넓게 쓰지만, 보이지 않아 배우기 어렵고 본문의
  가로 스크롤·선택 드래그와 손짓이 겹친다([§5 포인터](../mobile-platform.md)의 슬롭 판정이 그
  경합을 떠안는다).
- **덮개**는 **새 제스처도 새 chrome 도 안 만든다.** 세션이 많아져도 목록은 스크롤되므로 안
  좁아지고, 목록에 이미 있는 것(경로·브랜치·상태)이 그대로 고르는 근거가 된다.

그래서 U2 는 **화면을 늘리지 않는다** — 브리지가 세션을 여럿 드는 것이 전부이고, 고르는 자리는
이미 선 세션 목록이다. 지금의 탭 줄은 이 결정으로 **전제가 아니게** 됐다.

**「여럿 든다」가 무엇인지 코드로 재서 정한다.** 컨트롤 채널은 **하나**다([컨트롤 플레인 §4a]
(../control-plane.md) — SSH 코어가 `control` 을 한 자리만 든다). 그러니 U2 는 **화면 둘을 동시에
흘리는 것이 아니다** — 그건 채널을 늘리는 일이고 §4a 를 바꾸는 결정이다. U2 가 없애는 것은
**「돌아오면 처음부터」**다: 지금은 `remote_screen` 이 단일 변수라 다른 세션을 봤다 돌아오면 그
세션의 화면이 **빈 화면부터** 다시 쌓인다(`dropRemoteScreen` 이 놓는다).

| 슬라이스 | 무엇 | 완료 조건 |
| --- | --- | --- |
| **U2a**(완료 — 2026-09-04) | 브리지가 세션 **상태를 표로** 든다 — `runtime_id → {조립된 화면, 선언한 격자}`. 흐르는 스트림은 여전히 하나이고, 돌아온 세션은 **마지막 화면을 곧바로** 보이며 그 위에 새 프레임이 덮인다 | 목록 → A → 목록 → B → 목록 → A 에서 A 가 **빈 화면을 안 거친다**(판정자) |
| **U2b**(완료 — 2026-09-04) | 표에 **상한과 버림**(LRU). 폰이 큰 화면 여럿을 못 든다 — 조립기 하나가 이미 16 MiB 상한을 든다 | 상한을 넘기면 **가장 오래 안 본 것**이 먼저 버려진다(판정자) |
| **U2c**(완료 — 2026-09-04) | 목록이 **든 세션을 표시**한다 — 어느 줄이 이미 화면을 갖고 있는지. 덮개로 고르는 결정(위)이 실제로 값을 하려면 목록이 그것을 말해야 한다 | 목록 줄에 그 표시가 실제로 조립된다(판정자) |

**U2 는 새 화면도 새 손짓도 안 만든다** — 위 결정대로 고르는 자리는 이미 선 세션 목록이다.

**다만 「덮개」는 «나갈 자리»를 전제한다**(실기 2026-09-04). 원격 화면은 제목만 그리고 누를
자리를 안 만들어, 들어오면 앱을 죽이는 것 말고는 나갈 수 없었다 — 그러면 세션을 바꿀 길이
없으니 U0 의 결정이 통째로 못 쓰게 된다. 그래서 이 화면도 **설정·터미널과 같은 자리·같은
크기·같은 글리프**의 뒤로가기를 든다(§5.1 — 좌상단 52 정사각, `arrow_left`). 그리고 그
누름은 **하드웨어 뒤로가기와 같은 길로 나간다**(`maru_mobile_pop_screen`) — 화면만 빼고 뜻을
`.screen` 으로 남기면 그 서버에서 `attach` 가 계속 돌고 맥은 폰이 선언한 폭에 계속 눌려 있다
(실측: 나온 뒤에도 host 가 `observers=1 50x27`). 나가는 자리가 둘이면 **하는 일도 하나**여야
한다.

**셋 다 끝났고 실기 확인도 끝났다**(2026-09-04). 맥 앱의 `workspace.v1` 에 탭 다섯을 심어
host-backed runtime 을 다섯 세운 뒤(그전에는 runtime 이 하나뿐이라 상한을 넘길 수가 없었다)
시뮬레이터로 다섯 줄을 차례로 방문해 쟀다:

| 무엇 | 실기에서 본 것 |
| --- | --- |
| **U2c** — 목록이 든 세션을 말한다 | 넷을 방문하면 그 네 줄에만 앰버 점. 6pt 라 둥근 맛은 거의 없지만 **읽힌다** |
| **U2b** — 상한과 버림 | 다섯째를 열자 **가장 오래 안 본 첫 줄의 점만** 사라졌다(점 수는 넷 유지) |
| **U2a** — 빈 화면을 안 거친다 | 버려진 줄은 누른 지 1초에 「화면을 받는 중」, **들고 있던 줄은 1초에 이미 내용**이 있다 |

상한 `4` 는 **동작은 확인했지만 여전히 고른 값**이다 — 폰 메모리를 재서 정할 자리가 남는다.

**그 회차가 결함을 하나 찾았다 — 「전환이 막힌다」.** 화면을 빠르게 여닫으면(열고 2초, 나가고
1초) 원격의 `maru attach --stream` 이 **안 죽고 남는다**. 그 고아의 부모는 `sshd-session` 이고
stdout 은 살아 있는 파이프라, 원격의 「소비자가 갔나」 판정(`consumerIsGone`)은 당연히 거짓이다 —
**즉 폰이 채널을 안 닫는다**(그 시점 폰의 SSH 연결이 셋 ESTABLISHED). 그러면 [§4a](../control-plane.md)
의 「한 번에 control 하나」에 걸려 **그 뒤로 다른 세션을 눌러도 영영 안 뜬다**(들고 있던 세션만
캐시로 보이고, 아닌 세션은 「화면을 받는 중」에서 멈춘다). 「덮개」로 세션을 바꾸는 것이 U2 의
전부이므로 이것은 **U2 를 실질적으로 못 쓰게 만들었다.**

**고쳤다**(2026-09-04). 원인이 셋이었고 셋 다 같은 창(빠른 여닫기)에서 터졌다 —
⑴ `CHANNEL_CLOSE` 는 상대 번호를 실어야 해서(§5.3) 확인 전에는 못 보내는데 `closeControl` 이
그 오류를 내며 **이미 「닫았다」로 굳어** 있었고(그 오류는 `void` 반환 탓에 아무도 안 읽었다),
⑵ 그것을 고치자 닫은 뒤 온 `exec` 답이 `close_sent` 채널에 꽂혀 **SSH 세션이 통째로 죽었고**,
⑶ 그것까지 고쳐도 host tick 이 **열기를 닫기보다 먼저** 해서 열자마자 닫는 무한 진동이 됐다.
차례로 미룸(`closeDisposition`)·수용(§5.3 대로 `close_sent` 에서도 답을 받는다)·순서 뒤집기로
고쳤다. **⑶ 은 host tick 안이라 헤드리스 회귀가 없다** — 주석과 실기로만 막힌다.

**U1 이 실제 작업량이다.** 코드로 재 본 공백:

| 무엇 | 실측 |
|---|---|
| `chrome/ui/scroll_area` | **이 줄은 U1 을 시작할 때의 스냅숏이다**(당시: 마우스 휠 모델 — `wheel_residue_px`, `Drag`는 스크롤바용, 관성·bounce·콘텐츠 직접 드래그 전무). **2026-09-05 현재는 셋 중 둘이 섰다** — `Touch`(`begin`/`move`/`end`·`owner`·`slop_px`)가 콘텐츠를 직접 끌고 `decay_per_ms`·`max_velocity` 로 관성을 흘린다. **남은 것은 `bounce` 뿐**이다 |
| 터미널 스크롤 | **이 줄도 스냅숏이다**(당시: 관성이 host `fling_vy` 에 있고 컴포넌트 계층에는 없었다). **지금은 반대다** — host 의 `fling_vy`·`_flingVy` 는 **0건**이고, 브리지의 `body_fling` 이 `scroll_area.Touch.decay_per_ms` 를 써서 흘린다(아래 「관성을 wall-clock 으로」) |
| 히트 영역 | **보조 키바는 44 로 섰다**(아래 U1 절). 사이드바 카드 52는 통과, **탭 34는 여전히 미달** |
| ~~소프트 키보드 다시 올리기~~ | **없는 문제였다.** 앱이 `resignFirstResponder`를 안 부르고 내리는 UI 도 없으며 백그라운드 왕복 뒤에도 입력이 들어간다(실측) |
| ~~키보드 높이~~ | **닫았다**(아래 U1 절) |
| 눌리는 대상 | **보조 키바뿐**(브리지가 `maru_mobile_pointer` 로 받아 자기 사각형과 맞춘다 — `maru_mobile_keybar_rect`·`_count` 는 host 가 그 자리를 아는 용도다). 탭·사이드바는 그리기만 |

**폼 컴포넌트는 새로 만들 것이 없다** — `text_field`·`input_box`·`toggle`·`dropdown`·`confirm`·
`modal_box`가 이미 있다. 전부 마우스 caret + 하드웨어 키보드 모델이라 **터치에서 쓸 수 있게 하는
일**이다.

### U1 — 키보드 inset (완료)

**보조 키바가 키보드 아래로 사라지고 있었다.** 그 키바의 존재 이유가 "소프트 키보드에
Ctrl·Esc·Tab·화살표가 없다" 인데 정작 키보드가 뜨면 못 쓰게 됐다. 양 host 가 키보드 높이를 빼고
가용 높이를 넘기게 했다(계약은 [UX §5.3](../mobile-ux.md)).

**이 슬라이스는 순서를 세 번 바꾼 끝에 골랐다.** 적대적 검증에서 앞의 둘이 깨졌다:

| 후보 | 왜 아니었나 |
|---|---|
| 관성 스크롤 | 오늘 **소비처가 없다**(사이드바 5개·탭 3개는 안 넘친다). 이 저장소가 금지하는 "소비처 없는 인터페이스" |
| 히트 영역 44/48 | **물리적으로 안 들어간다** — 키 11개 × 44 = 514 > 390. 키를 3개 버려야 하고 그건 UX 결정 |
| "키보드 다시 올리기" | **없는 문제**였다(실측) |

**그리고 시뮬레이터 키보드를 켜는 법을 찾은 것이 전제였다** — `defaults` 가 안 통하고
I/O ▸ Keyboard 메뉴가 지배한다(같은 상태에서 Safari 조차 키보드가 안 떴다). 그전에는 이 결함이
화면에 보이지도 않았고 고쳐도 확인할 수 없었다.

**Android 는 도킹 키보드 캡처를 못 얻었다** — 에뮬레이터 Gboard 가 플로팅 모드로 돌아간다.
배선은 로그로 확인했다(`MARU_KEYBOARD height=511` → 그 프레임 `logical=411x529`, 평소 841).

### U1 — 보조 키바 (완료)

**30×32 였다.** 44 로 키우면 키 11개가 폰 세로 폭을 못 들어가(가용 390 에 514) 셋 중 하나를 골라야
했고, 다섯 배치를 실제로 만들어 화면으로 비교한 뒤 **크기를 지키고 가로 스크롤**로 갔다(사용자
결정). 규칙은 [UX §5.4](../mobile-ux.md)가 소유한다.

**레이아웃으로는 못 했다** — 음수 margin 을 `tree` 가 `error.NegativeValue` 로 거부해 화면이 통째로
검게 나갔고, `chrome/ui/scroll_area` 는 세로 전용이다. 키바를 레이아웃에서 빼고 브리지가 직접
그린다. **컴포넌트 계층에 가로 스크롤이 생기면 그쪽으로 옮긴다** — 그게 U1 에 남은 일이다.

**두 결함을 함께 고쳤다**: 브리지가 카드 테두리를 아예 안 그리고 있었고(`.quad` 가
`border_widths`/`border_role` 을 버렸다 — 고치니 사이드바·탭에도 윤곽선이 생긴다), 가운데 정렬을
글자 수 × 근사치로 재 화살표가 왼쪽으로 쏠렸다(`textWidth` 로 실제 폭을 잰다).

**적대적 검증을 더 안 나올 때까지 돌려 일곱이 나왔다**: 창 밖 키의 rect 가 남아 **안 보이는 키가 눌렸다** ·
`move` 뒤 관성이 같은 이동량을 **또** 적용해 두 배로 미끄러졌다 · `key_bar_ready` 가 항상 참이 돼
판정이 죽었다 · 끝에 닿아도 **관성이 안 죽었다** · **배경에서 잡음이 남아** 복귀 후 첫 터치가
통째로 키바로 갔다 · **그리는 자리와 판정하는 자리가 1px 어긋났다** · `<`/`>` 를 눌리게 만든 것이
**44 미달 버튼을 새로 만드는 꼴**이라 되돌렸다.

**자동 검증이 못 잡는 것이 그보다 많았다.** 화면을 함께 보며 여섯을 더 고쳤다 — 눌림 표시가 없어
`ctrl` 말고는 화면이 답하지 않았고, 임계 아래 손짓이 **스크롤과 입력을 둘 다** 냈고, 그리는 범위와
누르는 범위가 갈려 **보이는데 안 눌리는 키**가 있었고, `>` 가 화면 끝에 붙어 잘렸고, 창 폭이 키
배수가 아니라 오른쪽에 죽은 자리가 남았고, `copy` 예약 48px 이 늘 비어 있었다. **계약 테스트 41개는
그동안 내내 통과했다** — 이 축은 캡처와 손가락이 유일한 판정자다.

`copy` 는 결국 **상시 표시**로 바꿨다(사용자 결정). 나타났다 사라지며 줄이 흔들리는 문제가
사라져 예약할 이유 자체가 없어졌고, 그 자리에 키가 하나 더 들어간다.

**그 바꿈이 뒤에 죽은 것을 남겼다**(뒷 라운드에서 잡았다). `keyBarVisible` 이 `return true` 만
남아 **네 곳의 조건이 늘 참**이 됐고 — 히트 루프의 "안 보이는 키는 못 누른다" 는 주석은 있지도
않은 문을 지키는 것처럼 읽혔다(진짜 문은 창 밖 rect 를 0 으로 지우는 쪽이다) — `copy` 상시
표시를 지키던 테스트는 **고정 상수를 두 번 비교**하게 되어 무엇을 지워도 통과했다. 둘 다 없앴고,
자리 계약은 rect 비교(`copy` 자신의 rect 가 0 이 아닌 것 포함)로 옮겼다. **조건부를 상시로 바꿀
때는 그 조건을 지키던 판정이 같이 죽는지 본다** — 계약이 헐거워진 것은 테스트가 안 알려 준다.

### U 축에서 «지금 할 수 있는» 것 — 없다 (2026-09-05 정정)

**헤딩이 「U 축이 끝났다」는 뜻이 아니다** — 아래 표에 열린 줄이 둘 남아 있고(탭 히트 44·다중
세션), 그 둘은 **M3 에 묶여 지금은 손댈 수 없다**. U1 자체에도 `bounce` 가 남았다(위 표).

**전에는 「하나뿐이다」로 적혀 있었고 그 하나가 「가로 스크롤 일반화」였다. 그 일은 사라졌다** —
소비처가 키바 하나였는데, 키바가 두 줄 격자가 되면서 **안 흐르게 됐다**. 계약(§3.1)과 UX(§5.4)는
그것을 이미 적고 있었고 **이 계획 문서만 낡아 있었다**(발견 2026-09-05, M5 다음 슬라이스를 고르다가).

**코드는 아직 안 따라왔다** — `kb_sa`·`kb_touch`·`key_bar_max_scroll`·`kbScroll()` 이 남았는데
**어느 것도 대입되거나 불리지 않는다**. UX 문서가 「기계를 전부 없앴다」고 적은 그 기계의 잔해다.
가로에서 키바를 한 줄로 접는 슬라이스(아래 M5)가 가로 스크롤을 **`scroll_area` 로** 다시 세우므로,
그때 이 잔해를 지우고 컴포넌트 것으로 갈아 끼운다.

**같은 종류의 부채가 하나 더 있다 — 스크롤바다.** 컴포넌트에 `scroll_area.ScrollbarMetrics`·
`ScrollbarGeometry`(썸 기하·포인터→오프셋·트랙 클릭·히트 확장)가 **이미 있는데** 세션 목록은
그것을 안 쓰고 **손으로 그린다**(`sess_scrollbar_drawn`). 지금은 **표시 전용**이라 기하만 맞으면
되지만, 썸을 끌 수 있게 하는 순간 `offsetForPointer`·`thumbContains`·`withHitSpan` 을 손으로 다시
만들게 된다 — 「가로 스크롤 일반화」가 낡은 채 남아 있던 것과 **정확히 같은 모양**이다.

**아래 표의 나머지는 전부 M3 에 묶여 있다**(적대적 검증으로 확인):

| 후보 | 왜 지금 못 하나 |
|---|---|
| 탭 히트 44 | **여전히 탭 뒤에 아무것도 없다**(목록 줄은 56px 로 이미 그 기준을 넘는다 — S9b·S10d). **탭 뒤에 아무것도 없다** — `"zsh"/"vim"/"logs"` 는 하드코딩 텍스트고 눌러도 바꿔 넣을 세션이 없다. 히트 영역을 44 로 키우는 것은 **누를 것이 생긴 뒤** 일이다(포인터 경로 자체는 있다 — 본문 터치가 선택·스크롤을 이미 해석한다) |
| ~~가로 스크롤을 컴포넌트 계층으로~~ | **없어진 일이다**(2026-09-05 정정). 모바일은 `chrome/ui/scroll_area` 를 **세 군데서 쓴다** — 설정·서버 목록·세션 목록. 「긴 목록」이라는 두 번째 소비처는 U2 와 함께 실제로 생겼고, 그 자리는 **세로**라 이미 있는 컴포넌트로 붙였다(세션 목록은 그전까지 아예 안 흘러, 창에 안 들어가는 세션에 **닿을 수가 없었다**). **가로의 소비처였던 키바는 두 줄 격자가 되며 안 흐른다** — 그래서 이 줄은 닫힌다. 가로 축이 다시 필요해지는 것은 M5 가 키바를 한 줄로 접을 때이고, 그때는 이 컴포넌트로 세운다 |
| **다중 세션**(U2 ①) | **고른 세션의 화면은 본다**(S11 — 2026-08-29). 목록 줄을 누르면 그 세션의 화면 레코드를 받아 그린다(`maru attach --stream` → `MRSS` 프레임 → 조립기 → `rowRuns`). **읽기 전용이고 화면 하나씩이다** — 브리지가 `term_core` 단일 변수인 것은 그대로라, 여러 세션을 동시에 들지는 못한다. 아래는 그 전 서술이다. **여전히 못 한다 — 다만 이유가 바뀌었다.** 이제 원격 목록은 받는다(S10d). 막는 것은 둘이다: 브리지가 `term_core` **단일 변수**라 세션별 화면을 들 자리가 없고, 서버가 그 화면을 줄 메서드(`session.capture`)가 **라이브에 없다**([SSH 계획](ssh-client.md) S10e). 아래는 그 전 서술이다 — **모바일은 세션을 스스로 못 만든다** — [§1](../mobile-platform.md)이 로컬 PTY 를 금지했고 생성 경로가 코드에 없다. 세션은 원격에서 받아야 존재하고, **식별자 축(runtime handle)도 M3 가 정한다** |
| ~~화면들(U2 ②)~~ | **끝났다**(2026-08-21) — M3 가 정해졌고(§4a) 서버 목록·세션 목록·연결 진단이 실제 데이터로 선다(S9b·S10d). 세션 목록은 **받는 중·없다·줄들** 을 갈라 그린다 |

**관성을 wall-clock 으로 바꾸는 것은 끝났다.** 프레임당 감쇠라 실효 tick rate 를 타서, 같은 손짓이
30Hz Android 에서 60Hz iOS 의 **정확히 두 배** 멀리 미끄러졌다(200ms 에 200px 을 민 손짓이 610px
대 402px — 컴포넌트 단위 테스트로 재현했다). 예상대로 셋을 함께 고쳤다: 속도는 **px/ms** 가 되고
(이벤트 시각 간격으로 나눈다 — iOS `UITouch.timestamp`·Android `AMotionEvent` 시각), 감쇠는
`decay_per_ms^dt` 다. 값은 `0.995012`(= 60Hz 프레임당 0.92)이고, 튄 이벤트 하나가 화면을 날리지
않게 상한도 둔다. **처음에는 헤더의 `MARU_FLING_*` 가 그 값을 들었는데 그 미러 상수는 뒤에
없앴다**(아래 「host 에서 걷어낸 것」) — **지금 소유자는 컴포넌트**다:
`scroll_area.Touch.decay_per_ms`·`max_velocity`(그리고 `slop_px`·`stop_below`). —
Flutter `FrictionSimulation`·RN `OverScroller`/`decelerationRate` 가 쓰는 모델과 같다.

### M5 — 회전: 첫 슬라이스가 섰다 (실측 2026-09-05)

**결정: 회전은 «컴포지터에게 맡긴다».** Android 가 권하는 것은 정점 변환에 회전을 넣는
pre-rotation 이지만, 그것은 좌표계를 통째로 건드리는 일이라 별도 슬라이스다 — 먼저 「돌리면
제대로 그려진다」를 세우고, 합성 비용이 실제로 문제가 되면 그때 옮긴다.

**잠금은 근거가 없었다.** `AndroidManifest.xml` 의 `screenOrientation="portrait"` 가 액티비티를
세로로 묶고 있었고 그 이유는 코드에도 문서에도 없었다. 계약은 회전을 **하기로** 정해 뒀고
([§8](../mobile-platform.md)), 좌우 safe area 도 「가로 모드에서는 노치가 옆으로 간다」를 이유로
이미 다뤘다. 즉 잠금은 결정이 아니라 미착수의 현재 모습이었다 — 그래서 `unspecified` 로 풀었다.

**풀었더니 세 가지가 차례로 나왔다.** 앞의 것을 고쳐야 뒤의 것이 보였다:

| # | 본 것 | 왜 | 무엇을 했나 |
| --- | --- | --- | --- |
| 1 | 가로로 돌리면 **세로 크기 그대로 좌상단에 90° 누운 채** 그려지고 나머지는 검정 | `preTransform = caps.currentTransform` 은 「내가 이 회전을 **이미** 적용해 그린다」는 선언이다. 우리는 안 돌리고 그린다 | `ROTATE_90/270` 이고 IDENTITY 를 쓸 수 있으면 **IDENTITY 를 요청**한다 |
| 2 | 가로 화면(2400×1080)에 **세로 스왑체인**(1080×2400) | `currentExtent` 를 회전 시 어느 공간으로 주는지는 드라이버마다 갈린다 — 스펙은 90/270 에서 뒤바뀐 값을 말하지만 **이 에뮬레이터는 화면 방향 그대로 줬다** | 크기를 `ANativeWindow` 에게 묻는다 — **매 프레임 리사이즈 검사가 보는 것과 같은 곳** |
| 3 | **5초에 95번** 스왑체인 재생성 | IDENTITY 를 일부러 요청했으니 `currentTransform` 과 영구히 어긋나고, 드라이버가 매 프레임 `SUBOPTIMAL` 로 말한다 | `SUBOPTIMAL` 을 재생성 사유에서 뺀다. 진짜 리사이즈는 위의 창 크기 비교가 잡는다 (그 자리는 「드라이버가 `OUT_OF_DATE` 를 안 준다」는 실측 때문에 이미 있었다) |

**그리고 네 번째가 «눈으로만» 보였다.** 위 셋을 다 고쳐 가로가 제대로 그려진 뒤, 그 상태에서
소프트 키보드를 올렸더니 「Last login…」이 `esc`·`tab` 키 **밑에 깔렸고** 키바 아랫줄은
키보드에 잘렸다. 계약 테스트는 내내 초록이었다 — 격자는 제 바닥(`@max(2, …)`)을 지켰고 키바도
레이아웃이 준 자리에 그렸을 뿐, **둘이 같은 픽셀을 쓴다는 것**을 아무도 안 봤다.

원인은 남는 높이다. 세로 열이 `앱 바(52) + 본문(grow) + 키바(106)` 인데, 가로 1080 에서 키보드가
서면 논리 높이가 그 합보다 얕아진다 → 본문이 0 이 되고 격자는 제 바닥만큼 **사각형 밖으로**
그린다. **키바를 접는 쪽을 택했다** — 키바의 존재 이유는 「소프트 키보드에 없는 키」인데 그걸
남기려다 터미널이 사라지면 앞뒤가 바뀌고, 남겨 봐야 잘려서 못 누른다. 안 그리면 `key_bar_ready`
도 안 서서 없는 키가 눌리지도 않는다(그 규율은 이미 있었다). 문턱은 **본문 두 줄**이고, 그 수는
격자의 바닥과 **같은 상수**(`min_body_rows`)를 본다 — 두 곳이 갈리면 다시 넘친다.

이건 가로 레이아웃을 «정한» 것이 아니라 **넘침을 막는 바닥**이다. 가로에서 키바를 어떻게 할지는
아래 「남은 것」이 소유한다.

**고친 뒤 실측**(에뮬레이터 `zl_poc`, android-36):

| | 세로 | 가로 |
| --- | --- | --- |
| 스왑체인 | `1080x2400 transform=0x1(cur=0x1)` | `2400x1080 transform=0x1(cur=0x2)` |
| 논리 크기 | `411x841` | `865x363` |
| 원격 격자(`MRSV`) | `cols=51 rows=31` | `cols=108 rows=9` |
| 키보드를 올리면 | `cols=51 rows=16`, 키바 **그대로** | `cols=108 rows=3`, 키바 **접힘** |
| 재생성 횟수 | 회전 **한 번당 한 번** (Android 가 창을 부수고 다시 준다) | 같음 |
| 프레임 페이싱 | `median_ms=33.34 target=33.33 PASS` | `median_ms=33.49 PASS` |

**iOS 는 이 축의 결함이 구조적으로 없다.** `Info.plist.in` 에 방향 키가 없어 기본값(위아래 뒤집기
빼고 전부)을 따르고, host 는 크기를 캐시하지 않고 **매 tick `self.bounds` 를 다시 읽어**
`drawableSize` 와 `maru_mobile_available_logical` 에 넣는다 — Android 를 깨뜨린 「캐시한 extent +
선언한 transform」 조합이 아예 없다. **다만 화면으로는 못 쟀다** — 이 환경의 시뮬레이터는 기기
창이 안 열려(`count windows` = 0) Device▸Rotate 메뉴가 **비활성**이다. 그래서 지금 있는 근거는
소스 구조뿐이고, 그 성질이 사라지면 `tests/mobile_rotation_boundary.zig` 가 알린다.

**판정자는 텍스트다 — 그리고 그게 최선이다.** 이 축의 증상은 Vulkan 스왑체인 기하라 GPU 와 창이
있어야 나오는데 CI 에는 둘 다 없다. 그래서 `tests/mobile_rotation_boundary.zig` 가 세는 것은
「그렇게 그려지는가」가 아니라 **「그 결정이 아직 코드에 있는가」**다(위 세 줄 각각).

**남은 것**(이 슬라이스가 안 한 것):

- ~~**가로 레이아웃**(키바)~~ — **닫았다**(두 번째 슬라이스, 아래). 키보드까지 올리면 키바가
  통째로 접혀 Ctrl·Esc·화살표를 못 쓰는 것은 **그대로 남는다** — 그 자리는 높이가 정말 없어서
  접는 것이고(앱 바 52 + 키바 53 + 본문 두 줄 > 남는 높이), 더 벌려면 **앱 바를 숨겨야** 한다.
  그건 「덮개」 계약(U0: 목록이 유일한 길)과 부딪혀 **따로 정할 UX 결정**이다.
- **태블릿·멀티윈도우/분할 화면**. M5 의 나머지 절반이고 아직 미착수다.
- **pre-rotation 으로 옮기기**. 합성 비용을 재고 나서 정한다(위 결정 참조).

### M5 두 번째 슬라이스 — 키바 줄 수는 «폭이» 정한다 (2026-09-05)

첫 슬라이스가 가로를 열었더니 **본문이 아홉 줄**이었다. 앱 바 52 + 키바 106 이 논리 높이 363 에서
158 을 먹는다. 사용자가 「키바를 한 줄로」를 골랐고, **재 보니 그게 손해가 아니었다.**

**기준은 방향이 아니라 폭이다.** 두 줄이 된 이유가 폭이었으므로([UX §5.4](../mobile-ux.md) —
「세로 390 에 44×11 + 3×10 = 514」) 푸는 기준도 폭이어야 한다. 방향으로 가르면 「세로인데 넓은」
태블릿을 틀리게 답한다.

| | 논리 폭 | 한 줄일 때 키 폭 | 두 줄일 때 | 그래서 |
|---|---|---|---|---|
| 폰 세로 | 411 | 29 (**44 미달**) | 62 | 두 줄 |
| 폰 가로 | 865 | **67** | 138 | **한 줄** |

**가로 스크롤은 결국 안 썼다.** 고르실 때 미리보기에 넘침 표시(`‹ ›`)를 그렸는데, 재 보니 가로에서
열둘이 다 들어가고 키가 **오히려 넓어진다** — 밀 것이 없다. 그래서 죽어 있던 스크롤 잔해
(`kb_sa`·`kb_touch`·`key_bar_max_scroll`·`kbScroll`)는 되살리지 않고 **지웠다**.

**실측**(에뮬레이터 `zl_poc`): 가로 `cols=108 rows=9` → **`rows=11`**. 세로는 `cols=51 rows=31`
그대로(회귀 없음).

**판정자 넷**은 「가로면 한 줄인가」가 아니라 **「손가락 크기를 지키며 한 줄에 들어가면 한 줄인가」**를
잰다 — 그래서 **폭만 줄여 가며 문턱을 찾고** 그 양쪽을 본다(방향으로 갈랐다면 그 순회에서 줄 수가
안 바뀐다). 가장 좁은 키가 늘 44 이상인 것과, **하나도 안 숨는 것**도 같이 잰다.

### T — 손가락 id 와 소유권 (진행)

**두 host 가 지금 서로 다르게 동작한다.** 두 손가락으로 밀다가 **첫 손가락을 떼면** iOS 는
제스처가 끝나고(두 번째 손가락은 애초에 안 온다 — `multipleTouchEnabled` 기본값 `NO`),
Android 는 `getX(ev, 0)` 이 남은 손가락을 가리키게 되어 **좌표가 점프한 채 계속 끌린다**.
계약에 어느 쪽이 맞는지 적혀 있지도 않았다.

**그리고 관성을 시간 기준으로 바꾸면서 이 자리가 나빠졌다.** 점프한 `dy` 가 px/ms 속도 계산에
그대로 들어가 상한(`scroll_area.Touch.max_velocity`)까지 튀고, 손을 떼면 **한 번의 손가락 교체가
1600px 를 흘려보낸다**.

**레퍼런스를 소스로 읽었더니 길이 둘이다.** 문제의 뿌리가 "`index 0` 을 쓴다" 가 아니라
**"절대 기준값 하나를 둔다"** 였다:

| | 어떻게 | 소유자가 떼질 때 | 확인 |
|---|---|---|---|
| AOSP `ScrollView` | 절대 기준(`mLastMotionY`) | `onSecondaryPointerUp` — 남은 포인터를 **새 기준으로 잡고** `mVelocityTracker.clear()` | **원문** |
| Flutter `monodrag.dart` | **포인터별 델타**(`PointerMoveEvent.delta`) + 포인터별 `VelocityTracker` | `_giveUpPointer` 가 `_activePointer` 를 남은 것 중 첫 번째로 넘길 뿐 — **재기준도 속도 처리도 없다**(할 게 없다) | **원문** |
| React Native (Android) | 없음 — `ReactScrollView : ScrollView` 이고 `onTouchEvent` 가 `super` 로 넘긴다 | AOSP 것을 그대로 물려받는다 | **원문** |

Flutter 의 `MultitouchDragStrategy.latestPointer`("가장 최근 포인터만 추적, 떼면 다음 포인터가
이어받는다")가 3.19 부터 기본이고, 나머지는 `averageBoundaryPointers`("iOS 관습")·
`sumAllPointers`(3.19 이전 기본)다.

**진짜 병은 "절대 기준" 이 아니라 "기준 하나를 손가락들이 공유하는 것" 이다.** Flutter 도 엔진이
포인터마다 직전 위치를 들고 델타를 만든다 — 기준이 없는 게 아니라 **공유되지 않을 뿐**이다.

**그래서 Flutter 쪽을 고른다.** ABI 는 그대로 절대 좌표를 나르고(hit-test·선택·롱프레스가 이미
쓴다), 코어가 **id 별로** 직전 좌표·속도를 들고 소유자의 것만 화면에 적용한다. 이어받을 때 할
일이 없다 — 새 소유자는 자기 `down` 이후로 이미 자기 기준을 갱신해 왔다. 재기준·속도 버리기는
**빠뜨릴 수 있는 명시적 처리**이고, 이 저장소에서 그 부류가 반복해서 새어 나왔다(감쇠 세 곳·
슬롭 네 곳·반쪽 이관). 빠뜨릴 게 없는 구조가 낫다.

**UIKit 이 다중 터치를 어떻게 합성하는지는 확인하지 못했다** — Apple 문서에 없고 소스도 없다.
통설(무게중심)을 근거로 적지 않는다.

**그래서 소유권 규칙을 코어가 갖고 host 는 id 만 나른다**([계약 §3.1](../mobile-platform.md)).
host 에 두면 두 벌이 되고 두 벌은 갈린다 — 이 저장소에서 관성 감쇠(세 곳)·터치 슬롭(네 곳)·
스크롤 상태(세 곳)가 실제로 갈렸다.

| | 내용 |
|---|---|
| T0 | **계약** — id 의 의미(불투명 정수, `down`~`up` 동안 불변)·소유권·이어받기·재기준·속도 버리기 |
| T1 | **완료** — 세 포인터 함수가 `pointer_id` 를 싣고, `Touch` 가 **손가락별 슬롯**(기준·이번 프레임 이동량·속도)과 `owner` 를 든다. 소유권 규칙 8개를 컴포넌트 테스트가 값으로 잠갔다(이어받기 제거·소유권 무시·슬롯 안 비움 세 변이로 판정력 확인). host 는 **한 줄기 스트림**을 보낸다 — Android 는 `down` 에서 잡은 id 를 끝까지 쓰고(중간에 바꾸면 `up` 이 슬롯을 못 찾아 **소유권이 굳는다** — 구현 중 실제로 만들었다 고쳤다), iOS 는 `UITouch` 에 숫자 id 가 없어 **객체 주소를 접어** 쓴다 |
| T2 | **완료** — Android 가 `ACTION_POINTER_DOWN`/`_UP` 을 받고 `ACTION_MOVE` 는 **닿아 있는 전부**를 보낸다. 첫 `down` 이 목적지를 정하고 그 제스처의 나머지 손가락은 같은 곳으로 간다. 본문 관성은 host 몫이라 소유자가 떼질 때 host 가 기준을 다시 잡고 속도를 버린다(AOSP `onSecondaryPointerUp`). **브리지도 함께 열었다** — 키바·설정·세션 목록·본문이 전부 소유자 기준이 됐고, 특히 **본문은 `pointer_id` 를 버리고 있어 둘째 손가락이 닿으면 선택이 지워졌다**(적대적 검증 1회차). ~~host 만 열면 안 된다~~: 브리지에 한 손가락 전제 상태가 **13개** 남아 있다(`kb_moved`·`kb_pressed`·`kb_down_x/y`·`kb_stop_tap` 과 `set_*` 대응). 둘째 손가락의 `down` 이 `set_down_x/y`·`set_moved` 를 덮어쓰면 **첫 손가락의 "탭이냐 스크롤이냐" 판정이 오염된다** — 이 저장소가 반복해 겪은 반쪽 이관 그대로다. T1 적대적 검증 8회차에서 세었다 |
| T3 | **완료** — `multipleTouchEnabled = YES`, `touches` 전부 순회. `anyObject` 는 **제스처가 없을 때 첫 손가락을 고르는 한 곳**만 남겼고 판정자가 그 수를 잠근다. 제스처의 끝은 `event.allTouches` 로 **마지막 손가락**을 볼 때다 — 손가락마다 끝내면 둘째가 떼는 순간 첫 손가락이 잡고 있던 것이 풀린다. 배경 전환 정리에 복귀 때 본문 잡음을 푸는 자리를 더했다(적대적 검증 1회차 — 안 풀면 복귀 후 **키바·설정이 영영 안 눌린다**). **그때 이름은 `releaseBodyGrab` 이었고 지금은 없다** — 뒤이은 R(라우팅)·G(제스처 상태) 정리가 그 일을 흡수했다. 지금 그 성질을 지키는 것은 `maru_mobile_pointer` 의 **취소 갈래**다: `phase == 3` 이면 chrome·키바·본문 **셋 다에게** 가고 각자 `routeClear()` 로 놓는다(2026-09-05 코드로 재확인). ~~네 자리를 한 커밋에서 다 바꾼다~~ — 반쯤 하면 그 순간 `anyObject` 가 진짜로 임의 선택이 되어, 지금은 없는 결함을 새로 만든다. 판정자로 `anyObject` 사용 0 을 잠근다 |
| T4 | **판정자·문서·두 host 캡처** |

**핀치는 이 축이 아니다**(M13 폰트 줌). 다만 T1 의 "비소유자는 무시하되 **개수는 센다**" 가 그
자리를 열어 둔다.

**두 모델을 적대적으로 비교한 결과가 이 선택의 근거다.** A(기준 하나 + 명시적 이어받기)의 실패는
**누락**이다 — 조용하고, 표면이 늘수록 확률이 커지고, 이 저장소에서 세 번 났다. 게다가 AOSP 가
이어받을 때 부르는 `VelocityTracker.clear()` 는 **두 손가락으로 세게 밀다 하나를 떼며 놓는
손짓의 관성을 죽인다**. B(손가락별 기준)의 실패는 국소적이고 열거된다 — 슬롯 초과·모르는 id·
샌 슬롯, 셋 다 규칙 한 줄과 테스트 하나로 닫힌다. 그리고 이어받기 코드가 **없으므로** 다음
표면(M12 세션 전환)이 붙을 때 추가로 기억할 것이 없다.

**B 의 진짜 위험은 상태 크기가 아니라 T3 다** — 위 표에 적은 대로 원자적으로 바꾼다.

#### 남은 것 — 이 축과 분리한다

| | 판단 | 왜 분리하나 |
|---|---|---|
| **제스처 상태기계**(→ G, 아래) | 한다 | 근거가 다르다 — `kb_active`·`set_active`·`set_stop_tap`·`set_moved` 가 흩어져 있고 실제로 그중 하나가 톱니 판정으로 새어 **설정이 안 열렸다**. 손가락 id 와 묶을 이유는 없다 |
| **제스처 조합(arena)** | **안 한다** | RNGH 가 그것을 갖는 이유는 사용자가 임의로 중첩한 뷰들이 경쟁하기 때문이다. 우리 표면은 `chrome → 키바 → 본문` 셋이고 우선순위를 우리가 정한다 — 답이 하나로 정해진 협상에 협상 기계를 들이는 꼴이다. 중첩 스크롤이 생기면 재검토 |
| ~~좌우 inset(곡면·waterfall)~~ | **완료**(코드로만 — 이 에뮬레이터는 좌우가 0 이라 화면으로 못 본다) | `queryInsets` 가 top·bottom 만 읽는다. waterfall 컷아웃은 좌우 53px 를 요구하고(실측), 그 기기에서는 **본문 양끝 글자가 모서리에 말린다**. 홀펀치 기기에서는 안 드러나서 오래 잠복할 자리다 |
| ~~마우스·트랙패드 스크롤~~ | **Android 완료** | `ACTION_SCROLL` 을 받아 코어가 줄로 환산한다. **iOS 는 남았다** — 제스처 인식기를 안 써서 트랙패드 스크롤이 안 온다 |

### A — 터미널 앱 바 (뒤로가기)

**터미널에서 돌아갈 길이 안 보인다.** U3b 가 하단 바를 걷어내며 터미널 화면의 chrome 을 통째로
없앴고, 남은 길은 가장자리 스와이프뿐이다 — iOS 관례지만 **보이지 않고**, Android 는 시스템
뒤로가기가 따로 있어 두 플랫폼이 갈린다(사용자 요청 2026-08-17).

| | 내용 |
|---|---|
| A0 | **계약** — 상단 바를 둔다·높이는 다른 화면과 같다·오른쪽은 비운다([UX](../mobile-ux.md)) |
| A1 | **그리기와 배치** — 앱 바 52, 본문은 그만큼 줄어든다(격자 재계산이 따라와야 한다) |
| A2 | **누르기** — chrome 이 터미널 화면에서도 그 띠를 받는다(지금은 `screenTop() == .terminal` 이면 통째로 0 을 낸다). 눌림 표시·`Press` 는 다른 화면과 같은 규칙 |
| A3 | **판정자·기기** — 본문 줄 수가 실제로 줄었나, 바를 눌러 돌아가나, 바 위 터치가 본문·키바로 안 새나 |

**A1 을 A2 보다 먼저 두는 이유**는 배치가 틀리면 히트 자리도 같이 틀리기 때문이다 — 두 개를
한 커밋에 묶으면 "안 눌린다" 가 배치 탓인지 라우팅 탓인지 못 가른다(U1 에서 겪었다).

### G — 제스처 상태기계

**표면마다 제스처 상태를 하나로 모은다**(계약 §3.1 "한 제스처의 뜻은 상태 하나가 든다").
지금은 `set_active`·`set_moved`·`set_stop_tap`·`sess_pressed`·`kb_stop_tap`·`kb_moved`·
`ptr_down`·`ptr_moved`·`selecting` 이 흩어져 있고, "탭이다" 가 자리마다 다시 만들어진다 —
읽는 자리가 `set_active` 10 · `set_moved` 10 · `selecting` 8 · `ptr_moved` 7 곳이다(실측).

**이 축에서 실제로 난 결함들**: 조합 한 항이 톱니 판정으로 새어 설정이 안 열렸다 · 선택으로
들어갈 때 관성 속도를 안 거둬 떼는 순간 화면이 미끄러졌다(#2309) · 세션 목록이 설정 화면의
변수를 그대로 쓰고 있다.

| | 내용 |
|---|---|
| G0 | **계약** — 상태·전이·`stop_tap` 의 자리. 무엇을 안 하는지(arena)도 같이 |
| G1 | **컴포넌트** — `chrome.ui.gesture.Press` 와 단위 테스트. 아직 아무도 안 쓴다 |
| G2 | **설정·세션 목록 이관** — 여기서 두 화면이 나눠 쓰던 변수를 **가른다** |
| G3 | **키바 이관** — `kb_stop_tap`·`kb_moved`·`kb_pressed` |
| G4 | **본문 이관** — `ptr_down`·`ptr_moved`·`selecting`, 그리고 시계가 필요한 `long_pressed` |
| G5 | **판정자** — "표면마다 Press 하나"·"흩어진 bool 이 없다" |

G1 을 먼저 두는 이유는 **되돌릴 자리를 만들기 위해서다** — 컴포넌트가 틀린 것과 이관이 틀린
것은 별개이고, 한 커밋에 묶으면 회귀가 났을 때 어느 쪽인지 못 가른다(R 에서 같은 이유로 나눴다).

**표면마다 따로 옮긴다.** 셋을 한 번에 바꾸면 화면이 깨졌을 때 어느 이관이 깼는지 모른다 —
U1 에서 키바를 다시 짜며 겪었다(계약 테스트가 전부 통과하는 동안 화면은 깨져 있었다).

### R — 포인터 라우팅 통합 (완료)

**host 가 "이 터치를 어디로 보낼지" 를 판정한다** — 계약 §3 이 금지한 그것이다. ABI 진입점이
셋(`chrome_pointer`·`keybar_pointer`·`pointer`)이고, 어느 것을 부를지는 host 가 `chrome_active`·
`keybar_active` 로 정한다. 같은 상태가 **두 층에 두 벌** 있어서 배경 전환 정리를 host 마다 세 번
해야 하고, 실제로 한 번 빠뜨려 "복귀 후 첫 손짓이 통째로 삼켜지는" 결함이 났다. iOS 주석이 그 값을
그대로 적고 있다 — "브리지와 뷰 **양쪽**을 푼다".

Flutter 는 진입점이 하나이고 `down` 에서 한 번 hit-test 한 뒤 그 포인터의 경로를 기억한다
(`PointerRouter`). 우리도 같은 모양으로 간다: **`maru_mobile_pointer(phase, id, x, y, time)` 하나**로
모으고 라우팅은 코어가 `route[pointer_id]` 로 든다.

**T 를 끝내고 다시 쟀다**(2026-08-17):

| | 계획 작성 시 | T 뒤 |
|---|---|---|
| host 라우팅 상태 | 21곳(Android 10 · iOS 11) | **29곳**(Android 18 · iOS 11) |
| 계약 테스트의 직접 호출 | 68곳 | **60곳** |
| 브리지 진입점 | 3 | 3 → **1** |

T2 가 Android 를 다중 포인터로 재구성하며 라우팅 상태가 늘었다 — **미룰수록 커지는 쪽**이라
순서를 R 로 잡은 것이 맞았다.

**T 다음에 하는 이유**는 이것이 **동작이 안 바뀌는 리팩터**이기 때문이다. 살아 있는 결함 위에 큰
리팩터를 먼저 얹으면 어느 쪽이 깼는지 판정이 안 된다.

#### 진짜 난이도는 테스트의 **판정 방식**이 바뀌는 것이다

지금 `chrome_pointer`·`keybar_pointer` 는 **"내가 먹었다" 를 반환값으로** 돌려주고 host 가 그것으로
라우팅한다. 진입점을 하나로 모으면 그 반환값이 사라진다. 그러면 **"chrome 이 안 먹는다" 를
반환값으로 단언하던 테스트**들은 재는 자리를 옮겨야 한다 — 반환값이 아니라 **효과**로(본문이
받았으면 셀 판정이 서고, 키바가 받았으면 키 바이트가 나간다).

이것은 기계적 치환이 아니다. **"무엇을 재고 있었나" 를 테스트마다 다시 정해야** 하고, 잘못 옮기면
[통과 보장 테스트](../mobile-platform.md)가 된다(이 저장소에서 `keyBarVisible` 이 늘 참인 술어로
남아 네 곳의 조건이 죽은 적이 있다). 그래서 R 은 **슬라이스를 나눈다**:

| | 내용 |
|---|---|
| R0 | **계약** — 진입점 하나, 라우팅은 코어가 `down` 에서 정해 그 제스처 동안 유지. 반환값의 뜻이 무엇으로 바뀌는지 |
| R1 | **코어가 라우팅을 든다** — 세 함수는 남기되 내부를 한 경로로 모은다(동작·테스트 무변화). 여기서 라우팅 규칙이 값으로 잠긴다 |
| R2 | **진입점을 하나로** — 두 host 의 라우팅 상태 29곳을 지운다. 테스트 60곳을 **효과 기준으로** 옮긴다 |
| R3 | 판정자 — "host 에 라우팅 상태가 없다"·"진입점이 하나다" |

**R 이 만든 회귀 하나를 뒤이어 닫았다 — 관성이 host 에 남아 있었다.** host 에서 라우팅 지식을
걷어냈는데 **그 지식을 쓰던 관성 가드**(`if (!chrome_active && !keybar_active && …)`)를 대체 없이
지웠다. 그래서 키바를 비스듬히 튕기면 그 세로 성분이 본문 관성으로 새어 화면이 흘렀다
(재현: view_offset 18 → 16, 계약 테스트). **관성을 코어로 옮겨** 닫았다 — 키바·설정 관성이 이미
거기서 돌고 있었으므로 본문만 예외였던 셈이다. 두 host 에서 관성 코드가 통째로 사라졌고
(`fling_vy`·`_flingVy`·감쇠 루프·속도 측정), 헤더의 `MARU_FLING_*` 미러 상수도 함께 없앴다 —
값의 단일 출처는 `scroll_area.Touch` 하나다. 기기 확인: Android 녹화에서 스와이프(0.25초)마다
움직임이 0.7초까지 이어지며 감쇠했고(관성 생존), 키바 대각선 튕김 전후로 view_offset 이 두
플랫폼 다 그대로였다(Android 31→31 · iOS 53→53).

**넷 다 끝났다**(R0·R1 = PR#2296, R2·R3 = 이 변경). 잰 값은 계획대로 0 으로 갔다 — host
라우팅 상태 29곳 → **0**, 브리지 진입점 3 → **1**, 헤더 선언 51 → **49**. 배경 전환 정리는
host 마다 세 번에서 **한 번**이 됐다(목적지를 host 가 더는 모르니 취소 하나면 전부 놓인다).
테스트 60곳 중 **반환값을 실제로 단언하던 것은 셋뿐**이었고 그 셋만 `currentRouteName()` 으로
옮겼다 — 나머지 57곳은 부르기만 했다. 계획이 걱정한 "재는 자리를 통째로 옮기는 일" 은
**세 곳짜리 일**이었다는 뜻이다.

R1 을 먼저 두는 이유는 **되돌릴 자리를 만들기 위해서다** — 라우팅이 코어에서 도는 것과 진입점이
하나인 것은 별개 변경이고, 둘을 한 커밋에 묶으면 회귀가 났을 때 어느 쪽인지 못 가른다.

**Reanimated 는 해당 없다.** 그것이 푸는 문제는 JS 브리지 왕복을 피해 UI 스레드에서 도는 것인데,
우리는 브리지가 없다 — 터치 콜백에서 Zig 판정이 동기로 돌고 렌더러도 같은 프로세스다.

## M6 — 아틀라스 축출 (완료)

**아틀라스가 차면 그 뒤 글자가 조용히 사라졌다.** `atlas_add` 가 꽉 차면 그냥 `return` 했고
`next_slot` 은 sentinel 을 냈다 — 새 글자는 미스로 올라오는데 구울 자리가 없어 영영 안 그려진다.
오류도 로그도 없다. 512칸은 데모 피드로는 안 차서 아무도 안 보고 있었지만, **원격을 붙이면
실제 셸이 금방 채운다**(ASCII + 한글 + CJK + 박스 문자, 굵게/기울임이 각각 별도 슬롯).

**프레임 순번 LRU 로 정했다**(계약 §4). 고칠 때 두 번 틀렸고 실측으로 고쳤다 — 좌표로 victim 을
되찾으면 같은 좌표 항목이 둘일 때 엉뚱한 것을 덮어써 다섯 중 하나만 등록됐고, 하네스가 미스
목록을 역순으로 안 훑어(swap-remove) 대조군이 5개 중 4개만 구워졌다.

**host 는 안 바꿨다** — 두 플랫폼 다 이미 슬롯을 0 으로 지운 뒤 전체를 올려 잔상이 안 남는다.

남은 것은 **용량 자체**(512가 맞는 수인지)와 **성능 예산**이고 둘 다 실기기가 있어야 잰다.

## 코드 리뷰 후속 (M2 뒤)

`/code-review high` 가 13건을 냈고 **상위 여섯이 제품 경로 결함**이었다. 10라운드 적대적
검증이 문서·구조 정합성에 치우쳐 **오래 돌 때 생기는 것**을 못 봤다 — 시뮬레이터에서 몇 초
띄워 스크린샷만 확인했으니 512바이트도, 재개 후 글리프 손실도 드러날 수가 없었다.

| 결함 | 상태 | 검증 |
|---|---|---|
| 입력이 512바이트에서 영구히 죽음 | 수정 | **재현→해소**(`total=512` 고정 → `total=1995`) |
| 아틀라스 여유 슬롯 15개 | 수정 | **재현→해소**(성장 27자, 384x1024) |
| 미스 목록 swap-remove 로 절반 건너뜀 | 수정 | 배치당 8·6자로 늘어남 |
| 재개 후 성장 글리프 소실 | 수정 | 원본 버퍼에도 기록(경로 검증은 미실시) |
| 제품이 `/data/local/tmp` 의존 | 수정 | **tmp 를 비우고 정상 기동 확인** |
| 단폭 셀 종횡비 | 수정 | 화면 대조 |
| teardown 이 자식을 안 지움 | 수정 | 코드 검토(누수 계측 미실시) |
| 스왑체인 재생성 없음 | 수정 | **재현 불가**(아래) |
| `chor_started` 잔존 · 100% CPU 스핀 | 수정 | 코드 검토 |
| quad 버퍼 넘침이 조용함 | 수정 | `last_error` 로 노출 |
| 미리 굽는 글자 집합 중복 | 수정 | 헤더 단일 출처 |
| push 전용 job 의 무의미한 draft 가드 | 수정 | — |

**스왑체인 재생성은 이 환경에서 재현하지 못했다.** `wm size` 로 표시 해상도를 바꿔도
`vkAcquireNextImageKHR` 이 계속 `VK_SUCCESS` 를 돌려주고, `vulkan_recreated`·새 `logical=`
로그가 하나도 안 나오는데 화면은 새 크기로 맞아 보인다 — **SurfaceFlinger 가 낡은 버퍼를
늘려 준 것**이다(그 둘이 동시에 참인 다른 설명이 없다). 액티비티가 portrait 고정이라
`wm size` 는 앱 surface 를 리사이즈하지 않고 디스플레이만 바꾼다.

그래서 두 겹으로 고쳤다: (1) `OUT_OF_DATE`/`SUBOPTIMAL` 을 받으면 다시 만든다(스펙 경로),
(2) **매 프레임 창 크기를 직접 비교**한다 — 드라이버가 안 알려 줘도 잡히도록. 실기기에서
회전으로 확인해야 한다.

**에뮬레이터로 회전을 볼 수 있다**(2026-09-05 확인) — 위 「실기기」는 필요조건이 아니었다.
`AndroidManifest.xml` 의 `screenOrientation="portrait"` 를 `unspecified` 로 바꾸고
`adb shell settings put system accelerometer_rotation 0; ... user_rotation 1` 이면 돈다
(`dumpsys window` 의 `mRotation=ROTATION_90` 으로 확인).

### 페이싱 정책화 뒤 적대적 검증

**choreographer 체인이 배경↔복귀마다 늘어났다.** teardown 이 `g` 를 memset 해 소유 플래그가
지워지고, 재개할 때 새 체인을 거는데 **이미 떠 있던 체인은 스스로 다시 등록하며 살아남는다**.

계측이 그대로 판정자가 됐다 — 체인이 늘면 `drawFrame` 이 더 자주 불려 median 이 짧아진다.

| 왕복 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 1~2회 | 33.4 ms | 33.5 ms |
| 3~4회 | **16.7 ms**(주기 두 배) | 33.3 ms |

플래그를 `g` 밖으로 뺐다 — 체인은 앱 수명 동안 하나면 되고, 창이 없을 때는 `drawFrame` 이
알아서 쉰다.

### 리뷰 수정 뒤 적대적 검증

**내 수정이 결함을 하나 다시 만들었다.** 미스 목록을 스냅샷하려고 host 마다 `want[64]` 를
뒀는데, 그 `64` 는 Zig 의 `miss_cp` 크기와 같아야 하는 값이라 **5라운드에서 고친 셀 기하
중복과 같은 종류**였다. 스냅샷을 버리고 **역순 훑기**로 바꿨다 — 지워지는 자리가 항상
훑은 뒤쪽이라 앞쪽이 흔들리지 않고, host 가 목록 크기를 알 필요가 없어진다.

**오래 돌 때를 실제로 쟀다**(지난 검증이 빠뜨린 축).

| 확인 | 결과 |
|---|---|
| 배경↔복귀 8회 PSS | 62077 → 62069 KB (평평 — teardown 누수 없음) |
| 왕복 뒤 렌더 재개 | `quads=148` 재출력 |
| 아틀라스 성장 반복 | 배치마다 2~7자, 멈추지 않음 |
| 512바이트 넘는 입력 | `total=1995` 까지 전달 |

### 오래 사는 상태를 겨눈 적대적 검증

지난 라운드들은 **한 프레임**을 봤다. 이번에는 "여러 번 반복하면" 을 겨눴고, 그 축에서만
다섯 건이 나왔다. 셋은 실제로 앱을 죽이거나 화면을 지웠다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| 코어가 512KB 고정 버퍼 위에 서 있어 **resize 7번**이면 OOM | 헤드리스로 셈(`7번째 resize 에서 OutOfMemory`) | 수정 |
| resize 실패해도 크기 기록을 덮어 **없는 셀을 읽음** | 테스트에서 재현(`index 1320, len 1320`) | 수정 |
| staging 버퍼를 안 지운 채 device 파괴 → **SIGSEGV** | 창 크기 9회 변경으로 앱 사망, 툼스톤 `on_vkDestroyDevice_pre` | 수정 |
| 입력의 실패가 다음 build 의 `memset` 에 지워짐 | 코드 검토(§5 가 약속한 경로에서만 신호가 안 남음) | 수정 |
| Android 입력은 UI 스레드, 렌더는 native 스레드 — **동기화 없음** | logcat tid 대조(14832 vs 14850) | 수정 |

세 번째가 제일 컸다. 리뷰 때 "teardown 이 자식을 안 지움" 을 **코드 검토만으로** 닫았는데,
그때 본 것은 `teardownVulkan` 안이었고 진짜로 남는 자식은 **업로드 함수 안**에 있었다.
같은 표를 다시 보니 "누수 계측 미실시" 라고 내가 적어 뒀다 — 그 자리가 정확히 터졌다.

수정 뒤 같은 시나리오를 20회로 늘려 다시 돌렸다: **재생성 21회, 오류 0, 크래시 0**, 이후에도
`quads=148 / calls=1` 로 계속 그린다.

이 다섯 중 넷은 `tests/mobile_bridge_contract.zig` 로 내려 `zig build test` 에서 돈다(브리지가
OS 를 안 부르므로 시뮬레이터가 필요 없다). **옛 코드에서 실제로 깨지는 것까지 확인**했다 —
안 그러면 회귀 테스트가 아니다.

### 용량 한계를 겨눈 적대적 검증

앞 라운드가 "오래 돌면" 이었다면 이번은 **"꽉 차면"** 이다. 셋이 나왔고, 그중 둘은 서로 물려
있었다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| quad 버퍼 2048 — 태블릿 크기에서 **격자만으로 넘침**(폰 세로도 1828/2048) | 헤드리스로 네 크기 측정 | 수정 |
| Android 는 4096 에서 **조용히 자름**, iOS 는 늘림 — 상한이 서로 다름 | 두 host 코드 대조 | 수정 |
| 새로 넣은 뮤텍스가 **아틀라스 굽기(GPU 대기)까지** 감쌈 → 타이핑이 GPU 를 기다림 | 잠금 구간 재검토 | 수정 |

둘째가 이번 라운드의 교훈이다. **첫째를 고치자 둘째가 live 가 됐다** — 버퍼 상한을 2048 에서
12768 로 올리는 순간 Android 의 4096 이 실제로 자르는 값이 된다. 상한을 host 마다 적어 두는
구조 자체가 원인이라, 값을 옮기는 대신 **코어가 답하게** 했다(`maru_mobile_max_quads`).

의심 하나는 측정으로 닫았다. 아틀라스 조회가 셀마다 선형 탐색이라 큰 격자에서 비쌀 줄
알았는데, 꽉 찬 화면의 build 가 **0.04ms(폰) / 0.10ms(태블릿, 등록부 495개)** 였다 — 30Hz
예산 33.3ms 대비 무시할 수준이다. 자료구조를 바꿀 이유가 없다.

### "누가 치우는가" 를 겨눈 적대적 검증

앞 두 라운드가 "오래 돌면"·"꽉 차면" 이었다면 이번은 **"코어가 만든 것을 누가 가져가는가"**
와 **"계약 문구가 실제로 참인가"** 다.

| 결함 | 어떻게 드러났나 | 상태 |
|---|---|---|
| 코어가 만든 답(DA·DSR)을 **아무도 안 치움** — 질의 3000번에 15005바이트 | 데스크톱 소비처 grep → 모바일에 없음, 누적량 실측 | 수정 |
| `maru_mobile_input` 반환값이 **닿지도 않은 바이트를 셈** | 헤더 문구와 코드 대조 | 수정 |
| 조합 중 문자열이 셀 **밑에** 깔림(주석은 "위" 라고 적혀 있었다) | 그리는 순서 확인 | 수정 |
| 지난 라운드에 넣은 drift 로그가 매 프레임 도배 가능 | 내 코드 재검토 | 수정 |

첫째가 이번의 본체다. 데스크톱에는 `pendingResponse` 를 PTY 로 흘리고 `clearResponse` 하는
자리가 두 군데 있는데(`runtime.zig`·`pty_reader.zig`), 모바일에는 **그 자리 자체가 없었다**.
오늘도 ESC 를 누르고 `[c` 를 치면 닿는 경로이고, 원격 세션이 붙으면 셸이 알아서 질의한다.
흘려보낼 곳이 없는 지금은 버리는 게 맞지만, **조용히** 버리면 §5 를 어긴다.

`maru_mobile_take_response` 같은 ABI 를 지금 뚫는 것은 **소비처 없는 인터페이스**가 되므로
하지 않았다 — M3 에서 원격 쪽을 정할 때 함께 낸다.

### 코어 API 전수 대조 (데스크톱 ↔ 모바일)

지난 세 라운드의 결함이 전부 같은 자리에서 나왔다 — **데스크톱이 이미 하는 일을 모바일이
안 하는 곳**. 그래서 짐작하지 말고 `TerminalCore` 의 공개 API 109개를 전수로 갈랐다:
데스크톱(`src/app`·`src/platform/macos`·`src/chrome`)은 부르는데 모바일은 안 부르는 것이
**76개**.

대부분은 이름 충돌(`eql`·`hash`·`push`)이거나 아직 안 만든 기능이라, 두 부류로 다시 갈랐다.

**(가) 코어가 만드는데 가져갈 사람이 없는 것** — 지난 라운드 `pendingResponse` 와 같은 부류.
짐작 대신 **실제로 쌓이는지 쟀다**.

| 생산자 | 안 치우면 | 판정 |
|---|---|---|
| `pendingResponse` | 질의 3000번에 15005바이트, 무한 | **수정**(지난 라운드) |
| `shellEvents` | 상한 4096 에 닿고 **그 뒤 전부 드롭 + overflow 영구** — 프롬프트 사이클 2000회면 닿는다 | **수정** |
| `pendingClipboardWrite` | 1000번 써도 5바이트(덮어쓴다) | 유계 |
| `pendingNotification` | 슬롯 하나(최신만) | 유계 |
| `bellPending`·`clipboardReadPending` | bool | 유계 |
| 스크롤백 | 기본 상한 1000행에서 평평(2만 줄 먹여도 1000) | 유계 |

`shellEvents` 는 코어 주석이 **"프레임마다 drain 되면 닿을 일이 없다"** 고 전제하는 자리다.
모바일은 안 했다. 메모리는 유계지만 소비자(에이전트 상태·프롬프트 표시)가 생겼을 때 낡은
4096건과 선 채로 굳은 overflow 를 물려받는 함정이라, 쓰는 자리에서 함께 비운다.

덤으로 **모바일 코어의 메모리 평형점**을 얻었다: 80x24 격자 + 스크롤백 1000행에서 약
1.35MB(할당 바이트 실측, 평평해진 뒤).

**(나) 계획에 없던 기능 공백.** 나머지는 대부분 M4b·M9~M16 이 이미 안고 있었지만 둘이 빠져
있었다.

  - **키가 `core.encodeKey` 를 안 탄다.** 모바일은 `\r`·`0x7F`·`\t`·`\x1B` 를 손으로 적어
    넣는다. 데스크톱은 모든 키를 인코더에 태워 DECCKM(커서키 모드)·수정자(Ctrl·Alt)·kitty
    프로토콜·Option-as-Meta 를 처리한다. 계획에는 "보조 키바" 만 있어서, **키바를 만들어도
    바이트를 직접 적으면 인코딩이 틀린다**. 키바는 UI 고, 그 앞에 키 이벤트 ABI 가 필요하다.
  - **포커스 보고(DEC 1004)가 없다.** 데스크톱은 포커스 변화를 CSI I/O 로 흘린다(vim 의
    FocusGained/Lost). 모바일은 배경↔복귀가 데스크톱보다 훨씬 잦은데 아무것도 안 보낸다.

둘 다 M4b 앞에 놓는다 — 키 인코딩은 키바의 **선행 조건**이다.

### chrome/renderer · config 전수 대조

코어 API 대조가 값을 했으므로 같은 방식을 chrome/renderer 모듈(45개)과 config 키(93개)에
돌렸다. **가장 큰 것이 나왔다** — 모바일은 maru 의 합성 글리프 경로를 아예 안 탄다.

**합성 글리프.** `renderer.synthesizeGlyph` 는 "rasterizer 는 폰트 경로 **전에** 이걸 한 번
호출한다" 가 계약인 dispatch 단일 출처다. 박스 드로잉(U+2500~257F)·블록(U+2580~259F)·
브라유(U+2800~28FF)·파워라인(U+E0B0~)·legacy mosaic 을 **폰트 대신 절차 합성**해 셀에 꽉
채운다("폰트 글리프는 셀에 안 맞아 gap·흐림·끊김"). 두 모바일 host 는 그냥 폰트로 굽는다.

데모 대본에 TUI 한 줄을 넣어 화면으로 확인했다(`tools/mobile-harness/out/synth-before-android.png`):
박스가 **끊기고**, 블록에 **이음매**가 보이고, 브라유가 어긋난다. 계약 주석이 예고한 그대로다.

**그런데 호출만 추가해서는 못 고친다.** 모바일의 글리프 기하가 격자와 안 맞기 때문이다:

| | 값(논리 px) |
|---|---|
| 격자 한 칸 | **5 × 22** (열 간격 `cw/2`, `line_h = font_px + 7`) |
| 그리는 quad | **11 × 15** (`w = cw`, `h = font_px`) |
| 아틀라스 셀 | 24 × 32 (셰이더가 이 전체를 quad 에 매핑) |

폰트 글리프는 잉크가 셀 안쪽에 앉아 이 어긋남이 안 보인다. 합성 글리프는 **셀을 가장자리까지
채우는 것이 목적**이라 곧바로 드러난다 — 블록(█)은 세로로 7px 뜨고 가로로 6px 겹친다.
즉 **기하 정합이 합성의 선행 조건**이다. M4a3 으로 세운다.

**셀 속성.** terminfo 축으로도 봤다. `xterm-maru` 는 truecolor(`Tc`)·Sync 를 광고하는데,
모바일은 원격 전용이라 `TERM` 을 스스로 정하지 않는다 — 원격 PC 의 maru 세션이 이미 그 값으로
셸을 띄우므로 모바일이 terminfo 를 들고 갈 일은 없다. **문제는 그 광고를 렌더가 뒷받침하는가**
쪽이었다: 코어가 담는 셀 속성 12개 중 모바일은 `foreground` 하나만 읽는다. 대본에 SGR 한 줄을
넣어 화면으로 확인했다 — `bg`·`rev`·`under`·`bold` 가 전부 똑같은 평범한 글자다. 배경색은
상태줄·선택·`ls` 색이 전부 쓰는 것이라 M4a4 로 세운다.

**config.** 모바일이 config 를 안 읽는 것은 이미 계약 §7 에 있다. 대조로 새로 나온 것은
**같은 값이 여러 곳에 흩어져 있다**는 쪽이었다: 굽는 글자 크기 22 가 네 곳(iOS 2·Android 2)에
따로 적혀 있었다. 셀 크기는 헤더가 소유하는데 **그 셀을 채우는 크기**는 아니었다 — 한쪽만
고치면 두 플랫폼이 다른 굵기로 구워 픽셀 대조가 조용히 무의미해진다. `MARU_ATLAS_TEXT_PX`
로 올렸다.

나머지 모듈 공백은 대부분 이미 계획이 안고 있다(`state`·`input`·`interaction`·`intent_table`
→ M4a·M12, `scroll_area` → M4b, `typography`·`text_layout` → 아래 참고). 하나만 짚어 둔다:
모바일은 텍스트 배치를 `pushText` 로 직접 한다 — chrome 텍스트는 `appendEllipsizedTitle`
경유가 계약인데(cluster 모델) 그 경로를 안 탄다. chrome 라벨이 길어지면 말줄임이 없다.

### M2b 한글 IME — 여기서 멈춘 이유

`UITextInput` 까지는 넣었다(일본어·중국어 marked text 경로는 그것으로 선다). 한글만 남았고,
남은 일이 **휴리스틱 판단**이라 사용자 결정 전에는 안 넣는다.

확인된 사실: iOS 한글은 `setMarkedText` 를 안 쓰고 `deleteBackward`+`insertText` 로 마지막
음절을 갈아 끼운다. 우리가 `UITextInput` 을 구현하고 UIKit 이 그것을 쓰는 것까지 확인한
뒤에도 그렇다(`MARU_IME protocol=UITextInput` 이 찍히는데 조합은 안 온다). 같은 동작이
다른 iOS 프로젝트에서도 보고돼 있다(동작 비교만 참조 — 구현은 안 봤다).

남은 선택은 둘이고, 어느 쪽도 공짜가 아니다:

| 방식 | 장점 | 위험 |
|---|---|---|
| 패턴 기반(직전 insert 와 길이가 같은 backspace) | 언어 분기 없음 | **방금 친 글자를 backspace 로 지우는** 흔한 동작과 구분 불가 |
| 한글 범위 기반(자모·음절일 때만) | 오탐 없음 | 언어 특정 분기가 계약에 들어간다 |

**Android 는 별개로 여전히 미검증이다** — 에뮬레이터 Gboard 에 한국어 언어팩이 없고 받을
경로도 없다(Play 스토어 없는 이미지). 실기기 항목이다.
### M4a5 커서 렌더 (완료)

커서를 안 그리고 있었다. 그래서 화살표를 코어의 인코더에 태워 놓고도(M4a2) **눈으로 확인할
방법이 없었고**, 스크롤·선택도 같은 처지가 된다 — 로그가 유일한 판정자인 상태를 끝낸다.

모양도 표시 여부도 **코어가 정한다**. 블록은 **반투명**으로 얹는다(불투명하게 칠하면 그 칸
글자가 사라진다 — 전경/배경 맞바꿈은 셀 속성 reverse 가 하는 일이다).

| 확인 | 결과 |
|---|---|
| 타이핑 추적 | `abcdefgh` 뒤에 커서가 정확히 붙는다(화면 대조) |
| 세 모양 | 블록·밑줄·막대가 **화면에서 서로 다르게** 나온다(DECSCUSR `2 q`·`4 q`·`6 q`) |
| 숨김 | DECTCEM `CSI ?25 l` 로 사라지고 `h` 로 돌아온다(계약 테스트) |

계약 테스트는 "quad 가 하나 더 난다" 까지만 본다 — 셋 다 블록으로 그려도 그 수는 같으므로
**모양이 갈리는지는 화면으로** 확인했다.

### M4a4 셀 속성 렌더 (완료)

코어가 셀에 담는 속성 12개 중 **전경색 하나만** 읽던 것을 전부 푼다. 규칙은 데스크톱과 같은
것을 쓴다(reverse 는 default 를 테마 값으로 푼 뒤 맞바꾸고, dim 은 배경 쪽으로 절반 보간,
conceal 은 전경을 배경색으로).

**굵게·기울임은 아틀라스 키를 바꿔야 했다.** 같은 글자라도 다른 글리프라 슬롯이 따로 있어야
한다 — 키가 코드포인트뿐이면 굵은 판이 보통 판을 덮어써서 **한 줄이 굵어지는 순간 그 글자가
화면 전체에서 굵어진다**. 등록부 키를 코드포인트+스타일로 바꾸고, ABI 도 그에 맞춰
넓혔다(`atlas_add` 에 style, `missing_style` 추가). 가짜 굵게 대신 **번들 폰트 네 판**을
쓴다 — 가짜는 advance 가 달라져 자간이 어긋난다.

**quad 예산이 함께 바뀌었다.** 한 칸이 최대 6 quad(배경·밑줄·이중밑줄·취소선·윗줄·글자)를
내므로 최대 격자에 곱하면 3.5MB 다. 정적으로 잡는 대신 **격자를 따라 자라게** 했다 — 폰의
실제 최악은 3577 개였고(실측), 자라는 시점은 리사이즈뿐이라 플랫폼이 GPU 자원을 다시 세우는
순간과 겹친다. 배경·장식선은 같은 색이 이어지는 구간을 하나로 묶어 그린다(안 묶으면 80x24
에서 배경만 1920 개다).

| 확인 | 결과 |
|---|---|
| 두 플랫폼 화면 | **12개 전부** 눈으로 확인 — 배경(44)·반전(7)·밑줄(4)·굵게(1)·흐림(2)·기울임(3)·이중밑줄(21)·취소선(9)·윗줄(53)·밑줄색(58, 빨강)·숨김(8, 안 보임). 밑줄은 그 구간에만 걸린다 |
| 밑줄 자리 | **처음엔 틀렸다** — 칸 높이(22) 기준으로 잡아 글자 상자(15)에서 5 논리 px 떨어져 줄 사이에 떴다(픽셀 실측). 글자 상자 기준으로 옮겨 붙였다 |
| quad 버퍼 성장 | 기기에서 **두 단계 실측**: `n=1542 cap=1536` → 재생성 → `n=3076 cap=3072` → 재생성 → `quads=3082 calls=1` 로 온전히 그림 |
| 최악 quad(칸마다 색·장식이 다름) | 폰 3577 / 태블릿 12615 — 상한이 그만큼 따라 늘어 안 잘림 |
| 계약 테스트 | 8개(굵기가 다르면 다른 슬롯을 쓴다 포함) |

**여기서 오래 헤맸고, 원인은 내 결함이었다.** Android 를 돌리려 할 때마다 에뮬레이터가
사라져서 "표준 포트 대신 임의 IPv6 포트에 바인딩하는 환경 문제" 로 진단했다. 틀렸다.
에뮬레이터 로그의 마지막 줄이 답이었다:

```
Assertion failed: (pCreateInfo->size > 0), function vk_buffer_init
```

quad 버퍼를 동적 성장으로 바꾸면서 `maru_mobile_max_quads()` 가 **첫 build 전에 0** 을
돌려줬고, Android 는 창이 서는 순간(=build 보다 먼저) 그 값으로 GPU 버퍼를 잡는다. 크기 0
짜리 `VkBuffer` 가 드라이버 단언에 걸려 **에뮬레이터를 통째로 abort** 시켰다. iOS 는 매 프레임
용량을 다시 보므로 첫 프레임에 0 이어도 살아남아, **한쪽만 죽는 비대칭**이 원인을 가렸다.

거기에 두 번째 함정이 겹쳤다 — abort 가 크래시 기록을 남기면 다음 기동에서 에뮬레이터가
**동의 대화상자를 띄운 채 멈춘다**(로그: `Showing crashdialog to get consent`). 그래서 "부팅이
안 된다" 로 보였다. 기록을 지우고 `-no-metrics` 로 띄우면 정상 부팅한다.

교훈은 로그를 끝까지 읽는 것이었다. `adb devices` 가 비어 있는 것만 보고 환경을 의심하는
동안, 답은 에뮬레이터 로그 마지막 줄에 그대로 있었다. `maru_mobile_max_quads() > 0` 은
이제 계약 테스트가 지킨다.

## 기획 공백 (M9~M12, M2b, M3c)

PoC 는 "되는가" 에 답했고 지금 계획은 **PoC 가 드러낸 것**만 담고 있었다. 제품이 되려면
필요한데 아직 아무 데도 없던 것들을 넣는다. **둘은 새 결정이 아니라 이행 누락이다** —
데스크톱이 이미 계약으로 정해 둔 것을 모바일이 안 따른다.

### M9 접근성 (이행 누락)

[chrome 상호작용 이관](../chrome-interaction-migration.md)이 정한 계약: interactive node 가
**semantic descriptor** 를 내고 플랫폼 어댑터가 그것을 네이티브 접근성 요소로 투영한다.
**모바일에는 그 어댑터가 없었다** — GPU 로 그린 quad 뿐이라 VoiceOver·TalkBack 에게 빈 화면이었다.
GPU 로 UI 를 그리는 선택의 대가라 나중에 붙이기 비쌌다.

**2026-09-06 에 닫혔다.** 아래 슬라이스들이 브리지의 서술자와 두 host 어댑터를 세웠다 — iOS 는
`UIAccessibilityElement`, Android 는 `AccessibilityNodeProvider` 의 가상 뷰 계층이다.

#### 첫 슬라이스 — 브리지가 서술자를 낸다 (2026-09-06)

**tree 의 배관은 모바일에서 거의 안 쓰인다.** 데스크톱은 `tree` 노드가 서술자를 싣는데, 모바일은
**tree 노드 다섯 vs 누를 수 있는 사각형 서른일곱**이라 그 길로는 대부분이 안 닿는다. 그래서
그리는 자리가 직접 낸다(`noteA11y`).

**내는 자리를 rect 옆에 둔 것이 요점이다.** 이 파일에는 「그리는 자리와 누르는 자리가 같아야
한다」는 규율이 이미 있는데(`key_bar_rects`·`term_back_rect`…), 서술자를 다른 곳에서 만들면
**세 번째 진실**이 생긴다. 판정자 하나가 그것을 잠근다 — 「읽는 자리가 누르는 자리와 같다」를
`terminalKeyboardCenter()`·`terminalDisconnectCenter()` 로 대조한다.

**낸 것**: 터미널 앱 바 넷(뒤로 가기·자판·끊기 + 선택이 있을 때 복사) + 키바 열둘. 눌러 둔
수정자는 `selected`, 못 쓰는 키는 **빼지 않고** `enabled = false`(계약 P1 — 「누를 수 없는 컨트롤도
자리와 이름은 있다」). 뒤로가기는 아이콘뿐이라 **읽을 이름이 없어서** 문구를 새로 뒀다
(`mob_a11y_back` — 그리지 않고 스크린 리더에게만 간다).

**적대적 검증 세 회차가 결함 셋을 냈고, 셋 다 같은 모양이었다 — 「읽는 것」과 「눌리는 것」의
어긋남이다.** ① 밀린 화면이 덮고 있을 때도 터미널 앱 바·키바 서술자를 냈다(안 눌리는데 읽힌다).
② 이름을 `@min(len, cap)` 으로 잘라 UTF-8 반쪽을 냈다 — iOS 는 그것을 nil 로 만들어 이름이 통째로
사라진다. ③ 복사 버튼은 눌리는데 서술자가 없었다(눌리는데 안 읽힌다) — VoiceOver 사용자에게는
복사할 길이 아예 없었다. 곁가지로 **판정자 도우미가 스택이 차면 조용히 무동작**이라 「화면을
옮겼다」고 믿은 채 안 옮긴 것을 재던 것도 고쳤다(`setScreenForTest`).

**남은 것**: host 어댑터 둘, 그리고 나머지 화면들(세션 목록·서버 목록·설정 — 서른일곱 중 나머지).
**어댑터가 서기 전까지 사용자에게는 아무 변화가 없다.**

#### 둘째 슬라이스 — iOS 어댑터 (2026-09-06)

`ChromeView` 가 접근성 **컨테이너**가 되고 서술자를 `UIAccessibilityElement` 로 투영한다.
번역(역할 → trait)은 host 의 한 함수 안에서만 하고, Zig 에는 `UIAccessibility` 어휘가 0 건이다.

**요소를 들고 있는 것이 요점이다.** 데스크톱처럼 질의마다 새로 만들었더니 iOS 가 index 별로 물을 때
앞서 준 요소가 배열과 함께 사라졌다 — `idb ui describe-all` 로 보니 열다섯 중 **마지막 하나만**
이름과 자리가 있고 나머지 열넷은 이름 `null` 에 크기 0 인 빈 그룹이었다. 눈으로는 안 보이고
스크린 리더에게만 보이는 결함이라, **트리를 직접 읽지 않았으면 못 잡았다.**

**실기 확인**(시뮬레이터, `idb ui describe-all`):

| 화면 | 트리에 선 것 |
|---|---|
| 터미널 | 15개 — 뒤로 가기·자판·끊기 + 키바 열둘, 전부 `AXButton` 에 이름과 자리 |
| 세션 목록·서버 목록 | **0개** — 덮인 터미널의 버튼이 안 읽힌다(첫 슬라이스의 게이트가 실기에서 도는 증거) |
| 돌아오면 | 다시 15개 |

접근성 프레임 중심을 그대로 눌러(`idb ui tap 38 809`) ctrl 이 실제로 눌리는 것도 확인했다 —
**읽는 자리가 누르는 자리다.**

**적대적 검증 세 회차가 결함 셋을 더 냈다 — 셋 다 「훑는 사람만 겪는」 것들이다.**
① 배열 순서가 그리는 순서라 훑으면 오른쪽에 갔다가 왼쪽으로 되돌아왔다(`뒤로 가기 → 자판(298) →
끊기(246)`). ② 상태만 바뀌어도 레이아웃 변경 알림을 보내, 키바에서 수정자를 켜자마자 커서를
처음으로 잃었다. ③ 알림을 막아도 **요소 객체를 새로 만들고** 있어서 커서가 붙잡고 있던 것이
사라졌다 — 같은 객체의 trait 만 갈아 끼우도록 고쳤다. 실기 로그로 확인: 상태만 바뀌는 동안
알림 0건, 화면이 바뀔 때만 `MARU_A11Y elements=N`.

#### 읽는 순서를 브리지로 (2026-09-06)

iOS 어댑터에서 정렬하던 것을 **브리지로 옮겼다**(`sortA11yForReading`). Android 어댑터를 붙이는
순간 같은 규칙을 Java 에 다시 적게 되고, 그러면 두 host 가 조용히 갈린다 — 그 갈림은 스크린
리더에게만 보인다(사용자 결정 2026-09-06). 덤으로 순서가 **Zig 단위 판정자로 재는 성질**이 됐다.

#### 셋째 슬라이스 — Android 어댑터 (2026-09-06)

`InputView`(IME 를 받는 전면 뷰)가 `AccessibilityNodeProvider` 로 가상 뷰 계층을 든다. 노드는
질의마다 새로 만든다 — 그것이 이 플랫폼의 방식이다(iOS 와 반대).

**실기 확인**(에뮬레이터, `uiautomator dump` = TalkBack 이 읽는 그 트리):

| 잰 것 | 결과 |
|---|---|
| 노드 | **15개** — `android.widget.Button`, 이름·자리·`clickable=true`·`enabled=true`·`focusable=true` |
| 순서 | 브리지가 정한 읽는 순서 그대로(뒤로 가기 → 끊기 → 자판 → esc…pgdn) |
| 자리 | 기기 픽셀로 정확히 그린 버튼 위(`[21,1251][183,1366]` 등) |
| 상태 | ctrl 을 켜면 그 노드가 `selected="true"` 로 읽힌다 |
| 접힘 | 가로+키보드로 키바가 접히면 **그 노드들이 사라진다**(앱 바만 남는다) |
| 알림 | 생김새가 바뀐 프레임에만 `MARU_A11Y elements=15` |

**못 잰 것**: TalkBack 의 두 번 두드리기(`ACTION_CLICK`). `adb shell input tap` 은 터치 탐색을
안 거치고 앱에 바로 가서 그 길을 못 태운다(D-pad+Enter 도 안 닿았다). 그 길은 경계 판정자가
지키고, 실기기 확인으로 남긴다.

**적대적 검증 세 회차가 결함 셋을 더 냈다.** ① 주입하는 누름이 진짜 손가락과 **같은 id(0)** 를
써서, 손가락이 내려와 있는 동안 활성화하면 그 손가락의 자리를 덮어썼다(값을 헤더로 옮겼다).
② C→Java 호출이 스레드를 **붙이고 안 놓았다** — 이 파일의 다른 호출은 다 놓는다. ③ 노드 하나를
**네 번 나눠 물어** 이름과 자리가 서로 다른 프레임의 것이 될 수 있었다(ABI 헤더가 경고하던 바로
그것이다) — 한 번에 받도록 합쳤다.

**적대적 검증을 세 회 더 돌려 둘을 더 냈다.** ④ 커서가 index 로 붙잡는 사이 화면이 바뀌면 같은
index 가 다른 버튼이 된다 — 읽어 준 이름과 대조해 다르면 안 누른다. ⑥ 이름을 `NewStringUTF` 로
만들고 있었는데 그것은 modified UTF-8 을 기대해서 이모지에 abort 한다(이 파일의 클립보드 경로가
이미 그 이유로 UTF-16 변환을 쓴다 — 다음 슬라이스가 사용자 데이터를 이름으로 내므로 곧 닿는다).
⑤ 회전 축에서는 결함이 안 나왔다: 돌리면 자리가 따라오고, 가로에서 키바가 한 줄이 되는 것과
키보드가 뜨면 접히는 것이 트리에 그대로 나온다(15 → 3 → 15).

**곁가지 — 빌드가 죽었다.** 이중 중첩된 «비정적» 내부 클래스가 라이브러리 추상 클래스를 상속하면
d8 8.2.2 가 내부 오류로 죽는다(최소 재현까지 좁혔다). `static` 으로 바꿔 피했고, d8 에 `--lib` 도
준다.

#### 넷째 슬라이스 — 세션 목록 (2026-09-06)

**처음 만나는 화면이 안 읽히고 있었다** — 터미널만 읽혀서 스크린 리더 사용자는 세션을 고를 수조차
없었다. 목록의 톱니·「터미널」 줄·서버 항목·원격 세션 줄이 서술자를 낸다.

- **줄은 `list_item` 에 「몇 분의 몇」**을 싣는다. 목록이 흐르므로 집합 크기는 **있는 줄 전부**다.
- **값을 새로 낸다**(`maru_mobile_a11y_value`). 서버 개수, 세션의 둘째 줄(cwd·git·agent), 그리고
  **「열려 있음」**(눈에는 점 하나로 말하던 것 — 색은 안 읽힌다). 이름에 이어 붙이지 않는 이유는
  계약이 소유한다.
- **게이트를 일반화했다**: `screenTop() == .terminal` 이던 조건이 「지금 그리는 것이 맨 위 층이냐」가
  됐다 — 화면이 늘 때마다 그 조건을 고치지 않으려면 층이 스스로 말해야 한다.
- **이름·값을 복사해 든다.** 그리면서 만든 스택 버퍼가 값으로 오므로, 복사하지 않으면 host 가
  프레임이 끝난 뒤 남의 메모리를 읽는다. 이 파일의 판정자는 프레임 안에서 보므로 **못 잡는다** —
  그래서 ABI 로 읽는 판정자를 따로 세웠다.

**실기 확인**: Android `설정` / `터미널` / `서버, 0`, iOS 는 값이 `AXValue` 자리에 따로 실린다.

**적대적 검증 세 회차.** ① **결함** — 흐르는 목록의 줄이 고정 헤더 밑까지 뻗은 자리를 냈다(화면은
헤더가 덮지만 서술자에는 덮개가 없다). 창으로 잘라서 낸다. ② 글자 자리는 안 넘쳤지만 실측 여유가
5% 였다(15줄 × 181바이트, 세로가 긴 기기면 21줄) — 근거를 적고 배로 뒀다. ③ 번호는 밀어도 그대로다
(제품이 「센 것은 있는 줄이지 그린 줄이 아니다」를 이미 지키고 있었고, 판정자가 그것을 못박는다).
①·③ 은 변이로 붉어지는 것을 확인했다.

#### 다섯째 슬라이스 — 서버 목록·설정 (2026-09-06)

두 화면이 스크린 리더에게 빈 화면이었다. 이제 **나가는 길**(뒤로가기)부터 값까지 읽힌다.

| 화면 | 낸 것 |
|---|---|
| 서버 목록 | 뒤로 · 서버 줄(`list_item`, 값은 둘째 줄 — 주소이거나 「덜 적혔다」·「처음 붙는다」·「붙는 중」) · **줄마다 편집 버튼**(값에 어느 서버인지) · 추가 |
| 설정 | 뒤로 · 갈래 머리글(`text`, **붙임 머리글 포함**) · 줄마다 이름 + 값(토글은 `켜짐`/`꺼짐` + `selected`) |

**실기 확인**(Android): 서버 목록 `뒤로 가기`·`서버 추가`, 설정 20개 —
`모양` / `테마 프리셋, —` / `커서 깜빡임, 켜짐` / `폰트 크기(pt), 22`.
붙임 머리글은 **처음에 빠져 있었다** — 트리를 읽고서야 첫 갈래 이름이 어디에도 없다는 것을 봤다.

**같은 슬라이스에서 남은 화면 셋도 덮었다**(서버 편집·비밀번호·호스트키). 편집 칸은 이름과
**온전한** 값(화면은 앞을 자른다), 호스트키는 **지문을 통째로**(대조가 존재 이유다), 비밀번호는
**친 글자를 절대 안 읽고** 글자 수만 값으로 낸다.

**적대적 검증 세 회차가 둘을 더 냈다.** ① 비밀번호 화면의 가림표 서술자가 **그린 글자를 통째로
비껴갔다** — 지역 `y` 가 구분선·여백만큼 더 내려간 뒤에 자리를 계산했다(자리를 그리는 그 줄에서
붙들도록 고쳤고, 호스트키 지문도 같은 방식으로 못박았다). ③ 편집 중인 줄이 그렇다고 말하지 않았고,
**캐럿(▏)이 값에 섞여** 스크린 리더가 블록 문자를 읽었다 — `selected` 로 사실을 주고 값에서 캐럿을
뗀다. ② 호스트키 자리는 결함이 없었다.

**적대적 검증을 세 회 더 돌려 셋을 더 냈다.** ④ 서버 줄이 폭 전체라 **편집 띠에서 두 서술자가
겹쳤다**(포인터는 편집을 먼저 본다) — 누르는 규칙과 같은 폭으로 줄이고, 네 화면 전체에서 겹침 0 을
판정자로 세웠다. ⑤ 팝업에서 **고르지 않고 나가는 길이 없었다**(화면은 바깥 탭이 취소인데 그 자리에
서술자가 없다) — 이미 눌리는 자리를 읽히게 했다. ⑥ Android 어댑터가 **모든** 노드에 `clickable` 을
붙여, 글자(머리글·지문)에도 「두 번 탭하여 활성화」를 안내했다 — 뜻에 따라 가른다.

**그리고 세 회 더**: ⑦ 원격 화면에 **나갈 길이 없었다**(읽기 전용이라 누를 것이 뒤로가기 하나뿐인데
그것을 안 냈다 — 들어가면 갇힌다). ⑧ 서버 목록의 「몇 분의 몇」이 **「추가」 버튼까지 세어** 사실이
아니었다. ⑨ 팝업 닫기 문구를 **다른 화면의 「취소」에서 빌려** 써서, 그 화면이 바뀌면 여기가 조용히
따라 바뀌었다.

**또 세 회 더**: ⑪ 세션 줄의 이름이 제목도 경로도 없으면 **빈 문자열**이었다 — 빈 이름은 host 가
요소를 아예 안 만들어, 화면에는 있고 눌리는 줄이 스크린 리더에서는 **통째로 사라진다**(둘 다 원격이
주는 값이라 정상 상태다). ⑩·⑫ 는 결함이 없었고, 그 대신 판정자를 넓혔다 — 겹침은 여덟 화면과
**팝업이 열린 상태**까지, 빈 이름은 여덟 화면 전부에서 잰다.

**판정자가 두 번 «아무것도 안 재고» 있었다**: 하나는 앞 판정자가 켜 둔 편집 상태 탓에 팝업이 안
열렸고, 하나는 **서버 0개** 상태로 돌아 잴 줄이 없었다. 둘 다 전제를 단언하도록 고쳤다.

**적대적 검증이 팝업을 잡았다.** 설정의 선택 팝업이 열리면 포인터는 「항목 아니면 닫기」만
하는데(아래 줄도 뒤로가기도 안 눌린다), 서술자는 아래 것들이 그대로 나오고 **정작 눌리는 팝업
항목은 하나도 안 나왔다** — 양쪽이 동시에 어긋난 자리다.

#### 여섯째 슬라이스 — 터미널 본문 (2026-09-06)

**두 레퍼런스가 갈라지는 자리라 근거를 적는다.** Ghostty(macOS)는 표면 하나를 `.textArea` 로 두고
`accessibilityValue` 에 화면 글자를 통째로 주고, 줄 이동은 AppKit 의 텍스트 프로토콜
(`accessibilityLine(for:)`·`accessibilityString(for:)`)에 맡긴다. xterm.js(웹)는 그 프로토콜이 없어
**보이는 행마다 요소**를 두고, 새 출력은 `aria-live` 로 따로 알린다(20줄 상한·에코 중복 방지).

**우리는 xterm.js 쪽이다** — UIKit·Android 의 요소에는 텍스트 프로토콜이 없어서, 한 덩어리로 주면
서른 줄이 한 번에 읽히고 특정 줄로 못 간다(사용자 결정 2026-09-06).

- **이름은 줄 번호, 글자는 값.** 신원이 고정되어 값만 갱신된다 — 실측(iOS): 입력이 오가는 동안
  레이아웃 알림 **0건**이고 줄 요소가 그대로 산다.
- 빈 줄은 안 내고 끝 여백은 턴다.
- **실기 확인**(iOS): `StaticText 1 = "Last login: …"` / `2 = "%"` / `3 = "➜  ~"`.
  Android 는 셸이 없어 화면이 비어 있고, 그래서 줄이 0개다(빈 줄을 안 내는 규칙대로다).

**적대적 검증 세 회차가 셋을 냈다.** ① 결합 문자를 빠뜨려 **보는 글자와 읽는 글자가 달랐다**
(`❤` 와 `❤️` 가 같아진다). ② 서술자 글자 자리가 **본문이 들어오면서 모자랐다** — 결합 문자로
화면을 채우니 8 KiB 를 넘겼고, 넘치면 이름이 빈 것이 되어 그 줄들이 사라진다. 「글자 수」가 아니라
**바이트**로 재서 `줄 상한 × 줄 수 상한` 으로 다시 잡았다. ③ **커서가 있는 줄**이 안 읽혔다 —
화면은 깜빡이는 사각형으로만 말한다.

**남은 것**: 새 출력 알림(live region — 낭독을 못 재는 환경이라 실기기 확인과 함께),
스크롤백을 어떻게 훑게 할지, 선택 영역, 그리고 낭독 실측.
회전과 소프트 키보드는 **이 환경에서 못 재운다**(시뮬레이터 회전 명령이 없고, 하드웨어 키보드가
붙어 소프트 키보드가 안 뜬다) — 그 둘은 실기기 확인으로 남긴다.

### M10 모바일 config 스키마

[설정](../configuration.md)이 config 계약의 단일 출처인데 **모바일은 config 를 아예 안 읽는다**
(`mobile_bridge.zig` 의 `themeColors()` 가 값을 고정한다). 폰트 크기 하나 못 바꾸는 상태다.

**어디서 오는지는 정해졌다(사용자 확정, 계약 §1): 모바일 config 는 데스크톱과 따로다.**
파일도 스키마도 공유하지 않고, 원격 세션에 붙어도 PC 의 config 를 끌어오지 않는다. 공유하는
것은 값이 아니라 기계다 — `src/config` 의 파서·resolve 규율·"파일이 단일 출처" 원칙은
그대로 쓰고 스키마와 파일 위치만 모바일 것으로 둔다.

그래서 M10 의 일은 "어디서 받을까" 가 아니라 **모바일 스키마를 짜는 것**이다. 지금 값이
박혀 있는 자리가 곧 첫 후보다:

  - `font.size`(브리지 `font_px=15`)·줄 높이 — **M4a3(글리프 기하)과 함께 정해야 한다.**
    지금은 굽는 크기(`MARU_ATLAS_TEXT_PX`)와 그리는 크기가 따로 놀아, 크기를 config 로 여는
    순간 그 어긋남이 사용자에게 드러난다.
  - 테마(`themeColors()` 고정) — 데스크톱 `chrome.theme` 와 **같은 이름을 쓰되 값은 따로**.
  - 프레임 주기(30Hz 고정) — 모바일에는 데스크톱에 없는 축이 붙는다(저전력 모드·배터리).
  - 스크롤백 줄 수(코어 기본 1000) — 기기 메모리가 데스크톱과 다르다.
  - 원격 접속 프로필(호스트·인증) — **데스크톱에 대응하는 키가 없다.** M3 가 전송·인증을
    정한 뒤에 형태가 나온다.
  - 보조 키바 구성·터치 임계값 — 데스크톱에 대응 키가 없다(M4a2·M4b).

데스크톱 키 93개 중 `quick-terminal.*`·`shell.command`·`shell.args`·`input.option-as-meta`·
`input.right-click`·`session.keep-alive-after-quit` 처럼 **모바일에 뜻이 없는 것**은 안 가져온다.

### M11 스토어 배포

[배포](../distribution.md)는 macOS 채널·서명·공증·업데이트를 소유하지만 **모바일 스토어는
다루지 않는다**. 지금 상태로는 배포가 불가능하다.

  - `AndroidManifest.xml` 에 `android:debuggable="true"` 가 남아 있다(개발용 — `run-as` 로
    래스터 결과를 꺼내려고 넣었다). **배포 빌드에서는 반드시 빼야 한다.**
  - 앱 아이콘·런치 스크린이 없다.
  - iOS 는 privacy manifest(`PrivacyInfo.xcprivacy`)와 프로비저닝이 필요하다.
  - **`Info.plist` 를 새로 짜면 `CADisableMinimumFrameDuration` 을 옮겨 실어야 한다.** 지금은
    하네스 템플릿(`tools/mobile-harness/Info.plist.in`)에만 있고 `doc_claims.sh` 도 거기를 본다 —
    제품 번들을 따로 만들면 **판정자는 계속 통과하는데 번들에서만 빠진다**. 없으면 주기를
    config(M10)로 열어도 ProMotion 기기에서 조용히 60 으로 잘린다([계약 §3.2](../mobile-platform.md)).
  - Play 는 targetSdk 하한과 App Bundle 을 요구한다 — Gradle 을 안 쓰기로 한 결정([계약 §1])과
    다시 만나는 지점이라, 그때 Gradle 도입을 재검토한다.

### M4a·M12 포인터 (계약 §3.1)

**"세션 전환 UI" 라고만 적어 둔 것이 범위를 과소평가했다.** 실제 일은 **포인터를 chrome 의
`UiActionId` 경로에 태우는 것**이고, 스크롤·멀티터치는 그 위에 올라간다.

지금 받는 것은 `ACTION_DOWN`·`touchesBegan` 뿐이라 **탭과 롱프레스를 구분할 수 없다**(뗀
시점을 모른다). 먼저 M4a 로 down/move/up/cancel·포인터 id·시각을 코어로 넘기는 ABI 를 만들고,
그 위에서 판정한다.

**버튼을 좌표로 실행하지 않는다.** down→up 사이에 원격 세션 목록이 바뀌면 같은 인덱스가 다른
탭을 가리킨다 — `(UiActionId, snapshot_generation)` 으로 태워야 그 누름이 무시된다.

판정: 합성 이벤트 열을 넣어 intent 가 나오는지 **헤드리스로** 단언한다(모바일은 CI 가 없으니
이 경로가 유일한 자동 검증이다). 스크롤 관성·핀치는 플랫폼 인식기 결과를 받으므로 그쪽은
손 검증이다.

### M2b iOS IME preedit

Android 는 정했고 iOS 는 안 했다(계약 §7). `UITextInput` 의 marked text 를
`maru_mobile_set_preedit` 에 태우면 되는 자리다.

### M3c 연결 수명

M3 는 "무엇을 타고 가는가" 만 다뤘다. 모바일은 그 뒤가 더 어렵다.

  - **네트워크가 끊긴다** — 셀룰러↔Wi-Fi 전환, 지하철, 화면 잠금. 재접속·backoff·중복 세션
    방지가 필요하다. Mosh 가 존재하는 이유가 이것이다.
  - **백그라운드에서 소켓이 죽는다**(iOS 는 특히). 세션을 서버가 붙들고 있다가 다시 붙는
    모델인지, 클라가 상태를 들고 있는지 정해야 한다 — [영속 세션 호스트](../persistent-session-host.md)와
    같은 문제를 다른 조건에서 푸는 셈이다.
  - **자격증명을 어디에 두는가** — iOS Keychain / Android Keystore. 지금 계획에 없다.
  - **프로토콜 버전** — 모바일 앱과 데스크톱 host 의 버전이 갈린다(스토어 심사·사용자 업데이트
    지연). 호환 규칙이 필요하다.

## 앱 수준 공백 (M13~M16)

M9~M12 가 **기능·계약** 축이었다면 이건 **앱으로서 갖춰야 하는 것** 축이다. 코드로 확인한
현재 상태를 그대로 적는다.

### M13 표시 설정

**이 절의 앞부분은 낡았었다**(2026-09-05 정정) — 「`font_px` 가 상수 15 로 박혀 있다」였는데
M10d 가 이미 닫았다(`font.size`, 범위 [12,40]).

  - ~~**다크/라이트 전환을 안 본다**~~ — **닫았다**(2026-09-05, 아래 절). `traitCollection`(iOS)·
    `UI_MODE_NIGHT`(Android)를 읽어 코어에 알린다.
  - **핀치 줌**으로 폰트 크기를 바꾸는 것이 모바일 터미널의 사실상 표준이다(플랫폼 인식기 →
    코어, 계약 §3.1 의 "느낌은 플랫폼" 에 해당). **값을 바꿀 길은 이미 있다**(설정 화면) —
    남은 것은 손짓이다.
  - **접근성 글자 크기**(Dynamic Type / 글꼴 크기 설정)는 아직 안 본다. M9 접근성과 함께 봐야 한다.

### M13 시스템 다크/라이트 — 데스크톱 F2-9 를 잇는다 (2026-09-05)

**새로 정한 것이 없다.** 데스크톱이 이미 `theme.follow-system`·`theme.preset-light`·
`theme.preset-dark` 를 정했고(F2-9), 모바일만 그 계약을 안 따르고 있었다 — 시스템 값을 읽는
코드가 **0건**이었다. 그래서 이 슬라이스는 정책을 만드는 것이 아니라 **잇는 것**이다.

| | 데스크톱 | 모바일(지금) |
|---|---|---|
| 키 | `theme.follow-system`·`preset-light`·`preset-dark` | **같다** |
| 시스템 값 | `NSApp.effectiveAppearance` → `setSystemAppearance` | `traitCollection`(iOS)·`UI_MODE_NIGHT`(Android) → `maru_mobile_set_system_appearance` |
| 다크 기본 프리셋 | `.maru`(`#101010`) | **`.catppuccin_mocha`**(`#1e1e2e`) |
| 정하는 자리 | config 를 덮고 **원본을 스냅숏**해 뒀다가 끄면 되돌린다 | **`activeTheme()` — 그릴 때 고른다** |

**다크 기본이 다른 이유**: 모바일 기본 배경이 `#1e1e2e` 라 `catppuccin_mocha` 와 **같다**. `.maru`
로 두면 켜는 순간 화면이 `#101010` 으로 어두워진다 — 「기기가 다르면 기본값도 다르다」(계약 §4.5)가
색에 걸리는 자리이고, `Config.theme` 이 데스크톱 기본을 안 빌린 것과 같은 이유다.

**정하는 자리가 다른 이유**: 데스크톱은 config 를 라이브 resolve 하므로 덮어야 하고, 그러면
「파일에는 안 쓴다」를 **규율로** 지켜야 하며 되돌리려고 스냅숏이 필요하다. 모바일은 색을 **그릴 때**
읽으므로 그냥 그 자리에서 고르면 된다 — config 를 안 건드리니 **저장 경로가 시스템 색을 실을 길이
없고**(구조로 지킨다), 끄면 다음 프레임에 파일 색으로 돌아오며, 설정 화면의 `theme.preset` 줄도
**파일이 말하는 것**을 그대로 보인다.

**host 가 아직 안 알려 줬으면 안 따라간다.** `null` 을 다크로 치면 라이트 기기가 켜자마자
어두워진다 — 그래서 `system_is_dark` 는 `?bool` 이고, 모르는 동안은 파일 색이다.

**실측**(에뮬레이터, `theme.preset-dark = tokyo-night`·`preset-light = solarized-light`):
`cmd uimode night no` → 본문 픽셀 `(253,246,227)` = solarized-light `#fdf6e3`,
**앱이 떠 있는 채로** `night yes` → `(26,27,38)` = tokyo-night `#1a1b26`. chrome(앱 바·키바)도 같이 따라온다.

### M14 전원·네트워크 예의

모바일은 데스크톱과 달리 **자원이 사용자에게 보인다**(배터리·데이터·발열).

**갱신이 없으면 쉰다**(2026-09-06 — 사용자 결정). 터미널은 대부분의 시간이 정지 화면이라 여기서
얻는 것이 가장 크고, 저전력 여부를 **안 물어도 되므로** host 배선이 없다.

**깃발이 아니라 결과를 견준다.** 「바꾸는 자리마다 dirty 를 세운다」는 상태를 바꾸는 export 가
아흔 개라 하나만 빠뜨려도 화면이 언다 — 이 저장소가 그 모양으로 두 번 물렸다(전역 output 게이트가
커서 위상을 굶겼고, sync 게이트가 스크롤 리페인트를 막았다). 낸 quad 를 지난 프레임과 견주면
**빠뜨릴 목록이 없다**.

**빌드는 안 건너뛴다.** 건너뛰는 것은 GPU 뿐이라 관성 감쇠·길게 누름 승격·아틀라스 순번이 안
멈춘다. 그리고 host 는 **글자 굽기·config 저장·컨트롤 채널을 다 하고** 나서 쉰다 — 처음에 그 앞에
놨다가 「못 그린 글자가 영영 안 구워지고 저장이 사라진다」를 보고 되물렀다. **GPU 자원 획득도 빌드
뒤로 옮겼다**(Vulkan 이미지·Metal 드로어블 둘 다 한 번 잡으면 되돌릴 수 없다).

**페이싱 판정자를 눈멀게 하지 않는다.** `MARU_PACE` 는 프레젠트 간격을 재는데 쉰 간격이 섞이면
거짓으로 붉어진다 — 정지 화면에서도 표본 60 을 채우고 있었다. 그 측정은 시작할 때 끝나므로
(`pace_done`) **그 뒤부터** 쉰다. 테스트 전용 스위치를 안 만들고 이 성질로 푼 자리다.

**실측**(에뮬레이터): `MARU_PACE median_ms=33.85 n=60 verdict=PASS` 직후 `MARU_IDLE skipped=1`,
정지 8초에 **3,901 tick** 을 건너뛴다. 원격 출력이 오면 화면이 바뀐다(캡처 대조).

  - **저전력 모드를 안 본다.** 기본이 30Hz(계약 §3.2)이므로 저전력에서는 더 낮추거나
    갱신이 없을 때 아예 쉬는 쪽을 봐야 한다 — `isLowPowerModeEnabled`(iOS)·`PowerManager`(Android).
  - ~~**백그라운드에서 무엇을 멈추는가**가 정해지지 않았다~~ — **정해져 있었다**(2026-09-06 정정).
    [계약 §배경](../mobile-platform.md)이 두 플랫폼을 갈라 적고 실측까지 뒀다: iOS 는
    `beginBackgroundTask` 유예를 받고 만료되면 **정직하게 끊고**(실측 26초), Android 는
    포그라운드 서비스(`MaruSshService`)가 소켓을 든다(실측 20초 뒤 복귀에 줄들이 남아 있었다).
    이 줄만 낡아 있었다.
  - **데이터 절약** — 셀룰러에서 화면 갱신 전송량을 줄일지. 원격 프로토콜 설계(M3a)의 입력이다.

### M15 진단

**크래시 보고와 로그 수집이 없다.** 데스크톱은 사용자가 로그를 찾아 줄 수 있지만 폰은 아니다 —
재현 못 하는 버그가 그대로 미제로 남는다.

[trace·replay](../trace-replay.md)가 진단 산출물 계약을 소유하므로 거기에 모바일 축을 더한다. **개인정보
경계가 먼저다** — 터미널 로그에는 명령어·경로·호스트명이 들어가고, 그걸 수집하면 그 자체가
사고다(`src/redact.zig` 가 이미 그 판정을 갖는다).

### M16 첫 실행 경험

지금 앱을 처음 켜면 **아무 안내 없이 하드코딩된 화면**이 뜬다. 원격 전용(계약 §1)이므로 실제
제품의 첫 화면은 "무엇에 연결할까" 다.

  - 온보딩·서버 등록·페어링(M3c 의 자격증명 저장과 같은 화면).
  - **연결 실패 UX** — 지금은 실패해도 로그 한 줄뿐이다. 사용자에게 무엇이 잘못됐는지 보여야
    한다(네트워크·인증·버전 불일치가 각각 다른 안내다).
  - 권한 요청 — 알림 권한 정도지만 시점이 UX 다.
