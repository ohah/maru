# 네이티브 편집기 구현 계획

등폭 GPU 텍스트 뷰 기반 편집기(N1~N5)의 구현 계획이다. 계약의 단일 출처는 [네이티브 편집기](../native-editor.md)다.

## 네이티브 편집기 (N1 진행 중 — 제품 pane에 떠 있다)

계약은 [native-editor.md](../native-editor.md)가 소유한다. 여기서는 **순서와 각 단계의 출하 가능 여부만** 정한다.
2026-08-09 사용자 결정으로 `text` kind와 diff 본문을 CM6에서 Zig+Metal로 이관하며, 마크다운 렌더는 웹에 남는다.

- **N0b — 시각 기준 수령(코드 변경 없음).** [file-panel.md](../file-panel.md) §1·[editor-surface.md](../editor-surface.md)
  §3.5가 목업을 받아 배치를 확정한 것과 같은 절차다(../native-editor.md §1.1).
  - **N1 몫은 해소됐다(2026-08-09 사용자 결정 — "VSCode 기준으로 한다").** gutter 요소 순서·폭, 본문 여백,
    상태바 우측 항목 순서를 VSCode 소스에서 확인해 **../native-editor-visual-mapping.md §4.1에 계약으로 적었다**(glyph margin →
    줄 번호 → decorations → 본문, 줄 번호 최소 5자리, git 마커와 접기 화살표가 같은 영역, 상태바는 커서
    위치 → 들여쓰기 → 인코딩 → 줄바꿈 → 언어). **목업 없이 N1에 들어갈 수 있다.**
  - **남은 것이던 셀 환산은 확정됐다(2026-08-22).** Monaco는 px와 `ch`(문자 폭 배수)를 함께 지원하는데 우리
    gutter는 셀 격자에 서므로 decorations 폭을 셀 수로 정해야 했다. §4.1이 **2셀**(접기 화살표 + 여백)을
    기본 후보로 두고 **N1에서 실제 화면을 보고 확정**하기로 했는데, 화면을 보니 **접기 화살표 한 셀이
    모자랐다** — 줄 번호가 우측 정렬이라 번호의 마지막 자리와 화살표가 늘 맞붙었다(사용자 지적). 그래서
    **3셀**(접기 2 + 여백 1)이고, 화살표는 접기 span의 오른쪽 칸에 서서 양옆이 한 칸씩 뜬다. Monaco가 접기에
    더하는 `16px`(≈2ch)와 같은 값으로 수렴했다. git 마커는 폭을 먹지 않으므로(기존 `GutterMark` 세로 바
    재사용) 셀 배정 대상이 아니다.
  - **뒤 단계 몫은 그대로 남는다**: diff 좌우 배치는 N1.5 전, 호버 박스와 미니맵 폭은 N4~N5 전. 색은 이미
    확정이라(`syntax_theme.zig` 파생) 목업 대상이 아니다.
- **N0c — 기존 구현 대조(코드 변경 없음).** 각 슬라이스 착수 전에 **그 기능을 이미 만든 CM6 코드를 읽고 계약과 대조**한다.
  설계만으로는 안 보이던 것이 거기 있다 — 실제로 이 단계를 diff에 먼저 해 본 결과 `web/src/diff-view.ts`에서
  **본문 화면의 네 상태**(읽는 중·보여 줄 수 없음·변경 없음·비교)·**무한 재시도 금지**·**내부 값 노출 금지**·
  **"jsdom은 iframe·CSS가 없어 레이아웃 결함을 못 잡는다"**는 교훈이 나왔고 전부 native-editor.md에 반영했다.
  대조 대상: `diff-view.ts`·`diff-layout.ts`·`diff-theme.ts`(diff — **완료**), `editor.ts`(소스 편집 — **완료**:
  문서 가상화 탓에 브라우저 native 선택이 렌더된 줄만 덮어 ⌘A 후 삭제가 일부만 되던 결함을 발견해 §3.2·§10에
  반영), `content-menu.ts`·`file-panel-state.ts`(**완료** — 브리지 소멸·revision 단조 시계가 이미 계약에 반영돼 있음을
  확인). **"옮긴다"가 아니라 "무엇을 이미 풀었는지 확인한다"**가 목적이다 —
  코드 표현을 옮기지 않는다([project-rules.md](../project-rules.md) clean-room은 외부 레퍼런스 규율이고 이쪽은
  우리 코드지만, 웹 전제(iframe·CSS·브리지)에 묶인 해법을 그대로 가져오면 네이티브에서 틀린 구조가 된다).
- ~~**N0 — 성능 baseline**~~ **철회(2026-08-09 사용자 결정).** CM6 대비 계측 하니스를 세우는 것이 이 작업 대비
  과하다고 판단해 **단계를 없앤다**. 착수 전 성능 게이트는 없으며 N1이 첫 단계다. 대신 성능을 이관 근거·성과에서
  뺐고(../native-editor.md §1.0), "빨라졌다"를 문서·PR에 쓰지 않는다. 큰 파일·초장문 줄의 축소 임계는 baseline 없이도
  서는 장치라 그대로 두되 값은 해당 슬라이스에서 정한다(../native-editor.md §10).
- **N1 — 읽기 전용 등폭 뷰.** 화면에 파일이 뜬다.

  **진행 상황(2026-08-14)**: **"화면에 파일이 뜬다"가 닫혔다** — `MARU_NATIVE_EDITOR=<경로>` 훅이 파일을 편집기 Term으로 열고
  제품 tick의 `editor_ops.appendPaneFrame`이 leaf마다 그린다. 다만 **N1 완료가 아니다**: 접힘·선택·가로 스크롤 입력·
  스레딩이 남았고, 그것들은 아래 표가 소유한다.

  **탐색기 클릭이 네이티브 편집기를 연다(2026-08-19).** `.text` kind가 CM6 대신 네이티브 편집기 Term으로 열린다 —
  파일 Term을 만드는 **단일 분기점**(`pane.openFileTermInActivePane`)에 비교와 같은 자리를 하나 더 연 것이다.

  **기본이 네이티브다(2026-08-19 사용자 결정).** 이 계획은 원래 기본 전환을 N2에 두었고, 그 근거는 지금도 사실이다:
  비교는 CM6에서도 읽기 전용이라 바꿔도 잃는 것이 없었지만, `.text`는 CM6에서 편집·저장이 된다
  (`Mode.defaultFor(.text) == .source_edit`). 네이티브는 N1이라 읽기 전용이므로 **이 기본은 탐색기에서 연 파일을 고칠
  수 없게 만든다** — N2까지 그렇다. 사용자가 그 대가를 알고 앞당겼으므로, 여기 남기는 것은 *"안 된다"*가 아니라
  **무엇을 내주었는지**다. **`MARU_NATIVE_TEXT=0`이 되돌리는 길이고, 고쳐야 하는 파일을 만나면 그것이 편집 수단이다**
  (훅을 지우는 것은 편집이 붙은 뒤의 일 — 비교 훅과 같은 규율).

  이 전환으로 `MARU_NATIVE_EDITOR`(시작할 때 한 파일)의 자리는 사실상 없어진다 — 이제 아무 파일이나 클릭해서 연다.
  함께 정리한 것 둘:
  - **못 읽는 파일은 조용히 CM6로 간다**(§3.5 — UTF-8 아님·상한 초과·권한). 읽기를 Term 분기 **앞에서** 하는 이유가
    이것이다. 그러지 않으면 훅을 켠 것이 **특정 파일을 아예 못 여는 이유**가 된다.
  - **브리지 술어가 kind에서 entry로 올라갔다**(`Entry.usesEditorBridge`). `.text`가 두 경로로 열리므로 kind만으로는
    "이 문서가 CM6 브리지를 쓰는가"를 답할 수 없다. 그대로 두면 닫기가 **오지 않을 CM6 dirty 스냅샷을 기다려**
    네이티브로 연 탭이 닫히지 않는다(`filePanelEntryNeedsDirtyProtection`이 `mode.isEditable()`을 본다). kind 쪽
    술어는 `usesEditorBridgeByKind`로 이름을 바꿔, 호출부를 빠뜨리면 컴파일이 깨지게 했다.

    **선택 좌표계를 문서로 먼저 정했다(2026-08-19).** 본문 hit-test가 없어 선택·복사가 막혀 있었고, 그
  자리는 §4.1c가 *"선택 하이라이트가 오면 매핑 레이어 판단을 재평가하라"*고 예고해 둔 곳이다. 재평가
  결과와 걸친 자리의 결정표는 [visual-mapping §4.1g](../native-editor-visual-mapping.md)가 소유한다 —
  **레이어를 세우지 않고, 정방향에는 조각 시작 열 하나를 전달하고 역방향에는 clamp 규칙을 둔다.**
  구현은 그 문서를 따르는 다음 슬라이스다(좌표계 → 클릭·드래그 배선 → 복사 순).

    **줄 번호 규칙**(랩된 시각행에 반복 안 함·접힘은 건너뜀)·전체 접기/펼치기
  - **표시**: gutter(줄 번호)·스크롤바·**상태바 커서 위치**(§2.2, `ItemId` 확장 시작)·선택 하이라이트
  - **스레딩**(§2.1): 랩 재계산 분리. **창 리사이즈 중 매 프레임 발생하므로 N1에서 이미 필요하다**
  - **탭 계약**: 파일 Term을 `RenameTarget.term`에서 **제외**(§2.3)
- **N1.5 — git diff 본문(읽기 전용, ../native-editor-ui.md §7).** 좌우 배치·세로 동기·추가/삭제 배경(`diffFromTheme`)·
  변경 없는 영역 접기(§4 접힘 재사용)·**줄 대응과 문자 단위 강조를 이 단계가 계산**(§7 — git은 두 쪽 전문만 준다)·
  diff Term은 workspace에 저장하지 않음.
  **이 문서의 첫 제품 가치가 여기서 나온다**([editor-surface.md](../editor-surface.md) §1: "첫 제품 가치는 에이전트가
  만든 변경을 사용자가 Maru 안에서 검토하는 것"). **편집·IME·토큰이 전혀 필요 없다** — diff는 읽기 전용이고
  syntax 색이 없어도 성립한다(추가/삭제 배경이 diff의 언어다). 목록은 이미 GPU chrome이므로
  ([editor-surface-dock.md](../editor-surface-dock.md) §3.5) 이 슬라이스로 **검토 흐름 전체가 네이티브로 닫힌다.**
  - **순서를 이렇게 두는 이유**: diff를 마지막에 두면 제품 가치가 가장 늦게 나오고, 그때까지의 슬라이스는
    전부 "아직 쓸 수 없는 중간물"이 된다. 반대로 여기 두면 **N1.5에서 한 번 멈춰도 제품이 온전하다.**

  ### N1.5 구현 설계(2026-08-14)

  **지금 있는 것부터 적는다**(추측 위에 설계하지 않기 위해 코드를 훑고 적는다).

  | 조각 | 상태 |
  |---|---|
  | `git_backend.submitDiff` → `DiffResult{original, modified, ok, truncated}` | **있다.** 비동기 worker + `takeDiffResult` 폴링, 목록 결과와 슬롯 분리. `truncated`는 이미 `error.TooLarge`로 접힌다(`app_session.diffSidesForSurface`) — 잘린 내용을 온전한 파일처럼 그리지 않는다. b는 그것을 `unavailable = .too_large`로 잇기만 하면 된다 |
  | `DiffBase`(staged·unstaged·untracked·commit·turn_range·conflict)와 탭 라벨 | **있다**(`session/dock_panel.zig`) |
  | 유일성 키 `(경로, kind, base)`·workspace 미저장 | **정해져 있다**(§3.5) |
  | `syntax_theme.diffFromTheme` → `DiffColors` | **있다**(지금은 web CSS 변수로만 흐른다) |
  | 도크 소스 컨트롤 목록 | **있다**(GPU chrome) |
  | 편집기 뷰(셀 격자·gutter·스크롤바·`body` 사각·내용 여백) | **있다**(N1) |

  **줄 대응은 우리가 계산한다(2026-08-14 사용자 결정 — §7을 고쳤다).** 착수 전 조사에서 `DiffResult`가 주는 것은
  **양쪽 전문**이고 줄 대응은 `@codemirror/merge`가 JS에서 만든다는 것이 드러났다(`web/src/diff-view.ts`) — §7의 옛
  전제("줄 단위 차이는 git이 계산한다")는 실제 데이터 흐름과 달랐다. 셋을 놓고 골랐다:

  | | N1.5 | N2(편집 중 실시간) | 의존성 |
  |---|---|---|---|
  | `git diff` 출력 파싱 | 가장 빠름 | **불가**(타이핑마다 spawn) | 없음 |
  | **자체 differ**(택함) | Myers 한 벌 | **그대로 쓴다** | 없음 |
  | libgit2 `git_diff_buffers` | 됨 | 됨 | **런타임 의존성**(승인 사안) |

  **자체 differ를 택한 이유**: 파싱 경로는 N1.5에서 만든 것을 N2에서 버리게 된다. 그리고 옛 규칙의 근거였던
  "목록과 어긋난다"는 재검토 결과 **카운트가 아니라 경계 위치**의 문제였다(§7에 적었다) — 목록의 `+N -N`은
  최소 diff의 편집 횟수이고 우리도 최소를 내면 같다.

  **접힘은 이 슬라이스 밖이다.** §7이 *"변경 없는 영역 접기는 §4의 접힘 단계를 재사용한다"*고 하지만 접힘은
  **N1 잔여**다(`geometry`가 gutter 자리만 잡고 `content`가 폭 0으로 낸다). **현행 CM6도 접지 않는다** —
  `MergeView`의 `collapseUnchanged`는 기본 꺼짐이고 우리 설정에 없다(`diff-theme.ts`의 `.cm-collapsedLines`는
  쓰이지 않는 죽은 규칙이다). 그래서 접기 없이 내도 **기능 후퇴가 아니다**. 접힘이 N1 잔여로 들어올 때 이
  화면이 그것을 소비한다.

  **슬라이스**(각각 그 자체로 멈춰도 되는 지점을 둔다):

  | 슬라이스 | 내용 | 멈춰도 되나 |
  |---|---|---|
  | **a. L2 모델** | `session/editor/diff.zig` — **줄 단위 Myers** + 좌/우 행 배열(`kind: context\|added\|removed\|filler`, 줄 번호 `?u32`), 네 상태(`읽는 중·보여 줄 수 없음(이유)·변경 없음·비교`)를 **typed 결과**로. 순수·헤드리스 | 화면 없음(테스트만) |
  | **b. 배선** ✅ **(2026-08-14)** | 기존 `submitDiff`(두 쪽 전문) 폴링 → 상태 전이 → diff Term(두 문서·행 배열 소유). 유일성 키·workspace 미저장. **git 호출은 안 바꾼다**(CM6가 그대로 쓴다) | 상태 문구까지 화면에 뜬다 |

  **b는 이렇게 섰다(2026-08-14).** `session/editor/diff_state.zig`(순수 L2)가 백엔드 플래그를 네 상태로
  옮기고, `platform/macos/app_session/editor_diff.zig`가 그 판정을 Term 수명에 맞춰 든다. **git 호출은
  하나도 바뀌지 않았다** — 이미 있던 `submitDiff` → `takeDiffResult` → dock entry 경로가 그대로 두 쪽
  전문을 준다. 네이티브로 여는 것은 `MARU_NATIVE_DIFF=1` 훅으로만 켠다(기본은 CM6 그대로 — 화면이 서고
  골든이 붙는 c 전에 기본 경로를 바꾸지 않는다).
  - **재시도 창 6초**(CM6의 `120ms × 50회`를 시간으로 환산). 폴링이 tick이라 회수 대신 총 시간으로 잰다.
  - **판정 순서가 규칙이다**: 실패 → 잘림 → 도착 → 시간 초과. 잘림을 도착보다 먼저 보지 않으면 잘린
    내용으로 대응을 계산해 뒤가 통째로 삭제된 것처럼 보인다. 세 순서 모두 뮤턴트로 죽는 것을 확인했다.
  - **바이너리는 앞 8,000바이트의 NUL로 본다**(git `buffer_is_binary`와 같은 창) — 목록이 "Binary files
    differ"라 말한 파일을 본문도 같게 판정한다.
  - **판정이 서면 다시 계산하지 않는다**(래치). 매 프레임 2,000줄 대응을 돌리면 화면이 멈춘다. 내용이
    갈릴 때는 결과 배수가 `invalidate`를 **`freeDiffContent`보다 먼저** 부른다 — 행이 그 버퍼를 빌린다.
  - 화면은 아직 **한 줄**이다(네 상태의 문장). 좌우 배치는 c다.

  **c는 이렇게 섰다(2026-08-14).** 조합을 **컴포넌트 층**(`chrome/components/editor_view/diff_frame.zig`)이
  소유하고 제품과 Chrome Lab이 그것을 함께 부른다 — 한쪽만 조합을 들면 골든은 초록인데 제품만 틀린
  상태가 만들어진다(편집기 배경 층에서 실제로 그랬다).
  - **새 렌더 경로가 아니다**(§7). `frame.build`를 두 번 부르는 조합이라 gutter·스크롤바·랩·hazard가
    그대로 따라온다. `frame`에 **줄 번호 주입**(`line_numbers`)만 열었다 — diff는 번호가 순차가 아니라
    각자 문서의 것이고, 짝을 맞추려 넣은 빈 행에는 번호가 없다.
  - **세로는 하나, 가로는 각자**(§3.5). 행 배열이 같은 길이라 같은 인덱스가 같은 높이다. 열별
    `first_col`은 자리를 열어 두었고 입력은 N1 잔여(가로 스크롤)와 함께 온다.
  - **저장소를 반으로 가른다.** 두 열의 결과가 동시에 살아 있어야 한다(op이 text·run을 가리킨다) —
    같은 버퍼를 두 번 쓰면 왼쪽 글자가 오른쪽 것으로 바뀐다.
  - **캡처가 붙었다**: Lab 시나리오 `editor-diff` + 커밋 골든 `editor-diff-side-by-side.ppm`. 좌우 정렬·
    빈 행·각자 번호(왼쪽 1,2,_,3,4 / 오른쪽 1,2,3,4,5)가 픽셀로 고정된다. 세로 동기를 깨는 뮤턴트가
    단위 테스트를 죽이는 것도 확인했다.
  - 색 띠는 **d**다. 지금 캡처는 배치만 본다.
  - **출하 판정을 고쳤다가 다시 닫았다.** 초판 표가 c를 "출하 가능"이라 적었는데 그때는 사실이
    아니었다(색 없음 · 세로 스크롤 없음). **둘 다 붙었다(d + 세로 스크롤, 2026-08-14)** — 이제 긴
    비교를 끝까지 읽을 수 있고 추가·삭제가 색으로 갈린다.
  - **아직 못 채운 것은 텍스트 선택·복사다(2026-08-19 확인).** CM6에서는 WebKit이 주던 기능이고, 스크롤
    축(가로 막대·드래그)은 chrome이라 먼저 열 수 있었지만 **본문 선택은 hit-test가 필요**하다 — §4.1이
    *"포인터 경로가 붙을 때(N2~) 그때 함께 정한다"*고 미룬 자리이며, 커서를 어디에 놓느냐와 **같은
    좌표계 결정**이다. 그래서 이 항목은 N2와 함께 본다. "검토 흐름이 네이티브로 닫힌다"는 그때 온전해진다.
  - **기본 경로를 뒤집었다(2026-08-18).** 계획이 정한 조건대로 **실제 클릭 경로를 먼저 확인했다** —
    소스 컨트롤 도크 행을 클릭한 것과 같은 경로(`MARU_OPEN_SCM_DIFF` 캡처 훅 → `openDiffForScmRow`)로
    열어 제품 화면을 캡처했다. 그때 CM6 대비 **유일한 후퇴가 가로 막대**였고(CM6는 WebKit이 그려 준다 —
    `.cm-scroller { overflow-x: auto }`), 같은 슬라이스에서 채웠다. `MARU_NATIVE_DIFF=0`으로 되돌릴 수
    있게 남겨 둔다.
  - **스크롤은 문서 편집기(N1)와 같은 뿌리였고, 함께 풀렸다.** 휠은 편집기 pane이 통째로 소유한다 —
    셸이 아니라 문서라 스크롤백도 mouse reporting도 타지 않고, 안 소유하면 편집기 위 휠이 뒤 터미널을
    굴린다. 움직이는 단위는 **논리 줄**이다(`editor_first_line`이 시각 행이 아니라 논리 줄이라 랩이
    바뀌어도 화면 맨 위 줄이 그대로다) — 대가는 랩이 켜졌을 때 긴 줄이 한 번에 지나간다는 것이고,
    조각 단위(`first_piece`)가 붙으면 같은 함수가 그것을 함께 움직인다.

    **조각 단위 스크롤이 그 대가를 없앴다(2026-08-16 — visual-mapping §4.1d).** 아래 문단은 그 전
    상태의 기록이다: 이제 `editor_first_piece`가 붙어 한 줄짜리 문서도 조각으로 움직이고, 끝에 닿으면서
    화면도 꽉 찬다(옛 규칙은 마지막 논리 줄이 맨 위여서 화면이 거의 비었다 — 실측 99 → 83).

    **그 대가를 약하게 적었다(2026-08-16 적대적 검증).** "한 번에 지나간다"는 훑기가 거칠어진다는
    뜻으로 읽히는데, 극단에서는 **아예 못 움직인다**: 문서가 **한 줄**이면 논리 줄 상한이 0이라,
    랩으로 시각 행이 2,248개가 되어도(20만 자 한 줄, 실측) 첫 화면 밖을 볼 방법이 없다. minified
    파일을 랩으로 열면 실제로 그 상태다. 랩을 끄면 가로로 볼 수 있지만 그쪽도 §3.8 상한
    (`frame.max_first_col` = 10,000열)에 걸린다 — **둘을 합쳐도 20만 자 줄의 5%까지만 닿는다.**
    조각 단위 스크롤이 그 구멍을 닫는다. 비교의 문서는 **행 배열**이라
    상한도 행 수로 잡는다(문서 줄 수로 잡으면 빈 행만큼 일찍 멈춘다).

  **e는 이렇게 섰다(2026-08-15).**
  - **§5 스팬 층에 얹지 않았다.** 계획은 그렇게 적혀 있었지만 그 층은 **설계만 있고 구현이 없다**
    (tree-sitter 미도입, `SyntaxProvider` 없음). 대신 밴드와 같은 quad 경로로 34% 알파를 한 겹 더
    얹는다 — CM6도 `.cm-changedText`를 배경으로 그렸으므로 이탈이 아니라 같은 방식이다. 스팬 층이
    생기면 전경 강조로 옮길 수 있고, 그때도 계산(`intraline.zig`)은 그대로다.
  - **무엇이 한 글자인지는 위층이 정한다.** L2는 chrome을 모르는데(layering) "한 글자"는 grapheme
    cluster·표시 폭이라 그 어휘가 chrome(`text_layout`)에 있다. 그래서 L2는 **토큰 경계를 받아** 그
    위에서 최소 차이만 내고, cluster로 자르는 것은 `app_session/editor_diff.zig`가 한다 — 그 덕에
    이모지 ZWJ 시퀀스가 반으로 갈리는 일이 구조적으로 생기지 않는다.
  - **안 그리는 경우 셋**: 순수 추가·삭제(줄 전체가 이미 밴드다), 공통 글자 0(같은 이유), 초장문
    줄(§3.8). 앞의 둘은 결과가 같아 테스트가 구분하지 못하므로 **할당 전에 접는지**로 판정한다.
  - **바이트 → 열 변환은 `content.columnOfByte`가 소유한다.** 앞부분을 실제로 펴서 세므로 탭스톱·
    cluster·폭 규칙이 화면과 하나다(별도 걷기를 쓰면 두 곳이 되고 반드시 갈린다). 첫 캡처에서
    **강조가 줄 번호 위에 섰다** — 본문이 gutter 뒤에서 시작하는데 pane 원점부터 셌기 때문이고,
    `layout.contentLeft()`를 더해 고쳤다.
  - **랩된 줄의 이어진 조각에는 아직 안 그린다.** 열 계산이 줄 처음부터라 두 번째 조각의 시작 열을
    알아야 하는데 그 값은 `visual_map`이 자를 때만 안다. 그때까지 그 줄은 **밴드만** 남는다 —
    강조가 엉뚱한 자리에 서는 것보다 없는 편이 낫다.

  **b가 지켜야 할 두 가지**(a를 만들며 실측으로 드러났다 — 어기면 목록과 본문이 정면으로 어긋난다):

  - **줄 끝 문자를 줄에 포함해 넘긴다.** 개행을 떼고 넘기면 `"a\nb\n"`와 `"a\nb"`가 같은 배열이 되어 본문은
    "변경 없음"인데 git은 `+1 -1`을 낸다(끝 개행 제거는 마지막 줄의 변경이다). CRLF도 같다 — `\r`를 떼면
    본문 "변경 없음" 대 git `+2 -2`다. 표시할 때 떼는 것은 뷰의 몫이다(`diff.zig`가 두 경우를 테스트로 고정).
  - ✅ **적용됨** — `git_command.config_overrides`에 `-c diff.algorithm=myers`를 넣었다(모든 git 호출에
    일괄). 그 배열의 목적이 *"사용자 설정이 계약을 깨지 않게 덮어쓴다"*라 자리가 같다. 아래가 그 근거다.
  - **목록의 `git diff --numstat` 호출에 `--diff-algorithm=myers`를 명시한다.** numstat은 사용자의
    `diff.algorithm` 설정을 따르고, 같은 입력에서 `histogram`은 `+1756 -1696`을 냈다 — 기본값의 **7배**다
    (../native-editor-ui.md §7).
  | **c. 좌우 렌더** ✅ **(2026-08-14)** | 한 pane 안에 `frame.build` 둘. **가로는 각자, 세로는 동기**(§3.5). gutter 폭은 좌우 독립 | diff가 보인다(색·세로 스크롤이 d와 함께 붙어 출하 조건을 채웠다) |
  | **d. 색** ✅ **(2026-08-14)** | `diffFromTheme` → chrome `ColorRole`(`terminal_bg`를 올린 그 방식). 배경=diff 밴드, 좌측 색 띠(색만으로 구분하지 않기) | 색이 붙는다 |
  | **e. intra-line** ✅ **(2026-08-15)** | `session/editor/intraline.zig` — 대응된 줄 쌍 **안**에서만 문자 단위 차이. 초장문 줄은 §3.8 축소로 건너뛴다 | 정밀도가 오른다 |
  | **f. 접기(선택)** | §4 접힘을 먼저 만들고 변경 없는 영역에 적용 | N1 잔여를 함께 닫는다 |

  **검증 전략**: a·e는 헤드리스(픽스처 diff·CRLF·파일 끝 개행 없음·바이너리/하위 모듈 → "보여 줄 수 없음").
  c·d는 **Chrome Lab 시나리오 + 커밋 골든**(`tests/fixtures/golden/dock/`에 편집기 골든이 이미 산다 —
  `test-dock-visual-golden`이 지킨다). 좌우 정렬·filler 행·색 띠가 픽셀로 고정된다.

  **CM6에서 이식할 것**(N0c 대조 — 계약에 없고 코드에만 있던 것들):

  - **재시도 정책** `120ms × 50회`(≈6초), 초과하면 "보여 줄 수 없음". *"무한 재시도는 하지 않는다."*
  - **거절 이유는 셋뿐** — `too_large`·`binary`·그 외 일반 문장. 내부 값을 노출하지 않는다.
  - **"변경 없음" 판정**: CM6는 두 문자열이 같은지 본다. 우리는 **대응 결과의 변경 행이 0인가**로 본다(같은 뜻이면서 더 정확하다).
  - **가로 스크롤은 일부러 동기화하지 않는다** — *"양쪽 줄 길이가 다르므로 한쪽을 따라가면 다른 쪽이 엉뚱한 곳을 본다"*(`diff-layout.ts`). §3.5의 "각 편집기가 자기 안에서 가로 스크롤"의 근거가 이것이다.
  - **알파 층 셋**: 줄 배경 16% · 바뀐 글자 34% · 좌측 띠와 변경 gutter 60%, 띠 두께 2px·gutter 3px(`diff-theme.ts`). *"색은 알파로 얹는다 — 배경색을 가정하면 한쪽에서 글자가 안 읽힌다."*

  **그 결정은 닫혔다(2026-08-14) — 올렸다.** `ThemeColors.diff_added/diff_removed`(입력)와 `ColorRole.diff_added_bg/diff_removed_bg`(역할)를 열고, 제품이 `syntax_theme.diffFromTheme`에서 값을 받는다 — **웹(CM6)이 CSS 변수로 받던 그 함수**라 두 화면이 같은 초록·빨강을 쓴다.
  - **역할은 색만 정하고 세기는 op이 정한다**(`Quad.alpha`). 같은 색이 줄 배경(16%)과 좌측 띠(60%)에 함께 쓰이므로, 세기까지 역할로 나누면 토큰이 두 배가 되고 둘이 어긋난다.
  - **밴드는 `fill`이 아니라 `quad`다.** 편집기 텍스트 경로(`buildTextDrawList`)는 `.text`만 셀로 내리고 나머지를 버리므로, `fill`로 내면 **조용히 사라진다**. 배경(`surface`)이 같은 이유로 quad인 것과 같은 자리다.
  - **밴드는 시각 행을 따른다**(gutter와 같은 규칙) — 랩된 줄은 이어진 조각에도 같은 색이 깔려야 한 줄로 읽힌다.
  - **빈 행에는 색이 없다.** 짝을 맞추려 넣은 자리에 색을 칠하면 "그 자리에 무언가 있다"고 말하게 된다.
  - **왼쪽은 삭제만, 오른쪽은 추가만** 칠한다 — 한쪽에 둘 다 담으면 좌우를 나눈 이유가 사라진다.
  - Lab 토큰은 여전히 정적이다(사용자 테마가 골든을 바꾸지 못하게) — 그 시나리오가 판정하는 것은 색상값이 아니라 **어느 행에 밴드와 띠가 서는가**다.
- **N2 — 편집.** **버퍼 표현은 확정이 아니라 1순위 후보이며, 구현 전에 실측해 다시 고른다**(2026-08-10 사용자 결정 — ../native-editor-document-model.md §3.0). 초판이 "rope 확정"이라 적은 근거가 자기 모순이었고(멀티 커서로 돌렸는데 같은 절이 "piece table이 멀티 커서를 못 해서가 아니다"라고 인정한다), Zed 선례는 그쪽 근거이지 우리 측정이 아니다.
  - **착수 게이트는 없다**(2026-08-23 사용자 결정). 버퍼 표현은 **1순위가 rope**이고 §3.0이 *무엇을 보면 뒤집는지*를 표로 든다 — 편집 누적 후 열화 · 스냅샷 메모리 · `line_index` 흡수 실패 · 프레임 예산 초과. 게이트를 세우려 세 번 시도했고 세 번 다 무너진 경위도 그 절이 소유한다.
  - **`line_index.zig`의 운명도 그때 정한다** — 트리에 줄 수를 다는 구조를 고르면 흡수되고, 별도 인덱스를 유지하는 구조면 남는다.
  - **N1에서 buffer를 만들지 않은 이유가 이것이다.** 읽기 전용이라 슬라이스로 충분했고, 표현을 정하기 전에 인터페이스를 지으면 추측이 된다(selection은 VSCode 소스로 구조를 검증하고 지었지만 buffer는 그런 검증이 없다).
  - 위 게이트를 통과한 뒤 undo(delta, §3.3)와 함께 **구현과 프로파일 검증**을 한다.
  - **버퍼가 섰다(2026-08-24)** — `session/editor/buffer.zig`(persistent rope, L2 순수). 스냅숏이 `O(1)`이라
    §2.1의 워커 분리 전제가 갖춰졌고, 편집은 `Edit`을 돌려줘 **§3.3의 selection 매핑이 얹힐 자리**를
    인터페이스로 열어 뒀다(나중에 끼우면 `insert`/`delete` 서명이 바뀐다). §3.0이 든 뒤집을 신호 넷 중
    둘을 여기서 관측했고 둘 다 뒤집지 않았다 — 근거와 수치는 §3.0이 소유한다.

  - **편집 축이 섰다(2026-08-25).** 커서가 여럿(`⌘⌃D` — 임시 chord, §9.1) · 타이핑·Backspace·Delete·

    저장(BOM·줄끝·끝 개행 보존, 원자적 쓰기 + inode/해시 검증). **왕복 불변식 ①이 처음 판정된다** —

    **찾기 쪽은 구현됐다(2026-08-23)** — `Target.editor`가 서고, 일치 계산은 `session/editor/find.zig`(L2 순수,
    대소문자 규칙은 터미널과 공유)이며, 결과는 `search_match`/`search_match_current` 두 색으로 그려지고
    Enter/⇧Enter가 오간다. **접혀 숨은 매치로 가면 펴고 간다.**
    **왜 N2를 기다리지 않았나**: 이 기능은 없던 것이 아니라 **조용히 틀려 있었다** — 편집기 Term의 코어는
    1×1 sentinel이라 ⌘F가 늘 0/0을 냈다. 버퍼도 caret도 undo도 필요 없는 부분이라 먼저 닫았다.
    **남은 것**: 바꾸기(편집 연산이라 버퍼가 선행) · 현재 일치가 primary selection을 옮기는 것(caret 선행) ·
    스크롤바 결과 마커 · 대소문자/단어 단위 옵션 · 비교 뷰 검색(좌우 중 어느 쪽인지 판정이 선행).
  - **컨텍스트 메뉴**(§8.1): 편집기 대상 항목
  - **설정**(§9): 폰트 크기·탭 폭·랩 토글 + **런타임 크기 조절**
  - **렌더 ABI**: 커서 blink 단일 구간 전제를 **배열로 확장**(§1.1의 회귀 이력 주의)
  - **상태바 확장**(§2.2): 선택 크기·들여쓰기·인코딩 항목
  - **미저장 내용 백업**(§3.10): 전체 내용 + fingerprint를 debounce/종료 시 기록, 복원 시 fingerprint 비교.
    **편집·dirty가 서는 이 단계가 자리다** — 그 전에는 백업할 미저장 상태 자체가 없다
  - **같은 파일 두 곳에서 보기**(§2.4): "나눠서 보기" 명시 명령으로 두 번째 Term 생성 + 뷰 상태 분리
    (버퍼·undo·revision·dirty 공유 / selection·스크롤·랩·접힘 독립) + **뷰 하나를 닫을 때 dirty 확인 안 함**.
    `file-panel.md` 불변식 예외 추가가 같은 슬라이스에 든다(아래 표). **여기 두는 이유**: 편집·undo가 서면
    "문서 하나를 두 뷰가 공유한다"를 실제로 검증할 수 있고, 그 전에는 읽기만이라 공유 여부가 드러나지 않는다
  - **멀티커서 첫 조각이 섰다(2026-08-25)** — "다음 일치 추가"(§9.1). 일치 계산은 `session/editor/occurrence.zig`(L2 순수)이고 **`find`(⌘F)와 일부러 규칙이 다르다**: 대소문자를 가리고 씨앗이 낱말이면 낱말 경계를 본다. 검색은 *"어디 있나"*라 넓게 잡는 편이 낫지만 이쪽은 *"여기도 같이 고치겠다"*라 넓게 잡으면 의도하지 않은 자리를 편집한다. 제품은 primary를 제자리에 두고 **나머지 커서를 옆에 든다**(`editor_extra_selections`) — 마우스는 언제나 primary 하나만 움직이므로 제스처 경로 전부가 "몇 번째를 고치는가"를 들고 다닐 이유가 없다(§3.2a가 열 선택 원본을 단수로 둔 것과 같은 근거). 읽는 통로는 `selections()` 하나다. **chord는 `⌘⌃D` 임시**이고 근거는 위 §9.1이 든다. **남은 것**: 타이핑이 커서마다 들어가는 것은 caret·키 입력 슬라이스, 붙여넣기 분배와 조각 경계 기억은 §3.4가 소유한다.
  - **글자가 들어간다(2026-08-25)** — 타이핑·Backspace·Delete·Enter·Tab이 문서를 고친다. **경로가 둘로 갈린다**: 평범한 글자는 macOS가 `NSTextInputClient` 확정으로 보내므로 `sendCommittedText`가 자리이고, 편집 키만 `handleKeyEvent`로 온다 — 편집기 분기를 키 경로에만 뒀다면 **글자가 하나도 안 들어갔다.** 커서가 여럿이면 delta 하나에 range를 여럿 담아 §3.3의 "한 번의 연산 = undo 하나"를 지킨다. 삭제는 **글자 단위**다(byte 하나만 지우면 깨진 UTF-8이 남고 저장하면 파일이 깨진다) — 다만 code point 경계이지 cluster 경계는 아니다(결합 문자는 `grapheme` 층이 소유한다). 편집 뒤에는 **줄 배열·접힘 층·보이는 줄·파생 수치·렌더 스냅숏**을 다시 세운다(`refreshAfterEdit`) — 특히 렌더 스냅숏을 남기면 클릭이 **사라진 글자의 자리**를 답한다. **caret도 섰다**: 정방향 매핑은 새로 짓지 않고 `columnsAtOffsets`를 쓴다(§5.4 하나의 픽셀-레이아웃 소스 — 두 번째 출처를 지었다가 걷어냈다), 그래서 §4.1g가 "검증할 수 없다"고 적어 둔 **왕복 불변식 ①이 처음으로 판정된다**. **남은 것**: undo 스택·그룹핑(§3.3) · caret 이동 키(§3.2 이동 일습) · dirty와 저장(§3.5의 BOM·줄바꿈 되돌리기) · 한글은 N3.
  - **키 충돌 전수 조사가 N2 안에 있다**(../native-editor-ui.md §9.1). 편집기 액션이 확정되는 시점이라 여기서 기존
    `default_app_bindings`와 교차 대조한다. **확인된 충돌 하나: `⌘D`**(Maru=pane split, VSCode=다음 일치 추가) —
    둘 다 정당한 기능이므로 한쪽을 옮기는 결정이 필요하고, 소유는 `key-input-and-shortcuts.md`다.
  - **검색·타이핑 보조를 N2에 넣는 이유(선행 검토 결과)**: 둘 다 §1.1의 "VSCode 사용자 무회귀" 기준선이라
    뒤로 미루면 그때까지 나온 빌드가 **매일 쓰는 동작이 빠진 상태**가 된다. 검색은 편집 모델만 있으면 되고
    (일치 계산은 L2 순수), 타이핑 보조는 lexer 없이도 저하 동작이 가능하다(§3.7) — 즉 **N4를 기다릴 이유가
    없다.** 검색 결과 위치 표시는 풀 overview 스트립 대신 **스크롤바 마커**로 최소 구현하고, 스트립은 미니맵
    렌더 경로를 재사용할 수 있는 N5에서 올린다.
- **N3 — IME.** `NSTextInputClient`의 `replacementRange`·`markedRange`·`selectedRange`를 실제 위치로 확장한다.
  **터미널이 쓰는 바로 그 경로라 최대 리스크**이며 GUI 손 테스트가 유일 안전망이다. 멀티 커서 × IME 정책도 여기서
  실측으로 정한다(../native-editor.md §11).
- **N4 — 토큰과 LSP 표시.** 미니맵이 lexer 층에 의존하므로 N5보다 앞선다. 계약 절과의 대응:
  - **토큰**(§5·§5.3): **tree-sitter 1층**(런타임 배선 + `init`/`onEdit`/`spansForRange` provider) → LSP semantic
    tokens 층(보이는 범위 요청, 부분 덮기). N1.5에서 이미 뜬 diff 본문에 syntax 색이 여기서 얹힌다. 트리가 서면
    §3.7 타이핑 보조·§3.9 괄호 점프·§4 접힘이 문맥/구문 인지로 **정확해진다**(N2의 저하 동작에서 승격)
  - **tree-sitter 도입에 딸린 일**(2026-08-09 사용자 결정): `build.zig` C 컴파일 배선 · **번들 언어 명시 목록
    확정**(grammar마다 `parser.c`가 붙어 배포물이 커진다 — 열린 집합으로 두지 않는다) · grammar별 **라이선스 확인
    후** [third-party-licenses.md](../third-party-licenses.md) 표 갱신 · 파싱 상한과 파서 실패 격리(§5.3) ·
    전 문서 파싱을 렌더 루프에서 분리(§2.1)
  - **grammar가 없는 파일은 무색이다**(§5). 자체 lexer fallback을 만들지 않는다
  - **진단**(§5): 물결 밑줄(기존 밑줄 장식 확장)·gutter 마커. 출처가 LSP든 CLI 린터든 한 층
  - **레이아웃을 바꾸는 LSP 결과**: 인레이 힌트·ghost text(§4 가로 축)·code lens(세로 축)·
    LSP `foldingRange`가 들여쓰기 접힘을 덮음(§4)
  - **떠 있는 UI**: 자동완성 팝업(§8.2 — `dropdown` 재사용)·**호버/시그니처 박스**(§8.3 — 신규, 마크다운 최소
    서식 해석)
  - **네비게이션**(§5.2): 정의로 이동·진단 클릭·심볼/줄로 이동을 한 경로로. 되돌아가기 스택. root 밖 URI 권한 판정
  - **외부 편집 적용**(§3.6): 포맷·code action·자동완성 `additionalTextEdits` — undo 하나·커서 보존·revision 검증
  - **상태바 확장**(§2.2): 언어 항목
- **N5 — 미니맵·overview 스트립.** 미니맵(§6 — 전 문서 대상, lexer 층만, L2 폭 합 캐시 직접 읽기, 색 블록 quad)과
  overview 스트립(N2의 스크롤바 마커를 미니맵 렌더 경로로 승격). diff **목록**(도크 소스 컨트롤 뷰)은
  [editor-surface-dock.md](../editor-surface-dock.md) §3.5 소유라 이 순서 밖이고, diff **본문**은 N1.5로 앞당겼다.

**모든 단계에 걸치는 축 둘.** 특정 슬라이스에 속하지 않고 각 단계에서 함께 처리한다.

  **조용히 줄어드는 것을 그 단계의 완료로 보지 않는다.**

### 네이티브 편집기 후속 (N5 이후 — 계약 밖이거나 다른 문서 소유)

../native-editor.md §12가 "이 계약 밖"으로 둔 것들의 **구현 순서와 소유처**다. 선행 여부를 함께 검토했다.

|---|---|---|

| **sticky scroll** | N5 이후. 접힘 매핑(N1) 위에 얹히고 들여쓰기만으로도 1차 구현이 가능하다 | native-editor §4 확장 |

**선행으로 끌어올린 셋**: 문서 내 검색, 괄호/주석 토글, 스크롤바 검색 마커 → 전부 **N2**로 옮겼다(위 N2 항목). 근거는 "VSCode 사용자 무회귀"가 §1.1의 확정 기준이고, 이 셋은 LSP를 기다릴 필요가 없기 때문이다.

**chrome 이관(CIM)과의 관계 — 선행 조건이 아니다.** [chrome-interaction-migration.md](../chrome-interaction-migration.md)의
점진 이관은 이 순서와 **독립**이며, 그 완료를 기다리지 않는다. 근거는 **N1.5까지 레거시 컴포넌트 의존이 사실상
없다는 것**이다(../native-editor-layering.md §2.0) — `divider`·`find`는 이주 완료, `scroll_area`·`status_bar`는 신규 세대,
본문·diff 배치는 어차피 신규다. 레거시 접촉(`context_menu`·`dropdown`)은 N2·N4로 밀려 있어, 그 사이 이관이
도착하면 새 형태에 붙고 안 오면 붙였다가 함께 움직인다. **동시 진행 시 편집기 쪽 변경은 확장에 한정**한다.

### 네이티브 편집기 — 함께 갱신해야 하는 다른 문서

`native-editor.md`가 **"저 문서가 소유한다"고 가리키지만 그 문서는 아직 편집기를 모르는** 지점들이다. 각 단계 PR에서
[pr-checklist.md](../pr-checklist.md) "문서 정합성"에 걸리므로 미리 적어 둔다.

**중간에 멈춰도 제품이 온전한 지점은 N1.5와 N5다.** N2~N4 사이에서 멈추면 "일부 파일만 네이티브"라는 상태가
사용자에게 노출되므로, 슬라이스 경계를 그 둘에 맞춘다. LSP 클라이언트 자체(프로세스·JSON-RPC·grant)는 이 순서가
아니라 [editor-surface-tooling.md](../editor-surface-tooling.md) §8.2가 소유하며 N4와 독립적으로 진행할 수 있다.

**N3까지는 한국어 입력이 안 된다.** N2에서 편집이 되지만 한글 조합은 N3에서 붙으므로 **그 사이 빌드는 한국어
사용자에게 출하할 수 없다.** 이것이 N1.5를 앞으로 당긴 또 하나의 이유다 — 읽기 전용 검토 흐름은 IME와 무관하게
완결되므로, IME 리스크를 지기 전에 제품 가치를 한 번 낸다.

**N0 철회가 남긴 것**: 성능을 재지 않기로 했으므로 "CM6가 이미 충분히 빨라서 이관 근거가 무너지는" 분기는
아예 열리지 않는다 — 그 대신 **성능을 근거에서 먼저 뺐다**(../native-editor.md §1.0). 남은 근거는 룩 일관성과
역량·통제력 둘이고, 이 둘은 측정으로 뒤집히지 않는 종류라 **단계 순서는 그대로다**. 다만 규율 하나는 유지한다:
**성능 개선을 주장하는 서술을 문서·PR·커밋에 쓰지 않는다.** 쓰고 싶어지는 시점이 오면 그때가 측정을 다시
꺼내야 하는 시점이다.
