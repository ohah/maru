# Markdown 소스 모드 네이티브 이관 — 설계 검토안

> 상태: 구현 전 검토안. 사용자가 정한 방향은 `.md` 소스를 먼저 네이티브로 옮기고 읽기·리치는 후속 단계로 옮기는 것이다. 아래의 단일 탭·문서 소유권 방식은 아직 확정하지 않았다. [네이티브 편집기 §12](../native-editor.md)와 [파일 패널 §2.5](../file-panel-rich-edit.md)의 현행 동작을 바꾸기 전에 검토한다.

## 현재 경계와 문제

- `.md`는 `kind=.web`인 파일 `Term` 하나를 쓰고, 그 안에서 읽기·소스(CM6)·리치(ProseMirror)를 바꾼다. `web/src/viewer.ts`가 소스/읽기의 CM6 문서, 리치의 별도 문서 모델, 저장 기준점, revision, IME 및 모드 전환을 함께 소유한다.
- 일반 `text` 파일은 `kind=.editor`인 네이티브 파일 `Term`으로 열 수 있다. 그 경로의 문서·undo·저장·외부 변경·닫기 보호는 편집기 런타임이 소유한다. 파일 `Entry.native_editor`는 웹 편집 브리지를 건너뛰게 한다.
- 현재 `Term.kind`는 `.web`과 `.editor`를 배타적으로 취급한다. `collectWebSurfaces`는 `.web`만 내고, 편집기 입력·그리기는 `.editor`를 요구한다. 따라서 `.md`의 소스 화면만 바꾸면 같은 파일 탭의 내용과 surface 소유자가 갈린다. `setFilePanelMode`가 현재 하는 `entry.mode` 변경 + 웹 one-shot만으로는 안전한 전환이 아니다.

## 제안하는 제품 계약

1. **파일 탭의 신원을 유지한다.** 소스↔읽기↔리치 전환은 같은 파일 `Term`·탭·경로 유일성 안에서 일어난다. 전환할 때 탭을 닫고 다시 열지 않는다. 웹 surface는 읽기·리치에 필요하므로 소스 모드에서도 소유권을 잃지 않고 숨긴다.
2. **모드마다 편집자는 하나다.** 소스가 활성일 때 네이티브 편집기가, 리치가 활성일 때 웹 문서 모델이 입력을 받는다. 읽기에는 편집자가 없다. 숨은 편집기는 화면·입력·저장 명령의 권위가 없다.
3. **공통 기준은 Markdown UTF-8 바이트와 문서 revision이다.** 소스에서 읽기/리치로 갈 때 네이티브 문서의 현재 바이트와 revision을 웹에 넘긴다. 리치에서 나갈 때 웹이 직렬화한 Markdown과 revision을 네이티브 문서에 반영한다. 읽기는 그때 확정한 바이트의 스냅샷을 렌더한다. 전환은 디스크에 쓰지 않는다.
4. **전환은 확인된 인계다.** 출발 편집기의 IME 조합이 끝나고 같은 파일·surface 세대·revision의 스냅샷이 도착해야 새 모드를 표시한다. 실패·stale 응답·동시 close/save/reload가 있으면 전환을 취소하고 기존 모드와 미저장 내용을 유지한다. 단순 `entry.mode` 선변경은 하지 않는다.
5. **저장과 닫기는 하나의 최신 내용만 본다.** 현재 활성 모드가 제공한 문서 revision과 마지막 저장 기준점을 비교한다. 소스 저장은 네이티브 safe-save 경로를, 리치 저장은 기존 웹 직렬화·safe-write 경로를 사용하되, 성공 후 공통 저장 기준점을 갱신한다. 닫기·워크스페이스 이동·앱 종료는 인계 중이거나 IME 조합 중이면 fail-closed다. 외부 디스크 변경은 현재 문서와 저장 기준점에 한 번만 적용한다.
6. **리치 왕복 보존 계약을 유지한다.** 소스→리치→소스 왕복에서 기존 §2.5가 바이트 보존을 약속한 요소는 그대로 유지한다. §2.5가 허용한 정규화는 전환만으로 생겨도 변경으로 판정하고 dirty를 표시한다. 원시 HTML·각주·frontmatter의 원문 보존 검증을 계속 쓴다.

## 구현 경계

- `Term` 하나가 네이티브 문서/뷰와 Markdown 웹 surface를 함께 소유하도록 표현한다. 두 surface는 별도 ID·세대를 갖고, `Entry`는 파일 경로·모드·저장 상태의 단일 소유자다. `Term.kind`를 교체하면서 새 Term을 만드는 방식은 탭 신원과 pending close/save를 잃으므로 채택하지 않는다. 정확한 타입 배치는 첫 코드 슬라이스에서 닫힌 switch 전수를 대조해 정한다.
- 순수 상태 전이 모델을 먼저 분리한다: `stable(mode, revision)` → `handoff(from, to, expected_revision, request_id)` → `stable(to, revision)`. 중간에 실패·취소·더 새 요청이 오면 이전 stable 상태만 유지한다. UI는 완료된 상태만 표시한다.
- 웹 브리지는 `currentMarkdown` 스냅샷 요청/적용과 리치의 dirty·IME 상태만 맡는다. 네이티브 소스에서 CM6를 생성하거나 CM6 문서를 저장 기준으로 쓰지 않는다. 읽기 렌더와 리치 편집·Mermaid helper의 현행 보안 경계는 그대로 둔다.
- 명시적 `⌘S`, close 3-choice, 파일 rename/delete, 외부 변경 reload, workspace restore는 모두 새 소유권을 거쳐야 한다. `Entry.usesEditorBridge`를 단순히 `.markdown` 전체에 대해 끄면 리치 저장과 닫기가 깨지므로 모드/전이별로 나눈다.

## 단계와 완료 게이트

1. **상태·인계 계약:** 파일/surface 세대와 revision을 가진 인계 상태머신, stale·중복·OOM·IME·close 경합 테스트. 제품 모드는 아직 CM6 그대로다.
2. **소스 화면:** 같은 Markdown 파일 탭에서 네이티브 문서가 입력·선택·undo·검색·저장을 맡는다. 읽기와 리치는 기존 웹 surface를 쓴다. 소스↔읽기↔리치 각각의 미저장 왕복, 저장 후 재열기, 다른 탭/워크스페이스 왕복을 제품 경로로 검증한다.
3. **회귀·출하 게이트:** 한국어 IME 조합 중 전환/닫기, 외부 수정 충돌, 저장 실패, 웹 프로세스 재시작, rename/delete, restart restore, 긴 문서, Markdown 보안 fixture, 실제 Metal/WebKit 화면 전환을 검증한다. 실패 시 사용자의 미저장 내용을 보존하고 전환을 거부한다. 이 게이트를 통과한 뒤에만 `.md` 소스 기본 경로를 네이티브로 바꾼다.

읽기 전체와 리치 전체의 네이티브 이관은 각각 별도 후속 작업이다. 이 계획은 웹 렌더러나 ProseMirror를 제거하는 계획이 아니다.

## 사용자 확인이 필요한 계약

- 리치 편집 후 소스로 돌아와서 `Undo`를 누르면 **리치에서 확정한 변경 전체를 한 단계로 되돌리는 것**을 제안한다. 반대로 리치 내부의 세부 undo 이력은 리치 모드 안에서만 유지한다. 두 편집기의 내부 이력을 억지로 한 스택으로 합치지 않으면서, 소스에서 보이는 최신 변경은 되돌릴 수 있게 하는 경계다.
