# 원격 파일 트리 — 활성 pane 이 원격이면 그 기계의 폴더를 본다 (RF)

**사용자 요청 2026-09-05**: 「원격 SSH 에선 오른쪽 도크 파일 트리가 안 된다.」 그때의 답은 「아직
미개발」이었고, 이 문서가 그 축을 연다.

소유 관계: [파일 탐색기](../file-explorer.md)가 「트리가 무엇을 어떻게 보여 주는가」를 소유하고, 이
문서는 그 판정에 **원격 축**을 더한다. 전송(ControlMaster)·셸 규율·안전 계약은
[SSH 통합 §4·§6·§9](../ssh-integration.md)가 단일 출처이며 여기서 다시 정하지 않는다. 같은 모양의
문제를 먼저 푼 [원격 SCM](remote-scm.md)·[원격 감시](remote-watch.md)의 계약을 **재사용**하고,
어긋나는 자리만 이 문서가 적는다.

> **clean-room**: 같은 문제를 푸는 공개 도구(원격 편집기 플러그인 등)는 **동작 비교**로만 확인했고
> 코드·표현은 옮기지 않았다. 아래 설계는 maru 자신의 `remote_watch`·`git_command` 선례와 이 문서에
> 적힌 실측값에서 유도했다(`project-rules.md`).

## 0. 범위

**여는 것**: 원격 pane 이 활성일 때 그 기계의 디렉터리를 트리에 그리고, 펼치고, 파일을 **읽기 전용**으로
연다.

**여기서 안 여는 것**(각각 이유가 있다):

| 비범위 | 왜 |
|---|---|
| 맨 `ssh` 세션 | control socket 이 없어 명령을 보낼 자리가 없다 — §6 「접속 방식 = `maru ssh` 전용」과 같은 이유다 |
| 원격 파일 **저장**(편집) | 새 권한면이다(§5 가 드롭 업로드에 대해 정한 것과 같은 성질). RF6 이후 별도 결정 |
| Windows 원격 | 경로 규약(`/C:/…`)과 셸이 갈린다 — [§11](../ssh-integration.md)이 여는 축과 함께 정해야 한다 |
| 원격 휴지통 | 저쪽에 휴지통이 없다 — §4 의 **열린 질문 ④** |

## 1. 지금 무엇이 잘못됐나

트리의 cwd 축은 `followActiveTerminalCwd` → `git_ops.activeTerminalCwd` → `git_ops.termCwd` 이고,
**`termCwd` 는 원격에서 의도적으로 null 을 낸다**:

```zig
// OSC 7 authority가 로컬이 아니다 → 보고된 경로는 원격 것이다.
if (app_session_mod.termCwdIsRemote(term)) return null;
```

그래서 원격 pane 으로 옮겨도 트리는 **직전 로컬 root 에 그대로 멈춘다**(정책 ⑶ 「모르면 직전 값 유지」).
[파일 탐색기 §1](../file-explorer.md)의 표가 그 상태를 이미 이렇게 적고 있다 — 「`maru ssh` 원격 세션은
**로컬에 없는 경로**를 준다 → 검증 파이프라인이 거른다, **실패는 조용하고 root 는 그대로다**」.

**그 null 은 결함이 아니라 안전장치였다.** 원격 경로를 로컬 파일시스템에 대고 해석하면 로컬에 우연히
같은 경로가 있을 때 **남의 폴더**를 원격인 척 보여 주고, 거기서 이름 변경·삭제를 누르면 보고 있지도 않은
로컬 파일이 바뀐다(§9.4 가 링크 감지에서 막은 그 함정이고, SCM 은 [RS2](remote-scm.md)에서 같은 이유로
로컬 보호 가드를 세웠다). 옛 규정은 **읽을 방법이 없다**는 전제 위에 있었고, 그 전제는 이제 틀렸다 —
`ssh_upload.zig`·`git_command.zig` 가 ControlMaster 위에서 원격 명령을 이미 실행하고,
`remote_watch` 는 원격에 **우리 바이너리를 심어** 변화를 스트리밍한다.

그리고 2026-09-05 의 [RS6](remote-scm.md)가 마지막 조각을 놓았다: **원격 pane 의 cwd 를 정확히 아는
자리**(`git_ops.remoteCwd`)가 생겼다. 트리의 자동 따라가기는 그 값을 받으면 된다.

## 2. 계약

### 2.1 트리의 신원도 `(host, path)` 쌍이다

[RS6](remote-scm.md) §17.3 이 훅 cwd 에 대해, [§2.1](remote-scm.md)이 저장소에 대해 정한 것과 같은
모양이다. 로컬은 `host = null`.

- **root 는 쌍으로 저장한다**(`dock-tree-roots` 영속 포함). 경로만 저장하면 재시작 때 **로컬의 같은
  경로**가 복원되어 남의 폴더가 원격 이름표를 달고 뜬다.

  ⚠️ **그건 포맷 변경이다**(적대적 검증 2 회차 — 초안이 「저장한다」로 뭉갰다). 지금 `dock-tree-roots` 는
  `"<개수>:<len>:<경로>…"` 로 **경로만** 싣는다(`session/workspace.zig`). 그래서 RF3 은 ⑴ 새 필드를
  더할지 값을 늘릴지, ⑵ **옛 값을 전부 로컬로 읽는** 마이그레이션을 정해야 한다. 그 저장소에는 선례가
  있다 — 「옛 `dock-entry`/`dock-node`/`dock-group-*` 는 **읽기만** 유지한다(1 회 마이그레이션)」.
- **행 하나하나가 쌍을 안다**고 보지 않는다 — root 가 쌍을 알고 자식은 그 root 에 매인다. 트리는
  이미 root 별 서브트리 구조라, 쌍을 root 에 두면 「목록은 원격인데 클릭은 로컬」이 원리적으로 막힌다
  (RS2 가 목록·diff·쓰기를 한 판정에 묶은 것과 같은 이유).
- **로컬과 원격 root 를 한 화면에 함께 둘 수 있다**(멀티루트는 이미 있다). 그러면 root 마다 다른
  기계이므로, **모든 경로 소비처가 그 root 를 물어야 한다.** 이것이 이 설계의 가장 큰 위험이고 §5 가
  그 그물을 친다.

### 2.2 읽기 파이프라인은 하나다

`session/file_tree.zig` 의 모델(`Row`·`Kind`·`Identity`·펼침·선택)은 **이미 기계 중립**이다. 그러니
트리를 두 벌로 나누지 않는다.

갈리는 것은 **그 값을 어디서 얻느냐** 하나뿐이고, 그 자리는 `file_tree_backend.Backend` 다. 지금
`submit`/`submitFileHash`/`submitRootValidation` 세 종류의 job 이 로컬 스레드에서 `openat`·`readdir`·
`fstat` 을 친다. 원격 root 의 job 은 같은 `Result` 를 **원격 왕복으로** 채운다.

**Job 종류를 늘리지 않는다.** `.directory`·`.file_hash`·`.root_validation` 은 질문의 종류이지 전송
수단이 아니다. 늘리면 소비처의 switch 가 전부 두 배가 된다.

⚠️ **「파이프라인을 그대로 재사용한다」는 과했다**(적대적 검증 3 회차 — 초안의 결함). root 커밋 경로는
capability 를 **하드 요구**한다:

```zig
const validated_dir = result.validated_dir orelse {
    reportFileTreeRootOutcome(self, .identity_missing, .fp_root_capability_gone);
    break :root_result;
};
```

그리고 성공하면 그 fd 를 첫 스캔으로 **이관**한다(`submitValidatedRootScan` → `result.validated_dir = null`).
원격 root 는 그 자리를 **다른 갈래**로 지나야 하고, 그 갈림이 이 설계에서 가장 위험한 한 줄이다 —
잘못 쓰면 원격 root 가 「capability 없는 로컬 root」로 커밋된다. 그래서 §5 의 게이트가 **그 갈림이 정확히
둘인지**(로컬=capability 필수, 원격=원격 신원 필수)를 못 박는다. 원격 갈래는 capability 대신 **같은
왕복이 가져온 신원**을 증거로 요구한다 — 증거 없는 커밋 경로를 만들지 않는다.

### 2.2.1 예산은 트리 전체가 나눠 쓴다

`Backend` 는 AppSession 당 **하나**이고 `max_inflight = 4` 다. 로컬 스캔은 밀리초라 그 넷이 넉넉하지만,
원격 왕복은 그보다 두세 자릿수 느리다. 멀티루트(로컬 + 원격)에서 원격 job 이 슬롯을 물면 **로컬 root 의
스캔이 굶는다** — 사용자에게는 「원격을 열었더니 로컬 트리가 멎었다」로 보인다.

그래서 예산을 **기계별로** 나눈다(원격 root 가 쓸 수 있는 슬롯 상한을 따로 둔다). 값과 형태는 RF2 에서
실측으로 정한다 — 지금 정하면 근거 없는 숫자가 계약이 된다.

### 2.3 capability 는 국경을 못 넘는다 — 그 차이를 숨기지 않는다

로컬 경로는 **열린 no-follow 핸들**(`std.Io.Dir`)로 다룬다. `Result.validated_dir` 가 그것이고,
root 검증이 성공하면 그 핸들이 **첫 스캔으로 그대로 이관**된다. 그 설계의 값어치는 TOCTOU 다 — 경로를
다시 해석하지 않으므로, 검증과 사용 사이에 심링크가 갈려도 다른 것을 열지 않는다.

**원격에는 그 핸들이 없다.** 우리가 가진 것은 명령 한 줄과 그 출력뿐이다. 그래서:

1. **원격 job 은 신원을 텍스트로 받아 pin 한다.** 모델이 이미 그 형태라 타입은 안 바뀐다.
   ⚠️ **그 신원을 `(dev, ino)` 로 못 박지 않는다**(적대적 검증 1 회차 — 초안의 결함). 로컬조차 출처가
   OS 마다 다르다: POSIX 는 `fstat` 의 `(dev, ino)` 지만 **Windows 는 `GetFileInformationByHandleEx` 의
   `FileId`** 를 이름별 표로 읽는다(`file_tree_backend.FileIdMap`). 즉 `Identity` 는 이미 **불투명한
   비교값**이지 dev/ino 의미를 갖는 값이 아니다. 원격 wire 도 그 성질을 지킨다 — 저쪽이 무엇으로 재든
   **같은 기계 안에서 같으면 같다**만 보장하면 된다. 뜻을 부여하면 Windows 원격을 여는 날 계약이 깨진다.
2. **한 왕복 안에서 `stat` 까지 끝낸다.** 목록과 신원을 두 번에 나눠 물으면 그 사이가 창이 된다.
   원자성은 아니지만 창을 **왕복 한 번**으로 좁힌다.
3. **변경(이름·삭제)은 원격에서 신원을 다시 확인한 뒤 수행한다.** 로컬이 「이 inode 를 지운다」고 말할
   수 없으므로, 원격 명령이 `stat` → 비교 → 실행을 **저쪽 한 프로세스 안에서** 한다.
4. ⚠️ **그래도 로컬만큼은 아니다.** 이 차이는 문서에 남기고 UI 에도 남긴다 — 숨기면 다음 사람이
   「같은 보장」으로 읽고 그 위에 기능을 얹는다.

### 2.4 원격 경로는 로컬 syscall 에 **절대** 안 간다

§9.4 의 그물을 트리 축으로 연장한다. 원격 root 아래의 경로가 `Dir.cwd().openFile`·`statFile`·
`realpath`·watcher 등록에 닿으면 그 자체가 결함이다. §5 가 그 판정을 **게이트**로 세운다(산문으로
두면 새 소비처가 반드시 새어 나간다 — `cwd_axis` 게이트가 만들어진 이유가 그것이다).

### 2.5 못 하면 **화면이 말한다**

원격 목록을 못 읽으면(연결이 끊김·`stat` 없음·권한) 조용히 로컬로 떨어지지 않는다. 로컬로 떨어지는
것은 §2.4 위반이고, 조용한 것은 [RW6](remote-watch.md)이 배너를 만든 이유다. 트리는 그 root 를
**「원격이라 못 읽는다」**로 그린다 — 「비었다」와 다르다.

## 3. 무엇을 원격에 물을 것인가 — 전송 후보 (열린 질문 ①)

목록 하나를 얻는 데 필요한 것: 이름·종류(디렉터리/파일/심링크)·**신원**(§2.3 ⑴ — 그 기계 안에서만
뜻이 있는 불투명 비교값). 후보를 **실측 가능한 기준**으로 늘어놓는다. **고르는 것은 사용자 결정이다**(§4).

| 후보 | 원격 의존 | 형식 안정성 | 이미 있는 배관 |
|---|---|---|---|
| ⑴ `find -maxdepth 1 -printf` | **GNU findutils** | 우리가 포맷을 정하므로 안정 | 없음 — ⚠️ **macOS·BSD 에 `-printf` 가 없다** |
| ⑵ `ls -lai` | 어디나 있음 | **로케일·구현마다 갈린다**(이름의 공백·개행) | 없음 |
| ⑶ `stat` 포맷 문자열 | 어디나 있음 | **GNU `-c` 와 BSD `-f` 가 다른 문법** | 없음 |
| ⑷ **원격 헬퍼 바이너리** | 없음(우리가 심는다) | 우리가 정한 wire — 가장 안정 | ✅ [RW3](remote-watch.md)의 `maru-remote-watch` 설치·변종 선택(`uname -sm`)이 그대로 있다 |
| ⑸ sftp 서브시스템 | OpenSSH 기본 활성 | 프로토콜이라 안정 | 없음 — [§11](../ssh-integration.md)이 **다른 축**(Windows 이미지 업로드)에서 따로 검토 중이다 |
| ⑹ **인터프리터 한 줄**(`perl`) | perl(대부분의 Unix 에 기본, **Alpine·slim 컨테이너엔 없음**) | 우리가 wire 를 정하므로 안정 | 없음 — **설치가 아예 없다**(§3.2 에서 실측으로 추가된 후보) |

**⑷ 가 유력하다**: 이름에 개행이 들어가도 안 깨지는 wire 를 우리가 정할 수 있고, 설치·변종 선택·
자기완결(embed + stdin 파이프)·고아 방지 규율이 RW 에 **이미 있다**. 그리고 §2.3 ⑵⑶ 이 요구하는
「한 왕복에 목록+신원」·「저쪽 한 프로세스 안에서 신원 재확인 후 실행」은 셸 도구로는 사실상 못 지킨다 —
`[ "$(stat …)" = N ] && rm f` 는 그 자체가 TOCTOU 다.

**§11 과는 독립 결정이다.** 앞 판은 「두 결정이 서로를 구속한다」고 적었는데 **그건 과했다**
(사용자 지적 2026-09-06). 축이 다르다 — §11 은 **Windows 원격에 파일 하나를 쓰는** 문제이고
(그쪽의 출발점은 `DefaultShell` 이 레지스트리 값이라는 것), 이 문서는 **Unix 원격의 목록·신원**을
읽는 문제다(Windows 원격은 §0 에서 비범위). 게다가 §11 자신의 열린 질문 ⑤ 가 「Unix 도 sftp 로 옮길
것인가」이므로 **경로가 둘인 상태는 그쪽에서 이미 허용된 선택지**다. 나중에 §11 이 Unix 까지 sftp 로
옮기기로 하면 그때 **셋이 되지만 않게** 한 번 보면 된다.

### 3.1 실측 — sftp 는 신원을 주지 않는다 (2026-09-06)

명세를 믿고 정하지 않았다. 하네스와 같은 방식으로 일회용 `sshd` + `sftp-server`(macOS 26.2)를 띄워
**실제로 물었다.**

**⑴ 서버가 광고하는 확장 전부**:

```
posix-rename@openssh.com   statvfs@openssh.com    fstatvfs@openssh.com
hardlink@openssh.com       fsync@openssh.com      lsetstat@openssh.com
limits@openssh.com         expand-path@openssh.com  copy-data
home-directory             users-groups-by-id@openssh.com
```

**신원을 주는 것이 하나도 없다.** inode 확장도, 그 비슷한 것도 없다.

**⑵ 같은 디렉터리를 sftp 와 셸로 나란히 재면**:

| | sftp `ls -la` | `ssh … ls -lai` |
|---|---|---|
| 종류(디렉터리/파일/심링크) | ✅ 모드 문자열로 | ✅ |
| 이름의 공백 | ✅ 안 깨진다 | 파싱하면 깨진다 |
| **신원(inode)** | **없다** | `198688069` … |
| **링크 수(nlink)** | **`?`** — 그 값조차 안 온다 | `1` |
| 심링크가 가리키는 곳 | **안 준다**(링크마다 `readlink` 왕복이 더 든다) | `link.txt -> plain.txt` |

그래서 sftp 로 가면 신원을 `(경로, 크기, mtime, 권한)` 으로 **합성**해야 하는데, 그것은 §2.3 ⑴ 이
금지한 바로 그것이다 — 같은 자리에 다른 파일이 들어와도 같다고 읽는다. **RF6(변경)과 root pin 이 그
합성 위에 서면 안 된다.**

⚠️ **잰 것은 macOS 의 서버 하나다.** 확장 목록은 구현마다 다를 수 있다. 다만 「v3 ATTRS 에 inode 가
없다」는 프로토콜 축의 사실이라 리눅스 서버에서 뒤집힐 여지는 작다. 리눅스 실측은 RF1 에서 같은
스크립트로 한 번 더 돌린다.

### 3.2 실측 2 회차 — 「헬퍼가 정말 필요한가」 (2026-09-06)

⑷ 를 추천해 놓고 그 추천 자체를 쟀다. 같은 하네스(일회용 `sshd` + ControlMaster, macOS 26.2)에
**함정 이름이 든 디렉터리**를 만들고 물었다: 공백·작은따옴표·**개행**이 든 이름, 심링크, 디렉터리.

**⒜ 셸 도구는 예상대로 못 쓴다.**

| 방법 | 결과 |
|---|---|
| `ls -lai` | 개행 든 이름이 **두 줄로 쪼개진다** — 파싱이 원리적으로 불가능하다. 심링크는 `link.txt -> plain.txt` 로 이름 필드에 화살표가 섞인다 |
| `find … -exec stat -f '%i %HT %N' {} +` | 같은 이유로 쪼개진다(`%N` 이 raw) |
| `find -printf` | **미지원**(BSD/macOS 실측 확인) |
| `stat -c`(GNU) | **미지원**, `stat -f`(BSD)만 된다 — 문법이 갈린다는 것도 실측 확인 |

**⒝ 그런데 인터프리터 한 줄은 된다.** `perl` 로 `opendir`+`lstat` 을 돌려 **길이 접두 wire**로 내면:

```
16777234 198711741 f 13 has space.txt
16777234 198711740 l  8 link.txt
16777234 198711738 d  3 sub
16777234 198711743 f 11 nl<개행>name.txt      ← 길이 11 이 이름을 정확히 복원한다
```

`(dev, ino)` · 종류 · **길이로 경계를 준 이름**을 한 왕복에 준다. 즉 헬퍼 바이너리가 주는 것의 대부분을
**설치 없이** 얻는다. 이 기계의 가용성: `perl`·`python3`·`shasum`·`sha256sum` 모두 있었다.
⚠️ perl 이 없는 호스트가 있다(Alpine·slim 컨테이너). 그때는 기능이 없거나 ⑷ 로 떨어져야 한다.

**⒞ 왕복 비용**(localhost·ControlMaster = **네트워크 0 의 바닥값**):

| 잰 것 | 값 |
|---|---|
| 명령 한 번 왕복(10 회 평균) | **약 8 ms** — 프로세스 spawn 포함 |
| 항목마다 `stat` 을 따로(4 항목) | **38 ms** — 항목 수에 그대로 비례한다 |
| 2000 항목 `ls -lai` 출력 | **133 KB** |

⒞ 가 §2.3 ⑵ 「한 왕복 안에서 `stat` 까지」를 **실측으로 정당화**한다 — 항목마다 물으면 디렉터리 하나에
수백 ms 이고, 실제 원격은 여기에 RTT 가 얹힌다. 그리고 133 KB 는 한 왕복 출력 상한을 정할 근거다
(우리 wire 는 그보다 촘촘하다).

### 3.3 그래서 남은 것은 「어디에 install 을 요구하나」다

실측 뒤 후보가 둘로 좁혀졌고, **둘 다 유효하다**:

| | ⑹ perl 한 줄 | ⑷ 헬퍼 바이너리(= RW 것을 늘린다) |
|---|---|---|
| 설치 | **없음** — `noexec` 홈·반입 금지 호스트에서도 된다 | 필요(RW 가 이미 하고 있는 그 설치) |
| 읽기(RF2·RF4) | 충분하다(⒝) | 충분하다 |
| 변경(RF6)의 신원 재확인 | `lstat` → `unlink` — **창이 남는다**(perl 은 `unlinkat` 을 포터블하게 못 쓴다) | `openat`+`fstat`+`unlinkat` 으로 **가장 좁다** |
| 감시(RF5) | 장수 프로세스를 인터프리터로 — 폴링뿐 | RW 가 **이미 그 일을 하고 있다** |
| 메커니즘 수 | 읽기=perl · 감시=바이너리 → **둘** | 전부 한 바이너리 → **하나** |
| 못 쓰는 호스트 | perl 없는 minimal 이미지 | `uname` 을 모르는 OS·`noexec`·반입 금지 |

**결정의 축은 성능도 안정성도 아니다** — 실측상 둘 다 된다. 축은 「원격에 무엇을 남기는가」와
「어디까지 되게 할 것인가」다.

### 3.4 실측 3 회차 — perl 은 생각보다 없다 (2026-09-06)

「perl 은 거의 모든 Unix 에 기본」이라는 §3.2 의 전제를 쟀다. **틀렸다** — 컨테이너·미니멀 쪽에서는
전멸에 가깝다(docker 이미지 7 종, 비관적 끝단의 표본):

| 이미지 | perl | python3 | `stat -c` | `find -printf` |
|---|---|---|---|---|
| debian:stable-slim | ✅ | ✗ | ✅ | ✅ |
| ubuntu:24.04 | ✅ | ✗ | ✅ | ✅ |
| alpine:3.20 | ✗ | ✗ | ✅ | ✗ |
| rockylinux:9-minimal | ✗ | ✗ | ✅ | ✗ |
| busybox:stable | ✗ | ✗ | ✅ | ✗ |
| amazonlinux:2023 | ✗ | ✅ | ✅ | ✗ |
| fedora:latest | ✗ | ✗ | ✅ | ✗ |

- perl **2/7** · python3 **1/7**. ⚠️ 컨테이너 이미지는 최소 설치라 **풀 서버 설치보다 비관적**이다 —
  전통적 서버·개발 박스에는 대개 있다. 다만 「거의 어디나」는 못 쓴다.
- `stat -c` 는 전부 지원(GNU 는 물론 **busybox 도**) — 리눅스에선 사실상 보편이고 macOS(`-f`)만
  갈린다. 하지만 셸 조합의 **개행 이름 framing 문제**(§3.2 ⒜)는 그대로라 이것으로는 결론이 안 바뀐다.
- **결정타**: RW 바이너리의 리눅스 변종은 **musl 정적 빌드**다(`build.zig` — `x86_64-linux-musl`·
  `aarch64-linux-musl`, ReleaseSmall). 즉 위 표에서 perl 이 없는 다섯 이미지 **전부에서 돈다.**
  커버리지는 바이너리 쪽이 넓다.

### 3.5 결론 — ⑷ 로 간다 (제안)

세 번의 실측을 합치면:

| | ⑹ perl | ⑷ 바이너리 |
|---|---|---|
| 안전한 wire(개행 이름) | ✅ | ✅ |
| 커버리지 | macOS + debian/ubuntu 계열 | **macOS + 리눅스 전부**(musl 정적) — 못 도는 곳은 미지의 OS/arch 와 `noexec` 뿐 |
| 원격에 남는 것 | 없음 | 파일 하나 — **단 RW 가 이미 남기는 그 파일에 기능을 더하면 개수가 늘지 않는다** |
| 삭제(RF6) 안전성 | 틈이 남음 | 가장 좁음 |
| 감시(RF5) | 폴링뿐 | 이미 있음 |

perl 의 유일한 우위(안 남김)는 「남기는 것이 이미 현실」(RW, 사용자 승인 선례)이라는 사실 앞에서
실익이 준다. 반면 커버리지·삭제 안전성·메커니즘 수는 전부 ⑷ 쪽이다. **그래서 ⑷ — 기존
`maru-remote-watch` 를 「원격 파일시스템 도우미」로 넓혀 목록 명령을 더하는 것 — 을 제안한다.**
못 심는 원격(미지 OS·`noexec`)은 §2.5 대로 **화면이 말한다**(조용한 폴백 없음).

## 4. 열린 질문 — 사용자 결정이 필요하다

### ① 전송을 무엇으로 하나 (§3)

⑷ 헬퍼 바이너리 / ⑸ sftp / 둘 다(축별로). **§11 과는 독립이다** — 정하려면 §3 의 ⚠️ 두 가지가
필요하다: sftp 신원 실측과, 원격에 바이너리를 심는 것에 대한 정책 판단.

### ② 무엇을 root 로 세우나

로컬 규칙은 「활성 터미널의 cwd 폴더 **그 자체**」다(§1 정책 ⑶, 2026-08-31 사용자 결정). 원격도 같은
규칙이면 `remoteCwd` 를 그대로 받으면 된다. 그런데 원격은 **왕복이 든다** — `cd` 마다 root 교체가
접힘·스크롤을 버리고 원격 스캔을 새로 건다(로컬에서도 치르는 대가지만, 저쪽에서는 지연이 보인다).

- ㉮ 로컬과 **같은 규칙**(cwd 따라가기). 일관되지만 `cd` 마다 원격 왕복.
- ㉯ 원격은 **수동만**(폴더 열기…로 고른 root 유지). 조용하지만 「두 뷰가 같은 곳을 본다」가 깨진다.
- ㉰ 따라가되 **디바운스**. 절충이지만 규칙이 하나 더 생긴다.

### ③ 감시를 어디까지 하나

RW 의 감시자는 **저장소 하나**를 보고 `change` 한 줄만 낸다(`remote_watch.change_line`). 트리는
**펼친 디렉터리 여럿**을 보고, 어디가 바뀌었는지 알아야 그 서브트리만 다시 읽는다.

- ㉮ RW 프로토콜을 늘린다(`change <path>`) — 채널 하나를 SCM 과 공유. ⚠️ 지금 계약은 「트리거만
  바꾼다」이고, 경로를 실으면 그 계약이 바뀐다.
- ㉯ 트리 전용 채널을 하나 더 — 계약은 안 건드리지만 **세션 예산**을 먹는다(§11.4 ⑥: `MaxSessions`
  기본 10, pane 당 이미 둘을 쓴다. 실측으로 그 상한에 물린 적이 있다).
- ㉰ **안 한다**(수동 새로고침·펼칠 때만 읽기). 가장 싸고, 로컬과 다른 경험.

**✅ 확정(2026-09-06, RF5a): ㉮ 의 변형 — 「채널 하나를 두 뷰가 나눠 쓴다」. 프로토콜은 안 늘린다.**

셋 중 무엇도 그대로 고르지 않은 이유는 **도크가 한 번에 한 뷰**라는 사실이 셋의 전제를 바꾸기
때문이다. `pumpRemoteWatch` 는 이미 「소스 컨트롤 뷰가 보일 때만」 돌고, 그 밖에서는 `pause` 한다
(`git.zig` — 「감시는 화면을 위한 것」). 즉 **탐색기를 보고 있는 동안 SCM 감시자는 어차피 멈춰 있다.**
그 멈춘 채널을 탐색기가 자기 root 로 쓰면:

- **새 채널이 0 이다** — ㉯ 가 물던 세션 예산을 안 문다(감시자는 창 당 하나 그대로).
- **프로토콜이 그대로다** — ㉮ 가 바꾸려던 「트리거만 바꾼다」 계약을 안 건드린다. `change` 한 줄은
  여전히 트리거이고, 누가 그 트리거를 받느냐만 뷰가 정한다.
- **동시 수요가 없다** — 두 뷰가 같이 보이는 상태가 없으므로 채널 하나로 충분하다는 것이 *구조적으로*
  참이다(우연이 아니다).

경로가 안 실리므로 무효화는 **거친 것**이다: 트리거 하나에 **펼쳐 둔 디렉터리 전부**를 다시 읽는다.
로컬은 경로를 알아 그 서브트리만 읽지만(`fileTreeChanged` → `invalidatePath`), 원격은 트리거만 알고
대신 **읽을 대상이 유계다**(펼친 것만 · 큐가 중복 제거 · 원격 슬롯 2). 정밀 무효화가 필요해지면 그때
wire 판 4 로 경로를 실으면 되고(RF5b), 그 전에 굳이 계약을 바꾸지 않는다.

⚠️ **한계 둘을 화면이 알아야 한다**(§2.5). ⑴ **macOS 원격**의 감시자는 inotify 가 아니라 **git
다이제스트 폴링**이다(`watchPoll` — kqueue 가 편집을 안 알린다). 그래서 저장소 밖 변경·git 이 무시하는
파일은 안 잡히고, **git 앞머리가 없으면 아예 `exit_unsupported`** 다. ⑵ 리눅스 원격은 inotify 라 일반
변경을 잡지만 디렉터리 상한(`max_dirs = 65_536`)이 있다. 둘 다 「감시가 안 선다」는 **이미 있는 통지**
(`scm_remote_watch_gave_up` 와 같은 자리)로 말하고, 조용히 수동으로 내려가지 않는다.

### ④ 원격 삭제를 무엇으로 하나

⚠️ **RF6a·RF6b(이름 변경)는 이 결정을 안 기다린다.** 이름 변경은 되돌릴 수 있고(다시 바꾸면 된다)
휴지통이 필요 없어서, 삭제와 **다른 슬라이스**로 갈랐다(RF6c). 아래는 그때 볼 것이다.



로컬 삭제는 **macOS 휴지통**으로 옮기고 되돌릴 수 있다(`file_tree_mutation_backend` 가 대상을
`<이름>.maru-trash-<id>-<nonce>` 로 staging 한 뒤 Trash 로 옮긴다 — 실패하면 롤백한다). **원격에는
휴지통이 없다.**

- ㉮ **원격 삭제를 안 연다**(읽기 전용 + 이름 변경까지만). 되돌릴 수 없는 것을 안 만든다.
- ㉯ 원격 휴지통 디렉터리를 우리가 만든다(`~/.cache/maru/trash/`). 되돌리기가 생기지만 **원격에
  쓰레기를 쌓는 새 정리 정책**이 필요하다(§11.4 ② 가 업로드 정리에서 겪은 그 문제).
- ㉰ 그냥 `rm` + **확인 모달에서 「되돌릴 수 없다」를 말한다**.

**✅ 사용자 결정(2026-09-06): ㉰.**

조사 중에 ㉯ 를 밀어낸 사실이 하나 더 나왔다: `~/.cache/maru/trash/` 가 대상 파일과 **다른 마운트**면
`rename` 이 `EXDEV` 로 실패한다. 그러면 되돌리기를 지키려고 **복사+삭제**로 내려가야 하는데, ssh 너머로
큰 파일을 복사하다 끊기면 **반쪽 사본**이 남는다 — 「되돌릴 수 있다」를 지키려다 더 나쁜 실패를
만드는 것이다. 여기에 §11.4 ② 의 정리 정책 문제(남의 서버에 쓰레기가 쌓인다)가 더해진다.

㉰ 의 안전은 **되돌리기가 아니라 «엉뚱한 것을 안 지운다»** 에서 온다: 이름 변경과 같은 축으로
헬퍼가 저쪽 한 프로세스에서 `stat` → 신원 비교 → `unlinkat` 을 한다(§2.3 ⑶). 셸 `rm` 은 그 보장이
없다. 그리고 되돌릴 수 없다는 사실은 **확인 모달이 말한다** — 로컬은 되돌리기가 있고 원격은 없다는
차이를 숨기지 않는 것이 §2.3 ⑷ 다.

### ⑤ 파일을 열면 무엇이 열리나

`buildRemoteFileRead` 가 이미 있다 — `head -c 4MiB`, 절대경로만, **원격에서 자른다**. 그것으로 읽기
전용 뷰어는 바로 된다.

- 저장을 **영영 안 열 것인지**, RF6 이후 별도 트랙으로 둘 것인지.
- 잘린 파일을 **편집기에 띄우지 않는다**는 것은 확정으로 두는지(잘린 내용을 저장하면 원격 파일이
  잘린다 — 저장을 열 때 반드시 다시 볼 자리다).
- ⚠️ **외부 변경 판별을 원격에도 걸 것인지**(적대적 검증 6 회차 — 초안에 없던 축). 열린 파일이 밖에서
  바뀌었는지는 `.file_hash` job 이 판정하고, 그 소비처는 `verifySelfWriteEvent` 다 — 감시자 이벤트가
  **우리 자신의 쓰기**인지 가른다. 원격 파일에 그대로 걸면 판정 한 번에 **파일 바이트가 링크를 건너온다**
  (읽기 상한이 4 MiB 다). 후보: ㉮ **원격에서 해시**하고 값만 받는다(헬퍼·`shasum` 중 무엇인지는 ① 에
  매인다) ㉯ 원격 파일에는 외부 변경 판별을 **안 건다**(읽기 전용이면 자기 쓰기가 없으므로 자연스럽다)
  ㉰ 크기+mtime 으로 대신한다(싸지만 틀릴 수 있다).

## 5. 새는 길을 게이트로 막는다

`cwd_axis` 가 「`observation.cwd` 직독은 재고에 적힌 함수에서만」으로 만든 그 규율을 트리 축에도 세운다.
**산문으로 두면 반드시 샌다** — 그 게이트가 만들어진 계기가 「여섯 곳이 옛 축에 남아 있었다」였고,
이미지 갤러리는 `cwd` 가 아닌 **다른 필드**로 같은 구멍을 냈다(§9.4.1).

트리 축의 판정: **원격 root 아래 경로를 로컬 syscall 에 넘기는 자리가 0 인가.** 대상은
`file_tree_backend`·`file_tree_mutation_backend`·`file_panel` 의 열기·감시자 등록이다.

**게이트는 첫 배선(RF2)과 함께 세운다** — RF1 시점에는 원격 분기가 코드에 없어 재고가 비고, **빈
재고를 못 박는 게이트는 아무것도 안 잡는다**(「없어진 것」과 「원래 없던 것」을 구분 못 하는, 이
저장소가 가장 나쁘다고 적어 둔 실패 모드다). 형태(이름 재고 / 호출 지점 재고)는 그때 실측한다.

## 10. RF1 — wire 코덱과 root 키 (2026-09-06)

**들어간 것**: [`src/session/remote_file_listing.zig`](../../src/session/remote_file_listing.zig)
(배럴 `session.remote_file_listing`).

- **wire v1** — 머리(`maru-rfls 1`, 판 불일치 즉시 거부) · 디렉터리 자신의 신원(`D`) · **길이 접두
  이름**의 항목(`E`) · 원격 오류(`!` — 이것도 완결이다, §2.5) · 꼬리(`X <count>` — 없으면 잘린 것,
  count 불일치는 중간 유실). 인코더는 `remote_shell.quoteAppend` 와 같은 버퍼-append 꼴(할당 없음 —
  ReleaseSmall 헬퍼가 그대로 쓴다)이고, 넘치면 null 로 **잘린 레코드를 절대 만들지 않는다.**
- **상한**: 이름 1024 B(APFS 최대 1020 B 를 덮는다) · 오류 512 B · 항목 100,000 ·
  host 는 `CwdLabel.max_host` 를 **직접 참조**(RS6 이 잡은 「상한 두 벌」 재발 방지 — 순수 층끼리라
  comptime 못 없이 참조로 충분하다).
- **`RootKey{host, path}`** — 로컬은 `host=""`. `remoteRootIsValid` 는 절대경로·제어문자 거부·host
  비어있음 거부(`""` 는 로컬의 표기다)·상한.

**검증**: 판정자 10 개 — 함정 이름(공백·개행·따옴표·한글) 왕복 · 꼬리 부재=미완결 · 이름 한가운데
절단=오류 · 판 불일치(그리고 **RW 의 `change` 스트림이 섞인 모양**) · count 불일치 · 원격 오류 완결 ·
TrailingData · 이름 상한 양끝 · 쓰레기 입력 7 종 · RootKey/판정자. 뮤테이션으로 count 대조를 무력화해
그 판정자가 그 자리에서 죽는 것을 확인했다.

⚠️ **실행 경로**: 이 파일은 `file_tree.zig` 를 임포트하고 그 파일이 `../path_shape.zig` 를 쓰므로
**파일 단독 `zig test` 가 안 된다**(module path 밖). `zig test src/session.zig --test-filter …` 로
돌린다(배럴 루트). 단독 크로스컴파일도 같은 이유 + `config_doc_md` embed 로 막혀, Linux 검증은 CI
`check` 가 소유한다 — 이 모듈은 syscall 이 없는 순수 코드라 그 축의 위험은 없다.

### 10.1 적대적 검증 3 회 (2026-09-06) — 초안 코덱의 결함 셋

머지 전에 코덱 자신을 공격했다. **셋을 고쳤고 하나는 주석으로 못 박았다.**

| # | 결함 | 왜 위험한가 |
|---|---|---|
| 1 | **파서가 경로 탈출 이름을 안 걸렀다** | 이 wire 는 **신뢰 경계를 건너온다**(원격이 오염될 수 있다). 소비처는 root 와 이름을 이어 경로를 만드는데, `..`·`a/b`·NUL 이름이 통과하면 그 하나가 **root 밖**을 가리킨다. 정상 readdir 은 그런 이름을 낼 수 없으므로 왔다는 것 자체가 오염 신호다 → `UnsafeName` 으로 거부 |
| 2 | **신원(`D`) 없는 꼬리가 완결로 통과했다** | 빈 목록도 root pin 은 신원이 필요하다 — 신원을 생략한 헬퍼가 영영 안 드러난다 → 꼬리가 `saw_dir` 를 요구 |
| 3 | **`remoteRootIsValid` 가 꼬리 `/` 를 받았다** | `/srv/app` 과 `/srv/app/` 이 다른 키가 되어 같은 폴더가 트리에 두 root 로 선다 → 거부(`/` 하나는 예외) |
| 4 | (주석) 오류 메시지 자름이 바이트 경계다 | errno 문자열(ASCII) 전제 — UTF-8 메시지를 싣게 되면 글자 경계로 물려야 한다는 것을 그 줄에 적었다 |

판정자 12 개가 됐고, 1 번은 뮤테이션(`.`/`..` 거부 무력화)으로 실제로 잡는 것을 확인했다.


### 10.2 RF2a — 헬퍼 `list` 와 실물 왕복 게이트 (2026-09-06)

**들어간 것**:

  있어야 하고, 판이 그 사실을 보증한다(RW 설치 계약 그대로 — 옛 판이 깔린 원격은 다음 설치에서 갈린다).
- `tests/remote_file_listing_roundtrip.zig` + `zig build test-remote-file-listing` — **빌드가 만든 실물
  바이너리를 실제로 돌려** 세션 코덱 파서로 되읽는 게이트. 함정 이름(공백·개행)·심링크 3 종 구분·
  신원(이쪽 no-follow stat 과 대조)·오류 2 종 완결. `--maru-expect-passed=3` 으로 env 부재의 조용한
  skip 까지 막는다. 헬퍼가 인코더 **사본**을 드는 대가(§10 — std 만 임포트)를 이 게이트가 낸다:
  뮤테이션으로 헤더 한 바이트를 갈랐더니 세 판정자가 전부 `UnsupportedVersion` 으로 죽었다.

**구현에서 배운 것(Zig 0.16 syscall 갭)**: musl 타깃의 `std.c` 에는 `fstat`/`fstatat` 이 없고,
`std.posix.fstat`/`fstatat`/`getenv` 도 없다. 리눅스는 **`std.os.linux.statx` 하나**가 남은 길이다
(`Stat` 타입도 없다 — 오류 판정은 `std.os.linux.errno`). darwin 은 종전대로 `std.c.fstat` 계열.
dev 는 statx 의 major/minor 를 u64 하나로 접는다 — wire 계약이 「같은 기계 안에서 같으면 같다」뿐이라
접는 방식은 자유다(§2.3 ⑴).

**비범위(RF2b 로)**: 전송 argv(ControlMaster 위에서 `list` 를 부르는 쪽)·백엔드 원격 워커·표시·§5 게이트.

  `readAllFd` 는 64 KiB 에서 읽기를 **멈추는** 구조라 자식이 그보다 많이 쓰면 파이프가 차 `waitpid`
  가 교착한다 — 목록은 MB 축이라 못 쓰고, 새 러너는 넘치면 **fd 를 닫아** 자식을 EPIPE 로 끝낸다
  (헬퍼 `putAll` 이 그 계약이다). 넘침은 `-2` 로 갈라 「깨끗한 0」과 안 섞인다.
- `remote_file_listing.max_wire_bytes = 8 MiB` — 전송이 읽기를 자르는 상한(실측 §3.2 ⒞ 근거).
- `file_tree_backend.zig` — `submitRemoteDirectory`(macOS 전용, dest·ctl 을 job 이 소유) · worker 의
  원격 갈래 = **전송(runRemoteCapped) + 순수 매핑(remoteResultFromWire)** 둘로 갈라 매핑을 ssh 없이
  단위로 겨눈다. `Result.remote_error`(§2.5 — 말할 수 있는 실패: 원격 `!` 메시지 / `transport exit N`
  / `listing malformed` / `listing truncated`. **오독이 잘림보다 먼저다** — 오독은 항상 미완결을
  함의해 순서를 뒤집으면 malformed 가 죽은 가지가 된다. 판정자가 실제로 잡았다).
- **원격 슬롯 상한**(§2.2.1): `max_remote_inflight = 2` — 「로컬에 항상 둘을 남긴다」. RF3 이 제품
  트래픽으로 재측정한다.
- **§5 게이트**(`tests/remote_file_tree_axis_boundary.zig`, check-boundaries 소속): ⑴ 원격 갈래
  둘의 본문에 로컬 FS 호출 토큰 0 + `validated_dir` 0(capability 는 국경을 못 넘는다) ⑵
  `submitRemoteDirectory` 소비처 재고 — **RF3 전에는 0**(늘면 이유와 함께 재고를 올린다) ⑶ 로컬
  root 커밋의 capability 하드 게이트(`.fp_root_capability_gone`) 존치 — 갈래는 정확히 둘이어야 한다.
- **실물 sshd 왕복 게이트**(`zig build test-remote-file-tree`): `tools/remote-scm/ssh_harness.sh` 위에서
  제품 전송이 실물 헬퍼의 wire 를 왕복 — 신원이 이쪽 stat 과 일치·`seed.txt`/`.git` 종류·없는
  디렉터리의 `!` 완결. `--maru-expect-passed=2` 로 하네스 침묵 차단. 스크립트는 일반형(`exec "$1"
  list "$2"`)이다 — 제품 리터럴은 설치 계약 경로를 exec 하는데 하네스 sshd 의 HOME 은 실사용자
  홈이라, 거기 심는 것은 테스트가 사용자 캐시를 오염시키는 일이다(리터럴의 형태는 순수 판정자 몫).

**뮤테이션**: 매핑의 오독/잘림 우선순위(위) + §5 소비처 재고(가짜 `submitRemoteDirectory` 토큰을
소비처에 넣자 `expected 0, found 1` 로 즉사).

**비범위(RF3 로)**: root 세우기·「못 읽는다」 **표시**·`remoteCwd` 따라가기·영속 쌍 마이그레이션 —
전부 「트리에 원격 root 가 선다」에 매여 있다.


### 10.4 RF3a — 트리에 원격이 선다 (2026-09-06)

**② = ㉮(cwd 따라가기) 로 확정** — 근거는 기존 사용자 결정 둘이다: 2026-08-31 「root 는 cwd 폴더 그
자체, 예외 없음」과 §3.5 「두 뷰가 같은 곳을 본다」(SCM 도크는 RS6 부터 원격 cwd 를 따라간다 —
트리만 안 따라가면 그 불변식이 깨진다).

**구조 — 원격 모델은 로컬을 대체하지 않고 얹힌다**(`file_panel.RemoteExplorer`): 별도 `Tree`
인스턴스라 ⑴ 로컬의 접힘·스크롤·영속이 안 다치고 ⑵ 같은 철자의 두 기계 경로가 한 모델에서 충돌할
일이 없고(§2.1) ⑶ 로컬 소비처 65 곳을 라우팅하는 대신 **행 상호작용 접점 몇 곳만** 펜스하면 된다.
발행 행 목록은 하나이고, 원격이 활성이면 원격 모델이 그것을 채운다.

- **따라가기**: `followRemoteExplorer` — 가시성 게이트(§1.1 + 탐색기 뷰 한정) → `remoteScmTarget`
  재사용(SCM 과 같은 판정이어야 도크의 두 뷰가 다른 기계를 못 본다) → `applyRemoteExplorerTarget`.
  판정과 적용을 가른 것은 RS6 의 `remoteCwd` 분리와 같은 결 — 판정은 살아 있는 control socket 을
  요구해 단위에서 못 세우고, 적용부터는 실물로 태운다.
- **헬퍼 설치**: RW 펌프(`beginWatchInstall`) 재사용 + 탐색기 follow 에서도 drain — SCM 뷰 펌프는
  소스컨트롤 뷰에서만 돌아서, 탐색기만 쓰는 세션은 여기가 유일한 drain 자리다.
- **표시**: root 스캔 실패는 **트리를 비워 안내 행(.empty)이 서게** 한다 — root 행을 남기면 «펼쳐진
  빈 폴더» 로 보여 실패가 화면에 없다(§2.5). 안내 라벨은 투영에서 갈아 끼운다:
  `fp_remote_tree_unreadable`(실패)·`fp_remote_tree_loading`(첫 목록 전). 하위 실패는 그 노드만 접는다.
- **펜스**(§2.4): 행 활성화 — 접기/펼치기는 원격 모델로, 파일 열기는 `fp_remote_open_unsupported`
  안내로 거절(RF4 전까지 — 조용한 무동작이 아니다). 변경 진입점(`selectedFileTreeMutationTarget`)은
  원격이면 null(RF6 전까지). 원격 결과에 로컬 git check-ignore·감시자 등록을 안 댄다. open 상태는
  로컬 파일의 것이라 원격 행에 안 물린다(같은 철자가 «열린 것처럼» 빛나는 §2.4 표시 거짓 방지).
- **v1 비영속**: 재시작하면 따라가기가 다시 세운다(원격 SCM 과 같은 흐름). `dock-tree-roots` 쌍
  마이그레이션은 명시적 원격 root 고정이 생길 때(RF3b) — 지금 넓히면 아무도 안 쓰는 포맷 갈래다.

**검증**: 실패·성공 수직 판정자(`zig build test-remote-explorer`) — 적용→root 행→**성공 주입**(항목·
신원 pin·개행 이름 라벨)→**실패 주입**→«못 읽는다» 접힘→로컬 복귀. 결과 주입은
`pushResultForTest`(isIdleForTest 와 같은 test-only 규율 — 실물 전송은 RF2b 하네스가 소유).
뮤테이션: 접힘을 무력화하니 판정자가 그 자리에서 죽었다. §5 게이트 재고 갱신(소비처 = file_panel
원격 펌프 **하나**) + 펜스 존재 판정 추가.

**한계**: ⑴ 제품 실측(실서버에서 트리가 실제로 뜨는 것)은 수동 — RW 가 PR #3224 에서 한 형태의
캡처를 RF4 전에 한 번 남긴다. ⑵ recent_header 가 원격에서도 count 0 으로 뜬다(로컬 빈 상태와 같은
상수 행 — 정리는 후속). ⑶ 하위 디렉터리 실패는 시각적으로 조용하다(loading 멈춤) — err 은 남는다.

### 10.6 RF4 — 원격 파일이 열린다(읽기 전용) (2026-09-06)

**⑤ 확정**: v1 = **읽기 전용, 저장 없음**(저장은 별도 트랙 — 새 권한면). **상한(4 MiB) 이상이면
열지 않고 안내한다** — 잘린 내용이 온전한 척 뜨는 것이 최악이고, 장차 저장 축이 열리면 잘린 저장이
원격 파일을 자른다. **외부 변경 판별은 안 건다**(읽기 전용이라 자기-쓰기가 없고, 미러는 우리만 쓴다 —
원격 쪽 변경은 다시 열면 새로 받는다. 갱신 없는 스냅샷임을 한계로 남긴다).

**구조 — 임시 미러 + 기존 파이프라인**: 원격 바이트를 `$HOME/.cache/maru/remote-view/<dest·부모
해시>/<basename>` 에 내리고(초안은 `/tmp` 였다 — 1 회차 처방) **기존 로컬 열기 파이프라인**(신원 pin·구문 강조 포함)을 그대로 태운 뒤
문서를 `read_only` 로 만든다(편집·저장 진입점이 문서 층 가드들로 닫힌다 — 제품 최초의 read_only
소비자다). 새 EntryKind 를 만들지 않는다(닫힌 열거 관례) — diff 처럼 webview 로 가지 않고도 네이티브
에디터를 얻는다. basename 이 보존돼 탭·라벨이 원격과 같아 보이고, 해시 디렉터리가 「다른 기계·다른
폴더의 같은 이름」 충돌을 막는다(wire 의 UnsafeName 이 `/`·NUL 없는 이름을 보증한다).

**전송 — SSOT 재사용**: 읽기 명령은 `git_command.buildRemoteFileRead`(RS3 의 그 명령 — 인용·상한
소유) argv 를 그대로 `ssh_upload.runArgvCapped`(신규 — argv 판 capped 러너)로 실행한다. 스크립트를
다시 쓰면 두 벌이 된다. `sshArgv` 의 `BatchMode=yes` 가 「프롬프트 없음」을 전송 층까지 잇는다.
단발 워커 + tick 드레인(`finishRemoteFileOpen`) — in-flight 중 새 열기는 «바쁨» 안내로 거절하고,
비활성(낡은 행)의 클릭도 침묵이 아니라 «못 읽는다» 다(§2.5).

**검증**: 열기 수직 판정자(`test-remote-explorer`) — 결말(제품 드레인 함수를 직접 호출, test-only
표식 불요)→실패(127=«못 읽는다» 바이트)→과대(=«너무 큼»)→성공(미러 실바이트 대조·entry·**doc
read_only**)→바쁨 안내. 뮤테이션: read_only 세팅을 무력화하니 그 단언에서 즉사. §5 게이트 토큰을
열기 진입점+안내 존재로 갱신.

| 6 | capped 읽기 루프의 `n <= 0` 이 **EINTR·읽기 오류를 EOF 로 위장** — 목록 wire 는 `X` 꼬리로 잘림을 자기 방어하지만, 파일 읽기는 꼬리가 없어 시그널 한 번에 잘린 바이트가 exit 0 과 함께 «온전한 척» 열린다(§2.5 최악 케이스가 전송 층에서 재발) | `runArgvCapped`: EINTR 재시도 + 그 밖의 읽기 오류는 `-1`(실패) — «못 읽는다» 안내로. `runRemoteCapped`: EINTR 만 재시도(그 밖은 기존 «잘림» 의도 유지 — 파서가 판독) |

고치지 않고 기록만 한 것: 미러 해시(Wyhash)는 비암호라 **악의 원격 서버**가 부모 경로를 골라 다른
목적지의 해시 디렉터리와 충돌시킬 이론 경로가 있다 — 전제(내가 접속한 서버가 적)가 서면 그 서버는
파일 내용 자체를 속일 수 있어 충돌이 더 주는 것이 없고, 열 때마다 새로 받아 덮어쓰므로 남는 창도
좁다. 저장 축이 열리는 날 재평가.

### 10.12 실측 캡처 2 회차 — 감시·이름 변경·삭제 (2026-09-06)

§10.7 이 세운 레시피로 RF5a·RF6b·RF6c 를 실서버(colima, Linux aarch64 · 실 sshd)에서 찍었다.

**① 감시(RF5a)** — 캡처 지연 **중에** 원격에서 `appeared-by-watch.txt` 를 만들었더니, **사용자 조작
없이** 트리에 떴다. 감시자 트리거 → 펼친 디렉터리 재스캔이 제품에서 실제로 돈다는 뜻이다.

**② 이름 변경(RF6b)** — `old-name.txt` 행이 `new-name.txt` 로 바뀌어 뜨고, 원격에서 `ls` 해도 실제로
바뀌어 있다(로컬 표시만 바뀐 것이 아니다).

**③ 삭제 확인(RF6c)** — 확인 모달이 「선택한 항목을 원격에서 삭제할까요? **원격에는 휴지통이 없어
되돌릴 수 없습니다.**」 를 말하고 버튼이 **「영구 삭제」**(로컬은 「휴지통으로 이동」)다. 그리고
**파일은 안 지워졌다** — 요청은 묻기만 하고, 확인은 사람의 몫이라는 것이 캡처로도 증명된다.

**캡처 하네스에 넣은 것**(디버그 전용 env-gate, 미설정이면 무동작):

| env | 하는 일 | 왜 이 모양인가 |
|---|---|---|
| `MARU_OPEN_EXPLORER_RENAME=<경로>\|<새 이름>` | 그 행을 골라 이름을 바꾼다 | `enqueueFileTreeEdit` 를 부른다 — **원격 갈림이 사는 문**이라, 손으로 원격 커밋을 부르면 그 문을 안 지나 캡처가 실제 배선을 안 태운다(§10.10 의 그 함정) |
| `MARU_OPEN_EXPLORER_DELETE=<경로>` | 그 행을 골라 삭제를 **요청**한다 | 확인 모달이 뜨는 것까지가 이 픽스처의 일이다 — 확인을 누르는 것은 사람의 몫이라 캡처가 대신하지 않는다 |

**실측이 가르쳐 준 것**: 헬퍼 **판을 올린 직후 첫 캡처는 「못 읽는다」로 뜬다** — 설치(심기)가 그 tick 을
가져가기 때문이다. 판을 올린 뒤에는 캡처를 **두 번** 돌리거나 지연을 더 준다(원격에 판 4 와 판 5 가
나란히 있는 것은 정상이다 — 파일 이름에 판이 박혀 조용한 혼용이 없다).

### 10.8 RF5a — 원격 트리가 스스로 갱신된다 (2026-09-06)

**③ 확정 = ㉮ 의 변형**(§4 ③ 에 근거를 적었다): 채널 하나를 두 뷰가 나눠 쓰고 **프로토콜은 안 늘린다.**

**구조 — 대상을 뷰가 정한다**: `pumpRemoteWatch` 가 자기 게이트(「SCM 뷰일 때만」)를 들고 있던 것을
`remoteWatchTarget(self) ?WatchTarget{dest, root, owner}` 하나로 모았다. 도크가 안 보이면 `null`,
소스 컨트롤 뷰면 `(git_repo_dest, git_repo_remote_root, .source_control)`, 탐색기 뷰면
`(remote_explorer.dest, remote_explorer.root, .explorer)` 다. **spawn 하는 자리는 여전히 하나**이고
(§5 게이트가 센다), 트리거를 받는 자리만 주인으로 갈린다:

- `.source_control` → `refreshGitStatus`(기존 그대로)
- `.explorer` → `invalidateRemoteExplorerExpanded` → `Tree.invalidateExpanded()`

**거친 무효화를 모델이 유계로 만든다**: 감시자는 `change` 한 줄만 낸다(경로 없음). 그래서 **펼쳐 둔
디렉터리 전부**를 큐에 넣는다 — 접힌 것은 안 넣는다(안 보이는 것을 읽으면 왕복만 늘고 화면은 그대로다).
재예약이 자라지 않는 이유가 셋이다: `enqueueScan` 이 같은 경로를 중복 제거하고, 큐가 넘치면 root 만
남기는 coarse recovery 로 접히며, **발사는 원격 슬롯 상한(2)** 이 잡는다. 그래서 트리거가 몰려도
「예약 폭주」가 안 생긴다(판정자가 트리거 50 번에 예약 2 개를 단언한다).

**없음의 뜻을 하나로 접었다**: 예전 펌프는 「로컬 목록」을 `stop`, 「루트 모름」을 `pause` 로 갈랐다.
이제 대상이 없으면 **전부 `pause`** 다 — `stop` 이 지우는 것은 설치 답과 `.gave_up` 인데 그 둘은
**호스트의 성질**이라 화면이 바뀌었다고 버릴 값이 아니다(호스트가 바뀌는 전이는
`rememberGitRepoDest` 가 이미 `stop` 으로 잡는다). 도크 뷰를 오갈 때마다 설치를 다시 묻지 않는다.

**못 서는 원격은 화면이 말한다**(§2.5): 안내 키가 주인마다 다르다 — 소스 컨트롤은 「직접 새로고침」,
탐색기는 「폴더를 접었다 펴서 다시 읽어주세요」(`fp_remote_watch_gave_up`). 사용자가 다음에 할 일이
다르기 때문이다.

**검증**: 순수 층(`test-file-tree-model` — 새 이름, maru 그래프에 `RF5a` 필터)이 ⑴ 펼친 것만 예약
⑵ 트리거 50 번에도 예약이 안 자람 ⑶ 펼친 것이 없으면 no-op 을 단언하고, 수직(`test-remote-explorer`)이
대상 해석이 뷰를 따라가는 것과 트리거가 탐색기 갈래로 가는 것을 제품 함수로 단언한다. §5 게이트에
「감시 채널은 창 당 하나 — spawn 자리는 정확히 하나」를 못박았다(그것이 세션 예산 근거의 못이다).
뮤테이션 둘: 펼침 게이트 제거 → 순수 판정 즉사, 탐색기 대상 제거·비활성 게이트 제거 → 수직 즉사.

**한계**: ⑴ **macOS 원격**은 감시자가 git 다이제스트 폴링이라(`watchPoll` — kqueue 가 편집을 안
알린다) 저장소 밖·git 이 무시하는 변경을 못 잡고, git 앞머리가 없으면 `exit_unsupported` 다. 리눅스
원격은 inotify 라 일반 변경을 잡는다(디렉터리 상한 65,536). ⑵ 경로가 없어 **거친 재스캔**이다 —
큰 트리를 많이 펼쳐 두면 트리거 하나가 그만큼의 왕복을 부른다(정밀 무효화는 RF5b). ⑶ 도크 뷰를
오가면 감시 루트가 바뀌어 감시자를 **다시 띄운다**(설치 답은 지킨다 — `switchRoot`). ⑷ 실서버 GUI
왕복은 수동(§10.7 레시피).

### 10.9 RF6a — 변경 하부: 저쪽 한 프로세스가 신원을 다시 재고 비대체로 옮긴다 (2026-09-06)

**계약은 §2.3 ⑶ 이 이미 정해 뒀다**: 변경은 「원격 명령이 `stat` → 비교 → 실행을 **저쪽 한 프로세스
안에서**」 해야 한다. 셸로 쪼개면(`[ "$(stat …)" = N ] && mv`) 그 사이가 그대로 TOCTOU 창이라, 우리가
보던 것이 아닌 파일을 옮기게 된다. 그래서 이 슬라이스는 **헬퍼 판 4 의 `mv` 서브커맨드**다.

**헬퍼가 하는 일**(`mv <부모 절대경로> <이전> <새 이름> <dev> <ino>`): 부모를 **열어** 그 핸들 아래에서
`fstatat`(`SYMLINK_NOFOLLOW` — 링크는 링크 자신을 본다, 로컬 `identityAt` 과 같은 축)로 신원을 다시
재고, 기대값과 다르면 **안 옮기고** `stale` 로 말한다. 같으면 **비대체 rename** 을 건다 —
리눅스 `renameat2(RENAME_NOREPLACE)`, macOS·BSD `renameatx_np(RENAME_EXCL)`.

⚠️ **대체 rename 으로 조용히 안 내려간다.** 플래그를 모르는 커널·파일시스템이면 `unsupported` 로
말한다(§2.5). 내려가면 사용자가 모르는 사이 **남의 파일이 사라진다** — 그것이 이 모드를 만든 이유의
절반이다(나머지 절반이 신원 재확인이다).

**결과 wire 를 왜 따로 두나**(`maru-rfmv 1` — `src/session/remote_file_mutation.zig`): 화면이 할 말이
실패마다 다르기 때문이다. 「이름이 이미 있다」는 다른 이름을 고르면 되고, 「그 사이 다른 것이
들어왔다」는 트리를 다시 읽어야 하며, 「권한 없음」은 저쪽 문제다. exit code 로만 오면 셋이 한 덩어리가
되어 §2.5 를 못 지킨다. 그래서 코드를 **로컬 실패 분류와 1:1** 로 싣는다. `S` 를 못 보면 **잘린 것**
이고(목록의 `X` 와 같은 자리), 잘림을 성공으로 읽으면 안 바뀐 파일을 바뀐 것으로 그린다.

**명령 빌더를 안 만들었다**(초안과 다른 점). `git_command` 에 `buildRemoteRename` 을 두려 했으나,
전송이 이미 `runRemoteCapped(script, args)` 로 **위치 인자**를 넘긴다 — 인자로 넘기면 셸 인용을 아예
안 거치므로 개행·따옴표 이름이 원리적으로 안 깨진다. 문자열로 조립해 인용 규칙을 하나 더 만드는 것보다
안전하고 짧다.

**검증**: 순수 wire 판정자 4(`test-remote-file-mutation-wire` — 왕복·개행 진단·**잘린 답을 성공으로 안
읽음**·판/형태 거부) + **실물 왕복 게이트**(`test-remote-file-mutation` — 빌드가 만든 헬퍼를 실제로
돌린다): 대상 존재→`collision` **그리고 남의 내용이 그대로**(fail-closed 의 증거) · 신원 불일치→`stale`
그리고 원본 그대로 · 없음→`not_found` · `..`·`a/b`→`invalid` · 맞으면 실제로 바뀌고 **개행 이름**도 된다.
뮤테이션 둘: 신원 비교 제거 → `stale` 판이 즉사 · 비대체를 대체로 → `collision` 판이 즉사.

**한계**: ⑴ 아직 **UI 가 없다** — 펜스(`selectedFileTreeMutationTarget` 의 한 줄)는 그대로이고 RF6b 가
연다. ⑵ 삭제는 RF6c(④ 결정). ⑶ 판 4 로 올렸으므로 **옛 판이 깔린 원격은 다시 심는다**(파일 이름에 판이
박혀 있어 조용한 혼용은 없다). ⑷ 디렉터리 이름 변경도 같은 경로지만 실물 왕복 판정자는 파일로만 잰다.

### 10.10 RF6b — 원격 트리에서 이름을 바꾼다 (2026-09-06)

**펜스를 «연» 것이 아니라 «문을 하나 더 낸» 것이다.** 로컬 타깃(`selectedFileTreeMutationTarget`)의
원격 펜스는 **그대로 서 있다** — 그 함수의 소비처는 로컬 변경 백엔드이고, 그쪽은 휴지통 staging·롤백·
에디터 잠금이 **로컬 파일시스템 의미**에 묶여 있어 원격 경로가 들어가면 같은 철자의 로컬 파일이
대상이 된다(§2.4). 대신 원격 전용 타깃(`selectedRemoteFileTreeRenameTarget`)과 커밋
(`enqueueRemoteFileTreeRename`)을 따로 두고, **갈림은 `enqueueFileTreeEdit` 의 첫 문장** 한 자리다.

**단발 워커다**(RF4 의 파일 열기와 같은 모양): 사용자 조작 단발이라 큐가 필요 없고, `runRemoteCapped`
로 헬퍼 `mv` 를 돌린 뒤 tick 이 `finishRemoteRename` 으로 결말을 낸다. 인자는 **위치 인자**로 가므로
셸 인용을 아예 안 거친다(개행 이름이 원리적으로 안 깨진다 — RF6a 와 같은 이유).

**결말이 화면에서 갈린다**(§2.5 — 이것이 결과 wire 를 만든 값어치다):

| 결말 | 화면 | 왜 |
|---|---|---|
| `ok` | 조용히, **다시 읽는다** | 낙관적으로 행을 고쳐 그리지 않는다 — 로컬도 재스캔이 권위다 |
| `stale` | 「같은 것이 아닙니다」 + **다시 읽는다** | 트리가 낡았다는 뜻이다 |
| `collision` | 「이름이 이미 있습니다」 | 트리는 안 낡았다 — **다시 안 읽는다** |
| `not_found` | stale 과 같게 | 사라진 것도 트리가 낡은 것이다 |
| `unsupported` | 「덮어쓰지 않는 이름 변경을 못 해서 **안 바꿨습니다**」 | 조용한 덮어쓰기가 아니라는 것을 말한다 |
| `denied`·`io`·답 없음 | 「못 바꿨습니다」 | 답이 없거나 잘리면 **성공으로 안 접는다** |

**이름 규칙은 로컬과 같은 순수 함수**(`file_tree_mutation.validateName`)가 소유한다 — 원격이라고
느슨해지지 않고, 두 벌이면 한쪽만 고쳐진다. 만들기·삭제는 아직 안 연다(삭제는 ④ — RF6c).

**검증**: 수직 판정자(`test-remote-explorer`) — 이름 규칙·같은 이름 거절을 **제품 문**
(`enqueueFileTreeEdit`)으로 태우고, 결말 여섯 갈래의 안내 바이트와 재읽기 여부를 단언한다. §5 게이트에
「갈림은 그 문의 첫 문장이고, 원격 커밋은 로컬 백엔드 심볼을 하나도 안 쓴다」를 못박았다.

⚠️ **판정자의 결함을 한 번 잡았다**: 처음에는 `enqueueRemoteFileTreeRename` 을 **직접** 불러서, 갈림을
지우는 뮤테이션이 **통과했다**(원격 경로가 로컬 백엔드로 가는데 판정이 못 봤다 — §2.4 위반을 못 잡는
판정자였다). 제품 문으로 바꾼 뒤에야 물었다. 부재 증명의 함정과 같은 결이다.

**한계**: ⑴ 만들기·삭제는 안내로 거절(RF6c) ⑵ 낙관적 UI 가 없어 이름이 바뀌기까지 왕복 한 번이 보인다
⑶ 디렉터리 이름 변경도 같은 경로지만 실물 판정은 파일로만 잰다 ⑷ 실서버 GUI 왕복은 수동(§10.7 레시피).

### 10.11 RF6c — 원격에서 지운다, 되돌릴 수 없다고 말하면서 (2026-09-06)

**④ 사용자 결정 = ㉰**(§4 ④ 에 근거). 조사 중에 ㉯ 를 밀어낸 사실이 하나 더 나왔다: 원격 휴지통이
대상과 **다른 마운트**면 `rename` 이 `EXDEV` 로 실패해, 되돌리기를 지키려고 **복사+삭제**로 내려가야
한다 — ssh 너머로 큰 파일을 복사하다 끊기면 **반쪽 사본**이 남는다. 「되돌릴 수 있다」를 지키려다 더
나쁜 실패를 만드는 것이다.

**㉰ 의 안전은 되돌리기가 아니라 「엉뚱한 것을 안 지운다」에서 온다**: 헬퍼 판 5 의 `rm` 이 이름 변경과
**같은 축**으로 저쪽 한 프로세스에서 `stat` → 신원 비교 → `unlinkat` 을 한다(§2.3 ⑶). 셸 `rm` 은 그
보장이 없다. 되돌릴 수 없다는 사실은 **확인 모달이 말한다**(§2.3 ⑷ — 차이를 숨기지 않는다):
문구는 「원격에는 휴지통이 없어 되돌릴 수 없습니다」, 버튼은 「영구 삭제」다(로컬은 「휴지통으로 이동」).

**재귀 삭제를 안 한다.** 디렉터리는 `AT_REMOVEDIR` 로 **빈 것만** 지운다. 한 프로세스 안에서 신원을
재는 보장이 **트리 전체로는 성립하지 않고**(내려가는 동안 아래가 바뀔 수 있다), 되돌리기가 없는 곳에서
재귀 삭제는 사고의 크기가 다르다. 안 빈 폴더는 화면이 「먼저 비워주세요」로 말한다.

**같은 코드가 두 뜻이다**: `collision` 이 이름 변경에서는 「이름이 이미 있다」, 삭제에서는 「폴더가 안
비었다」다. 그래서 결말 소비가 **종류로 먼저 갈린다**(`RemoteMutationKind`) — 한 갈래로 합치면 사용자가
엉뚱한 안내를 읽는다.

**확인 사이에 대상을 굳힌다**(`pending_remote_delete`): 확인을 누르는 사이 선택이 움직여도 **처음 물었던
그것**을 지운다(로컬 `pending_file_tree_delete` 와 같은 규율). 신원까지 굳히므로 그 사이 저쪽이 갈리면
헬퍼가 `stale` 로 막는다. 취소는 그 대상을 **비운다** — 안 비우면 다음 확인이 옛 대상을 지운다.

**검증**: 실물 왕복(`test-remote-file-mutation`) — 신원 불일치면 **파일이 그대로 남고**, 안 빈 디렉터리는
`collision` 이며 그 안의 파일이 살아 있고, 빈 디렉터리는 지워지고, 성공 시 **옆 파일은 그대로**다.
수직(`test-remote-explorer`) — 요청이 **지우지 않고 묻고**, 대상이 굳고, 취소가 비우고, 결말이 삭제 뜻으로
갈린다. §5 게이트 — 요청 본문에 워커 호출이 **없고**, 확인 본문만 굳힌 대상으로 지우며, 양쪽 다 로컬
휴지통 배관을 안 타고, 로컬 진입점이 원격을 **먼저** 가른다.
뮤테이션 셋: 삭제 신원 비교 제거 → 실물 판정 즉사 · `AT_REMOVEDIR` 제거 → 안 빈 디렉터리 판 즉사 ·
확인 생략(바로 삭제) → 수직 즉사.

⚠️ **게이트 헬퍼의 결함을 하나 고쳤다**: `fnBody` 가 `\nfn ` 만 보고 잘라서, 뒤가 전부 `pub fn` 이면
본문이 **다음 함수들까지 삼켰다** — 그러면 「이 본문에 X 가 없다」는 부정 단언이 남의 코드를 보고
죽는다(RF6c 에서 실제로 걸렸다). 둘 다 보게 고쳤다.

**한계**: ⑴ **되돌릴 수 없다**(설계상 — 확인이 그것을 말한다) ⑵ 재귀 삭제 없음 ⑶ 실서버 GUI 왕복은
수동(§10.7 레시피) ⑷ 판 5 로 올렸으므로 옛 판이 깔린 원격은 다시 심는다.

### 10.7 실측 캡처 — 실서버에서 트리와 파일 열기 (2026-09-06)

RF3a·RF4 가 약속한 «실서버 제품 왕복» 을 실제 리눅스 서버(colima, aarch64 · 실 sshd)에서 찍었다.
헤드리스 캡처(`MARU_SCREENSHOT`)라 GUI 조작 없이 제품 경로만 지난다.

**확인된 것** — ⑴ **트리**: 오른쪽 도크에 원격 `maru-demo` 가 뜬다(`docs/`·`src/` 폴더, `.gitignore`
= git 아이콘·`build.zig`·`README.md`, 하단 상태바 `colima:/home/yoonhb.linux/maru-demo`). ⑵ **파일
열기**: `build.zig` 행이 열려 **원격 실파일 내용**이 Zig 구문 강조와 함께 뜨고, 경로 밴드가 미러
(`~/.cache/maru/remote-view/c548ee1f7fe4146e/build.zig`)를, 하단 우측이 **「읽기 전용」** 을 말한다 —
RF4 의 경로-접두 read_only 가 제품에서 실제로 선다.

**캡처 하네스에 넣은 것(디버그 전용 env-gate, 미설정이면 무동작)**:

| env | 하는 일 | 왜 필요했나 |
|---|---|---|
| `MARU_OPEN_EXPLORER=1` | 도크를 탐색기 뷰로 **유지** | follow 게이트가 «도크 가시 + 탐색기 뷰» 다. 첫 frame 한 번으로는 안 된다 — 원격 SCM follow 가 나중 tick 에 뷰를 소스 컨트롤로 덮는다(실측) |
| `MARU_OPEN_EXPLORER_FILE=<원격 절대경로>` | 그 파일 행을 **클릭과 같은 길**(`activateFileTreeRow`)로 한 번 연다 | 손으로 `openRemoteFileReadOnly` 를 부르면 원격 펜스·`supported` 판정을 건너뛴다 — REMOTE_SCM 픽스처가 앱 core 대신 PTY 를 쓰는 것과 같은 이유 |
| (확장) 셸 pane 재초점 | **마지막 셸 pane** 을 활성으로 | 복원된 workspace 의 활성이 편집기이거나 옛 로컬 셸이면 follow 게이트가 아예 안 선다 — 실측에서 세 번 속았다 |

**실측이 가르쳐 준 함정**: `MARU_FORCE_REMOTE_SCM` 은 활성 pane 의 PTY 에 OSC 를 흘리는데, **프롬프트가
있는 셸은 매 프롬프트마다 자기 OSC 7 로 로컬 cwd 를 되보고해** 강제 원격과 경합한다(붙었다 떨어졌다
한다). 결정론적 캡처는 `MARU_CONFIG` 의 `shell.command` 로 **OSC 두 줄을 찍고 잠드는 스크립트**를 쓰고
`MARU_FORCE_SPLIT=1` 로 그 세션의 pane 을 새로 띄우는 쪽이다(새 pane 이 config 셸로 뜬다). 프롬프트가
없으니 되보고가 없다.

**한계**: 캡처는 사람이 눈으로 보는 확인이고 CI 가 아니다(자동 시각 회귀는 없다). 원격 목록·파일
읽기의 **전송 실물**은 RF2b 하네스(실 sshd)와 RS3 축 판정자가 CI 에서 소유한다.

**한계**: ⑴ 미러의 전체 경로(탭 툴팁 등)는 캐시 경로다 — 라벨은 basename 이라 같아 보이지만 전체
경로 표시는 거짓이고, host 접두 표시(§9.3)도 없다(후속: entry 원격 표식). ⑵ 스냅샷이다 — 원격이
