# 원격 SCM — 활성 pane 이 원격이면 그 저장소를 본다

**사용자 결정 2026-08-31**: 「원격일 때도 변경사항이 갱신되게」, 그리고 **쓰기까지 전부** 원격으로 간다.

소유 관계: [에디터 Surface 도크 §3.5](../editor-surface-dock.md)가 「저장소를 어떻게 고르는가」를 소유하고,
이 문서는 그 판정에 **원격 축**을 더한다. 전송(ControlMaster)·안전 규율은 [SSH 통합 §4·§9](../ssh-integration.md)가
단일 출처이며 여기서 다시 정하지 않는다.

## 1. 지금 무엇이 잘못됐나

`git_ops.termCwd` 는 원격 Term 에 **null 을 낸다**([git.zig](../../src/platform/macos/app_session/git.zig)) —
OSC 7 은 host authority 를 버리고 경로만 남기고, 커널 조회는 로컬 `ssh` 클라이언트의 cwd 를 답하기 때문이다.
그래서 `gitRepoTarget` 의 1 순위가 비고 **2 순위(직전에 읽은 로컬 저장소)가 답한다.**

결과: **원격 pane 으로 포커스를 옮겨도 도크에는 로컬 저장소의 목록이 그대로 남는다.** 사용자는 그것을
지금 보는 터미널의 것으로 읽는다. 그 상태에서 스테이지·되돌리기를 누르면 **보고 있지도 않은 로컬 파일**이
바뀐다 — §9.4 가 링크 감지에서 막은 것과 같은 함정이고, 목록은 그보다 위험하다.

옛 규정(§3.5 ⑵ 「원격은 지우지 않는다」)은 **읽을 방법이 없다**는 전제 위에 있었다. 그 전제는 이제 틀렸다 —
[ssh_upload.zig](../../src/platform/macos/ssh_upload.zig) 가 ControlMaster 위에서 원격 명령을 이미 실행한다.

## 2. 계약

### 2.1 저장소 신원은 (host, path) 쌍이다

§9.2 가 cwd 에 대해 정한 것과 같은 모양이다. 로컬은 `host = null`.

- **활성 Term 이 원격이면** 그 Term 의 관측 cwd 와 `ssh_remote_dest` 가 대상이다.
- 원격 저장소 루트는 **원격에서** 정한다(`rev-parse --show-toplevel`) — 로컬 walk-up 은 원격 경로에 뜻이 없다.
- 두 축을 **함께** 저장한다(`git_repo` 옆에 `git_repo_dest`). 목록·diff·쓰기가 같은 쌍을 봐야
  「목록은 원격, 클릭은 로컬」이 원리적으로 불가능해진다.

### 2.2 원격은 셸을 거친다 — 그것이 유일한 예외다

[git_command.zig](../../src/session/git_command.zig) 헤더의 읽기 전용 계약은 「셸·alias 를 거치지 않는다」였다.
원격에서는 `ssh <dest> <command>` 가 **원격 로그인 셸**에 문자열을 넘기므로 그 조항이 성립하지 않는다.
그래서 예외를 좁게 정의한다:

1. **모든 토큰을 작은따옴표로 인용**한다(내부 `'` 는 `'\''`). 인용은 argv 를 만드는 순수 함수가 하고,
   L4 는 그 결과를 그대로 exec 한다.
2. **제어문자가 든 토큰은 거부**한다(`0x00`–`0x1F`, `0x7F`). 인용으로도 안전하지만, 그런 값이 왔다는
   것 자체가 관측이 오염됐다는 뜻이라 명령을 만들지 않는다.
3. **config·env 덮어쓰기를 원격에도 그대로 싣는다** — `env GIT_OPTIONAL_LOCKS=0 … git -c core.pager=cat …`.
   로컬에서 닫아 둔 구멍(pager·hook·external diff·credential helper)이 원격에서 열리면 안 된다.
4. **원격 `git` 은 PATH 로 찾되, 그 PATH 를 우리가 넓힌다.** 로컬은 절대경로 계약이지만(§6 PATH hijack)
   원격의 설치 위치는 우리가 모른다. 그 대신 원격 명령은 항상 우리가 만든 문자열이고 사용자 입력이
   토큰으로 들어가지 않는다.

   그런데 **non-interactive ssh 의 PATH 는 로그인 셸보다 좁다** — 실측(2026-09-01, harness sshd)으로
   `/usr/bin:/bin:/usr/sbin:/sbin` 이다. Homebrew(`/opt/homebrew/bin`)나 `~/.local/bin` 에 깐 git 은
   **그 목록에 없다.** 그래서 PATH 를 넓히는데, **그 방법이 중요하다.**

   ⚠️ **로그인 셸에 `PATH=…; cmd` 를 직접 넘기면 안 된다.** ssh 는 명령을 **사용자의 로그인 셸**에 넘기고,
   그것이 POSIX 셸이라는 보장이 없다(실측 2026-09-01):

   | 셸 | `PATH="…:$PATH"; 'echo' 'ok'` |
   | --- | --- |
   | bash·zsh·ksh·dash | PATH 가 넓어진다 |
   | **csh·tcsh** | `PATH=…: Command not found.` — **PATH 는 안 바뀐다**(조용히) |
   | **fish** | `"$PATH"` 는 리스트를 **공백으로** 잇는다 → `/usr/bin` 이 사라질 수 있다 |

   그래서 로그인 셸에는 **전부 인용된 토큰만** 준다. 확장은 전부 `sh` 안에서 일어나고, 그 `sh` 는 정의상
   POSIX 다. 실제 명령 토큰은 `"$@"` 로 받으므로 **인용이 한 겹으로 끝난다**:

   ```
   'sh' '-c' 'PATH="$HOME/.local/bin:…:$PATH"; exec "$@"' 'sh' 'env' 'GIT_…' 'git' '-C' '…' 'status' …
   ```

   - **덮지 않고 앞에 붙인다** — 사용자가 PATH 로 고른 git 이 있으면 그쪽이 이긴다.
   - bash·zsh·csh·tcsh·ksh·dash 여섯에서, **제품이 만든 실제 문자열**로, 공백과 작은따옴표가 든 경로를
     써서 확인했다.

   ⚠️ **이 규율은 원격 SCM 만의 것이 아니다.** 같은 처방이 세 곳에 따로 적혀 있었고 — 원격 SCM ·
   훅 설치([agent_hooks.zig](../../src/cli/agent_hooks.zig)) · 이벤트 스트리머
   ([ssh_upload.zig](../../src/platform/macos/ssh_upload.zig)) — **셋 다 같은 전제를 깔고 있어 셋 다
   틀렸다.** 값은 경계 판정자로 묶여 있었지만 판정자는 **값**만 볼 뿐 **형태**를 못 봐서, 형태가 틀린
   채 셋이 나란히 초록이었다. 그래서 소유자를 하나로 옮겼다:
   [session/remote_shell.zig](../../src/session/remote_shell.zig). 경계 판정자도 「두 값이 같다」에서
   **「사본을 다시 만들지 않는다」**로 바꿨다 — 중복을 지키는 것보다 지우는 편이 낫다.

   그 자리에서 함께 드러난 것: 훅 설치의 표식 `!maru-not-installed` 는 **csh 원격에서 도착하지 않았다**
   (히스토리 확장이 `maru: Event not found.` 로 바꾼다). 뒤 명령은 `;` 뒤에서 그대로 돌아 **exit 0** 이라
   로컬은 「설치됐다」로 읽었다 — 그 모듈이 약속한 「조용히 «설치했다» 로 넘어가지 않는다」가 정확히 그
   자리에서 깨졌다. 토큰의 `!` 는 못 막지만(사용자 경로다) **우리가 고르는 값**은 고칠 수 있어 표식에서
   `!` 를 뺐다.

6. **`!` 는 막지 않는다 — 막는 편이 더 나쁘다**(실측 2026-09-01). csh/tcsh 의 히스토리 확장은
   **작은따옴표 안에서도, 비대화형에서도, `sh -c` 껍데기 안에서도** 일어난다(로그인 셸이 우리 문자열을
   먼저 파싱한다). 그래서 csh 원격에서 경로에 `!` 가 있으면 그 명령은 실패한다 — 다만 비대화형 셸의
   히스토리는 비어 있어 **다른 명령으로 바뀌지는 않는다**. 토큰에서 `!` 를 거부하면 압도적 다수인 POSIX
   셸 원격에서도 그 경로를 못 읽게 되고 안전은 늘지 않는다(오발이 아니라 실패다). **허용하고 한계로 적는다.**

7. **「원격에 git 이 없다」를 구별한다**(✅ 2026-09-01 — §10). 실측으로 **`exit 127`(명령 없음)과
   `exit 255`(ssh 전송 실패)는 갈린다**. 그런데 읽기 경로의 `Output` 은 `{ bytes, truncated }` 라
   **종료 코드를 안 나른다** — 지금은 둘 다 `error.GitFailed` 로 뭉개져 「읽지 못함」으로 뜬다. 이유를
   화면까지 보내려면 그 타입과 24 개 사용처를 넓혀야 하므로 RS4 에서 §6.7(실패는 git 이 한 말 그대로)과
   **함께** 연다. 그때까지 이 조항은 **의무이지 구현이 아니다.**
5. **새 연결을 몰래 열지 않는다.** `-S <control socket>` 로만 붙고, 호출 전에 그 소켓의 존재를 확인한다.
   소켓이 없으면 원격 SCM 은 **꺼진 채로 그 사실을 말한다**(비밀번호 프롬프트가 뜨는 것이 최악이다).

### 2.3 화면

- 도크 머리에 **`user@host`** 를 적는다. 로컬과 원격을 눈으로 못 가르면 §1 의 사고가 이름만 바뀐 채 돌아온다.
- 원격에서 아직 지원하지 않는 동작은 **비활성으로 보여 주고 이유를 말한다**(§3.5 의 Fetch 규율과 같다).

**RS3 이 남긴 빚 하나**(적대적 검증 11회차): 열려 있는 **원격 diff Term 자체**에는 host 표시가 없다.
브랜치 줄이 말해 주지만, 그 diff 를 열어 둔 채 로컬 pane 으로 옮기면 브랜치 줄은 로컬을 가리키고 **그 탭이
어느 기계의 파일인지 말하는 것이 화면에 없다.** 읽기 전용이라 위험한 동작은 없지만 §2.3 의 물음은 그대로
남는다 — RS4 에서 탭 라벨에 붙인다.

**RS3a 에서 새로 정한 것 둘.**

1. **작업트리 쪽은 git 으로 못 읽는다.** `git show :<path>` 는 index 이고 `HEAD:<path>` 는 커밋이라, 작업트리의
   지금 내용을 내는 git 명령이 없다. 그래서 **그 한 자리만** git 이 아닌 명령을 원격에 보낸다
   (`head -c <상한> -- '<abs>'`). §2.2 의 인용·검증 규율은 그대로 적용되고, 상한은 **원격에서** 건다 —
   로컬은 받은 뒤 자르지만 원격은 그전에 바이트가 링크를 다 건너온다.
2. **저장소 루트를 목록과 같은 왕복에 얹는다.** 따로 물으면 원격 왕복이 하나 더 늘고, 그 사이 pane 이
   바뀌면 루트와 목록이 **다른 저장소**의 것이 된다.

그리고 diff entry 는 **열 때 (host, root) 를 박는다** — `diff_repo` 와 같은 이유다. 나중에 세션 상태를 다시
읽으면, diff 를 열어 둔 채 다른 pane 으로 옮겼을 때 그 비교가 다른 호스트의 것으로 해석된다.

**원격 diff Term 이 읽기 전용인 것은 이미 성립한다** — `saveDocument` 가 `editor_diff != null` 이면 거부한다.
RS4 에서 원격 쓰기를 열 때도 이 자리는 그대로 둔다(diff 뷰어는 저장하는 화면이 아니다).

**RS2 가 「읽기」보다 「가드」에 더 들었다.** 원격 목록을 띄우는 것 자체는 배선 몇 줄인데, 그 화면이 떠 있는 동안
**로컬에 손이 가는 길**이 열 곳 넘게 있었다(아래 §5). 그 길을 막지 않고 목록만 띄우면 RS2 는 기능이 아니라 사고다.

**RS1 을 먼저 떼는 이유**: 안전 조건이 전부 이 층에 있다(§2.2). 배선보다 먼저 전수로 고정해 두면,
뒤 단계는 「그 argv 를 어디로 보내나」만 다루게 된다.

## 4. 검증

- **인용·주입**: 공백·작은따옴표·`;`·`$(…)`·개행이 든 경로가 원격에서 **한 인자로** 도착하는지, 제어문자가
  든 토큰은 명령 자체가 만들어지지 않는지. 이 저장소에서 원격 명령을 만드는 첫 자리이므로 전수로 짚는다.
- **덮어쓰기 보존**: 로컬 argv 의 `-c` 쌍과 env 가 원격 문자열에도 **하나도 빠짐없이** 실리는지.
- **라우팅**(RS2 부터): 활성 pane 이 원격↔로컬로 바뀔 때 목록이 그 pane 의 저장소로 갈아타는지, 그리고
  원격 목록을 보는 동안 로컬 경로로 가는 쓰기가 **원리적으로** 없는지(쌍을 함께 읽는다).
- **실물 SSH**: 기존 `tools/session-host/p5d_ssh_smoke.sh` 하네스가 harness-owned localhost OpenSSH 를
  띄운다 — RS2 부터 그 위에서 `status` 한 번을 끝까지 본다.

## 5. 적대적 검증 기록 (2026-08-31, RS2·RS3)

**1회차 — 자동 경로.** 인텐트를 안 거치고 tick 이 굴리는 읽기 셋이 `git_repo`(원격 경로)로 **로컬 git** 을 불렀다:
`pumpScmLog`(히스토리) · `pumpCommitFiles`(펼친 커밋·턴의 파일 목록) · `captureTurnSnapshot`. 셋 중 마지막이
가장 나쁘다 — `add -A` 로 **작업트리를 통째로 임시 index 에 굳히는** 경로라, 로컬에 같은 경로가 있으면 그 로컬
트리가 원격 세션의 턴 스냅샷으로 박힌다. 셋 다 `scmTargetIsRemote` 로 막았다.

**2회차 — 전환의 잔여.** 「호스트가 바뀌면 직전 동작 결과 줄을 버린다」를 `rememberGitRepo` 가 하는 줄 알았는데
그쪽은 **경로로만** 판정해서, 로컬 `/srv/app` → 원격 `/srv/app` 처럼 **경로가 같고 호스트만 바뀌는** 전환을 못 본다.
그 상태에서는 원격 안내가 로컬 목록 위에 남는다. 판정을 `rememberGitRepoDest` 로 옮겼다.

**3회차 — 게이트 우회.** 인텐트 게이트가 첫 겹인데 쓰기로 들어가는 길이 그것만이 아니었다: 커밋은 **키 입력**
경로(`settleCommitInput`)로도 들어오고, 기준(base) 변경은 **상태바 메뉴**라 인텐트를 아예 안 거친다. 두 번째 겹을
`submitWrite` 와 커밋 제출 자리, `setScmBase` 에 뒀다.

**4회차 — 판정자가 나를 잡았다(둘).** ⑴ 「원격이면 `.unknown`」 단언이 처음에 빨갛게 났는데, 그 실패가 가드의
전제를 드러냈다 — 활성 Term 이 로컬이면 **1 순위가 답하는 것이 맞고**, 가드가 필요한 상태는 1 순위가 비는 원격
Term 하나뿐이다. ⑵ 「호스트가 바뀌면 안내를 버린다」를 **한 방향만** 구현해 두었다(로컬→원격). 원격→로컬에서
남은 안내를 판정자가 잡아 양방향으로 고쳤다.

**5~7회차 (RS3a) — 셋 중 둘이 진짜였다.**

**5회차 — 소유권.** diff entry 에 `(host, root)` 를 박는 세 자리가 `freeDiffPaths` **뒤에** 대입하는지 봤다.
셋 다 그 순서였다(재오픈이 먼저 푼다) — 이상 없음.

**6회차 — 소켓이 사라지면 로컬로 떨어졌다.** ⚠️ `remoteControlSocketFor` 가 null 이면 `remote = null` 로
넘어가 **원격 경로를 로컬 git 에 넘겼다.** 로컬에 같은 경로가 있으면 남의 파일 내용이 「원격 비교」로 뜬다 —
RS2 가 목록에서 막은 사고가 diff 로 돌아온 것이다. 소켓이 없으면 **요청을 걸지 않고 실패로 표시**한다:
그 화면은 이유를 말하고, 로컬 파일을 원격인 척 보여 주지 않는다.

**7회차 — 잘림을 로컬 상한으로만 봤다.** ⚠️ `runArgvWithEnv` 는 `max_output_bytes`(16 MiB)로 판정하는데
원격은 그 전에 `head -c` 로 **4 MiB 에서 잘린다.** 그대로 두면 잘린 파일이 `truncated = false` 로 와
**온전한 파일처럼** 뜬다(뷰어가 「너무 큼」을 말할 기회를 잃는다). 원격 상한으로 다시 판정한다.

**8~10회차 (RS3b) — 하나가 위험했다.**

**8회차 — 비활성 저장소 행에 원격 표식이 박혔다.** ⚠️ 목록은 저장소를 여럿 싣고(§3.5.1c) **비활성
저장소 행**도 파일 줄을 낸다 — 그 행을 열면 `repo_override` 로 다른 경로가 온다. `stampDiffRemote` 가
활성 목적지를 **무조건** 박고 있어서, **로컬 저장소 행에 원격 표식**이 붙었다. 그 비교는 원격에서
`<원격 루트>/<rel>` 을 읽으려 들고, 원격에 우연히 같은 경로가 있으면 **남의 파일**을 그 자리에 보여 준다.
그 비교가 선 저장소가 **활성 원격 저장소일 때만** 박도록 고쳤다.

**9회차 — 버퍼 예산.** `runs = text_ops` 라 `text_ops += 1` 하나로 op·run 이 함께 늘어난다. 예산이
모자라면 원격에서 **도크가 통째로 빈다**(로컬 테스트로는 영영 안 보이는 종류) — 이상 없음.

**10회차 — 실패 뒤 회복.** 소켓이 없어 `diff_failed` 로 표시하면 tick 재시도 루프가 그 entry 를 건너뛴다.
다시 열면 `requestDiffContent` 가 그 값을 되돌리므로 소켓이 돌아온 뒤 사용자가 다시 누르면 열린다 —
「조용히 실패한 채 남는다」가 아니다. 이상 없음.

## 6. RS4 계약 — 실측으로 정한 것 (2026-09-01)

**코드를 쓰기 전에 실물 `sshd` + ControlMaster 로 일곱 가지를 쟀다.** 아래는 그 결과이고, 추측이 아니라
측정에서 나온 조항이다.

### 6.1 `discard` 는 범위에 없다 — **로컬에도 없다**

`git_write_command.Kind` 는 `stage`·`unstage`(±`_unborn`·`_all`)·`commit`·`fetch` 뿐이다. 되돌리기는
**로컬에도 구현되어 있지 않으므로** 원격 축의 일이 아니다(앞선 계획에 「discard」를 적은 것은 확인 없이 쓴
것이라 여기서 지운다).

### 6.2 커밋 메시지는 **stdin** 으로 간다

로컬은 `commit -F <메시지 파일>` 인데 **그 파일은 로컬에 있다** — 원격에서 그 경로는 없거나 남의 파일이다.
실측: `git commit -F -` 가 stdin 에서 읽고, 제목·본문·따옴표·한글이 그대로 보존된다.

**그래서 backend 에 stdin 파이프가 필요하다.** 지금 `spawnCapture` 는 `dup2(devnull, 0)` 으로 stdin 을
막는다(저장소 훅이 `read` 로 멈추는 것을 막는 **의도적** 설계다 — §1). 그 옵션은 **원격 커밋에만** 연다.
`ssh_upload.uploadBytes` 가 같은 패턴을 이미 갖고 있다.

### 6.3 원격 `fetch` 는 **우리가 실행하지 않는다** — 활성 pane 에 넣는다

실측한 이유: **우리 명령에는 agent 도 PATH 도 없다.**

```
ssh -S <ctl> <dest> 'echo $SSH_AUTH_SOCK; echo $PATH'
  SSH_AUTH_SOCK=[]                          ← agent 없음
  PATH=/usr/bin:/bin:/usr/sbin:/sbin        ← 최소 PATH
```

이것은 non-interactive ssh 의 성질이라 우리가 고칠 수 없다. magit + TRAMP 가 십 년째 같은 자리에서
아프다(그쪽 이슈의 절반이 `SSH_AUTH_SOCK` 미전달이고, 나머지가 「물어놓고 답할 곳이 없다」이다).

**maru 에는 그 답이 이미 있다**: `push`·`pull` 이 쓰는 길 — **활성 pane 의 터미널에 명령을 넣어 주고
실행은 사용자가 한다**(쓰기·원격 §4). 그 pane 은 이미 그 호스트에 붙어 있고 키·agent 가 살아 있으며,
프롬프트가 떠도 **사용자가 보고 답할 수 있다.**

- 대가를 적어 둔다: **결과를 우리가 모른다.** 로컬 fetch 는 완료를 받아 목록을 다시 읽지만, 주입은
  사용자가 실행하므로 갱신 시점을 알 수 없다 — 그때는 사용자가 새로고침을 누른다.
- **자격증명을 우리 코드가 만지지 않는다**(VS Code 의 askpass 중계는 그 반대를 택한다 — §6.8).

### 6.4 주입 대상은 **활성 pane 의 활성 Term** 이다 (사용자 결정 2026-09-01)

목록도 활성 pane 기준이므로(RS2) 정상 상태에서 둘은 **항상 같은 pane** 이다. 그래서 별도 호스트 대조를
두지 않고, **주입 시점에 활성 pane 을 다시 판정**한다.

⚠️ 다만 `followActiveTerminalRepo` 는 **도크가 보일 때만** 돈다. 도크를 접은 채 pane 을 옮기면 목록 상태가
낡는데, 지금은 ⑴ fetch 진입점이 도크 버튼뿐이고(`action.zig` 에 키바인딩 0개) ⑵ 뷰 재진입이 다시 판정해
닫혀 있다. **그 방어는 간접적이다** — 누가 `scm_fetch` 키바인딩을 더하면 도크가 접힌 채로도 실행된다.
그래서 주입 자리에서 활성 pane 을 다시 묻는 것이 계약이다.

### 6.5 원격 argv 에 **PATH 처방**이 필요하다 — RS1~RS3 에도 이미 있는 구멍

§2.2 ⑷ 는 「원격 `git` 은 PATH 로 찾는다」인데, 위 실측대로 그 PATH 는 `/usr/bin:/bin:/usr/sbin:/sbin` 이다.
**Homebrew git 만 있는 원격에서는 원격 SCM 이 통째로 실패한다**(실측 환경은 `/usr/bin/git` 이라 우연히
통과했다). argv 판정자는 문자열만 보므로 이것을 못 잡는다.

`src/cli/agent_hooks.zig` 가 같은 함정을 겪고 처방을 남겼다 — **PATH 접두를 붙이고, 없으면 마커를 내고
조용히 끝낸다.** 원격 SCM 도 그 처방을 재사용한다: 못 찾았을 때 「실패」가 아니라 **왜 못 했는지**를 말한다.

### 6.6 `exit 255` 는 모호하다 — **자동 재시도를 하지 않는다**

```
원격 명령이 255 반환 → ssh 보고 255      전송 실패 → 255
원격 명령이   1 반환 → ssh 보고   1
```

「연결이 끊겼다」와 「원격 명령이 255 로 끝났다」를 **구별할 수 없다.** 끊김 실측에서는 커밋이 안 됐지만
(ssh 가 죽으면 원격 명령도 죽는다), 그 판정을 exit 코드로 자동화하면 **두 번 커밋될 수 있다.**

### 6.7 실패는 **git 이 한 말을 그대로** 전한다

`index.lock` 경합을 재현하니 git 이 정확히 말한다 — 「다른 git 프로세스가 돌고 있다」. 원격 저장소에서는
**사용자가 그 터미널에서 직접 git 을 돌리고 있을 수 있으므로** 이 상황이 드물지 않다. 원격 쓰기의 stderr 를
반드시 화면에 싣는다(그 문구가 「우리 탓이 아님」을 스스로 말한다).

또한 **원격은 `.git` 을 감시하지 않으므로**(RS2) 쓰기 뒤 목록 갱신을 **명시적으로** 걸어야 한다.

### 6.8 참고한 선례 (clean-room — 공개 동작·이슈 트래커 수준)

- **VS Code Remote-SSH**: `GIT_ASKPASS` + `VSCODE_GIT_ASKPASS_MAIN` + **`VSCODE_GIT_IPC_HANDLE`** 로
  역채널을 만들어 원격 git 의 자격증명 요청을 로컬 UI 로 끌어올린다. 대가는 **자격증명이 채널을 건넌다**는
  것과 상주 서버가 필요하다는 것이다. maru 의 `remote_agent_stream` 은 **단방향**이라 지금은 그 길이 없다.
- **magit + TRAMP**: 상주 서버 없이 ssh 로 명령을 던지는 모델 — maru 와 가장 가깝고, 정확히 이 절이 막으려는
  자리에서 아프다.

소스를 읽지 않았고 코드 표현을 가져오지 않았다.

### 6.9 인용은 실제 셸로 검증했다

RS1 의 작은따옴표 규칙을 `sh` 에 통과시켰다 — `it's here.zig` · `a b;rm -rf /` · `$(id)` · `` `id` `` · `*` 가
전부 **리터럴 한 토큰**으로 도착한다. 원격 셸도 같은 POSIX 규칙이므로 RS4 의 쓰기 argv 도 이 층을 그대로 쓴다.
메타문자가 든 경로를 실제 원격에 stage 해 확인했다(`A  "it's here;rm -rf tmp.txt"` — `rm` 은 실행되지 않았다).

## 7. 적대적 검증 기록 (2026-09-01, RS4a)

**여덟 회 중 다섯이 진짜였고, 그중 셋이 같은 뿌리다** — 「경로만 보면 두 기계가 같은 값」.

**1~3회차 — 원격 argv.** 로컬이 닫아 둔 `-c` 덮어쓰기·env 가 원격 문자열에 하나도 빠짐없이 실리는지,
`argv` 는 fetch 인데 `env` 는 index 로 도는 길이 있는지(`kindOf` 가 argv 에서 되읽어 그 자리를 없앴다),
셸 메타문자·제어문자가 든 경로가 한 인자로 도착하는지 — 셋 다 판정자로 고정했고 제품을 되돌리면 빨갛다.

**4회차 — 비활성 «로컬» 저장소 행.** ⚠️ 목록은 저장소를 여럿 싣고 비활성 행도 동작 버튼을 낸다.
활성 목적지를 무조건 붙이면 **로컬 저장소 행의 스테이지가 원격으로** 간다 — 원격에 우연히 같은 경로가
있으면 **남의 index 를 바꾼다.** RS3 8회차가 diff 에서 잡은 함정이고, **쓰기는 보여 주는 것이 아니라
바꾼다.** `writeTargetFor` 가 **그 행의 저장소**로 판정하고, 소켓이 없으면 `.unavailable` 로
**보내지 않는다**(로컬로 떨어뜨리면 원격 경로를 로컬 git 이 받는다).

**5회차 — ssh 가 한 말을 git 이 한 말로 냈다.** ⚠️ `writeErrorText` 는 stderr 마지막 줄을 실패 사유로
내는데, 소켓이 죽으면 그 자리에 **ssh 자신의 말**이 온다(실측: `Host key verification failed.` + 255).
사용자는 **자기 저장소를 의심**하게 된다. `ssh` 는 자기 실패에만 255 를 쓰므로 `transportFailed()` 로
가르고 별도 문구를 낸다 — §6.7 의 「실패는 git 이 한 말 그대로」는 **git 이 돌았을 때**의 계약이다.

**6회차 — 배치 상한 둘이 서로 모른다.** 로컬은 `ARG_MAX`(64 KiB)로 자르는데 원격은 인용이 최대 4 배로
부푼 문자열을 8 KiB 버퍼에 담는다. 흔한 60 B 경로 256 개가 넘긴다. **오늘 배치를 쓰는 제품 경로는
없으므로 잠재 결함이다** — 그래도 `remoteBatchEnd` 를 두고, 넘칠 때 `error.RemoteCommandTooLong` 으로
**실패가 자기 이름을 말하게** 했다(`GitFailed` 로 뭉개면 사용자가 저장소를 의심한다).

**7회차 — 상대경로 `git`.** ⚠️ 원격일 때 `git_exe` 로 이름 `"git"` 을 넘긴다(`buildRemote` 가 `argv[0]`
을 버리므로). 그 값이 **로컬 갈래로 새면** `execve("git", …)` 가 되는데, POSIX 는 PATH 를 안 뒤지고
**cwd 기준 상대경로**로 푼다 — 저장소 안에 `git` 이라는 실행 파일이 있으면 그것이 돈다. 「명령 실패」와
「남의 스크립트 실행」은 하늘과 땅이라 `runWriteSync` 에서 fail-closed 로 닫았다.

**8회차 — 쓰기 대상을 경로만으로 판정했다.** ⚠️ `scm_write_repo` 가 경로만 들어서, 원격 `/srv/app` 에
쓰는 동안 pane 이 로컬 `/srv/app` 으로 바뀌면 「같은 저장소」로 읽혀 **로컬 목록에 원격 쓰기의 결과**가
붙는다. RS2 2회차가 목록 축에서 잡은 것과 같은 부류다 — `(경로, 호스트)` 쌍으로 대조한다.

## 8. RS4b — 커밋 메시지는 stdin 으로 간다 (2026-09-01)

§6.2 가 정한 것을 배선했다. 로컬은 여전히 **메시지 파일을 로컬에** 쓰고, 원격이면 실행 층이 그 바이트를
읽어 `commit -F -` 의 stdin 으로 흘린다 — 그 경로를 원격에 그대로 넘기면 없는 파일이거나 **남의 파일**이다.

### 8.1 stdin 을 열어도 hook 보호는 유지된다

`spawnCapture` 는 stdin 을 `/dev/null` 로 막는다 — 저장소가 심어 둔 hook 이 `read` 로 멈추는 것을 막는
**의도적** 설계다(§1). 원격 커밋에서 그 자리를 열되, **다 보내면 write 끝을 닫는다.** 그러면 자식은 EOF 를
보므로 그 보장이 그대로다. 실측으로 확인했다: `commit -F -` 는 stdin 을 **먼저 다 읽고**, 이어 도는
`pre-commit` hook 은 **빈 stdin** 을 받는다.

### 8.2 ⚠️ 순차로 쓰면 멈춘다 — `poll` 로 겹쳐 돌린다

「stdin 을 다 쓴 뒤 stderr 를 읽는다」로 두면, 자식이 우리 입력을 다 소비하기 전에 stderr 파이프를
가득 채우는 순간 **둘 다 선다.** 원격 커밋에서 그 상황은 흔하다 — `pre-commit` hook 이 수천 줄을 쏟는
동안 우리는 아직 메시지를 보내는 중이다.

**판정자가 그 상황을 결정적으로 만든다**: 스테이지된 파일(있어야 hook 이 돈다) + 2 만 줄을 stderr 로
쏟는 hook + 파이프 버퍼보다 훨씬 큰 512 KiB 메시지. 순차 구현으로 되돌리면 그 판정자가 **실패한다**
(ssh 가 우리 입력을 못 받아 메시지가 끊긴다).

⚠️ **첫 판정자는 헛돌았다.** 스테이지된 것이 없으면 git 은 hook 을 **안 부르고**, 그러면 stderr 가 안
쏟아져 겹침이 일어나지 않는다 — 순차 구현으로도 초록이었다. 그리고 파일 내용이 매번 같으면 두 번째
실행에서 같은 일이 벌어진다(재실행 안전성이 곧 판정력이다).

### 8.3 SIGPIPE 는 fd 단위로 막는다

자식이 먼저 죽으면 파이프 write 가 **SIGPIPE 로 앱을 죽인다.** 이 저장소는 그것을 전역 무시가 아니라
fd 단위(`F.SETNOSIGPIPE`)로 막는다(`runtime_manager.OutputWake` 와 같은 규율) — 전역 무시는 곳곳의
처분을 바꾼다.

### 8.4 메시지 상한

원격으로 보내는 메시지는 1 MiB 에서 **자르지 않고 거절한다**. 잘린 커밋 메시지는 「덜 적힌 것」이 아니라
**다른 메시지**이고, 그것은 되돌릴 수 없는 자리에 박힌다. 로컬은 파일을 그대로 넘기므로 이 상한이 없다 —
원격만의 조항이다.

## 9. RS4c — fetch 는 우리가 실행하지 않는다 (2026-09-01)

§6.3 이 정한 것을 배선했다. 근거는 실측이다:

```
ssh -S <ctl> <dest> 'echo $SSH_AUTH_SOCK; echo $GIT_ASKPASS; tty'
  SSH_AUTH_SOCK=[]   GIT_ASKPASS=[]   tty=not a tty
```

agent 도 askpass 도 tty 도 없다 — 인증이 필요한 원격에서 **항상** 실패하고, 물어볼 곳조차 없다.
이건 non-interactive ssh 의 성질이라 우리가 고칠 수 없다.

**maru 에는 그 답이 이미 있었다**: `push`·`pull` 이 쓰는 길 — 활성 pane 의 터미널에 명령을 넣어 주고
실행은 사용자가 한다. 그 pane 은 이미 그 호스트에 붙어 있고 키·agent 가 살아 있으며, 프롬프트가 떠도
**사용자가 보고 답할 수 있다.** `fetch` 도 그 길로 보내고, **주입 자리를 하나로 합쳤다**
(`injectIntoActiveTerminal`) — 두 벌이면 「push 는 그 pane 에, fetch 는 다른 pane 에」가 생긴다.

**대가를 화면에 말한다.** 우리가 실행하지 않으므로 **결과를 모른다** — 조용히 두면 사용자는 목록이 곧
갱신될 것으로 읽는다. 그래서 「터미널에 넣었습니다 — 거기서 실행한 뒤 새로고침하세요」를 낸다.

### 9.1 RS2 의 진입점 가드를 지웠다

RS2 는 「원격 목록을 보는 동안 로컬을 만지는 동작」을 `applyScmDockIntent` 입구에서 통째로 끊었다.
RS4a~c 가 그 동작들을 **원격으로 보내면서** 막을 것이 하나도 안 남았다 — 모든 인텐트가 통과였다.

**아무것도 안 막는 게이트는 다음 사람에게 「여기서 지킨다」고 거짓말한다.** 그래서 지웠다. 지금 지키는
자리는 둘이고 둘 다 **대상을 정하는 자리**다: `writeTargetFor`(소켓이 없으면 `.unavailable` — 보내지
않는다)와 그 판정을 지나는 `submitWrite`·커밋 제출.

옛 게이트의 나머지 값 — 「새 인텐트가 늘면 분류를 강제한다」 — 은 판정자의 **exhaustive switch** 로
옮겼다. 인텐트가 늘면 거기서 컴파일이 깨지고, 더하는 사람은 그것이 **원격에서 무엇을 하는지** 적어야 한다.

### 9.2 적대적 검증 (RS4c, 3회)

**1회차 — 「실행은 사용자가 한다」가 사실인가.** 문서와 화면 문구가 그렇게 말하는데, 주입이 곧 실행이면
그 말이 거짓이다. 넣는 문자열에 **개행이 없고** `encodePaste` 도 붙이지 않는다(개행을 CR 로 **정규화**할
뿐이다). bracketed paste 를 켠 셸에서는 괄호로 감싸여 더더욱 실행되지 않는다 — **이상 없음.**

**2회차 — 그 pane 이 정말 그 기계인가.** ⚠️ **아니었다.** §6.4 는 「주입 시점에 활성 pane 을 다시
판정한다」인데 **터미널인지만** 다시 물었다. 목록의 호스트와 pane 의 호스트가 어긋나면 명령이 **엉뚱한
기계**에서 돈다 — `fetch` 는 다른 저장소를 가져오고, **`push` 는 다른 저장소에 쓴다**(그 길은 원래부터
있었다). `followActiveTerminalRepo` 가 **도크가 보일 때만** 도는 탓에 그 어긋남은 실제로 생길 수 있다.
주입 자리에서 두 호스트를 직접 대조한다.

그 자리를 고치다 **둘째 결함**이 나왔다: 거절해도 「터미널에 넣었습니다」를 **덮어썼다.** 사용자는
터미널에서 명령을 찾다가 없는 것을 보고, 왜 없는지는 영영 모른다. 주입 함수가 성공 여부를 돌려주고,
호출자는 **넣었을 때만** 그렇게 말한다.

**3회차 — pane 이 셸 프롬프트가 아니면.** vim·less·도는 빌드에 붙여넣으면 그 프로그램이 받는다.
`maru` 는 OSC 133(semantic prompt)을 **파싱하긴 한다.** 그런데 ⑴ 그 이벤트는 **소비하면 비우는 큐**라
「지금 프롬프트인가」라는 상태가 아니고, ⑵ host-backed Term 의 코어는 placeholder 라 그 값을 관측으로
흘려야 하며, ⑶ 무엇보다 **원격 셸 대부분은 OSC 133 을 안 낸다** — 그러면 「모르니까 막는다」가 되어
흔한 경우를 막는다.

그래서 **방어를 만들지 않고 한계로 적는다.** 같은 성질이 `push`·`pull` 에 원래부터 있었고(같은 주입
경로다), 붙여넣기 자체는 실행이 아니라 사용자가 화면에서 보고 지울 수 있다. 「모를 땐 넣고 돌고 있는
것을 알면 안 넣는다」는 나중에 셸 통합 상태가 관측으로 서면 그때 붙일 값이다.

## 10. 남은 두 한계를 닫는다 (2026-09-01)

RS4 를 끝내며 **의도적으로 남겨 둔** 둘이다. 남긴 이유를 그때 적었고, 여기서 그 이유가 여전히 맞는지
다시 재고 닫는다.

### 10.1 「원격에 git 이 없다」를 이름으로 말한다 (§2.2 ⑺)

읽기 실패가 **「읽지 못함」 하나로** 뭉개져 있었다. 그런데 세 상태는 사용자가 할 일이 각각 다르다:

| 종료 코드 | 뜻 | 사용자가 할 일 |
| --- | --- | --- |
| **127** | 원격 PATH 에 `git` 이 없다 | **그 원격에 git 을 깐다** |
| **255** | ssh 가 자기 실패로 끝났다 | **연결을 다시 붙인다** — 저장소 이야기가 아니다 |
| 그 밖 | git 이 거부했다(128=fatal, 1=거절) | 저장소를 본다 |

미룬 이유는 「`Output` 을 24 곳에서 넓혀야 한다」였는데, **다시 보니 그럴 필요가 없었다.** 종료 코드를
`runArgvWithEnv` 에서 **타입 있는 오류**로 올리고(`ExitCommandNotFound`·`ExitTransportFailed`),
`runOn` 이 **원격일 때만** 이야기로 바꾼다(`mapRemoteExitError`). `Result` 에는 `failure` 한 필드만
늘었다.

**로컬은 그 해석을 안 받는다.** 로컬 git 은 127·255 를 안 쓰고, 쓴다면 그것은 git 이 한 말이라 우리가
다시 해석하면 안 된다.

⚠️ **판정자를 한 번 잘못 썼다.** 처음엔 가짜 `git_exe` 를 넘겨 「git 없는 원격」을 만들려 했는데,
`buildRemote` 는 `argv[0]` 을 버리므로(RS4a 의 설계다) 원격은 여전히 `git` 을 찾는다 — 판정자가 빨갛게
나서 그 사실을 알려 줬다. 이 기계에는 `/usr/bin/git` 이 늘 있어 그런 원격을 **만들 수 없다.** 그래서
둘로 갈랐다: **실물 전송 위에서 진짜 127** 을 내고(`sh -c 'exit 127'`), **번역 규칙은 순수 함수**로 떼어
따로 센다. 「원격을 못 만든다」가 규칙을 안 보는 핑계가 되지 않게.

### 10.2 「그 터미널이 지금 무언가 돌리고 있나」를 본다 (§9.2 3회차)

RS4c 에서 **방어를 안 만들기로** 했었다. 이유는 셋이었는데 **둘이 틀렸다**:

- ⑴ 「OSC 133 이벤트는 소비하면 비우는 큐라 상태가 아니다」 → **틀렸다.** `TerminalCore.semantic_state`
  가 현재 영역을 **상태로** 들고 있다(A→prompt, B→input, C→command).
- ⑵ 「host-backed 는 placeholder 라 관측으로 흘려야 한다」 → **이미 흐르고 있었다.**
  `RuntimeObservation.semantic_state` 가 wire 에 있다.
- ⑶ 「원격 셸 대부분이 OSC 133 을 안 낸다」 → **맞다.** 그래서 이것이 설계를 정한다.

⑶ 때문에 **기본값이 닫기 확인과 반대**다:

- `termHasRunningJob`(닫기 확인)은 「**모르면 물어본다**」 — 잘못 닫으면 돌던 작업이 죽는다.
- `activeTermKnownBusy`(주입)는 「**모르면 넣는다**」 — 모름을 막음으로 접으면 흔한 경우를 통째로 막고,
  그때 사용자는 왜 안 되는지도 모른다.

컨트롤 플레인의 `atPromptWire` 가 같은 이유로 3상을 보존하고 있어, 그 규율을 그대로 따랐다.
**alt 화면**(vim·less)은 semantic 과 무관하게 「돈다」다 — 거기 넣으면 편집 중인 파일에 글자로 박힌다.

**교훈**: 「방어를 만들지 않는다」고 적을 때 그 근거 셋 중 둘이 확인 없이 쓴 것이었다. 한계로 적는 것도
**실측 위에** 적어야 한다.

### 10.3 적대적 검증 (한계 둘, 3회) — **셋 다 진짜였다**

**1회차 — 로컬 `execve` 실패도 127 이다.** ⚠️ `spawnCapture` 의 자식은 `execve` 가 실패하면 스스로
`_exit(127)` 한다(셸 관례). 즉 「로컬 git 은 127 을 안 쓴다」는 내 주석이 **거짓**이었고, 로컬 git 을 못
띄운 상황이 「원격에 git 이 없다」로 뜰 수 있었다 — 사용자는 **엉뚱한 기계**를 손본다. 종료 코드 해석을
`remote_exit_codes` 스위치로 **원격일 때만** 켠다.

**2회차 — 낡은 관측(`.stale`)을 믿었다.** ⚠️ 거기 남은 `.command` 로 막으면 사용자는 프롬프트를 보면서
「명령이 돌고 있습니다」를 읽는다. **「모르면 넣는다」의 「모른다」에는 낡음도 든다.**

그리고 **그 수정의 반증이 실패를 못 냈다** — 스모크 세션의 Term 은 in-process 라 판정자가 그 갈래를
**한 번도 안 지났다.** 고쳤는데 아무도 안 보는 상태였다. `atPromptWire` 처럼 순수 함수
(`observationKnownBusy`)로 떼어 아홉 조합을 전수로 센다.

**3회차 — 실패 사유가 호스트를 넘었다.** ⚠️ 호스트가 갈릴 때 안내 줄(`scm_write_error`)은 지우는데
`git_failed`·`git_failure` 는 안 지웠다. 원격에서 「git 이 없습니다」를 낸 뒤 로컬로 옮기면(경로가 같으면
`rememberGitRepo` 가 그 전환을 못 본다) 그 문구가 **로컬 목록 위에** 남는다.

**RS2 2회차와 같은 뿌리이고, 이 축에서 다섯 번째다** — 목록 안내 · diff 표식 · 쓰기 대상 · 갱신 대상 ·
읽기 실패 사유. 새 상태를 더할 때마다 **「이것은 (경로, 호스트) 쌍인가」**를 먼저 물어야 한다.

### 10.4 적대적 검증 5회 더 — **넷이 진짜였다**

**1·3회차 — 「한쪽만 고쳤다」가 또 나왔다.** 목록 읽기에는 이름을 붙였는데 **diff 오른쪽**
(`worktreeSideOn`)과 **쓰기**(`WriteResult`)는 안 붙였다. 같은 사고에 세 화면이 서로 다른 말을 한다 —
목록은 「연결이 끊겼다」, diff 는 「읽지 못함」, 스테이지는 셸이 뱉은 `sh: git: command not found`.
사용자는 그것을 **세 개의 다른 문제**로 읽는다. 셋이 같은 말을 하게 했다.

**2회차 — `push`·`pull` 의 동작이 바뀌었다**(결함이 아니라 변경). 주입 자리를 하나로 합치면서 그 둘도
호스트 대조·busy 판정을 탄다. 로컬 저장소인데 활성 pane 이 원격이면 이제 **거절한다** — 전에는 원격
셸에 `git push` 가 꽂혔고, 그것은 **다른 저장소에 쓰는** 일이었다.

**4회차 — `remote_exit_codes` 를 켠 자리 감사.** 제품 두 자리(`runOn` 원격 갈래 · `worktreeSideOn`)뿐이고
둘 다 원격이다 — 이상 없음.

**5회차 — 원격인데 로컬 git 이 없으면 통째로 죽었다.** ⚠️ `buildRemote` 가 `argv[0]` 을 버리는데도
제출부가 `locate()` 를 요구했다. 로컬에 git 이 없는 사용자는 원격 SCM 을 **전혀 못 쓰고**, 화면은
**엉뚱한 기계**를 가리켜 「git 이 설치되어 있지 않습니다」라고 말한다.

**쓰기는 RS4a 에서 이렇게 고쳤는데 읽기를 빠뜨렸다** — 1·3회차와 같은 부류다. 안내(`scmEmptyNotice`)도
원격을 알게 해 **첫 제출 전 창**까지 닫았다.

> **이 축에서 반복되는 두 뿌리를 여기 못박는다.**
> ⑴ 새 상태를 더할 때 **「이것은 (경로, 호스트) 쌍인가」** — 다섯 번 나왔다.
> ⑵ 원격 축을 고칠 때 **「형제 자리가 어디인가」** — 읽기·diff·쓰기 셋이 늘 함께 간다.

## 11. 정정 — 「알려진 flaky 29 개」는 flaky 가 아니었다 (2026-09-01)

RS4a~c 와 §10 의 PR 본문·커밋 메시지에 `session_host.{client_external_pump, external_pump_owner,
external_loop_owner, external_tty}` 29 개를 **「깨끗한 main 에서도 빨간 알려진 flaky」**라고 적었다.
근거는 「같은 커밋에서 0 → 36 으로 흔들린다」였다.

**그 두 실행의 차이는 flaky 가 아니라 포그라운드/백그라운드였다.** 같은 커밋(`3412772d`), 같은 시점,
깨끗한 트리로 연속 두 번 재 보니:

```
zig build test-macos-app-host-abi            (포그라운드)  4324 passed; 99 skipped;  0 failed
(zig build test-macos-app-host-abi ...) &    (백그라운드)  4288 passed; 99 skipped; 36 failed
```

`&` 로 띄우면 controlling terminal 이 없어 시그널·tty 계열이 떨어진다(`UnsupportedSignalDisposition`).
다른 세션이 같은 현상을 겪고 알려 주기 전까지 하루 종일 그 29 개를 눈가리개로 달고 일했다.

**무엇이 실제로 잘못됐나**: 배포된 결함은 없다 — CI 는 그 테스트들을 제대로 돌렸고 매 PR 에서 통과했다.
잘못된 것은 **판정 방법**이다. 그 29 개가 가려 두는 동안 그 모듈의 진짜 회귀는 「늘 그러던 것」으로
지나갔을 것이다. 실패 **집합**을 매번 대조해 위험을 줄이긴 했지만, 기준선 자체가 오염돼 있었다.

**규칙**: 게이트는 **포그라운드**로 돌린다. 불가피하게 백그라운드였다면, 실패가 나온 그 순간
**포그라운드로 한 번 더** 보고 판정한다 — 「flaky」라고 적기 전에.

> 같은 모듈을 떨어뜨리는 **다른** 원인이 하나 더 있다: 살아 있는 maru 앱. 증상만으로는 구별되지 않는다.

## 12. RS4a·b·c 를 **제품에서** 확인했다 — 그리고 결함이 하나 나왔다 (2026-09-02)

RS4a(스테이지)·RS4b(커밋)·RS4c(fetch 주입)은 판정자로만 초록이었고 **아무도 화면에서 본 적이 없었다.**
셋을 제품으로 돌려 **원격 저장소의 git 상태**와 대조했다.

### 12.1 「원격으로 갔다」를 어떻게 증명하나

하네스의 원격은 `127.0.0.1` 이라 **로컬과 같은 파일 시스템**이다 — 파일이나 ref 만 보면 ssh 로 간 것과
로컬 git 이 같은 경로를 만진 것이 **구분되지 않는다.** 그래서 목격자를 하나 세웠다.

원격 명령은 `sh -c 'PATH="$HOME/.local/bin:$HOME/bin:…:$PATH"; exec "$@"' sh git …` 를 지난다(§2.2).
그 PATH 앞단의 **`$HOME/bin` 은 이 기계의 로컬 PATH 에 없다.** 거기에 argv·`SSH_CONNECTION`·`PWD` 를
적고 진짜 git 을 exec 하는 래퍼를 두면, **그 로그에 줄이 남았다는 사실 자체가 원격 경로를 지났다는
뜻**이다. `SSH_CONNECTION` 이 채워져 있는지로 한 번 더 대조한다.

### 12.2 결과

| | 무엇을 봤나 | 원격 상태 | 목격자 |
|---|---|---|---|
| RS4a 스테이지 | 도크 「스테이지된 변경 1 · rs4a-stage-me.txt +1 −0 A」 | `?? rs4a-stage-me.txt` → `A  rs4a-stage-me.txt` | `<add> <-A> <-->`, `ssh=[127.0.0.1 …]`, **한 번만**(래치가 돈다) |
| RS4b 커밋 | 도크가 비고 커밋 상자가 placeholder 로 | HEAD 가 `RS4b 제품검증 101329` 로, 트리 깨끗 | `<commit> <-F> <->` — 메시지가 **stdin** 을 탔다 |
| RS4c fetch | 터미널에 `git fetch --prune` 이 **글자로**, 도크에 「거기서 실행한 뒤 새로고침하세요」 | `origin/main` **안 움직였다**(origin 은 한 커밋 앞서 있었다) | `<fetch>` **0 건** |

RS4c 의 「안 움직였다」가 핵심이다 — 개행 없이 넣으므로 **실행은 사용자 몫**이라는 계약(§9)이
화면에서 지켜졌다. 브랜치 줄이 `↑1 ↓0` 인 것도 같은 사실의 다른 얼굴이다(앞선 origin 을 아직 모른다).

### 12.3 그 화면에서 나온 결함 — 미푸시 점이 **호스트 글자 위에** 얹혔다

`127.0.●0.1 main`. `src/chrome/components/scm_dock/view.zig` 의 점 위치가

```zig
const dot_x = branch_x + name_w + gap;   // 이름이 branch_x 에서 시작한다고 친다
```

인데, 원격이면 이름은 host 접두 **뒤**에서 시작한다(`name_x = branch_x + host_w + gap`).
**로컬은 두 식이 같은 값이라 드러나지 않았다** — 「경로만 보면 두 기계가 같은 값」과 같은 뿌리다(§1).

같은 블록에 두 번째 결함이 있었다: 침범 검사에 쓰는 `branch_end` 가 그 자리에서는 **아직 `↑↓`·칩만큼
안 좁혀진** 값이었다. 주석은 「오른쪽 묶음을 침범하지 않을 때만 그린다」라 적어 두고 실제로는 안 지켰다.
점 블록을 이름 뒤(두 값이 확정된 뒤)로 옮겨 **둘을 함께** 고쳤다.

**판정자는 이미 있었는데 초록이었다.** 「이름 뒤에 점이 선다」 판정자가 `remote_host` 를 안 세워서,
틀린 식과 맞는 식이 같은 값이 되는 자리만 보고 있었다. 원격 축을 세운 판정자를 더했고, 고침을
되돌리면 **빨개지는 것**까지 확인했다(옛 판정자는 그때도 초록이었다 — 볼 수 없었다).

두 번째 결함은 **길이 하나로는 못 잡았다.** 긴 이름 하나로 「점이 없다」를 보는 판정자는 고친 쪽도 안
고친 쪽도 초록이었다(겹치는 구간이 좁고 폰트에 딸린 값이다). 상수를 맞히는 대신 **성질**을 센다 —
이름 길이를 훑으며 「점이 나왔다면 `↑` 왼쪽이다」, 그리고 「한 번도 안 나왔으면 아무것도 안 센 것이다」.

## 13. 적대적 검증 3 회 (2026-09-02) — 워크트리 행이 로컬 git 으로 샜다

§12 로 RS4 를 닫은 뒤 세 갈래로 공격했다. 하나가 뚫렸다.

### 13.1 1 회차 — 「어느 기계인가」의 철자가 둘이다 → 결함 아님

SCM 브랜치 줄은 `git_repo_dest` 원문(`user@host`)을, 폴더줄은 `termDisplayHost`(= `user@` 를 뗀 host)를
쓴다. 한 화면에 같은 기계가 두 철자로 적힌다.

**계약이다**: RS3b §2.3 이 「도크 머리에 `user@host` 를 적는다」를 정했고, 폴더줄이 사용자명을 떼는 것은
「좁은 줄에서 사용자명은 어느 기계인가를 말하지 않는다」는 별개 결정이다(ssh-integration.md §9.3).

⚠️ **다만 두 결정이 서로를 참조하지 않는다.** §9.4 의 표시 규율 문단은 「그 규율을 지나는 자리는 둘」이라
적는데, 브랜치 줄은 host 를 적으면서 그 규율 밖에 있다 — 읽는 사람이 「빠졌다」고 판단해 «없는 일»을
할 수 있는 모양이다(그 표가 이미 두 번 그렇게 했다).

### 13.2 2 회차 — 원격 저장소의 **워크트리 행**이 로컬 git 으로 샜다 → 결함 확정

원격 저장소에 워크트리를 하나 만들고(`git worktree add`) 그 행에서 전체 스테이지를 걸었다.

```
실행 전   wt-a:  ?? probe.txt
실행 후   wt-a:  A  probe.txt        ← 스테이지됐다
목격자    wt-a 0 건 · <add> 0 건      ← 원격 PATH prologue 를 안 지났다 = 로컬 git 이 썼다
```

읽기도 같았다. 목격자에 `wt-a` 가 **0 건**인데 도크는 `wt-probe` 브랜치와 배지 `1` 을 그렸다 — 그 값은
**로컬 git 이 원격 경로를 읽은 결과**다. 두 기계였다면 같은 경로의 **남의 저장소**가 원격 그룹 밑에
뜨고, 거기에 쓴다.

**뿌리**: 두 자리가 「활성이 아니면 로컬 행이다」라고 쳤다.

| 자리 | 무엇이 틀렸나 |
|---|---|
| `writeTargetFor` | 활성 저장소와 **경로가 다르면** `.local`. 워크트리는 경로가 다르다 |
| `submitRepoStatus` | 원격 인지가 **한 줄도 없다** — `locate` 로 로컬 git 을 찾아 그 경로에 돌린다 |

**첫 고침이 과했고, 기존 판정자가 그것을 잡았다.** 「원격이면 비활성 행 전부 차단」으로 막았더니
RS4a 4 회차의 「비활성 **로컬** 저장소 행은 로컬로 간다」가 깨졌다 — 안전하게 만든다고 멀쩡한 동작을
막은 것이다. 판정을 **행마다** 하도록 좁혔다: 주 워크트리 경로(`Entry.origin`)가 같으면 같은 저장소
가족이다. 워크트리는 그 값을 저장소와 공유하고 진짜 로컬 행은 다르다. 읽기·쓰기가 **같은 함수**
(`sameRepoFamily`)를 지난다 — 두 벌이면 한쪽만 고쳐진다.

원격 워크트리를 **원격으로** 읽고 쓰는 것은 기능이다(워커·Job 이 그 행의 목적지를 모른다). 지금은
「보내지 않고 이유를 말한다」로 끊는다 — 소켓이 없을 때와 같은 처리다.

⚠️ **「읽는 중…」으로 두지 않았다.** 아무도 안 읽으므로 그 문구는 영영 안 바뀐다 — 남의 기계 값을
지우면서 다른 거짓말을 들이는 셈이다. 못 읽는다는 사실(`failed` → 「읽지 못함」)을 적는다.

### 13.3 3 회차 — 고침이 기대는 전제 → 결함 아님

`sameRepoFamily` 는 「`git_repo_dest` 가 있으면 그 가족은 원격」에 기댄다. `git_repo_dest` 는
`submitGitRead` 에서 `git_repo` 와 **함께** 갱신되므로 둘이 어긋나는 창이 없다.

⚠️ 남는 위험 하나: `scm_repo_status` 캐시는 **경로로만** 맞춘다. 로컬 `/srv/app` → 원격 `/srv/app`
전환에서 그 항목은 목록에 계속 있으므로 안 버려지고, 다시 읽히기 전 한 번은 **저쪽 기계의 값**이
그려질 수 있다. 지금은 원격 가족을 `failed` 로 적어 그 창이 좁지만, 근본은 캐시에 host 축이 없는 것이다.
