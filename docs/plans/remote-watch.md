# 원격 감시 — 저쪽에서 바뀌면 도크가 안다 (RW)

**지금**: 원격 저장소는 아무도 감시하지 않는다. 원격에서 파일을 고쳐도 도크는 **포커스 전환이나
사용자의 새로고침** 전까지 그대로다. 로컬은 `.git` 감시자가 즉시 반영하므로, 사용자에게는
**「원격만 안 된다」**로 보인다.

소유 관계: [원격 SCM](remote-scm.md)이 「원격 저장소를 어떻게 읽고 쓰는가」를 소유하고, 이 문서는
**「언제 다시 읽는가」**만 더한다. 전송(ControlMaster)·설치 규율은
[SSH 통합 §4·§6·§9.5](../ssh-integration.md)가 단일 출처다.

> **clean-room**: 같은 문제를 푸는 공개 도구들은 **동작 비교**로만 확인했고 코드·표현은 옮기지 않았다.
> 아래 설계는 maru 자신의 `remote_install` 선례와 이 문서에 적힌 **실측값**에서 유도했다
> (`project-rules.md`).

## 1. 왜 지금 구조로는 안 되나

`submitGitRead` 가 그 이유를 이미 적고 있다:

> **원격은 감시하지 않는다.** `.git` 을 지켜보는 것은 로컬 파일시스템 감시자이고, 원격 경로를 주면
> 로컬에 우연히 있는 같은 경로를 감시하게 된다 — 남의 저장소가 바뀔 때마다 원격 목록을 다시 읽는다.

로컬 감시자를 원격 경로에 겨누는 것은 **이 세션 내내 고쳐 온 「경로는 두 기계 사이에서 키가 아니다」**
그 자체다. 그러니 감시는 **저쪽에서** 일어나야 한다.

## 2. 계약

- **트리거만 바꾼다.** 읽기 파이프라인(§원격 SCM)은 그대로다 — 「바뀌었다」한 줄이 오면 지금 하던 읽기를
  걸 뿐이다. 파싱 계약을 원격·로컬 두 벌로 나누지 않는다.
- **없으면 조용히 폴백한다.** 감시자를 못 심으면 지금 동작(포커스·새로고침)이 그대로 남는다. 기능이
  없다고 세션이 깨지지 않는다 — `remote_install` 의 `|| exit 1` 규율과 같다.
- **자기완결.** 원격이 네트워크로 무언가를 내려받게 하지 않는다. 페이로드는 maru 바이너리에 embed 하고
  **stdin 으로 파이프**한다(terminfo 와 같은 길).
- **사용자 파일을 안 고친다.** `$HOME/.cache/maru/` 안에만 쓴다. `~/.zshrc` 는 건드리지 않는다(§9.5).
- **고아를 남기지 않는다.** 채널이 끊기면 원격 프로세스도 죽는다. 이것은 **측정으로 확인할 항목**이다
  (§5).

## 3. 왜 셸 스크립트로는 안 되나 — 실측

감시 API 는 있는데 **셸에서 부를 CLI 가 없다**(2026-09-03 이 기계에서 측정):

```
inotifywait 없음   fswatch 없음   watchman 없음   entr 없음
FSEvents.framework 있음   sys/event.h(kqueue) 있음
```

`inotify` 는 리눅스 커널 API 이고 `inotifywait` 은 `inotify-tools` **패키지**다. `fswatch` 는 서드파티다.
FSEvents 는 C 호출, inotify·kqueue 는 syscall 이라 **셸에서 접근할 방법이 없다.**

그래서 셸로 가면 **폴링이 천장**이다. 그 천장의 값도 쟀다 — `status --porcelain=v2` + `diff --numstat` ×3
한 주기가 작은 저장소 ~46 ms, maru3(추적 1,603 개) ~53 ms. 2 초 간격이면 wall 2~3 %, CPU 1 % 미만.
작지만 **저장소 하나·원격 하나당 영원히**이고, 무엇보다 **사용자 서버**에서 도는 비용이다.

⚠️ **폴링만으로는 틀린 화면도 나온다.** 「`status` 하나로 탐침하고 바뀔 때만 전체를 읽자」는 안을
검토했다가 버렸다. 근거 둘을 **실측했고, 하나는 처음 쓴 형태가 틀려서 고쳤다**:

- ✅ **이미 ` M` 인 파일을 더 고치면 status 는 바이트가 같은데 numstat 만 바뀐다.** 실측: status 가
  `1 .M N... … f.txt` 로 **동일**한 동안 `diff --numstat` 은 `1 1` → `4 2` 로 바뀌었다. 그 숫자가
  행마다 보이는 `+N −M` 이다.
- ⚠️ **「fetch 로 behind 가 바뀌어도 status 는 그대로」는 그대로는 거짓이다.**
  `status --porcelain=v2 --branch` 는 `# branch.ab` 줄을 **포함**해서, upstream 기준 ahead/behind 가
  바뀌면 status 도 바뀐다(실측: `+0 -0` → `+0 -1`).
  **참인 형태는 이것이다**: 도크의 `↑↓` 는 `rev-list --count --left-right origin/HEAD...HEAD`
  (**기본 브랜치** 기준)인데 `branch.ab` 는 **upstream** 기준이라, 둘이 다른 브랜치를 가리키면 갈린다.
  실측(브랜치 `feat`, upstream `origin/feat`, `origin/HEAD`=`origin/main`, `origin/main` 에만 새 커밋):
  `# branch.ab +0 -0` **그대로**인데 `rev-list` 는 `1 1` → `2 1`. **화면 숫자만 바뀌고 탐침은 못 본다.**

## 4. 설치 — `remote_install` 과 같은 길

기존 계약(`src/cli/ssh.zig`)이 형태를 정해 두었다:

```zig
pub const remote_install =
    "if infocmp xterm-maru >/dev/null 2>&1; then exit 0; fi; " ++   // 멱등
    "command -v tic >/dev/null 2>&1 || exit 1; " ++                  // 없으면 안전 폴백
    "tic -x -o \"$HOME/.terminfo\" - 2>/dev/null";                   // stdin 페이로드
```

감시자도 같은 세 박자로 심는다: **멱등 확인 → stdin 으로 받은 것을 maru 전용 디렉터리에 → 실패하면
`exit 1`**. 다른 점은 페이로드가 텍스트가 아니라 **작은 정적 바이너리**라는 것뿐이다.

**크기를 쟀다** — 그리고 **실제로 돌려서 동작을 확인한 뒤** 다시 쟀다(§5·§6). 처음 잰 값은
**동작하지 않는 코드의 크기**였다(아래 ⚠️):

**아래는 RW1 구현체(`tools/remote-watch/`)를 두 플랫폼에서 돌려 본 뒤 잰 값이다**(§5.1):

| 타깃 | 감시 방식 | raw | gz |
|---|---|---|---|
| x86_64-linux-musl | inotify | 203 KB | **94 KB** |
| aarch64-linux-musl | inotify | 203 KB | **103 KB** |
| aarch64-macos | kqueue | 162 KB | 55 KB |

리눅스 두 아키텍처를 embed 하면 앱에 **~197 KB(gz)** 가 붙는다. 아키텍처 판별은 `uname -sm` 한 번이다.

⚠️ **이 값은 최초 시제품(gz 32/35 KB)의 3 배다.** 늘어난 몫은 **이식성 값**이다: 디렉터리 순회를
`std.Io.Dir` 에 맡겼기 때문이다. 그렇게 한 이유가 바로 아래 함정이고, 크기를 3 배로 치르더라도
「조용히 아무것도 감시하지 않는」 판보다 낫다.

⚠️ **`FTW_D` 상수가 libc 마다 다르다 — glibc 는 1, musl 은 2.** glibc 값을 쓴 시제품은 컴파일도 되고
`nftw` 도 성공(`r=0`)했는데 **watch 를 하나도 안 걸었다**(`w=0`) — 조용히 아무것도 감시하지 않았다.
컨테이너에서 **돌려 보고서야** 드러났다.

**구현은 `nftw` 를 아예 안 쓴다.** 디렉터리 판정을 `std.Io.Dir` 의 항목 종류에 맡겨 libc 상수를
경로에서 지웠고, 경계 test(`tests/remote_watch_contract_boundary.zig`)가 **주석을 벗긴 소스에서**
`nftw`·`FTW_D` 가 없음을 센다(「언급하는가」가 아니라 「쓰는가」를 세야 한다 — 처음 쓴 판정자가 자기
설명 주석에 걸렸다).

## 5. 수명 — 고아를 남기지 않는다

감시자는 **설계상 조용하다**(바뀔 때만 출력). 그래서 「쓸 때 EPIPE 로 죽는다」에 기댈 수 없다.
다섯 경우를 재 봤다(모두 「띄운 뒤 살아있음」을 먼저 확인하고, 로컬 ssh 를 SIGKILL):

| 케이스 | ssh 죽인 뒤 |
|---|---|
| 셸 루프 · 수다스러움 | 죽음 |
| 셸 루프 · **조용함** | **고아** |
| 바이너리 · 수다스러움 | 죽음 |
| 바이너리 · **조용함 · 무대응** | **고아** |
| **바이너리 · 조용함 + stdin `poll`** | **죽음** ✅ |

**결론**: 감시 fd 와 **stdin 을 같은 `poll` 에 넣고, stdin 에 이벤트가 오면 종료한다.** 바이너리는
pollfd 하나로 끝나고, 셸은 `cat` + 백그라운드 잡을 엮어야 한다 — 이 차이도 바이너리를 고르는 이유다.

⚠️ **채널의 stdin 을 열어 둬야 한다.** 백그라운드로 띄운 ssh 는 stdin 이 처음부터 EOF 라 감시자가
**뜨자마자 죽는다.** 증상은 「감시가 그냥 안 된다」로만 보인다.

이 함정에 **세 번** 걸렸다 — 셸 결속 시험 두 번, 그리고 리눅스 컨테이너에서 바이너리를 stdin 으로
밀어 넣었을 때 한 번(`cat` 이 stdin 을 다 먹어 EOF 라 감시자가 즉시 종료했다). 설치와 실행이 **같은
stdin 을 쓸 수 없다**는 뜻이기도 하다: 설치는 한 exec, 감시는 다른 exec 여야 한다.

### 5.1 끝에서 끝까지 — 두 플랫폼에서 돌렸다

| | macOS(kqueue) | Linux(inotify) |
|---|---|---|
| 실행 환경 | 하니스 원격에 **ssh 채널로** 띄움 | alpine 컨테이너(aarch64) |
| 감시 등록 | 디렉터리 81 개 → fd **89 개**(디렉터리 + 상수) | 디렉터리 4 개 → watch **4 개** |
| 변화 감지 | `touch` → `change` 가 **ssh 채널로 로컬까지** 도착 | `touch`·`mkdir`·`rm` 각각 `change` |
| 채널 종료 | 로컬 ssh SIGKILL → **죽음** | stdin 닫힘 → **죽음** |

즉 §2 의 계약(트리거만 바꾼다 · 고아를 안 남긴다)이 **두 플랫폼 실물에서 성립**한다.

## 6. 한도 — 여기가 진짜 천장이다

감시는 **디렉터리당 하나**다. maru3 기준 디렉터리 **2,515 개**(캐시 제외) / 5,657 개(전체).

**한도의 축이 플랫폼마다 다르다** — 이것을 헷갈리면 엉뚱한 값을 본다:

| | 무엇이 한도인가 | 실측 |
|---|---|---|
| inotify(리눅스) | `max_user_watches` (**fd 가 아니다** — 인스턴스는 fd 1 개뿐) | 1,048,576 · 인스턴스 상한 128 |
| kqueue(macOS·BSD) | **fd 1 개/디렉터리** → `ulimit -n` | 이 Mac 1,048,576 |

⚠️ 위 `max_user_watches` 는 **컨테이너 VM 값**이라 일반 서버를 대표하지 않는다. 같은 컨테이너에서
`ulimit -Sn` 은 **1,024** 였다 — 리눅스의 흔한 기본값이다. inotify 는 그 fd 한도에 안 걸리지만,
**kqueue 를 쓰는 BSD 원격이라면 2,515 개 디렉터리가 그 한도를 넘는다.**

⚠️ **macOS·BSD 원격은 지금 감시하지 않는다**(§8.6 ① — kqueue 가 파일 편집을 안 알린다). 아래 kqueue
줄은 FSEvents 가 붙은 «뒤» 의 값이다.

**한도를 넘으면 폴링으로 격하한다**(RW7d). 조용히 반쪽만 감시하는 것이 최악이기 때문이다 — 화면이
「최신」인 척하면서 일부 변경을 영영 놓친다. 폴링은 반쪽이 아니라 **도크가 읽는 것과 같은 범위**를
보므로(§11.3) 잃는 것은 **지연뿐**이다.

> **이 문장은 두 번 뒤집혔다.** 처음엔 이렇게 적었다가, RW5 에서 「폴링으로 격하하지 않는다」로
> 뒤집었고(근거: 감시자의 한도 경로는 아무것도 감시하지 않고 끝나므로 격하할 반쪽 상태가 없다),
> RW7 이 폴링을 실제로 만들자 다시 원래대로 왔다. **RW5 의 근거는 「폴링이 없다」는 사실에 기대고
> 있었고, 그 사실이 바뀌었다.**

실물로 확인했다: 컨테이너에서 `max_user_watches` 를 **1** 로 낮춰 inotify 를 고갈시키면, 판 1 은
`exit_watch_limit` 으로 죽었고 판 2 는 **살아서 폴링으로 파일 수정을 잡는다.**

⚠️ **이때는 화면이 말하지 않는다.** 격하가 감시자 «안»에서 일어나 앱은 그 사실을 모른다 — 출력은
여전히 `change` 한 줄뿐이기 때문이다(계약 §2). **그래도 §6 의 규율을 어기지 않는다**: 저 규율이 막는
것은 「반쪽을 최신인 척 보여 주는 것」인데, 폴링은 반쪽이 아니다. 사용자가 느끼는 차이는 **지연**뿐이고,
그것을 배너로 말하면 RW6 이 세운 「영구 실패에서만 말한다」를 어기는 잔소리가 된다.

**「이 원격에서는 못 한다」일 때는 여전히 화면이 말한다**(RW6) — 폴링조차 못 하는 경우(`git` 이 없다·
저장소가 아니다)가 그것이고, 그때만 `exit_unsupported` 다.

## 7. 단계

> **진행**(계획 문서가 진행의 단일 출처다 — [PR 체크리스트](../pr-checklist.md) 「문서 상태 표기 규율」):
> RW1 **완료** · RW2a **완료** · RW2b **완료** · RW3 **완료**(트리거 접속 포함 — RW4 를 흡수했다) ·
> RW2c **완료**(§6.1 — 실은 것을 실제로 심는다) · RW5 **완료** · RW6 **완료** · **RW7 완료**(§11 — macOS·BSD 를 폴링으로 되살렸고, 리눅스의 한도
> 초과도 포기 대신 격하한다).

- **RW1 — 감시자 바이너리**: 리눅스는 inotify, **macOS·BSD 는 폴링**(RW7). kqueue 는 버렸다 —
  디렉터리에 건 `EVFILT_VNODE` 는 파일 «편집» 을 안 알리고 디렉터리마다 fd 를 써서 한도에도 걸린다
  (§8.6 ① 실측). 그 두 함수는 **지웠다**: 측정으로 틀렸다고 밝혀진 코드를 남겨 두면 다음 사람이
  되살린다. stdin `poll` 로 수명 결속. 인자는
  감시할 루트 하나. 출력은 「바뀌었다」한 줄(디바운스는 로컬이 진다).
- **RW2a — 설치 계약**: `uname -sm` → 변종 판별, 멱등 확인(`--version` 을 **실행**해 본다), stdin 으로
  받은 바이트를 `$HOME/.cache/maru/` 에 임시 이름→`mv` 로 심기, 못 쓰면 `exit 1`.
  **순수 계층**(`src/session/remote_watch_install.zig`)이라 명령을 만들 뿐 실행하지 않는다.
- **RW2b — 페이로드 배달**: 빌드가 만든 변종을 앱이 손에 쥐는 길(번들 리소스 또는 embed).
  ⚠️ `maru_terminfo` 가 **세 모듈**에 등록된 함정과, `maru_mod` 에 넣으면 **wasm·모바일까지** 리눅스
  바이너리를 지고 가는 문제를 함께 풀어야 한다 — 그래서 RW2a 와 갈랐다.
- **RW3 — 채널(+트리거)**: ControlMaster 위에 긴 exec 하나. stdin 파이프 유지, 재시작·백오프, 소켓
  부재 감지(`remoteControlSocketFor` 재사용). 「바뀌었다」가 오면 **`refreshGitStatus` 만** 부른다 —
  읽기 파이프라인은 안 건드린다.
  - **선례가 있었다**: `ssh_upload.spawnAgentEvents` 가 같은 모양의 긴 수명 원격 스트림이고, 소비는
    스레드가 아니라 **`O_NONBLOCK` + 틱 드레인**이다. 「선례 없는 기계」라던 이 문서의 앞선 판단이
    틀렸다 — 새로 만든 것은 **stdin 을 파이프로 두는 갈래** 하나뿐이다.
  - **디바운스는 안 넣었다.** 읽기 슬롯(`git_inflight`)이 이미 직렬화하고, 감시자는 다이제스트가 바뀔
    때만 한 줄을 낸다. 실측에서 연타로 읽기가 쌓이는 모습을 못 봤다 — 보이면 그때 넣는다.
- **RW5 — 영구 실패는 포기한다**: 감시자가 「이 원격에서는 못 한다」(`exit_watch_limit`·
  `exit_unsupported`)고 말하면 **다시 안 띄운다.** 대상이 바뀌면 `rememberGitRepoDest` 가 채널을
  통째로 놓으므로 그때 풀린다.
  - **왜 필요했나(실측)**: 즉시 실패하는 감시자에 **30 초 동안 7 번** 기동했다 — 백오프는 제대로 도는데
    멈추지 않는다. 사용자가 도크를 열어 둔 내내 5 초마다 ssh 자식이 뜨고, 그건 **남의 서버**에서 도는
    비용이다. 고친 뒤 **1 번**이다.
  - **일시적 실패는 계속 재시도한다**: 정상 정리(`-1`)·소켓 끊김·`127`(명령 없음, 설치가 다시 될 수
    있다)·`255`(전송 실패). 실측 대조군에서 감시자를 `SIGKILL` 하면 여전히 재기동한다.
  - ⚠️ **~~폴링으로 격하하지 않는다~~ — RW7d 가 뒤집었다.** 이 항목의 근거는 「폴링이 없다」는
    사실에 기대고 있었다(그래서 격하할 곳이 없었다). RW7 이 폴링을 만들자 근거가 사라졌고, 이제
    한도(`exit_watch_limit`)는 **포기가 아니라 격하**다 — 잃는 것은 지연뿐이다(§6 · §11.7).
    남는 「포기」는 폴링조차 못 하는 경우뿐이다(`exit_unsupported`).
- **RW6 — 포기를 화면이 말한다**: `.gave_up` 이 되면 `scm_remote_watch_gave_up` 을 띄운다. 선례가
  같은 저장소에 있다 — 에이전트 채널이 재시도 상한을 넘을 때 `agent_remote_channel_gave_up` 으로
  똑같이 한다(`scheduleStreamerRetry`).
  - **영구 실패에서만 말한다.** 일시적 끊김(슬립·네트워크 전환)에도 띄우면 배너가 잔소리가 되고,
    그러면 사용자가 배너 자체를 무시해 **정작 영구 실패일 때 안 읽힌다.** 판정자가 일시 갈래에
    `showNoticeKey` 가 없음을 센다.
  - **한 번만 뜬다.** `.gave_up` 은 `pumpRemoteWatch` 의 switch 가 곧장 return 하는 흡수 상태라
    그 줄에 두 번 닿을 수 없다. 대상이 바뀌어 `rememberGitRepoDest` 가 채널을 놓아야 풀린다.
  - ⚠️ **「잠시 멈춤」과 「놓아줌」을 갈랐다**(적대적 검증 2026-09-04 1 회차). `stop()` 하나로 두 뜻을
    쓰고 있었는데, 도크를 감추면 그것이 `.gave_up` 을 `.idle` 로 되돌려 **RW5 가 도크 토글마다 풀렸다** —
    못 하는 원격에 ssh 자식이 다시 뜨고 배너도 되풀이된다. 「못 한다」는 **호스트**의 성질이라 화면과
    무관하므로 `pause()` 는 그 판단을 지키고, 대상이 바뀌는 `stop()` 만 지운다. **`.backoff` 도 같다**
    (4 회차 — 3 회차에서 빠뜨렸다): 무너뜨리면 재개가 `.backoff` 갈래를 안 지나 `retry_at_ns` 를
    건너뛴다. 그리고 채널은 **무엇을 보고 있는지**도 기억한다(6 회차) — 같은 호스트에서 저장소만
    바뀌는 전환은 `rememberGitRepoDest` 가 못 보는 축이라, 그것이 없으면 옛 저장소를 계속 본다.
    **자식·판단·대상은 각각 다른 수명을 산다**(8 회차) — `releaseChild()` 가 자식만 지고 `pause`/`stop`
    이 나머지를 각자 정한다. 셋을 한 함수에 뭉쳤던 것이 이 축 결함들의 공통 원인이었다.

## 8. 검증

- **고아 없음이 1급 판정이다.** §5 의 다섯 경우를 회귀로 고정한다 — 특히 「조용한 감시자 + 채널 강제
  종료」. 남의 서버에 무한 루프를 쌓는 것이 이 트랙의 최악 실패다.
- **stdin 을 닫고 띄우면 즉시 죽는지**를 함께 센다(§5 의 함정 — 안 세면 「그냥 안 됨」으로 보인다).
- 설치 실패(`exit 1`) 시 **세션이 멀쩡한지**. 감시는 부가 기능이지 접속 조건이 아니다.
- 한도 초과 → 폴링 격하 → **화면이 그 사실을 말하는지**.
- 제품 확인은 하니스 + 목격자 래퍼로 한다([원격 SCM §12.1](remote-scm.md)) — 원격이 `127.0.0.1` 이라
  파일만 봐서는 「저쪽에서 일어났다」를 증명할 수 없다.

### 6.1 배달 — 실은 것을 «아무도 안 집어 갔다» (RW2c 로 고침)

> ⚠️ **이 절을 파다가 더 앞의 문제가 나왔다 (2026-09-05).** CI 커버리지를 논하기 전에, **번들에 실은
> 네 변종을 제품이 한 번도 읽지 않았다.** 실측(제품 소스 전수):
>
> | 설치 계약의 조각 | 제품 참조 |
> |---|---|
> | `variantFromUname`(uname → 변종) | **0** |
> | `check_script`(`--version` 으로 멱등 확인) | **0** |
> | `assetRelPath`(번들의 어느 파일인가) | **0** — 판정자에서만 언급 |
> | `Contents/Resources/remote-watch/` 를 읽는 코드 | **없음** |
>
> `spawnRemoteWatch` 는 `$HOME/.cache/maru/…` 를 **그냥 `exec`** 했다. 없으면 `127` 이 오고 RW5 가
> 그것을 「일시적」으로 읽어 5 초마다 되풀이하므로, 증상은 **「그냥 안 된다」** 였다. §8.1 의 실물
> 검증이 통과한 이유도 이것이다 — **사람이 손으로 그 바이너리를 넣어 두었다.**
>
> **RW2c 가 그 자리를 잇는다**: 띄우기 전에 `uname -sm` 으로 변종을 가르고, `check_script` 로 이미
> 있고 우리 판인지 **실행해** 보고, 아니면 번들에서 `assetRelPath` 로 집어 `install_script` 에 stdin
> 으로 밀어 넣는다. 무거운 쪽(수백 KB 전송)은 **백그라운드 스레드**가 진다 — ssh 왕복을 UI 틱에서
> 하면 화면이 선다(`uploadWorker` 와 같은 규율).
>
> **컴파일러가 못 잡는 부류였다.** 쓰이지 않는 `pub` 은 오류가 아니다 — 그래서 판정자가 네 심볼이
> 제품에서 실제로 쓰이는지 센다(`설치 계약이 «죽은 계약» 이 아니다`).

#### CI 커버리지 — 어디까지 걸리나 (2026-09-05 정정)

> ⚠️ **처음 쓴 이 절은 틀렸다.** 「CI 는 `Maru.app` 을 만들지 않는다 — 커버리지 **0**」이라고 적었는데,
> 근거가 「`ci.yml` 에 `macos-app-build` 라는 **이름**이 없다」였다. 태스크 이름이 아니라 **의존**을
> 봤어야 했다: `session-host-bundled-cli-macos` 가 돌리는 P5d 게이트가
> `run_session_host_p5d.step.dependOn(macos_app_bundle_command)` 로 **번들을 만든다**(build.zig).
> 그 번들 스텝 안에 네 변종 `[ -s … ]` 검사가 있다. 「이름이 걸렸나」로 판정하면 공허하게 통과한다 —
> 이 문서가 §8.6 에서 스스로 적은 함정과 같은 자리다.

실제 그물:

| 무엇을 보는가 | PR | push(main) |
|---|---|---|
| 네 변종 **컴파일** — `boundary_step.dependOn(remote_watch_step)` (build.zig) | ✅ `check` 잡(ubuntu) | ✅ |
| 번들에 **싣고 비어 있지 않은가** — `for v in …; [ -s … ]` | ❌ | ✅ P5d |

그 컴파일 게이트는 ubuntu 러너에서 도는데, **리눅스 zig 가 macOS 타깃을 크로스 컴파일할 수 있는지
실측했다** — 된다(`zig 0.16.0` linux-aarch64 → `x86_64-macos`·`aarch64-macos` 둘 다 성공). 저장소가
이미 「ubuntu `check` 에서는 macOS 게이트가 컴파일조차 안 돼 20% 가 CI 밖에 있었다」를 겪었기 때문에
추측하지 않고 쟀다.

**PR 에 남은 구멍은 `cp -R` 한 줄이다** — 변종이 빌드되는 것은 PR 이 보고, 그것이 번들 안으로
들어갔는지만 main push 로 미뤄진다. 번들 잡을 PR 로 당기지 **않는다**: 그 잡이 PR 에서 빠진 것은
2026-08-31 사용자 결정이고(실제 프로세스를 띄우고 타이밍에 매달려 러너 부하에 취약하다 — hang 하나가
32 분을 태우고 무관한 PR 다섯을 연달아 취소시켰다), 남은 구멍의 크기가 그 대가에 못 미친다.
배달이 깨지면 main push 에서 몇 시간 안에 드러나고, 그때도 다른 PR 을 막지 않는다.

### 8.2 되먹임 — 우리 읽기가 감시자를 깨우고 있었다 (2026-09-03)

적대적 검증에서 **가장 큰 것**이 여기서 나왔다. 파일 둘을 고쳤는데 원격 git 명령이 **54 개**
(≈5~6 사이클) 돌았다. 감시자를 의심했지만 결백했다:

| 무엇 | 감시자를 깨운 횟수 |
|---|---|
| 파일 하나 쓰기 | 1 |
| 유휴 3 초 | 0 |
| **`git status` 한 번** | **2** ← 우리 **읽기**가 깨운다 |
| `worktree list` + `diff` | 0 |
| **`--no-optional-locks status`** | **0** |

즉 **읽기가 자기 자신을 부르고 있었다.** `git_command` 의 공통 옵션에 `--no-optional-locks` 를 넣어
끊었다 — 빠른 변경 둘이 **54 → 9**(정확히 한 사이클)가 됐고, 벌린 변경 둘은 18 그대로다.

**원격만의 문제가 아니었다.** maru3 에서 재 보니 일반 `status` 는 `.git/index` 를 다시 쓰고 플래그를
붙이면 안 쓴다 — 로컬 `.git` 감시자도 우리 읽기에 깨어 왔다. 원격에서 왕복이 비싸 눈에 보였을 뿐이다.

**어느 파일이 이벤트를 내는지도 갈랐다 (2026-09-04).** 이벤트가 실어 오는 «이름»을 찍는 진단 감시자를
제품과 같은 마스크로 띄우고 갓 더럽힌 저장소에서 재니:

| 무엇 | 이벤트 |
|---|---|
| 일반 `status` | `.git/index.lock` CREATE → MODIFY → MOVED_FROM, 이어서 `.git/index` MOVED_TO |
| `--no-optional-locks status` | 없음 |
| 진짜 파일 변경(대조군) | 작업트리 파일 MODIFY 하나 |

잠금 파일과 index 재기록은 **따로가 아니라 한 동작**이었다 — git 은 `index.lock` 에 쓴 뒤 그것을
`index` 위로 rename 한다(원자적 쓰기). 위 표의 「깨움 2」는 원시 이벤트 4 개가 read 배치 2 번으로
묶인 값이다. 앞서 「잠금 파일 쪽으로 보이나 못 잡았다」고 미룬 것을 이것이 대신한다.

**대가도 쟀다.** `core.untrackedCache` 는 **기본이 꺼짐**이라 이 플래그가 잃을 캐시가 애초에 없다.
억지로 켜 두고 5 만 파일(추적 2 만 · 미추적 3 만)에서 `status --untracked-files=all` 을 재도
일반 0.11~0.13 s vs 플래그 0.08~0.12 s — **불리하지 않고**(꺼진 기본값에서는 일반 쪽에 0.28 s
이상치가 있었다) 출력은 동일하다.

호환성도 쟀다: git **2.15.4** 도 이 플래그를 받고(대조군으로 가짜 플래그는 `exit 129`), stat 캐시를
더럽힌 상태에서 `status`·`diff`·`diff --cached`·`worktree list` 출력이 **전부 동일**하다.

|---|---|
| `pause()` 가 `.backoff` 도 지키는가 | ✅ **결함** — `.gave_up` 만 지키고 `.backoff` 는 무너뜨렸다. 그러면 재개가 switch 의 `.backoff` 갈래를 안 지나 `retry_at_ns` 를 건너뛴다 — 죽은 원격에 **도크 토글마다** ssh 자식이 뜬다. 3 회차와 **같은 부류**를 절반만 고쳤던 것이다 |
| 같은 호스트에서 **저장소만** 바뀌면 어떻게 되나 | ✅ **큰 결함** — 채널이 감시 루트를 기억하지 않아 **옛 저장소를 계속 봤다.** `git_repo_dest` 가 그대로라 `rememberGitRepoDest` 는 조기 반환한다 — 그 자리가 못 보는 축이다. 새 저장소의 변경은 영영 안 오고, 옛 저장소의 변경이 엉뚱한 새로고침을 건다 |
| `reapPid` 가 블로킹 `waitpid` 라 UI 를 세우는가 | ⚠️ **한계** — 아래 |
| 드레인 루프가 무한히 돌 수 있는가 | ❌ 파이프 버퍼(64 KiB)가 상한이라 512 바이트씩 최대 128 회다 |
| `.backoff` 인데 `started` 인 상태가 있는가 | ❌ `.backoff` 로 가는 세 경로(소켓 없음·기동 실패·EOF 뒤 `stopReporting`)가 모두 `started == false` 다 |

**`.gave_up` 은 호스트만의 성질이 아니다.** 6 회차가 그것도 바로잡았다 — `exit_unsupported`(감시 수단이
없다)는 호스트의 성질이지만 `exit_watch_limit`(디렉터리가 너무 많다)은 **저장소마다** 다르다. 그래서
저장소가 바뀌면 `stop()` 으로 판단째 놓는다: 큰 저장소에서 포기했다고 옆의 작은 저장소까지 포기할
이유가 없다.

**`reapPid` 실측.** `stopRemoteWatch` 는 UI 틱에서 블로킹 `waitpid` 를 친다. 같은 순서(파이프 둘 닫기 →
`SIGTERM` → `waitpid`)로 재니 **TERM 을 받는 자식은 6 ms**, **무시하는 자식은 영원히 안 끝난다**(10 초
상한에서 잘랐다). 우리 자식은 `env ssh …` 라 TERM 을 받으므로 앞쪽이고, `stopAgentEvents` 도 같은 모양
이다. **고치지 않았다** — 바꾸려면 그 규율을 두 채널에 함께 세워야 한다.

### 8.5 RW6 적대적 검증 (2026-09-04, 7~11 회차)

6 회차가 넣은 루트 기억을 다시 공격했다. **내 수정이 두 번 연속 반쪽이었다** — 7 회차가 6 회차의 구멍을
막으면서 새 구멍을 냈고, 8 회차가 그것을 잡았다.

| 공격 | 결과 |
|---|---|
| 주석과 가드가 같은 말을 하는가 | ✅ **결함** — 「버퍼를 넘으면 다음 tick 이 다시 띄운다」고 적었지만 가드가 `root_len != 0` 을 요구해 **그 경우 아예 안 걸렸다**. 무엇을 보는지 모르는 감시자가 조용히 남는다 |
| 그럼 `started` 로 물으면 되는가 | ✅ **결함**(7 회차의 대가, 8 회차가 잡았다) — `.gave_up`·`.backoff` 는 둘 다 `started == false` 라, **A 에서 포기하고 B 로 옮기면 B 가 영원히 감시되지 않는다** |
| `pause()` 가 루트 기억을 지워도 되는가 | ✅ **결함** — 지우면 「어느 저장소에 대한 판단인가」가 사라져, 도크를 껐다 켠 뒤 저장소를 바꾸면 같은 구멍이 난다 |
| `refreshGitStatus` 뒤에 쓰는 `dest` 가 UAF 인가 | ❌ 그 호출 사슬(`submitGitRead`·`remoteScmTarget`·`gitRepoRoot`·`markRepoStatusStale`)은 `git_repo_dest` 를 해제하지 않는다 |
| `stop()` 뒤 한 tick 을 버리는가 | ❌ 같은 tick 에 다시 띄운다(`.idle` → `!started` → spawn) |
| `Channel` 이 커져 스택을 위협하는가 | ⚠️ 1104 바이트다(루트 버퍼 1024). `@sizeOf(AppSession)` 게이트는 없고, `var session: AppSession = undefined` 를 쓰는 테스트들이 전체 게이트에서 돈다 |
| 창이 둘이면 감시자도 둘인가 | ⚠️ **그렇다** — 아래 |

**결론은 규율 하나다.** 「자식」과 「판단」과 「판단의 대상」은 **각각 다른 수명**을 산다.

| | 자식 | 판단(`phase`) | 대상(`root`) |
|---|---|---|---|
| `pause()` — 화면이 안 보인다 | 놓는다 | 지킨다 | 지킨다 |
| `stop()` — 대상이 바뀌었다 | 놓는다 | 지운다 | 지운다 |

셋을 한 함수에 뭉쳤던 것이 3·4·7·8 회차 결함의 **공통 원인**이다. 지금은 `releaseChild()` 가 자식만
지고, `pause`/`stop` 이 나머지를 각자 정한다.

**띄우기 «전» 에 답한다.** 추적할 수 없는 루트(`canTrack` 이 false)는 **아예 안 띄운다.** 띄워 놓고
무엇을 보는지 모르면 전환을 영영 못 보고, 그렇다고 매 tick 「달라졌다」로 읽으면 재기동 폭주다 —
띄우기 전에 거르는 것만이 두 함정을 다 피한다. 그 덕에 `started ⇒ 기억 있음` 이 보장된다.

**창마다 감시자가 하나씩 뜬다.** `AppSession` 은 창마다 만들어지므로(`app_session.zig` 「창마다 Swift가
`maru_macos_app_session_create` 를 부른다」) 창 둘이 같은 원격 저장소를 열면 그 원격에 감시자가 **둘**
뜬다. 고치려면 프로세스 전역 소유자가 필요한데, 같은 파일이 daemon 연결에서 이미 그 문제를 module-local
단일 소유로 우회하고 있다 — 그 모양이 후속의 자리다. **이 트랙에서 하지 않았다.**

### 8.6 감시자 «바이너리» 적대적 검증 (2026-09-04, 12~16 회차)

지금까지는 앱 쪽만 팼다. 이번엔 감시자 자체를 팼고, **가장 큰 것이 여기 있었다.**

| 공격 | 결과 |
|---|---|
| kqueue 가 파일 편집을 알리는가 | ✅ **가장 큰 결함 — 안 알린다** |
| 한도 보고가 살아 있는가 | ✅ **결함 — 죽은 코드였다** |
| 시작 뒤 생긴 디렉터리를 보는가 | ✅ **결함 — 안 본다** |
| 수집이 도중에 실패하면 어떻게 되나 | ✅ **결함 — 삼키고 절반을 「전부」로 알았다** |
| 내 판정자가 「정의」를 「호출」로 세는가 | ✅ **결함 — 그랬다**(3 회차에서 잡고도 반복) |

#### ① kqueue 는 파일 편집을 못 본다 (실측)

`EVFILT_VNODE` 를 **디렉터리**에 걸면 「그 디렉터리 자체」의 변화만 온다. 같은 디렉터리에서 하나씩:

| 동작 | 알림 |
|---|---|
| **파일 내용 수정(append)** | **0** |
| **파일 덮어쓰기** | **0** |
| `touch`(mtime) · `chmod` | **0** |
| 새 파일 · 삭제 · 이름 바꾸기 | 1 |

**가장 흔한 경우가 안 온다.** 그런데 만들기·지우기는 오므로 화면은 살아 있는 것처럼 보인다 — §6 이
「최악」이라 못 박은 **조용한 반쪽 감시**다.

⚠️ **다만 「내내」는 아니었다**(§11 을 쓰며 다시 쟀다). kqueue 는 디렉터리마다 fd 를 여는데, 옛 감시자를
maru3(디렉터리 **4,926 개**)에 붙이면 `ulimit -n` 이 **4096 이어도 `exit_watch_limit`(2)** 로 죽는다.
macOS 의 `launchctl limit maxfiles` 는 **256** 이다. 즉 **큰 저장소는 정직하게 죽었고**, 조용한 반쪽
감시는 **디렉터리가 한도 아래인 작은 저장소**에서만 일어났다. macOS 원격은 두 가지로 동시에 깨져
있었던 셈이다. §8.1 의 실물 검증이
이것을 놓친 이유도 여기 있다: git 명령은 `.git/index.lock` 을 **만들고 rename** 하므로 디렉터리 항목이
바뀌어 알림이 왔다.

**파일마다 fd 를 여는 길은 닫혀 있다** — maru3 하나가 파일 **29,694 개**(디렉터리 4,595 개)인데 리눅스의
흔한 `ulimit -Sn` 은 **1,024** 다. 제대로 하려면 macOS 는 FSEvents 가 필요하고 그건 CoreServices +
run loop 라 이 작은 바이너리의 모양이 아니다.

**그래서 지금은 `exit_unsupported` 다.** RW5 가 다시 안 띄우고 RW6 이 사용자에게 말하며, 화면은
포커스·새로고침으로 돌아간다. 되살릴 자리(`watchKqueueDirs`)는 남겼다 — **FSEvents 가 후속이다.**

#### ② 한도 보고가 죽은 코드였다

```zig
const max_dirs: usize = 65_536;
fn collect(...) { if (out.items.len >= max_dirs) return; ... }   // 정확히 그 수에서 멈춘다
if (dirs.items.len > max_dirs) return exitWith(exit_watch_limit); // 그래서 «절대» 참이 안 된다
```

`collect` 가 상한을 **넘지 않으므로** `>` 는 영원히 거짓이다. 상한을 넘는 저장소가 조용히 반쪽만
감시됐다. `>=` 로 고쳤다. **판정자는 `exit_watch_limit` 이라는 «문자열»만 세고 있어서 초록이었다** —
이제 비교식 자체를 센다.

#### ③ 시작 뒤 생긴 디렉터리를 안 봤다 (실측 · 리눅스)

| 동작 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 새 디렉터리 생성 | 1(부모에서) | 1 |
| **그 안에 파일 생성** | **0** | 1 |
| **그 안의 파일 수정** | **0** | 1 |
| 중첩된 새 디렉터리의 파일 | **0** | 1 |

`git checkout` 이 디렉터리를 만드는 브랜치로 옮기거나 새 모듈을 만들면 그 뒤 편집이 통째로 안 보였다.
이벤트의 **`IN_ISDIR` 비트 하나**만 보고 다시 무장한다 — 경로도 이름도 여전히 안 읽는다(계약 §2 가
막는 것은 「두 번째 파싱 계약」이고, 이 비트는 **이 프로세스 안의 질문**이다).

#### ④ 리눅스 갈래는 건재하다 (대조군)

파일 내용 수정 1 · `touch` 1 · 새 파일 1 · 새 디렉터리 1 — **inotify 는 제대로 온다.** ①이 kqueue
고유의 문제임을 이 대조군이 가른다.

**남긴 한계 둘.** ⑴ `showNotice` 는 `dismissMessageOverlays` + `cancelPendingClose` 를 부르므로 배경
이벤트가 사용자의 팔레트·find·확인 모달을 닫는다 — 저장소 전체(호출 117 곳)가 그렇고 에이전트 채널
선례도 같아서 이 PR 에서 예외를 만들지 않았다. ⑵ 원격 A → B → A 로 오가면 A 의 판단이 `stop()` 으로
풀려 다시 시도하고 배너도 다시 뜬다. 새 접속은 결과가 다를 수 있으니 의도한 동작이지만, 두 원격을
번갈아 보면 성가실 수 있다.

## 9. 터널(Tailscale)을 써도 이 트랙은 그대로다

**자주 나오는 질문이라 여기 적어 둔다**: mesh VPN 을 도입하면 이 감시자가 필요 없어지는가 — **아니다.**

[컨트롤 플레인 「닿기는 우리 몫이 아니다」](../control-plane.md)가 이미 선을 그어 두었다: Tailscale 은
**닿기(NAT·주소)** 를 주고 「셸·PTY·다중 채널」은 **안 준다 — 네트워크 계층이기 때문이다**. 파일은
여전히 저쪽 디스크에 있고, **그 변화를 알려면 저쪽에서 도는 무언가가 있어야 한다.** VPN 은 그것을
대신해 주지 않는다.

같은 문서가 「Tailscale SSH 를 써도 **maru 쪽은 여전히 평범한 SSH 라 코드가 그대로다**」라고 적는다.
ControlMaster·ControlPath 는 **클라이언트 옵션**이라 tailnet 위에서도 그대로 돈다 — §4 의 설치와 §RW3
의 채널이 바뀔 이유가 없다.

**달라지는 것 둘**(둘 다 좋은 쪽이지만, 어느 것도 이 트랙을 없애지 않는다):

- **RTT 가 줄 수 있다** — 직접 경로면 exec 당 왕복이 짧아져 폴백(폴링) 비용이 내려간다. 다만 0 이
  되지는 않으므로 네이티브 감시가 여전히 낫다.
- **연결이 안정적이다** — 로밍·네트워크 전환에서 control socket 이 덜 죽어 RW3 의 재시작·백오프 부담이
  준다. 죽는 경우 자체가 사라지지는 않으므로 **그 기계를 빼지는 못한다.**

⚠️ **유혹 하나를 미리 자른다**: 「터널 위로 원격 FS 를 마운트해 로컬에서 감시하자」. 네트워크
파일시스템은 **네이티브 감시가 조용히 실패하는** 대표적인 자리다(감시 라이브러리들이 그래서 폴링
폴백을 둔다). 결국 폴링으로 떨어지는데 그 폴링은 **로컬에서** 도니 §3 의 「exec 당 RTT」 문제가 그대로
돌아오고, 마운트 의존성만 늘어난다.

## 10. 비범위

- **맨 `ssh` 세션**: control socket 이 없어 채널을 못 연다(§6 「접속 방식 = `maru ssh` 전용」과 같은 이유).
- **원격이 결과를 스트림하는 형태**: 감시자가 git 을 돌려 파싱된 상태를 흘려보내면 exec 가 0 이 되지만,
  파싱 계약이 두 벌이 되고 버전 스큐가 생긴다. RW1~5 가 자리 잡은 뒤 재검토한다.
- **Windows 원격**: `maru ssh` 자체가 POSIX 원격을 전제한다.

### 11.1 왜 되살려야 하나

§8.6 ①이 macOS·BSD 갈래를 `exit_unsupported` 로 내렸다. 「어차피 안 되던 것을 안 된다고 말하게 했을
뿐」이지만, **macOS 원격은 이 트랙이 작정하고 넣은 대상**이다:

- `remote_watch_install.variantFromUname` 이 **`Darwin` 을 명시적으로 판별**한다.
- 빌드가 `macos_x86_64`·`macos_aarch64` 두 변종을 만든다.
- RW2b 는 **넷 중 하나라도 없으면 빌드를 세운다**.

그러니 「대상이 아니다」로 닫을 수 없다. 그리고 완전히 못 하던 것도 아니었다 — 실측에서 새 파일·삭제·
이름 바꾸기는 **왔다**(안 온 것은 편집이다). 지금은 그것마저 없다.

또 하나: **kqueue 는 fd 한도에도 걸린다.** maru3 는 디렉터리가 4,926 개인데 macOS 의
`launchctl limit maxfiles` 는 **256** 이다 — 옛 감시자를 붙이면 `ulimit -n` 4096 에서도
`exit_watch_limit` 이었다(실측). 즉 되살리는 길이 무엇이든 **fd 를 디렉터리 수만큼 쓰면 안 된다.**
폴링은 fd 를 거의 안 쓴다.

### 11.2 왜 FSEvents 가 아닌가

macOS 에서 「제대로」 하는 길은 FSEvents 다. 그런데 이 바이너리에는 안 맞는다:

- **크로스 컴파일이 깨진다.** 이 감시자는 **ubuntu 러너에서 macOS 타깃으로** 컴파일된다(§6.1 — CI 에
  남은 유일한 실제 그물). zig 가 싣는 macOS 것은 `libc/darwin/libSystem.tbd` **하나뿐**이고 Apple
  프레임워크는 없다(실측). CoreServices 를 링크하려면 macOS SDK 가 필요하다.
- **모양이 다르다.** FSEvents 는 CFRunLoop 위에 산다. 지금 감시자는 `poll` 하나로 stdin 과 이벤트를
  함께 기다리는 60 줄짜리다(§5 의 고아 방지가 거기 걸려 있다).
- 저장소에 FSEvents 코드가 있긴 하지만 **Swift 앱 호스트**(`MaruAppHost.swift`)의 것이라 독립
  바이너리에는 못 쓴다.

### 11.3 무엇을 폴링하나 — **도크가 읽는 것과 같은 범위**의 다이제스트

**파일을 훑지 않는다. 도크가 읽는 git 명령을 돌려 그 출력의 다이제스트만 비교한다.** 실측(maru3):

| 방법 | 한 번 비용 | 무엇을 놓치나 |
|---|---|---|
| 전체 파일 `stat` 걷기 (29,694 개) | **0.37 ~ 0.83 s** | `.gitignore` 를 안 따라 빌드 산출물까지 걷는다 |
| 추적 파일만 `stat` (1,661 개) | 0.02 s | **untracked 를 못 본다** — 화면이 보여 주는 바로 그것 |
| `status --porcelain=v2 --branch -uall` | 0.03 s | 브랜치·워크트리 목록 · 행의 `+N −M` |
| 위 셋(+`for-each-ref`·`worktree list`) | 0.04 s | **행의 `+N −M`** — §3 이 이미 잰 구멍 |
| **다섯 읽기를 합친 다이제스트** | **0.07 s** | — |

⚠️ **`status` 하나로는 좁다**(적대적 검증에서 잡았다). 도크는 `status` 말고도 `worktree_list` ·
`branches` · `log` 를 읽는다. `status --branch` 는 HEAD oid 와 ahead/behind 를 실어 오므로 **파일 수정 ·
스테이지 · 커밋 · amend · 브랜치 전환 · untracked 를 전부 잡지만**(실측), 다른 곳에서 만든 브랜치나
워크트리는 못 잡는다 — **그것들은 `.git/refs` 를 건드리므로 inotify 는 잡는다.** 즉 status 만 쓰면
폴링이 inotify 보다 **좁아진다.**

⚠️ **그리고 셋으로도 좁다** — §3 이 **이미 재서 적어 둔** 구멍 둘이 남는다(§11.4). RW7 의 첫 판이
그것을 그대로 밟았다: 이미 수정된 파일을 더 고치면 `status` 바이트가 **같아서** 행의 `+N −M` 이 조용히
낡았다(실측: 다이제스트 동일, `numstat` 은 `1 1` → `3 3`).

그래서 **다섯 가지**를 이어 붙인다:

```
git status --porcelain=v2 --branch --untracked-files=all      ← 필수(여기서 git·저장소 여부가 드러난다)
git for-each-ref --format='%(refname) %(objectname)'
git worktree list --porcelain
git diff --numstat --find-renames --no-ext-diff --no-textconv           ← 행의 +N −M (작업트리)
git diff --numstat --find-renames --no-ext-diff --no-textconv --cached  ← 행의 +N −M (스테이지)
```

⚠️ **머리 줄 `↑↓` 를 위한 `rev-list` 는 «없다» — 위가 이미 덮는다**(2026-09-05 실측). 한때 넣었다가
뺐다: `↑↓` 는 **어느 한쪽 ref 가 움직여야만** 바뀌고, 그러면 `for-each-ref` 의 oid 가 바뀐다.
`refs/` 밖인 분리 HEAD 는 `status --branch` 의 `branch.oid` 가 덮는다. 넣었던 근거(§3)는 **`status`
단독** 기준의 측정이었고, `for-each-ref` 가 들어온 뒤로는 **같은 사실을 두 번 묻는 것**이었다.
(도크가 숫자를 «그릴» 때는 여전히 클라이언트가 `rev-list` 를 돌린다 — 그쪽은 값이 필요하다.)

**첫 줄만 필수다.** 나머지는 실패해도 「실패했다」를 해시에 적고 계속한다 — `origin` 이 없는 저장소
에서 `rev-list` 가 실패한다고 감시가 통째로 멀면 안 된다(그 저장소가 오히려 흔하다). 실측으로
확인했다: origin 없는 저장소에서도 변경을 잡고 유휴 오탐은 0 이다.

다섯을 합쳐 한 번 **0.07 s**, 5 초 주기면 저쪽 코어의 **약 1.4%** 다. `rev-list` 를 빼서 준 값은
번갈아 3 회 재서 확인했다(60 초분: 여섯 0.93~0.98 s · 다섯 0.79~0.84 s — 일정하게 0.1 s 대). 한 번은
다섯 쪽이 더 나오기도 했는데 그것은 **부하 잡음**이었고, 그래서 번갈아 쟀다.

그리고 **도크가 열려 있는 동안만** 돈다 — 감추면 앱이 채널을 놓는다.

### 11.4 §3 을 어떻게 넘어서나 (⚠️ 처음 쓴 이 절은 틀렸다)

> **정정 (2026-09-04).** 이 절은 원래 「§3 이 버린 것은 **클라이언트 쪽** 폴링이고 근거는 exec 당
> 왕복이다」라고 적었다. **§3 을 잘못 읽은 것이다.** §3 이 잰 것은 **원격에서 도는 셸 폴링**이고,
> 근거도 왕복이 아니라 ⑴ 사용자 서버에서 영원히 도는 비용과 ⑵ **「폴링만으로는 틀린 화면이 나온다」**
> 였다. 그리고 RW7 의 첫 구현이 ⑵ 를 **그대로 밟았다**(아래).

**§3 의 ⑴ 비용**은 받아들인다. §3 이 잰 값은 2 초 주기에 CPU 1% 미만이었고, RW7 은 5 초 주기에
**1.6%**(6 읽기 · maru3 실측)다. **다만 도크가 열려 있는 동안만이다** — 도크를 감추면 앱이 채널을
놓으므로(`pumpRemoteWatch` 의 `pause`) 저쪽에서 아무것도 안 돈다. 「영원히」가 아니다.

**§3 의 ⑵ 틀린 화면은 «막았다».** §3 이 실측으로 적어 둔 구멍 둘을 다이제스트가 덮는다:

| §3 이 잰 구멍 | 왜 `status` 로는 못 보나 | 다이제스트가 덮는 법 |
|---|---|---|
| 이미 ` M` 인 파일을 더 고침 | `status` 바이트가 **같다**(실측: `numstat` 만 `1 1` → `3 3`) | `diff --numstat` 작업트리·스테이지 |
| fetch 로 `↑↓` 만 바뀜 | 도크의 `↑↓` 는 `origin/HEAD...HEAD` 기준인데 `branch.ab` 는 **upstream** 기준이다 | **`for-each-ref`** — ref 가 움직여야만 `↑↓` 가 바뀐다 |

> **두 번째 줄의 답이 바뀌었다 (2026-09-05).** 처음엔 `rev-list` 를 넣어 막았는데, 적대적 검증에서
> **군더더기**임이 드러났다 — §3 의 측정은 **`status` 단독** 기준이었고 `for-each-ref` 가 그 자리를
> 이미 진다. 실측으로 확인했다: 비기본 기준(`origin/feat`)만 움직여도, 분리 HEAD 를 옮겨도, `rev-list`
> 없이 다이제스트가 바뀐다. **내가 세운 근거를 내가 무너뜨린 자리다.**

⚠️ **RW7 의 첫 판은 이 표가 없었다.** `status` + `for-each-ref` + `worktree list` 만 봤고, 실측하니
「이미 수정된 파일을 더 고쳐도 다이제스트가 그대로」였다 — 행의 `+N −M` 이 조용히 낡는다. **§3 이 이미
적어 둔 경고를 읽고도 그대로 밟았다.**

### 11.4.1 §10 과는 충돌하지 않는다

**§10 이 뺀 것은 「원격이 파싱된 상태를 흘려보내는 형태」다** — 파싱 계약이 두 벌이 되기 때문이다.
여기서는 다이제스트가 **감시자 안에서만** 살고 밖으로 나가는 것은 여전히 `change` 한 줄이다. 계약은
하나 그대로다.

### 11.5 ⚠️ 굳히기 — 감시자가 git 을 돌리려면 «먼저» 필요한 것

감시자가 git 을 돌린다는 것은 **남의 저장소 config 가 시킨 프로그램을 우리가 실행할 수 있다**는 뜻이다.
클라이언트는 이미 `git_command.config_overrides` 로 그것을 막고 있는데, **그 목록에 구멍이 있다**
(실측 2026-09-04, git 2.50.1):

| 설정 | 언제 실행되나 | 상태 |
|---|---|---|
| `core.hooksPath` · `diff.external` · `core.pager` · `credential.helper` · `protocol.ext.allow` | 각자 | ✅ 이미 막혀 있었다 |
| `diff.<name>.textconv` | `diff` | ✅ 이미 막혀 있었다 — `build` 의 두 `diff` 가 모두 `--no-textconv` 를 건다 |
| `core.fsmonitor` | **`status` 마다** | ✅ **이번에 막았다**(`-c core.fsmonitor=`) |
| **`filter.<name>.clean` · `.smudge`** | **`status` · `diff` · `diff --numstat`** | ❌ **아직 열려 있다** |

⚠️ **`filter` 는 `diff` 만의 문제가 아니다**(실측). 크기가 **같은** 변경이면 `git status` 가 내용을
비교해야 해서 `clean` 필터를 **매번** 돌린다 — 크기가 다르면 안 돈다. 도크는 열려 있는 내내 `status`
를 돌리므로 이것이 가장 자주 지나는 문이다.

지금 목록으로 실측한 상태:

| 무엇 | 실행되는 프로그램 |
|---|---|
| 지금 목록 + `status`(크기 같은 변경) | **`filter.clean`** |
| 지금 목록 + `diff --no-ext-diff --no-textconv --numstat` | **`filter.clean`** |
| 거기에 `-c filter.<이름>.clean= -c ….smudge=` 까지 | 없음 |

**⚠️ 그런데 이 문은 닫으면 안 된다**(2026-09-04 실측 — 닫는 기계를 짓기 «직전» 에 잡았다).

| | 필터 그대로 | 필터를 끄면 |
|---|---|---|
| `status`(stat 캐시 무효) | 변경 없음(옳다) | **`1 .M … f.dat` — 가짜 수정** |
| `add` 뒤 index 내용 | `POINTER`(옳다) | **원본 그대로 — 저장소 오염** |

Git LFS 가 정확히 이 구조다. 끄면 추적 파일 전부가 수정된 것처럼 보이고, 그 상태로 스테이지하면
포인터 대신 **원본이 히스토리에 들어간다.** `--attr-source=<빈 트리>` 도 결과가 같다(속성이 없으면
필터도 안 걸린다) — **더 싼 우회가 아니라 같은 오답이다.**

**그래서 선을 이렇게 긋는다**(단일 출처는 `git_command.config_overrides` 의 주석):

- **막는다 — 없어도 답이 같은 것**: 훅 · pager · 외부 diff · 자격증명 helper · `ext::` 원격 ·
  `fsmonitor`. 전부 편의이거나 최적화라 꺼도 git 은 같은 답을 낸다.
- **막지 않는다 — 없으면 답이 틀리는 것**: `filter.*`. git 의 설계상 **실행이 곧 정답의 조건**이고,
  다른 git 클라이언트도 전부 그렇게 한다.

즉 §11.5 는 **RW7 의 전제가 아니다.** 감시자가 `status` 를 돌려도 사정은 클라이언트와 똑같다.

### 11.6 ⚠️ PATH — 감시자는 지금 처방을 안 지난다

`watch_script` 는 `exec "$HOME/.cache/maru/maru-remote-watch-1" "$1"` 뿐이라 `remote_shell.path_assign`
이 없다. 즉 감시자의 PATH 는 **비대화형 ssh 의 좁은 PATH**(`/usr/bin:/bin:/usr/sbin:/sbin`)다 — Homebrew
git·`$HOME/.local/bin` 은 안 보인다. 셸 대입이 `exec` 한 자식에게 전달되는 것은 확인했으므로(실측),
`watch_script` 앞에 `path_assign` 을 붙이면 된다. **RW7a 가 그것부터 한다.**

### 11.7 RW5 의 결정을 다시 연다

RW5 는 「**폴링으로 격하하지 않는다**」고 못 박았고, 근거는 「감시자의 한도 경로는 아무것도 감시하지
않고 끝나므로 **격하할 반쪽 상태가 없다**」였다. 그 근거는 **폴링이 반쪽일 때만** 성립한다.

§11.3 의 다이제스트는 반쪽이 아니다 — **도크가 읽는 것과 같은 범위**를 보기 때문이다(그래서 `status`
하나가 아니라 셋을 이어 붙인다). 그래서 RW7 이 들어오면:

- `exit_watch_limit`(디렉터리가 너무 많다)에서 **포기 대신 폴링으로 내려간다.**
- 잃는 것은 **지연**뿐이다(즉시 → 주기). 도크가 읽는 범위 안에서 놓치는 변경은 없다.
- 리눅스는 inotify 를 그대로 쓴다. 폴링은 **못 하는 자리**에서만 돈다.

### 11.8 단계

- **RW7a — PATH 와 굳히기**: `watch_script` 에 `path_assign` 을 붙이고, `core.fsmonitor` 를
  `config_overrides` 에 넣는다. 감시자가 쓸 `-c` 목록의 **단일 출처를 L2 에 둔다**(지금은 앱만 쓴다) —
  두 벌이 되면 한쪽만 굳는다.
- **RW7b — 폴링 갈래**: 감시자에 「루트에서 `git status` 를 돌려 다이제스트를 비교하고, 바뀌었으면
  `change` 한 줄」을 넣는다. stdin 은 **같은 대기**에 그대로 둔다(§5 — `poll` 에 타임아웃을 주는 모양).
  git 이 없거나 저장소가 아니면 `exit_unsupported`.
- **RW7c — macOS·BSD 를 폴링으로 돌린다**: `watchKqueue` 의 `exit_unsupported` 를 폴링 진입으로
  바꾼다. 디렉터리 kqueue 는 **얹지 않는다** — 이유가 둘이다. ⑴ **fd 한도**: 디렉터리마다 fd 를 쓰면
  maru3 크기(4,926 개)에서 macOS 의 256 한도에 즉시 걸린다(실측). ⑵ 만들기·지우기만 빨리 알아 봤자
  폴링이 어차피 잡는데, 두 경로가 같은 사실을 각자 들면 §8.5 가 정리한 「수명이 다른 것을 한 곳에
  뭉치는」 함정으로 되돌아간다.
- **RW7d — 한도에서 격하 (완료)**: `exit_watch_limit` 을 포기 대신 폴링으로 내린다. **판 2 부터
  감시자는 그 코드로 나가지 않는다** — 최초 무장 실패 · 재무장 중 한도 초과 · 재무장 실패 세 자리
  모두 폴링으로 간다. 상수는 남긴다(원격에 판 1 바이너리가 돌면 그쪽은 여전히 그 코드로 나가고,
  앱은 그것을 영구 실패로 읽어야 한다 — 판이 갈리면 다음 설치에서 바뀐다).
  - 실물 실측: 컨테이너에서 `max_user_watches` 를 **1** 로 낮추니 판 1 은 죽고 판 2 는 **살아서
    파일 수정을 잡았다.**
  - **배너는 안 뜬다.** 격하가 감시자 안에서 일어나 앱이 모르기 때문이고, 그것으로 충분하다 —
    §6 의 규율이 막는 것은 「반쪽을 최신인 척」인데 폴링은 반쪽이 아니다.

### 11.9 열린 질문 — **쟀고, 답했다** (2026-09-05 실측 · 2026-09-06 판정)

넷 다 「재야 한다」로 남겨 두었던 것을 실측했다. **주기 5 초는 큰 저장소·콜드 캐시에서 틀렸다.**

측정 조건: Apple M4 Max(16 코어) · APFS SSD · git 2.50.1 · 감시자와 **같은 다섯 읽기·같은 경화 인자**
(`--no-optional-locks -c core.fsmonitor=` …). 각 5 회 중앙값, 워밍업 2 회. 다이제스트는 원격에서 도는
계산이므로 네트워크는 이 값에 안 들어간다 — 저쪽 CPU 비용의 모형으로 맞다.

#### ① 큰 저장소의 상한 — **선형이 아니다**

`watchPoll` 은 다이제스트를 루프 «안에서 동기로» 돌린다(`waited_ns = 0` → `digest(...)`) — 그래서
겹치지 않고, **실효 주기는 `5 초 + 비용`** 이며 한 코어 점유는 `비용 / (5 초 + 비용)` 이다.

| 추적 파일 | 다이제스트 한 번 | 실효 주기 | 한 코어 점유 |
|---|---|---|---|
| 1,690 (maru3) | **0.057 s** | 5.06 s | 1.1 % |
| 50,000 | **0.169 s** | 5.17 s | 3.3 % |
| 400,000 | **2.677 s** | **7.68 s** | **34.9 %** |

50 k → 400 k 는 파일이 8 배인데 비용은 **16 배**다. 40 만 파일에서 무엇이 먹는지도 갈랐다:

| 읽기 | 40 만에서 |
|---|---|
| `status --porcelain=v2 --branch --untracked-files=all` | **1.423 s** |
| `diff --numstat --find-renames …` | **1.187 s** |
| `for-each-ref` · `worktree list` · `diff --cached` | 합쳐 0.042 s |

둘이 전부다. `--untracked-files=all` 은 §3 이 이미 비싸다고 적어 둔 자리이고, `diff --numstat` 은 §11.3
이 「도크가 읽는 것과 같은 범위」를 위해 **일부러** 넣은 것이다 — 즉 싸게 만들려면 계약을 줄여야 한다.

#### ② 주기 5 초가 맞나 — **작은·중간 저장소에만 맞다**

①의 표가 답이다. 점유를 한 코어의 5 % 로 묶으려면 `비용/(주기+비용) = 0.05`, 즉 **주기 = 비용 × 19** 다 —
maru3 **1.1 s** · 5 만 **3.2 s** · 40 만 **51 s**. 5 초 고정은 40 만에서 열 배 과하고, maru3·5 만에서는
오히려 **더 자주 돌아도 된다.** 사용자가 느끼는 지연(최대 한 주기)과의 균형은 비용이 정해지면 따라오므로,
남는 결정은 「상한을 몇 %로 둘 것인가」 하나다.

#### ③ 콜드 캐시 — **거의 공짜다**(로컬 저장매체 기준)

> ⚠️ **처음 쟀을 때 틀린 결론을 냈다.** 디스크 이미지를 뗐다 붙여 「콜드」를 만들었더니 5 만 파일에서
> 6.502 s vs 0.177 s, **36.8 배**가 나왔다. 그걸 콜드 캐시 비용으로 읽고 「첫 회가 주기보다 길다」고
> 적었는데, **그건 이미지 계층의 비용이었다.** 볼륨을 떼도 sparsebundle 백킹 파일은 호스트 페이지
> 캐시에 남는다 — 즉 그 측정에 「캐시가 비었다」는 성질이 없었다.

`sudo purge` 로 **시스템 페이지 캐시를 실제로 비우고** 내장 APFS 의 40 만 파일 저장소를 쟀다.

| 40 만 파일 | 콜드(purge 직후) | 바로 다음(따뜻함) | 배수 |
|---|---|---|---|
| `status --untracked-files=all` | **1.558 s** | — | |
| `diff --numstat` | **1.191 s** | — | |
| 합계 | **2.859 s** | 2.631 s | **1.1 ×** |

**로컬 SSD 에서는 콜드가 사실상 공짜다.** 비용은 IO 가 아니라 40 만 번의 `stat` — CPU 에 묶여 있어서
캐시가 비어 있든 아니든 같다. 「원격이 방금 부팅했으면 훨씬 비싸다」는 걱정은 **로컬 저장매체에 한해
근거가 없다.**

**남는 것은 네트워크 파일시스템이다.** NFS·SMB 위의 저장소는 `stat` 마다 왕복이 붙어 성질이 아예
다르다 — 그건 **못 쟀다**(마운트에 root 가 필요하다). git 의 fsmonitor 도 network-mounted
filesystem 은 지원하지 않는다고 man 이 명시하므로, 그 경우는 여전히 열려 있다.

#### ④ 다이제스트가 안정적인가 — **안정적이다**

걱정했던 세 축을 전부 쳤다. 흔들림 **0**.

| 축 | 결과 |
|---|---|
| 같은 판 5 회 반복 | 해시 동일 |
| git **2.50.1 vs 2.55.0** — maru3 · 5 만 · 40 만 세 저장소 | **세 쌍 모두 동일** |
| `for-each-ref` 순서 (브랜치·태그를 뒤섞어 생성) | refname 사전순으로 정렬 — 생성 순서와 무관 |
| `worktree list` 경로 표기 (`/tmp` 로 접근 vs `/private/tmp` 로 접근) | 언제나 실경로(`/private/tmp/…`)로 정규화 — 동일 |

「안 바뀌었는데 바뀌었다」는 이 네 축에서는 안 난다. 이 항목은 **닫는다.**

#### ⑤ 폴링 중에도 stdin EOF 를 즉시 받나 — **쟀다**(앞선 회차)

**쟀다**(§11 머리의 표) — 250 ms tick 으로 세므로 정상·git 멈춤·git 출력 흘림 세
경우 모두 **60 ms 안**이다. 자식을 띄우는 갈래라 §5 를 «새로» 지켜야 했고, 첫 판이 그것을 놓쳐
고아를 만들었다(17 회차).

#### 이 절이 남기는 후속

**남는 것은 ① 하나이고, 그것도 «안 되는 것»이 아니라 «비싼 것»이다.** ③ 은 로컬 저장매체에서
공짜로 판명됐고 ④ 는 닫혔다. 즉 「고정 주기가 틀렸다」의 근거는 **큰 저장소 하나**다 — 40 만
파일에서 한 코어의 34.9 % 를 남의 서버에서 계속 쓴다. 그 아래 판정 문단이 범위와 착수 조건을 적는다.

고치는 길은 둘이고 서로 배타적이지 않다.

1. **적응형 주기.** 감시자가 자기 비용을 재서 주기를 그 배수로 잡는다(비용 × 19 ≈ 한 코어 5 %).
   큰 저장소는 저절로 느려지고, 작은 저장소는 지금보다 **더 빨라진다**(maru3 는 1.1 s 로도 충분하다).
2. **`-c core.fsmonitor=true`.** §11.10 이 잰다 — 같은 40 만에서 `status` 1.423 → 0.272 s,
   `diff --numstat` 1.187 → 0.037 s 로 **약 8 배**다. 지금은 이 자리를 통째로 끄고 있다.

「돌고 있으면 다음 tick 을 건너뛴다」는 **필요 없다** — `watchPoll` 이 이미 직렬이라 겹치지 않는다
(처음엔 필요하다고 적었다가 루프를 읽고 지웠다).

#### 판정 — **결함이 아니라 튜닝이다. 지금은 안 한다** (사용자 결정 2026-09-06)

⚠️ **이 절을 「열린 질문」으로만 읽으면 «감시가 안 되는 구멍»으로 오해한다.** 실제로 한 번
그렇게 읽혔고(2026-09-06, 다음 작업을 고르는 자리에서), 사용자가 「fsmonitor 안 띄워도 지금 되긴
하지 않냐」고 물어 바로잡혔다. **된다.** 감시자는 지금 제품에서 제 일을 하고, 아래는 그 위의
비용 최적화다.

그 오해를 안 만들도록 아픈 범위를 좁혀 적는다:

- **폴링 갈래를 타는 원격만** 해당한다 — macOS·BSD, 또는 리눅스에서 `max_user_watches` 를 소진한
  경우다. **리눅스 원격은 inotify** 라 폴링 자체를 안 한다(④ 대조군이 그것을 가른다).
- 그 위에서도 **저장소가 커야** 아프다: 1,690 파일 **1.1 %** · 5 만 **3.3 %** — 무시할 수준이고,
  34.9 % 는 **40 만 파일**의 값이다. 즉 아픈 조합은 「macOS 원격 + 초대형 저장소」 하나다.
- 그 조합의 **신고는 없다**. 실측이 먼저 나온 것이지 증상이 먼저 나온 것이 아니다.

**둘 중 하나만 하면 된다 — 그리고 그건 ⑴ 이다.** ⑴ 적응형 주기는 남의 서버에 **아무것도 안**
**띄우고**, 작은 저장소를 오히려 **더 빠르게** 만들며, 정할 것이 「상한 몇 %」 하나다. ⑵ fsmonitor 는
남의 서버에 **데몬을 띄우는 새 권한면**이고(§11.10 이 그 값어치를 재 두었다), NFS·SMB 에서는 git 이
지원하지 않아 **가장 아플 수 있는 자리를 어차피 못 푼다**(③ 이 남긴 그 한계).

**여는 조건**: 「macOS 원격에서 감시자가 서버를 먹는다」는 신고가 오거나, 그 조합이 실사용에
보이면 그때 **⑴ 만** 연다. 그 전에 계약을 안 바꾼다 — 지금 값(5 초 고정)은 신고된 적 없는
극단을 위해 바꿀 이유가 없고, 바꾸면 잘 도는 다수의 동작이 함께 움직인다.

### 11.10 fsmonitor — 우리가 끈 것이 «업계가 이 문제를 푸는 방법»이었다 (2026-09-05 실측)

「큰 저장소에서 `status` 가 느리다」의 표준 답은 **fsmonitor** 다 — Watchman 이거나, git 2.37+ 의
내장 데몬(`git fsmonitor--daemon`). `O(파일 수)` 를 `O(변경 수)` 로 바꾼다. maru 는 이것을
`-c core.fsmonitor=` 로 **끈다**(§git_command 의 경화 목록).

#### 얼마나 듣나 — 8 배 (40 만 파일)

| 읽기 | 끔(지금) | 켬(내장 데몬) |
|---|---|---|
| `status --porcelain=v2 --branch --untracked-files=all` | 1.423 s | **0.272 s** |
| `diff --numstat --find-renames …` | 1.187 s | **0.037 s** |
| 합계 | 2.709 s | **≈0.35 s** |

한 코어 점유가 34.9 % → **약 6.6 %** 가 된다.

#### 끈 근거는 «문자열 형»에만 맞다

경화 주석은 「`core.fsmonitor` 는 저장소 config 가 시킨 프로그램이라 `status` 마다 돈다」고 적는다.
맞다 — 실측으로 `status` 한 번에 그 스크립트가 **2 회** 실행된다. 그런데 `core.fsmonitor=true` 는
**boolean 형**이라 저장소가 지정한 프로그램이 아니라 **git 자기 데몬**을 띄운다. 주입을 막는 힘은 같다:

| 명령줄 | 저장소가 심은 스크립트 실행 |
|---|---|
| (덮지 않음) | **2 회** |
| `-c core.fsmonitor=` (지금) | 0 |
| `-c core.fsmonitor=true` | **0** |

즉 지금 정책은 **실행 벡터와 함께 최적화까지 버렸다.** `true` 로 덮으면 둘 다 얻는다.

#### 공짜는 아니다 — 착수 전에 정할 것

- **남의 기계에 장수 데몬이 뜬다.** 감시자 프로세스 하나와 무게가 다르다. 이건 제품 결정이다.
- **네트워크 마운트 파일시스템은 지원하지 않는다**(man 이 명시). §11.9 ③ 이 열어 둔 그 경우를
  fsmonitor 로는 못 구한다.
- **읽기 경로에도 같은 판단을 할지는 별개다.** 여기 잰 것은 감시자의 다이제스트다. 도크의 읽기
  (`git_command.config_overrides`)까지 함께 바꿀지는 같은 자리에서 다시 봐야 한다.

#### 판정 — **안 켠다** (사용자 결정 2026-09-06)

§11.9 의 판정이 이 절의 답도 정한다: 폴링 비용은 **아픈 조합이 하나뿐인** 최적화 대상이고,
그것을 푸는 데 **fsmonitor 는 필요 없다**. 적응형 주기가 남의 서버에 아무것도 안 띄우고 같은
문제를 풀며, fsmonitor 는 **장수 데몬이라는 새 권한면**을 여는 데다 NFS·SMB 에서는 git 이
지원조차 안 해 가장 아플 수 있는 자리를 못 푼다.

**이 절은 「그때 이만큼 빨라진다」는 값을 재 둔 것으로 남긴다** — 버리지 않는 이유는, 적응형
주기로도 모자란 날이 오면 그 판단이 여기서 다시 시작하기 때문이다. 그날의 조건은 §11.9 의
「여는 조건」과 같고, 그때도 **⑵ 는 ⑴ 을 해 보고 나서** 본다.
