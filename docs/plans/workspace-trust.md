# 워크스페이스 신뢰와 도구 환경 구현 계획

상태: WT1·WT2a 완료, WT2b~WT5 미착수(WT2 는 둘로 나눴다 — 아래). 2026-10-07 사용자 승인(「순서대로 진행해주시죠」). 계약은 [tooling §8.1](../editor-surface-tooling.md)·§8.2a 가 소유하고, 이 문서는 지금 코드와 그 계약 사이의 차이와 그것을 메우는 단계를 소유한다.

## 왜 — 지금 코드와 계약의 차이

언어 서버 1단(§8.2a, 2026-09-17)은 §8.1 의 「trusted workspace 확인」만 옮겼고 나머지 항목은 말없이 빠졌다(결정 기록 없음 — 커밋·PR·세션 기록 전수 확인). 그 뒤 적대적 검증 여러 회차(2026-10-07)로 드러난 차이:

- **모달이 사실과 달랐다**(WT1 에서 고침). 「이 저장소에서 ‹서버› 를 실행할까요?」라고 서버 하나를 물었지만 답은 root 단위로 기억되어 그 root 의 다른 서버·나중에 바뀌는 후보까지 묻지 않고 뜬다. 「설정을 읽고 빌드를 실행할 수 있습니다」는 영향이 저장소 안에 머무는 것처럼 읽혔다 — 실제로는 사용자 권한으로 격리 없이 저장소 밖 파일·네트워크·ssh-agent 에 닿는다(§8.1 의 「sandbox 하지 못하는 한계를 확인 UX 에 명시」 미이행).
- **신뢰가 창마다 따로 캐시됐다**(WT2a 에서 고침). 신뢰 표는 세션(창)마다 한 번 읽고 자기 캐시만 고쳤다. 창 A 의 결정을 창 B 가 몰랐고, 두 창이 같은 root 를 동시에 물을 수 있었다.
- **신뢰 키가 경로 문자열이었다**(WT2a 에서 고침). `/tmp`↔`/private/tmp`·심링크·대소문자 차이로 같은 저장소가 다른 키가 되어 거부가 안 먹었다. 같은 경로에 다른 저장소를 다시 받으면 신뢰가 이어진다(이것은 남는다 — 「결정 대기」). 홈에 dotfiles `.git` 이 있으면 홈 아래 자기 `.git` 이 없는 폴더의 파일은 전부 root=홈이 된다(`file_tree_backend.zig` `projectRootForFile` — 가장 가까운 `.git`).
- **서버 환경이 앱 환경 그대로다.** §8.1 의 환경 계약(사용자 셸 환경에서 내부·세션 변수를 뺀 것 — 옛 §8.1 은 「최소화한 environment」였다)과 다르다. Finder 로 띄운 앱의 PATH 는 짧아 `~/.cargo/bin`·`~/go/bin`·nvm 아래 서버를 못 찾고, 그때는 신뢰를 묻기도 전에 「없음 — 설치」로 끝난다.

## 결정 (2026-10-07)

- **신뢰는 저장소 단위 하나**로 LSP·포매터·린터·작업을 덮는다. 서버별로 묻지 않는다(위험의 단위는 「저장소가 정한 코드가 내 권한으로 돈다」이고, 서버별 허락은 묻는 횟수만 늘린다). VS Code Workspace Trust·JetBrains Trusted Projects·Zed Worktree Trust 와 같은 단위다.
- **신뢰 전에는 언어 서버를 띄우지 않는다**(지금 동작 그대로). 서버마다 위험이 다르지만(clangd < gopls < pyright < rust-analyzer ≈ zls ≈ typescript-language-server — rust-analyzer 「모든 코드를 신뢰한다고 가정」, clangd 는 `--query-driver` 없이는 컴파일러를 실행하지 않는다, pyright 는 PATH 의 `python` 을 실행한다 — 각 서버의 공식 문서) 서버별 예외는 유지 부담 때문에 두지 않는다.
- **서버 환경은 최소화하지 않고 사용자 셸 환경을 따른다** — 내부·세션 변수를 빼고 PATH 는 절대 경로 항목만. 서버는 사용자 권한으로 돌아 환경을 줄여도 `~` 아래 파일을 그대로 읽으므로 최소화의 보안 이득은 작고, 허용 목록은 기본값을 바꾼 툴체인(`RUSTUP_HOME`·`GOPATH`·`VIRTUAL_ENV`·프록시·인증서)을 깨뜨린다. 진짜 격리가 필요해지면 OS 샌드박스의 일이다.
- 위에 맞춰 §8.1 을 고쳤다(도구별 allowlist → 저장소 단위 신뢰, 최소화한 environment → 위 규칙, 셸은 환경을 담는 데만).

## 결정 대기

- **같은 자리에 다시 받은 저장소**(WT2a 뒤): 신뢰 키는 (볼륨, 실제 경로)라 지우고 같은 자리에 다시 받은 저장소는 같은 키다 — 신뢰가 이어진다. 저장소 신원(디렉터리 inode·첫 커밋 등)으로 가를지는, 다시 받은 것을 「다른 저장소」로 볼지의 결정이다.
- **셸 설정 자동 실행을 끄는 스위치**(WT3 전): §8.1 이 환경을 「사용자 셸 환경」으로 정했으므로 해석기는 사용자 셸 설정(`.zprofile`·`.zshrc`)을 실행한다(VS Code·JetBrains 와 같다). 남은 것은 그것을 끄는 스위치(끄면 앱 환경 + 통상 설치 위치)를 둘지다.

## 단계

### WT1 — 모달을 정직하게 (완료)

- 신뢰 확인을 여러 줄 **신뢰 시트**로 보인다: 무엇을 신뢰하는지(이 저장소의 언어 서버 전체 + root 경로, 중간 생략), 무엇이 일어날 수 있는지(사용자 권한·격리 없음·저장소 밖 파일·네트워크·ssh-agent·빌드 스크립트·툴체인 다운로드), 실제 실행 파일은 저장소 설정(shim)이 고를 수 있다는 것. 지금 확인 모달은 512 B 한 덩어리라 넘치면 경고 문장부터 잘린다.
- 버튼은 허용/거부 그대로, 결정의 저장(root 단위)도 그대로다.
- **종료:** 신뢰 시트 판정자(좁은 창·두 언어에서 경고 문장이 잘리지 않는다·root 경로 중간 생략), Lab 골든, 제품 경로 판정자(LSPB2 의 모달 단언).

WT2 는 둘로 나눴다(2026-10-07) — 저장소를 옮기는 일(WT2a, 동작은 그대로)과 묻지 않을 root 를 정하는 일(WT2b, **동작 변경**)은 검토의 축이 달라서다.

### WT2a — 앱 전역 신뢰 저장소 (완료)

- 신뢰 표를 **앱 전체에 하나**로 올리고 세대 번호를 둔다(`session/lsp/trust.zig` `Store`, `editor/trust_store.zig` — 표는 그 파일 밖에서 못 고친다). 각 창은 pump 첫머리에서 세대를 비교해(`lsp.zig` `applyTrustChanges`) 결정을 제 클라이언트에 적용한다(`applyDecision` — 이 창의 답도 같은 길): 거부면 떠 있는(뜨는 중 포함) 서버를 내리고 그 진단을 걷어 `.denied`, 허용이면 기다리던·묻던·거부됐던 클라이언트를 **잠든 채로** 둔다 — 열린 문서가 있으면 같은 pump 가 깨워 띄우고, 문서가 닫힌 클라이언트는 띄우지 않는다(ABI 변경 없음 — 퀵 터미널까지 덮인다).
- **한 저장소는 한 창만, 지금 보고 있는 창(key 창)이 묻는다** — 앱 전역 「묻는 자리」(`Store.claim`). 다른 창은 「허락 대기」로 그 답을 기다린다. 묻던 창이 포커스를 잃으면(다른 창으로 갔다·퀵 터미널이 숨었다) 모달을 답 없이 내리고 자리를 내놓아, 포커스가 간 창이 묻는다 — 질문이 사용자를 따라간다(뒤쪽 창·숨은 퀵 터미널이 자리를 붙잡지 않는다). 다른 오버레이가 모달을 덮으면 그 창이 다시 묻고, 창이 닫히면 자리를 놓는다. 「key 창」은 세션의 `window_focused` 이고, Swift 가 tick 마다 그 창의 실제 key 상태와 맞춘다(앱이 활성일 때, 바뀔 때만 — `reconcileSessionFocus`). 예전에는 key 알림만 받아서 세션이 생기기 전에 지나간 알림(새 창·복원)과 delegate 가 없는 quick 패널이 빠졌다 — 복원된 창 둘이 다 「key」라 `maru sessions list` 가 `focused` 를 둘 냈다(실측, 고친 뒤 클릭한 창 하나만·앱이 뒤로 가면 없음).
- **상태는 셋:** 신뢰 / 거부(기억) / 미정. 「거부됨 — 다시 묻기」는 기억된 거부를 두고 **그 창에서** 다시 묻는다 — 같은 저장소의 그 창 클라이언트가 함께 기다리고(문서가 닫힌 것도 띄우지 않는다), 답은 그 전부에 서며, 누른 뒤에 다른 창에서 답이 서면 — 같은 결정이 다시 선 것이어도(`Store.touch`) — 그것이 답이다(같은 질문을 또 하지 않는다). 모달이 답 없이 닫히면 다음 gate 가 또 묻는다. 「잊기」(미정으로 되돌리기)는 WT4.
- **신뢰 키와 작업 root 를 나눈다.** 키는 (볼륨, 실제 경로) — 한 fd 에서 `F_GETPATH`(std 의 realpath 와 같은 길: 심링크·`/tmp`·대소문자를 푼다)와 볼륨 UUID(`fgetattrlist` — 다시 붙여도 같고, 같은 자리에 붙은 다른 디스크는 다르다)를 함께 얻는다. UUID 가 없는 파일 시스템(devfs·일부 네트워크)은 장치 번호로 물러선다(다시 붙이면 바뀌어 다시 묻는다). 작업 root(서버의 rootUri·표시)는 연 이름 그대로 둬 URI 대조가 흔들리지 않게. root 가 심링크면 그 대상이 바뀔 수 있으므로 **묻기·띄우기 직전에 키를 다시 푼다**(옛 대상을 물으면 답이 옛 대상에 기록된다). 키는 root 의 것이라, 한 클라이언트가 root 의 새 키를 보면 그 root 의 이 창 클라이언트를 모두 새 키로 맞추고 옛 키로 떠 있던 서버를 내린다(`rekeyRoot`). 키를 못 구하면(root 가 사라졌다·못 연다) 묻지도 띄우지도 않고 「실패 — 다시」로 선다.
- **신뢰 부여는 사용자의 답으로만**(confirm 의 수락 — 클릭·Enter·Y). 표에 쓰는 자리는 `recordTrust` 하나, 허용으로 답하는 자리는 chrome 의 confirm 수락 하나이고 ABI·컨트롤 플레인은 신뢰를 건드리지 않는다. 판정자 하니스 스위치(`auto_trust_answer`)는 테스트 빌드에서만 읽히고, 판정자 전용 주입 함수는 제품 빌드에서 부르면 컴파일되지 않는다.
- **저장 위치**는 상태 디렉터리 `~/Library/Application Support/maru/lsp-trust`(줄마다 `allow\t‹볼륨 16진›\t‹실제 경로›`, 마지막 줄이 이긴다, 파일은 소유자만 읽는다 — 디렉터리는 작업 공간·웹 데이터와 함께 쓰는 자리라 권한을 건드리지 않는다). **개행으로 끝나지 않은 줄은 읽지 않는다** — 덧붙이다 끊긴 줄은 경로가 잘려 부모 폴더의 결정으로 읽힐 수 있다. 다음 덧붙이기는 그 줄을 `\t\n` 으로 닫아(칸이 남아 어느 형식으로도 안 읽힌다) 붙지 않게 한다. 판정자 주입(`trust_store.setDirForTest` — `backup.zig` 와 같은 꼴)이 없으면 테스트 빌드는 파일을 읽지도 쓰지도 않는다(옛 자리도 주입한 것만 — 세션의 설정 경로로 구하면 사용자의 옛 파일을 지울 수 있다).
- **이관:** 옛 자리(설정 파일 옆 `lsp-trust` — 기본 `~/.config/maru/lsp-trust`)는 **새 파일이 아직 없을 때만** 이관한다: root 마다 마지막 줄 → 실제 키로 → 같은 키에 갈리면 거부가 이김 → 키를 못 구하는 root(사라졌거나 지금 못 여는 경로)는 버림(다시 묻는다) → 새 자리에 통째로 쓴 뒤에야 옛 파일을 지운다(못 쓰면 남겨 다음 실행이 다시 이관한다 — 그래서 그 실행은 새 자리에 덧붙이지도 않는다: 덧붙인 한 줄이 새 파일을 만들면 다음 실행이 이관이 끝난 것으로 본다). 새 파일이 있으면 이관은 끝난 것이다(옛 파일이 남아 있어도 다시 합치지 않는다 — 합치면 옛 거부가 그 뒤의 「다시 묻기」 허용을 매번 덮는다. 두 자리가 같은 파일인 경우도 여기서 끝난다). 새 파일을 못 읽으면(권한·1 MB 초과) 이관도 덮어쓰기도 덧붙이기도 하지 않는다 — 이번 실행은 메모리로 쓴다.
- **판정자:** LST1~LST12(표·줄 형식·끊긴 줄·이관·묻는 자리·키 정규화·볼륨·주입·권한·못 읽는 새 표), LSPB20(두 창 — 한쪽 결정이 다른 쪽에 서고, 다른 데서 온 거부가 떠 있는·뜨는 중인 서버를 내리고 진단을 걷고, 다른 데서 온 허용이 거부된 창을 띄운다), LSPB21(key 창만 묻기 — 토스트가 덮어도 그 창이 다시 묻고, 포커스를 따라가고, 창 닫힘이 자리를 놓고, 두 창의 다시 묻기에서 한쪽 답(허용·거부)이 다른 쪽의 답이다), LSPB22(심링크 이름으로 열어도 한 번 묻고 실제 경로 한 줄, 묻는 사이 심링크가 바뀌면 그 이름은 띄우지 않고 새 저장소를 묻고, 그 뒤의 다시 묻기는 지금의 대상을 묻는다), LSPB23(신뢰 부여 자리의 수), LSPB24(다시 묻기가 문서 닫힌 서버를 띄우지 않는다), LSPB25(키를 못 구하면 「실패」), LSPB26(root 의 새 키가 옛 키로 떠 있던 같은 root 서버를 내린다), LSPB27(옛 키를 묻던 모달은 답 없이 내리고 새 대상을 묻는다).
- **남는 것:** 같은 자리에 다시 받은 저장소는 같은 키다(신뢰가 이어진다 — 「결정 대기」). 떠 있는 서버의 root 는 다음 열기·띄우기·묻기 전까지 다시 풀지 않는다 — 심링크 대상이 바뀐 뒤 그 root 에 아무 일도 없으면 그 서버는 옛 허용으로 돈다. 앱이 뒤에 있으면(key 창이 없으면) 묻지 않고 기다린다 — 돌아오면 묻는다. 한 번도 활성화되지 않은 실행(백그라운드로 띄운 앱·CI 스모크)은 포커스를 맞추지 않아 창마다 기본값(「key」)이다 — 그동안은 먼저 tick 한 창이 묻는다. 「허락 대기」는 이 창·다른 root·다른 창의 모달을 가르지 않는다. 옛 자리 이관은 처음 한 번 메인 스레드에서 옛 root 마다 디렉터리를 연다(끊긴 네트워크 마운트에서 멈출 수 있다). 신뢰 파일은 덧붙이기만 해서 줄어들지 않는다(이관 때 한 번 통째로 쓴다).

### WT2b — 신뢰할 수 없는 root

- `~` 와 그 조상·`/` 는 묻지 않고 거부한다. 홈 dotfiles `.git` 때문이면 상태바에 이유를 보인다.
- 가장 가까운 `.git` 이 없어 파일의 부모 폴더가 root 가 되는 파일은 묻지 않고 LSP 없이 연다(**동작 변경** — 지금은 그 폴더를 root 로 묻고 신뢰하면 서버가 뜬다).
- **종료:** `~`·조상·`/` 거부 판정자, `.git` 없는 파일 판정자, 상태바 이유 문구(두 언어).

### WT3 — 도구 환경 해석기 (결정 대기 해소 뒤)

- **비동기**로 사용자 셸 환경을 담는다 — 서버 띄우기가 메인 tick 안이라 셸을 기다리면 앱이 선다. 워커 스레드에서 fork+exec(`std.process.run` 은 앱 Io 에서 못 쓴다), 결과는 세대가 붙은 값으로 메인에 넘긴다.
- **언제:** 서버 표에 있는 문서가 처음 열릴 때. 그동안은 「환경 준비 중」 — 담기 전에는 「없음」을 판정하지 않는다(지금은 앱의 짧은 PATH 로 먼저 「없음」을 정해 신뢰를 묻지도 않는다).
- **어떻게:** 사용자 셸(`getpwuid`)에 `-l -i`(셸별 표 — csh·tcsh 는 `-l` 을 빼고 `-i -c`(`-l` 은 단독으로만 쓸 수 있다), fish 는 `-i` 없음, nushell 별도), `/usr/bin/env -0` 을 별도 fd 로, cwd=`$HOME`(저장소의 direnv·mise 훅이 신뢰 전에 돌지 않게), 입력 없음, 터미널에서 떼어 냄, 표식 변수, zsh 자동 업데이트 끄기. 끝 판정은 셸 프로세스 종료(EOF 를 기다리면 셸이 띄운 데몬이 fd 를 쥐어 시한까지 간다), 출력은 시작·끝 표식으로 검증. 터미널에서 띄웠어도 건너뛰지 않는다(물려받은 환경에는 다른 저장소의 direnv·venv 가 섞인다 — 실패했을 때의 대체로만 쓴다). 시한을 넘기면 그룹째 끝내고 앱 환경으로 대신하며 상태바에 「환경을 못 읽음」. 「다시 읽기」 명령. 판정자에서는 진짜 사용자 셸을 띄우지 않는다.
- **위생:** maru 내부·터미널 세션 변수(`TERM*`·`TMUX*`·`PWD`·`SHLVL`·`ZDOTDIR` 등)를 지운다 — PTY 쪽 목록과 **같은 목록 하나**를 공유한다. `NODE_OPTIONS`·`PYTHONPATH` 같은 런타임 옵션은 지우지 않는다(사용자가 일부러 넣은 값이고 막을 위협이 없다). PATH 는 상대 경로·빈 항목(`::` = 현재 폴더)을 버리고, 저장소 아래 항목은 신뢰 전 실행 파일 해석과 경고에만 걸러 낸다. 비밀 이름 패턴으로 지우지 않는다 — 사용자 제외 목록과 「전달되는 변수 이름 보기」를 둔다.
- **종료:** 순수 판정자(셸별 argv·`env -0` 파싱·위생·PATH 정리), 가짜 셸로 시한·실패·대체·표식 검증, 「준비 중」 동안 「없음」을 안 내는지, Finder 실행 실측(`~/.cargo/bin` 의 rust-analyzer 가 잡힌다).

### WT4 — 신뢰 관리

- 목록·철회·잊기. **컨트롤 플레인·CLI 는 조회·철회만** 한다(부여는 없다 — 에이전트가 신뢰를 주지 못하게, WT2a 의 「신뢰 부여는 사용자의 답으로만」). 신뢰 목록은 config 가 아니므로 설정 화면의 단일 출처 규칙(파일이 SSOT)에 예외 절을 두거나 명령 팔레트·상태바 메뉴로 관리한다.
- 철회하면 모든 창에서 그 root 의 서버를 **유예 없이** 그룹째 종료하고 기다리던 요청·진단·해석 캐시를 지운다. 대화상자에 되돌릴 수 없는 것을 적는다(이미 쓴 캐시, 적용된 포맷, setsid 로 빠져나간 데몬).
- **종료:** 철회 판정자(모든 창·즉시 종료·캐시 무효화), 제품 앱 실측.

### WT5 — 저장소별 환경과 실행 파일 표시

- direnv·mise: 기본 끔. 신뢰 뒤에, 그 도구 자체의 허락(`direnv allow`·`mise trust`)이 있을 때만. shim 은 이 설정과 무관하게 저장소 버전 파일을 따른다는 것을 보인다.
- 실행 파일: 신뢰 전에는 경로 조회만(shim 이면 「shim(mise) — 실제 버전은 저장소가 정함」), 신뢰 뒤 `rustup which`·`mise which`(cwd=root) 로 실제 경로 + 서버가 알려 준 버전(없을 수 있다).

## 범위 밖 (별도 결정 거리)

- **git 이 신뢰 전에 저장소가 정한 명령을 실행할 수 있다.** 도크의 git 조회는 위험 설정 일부를 막지만 파일 필터(`filter.*`)는 정확성 때문에 허용한다(`session/git_command.zig` `config_overrides`) — `.git` 이 든 압축 파일을 열면 신뢰 전에 돈다. VS Code·JetBrains 는 신뢰 전에 git 을 끈다.
- 원격(SSH) 저장소의 신뢰 키(호스트 키 지문·원격 사용자·원격 실제 경로)와 원격 쪽 환경 해석, devcontainer, 조상 디렉터리 설정 파일 지문(신뢰 뒤 새로 생기면 다시 묻기), 서버별 제한 모드, 감사 로그, 조직 정책.
