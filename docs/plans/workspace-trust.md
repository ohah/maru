# 워크스페이스 신뢰와 도구 환경 구현 계획

상태: WT1·WT2a·WT2b·WT3a·WT3b·WT4a·WT4b·WT5a·WT5b-1 완료(WT3b 는 Finder 실측 대기), WT5b-2·3 미착수(WT2·WT3·WT4 는 둘로, WT5 는 WT5a 와 WT5b-1~3 으로 나눴다 — 아래). WT3 의 「결정 대기」 때문에 WT4 를 먼저 했다(2026-10-08 사용자 결정). 2026-10-07 사용자 승인(「순서대로 진행해주시죠」). 계약은 [tooling §8.1](../editor-surface-tooling.md)·§8.2a 가 소유하고, 이 문서는 지금 코드와 그 계약 사이의 차이와 그것을 메우는 단계를 소유한다.

## 왜 — 지금 코드와 계약의 차이

언어 서버 1단(§8.2a, 2026-09-17)은 §8.1 의 「trusted workspace 확인」만 옮겼고 나머지 항목은 말없이 빠졌다(결정 기록 없음 — 커밋·PR·세션 기록 전수 확인). 그 뒤 적대적 검증 여러 회차(2026-10-07)로 드러난 차이:

- **모달이 사실과 달랐다**(WT1 에서 고침). 「이 저장소에서 ‹서버› 를 실행할까요?」라고 서버 하나를 물었지만 답은 root 단위로 기억되어 그 root 의 다른 서버·나중에 바뀌는 후보까지 묻지 않고 뜬다. 「설정을 읽고 빌드를 실행할 수 있습니다」는 영향이 저장소 안에 머무는 것처럼 읽혔다 — 실제로는 사용자 권한으로 격리 없이 저장소 밖 파일·네트워크·ssh-agent 에 닿는다(§8.1 의 「sandbox 하지 못하는 한계를 확인 UX 에 명시」 미이행).
- **신뢰가 창마다 따로 캐시됐다**(WT2a 에서 고침). 신뢰 표는 세션(창)마다 한 번 읽고 자기 캐시만 고쳤다. 창 A 의 결정을 창 B 가 몰랐고, 두 창이 같은 root 를 동시에 물을 수 있었다.
- **신뢰 키가 경로 문자열이었다**(WT2a 에서 고침). `/tmp`↔`/private/tmp`·심링크·대소문자 차이로 같은 저장소가 다른 키가 되어 거부가 안 먹었다. 같은 경로에 다른 저장소를 다시 받으면 신뢰가 이어진다(이것은 남는다 — 「결정 대기」). 홈에 dotfiles `.git` 이 있으면 홈 아래 자기 `.git` 이 없는 폴더의 파일은 전부 root=홈이 된다(`file_tree_backend.zig` `projectRootForFile` — 가장 가까운 `.git`) — WT2b 에서 고침(홈 root 는 묻지 않는다).
- **서버 환경이 앱 환경 그대로다.** §8.1 의 환경 계약(사용자 셸 환경에서 내부·세션 변수를 뺀 것 — 옛 §8.1 은 「최소화한 environment」였다)과 다르다. Finder 로 띄운 앱의 PATH 는 짧아 `~/.cargo/bin`·`~/go/bin`·nvm 아래 서버를 못 찾고, 그때는 신뢰를 묻기도 전에 「없음 — 설치」로 끝난다.

## 결정 (2026-10-07)

- **신뢰는 저장소 단위 하나**로 LSP·포매터·린터·작업을 덮는다. 서버별로 묻지 않는다(위험의 단위는 「저장소가 정한 코드가 내 권한으로 돈다」이고, 서버별 허락은 묻는 횟수만 늘린다). VS Code Workspace Trust·JetBrains Trusted Projects·Zed Worktree Trust 와 같은 단위다.
- **신뢰 전에는 언어 서버를 띄우지 않는다**(지금 동작 그대로). 서버마다 위험이 다르지만(clangd < gopls < pyright < rust-analyzer ≈ zls ≈ typescript-language-server — rust-analyzer 「모든 코드를 신뢰한다고 가정」, clangd 는 `--query-driver` 없이는 컴파일러를 실행하지 않는다, pyright 는 PATH 의 `python` 을 실행한다 — 각 서버의 공식 문서) 서버별 예외는 유지 부담 때문에 두지 않는다.
- **서버 환경은 최소화하지 않고 사용자 셸 환경을 따른다** — 내부·세션 변수를 빼고 PATH 는 절대 경로 항목만. 서버는 사용자 권한으로 돌아 환경을 줄여도 `~` 아래 파일을 그대로 읽으므로 최소화의 보안 이득은 작고, 허용 목록은 기본값을 바꾼 툴체인(`RUSTUP_HOME`·`GOPATH`·`VIRTUAL_ENV`·프록시·인증서)을 깨뜨린다. 진짜 격리가 필요해지면 OS 샌드박스의 일이다.
- 위에 맞춰 §8.1 을 고쳤다(도구별 allowlist → 저장소 단위 신뢰, 최소화한 environment → 위 규칙, 셸은 환경을 담는 데만).
- **셸 설정 자동 실행을 끄는 스위치를 둔다**(2026-10-08 사용자 결정): 해석기는 사용자 셸 설정(`.zprofile`·`.zshrc`)을 실행한다(VS Code·JetBrains 와 같다). 끄면(`lsp.shell-environment = false`) 셸을 띄우지 않고 앱 환경(위생을 거친 것 — 아래) + 통상 설치 위치로 찾는다. 기본은 켬.

## 결정 대기

- **같은 자리에 다시 받은 저장소**(WT2a 뒤): 신뢰 키는 (볼륨, 실제 경로)라 지우고 같은 자리에 다시 받은 저장소는 같은 키다 — 신뢰가 이어진다. 저장소 신원(디렉터리 inode·첫 커밋 등)으로 가를지는, 다시 받은 것을 「다른 저장소」로 볼지의 결정이다.

## 단계

### WT1 — 모달을 정직하게 (완료)

- 신뢰 확인을 여러 줄 **신뢰 시트**로 보인다: 무엇을 신뢰하는지(이 저장소의 언어 서버 전체 + root 경로, 중간 생략), 무엇이 일어날 수 있는지(사용자 권한·격리 없음·저장소 밖 파일·네트워크·ssh-agent·빌드 스크립트·툴체인 다운로드), 실제 실행 파일은 저장소 설정(shim)이 고를 수 있다는 것(WT5a 에서 늘 보이던 이 일반 경고를 실행 파일 경로 + 감지한 출처 경고로 바꿨다 — 아래 WT5a 결정). 지금 확인 모달은 512 B 한 덩어리라 넘치면 경고 문장부터 잘린다.
- 버튼은 허용/거부 그대로, 결정의 저장(root 단위)도 그대로다.
- **종료:** 신뢰 시트 판정자(좁은 창·두 언어에서 경고 문장이 잘리지 않는다·root 경로 중간 생략), Lab 골든, 제품 경로 판정자(LSPB2 의 모달 단언).
- **후속 — 시트의 기본값**(2026-10-08 사용자 결정, WT4a 적대적 검증에서 나옴): 시트는 문서를 열고 서버를 찾은 뒤 **비동기로** 뜬다. 처음 포커스가 「허용」이고 `Y` 가 허용 단축키라 편집기에 치던 Enter·`y` 가 그대로 허락이 될 수 있었다. 이제 시트는 `confirm.State.guardAsync` 로 뜬다:
  - 처음 포커스는 「거부」 — 치던 Enter 는 거부로 기억되고(보수적인 쪽) 상태바에서 다시 물을 수 있다.
  - 글자 단축키를 받지 않는다(표식 `[Y]`/`[N]` 도 안 그린다) — 치던 글자는 답이 아니다.
  - 화살표는 돌지 않는다 — 처음엔 ←/→ 가 두 버튼 사이를 돌아 `)` 를 → 로 건너뛰고 Enter 로 줄을 바꾸는 흔한 입력도 「허용」에 닿았다(적대적 검증 1회차). 이제 → 는 거부에 머물고 「허용」은 ← 로만 닿는다.
  - ← 로 「허용」에 옮긴 뒤의 ⏎ 는 바로 허락하지 않고 한 번 더 묻는다(포커스는 다시 거부). 그 사이 다른 키(글자·⌫·↑↓·Tab·⌘←·⌥←·⇧← 등)는 포커스와 다시 묻던 것을 처음으로 되돌린다 — 그 입력이 두 줄 이어지면 재확인을 통과하던 구멍(적대적 검증 2회차).
  - **다시 묻는 문장에서의 키보드 허용은 ⌘⏎ 하나다**(문장이 그 키를 말한다) — 맨 ⏎ 로 받으면 「← ⏎ ← ⏎」(줄을 두 번 나누는 편집, TUI 의 예/아니오를 두 번 고르는 입력)가 그대로 허락이 됐다(적대적 검증 3회차, 사용자 결정 2026-10-08).
  - 클릭은 그대로 허용이다. 한계: 시트가 뜬 순간 작업영역 가운데를 누르던 클릭이 버튼에 떨어질 수 있다(패널 밖 클릭은 거부로 기억된다).
  - 다른 길(뜬 직후 잠깐 키를 막기)은 시간에 기대는 판정이라 택하지 않았다. 같은 위험이 있던 **브라우저 권한 확인**(에이전트 요청으로 비동기로 뜬다)에도 같은 보호를 걸었다(사용자 결정 2026-10-08). 판정자 LSPB37(실제 키 경로)·권한 확인 판정자·confirm 컴포넌트 판정자, Lab 골든(신뢰 시트 둘·권한 확인).

WT2 는 둘로 나눴다(2026-10-07) — 저장소를 옮기는 일(WT2a, 동작은 그대로)과 묻지 않을 root 를 정하는 일(WT2b, **동작 변경**)은 검토의 축이 달라서다.

### WT2a — 앱 전역 신뢰 저장소 (완료)

- 신뢰 표를 **앱 전체에 하나**로 올리고 세대 번호를 둔다(`session/lsp/trust.zig` `Store`, `editor/trust_store.zig` — 표는 그 파일 밖에서 못 고친다). 각 창은 pump 첫머리에서 세대를 비교해(`lsp.zig` `applyTrustChanges`) 결정을 제 클라이언트에 적용한다(`applyDecision` — 이 창의 답도 같은 길): 거부면 떠 있는(뜨는 중 포함) 서버를 내리고 그 진단을 걷어 `.denied`, 허용이면 기다리던·묻던·거부됐던 클라이언트를 **잠든 채로** 둔다 — 열린 문서가 있으면 같은 pump 가 깨워 띄우고, 문서가 닫힌 클라이언트는 띄우지 않는다(ABI 변경 없음 — 퀵 터미널까지 덮인다).
- **한 저장소는 한 창만, 지금 보고 있는 창(key 창)이 묻는다** — 앱 전역 「묻는 자리」(`Store.claim`). 다른 창은 「허락 대기」로 그 답을 기다린다. 묻던 창이 포커스를 잃으면(다른 창으로 갔다·퀵 터미널이 숨었다) 모달을 답 없이 내리고 자리를 내놓아, 포커스가 간 창이 묻는다 — 질문이 사용자를 따라간다(뒤쪽 창·숨은 퀵 터미널이 자리를 붙잡지 않는다). 다른 오버레이가 모달을 덮으면 그 창이 다시 묻고, 창이 닫히면 자리를 놓는다. 「key 창」은 세션의 `window_focused` 이고, Swift 가 tick 마다 그 창의 실제 key 상태와 맞춘다(앱이 활성일 때, 바뀔 때만 — `reconcileSessionFocus`). 예전에는 key 알림만 받아서 세션이 생기기 전에 지나간 알림(새 창·복원)과 delegate 가 없는 quick 패널이 빠졌다 — 복원된 창 둘이 다 「key」라 `maru sessions list` 가 `focused` 를 둘 냈다(실측, 고친 뒤 클릭한 창 하나만·앱이 뒤로 가면 없음).
- **상태는 셋:** 신뢰 / 거부(기억) / 미정. 「거부됨 — 다시 묻기」는 기억된 거부를 두고 **그 창에서** 다시 묻는다 — 같은 저장소의 그 창 클라이언트가 함께 기다리고(문서가 닫힌 것도 띄우지 않는다), 답은 그 전부에 서며, 누른 뒤에 다른 창에서 답이 서면 — 같은 결정이 다시 선 것이어도(`Store.touch`) — 그것이 답이다(같은 질문을 또 하지 않는다). 모달이 답 없이 닫히면 다음 gate 가 또 묻는다. 「잊기」(미정으로 되돌리기)는 WT4.
- **신뢰 키와 작업 root 를 나눈다.** 키는 (볼륨, 실제 경로) — 한 fd 에서 `F_GETPATH`(std 의 realpath 와 같은 길: 심링크·`/tmp`·대소문자를 푼다)와 볼륨 UUID(`fgetattrlist` — 다시 붙여도 같고, 같은 자리에 붙은 다른 디스크는 다르다)를 함께 얻는다. UUID 가 없는 파일 시스템(devfs·일부 네트워크)은 장치 번호로 물러선다(다시 붙이면 바뀌어 다시 묻는다). 작업 root(서버의 rootUri·표시)는 연 이름 그대로 둬 URI 대조가 흔들리지 않게. root 가 심링크면 그 대상이 바뀔 수 있으므로 **묻기·띄우기 직전에 키를 다시 푼다**(옛 대상을 물으면 답이 옛 대상에 기록된다). 키는 root 의 것이라, 한 클라이언트가 root 의 새 키를 보면 그 root 의 이 창 클라이언트를 모두 새 키로 맞추고 옛 키로 떠 있던 서버를 내린다(`rekeyRoot`). 키를 못 구하면(root 가 사라졌다·못 연다) 묻지도 띄우지도 않고 「실패 — 다시」로 선다.
- **신뢰 부여는 사용자의 답으로만**(신뢰 시트의 「허용」 — 클릭, 또는 ← 로 고른 뒤 ⏎ 로 다시 묻게 하고 ⌘⏎; WT1 후속). 표에 쓰는 자리는 `recordTrust` 하나, 허용으로 답하는 자리는 chrome 의 confirm 수락 하나이고 ABI·컨트롤 플레인은 신뢰를 건드리지 않는다. 판정자 하니스 스위치(`auto_trust_answer`)는 테스트 빌드에서만 읽히고, 판정자 전용 주입 함수는 제품 빌드에서 부르면 컴파일되지 않는다.
- **저장 위치**는 상태 디렉터리 `~/Library/Application Support/maru/lsp-trust`(줄마다 `allow\t‹볼륨 16진›\t‹실제 경로›`, 마지막 줄이 이긴다, 파일은 소유자만 읽는다 — 디렉터리는 작업 공간·웹 데이터와 함께 쓰는 자리라 권한을 건드리지 않는다). **개행으로 끝나지 않은 줄은 읽지 않는다** — 덧붙이다 끊긴 줄은 경로가 잘려 부모 폴더의 결정으로 읽힐 수 있다. 다음 덧붙이기는 그 줄을 `\t\n` 으로 닫아(칸이 남아 어느 형식으로도 안 읽힌다) 붙지 않게 한다. 판정자 주입(`trust_store.setDirForTest` — `backup.zig` 와 같은 꼴)이 없으면 테스트 빌드는 파일을 읽지도 쓰지도 않는다(옛 자리도 주입한 것만 — 세션의 설정 경로로 구하면 사용자의 옛 파일을 지울 수 있다).
- **이관:** 옛 자리(설정 파일 옆 `lsp-trust` — 기본 `~/.config/maru/lsp-trust`)는 **새 파일이 아직 없을 때만** 이관한다: root 마다 마지막 줄 → 실제 키로 → 같은 키에 갈리면 거부가 이김 → 키를 못 구하는 root(사라졌거나 지금 못 여는 경로)는 버림(다시 묻는다) → 새 자리에 통째로 쓴 뒤에야 옛 파일을 지운다(못 쓰면 남겨 다음 실행이 다시 이관한다 — 그래서 그 실행은 새 자리에 덧붙이지도 않는다: 덧붙인 한 줄이 새 파일을 만들면 다음 실행이 이관이 끝난 것으로 본다). 새 파일이 있으면 이관은 끝난 것이다(옛 파일이 남아 있어도 다시 합치지 않는다 — 합치면 옛 거부가 그 뒤의 「다시 묻기」 허용을 매번 덮는다. 두 자리가 같은 파일인 경우도 여기서 끝난다). 새 파일을 못 읽으면(권한·1 MB 초과) 이관도 덮어쓰기도 덧붙이기도 하지 않는다 — 이번 실행은 메모리로 쓴다.
- **판정자:** LST1~LST12(표·줄 형식·끊긴 줄·이관·묻는 자리·키 정규화·볼륨·주입·권한·못 읽는 새 표), LSPB20(두 창 — 한쪽 결정이 다른 쪽에 서고, 다른 데서 온 거부가 떠 있는·뜨는 중인 서버를 내리고 진단을 걷고, 다른 데서 온 허용이 거부된 창을 띄운다), LSPB21(key 창만 묻기 — 토스트가 덮어도 그 창이 다시 묻고, 포커스를 따라가고, 창 닫힘이 자리를 놓고, 두 창의 다시 묻기에서 한쪽 답(허용·거부)이 다른 쪽의 답이다), LSPB22(심링크 이름으로 열어도 한 번 묻고 실제 경로 한 줄, 묻는 사이 심링크가 바뀌면 그 이름은 띄우지 않고 새 저장소를 묻고, 그 뒤의 다시 묻기는 지금의 대상을 묻는다), LSPB23(신뢰 부여 자리의 수), LSPB24(다시 묻기가 문서 닫힌 서버를 띄우지 않는다), LSPB25(키를 못 구하면 「실패」), LSPB26(root 의 새 키가 옛 키로 떠 있던 같은 root 서버를 내린다), LSPB27(옛 키를 묻던 모달은 답 없이 내리고 새 대상을 묻는다).
- **남는 것:** 같은 자리에 다시 받은 저장소는 같은 키다(신뢰가 이어진다 — 「결정 대기」). 떠 있는 서버의 root 는 다음 열기·띄우기·묻기 전까지 다시 풀지 않는다 — 심링크 대상이 바뀐 뒤 그 root 에 아무 일도 없으면 그 서버는 옛 허용으로 돈다. 앱이 뒤에 있으면(key 창이 없으면) 묻지 않고 기다린다 — 돌아오면 묻는다. 한 번도 활성화되지 않은 실행(백그라운드로 띄운 앱·CI 스모크)은 포커스를 맞추지 않아 창마다 기본값(「key」)이다 — 그동안은 먼저 tick 한 창이 묻는다. 「허락 대기」는 이 창·다른 root·다른 창의 모달을 가르지 않는다. 옛 자리 이관은 처음 한 번 메인 스레드에서 옛 root 마다 디렉터리를 연다(끊긴 네트워크 마운트에서 멈출 수 있다). 신뢰 파일은 덧붙이기만 해서 줄어들지 않는다(이관 때 한 번 통째로 쓴다).

### WT2b — 신뢰할 수 없는 root (완료)

- root 가 홈이거나 그 위(`/` 포함 — 실제 경로로 비교, 경로 성분 경계)면 묻지도 띄우지도 않는다 — 상태바 「‹서버› 꺼짐 — 홈 폴더는 저장소로 보지 않음」(`Phase.home_root`). 홈 dotfiles `.git` 이 홈 아래 모든 파일의 root 가 되는 경우다.
- root 에 `.git` 이 없으면(가장 가까운 `.git` 이 없어 파일의 부모 폴더가 root 가 됐다) 묻지도 띄우지도 않는다 — 「‹서버› 꺼짐 — git 저장소 밖」(`Phase.outside_repo`). **동작 변경**: 예전에는 그 폴더를 root 로 묻고 허용하면 서버가 떴다.
- 판정은 신뢰 키를 구한 직후, 서버 찾기보다 **먼저** — 서버가 없어도 「설치」가 아니라 이유를 보인다(어차피 안 띄운다). 묻는 root 로 판정되면 클라이언트에 굳힌다(기다리는 창이 tick 마다 파일 시스템을 다시 보지 않게) — root 의 키가 바뀌면(심링크 대상이 바뀌었다, WT2a `rekeyRoot`) 판정도 다시 한다. 거부된 root 는 상태바를 누르면 **root 부터** 다시 푼다(상위 폴더에서 `git init` 했어도 풀린다); 그동안 같은 root 의 클라이언트는 띄우지 않는다(문서가 닫힌 것까지). 표에는 아무것도 적지 않는다(묻지 않았으니 답도 없다). HOME 을 못 구하면 홈 판정은 건너뛰고 묻는다(`.git` 은 있으니 보통 묻기). root 의 키가 바뀌면 옛 대상의 진단과 연 문서를 서버가 이미 죽어 있어도 걷는다(새 대상이 거부·묻지 않는 root 여도 옛 밑줄이 남지 않게). 판정을 아직 안 거친 클라이언트에는 어느 창의 결정도 적용하지 않는다(gate 가 표를 직접 읽는다 — 묻지 않는 root 가 이관된 옛 거부로, 키가 바뀐 클라이언트가 이 창의 거부로 「거부됨」에 굳어 다른 창의 허용을 못 받는 일이 없게). 「꺼짐」을 누르면 굳힌 키도 버려 다시 푼다(심링크 대상이 홈에서 저장소로 바뀌었을 수 있다).
- **남는 것:** 같은 root 에 떠 있는 서버와 거부된 서버가 섞인 채(그 사이 `.git` 을 지웠다) 「꺼짐」을 누르면 root 가 바뀐 문서가 떠 있던 서버에 열린 채 남는다(didClose 없이 — 그 서버는 유휴 종료되지 않고, 그 서버의 진단도 「꺼짐」인 문서에 계속 선다). 새 클라이언트를 만든 직후 메모리 할당이 연달아 실패하면 판정을 건너뛰고 뜰 수 있다(WT2a 부터 있던 구멍 — 막으려면 새 클라이언트를 「대기」로 시작하게 하는 방어가 필요하다).
- **판정자:** LSPB28(홈 아래 파일·저장소 밖 파일 — 서버가 없어도 이유가 먼저, 서버가 있어도 안 띄움, 표 그대로, 누르면 문서 닫힌 서버는 안 띄우고, root 부터 다시 봐 그 폴더나 상위 폴더의 `git init` 뒤에는 묻는다), LSPB28a(조상 판정 — 경로 성분 경계), LSPB29(다시 띄울 때 심링크가 저장소 밖을 가리키면 묻지 않고 「저장소 밖」·옛 진단 걷힘), LSPB30(키가 바뀌어 판정을 기다리는 클라이언트에는 이 창의 거부를 세우지 않는다 — 다른 창의 허용 뒤 다시 열면 뜬다), LSPB31(「꺼짐」을 누르면 키도 다시 풀어 홈에서 저장소로 바뀐 심링크를 묻는다), LSPB10(상태바 문구 phase × 언어 — 새 단계 둘 포함).

### WT3 — 도구 환경 해석기

WT3 는 둘로 나눈다(2026-10-08) — 무엇을 실행하고 무엇을 넘길지의 순수 계산(WT3a)과, 그것을 실제로 돌려 서버 찾기·띄우기에 잇는 일(WT3b).

- **비동기**로 사용자 셸 환경을 담는다 — 서버 띄우기가 메인 tick 안이라 셸을 기다리면 앱이 선다. 워커 스레드에서 fork+exec(`std.process.run` 은 앱 Io 에서 못 쓴다), 결과는 세대가 붙은 값으로 메인에 넘긴다.
- **언제:** 서버 표에 있는 문서가 신뢰 범위 안에서 처음 열릴 때(WT3b 「언제」). 그동안은 「셸 환경 읽는 중」 — 담기 전에는 「없음」을 판정하지 않는다(WT3 이전에는 앱의 짧은 PATH 로 먼저 「없음」을 정해 신뢰를 묻지도 않았다).
- **어떻게:** 사용자 셸(`getpwuid`)에 `-l -i`(셸별 표 — csh·tcsh 는 `-l` 을 빼고 `-i -c`(`-l` 은 단독으로만 쓸 수 있다), fish 는 `-l -i -c` — 처음엔 `-i` 를 빼려 했으나 fish 에도 있고 빼면 `config.fish` 의 대화형 블록을 건너뛴다(WT3a 적대적 검증), nushell 등은 지원 안 함), `/usr/bin/env -0` 을 비공개 임시 파일로(WT3a — fd 로 받지 않는 이유), cwd=`$HOME`(저장소의 direnv·mise 훅이 신뢰 전에 돌지 않게), 입력 없음, 터미널에서 떼어 냄, 표식 변수, zsh 자동 업데이트 끄기. 끝 판정은 셸 프로세스 종료(파이프의 EOF 를 기다리면 셸이 띄운 데몬이 fd 를 쥐어 시한까지 간다 — 파일이라 그 문제가 없다), 출력은 시작·끝 표식으로 검증. 터미널에서 띄웠어도 건너뛰지 않는다(물려받은 환경에는 다른 저장소의 direnv·venv 가 섞인다 — 실패했을 때의 대체로만 쓴다). 시한을 넘기면 그룹째 끝내고 (담아 둔 셸 환경이 없으면) 앱 환경으로 대신하며, 그 환경에서 서버를 못 찾으면 상태바가 「셸 환경을 못 읽음」이라고 말한다(WT3b). 「다시 읽기」 명령. 판정자에서는 진짜 사용자 셸을 띄우지 않는다.
- **위생:** 터미널 세션 변수(PTY 쪽과 **같은 목록 하나** — `inherited_env.zig` 의 이름들), 셸 상태 변수(`PWD`·`OLDPWD`·`SHLVL`·`_`·`ZDOTDIR`), maru 내부 변수(`MARU_` 로 시작하는 이름 전부, PTY 가 자식에 넣는 `FORCE_HYPERLINK`), 셸에 우리가 준 것(표식·`DISABLE_AUTO_UPDATE`)을 지운다. 해석에 성공했든 대체 경로(앱 환경)든 같은 함수(`shell_env.sanitize`)를 거친다. `NODE_OPTIONS`·`PYTHONPATH` 같은 런타임 옵션은 지우지 않는다(사용자가 일부러 넣은 값이고 막을 위협이 없다). PATH 는 상대 경로·빈 항목(`::` = 현재 폴더)을 버린다. 저장소 아래 항목은 거르지 않는다 — 서버 찾기는 실행이 아니고(WT3b 결정), 신뢰 전에 실행하는 일도 두지 않았다(WT5a — 버전은 서버가 알려 준다). 비밀 이름 패턴으로 지우지 않는다 — 사용자 제외 목록과 「전달되는 변수 이름 보기」를 둔다.
- **종료:** 순수 판정자(셸별 argv·`env -0` 파싱·위생·PATH 정리), 가짜 셸로 시한·실패·대체·표식 검증, 「준비 중」 동안 「없음」을 안 내는지, Finder 실행 실측(`~/.cargo/bin` 의 rust-analyzer 가 잡힌다).

#### WT3a — 해석기의 순수 계산 (완료)

- `session/lsp/shell_env.zig`(OS 중립 순수): 셸 이름(로그인 셸 경로의 끝 성분)별 인자(zsh·bash·sh·dash·ksh 계열 `-l -i -c`, csh·tcsh `-i -c`, fish `-l -i -c`, 그 밖 — nushell 포함 — 은 「지원 안 함」으로 앱 환경 대체), 셸에 줄 명령(시작 표식 · `/usr/bin/env -0` · 끝 표식을 **앱이 미리 만든 비공개 파일**(0600, 0700 디렉터리)에 `>>` 로 덧붙인다 — 실측 2026-10-08: csh·tcsh 는 시작할 때 3번 이상 fd 를 닫아 `/dev/fd/3` 이 「Bad file descriptor」, zsh `noclobber` 는 없는 파일에는 `>>` 도 막는다. 미리 만든 파일 + `>>` 는 zsh·bash·sh·dash·ksh·csh·tcsh 모두 `noclobber` 에서도 통과. 경로는 작은따옴표로 감싸고, 셸마다 뜻이 갈리는 글자(따옴표·`!`·공백 등)가 있으면 쓰지 않는다 — 실행 파일은 절대 경로라 별칭은 끼지 않는다(사용자 설정이 그 경로 이름으로 함수를 정의하면 낄 수 있지만 사용자 자신의 설정이다)), 셸에 줄 환경(아래 「셸에 줄 바탕」 + 표식 변수·`DISABLE_AUTO_UPDATE`), 출력 파싱(표식이 둘 다 있어야 성공 — 설정 파일이 `exec` 로 다른 프로그램을 띄우거나 도중에 죽으면 실패), 위생(아래), PATH 정리(절대 경로 항목만·빈 항목과 상대 경로를 버리고 중복은 처음 것), 저장소 아래 PATH 항목 걸러 내기(신뢰 전 실행 파일 해석용 — WT5a 에서 쓸 곳이 없어 지웠다).
- **위생 목록 하나**: 터미널 세션 변수(`TERM`·`COLORTERM`·`TERMINFO`·`TERM_PROGRAM(_VERSION)`·`CLICOLOR_FORCE`·`FORCE_COLOR`·`MARU_PANE_ID`·`MARU_HOOK_*`·`TMUX`·`TMUX_PANE`)는 중립 모듈 하나(`inherited_env.zig`)이고 macOS·Windows PTY 와 해석기가 함께 쓴다(예전에는 두 백엔드에 같은 목록이 손으로 있었다). 해석기는 거기에 셸 상태 변수·maru 내부 변수(`MARU_` 접두·`FORCE_HYPERLINK`)·셸에 준 것을 더 뺀다(`sanitize` — 해석 결과와 대체 경로 공용).
- **셸에 줄 바탕**(사용자 결정 2026-10-08): 앱을 터미널에서 띄웠으면(앱 환경에 `SHLVL` — Finder·Dock 은 launchd 환경이라 없다; `open` 은 부른 셸의 환경을 통째로 넘기므로 터미널 실행으로 본다, 실측 WT3a 적대적 검증) 그 터미널 저장소의 direnv·venv(`VIRTUAL_ENV`·`GOFLAGS`·`.venv/bin` 이 든 PATH)가 섞여 있고 로그인 셸을 거쳐도 남는다(path_helper 는 기존 항목을 뒤에 붙이고, direnv 훅은 프롬프트에서만 돈다 — 실측, WT3a 적대적 검증). 그때는 사용자·로캘·임시 폴더·에이전트 소켓(`HOME`·`USER`·`LOGNAME`·`SHELL`·`TMPDIR`·`LANG`·`LC_*`·`__CF_USER_TEXT_ENCODING`·`SSH_AUTH_SOCK`·`XPC_FLAGS`·`XPC_SERVICE_NAME`)과 시스템 PATH 만 바탕으로 준다(실측: 이 바탕으로도 zsh·bash·sh·ksh·dash 의 로그인 셸이 `path_helper`·`brew shellenv`·`~/.cargo/bin`·`.zshrc` 의 PATH 를 다 다시 세운다). 아니면 앱 환경(launchd — `launchctl setenv` 값 포함)에서 터미널 세션 변수만 뺀다. 한계: 셸을 못 읽어 앱 환경으로 대신할 때는 이 바탕 정리가 없다. 터미널(또는 `open`)로 띄우면 `launchctl setenv` 값이 바탕에서 빠진다(같은 사용자라도 띄운 방식에 따라 서버 환경이 갈린다).
- **결과 읽기**: 표식 둘에 더해 **셸에 준 표식 변수가 결과에 있어야** 성공이다(명령이 `;` 로 이어져 `env -0` 이 실패해도 표식은 찍힌다). 셸에 준 것(표식·`DISABLE_AUTO_UPDATE`)은 서버에 넘기지 않는다. 정리해서 빈 PATH 는 넘기지 않는다(빈 PATH 는 현재 폴더 — 서버의 cwd 인 저장소 — 를 찾는다, macOS 실측).
- **한계**: `/usr/bin/env -0` 은 macOS 12.3 부터다(Apple `shell_cmds` — 11.x·12.0~12.2 의 `env` 는 `-0` 이 없어 `illegal option`, WT3a 적대적 검증). 앱 하한은 11.0 이므로 그 아래에서는 셸을 띄우지 않고 앱 환경으로 대신한다(WT3b — 「지원 안 하는 셸」과 같이 다뤄 「못 읽음」을 띄우지 않는다). 근본 대안은 번들 안 maru 바이너리로 환경을 덤프하는 것(`/usr/bin/printf` 의존도 없어진다 — 후보). csh·tcsh 는 macOS 의 `path_helper` 가 `/etc/csh.login` 에만 있어 `-i -c` 로는 시스템 경로(`/usr/local/bin`·`/opt/homebrew/bin`)가 안 붙는다(Finder 실행과 같아 퇴행은 아니다). 표식은 `/usr/bin/printf` 로 찍는다 — 그것이 없는 시스템(NixOS 등)에서는 늘 실패해 앱 환경으로 대신한다(macOS 는 있다; 이식할 때 `/usr/bin/env -i -0 ‹표식›=` 으로 바꿀 수 있다 — 실측). `pathWithout` 은 글자로만 갈랐다(WT5a 에서 쓸 곳이 없어 지웠다). bash 만 펼치는 PATH 의 `~/bin` 은 상대 경로로 보고 버린다(그런 PATH 로 찾던 서버는 「없음」). tcsh `-i -c` 는 `$?prompt` 가 0 이라 `.cshrc` 의 `if ($?prompt)` 블록은 안 읽는다.
- **후보(이 단계 밖)**: 터미널 세션 목록에 다른 터미널·멀티플렉서의 신원(`ZELLIJ*`·`STY`·`KITTY_WINDOW_ID`·`WEZTERM_PANE`·`ITERM_SESSION_ID`·`TERM_SESSION_ID`·`LC_TERMINAL`)을 더할지 — `TMUX` 를 떨구는 것과 같은 이유지만 PTY 동작을 바꾸는 일이라 따로 정한다.
- **종료:** 순수 판정자(셸별 argv·명령·환경·파싱·위생·PATH 정리 — 저장소 걸러 내기는 WT5a 에서 함수째 지웠다), PTY 판정자는 그대로 통과(목록을 옮겨도 동작이 같다).

#### WT3b — 해석기를 돌려 잇기 (구현 완료 — Finder 실측 대기)

- 워커 스레드에서 비공개 임시 디렉터리·파일을 만들고 셸을 띄워(fork+exec, `setsid`, stdin·stdout·stderr 는 `/dev/null`, cwd=`$HOME`) 시한(10 초 — VS Code 와 같다) 안에 셸 종료를 기다린 뒤 파일을 읽고 지운다. 결과는 세대가 붙은 값으로 메인에 넘긴다. 시한을 넘기면 그룹째 끝낸다. 실패하면 앞서 담은 셸 환경이 있으면 그것을, 없으면 앱 환경을 쓴다(아래).
- **셸을 안 띄우는 경우**(스위치 끔·macOS 12.3 미만·지원 안 하는 셸·로그인 셸을 못 구함·안전하지 않은 임시 경로)와 앞서 담은 셸 환경이 없을 때의 **실패**(시한·`Malformed`·띄우기 실패 — 임시 디렉터리·스레드·fork)는 앱 환경을 `shell_env.sanitize` 로 거른 것으로 대신한다 — 해석 결과와 같은 위생. 앞의 다섯은 조용히(「못 읽음」 없이) 대신하고, 실패는 그 앱 환경에서 서버를 못 찾았을 때만 「없음」이 「셸 환경을 못 읽음(다시 읽기)」이라고 말한다(찾으면 따로 알리지 않는다). 누르면 다시 읽고, **다시 읽었는데도** 못 읽으면 「없음 — 셸 환경을 못 읽음(설치)」 — 누르면 설치로 간다(`exec tmux` 처럼 늘 실패하는 셸 설정에서 클릭이 다시 읽기만 되풀이하면 설치로 갈 길이 없다 — 다시 읽기는 팔레트에 남는다; 3회차 적대적 검증). 문구에서 원인을 지우지 않는다 — 설치 위치가 셸 설정에만 있으면(`~/.cargo/bin`) 설치해도 못 찾아 사용자가 짐작할 길이 없다(9회차). 실패하면 원인(`reason` — 시한·`Malformed` 등)을 앱 로그(`lsp` 범위 경고)에 한 줄 남긴다 — 상태바는 「못 읽음」만 말한다(9회차). **앞서 담은 셸 환경은 실패해도 지킨다** — 다시 읽기의 시한·일시적 rc 오류 한 번으로 잘 돌던 서버가 다음 기동부터 앱 PATH 로 찾아 「없음」이 되면 세션 끝까지 못 푼다(9회차); 스위치를 끈 것 같은 조용한 대신은 늘 앱 환경이다. 셸 환경을 지킨 실패에서 서버를 못 찾으면 보통 「없음 — 설치」다 — 그 환경에서 못 찾은 것은 셸 탓이 아니다(원인은 로그에; 10회차).
- 서버 찾기는 **거르지 않는다** — 처음엔 신뢰 전 찾기에서 저장소 아래 PATH 항목을 빼려 했으나, 찾기는 실행이 아니라(실행은 허용 뒤) 막는 위협이 없고 저장소 안에 설치한 서버가 늘 「없음」이 되어 신뢰를 묻지도 못했다(LSPB9 가 드러냈다). 신뢰 전에 실행하는 일은 두지 않았다 — 버전은 서버가 `initialize` 에서 알려 준다(WT5a; 그래서 `shell_env.pathWithout` 은 지웠다).
- **언제**: 서버가 필요한 문서가 신뢰 범위 안(홈 root·저장소 밖이 아닌 곳 — 신뢰 **결정**과는 무관하다: 거부한 저장소의 문서를 열어도 셸은 한 번 돈다, cwd 가 홈이라 저장소가 끼어들 수 없다)에 생겼을 때 그 gate 가 처음 시작한다(편집기를 안 쓰는 실행·홈 root·저장소 밖 문서로는 사용자 셸 설정을 돌리지 않는다 — pump 는 결과를 받기만 한다), 또는 사용자가 다시 읽을 때, 또는 아직 아무도 안 읽었는데 사용자가 이름 목록 명령(「Show Environment Variable Names」 — WT5b-1)을 부를 때. 다시 읽기도 아직 아무도 시작하지 않았으면 그 창의 스위치로 먼저 정한다(꺼 둔 사용자의 셸을 기본값으로 띄우지 않게 — 3회차 적대적 검증); 언어 서버가 꺼져 있으면 읽지 않고 그렇다고 알린다. 읽기 시작·다 됨에 모든 창이 상태바를 다시 그린다(결과는 한 창의 pump 가 받고 다시 읽기는 한 창이 부른다 — 바뀐 횟수를 창마다 견준다). 담기 전에는 서버를 찾아보지 않고 첫 후보 이름으로 「준비 중」 클라이언트를 세우고, 담은 뒤 고른 서버가 다르면(TS 처럼 후보가 여럿인 언어) 그 클라이언트를 이어 쓴다 — 새로 만들면 옛 것이 gate 를 다시 안 지나 「준비 중」으로 버려진 채 남았다(6회차 적대적 검증). 이어 쓰는 것은 그 문법의 첫 후보 이름으로 선 「준비 중」뿐이다(문법이 아니라 이름 — TS·TSX·JS 는 서버를 나눠 써 다른 문법의 문서가 세운 클라이언트일 수 있다; 「실패」 등 다른 서버의 클라이언트를 이어 쓰면 새 서버를 띄워 보지도 않고 그 상태를 보인다 — 7회차). 다시 읽는 동안 처음 보는 문법은 이미 담아 둔 환경으로 찾는다(기억은 안 한다 — 첫 후보로 세우면 떠 있는 서버를 두고 새 클라이언트가 생겨 버려졌다). 문서 없는 「준비 중」은 다른 창의 허용·거부에 그대로 둔다 — 다 담은 뒤 gate 가 표를 직접 읽는다(서버가 없으면 「없음」이 거부보다 먼저 — WT3b 이전과 같다). 잊기는 문서가 없어도 「결정 없음」으로 둔다 — 그대로 두면 다 담은 뒤 gate 가 결정 없는 표를 읽고 곧바로 묻는다(잊기는 다시 묻기가 아니다 — 8회차; 서버가 없던 클라이언트도 「결정 없음」이 되지만 누르면 root 부터 다시 봐 「없음」이 선다). 「없음」 클라이언트를 다시 고를 때(`repickIfMissing`) 그 서버의 클라이언트가 이 root 에 이미 있으면 이름을 바꾸지 않는다 — 설치하고 다시 읽는 사이 다른 문법(JS)이 그 서버를 세웠으면 같은 (root, 서버) 클라이언트가 둘이 됐다(8회차 — WT3b 이전부터 있던 구멍이 다시 읽기로 자주 드러났다).
- **스위치는 앱 전역**이고 처음 시작할 때 한 번 그 창의 설정으로 정한 뒤, 사용자의 명시 행동(세팅 토글·행 되돌리기·Reload Config(파일 감시 자동 reload 포함)·전체 리셋)으로만 바뀐다 — 창마다의 설정 미러로 매 tick 견주면 자동 reload 를 끈 창 하나가 다른 값을 들 때 tick 마다 셸을 띄웠다(WT3b 적대적 검증 — `window.quit-after-last-window-closed` 와 같은 규율). 세팅 화면은 다른 창에서 바꾼 값으로 그 창의 미러를 되맞춘다(아무도 정하지 않았으면 창 설정 그대로). 켜기만으로는 셸을 띄우지 않는다 — 처음으로 되돌아가 다음에 서버가 필요한 문서의 gate 가 시작한다(언어 서버를 껐거나 그런 문서가 없을 때 세팅을 만져 셸 설정이 돌지 않게 — 4회차 적대적 검증); 끄면 셸 없이 바로 앱 환경.
- 결과 슬롯은 세대가 더 새로운 쪽이 이긴다(늦게 끝난 옛 워커가 새 결과를 지우면 「읽는 중」에 갇혔다). 슬롯은 잠금 안에서만 읽고 쓴다(원자 CAS 로 두면 워커가 세대를 비교하는 사이 메인이 그 결과를 해제할 수 있었다 — 5회차 적대적 검증). 셸 자식은 exec 전에 3번 이상 fd 를 닫는다(CLOEXEC 가 빠진 앱 fd — 컨트롤 소켓 잠금 등 — 를 셸이 띄운 데몬이 쥐지 않게).
- 앱 전역 하나(`platform/macos/tool_env.zig`) — 환경은 사용자의 것이라 창마다 셸을 띄우지 않는다. 상태: 대기 → 읽는 중 → 담음 / 조용한 대신 / 실패(담아 둔 셸 환경 또는 앱 환경). 환경이 바뀌면 「없음」·「준비 중」 클라이언트는 문서가 열려 있으면 gate 가 매 tick 다시 찾고(문서가 닫힌 것은 다시 열 때), 기억해 둔 서버가 새 환경에서 없어지면 `repickIfMissing` 이 기억을 비운다 — 따로 알리는 장치는 두지 않았다(넣었더니 변이가 살아남았다 — 하는 일이 없었다). 떠 있는 서버는 띄울 때의 환경으로 돈다(다시 띄울 때 새 환경). 다시 읽는 동안은 옛 환경으로 띄우지 않는다.
- 판정자 기본(가짜 셸을 주입하지 않은 테스트 빌드)은 셸을 띄우지 않고 **지금의** 앱 환경을 거르지 않고 준다 — 판정자는 테스트마다 `setenv` 로 가짜 서버의 동작(`MARU_FAKE_LSP_*`)을 고르는데 위생은 `MARU_` 를 뺀다. 위생·해석 경로는 가짜 셸을 주입한 판정자가 잰다. 판정자 사이에서는 `resetForTest` 가 떠 있는 워커를 다 기다린다(앞 판정자의 남은 워커가 다음 판정자의 슬롯·집계에 끼면 샤드 순서에 따라 빨개지거나 헛돈다 — 4회차 적대적 검증); 느린 셸은 시간이 아니라 관문 파일로 붙잡고 끝내기 전에 놓아 준다.
- 사용자 제외 목록의 설정 키와 「전달되는 변수 이름 보기」는 이 단계 밖이었다 — WT5b-1 에서 했다(`sanitize` 의 `excluded` 인자는 지우고 envp 를 만들 때 거른다).
- 서버 찾기(`locate`)와 띄우기(`spawn`)가 해석한 환경을 쓴다. 담기 전에는 「셸 환경 읽는 중」 — 「없음」을 판정하지 않는다. 팔레트 「Language Server: Reload Shell Environment」.
- 스위치 `lsp.shell-environment`(기본 켬, 세팅 화면에 같은 토글). 끄면 셸을 띄우지 않는다.
- `setsid` 는 필수다 — 빠지면 터미널에서 띄운 앱의 셸이 그 터미널의 `/dev/tty` 를 잡아 입력을 기다리거나 포그라운드를 빼앗을 수 있다(`setsid` 면 compinit 의 insecure 프롬프트·`read -q` 가 「can't open terminal」로 바로 끝난다 — 실측).
- **남는 것**: 앱을 끝낼 때 읽는 중인 셸은 끝내지 않는다(워커는 detach — 셸은 새 세션이라 SIGHUP 도 안 받는다; 시한도 워커가 재므로 rc 가 멈춰 있으면 고아로 남고, 정상 종료면 임시 파일이 지워지지 않는다). 다시 읽기를 연타하거나 읽는 중에 스위치를 끄면 옛 셸을 끝내지 않는다(각 셸은 시한 10 초까지 — 결과는 세대로 버린다). 둘 다 띄운 셸의 그룹을 원자값으로 들고 끝내는 자리를 정해야 해 따로 다룬다(3회차 적대적 검증). 셸 자식은 exec 전에 `getdtablesize()` 까지 fd 를 닫는다 — `ulimit -n` 이 큰 환경에서는 수십만 번의 close 다(자식 쪽이라 앱은 안 선다; 열린 fd 만 닫는 길은 이식할 때 함께 본다). 「없음」 클라이언트는 gate 가 tick 마다 다시 찾는다(설치를 바로 잡으려고) — 사용자 셸 PATH 가 길면 `access` 가 그만큼 늘고(Dock 실행 대비; 터미널에서 띄운 앱은 원래 그랬다), 네트워크 마운트 항목이 있으면 메인이 설 수 있다. 다시 찾기를 완료 횟수·간격으로 묶는 것은 따로 다룬다. OOM 으로 대신할 환경을 못 만들면 상태는 「다 됨」인데 띄울 환경이 없다(「준비 중」에 남는다) — 막는 방어는 두지 않았다(5회차 적대적 검증). 홈 root·저장소 밖 문서만 연 세션은 셸을 안 띄우므로(계획 「언제」) 상태바의 서버 이름이 찾아보지 않은 첫 후보다(TS 면 설치 안 된 `tsgo` — 예전엔 앱 PATH 로 찾은 이름; 7회차) — 처음 읽는 동안의 「셸 환경 읽는 중」도 그 이름이다. 팔레트의 다시 읽기는 서버가 다 떠 있으면 결과를 따로 알리지 않는다. 다른 창의 신뢰 모달은 다시 읽는 동안 다시 뜨지 않는다(그 클라이언트는 「준비 중」 — 다 읽은 뒤 묻는다). 셸 바탕의 `HOME`·`TMPDIR` 은 앱 환경 값이다(cwd 도 그 `HOME` — WT5b-1 결정: `getpwuid` 로 고정하지 않는다) — direnv·nix devshell 이 그것을 저장소 안으로 바꾼 터미널에서 앱을 띄우면 셸 설정을 그 저장소 안에서, 그 저장소를 cwd 로 읽는다(사용자가 이미 허용한 direnv 다). 담아 둔 셸 환경이 없는 대체(스위치 끔·첫 실패)는 앱 환경을 거른 것이라, direnv 가 켜진 터미널에서 띄웠으면 그 저장소의 PATH 항목이 다른 저장소의 서버 찾기에 잡힐 수 있다(WT3a 「한계」 — 신뢰 모달은 이름만 보인다; 경로 표시는 WT5). 셸 설정이 export 한 값(토큰·`NODE_OPTIONS`)은 허용한 저장소의 서버·빌드 스크립트까지 간다(WT3a 결정 — 제외 목록과 「전달되는 변수 보기」는 WT5b-1 에서 했다; `DYLD_*` 는 macOS 가 SIP·hardened runtime 으로 지운다, Linux 로 이식할 때 `LD_PRELOAD` 는 같은 결정으로 명시한다; 12회차 적대적 검증). TS·JS 가 나눠 쓰는 클라이언트를 이어 쓸 때 그 문법은 처음 세운 문서의 것으로 남는다(9회차).
- **종료:** 가짜 셸로 시한·실패·대체·표식 검증, 가짜 셸이 `/dev/tty` 를 못 연다, 「준비 중」 동안 「없음」을 안 내는지, 끈 스위치는 셸을 안 띄우는지, macOS 12.3 미만에서는 셸을 안 띄우는지, **Finder(또는 Dock)로 띄운** 앱의 실측(`~/.cargo/bin` 의 rust-analyzer 가 잡힌다 — `open` 은 터미널 환경을 넘기므로 Finder 실측이 아니다).

### WT4 — 신뢰 관리

WT4 는 둘로 나눴다(2026-10-08) — 앱 안의 관리(WT4a)와 컨트롤 플레인·CLI 의 조회·철회(WT4b, 공용 wire 에 새 control 을 더하는 일).

#### WT4a — 앱 안의 신뢰 관리 (완료)

- **어디서**: 명령 팔레트(사용자 결정 2026-10-08 — 설정 화면 예외·상태바 메뉴 대신). 「Language Server: Repository Trust…」(한글 검색 「언어 서버 저장소 신뢰 결정 목록」)가 목록 피커(복구 목록과 같은 컴포넌트 — 휠·스크롤바 포함)를 연다 — 표의 결정(허용/거부)과 저장소 경로(`~`·앞 줄임), 경로로 거른다(실제 경로로도, 보이는 `~/…` 로도). 세 명령은 탭을 만들지 않아 탭 바 없는 최소 세션에서도 먹는다. 고르면 관리 확인 상자. 「Language Server: Revoke Trust for This Repository」·「…Forget Trust for This Repository」는 지금 편집기 문서의 저장소를 바로 그 상자로(할 것이 없으면 — 언어 서버 문서가 아니다·결정이 없다·신뢰하지 않았는데 철회 — 상자 없이 알림).
- **관리 상자**: 허용된 저장소 [철회][잊기][취소], 거부된 저장소 [잊기][취소], 「이 저장소」 명령은 그 동작 하나. 목록에서 고르면 연 순간의 사본이 아니라 **그때 표의 결정**으로 상자를 띄운다(그 사이 다른 창이 잊었으면 상자 없이 「결정이 없다」). 안내 줄 — 저장소 경로(**맨 앞** — 낮은 창에서 모달이 끝부터 줄여도 대상이 남는다; 질문에는 저장소가 없다), 고를 수 있는 동작의 뜻, 「모든 창에서 바로 내린다」, **되돌리지 않는 것**(서버가 이미 만든 캐시·빌드 산출물, 적용한 포맷·수정, 따로 떠난 데몬). 처음 포커스는 취소다(두 동작 모두 서버를 내리므로 Enter 는 아무것도 안 바꾼다 — 확인 상자 규칙). **신뢰를 주는 길은 없다** — 허용은 신뢰 시트의 답뿐(LSPB23).
- **철회** = 거부로 기억(다시 안 묻는다) — WT2a 의 거부 전파 그대로: 모든 창에서 서버를 유예 없이 그룹째 내리고 기다리던 요청·진단을 지운다.
- **잊기** = 결정을 지운다. 표에 「잊었다」 표시(`Store.forget` — 세대가 오르고 `changed_at` 이 언제 잊었나를 든다)를 남기고 파일에 `forget` 줄을 덧붙인다. 각 창은 자기가 마지막으로 본 뒤에 잊었으면 그 저장소의 **그 순간 있던** 클라이언트를 — 서버를 유예 없이 내리고 진단·연 문서를 걷어 — **「‹서버›: 신뢰 결정 없음 — 묻기」**(`Phase.unasked`)로 둔다; 곧바로 묻지 않는다(누르면 묻는다 — 묻지 않는 root 판정부터 다시 하므로 잊은 뒤 `.git` 을 지웠으면 「저장소 밖」). 잊은 뒤에 새로 생기는 클라이언트(새 창에서 그 저장소를 열거나, 같은 창에서 그 저장소의 다른 언어 서버가 필요해졌다)는 결정이 없으니 열 때 묻는다 — 앱을 다시 띄운 뒤와 같다. 다시 읽을 때 `forget` 줄은 표시 없이 항목을 지운다.
- **저장 실패**: 철회·잊기가 파일에 남지 못하면(못 읽은 표라 손대지 않는다·자리를 못 만들었다·쓰기 실패) 표에는 서서 서버는 내리지만 「저장하지 못했다 — 이번 실행에만, 다음엔 이전 결정을 읽는다」고 알린다(철회했는데 다음 실행에 허용이 돌아오는 것을 사용자가 알게).
- **판정자**: LST13(잊기 — 표시·세대·`forget` 줄 읽기/쓰기), LST14(못 읽은 표에는 결정·잊기를 덧붙이지 않고 「못 남겼다」), LSPB35(목록 휠·막대·굴린 뒤 클릭·`~/…` 거르기·연 뒤 잊힌 저장소·저장 실패 알림), LSPB36(「결정 없음」 클릭이 root 판정부터 다시), LSPB32(두 창 — 목록에서 잊기, 모든 창에서 바로 내리고 진단을 걷고 묻지 않음, 누르면 묻고 허용하면 다른 창도 뜸, 「이 저장소 철회」가 두 창을 내림, 거부된 것은 [잊기]만, 취소는 아무것도 안 바꿈, 파일 줄 순서), LSPB33(「이 저장소」 명령의 알림 셋·빈 목록·경로 거르기), LSPB34(「결정 없음 — 묻기」를 누르면 묻는 동안 문서 닫힌 같은 저장소 서버를 띄우지 않는다), LSPB23(철회는 거부만 적고 잊기 자리는 하나, 목록 파일은 표를 읽기만 한다).
- **남는 것·한계**:
  - 「해석 캐시」 지우기는 WT3(환경 해석기)이 생긴 뒤의 일이다.
  - 열린 목록의 행은 연 순간의 결정을 보이고, **떠 있는** 관리 상자의 버튼도 그대로다 — 상자가 떠 있는 사이 다른 창에서 잊었으면 [철회]는 거부를 새로 세운다(보수적인 쪽), [잊기]는 할 일이 없다.
  - 파일은 덧붙이기만 해 줄지 않는다. 1 MB 를 넘으면 못 읽은 표로 보고 그 실행은 메모리로만 쓴다(관리 상자는 「저장하지 못했다」고 알린다). 결정 수에 비해 줄이 많을 때의 다시 쓰기(압축)는 남는 일이다 — 여러 앱 인스턴스가 같은 파일에 덧붙이는 중에 통째로 다시 쓰면 다른 인스턴스의 줄을 잃을 수 있어 그 규율과 함께 정한다.
  - 신뢰 시트의 답이 파일에 못 남은 것은 말하지 않는다 — 다음 실행이 다시 묻는다. 단 「다시 묻기」에서 거부로 답한 것만은 파일의 옛 허용으로 돌아간다.
  - WT4a 이전 바이너리는 `forget` 줄을 모른다(못 읽는 줄로 건너뛴다) — 이전 판으로 되돌리면 잊은 허용·거부가 되살아난다. 철회(`deny` 줄)는 이전 판도 읽는다.
  - 잊은 뒤에도 그 저장소를 연 다른 창이나 그 저장소의 다른 언어 서버는 결정이 없으니 열 때 곧바로 묻는다 — 「결정 없음」으로 남는 것은 잊는 순간 있던 클라이언트뿐이다(안내 「다음에 다시 묻습니다」와 같은 뜻). LSP 를 껐어도 목록은 열리고 철회·잊기가 표에 적힌다(다시 켜면 그 결정을 따른다). 「이 저장소」 명령은 LSP 를 껐으면 그렇다고 알린다.

#### WT4b — 컨트롤 플레인·CLI 조회·철회 (완료)

- 컨트롤 플레인과 CLI 에 신뢰 결정 **조회**와 **철회·잊기**를 더한다(부여는 없다 — 에이전트가 신뢰를 주지 못하게). 철회·잊기의 효과는 WT4a 와 같은 길(앱 전역 표 → 각 창의 `applyTrustChanges`)이다.
- **메서드**: `lsp.trust.list`·`lsp.trust.revoke {path, volume?}`·`lsp.trust.forget {path, volume?}`(표의 단일 출처 [컨트롤 플레인 §6](../control-plane.md)). wire 절반은 `session/control_lsp_trust.zig`(L2 순수 — 요청 해석·응답 직렬화), 표에 닿는 일은 `editor/lsp.zig` `controlTrust`(ABI 는 표를 모른다 — LSPB23). 응답은 바뀐 것(`changed`)과 파일에 남았나(`saved`)를 말한다 — 앱 안에서는 알림이 뜨지만 CLI 는 그것을 못 본다.
- **누가 부르나(2026-10-09 사용자 결정 「같은 사용자면 바로」)**: 셀렉터 없이 붙은 연결(같은 uid 의 그 사용자 자신 — SSH 로 붙은 폰 포함)은 확인 없이 열고, 셀렉터를 댄 연결은 균일 `unauthorized`([보안 §8.3](../control-plane-security.md)). 근거: 같은 uid 는 신뢰 파일을 직접 고칠 수 있다. 철회는 권한을 낮추기만 하고, 잊기는 거부를 「결정 없음」으로 되돌릴 수 있다(그 저장소를 다시 열면 묻는다 — 에이전트가 잊힌 뒤 허용 클릭을 유도할 여지; 대안 「잊기만 앱 안 확인」을 함께 보이고 택한 결정). 잊기는 곧바로 묻지 않는다. 셀렉터 거절은 방어 경계가 아니다(셀렉터는 주장이다 — 빼고 붙으면 된다). maru 패인 안의 CLI 도 이 명령에서는 셀렉터를 보내지 않는다.
- **창이 없어도(2026-10-09 사용자 결정 「표를 읽어 처리」)** 표를 읽는다 — 표는 창의 것이 아니다. 옛 자리 이관에 쓸 설정 경로는 첫 창의 것, 창이 없으면 기본 설정 경로.
- **철회는 지금 허용인 결정만** 거부로 적는다(결정이 없던 저장소에 거부를 새로 세우지 않는다 — 관리 상자와 같은 규칙). **찾기**: 표에 그 경로 글자가 그대로 있으면 그것(목록이 준 경로 — 지워진 저장소도 잊을 수 있다), 없으면 실제 경로로 풀어 찾는다(사용자가 친 심링크·`/tmp`). 같은 경로가 여러 볼륨에 있으면 `volume`(목록의 16진)으로 고른다. CLI 는 상대 경로를 현재 디렉터리 기준으로 펴고 절대 경로도 정리한다(끝 `/`·`.`·`..`). 응답은 맞은 저장소(`repository` — 심링크를 풀었으면 친 글자와 다르다)를 말하고, 결정이 없으면 그 경로를 품은 가장 가까운 저장소(`containing` — 실제 경로로 풀리면 같은 볼륨만)를 알려 준다 — 저장소 하위 폴더에서 `revoke .` 를 치면 「결정 없음」만으로는 신뢰된 적 없는 것으로 읽혔다(3회차 적대적 검증; 위로 올라가 바꾸지는 않는다). CLI 는 빈 경로 인자를 거절하고(펴면 현재 디렉터리가 되어 엉뚱한 저장소에 닿는다) `..` 는 글자로 접는다(심링크를 따라 풀지 않는다). 경로 안의 NUL 은 거절한다(NUL 앞까지로 열려 다른 저장소에 닿는다).
- **계획의 「관문·세대·옛 host 거절」**은 영속 세션 host wire 의 어휘였다 — 이 메서드는 앱 컨트롤 플레인이라 대응하는 것은 hello 광고(`lsp.trust.*` 셋)·§8.3 판정(셀렉터)·옛 앱의 `method_not_found`(CLI 가 「이 Maru 는 지원하지 않는다」로 읽는다)다.
- **관리 상자(WT4a)의 답은 지금 표를 다시 본다** — 상자를 띄운 뒤 다른 창·컨트롤 플레인이 잊었으면 아무것도 안 하고(「결정 없음」 알림), 거부로 바뀌었으면 「철회」를 다시 적지 않는다. 예전에는 상자가 띄울 때의 결정으로 답해, 잊힌 저장소에 거부가 새로 섰다(두 창만으로도 재현되던 WT4a 결함 — 컨트롤 플레인이 외부에서도 일으킬 수 있게 되어 함께 고쳤다).
- **남는 것**: 떠 있는 신뢰 시트·관리 상자·신뢰 목록은 컨트롤 철회로 **다시 그려지지는** 않는다(시트가 떠 있으면 사용자의 클릭이 이긴다 — 상자의 답은 위처럼 지금 표를 본다). 응답은 철회·잊기의 효과가 각 창에 **퍼지기 전**에 돌아온다(다음 pump 가 따른다). 표에 그 글자가 없는 경로는 메인 스레드에서 실제 경로로 푼다(`open`) — 응답 없는 네트워크 마운트 경로를 주면 그동안 앱이 선다(같은 uid 가 일으키는 가용성 문제). 비 UTF-8 경로는 JSON 문자열이 못 된다 — macOS(APFS)는 파일 이름을 UTF-8 로만 저장해 생기지 않는다(이식할 때 본다).
- **종료:** 조회·철회·잊기의 wire 판정자(서버 직렬화기 출력을 CLI 렌더와 실제 디코더에 통과 — `control_lsp_trust`·`cli/lsp_trust`), 디스패치 판정자(셀렉터 거절·params·부여 메서드 없음), 부여 요청이 없다는 자리 수 판정자(LSPB23 — 컨트롤 철회도 `recordTrust(…, .deny)` 하나), 제품 경로 판정자(LSPB38 — 떠 있는 서버를 내리고 파일에 남음·잊기는 「결정 없음」·심링크와 맞은 저장소·하위 폴더의 품은 저장소·창 없이; LSPB38b — 여러 볼륨·틀린 볼륨; LSPB39 — 관리 상자의 답이 지금 표를 다시 봄), hello 광고 판정자, 제품 앱 실측.

### WT5 — 저장소별 환경과 실행 파일 표시

WT5 는 둘로 나눈다(2026-10-09) — 무엇이 실행되는지 보이는 일(WT5a)과 저장소별 환경을 고르는 일(WT5b).

#### WT5a — 실행 파일과 버전 보이기 (완료)

- **결정(2026-10-09 사용자 「권장대로」 — 다른 편집기 대조 뒤)**: 띄운 경로 그대로 + 서버가 알려 준 버전(`initialize` 응답의 `serverInfo` — 없을 수 있다)을 보인다. shim 뒤의 진짜 바이너리를 `mise which`·`rustup which` 로 풀지는 **않는다** — VS Code·JetBrains·Zed·Neovim·Helix 어느 것도 풀지 않고(띄운 경로를 그대로 보인다), 도구마다 명령표·시한·실패 처리가 늘어난다. 대신 띄운 경로가 shim 자리(mise·asdf·pyenv·rbenv·nodenv·volta·proto·goenv·aqua 의 shim, rustup 대리)면 그렇다고 알린다 — 「‹도구› shim 을 거쳐 실행되어 버전은 저장소가 고를 수 있습니다」.
- **결정(구현 중 — 계획의 「shim 안내」를 이렇게 읽었다)**: WT1 의 **늘 보이던** 일반 경고(「실제로 실행되는 파일은 저장소 설정이 고를 수 있습니다」)는 지웠다 — 이제 실행 파일 경로를 늘 보이므로, 경고는 출처를 **감지했을 때만**(shim·저장소 안) 붙인다(늘 붙는 경고는 읽히지 않는다). 대가: 표에 없는 버전 관리자의 shim 은 경고 없이 경로만 보인다 — 그래서 표에 흔한 것(proto·goenv·aqua)을 더했다(적대적 검증 — jenv 는 서버 표에 Java 가 없어 닿지 않아 뺐다).
- **보이는 곳**: ① **신뢰 시트**의 안내 줄 — 찾아 낸 실행 파일 경로(`~` 로 줄임)와 shim 안내. 다른 편집기의 신뢰 창은 「이 폴더를 신뢰하나」만 묻는다 — 이름만 보고 허용하는 한계(WT1 「실제로 실행되는 파일은 저장소 설정이 고를 수 있습니다」)를 경로로 메운다. ② 팔레트 「Language Server: Show Server Info」 — 지금 문서의 서버 이름·실행 파일(shim 안내)·버전·저장소·신뢰 결정·상태(다른 편집기의 `:LspInfo`·Output 패널 자리). ③ 앱 로그 — 서버를 띄울 때 경로와, 버전을 받으면 버전을 한 줄(tooling §8.1 「실제 executable/version 을 trace 에 노출」).
- **구현**: 출처 판정은 순수 `session/lsp/exe_origin.zig`(저장소 안이 이긴다 → shim 폴더 → rustup 대리 → 그 밖), rustup 대리는 L4 가 **같은 폴더의 `rustup`** 과 같은 파일(장치·inode — 하드 링크든 심링크든)인지 잰다(`~/.cargo/bin`·Homebrew rustup 의 bin — 그 폴더엔 `cargo install` 한 일반 바이너리도 있다; 처음엔 `$CARGO_HOME/bin` 만 봐 Homebrew 를 놓쳤다, 적대적 검증). shim 폴더 자리는 **사용자 셸 환경**(`tool_env`)의 변수를 따른다(mise 는 `MISE_DATA_DIR` → `$XDG_DATA_HOME/mise` → `~/.local/share/mise`). 띄운 서버의 출처는 `recordLaunch` 가 그 서버가 받은 환경으로 굳힌다 — 정보 명령이 나중에 다시 재면 셸 환경을 다시 읽는 동안 자리 변수가 비어 「그 밖」이 된다(적대적 검증). 시트의 실행 파일은 **두 줄**이다 — 출처 경고(shim·저장소 안일 때만, 경고 줄이라 줄바꿈)와 경로 줄(`.fit = .path` — 한 행에 가운데를 줄인다). 한 줄로 두면 긴 경로가 좁은 창에서 글자 단위로 접혀 경고가 밀려났다(LSPB19). 띄운 경로는 `spawnClient` 가 굳힌다(gate 가 찾은 경로와 다를 수 있다 — 그 사이 셸 환경 다시 읽기·다른 후보). 서버 이름·버전은 128 바이트에서 자르고(UTF-8 경계) 제어 문자(개행·ESC·DEL)는 공백으로 바꾸며(알림은 `\n` 으로 줄을 나눈다 — 서버가 「저장소: … (허용)」 같은 줄을 위조하거나 빈 줄로 진짜 줄을 밀어낼 수 있었다, 적대적 검증) 다시 띄우면 지운다. 저장소 안인지는 root 의 두 표기(보이는 경로·실제 경로 — `/tmp` → `/private/tmp` 처럼 PATH 표기와 갈린다)와 실행 파일의 실제 경로(저장소 밖 링크가 저장소의 빌드 산출물을 가리킬 때)로 본다(적대적 검증). 정보 명령은 알림(512 바이트 — 넘치면 끝이 「…」, 6 행까지)이고 줄 순서는 상태·버전·저장소와 결정·출처 경고·경로다 — 넘치면 끝부터 잘려 앞의 상태·버전·저장소가 남는다(아주 좁은 창에서는 경로 줄이 통째로 밀려날 수 있다). 띄운 경로·버전은 **떠 있는** 서버만 말한다(재시작 대기·실패·거부 뒤의 지난 값은 지금의 것이 아니다 — 그때는 「떠 있지 않음」과 지금 찾아 낸 경로 — 「아직」은 실패·거부 뒤에 거짓이라 뺐다), `initialize` 응답 전이면 「서버 응답을 기다리는 중」. 떠 있지 않은데 셸 환경을 담기 전·다시 읽는 중이면 실행 파일을 찾지 않고 「셸 환경을 읽은 뒤에 찾습니다」(앱의 짧은 PATH 로 찾으면 「찾지 못함」 — 상태바가 그동안 「없음」을 판정하지 않는 것과 같다, 적대적 검증). 알림의 모든 줄은 제어 문자를 공백으로 바꿔 쓴다(폴더 이름에도 개행이 들 수 있다).
- **남는 것**: 상태바 호버는 두지 않았다(정보 명령 하나). 시트는 묻는 클라이언트 하나의 실행 파일만 보인다(허락은 저장소의 모든 서버에 선다 — 셋째 줄이 그것을 말한다). 정보 명령을 신뢰 시트가 떠 있을 때 부르면 알림이 시트를 닫는다(결정 없이 — 다시 묻는다; 시트가 떠 있으면 팔레트가 안 열려 실제로는 닿지 않는다). 묻지 않는 root(저장소 밖·홈 — WT2b)에서 정보 명령은 상태와 버전 두 줄만 보인다(상태 줄의 phase 와 gate 와 같은 `refusalFor` 를 둘 다 본다 — phase 만이면 gate 가 root 를 보기 전에 새고, `refusalFor` 만이면 `git init` 뒤 누르기 전의 「저장소 밖」 상태 줄과 어긋난다; 떠 있는 서버는 root 를 다시 보지 않는다 — 그 뒤 `.git` 이 사라져도 돌고 있는 실행 파일을 숨기지 않는다) — 그 폴더를 「저장소」라 하거나 그 아래 실행 파일을 「저장소 안」이라 하면 거짓이고, 그 root 로는 셸 환경도 읽지 않는다(적대적 검증). 서버가 이름만 알려 주면(버전은 선택 필드) 「서버가 알려 주지 않음 (‹이름›)」.
- **종료:** shim 판정 순수 판정자(`LSPO1`~`LSPO4` — `exe_origin` 의 자리별·자리 변수·rustup 대리; 처음 이름 `exe_origin:` 은 편집기 빠른 고리 필터에 안 걸려 0번 돌았다), `LSJ serverInfo`, 시트의 출처 경고·경로 줄(LSPB2 — 가짜 서버는 저장소의 zig-out 안이라 「저장소 안」)·두 언어·좁은 창에서 경고가 끝까지(LSPB19), 정보 명령의 제품 경로(LSPB40 — 가짜 서버의 `serverInfo`·`MARU_FAKE_LSP_NOSERVERINFO`·내린 뒤 「떠 있지 않음」·`MARU_FAKE_LSP_INIT=silent` 로 응답 기다림·경로가 맨 끝·상한을 넘는 경로의 「…」), rustup 대리·심링크 root·저장소 밖 링크 제품 경로(LSPB41), 서버 문자열의 상한·글자 경계·제어 문자·빈 이름(`LSJ serverText` — 규칙 하나 `rpc.displayByte` 를 알림·로그도 쓴다, 로그 사본은 LSPB42; 제품 경로는 LSPB40 — `MARU_FAKE_LSP_SERVERINFO_NAME`·`_VERSION`), 자리 변수는 앱 환경이 아니라 사용자 셸 환경의 것이고 담기 전엔 정보 명령이 찾지 않으며 다시 읽는 동안에도 띄운 서버의 출처는 그대로이며 떠 있는 동안 `.git` 이 사라져도 실행 파일을 보임(LSPE15 — 가짜 로그인 셸만 세운 `VOLTA_HOME`), 출처 경고 없는 다섯 줄 시트(LSPE1), mise·aqua 의 `XDG_DATA_HOME`·proto·goenv(`LSPO`), 묻지 않는 root 의 두 줄 정보 — gate 가 root 를 보기 전에도·그 폴더에서 `git init` 한 뒤 누르기 전에도(LSPB28), 이름만 알려 주는 서버(LSPB40 ⑷b — `MARU_FAKE_LSP_SERVERINFO_VERSION=` 빈 값), 신뢰 시트 골든 두 장(넓은 창·좁은 창 — 다시 떴다).

#### WT5b — 저장소별 환경 (셋으로 나눈다 — 2026-10-09 사용자 결정)

##### WT5b-1 — 환경 위생: 제외 목록·변수 이름 보기·미뤄 둔 결정 둘 (완료)

- **결정(2026-10-09 사용자, 넷 다 권장안)**:
  - **`HOME` 은 앱 환경의 것을 그대로** 둔다(`getpwuid` 로 고정하지 않는다). 격리 HOME 실행·판정자가 기대는 동작이고, VS Code 도 프로세스 환경을 그대로 준다. 셸의 cwd 도 같은 `HOME` 으로 맞춘다(지금은 cwd 만 `getpwuid` 의 홈이라 둘이 어긋날 수 있다).
  - **대체(스위치 끔·첫 실패)의 PATH 는 줄이지 않는다.** 스위치를 끈 것은 「띄운 환경을 써라」는 뜻이고, 줄이면 터미널에서 띄운 앱이 서버를 못 찾는다. 다른 편집기도 해석에 실패하면 프로세스 환경을 그대로 쓴다. 그 터미널 저장소의 direnv·venv PATH 가 섞일 수 있다는 것은 문서에 적는다.
  - **「전달되는 변수 이름 보기」는 목록 상자**다 — 팔레트 명령이 신뢰 목록(WT4a)과 같은 모양의 스크롤 목록을 연다. 값은 보이지 않고 이름만, 제외 목록으로 빠진 이름은 「제외됨」으로.
  - **제외 목록은 설정 키 `lsp.environment-exclude`** — 쉼표로 가른 이름들, 이름 끝의 `*` 만 접두로 본다(예 `AWS_*, GITHUB_TOKEN`). 그 밖의 글롭은 없다.
- **구현**: 판정은 순수 `shell_env.excludedBy`(쉼표 목록·끝 `*`). 시스템 위생(`sanitize`)과 달리 **서버에 줄 envp 를 만들 때** 거른다 — `tool_env` 는 위생만 거친 원본(`current.resolved`)을 그대로 두고 envp 만 목록으로 만든다(`filteredEnvp`). 그래서 목록을 바꿔도 셸을 다시 띄우지 않고(`setExcluded` 가 `filteredEnvp` 로 envp 만 다시 만든다), 목록 상자가 걸린 이름을 「제외됨」으로 보인다. 쓰이지 않던 `sanitize`·`resolve`·`keep` 의 `excluded` 인자는 지웠다. 목록은 앱 전역 하나다(해석기가 하나) — 스위치 `lsp.shell-environment` 와 같은 규율: 처음 정하기는 gate·목록 상자(`initExcluded` — 아직 아무도 안 정했을 때만), 바꾸기는 세팅 커밋·행 되돌리기·Reload Config·전체 리셋 넷, 다른 창의 미러는 세팅 화면이 되맞추되 앱 전역 슬라이스를 빌리지 않고 창 arena 로 복사한다(다른 창이 바꾸면 전역은 풀린다). 세팅 화면은 빈 값을 받는다(목록 비우기 — `setText` 는 빈 값을 거부한다). 세팅 화면의 편집 칸(128 바이트)보다 긴 값은 편집에 들이지 않고, 치다가 넘치면 버린 글자를 알린다 — 잘린 채 저장되면 뒤쪽 이름이 서버로 간다(적대적 검증; 모든 text 행이 같다 — `config-gui.md` §6.2). 목록 상자는 신뢰 목록(`trust_ui`)에 모드 하나를 더했다(같은 피커·휠·막대·거르기). 셸의 cwd 는 앱 환경의 `HOME`(없으면 `getpwuid`) — 판정자와 제품이 같은 길이다.
- **남는 것**: 셸 cwd 가 앱 환경의 `HOME` 을 따르므로 direnv·nix devshell 이 `HOME` 을 저장소 안으로 바꾼 터미널에서 띄운 앱은 그 저장소에서 셸을 읽는다(「cwd 는 홈 — 저장소 훅이 신뢰 전에 안 돈다」는 그 경우 서지 않는다 — 결정이 받아들인 범위; 쓸 수 없는 `HOME` — 상대 경로·없는 폴더 — 은 `getpwuid` 로 대신한다). 「Show Environment Variable Names」는 아직 아무도 안 읽었으면 읽기를 시작한다(사용자의 명시 행동 — 다시 읽기 명령과 같다; 홈 root 문서만 연 세션에서도). 떠 있는 서버는 목록을 바꿔도 다음 띄우기까지 옛 환경이다(내리고 다시 띄우지 않는다). 서버 찾기(PATH)에는 제외 목록을 쓰지 않는다(`PATH` 를 빼도 찾기는 된다 — 서버만 빈 PATH 로 뜬다). 출처 판정의 자리 변수(`MISE_DATA_DIR` 등)는 거른 envp 를 읽는다 — 서버가 실제로 받은 것과 같다.
- **종료:** `LSPX1`(제외 목록 판정), `LSPE16`(제품 경로 — gate 가 정한 목록으로 가짜 로그인 셸이 세운 변수가 서버 환경에서 빠짐·이름 목록 상자·고르면 닫힐 뿐·목록을 바꿔도 셸을 다시 안 띄움), `LSPE17`(앱 전역 — 처음 연 창이 이김·세팅 커밋·빈 값·다른 창 미러 사본·바꾸는 자리 넷을 자리마다·편집 칸보다 긴 값은 편집에 안 들임), `LSPE18`(이름 목록 명령이 읽기를 시작·「읽는 중」·LSP 꺼짐 알림), 셸 cwd 가 `HOME` 을 따르고 쓸 수 없으면 `getpwuid`(`tool_env` 의 가짜 셸 판정자 — `FAKE_CWD`). 목록을 못 담으면(메모리) envp 를 먼저 만들어 실패하면 목록도 그대로다(목록 상자가 「제외됨」이라는데 서버는 받는 일이 없다 — 적대적 검증).

##### WT5b-2 — direnv·mise

##### WT5b-3 — config discovery

- 계약 §8.1 「config discovery 결과…를 노출」 — WT5a 는 같은 문장의 「실제 executable/version」 절반만 했다. 서버가 읽은 설정 파일(어떤 `zls.json`·`pyrightconfig.json`)을 보이는 일은 어느 단계에도 없었다 — 여기서 정한다(적대적 검증). 서버마다 알려 주는 방식이 달라 무엇을 「찾았다」고 할지부터 정한다.

## 범위 밖 (별도 결정 거리)

- **git 이 신뢰 전에 저장소가 정한 명령을 실행할 수 있다.** 도크의 git 조회는 위험 설정 일부를 막지만 파일 필터(`filter.*`)는 정확성 때문에 허용한다(`session/git_command.zig` `config_overrides`) — `.git` 이 든 압축 파일을 열면 신뢰 전에 돈다. VS Code·JetBrains 는 신뢰 전에 git 을 끈다.
- 원격(SSH) 저장소의 신뢰 키(호스트 키 지문·원격 사용자·원격 실제 경로)와 원격 쪽 환경 해석, devcontainer, 조상 디렉터리 설정 파일 지문(신뢰 뒤 새로 생기면 다시 묻기), 서버별 제한 모드, 감사 로그, 조직 정책.
