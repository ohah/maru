# 사이드바 에이전트 목록(워크스페이스 카드 하위 목록)

이 문서는 왼쪽 워크스페이스 사이드바의 **카드 하위 세션 목록**과 그에 따른 **카드 동적 높이**의 단일 출처다.
카드 자체의 줄 구성(이름·브랜치·경로)은 [탭·split·레이아웃 전략](tabs-splits-layout.md)이, 에이전트 **상태 판정**은
[에이전트 세션 관측](agent-session.md)이, 그룹 헤더·접힘 행 모델은 [사이드바 그룹 전략](sidebar-groups.md)이
각각 단일 출처다. 이 문서는 그 셋 위에 "한 워크스페이스가 들고 있는 **Term들**을 어떻게 나열·조작하는가"만 얹는다.

> **파일 이름과 제목은 아직 "에이전트 목록"이다.** 2026-08-11 개정으로 목록 대상이 에이전트에서 **모든 Term**
> (터미널·브라우저·파일 포함)으로 넓어졌다(§2). 파일명을 바꾸면 [AGENTS.md](../AGENTS.md)의 두 링크와 교차 참조를
> 함께 고쳐야 해서, 개명은 행 variant 개명(§2)과 같은 후속으로 미룬다. 내용의 권위는 이 문서가 그대로 갖는다.

## 1. 목표 UX

워크스페이스 카드가 지금은 에이전트를 **탭당 대표 1개**로 압축해 보여준다(제목 옆 아이콘 + 4번째 상태줄). 한
워크스페이스에서 에이전트를 둘 이상 돌리면 나머지는 화면에 존재하지 않는다. 목표는 그 압축을 풀어 **그 워크스페이스가
들고 있는 모든 Term을 카드 하위 목록으로** 드러내는 것이다.

```
● my-workspace                          [기본]
  ⎇ main                                     ← 카드 헤더: 활성 Pane의 활성 Term 기준(현행 유지)
  ~/project
  ┌─────────────────────────────────┐
  │ 4  ▁▅▇▃ 2  ▁▅▇▃              ⌄ │      ← 클릭하면 접힘/펼침. 개수 뒤는 running 집계 배지(§2)
  └─────────────────────────────────┘
    ✓ ✶ 배포 스크립트 고쳐줘         1m       ← 마지막 사용자 프롬프트 + 마지막 활동 시각
        project  ⎇ main                      ← 그 Term의 폴더·브랜치(§2.1 — 항상)
        네, 수정했습니다…                      ← 마지막 에이전트 응답(흐린 색)
    ✓ ✶ 빌드 깨짐                  now
        web  ⎇ feat/ui                       ← 다른 디렉터리·worktree면 여기서 드러난다
        원인은 tsconfig…
    zsh                                      ← 에이전트 아닌 터미널(§2)
        project  ⎇ main
    * README.md                              ← 파일 Term, `*` = 저장 안 된 편집
```

- **개수 토글 행이 먼저 오고** 그 아래 행들이 붙는다. 기본은 **펼침**이다 — 접기는 카드가 길어질
  때 사용자가 선택하는 것이고, 기본을 접힘으로 두면 이 기능의 목적(안 보이는 것을 드러내기)이 첫 화면에서
  무효가 된다.
  > **정정(2026-07-26)**: 처음엔 "1개면 토글 없이 행 하나"였다(토글이 군더더기라고 봤다). 실사용에서 에이전트
  > 하나짜리 카드를 접을 수 없어 목록이 길어지는 게 불편하다는 피드백을 받아 바꿨다 — 접기는 개수가 아니라
  > **"이 카드를 지금 얼마나 펼쳐 둘 것인가"**의 문제다.
- **목록을 낼지 말지**(개정 2026-08-11, 사용자 결정):
  - 에이전트가 **하나라도 있으면** Term이 1개여도 낸다(위 2026-07-26 정정을 그대로 지킨다).
  - 에이전트가 **0이면** Term이 **2개 이상일 때만** 낸다. 터미널 하나짜리 워크스페이스는 카드 헤더
    (`sidebarCardTerm` = 활성 pane의 활성 Term)가 이미 그 Term의 폴더·브랜치를 그리므로 행을 더해도 같은 정보가
    두 번 나올 뿐이고, 대신 **모든 카드**가 토글 때문에 길어진다.
- **토글 라벨은 개수 숫자 `N`뿐이다**(개정 2026-08-12, 사용자 결정). 원래는 `N sessions`였다 — 목록이 에이전트
  전수에서 Term 전수로 넓어져 `N agents`가 개수와 실제 행 수가 어긋났기 때문에 고른 단어였다. 그 자리에 running 집계
  배지가 들어오면서(§2) 단어가 배지와 상태 문구를 밀어내 좁은 사이드바에서 말줄임을 만들어, **단어를 걷고 숫자만**
  남겼다. 세는 대상이 Term 전수라는 사실은 그대로다.
  - 숫자를 배지로 대체하지 **않는** 이유: 배지는 `running`만 세고 숫자는 idle을 포함한 **전체**를 센다. 둘은 다른
    질문이라 한쪽이 다른 쪽을 대신하지 못한다.
  - 종류별로 나눠 적지 않는(예: `2 agents · 1 terminal`) 이유는 그대로다 — 라벨 길이가 구성마다 달라져 말줄임이
    잦아진다(사용자 결정).
- **행을 누르면** 그 에이전트가 도는 자리로 이동한다(§5).
- 카드 높이는 이 내용에 따라 **행마다 다르다**(§3).

**베이스/결정**: 이 배치는 Maru 독립 설계다. 카드 안에 접이식 하위 목록을 두는 형태 자체는 흔한 UI 관용이고, 여기서의
결정은 (1) **압축 대신 전수 나열**, (2) **개수와 무관한 접기 토글**, (3) **기본 펼침** 셋이다. (1)과 (3)은 "안 보이는
실행 중 에이전트를 없는 것처럼 만들지 않는다"에서, (2)는 "길이 제어는 사용자 몫"에서 나왔다.

## 2. 무엇을 나열하는가 — Term 단위 전수

**Term 하나가 행 하나다.** 그 워크스페이스의 **모든 Pane × 모든 Term**을 훑어 전부 행으로 만든다
(`workspace.collectWorkspaceSessions` — 단일 출처).

> **개정(2026-08-11, 사용자 결정)**: 예전에는 `agent_kind != .none`인 Term만, 그리고 `kind == .terminal`인 Term만
> 행이 됐다. 즉 **에이전트를 안 돌리는 셸·브라우저·파일 탭은 목록에 존재하지 않았다**. 아래 "안 보이는 것을 없는
> 것처럼 만들지 않는다"는 원칙은 에이전트만의 것이 아니므로 두 필터를 모두 걷어냈다. 이 목록의 축은 이제
> "무엇이 돌고 있는가"가 아니라 **"이 워크스페이스가 무엇을 들고 있는가"**다.

Pane 단위로 묶지 않는 이유: Pane은 여러 Term을 가로 탭으로 담고 **활성 Term 하나만 화면에 그린다**. Pane당 대표 하나만
내면 같은 Pane의 가려진 탭에 있는 것이 목록에서 사라진다 — 화면에 안 보이는 것을 드러내는 것이 이 기능의
목적이므로 그 압축은 목적과 정면으로 충돌한다. **화면에 보이지 않아도 PTY도 프로세스도 살아 있다**는 사실을 목록이
그대로 반영해야 한다.

**한 Term은 한 행이므로 중복 제거가 필요 없다.** 에이전트를 돌리는 Term은 `agent_kind != .none`이라 에이전트 행으로
그려지고, 같은 Term이 터미널 행으로 또 나오지 않는다. "터미널이 에이전트를 실행 중이면 에이전트만 보인다"는 요구가
별도 판정 없이 이 1:1 규율에서 그대로 나온다 — 에이전트 감지는 Term의 PTY 포그라운드 프로세스가 하므로
(`pollAgentKinds`·`classifyAgent`) `agent_kind`/`agent_state`가 Term마다 붙기 때문이다.

**종류별 표현**은 라이브 재조회로 갈린다(행은 인덱스만 들고 kind를 캐시하지 않는다 — §5와 같은 규율).

| Term | 라벨 | 아이콘 |
| --- | --- | --- |
| 에이전트 | 마지막 프롬프트, 없으면 `종류 · 상태`(§7) | kind 아이콘(✶ claude / ◆ codex) |
| 터미널 | `termLabel`(custom_name > OSC 제목 > cwd basename) | 없음 — 등록된 터미널 아이콘 자산이 없다 |
| 브라우저 | `termLabel`(패널 라벨) | `web` |
| 파일·마크다운 | `termLabel`(파일 basename), 저장 안 된 편집이 있으면 앞에 `*` | 탐색기 트리와 **같은 분류기**(`chrome.file_tree_icon.classify`) |

**아이콘은 이름줄 선두에 인라인으로 둔다**(개정 2026-08-11, 사용자 결정). 예전에는 행 왼쪽에 독립 gutter
(`icon_cols = 3`)를 잡고 아이콘을 **슬롯 세로 중앙**에 놓았는데, 두 가지가 문제였다.

- **비용**: 글리프 하나 때문에 그 행의 **모든 줄**이 3칸(실측 사이드바 348px·cw 8이면 24px, 폭의 7%)을 냈다.
  정작 잘리는 것은 폴더·브랜치·마지막 응답 줄이다.
- **효과 없음**: 세로 중앙 배치라 줄 수가 다른 행끼리 아이콘 높이가 제각각이어서, 세로 gutter의 유일한 장점인
  "왼쪽에 아이콘 열이 서서 스캔하기 좋다"를 실제로는 얻지 못했다.

인라인은 이름줄만 밀고 보조줄은 전폭을 쓴다. 아이콘 자산이 없는 일반 터미널 행도 `icon_slot_reserve`로
**자리는 잡아** 목록 안에서 라벨 좌단이 어긋나지 않게 한다.

**gutter 배치는 남기지 않는다**(사용자 결정) — 위 두 문단이 그 이유이고, 선택지를 남기면 같은 목록에
두 레이아웃을 유지·검증해야 한다. `agents` 배열은 접기 토글 삼각 전용으로만 남는다.

**행 전체는 `session_row_indent_cols`만큼 들여쓴다.** 카드 하위 목록이라는 위계가 보이지 않으면 카드와 행이
같은 좌단에서 시작해 "펼쳐진 목록"으로 안 읽힌다(사용자 피드백). 아이콘이 그 열에 오고 이름 본문은 거기서
`icon_cols`만큼 더 간다. 보조줄은 **이름 본문과 같은 열**에 맞춰(호출자가 indent를 한 칸 더 준다) 아이콘만
왼쪽으로 튀어나온 hanging 배치가 된다. 값은 **1칸**이다 — 위계를 보이게 하는 최소치이고, 좁은 사이드바에서
2칸은 여백이 과하다는 피드백을 받아 줄였다.

**접기 토글 삼각(▶/▼)만 gutter에 남는다.** 텍스트 줄에 두면 1칸이라 "눌러야 할 토글"로 안 읽혔다(피드백 2회).

아이콘을 이름 **문자열**에 섞지 않고 **별도 셀**로 내는 이유는 이름줄이 `widen_icons = false`이기 때문이다 —
제목에 우연히 섞인 등록 PUA가 2칸으로 커지는 걸 막는 규칙이라, 아이콘을 문자열 앞에 붙이면 같은 규칙에 걸려
1칸으로 쪼그라든다(예전 "깃 아이콘이 너무 작다" 피드백과 같은 현상). 핀(📌)과 같은 방식이다.

파일 아이콘을 탐색기 트리와 같은 분류기로 뽑는 이유는 같은 파일이 두 곳에서 다른 아이콘으로 보이면 같은 것으로
읽히지 않기 때문이다. dirty 마커를 라벨 **앞**에 두는 이유는 에이전트 행이 상태 마커를 같은 자리(라벨 선두)에 두기
때문이다 — 한 목록에서 "행 앞이 상태"라는 읽기 규칙이 하나로 유지되고, 뒤에 붙이면 우측 정렬된 시각과 자리를 다툰다.

> **미해소 — dirty 마커가 둘이다.** 파일 패널 **헤더**는 같은 dirty를 `●`(U+25CF)로 그린다(`dock_layout.dirty_col`).
> 사이드바는 사용자 지정대로 `*`를 쓴다. 한 상태에 마커가 둘인 것은 정합이 필요한 부채다.

**행 variant 이름은 아직 `agent`/`agent_toggle`이다.** 이제 터미널·브라우저·파일도 이 variant를 쓰지만, 개명하려면
`app_session.zig`의 exhaustive switch 25곳을 함께 고쳐야 해서 동작 변경과 기계적 개명이 한 diff에 섞인다. 개명은
후속으로 분리한다.

정렬은 **트리 순서**(Pane 순회 → Pane 안 Term 순서)를 쓴다. 상태나 시각으로 재정렬하면 같은 자리의 세션이 상태
변화마다 목록에서 튀어 클릭 대상이 흔들린다.

**기존 대표 표시는 제거한다.** 제목 옆 대표 아이콘과 4번째 상태줄(파형/✓)은 이 목록으로 **대체**된다(사용자 결정).
같은 정보가 두 곳에 서로 다른 형태로 나오면 어느 쪽이 권위인지 알 수 없고, 대표 하나를 고르는 규칙
(`tabAgentRepresentative`의 blocked > running > idle > unknown 우선순위)도 목록 앞에서는 의미가 없다.

**정정(사용자 결정 2026-08-12): `running` 집계 배지를 되살리되, 자리는 카드가 아니라 `sessions` 토글 행이다.**
위 제거는 "목록이 항상 보인다"를 암묵적으로 가정했는데, 목록은 `agents_collapsed`로 **접힌다**. 접히면 무엇이
도는지가 화면 어디에도 남지 않아 이 문서가 내세운 «안 보이는 것을 없는 것처럼 만들지 않는다»가 접힘에서 정확히
뒤집혔다(사용자 보고: "세션을 닫아도 파형은 돌았으면").

되살리는 것이 위 근거와 충돌하지 않는 이유는 **다른 정보이기 때문**이다. 제거된 상태줄은 여럿을 대표 하나로
압축한 것이고, 배지는 **종류별로 몇 개가 도는가**를 센다(`tabRunningCountsByKind`) — 목록이 답하지 못하는 질문이고
대표 선택 규칙이 개입하지 않는다.

**자리를 카드에서 토글 행으로 옮긴 이유**(사용자 보고 2026-08-12: "세션 위의 부모 탭에서도 나온다 — 없애 달라"):
카드에 두면 바로 아래 세션 행의 파형과 **같은 파형이 위아래로 겹쳐** 보여, 요약과 상세가 한 화면에서 서로를
가린다. 토글 행은 목록의 접힘과 무관하게 **항상 한 줄** 있으므로, 카드에 4번째 줄을 만들지 않고도 "무엇이 몇 개
도는가"가 늘 보인다 — 되살린 원래 근거를 카드 없이 지킨다. 카드 상태줄은 §2 본문대로 **비워 둔다**.

- 자리: `sessions` 토글 행의 개수 라벨 뒤. 형태는 `▸ 1  ▁▅▇▃ 2  ▁▅▇▃ · 진행중`이다.
- **라벨은 개수 숫자만**이다(`1 sessions` → `1`). 배지가 옆에 오면서 단어가 배지·상태 문구를 밀어내 좁은 폭에서
  말줄임을 만들었다(사용자 결정). 숫자는 남긴다 — 배지는 **running만** 세므로 idle을 포함한 전체 세션 수는 숫자만이
  답한다(둘은 다른 질문이다).
- 형태: 종류마다 `▁▅▇▃`(현재 프레임) + **한 칸** + 개수. **개수가 1이면 숫자를 생략**한다(파형이 이미 "하나"를
  말한다). 종류가 둘이면 **두 칸** 띄워 나란히 둔다(`▁▅▇▃ 2  ▁▅▇▃`) — 파형·개수 간격과 같은 한 칸이면 어디까지가
  한 배지인지 흐려진다. 숫자를 파형에 붙여 쓰면 마지막 바에 달라붙어 읽기 어렵다(사용자 피드백).
- **배지는 접힘과 무관하게 항상** 붙는다. 카드에서 걷어낸 뒤로 이 줄이 집계의 유일한 자리이기 때문이다.
  반면 뒤따르는 대표 상태 요약(`· 진행중`)은 **접혔을 때만**이다 — 펼치면 각 행이 자기 상태를 보여줘 잉여이고,
  배지와 달리 목록이 답할 수 있는 질문이다.
- **종류 아이콘은 붙이지 않고 색으로 가른다**(사용자 결정). 그래서 색칠이 codepoint로는 종류를 알 수 없어,
  문자열을 만든 쪽이 열 구간(`BadgeSpan`)을 기록하고 색칠 루프가 그대로 읽는다. 배지 본문은 시작 열을 **인자로**
  받는다(`runningBadgeText`) — 앞의 개수 라벨 폭이 span에 안 실리면 색만 왼쪽으로 밀린다.
- **색칠 순서**: 같은 줄에 배지 파형(종류별 색)과 요약 파형(대표 kind 색)이 공존하고 둘 다 같은 블록 문자라,
  색칠 루프는 `badge_spans`를 스피너 판정보다 **먼저** 본다. 뒤집으면 두 종류 배지가 모두 대표 한 색이 된다.
  오염 방지는 row 종류(`.agent_toggle`)로 좁히는 것이 맡는다 — slot만 맞추면 다른 행의 같은 열이 물든다.
- `running`이 0이면 배지는 빈 문자열이고 개수 뒤 간격도 붙이지 않는다(꼬리 공백이 상태 문구를 밀지 않게).

목록 행의 개별 마커(파형·`✓`·`?`)는 그대로 둔다 — 배지는 요약이고 행은 상세다.

### 2.1 행마다 폴더·브랜치를 표시한다

카드 헤더의 브랜치·경로줄은 지금처럼 **활성 Pane의 활성 Term 하나**를 기준으로 둔다(`tab.activePane().activeTerm()`).
그건 "지금 보고 있는 곳"을 말하는 줄이라 그대로가 맞다. 대신 **에이전트 행마다 그 Term의 폴더·브랜치를 함께** 낸다.

한 워크스페이스 안에서도 Pane마다 작업 디렉터리가 다를 수 있고, git worktree를 쓰면 **브랜치까지 다르다**. 그런데
비활성 Term도 계속 돈다 — "화면에 안 보여도 살아 있다"가 이 목록의 전제인 이상, 그 에이전트가 **어디서** 도는지도
같은 이유로 드러나야 한다.

**차이가 있을 때만 표시하지 않는다.** 조건부로 두면 "줄이 없음"이 **카드와 같다**와 **아직 cwd를 모른다**(OSC 7도 커널 조회도 답을 못 준 상태 — 2026-08-12에 축이 2단이 되며 훨씬 드물어졌다)
두 가지를 동시에 뜻하게 되어, 사용자가 매번 어느 쪽인지 추론해야 한다. 항상 같은 자리에 같은 형식으로 두는 편이 읽기 쉽다.

표기는 **짧게** 한다 — 사이드바는 좁아 절대 경로와 브랜치를 한 줄에 넣으면 양쪽 다 잘린다.

- 폴더와 브랜치는 **각각 한 줄**이다. 처음엔 한 줄에 이어 붙이기로 했으나, 실제 화면에서 브랜치가 잘렸다
  (`feat/session-host-durabl…`) — 사이드바 폭에서 둘을 한 줄에 넣을 수 없다는 것이 실측으로 확인됐다.
- 폴더: 경로 전체가 아니라 **마지막 세그먼트**만(`maru2`). 폭이 좁아 전체 경로는 어차피 잘린다.
- 브랜치: git repo 안일 때만 그 아래 줄에(카드 보조줄과 같은 규칙).

데이터는 이미 **Term 단위**로 존재한다(`termGitBranch`·`sidebarCwdPath`). 브랜치는 cwd가 바뀔 때만 `.git/HEAD`를
walk-up해 캐시하므로 비활성 Term을 함께 읽어도 비용이 늘지 않는다.

## 3. 행 모델과 동적 높이

사이드바는 이미 **가변 높이 행**을 다룬다. `sidebar.Row`가 union이고 `rowHeight`/`rowTop`/`slotAt`/`contentHeight`가
고정 나눗셈이 아니라 **행 높이 누적**으로 좌표를 환산한다(그룹 헤더가 카드보다 낮은 것을 이 방식으로 이미 처리한다).
따라서 카드 높이를 카드마다 다르게 만드는 것은 새 메커니즘이 아니라 **기존 프리미티브의 확장**이다.

`Row`에 두 종류를 더한다.

| Row | 내용 | 높이 |
| --- | --- | --- |
| `card` | 기존(이름·브랜치·경로) | **줄 수로 계산**(고정 slot 폐기) |
| `agent_toggle` | `N agents` + 접힘 표시. 소속 tab 인덱스 | 한 줄 + 여백 하나(그룹 헤더보다 얇게 — 카드에 딸린 부속으로 읽히게) |
| `agent` | ① 상태·kind·라벨·시각 ② 폴더·브랜치(§2.1) ③ 마지막 응답(보강 성공 시) | **1~3줄** |

`agent` 행의 줄 수는 고정이 아니다 — ①은 항상, ②는 cwd를 아는 한 항상, ③은 대화 보강이 성공했을 때만 나온다.
높이 계산은 이 셋을 세어 정한다.

카드 높이가 고정 `card_slot_h`에서 **줄 수 기반**으로 바뀌는 것이 이 슬라이스의 핵심 변경이다. 지금은 브랜치·경로줄이
없어도(git repo 밖) 슬롯 높이가 그대로라 빈 공간이 남는다. 줄 수 기반으로 바꾸면 그 낭비가 사라지고 에이전트 행도 같은
규칙으로 얹힌다.

**구현됨(2단계).** 줄 기하는 chrome이 소유한다 — `sidebar.Metrics`(줄 높이·줄 스텝·카드 여백·헤더 행 높이)를
`Metrics.init(cell_height, header_row_h)`가 cell에서 파생하고, `cardHeight(lines, m) = blockHeight(lines, m) + 2×여백`이
카드 높이의 단일 출처다. 여백은 cell×0.375로 잡아 **4줄 카드가 옛 고정 슬롯(cell×5.2)과 같은 높이**가 되므로, 이번
변경은 줄이 적은 카드의 빈 공간만 없앤다(회귀 가드 테스트로 고정). platform은 `sidebarCardLines(tab)`으로 줄 수를 세어
`Row.card.lines`에 실어 준다 — 그 함수가 **행 높이와 렌더가 공유하는 단일 출처**이고, 조건(브랜치·경로·상태줄)을 카드
조립부와 1:1로 맞춘다.

부수 효과 하나: 옛 고정 슬롯에서는 블록이 슬롯 안에 세로 중앙 정렬돼 **줄이 늘 때마다 이름줄이 위로 올라갔다**. 동적
높이에서는 카드가 자라고 이름줄은 카드 상단 여백 아래 고정된다(블록중앙 오프셋이 항상 여백과 같아진다). 리네임 caret도
같은 계산을 공유하므로 함께 상단 정렬된다.

**불변식**: `rowTop`/`slotAt`/`contentHeight`는 이 세 종류를 모두 누적 대상으로 다뤄야 한다. 하나라도 빠지면 클릭 좌표와
렌더 좌표가 어긋나 "보이는 곳과 눌리는 곳이 다른" 회귀가 난다(그룹 헤더 도입 때 이미 겪은 클래스).

### 3.0 줄 수가 바뀌면 반드시 다시 투영한다

행 높이는 투영 시점의 줄 수(`Row.card.lines` / `Row.agent.lines`)로 굳는다. 그 값이 굳은 **뒤에** 줄 수가 바뀌면
밴드·hit-test가 쓰는 높이와 실제로 그려지는 글자가 어긋나, 활성 밴드가 이름줄이 아니라 아래 줄에 걸리고 클릭이
이웃 행에 닿는다. 실측으로 확인된 변화 경로가 셋이다(전부 사용자 제보):

| 경로 | 왜 늦게 바뀌나 |
| --- | --- |
| 새 워크스페이스 | 관측(cwd·git 브랜치)이 채워지기 **전에** 투영된다 — 그 순간엔 브랜치가 없어 1줄 |
| Term 전환(터미널 ↔ web 패널) | web Term은 cwd·브랜치가 없어 카드가 1줄, 터미널은 3줄 |
| 에이전트 응답 도착 | 응답 줄이 새로 생겨 행이 한 줄 늘어난다 |

**고정 높이(min-height)로 덮지 않는다.** 그러면 1줄 카드도 3줄 자리를 차지해 목록이 그만큼 길어지고, 이 절의 전제
("카드 높이는 내용에 따라 다르다")와 정면으로 충돌한다. 어긋남의 원인은 높이가 변하는 것이 아니라 **변한 뒤 다시
투영하지 않는 것**이다. 그래서 카드는 매 tick 줄 수를 대조해(`reprojectSidebarIfCardLinesStale`), 에이전트 행은
응답 유무가 바뀔 때 재투영한다.

### 3.1 활성 밴드는 카드 + 목록 전체를 덮는다

활성 워크스페이스의 하이라이트 밴드는 카드 하나가 아니라 **그 카드에 딸린 에이전트 목록까지 한 덩어리로** 칠한다.
목록은 그 워크스페이스의 부속이므로, 카드만 칠하면 "어디까지가 이 워크스페이스인지"가 화면에서 끊긴다.

`view()`가 활성 카드 row를 찾은 뒤 이어지는 `agent_toggle`/`agent` row가 끝나는 지점까지 높이를 누적해 밴드
하나로 낸다(`bandFillSpan`). 호버·드롭 밴드는 종전대로 row 하나만 덮는다 — 그쪽은 "지금 가리키는 대상"이라
범위가 넓어지면 오히려 어디를 누르는지 흐려진다.


**목록 행 호버는 전용 색(`row_hover_bg`)을 쓴다.** 활성 카드의 목록 행은 **활성 밴드 위에 놓이므로**, 카드 호버색
(`tab_hover_bg` — 배경↔활성 중간)을 겹치면 활성색보다 어두워 호버가 사라지고, `tab_active_bg`를 겹치면 활성색과
**완전히 같아** 역시 구분이 0이다(실제로 그 상태였다 — 사용자 제보). 그래서 배경→활성 방향을 한 번 더 연장한 색을
쓴다. 사용자가 사이드바 색을 바꿔도 "호버가 활성보다 한 톤 밝다"는 관계가 유지된다.

### 3.2 밴드 기하는 클릭 판정과 같다

**모든 밴드(카드·헤더·호버·드롭)는 그 행이 실제로 눌리는 구간과 같은 rect를 쓴다.** 호버 하이라이트는 "지금
누르면 이게 눌린다"는 표시라, 클릭 판정(`slotAt` — 사이드바 폭 × 행 높이)과 눈에 띄게 다르면 어긋난 것으로
읽힌다. 실제로 그 상태였다(사용자 제보 2건, 2026-07-28).

| 밴드 | 옛 기하 | 증상 | 지금 |
| --- | --- | --- | --- |
| 카드 | 행에서 사방 `card_gap`(rich 8px) 인셋 | 밴드 밖 8px 띠를 눌러도 카드가 눌린다 | **행 전체**(인셋 0) |
| 목록 행 | 행에서 사방 `card_gap` + `list_pad_v/2` 인셋 | 1줄 토글 행(26px)이 6px 띠로 쪼그라들어 글자를 가로지른다 | 행에서 사방 **`list_pad_v/2`**만 |

`card_gap`은 이제 **카드 텍스트 좌측 들여쓰기 전용** 토큰이다 — "떠 있는 카드"(별개 rect로 분리) 룩은 클릭
정합과 맞바꿨다(사용자 결정). 목록 행만 한 겹(`list_pad_v/2`) 들이는데, 이는 (a) 목록 행이 카드에 딸린 부속임을
보이고 (b) 활성 밴드 위에서 위아래 행과 맞닿지 않게 하려는 것이며(사용자 피드백), 인셋이 얕아 클릭 판정과
어긋나 보이지 않는다. 목록 행 밴드가 글자를 반드시 덮는 근거: 행 높이 = 글자 블록 + 위아래 여백(≥`list_pad_v`)
이므로 `list_pad_v/2` 인셋으로는 글자 블록을 침범할 수 없다(`listRowBandV`).

### 3.3 span 기하는 chrome 함수 하나에서만 나온다

밴드와 **겹쳐** 그려지는 것들 — per-card 배경 tint, 좌측 accent 막대, 드래그 고스트 밴드/삽입선, nest 타깃
하이라이트 — 은 색이 카드별 RGB라 chrome op(role 기반)으로 실을 수 없어 platform이 직접 그린다. 그렇다고
**기하까지 platform이 다시 계산하면 반드시 드리프트한다**: 실제로 밴드 인셋을 바꿨을 때 platform 쪽 `card_gap`
산술이 남아 막대만 밴드 안쪽에 떠 보였다.

그래서 span 기하는 chrome의 두 함수가 단일 출처다.

| 함수 | 답하는 질문 |
| --- | --- |
| `cardSpanEnd(rows, index)` | 이 카드의 span은 어디서 끝나나(뒤따르는 `agent_toggle`/`agent` row까지) |
| `spanRect(rows, from, to, w, m)` | 그 구간의 rect는 무엇인가(x=0·w=사이드바 폭·y=앞선 row 높이 누적·h=구간 합) |

`bandFillSpan`은 `spanRect` 결과를 그대로 quad로 만들고, platform(`rebuildSidebar`)은 같은 두 함수를 불러
**헤더 높이와 색만** 더한다(스크롤은 `sidebarScrollClipQuad`가 뺀다). platform에는 이제 row 높이 누적 루프가
없다 — 밴드 rect를 바꾸면 겹쳐 그려지는 것들이 자동으로 따라온다.

## 4. 접기 상태

토글 상태는 **워크스페이스(Tab)에 저장**한다 — 그룹의 `group_collapsed`와 같은 자리, 같은 수명이다. workspace 파일에
영속하지 않는다: 에이전트 구성은 세션마다 달라지고(어제 2개, 오늘 0개), 접힘 상태만 남으면 복원 후 빈 토글이나 어긋난
상태가 된다. **파생 상태는 영속하지 않는다**는 기존 규율(에이전트 아이콘·상태와 동일)을 그대로 따른다.

에이전트가 1개 이하로 줄면 토글 행 자체가 사라지므로 저장된 접힘 값은 무시된다(다시 2개가 되면 기본 펼침).

## 5. 클릭 라우팅

에이전트 행을 누르면 **세 단계**로 그 자리에 도달한다.

```
1. 그 Term이 속한 워크스페이스로 전환   (다른 카드였다면)
2. 그 Term이 속한 Pane으로 포커스        focusPaneByPtr
3. 그 Pane 안에서 그 Term 탭 활성화       focusTerm
```

셋 다 기존 함수가 있다. **3단계가 핵심**이다 — Pane까지만 이동하면 그 Pane의 현재 활성 탭이 보일 뿐, 사용자가 목록에서
지목한 에이전트는 여전히 가려진 탭에 있다.

행이 가리키는 Term이 사이 tick에 사라졌을 수 있다(사용자가 닫음·프로세스 종료). 행은 **Term 포인터가 아니라 인덱스
경로(tab/pane/term)** 를 들고, 클릭 시점에 재조회해 유효하지 않으면 무동작한다(stale 포인터 deref 금지 — 사이드바 드래그
경로에서 이미 겪은 UAF 클래스).

토글 행 클릭은 접힘만 바꾸고 포커스를 옮기지 않는다.

## 6. 렌더 경계

현재 `buildSidebarDrawList`는 `names`/`branch_lines`/`path_lines`/`status_lines` **고정 4배열**을 row 인덱스로 병렬
색인한다. 카드 한 장이 최대 4줄이라는 가정이 인터페이스에 박혀 있어 가변 개수의 에이전트 행을 실을 수 없다.

**행 목록으로 일반화한다**: 카드/토글/에이전트를 구분하지 않고 `{ 소속 row, 들여쓰기, 텍스트, 역할(색), 선행 아이콘 }`의
평탄한 줄 배열을 넘기고, row별 시작 인덱스와 개수를 함께 준다. 렌더러(.m)는 지금처럼 "row 안 몇 번째 줄"만 알면 되고,
줄 수 상한이 인터페이스에서 사라진다.

색·아이콘은 지금 규율을 유지한다 — kind는 브랜드색(claude 코랄 / codex 청록), 상태는 별도 표현, 대화 텍스트는 흐린 색.
글리프는 **터미널 폰트가 보유한 것만** 쓴다(미보유 코드포인트는 CoreText fallback으로 넘어가 글리프가 어긋난다 — 기존
아이콘 선정에서 이미 겪은 문제).

## 7. 마지막 대화 보강

행에 **마지막 사용자 프롬프트**와 **마지막 에이전트 응답**을 함께 보여준다. 이 데이터는 화면이 아니라 각 CLI가 남기는
**세션 기록 파일**에서 읽는다.

**왜 화면이 아닌가**: 상태 판정(`❯` 프롬프트, `esc to interrupt` 같은 짧은 마커)과 달리 대화 **본문**을 화면 위치로 뽑는
것은 프롬프트 박스 테두리·줄바꿈·들여쓰기에 훨씬 민감하다. 더 결정적으로, `/clear`를 하거나 응답이 길어 프롬프트가 스크롤
밖으로 밀리면 그 텍스트는 **화면에 존재하지 않는다**. 화면은 대화의 렌더 결과이지 대화가 아니다.

**왜 훅이 아닌가**: 세션 파일과 Term을 잇는 데 provider 훅(사용자 config 수정)이 필요하지 않다는 것을 실측으로 확인했다
(§7.2). 훅은 사용자의 provider 설정 파일을 Maru가 고쳐 쓰고 설치·제거·자가정리를 유지해야 하며, 사용자가 그 설정을
손대면 조용히 깨진다. 그 비용을 치를 만한 정확도 이득이 없다.

### 7.1 계약

1. **선택적 보강이다.** 매핑·파싱에 실패해도 행은 아이콘·상태·시각으로 정상 동작하고, 대화 줄만 비운다. 이 계약이 없으면
   provider가 포맷을 바꿀 때 목록 전체가 죽는다.
2. **파일을 추측하지 않는다.** provider가 자식 env로 밝힌 세션 신원으로만 파일을 고른다(§7.2.1). 신원을 얻지
   못하면 **아무것도 보여주지 않는다** — 그럴듯한 후보를 고르는 것이 바로 틀린 대화를 띄우는 길이었다.
3. **스캔 범위를 좁힌다.** provider별로 서브에이전트 기록을 반드시 배제한다(§7.3).
4. **tail만, mtime 변화 시에만, throttle.** 파일 전체를 파싱하지 않는다.

### 7.2 매핑 — 실측으로 확정한 것

설계 후보 셋을 실제 데이터로 검증했고, **둘이 반증됐다**.

| 후보 | 결과 |
| --- | --- |
| 프로세스 시작 시각 ↔ 세션 시작 시각 매칭 | ❌ **반증**. `--continue`/`--resume`이 흔해 프로세스는 방금 떠도 파일 시작은 며칠 전이다. 정답을 아는 프로세스로 대조해 **틀린 세션을 고르는 것**을 확인했다(차이 -2.3일까지 관측). |
| 매핑을 한 번 확정하고 고정 | ❌ **반증**. `/clear`로 **같은 프로세스가 세션 파일을 갈아탄다**(같은 pid가 파일 A로 대화하다 파일 B로 이동). 고정하면 그 시점부터 영원히 옛 대화를 보여준다. |
| 활동 상관(그 시점에 갱신된 파일) | ❌ **폐기**(아래) |
| **provider가 밝힌 세션 신원**(자식 env) | ✅ 채택 |

**활동 상관을 폐기한 이유**: 한동안 채택했지만 결국 추측이었고, 그 추측이 실제로 틀린 대화를 보여줬다 —
새로 띄운 터미널에 직전 세션의 대화가 붙고(그 순간 최신 파일이 옛 세션 것이라), 같은 작업 디렉터리에서
에이전트 둘을 돌리면 서로의 대화를 물었다(둘 다 같은 "최신 파일"을 고른다). 시간 비교·형제 충돌 회피 같은
보정을 얹을수록 코드만 늘고 여전히 휴리스틱이었다. **틀린 대화를 보여주느니 비운다**(계약 1)는 원칙과도
정면으로 어긋났다.

### 7.2.1 채택안 — provider가 자식에게 내려주는 세션 신원

두 provider 모두 **자식 프로세스 환경변수**로 자기 세션을 밝힌다. 그 값이 곧 파일을 지목하므로 추측이 없다.

| | 환경변수 | 파일 결속 |
| --- | --- | --- |
| claude | `CLAUDE_CODE_SESSION_ID` | 그 값이 **파일명 그 자체**(`<id>.jsonl`) |
| codex | `CODEX_THREAD_ID` | rollout 파일명의 접미사(`rollout-<ts>-<thread_id>.jsonl`), `session_meta.id`와 같은 값 |

**왜 자식인가**: 두 provider 모두 자기 프로세스 env에는 이 값이 없다(실측). 자식을 띄울 때만 주입한다. 그래서
`proc_listchildpids`로 에이전트 pid의 직속 자식을 열거하고 `KERN_PROCARGS2`로 그 env를 읽는다 — argv 파싱에
이미 쓰던 경로다.

**적대적 검증으로 확인·정정한 것**:

- 자식은 **직속**이다(손자가 아니다) — `proc_listchildpids`로 잡힌다.
- `proc_listchildpids`의 반환값은 **자식 개수**다. 형제 API(`proc_listpids`·`proc_listpgrppids`)가 바이트를
  돌려주므로 나누고 싶어지지만, 나누면 자식 2개가 0으로 접혀 **이 경로 전체가 조용히 무동작**이 된다(실제로
  그 버그를 넣었다가 실측으로 잡았다).
- 자식은 항상 존재하지만(claude는 `caffeinate`를 장수 자식으로 둔다) **세션 신원을 가진 자식은 Bash 도구 실행
  중에만** 있다. 그래서 한 번 얻은 값을 캐시한다.
- `/clear`로 세션이 갈리면 새 id가 내려오므로 자동으로 따라간다(신원이 바뀌면 매핑을 버리고 새로 잡는다).

### 7.2.2 보강 — claude 상태줄 훅(옵션, 기본 on)

§7.2.1은 **자식이 존재할 때만** 신원을 읽는다. 도구를 한 번도 실행하지 않는 세션은 그 창이 없어 대화 줄이 빈다.
그 빈틈을 claude 상태줄로 메운다 — `sidebar.agent-transcript-hook`으로 끌 수 있다(기본 on).

**무엇을 쓰는가**: claude는 `settings.json`의 `statusLine.command`를 매 턴 실행하면서 **stdin으로 JSON**
(`session_id`·`transcript_path`·cwd·`rate_limits`)을 주고 **stdout을 상태줄에 그린다**. 우리는 stdin만 쓰고
stdout에 아무것도 내지 않으므로 **화면이 바뀌지 않는다**. 스크립트는 `session_id`를
`<cache>/maru/agent-sessions/<MARU_PANE_ID>`에 적고 Maru가 그 파일을 읽는다. `MARU_PANE_ID`는 PTY에 이미 주입하는
값이라 **어느 pane의 세션인지가 자동으로 붙는다** — 소켓도 포트도 없이 파일 하나다.

**사용자 커스텀 상태줄은 지우지 않고 감싼다.** `statusLine`은 필드가 하나뿐이라 나란히 둘 자리가 없고, 그렇다고
건너뛰면 그 사용자는 이 기능을 아예 못 쓴다. 그래서 원래 명령을 우리 스크립트가 **같은 payload로 실행**하고
stdout을 통과시킨다.

```sh
payload=$(cat)
if [ -n "$MARU_PANE_ID" ]; then … session_id 기록 … fi
# ===== maru: 아래는 설치 전에 쓰시던 상태줄입니다(제거 시 그대로 복원됩니다) =====
printf '%s' "$payload" | sh -c '<원래 명령>'
# ===== maru: 사용자 상태줄 끝 =====
```

`settings.json`은 **JSON이라 주석을 못 쓰므로** 표식은 스크립트 파일 안에 둔다. 사용자가 열어봐도 어디부터 자기
것인지 보인다. 다만 **표식은 사람이 읽으라고 있는 것이지 우리가 믿는 근거가 아니다** — 복원의 근거는 아래 마커다.

**원본의 단일 출처는 설치 마커다**(`.maru-statusline-installed`, 스크립트와 같은 디렉터리). 설치할 때 감쌀 원래
명령을 **스크립트보다 먼저** 마커에 적고, 갱신·복원 모두 마커를 우선 신뢰한다.

```
maru-statusline v2
wrapped 1 <본문 바이트 수>
<원래 명령 — 바이트 그대로>
```

`wrapped 0`은 "설치 시점에 감쌀 것이 **없었다**"는 확정 정보다. 마커가 없거나 깨진 것과 다르다 — 그 둘은 "모른다"다.

**길이를 적는 이유**: v1은 본문을 "파일 끝까지"로 읽었다. 그래서 마커가 어느 지점에서 잘려도 **짧고 틀린 명령으로
유효하게 파싱**됐고(절단 길이를 전수로 돌려 실측), 그 쓰레기가 옵션을 끌 때 사용자 `settings.json`에 복원됐다.
길이가 어긋나면 "모른다"로 접힌다.

**왜 스크립트를 믿으면 안 되나**: 스크립트는 우리가 매 실행마다 덮어쓰는 파일이다. 그 안의 wrap을 유일한 근거로
삼으면, 어떤 이유로든 wrap 없는 본문을 한 번 쓰는 순간 원본이 **영구 소실**된다. 실제로 그렇게 잃었다 — maru
인스턴스 여럿이 동시에 살아 있을 때 A가 `스크립트 없음 → 사용자 명령 감싸 설치`를 도는 사이 B가 `스크립트(아직
없음) 읽기 → settings(이미 우리 것) 읽기`로 엇갈려 **`refresh` + wrap 없음**으로 판정했고, B가 A의 결과를 wrap
없는 본문으로 덮었다. 사용자 상태줄은 그대로 사라졌고 되찾을 근거가 남지 않았다.

**규율**:

- **"없다"와 "못 읽었다"를 절대 같게 보지 않는다.** 이 구분이 나머지 규율 전체를 떠받친다. `settings.json`이나
  스크립트를 읽지 못하면(권한·크기·**0바이트**·손상 JSON) 그것은 "원래 없었다"가 아니라 **모른다**이고, 모르는
  자리에서는 **아무것도 쓰지 않는다**. 0바이트를 "없음"으로 접었더니 claude가 파일을 쓰는 중간 창에 걸려
  `.install`로 판정하고 마커에 "감쌀 것 없었음"을 확정으로 찍어 원본을 지웠다(적대 검증 실측).
- **파괴적 다운그레이드 금지.** `refresh`인데 스크립트에 wrap이 없고 마커도 없으면(= 마커 이전 설치이거나 손상)
  **아무것도 쓰지 않는다**. 감쌌던 것이 있었는지 없었는지 모르는 상태에서 wrap 없는 본문을 쓰는 것은 손실을
  확정하는 일이다. 사용자가 `statusLine`을 자기 것으로 되돌리면 그때 `wrap_existing`으로 정상 복귀한다.
  스크립트 **파일이 없으면**(못 읽은 것이 아니라 정말 없으면) 예외로 재생성한다 — `statusLine`이 없는 파일을
  가리키는 상태를 두는 편이 더 나쁘다. 다만 그 재생성은 **마커에 확정을 남기지 않는다**.
- **모르는 값은 마커에 기록하지 않는다.** `wrapped 0`은 나중에 `statusLine` 키를 지우는 근거가 되므로, 확정이
  아닌 자리에서 찍는 순간 그 자체가 손실 경로다. 마커를 갱신하는 것은 설치·감싸기(= settings를 읽어 확인한
  경우)와 스크립트 wrap을 마커로 **승격**하는 1회 마이그레이션뿐이다.
- **인스턴스 간 직렬화.** read-modify-write 전체를 마커 파일 `flock(LOCK_EX|LOCK_NB)`으로 감싼다. 논블로킹이라
  데드락이 없다. **경합과 "잠글 수 없음"은 다르다** — `EWOULDBLOCK`이면 다른 인스턴스가 같은 일을 하고 있으니
  물러나고, 권한이나 파일시스템 때문에 애초에 잠글 수 없으면 **락 없이 진행한다**(락을 넣기 전과 같은 위험이지
  조용한 영구 무동작보다 낫다). 락 fd에는 `CLOEXEC`이 필수다 — exec된 자식(PTY 셸·curl·ssh)에게 새면 그 자식이
  사는 내내 모든 인스턴스에서 설치도 제거도 조용히 멈춘다(같은 규율: `app_instance_lease.zig`). 잠근 뒤에는
  **inode를 다시 확인한다**: 다른 인스턴스가 마커를 지우고 새로 만들면 이름은 같아도 다른 파일이라 락이 아무것도
  막지 못한다. 훅을 **끈** 사람에게는 마커를 만들지 않는다(잠글 것이 없으면 잠그지 않는다).
- **원자적 교체.** 스크립트와 `settings.json`은 같은 디렉터리 임시 파일에 쓰고 `fsync`한 뒤 `rename`으로 갈아
  끼운다. 반쯤 쓰인 스크립트를 claude가 실행하거나, 우리가 죽은 자리에 잘린 `settings.json`이 남는 일이 없다.
  대신 rename이 가진 두 성질을 **명시적으로 되돌린다**: 심링크를 따라가지 않고 대체하므로 실체 경로를 해석해
  그쪽에 쓰고(dotfile 관리자가 `settings.json`을 심링크로 두는 구성이 흔하다), 새 파일이 umask 기본 권한을 받으므로
  기존 파일의 권한을 승계한다(`0600`이 조용히 `0644`가 되지 않게). 마커만은 락 fd에 **제자리로** 쓴다 —
  rename하면 락이 걸린 inode가 바뀌어 직렬화가 풀린다. 그 대신 부분 쓰기는 즉시 0으로 되돌리고, 길이 필드가
  잘림을 잡는다.
- **쓰기 직전에 근거를 다시 본다.** `statusLine`은 우리가 읽은 값이 아직 그대로일 때만 갱신한다
  (compare-and-swap). 읽기와 쓰기 사이에는 스크립트 파일 쓰기가 통째로 들어 있고, 그 사이 claude나 사용자가 바꾼
  값을 덮으면 그것이 이 사고의 축소판이다. 읽지 못한 파일은 **새로 쓰지 않는다** — 옛 코드는 읽기 실패를 "빈
  객체"로 접어 0바이트 창에서 사용자 설정 전체를 `statusLine` 하나만 남기고 날렸다.
- **끄기는 복원을 확인한 뒤에 지운다.** 복원 쓰기가 실패했는데 스크립트·마커를 지우면 사용자가 나중에 파일을
  고쳐도 되살릴 것이 없다. 현재 상태를 못 읽었으면 `settings.json`도 우리 파일도 건드리지 않는다.
- **복원은 직전 상태로만.** `statusLine`이 없는 상태에서 설치하면 마커에 `wrapped 0`을 적는다. 이전 세대의 원본을
  마커에 남겨두면 옵션을 끌 때 사용자가 스스로 지운 상태줄이 되살아난다 — 그건 복원이 아니라 시간 여행이다.

- 설치 위치는 claude 자신의 규칙을 따른다 — `$CLAUDE_CONFIG_DIR`이 있으면 그것, 없으면 `$HOME/.claude`. **그
  디렉터리가 없으면 아무것도 하지 않는다**(claude를 안 쓰는 사람의 홈에 디렉터리를 만들지 않는다). 트랜스크립트를
  읽는 경로도 같은 판정을 쓴다 — 한쪽만 `$HOME/.claude`로 고정하면 훅은 엉뚱한 곳에 설치되고 대화는 영원히 빈다.
- `settings.json`은 `statusLine` 키만 갈아 끼우고 나머지는 보존한다. **읽거나 파싱하지 못하면 아무것도 쓰지
  않는다** — 우리가 모르는 상태의 사용자 파일을 고치는 것보다 두는 편이 안전하다.
- pane 게이트는 **우리 기록만** 건너뛴다. 조기 `exit`으로 묶었더니 Maru 밖 세션에서 사용자 상태줄이 통째로
  사라졌다(실행 검증에서 잡았다). 감싼 명령은 pane이 없어도 항상 실행한다.
- 우리 기록이 **사용자 명령보다 먼저**다. 그 명령이 실패해도 신원은 이미 남는다.
- 감싼 명령은 `sh -c '<원래 명령>'`으로 실행하므로 홑따옴표를 `'\''`로 끊어 붙인다. **되찾을 때는 그 이스케이프를
  풀어 원문으로 되돌린다** — 풀지 않으면 갱신마다 한 겹씩 더 쌓여 명령이 서서히 망가진다.
- 옵션을 끌 때 복원할 원본은 **마커 → 스크립트 wrap** 순으로 찾는다. 둘 다 없으면(마커 이전 설치) `statusLine`
  키를 지운다 — 우리 스크립트를 지우면서 그것을 가리키는 포인터를 남길 수는 없다. 사용자 것이면 애초에 건드리지 않는다.
- provider **hook event**는 설치하지 않는다. 과거 `MARU_AGENT_MAP_HOOK_V2` 계열은 provider 실행 흐름에 개입했지만
  상태줄은 표시 전용이라 실패해도 세션이 멈추지 않는다 — 이 차이가 상태줄을 택한 이유다
  ([에이전트 상태 감지 §사이드바 대화 표시와의 경계](agent-session.md)).
- 이 경계는 CI 게이트 `mise run test-provider-session-removal`이 지킨다. 옵션이 꺼진 기본 경로에서 provider 파일
  **무변경**, 켠 경로에서 `statusLine` 외 JSON 바이트 보존과 감싼 사용자 명령 보존을 무인 검증한다. 켠 뒤 늘어나는
  파일은 스크립트와 마커 **둘뿐**이고, 끄면 둘 다 사라진다. 같은 게이트가 **스크립트가 wrap을 잃은 채 남은 상태**로
  다시 켜도 마커에서 원본이 되살아나는지까지 본다(위 경합 사고의 회귀 테스트).
- 위 규율 중 **파일에 대한 넷**(직렬화·원자 교체·쓰기 순서·"모르면 손대지 않음")은 같은 게이트의 두 번째 테스트가
  제품 경로에서 따로 검증한다. 마커 **내용** 로직만 덮여 있던 동안에는 락을 통째로 지워도, 원자 교체를 제자리
  쓰기로 되돌려도, 마커를 스크립트 뒤에 써도 게이트가 green이었다(적대 검증이 뮤테이션으로 실측). 지금은 셋 다
  red가 된다.

**codex는 해당 없다** — 외부 스크립트를 실행하는 상태줄/훅 설정이 없어 자식 env 경로만 쓴다.

**한계**: Bash 도구를 한 번도 쓰지 않는 세션은 신원을 얻을 수 없어 대화 줄이 빈다(§7.2.2를 끈 경우). 코딩 에이전트의 실사용에서는
거의 항상 잡히지만, 설명만 요청하는 세션은 그렇다. 원격 host-backed Term도 pid가 이 기계에 없어 마찬가지다 —
어차피 기록 파일도 이 기계에 없으므로 옛 폴백은 **로컬의 엉뚱한 세션을 물 위험**이 있었고, 폴백 제거가 그것도
함께 없앴다. 둘 다 계약 1대로 "빈칸"이라는 안전한 실패다.

활동 상관이 성립하는 근거도 실측했다.

- **유휴 세션은 스스로 갱신되지 않는다.** 최근 활동 세션 21개를 60초 관찰해 갱신된 파일은 **활동 중인 1개뿐**이었다.
  하트비트 같은 배경 쓰기가 없으므로 "갱신됨 = 그 세션이 방금 말했다"가 성립한다.
- **교대 입력을 정확히 추적한다.** 같은 작업 디렉터리에 세션 둘을 두고 번갈아 입력하며 매 시점의 최신 파일을 정답과
  대조했다 — **claude 4/4, codex 3/3**.
- **동시 활동도 갈린다.** 두 세션을 동시에 돌려도 실제 파일 쓰기 시점은 1.6초 벌어졌고, 파일 mtime은 **나노초 해상도**다.
- **재개는 같은 파일에 append된다**(양쪽 CLI). 세션이 이어질 때 파일이 새로 생기지 않으므로 추적이 끊기지 않는다.

고정하지 않고 매번 따라가는 방식은 `/clear`·resume·재시작에 **자동으로 적응**하며 상태를 덜 든다.

### 7.3 provider 어댑터

`agent_observer`가 provider별 규칙 집합을 두는 것과 같은 패턴으로, **경로 규칙 + 레코드 파서 + 서브에이전트 배제**를
provider마다 둔다. 위쪽(행 모델·렌더·throttle)은 공통이다.

| | claude | codex |
| --- | --- | --- |
| 경로 | 작업 디렉터리를 인코딩한 디렉터리 아래 세션 파일 | 날짜 계층 아래 세션 파일 |
| 작업 디렉터리 판별 | 디렉터리 이름으로 즉시 | 파일을 열어 첫 레코드에서 읽어야 함 |
| **서브에이전트 배제** | 서브에이전트는 `<세션 id>/` **하위 디렉터리**에 쌓인다 → **직속 파일만** 스캔 | 서브에이전트가 **같은 계층에 섞인다** → 첫 레코드의 세션 출처 필드가 사용자 세션인 것만 |
| 대화 추출 | 사용자/어시스턴트 레코드의 텍스트 블록 | 응답 레코드의 role + content |

**서브에이전트 배제는 선택이 아니라 필수다.** 실측에서 한 작업 디렉터리의 직속 파일이 54개인데 하위까지 포함하면
**1805개**였고, 서브에이전트 기록이 거의 항상 더 최근이다. 배제하지 않으면 사용자 카드에 서브에이전트 내부 대화가 뜬다
(검증 중 실제로 이 오류를 재현했고, 그 덕에 이 제약을 찾았다).

codex 쪽 실측은 더 극단적이다 — **최근 파일 40개 중 32개가 서브에이전트**였다. claude는 하위 디렉터리라 "직속만
스캔"으로 공짜로 배제되지만, codex는 같은 계층에 섞이므로 **후보를 열어 `session_meta.thread_source == "user"`를
확인하는 것 말고는 방법이 없다**. 그래서 codex만 후보를 여러 개(§7.7) 열어본다.

### 7.4 성능

| 측정 | 값 |
| --- | --- |
| claude: 작업 디렉터리(54개)에서 최신 파일 찾기 | 0.14ms |
| codex: 최근 파일 20개만 열어 판별 | 1.3ms (전량 233개 파싱은 82ms — 61배) |
| 대용량 파일 읽기 | 79MB 파일도 **끝 256KB**만 |
| tail 256KB 회수율 | 절단이 실제 일어나는 파일(256KB 초과) **71개 전수 100%** |
| 마지막 대화가 파일 끝에서 떨어진 거리 | 중앙값 **3KB**, 최악 **14KB**(256KB의 18배 여유) |

Term 8개 기준 매 tick 스캔해도 1.1ms지만 **tick마다 할 이유가 없다**. mtime이 변한 파일만, throttle을 두고 읽는다.
관측 주기 규율은 [에이전트 세션 관측](agent-session.md)의 polling 정책을 따른다.

**이 여유는 claude 이야기다.** codex는 프롬프트가 훨씬 뒤로 밀려(위) `max_tail_bytes`만으로는 부족하고, §7.8의
병합이 그 자리를 메운다.

**claude에서 `max_tail_bytes`가 충분한 이유는 구조적이다.** 대화가 끝나면 그 뒤로는 더 쓰이지 않으므로 마지막 프롬프트·응답은
항상 파일 **끝 근처**에 있다. 거대한 도구 결과는 그 대화 **앞**에 쌓이지 뒤에 쌓이지 않는다. 전수 측정에서도 최악이
끝에서 14KB였다. 회수에 실패한 세션들은 절단과 무관하게 **파일 전체를 읽어도 대화 레코드가 없는** 것들이었다
(막 시작했거나 중단된 세션 — 전부 22KB 이하).

### 7.5 무엇을 어디에 그리는가

행은 최대 4줄이고(`sidebarGlyphRow`의 줄 인덱스가 2비트다) 4단계가 그 마지막 칸을 쓴다.

| 줄 | 대화 **전** | 대화 **후** |
| --- | --- | --- |
| 1 | `Claude Code · ✓ 대기중` | `✓ 배포 스크립트 고쳐줘`  ⟨우측 `12m`⟩ |
| 2 | 📁 폴더 | 〃 |
| 3 | ⎇ 브랜치 | 〃 |
| 4 | — | `네, 수정했습니다…` |

- **프롬프트는 줄을 늘리지 않는다.** 1행의 종류 이름·상태 문구가 자리를 내준다 — 이 행에서 알고 싶은 건 "무엇을
  시켰는가"이고, 진행 여부는 앞의 **마커**(파형·✓)가 이미 말한다. 종류는 gutter 아이콘에 남는다. 마커는
  `agentStatusLine` 결과의 첫 공백 앞을 그대로 쓴다(따로 만들면 상태 문구가 바뀔 때 둘이 어긋난다).
- **응답만 줄을 늘린다.** 그래서 줄 수 계산(`sidebarAgentRowLines`)과 조립부의 append 조건이 1:1이어야 한다 —
  어긋나면 응답이 행 높이 밖에 그려져 아래 행을 침범한다.
- 기록을 못 읽으면(계약 1) 두 자리 모두 예전 모습으로 돌아간다. 즉 **4단계는 순수 가산**이다.

**마지막 활동 시각**(`now`·`12m`·`3h`·`2d`)은 1행 **우측**에 고정 폭으로 앉는다(✕ 왼쪽, 간격 한 칸).

- 기준은 **출력 > 기록 mtime > 빈칸** 순이다. 주 기준은 `agent_last_output_ms`(그 Term이 마지막으로 출력한 시각),
  폴백은 그 Term에 매핑된 세션 기록 파일의 mtime이다.
- **폴백이 필요한 이유**: `agent_last_output_ms`는 awake clock이라 앱을 새로 켜면 0이다. 그런데 사이드바를 보며
  "언제 마지막으로 움직였나"를 가장 알고 싶은 순간이 바로 그때다. mtime은 wall clock이라 앱 생애와 무관하고, 이미
  매핑된 파일이라 추가 IO가 없다.
- **mtime은 대화만이 아니라 도구 실행도 따라간다**(실측: 도구만 연달아 도는 세션의 mtime이 25초 전 —
  `tool_use`/`tool_result`가 그때그때 기록된다). 그럼에도 출력을 우선하는 이유는 PTY 출력이 파일 쓰기보다 촘촘하고
  즉각적이며, 캐시의 mtime은 마지막으로 **폴링해 읽은** 시점 기준이라 최대 폴링 주기만큼 뒤처지기 때문이다.
- 매핑 자체가 없으면(cwd 미확인·디렉터리 없음·codex 후보 밖) 폴백도 못 쓰고 빈칸이다.
- **상대 표기**다. 절대 시각(`14:23`)이 아닌 이유는 이 줄이 답하는 질문이 "언제였나"가 아니라 "얼마나 됐나"라서다 —
  방금 멈춘 것과 어제 멈춘 것을 한눈에 가르는 게 목적이고, 정확한 시각이 필요하면 그 자리로 가면 된다.
- 폭을 **최대 3칸**으로 묶고 큰 값은 `99d`에서 멈춘다. 제목이 이 폭만큼 일찍 잘리므로, 폭이 들쭉날쭉하면 잘리는
  지점이 행마다 달라져 목록이 어수선해진다.
- **제목이 시각 왼쪽에서 멈춘다.** 안 그러면 긴 프롬프트의 말줄임표 위에 시각이 덧그려져 둘 다 못 읽는다(고정 ✕에서
  겪은 것과 같은 문제).
- 카드 헤더와 그룹 헤더에는 두지 않는다 — 카드는 워크스페이스이지 한 에이전트가 아니라 "언제"의 주체가 모호하고,
  아래 목록의 행마다 자기 시각이 이미 있다. 접힘 토글에는 **대표 에이전트의 시각**을 둔다(요약이 유일한 단서라
  파형 색과 같은 이유). 이름 편집 중에는 숨긴다(핀·✕와 같은 이유).
- 접힘 토글의 시각은 **대표 에이전트의 것**이다 — 아이콘·상태·시각이 서로 다른 에이전트를 가리키면(예: 대기중인
  것은 A인데 시각은 B의 최근 활동) 읽는 사람이 오해한다. "가장 최근 활동"이 더 궁금할 수 있지만, 그러려면 펼치면 된다.

### 7.6 알림 본문에도 싣는다

provider가 주는 알림 문구는 `Claude is waiting for your input`처럼 **어느 세션인지 말해주지 않는다**. 에이전트를
여럿 돌리면 배너만 보고는 무엇에 대한 알림인지 알 수 없어 결국 창을 뒤져야 한다. 제목의 위치 라벨(탭 › 팬)이 자리를
알려준다면, 마지막 프롬프트는 **무엇을 시킨 건지**를 알려준다.

```
제목:  main › zsh · Claude Code
본문:  Claude is waiting for your input
       ❯ 배포 스크립트 고쳐줘
       네, 수정했습니다…
```

- **프롬프트가 먼저**다 — OS 배너는 몇 줄만 보여주고 자르므로 식별에 더 쓸모 있는 쪽이 앞에 와야 한다.
- 대화 줄은 표시 상한(`max_text_bytes`)보다 **짧게** 자른다. 긴 원문을 통째로 넣어봐야 뒤가 안 보이면서 알림만 커진다.
- 대화를 못 읽었으면 provider 문구만 그대로 나가 **기존 동작과 byte-identical**이다.
- 이는 [에이전트 세션 관측](agent-session.md)의 "OSC 9 본문을 가공 없이 전달한다"를 **본문 뒤에 덧붙이는 방향으로**
  확장한 것이다 — provider 문구 자체는 고치지 않는다.

### 7.7 codex가 claude와 다른 네 가지

공통(행 모델·렌더·throttle·매핑 규율·계약)은 그대로 두고 **provider 차이만** 흡수했다.

| | claude | codex |
| --- | --- | --- |
| 경로 | 작업 디렉터리를 인코딩한 디렉터리 | **날짜 계층** `YYYY/MM/DD/rollout-….jsonl` |
| 작업 디렉터리 판별 | 디렉터리 **이름**으로 즉시 | 파일을 열어 **첫 `session_meta`**에서 |
| 서브에이전트 배제 | 하위 디렉터리라 직속 스캔으로 공짜 | `thread_source == "user"` 확인 필수(실측 40개 중 32개가 서브에이전트) |
| 대화 추출 | `last-prompt` + `assistant`의 `text` 블록 | **`event_msg`의 `user_message`/`agent_message`** |

**후보를 여러 개 열어본다.** codex는 디렉터리 이름이 아무것도 말해주지 않아 파일을 열어야 신원을 안다. 그런데
서브에이전트가 상위를 차지하므로 하나만 열면 대부분 빗나간다. 그래서 stat은 전수로 돌려(실측 232개 ≈ 1ms) mtime
내림차순 상위 20개만 열고, `thread_source == "user"`이고 cwd가 같은 **첫 후보**를 고른다. 여는 쪽이 진짜 비용이라
(전량 파싱 82ms) 이 분업이 성능을 결정한다.

**날짜로 자르지 않는다.** resume은 옛 파일에 append하므로(양쪽 CLI 실측) 며칠 전 디렉터리의 파일이 방금 갱신될 수
있다. 날짜 상위 N일만 훑으면 그 세션을 영영 놓친다.

**`response_item`이 아니라 `event_msg`를 본다.** `response_item`의 `role == "user"` 메시지에는 환경 컨텍스트·규칙
파일·이미지 마커가 섞여 들어와, 사람이 친 말과 구분하려면 주입 태그 목록(`<environment_context>`·`<user_instructions>`
·`<skills_instructions>` 등 10종)을 따라다녀야 한다. 반면 `event_msg`의 `user_message`/`agent_message`는 **UI에
보여줄 원문**이라 그 필터가 통째로 필요 없다.

이건 추측이 아니라 **codex 자신의 추출기와 같은 선택**이다 — `codex-rs/state/src/extract.rs`가 세션 기록에서 대화
미리보기를 뽑을 때 정확히 이 이벤트를 읽는다. 같은 소스에서 규칙 둘을 더 가져왔다:

- `## My request for Codex:` 마커가 있으면 **그 뒤만** 쓴다(`strip_user_message_prefix`). 컨텍스트를 덧대 보낼 때
  실제 요청의 시작을 이 마커가 표시한다.
- 이미지만 보낸 턴은 본문이 비므로 `[Image]` 자리표시자를 둔다. 빈 줄로 두면 그 턴이 없던 일이 된다.

### 7.8 못 찾은 항목은 지우지 않는다

**provider 무관 공통 규율이다.** tail에서 프롬프트나 응답을 못 찾았을 때 그 자리를 **비우지 않고 이전 값을 지킨다**.

codex에서 이게 필수임이 실측으로 드러났다 — 마지막 응답은 파일 끝 근처(5~173KB)지만 그에 대응하는 사용자
프롬프트는 **최대 22MB 앞**에 있었다(긴 턴에 추론·도구 레코드가 대량으로 쌓인다). claude는 최악 14KB라 사정이
전혀 다르다.

`max_tail_bytes`를 22MB로 키우는 건 답이 아니다 — 매 갱신 비용을 그만큼 올리면서 더 긴 턴에는 또 부족하다. 대신
**사용자가 프롬프트를 친 직후에는 그게 파일 끝**이라 작은 tail로 반드시 잡히고, 그 뒤 턴이 길어져도 이 병합이 값을
지킨다. 못 지키면 턴이 길어지는 순간 "무엇을 시켰는지"가 화면에서 사라진다.

claude에도 같은 규율을 적용한다. 지금 회수율이 높아 실익은 작지만, **규율이 하나여야** 두 provider의 코드가 갈리지
않고 provider가 포맷을 바꿔 회수가 나빠져도 조용히 비지 않는다.

**후보가 Term의 마지막 출력보다 한참 과거면 거부한다.** 활동 상관의 전제는 "그 Term이 방금 말했고 그 순간 갱신된
파일이 그 세션"인데, 픽이 **그 순간 최신 파일**만 보고 시간 관계를 보지 않으면 전제가 깨진다 — 새로 띄운 에이전트가
아직 아무것도 쓰지 않았는데(시작 화면만 그렸다) 직전 세션 파일이 여전히 최신이라 그걸 물고, 새 터미널에 남의 옛
대화가 붙는다(사용자 제보 — 시작 화면뿐인 pane 둘에 서로 다른 과거 대화가 떴다). claude는 시작 직후 몇 초간 자기
파일이 없고, codex는 시작하면서 즉시 `session_meta`를 포함해 수십 KB를 쓰므로 이 창이 거의 없다(실측).

거부한 뒤 claude는 **매핑을 확정하지 않고 물러난다** — 곧 자기 파일이 생기므로 폴링 주기마다 다시 본다(단일 디렉터리
스캔이라 값싸다). codex는 트리 전체를 훑어야 해서 시도 시각을 기록하고 다음 출력까지 기다린다.

**세션 파일이 바뀌면 먼저 비운다.** 안 그러면 병합이 옛 세션의 대화를 새 세션 행에 남긴다. 그래서 소유 버퍼는
슬라이스가 아니라 **오프셋**으로 든다 — 병합이 구조체를 복사하므로, 슬라이스였다면 사본의 필드가 원본 버퍼를
가리켜 dangling이 된다.

## 8. 관측 가능성

- 매핑 결과(어느 Term ↔ 어느 세션 파일)와 확정/미확정 여부를 `MARU_DEBUG` 게이트 아래 남긴다. **대화 본문·작업
  디렉터리 경로는 로그에 남기지 않는다**([필수 프로젝트 규칙](project-rules.md)의 redaction 기준 — 홈 경로가 그대로 드러난다).
- 목록 자체는 기존 observer 스냅샷을 소비한다. 사이드바 전용 상태 판정을 새로 만들지 않는다.

## 9. 단계 분해

각 단계가 독립적으로 동작하고, 3단계까지만 해도 사용자에게 쓸모가 있다(대화 텍스트 없이 목록·이동만으로도 목적 달성).

1. **문서**(이 PR) — 계약과 경계 확정.
2. **동적 높이 ✅** — 카드 높이를 줄 수 기반으로. 에이전트 행 없이 기존 카드만으로 회귀 없음을 고정했다(§3 "구현됨").
3. **에이전트 행 목록 ✅** — Term 전수 나열, 행마다 폴더·브랜치(§2.1), `N agents` 토글, 클릭 라우팅(워크스페이스 → Pane → Term), 기존 대표 표시 제거, 활성 밴드 확장(§3.1).
4. **claude 어댑터 ✅** — 매핑(활동 상관·직속 스캔) + 대화 추출 + 행 렌더(§7.5) + **알림 본문 보강**(§7.6).
5. **codex 어댑터 ✅** — 경로(날짜 계층)·신원 확인(`session_meta`)·레코드 모양·주입 블록 필터 차이를 흡수(§7.7).

**목록 기능은 여기까지로 완결됐다.** §1의 목표 UX(전수 나열·접기·클릭 이동·폴더/브랜치·마지막 대화·활동 시각)가
전부 구현됐다. 남은 것은 §11 범위 밖 항목들이다.

## 10. 검증

- **행 모델**: Term 0/1/2+ 각각에서 `rowTop`·`slotAt`·`contentHeight`가 일치하는지(보이는 곳 = 눌리는 곳).
- **목록 게이트**(§1, 2026-08-11): 터미널 1개 + 에이전트 0이면 목록이 **없고**, Term 2개면 생기며, 그중 하나가
  에이전트가 돼도 **행 수와 토글 개수가 그대로**인지(= 같은 Term이 에이전트 행과 터미널 행으로 쪼개지지 않는다).
  종류에 따라 라벨(상태 문구 vs `termLabel`)과 gutter 아이콘이 갈리는지.
  → `app_session.zig`의 `"사이드바 세션 목록: 터미널도 행이 되고, 에이전트 Term은 한 행으로만 나온다"`.
- **인라인 아이콘**(§2, 2026-08-11): 아이콘이 이름줄 **같은 행**에 width 2로 오고, **이름줄만** `icon_cols`만큼
  밀리며 **보조줄은 안 밀리는지**(gutter와의 결정적 차이). `icon_slot_reserve`가 글리프 없이도 같은 만큼 밀어
  아이콘 없는 행의 라벨 좌단을 맞추는지.
  → `coretext_frame_builder.zig`의 `"buildSidebarDrawList inline_icons: name line only shifts; aux lines keep full width"`.
- **클릭 라우팅**: 가려진 Term(비활성 Pane의 비활성 탭)을 지목했을 때 3단계가 모두 수행되는지. 사라진 Term을 가리키는
  행이 무동작인지. 목록이 Term 전수라 `.agent` variant만으로는 에이전트 행을 못 고른다 — **라이브 `agent_kind`로**
  집어야 한다(기존 테스트가 그렇게 고쳐졌다).
- **접기**: 토글이 개수와 무관하게 생기고 접히는지. 영속되지 않는지.
- **드롭 좌표**: pane grip을 "사이드바 빈 영역"에 떨어뜨리는 경로는 좌표와 hit-test가 **같은 투영**을 봐야 한다.
  목록 행이 카드 아래에 붙으면서 stale `sidebar_rows`로 잰 빈 영역이 실제로는 행 위가 되는 회귀가 드러났다
  (행 위 드롭은 `visibleTab`이 null이라 no-op).
- **폴더·브랜치**: 서로 다른 cwd의 Pane 둘과 worktree(브랜치가 다른 경우)에서 각 행이 자기 값을 내는지. git repo 밖 Term은 브랜치를 생략하는지.
- **매핑**: fixture 기반 — 유휴 파일 무시, 교대 활동 추적, `/clear`로 파일이 바뀌었을 때 새 파일을 따라가는지,
  서브에이전트 기록이 후보에서 배제되는지.
- **degrade**: 세션 파일이 없거나 포맷이 달라도 행이 아이콘·상태·시각으로 정상 동작하는지.
- **활동 시각**: 표기가 폭 상한(3칸) 안에 머무는지, 제목이 시각 왼쪽에서 멈추는지(겹치지 않는지), 시각이 없을 때
  제목이 ✕ 앞까지 가는지.
- **대화 소비 경로**(4단계): 캐시에 대화를 넣었을 때 라벨이 프롬프트로 바뀌고 상태 마커가 남는지, 줄 수가 정확히
  하나 늘고 4를 넘지 않는지, 알림 본문에 프롬프트가 응답보다 **먼저** 붙는지, 대화가 없으면 알림이 provider 문구와
  byte-identical인지.

**파일 → 캐시 구간은 단위 테스트가 덮지 않는다.** 실제 FS 배치와 provider 포맷에 의존하므로 fixture로 고정하면
"우리가 믿는 포맷"만 검증하게 된다. 이 구간은 앱을 띄워 확인한다 — 그래서 계약 1(선택적 보강)이 안전망이다.
