# 하단 상태표시줄

창 바닥에 붙는 **창 전폭** chrome 띠. 좌측은 "지금 어디에 있나"(맥락), 우측은 "지금 무슨 일이 일어나나"(상태)를 보여준다.

이 문서는 **구현된 것**을 적는다. 계획·후보는 마지막 §6에만 둔다 — 코드보다 앞선 서술을 만들지 않는다.

## 1. 왜 전폭인가

사이드바 아래까지 지나간다. 그래서 `dock_layout.Geometry.workspace`(사이드바·타이틀바를 뺀 작업영역) **안에 살지 않는다**.

이 결정이 구현 전체의 모양을 정했다: `compute`가 `available`을 만들기 **전에** 창 높이에서 먼저 깎는다(`usable_h`). 그래야 terminal·dock·divider·조기 반환이 한 지점에서 정합한다. 작업영역-폭이었다면 `available` 안에서 처리했을 것이다.

```
backing_height_px
  └─ usable_h = backing_height_px − status_bar_h
       ├─ status_bar : x=0, y=usable_h, w=backing_width_px  ← 전폭
       ├─ available  : h = usable_h − titlebar_height_px
       └─ dock_available / dock_top
```

## 2. 높이와 여백

| 값 | 상수 | 근거 |
|---|---|---|
| 높이 | `max(status_bar_height_pt = 22, 셀 높이 + 2×status_bar_v_pad_pt)` | **텍스트 행을 담고 여백이 남는 높이**와 폰트 독립 하한 중 큰 쪽. 상단 타이틀바 띠(`computeTitlebarStripPx`)가 쓰는 `@max(cell_height_px, 최소 pt)`와 같은 패턴이다 |
| 텍스트 위아래 여백 | `status_bar_v_pad_pt = 4` | 한쪽. 고정 높이만 쓰면 기본 폰트에서 위아래 2px밖에 안 남아 빡빡했다(사용자 지적) |
| 가장자리 여백 | `status_bar_edge_pad_pt = 8` | 좌·우 안쪽 |
| 항목 간격 | `status_bar_gap_pt = 12` | 아이콘+텍스트 묶음끼리 붙어 보이지 않을 만큼 |

**하한은 폰트 독립이다.** 도크 view bar가 폰트 파생만으로 오르내리던 회귀(실측 53px↔80px)를 피한 이유가 그 하한이다 — 작은 폰트에서 바가 실처럼 얇아지지 않는다.

**다만 높이 자체는 폰트를 따라 커진다.** 텍스트가 터미널 셀 높이를 쓰는 이상 바가 그걸 담아야 하기 때문이다. 고정 높이만 쓰면 폰트를 키웠을 때 세로 중앙 계산이 0으로 포화돼 **글자가 바 아래(창 밖)로 넘친다.** 테스트가 이 계약을 못박는다.

여백 상수(`edge_pad`·`gap`)는 **터미널 폰트에서 파생하지 않는다.** 도크 view bar가 폰트 파생이었다가 폰트를 키우면 같은 아이콘 줄이 오르내리는 회귀를 냈고(실측 53px↔80px) 폰트 독립 pt로 옮겼다. 창 전폭 chrome이라 같은 이유가 더 강하게 적용된다.

**항상 선다.** 도크·사이드바 상태와 무관하다 — 조건부로 만들면 바 높이가 프레임마다 달라져 터미널 grid가 출렁인다.

**끄는 수단은 설정 하나뿐이다** — `status-bar.show = false`(기본 `true`). 바가 창 높이를 실제로 먹으므로 정보보다 행 수가 중요한 사용자에게 되돌릴 길이 있어야 한다. 끄면 높이가 0이 되고 §5.4의 소비처가 **자동으로** 따라온다(게이트가 `statusBarHeightPx` 하나라 목록을 손댈 필요가 없다). 이건 사용자가 명시적으로 바꾸는 설정이지 프레임마다 바뀌는 상태가 아니라, 아래 규칙이 막으려는 대상이 아니다.

**또 다른 예외는 quick terminal(`chrome_minimal`)이다.** 그 모드는 chrome을 통째로 걷어낸다(`paneBarHeightPx`도 0을 돌려 탭 바를 끈다). 위 규칙이 막으려는 것은 **토글되는 상태**이지 세션 생성 시 고정되는 모드가 아니다 — 고정 모드는 프레임마다 바뀌지 않으니 grid가 출렁이지 않는다.

## 3. 배치 규칙 (`chrome/components/status_bar.zig`)

순수 모듈이다(AppKit/renderer/PTY 의존 0, 할당 0 — 호출자가 버퍼를 준다).

- **좌측은 왼쪽부터, 우측은 오른쪽부터** 채운다. 우측을 먼저 배치하고 그 좌단이 좌측의 상한이 된다.
- **부딪히면 우측을 먼저 지킨다.** 우측 항목(개수·상태값)은 폭이 작고 고정적이라 잘리면 의미가 사라지는 반면, 좌측(경로·브랜치)은 길어서 부딪히는 원인 자체가 대개 좌측이다.
- **양쪽 다 뒤쪽 항목부터 통째로 버린다.** 자리를 못 얻는 항목이 나오면 거기서 멈춘다 — 앞이 못 들어간
  자리를 뒤가 차지하면 폭에 따라 **표시되는 항목의 정체가 바뀐다**(긴 브랜치명에 브랜치가 사라지고
  경로가 그 자리로 올라오는 식). 배치는 글자를 자르지 않는다 — 자르는 건 호출자가 텍스트 단계에서 할 일이다(그래야 폭 계산이 한 곳에 남는다).
- **버린 수를 `dropped`로 노출한다.** 조용한 절단은 "다 그렸다"로 읽힌다.
- **배열 순서가 곧 우선순위다.** 좌측은 앞이 더 왼쪽이자 더 오래 살아남고, 우측은 **앞이 더 오른쪽**이다.

폭은 **px로 받는다.** 상태바는 터미널 grid 밖(바닥)이라 grid 행/열이 없다 — `metal_frame.zig`가 `row >= frame.size.rows`인 셀·글리프를 조용히 버리므로 grid 좌표로는 애초에 그릴 수 없다. 항목은 각자 자기 frame을 갖고 절대 px origin에 놓인다.

## 4. 지금 있는 항목

| 자리 | 항목 | 출처 | 없을 때 |
|---|---|---|---|
| 좌 0 | git 브랜치 (`git_branch` 아이콘) | `termGitBranch` — 활성 Term | repo 밖이면 항목 없음 |
| 좌 1 | 작업 경로 (`folder` 아이콘) | `sidebarCwdPath` — `$HOME`을 `~`로 축약 | cwd 없으면 항목 없음 |
| 우 0 | **막힌 에이전트 수** (`hourglass`, 강조색) | `blockedAgentCount` — 창 전체 Term 중 `agent_state == .blocked` | 0이면 항목 없음 |
| 우 1 | 실행 중 에이전트 수 (종류 아이콘) | `runningAgentCount` — 창 전체 Term 중 `agent_state == .running` | 0이면 항목 없음 |
| 우 2 | 안 읽은 알림 수 (`bell` 아이콘) | `notification_unread` | 0이면 항목 없음 |

**왜 이 넷인가.** Maru는 에디터가 아니라 터미널 + 워크스페이스 + 에이전트 세션이다. 그래서 VSCode식 에디터 항목(인코딩·줄바꿈·들여쓰기)은 맞지 않는다 — 편집 중인 문서가 없다. 대신:

- **브랜치·경로**는 사이드바 카드에도 있지만, **사이드바를 접으면 사라진다**. 상태바는 그때도 남는다.
- **막힌 에이전트**가 우측 끝이다. running은 알아서 굴러가지만 blocked는 **사람이 손을 대야** 풀리는데, 지금 보고 있는 터미널이 아니면 알 방법이 없다 — 그래서 가장 시급하다. **모양으로 구분한다**(모래시계 + 테마 accent): 색만 다르면 "저 색이 무슨 뜻인지"를 배워야 하고, running과 같은 아이콘을 쓰면 개수가 무엇의 개수인지 모호해진다. 그래서 한 항목에 두 상태를 섞지 않고 **별도 항목**으로 뒀다.
- **실행 중 에이전트 수**는 상태바가 더할 수 있는 고유한 값이다. 한 번에 터미널 하나만 보이므로 "지금 안 보이는 곳에서 무엇이 돌고 있나"는 다른 UI가 답해 주지 않는다.
- 경로는 **repo 밖에서도 그린다** — 사이드바 카드는 "repo 안일 때만 폴더줄"이지만(카드는 repo 맥락을 보여주는 자리다), 상태바는 "지금 어디에 있나"가 목적이라 repo 밖 cwd가 오히려 유용하다. **의도적 차이**다.

각 항목 텍스트는 바 폭의 **1/3**에서 말줄임한다 — 한 항목이 바를 독차지하지 않게 하고 반대쪽 자리를 남긴다.

**경로만 자르는 방식이 다르다.** 일반 말줄임은 선두를 고정하고 끝을 자르는데(`…`가 뒤에 붙는다), 경로에 그러면
`~/Documents/works…`처럼 **잎(현재 디렉터리)이 먼저 사라진다** — "지금 어디에 있나"가 목적인 자리에서 정작 그
정보를 버리는 셈이다. 그래서 경로는 **컴포넌트 단위로** 줄여 뿌리와 잎을 둘 다 남긴다(`~/a/…/z`,
`chrome/text_layout.zig`의 `elidePathMiddle`). 남기는 꼬리는 들어가는 것 중 가장 긴 것이다 — 경로는 뒤로 갈수록
구체적이기 때문이다. 줄일 중간이 없으면(컴포넌트 2개 이하) 원본을 넘겨 일반 말줄임이 받는다.

### 브랜치 항목을 누르면 — 목록을 띄우고 **명령을 넣어 준다**

로컬 브랜치 목록(`for-each-ref --sort=-committerdate`, 최근 순 상한 200개 중 메뉴에는 12개)을 컨텍스트 메뉴로 띄우고,
고르면 활성 터미널에 **`git switch <name>`을 입력해 준다.** 엔터는 사용자가 친다.

**우리가 checkout을 실행하지 않는 이유**는 `docs/editor-surface.md` §6의 읽기 전용 계약이다 — write git은
`git_read` grant 밖이고, hook 실행·index 쓰기를 우리가 하지 않겠다고 정해 둔 것이다. 실행 주체가 셸이면
dirty tree·충돌·hook 출력이 **평소처럼 사용자에게 보인다**는 이점도 같이 온다.

> ⚠️ **메뉴는 `ui/` 상호작용 계층을 쓰지 않는다.** 재사용한 `components/context_menu.zig`는 색 토큰과 `draw`
> 계약은 따르지만 hit-test를 자기 손으로 한다(`menuRect`/`itemAt`). 그래서 이 기능 안에 규약이 둘이다 —
> **항목 클릭까지는 typed tree**(§5.6), **그 뒤 메뉴는 hand-rolled**다. 브랜치 메뉴만 따로 typed tree로 만들면
> 메뉴 구현이 둘이 되므로 하지 않았고, 공유 컴포넌트를 통째로 옮길 때 함께 간다
> ([이관 후보로 기록](chrome-interaction-migration.md#2-기존-구현-inventory)).

- 목록 읽기는 백엔드 스레드다(`submitBranches`) — 클릭이 UI를 멈추지 않는다. 연타는 `branch_menu_pending`이 막는다.
- 명령 문자열은 순수 함수가 만든다(`git_command.branchSwitchCommand`): **개행을 붙이지 않고**(붙이면 그 순간
  실행된다) 셸 메타문자·공백이 든 이름은 거절한다(손상된 목록이 셸로 흘러들지 않게).

## 5. 렌더 경로에서 지켜야 하는 것

이 다섯은 **화면에서만 드러나는 계약**이라 어기면 조용히 깨진다. **자동 가드가 있는 것과 없는 것이 갈린다:**

| 계약 | 자동 가드 |
|---|---|
| §5.1 배경 레이어 | ✅ 값으로 못박음(`status_bar_layer == 2` + over/header/under 배제) |
| §5.2 strip 클리핑 | ✅ **Chrome Lab 골든이 픽셀로 본다**(`sidebar-status-strip` 시나리오 → `sidebar-strip-stops-above-status-bar`). Zig 쪽 스탬프 테스트에 더해 `.m`이 그 값으로 실제로 자르는지까지 덮는다 |
| §5.3 셀 scissor | ✅ **산술을 Zig로 옮겼다**(`sidebarScissorPx`) — 게이트·클램프·뒤집힘 방지를 순수 함수 테스트가 덮는다. `.m`은 받은 구간을 그대로 쓴다 |
| §5.4 소비처 축소 | ✅ grid 높이·사이드바 뷰포트 단언들이 수치로 고정 |
| §5.5 포인터 삼킴 | ✅ **그려진 quad에서 rect를 읽어** 판정과 대조한다(폰트를 바꿔 가며 3회). 판정식을 테스트에 다시 쓰면 같은 실수를 두 번 적는 것이라 드리프트를 못 잡는다 |

**다섯 다 자동 가드가 붙었다.** 마지막까지 남아 있던 §5.2는 Chrome Lab에 사이드바 strip 시나리오를 더해 닫았다 —
`.m`이 창 바닥까지 그리도록 되돌리는 뮤테이션에 골든이 죽는 것을 확인했다.

### 5.1 배경 quad는 layer 2(bottom)여야 한다

항목 텍스트는 `pane_frames`를 타고 **터미널 레이어**의 셀 패스로 그려진다. 그래서 **아이콘과 라벨이 서로 다른 색을**
가질 수 있다(셀마다 `style.foreground`가 따로다 — blocked 항목이 accent 아이콘을 쓰는 근거). chrome draw-op 경로는
`Op.Text.role`이 op당 하나라 그게 안 되는데, 상태바는 그 제약을 **경로가 달라서** 비껴갔다
([chrome-strategy.md](chrome-strategy.md) 아이콘 절). `.m`의 버킷팅은 `2=bottom · 0=under · 4=header · 그 밖=over`인데, **over는 별도 오버레이 CAMetalLayer**라 터미널 레이어 **전체 위에** 합성된다 — 배경을 거기 두면 **자기 텍스트를 덮는다**(실제로 그 상태로 두 조각이 머지됐다).

bottom은 터미널 레이어 맨 처음이라 그 뒤의 모든 것이 위에 그려진다. 띠를 침범할 수 있는 것들은 이미 막혀 있다 — 터미널 grid는 짧아졌고(§1), 사이드바 배경 strip은 §5.2가 끊고, 사이드바 셀은 §5.3이 자른다.

> ⚠️ bottom 버킷은 값 2 **하나뿐**이라 탭 밴드와 레이어를 공유한다. 테스트가 상태바를 특정할 땐 레이어가 아니라 **기하**(전폭 + 바 y)로 찾아야 한다.

### 5.2 사이드바 배경 strip을 상태바 위에서 끊는다 (ABI v167)

strip은 `.m`이 바닥을 직접 정하는 표면이다([metal-ui-layout.md](metal-ui-layout.md) §5의 승인 예외). Zig가 값을 실어 주는 것 말고는 그 바닥을 옮길 방법이 없어 `MetalFrame.status_bar_height_px`를 냈다.

**높이의 단일 권위는 `dock_layout`이다** — `chromeGeometrySnapshot`이 `dockGeometry().status_bar.h`를 그대로 싣는다. 따로 계산하면 *작업영역을 깎은 값*과 *strip을 자르는 값*이 갈려 덮이거나 틈이 생긴다. 값이 chrome 기하 **스탬프**를 타므로 셀과 같은 프레임에 고정된다.

### 5.3 사이드바 셀 scissor를 아래로도 자른다

`sidebarBandCell`은 세로 경계를 보지 않는다(폭·칸수만 본다) — 스크롤이 0이어도 맨 아래 카드가 띠 안까지 발행된다. 지금까진 drawable 가장자리가 대신 잘라 줘 안 드러났을 뿐이다.

**자를 구간은 Zig가 정한다**(`sidebarScissorPx` → ABI v168 `sidebar_scissor_top/bottom_px`). 게이트("스크롤됐나", "상태바가 있나")와 클램프, 뒤집힌 rect 방지가 전부 그 순수 함수에 있고 `.m`은 받은 구간을 **그대로** 쓴다 — 배치를 아는 곳을 하나로 두는 규율이다([metal-ui-layout.md](metal-ui-layout.md) §5).

자르는 이유가 위아래 서로 다르다: **위**(헤더)는 스크롤된 카드가 헤더 위로 새는 것을 막고 — 스크롤이 0이면 샐 것이 없어 안 자른다 — **아래**(상태바)는 스크롤과 무관하게 자른다. `bottom <= top`이면 아예 안 자른다.

### 5.4 창 높이를 먹는 소비처를 함께 줄인다

`Geometry` 하나가 아니다. 상태바가 높이를 먹으면 다음이 함께 짧아져야 한다:

- **spawn grid** — `gridPadding()`의 bottom으로 흡수한다. 거기서 더하면 `gridFromBacking` **호출부 셋**(spawn config·메트릭 재계산·resize)이 한 번에 정합한다.
- **사이드바 목록 뷰포트**(`sidebarMaxScrollPx`)와 **스크롤바 thumb 분모** — 한 쌍이다. 갈리면 thumb이 트랙 끝에 닿아도 스크롤이 남는다.
- **사이드바 배지 클리핑 하단**(`vp_bottom`).

**바뀌면 안 되는 것**도 있다: `pxTopLeftToPtBottomLeft`(AppKit 좌표 뒤집기의 **원점** — 높이가 아니라 기준선), 시각 벨 full-screen quad, 배경 이미지. 창 전체를 덮는 게 의도인 표면들이다.

### 5.5 포인터를 삼킨다

라우팅이 "어느 pane에도 안 맞으면 활성 surface로 fallback"이라, 안 막으면 상태바 휠이 터미널 스크롤백을 움직이고 클릭이 선택 드래그를 시작한다.

- **휠은 사이드바 판정보다 먼저** 막는다 — 상태바는 전폭이라 사이드바 아래를 지나가고, 뒤에 두면 그 구간이 사이드바 스크롤로 샌다.
- **클릭은 down(`kind == 1`)만** 막고 드래그는 통과시킨다 — 터미널에서 시작한 선택이 상태바 위를 지날 때 끊기면 안 된다.
- 판정은 렌더 rect와 **같은 산술**을 쓴다(`pointInStatusBar` ↔ `appendStatusBarBackground`). 갈리면 보이는 자리와 눌리는 자리가 어긋난다.

## 5.6 상호작용은 typed tree로 발행한다

hover·클릭은 손으로 만들지 않는다. 배치가 정한 슬롯을 `status_bar.publish`가 `chrome/ui/tree`의 `RectEntry`(kind `button` + action)로 내고, 호스트는 그 tree로만 판정한다 — **그리기는 기존 lowering이 그대로** 한다([chrome-interaction-migration.md](chrome-interaction-migration.md) §2의 분리, `chrome/components/divider.zig`와 같은 규율).

- **id는 슬롯 순서가 아니라 의미다**(`ItemId`). 인덱스를 id로 쓰면 브랜치가 없는 repo에서 경로가 첫 슬롯이 되며 id가 밀려 "누른 것과 실행된 것"이 갈린다.
- **자리를 못 얻은 항목은 tree에 없다** — 안 보이면 눌리지도 않는다.
- **열 대상이 없는 항목은 호버도 안 준다.** 눌리는 것처럼 보이는데 아무 일도 안 일어나는 편이 아무 표시도 없는 것보다 나쁘다(지금은 브랜치가 그렇다).
- **호버 rect = 판정 rect**다. 항목 좌우로 `status_bar_item_pad_pt`만큼 넓혀 배경이 글자에 붙지 않게 하되, 넓히는 곳이 `publish` 한 곳이라 **보이는 자리와 눌리는 자리가 구조적으로 같이** 넓어진다. 여백은 항목 간격(`gap`)의 절반보다 작아야 이웃 호버끼리 안 겹치고, 바 밖으로는 clamp된다.
- 클릭은 **이미 있는 표면을 여는 것만** 한다: 알림 → 알림 패널, 에이전트 → 세션 도크, 경로 → 탐색기 도크. 새 UI를 지어내지 않는다.

## 6. 검증의 구조적 구멍과 후속

### 헤드리스로 못 찍는 항목이 있다

`MARU_SCREENSHOT` 단독은 "내용 있는 첫 frame 한 장 뒤 종료"인데, **브랜치·경로는 셸이 OSC 7을 보낸 뒤에야** 값이 생긴다 — 그 프레임엔 좌측 항목이 아예 없다.

**`MARU_SCREENSHOT_DELAY_MS=<ms>`로 캡처를 늦추면 찍힌다.** 관측이 도착한 뒤를 찍으므로 좌측 항목도 헤드리스로 검증된다:

```
MARU_SCREENSHOT_DELAY_MS=1500 MARU_SCREENSHOT=<path> ./zig-out/Maru.app/Contents/MacOS/maru-macos-app
```

> 이 지연 경로는 **두 곳의 draw 게이트를 모두 열어야** 동작한다 — tick 루프의 "generation이 바뀌었을 때만 draw"와 `drawMetalFrame` 안의 같은 조기 반환. 캡처는 renderer의 draw **안에서** 일어나므로, 유휴 셸에서 draw가 끊기면 마감이 지나도 찍을 기회가 없다(둘 중 하나만 열었을 때 `metal_frames_drawn=1`로 멈추는 것을 실측했다).

이 구멍 때문에 §5.1의 결함이 늦게 잡혔다(지연 캡처가 고쳐지기 전이다). 잘못된 레이어는 **배경만 있고 항목이 없던 조각**에서 골랐고(그땐 덮을 텍스트가 없어 증상이 없었다), **좌측 항목 두 조각이 글자가 안 보이는 채로 머지된 뒤에야** 드러났다 — 그 둘은 셸 관측에 의존해 헤드리스로 찍을 수 없었기 때문이다. 알림 항목은 셸과 무관해 첫 frame에 세울 수 있었고, 그때서야 잡혔다.

그래서 셸 무관 항목에는 self-verify 게이트를 뒀다(저장소의 `MARU_FORCE_SPLIT`·`MARU_FORCE_UNFOCUSED_CURSOR`와 같은 성격):

```
MARU_FORCE_NOTIFICATIONS=<n>   # 안 읽은 알림 n개
MARU_FORCE_AGENT=1             # 활성 Term을 running으로
```

> 픽셀 검증 주의: **"배경색이 아닌 픽셀"을 글자로 세면 안 된다.** 바 자신의 안티앨리어싱 가장자리가 섞인다(바 배경과 1단위 차이로 나타난다). 잉크는 밝기로 갈라야 한다. 이 오인 때문에 있지도 않은 "폭 초과" 결함을 한 번 보고했다.

### 정해 뒀지만 지금 하지 않는 것 — strip에 **가장자리**를 넘기기

§5.2가 ⚠️로 남은 자리다. `.m`은 `status_bar_height_px`(**높이**)를 받아 `drawable_h - height`로 strip 바닥을 만든다. 즉 **"바는 창 바닥에 붙어 있다"는 가정이 코드가 아니라 머릿속에 있다** — 바가 위로 가거나 떠 있게 되면 `.m`은 에러 없이 조용히 틀린 값을 계산한다.

**방향은 정해져 있다: 높이 대신 가장자리(`strip_bottom_px` 또는 rect)를 넘긴다.** 근거 셋:

1. 수신자가 **크기에서 위치를 추론하는 일**이 없어진다.
2. 한 기능에 규약이 둘인 상태가 해소된다 — 셀 scissor는 이미 `[top, bottom)` 가장자리를 받는데(§5.3) strip만 높이를 받는다. 읽는 사람이 같은 상태바에서 두 규칙을 배워야 한다.
3. `status_bar_height_px`의 `.m` 소비자는 이제 **strip 하나뿐**이다(scissor가 자기 필드를 갖게 된 뒤로). 단일 소비자인데 이름이 소비처를 안 가린다.

**그런데 지금 단독으로 하지 않는다.** 검증은 하나도 안 늘고 ABI 버전만 올라간다(§5의 동기화 지점 다섯을 뺄셈 하나에 쓰는 셈이다). §5.2가 미검증인 **진짜 이유는 "누가 빼느냐"가 아니라 "strip이 실제로 그려지는지 아무도 안 본다"**이고, 값을 옮겨도 그건 그대로다.

**언제 하나** — 다음 셋 중 하나가 오면 그 김에 함께 한다. 그때는 어차피 그 코드를 여는 참이라 추가 비용이 거의 없고, 반대로 그때도 안 맞추면 규약 둘이 굳는다.

- strip 관련 변경이 생길 때
- 바의 위치·모양이 바뀔 때(전폭이 아니게 되거나, 바닥 고정이 아니게 될 때)
- `.m`이 소유한 표면이 하나 더 같은 값을 필요로 할 때

> **이 판단은 이제 바뀌었다.** 위에서 말한 "strip을 볼 수 있게 만드는 것"을 실제로 했다 — Chrome Lab에 사이드바
> 전체를 그리는 시나리오가 아니라 **strip만 그리는 시나리오**(`sidebar-status-strip`: 빈 프레임 + 사이드바 폭·상태바
> 높이)를 더하면 됐다. 사이드바 셀 합성이 필요할 거라 본 것이 과대평가였다 — strip은 `.m`이 두 값만으로 그리므로
> 값을 실어 주는 것으로 충분했다. 브리지 인자 둘, 시나리오 하나, 골든 하나다.
>
> 남은 것은 **값 규약 정리**(높이 → 가장자리)뿐이고, 그건 여전히 위 트리거 셋을 기다린다. 다만 이제 그 이관을
> 할 때 **골든이 회귀를 잡아 준다** — 검증 없이 값만 옮기던 상황이 아니다.

### 리소스 항목(설계 확정 — 미구현)

"어느 세션이 내 램을 먹고 있나"를 상태바가 답한다. v1은 **이 창의 터미널 프로세스 합계 한 줄**이다
(예: `1.4 GB · 2.6%`) — 앱 자신과 웹 콘텐츠는 창에 귀속되지 않아 뺀다(아래 "창 단위").
탭별 내역 패널은 이 숫자가 쓸모 있다고 확인된 뒤에 정한다 — 패널을 먼저 지으면 쓸모를 모른 채 계층 목록·정렬·
접기·스파크라인까지 딸려 온다.

#### 무엇을 세는가 — 소유 관계를 실측으로 확정했다

macOS에서 Maru에 딸린 프로세스는 **한 가지 방법으로 모이지 않는다.** 2026-08-09 실측:

| 대상 | 부모 | 모으는 법 | v1 |
|---|---|---|---|
| 터미널 셸 + 자손(zsh→claude→도구…) | 앱(in-process) | **backend seam**(`TermRuntimeBackend`)이 pid를 알고 트리를 훑는다 | ✅ |
| 앱 자신(렌더러·글리프 아틀라스) | launchd | `getpid()` | ❌ 제외(아래 "창 단위") |
| host-backed 터미널 | **session host** | host가 `live_child_pid`를 가짐 → RPC 필요 | ❌ 후속 |
| WebKit 콘텐츠/GPU/네트워킹 | **launchd(ppid=1)** | 전체 pid 스캔 + responsible-pid 귀속 | ❌ 제외(아래) |

**⚠️ "앱의 자식을 훑는다"는 틀린 기본기다.** 실측으로 두 번 깨졌다:

1. **WebKit XPC는 우리 자식이 아니다** — `com.apple.WebKit.GPU`의 ppid가 **1**이다. 자식 트리를 아무리 훑어도
   웹 탭 메모리는 안 보인다.
2. **`responsibility_get_pid_responsible_for_pid` 하나로 통일하려던 안도 죽었다** — 그 심볼은 실재하고 root 없이
   동작하며 WebKit XPC를 앱에 정확히 귀속하지만(실측: `SafariPlatformSupport` 10 MB), **fork한 자식은 자기
   자신이 responsible**이라(실측: `yes` pid의 responsible == 자기 pid) 정작 터미널 셸·에이전트를 못 잡는다.

그래서 v1은 **터미널 트리 walk 하나**만 쓴다.

#### 왜 앱 자신도 빼는가 — 상태바는 창 단위다

`TerminalSurface`(창)마다 자기 `AppSession`이 있고 상태바도 창마다 그려진다. 그런데 **앱 프로세스는 앱 전역**이다
— 창이 둘이면 두 상태바가 같은 65 MB를 각각 표시하고, 사용자가 둘을 더하면 실제보다 커진다. 웹(WebKit XPC)도
같은 이유로 창에 귀속되지 않는다.

그래서 규칙을 하나로 정한다: **창 단위로 귀속되는 것만 센다.** v1 항목의 뜻은 "이 창의 터미널 프로세스"이고,
앱 자신·웹 콘텐츠는 들어가지 않는다. 앱 전역 총량이 필요해지면 그건 상태바가 아니라 (후속) 패널의 일이다.

#### 어디에 붙이는가 — app_session이 pid를 만지지 않는다

`pollAgentKinds`가 이미 **모든 탭×pane×Term**을 돌며 `backendFor(term).readObservation`으로 관측을 읽는다.
주기는 둘이다 — 화면/활동 판정은 `agent_observer_interval_ms`(100ms), **프로세스 조회는
`agent_poll_interval_ms`(500ms)**로 따로 스로틀되고 후자만 `include_foreground=true`로 넘어간다.
리소스는 syscall 쪽이므로 **후자 계열**(더 느린 자체 주기)에 붙인다. 그리고 그 관측(`RuntimeObservation`)은 **이미 `foreground_pgid`·`foreground_processes`를
실어 나른다** — 프로세스 신원이 이 seam을 이미 건너고 있다는 뜻이다.

리소스도 **같은 seam**으로 넘긴다(관측 필드 추가 또는 형제 호출). 이득이 둘이다:

1. `app_session`이 pid·libproc을 직접 만지지 않는다 — 플랫폼 조회는 backend 구현 안에 남는다(기존 경계 유지).
2. **host-backed가 재설계가 아니라 구멍 메우기가 된다.** host는 이미 관측 질의에 답하고 `live_child_pid`를
   가지므로, 나중에 그 backend가 같은 필드를 채우면 끝이다. 지금 app_session에서 트리를 훑어 두면 그때 다시 뜯어야 한다.

#### 웹 탭 메모리를 빼는 이유(사용자 결정 2026-08-09)

넣으려면 **문서화되지 않은 심볼**에 의존해야 한다. 이 저장소는 libproc을 쓸 때마다 "모두 macOS 공개
libSystem/libproc API다"를 근거로 달아 왔고([src/pty/macos.zig]), 그 규율을 리소스 표시 하나 때문에 깨지
않는다. **대가는 정직하게 진다** — 이 항목은 "이 창의 터미널 프로세스"만 뜻하고, 마크다운·브라우저 탭
메모리는 빠진다(앱 자신도 위 "창 단위" 규칙으로 빠진다).

#### 측정 API와 두 가지 함정

`proc_pid_rusage(pid, RUSAGE_INFO_V0, &out)` 하나면 된다. **V0을 쓴다** — `ri_phys_footprint`·`ri_user_time`·
`ri_system_time`이 V0에 이미 있고 V2와 값이 같은데(실측 동일), 필드가 11개(96바이트)뿐이라 **손으로 옮기는
extern struct의 틀릴 여지가 가장 작다**. Zig 미러에는 `@sizeOf == 96` comptime 단언을 건다 — 레이아웃 드리프트를
컴파일 타임에 잡는다.

- **함정 ①: 실패하면 구조체를 읽지 마라.** `rc != 0`이면 out이 **안 채워진다** — 실측에서 7.6e12 MB 같은
  쓰레기가 나왔다. 죽은 pid·권한 밖 pid는 상시 발생한다(샘플링 중 프로세스가 사라지는 것이 정상이다).
- **함정 ②: 메모리는 RSS가 아니라 footprint다.** RSS는 공유 라이브러리를 프로세스마다 중복 계산해 트리 합계를
  부풀린다. `phys_footprint`가 활성 상태 보기의 "메모리"와 같은 기준이다.

#### CPU%는 차분이라 규칙이 따로 있다

`ri_user_time + ri_system_time`은 **누적 나노초**다. 백분율은 Δcpu / Δ벽시계이므로:

- **첫 샘플에는 값이 없다**(0%가 아니라 **표시 없음**이다 — 0%는 거짓말이다).
  - ⚠️ 이 규칙은 아래 "표시 폭 고정"과 부딪힌다: 메모리만 먼저 내면 폭이 변해 좌측 경로가 흔들린다.
    **해소 = 두 번째 표본까지 항목 자체를 내지 않는다.** 시작 후 1~2초 뒤 나타나고, 그 뒤로는 폭이 고정된다.
    `--%` 같은 자리표시자는 쓰지 않는다 — 고장으로 읽힌다.
- pid 집합이 매 샘플 바뀌므로 **pid별 이전 값 맵**이 필요하다. 새로 생긴 pid는 이번 창에서 0, 사라진 pid는 빠진다
  — 집합 차이를 무시하고 합계끼리 빼면 프로세스가 죽을 때 **음수**가 나온다.
- 멀티코어에서 100%를 넘을 수 있다(활성 상태 보기와 같은 규칙).
- **경과는 tick 개수가 아니라 벽시계로 잰다.** 이 저장소의 스로틀은 `ticksForMsAtRate`로 **tick을 세는데**,
  프레임 루프가 흔들리면 `ticks/hz`가 실제 경과와 어긋난다 — 하필 **머신이 바쁠 때**, 즉 사용자가 CPU%를
  들여다보는 바로 그 순간에 틀린다. 샘플마다 단조 시계를 같이 찍는다(Zig 0.16은 `std.time.Timer`·
  `nanoTimestamp`가 없다 — `clock_gettime(.MONOTONIC)`, [src/session/control_bridge.zig] `monotonicMs` 관례).
- **공백이 길면 이전 표본을 버린다.** 상태바를 껐다 켜거나 디스플레이가 잠들면 Δ벽시계가 분 단위가 되고, 그
  비율은 "지금"이 아니라 장기 평균이다. 상한(예: 5초)을 넘으면 첫 표본으로 되돌려 **표시 없음**으로 둔다.

#### 비용과 게이트

실측(이 머신, 634 프로세스): 재귀 트리 walk **148개 1.5 ms**. 실제 탭 하나는 5~15 프로세스라 0.1 ms 미만이다.
(참고: 폐기한 responsible-pid 안의 전체 pid 스캔도 **165개 0.3 ms**였다 — 그 안이 죽은 이유는 비용이 아니라
fork 자식을 못 잡는 것이었다.) 그래도 렌더 tick에서 돌리지 않는다:

- **주기는 별도**로 둔다(에이전트 폴링 `agent_poll_interval_ms`=500ms보다 느린 1~2초). 리소스는 초 단위로 변하는
  값이고, 자주 재도 사람이 못 읽는다.
- **상태바가 안 보이면 샘플링하지 않는다.** `status-bar.show=false`뿐 아니라 **quick terminal(`chrome_minimal`)**
  도 포함이다 — 둘 다 `statusBarHeightPx`가 0을 돌려주는 경로라 게이트를 그 단일 판정에 건다.
- 트리 walk에 **깊이·개수 상한**을 둔다(폭주 방어 — fork 폭탄이나 순환에서 tick을 붙잡지 않게).
- **[performance-budget.md] micro-slice 규율 준수**: frame tick을 건드리면 bounded 증명이 필요하다. 여기 근거는
  ⑴ 위 실측(전형 탭 0.1 ms 미만, 병적 상황도 상한으로 bounded) ⑵ **새 종류의 일이 아님** — 같은 tick의
  `foregroundProcessNames`가 이미 500ms마다 `proc_listpgrppids`·`proc_name` syscall을 한다. **파일/경로 I/O는
  0**이다(libproc은 path lookup이 아니다) — 그 표의 "frame tick FS I/O = 0" 항목을 깨지 않는다.
- **표시 문자열이 바뀔 때만 `metal_dirty`**를 세운다. 원값이 흔들려도 `1.4 GB`가 그대로면 다시 그리지 않는다 —
  매초 전체 재렌더는 배터리에 그대로 실린다.

#### keep-alive를 켜면 터미널이 0이 된다

PTY가 host 프로세스 안에 있어(§ `runtime_manager.live_child_pid`) 앱에서 트리를 못 훑는다. 그때 **0을 보여 주면
고장으로 읽힌다** — 항목을 아예 내리거나 "host 세션은 집계 밖"을 알 수 있게 한다. host RPC로 제대로 세는 것은
후속이다(사용자 결정: 세션 host는 아직 구현이 덜 돼 엣지 케이스로 둔다).

#### 표시 폭은 고정한다 — 안 그러면 경로가 매초 흔들린다

§3은 "우측을 먼저 배치하고 그 좌단이 좌측의 상한"이며 **우측은 폭이 작고 고정적**이라는 근거로 좌측을 자른다.
값에 따라 자릿수가 변하는 숫자는 **그 전제를 깨뜨린다** — 리소스 항목이 한 칸 넓어지는 순간 좌측 경로가 다시
생략되고, 사용자는 매초 경로가 흔들리는 것을 본다(리소스 숫자보다 훨씬 거슬린다).

그래서 **셀 수가 값에 따라 변하지 않게 고정 폭으로 포맷한다**(오른쪽 정렬 패딩). 자릿수가 늘어나는 경계
(예: 9.9 GB → 10.1 GB)에서도 칸 수가 같아야 한다.

#### 검증은 순수 계산과 syscall을 갈라서 한다

libproc은 헤드리스로 못 고정한다(살아 있는 프로세스가 필요하고, 값이 매번 다르다). 그래서 **순수 계산과
플랫폼 어댑터를 분리**한다(저장소 관례 — L2 순수 + platform):

- **순수(테스트 대상)**: pid→표본 맵을 주입받아 ⑴ 트리 합산 ⑵ CPU% 차분(집합 변화·음수 방지·공백 폐기)
  ⑶ 고정 폭 포맷 ⑷ 첫 표본 "표시 없음"을 단언한다.
- **어댑터(테스트 밖)**: `proc_pid_rusage`·`proc_listchildpids` 호출과 `rc != 0` 처리. 여기엔 로직을 두지 않는다
  — 로직이 어댑터로 새면 그 부분은 영영 검증되지 않는다.

#### 자리 — 우측 배열은 이미 꽉 찼다

`max_status_bar_right_items = 3`(blocked·running·알림)이라 **상수를 4로 늘려야** 한다. 우측 배열은 **앞이 더
오른쪽**이고 폭이 모자라면 뒤부터 버리므로, 리소스는 **배열 마지막**(가장 왼쪽)에 둔다 — 가장 먼저 버려져야
하는 항목이다. 막힌 에이전트가 리소스 숫자에 밀려 사라지면 안 된다.

`ItemId`에 값을 **반드시 추가**한다. `publish`는 폭 배열과 **같은 순서의 id 배열**을 받아 슬롯 `index`로
되짚으므로, 항목만 늘리고 id를 안 늘리면 인덱스가 밀려 "누른 것과 실행된 것"이 갈린다(§5.6이 그래서 인덱스를
id로 쓰지 말라고 못 박아 뒀다). v1은 클릭 동작이 없지만 id는 지금 넣는다.

#### 값이 없으면 항목이 없다

이 창에 터미널 Term이 없거나(웹 탭만 열린 창) 표본을 하나도 못 얻으면 **항목 자체를 내지 않는다** — 기존
우측 항목들의 "0이면 항목 없음" 관례와 같다. 0을 그리면 "0 바이트를 쓰는 중"으로 읽힌다.

**항목별 config 토글은 만들지 않는다.** 상태바 전체 토글(`status-bar.show`)이 이미 있고, 항목마다 스위치를
다는 것은 요구가 없는 상태에서 설정 표면만 넓힌다.

#### 아이콘은 나중에

`icons.zig`는 **닫힌 등록부**(PUA + 빌드타임 SVG→coverage)라 메모리/칩 아이콘을 쓰려면 SVG를 추가해야 한다.
v1은 **텍스트만**으로 낸다 — 숫자가 쓸모 있다고 확인된 뒤에 아이콘 파이프라인을 건드린다.

### 아직 안 한 것

§6에 적어 뒀던 셋(브랜치 클릭 대상·경로 중간 생략·표시/숨김 설정)은 **전부 붙었다.** 남은 것은 위 §5.2의
검증 공백 하나이고, 그건 "안 한 것"이 아니라 **조건이 붙은 것**이다(트리거 셋이 위에 적혀 있다).
