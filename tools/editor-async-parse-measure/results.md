## 확인한 것

메인이 rope를 편집해도 워커가 붙든 이전 스냅샷은 원문 byte와 같았다. 워커의 별도 cold parse와
복사된 트리의 전체 노드 종류·좌표·필드·named/missing/extra/error 속성을 비교했다.
원본 allocator는 메인에서만 호출하고, 워커의 평탄화는 별도 page allocator를 사용했다.
메인과 워커의 동시 스케줄 구간 길이는 측정하지 않았다.

바이트 변조, 복사 끝 누락, 트리 좌표 변조, 최신 스냅샷을 이전 것으로 오인계, 메인 편집 누락을
각각 별도 실행에서 주입했으며 모두 실제 assertion으로 거절했다. 이 실패 실행은 성능 집계에서 제외했다.
독립 검증기는 원시 로그를 다시 읽어 300개 행과 집계를 대조하고 바이너리·원문·실제 제품 사본·계측 패치를
해시로 확인했다. 집계 변조·행 변조·표본 누락·바이너리 identity·fixture identity 손상도 거절했다.

## 설계에 반영할 판단

스냅샷 보유나 Provider 복사 비용만으로 워커를 배제할 근거는 이 표본에서 나오지 않았다.
반면 **파싱만 옮기고 마지막 트리 해제를 메인에 남기면 긴 메인 작업이 남을 수 있다**.
후속 설계에는 트리의 퇴역·최종 해제 소유권을 포함해야 한다. 실제 증분 편집에서 매번 이 최대 비용이
발생한다고 일반화하지 않는다. 공유 subtree 수명에 따라 마지막 해제 시점과 작업량은 달라진다.

이 결과만으로 제품 워커·퇴역 큐·메모리 상한을 승인하거나 구현하지 않는다.
실제 UI 입력 지연, peak 메모리, 활성 sticky summary, 설치·캐시 무효화,
취소·종료·OOM·문서 판 수락 정책은 아직 검증하지 않았다.
