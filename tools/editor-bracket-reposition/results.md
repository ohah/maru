# 괄호 구조 재사용 비교 실측

측정 소스: `95cf7b84fe53adb14f6a4848343eb43d341d2c6e`. Zig 0.17.0 ReleaseFast에서 실제 AppSession의
편집 호출과 모든 뷰의 괄호 준비가 끝날 때까지 pane frame 호출을 측정했다.
기준은 같은 소스 사본에서 재사용 분기만 제거한 실행 파일이다. main의 별도 빌드나
다른 버전의 배포 앱을 기준으로 삼은 수치가 아니다.

실측 종료 후 `resolve`·`dropLongLines`의 설명 주석 두 개를 각 함수 바로 앞으로
옮겼다. 실행문은 측정판과 동일하며, 원시 자료의 측정 HEAD는 바꾸지 않는다.

## 범위와 판정

- 다섯 원문 × 일반/공유 × 구조 유지/괄호 추가 × 기준/재사용의 전체 40셀을 검사했다.
- 성능은 각 셀 20편집씩 3반복(총 2,400편집), 정확성은 별도 1반복(800편집·1,200뷰)이다.
- 일반 편집은 공백 하나를 앞에 추가한다. 토큰 수가 같고, 실제 전체 판정 호출은 기준이 뷰당 1회, 재사용이 0회여야 한다.
- 구조 편집은 ` (`를 추가한다. 토큰이 정확히 하나 증가하고 양쪽 모두 뷰당 1회 전체 판정해야 한다.
- 매 입력의 정확한 prefix와 원래 suffix를 검사한다. 별도 정확성 실행은 독립 파싱한 토큰·색/짝 정보·탐색 인덱스를 모든 뷰와 대조한다.
- 기준/재사용 실행 순서는 파일·뷰·편집 종류·반복에 따라 교대한다. 전체 성공 프로세스는 160개다.
- `verify.py`가 실제 Git 소스·사본·생성기·원문·실행 파일·원시 로그 해시와 실행 순서·표본·집계를 다시 검사했다.

## 해석의 한계

이 값은 test allocator를 사용하는 제품 하네스의 함수 경과시간이다. 실제 AppKit/HID 입력이나 GPU present 지연을 뜻하지 않는다.
실제 전체 판정 호출을 세는 테스트 전용 atomic 계수도 활성화되어 있다. 배포 실행 파일에는 이 계수 저장소가 없다.
준비가 끝날 때까지 실제 프레임 간 대기 없이 호출하므로 frame 반복 수도 원시 로그에 보존한다.
짝이 없는 여는 괄호를 계속 앞에 추가하는 구조 사례는 파서 오류 복구 비용을 포함한다. 일반 입력의 대표 지연으로 일반화하지 않는다.
배경 프로세스·디스크 공간 변동을 완전히 통제하지 못했다. 실행 중 과거의 비활성 검증 캐시 중간물을 정리하고 실행 파일은 논리 바이트를 보존해 압축했다.
모든 셀의 분포를 공개하며, 프레임 비용 감소가 전체 편집 지연의 모든 표본에서 감소한다는 주장을 하지 않는다.
구조가 같아도 전체 괄호 목록과 현재 줄 길이를 확인한다. 새 문서 캐시나 영속 메모리는 추가하지 않았다.

```sh
python3 tools/editor-bracket-reposition/measure.py \
  --output <새-저장소-밖-절대경로> \
  --fixtures <고정-다섯-원문-폴더> --deps "$PWD/zig-pkg"
python3 tools/editor-bracket-reposition/verify.py <완료된-측정-경로>
python3 -m unittest discover -s tools/editor-bracket-reposition -p 'test_*.py'
```

원시 자료는 `/Users/yoonhb/.cache/maru-agent-artifacts/bracket-reposition-measure-4`에 보존한다.
`receipt.json`은 소스·생성기·원문·실행 파일·성공 순서, `samples.json`은 모든 입력,
`summary.json`은 전체 분포, `independent-final.json`은 독립 재검증 결과다.
원문·계측 사본·실행 파일과 각 실행의 원시 로그도 같은 폴더에 있다.

첫 준비 실패 자료와 실제 구조 변경을 입증하지 못한 주석 입력 자료는 정식 자료에 합치지 않았다.

이 문서의 최종 보강판 분포와 구분한다. 자세한 실패·재개 계약은 [계획](../../docs/plans/editor-bracket-shape-reuse.md)이 소유한다.
