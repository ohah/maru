## 확인한 내용

`flat-50000.zig` 공유 2뷰에서 승격 전체 중앙값은 2.269ms, 후보 조회는 1.574ms,
범위 변환은 0.148ms, 설치는 0.543ms였다. 후보 조회가 가장 큰 하위 구간이었다.
후보 조회 API 안의 세부 작업까지 이 실측으로 구분한 것은 아니므로, 이를 전체 트리 순회 비용으로 단정하지 않는다.
보이는 줄 0.313ms와 마무리 0.106ms는 설치에 포함된 자식이다. 다시 더해 전체 비용을 부풀리지 않는다.

모든 입력에서 각 구간의 실제 호출 수가 뷰 수와 같고 후보가 비어 있지 않음을 확인했다.
승격은 기존 INNER 부모 안, 조회·변환·설치는 승격 안, 보이는 줄·마무리는 설치 안에 들어갔다.
편집·사용자 접기·LSP 응답의 같은 함수 호출은 문맥 플래그로 제외했고, 입력 시작/끝에서 플래그 복원을 검사했다.

독립 검증은 표본/순서, 호출 문맥/작업량, 포함 시간/겹침, schema/소스 모델, 원본·생성기·바이너리·로그 증거를 공격했다.
의미 반례에서는 로그 해시를 일부러 다시 맞춘 뒤에도 행·범위 검증이 거절하는지 확인했다.
원본은 읽기 전용으로 빌린 격리 사본에서 검사했고, 사본의 운반 경로만 다시 결합했다.
다섯 가설의 정상 전후 대조군과 23개 손상 거절, 원본 전후 불변을 확인했다.

준비 중 오류 반환형의 중괄호를 함수 본문 시작으로 오인하던 생성기 조건을 고쳤다.
상위 제품 드라이버에 없는 과거 prototype의 대기 옵션도 제거했다. 첫 준비 시도는 CLI 거절로 끝났으며 표본에 넣지 않았다.
JSON의 true와 정수 1을 같은 크기 값으로 받아들이지 않도록 원문 metadata의 타입도 검사한다.

```sh

python3 tools/editor-fold-promotion-measure/verify.py <같은 외부 경로> --receipt <새 외부 기록.json>
python3 -m unittest discover -s tools/editor-fold-promotion-measure -p 'test_*.py'
```

`verify-order.*`와 `promotion-verify-proof.json`에 실제 순서·옵션·로그 해시를 보존한다.

## 한계

고정 다섯 원문·일반/공유·테스트 allocator를 사용하는 fixture의 함수 경과시간이다.
계측과 배경 부하의 영향이 포함되며 AppKit/HID·GPU present·RSS·모든 언어/입력의 최악 지연을 뜻하지 않는다.
이 실험은 전후 개선량 비교가 아니다. 캐시 추가나 승격 생략을 승인한 것도 아니다.
단일 뷰의 기존 접힘 해제, 공유 뷰의 머리/끝 일치 보존, 가로 폭·스크롤 복원과 실패 동작은
후속 구현에서도 보존해야 한다. 범위 값이 같다는 이유만으로 설치 부수 효과를 생략하지 않는다.
