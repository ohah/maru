## 확인된 실행 위치

동기·비동기 각각 독립 3프로세스와 30입력, 총 6프로세스·180입력의 정상 본문·native/표시
기록을 검사했다. 모든 trace는 준비된 대상에 붙어 생산자 시작 전에 기록을 시작했고,
대상의 정상 종료까지 포함한다. SDK 재내보내기·실제 코드 주소·dSYM·atos 재해석을 대조했다.

아래 비중은 전체 trace에서 main thread로 식별한 **Running 표본의 포함 weight** 기준이다.
키별 대기 경과시간이나 정확한 CPU 시간을 뜻하지 않는다. 포함 비중을 더해 전체 비용으로 읽지 않는다.

비동기에서는 `appendPaneFrame` 아래의 `promoteFoldRangesToSyntax → foldSpansCached → folds.Cache.visit`와
`sticky.compute → Summary.hasSymbols → fullCount`에 메인 실행 표본이 반복해서 모였다.
동기의 고정 머리줄 경로 비중은 약 6.8–7.8%였고 접힘 승격은 관측 0–0.06%였다.
해당 이름은 XML 라벨이 아니라 대상 Mach-O UUID·실제 코드 영역·유일한 load address와 보관 dSYM을
연결한 주소 해석에서 나온 것이다. 미해결/중복 심벌과 외부 코드는 특정 제품 함수로 추정하지 않았다.

## 판단과 다음 대조

기존 비프로파일 측정의 큰 문서 공유 100ms 입력은 비동기 native 도착 전 중앙값이
세 프로세스에서 약 140–148ms였다. 이번 결과는 그 조건에서 **메인의 트리 순회 위치**를 좁혔다.
이 두 결과만으로 매 입력 지연의 원인이나 캐시 최적화의 개선율이 확정되지는 않는다.

다음은 비동기 결과 설치 시 접힘 캐시·심볼 요약의 재구축 여부를 제품 판정자로 재현하고,
같은 입력과 기존 표시 정확성을 보존하면서 재구축을 줄이는 대조다. 개선량은 프로파일러 없는
동일 행렬에서 따로 재측정한다. 이 PR은 제품의 tree 수명·캐시·worker·timer·UI를 바꾸지 않는다.

## 검증과 제한

실제 코드 주소를 누락·변조하거나 다른 PID/경로/종료 원인, 잘못된 참조·표본 순서·weight,
재귀 중복·빈 스택과 잘못된 시작 통지를 정상으로 채택하지 않는 계약을 검사했다.
전체 main self weight에는 누락 스택을 포함하고 합계가 보존된다. 기존 reader의 기본 이미지
계약을 유지하면서 명시적 앱 이름의 정확한 바인딩도 확인했다.

원시 자료는 외부 `input-attribution-cohort-2`, 분석·심벌·SDK 재내보내기는
`input-attribution-analysis-2`에 보존한다. `input-attribution-pilot-1`은 환경 허용 목록 적용 전 자료라
채택하지 않았다. `pilot-2`와 `cohort-1`은 수집/판정기 준비 중의 진단으로 최종 표에 넣지 않았다.
[계약과 민감정보 처리](README.md)를 따른다. 공개 결과에는 환경 값을 포함하지 않는다.

프로파일러 부하·마지막 색 준비·종료 비용을 포함한 준비 뒤 전체 trace다. 광학/IME 증거,
일반적인 CPU 개선율, 전력, 키별 대기 구간과 정확한 trace 시계 정렬은 검증하지 않았다.
