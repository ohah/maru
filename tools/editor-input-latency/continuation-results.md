# 괄호 분석의 후속 프레임 요청 보존

측정일: 2026-10-30 KST. [최초 실측](results.md)에서 발견한 입력 후 괄호 색 복구 지연을 수정했다.
수정 후에도 동일한 6조건 × 2모드 × 독립 3프로세스, 1,080 HID 입력을 검사했다.
[기계 판독 비교](continuation-results.json)는 양쪽 원시 증거·fixture·모집단을 다시 검증한 결과다.

## 원인과 수정

`advanceSyntax`는 프레임을 만드는 도중 괄호 목록을 예산만큼 진행한다. 미완료 때 세운
`metal_dirty`가 같은 tick의 전체 프레임 게시 성공 처리에서 지워져 다음 조각이 멈췄다.
`BRCONT` 제품 테스트에서 게시 세대가 증가하고 괄호 목록은 미완료인데 dirty가 꺼지는 것을
수정 전에 재현했다. 기존 `BPP3`은 프레임 생성까지만 호출해 게시 뒤 소거를 놓쳤다.

미완료 괄호 순회와 동기 파싱 재개는 기존 `reproject_after_frame`도 함께 세운다.
전체 프레임 게시가 그 요청을 다음 tick의 dirty로 넘긴다. 준비 완료·트리 부재·옵션 비활성화는
계속 그리기를 요청하지 않는다. 프레임 예산, 색·짝 규칙, 실패 정책이나 worker 수는 변경하지 않았다.

공유 분할은 약 2.0–3.6MiB 증가했다. 소스 변경은 새 할당을 추가하지 않지만 더 촘촘한 렌더 진행의
전체 앱 최대 RSS까지 완전히 같다고 주장하지 않는다. 자식 프로세스나 시스템 전체 메모리는 제외한다.

## 검증과 실패 자료

- 제품 검사 14개와 모듈 초기화 4개를 Debug/ReleaseFast에서 통과했다. 전체 게시 뒤 요청 유지,
  동기/비동기·공유 분할·색/강조 옵션·독립 색 풀·IME preedit·중간 편집/Undo·작업 중 비활성화·
  빈 문서·미지원 문법·완료 뒤 idle을 검사한다. 완료한 괄호 위치와 단계·짝 정보는 같은 옵션의 cold 분석과 일치했다.
- 기존 비동기 입력의 행동 6개와 초기화 4개도 두 모드에서 통과했다. 실패·명시적 재분석·공유 소비처·
  언어 변경/수명·병합 경로를 회귀 검사했다.
- 두 지속 요청을 false로 바꾸는 컴파일 가능한 변이에서 지속 작업 검사 10개가 실패하고 8개 대조가
  유지됐다. 정확한 원본 복원 뒤 18개 모두 통과했다.
- 실제 자료 6묶음에서 전면 상태·표시 시각·세대·모드·A/B 누락의 의미 변조를 모두 거절했다.
  변조 자료의 해시도 갱신하므로 해시 불일치만 잡는 검사가 아니다. 원본은 전후 모두 수락됐다.
- 첫 `3000-typing-attempt-0`의 sync 실행은 native keyDown은 도착했지만 본문 판과 첫 줄이
  바뀌지 않아 `presentation_timeout`으로 거절됐다. 유효 지연 표본이 없어 통계에 넣지 않았다.
  `attempt-1`은 독립 6프로세스 전체를 새로 실행했다. 같은 빌드의 별도 IME 로그 진단도 정상 입력을
  확인했다. 입력 불성립의 근본 원인은 미확정이며 괄호 수정이 이를 해결했다고 주장하지 않는다.
- 실패 자료는 당시 시각·문서 상태·실제 첫 줄을 함께 보존한다. 실제 callback을 끈 음성 대조에서는
  문서 판이 0→1, 첫 줄은 `// x`가 됐지만 표시 시각은 0이어서 거절됐다. 입력 자체가 성립하지 않은
  앞선 실행(문서 판 0 유지)과 구분했다.

최초 확대 테스트에서 빈 문서도 괄호 작업이 생긴다고 기대한 오류를 고쳤다. 빈 원문은 provider가
없는 기존 계약을 유지하며 계속 그리기를 요청하지 않는다. 새 helper의 한글 IME/편집 fixture 3개는
제품 UI 문구가 아니므로 i18n 원장에 근거와 함께 추가했다. 최초 경계 검사 실패와 정정 후 결과를 구분했다.

제품 수정 빌드는 `f59031145`이며, 이후 강화한 테스트와 결과 문서만 후속 커밋에 들어간다.
이전 빌드는 `e2661e916`이다. 그 사이 LSP 종료 처리 변경도 있었지만 본 측정은 LSP를 껐다.
같은 Mac16,9/macOS 26.5.1/16CPU의 ReleaseFast 비교이며 측정 사본에 공통 계측을 더했다.
수정 후 계측에는 실패 상태를 보존하기 위한 읽기가 추가되어 이전 수집기와 완전히 같지는 않다.
수정 후 1분 load average는 33.22–97.23으로 높았다. 첫 표시 수 ms 차이를 수정의 인과 효과나
저부하의 보편적인 개선으로 해석하지 않는다. 과거와 현재의 앱 해시를 모두 보존한다.

OS `presentedTime`을 썼으며 물리 키보드·광자 지연이나 매 프레임 PNG/OCR 검증이 아니다.
문자열은 NSTextInputClient로 검사했다. 합성 Zig 원문의 첫 주석 입력이며 LSP·wrap은 껐다.
공유 분할+IME·구조 변경의 GUI 지연·붙여넣기·다중 창·OOM 지연은 이 성능 모집단 밖이다.
