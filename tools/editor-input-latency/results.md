# 비동기 파싱의 실제 입력 표시 지연 실측

측정일: 2026-10-30 KST. 제품 소스 변경 없이 외부 계측 사본의 같은 실행 파일에서 두 모드를 비교했다.

## 결과

첫 표시는 큰 문서에서 개선됐지만 작은 문서에서는 느려졌다. 비동기 모드의 괄호 색 복구는
입력 표시보다 훨씬 늦었다. 모든 입력에서 비동기 전환이 유리하다는 결론은 아니다.

각 숫자는 독립 프로세스 3개의 중앙값을 다시 중앙값으로 집계했다. p95도 프로세스별
p95의 중앙값이며 전체 표본을 합친 p95가 아니다. 마지막 색은 마지막 입력 게시부터 잰다.

## 입력 사이 색 관측

첫 5입력을 제외하고 마지막 입력의 긴 복구 대기도 빼면 프로세스당 관측 창은 24개다.
각 창은 첫 표시 통지를 관측한 뒤 최소 120ms 후 닫히고, 다음 tick에서 다음 입력을 게시한다.
창 안에 완료 통지를 관측한 수이며 다음 키 직전까지의 정확한 완료율은 아니다.
미관측 값 0을 0ms 완료로 계산하지 않는다.

## 원인 분리와 다음 작업

동일 실행 파일의 별도 진단에서 50,000 함수·일반 입력 6회를 사용하고 커서 blink 주기만 바꿨다.
조건/모드별 한 프로세스이므로 본 성능 모집단이나 안정적인 개선량으로 합치지 않는다.

| blink 주기 | async 마지막 문법 색 | async 괄호 포함 색 | 두 준비 프레임의 세대 차이 |
|---|---:|---:|---:|
| 500ms | 229.34ms | 13,060.71ms | 28 |
| 100ms | 222.74ms | 2,583.60ms | 28 |

문법 분석 시각과 세대 차이는 비슷한데 완료 시간이 blink 주기에 비례했다. 이 workload에서
괄호 작업 진행이 후속 프레임 공급에 의존한다는 근거다.
`editor/mod.zig`의 `advanceBrackets`는 미완료 때 `metal_dirty`를 세우지만 전체 프레임 게시 뒤에는
`reproject_after_frame`이 없는 경우 그 플래그가 지워진다. 다음 작업은 이 연속 요청의 소실을
제품 판정자로 재현하고 화면 게시와 작업 지속의 계약을 고치는 것이다.

외부 사본에서 `reproject_after_frame`도 세우는 단순 변경을 시도했으나 첫 sync 대조군부터
`presentation_timeout`으로 거절됐다. 앱은 키 이벤트와 프레임을 처리했지만 유효한 표시 표본은 없었다.
이 실패가 제품 변경 때문인지 계측과의 상호작용인지는 미확정이다. 수정 효과로 주장하지 않으며
최초 실측 PR은 해당 제품 변경을 포함하지 않았다. 당시 `--continuation-fix` 옵션의 자료는
일반 집계기가 성능 모집단에서 거절한다. 후속 제품 수정의 진행은
[입력 지연 계획](../../docs/plans/editor-input-latency.md)을 따른다.

## 한계

OS가 보고한 Metal drawable 표시 시각이며 물리 키보드·카메라/광자 지연 측정은 아니다.
문자열은 NSTextInputClient의 가상 문서에서 확인했고 매 프레임 PNG/OCR을 검증하지 않았다.
높은 부하의 Mac 한 대에서 수행한 제한된 비교다. 첫 주석에 입력하는 합성 Zig 문서이며
LSP·wrap을 끈 조건이다. 구조 변경·붙여넣기·Undo·공유 분할+IME·다중 창·저부하 환경은 미측정이다.
관측 장치의 비용은 두 모드에 공통으로 들어가며 과거 출시 바이너리와의 전후 비교도 아니다.
