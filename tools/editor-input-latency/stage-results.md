# 색 표시의 단계별 대기와 timer 주기 대조

2026-10-31 KST. [후속 요청 보존 수정](continuation-results.md) 뒤 남은 연속 입력 중 색 대기를 분석했다.
제품 코드는 변경하지 않았다. 기존 원시 자료를 다시 검증해 표시 단계를 분해했고, 같은 실행 파일로
timer 설정만 바꾼 별도 진단을 추가했다. 단계를 worker의 CPU 시간으로 바꿔 부르지 않는다.

## 기존 기록의 단계 분해

입력 게시→native keyDown→첫 변경 표시→문법 준비 표시→괄호 준비 표시를 나눴다.
각 프로세스 마지막 입력의 원시 시각으로 계산했으며 프로세스 안에서는 단계 합이 전체 지연과 같다.
아래는 독립 3프로세스의 **각 항목별 중앙값**이라 열의 중앙값들을 더해 전체 중앙값으로 쓰면 안 된다.

| 50,000 함수 / 비동기 | 게시→native | native→첫 표시 | 첫 표시→문법 준비 | 문법→괄호 준비 | 문법→괄호 프레임 세대 차이 |
|---|---:|---:|---:|---:|---|
| 일반 입력 | 0.54ms | 37.15ms | 186.74ms | 466.84ms | 28–29 |
| 두벌식 | 1.37ms | 68.14ms | 200.07ms | 466.84ms | 28–29 |
| 공유 분할 ASCII | 0.54ms | 37.47ms | 333.46ms | 466.84ms | 28–29 |

작은 문서 3조건은 마지막 입력의 첫 표시부터 문법 준비 표시까지 중앙값 0ms였다.
이는 같은 준비된 프레임이 표시됐다는 뜻이다. 완료 통지 부재를 0ms로 계산한 것이 아니다.
전체 sync 대조군과 프로세스별 값은 [단계 결과 JSON](stage-results.json)에 보관한다.

큰 문서의 문법 준비 이후 대기는 약 467ms로 비슷하지만 문법 준비까지의 대기는 공유 분할에서
더 길었다. **worker 실행·완료 전달·뷰 설치·접힘 승격·렌더 CPU를 각각 잰 자료는 아니므로**
이를 파서 시간이나 설치 함수의 비용으로 확정하지 않는다.

## 실제 입력 간격

기존 수집기는 첫 표시 통지를 읽은 뒤 최소 120ms를 기다리고 **앱 메인 스레드의 다음 tick에서**
다음 키를 게시한다. 120ms는 고정 키 주기가 아니다. 메인이 바쁘면 게시 자체가 늦어진다.
안정 구간의 실제 연속 게시 간격을 다시 계산했다.

| 비동기 조건 | 프로세스별 키 간격 중앙값의 중앙값 | 문법 준비 관측 | 괄호 준비 관측 |
|---|---:|---:|---:|
| 3,000 일반 | 199.88ms | 72/72 | 72/72 |
| 3,000 두벌식 | 200.03ms | 72/72 | 72/72 |
| 3,000 공유 분할 | 216.56ms | 72/72 | 72/72 |
| 50,000 일반 | 347.15ms | 62/72 | 0/72 |
| 50,000 두벌식 | 348.89ms | 41/72 | 0/72 |
| 50,000 공유 분할 | 499.79ms | 65/72 | 0/72 |

관측 창은 첫 5입력과 마지막 입력을 제외한 프로세스당 24개다. 창 안에서 완료를 관측한 수이며
다음 키 직전까지의 정확한 완료율은 아니다. 입력 후 표시 시각 자체의 유효성을 부정하는 결과는
아니지만, 기존 자료를 120ms 고정 연타·외부 키 입력 폭주의 지연이나 처리량 증거로 쓰면 안 된다.
게시→native가 짧다는 값도 메인이 막힌 동안 외부 키의 대기가 짧다는 증명이 아니다.

## timer 주기만 바꾼 별도 실행

제품의 기본 `render.frame-rate=60`은 유지했다. [설정 계약](../../docs/configuration.md)에 있는
30·60·120Hz를 격리 config에만 기록했다. 화면 주사율을 바꾼 실험은 아니다.
50,000 함수·일반 입력 6회, 설정별 sync/async 각 독립 3프로세스의 **18프로세스·108입력**이다.
각 프로세스의 앞 5입력 뒤 마지막 1개의 단계를 비교하므로 원래 900개 안정 구간과 합치지 않는다.
실행 순서는 60→30→120이며 모드 순서는 각 설정 안에서 AB/BA를 교대했다.

| 요청한 timer 설정 | 첫 표시→문법 준비 중앙값 | 문법→괄호 준비 중앙값 | 문법→괄호 세대 차이 |
|---|---:|---:|---|
| 30Hz | 200.07ms | 947.01ms | 29, 29, 30 |
| 60Hz | 213.41ms | 506.85ms | 28, 30, 32 |
| 120Hz | 200.07ms | 373.47ms | 28, 28, 29 |

문법 이후의 지연은 같은 정도의 프레임 세대를 거치며 timer 설정에 따라 줄었다.
**남은 괄호 준비가 프레임 진행과 결합되어 있다는 근거**다. 120Hz 설정이 60Hz보다 정확히
두 배 빠르지는 않았다. 실험 직후 연결 화면 조회는 최대/현재 모드 75Hz였고 표시 시각에도
약 13.34ms 단위가 보였다. 표시 경로 제약과 부합하지만 각 프레임의 창-화면 소유권이나
`nextDrawable` 대기를 계측하지 않았으므로 이를 확정 원인으로 삼지는 않는다.

문법 이전의 약 200ms는 timer 주기를 바꿔도 비슷했다. 그 구간의 내부 비용은 별도 계측 대상이다.
전력·idle wakeup을 재지 않았으므로 기본값을 120Hz로 올리는 제안이나 근거로 쓰지 않는다.
모든 원시 자료·실행 파일 해시·config 해시를 검증한 [대조 JSON](cadence-results.json)을 함께 둔다.

## 검증과 실패 자료

- 단계 분석은 먼저 기존 앱/문서/로그/결과 해시·전면 상태·문서 판·실제 모드·프레임 세대를 검증한다.
  마지막 색이 없으면 단계 분석도 실패하며 중간 미완료를 0ms로 평균하지 않는다.
- 검증된 실제 자료에 실패·복원 실패·프로세스/모드/flow·입력 누락·메모리·순서·전면 상태·문자열·
  clock 타입/역전·표시 부재·이전 입력의 늦은 통지·색 역전/부재·키·세대 변조를 넣었다.
  각 변조가 의미 검사에서 거절됐고 원본 대조군은 전후 유지됐다. 제품 소스를 변조한 실험은 아니다.
- timer 수집기는 실제 child 대신 대역을 실행하는 CI 검사로 config 내용·진단 표지·해시 기록을 확인한다.
  단순 선언 존재가 아니라 작성된 파일과 실행 환경을 검사한다. 진단을 켜도 강제 재그리기를 유발하는
  `MARU_DEBUG`는 켜지 않으며 diagnostic 자료는 기본 성능 집계에서 거절한다.
- 첫 cadence 묶음의 첫 sync 실행은 native 키 도착 후에도 문서 판이 0인 채여서 거절됐다.
  유효 표본이 없으므로 제외했고 원시 자료를 보존했다. 같은 앱의 별도 IME 로그 진단 2프로세스는
  정상 입력됐으며 로그 비용 때문에 대조 수치에 섞지 않았다. 새 독립 묶음의 18프로세스는 모두 통과했다.
  처음 입력이 성립하지 않은 근본 원인은 여전히 미확정이다.
- 두 보고서는 원시 자료를 다시 읽어 동일 결과가 재생성되는지 대조했다. CPU 시간이나 완료
  callback 시각을 표시 시각 대신 넣지 않는다.

## 재현

```sh
python3 tools/editor-input-latency/stages.py <기존 suite> --output <새 단계 JSON>
python3 tools/editor-input-latency/cadence.py --build <기존 빌드> --output <새 외부 경로>
python3 tools/editor-input-latency/review_stages.py <개별 묶음> --output <새 외부 검증 경로>
python3 -m unittest discover -s tools/editor-input-latency -p 'test_*.py'
```

실제 macOS 입력 권한과 전면 창이 필요하다. 실행 실패 자료를 지우거나 자동으로 같은 경로를 재사용하지 않는다.
`cadence.read_experiment`는 세 설정의 원시 기록·동일 빌드/호스트·온전한 모집단·요청 설정·config·
runner 해시를 다시 확인한다. 부분 완료된 `cadence.json`을 완성된 결과로 수락하지 않는다.

로컬 원시 자료의 기준은 `~/.cache/maru-agent-artifacts/`다.

| 자료 | 하위 경로 |
|---|---|
| 기존 36프로세스 | `input-latency-fixed-suite-1/` |
| 실제 단계 의미 변조와 대조 | `input-latency-stage-review-final/` |
| 실패한 첫 cadence 묶음 | `input-latency-cadence-1/` |
| IME 로그 진단 | `input-latency-cadence-route-1/` |
| 완성된 18프로세스 | `input-latency-cadence-2/` |

앱은 #4660에서 검증한 `f59031145`의 같은 불변 ReleaseFast 실행 파일이다. 머지 커밋 `31f81d046`과의
`src/` 차이는 테스트 helper의 색 판정 기대값 강화뿐이며 제품 런타임은 같다. 새 빌드나 새 제품 실행
계측을 추가하지 않았다. 같은 Mac16,9/macOS 26.5.1/16CPU이며 cadence별 1분 load average는
약 27.40–33.41이었다. 이 시점 차이와 고정 설정 순서를 고려해 보편적인 향상 비율로 확대하지 않는다.

## 후속 범위

다음 입력 지연 검증은 앱 메인 스레드가 바빠도 고정 주기로 키를 게시하는 외부 생산자를 별도 설계한다.
우선 ASCII의 입력 순서·본문 접두부·각 입력을 처음 담은 프레임을 연결하고, 입력 유실·프레임이
여러 입력을 함께 담는 경우·포커스 상실을 검증한 뒤 실제 연타의 지연과 큐 대기를 비교한다.
IME는 한 키와 문서 판이 일대일이 아니므로 ASCII 결과를 그대로 확장하지 않는다.

제품 최적화 후보는 프레임마다 한 조각만 진행하는 괄호 작업의 분리와 완료 뒤 뷰 작업의 비용 귀속이다.
worker 이관 효과·메모리 비용이나 접힘 승격의 CPU 비용은 아직 측정하지 않았으므로 확정 설계로 쓰지 않는다.
