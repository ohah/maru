# 비동기 완료의 괄호 잎 준비 검증

## 발견과 수정

실제 Runtime 완료를 두 뷰에 설치한 뒤 첫 괄호 조회의 재수집이 각각 1회였다.
재수집 0 회귀는 수정 전 `expected 0, found 1`로 실패했다. worker가 현재 입력의 잎 목록만
준비하고 설치 검증 뒤 독립 배열에 복사하면 두 뷰의 첫 수집은 0회다. 풀·짝·색·탐색은
뷰의 기존 경로로 만든다. 기존 배열 용량·수신 판 증가와 미완료 캐시 부재의 frame 요청은 유지한다.

기존 BRCONT edit 검사는 worker 설치 후 목록 ready만 보고 종료해 색/탐색의 실제 준비를
기다리지 않았다. 현재 판의 `bracketSource`를 기다리도록 수정했으며 기존 토큰·깊이·dirty·idle
대조는 유지했다. 제품 표시 경로는 이미 이 공개 조건을 사용한다.

## 실측 계약과 범위

같은 ReleaseFast 실행 파일에서 worker 잎 준비만 끄고 켠다. 심볼·접힘 준비, frame rate와
다른 정책은 같은 상태다. 각 fixture는 3천/5만 함수 × 50/100ms × 단일/공유 뷰 × 각 3반복으로
48프로세스·1,440입력을 포함한다. 첫 키도 포함하고 반복 순서는 교대한다. 프로파일러는 붙이지 않는다.

첫 표시와 입력별 구문 준비 표시·최종 색을 분리한다. 구문 준비는 성공한 Metal 프레임의
`presentedTime`·세대·문서 접두부와 연결하며, 다음 키 게시 전 표시 횟수는 30키 중 앞 29개의
실제 표시/게시 시각으로 계산한다. 메인 callback 시각이나 worker CPU 시간으로 대체하지 않는다.

실측은 LSP·복원·자동 줄바꿈을 끄고 접기를 실행하지 않은 뷰의 PID 대상 ASCII 입력이다.
물리 HID·OS IME·광학 표시를 검증했다고 주장하지 않는다. 개별 잎의 긴 분류·native 함수는
강제 선점하지 않으며, worker 완료 지연과 추가 배열/RSS 비용이 있다. 색·강조가 꺼진 경우도
worker 준비는 발생할 수 있고 뷰의 기존 drop은 유지한다. 모든 문서/언어/환경의 개선을 보장하지 않는다.

## 거절한 여러 줄 묶음

`async-bracket-multiline-study-1`은 성공한 19프로세스와 첫 키 게시 전 실패 1프로세스에서 중단했다.
실패는 `producer_late`, 게시 수 0, wake 지각 6.817ms, 게시 준비 지각 45.374ms였다.
그 사이 준비 구간은 38.556ms이고 허용 지각은 기존 20ms다. 어느 OS 호출이 길었는지는
이 로그로 확정하지 않는다. 제품 입력 처리 경로의 실패나 원인 수정을 주장하지 않는다.

원본·성공 기록과 실패 기록을 모두 보존하고 불완전한 전체 묶음을 성능 모집단에서 제외한다.
기존 한도·앱·생산자를 바꾸지 않고 새 `async-bracket-multiline-study-2`로 전체를 다시 시작했다.
새 실행의 통과를 첫 실패의 수리로 표현하지 않는다. 증거는 원본과
`~/.cache/maru-agent-artifacts/async-bracket-invalid-cohort-1.json`에 있다.


## 판정기의 추가 결함과 최종 재검증

동일 프레임 세대인데 첫 표시의 구문 ready가 false인 모순과, 준비 성공 계수가 시도 계수보다
큰 모순을 기존 측정 reader가 받아들이는 것을 실제 대역에서 재현했다. 각각 같은 세대/ready
일치와 ready≤attempted를 강제하고 독립 회귀를 추가했다. 재현은
`/tmp/maru-async-bracket-reader-red.log`에 보존한다.

수정한 reader로 채택한 네 묶음(두 fixture × 두 경로)의 원시 96프로세스를 다시 검증해 모두
통과했다. 원래 관측기와 추가 판정기의 차이는 각 study의 tool snapshot 및 결과 JSON의
`final_reader_dependencies`로 구분한다. 수집한 앱·생산자·프레임 기록과 시간값은 바꾸지 않았다.

## 판정과 한계

대형 문서의 마지막 괄호 색이 프레임 수집을 기다리는 구간은 줄었지만 worker 완료 공개가
늦어져 구문 표시가 지연되는 조건이 있다. 작은 문서의 다음 게시 전 구문 표시 횟수와
첫 표시 p95/최대가 나빠진 표본도 그대로 보존했다. 큰 문서는 두 경로 모두 50/100ms 입력 중
다음 게시 전 구문 표시가 0/87이었으며, 빠른 연타의 구문 저하가 전부 해결된 것은 아니다.

한 호스트의 제한된 fixture다. 동시 외부 빌드를 관측했고 본 작업의 경계 검사만 측정 중
멈췄다가 재개했다. 다른 작업은 중단하지 않았다. 거절 묶음을 교체한 유효 묶음과 한 줄 묶음의
96프로세스·2,880입력을 한 분포로 합치지 않는다. pilot 2프로세스와 미완료 20프로세스는 이
집계에 넣지 않는다. 새 전체 실행의 통과를 초기 생산자 실패의 원인 수리로 해석하지 않는다.

불변 앱/소스는 `~/.cache/maru-agent-artifacts/async-bracket-control-build-1`, 제품 소스 HEAD는
`66d6615b7bf1ada023378a0d95783ca5073ed462`이며 측정 후 앱을 다시 빌드하지 않았다. 새로운 준비 정책의 효과만 분리한 같은
바이너리 대조이며, PR 전체 전후·CPU 시간·물리 키보드/IME·전력 개선율로 일반화하지 않는다.
