# 비동기 완료의 접힘 후보 준비 검증

## 재현과 수정

실제 Runtime 완료를 두 뷰에 설치하는 판정자가 수정 전 `expected 0, found 33`으로 실패했다.
worker에서 byte 후보를 준비하고 현재 판의 후보만 독립 복사한 뒤 첫 뷰 조회의 트리 순회는
양쪽 모두 0이다. 행 투영·접힌 머리·LSP 우선순위는 기존 뷰 경로가 소유한다.

처음 작성한 복사 경로는 매 완료마다 배열을 새로 만들 수 있었다. 기존 용량을 재사용하는
`copyMatchedInto`로 바꾸고, 할당 실패 시 기존 대상의 내용/참조 보존을 검사했다.
같은 판의 조회는 트리 비교·정렬도 생략하며, 독립 전체 접힘 대조는 그대로 유지한다.

## 실제 고정 주기 입력 대조

같은 ReleaseFast 실행 파일에서 접힘 후보 준비만 켜고 끈다. 심볼 요약은 양쪽 모두 켠다.
3천/5만 함수 × 50/100ms × 단일/공유 뷰 × 각 3회 × 준비 끔/켬의 전체 행렬을 사용한다.
인접 실행 순서는 교대하고 첫 입력도 포함한다. 실제 worker 분기와 최종 뷰의 순회, 입력 ID·
본문 접두부·Metal 표시·최종 색·설정 보존을 검증한다. 프로파일러는 붙이지 않는다.

같은 판의 조회 생략은 양쪽에 이미 적용되어 있다. 따라서 이 대조는 PR 전체의 전후 차이가
아니라, worker 후보 준비와 설치 복사의 효과만 분리한다.

행렬은 2026-11-02에 완료했다. UI 레이아웃·스타일 변경은 없으며
새 PNG의 전후 픽셀 동등성·물리 HID·IME·광학 표시를 검증했다고 주장하지 않는다.

## 실제 접힘 후보가 있는 여러 줄 함수

위 한 줄 함수는 접을 후보가 없어 트리 재탐색 제거의 효과만 확인했다. 후보 배열의 실제
수집·복사 비용을 빠뜨리지 않도록 각 함수에 여러 줄 본문을 가진 별도 fixture를 추가했다.
`--fixture multiline`로 두 번째 48프로세스·1,440입력 행렬을 같은 앱으로 완료했다.
fixture 종류는 manifest·record·요약에 표시하고 원시 파일을 종류별 정규식이 아닌 정확한
생성 bytes와 대조한다. 종류가 섞이거나 알 수 없으면 거절한다.

각 조건·경로마다 3프로세스·90키이며, 예상 밖 실패·재시도·제거가 없다. 별도 pilot 2회는

앱은 제품 소스 `4ff11c72e8c489eba98970417e0c2d696db23cb4`에서 만들었다.
여러 줄 fixture는 이후 도구만 확장해 같은 앱에 입력했으며 해당 도구의 실제 해시·사본은
두 번째 study의 tool snapshot에 보존했다. 측정 후 앱을 다시 빌드하지 않았다.


측정 설정은 LSP·workspace 복원·자동 줄바꿈을 끄고 접기를 실행하지 않은 뷰의 ASCII 입력이다.
LSP가 접힘 소스를 제공하거나 이미 접힌 상태의 실제 GUI 지연은 이번 실측 범위 밖이다.
LSP 우선순위·접힌 상태의 보존은 앞의 native/제품 회귀 범위와 구분한다. worker는 뷰의 LSP
상태를 받지 않으므로 해당 뷰가 구문 후보를 소비하지 않아도 후보 준비 비용이 생긴다.


로컬 최종 `zig build check-boundaries check-doc-links check-doc-line-refs check-config-docs -j2`가
exit 0으로 통과했다. 마지막 문서 갱신 뒤 문서/config 검사도 다시 통과했다.
`async-fold-validation-1/logs.json`과 `postverify.json`에 로그 해시와 최종 reader의 네 묶음
재검증 결과를 보존한다. 이는 CI 완료·머지를 대신하는 기록이 아니다.
