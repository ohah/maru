# 접힘 후보 재사용의 실제 표시 지연

같은 진단용 ReleaseFast 앱에서 worker의 `copyMatchedOnto`만 켜고 끈다. 두 경로 모두 최종 접힘 준비와 괄호 재사용은 유지한다. 제품 소스 변경은 없다.

여러 줄 함수 3천/5만 개 × 단일/공유 뷰 × 100ms 게시 × 경로별 3프로세스이며 총 24프로세스·720입력이다. 각 조건·경로는 90키다. 반복 순서를 교대하고 첫 키도 포함한다. 프로파일러는 붙이지 않는다.

| 함수 수 | 뷰 | 첫 표시 중앙값(ms) | 첫 표시 p95(ms) | 마지막 입력→구문 표시 중앙값(ms) | 다음 입력 전 구문 표시 |
| --- | --- | --- | --- | --- | --- |
| 3000 | 공유 | 27.84 → 34.65 | 44.13 → 40.26 | 40.49 → 30.24 | 87/87 → 87/87 |
| 3000 | 단일 | 30.16 → 31.67 | 45.73 → 42.22 | 41.42 → 32.79 | 87/87 → 87/87 |
| 50000 | 공유 | 38.87 → 35.20 | 47.41 → 44.52 | 146.11 → 88.75 | 0/87 → 87/87 |
| 50000 | 단일 | 36.80 → 34.28 | 42.82 → 45.93 | 137.45 → 74.09 | 0/87 → 86/87 |

표는 재사용 끔 → 켬이다. 첫 표시는 90키의 pooled median/nearest-rank p95, 마지막 구문 표시는 프로세스별 마지막 키 지연 3개의 중앙값이다. 서로 다른 통계를 더하지 않는다. 이 모집단의 구문 준비 프레임은 최종 색도 준비됐다. 다음 입력 전 표시는 각 프로세스의 앞 29키를 분모로 삼는다.

큰 문서의 구문 갱신 개선은 확인됐지만 글자 첫 표시 개선은 일관되지 않는다. 작은 공유 뷰의 첫 표시 중앙값과 큰 단일 뷰의 p95는 증가했다. 통계적 유의성이나 모든 문서에서의 개선을 주장하지 않는다. 50ms 연타·다른 언어·실제 IME·물리 HID·광학 표시는 이 모집단에서 검증하지 않았다. CGEventPostToPid 게시부터 성공한 Metal 프레임 presentedTime까지를 측정한다. LSP·복원·자동 줄바꿈은 끈 상태다.

## 측정 신뢰성과 수정

- 워밍업 전후 계수를 분리해 입력 중 재사용이 실제 발생했는지 검사한다. 초기 계수만 있는 자료·경로 혼합·역행·잘못된 숫자·누락된 구문 프레임·뷰 재수집을 거절한다.
- 앱의 상대 경로 출력은 실행별 외부 디렉터리에 격리했다. 생산자와 입력 소스 복원 도구에는 앱의 가상 프로필 환경을 넘기지 않는다. 합성 비밀 환경과 복원 경로를 독립 테스트했다.
- 포커스 손실 시 앱 활성·key window·responder·전면 PID/bundle·입력 소스를 기록한다. 입력 내용·창 제목·환경 변수는 기록하지 않는다. 포커스 판정과 20ms 생산자 허용 한도는 완화하지 않았다.
- Python 계약 검사 87개가 통과했다. 별도 실패 가설 21개를 포함하며 정상 재사용·전체 준비 대조도 통과했다.
