# 첫 표시 상위 지연과 관측기 CPU 귀속

상태: 기존 360키의 첫 표시를 원시 frame/drawable/예산 기록에 다시 연결했고, 새 앱의
12프로세스·360키로 재현 및 관측기 CPU 분리 수집을 완료했다. 제품 소스는 변경하지 않는다.

## 기존 자료의 첫 표시

공식 지표는 첫 키를 포함한 조건별 90키다. 상위 표본은 조건별 가장 느린 5키이며 순서를
구분한 표는 원인 조사를 위한 보조 지표다. 첫 두 키를 제외한 값으로 공식 p95를 대체하지 않는다.

| 조건 | 전체 90키 p95(ms) | 첫 두 키 6개의 중앙값(ms) | 이후 84키 p95(ms) |
| --- | --- | --- | --- |
| 기존 예약·단일 | 46.76 | 45.06 | 43.68 |
| 대상 후보·단일 | 49.68 | 52.29 | 43.47 |
| 기존 예약·공유 | 45.38 | 42.57 | 42.02 |
| 대상 후보·공유 | 47.77 | 50.10 | 42.29 |

후보의 상위 10키 중 9키는 첫 두 입력이었고, 8키에는 앱 도착부터 첫 프레임 준비까지 투영
거절이 없었다. 공유 key 8과 단일 key 2의 느린 표본에는 거절이 있었다. 거절 유무는 그 구간에
사건이 있었다는 증거이며 거절만의 추가 비용이나 전체 원인을 분리한 실험은 아니다.

각 키의 게시→앱 keyDown→producing tick→허용 투영→준비→Swift/C renderer→commit 직전→
실제 표시 구간을 연결하고 합계가 전체 지연과 같아야 한다. 같은 generation의 다른 drawable이나
다른 thread/본문 prefix를 허용하지 않는다. 모든 12개 실행에서 입력 준비 이후 첫 native 도착
이전의 새 설치 사건은 0건이었다. 그 첫 키 도착 지연을 완료 후 추가 tick의 결과로 귀속할 수는
없지만, 후보의 예산은 시작 전부터 켜져 있으므로 후보 전체와 무관하다고 확정하지도 않는다.

## 유휴 CPU에서 아직 모르는 것

기존 유휴 구간의 추가 요청·추가 세션 tick은 0건이었다. user/system CPU 차이는 남아 있지만
드라이버가 posts JSON과 상태를 반복 확인하는 비용을 포함한다. 해당 자료만으로 제품 CPU의
회귀나 원인을 확정하지 않는다.

새 `--observer-cpu` 사본은 `CLOCK_THREAD_CPUTIME_ID`로 `maybeRunInputStream` 구간의
main-thread CPU를 기록한다. handler 내부 snapshot은 현재 호출의 진행 중인 구간도 포함해
경계에 걸친 호출을 두 번 더하거나 누락하지 않는다. process user/system CPU와 관측기 CPU를
구분하며 차이는 '나머지 process CPU'다. 여기에도 다른 계측 비용과 worker가 있으므로 순수한
제품 CPU나 전력으로 이름을 바꾸지 않는다. 두 snapshot 호출의 경계가 완전히 동시에 발생하는
것은 아니며, driver CPU가 process CPU를 넘으면 자료를 거절한다.

새 앱은 같은 예약/대상 후보의 12프로세스를 다시 수집한다. 이전 앱과 별도 모집단이며 첫 표시
재현과 CPU 구성 확인에 사용하고 이전 값과 한 분포로 합치지 않는다.

## 새 앱의 재현 결과

각 조건은 3프로세스·90키다. 첫 표시의 중앙값/p95는 첫 키 포함 pooled 값이며 이후 키 표는
보조 진단이다. 마지막 구문 표시는 프로세스별 마지막 입력 3개의 중앙값으로 구간 중앙값을 더하지 않는다.

| 지표(ms, 기존 예약 → 후보) | 단일 뷰 | 공유 2뷰 |
| --- | --- | --- |
| 첫 표시 중앙값 | 29.23 → 34.96 | 36.75 → 33.77 |
| 첫 표시 p95 | 38.86 → 45.16 | 44.85 → 45.10 |
| 첫 두 입력 이후 84키의 p95(보조) | 38.70 → 45.16 | 44.14 → 42.82 |
| 마지막 입력 → 구문 표시 중앙값 | 62.93 → 56.41 | 69.87 → 65.23 |

단일 뷰 p95 차이는 초기 입력 이후에도 남았다. 새 후보의 상위 10키 중 첫 두 키는 1개,
투영 거절이 있는 키는 7개였다. 이전 모집단의 초기 입력 집중 패턴이 새 모집단 전체를
설명하지 못한다. 두 모집단과 최초 입력을 그대로 보존하며 원인에 맞게 지표를 잘라 바꾸지 않는다.

### 거절 이후 재예약이 없는 경로

새 후보의 상위 7키에서는 직전 허용 프레임이 바로 이전 키의 prefix였다. 현재 키 도착 후
투영이 거절됐고, `이전 허용 시각 + ceil(1e9/60)`의 기한이 지난 뒤 다음 허용 투영까지
12.12~17.87ms가 더 걸렸다. 그 다음 허용은 해당 키의 첫 producing frame이었고, 그 키의
구문 설치 완료는 모두 그 이후였다. 원시 기록의 거절·기한·다음 허용·이전 prefix·설치 시각을
각 키의 `denial_context`로 보존한다.

현재 진단 구현의 요청은 실제 구문 설치에만 연결돼 있다. 직전 요청이 프레임 생성으로 소비된
뒤 일반 입력이 투영 예산에 막히면 dirty는 유지하지만, 거절 자체가 기한 재예약을 만들지는
않는다. 따라서 다음 정기 tick이나 나중 구문 설치를 기다릴 수 있다. 이 누락 경로와 실제
기한 후 지연을 확인했지만, 기한 재예약으로 p95가 얼마나 줄지는 수정 대조 전에는 확정하지 않는다.

### 관측기 CPU 분리

2초 유휴의 CPU 중앙값이며 단위 ms다. 행마다 프로세스별 중앙값을 구했으므로 서로 더하지 않는다.

| 구간 | 단일 예약 | 단일 후보 | 공유 예약 | 공유 후보 |
| --- | --- | --- | --- | --- |
| 전체 process CPU | 94.23 | 93.95 | 88.56 | 92.02 |
| 관측 드라이버 handler CPU | 51.09 | 50.98 | 48.13 | 50.68 |
| 나머지 process CPU | 43.14 | 43.57 | 40.43 | 41.34 |

각 실행의 관측기 비중은 약 52~55%였다. 입력 구간 비중은 약 3~4%였다. 유휴 추가 요청/추가
세션 tick은 모두 0건이다. 이전 공유 유휴 CPU의 큰 차이는 새 모집단에서는 재현되지 않았다.
이것은 이전 수치의 소급 보정이나 회귀 부재 증명이 아니다. 관측기 비용을 분리해 볼 필요가
있음을 확인했으며, 나머지 process CPU에도 다른 계측·main/worker 작업이 남아 있다.

## 판정과 다음 대조

제품 전환은 계속 보류한다. 다음 후보 수정은 **예산 때문에 투영을 보류한 경우에도 대상 창의
단일 pending 요청을 기한에 예약**하는 것이다. 기존 렌더가 새 세대를 만들면 소비하고
구문 완료 요청과도 합쳐야 한다. busy retry·숨긴/닫힌 대상·예산 준수·유휴 종료와 첫 표시 p95를
별도 대조로 검사해야 한다. 이 PR은 원인 조사이며 해당 수정이나 제품 정책은 구현하지 않는다.

복원 판정은 유지한다. 물리 HID·IME·광학 표시·에너지 검증은 포함하지 않는다.

- Python 계약 106개와 실제 native thread CPU clock 조회가 통과했다.
