# 구문 완료 후 프레임 요청 대조

상태: 같은 앱의 예약/완료 후 요청 대조를 수집·독립 재계산·손상 검증했다. 제품 소스는 변경하지 않았다.

## 결과와 판정

각 조건·경로는 3프로세스·90키다. 첫 표시 통계는 첫 키를 포함한 90키의 pooled median/
nearest-rank p95다. 나머지 표는 프로세스별 값 3개의 중앙값이며 서로 더하지 않는다.
표는 기존 예약 → 완료 후 요청 순서다.

| 입력/표시 지표 | 단일 뷰 | 공유 2뷰 |
| --- | --- | --- |
| 첫 글자 표시 중앙값(ms) | 29.96 → 34.47 | 33.56 → 36.37 |
| 첫 글자 표시 p95(ms) | 45.60 → 43.80 | 47.36 → 46.70 |
| 마지막 입력 → 구문 표시 중앙값(ms) | 80.72 → 62.79 | 80.30 → 82.58 |
| 설치 → tick 진입 대기 중앙값(ms) | 8.94 → 0.11 | 14.86 → 0.10 |
| 설치 → 구문 표시 중앙값(ms) | 35.55 → 23.16 | 37.77 → 30.41 |
| 다음 키 전 구문 표시(각 87구간) | 0/87 → 1/87 | 0/87 → 0/87 |

| 입력 구간 비용(프로세스별 중앙값) | 단일 뷰 | 공유 2뷰 |
| --- | --- | --- |
| process user+system CPU(ms) | 1719.02 → 1681.31 | 1794.32 → 1862.56 |
| CPU 비율(1코어=100%, %) | 82.54 → 81.04 | 86.12 → 88.75 |
| host tick 호출 | 126 → 148 | 125 → 138 |
| draw 호출 | 39 → 57 | 39 → 44 |
| 실제 관측 drawable 표시 | 37 → 55 | 37 → 42 |

CPU 입력 구간은 stream 준비 직후부터 최종 표시 관측까지다. 첫 게시 전 producer 대기도
포함하며 양쪽 벽시계 구간은 약 2.05~2.11초다. 표시 진단의 드라이버·카운터 비용도 포함한다.
CPU 비율은 프로세스별 CPU/벽시계로 계산한 값의 중앙값이고, 서로 다른 중앙값을 나눠 만들지 않는다.

2초 유휴 구간의 CPU 중앙값은 단일 100.11→106.40ms, 공유 103.48→103.58ms였다.
두 경로 모두 유휴 통지/요청/실행/합침 0건이며 약 60Hz의 기존 tick은 계속됐다.
유휴 draw 중앙값은 단일 5→6회, 공유 5→5회였다. 진단 드라이버의 반복 확인도 포함하므로
제품의 일반적인 idle CPU나 전력으로 해석하지 않는다. 모든 구간의 같은 generation 반복 draw는
0회였지만, 완료 후 요청에서는 더 많은 서로 다른 프레임을 그렸다. 실제 합침 분기는 이번
표본에서 발생하지 않았고 합침 계수의 의미/정산은 합성 대조로만 확인했다.

**현재 전체 tick 추가 호출 방식은 제품 반영을 보류한다.** 설치 후 대기는 줄었지만 첫 글자
표시 중앙값은 양쪽 모두 늘었고 공유 뷰의 최종 구문 표시·CPU도 나빠진 표본이다. 한 호스트의
작은 표본으로 통계적 회귀나 원인을 확정하지는 않는다. 공유 뷰의 워커 실행 중앙값도
37.16→45.73ms로 늘었으나 이를 렌더링과의 CPU 경쟁 때문이라고 단정하지 않는다.

다음 설계 후보는 전체 앱 tick을 추가하는 대신 대상 프레임 요청을 기존 예약과 합치는 것이다.
실제 요청 경로·cadence 예산·중복 준비를 먼저 검토하고 별도 대조로 확인해야 하며, 이 PR에서는
그 구조나 제품 프레임율/전력 정책을 구현하지 않는다.

## 대조 계약

같은 ReleaseFast 앱에서 기존 타이머 예약(`scheduled`)과 새 구문 결과 설치 후 메인 큐에
한 번 프레임을 요청하는 경로(`immediate`)를 교대로 실행한다. 기존 타이머는 양쪽 모두 유지한다.
대기는 새 결과가 실제 뷰에 설치된 완료 콜백에서만 요청한다. 이미 큐에 자기 요청이 있으면
합치며, 콜백을 처리하는 도중 동기적으로 tick을 재진입하지 않는다. 실제 앱은 weak controller로
등록한 콜백을 사용하고, 콜백을 등록하지 않은 helper는 요청을 무시한다.

5만 개 여러 줄 Zig 함수·50ms·30키·단일/공유 뷰·경로별 각 3프로세스로 구성한다.
총 12프로세스·360키의 문서/입력/표시를 검증하고 각 프로세스 마지막 입력 12개만 단계별
시각을 귀속한다. 반복 순서를 교대하고 두 경로의 소스·앱·생산자·행렬·실제 분기를 대조한다.

입력 시작·마지막 색 표시 이후·그 뒤 2초 유휴 구간의 process user/system CPU 누적값과
설치 통지·예약·실행·합침·host tick·draw 호출 수를 기록한다. CPU는 `getrusage(RUSAGE_SELF)`
기반이며 자식 프로세스는 제외한다. 입력 구간 길이가 경로별로 달라질 수 있으므로 CPU 경과와
벽시계 구간을 함께 보존한다. 유휴 상태에 추가 통지/요청이 생기거나 요청이 남으면 거절한다.

실제 표시 drawable 수와 같은 generation의 반복 draw 수도 시간 구간별로 보존한다. 반복 draw가
곧 불필요한 렌더링이라는 의미는 아니며 caret 등의 정당한 재표시가 포함될 수 있다. CPU나
tick/draw 수를 전력 측정으로 바꾸지 않는다. 계측 부하가 있는 진단 대조이며 제품 개선율이나
다른 문서/입력/환경의 일반 결론으로 확장하지 않는다.

## 재현

```sh
python3 tools/editor-input-latency/prepare.py --stream --fold-reuse-control --parse-stages --display-stages --frame-wake-control --output <새 외부 빌드 경로> --deps <실제 zig-pkg 경로> --cache <빌드 캐시>
python3 tools/editor-input-stream/frame_wake_study.py --build <고정 빌드 경로> --output <새 외부 수집 경로>
python3 tools/editor-input-stream/frame_wake_report.py <수집 경로> --output <새 외부 보고서 파일>
python3 tools/editor-input-stream/frame_wake_review.py <수집 경로> --output <새 외부 손상 대조 경로>
python3 -m unittest discover -s tools/editor-input-stream -p 'test_*.py'
```

실제 전면 입력 전에 Mac 조작 중단 시간을 조율한다. private profile·cwd·허용 목록 환경과
기존 입력/문서/Metal 세대·표시 시각·provider 설정·입력 소스 복원 검증은 유지한다. 실패한
모집단은 보존하고 전체 대조를 새 외부 경로에서 다시 수집한다.

## 한계

한 호스트의 ASCII PID 대상 입력이며 물리 HID·IME·광학 표시·에너지는 검증하지 않는다.
LSP·복원·자동 줄바꿈을 끄고 실제 접기를 실행하지 않는다. 각 구간의 중앙값은 더하지 않는다.
진단 앱에서 기존 cadence보다 추가 tick을 허용하는 실험이며 제품의 frame-rate·전력 정책을
변경하는 결정은 포함하지 않는다. 유휴 CPU는 표시 완료 뒤의 제한된 2초 관측이다.
