# 고정 주기 외부 입력 결과

2026-11-01의 단일 Mac에서 제품 HEAD `3556d940ffd6e81d597455a6259b8f56f5606d1a`를
외부 ReleaseFast 사본으로 측정했다. macOS 26.5.1·arm64·논리 CPU 16개이며 별도 조회에서
디스플레이 최대 주파수는 75Hz였다. CPU·광학 표시 실측은 아니다.
[기계 판독 결과](results.json)와 [도구 계약](README.md)을 함께 읽는다.

## 전체 입력의 첫 표시

모든 조건에서 독립 3프로세스 × 30입력이다. 총 48프로세스·1,440입력의 게시·native 도착·
정확한 문서 접두부·Metal 표시와 최종 본문을 검증했다. 이 묶음은 실패·재시도 없이 완료했다.
첫 입력을 포함한 조건별 90키의 pooled 중앙값 / nearest-rank p95(ms)이며,
키 90개를 독립 프로세스 반복 90개로 해석하지 않는다.

| 함수 수 | 게시 간격(ms) | 뷰 | 동기 중앙값 / p95(ms) | 비동기 중앙값 / p95(ms) |
|---:|---:|---|---:|---:|
| 3000 | 50 | 공유 2분할 | 30.6 / 43.7 | 55.9 / 63.4 |
| 3000 | 50 | 단일 | 33.2 / 45.4 | 45.6 / 53.9 |
| 3000 | 100 | 공유 2분할 | 33.3 / 41.5 | 51.7 / 60.8 |
| 3000 | 100 | 단일 | 37.0 / 46.4 | 43.6 / 52.8 |
| 50000 | 50 | 공유 2분할 | 234.4 / 414.0 | 105.0 / 329.0 |
| 50000 | 50 | 단일 | 91.0 / 177.1 | 71.8 / 181.6 |
| 50000 | 100 | 공유 2분할 | 70.0 / 83.2 | 176.8 / 336.8 |
| 50000 | 100 | 단일 | 66.5 / 76.1 | 92.4 / 181.3 |

비동기가 모든 조건에서 빨라지지 않았다. 큰 문서·공유 분할의 50ms 입력은 동기 234.4ms →
비동기 105.0ms였지만, 100ms 입력은 70.0ms → 176.8ms였다. 작은 문서는 비동기 첫 표시가
더 느렸다. 특정 조건의 개선만 골라 전체 전환의 이득으로 주장하지 않는다.

큰 문서·공유 분할·100ms에서 게시→native 도착의 프로세스별 중앙값은
동기 **0.63 / 0.62 / 1.67ms**, 비동기 **139.69 / 145.96 / 148.40ms**였다.
이 차이는 외부 게시를 고정해야 관측할 수 있는 입력 대기다. 시각만으로 메인의 CPU 비용이나
특정 함수의 원인을 확정할 수는 없다. 후속은 동일 입력 조건에서 메인의 실제 스택과 주소를
연결해 대기의 원인을 분리하는 것이다. 이 단계에서 제품 timer나 worker 구조는 바꾸지 않았다.

후속 [메인 실행 위치 조사](../editor-input-attribution/results.md)는 같은 불변 앱에 프로파일러를
붙인 별도 진단이며, 그 시각을 이 성능 모집단에 합치지 않는다.

생산자의 최대 마감 지각은 전체 묶음에서 약 7.2ms였고 20ms 수집 한도를 모두 지켰다.
큰 문서에서 마지막 게시 후 문법·괄호 색 준비 표시의 비동기 조건별 중앙값은 약 728–912ms였다.
세부 최댓값·native 대기·native 이후 표시·프레임 병합 개수·프로세스별 RSS는 JSON에 있다.
RSS peak는 앱 시작부터의 최대값이고 입력 순간 추가 할당량이 아니다.

## 독립성과 실패 경계

- 앱 메인만 500ms 멈춘 별도 대조에서 그 사이 **5개**가 계속 게시됐다. 해당 키는 재개 후
  도착했으며, 12입력은 8개의 첫 표시 프레임에 연결됐다. 인위적 정지 수치는 위 표에 섞지 않았다.
- 표시 관측 등록을 끈 대조에서는 8개 native 입력·최종 본문을 유지하면서 실제 31개 프레임의
  관측을 억제했다. 표시 완료를 위조하지 않고 `stream_timeout`으로 거절했다.
- 세 번째 ID를 보내지 않은 대조는 `[1,2,4]` 게시와 native ID 누락·접두부 불일치를 검출했다.
- 최종 정상 기록의 입력·문서·프레임·일정·포커스·설정 손상 24개는 거절했고 정상 전후 대조는
  유지했다. [거절 이유와 원본 해시](validation.json)를 남겼다. 이는 제품 변이를 실행한 횟수가 아니다.
- 최종 정상 묶음과 세 가지 대조에서 입력 소스 복원과 실제 provider 설정 세 파일의 해시 보존을 확인했다.
  Python 계약 57개, 기존 닫힌 루프 계약 41개와 native 잘못된 count 인자 4종도 별도로 검사했다.

## 준비 중 발견한 문제

첫 사전 실행은 baseline 검사 실패로 **키 게시 전** 중단했다. 두 번째 실행의 추가 진단에서
창이 전면이어도 입력 대상이 `notice`인 것을 확인했다.
준비 단계는 알림 내용을 기록하고 제품 Esc 처리·작업 영역 포커스 API를 거친다. 그 과정에서
측정 앱이 실제 Claude·Codex 훅 경로와 Codex 승인을 갱신한 것도 확인했다. 현재 `--stream`
사본은 해당 provider 설치·정리의 다섯 진입점을 막고 실제 설정 해시를 대조한다.
초기 변경 전 앱 경로는 기록하지 못해 사용자에게 확인 중이며, 현재 훅이 가리키는 실행 파일은 보존한다.

세 번째 사전 실행은 첫 마감 뒤 약 65ms에 게시 준비가 끝나 **게시 0개**로 거절됐다.
현재 생산자는 최초 Workspace·TIS·이벤트 객체 준비를 일정 시작 전에 수행하며 wake/post-ready
시각도 보관한다. 최초 지연의 세부 원인을 이 기록만으로 확정했다고 주장하지 않는다.
겹쳐 시작한 초기 빌드 사본은 수집에 쓰지 않고 보존했다. 준비 도구에 프로세스 잠금을 추가해
동일 사본의 동시 덮어쓰기를 거절한다.

## 증거와 한계

외부 보관 위치는 `~/.cache/maru-agent-artifacts/` 아래다.
정상 묶음 `input-stream-matrix-1`, 불변 앱 `input-stream-final-build-4`,
독립성 대조 `input-stream-main-pause-1`, 실패 대조 `input-stream-drop-present-1`·`input-stream-skip-1`,
원시 손상 검사 `input-stream-raw-review-2`를 보존한다. 준비 실패는 `input-stream-pilot-1/2/3`,
성공 사전 실행은 `input-stream-pilot-4`·`input-stream-shared-pilot-1`·`input-stream-large-pilot-1`이다.
사전 실행은 경계 검사와 겹친 진단이므로 위 성능 모집단에 합치지 않았다.

정상 묶음 동안 직접 실행한 경계 검사 프로세스 그룹만 잠시 멈췄고 수집 뒤 재개했다.
`input-stream-matrix-1-host-receipt.json`이 실행 명령·종료·재개를 기록한다.
실행별 호스트 load average는 raw record에 있으며 조용한 환경의 보편적 성능으로 확대하지 않는다.

전송은 **CGEventPostToPid**이며 과거 전역 HID 게시 수치와 직접 합치지 않는다. ASCII 1키=1편집만
검사했고 IME·물리 키보드·매 프레임 PNG/OCR·광자 지연·CPU 귀속·전력은 별도 범위다.
