## 왜 4ms만 적용하지 않는가

첫 호출이 짧아져도 재개 호출은 4ms를 넘었다. 별도 콜백 진단의 가장 긴 검사 간격은
벽시계 18.110ms·같은 구간 스레드 CPU 15.339ms였다. 해당 C 호출은 20.909ms 뒤
다음 콜백에서 만료를 확인해 pending으로 반환했다. 단순 실행 대기만으로 설명되지 않는 계산 구간이 있다.
이 진단은 특정 내부 C 함수의 귀속 증거는 아니다. 추가 계측 시간은 성능 모집단에 섞지 않았고,
두 시계의 읽기 시점 차이가 있어 ns 단위 동일성을 요구하지 않는다.

재개 API는 이전 트리·변경 범위를 버리고 `changed_all`로 남긴다. 50,000 선언의 분할 60입력은
모두 전체 변경으로 끝났다. 호출 합이 작아진 숫자를 같은 작업의 개선율로 읽을 수 없다.
생략된 변경 범위 계산 대신 후속 캐시가 전체를 다시 볼 수 있기 때문이다.
후보를 적용한 실제 뷰·캐시 비용은 별도 통합 비교가 필요하다.

제품 syntax State의 재개는 기존 입력 판을 지우며 완료 후 자동으로 새 판을 발급하지 않는다.
정상 `updateForInput` 재발급 뒤에는 공유 결과 복사와 접힘·괄호 대조가 통과했다.
기존 API의 계약 확인이며 후보를 실제 공유 편집·Undo·IME·렌더 경로에 적용한 성공은 아니다.

## 정확성과 검증 보강

매 정확성 입력의 모든 C 노드 종류·자식/필드·상태·byte·행·열과 색 질의 결과가 새 파싱과 일치했다.
pending 뒤 다른 최신 원문, cold pending, byte 역편집과 한글·이모지 전체 치환을 대조했다.
byte 역편집은 실제 Undo 스택이나 물리 IME 실행이 아니다.

기존 공백 역편집 대조만으로는 reset 제거 결함을 놓쳤다. 처음 pending 원문으로 돌아가기 전에
다른 최신 원문을 비교하도록 고쳐 실제 `PendingLatestMismatch`를 검출했다.
전체 노드의 좌표를 판정에서 빼는 C 사본도 잘못 이동시킨 트리 대조에서 실패했다.

기록 검증기에서는 상태 실행 파일을 측정 파일과 같은 것으로 바꾸고 해시도 고치면 통과하던 결함을
수정 전 허용·수정 후 거절로 재현하고 두 실행 파일의 충돌을 금지했다. 제품 파서의 결함은 아니다.
`src` 밖의 실제 test runner 소스와 mise 설정도 핀한 Git에 대조한다. runner 사본을 바꾸어도
받아들이던 누락을 수정 전후 재현으로 확인해 막았다.

다섯 실제 C/구문 상태 결함 사본은 의도한 검사에서 실패했고 정상 전후 대조는 통과했다.
별도 원시 기록 손상 검사도 정상 자료와 손상 자료를 구분한다. 컴파일·선택 개수·판정 도구 개발 오류를
의미 결함 검출로 세지 않는다. 프로젝트 reader를 import하지 않는 별도 token/order-statistics reader가
40로그·800입력의 모든 집계·첫 입력 지표를 대조했다.
