# worker 접힘 후보 증분 준비

같은 ReleaseFast 실행 파일에서 접힘 후보 재사용만 끄고 켰다. 양쪽 모두 증분 파싱·심볼
준비·괄호 재사용을 유지했다. 제품 후속 후보의 실제 소스는 `source.json`의 파일별 해시로
고정했다. 실행 파일 SHA-256:
`fd7453d53847b295883981b35900d8c5e7fe0cc76b5d8e04da4b7d2ea2f06cdc`.

[집계](fold-results.json), [재현 명령](README.md), [구현 계약](../../docs/plans/editor-async-fold-preparation.md)을
함께 본다. 원시 소스·실행 파일·32개 로그·`source.json`·`runs.json`·`result.json`은
`~/.cache/maru-agent-artifacts/worker-fold-reuse-measure-2/`에 있다. 독립 원시 토큰 대조와
결함 주입은 `worker-fold-reuse-validation-1/`·`worker-fold-reuse-mutations-1/`에 보존한다.

## 시간과 작업량

각 행/경로는 3프로세스의 60편집을 합친 중앙/최대 ms다. 문서 중간 줄 앞에 공백을
한 글자씩 삽입하고 완료를 기다린다. 서비스 제출 시작부터 완료를 가져오기까지의 경과이며
파싱·다른 준비·대기를 포함한다. 초기 파일 열기는 이 표의 편집 시간에 포함하지 않는다.

| 입력 | 접힘 전체 준비 중앙/최대 | 접힘 증분 준비 중앙/최대 |
|---|---:|---:|
| 한 줄 함수 3,000개 | 5.77 / 6.09 | 1.09 / 1.37 |
| 한 줄 함수 50,000개 | 116.01 / 130.56 | 38.77 / 56.51 |
| 여러 줄 함수 3,000개 | 5.85 / 6.27 | 1.14 / 1.60 |
| 여러 줄 함수 50,000개 | 121.04 / 133.62 | 40.11 / 55.66 |

성능 24프로세스/480편집과 정확성 8프로세스/160편집이 전부 성공했다. 정확성에서는 매
편집마다 독립 전체 트리·괄호 잎·접힘 byte 후보를 대조했다. 실제 입력 위치는 각 프로세스의
문서 중간 줄이며 초기 기준 준비 뒤 후속 편집이다. fixture와 정확성 구간을 한 분포로 합치지 않는다.

방문 수는 `Cache.nodes` 계수이며 native API 내부 작업량을 전부 세는 값은 아니다.
50,000함수의 접힘 방문 노드 중앙값은 전체 1,250,002개에서 증분 3개(한 줄)/5개(여러 줄)였다.
3,000함수는 전체 75,002개에서 증분 3개였다. 후보는 한 줄 0개, 여러 줄 6,000/100,000개로
각 짝지은 경로에서 같았다. 후보 수는 뷰에 표시되는 접힘 행 수와 다르다. 기존 행 투영이
같은 시작 줄을 합치며 별도 제품/worker 검사에서 전체 행 범위와 대조했다.
모든 결과에서 괄호는 rebuilds=0/partials=1이었다. 접힘 변경 범위 재사용은 전체 0/증분 1로
실제 실행 분기를 확인했다. 독립 reader가 raw/JSON·로그/소스/fixture/실행 파일 해시와
32프로세스 행렬, 시간 통계를 다시 계산했다.

## 실패와 수명 검증

- 원본 접힘 캐시의 트리 핸들에 native 호출을 하지 않는 검사와 독립 배열/트리 소유를 확인했다.
- 이름/줄 추가·삭제·중첩·손상 괄호·주석/문자열 전환·NFD/이모지/CRLF와 JS/Python/CSS/HTML/JSON을
  전체 후보·현재 줄 투영과 대조했다. 같은 본문은 방문 0으로 재사용하고 원본은 바꾸지 않았다.
- 잘못된 parser/세대, dirty 원본, 없는 대상 트리를 거절했다. Zig 복사/부분 갱신 실패는 자원을 회수한다.
- 실제 준비 장벽 취소와 선택적 캐시 부재 뒤 전체 복구, 대기 교체·종료·연속 편집의 기준 퇴역을 확인했다.
- 편집 통지를 뺀 격리 결함은 재사용 회귀가 실패했다. 독립 기준 대신 원본 핸들을 쓰는 결함은
  원본 핸들 비접근 검사에서 실행 실패했다. 컴파일 오류를 결함 검출로 세지 않았다.

## 해석 범위

계측 시각을 worker에 추가한 앞선 단계 진단과 다른 실행 파일·모집단이다. 이번 비교는
native 서비스 경과이며 GUI의 입력/Metal 표시·물리 HID·IME·CPU 시간·RSS 개선이 아니다.
서로 다른 부하의 과거 결과와 합치지 않는다. 배열 복사/위치 보정·뷰 투영은 선형 비용이
남고 초기 전체 수집도 유지한다. C allocator 실패의 전수 주입이나 모든 언어·큰 구조
변경의 개선을 증명하지 않는다. 이번 workload에서도 서비스 완료는 큰 문서에서 수십 ms다.

최종 채택 묶음은 #4682 머지와 최신 main 리베이스 뒤의 새 전체 대조다. 앞선
`worker-fold-reuse-measure-1/`도 보존하지만 이 표와 한 분포로 합치지 않는다.
측정 뒤 변경은 결과 문서뿐이며 제품 소스 동등성은 검증 영수증으로 확인한다.
