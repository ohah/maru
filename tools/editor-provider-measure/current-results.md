기준은 실제 main `4ac6691a2a32f2ba4d7e0948ed37691fb2c815b1`이다. 제품 src·빌드·ABI는
바꾸지 않고 별도 ReleaseFast 사본에서 경과시간을 관측했다. 이전 측정과의 개선량 비교가 아니다.

## 호출 수와 판단

모든 입력에서 일반은 native 파싱 한 번이고, 공유는 native 파싱 한 번과 완료 트리 인계 한 번이었다.
새 `FRAME_CALLS`는 Provider·괄호 갱신을 일반 1뷰/공유 2뷰 모두 관측했는지 확인한다.
이 하네스의 공유 실행은 각 프로세스 첫 입력에서 범위 재사용 0, 이후 19입력은 1이었다.
각 공유 행 60입력 중 3개/57개를 그대로 보존했다. 처음부터 모든 범위를 재사용한다고 가정하거나
초기 비용을 분포에서 빼지 않았다. 이 초기화 관측을 실제 GUI의 모든 첫 입력에 일반화하지 않는다.

큰 합성 Zig 공유 입력은 전체 p50 36.713ms 중 Provider 포함 구간이 24.258ms였고 C 파싱은
17.525ms, C 범위 계산은 7.571ms였다. 전체 p95 54.292ms·최대 87.610ms도 남겼다.
반면 실제 build.zig 공유 입력은 전체 8.260ms·구문 색 2.823ms, Swift 공유 입력은
전체 10.245ms·구문 색 3.308ms였다. 따라서 파일 규모/구성별 병목을 구분해야 한다.

다음 판단은 실제 파일의 본문 구문 색 작업을 더 분리해 중복 질의·span 조립·변환 중
무엇이 반복되는지 확인하는 것이다. 이 수치만으로 worker 이동·저장소 교체·새 UX를 승인하거나
특정 최적화의 효과를 확정하지 않는다. 과거 수치를 빼서 누적 개선량을 만들지 않는다.

## 고친 계측 결함과 검증

기존 도구는 직접 괄호 refresh 호출만 알았고 새 복사/복귀 블록을 찾지 못해 준비를 거절했다.
또 Provider 상위 타이머가 공통 `editProvider` 호출 대신 내부 native fallback만 감싸,
공유 복사 시간을 빠뜨렸다. 실제 기록의 하위 시간이 상위 시간을 넘는 검사로 이를 잡았다.
첫 사본은 준비 실패, 두 번째 사본의 800입력은 포함 시간 불일치로 거절해 결과로 쓰지 않았다.
해당 로그/부분 사본은 보존했고 메타데이터를 사후 고쳐 채택하지 않았다.

프레임 schema 1은 옛 `bracketRefresh`, schema 2는 복사/재수집을 포함한 `bracketUpdate`다.
버전·필드·동작·호출 계측 대상을 함께 확인하고 혼합·불명 버전·누락 호출·시간 포함 위반을 거절한다.
현재 유효한 Provider schema 3을 불명 버전으로 주입하던 검증 도구도 고쳐, 실제 불명 값 999와
schema 3의 복사/범위 계수 손상을 검사한다. 프레임 13개·저장소 10개 단위 검사가 통과했다.

다섯 독립 가설은 모집단, 시간/호출 수, 제품/전수 대조, 근거 파일/형식, CLI를 손상했다.
49개 손상 사례를 거절하고 각 묶음 전후 정상 대조와 원본 자료 대조를 통과했다.
최종 reader에서도 다시 확인했으며, 전체/구간 통계와 첫 입력은 별도 원시 기록 계산과 일치했다.
옛 schema 1 입력/원시 기록 800개도 읽기 대조했다. 옛 실행 파일이 없어 옛 전체 provenance는
거절됐으므로 그 검사를 성공으로 세지 않는다. 이번 자료는 원본/계측 소스·실행 파일을 모두 보존했다.
pane reader의 옛 pane schema 2/프레임 schema 1 원시 기록 800개도 별도로 읽기 대조했다.
그 결과도 옛 실행 파일의 전체 provenance를 대신하지 않는다.

측정 뒤 추가한 `--frame-details`는 같은 유효 자료의 프레임/저장소 표를 내보낸다.
계측 생산자와 실행 파일은 그대로이며, 최종 분석 도구 사본과 다섯 가설 결과를 별도로 보존했다.
