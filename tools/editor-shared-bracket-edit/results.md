# 공유 편집 후 괄호 목록 재사용 실측

일반 입력·괄호 증가·같은 증가 바이너리의 추가 반복을 대조했다. 성능 104개 실행/2080편집과
별도 정확성 12개 실행/240편집의 원시 자료를 보존한다. 작은 차이를 보편적 개선으로 확정하지 않는다.

## 입력과 결과

ReleaseFast의 동일한 계측 문맥에서 기존 경로와 후보의 세 제품 블록만 다르게 구성했다.
각 파일·조건의 성능 프로세스는 세 번이며 순서를 번갈았다. 성능 24개 실행/480편집과
별도 정확성 8개 실행/160편집을 완료했다. 첫 입력은 실행별 첫 표본의 중앙값이고,
입력 p50/p95는 조건별 60개 표본의 중앙값/nearest-rank 값이다. 괄호 구간은 두 뷰 합계다.
원시 32개 로그·집계 재계산·다섯 손상 로그와 정상 대조·입력/전체 소스/바이너리 해시를
확인했다. 모든 입력에서 부분 재수집 합계는 2회→1회이며 독립 배열을 유지했다.

단위는 ms이며 기존 → 후보 순서다.

| 파일 | 첫 입력 중앙값 | 입력 p50 | 입력 p95 | 괄호 갱신 p50 |
|---|---:|---:|---:|---:|
| flat-15000.zig | 13.987 → 13.716 | 13.149 → 12.720 | 14.047 → 13.438 | 0.968 → 0.542 |
| flat-3000.zig | 3.096 → 3.098 | 2.845 → 2.756 | 3.051 → 2.940 | 0.141 → 0.075 |
| flat-50000.zig | 56.150 → 50.576 | 47.382 → 45.600 | 56.545 → 53.319 | 4.278 → 2.223 |
| real-build.zig | 8.588 → 8.451 | 8.513 → 8.389 | 8.872 → 8.707 | 0.142 → 0.079 |

정확성 실행은 매 입력의 본문·줄·접힘·전체 괄호 잎·색 토큰·짝/단계 결과·탐색 인덱스를
측정 구간 밖에서 전체 파싱/판정과 비교했다. 기준과 후보 모두 일치했다. 별도 제품 검사는
Zig/Markdown의 모든 byte 탐색, 독립 풀·긴 줄·다른 언어/문서/판·할당 실패와 실제 분할
입력·Undo/Redo·원본 종료를 검사한다. 성능 입력은 이 표의 Zig 파일 네 개로 제한한다.

## 범위와 비용

보존한 계측 사본의 `BracketIndex`, `onEditSpanFromReady`, `updateForInputImpl`을
실제 기준 커밋 `f1fda982d`와 현재 후보 소스에 각각 대조했다. 세 제품 블록의 해시가
일치하며 나머지 제품 문맥은 같다. 이 사본은 이전 앱 런타임 문맥을 유지하므로 최신 앱의
절대 지연이나 실제 GUI/HID·GPU present 지연으로 표현하지 않는다. 입력의 전체 시간은
native 파싱 등 다른 구간도 포함한다. 서로 다른 중앙값을 더해 전체를 재구성하지 않는다.

두 조건의 타입 필드와 초기 잎 배열 용량은 같다. 후보는 기존 용량 안에서 배열 값을
덮으며 단위 검사에서 할당 실패 allocator로도 추가 할당 없이 성공한다. 일반 공백 입력 외에 괄호 증가에 따른 확장 비용도 아래 별도 대조에서 확인했다.
allocator 관리 비용·C 할당·RSS·GPU 메모리의 개선을 주장하지 않는다. 외부 컴파일/테스트
동시 실행을 프로세스별 `*-load.json`에 기록했으며 작은 차이를 보편적 개선으로 확정하지 않는다.

## 재현 자료

기본 위치는 `$HOME/.cache/maru-agent-artifacts`다. `shared-bracket-edit-measure-1`의
`prebuild.json`, `binaries.json`, `inputs.json`, `order.json`, `summary.json`,
`readback-adversarial.json`과 `shared-bracket-edit-canonical-block-proof.json`에 보존했다.
실행 파일은 cache 밖에 보관한다. 준비/실행/자료 재검증 스크립트는 같은 루트의
`prepare-shared-bracket-edit-measure.py`, `run-shared-bracket-edit-measure.py`,
`readback-shared-bracket-edit-measure.py`다. 준비는 새 출력 경로를 요구한다.
제품의 다섯 결함 주입은 이 디렉터리의 `review.py`이며 성능 자료 검증과 구분한다.

## 괄호 증가와 추가 반복

첫 입력으로 `fn bracket_growth() void {}\n`을 넣고 이어 공백 19개를 입력했다.
성능 40개 실행/800편집과 별도 정확성 4개 실행/80편집의 전체 결과가 일치했다.
모든 입력에서 잎 수는 초기보다 정확히 네 개 늘고 부분 재수집 합계는 2회→1회였다.
그 후 같은 소스·입력·보존 바이너리로 성능 40개 실행/800편집을 추가 교차 실행했다.
각 조건의 표본 200개를 모두 보존한다. 후속 p95는 첫 입력을 별도로 설명하기 위한
추가 열이며 전체 p95에서 첫 입력을 제외하거나 실패 표본을 지우지 않는다.

| 자료 / 파일 | 첫 입력 중앙값 | 입력 p50 | 전체 입력 p95 | 후속 19개 입력 p95 |
|---|---:|---:|---:|---:|
| 증가 / flat-50000.zig | 66.116 → 64.313 | 47.463 → 46.580 | 56.526 → 62.688 | 54.699 → 53.073 |
| 증가 / real-build.zig | 14.693 → 14.633 | 8.443 → 8.374 | 8.971 → 9.674 | 8.758 → 8.934 |
| 추가 반복 / flat-50000.zig | 69.071 → 67.304 | 49.292 → 46.139 | 60.088 → 57.973 | 58.602 → 55.481 |
| 추가 반복 / real-build.zig | 14.773 → 14.798 | 8.524 → 8.463 | 13.669 → 9.170 | 8.881 → 8.768 |

첫 증가 자료에서 큰 파일의 후보 rep 9의 두 일반 입력은 native 파싱 38.638ms·32.433ms와
전체 84.433ms·75.190ms를 기록했다. 전체 p95 증가를 숨기지 않는다. 전체 p95는 첫 입력이
정확히 5% 섞인 분포의 경계에 있어 이 표본들과 첫 입력의 순위가 함께 영향을 준다.
외부 고부하 실행도 기록됐지만 이것이 원인이라고 확정하지 않는다. 같은 바이너리의
반복에서는 두 파일 모두 전체 p95가 감소했다. 실제 build.zig의 반복 첫 입력은
14.773→14.798ms로 약 0.025ms 늘었다. 모든 입력과 분포가 항상 개선된다고 주장하지 않는다.

확장 뒤 배열 용량은 두 조건 모두 같았다. 큰 파일의 원본/분할 뷰는 각각
252170/300016개, 실제 build.zig는 22118/25033개였다. 분할 뷰의 초기 용량
200000개·16678개가 처음 네 괄호 증가로 확장된다. 후보 때문에 추가로 커진 용량은 없다.
이는 논리적 배열 용량이며 allocator/C/RSS/GPU 메모리 측정은 아니다.

증가 자료는 `shared-bracket-edit-growth-1`, 추가 반복은
`shared-bracket-edit-growth-repeat-1`에 있다. 각 원시 로그·집계·독립 배열·단계별
정확성과 해시를 다시 읽었고 자료별 다섯 손상 로그와 정상 대조가 통과했다.
추가 반복은 기존 바이너리와 소스를 공유하며 정확성 실행을 새로 했다고 세지 않는다.
