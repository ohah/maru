# 공유 분할 괄호 목록 복사 실측

## 범위와 방법

보존한 계측 사본에서 `BracketIndex`와 `State.prepareSharedSnapshot` 두 제품 블록만
치환했다. 기준 블록은 선행 head `9f1eedf9e`와, 후보 블록은 실제 작업 소스와 동일하다.
선행 실제 main `6dee25c06`의 전체 트리도 이 기준 head와 같다. 나머지 계측 문맥은
양쪽이 동일하다. 이 문맥에는 이전 프레임/접힘 계측이 포함되어 있으므로 최신 앱 전체의
GUI/HID·Metal present 지연으로 표현하지 않는다. 제품 경로의 원본 종료·색·모든 byte의
탐색·편집·Undo/Redo·할당 실패 대조는 실제 작업 소스에서 별도로 수행했다.

원본은 입력과 Undo로 원문을 복원한 뒤 준비한다. 분할 자체·준비·첫 입력을 빠뜨리지 않는다.
기준과 후보의 실행 순서를 번갈아 바꾸며 첫 5개 파일은 성능 30개 실행·600편집,
매 입력 전체 접힘/표시 축 대조는 10개·200편집으로 분리했다. 뒤의 일반 입력 반복은
2개 파일의 추가 성능 40개 실행·800편집이다. 괄호가 늘어나는 입력은 별도 실행 파일로
40개·800편집과 정확성 4개·80편집을 대조했다. 실행별 중앙값과 입력 표본 집계를 구분한다.

준비는 세 프레임 이상을 연속 실행하고 남은 괄호 작업을 완료하는 측정 구간이다.
실제 화면의 프레임 간 대기나 GPU 제출 시간은 포함하지 않는다. 첫 준비 구간의 native
parse 시간 0을 C 파싱 호출 횟수의 직접 계측으로 표현하지 않는다. 모든 실행의 처음부터
20개 입력 기록·캐시 준비·불일치 0·지연 0·실행 파일/소스/입력 해시를 확인했다.

준비·첫 입력은 각각 실행별 중앙값이다. 준비+첫 입력은 같은 실행에서 합친 뒤 중앙값을
구한다. 입력 p50/p95는 파일·변형별 전체 입력을 합친 값이며 p95는 nearest-rank다.
첫 대조는 3쌍, 후속 일반/증가 입력은 10쌍이다. 이 작은 표본을 모든 환경의 성능 보장으로
해석하지 않는다. 증가한 입력 시간도 그대로 보존한다.

## 제품 타입 크기

| Type | Before | After | Delta |
|---|---:|---:|---:|
| index | 200 | 208 | 8 |
| state | 1600 | 1608 | 8 |
| runtime | 17792 | 17824 | 32 |

`index`는 native `BracketIndex`, `state`는 편집 구문 `State`, `runtime`은 공통
`TermRuntime`이다. 별도의 실제 제품 소스 사본을 ReleaseFast 테스트 진입점에서 타입
계산해 추출했다. 이 사본의 의도적인 compile-log 진단은 테스트 통과로 세지 않는다.
공통 런타임의 변화는 편집기뿐 아니라 해당 타입을 쓰는 Term에도 해당한다. allocator
관리 비용·외부 C 할당·프로세스 RSS·GPU 메모리는 포함하지 않는다. 이전 계측 문맥의
runtime 크기는 달랐으므로 위 별도 제품 타입 대조를 크기의 근거로 사용한다.

## 배열 여유 용량과 교환 관계

첫 괄호 증가 입력은 새 함수 선언을 넣어 양쪽 문서에 괄호 4개를 추가하고 나머지 입력은
공백을 넣는다. 모든 실행에서 실제 항목 수 증가를 확인했다. 대형 Zig는 첫 증가 입력이
67.660→68.932ms였고 준비+첫 입력은 138.796→83.512ms였다. 실파일은 첫 증가 입력
15.190→15.182ms였다. 일반 공백 반복에서도 대형 Zig의 첫 입력은 55.020→56.095ms로
증가했고 입력 p95는 58.274→58.508ms였다. 모든 입력의 속도 향상을 주장하지 않는다.

사본은 현재 항목만 소유하므로 원본의 여유 용량을 복제하지 않는다. 문서가 작아진 뒤에도
남아 있는 큰 여유 용량을 새 뷰에 옮기지 않는다는 이점이 있다. 실제 남은 용량이 있는
빈 목록을 실패 allocator로 복사하는 native 대조에서도 새 할당이 없음을 확인한다.
반면 첫 증가 입력에서 후보 배열은 확장돼 저장 위치가 바뀌었고 기준은 기존 여유를 썼다.
확장은 기존 `std.ArrayList` 정책을 따른다. 별도 용량 상한이나 새 성장 정책을 추가하지 않는다.

다음은 대형 Zig의 논리적 잎 저장소 용량이다. 잎 한 개는 12바이트이며 allocator/RSS와
구분한다. 복사 직후의 절약을 문서 수명 전체의 메모리 절약으로 일반화하지 않는다.

## 검증과 보존 자료

제품 독립 결함 5개는 parser·세대 검사, shift 중간 상태 바인딩, 배열 독립 소유,
선택적 할당 실패의 본체 보존을 각각 공격한다. 정상 대조와 원본 종료·취소·할당 실패 뒤
재수집, 독립 풀, Markdown의 색 비활성/탐색 활성, 실제 분할과 괄호 증가·Undo/Redo를
별도 제품 검사로 대조한다. C allocator의 모든 실패를 강제한 증거는 아니다.

기준 경로는 `/Users/yoonhb/.cache/maru-agent-artifacts`다. 첫 교차 대조는
`shared-bracket-snapshot-measure-1`, 일반 반복은 `shared-bracket-snapshot-input-repeat-1`,
증가 입력은 `shared-bracket-snapshot-growth-1`, 실제 타입 크기는
`shared-bracket-snapshot-layout-1`에 보존한다. 각각 원시 로그·소스·실행 파일·입력과
해시 관계를 보존하며 원본 실행 파일은 `.zig-cache` 밖에 따로 보관한다.

`run-shared-bracket-measure.py`, `run-shared-bracket-input-repeat.py`,
`run-shared-bracket-growth.py`가 실행 순서·환경·집계를 소유한다. 동일 이름의
`readback-` 스크립트는 원시 기록과 첫 입력·계수·독립 배열·레이아웃·집계를 다시 검사한다.
보존한 40개·40개·44개 로그를 다시 읽었고 각 검증기에 손상 로그 다섯 개와 정상 대조를
적용했다. 이 손상 로그 대조는 제품 소스 결함 검증과 구분한다. 이미 사용한 출력 경로의
원시 로그를 덮어쓰는 재실행은 허용하지 않는다.
